# 08 — E-06 裁定 / VERDICT

> 任务完成标准要求明确回答六个问题。本文逐条回答，并给出后续建议。

---

## Q1. `.tvm0` 的哪些结构已经证实？

**已证实（`VERIFIED`）：**

| 结构 | 值 |
|---|---|
| 容器类型 | **aPLib（AP32）压缩块**，非虚拟化容器 |
| 节内头部位置 | 节起始 **+0x04** 处的 `"AP32"`；前 4 字节为独立 u32 前缀 |
| 头部总长 | **0x18（24 字节）** |
| `S+0x08` | **压缩流长度** |
| `S+0x0C` | **压缩流 CRC32** |
| `S+0x10` | **原始（解包后）长度** |
| `S+0x14` | **原始数据 CRC32** |
| `S+0x18` | **压缩流起点** |
| 原尺寸 | **2,853,888 B**（与恢复镜像 `.tvm0` 相等） |
| 双 CRC | **均通过** |
| 同一格式的普遍性 | 全镜像 **10 处**，10/10 双 CRC 通过 |

**未证实：** 前 4 字节前缀的算法（`UNKNOWN`，不影响解包）。

---

## Q2. 是否得到可独立验证的解码结果？

**是（`VERIFIED`）。** 三重独立锚定：

1. **头部自校验**：`crc32(packed)==+0x0C` 且 `crc32(out)==+0x14`（10/10 通过）。
2. **与既有恢复镜像逐字节一致**：`.text` 8,047,104/8,047,104；`.tvm0` 2,853,888/2,853,888（均 100.0000%）。该镜像由**既有工作产出、非本轮生成**。
3. **不需解包的尺寸等式**：头部 `orig_len` 与恢复镜像同 VA 区段 RawSize **精确相等**。

> **纪律说明：** 因使用了外部参考实现（PyPI `aplib`），结论**未**依赖其可信度——(1)(3) 两项与任何实现无关，(2) 来自独立产物。

**此外**：末节 `.tp3` 内 **8 个 AP32 块**亦全部通过双 CRC，解出 **5,162,839 B**。

## Q3. 解码后内容是否改善了函数边界或交叉引用的可信度？

**是，且改善显著。**

| 项 | 改善前 | 改善后 |
|---|---|---|
| `.text` 可扫描性 | 单次 `disasm()` 遇坏字节即停（≈0.01%） | **带重同步扫描覆盖到节尾（2,892,767 条指令）** |
| `.text`→消息解析簇 `call` | 假 **0** | **685（224 个目标）** |
| `.text`→`.tvm0` | 字节扫描 3,871 / 单次 disasm 51 | **3,755（784 个目标）** |
| `.tvm0` 性质 | 不明（疑似 VM 容器） | **aPLib 压缩的原生混淆代码** |
| `.data` 缺口 | "99.86% 缺失" | **"208.1 MB BSS，非缺失"** |

**结论：** "客户端解析簇无调用者"这一**中间结论被推翻**；解析簇**确实可达**。

## Q4. 是否找到 `.data` 初始化来源的直接证据？

**部分：本轮的主要成果是**排除了**错误线索，并**修正了问题本身**。

| 结论 | 等级 |
|---|---|
| `.data` 的 208.1 MB 是**未初始化 BSS**（加载时清零），**并非丢失数据** | **VERIFIED** |
| 原版与恢复镜像的 `.data` **逐字节相同** → 不是恢复缺陷 | **VERIFIED** |
| 旧解释"候选 vtable 落在缺失 `.data` 中" | **REFUTED** |
| `.data` 初值来自某 AP32 压缩块 | **REFUTED** |
| `.data` 初值来自末节 `.tp3` | **无证据**（该节是 TenProtect 载荷） |
| 加载期存在对 `.data` 的指针修复（`.rimp` 420 项） | **VERIFIED（存在性）** / 语义 `PARTIAL` |

**净结论：** `.data` **不需要**"初始化来源"（BSS 居多数）；其**已初始化部分**（300,544 B，含 2,375 个 →`.text` 指针）**已在文件内**，可直接参与 xref。

## Q5. 是否新增通往客户端 opcode 分派或 Configstring body 的直接证据？

**都没有。**

| 目标 | 新增直接证据？ | 说明 |
|---|---|---|
| opcode 分派（`0x02`→`0xA2E50`） | **否** | 全节指令级扫描（含重同步）后仍为 **0**；同一簇其他函数有 131 个调用者 |
| Configstring body | **否** | 本轮焦点在客户端镜像；解包 `.text` 与恢复镜像完全相同，不产生新证据 |

**但有重要的**否定性**加强：**
- `0xA2E50` 在**高完备搜索面**（`.text` 全节指令级、`.rdata` 30,895 个指针、`.data` 已初始化区 2,375 个指针）**均不可达**。
- 这不是工具假象（该假象已由 F-06 定位并修正）。
- **仍不排除**运行时生成代码/回调/`.tvm0` 内间接分派。

## Q6. 下一步：E-07、E-08，还是 BLOCKED？

### 建议：**部分继续 E-07（可离线），部分记录为 BLOCKED（需授权）**

**应当继续（可离线、有明确收益）：**

| 优先级 | 行动 | 理由 |
|---|---|---|
| **A1** | **从 `.tvm0` 的 5 个已知入口点反向解码控制流**（而非从节首线性解码） | 入口已由 50 个 `.text` `call` 确定（最强 `0xD9AB8AC`，601 次）；这是唯一能触及 `.tvm0` 语义的静态路线 |
| **A2** | 对 `.text` 采用**递归下降 + 重同步**，重建完整调用图 | 本轮已知线性扫描会漏；递归下降可给出更可靠的"谁调用谁" |
| A3 | 复核 `.text` 内的**间接分派**（跳转表/函数指针）是否指向 `0xA2E50` | 直接 `call` 已排除，间接路径尚未系统枚举 |
| A4 | 将本轮修正回写 `14_SERVER_KNOWLEDGE_ATLAS_001`（`.data` BSS、`.tp3` 内容、扫描方法） | 避免旧错误结论继续传播 |

**应记录为 `BLOCKED`（需授权，超出只读静态范围）：**

| 项 | 为何 BLOCKED |
|---|---|
| 加载期观察 `.tvm0` 解压时机 | 需启动样本（任务约束禁止） |
| 运行时 dump / 断点确认 `0xA2E50` | 需注入/内存读取（禁止） |
| TenProtect 载荷的运行期行为 | 同上，且属反保护范畴 |

### 不建议

- **不建议**把 `.tvm0` 的原始字节扫描命中当调用者（已由 F-05/F-06 量化否决）。
- **不建议**继续扩大对 `.text` 的线性字节扫描 —— 已到节尾，收益饱和。

## 总裁定

**E-06 判定：`SUCCESS (格式层) + PARTIAL (语义层)`**

| 目标 | 结果 |
|---|---|
| 核对样本身份 | ✅ 完成（并查明 `C-2697-Rec` 与 `C-2697` 的真实关系） |
| 解析 `.tvm0` 容器结构 | ✅ **完成，格式已还原**（aPLib/AP32，24B 头，双 CRC） |
| 建立解码假设 | ✅ 完成（H1–H8，含 7 项排除） |
| 静态解码并独立验证 | ✅ **完成**（双 CRC + 既有镜像 + 尺寸等式） |
| 重估代码边界/xref 可信度 | ✅ 完成（**推翻**"解析簇无调用者"，修正 `.text` 扫描方法） |
| 解释 `.data` 初始化来源 | ✅ 部分（**修正问题本身**：BSS 非缺失；排除压缩块来源） |
| 找出 opcode 分派 / Configstring 新证据 | ❌ **未获得**（`0xA2E50` 仍 0 调用者） |

**最重要的一句话：**
> `.tvm0` 的**格式之谜已解**（它是 aPLib 压缩块，不是虚拟机），并由此**修正了三条此前的错误判断**（`.data` 是 BSS 而非丢失、末节 `.tp3` 是反作弊载荷而非游戏逻辑、`.text` 存在大量被工具漏掉的调用）；但**协议分派链仍未闭合**，卡点已从"格式未知"转移到"**`.tvm0` 的混淆控制流**"。
