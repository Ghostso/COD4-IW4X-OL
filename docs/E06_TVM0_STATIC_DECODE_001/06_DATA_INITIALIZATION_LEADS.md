# 06 — `.data` 初始化来源线索 / DATA INITIALIZATION LEADS

> 任务要求：判断结果能否解释 `.data` 的初始化来源、缺失数据的去向。
> 等级：`VERIFIED` / `STATIC-INFERENCE` / `UNKNOWN` / `BLOCKED`

---

## 1. 先纠正一个长期表述：`.data` 的"缺口"很可能**不是**缺口

### 1.1 实测数据

| 项 | `C-2697`（发行版） | `C-2697-Rec`（恢复镜像） |
|---|---|---|
| `.data` VSize | `0x0D05C420`（218.1 MB） | `0x0D05C420`（218.1 MB） |
| `.data` RawSize | `0x00049600`（300,544 B） | `0x00049600`（300,544 B） |
| 存在比例 | **0.138%** | **0.138%** |
| 该 0.138% 的字节 | — | **与原版逐字节相同** |

**关键：原版与恢复镜像的 `.data` 原始区完全一致。**
→ **这不是恢复工具造成的数据丢失**；发行版本身就是这样。

### 1.2 PE 语义：`VSize >> RawSize` 就是 **BSS**

按 PE 规范，对 `VA ∈ [SecVA + RawSize, SecVA + VSize)` 的地址，加载器**映射为零**（不占文件）。

| `.data` 区间 | 地址范围 | 大小 | 性质 |
|---|---|---|---|
| 已初始化（文件内） | `0x008F1000 .. 0x0093A600` | 300,544 B | 哨兵/初值/指针表 |
| **未初始化（BSS 尾）** | `0x0093A600 .. 0x0D94D420` | **208.1 MB** | **加载时清零** |

**裁定：`VERIFIED`。** `.data` 的 208.1 MB "缺口"是**未初始化数据（BSS）**，其"内容"就是 0，**没有丢失任何数据**。

### 1.3 佐证：同一发行版的服务端也是同构

| 对象 | 未初始化节 | VSize | 大小 |
|---|---|---|---|
| `S-2697` 服务端 | `.bss` | `0x157F26C8` | 343.9 MB |
| `C-2697` 客户端 | `.data` 尾 | `0x0D012E20` | 208.1 MB |

两者都在 `.bss`/`.data` 尾使用**数百 MB 的零填充** —— 该引擎的既有风格（`Com_InitZoneMemory` 类大区分配）。

## 2. 这对前几轮结论的影响（**必须修订**）

上一轮（`14_SERVER_KNOWLEDGE_ATLAS_001`）把 `.data` 0.14% 记为：

> "`.data` 声明 218 MB，仅 0.14% 在文件内 → 候选 vtable 可能落在缺失的 99.86% 中。"

**本轮修订：**

| 旧表述 | 修订后 |
|---|---|
| "`.data` 有 99.86% 缺失" | "`.data` 有 208.1 MB 属**未初始化 BSS**，内容按定义是 **0**，非缺失" |
| "候选 vtable 可能落在缺失区" | **不成立**：BSS 区在加载时清零，**不可能**承载已初始化的 vtable |
| "该缺口削弱'客户端不支持'的推断" | **不再成立**：该论据无效 |

**净影响：**
- `.data` **无法**再作为"找不到分派"的宽容解释。
- `.rdata` 指针表是**完整且可搜**的（30,895 个 →`.text`、613 个连续表）。
- 因此"**`.text`/`.rdata` 中均无 `0xA2E50` 的调用者或指针**"这一负面证据的**强度上升**（但仍受 `.tvm0` 未解码与"运行时可能生成"限制）。

## 3. `.data` 的**真实**已初始化部分是什么

| 指标 | 值 |
|---|---|
| 文件内大小 | 300,544 B |
| 对齐 u32 中 →`.rdata` 的指针 | 18,156 |
| →`.data`（自身） | 9,084 |
| →`.text` | 2,375 |
| →`.tvm0` | 56 |
| 与原版比对 | 逐字节相同 |

**STATIC-INFERENCE：** 该区含**已初始化的指针表/初值**（含 2,375 个 →`.text` 指针）。它是**真实数据**，应纳入 xref 搜索。

## 4. 指向 `.data` 的引用来自哪里

| 引用源 | 指向 `.data` 已初始化区 | 指向 `.data` BSS 尾 |
|---|---|---|
| `.rdata` 指针 | 3,458 | 18,876 |

**解释（STATIC-INFERENCE）：** 大量 `.rdata` 指针指向 **BSS 尾** —— 这是**运行期全局对象**的预期形态（如预分配的实体数组、快照缓冲），其**初始值**定为 0，运行期才被写入。这与"客户端把大量状态放在 `.data` 的未初始化区"一致，**不**提示任何被隐藏的代码表。

## 5. `.data` 初始化来源：直接证据？

**答：** 目前**没有**全部直接证据，但**排除了**一条错误线索：

| 假设 | 裁定 |
|---|---|
| `.data` 初值来自某 AP32 压缩块 | **REFUTED**：`C-2697` 的 `.data` 原始区**未经压缩**（不含 `"AP32"`），且与恢复镜像**逐字节相同** |
| `.data` 初值来自末节 `.tp3` | **未发现证据**：末节解出的是 TenProtect/TesSafe 的 12 个 PE，非 `.data` 初值 |
| `.data` 初值来自 `.rimp` 之外的修复表 | **PARTIAL**：`.rimp` 有 **420** 个值指向 `.data`（见 `07`），说明存在**加载期修复**，但那是**指针重定位**而非数据来源 |
| `.data` 的 208 MB 需要"来源" | **REFUTED（问题本身不成立）**：BSS 无需来源 |

| 结论 | 等级 |
|---|---|
| `.data` 的 208.1 MB 是**未初始化 BSS**，非丢失数据 | **VERIFIED** |
| 原版与恢复镜像的 `.data` **逐字节相同** | **VERIFIED** |
| "候选 vtable 落在缺失 `.data` 中"的旧解释 | **REFUTED** |
