# 02 — `.tvm0` 容器结构 / TVM0 CONTAINER LAYOUT

> 等级：`VERIFIED`（可由字节直接复算）
> 原始证据：`_data\RAW_RESULTS.txt` 的 `t01/t02/t10` 段；脚本 `_tools\t02_headers.py`、`_tools\t10_all_ap32_fixed.py`

---

## 1. 关键发现：`.tvm0` 不是虚拟化容器，而是 aPLib 压缩块

`.tvm0` 的**文件内**原始字节以一个**块头**开始：

```
file offset 0x529800 : 32 b4 bb b1 | 41 50 33 32 | 18 00 00 00 | a4 04 11 00 | dc a4 f5 86 | 00 8c 2b 00 | f3 f1 e5 0e | <packed data...>
                       └─ 4B prefix ┘ └─ "AP32" ─┘ └ hdr_size ┘ └ packed_len ┘ └packed_crc ┘ └ orig_len ─┘ └ orig_crc ─┘
```

### 1.1 头部字段（全部实测）

| 相对 `AP32` 签名 | 宽度 | 值（`.tvm0`） | 含义 | 等级 |
|---|---|---|---|---|
| `S-0x04` | u32 | `0xB1BBB432` | 前缀/校验值（**非**恒定） | VERIFIED（存在） / 语义未定 |
| `S+0x00` | 4B ASCII | `"AP32"` | 打包器标识（aPLib） | VERIFIED |
| `S+0x04` | u32 | `0x18` (24) | **头部总长**（含签名与前缀） | VERIFIED |
| `S+0x08` | u32 | `0x001104A4` (1,115,300) | **压缩流长度** | VERIFIED |
| `S+0x0C` | u32 | `0x86F5A4DC` | **压缩流 CRC32** | VERIFIED |
| `S+0x10` | u32 | `0x002B8C00` (2,853,888) | **原始（解包后）长度** | VERIFIED |
| `S+0x14` | u32 | `0x0EE5F1F3` | **原始数据 CRC32** | VERIFIED |
| `S+0x18` | … | — | **压缩流起点** | VERIFIED |

**注意：** `"AP32"` 出现在**节起始 +0x04**，即节前 4 字节是一个独立 u32（`0xB1BBB432`），**头部整体是 24 字节（0x18）**。先前的扫描若以 `"AP32"` 为节起点会**偏移 4 字节**，导致解包失败——本轮已纠正。

### 1.2 `.tvm0` 的容器结构（结论）

```
[0x00..0x04)  4B 前缀 (0xB1BBB432)
[0x04..0x1C)  24B AP32 头部 (hdr_size 已含这 24B)
[0x1C..0x1C+packed_len)  aPLib 压缩流
[尾部]        填充/未使用（到 RawSize 0x110600 为止）
```

- 压缩流占 `0x1C .. 0x1104A4+0x1C = 0x1104C0`。
- 该节 **RawSize = 0x110600**，压缩流后余 `0x140` 字节（填充/对齐）。
- **不存在**第二层容器：解包结果内 `"AP32"` 出现 **0** 次，`PE\0\0` 出现 **0** 次。

### 1.3 为什么它看起来"高熵"

- 压缩流本身熵高（属 aPLib 编码，非加密）。
- 但 `.tvm0` 在**恢复镜像中已是解包后的内容**，其解包后熵为 **5.66 bit/byte**、零字节占 **21.4%**、`0xCC` 仅 0.06% —— 这是一个**结构化**的数据/代码混合体，**不是**加密块。

## 2. 同一容器格式的普遍性（重要）

`"AP32"` 头部格式**不只是 `.tvm0`**：在 `C-2697` 中共命中 **10 处**，全部为**同一 24 字节格式**：

| # | 文件偏移 | 所在（伪装）区段 | packed_len | orig_len | 双 CRC 校验 |
|---|---|---|---|---|---|
| 0 | 0x00000404 | `.tp3`(VA 0x1000) | 3,752,773 | 8,047,104 | ✔ |
| 1 | 0x00529804 | **`.tvm0`**(VA 0xD958000) | 1,115,300 | 2,853,888 | ✔ |
| 2 | 0x0063A523 | `.tp3`(VA 0xDC11000) | 1,260 | 1,216 | ✔ |
| 3 | 0x0063AA2B | 同上 | 11,942 | 13,664 | ✔ |
| 4 | 0x0063D8ED | 同上 | 4,931 | 11,573 | ✔ |
| 5 | 0x0063EC4C | 同上 | 602 | 1,073 | ✔ |
| 6 | 0x0063EEC2 | 同上 | 127 | 321 | ✔ |
| 7 | 0x0063EF5D | 同上 | 3,916 | 16,054 | ✔ |
| 8 | 0x0063FEC5 | 同上 | 3,339,519 | 5,115,080 | ✔ |
| 9 | 0x0096F3E0 | 同上 | 4,200 | 3,858 | ✔ |

**结论：** `"AP32"` 是**贯穿整个发行版**的段级压缩容器；`.tvm0` 只是其中一个（名字具误导性）。

**独立结构证据（不依赖解包）：** 头部自带的两个 CRC32 —— `+0x0C` 覆盖压缩流、`+0x14` 覆盖解包结果 —— 构成**自校验**。10/10 块**双向 CRC 均通过**（见 `04`）。

| 指标 | 值 |
|---|---|

| 熵（全局） | 5.6555 bit/byte |
| 零字节 | 21.39% |
| `0xCC`（int3） | 0.06% |
| 内含 `"AP32"` | 0 |
| 内含 `PE\0\0` | 0 |
| 是否 `MZ` 开头 | 否 |
| ASCII 串（≥6） | 614（多为短碎片，非有意义字符串） |

**解释（STATIC-INFERENCE）：** 该节是**栈混淆/VM 化的 x86 代码**（见 `04` §6 的反汇编特征），不是数据表、不是资源、也不是第二层压缩。

## 4. 首节 `.text` 的同一格式（对照）

| 项 | `.text`（VA 0x1000） | `.tvm0`（VA 0xD958000） |
|---|---|---|
| AP32 位于节内偏移 | 0x04 | 0x04 |
| hdr_size | 0x18 | 0x18 |
| packed_len | 0x394345 | 0x1104A4 |
| orig_len | 0x7ACA00 | 0x2B8C00 |
| 前缀 u32 | 0xB1D3F293 | 0xB1BBB432 |
| 双 CRC | ✔ | ✔ |

**含义：** 发行版对**代码区段**（`.text`）与**混淆区段**（`.tvm0`）使用**同一压缩容器**。因此 `.tvm0` 的"格式问题"其实与 `.text` 是**同一个已解决问题**。
