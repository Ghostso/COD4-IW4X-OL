## 02. 问题的精确定义

**预期行为**
`recv()` 收到的字节被写入某个缓冲，该缓冲（连同比特长度）被交给
`bit-reader 构造函数 0xB779A0(buf, nbits)`，由此产生的 reader 对象挂在会话的 `[+0xB0]`，
随后由 `0xBA4430` 分发出 opcode/消息。

**实际行为**
可以证明：
- 会话对象里有一个 bit-reader（`[+0xB0]`，构造 `0xB779A0`，34 字节）
- `0xBA4430` 用 `[+0xB0]` 读字节并用 `0x81/0x83/0x84/0x85` 分发
- `0xB779A0` 的构造参数确实是 `(buf, nbits)` 二元组

**不能证明**：
- 传给 `0xB779A0` 的 `buf` **就是** recv() 写入的那个缓冲

**偏差（原报告原话，地址已按本审计更正）**
> "因此，目前不能证明 `0xB765A0` 读取的字节就是 recv 的后续 payload。
> 可以证明两端使用同一个会话对象、同一长度/类型控制链，
> **不能把'对象构造'写成'payload 已复制'**。"

> ⚠️ 原报告写的是 `0x7765A0`，那是错误地址（见 §01 更正表）。引文其余部分仍成立。

## 06. 客户端逆向定位

| 项 | 值 |
|---|---|
| 映像 | `codoMP_client_shipRetail.exe`，ImageBase `0x00400000`，SizeOfImage `0x0E659000`，7 个节区全名 `.tp3` |
| 接收分发函数 | **`0xBA4430`**（成员函数，`mov esi,ecx`） |
| 1 字节读取器 | **`0xB765A0`**（包装 `0xB783C0`） |
| 比特预算 | **`0xB9BBB0`**：`[+0x1C] − [+0x24] + 0x1F` |
| bit-reader 构造 | **`0xB779A0`**，对象 34 字节（`push 0x24`），`ecx=this, arg1=buf, arg2=nbits` |
| 房间信道建流 | **`0x637000`**：`push nbits(=[ebp+0x24]*8); push buf(=[ebp+0x20]); call 0xB779A0` |

### 6.1 接收分发 `0xBA4430`（本轮新解）

```asm
00BA4458  mov  esi, ecx
00BA445A  cmp  dword ptr [esi+0xC8], 4      ; 状态 4 -> 返回 0
00BA447E  cmp  dword ptr [esi+0xC8], 2      ; 必须 ==2
00BA4491  call 0xBA41D0                     ; 状态机/装配
00BA44A0  call 0xBA0CC0                     ; 前置提取
00BA44AD  mov  ecx, [esi+0xB0]              ; ★ bit-reader 对象（不是字节缓冲）
00BA44B3  call 0xB9BBB0                     ; eax = 剩余比特
00BA44B8  mov  edi, [esi+0xAC]              ; 长度
00BA44D8  call 0xB765A0                     ; 读 1 字节
00BA44F6  cmp  al, 0x81                     ; ★ 类型码分发
```

类型码比较点：`0xBA44F6`(`0x81`)、`0xBA4557`(`0x83`)、`0xBA45F0`(`0x84`)，`0x85` 在后续分支。

### 6.2 ★ `[esi+0xB0]` 是 bit-reader 对象，不是 recv 缓冲

构造函数 `0xB779A0` 的字段：
```
[+0x00] vtable  [0xDB6AE4] → 再赋 [0xD59834]
[+0x14] 总比特数（nbits）
[+0x18] 总比特数
[+0x1C] 缓冲总比特（= 剩余计算基准）
[+0x21] 标志字节
[+0x24] 已消耗比特（由 0xB9BB90 设定）
```

⇒ 这条链是 **`字节buf + nbits` → 位流对象 → `readBits/readData`**。
字节缓冲**不在** `[+0xB0]` 里，"payload 已复制"这个问题因此要换个问法。

### 6.3 顺带独立验证 ISSUE-0010 的"下行走位流"

`0x637000` 的建流方式（`nbits = 字节数×8`，随后 `readBits(3)` + `readData(8)`）
与 `ROOM_DIRECTION_SPLIT_20261028` 的记录**逐条吻合**。
本轮用一次全新转储**独立复现**，不是转述。

**陷阱检查**

| 陷阱 | 结果 |
|---|---|
| RVA/VA 混淆 | **本轮发现两处十六进制位错误**（`0x7765A0`→`0xB765A0`、`0x7A44F6`→`0xBA44F6`） |
| 跨版本 | 否（全部 3.19） |
| TQOS/TDR 误认 | 否 |
| 静态串≈执行 | 否（用可达性与字段写入判定） |
| 套用外部结构 | 否 |

**FIRST_UNPROVEN_EDGE**（精确化）：

## 18. 最终技术结论

**当前状态**：`OPEN`。缺口已从"地址全错、不知在哪"缩小到**一条 store 未找到**。

**已经证明的事实**：
1. `0x7765A0` **不是函数**（落在 `0x776580` 指令中间，是 sprintf 分发器）。
2. 真实读取器 = `0xB765A0`（包装 `0xB783C0`）；真实分发 = `0xBA4430`；类型码比较在 `0xBA44F6` 起。
3. `[esi+0xB0]` 是 **34 字节 bit-reader 对象**（构造 `0xB779A0`），不是字节缓冲。
4. bit-reader 的构造参数是 `(buf, nbits)`；剩余比特 = `[+0x1C] − [+0x24] + 0x1F`。
5. `0x637000` 用 `nbits = 字节数×8` 建流，与 `ROOM_DIRECTION_SPLIT` 一致（**独立复现**）。

**尚未证明的事实**：recv 写入的字节缓冲如何变成 `0xB779A0` 的 `buf` 参数。

**第一条未闭合证据链**：`recv 字节缓冲 → 0xB779A0(buf,nbits)` 的 `buf`。

**当前最可信根因**：H1（同一缓冲直接传入），但 13 处分配点附近均未见 `mov [reg+0xB0]`。

**下一步最小实验**：E9 需改为"在 `0xBA4430` 入口下断点或读 `[esi+0xA8]` 与 `[esi+0xB0]` 指向对象内 `buf` 字段的关系"，
而不是原设计的"指针直接比对"。

**最小修复条件**：一次能覆盖**接收时刻**的转储（本轮 `snap_002` 是单点采样，客户端未连接，故无活动会话）。

**完成验收标准**：§16。

**是否可以交给开发 Agent 直接修复：NO**
必须先完成：**E9（改写后的版本）**。
好消息：本轮的转储已经证明 **EDGE 的可观测性没问题** —— 一次有活动会话的转储就能闭合它。
