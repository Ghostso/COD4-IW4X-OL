## 一、直接回答任务书要求的四个问题

### 1. 我们目前有哪些协议结论**真正获得了交叉佐证**？

**只有一类：2697 configstring（`0x04`）消息的 body 内部布局。**

| 字段 | 服务端 writer | 客户端 reader | 本任务复核 |
|---|---|---|---|
| count1 = 2 字节（16 bit LE） | `0xA0807` WriteShort | `0xA26AF` push 2 → ReadData → `movsx word` | ✔ 活体反汇编 |
| 索引增量（连续 1bit；否则 0+13bit） | `0xA0400` | `0xA26E2`/`0xA26F4` push 0xD | ✔ |
| A1 字符串（strlen+1，含 NUL） | `0x99651` | `0xA25F0` NUL 扫描 | ✔ |
| A2 段计数 = **11 bit** | `0xA084D` mov 0xB | `0xA2765` push 0xB | ✔ 两侧独立 |
| A2 条目值 = 10 bit | `0xA088A` mov 0xA | `0xA27D7` push 0xA | ✔ |
| A3 = 10/7/4/n×12 bit | `0xA08AD..0xA0950` | 子过程 `0xA2480` push 10/7/4 | ✔ |
| 索引上限 0x1DD6 / sentinel 0x1DD7 / 区间 0..0x13（跳 0x12） | 校验 | `0xA2702`/`0xA2728` | ✔ |

**次强（字段形状一致，但绑定未证）：** Reliable Command `0x02` 的载荷形状（long+short+data，上限 `0x3FC`）。**服务端 PROVEN；客户端形状 PROVEN；opcode 绑定 BLOCKED。**

**服务端自洽（单源但指令级）：** gamestate 字段序、snapshot 调用序列、netchan 常量、注册门控格式链。

### 2. 哪些仍**只有单一证据来源**？

（详见 `XVAL01_UNSUPPORTED_CLAIMS.md` A 节）

- 服务端 writer 规格类：C-010/011/021/022/023（仅 2697 单样本）。
- 客户端 `0xA2E50` 形状：C-008（与 C-007 **共享同一字段定义**，不构成独立验证）。
- Demonware 分帧器 `0x6ABBC0`：C-025（**仅 E-19 一份，本轮未独立复核**）。
- 握手/加密（XOR、记录层原语、189 vs 219）：源码单源或 `SOURCE-CONFLICT`。

### 3. 哪些冲突会**阻塞互通**？

| 阻塞 | 冲突/缺口 | 状态 |
|---|---|---|
| B1 | 客户端 `0x02 → 0xA2E50` 绑定（CONF-X03） | BLOCKED |
| B2 | 客户端 `0x06` 读取/对齐/终止 | BLOCKED |
| B3 | 客户端实时 `0x03` 消费者（demo 路径已 REFUTED） | BLOCKED |
| B4 | 客户端 `0x04` 外层值级识别 | BLOCKED |
| B5 | 客户端 snapshot delta 解码 / 帧边界 | BLOCKED |
| B6 | COOKIE_ECHO 189 vs 219（CONFLICT-01） | SOURCE-CONFLICT |

> 这 6 项任一未解，**不得**宣称"2697 客户端与服务器协议兼容"或"可进入大厅/可玩"。

### 4. 完成技术论证还缺少哪几项**关键证据**？

1. 客户端 `0x02` 读取点与分派表项；
2. 客户端 `0x06` 读取/对齐/终止分支；
3. 客户端实时 `0x03` consumer；
4. **一条真实的 2697 战斗通道字节流**（唯一能把"形状"升级为"字节级"）；
5. 同 SHA-256 客户端的**运行时解包 dump**（解除 `.data` 99.86% 缺失的结构性限制）。

## 二、对**服务器开发**的建议

1. **可行性**：值得做，但定位为"**协议兼容 + 最小战斗服 MVP**"，不是从零重建完整 CODOL（沿用 `11_CUSTOM_SERVER_FEASIBILITY §1`）。
2. **技术路线（三源合一）**：
   - 以 **2697 原生服务端为协议 oracle**（writer 规格真值）；
   - 以 **OLD/1113 源码为算法/骨架参照**（引擎层可复用）；
   - 以 **C# Codec/战斗服为可构建实验底座**（离线向量，不上线）。
3. **可立即实现（服务端自洽，离线可测）**：
   - Reliable `0x01`/`0x02` 编码器（字段序 + 0x3FC）；
   - Configstring `0x04` body 编码器（**字段已两侧证**——最可信）；
   - Gamestate 顶层字段序（宽度/顺序已证）。
4. **暂不要实现/宣称（等证据）**：
   - 客户端互操作、"可进入大厅/可玩"；
   - Snapshot 完整帧生成（帧边界未闭合）；
   - 任何"0x02 客户端已支持"的断言。
5. **许可**：OLD/CoD4x 为 AGPL/GPL，复制源码须单独评估发布义务。

## 三、对**互通验证**的建议

1. **先解阻塞再跑实机**：优先做纯静态 A-01/A-02/A-03（定位 `0xA2660` 调用者、`0x06`/`0x04` 读取点），这是**通往互通的最短静态路径**。
2. **不要先写战斗服**：历史证据（`BATTLE_RX=0`）显示客户端**根本没走到拨号战斗端点**；问题在握手/会话，不在战斗服缺失。
3. **分层陈述**：平台/预订层（21/5、6/14）与游戏实时消息路径必须分开；目前所有可复现抓包都在**平台层**。
4. **互通验收门槛**：必须同时具备 (a) 客户端分派闭合 **且** (b) 一条真实战斗字节流；缺一不可。

## 四、对**复现工作**的建议

1. **身份先行**：一律按 **SHA-256** 而非文件名判身份——工作区有 40+ 份同名的 `3.3.3.3`（`36997674…`）副本，极易误当 2.6.9.7。
2. **地址口径强制自检**：`REV-017` 记录 VA/RVA 混淆已**三次**复发；任何静态结论须附"地址基准自检"。
3. **先解码 `.tvm0` 再搜索**（禁止扫描原始 E8/E9，可靠性 0.0%）；`.rimp` 指针修复优先于其它静态项（可恢复 `.rdata`/`.data` xref 面）。
4. **禁止四项升级**（沿用 `atlas 15 §3`）：
   - 不把"镜像缺调用引用"当"客户端不支持"的强否定；
   - 不把 RVA 候选直接认定为消息解析器；
   - 不把候选函数直接认定为 opcode 处理函数；
   - 不把 TenProxy/IIPS/TCLS/libcurl/SOCKS/QOS 的存在当成游戏协议链闭合。
5. **二手报告纪律**：`SECONDARY-ANALYSIS` 只作搬运；引用须回溯到**原始字节/指令/RVA**。本任务已对关键断言做活体复核（`_data\INDEPENDENT_VERIFICATION_LOG.md`）。

## 五、风险加权结论（可复算）

依 E-15 权重标度重算（`XVAL01_UNIFIED_QUESTION_REGISTER_UPDATE.md`）：

- **总权重（分母）= 195**，**加权得分 = 78.8**，**风险加权解决率 = 78.8/195 = 40.41%**（XVAL-01 时点）。
- **I4 层解决度 = 24/104 = 23.1%**（高权重层仍是最大缺口）；**I2 层 = 28.8/33 = 87.3%**（低权重事实类多已闭合）。
- 结论：**服务端"编码器"规格基本就绪；客户端"实时消费链"是决定互通的唯一瓶颈。**

## 六、总裁决（一句话）

> 本项目已有**三类原始证据齐备**（2.6.9.7 客户端、2697 服务端、OLD/1113 含源码）与**逐命题反汇编台账**；但**唯一获得两侧指令级交叉佐证的协议结论是 configstring（0x04）的 body 内部布局**；reliable command 仅到"形状一致、绑定未证"；gamestate/snapshot/0x06/握手均停在服务端单侧或冲突。**客户端侧全部 BLOCKED 的根因是镜像结构不完备（`.data` 99.86% 缺失 + `.tp3` 未恢复 + `.tvm0` 未解码），而非"客户端不支持"。在取得同版本客户端运行时镜像与一条真实战斗字节流之前，任何"2697 客户端 ↔ 服务器互操作"的结论仍只能是形状级推断。**
