# 07 — E-08 裁定 / VERDICT

> 完成标准要求明确回答四个问题。逐条回答，并给出对 `14_SERVER_KNOWLEDGE_ATLAS_001` 的更新。

## Q1. 客户端 body 解码路径是否得到直接证据支持？

**答：部分 —— 只有"位层"得到直接证据，"字段层"没有。**

| 层 | 客户端证据 | 等级 |
|---|---|---|
| 位序（LSB-first） | 客户端 1 位读取函数 @ RVA 0x1A07B0/0x1A07E7：`and r,7 ; shl 1 ; shr r,3 ; test ; setne` | **DIRECT** |
| 位索引（byte=p>>3, bit=p&7） | 同 | **DIRECT** |
| **字段顺序（0x04→count→A1→A2→A3→0x06）** | **无** | **BLOCKED** |
| **各字段宽度（16 / 10 / 7 / 4 / 12 位）** | **无** | **BLOCKED** |
| **终止规则（`0x06` 定位）** | **无** | **BLOCKED** |
| 索引增量解码（1bit / 0+13bit） | **无** | **BLOCKED** |

**关键障碍：** 客户端 **1 位读取函数被 115 个调用点共用**（`DIRECT`），它是**所有位流消息**的公共原语，**不能**据此判定"哪个调用者解析 configstring"。客户端**无符号表**（COFF 符号 0），且任务禁止运行时观测。

**结论：** 客户端 body 解码路径**未被**直接证据支持到字段级。**注意：不能把"找不到"当作"不存在"**（E-06 已确立此纪律；本项目已有"工具提前停止造成假 0 命中"的先例）。

## Q2. 服务端字段写入顺序与客户端读取顺序是否一致？

**答：无法判定（`BLOCKED`）。**

- 服务端顺序已**完全闭合**（`DIRECT`）：`0x04 | count1 | A1 | A2 | A3 | 0x06`，含索引增量与各字段位宽。
- 客户端**未定位**对应读取器 → **没有可比较的另一侧**。
- **唯一可比的是位序**：两侧均为 LSB-first（`DIRECT`）。这是**必要条件**，**不是**兼容性证明。

**明确声明：** 依任务约束 6，**不**因"服务端能这样写"而宣称"客户端会这样读"。

## Q3. 哪些字段可以确认，哪些仅有形状匹配？

| 类别 | 内容 |
|---|---|
| **已确认（服务端，DIRECT）** | `0x04`；`count1`(2B)；索引增量（1bit / 0+13bit，首索引 -1）；A1 `{index, len+1 bytes}`；A2 `{10b count, 每项 index+10b}`；A3 `{10b count, 每项 index+10b+7b+4b n+n×12b}`；`0x06`；全部越界/去重/黑名单失败分支 |
| **已确认（两侧，DIRECT）** | 位序 LSB-first；位索引 `p>>3` / `p&7` |
| **仅形状匹配** | **无。** 本轮**没有**把任何"形状相似"升级为证据 |
| **冲突** | `count1` 宽度：指令级 2 字节 **vs** 内联注释串暗示 8 位 → **双留**（`06` C-01） |
| **未定** | `[ebp-0x1e14]` 位计数用途；A2/A3 业务语义；`0x1DD7` sentinel 语义 |

## Q4. 是否能够建立独立于现有 Codec 自测的验证向量？

**答：能，但只能到"服务端规格自洽"这一级。**

- 已产出 **V-A（索引增量）/ V-B（A2）/ V-C（A3）** 三套向量，**来源为本轮独立反汇编**（非引用既有 C# Codec 的字段定义），生成器为独立实现（`_tools\s27_vectors.py`）。
- 已**人工复核**两条（IDX-004、A2-003）逐位正确。
- **但**：**全部是 `CONSTRUCTED`（候选向量）**，**没有**任何原始抓包字节 ⇒ **不构成 Golden Vector**。
- 因此它们能提升**服务端编码器**的置信度，**不能**提升"与真实客户端互通"的置信度。

## 附加问题：哪些未解决项会阻断服务器最小闭环？

| 阻断项 | 为什么阻断 |
|---|---|
| **U-01 客户端 body 读取顺序** | 无此证据，无法确认服务端字段序被接受 —— 直接决定"客户端能否进入世界" |
| **U-02 `count1` 宽度（8 vs 16）** | 若实际为 8 位而按 16 位编码，**后续所有位字段整体错位** |
| **U-07 `0x06` 非字节对齐时的定位/填充** | 若客户端按字节对齐定位终止符，则位流长度必须补足；否则解析越界 |
| U-03 `0x04` 后是否还有未识别字段 | 字段边界错误 |
| U-06 A1 合法索引区间表含义 | 索引被拒会导致**整个发布失败**（返回 0） |

## 本轮对既有档案的更新（**追加**，不覆盖）

### UPD-01 — body 位编码：`BLOCKED` → **服务端侧已闭合**

- 旧（E1）：`configstring` 状态为 `VERIFIED_HEADER_TRAILER_BODY_BLOCKED`，body 标 `BLOCKED`。
- 新（E08）：**服务端** body 结构已逐字段闭合（索引增量 / A1 / A2 / A3 / 各上限）。
- 修订原因：本轮首次对 `0xA0807..0xA0997` 做**逐指令**追踪（此前未拆解）。
- 差异：新增 5 类字段宽度、索引增量规则、失败分支清单；**客户端侧仍 BLOCKED**。

### UPD-02 — 0xA0807 / 0xA0997 的归属更正

- 旧：任务描述为"客户端"地址。
- 新：实测为 **2697 服务端** `_CODOL2697_WriteConfigstrings` **函数体内**偏移；客户端同 RVA 为函数尾/int3。
- 修订原因：样本身份标注错误（同类问题见既有 CONFLICT-05）。
- 差异：客户端 = 函数尾；服务端 = 活跃字段写入点。

### UPD-03 — 新增两侧同构证据：位序

- 新：客户端存在 LSB-first 位读取原语，与服务端 `MSG_WriteBits` **位序一致**（`DIRECT`）。
- 意义：字段级兼容的**必要条件已满足**，但**不构成充分条件**。

### UPD-04 — 新增冲突：`count1` 宽度

- 新：指令级（2 字节）与内联注释串（暗示 8 位）**冲突**，已登记双留。

### UPD-05 — 新增可复算测试向量（候选）

- 新：V-A/V-B/V-C 三套（构造级），生成器 `_tools\s27_vectors.py`。

### UPD-06 — 方法学：VA/RVA 混淆第三次复发
