# NETCHAN_BUFFER_FLOW — 缓冲区与应用层入口关系

## 1. 038 的核心修正

037 把 `0x5F830 ← 0x208380 ← 0x1FF820 ← 0x20059B` 当作“应用层消息入口”推荐链。038 复核后确认：

- `0x2000A0` 函数入口按 `[ebx+0xBC]` 做 0..25 分派。
- `0x20059B` 是该分派器的一个分支，调用 `0x1FF820`。
- `0x1FF820 → 0x208380 → 0x5F830` 是一条客户端对象状态/字段更新链。
- 其调用者 `0x200F10/0x200F34` 遍历 `[ebx+0x120]` 的数组，逐项调用，不是从 UDP/netchan 缓冲按 opcode 读取。

**判定：** 该链是 `CONFIRMED_CROSSREF` 的客户端状态更新链，**不是** `CONFIRMED_DIRECT` 的应用层网络消息入口。

## 2. 应用层入口的真实模块问题

| 模块 | 是否包含 | 证据 |
|---|---|---|
| `codoMP_client_shipRetail.exe` | OOB 字面量与应用/状态相关代码 | `getchallenge`、`gamestateupdate` 等 |
| `codoMP_client_shipRetailBase.dll` | 引擎主体、`.text` 7.4MB、`.tvm0` 31MB | PE 节区与字符串归属 |
| `image_best.bin` | EXE 的运行时镜像，不是 DLL | 同基址/时间戳/入口 |

`image_best.bin` 中：
- 1,279 个 `jmp dword ptr [reg*4+disp]` 候选；
- 1,187 个候选的目标表可在映像内解析；
- 但没有一个能通过“读取 netchan 缓冲 → opcode → 进入解析器”的上下文验证。

主 DLL 中：
- `netchan`、`gamestate`、`configstring` 字符串为 0；
- `opcode` 仅出现在 Lua/调试/描述符字符串；
- `.text` 中 738 个间接跳转表，绝大多数与网络无关；
- `.tvm0` 未解码，字节扫描无效。

## 3. 间接证据与阻塞

### 3.1 EXE 调用图质量

- `image_best.bin` 中 E8 调用点共 201,125 个。
- 目标落在文件内的 158,065 个；其中落在启发式函数入口的 91,770 个，落在边界外的 66,295 个（41.9%）。
- 这说明恢复镜像的线性调用图不完整，不能仅靠 E8 交叉引用断言“无调用者”。

### 3.2 `.tvm0` 不能按普通 x86 解释

- EXE 的 `.tvm0`（`0xE5D3000`，4KB）无有效 opcode 表上下文。
- 主 DLL 的 `.tvm0`（31MB）尚未解码。
- 对类似区域的 E8/E9 字节扫描显示：4,414 个命中中仅 1 个目标落在 `.text` 函数入口（比率 0.02%）。

**判定：** 在未解码 `.tvm0`、未获得运行时内存视图或完整重定位信息前，应用层 opcode 分派必须保持 `UNKNOWN`。

## 4. 已知但不应混淆的三类分派

| 类型 | 证据 | 状态 |
|---|---|---|
| OOB 命令文本分派 | `0x1C05F0` 状态门与字面量 | `CONFIRMED_DIRECT` |
| 应用层消息 opcode 分派 | 未定位 | `UNKNOWN` |
| snapshot/entity 增量字段类型分派 | `0x5F830` 与两张表 | `CONFIRMED_DIRECT`（结构） |

三者不是同一张表，不得合并。

---

## 5. 结论

**未确认**“netchan 重组缓冲如何传入应用层解析函数”。  
**未确认**缓冲起始地址、有效长度、读指针、消息头、opcode 读取方式与错误路径。  
所有相关字段应保留 `UNKNOWN`。
