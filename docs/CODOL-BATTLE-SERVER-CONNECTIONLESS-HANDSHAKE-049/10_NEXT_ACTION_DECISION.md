# 10 — 050 唯一优先目标与可执行步骤

## 0. 结论

049 已完成**握手模块实做**(工作包 A–C,65/65 测试通过)并取得 in-match 收包链的**新可复核结果**
(工作包 D:P5 启动链、泵调用者、出队地址修正、第 3 节区量化)。

当前唯一阻塞 in-match 主链的**最小未闭环边**是:

> **P5 `recv` 的缓冲 == `0x7765A0` 读取的缓冲(或给出带地址的否定证据)。**

这条边一旦闭合,`OpcodeDispatch / Gamestate / ConfigStrings / Snapshot` 四模块可并行开展。

---

## 1. 唯一优先目标(050-T1)

**证明或否证:P5 消费路径中 `0x7765A0` 的 `arg1`(缓冲)与 `0x873A00`(`recv(sock,buf,len)`)
的 `buf` 是同一对象/同一缓冲。**

**判定为完成的验收(二选一):**

- **A(肯定):** 给出 `recv(buf) → [会话对象字段] → 0x7765A0(arg1)` 的完整指令/数据流链,
  每步带 RVA、寄存器/栈变量、字段偏移;或
- **B(否定):** 给出带地址的负证据,说明 `0x7765A0` 的输入来自**另一**缓冲/队列
  (含被检查范围、以及"为什么不是 recv 缓冲")。

**禁止:** 仅凭"都在 `0x7Axxxx` 区域"或"都被 `esi` 引用"断言同一缓冲。

## 2. 为什么是这个目标

- `06` §6:`recv` 与"读字节+分支"两端都已证实,**唯一缺口**是它们之间的缓冲传递。
- `09` Part B:模块 3/5/6/7 的 `MinimumMissingFact` **全部**是"缓冲来源未证"。
- `08` §6:第 3 节区缺失只影响"解析器可能在第 3 节"的替代解释,
  **不**阻塞这条可在 present 区域闭合的边 → 本目标性价比最高。

## 3. 可执行步骤(按顺序,全部只读静态)

### 步骤 1 — 精确定位 `0x7765A0` 的调用参数来源
- 输入:`0x7A4430..0x7A4800` 反汇编(`evidence\d40`)、`0x7765A0` 反汇编(`evidence\d44`)。
- 动作:
  1. 在 `0x7A4430` 内回看 `call 0x7765A0`(`0x7A44D8`)之前对 `[ebp-0x14]`、`[ebp-0xE]`、
     `esi` 的赋值(`0x7A44AD`..`0x7A44D8` 区间)。**049 已定位:** 输入缓冲 = `[esi+0xB0]` 经
     `0xB9BBB0` 取指针,长度 = `[esi+0xAC]-1`(见 `06` §8);
  2. 记录 `0x7765A0` 的 6 个实参在调用点的寄存器/栈位置;
  3. 沿 `[esi+0xB0]` 反向数据流,判断它是否与 `0x7A20A0` 的 `recv` 缓冲
     `[esi+0xA8]` 指向同一对象(注意偏移不同:`0xA8` vs `0xB0`;`0xAC` 是长度)。
- 产物:`evidence\050_T1_arg1_provenance.json`。

### 步骤 2 — 定位 `recv` 缓冲的会话字段
- 输入:P5 `recv` 包装 `0x873A00`(`evidence\d42`)、`0x7A20A0`(`evidence\d45`)。
- 动作:
  1. `0x7A20A0` 内 `0x7A20CC` 的 `lea edi,[esi+0xA8]` 是 recv 缓冲;确认 `esi` 的语义
     (会话对象基址);
  2. 在 `0x7A41D0`/`0x7A4430` 中检查是否也以 `[esi+0xA8]`(或 `[esi+0xAC]` 长度)作为
     `0x7765A0` 的输入;
  3. 若匹配 → 记录为**同一缓冲的证据**;若不同 → 记录为**否定证据**。
- 产物:合并进 `050_T1_arg1_provenance.json`。

### 步骤 3 — 复核 `0x7765A0` 的读取语义
- 动作:确认 `0x7765A0` → `0x7783C0` 的缓冲游标读是否推进同一个 `[esi+...]` 游标;
  确认读出的字节是否就是 `0x7A44F6` 比较的那个字节。
- 产物:`evidence\050_T1_reader_semantics.json`。

### 步骤 4 — 回灌 047 工程
- 若步骤 1–3 给出肯定链:在 `FinalCodolOpcodeDispatcher` 中**仍不**注册具体 opcode
  (字节值 0x81/0x83/0x84/0x85 的语义未证),但更新 `ProtocolModuleReadiness.OpcodeDispatch`
  的 `MinimumMissingFact` 为"字节值→opcode 名映射";
- 若给出否定链:记录新的缓冲来源,并重排后续目标。

## 4. 明确不要做的事(避免重复劳动)

- 不要重查 TQOS(`0x85Dxxx`/`0x87xxxx`)—— 已多次定性为平台层。
- 不要重查 `EXE_LOSTRELIABLECOMMANDS` 的 13 个上游 —— 已定性为错误上报。
- 不要把 `0x1C13A0`(连接无关)当作 in-match opcode 分派。
- 不要为补齐第 3 节区而启动客户端/读内存(需单独授权;且本目标不依赖它)。
- 不要因 `0x7765A0` 读出 `0x81/0x83/0x84/0x85` 就声称这些是官方 opcode。
