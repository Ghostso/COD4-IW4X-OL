## 1. 0x85 处理器 `0xBA3710` 的完整流程

```
入参：  edi = 连接对象 ; [ebp+8]=buf ; [ebp+0x10]=len ; [ebp+0x14]=?
0xBA3794  call 0xB783C0            ; 读 4 字节（seq）
0xBA37C2  call 0xB783C0            ; 再读 16 字节
0xBA3844  mov eax,[edi+0x5EC] / inc / 写回   ; 收包计数器
0xBA3853  cmp [ebp-0x394],eax      ; 收到的 seq == 旧计数 ? 否则复位
0xBA38A4  mov ecx,[edi+0xB0] / call 0xB9BBB0 ; 取数据流 → esi = 结果-5
0xBA38BB  mov edx,[edi+0xAC] / sub edx,4     ; 长度
0xBA38ED  call 0xBA02A0            ; 由 [edi+0x620] 生成 20 字节 key20
0xBA38FE  call 0xC73800            ; keyed-hash init（alg = "sha1"）
0xBA392C  call 0xC73760            ; keyed-hash update(data, len)
0xBA395A  call 0xC737A0            ; keyed-hash final → 20 字节摘要
0xBA398D  …… 把摘要与「报文末 20 字节」逐字节 XOR + OR …… ; 全 0 才通过
```

---

## 2. 关键：这是**带密钥的 SHA1 MAC**，不是查表异或

`0xC73800` 里推入的是算法名指针 `0xD40E7C`，该处内存为：

```
0xD40E7C:  "sha1\0\0\0\0SHA1\0\0\0\0des-ede3-ofb\0DES-EDE3-OFB\0"
```

而 `0xC77ED0`（final 核心）里有一段**逐字节 `xor 0x5C`**：

```asm
0xC77F50  mov edx,[ebx+0x328]      ; ← 密钥材料在 对象+0x328
0xC77F56  mov cl,[edx+eax]
0xC77F5C  xor cl,0x5C              ; ← 0x5C = HMAC 的 opad 常量
0xC77F5F  mov [eax+edx],cl
…
0xC77F71  call [esi+0xE88674]      ; 步骤②
0xC77F8F  call [esi+0xE88678]      ; 步骤③（喂 (key^0x5C)）
0xC77FA9  call [esi+0xE88678]      ; 步骤④（喂 message）
0xC77FBF  call [esi+0xE8867C]      ; 步骤⑤ final
```

⇒ 校验值 = **带密钥的 SHA1 MAC**，密钥取自**对象 +0x328**，
并对密钥做 `xor 0x5C`（opad）后参与哈希。

## 3. 为什么现有服务端实现必然失败

`CODOLServer\lobby_server\lobby_plain_probe.py` 里的：

```python
def build_0x85_checksum(v1, inner16, src20, frame_len=200):
    tag = codec_02a0(src20)[:8]          # ← 只取 0xBA02A0 查表结果的前 8 字节
    return build_frame(0x85, u32(v1) + inner16 + tag, ...)
```

它只做了 **`0xBA02A0` 的查表异或**（20 字节中间量）并截前 8 字节，
**完全没有做**：

1. 20 字节的 keyed-hash（SHA1），
2. 密钥源 `对象+0x328` 的 `xor 0x5C`（opad）处理，
3. 用报文本体做 update、取 **20 字节**摘要、
4. 与「报文末 20 字节」比较。

⇒ 这解释了 SESSION 文档里「0xBA02A0 复刻验证**未命中**客户端载荷」的现象：
**0xBA02A0 只是中间量，最终 MAC 才是进帧字段**，而现有实现停在中间量上。

---

## 4. 对「闭合第一档」的直接含义

要闭合 ⑤，服务端必须按上面链路**真正实现 keyed SHA1 MAC**，而这需要两个运行期量：

| 量 | 位置 | 现状 |
|---|---|---|
| 握手密钥 → key20 | `对象+0x620` → `0xBA02A0` | 观察器可导出（`--handshake-key-file`） |
| MAC 密钥材料 | `对象+0x328` | **未定位** |
| 报文/长度 | `[对象+0xB0]` / `[对象+0xAC]` | **未定位** |

三个量都在**同一个对象（0x85 处理器的 `edi`）**上——把它定位，
三处一次性拿到。这也是 SESSION 文档 §1.15 指出的"下一步唯一入口"。
