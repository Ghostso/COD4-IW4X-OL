分析对象：

## 核心结论（先看这个）

**本采集里不存在大厅连接。** 客户端发出到外部 `116.130.224.66:8000` 的是 **UDP**，
载荷以 ASCII `ur`（`75 72`）开头，是 IIPS 的“地址/外网地址发现”，不是大厅登录。

19.73 秒后属于 PID 19040 的出站流量只有三类：

1. UDP → `116.130.224.66:8000`（1 发 1 收，19.72–19.73s，IIPS 探测，随后立即关闭）
2. UDP → `239.255.255.250:1900`（SSDP 组播，本地服务发现）
3. UDP → `182.50.14.56:8081`（QoS 心跳，tqos.gamesafe.qq.com）

在这三者之外，pktmon 里所有 19.73 秒后的 TCP/UDP 目标都无法与游戏的 AFD 时间线对上，
属于其他进程（CEF、WeGame、浏览器、系统服务）的流量。

因此：**大厅服务地址目前的数据里没有出现过**，客户端根本没能寻址到大厅。

## 关于“后续大厅连接”的推断

错误 `[100]无法连接大厅服务` 的出现位置，正好在这三件事之后：

1. 19.72s IIPS 地址发现（拿到公网出口）
2. 19.75s SSDP
3. 之后只剩 QoS

也就是说，客户端在拿到公网地址后 **没有向任何大厅地址发起连接**。
最可能的解释有两种，本数据无法区分：

- 大厅地址来自某个上游接口（TCLS/Cross/IIPS 配置），本次采集里该接口没有返回可用地址；
- 或者返回了地址，但客户端判定无效而直接放弃。

要区分这两者，需要拿到大厅地址来源接口的明文载荷。

## 结论（10 行内）

1. 数据里没有大厅连接候选。
2. 客户端唯一主动外连的“疑似服务”是 `116.130.224.66:8000`，但它是 UDP `ur` 地址发现。
3. `42.187.183.203:14309` 是 IIPS 配置下发（含明文 INI），不是大厅。
4. 19.73s 后 PID 19040 只剩 SSDP 与 QoS 心跳。
5. 没有任何 TCP 连接 8000，也没有 lobby 语义端口。
6. 客户端不监听公网端口，只监听 127.0.0.1 的 CEF 回环。
7. pktmon 中其余流量几乎全可归因到其他进程。
8. 当前无法确定大厅地址来源，因为该接口没有返回可解析地址。
9. 要写服务器，下一步必须定位“大厅地址从哪来”，而不是猜端口。
10. 建议复查的方向：TCLS/Cross 返回体、IIPS 配置其它字段、游戏内硬编码域名。
