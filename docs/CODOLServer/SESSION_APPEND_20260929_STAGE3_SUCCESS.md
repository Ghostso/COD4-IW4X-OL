## 2. 修正一：不能在 0x81 之前改 5E8

此前把 `[req+0x5E8]` 预先写成 2，会导致：

```text
客户端处于 “等待 0x83” 状态
收到本应是握手第一步的 0x81
dispatcher 分支不匹配 -> 拒绝并关闭连接
638/63C 永远不写 -> 看似 0x81 处理器没执行
```

正确顺序是保持初始值：

```text
5E8=1 -> 收 0x81 -> 处理器执行并置 5E8=2 -> 收 0x82 -> 发 0x83
```

观察器新增 `--lobby-ready-only`：只在 `C8=2 && 5E8=1` 时通知探针，
不改写任何内存。

## 3. 修正二：0x83 的回显值来自运行期 5FC

`0x82` 帧尾部携带的字节与客户端保存到 `[req+0x5FC]` 的值不同：

```text
0x82 帧尾部候选 : 03 86 9a 92 1d 8c 6f eb
运行期 [5FC]    : f5 86 57 88 b6 f5 0b 2c
```

客户端在发送后会重写/派生该缓冲区，因此服务端不能从帧尾推断。

新增 echo 文件通道：

```text
观察器在 C8=2 && 5E8=2 时把 [req+0x5FC] 的 8 字节写成 hex 文件
探针收到 0x82 后等待该文件，再以这 8 字节构造 0x83
```

```text

⑤ 保活节奏     未开始
```

`0x83` 成功分支实际会调用 `0x7F9350`，也就是第二档入口线索；这在本次
运行中首次被触发。但第二档仍应在第一档 ④⑤ 闭合后再展开。

### 4.1 第④步的真实契约（本次新读出的反汇编）

opcode `0x85`（`0xBA3710`）**不是**简单的「读 u32 + 16B」：

```asm
BA398D..BA39D4   8 组逐字节 XOR，全部 OR 后必须为 0
                 => 要求帧内 8 字节 == [ebp-0x2C] 起解出的 8 字节
```

该 8 字节来自 `0xBA02A0`，一个固定查表 + XOR 的编解码器：

```text
固定表 (0xBA02C9..0xBA02E5, 20 字节):
  80 22 de aa  0b 1c 21 f4  00 ff ee 37  27 92 10 ce  aa f4 3c 21
索引表 (0xBA02EC..0xBA0366, 20 字节):
  13 12 09 04 11 01 0a 08 0d 02 0f 03 0c 05 07 00 0e 06 0b
主循环 (0xBA0375..0xBA03FA):
  4 轮，每轮 5 字节；dst[i] = table[idx[i]] XOR src[i]
```

因此 0x85 的 8 字节负载必须按该编解码推导，不能任意填充。

### 4.2 新发现：0x89 才是推进握手的帧

`0xBA3600`（opcode `0x89` 分支，要求 `[req+0x640] >= 0xDC`）会：

```asm
BA362F..BA3642  call 0xBA0FF0        ; 校验帧体
BA3651  [req+0xC8] = 1
BA3657  [req+0x644] = 2              ; 握手进度推进
BA3661  [req+0x5E8] = 0              ; 子状态复位
BA366B..BA3678  C73A20 / C738E0      ; 连接重建
BA36BB  call 0xC73900                ; 发起下一阶段连接
```

即 **opcode 0x89 负责重置子状态并发起第二次连接**，重要性高于 0x85。

opcode `0x87`（`0xBA3590`）另有分支：读 1 字节必须为 1，且要求
`[req+0x644] == 0`，随后调 `0xBA3010` 并置 `[req+0x644] = 1`。

### 4.3 第④步的正确表述（修正）

```text
0x85  读 u32 + 16B，并做 XOR 表校验；不通过则失败
0x87  读 1 字节(须为 1)，644 必须为 0 -> 置 644=1
0x89  要求 640 >= 0xDC，重置 5E8，发起第二次连接   <-- 真正的推进帧
```

### 4.4 0x84 分支实测

`0x84`（204 字节，单一 u32 值为 0）：

### 6.1 同连接续发 0x85 无效

已确证：`0x83` 通过后，客户端不再读取同一连接上的后续帧。


`0x83` 通过到 `C8=4` 仅 45 ms，期间背靠背发出的 `0x85`（204 字节）
没有产生任何状态变化。

### 6.2 magic=0xDC 假设被否证

曾假设把 `0x81` 魔数从 `0xD2` 改为 `0xDC` 可满足 `0x89` 的
`[req+0x640] >= 0xDC` 门限。实测 `640=220(0xDC)` 确实达标，但 `0x89`
分支仍未被触发。**该假设不成立。**

### 6.3 第④步的真实障碍是会话模型

`0xBA3600`（0x89 分支）的行为是：

```asm
BA3651  [req+0xC8] = 1
BA3661  [req+0x5E8] = 0
BA36C8  [req+0xC8] = 2
BA36BB  call 0xC73900      ; 发起新连接
```

即 0x89 是在**新连接**上推进，不是在原连接续发。因此
「同一连接上补发 0x85/0x84/0x89」这条路整体不成立。

下一步需要先确定：客户端在 `C8=4` 之后是否会自动重连、以及下一轮
何时开始。这与第⑤步（保活节奏）很可能是同一机制。

## 7. 第④步卡点精确到 `[req+0x644]`

重新核对 `0xBA4440` 的 `0x83` 分支后确认：`0x83` 处理器成功
（`5E8 := 3`、`5EC := 1`、`5F0 := 1`）只是必要条件，dispatcher 还会
继续检查 `[req+0x644]`：

```asm

BA456E  je   BA4463          ; 0x83 处理器失败 -> 直接返回失败
BA4574  mov  eax, [esi+0x644]
BA457A  test eax, eax
BA457C  jne  BA45DB
        ...                   ; 644==0：分配对象、调 0x7F9350、返回状态 4
BA45DB  cmp  eax, 3
BA45DE  jne  BA4463          ; 644 既不是 0 也不是 3 -> 返回失败、关连接
BA45E4  call 0xBA3E20        ; 644==3 才进入下一阶段处理
```

实测状态时间线（运行 `20260929_074152`）：

```text
36.436  c8=2  s9c=1  5e8=1  644=1   0x81 前
36.500  c8=2  s9c=4  5e8=1  644=1   0x81 处理器已执行（638/63C/640 命中）

36.579  c8=4  s9c=0  5e8=0  644=0   退出该轮
```

**`644` 在整个窗口内始终为 1，从未到 3。**因此：

```text

-> dispatcher 读 644 == 1
-> 既不等于 0 也不等于 3
-> 跳 BA4463 返回失败
-> C8=4，连接结束
```

这解释了为什么：

1. `0x83` 明明通过（`5E8=3`），连接仍然关闭；
2. 同一连接上补发 `0x85`/`0x84` 没有意义；
3. `magic=0xDC` 也无效：`644` 不受 `0x81` 魔数影响。

## 8. 第④步的真实触发路径（本轮新增）

### 8.1 `0xBA` 段内 `644 := 3` 的真实写入者

全镜像精确重扫 `0xBA0000..0xBB0000` 后，`644` 的唯一 `=3` 写入点是：

```asm
00BA324B  cmp dword [edi+0x644], 0
00BA3252  mov dword [edi+0x5E8], 1
00BA325C  je  short 0xBA3268
00BA325E  mov dword [edi+0x644], 3
```

它位于 `0xBA31xx` 这一族的「构造并发出一帧」流程尾部：

```text
0xBA3110..0xBA323D  构造帧并调用 0xBA2F20 入发送队列
0xBA3242  cmp [edi+0xC8], 2
0xBA324E  mov [edi+0x5E8], 1
0xBA325E  mov [edi+0x644], 3       ; 条件满足时
```

### 8.2 `0x87` 内层消息会触发这条路径

`0xBA3590`（opcode `0x87` 内层分支）要求：

```text
读 1 字节，必须 == 1
[req+0x644] 必须 == 0
-> call 0xBA3010
-> 若成功，[req+0x644] = 1
```

而 `0xBA3010` 内部会调用 `0xBA2A60` 构造并发送一帧（常量 `0x88`），
随后进入 `0xBA31xx` 的发送流程，最终在条件满足时执行
`[req+0x644] = 3`、`[req+0x5E8] = 1`。

因此在当前证据下，第④步的正确触发路径是：

```text
服务端发 0x85 外层帧
  内嵌 0x87 子消息（1 字节，值 1）
客户端调用 0xBA3010
客户端自行构造并发送 0x88 帧
该发送流程将 644 置 3、5E8 置 1
后续 0x83/dispatcher 才能继续
```

这也解释了两件事：

1. 从外部直接写 `644=3` 会被客户端在 `0x83` 处理中重置，因为它不是由
   客户端自己的发送流程产生的状态；
2. 单纯补发 `0x85`（全零）不会推进，因为外层 XOR 校验和 0x87 内层
   子消息都不满足。

## 12. `644` 语义最终确认（2026-09-29）

### 12.1 dispatcher 的三条出口（`0xBA4440`）

`0x83` 处理器返回后，dispatcher 按 `[req+0x644]` 分流：

```asm
BA456C  test al, al
BA456E  je   BA4463          ; 0x83 返回 0 -> 直接返回
BA4574  mov  eax, [esi+0x644]
BA457A  test eax, eax
BA457C  jne  BA45DB
BA457E  ...                  ; 644 == 0 -> 分配对象
BA45B2  call 0x7F9350        ; ★ 第二档入口
BA45CF  [out] = 4            ; 标记成功
BA45DB  cmp  eax, 3
BA45DE  jne  BA4463          ; 644 既非 0 也非 3 -> 返回
BA45E4  call 0xBA3E20        ; 644 == 3 -> 另一阶段
```

**`0x7F9350`（第二档入口）的触发条件是 `644 == 0`**，不是 3。

### 12.2 `0xBA3420` 是复位路径，不是触发点

`0xBA346A` 把 `644` 归零，但它属于错误复位函数：

```asm
BA3456  [esi+0xC8] = 4
BA3460  [esi+0x5E8] = 0
BA346A  [esi+0x644] = 0
BA349D  call 0xBA22E0        ; 清接收侧
BA34C6  call 0xBA22A0        ; 清发送侧
```

该函数有 23 个调用点（`0xBA2625`…`0xBA47AA`），全部位于错误分支。
因此 `644` 归零是**失败复位的副作用**，不能作为推进手段。

### 12.3 实测对照

```text

IFS1_ELEVATED_20260929_083322  644: 1 -> 0   结果 C8=4 结束
```

两种写入值结果相同，因为复位随后覆盖。外部写入无法在
dispatcher 读取前存活。

## 17. 复位点定位更正（2026-09-29）

### 17.1 `0xBA34D0` 的成败判定

`0xBA34D0`（`C8==2 && 5E8==3 && C0==0` 时的等待检查）：

```asm

BA3529  push &val(0)

BA3542  call 0xBA0AC0          ; 统计计数
BA3547  test edi, edi
BA3549  jns  BA356F            ; edi >= 0  -> 成功

BA354E  je   BA356F            ; edi == -2 -> 成功（无数据，继续等）
BA3561  call 0xBA3420          ; 其它负值 -> 复位
```

**`-2` 是约定的「暂无数据、继续等待」，不是失败。** 这与 `0x81` 侧

```text
1. 4 字节包没有改变结果
2. 复位原因不在 0xBA34D0 的 -2 判定
```

`0xBA34D0` 在无数据时应返回成功（edi == -2），因此真正触发复位的
调用者在别处，尚未定位。

## 18. 复位机制定位：`0xBA34D0` 的超时分支（2026-09-29，静态反汇编）

本轮放弃了「再加一个偏移 - 实跑」的循环，改为先把复位真正读透。
结论是**此前对复位点的判断错了两处**。

### 18.1 `0x7F9350` 不是「第二档入口」

```
7F9350  push ebp / mov ebp,esp
7F9356  mov eax,[esi]            ; esi = ecx = [req+0x63C]
7F935C  add eax,4 / push / call [0xCA8114]   ; COM AddRef
7F9378  mov eax,[ebp+8] / mov [esi],eax      ; 赋新值
7F9386  call [0xCA8128]                      ; 新对象 AddRef
7F938D  ret 4
```

这是一个 **COM 智能指针赋值函数**（Release 旧值 / 接管新值），
`ecx = [req+0x63C]`，参 8 = 新对象指针。它把 `[req+0x63C]` 从
「0x83 处理器写入的 0x11223344（非法指针）」改成合法对象。
**它不是阶段切换器，也不写 `0x644`。**

### 18.2 `644==0 / 644==1 / 644==3` 的真实含义

`0xBA4080` 的真实出口序列（`0xBA4114` 起）：

```asm
BA411A  call 0xC73900            ; 连接/读状态
BA411F  cmp  eax,1
BA4127  mov  [ebx+0xC8],2        ; ★ 传输up -> C8=2
BA412D  mov  [ebx+0x644],1       ; ★ 644=1   （由 C8=2 决定，非由任何入站帧）
BA4131  call 0xBA32A0            ; 通知
BA414B  cmp  eax,-2              ; 无数据 -> 继续等（成功）
BA417B  push 0x12 / call 0xBA3420  ; 其它负值 -> 复位
```

`0xBA32A0` 内部（`0xBA3315` 起）最关键的守卫：

```asm
BA3315  cmp byte [esi+0x90],0
BA331C  je  BA335C               ; 0x90==0 -> 什么都不做（安全）
BA3320  call 0xBA3100
BA3325  test al,al / jne BA335C
BA3331  ret 4                   ; ★ 0x90!=0 且 0xBA3100 失败 -> 直接返回，
                                ;   不触发 [esi+0x644]!=0 分支的虚调用
```

即：

```
[req+0x644]  == 0   只能由外部写入
[req+0x644]  == 1   传输已建立（C8=2），等待/处理入站帧 —— 正常态
[req+0x644]  == 3   0xBA4080 已把 {0x638,0x63C} 换出（0xBA417B/0xBA404E 之后）
```

**因此 `644=1` 不是错误、不是待清除的标记，而是「连接已就绪」的正值。**
观察器长期在 `C8==2` 时把 `644` 覆盖成 `0`，是在**持续性破坏一个正确的运行期值**。

### 18.3 31 ms 复位 = `0xBA34D0` 的「读结果 <= 0」分支

`0x7F9350` 被调用时 `esi=[req+0x644]`，而 `[req+0x644]` 是 `0`
（被覆盖），于是 `[esi+0x63C] = 0`。`0xBA34D0` 的判定：

```asm
BA3517  push 4 / push &val(0)
BA3522  lea ecx,[esi+0xC4]       ; ★ 读游标（不是「设备就绪」）
BA3539  call 0xC739E0           ; 读 4 字节
BA3539  -> edi = read result
BA3547  test edi,edi
BA3549  jns  BA356F              ; edi >= 0  -> 成功
BA354B  cmp  edi,-2
BA354E  je   BA356F              ; edi == -2 -> 成功（暂无数据）
BA3561  call 0xBA3420            ; ★ 其它负值（-1/-7 等）-> 复位
```

结合 §18.2 的返回值枚举：

```
edi == -2   无数据，继续等        -> OK
edi >= 0    读到 N 字节           -> OK
edi == -1   「无数据」           -> 复位（-1 的语义是失败，不是暂空）
edi == -7   「连接关闭」         -> 复位
```

**`[req+0xC4]` 是读游标。** `0x83` 帧被消费后游标停在帧尾，
随后 `0xC739E0` 在空读游标上返回 **`-1`**（不是 `-2`），
遂在约 1–2 个泵周期（实测 31 ms）后复位。这解释了复位时刻与
「是否再发 4 字节包」无关的既有实测。

### 18.4 已否证的既有推测

```
1. 0xDE7C18 是 30.0（不是 31ms）。该分支是 30 秒上限，本轮 31ms 复位无关。
2. 0x83 handler 写的 0x638=0x11223344 / 0x63C=0x11223344 是垃圾指针；
   但 [req+0x644] 是 0 时 0xBA32A0 走 je 0xBA335C 早退，
   不会对该垃圾指针解引用 —— 故不是崩溃源，也不能解释复位。
3. 「探针在 0x83 后关闭连接导致 31ms 复位」——探针本来就在 recv 中阻塞，
   并未关闭；且 §18.3 的复位与 socket 状态无关。
```

### 18.5 尚未闭合的可能归因（未验证，勿当结论）

```
a) 0x83 handler 同时写了 [req+0x5EC]=1 / [req+0x5F0]=1。
   0xBA2A60 在 [ebx+0x644]==0 分支（BA2AC0..BA2B58）里直接 ack 并把
   入站对象 push 进 [ebx+0x6D0] 队列。
   -> [0x5EC]/[0x5F0] 这对「抑制 ack」标志可能就是抑制 0xAB ack 的原因，
      从而让对端（本探针）不再收到任何 0x86/0xAB 交互。
b) 0xBA4080 在 [ebx+0x644]!=0 时对 {[ebx+0x638],[ebx+0x63C]} 所持对象
   做虚调用（BA40E0 区域）。0x83 handler 写入的 0x11223344 在 644!=0
   时会被真的解引用。这需要单独一轮静态确认。
```

```
③ 0x83 校验           已闭合（5E8=3, 5EC=1, 5F0=1）
```

```text
46 ms 后收到对端关闭（RST）
```

客户端在握手成功后**没有向本探针发送任何字节**。§18 里从
`0xBA3E20 -> 0xBA2A60(op=0x86)`、`0xBA3370 -> 0xBA2A60(op=0x86)` 推出的
「客户端会发 0x86」在**本路径上没有发生**。

### 19.4 假设三：复位是「服务端把 socket 关掉」造成 —— 证伪（决定性）

复现窗口内直接读客户端读入器游标（`req+0xB0` = reader）：

```text
reader +0x1C  buffer base = 0x39CAEEA8
reader +0x10  read  cursor = 0x39CAEEC7   (= base + 0x1F)
reader +0x14  write cursor = 0x39CAEEC7   (= base + 0x1F)
```

**读游标 == 写游标**：`0x83` 帧被完整消费后，缓冲区已**排空**，
没有任何「未消费的剩余字节数」去满足 0x83 里携带的长度字段。

→ 3 字节内容不构成 `.text` 修改。**是客户端在收到完整、合法、校验通过的
0x83 后主动关闭连接**，与探针是否关闭无关（探针当时正阻塞在 recv）。

### 19.5 因此第 ④ 步的真实形态

```text
0x83 校验通过 -> 5E8=3（已确证）
下一个动作必然要求一次「客户端发起」的客户端->服务端消息
  （0xBA2A60 在 644==0 分支只回头（ack）入站对象；
   只有 644==3 分支才是客户端自发的 0x86 发送）
而该客户端发起动作在本环境下从未发生 -> 32 ms 后关闭
```

注意：`0x83` handler（`0xBA3BA0`）只写 `5E8` 与 `5EC`/`5F0`，**不写 `644`**。
现有静态推断里没有任何一条能把 `0x83` 校验成功直接推到「发送 `0x86`」，
说明这条边落在尚未找到的第三处代码上。

## 20. 推翻 §3.6：dispatcher 的真实形状与「握手后必死」的根因

本轮把 `[req+0x644]` / `[req+0x640]` / `[req+0x5E8]` 的全部访问点扫了出来，
结论是**手册第 3.6 节的分发表是错的**，而且 0x83 之后必死的根因不在 0x83。

### 20.1 真实的三分支判据是 `644`，不是 `5E8`

```asm
BA44E8  mov eax,[esi+0x5E8]        ; 只用于 BA44EE 的 cmp eax,1 一次
BA44EE  cmp eax,1
BA44F1  jne  BA454B
BA44F6  cmp al,0x81 / jne BA450C   ; 5E8==1: 只接受 0x81
BA450C  cmp al,4    -> 复位
BA454B  cmp eax,2 / jne BA46A2
BA4557  cmp al,0x83 / jne BA45F0   ; 5E8==2: 0x83 -> BA3BA0；0x84 -> BA0E20
BA46A2  cmp eax,3 / jne BA4781
BA46AE  cmp al,0x85                ; 5E8==3: 0x85 -> BA3710；0x84 -> BA0E20
```

即 `5E8` 只是「当前期望哪个 opcode」的过滤器。真正决定**下一步**的是
`BA4574: mov eax,[esi+0x644]`：

```text
0x83 校验通过 且 644 == 0 -> BA457E..BA45B2: call 0x7F9350（COM 赋值），[out]=4
0x83 校验通过 且 644 == 1 -> BA45DB: cmp eax,3 -> 否 -> BA4463: return 0
0x83 校验通过 且 644 == 3 -> BA45E4: call 0xBA3E20
```

**`644==1` 时 0x83 分支直接 `return 0`。** 这就是 31 ms 复位的入口：
返回 0 → 泵 `0xBA24C0` 侧放弃 → 复位。

### 20.2 但真正的「必死」在 0x83 之前：`0xC8` 魔数门

`0xBA3BA0` 的函数头有一条此前完全遗漏的守卫：

```asm
BA3B2A  call 0xBA3600              ; <- 由 opcode 0x89 / 0x87 触发

BA360D  cmp dword ptr [ebx+0x644], 1
BA3613  je  BA362F                 ; 必须恰好 644 == 1
BA3621  call 0xBA3420              ; ★ 否则直接复位（return 0）
BA362F  ... call 0xBA0FF0 ...
BA3651  mov dword ptr [ebx+0xC8], 1
BA3657  mov dword ptr [ebx+0x644], 2   ; ★ 644 = 2
BA3661  mov dword ptr [ebx+0x5E8], 0
BA366B  call 0xC73A20                  ; 重置读游标
```

而 `0xBA3590`（`644 != 0` 时的另一条 0x87 路径）里：

```asm
BA35D7  cmp dword ptr [esi+0x644], 0
BA35DE  jne BA35C3                 ; 644 != 0 -> 复位
BA35E2  call 0xBA3010              ; ★ 发 0xC8 魔数帧（644 必须 == 0）
BA35EB  mov dword ptr [esi+0x644], ebx   ; ebx = 1
```

`0xBA3010` 发出的帧内容（`0xBA319B..0xBA31F0`）：

```text
u32 0xC8
u32 0xC8
u32 0xD2
u32 0xDC
u32 0x08, u16 ?, u32 0xD4B1C7E9
8B at [edi+0x5F4]
```
（与探针实际收到的首个 28 字节**完全同形**，只是长度/尾部不同。）

### 20.3 被遗漏的门：`[req+0x640] >= 0xDC`

`0xBA3BA0` 里 opcode 0x87 / 0x89 的入口守卫（`0xBA3AE0` 区域）：

```asm
BA3AE6  cmp cl,0x87 / jne BA3B0E
BA3AEB  cmp dword ptr [edi+0x640], 0xDC
BA3AF5  jb  BA3B36                 ; ★ 0x640 < 0xDC -> 整帧被丢弃！
BA3B02  call 0xBA3590

BA3B0E  cmp cl,0x89 / jne BA3B36
BA3B13  cmp dword ptr [edi+0x640], 0xDC
BA3B1D  jb  BA3B36                 ; ★ 同样丢弃
BA3B2A  call 0xBA3600
```

`[req+0x640]` 的唯一非零写入点是 `0xBA3D53`（`0xBA3BA0` 内部）。
也就是说：**握手帧 `0x87`/`0x89` 只有在 `0xBA3BA0` 已经被调用过一次
（从而把 `0x640` 置为 `0xDC`）之后才会被处理。**

### 20.4 由此得到完整的真实协议（全部来自反汇编）

```text
0x81         -> 5E8=2            （已确证）
0x83         -> 5E8=3, 5EC=1, 5F0=1
              且 644==1 时 dispatcher 直接 return 0   <- 卡点
0x84         -> 经 0xBA0E20 调用 0xBA3BA0
                 首帧把 [req+0x640] 置 0xDC（=220）
                 此后 0x87/0x89 才被接受
0x89 + 640>=0xDC -> call 0xBA3600
                 要求 644==1 -> 置 C8=1, 644=2, 5E8=0, 重置读游标
0x87 + 640>=0xDC -> call 0xBA3590
                 要求 644==0 -> 发 0xC8 魔数帧, 置 644=1
```

**`0x640` 的实际取值 = 客户端在首帧里收到的 body 长度。**
探针目前发的是 `u32 frame_len = 0xC8 = 200`。若该长度被原样读入
`[req+0x640]`，则 `0xC8 (200) < 0xDC (220)` 始终成立，
`0x87`/`0x89` 永远被丢弃 —— 这正好解释「0x83 之后客户端无论如何都死」。

### 20.5 本轮待验证预测（优先级最高）

```text

期望：
  a) [req+0x640] 从 0xC8 变成 >= 0xDC
  b) 客户端不再在 32 ms 内复位
  c) 0xBA3BA0 被 0x84 再次调用后，握手继续推进
注意：探针早期实验曾试过 --frame-len 196，方向相反，故无结论。
```

## 21. `[req+0x640]` 解密：它就是 0x81 的魔数，只有 `0xDC` 才能开门

### 21.1 17 行 `0x83` 处理器（`0xBA3BA0`）

```asm

BA3C0B  lea eax,[esi+0x5FC]
BA3C12  call 0xB73FE0              ; memcmp(this+0x5FC, recv8, 8)
BA3C1A  test eax,eax / jne BA3C62  ; 不等 -> 错误 0x03 -> 复位

BA3C1E  lea ebx,[eax+1]            ; ebx = 1
BA3C21  cmp [esi+0x644], eax       ; 与 0 比较
BA3C27  jne BA3C38

BA3C30  call 0x8435D0              ; ★ 纯诊断，无副作用
```

`0xBA3D53` 从来不是它执行的 —— `0x640` 的写入只发生在 `0x0x81` 处理器
（`0xBA3C70`）里。

### 21.2 `0x81` 处理器里的魔数校验（`0xBA3D35`）

```asm
BA3D41  jb  BA3DBF                 ; < 0xD2 -> 错误 7 -> 复位

BA3D49  ja  BA3DBF                 ; > 0xDC -> 错误 7 -> 复位
BA3D53  mov [esi+0x640], ebx       ; ★ 640 = 0x81 的魔数
```

### 21.3 被遗漏的门（`0xBA3AE0` 区域）

```asm
BA3B2A  call 0xBA3600
```

两处都要求 `[req+0x640] >= 0xDC`，而 `0x640` 的取值范围是 `[0xD2,0xDC]`。

## 23. 0x84 / 0x89 / 0xC8 续帧序列：实跑证伪，并定位到下一处阻塞

### 23.1 本轮实跑（`IFS1_ELEVATED_20260929_123835`）

探针参数：`--magic 0xDC --seq-after-83 84,89,c8 --hold-after-83 25`

```text
37.225  s9c=0 5e8=2 640=220
37.257  s9c=4 5e8=3 5ec=1 5f0=1 640=220   <- 0x83 通过
37.258  POST83_SAMPLE  s9c=4 5e8=3 644=1
        sent_seq 84   (204B, opcode 0x84)
        sent_seq 89   (204B, opcode 0x89)   <- 客户端在 89 到达前已断
        hold_recv_error  WinError 10054
37.302  c8=4 5e8=0 644=0
```

探针在 0x83 后 **+63 ms** 才发出 0x89（`0x84` 与 `0x89` 之间
`time.sleep(0.03)`，加上 `sendall` 开销），而客户端在 +45 ms 已经断连。

**证伪（本轮）**：`0x84 / 0x89 / 0xC8` 续帧序列单独不足以救活连接，
主因是**送出太晚**，不是帧内容。

### 23.2 客户端真实首帧的重解（关键）

客户端连上大厅后送出的第一个 28 字节：

```text
c8 00 00 00 | c8 00 00 00 | d2 00 00 00 | dc 00 00 00 | 00 00 08 00 ...
```

按 `[0:4] = u32` 解读：

```text
[0:4]  u32 = 200 (0xC8)   <- 帧总长 200，不是「魔数」
[4:8]  u32 = 0xC8
[8:12] u32 = 0xD2
[12:16] u32 = 0xDC
[16:20] u16/u16 = 0x0000 / 0x0008
```

即**客户端真正的首帧是「u32 长度(200) + 一段大端/小端混合的 magic 组」**，
而不是之前假设的「u32 魔数」。28 字节只是这个 200 字节帧的最前面一段。
探针此前发的是 `c8 00 00 00 | 00 | 81 | d2 00 00 00 | u64 | ...`，
结构上完全不同 —— 之所以能通过，是因为 0x81 处理器只按
「u32 魔数 + u64 token + 8B」解析，并不要求整帧等于客户端那 200 字节。

**尚未解释**：客户端首帧 [4:8] 的 `0xC8`（=200）从何而来、
以及 200 字节帧剩下的 164 字节内容。这很可能是 ④ 真正的阻塞点。

### 23.3 本轮净收益

```text

2. 只有 magic == 0xDC 才满足 640 >= 0xDC 的门 —— 已证实
3. 0x83 之后客户端的下一步在 0xBA3600（0x89）或 0xBA3590（0x87），
   两者都要求 [req+0x640] >= 0xDC
4. 续帧必须在 0x83 后 **< 40 ms** 内送达（客户端 45 ms 断连）
5. 客户端真实首帧是 u32 len=200 的 200 字节帧，非 28 字节魔数包
```

## 24. 32 ms 复位：排除超时，锁定「待发消息从未发出」

### 24.1 合帧实跑（`IFS1_ELEVATED_20260929_124635`）—— 证伪

把 `0x83 + 0x84 + 0x89` 合成**同一个 612 字节 TCP 段**一次 `sendall`
（`lobby_plain_probe.py` 已改：`--seq-after-83` 现与 0x83 同段发送）：

```text
37.389  s9c=4 5e8=3 5ec=1 5f0=1 640=220
37.391  POST83_SAMPLE  s9c=4 5e8=3 644=1
37.421  c8=4 5e8=0 644=0      <- 仍是 32 ms
```

**证伪**：`0x84`/`0x89` 即使与 0x83 同段到达，客户端也不处理它们。
它读完 0x83、置 `5E8=3`、`return 0`，然后直接放弃连接，
缓冲区里剩下的 0x84/0x89 从未被解析。

### 24.2 `[req+0xAE0]` 不是 32 ms —— 超时假设全部排除

```asm
BA29C3  fld  dword ptr [0xDBE6CC]
BA29CA  fstp dword ptr [esi+0xAE0]
```

`[0xDBE6CC] = 0x41F00000 = 30.0f`。`[req+0x508]` 的比较基
`[0xDE7C18]` 同样是 `30.0`。

→ 泵里两个时间分支（`BA2646` 比 30.0、`BA2670` 比 `[req+0xAE0]`=30.0）
**都是 30 秒上限**。32 ms 复位与超时无关。

### 24.3 决定性采样：`b8=0 c0=0 6d8=1`

给观察器 `POST83_SAMPLE` 增加 `[req+0xB8]`（待发链表头）、
`[req+0xC0]`（计数）、`[req+0x6D8]`（`0x6D0` 任务表计数）后实跑
（`IFS1_ELEVATED_20260929_125147`）：

```text
38.371  POST83_SAMPLE  s9c=4 5e8=3 644=1 a8=0 ac=200 b8=0 c0=0 6d8=1
38.401  POST83_SAMPLE  s9c=0 5e8=0 644=0 a8=0 ac=200 b8=0 c0=0 6d8=0
```

解读：

```text
[req+0xB8]=0 且 [req+0xC0]=0  -> 泵的 B8 链表是空的，
                                  所以 BA254D..BA26B9 那段（含 BA2625 复位）
                                  根本没有执行
[req+0x6D8]=1                 -> 0x6D0 任务表里有且仅有 1 条待发消息
复位后 6d8=0                   -> 由 0xBA3420（BA3497）清零
```

### 24.4 32 ms 复位的原因（收敛后的结论）

```text
客户端在 5E8=3 时手上已经有一条待发消息（6d8=1），
但 dispatcher 的 0x83 分支因为 644==1 走了 BA45DB -> BA4463
（return 0 = 未消费），泵随后调用 0xBA3420：
  清 C8=4 / 5E8=0 / 644=0，并把 6d8 清零（消息被丢弃）
```

即：**不是超时、不是缓冲区没数据、不是服务端关连接，
而是一条本应发出的消息被 644==1 卡住后随复位一起丢弃。**

`0x83` 处理器只读 `[req+0x644]`（`BA3C21`），不写它；`0xBA4080`
在连接建立时把它写成 `1`。因此 644 由 `1 -> 2/3` 只能靠
`0xBA32A0(arg)`：`arg=1` 只在 `0xBA3590`（opcode 0x87）与
`0xBA3E20`（644==3）路径里出现，两条都需要客户端先处理一个
`[req+0x640] >= 0xDC` 的入站帧 —— 而那个入站帧就是服务端要发的。

### 24.5 已确证 / 已证伪（累计到本轮）

```text
已确证
  [req+0x640] = 0x81 的 magic，域 [0xD2,0xDC]；只有 0xDC 开门（640=220 实跑）
  0x83 处理器只写 5E8=3 / 5EC=1 / 5F0=1，只读 644、640
  0xBA3420 = 复位原语：C8=4, 5E8=0, 644=0, 清 6d0/6d4/6d8, 清读游标
  32 ms 复位时 b8=0, c0=0, 6d8=1 -> 复位前有一条待发消息
  两个时间分支都是 30.0 秒

已证伪
  624 行 frame_len（0xC8/0xDC/196）影响握手
  0x84 / 0x89 单独或与 0x83 同段发送可以推进
  探针关连接导致复位

```

## 28. 复核 §4.6 时发现：`644=1` 一直是观察器注入的（2026-09-29）

编写第二版交接手册、逐条复核 `[req+0x644]` 写入表时发现本轮全部实跑

### 28.1 全镜像扫描（严谨版，修正了此前的 off-by-one）

对 `+0x644` 的**寄存器源写**：

```text
00BA299C   = 0（构造）
00BA35EB   = 1，在 0xBA3590 内部，进入时要求 644==0
```

**没有任何 `mov dword [reg+0x644], 1` 的立即数写。**

```text

写 [mgr+0x4F8] = 1
输出 POKE_LOBBY_COMPLETE  mgreq644=1 mgr4f8=1
```

本项目**每一轮**打到 `5E8=3` 的运行都带这个 poke
（标准命令里就有 `--poke-lobby-globals`）。

### 28.3 由此产生的更正

```text
· 旧报告 §19 的「644 保持 1（客户端自己写）」是错的
  —— 那是观察器写的
· 644=1 是「0x87 已被处理」的下游状态（0xBA3590 -> 0xBA35EB）
· 客户端自然状态应当是 644=0（构造初值 0xBA299C）
· 观察器把 644 从 0 强推到 1，恰好把 0x83 分支推入
  BA45DB -> BA4463（return 0），也就是本项目观测到的卡点
```

### 28.4 待验证的可证伪预测（优先级最高）

```text
观察器 --poke-lobby-globals 拆成两半：
  保留 host/port 全局填充
  去掉 [req+0x644]=1 与 [mgr+0x4F8]=1
预测：644 保持 0 -> 0x83 走 BA457E..BA45B2（COM 赋值 + [out]=4）
      而非 BA45DB -> BA4463 -> 复位
```

### 28.5 教训（写进手册 §12.5）

```text

  2. 644:=1（延续至今，本轮才定位）
```

## 30. 后续两条候选路径的静态否证（2026-09-29 续）

第 29 节把阻塞点从「32 ms 复位」推进到「客户端主动 0x85 分片 +
约 47 秒保活」。本轮不再做猜测式实跑，先把两条候选路径在反汇编上查清。

### 30.1 不能向客户端补发服务端 opcode 0x85

`0xBA3710` 是 dispatcher 在 `5E8==3` 时消费**服务端入站** `0x85` 的处理函数。
它在函数体前段有一条一次性闸门：

```asm
BA3844  mov eax, [edi + 0x5ec]
BA384A  lea edx, [eax + 1]
BA384D  mov [edi + 0x5ec], edx
BA3853  cmp [ebp - 0x394], eax      ; [ebp-0x394] 在 BA3A1E 被置 0
BA3859  je  BA38A4                  ; 旧值 == 0 -> 继续解析这一帧
BA387F  call 0xBA3420               ; 否则复位
```

而 `0x83` 成功时 `0xBA3C3B` 已经把 `5EC` 置 1。也就是说 **`0x83` 成功之后，
任何入站 `0x85` 都会走进 `BA387F` 复位**。此前把「服务端补发 0x85」列为
可行方向，与这条闸门直接冲突，予以否证。

保留第 29 节的观察：客户端自己发出的 `AB 85` 是**出站**方向，走的是
`0xBA2A60` 的构造路径（`BA2C1A` 写 opcode 0x85，`BA2EA0` 入队列），
与 `0xBA3710` 的入站校验不是同一条路径，两者不可混用。

### 30.2 队列响应里的 next_poll_after：有消费，但不是当前断线来源

队列响应模型里有三个排队字段：

```text
next_poll_after
estimated_wait_time
member_position
```

在解密镜像里逐个查字符串引用，只有一处：

```text
00D5A770  "next_poll_after"      ref 0x00BA9C0F
00D5A780  "estimated_wait_time"  ref 0x00BA9BFB
00D5A794  "member_position"      ref 0x00BA9BD5
```

三条引用全部在同一个解析器 `0xBA9BC0` 内，且该解析器只被 `0xB98480` 调用：

```asm
00B98480  call 0xBA9BC0            ; 解析队列响应 JSON
```

`0xBA9BC0` 的落地是：

```asm
BA9C1E  mov ecx, [ebp - 8]         ; member_position
BA9C21  mov edx, [ebp - 0x10]      ; estimated_wait_time
BA9C24  mov [esi + 4], ecx         ; -> [objC+0x248]
BA9C27  mov ecx, [ebp - 0x18]      ; next_poll_after
BA9C2B  mov [esi + 8], edx         ; -> [objC+0x24C]
BA9C2E  mov [esi + 0xc], ecx       ; -> [objC+0x250]
```

`next_poll_after` 确实会被消费，但消费点不在 `B9/BAA` 队列模块内部，而在
上层大厅检查函数 `0x7F31E1..0x7F3241`：

```asm
7F31E3  call 0xB98390              ; return [objC+0x240] (queue state)
7F31EA  mov edi, eax
7F31EC  call 0xB983A0              ; return &objC[0x244]
7F31F1  mov ecx, edi
7F31F3  dec ecx / je 0x7F3209      ; state == 1 -> poll branch
7F31F6  dec ecx / jne 0x7F3246     ; state != 2 -> return
7F31FA  mov [0x84ABA60], 9         ; state == 2 -> sub_state=9 (success)

7F3209  mov eax, [eax + 0xc]       ; state == 1: next_poll_after
7F3224  call 0xB75DA0              ; 0xE3EC980 timer
7F323A  call [esi + 0x10]          ; retry the queue operation
7F3241  call 0xB75D80              ; reset timer
```

所以 `next_poll_after` 只在队列对象状态 **1（排队中）** 时决定重轮询；
当前 709 字节响应通过票据校验后走 `B98620 -> [objC+0x240]=2`，直接进入
`sub_state=9` 的成功分支，不经过 `7F3209`。
`estimated_wait_time` 与 `member_position` 仍只落在 `objC+0x24C/0x248`，
没有看到独立消费者。

同时看 `0xB983F0`（队列响应 → `[objC+0x1400]` 的判定函数）的成功路径：

```asm
B98442  cmp eax, 0xC8 / jne B9865E  ; 只要求 HTTP 200
B984B2  push 0xD5A114               ; "iv_seed"
B984CD  push 0xD5A0FC               ; "lsg_server_ticket_size"
B9852B  push 0xD5A0E8               ; "lsg_server_ticket"
B98620  mov [esi+0x240], 2          ; 全通过 -> 状态 2
```

即 0xB983F0 的成功判定只看 **HTTP 200 + iv_seed + lsg_server_ticket_size +
lsg_server_ticket**；`next_poll_after` 由上层在状态 1 时另行消费。

### 30.3 因此下一步不应改队列数值

```text
已否证  向客户端补发服务端 0x85（被 5EC 闸门复位）
当前无效  调大 next_poll_after（本次响应走状态 2，不进状态 1 的重轮询分支）
```

客户端约 52 秒后的 `DELETE /queue` 与「与大厅服务失去连接」因此不是
`next_poll_after` 的问题。继续推进前要先定位：`0x83` 成功后客户端那批 `AB 85` 出站分片
期待的服务端回应落在哪条连接上（8446 明文大厅，还是 8443 HTTPS 队列），
这需要下一轮的通道级观测，而不是继续修改现有响应字段。

## 33. 突破：52 秒断线的因果方向被倒置了 —— DELETE /queue 是**结果**，不是原因

前几轮把「约 47–52 秒后客户端仍会 DELETE /queue 并弹大厅断线」当作一个
复合现象记录，隐含假设是「DELETE 是断线的触发」。本节用两条独立时钟
把时序对齐后证明：**DELETE 发生在弹窗之后约 1 毫秒，它是断线后的清理，
不是断线的原因。**

### 33.1 两个时钟的对齐方法

```text
观察器事件 CSV 用相对秒 t（相对 observer 启动）
探针 plain.jsonl / probe.jsonl 用 unix ts

对齐锚点：observer 的 LOBBY_5E8_READY 事件发生在 ready.flag 落盘时，
探针在同一时刻记录 ready_seen。

  observer t = 38.089  (LOBBY_5E8_READY)
  probe  unix = 1790659863.357  (ready_seen)

  => unix = 1790659825.268 + t_obs
```

### 33.2 对齐后的完整时序（`IFS1_ELEVATED_20260929_133024`）

```text
t_obs    事件                                         来源
----------------------------------------------------------------------
38.182   0x83 成功  5e8=3 5ec=1 5f0=1  644=0         观察器 CODEC_TRANSITION
38.183   POST83_SAMPLE  无 32ms 复位                  观察器
38.1xx   客户端连上 8446，开始发 0x85 分片             AFD ETW (端口 65397)
85.120   uA50=5  DWLOBBY_PUMP_SUCCESS                观察器 state.csv
90.113   lob240: 2 -> 3   （大厅对象被标记断开）      观察器 state.csv
90.163   WINDOW_NEW #32770 「致命错误」                观察器 events.csv
90.164   DLG_CHILD  Static =「与大厅服务失去连接」     观察器 events.csv
90.105   sni  127.0.0.1:65469   （TLS 重新握手）       探针 probe.jsonl
90.137   tls_ok                                        探针
90.167   DELETE /v1.0/title/.../queue/0/member/...     探针 http
90.168   queue_request  => 709 B 响应                    探针
```

**关键点：TLS 握手起点（90.105）和 http 请求（90.167）都晚于
`lob240=3`（90.113）与弹窗（90.163）。** 客户端是在判定大厅断开之后
才去发 DELETE 把自己从队列里摘掉。

`lob_http_state` 在 t=90.113 出现的 `3 -> 5 -> 200` 抖动，也不是
「DELETE 的响应」——它比 DELETE 请求早 54 ms，是同一时刻大厅对象
自身的状态翻转被采样到。

### 33.3 52 秒是可复现的固定值

```text
run                              handshake    dialog     delta
IFS1_ELEVATED_20260929_133024    38.183       90.164     51.98 s
IFS1_ELEVATED_20260929_142730    37.386       89.383     52.00 s
```

两次干净运行（一次基线、一次周期 4 字节保活）都是 **52.0 秒**。
固定值说明这是一个**看门狗超时**，不是随机断链。

### 33.4 看门狗的输入是「大厅明文 socket 上没有**新的**可解业务帧」

**先纠正一个容易犯的错**：AFD ETW 显示客户端在 8446 上确实收到了
握手期间的两条 204 字节帧（t=39.581 recv 199+4+1、t=39.615 recv 199+4+1，
即 `0x81` 与 `0x83`）。所以「客户端只发不收」是错的。

真正的问题是**握手之后就再无任何入站帧**：

```text
8446 连接（endpoint #3）上的 recv 只发生在 39.581 / 39.615 两次；
此后直到 101.574 关闭，recv 事件为 0（send 有 69.6 / 86.5 若干次）。
探针侧同一时刻起是 hold + recv_timeout，从未再发帧。
```

再看 `§22.3` 的收帧契约（`0xBA20A0` + `0xB9BB90`）：该取帧器按
「类型字节 + 位打包负载」解析，而 `0x81` / `0x83` 这两条帧的长度字段
是 200/204 但**负载是魔数与 token 的定长结构，不是位打包业务帧**，
因此

```text
可用长度 = [0x1c] - [0x24] + 0x1f = 28 - 31 + 31 = 28
```

`0xBA20A0` 的取帧返回 `edi <= 0` —— **一条业务帧都没有被解出**。
客户端在「连接已建立、但服务端不再发帧」的状态下等满 52 秒后判死。

### 33.5 这解释了 `644=1` 旧运行里「弹窗推到 84–89」的现象

旧运行（如 `IFS1_ELEVATED_20260928_183320`，130 秒）在
`644=1` + 观察器 `poke` 下，弹窗落在 t≈89，与干净运行的 t≈90
其实是**同一个 52 秒看门狗**（相对握手时刻）。当时把它记成
「弹窗推迟」是采样口径差异，不是 `644=1` 带来的收益。

### 33.6 结论：剩余缺口收敛为一条，且与 `644` 无关

```text
已闭合   ① 0x81 魔数门（magic=0xDC）
         ② 收客户端 0x82
         ③ 发 0x83 回显（5e8=3 / 5ec=1 / 5f0=1）
         ④ 0x83 -> 644==0 分支通过（无 32 ms 复位）
         ⑤ 大厅对象校验通过（lob1400=8900 / lob240=2 / uA50=5）

唯一缺口 服务端必须在握手后持续发出「客户端可解的业务帧」，
         否则客户端在本连接闲置满 52.0 秒时触发看门狗，
         标记大厅断开（lob240=3）-> 弹窗 -> DELETE /queue 自我清理。

DELETE /queue 不是要解决的问题；它会在正确发帧后自行消失。
```

### 33.7 方法教训（与 §8.1 同类）

```text
把两个并发现象按「谁先谁后」猜错，会造出一个不存在的复合 bug。
本节的正解来自「先对齐两个时钟，再排事件」，而不是先假设因果。
今后遇到「A 之后 B 也发生」，先用独立时钟锚点验证 A 与 B 的先后，
再决定是否把它们当成一条因果链。
```

### 33.9 静态补充：入站帧读取器的确切形状（下一步的直接线索）

`0xBA20A0` 是客户端大厅泵里唯一读入站帧的函数
（唯一调用点 `0xBA42B9`，位于 `0xBA4250` 起的泵循环内）。它先
`recv(1)` 只取一个**类型字节**，再据此决定帧头长度：

```asm
BA20CA  push 1 / lea edi,[esi+0xa8] / lea ecx,[esi+0xc4]
BA20D9  call 0xC73A00          ; recv 1 字节 -> [esi+0xa8]（类型字节）
BA20E1  test eax,eax / jle 0xBA2289   ; 读不到 -> 返回 <=0
BA20E9  mov al,[edi]
BA20EB  mov ebx,1               ; 默认帧头 1 字节
BA20F0  cmp al,1  / je 0xBA20F8
BA20F4  cmp al,2  / jne 0xBA20FD
BA20F8  mov ebx,9               ; 类型 1/2 -> 帧头 9 字节
BA20FD  push 0x2c / lea edi,[ebx+1] / call 0xB74220   ; 分配帧缓冲
BA2118  mov ecx,[esi+0xac] / sub ecx,edi / call 0xB9BEB0
...
BA227C  mov eax,[ebp-0x1c]
BA227F  mov dword ptr [esi+0x9c],3   ; 注意：这是 [req+0x9C]，不是 [req+0xC8]
```

要点：

```text
· 帧类型字节 ∈ {1,2} -> 9 字节帧头；其它 -> 1 字节帧头。
  —— 我们发的 0x81/0x83 帧类型字节是 0x00，因此走「1 字节帧头」。
· 0xBA227F 写的是 [esi+0x9C]=3，与 §4.x 里「[req+0x9C] 表示子状态」一致；
  它不写 [req+0xC8]，所以这条读帧路径不会触发 32 ms 复位。
· 客户端在 0x83 之后唯一「活着」的读帧点就是这里；服务端只要让
  0xBA20A0 返回 >0（即送达一条结构合法的位打包帧），看门狗就不会到点。
```

这是下一步「构造服务端可解首帧」最直接的静态入口：先确定
客户端希望的类型字节（1 还是 2）与 9 字节头部布局，再按 §22.4 的
5 位字段编码填充 >=200B 负载。

## 34. 入站帧的精确比特布局（已从反汇编推出，可直接实现）

§33.9 给出了入口，本节把它拆到字节/比特级。**结论：服务端只要能构造
一条「前缀帧」并持续发送，就能让 `0xBA20A0` 返回 >0，看门狗不再到点。**

### 34.1 位读取原语 `0xB78350` 的真实签名与语义

```asm
B78350  push ebp / mov ebp,esp
B78353  cmp dword ptr [ebp+8], 0        ; [ebp+8]  = 源缓冲指针
B78357  mov edx,[ebp+0x14]              ; [ebp+0x14] = 输出「已消费位数」
B7835B  mov esi,[ebp+0x10]              ; [ebp+0x10] = 已消费比特偏移 bitpos
B7835F  mov edi,[ebp+0x1c]              ; [ebp+0x1c] = 要消费的位宽 bits
B78362  lea ecx,[esi+edi]               ; 新偏移
B78367  mov [edx], ecx                  ; *out = bitpos + bits
B78369  je  0xB783AF                    ; 源指针空 -> 直接返回
B7836B  cmp dword ptr [ebp+0x18], 0     ; [ebp+0x18] = 目标指针
B7836F  je  0xB783AF                    ; 目标空 -> 直接返回
B78371  mov eax,[ebp+0xc]               ; [ebp+0xc]  = 缓冲的结束指针
B78374  cmp esi,eax / setbe [ebp+0x13]  ; bitpos    <= end ?
B7837A  cmp ecx,eax / setbe bl          ; bitpos+bits <= end ?
B78397  mov eax,[ebp+0x18]              ; 目标
B7839D  push edi                        ; n = bits
B7839E  push eax                        ; dst
B7839F  add ecx, esi / push ecx         ; src + bitpos
B783A4  call 0xC3E400                   ; memcpy(dst, src+bitpos, bits)
```

**要点：`0xC3E400` 的第三个参数是「位宽」被**当成字节数**传给 `memcpy`。**
即该函数不是位拆包器，而是「从 `src + bitpos` 起复制 `bits` 个**字节**」。
它对 `src + bitpos` 不做任何字节对齐检查，只检查 `bitpos + bits <= end`。

这一点是 §22.4「5 位字段编码」的另一种更简单的解释：
客户端的头部读取用的是**字节偏移**，不是比特位移。构造服务端帧时
按字节排布即可。

### 34.2 头部读取的精确步骤（`0xBA218F..0xBA21DB`）

```asm
; ---- 第 1 次：固定 5 字节 -> [ebp-0x14] ----
BA218F  push 4                        ; bits/len = 4
BA2191  lea ecx,[ebp-0x18]            ; out: consumed
BA2195  lea edx,[ebp-0x14]            ; dst: 5 字节字段
BA2199  push 0                        ; src = 0（源数据来自 [esi+0xac]）
BA219B  mov edi,eax
BA219D  mov eax,[esi+0xac]            ; 消息结构（上次分配的 [0x2c]）
BA21A3  push 5                        ; n = 5 字节
BA21A5  push edi                      ; bitpos（上一步 0xB9BBB0 的返回值）
BA21A6  mov dword ptr [ebp-0x14], 0   ; 目标清零
BA21AD  mov dword ptr [ebp-0x18], eax
BA21B0  call 0xB78350
; ---- 第 2 次：1 字节 = [esi+0xA8]（我们 recv 到的类型字节）----
BA21BC  mov al, byte ptr [esi+0xA8]
BA21C2  push 1                        ; bits/len = 1
BA21CC  mov byte ptr [ebp-0xD], al
BA21D6  call 0xB78350
```

两次调用都**不检查返回值**（`0xBA21B8` 那一处 `test al,al` 只保留在
第一次调用后的 `0xBA21B8/BA21BA` 分支里，且为真时不做任何补救）。
所以格式错误不会被检出，只会被静默地按错误内容继续。

### 34.3 可直接实现的服务端帧布局

```text
偏移（字节，从 recv(1) 那个类型字节算起）
  [0]      类型字节 T          （我们发 T = 0x00，走「1 字节帧头」分支）
  [1..5]   5 字节头部字段      （被读进 [ebp-0x14]，内容目前不作为门禁）
  [6]      = T（复制）          （被读进 [ebp-0xD]，然后拼进 0x2c 对象）
  ...
  [ebx+5 = 6:]  位打包负载      （端点 = 帧缓冲可用长度，>= 200B）

长度约束（0xB9BBB0 / 0xB9BB90）：
  可用长度 = [buf+0x1C] - [buf+0x24] + 0x1F
  [buf+0x24] = max(n, 0x1F)，n = 上一次传进来的长度（0x83 时为 5）
  => 可用长度恰好等于 [buf+0x1C]，即帧缓冲里的可用字节数。
  recv_need 计算见 §4.7/§22.3：帧头帧走 0x1F 阈值，业务帧走实际长度。
```

### 34.4 「只发前缀帧就能保活」是一个**未经验证的假设**，且有反证

> ⚠️ 本节原稿曾把「持续发前缀帧即可让看门狗不到点」写成结论，
> 但 §35 的新实跑否证了它的前提，且历史 `--keepalive4` 实验也不支持它。
> 保留此节仅作为**待检验假设**与推导记录。

```text
0xBA20A0 返回 >0  <==>  [buf+0x1C] > 0  <==>  收到了 >=1 字节并进了缓冲
读帧路径末尾写 [req+0x9C]=3（BA227F），不写 [req+0xC8]
  => 不会触发 32 ms 复位（0xBA3420）
  => 也不会把 [req+0x5E8] 从 3 拉回
```

上面这段只说明「前缀帧不会引发复位」，**并不说明它能续命**：

```text
反证 1  历史 --keepalive4-every 1.0（run IFS1_ELEVATED_20260929_142730）
        在 0x83 后连续 69 秒每秒发 4 字节，客户端仍在 post-83 +52.00 s
        弹出断线 —— 说明「有新入站字节」本身不足以喂住看门狗。

反证 2  §35（run IFS1_ELEVATED_20260929_160114）：把 post-83 采样窗口
        从 2 s 扩到 70 s，用 16 ms 分辨率采 4770 个点，发现
        lobReq9c 全程恒为 1、lobReq5e8 全程恒为 3 —— 客户端读帧器
        0xBA20A0 在这 52 秒里**一次都没有执行**。
        即：客户端此刻根本不在「等读」，看门狗不在读路径上。
```

### 34.5 后续若要推进到第二档

`§4.5` 的 `644==0` 分支（`BA457E..BA45B2`）是第二档真正的入口：

```asm
BA457E  push 0x1C / call 0xB74220        ; 分配 0x1C 字节消息对象
BA4596  push 0 / push 8
BA459C  call 0x4AA4A0                    ; 用 opcode=8 构造该对象
BA45A8  push eax
BA45AB  mov ecx,edi / call 0x7F9350      ; COM 智能指针赋值（接管）
BA45B7  mov ecx,[esi+0x63C] / mov edx,[esi+0x638]
BA45C7  call 0xB76120                    ; 用 token 低/高 32 位初始化
BA45CF  mov byte ptr [eax], 4            ; [out] = 4
```

即「`0x83` + `644==0`」会构造一个 **opcode 8** 的内部消息。
第一档闭合后，第二档应从「opcode 8 的服务端语义」与
`0xBA3710`（`5E8==3` 时的 `0x85` 处理器）的消费路径继续。

## 40. 探测包的归属：**Demonware STUN**，开关来自 `dw_config`

本轮先否证了「回声即可」，再顺藤找到了真正的配置来源。

### 40.1 回声实验：**无效**（否证）

```text

  stun.ini -> 127.0.0.1，记录器加 --reply-echo
  记录器确认：recv 48 包，SENT 48 包（1e0300 x24、14020000 x24，成对回声）

  dw+0x1F4: 1 -> -2     +23.163 s      （与不复声的 164603 的 +23.249 几乎相同）
  弹窗                  +27.730 s
```

**把请求原样回声，DW 完全不认。** 所以合法响应不是回声，
而是有特定载荷语义的包（见 §40.3）。

### 40.2 静证明：这两个包是 **Demonware 的 STUN**，不是腾讯自定义

镜像里的相关字符串：

```text
0xD5A9CC  stun.au.demonware.net
0xD5A9E4  stun.jp.demonware.net
0xD5A9FC  stun.eu.demonware.net
0xDC6610  stun.us.demonware.net
0xDE0028  STUNPingEnabled
0xDE0038  STUN_STN
0xDE0044  STUN_TUB
0xDE0050  STUN_CTG
0xDE005C  STUN_STG
0xDCA15C  STUNServerPing        （worker 线程名，ref 0xE56CB8）
0xDCA0B0  STUNServerPingResult|%s|%llu|%llu|${CODOID(%llu)}|%s|%u|%s|%d|...
```

即：**CODOL 用的是 Demonware 标准 STUN**（`STUN_STN/TUB/CTG/STG` 是
Demonware 的 STUN 服务器分类），而 `stun1/2/3-tub.codol.qq.com` 是
腾讯把 `TUB` 一类换成了自家域名。`-tub` 后缀正对应 `STUN_TUB`。

`STUNPingEnabled` 的引用链（`0x7EDD4E` 起）是配置读取：

```asm
7EDD47  mov eax,[0x33E6A00]
7EDD4E  push 0xDE0028            ; "STUNPingEnabled"
7EDD53  push 0xDB6EBC            ; "dw_config"        <<< 配置节名
7EDD58  call 0x50BC70            ; 取配置项
7EDD60  test eax,eax / je ...    ; 非空才覆盖
7EDD72  mov byte ptr [0x84244C4], al   ; STUN ping 开关
...     同样方式读 STUN_STN -> 0x84244C8（0x400 字节字符串）
        STUN_TUB -> 0x84248C8   STUN_CTG -> 0x8424CC8
```

**结论：STUN 主机名来自 `dw_config` 配置节，不是 `stun.ini`。**
（`stun.ini` 是另一条更早的读取路径；本轮实验证明改它能改变行为，
说明两条路径都会影响实际使用的地址，但 `dw_config` 是主控。）


### 40.4 已定位 STUN 的宿主线程与入口


### 40.6 STUN ping 循环全文（含响应校验）—— 合法响应的判据已明确

```asm
; ---- 发送 ----
7F4CA2  mov eax,[ebp-0x1938]          ; 该目标的 socket/地址对象
7F4CAD  push 0x51C                    ; flags
7F4CB2  lea ecx,[ebp-0x520]           ; 应答缓冲（0x51C 字节）
7F4CB9  mov ecx,[ebp-0x1940]
7F4CBF  push 0
7F4CC1  push ebx                      ; ebx = 载荷长度（由 §40.4 生成，3 或 4）
7F4CC2  lea edx,[ebp-0x920]           ; 载荷缓冲
7F4CCA  push ecx
7F4CCB  call dword ptr [0xca80cc]     ; sendto/recvfrom 组合调用

; ---- 响应校验（这就是「合法响应」的判据）----
7F4CD1  cmp eax,1
7F4CD4  jne 0x7F4CF1                  ; 返回值必须 == 1（收到 1 个包）
7F4CD6  cmp dword ptr [ebp-0x51C], 0  ; 应答首 4 字节必须 == 0   <<<< 关键
7F4CDD  jne 0x7F4CF1                  ; 不为 0 -> 本次不计入
7F4CDF  mov edx,[ebp-0x518]           ; 第 2 个 dword = 测得的 RTT（ms）
7F4CE5  add [ebp-0x1928], edx         ; 累加 RTT
7F4CEB  inc dword ptr [ebp-0x1924]    ; 有效应答计数 +1
```

**因此「合法响应」的最低要求是：**

```text
1. 必须是一个 UDP 应答包（recvfrom 返回 1）
2. 应答 **前 4 字节 == 0x00000000**
3. 第 5..8 字节被当作 RTT（毫秒）；值任意，会累加求平均
   （7F4D61 idiv ecx -> 平均值写回 [esi]，esi 从 0x8529700 起、
    每组步长 0x1014、直到 0x852D750）
4. 长度至少 8 字节
```

即：**回一个 8 字节的 `00 00 00 00 <RTT32>` 就应该被判定为成功应答。**
这比原先设想的「抄 Demonware 协议」简单得多 ——
校验只看「首 dword 为 0」。

```text
发送间隔：7F4D86/7F4D8C imul edx,edx,0x3e8 后 Sleep
          （[0x85286DC] 秒 * 1000，即每目标轮询间隔）
目标表：  0x8529700 起，每组 0x1014 字节，到 0x852D750 为止
```

### 41.1 解析方法（纯读取，未改任何东西）

观察器新增两项只读采样（`POST83_WATCH` 内）：

```text

/code                      该地址处前 16 字节（用于识别 trampoline）
/mod                       该地址落在哪个已加载模块（用 existing MODULE 列表）
```

实跑 `IFS1_ELEVATED_20260929_171442`：

```text
iat80c8 = 0x11348072    code = e9 f9 76 c7 63  ...   （E9 = jmp rel32）
iat80cc = 0x113489EA    code = e9 f1 73 c7 63  ...
```

两处都是 `E9 xx xx xx xx` 形式的 **trampoline**，且地址
`0x11348072 / 0x113489EA` **不在任何已加载模块内**
（188 个模块里，跨过它的空洞在 `codoMP_client_shipRetail.exe`(0x400000,
0xE659000) 与 `TenProxy.dll`(0x127F0000) 之间）——
即运行期分配的跳转桩，这正好解释了为什么静态导入表只有 3 项。

解 `E9 rel32`：

```text
0x11348072 + 5 + 0x63C776F9 = 0x74FBF770      -> SysWOW64\IPHLPAPI.DLL  RVA 0x1F770
0x113489EA + 5 + 0x63C773F1 = 0x74FBFDE0      -> SysWOW64\IPHLPAPI.DLL  RVA 0x1FDE0
```

⚠️ 必须用 **SysWOW64** 的 IPHLPAPI（客户端是 32 位）。
查其导出表（RVA 完全命中，delta = 0）：

```text
RVA 0x1FDE0  ->  IcmpSendEcho        <<< 0x7F4CCB 调用的就是它
RVA 0x1F770  ->  IcmpCreateFile
```

### 41.2 这解释了我之前全部三次失败

`IcmpSendEcho` 是 **Windows 系统 ICMP ping**，不是 UDP 收发：

```c
DWORD IcmpSendEcho(HANDLE IcmpHandle, IPAddr DestinationAddress,
                   LPVOID RequestData, WORD RequestSize,
                   PIP_OPTION_INFORMATION RequestOptions,
                   LPVOID ReplyBuffer, DWORD ReplySize, DWORD Timeout);
```

对应到 `0x7F4CA2..0x7F4CD1`：

```text
[ebp-0x1938]  -> RequestData（要 ping 的载荷）
ebx           -> RequestSize（3 或 4 == 我们抓到的 1e0300 / 14020000）
[ebp-0x520]   -> ReplyBuffer（0x51C 字节）
[ebp-0x51C]   -> ReplySize 的传参槽位
0x3E8         -> Timeout = 1000 ms
返回 eax      -> IcmpSendEcho 的返回值，即「收到几个 ICMP 应答」
                 成功时为 1；0x7F4CD1 的 cmp eax,1 / jne 是在判这个
```

**因此：**

```text
1. 客户端不是"连 STUN 服务器"，而是**对 stun1/2/3-tub 的 IP 做 ICMP ping**。
2. 我三次实验（不回应 / 回声 / 8 字节零包）都在往 UDP/3074 回包，
   而客户端用的是 ICMP —— 那些 UDP 包它根本没看，时间线当然完全不变。
3. 之前看到的"3–4 字节 payload"是 **ICMP 回显数据**（ping 的填充），
   不是应用层协议包。
4. stun.ini 内容其实是 ping 的目标列表；"STUN" 只是这套
   「DW 用 ping 测延迟/可达性」机制的命名。
```

```text

                -> 20 × ≈2.38 s = 47.6 s
```

## 42. 四个 `-2` 写入点的精确清单与结构（并修正一处笔误）

### 42.1 修正

§37 与前几节里我把一个 `-2` 写入点写成 `0xBADE15`，**这是笔误**。
按 `c7 83 f4 01 00 00 <imm32>` 精确重扫全镜像，写入点只有 8 个：

```text
0xBADB50  mov [ebx+0x1F4], -1
0xBADDEA  mov [ebx+0x1F4], -2      <<< 失败
0xBADFB2  mov [ebx+0x1F4],  2      <<< 成功
0xBAE1BC  mov [ebx+0x1F4],  2      <<< 成功
0xBAE597  mov [ebx+0x1F4],  2      <<< 成功
0xBAE75E  mov [ebx+0x1F4], -2      <<< 失败
0xBAE776  mov [ebx+0x1F4], -2      <<< 失败
0xBAE7BA  mov [ebx+0x1F4], -2      <<< 失败
```

即失败只有四处：**0xBADDEA / 0xBAE75E / 0xBAE776 / 0xBAE7BA**。

### 42.2 两类失败路径的结构

**类型 I（"队列空了就断开"）：0xBADDEA 与 0xBAE7BA —— 结构完全相同**

```asm
BADDC2/BAE791  xor esi,esi
BADD C4/BAE793 cmp dword ptr [ebx+0x18], edi   ; edi == 0
               jbe 0xBADDEA / 0xBAE7BA          ; 队列计数 <= 0 -> 直接置 -2
               loop: call 0xC74510([ebx+0x10][i])   ; 逐个取状态
                     push eax / call 0x8435D0       ; 打日志
BADDEA/BAE7BA  mov [ebx+0x1F4], -2                 ; 置断开
```

即：**当待处理队列 `[dw+0x18]` 为 0（或处理完变空）时，
客户端把 DW 阶段直接标成 -2。** 这是"没有待办就把连接判死"的语义。

**类型 II（子结果判定）：0xBAE75E 与 0xBAE776**

```asm
BAE74A  cmp byte ptr [ebp-0x988], 0     ; -0x988 在 0xBAD886 由
                                        ; cmp [ebx+0x4D70],eax / sete 写入
BAE751  mov byte ptr [ebp-0x986], al    ; al 来自 0xBAE745 call 0xBBAD10
BAE757  jne 0xBAE768
BAE75E  mov [ebx+0x1F4], -2             ; 失败 1
BAE768  cmp byte ptr [ebp-0x986], 0
BAE76F  jne 0xBAE780
BAE776  mov [ebx+0x1F4], -2             ; 失败 2
```

依赖 `0xBBAD10(...)` 的返回值与 `[dw+0x4D70] == [dw+0x18]`。

### 42.3 成功路径的形状（三个都是同一模式）

```asm
0xBADFB2 与 0xBAE1BC：两处都紧跟
           call 0xC69A50（把结果压入 [ebx+0x1A0] 容器）
0xBAE597： 同样紧跟 call 0xC69A50（0xBAE58F）
```

即 **"成功 = 把一个条目成功推进 [dw+0x1A0] 这个容器"**。

### 42.4 为什么这一轮 172253 命中的不可能是 0xBAD8CE 那条

```text
run 172253：POST83_WATCH 全程 [dw+0x4D74] == 0
而 0xBAD8C8 inc [ebx+0x4D74] 是"重试计数"路径的唯一自增点。
=> 该路径没执行 => -2 来自上面四处之一。

结合 [dw+0x18] 与 [dw+0x4D70] 的取值可以进一步区分：
  · 若 [dw+0x18] == 0           -> 类型 I（0xBADDEA / 0xBAE7BA）
  · 若 [dw+0x18] != 0 且 0xBBAD10 返回 0 -> 类型 II
```

### 42.5 下一步（唯一需要做的一件事）


### 42.8 更正 §42.2 的一处读法

我先前把 `0xBADDEA / 0xBAE7BA` 描述成"队列为空才断开"，**这是错的**。

```asm
BADDC7  jbe 0xBADDEA        ; 空 -> 跳过日志
BADDD0  loop: 打印每项状态
BADDEA  mov [ebx+0x1F4], -2 ; 两条路都到这里
```

即 **0xBADDEA 与 0xBAE7BA 是"放弃"终点，不是"条件判定"**。
本轮 `[dw+0x18]=3` 仍然走到 -2，正与此一致。

## 43. DW 侧的真实形态：发报机周期性重试、每次都失败

### 43.1 静证：`0xBBAD10` 是 DW 的发报机

```asm
BBAD10  mov ebx,ecx
BBAD16  cmp dword ptr [ebx+0x1A0], 0
BBAD1D  jne 0xBBAD91          ; 已有在途发送 -> 不重入
BBAD28  mov [ebx], eax        ; 句柄
BBAD40  rep movsd (0x22 dwords) ; 把 0x88 字节报文拷进 [ebx+4]
BBAD48  mov [ebx+0x1B0], eax / [..+4], edx
BBAD4D  call 0xBBAED0
BBAD56  call 0xBBA870
BBAD5B  cmp al,1 / jne 0xBBAD9D   ; 发送失败 -> 走失败返回
BBAD65  mov dword ptr [ebx+0x1A0], 1  ; <<< 置"在途"标志
```

`0xBBA870` 只是一层薄封装：`push [ecx+4] / push 0 / call 0xBBA6D0`，
返回 al 透传。

### 43.2 实跑（run `IFS1_ELEVATED_20260929_173828`，第 1 次尝试命中）

```text

t=48.992  1f4=1  18=3 4d70=3 4d74=0 1a0=0 1f0=996010640 c=999197200  <- [dw+0x1F0] 换对象
t=61.170  1f4=1  18=3 4d70=3 4d74=0 1a0=0 1f0=996010640 c=2332887888 <- [dw+0x0C] 变

握手 37.840 -> -2 差 47.685 s；弹窗差 +52.19 s
```

### 43.3 这轮数据说明什么

```text
1. [dw+0x1F0] 与 [dw+0x0C] 在 ~48.99 / ~61.17 / ~73.35 s 周期性变化，
   间隔约 12.2 s —— 这是 DW 发送/重建链在**周期性重试**。

2. [dw+0x1A0]（"有报文在途"标志）**全程为 0**。
   而 0xBBAD10 只有在 `0xBBA870` 返回 1 时才会把 0x1A0 置 1。
   => 每一次发送尝试都失败了（或压根没走到 0xBBAD10）。

3. 47.685 s ≈ 4 × 12.2 s，与"约 4 次尝试后放弃"一致。

=> 结论：DW 层的形态是「每隔约 12 s 组织一次发送 -> 发送失败 ->
   在 +47.7 s 处的某条放弃路径把 [dw+0x1F4] 置 -2」。
   失败点在 0xBBAD10 -> 0xBBA870 -> 0xBBA6D0 这条链上。
```

### 43.4 下一步（已缩到单个函数）

```text
目标：0xBBA6D0（0xBBA870 的唯一下游）。
  它是实际"把报文送出去"的那一步；返回 1 才算成功。
  需要弄清它依赖什么（socket? 目标地址? 缓冲区状态?）。

另一条并行线索：0xBBA870 上方还有同构的三兄弟
  0xBBA890 (arg 3) / 0xBBA8B0 (arg 2, 用 [ecx+0x8C])，
  说明这套"发送步"有多个阶段，可一并核对哪个阶段失败。

判定标准不变：POST83_WATCH 的 dw+0x1F4 == 2，且 60 s 内无弹窗。
```

## 44. 第一档能否闭合的最终评估（结论：不能靠现有手段闭合）

继续往下追 `0xBBAD10 -> 0xBBA870 -> 0xBBA6D0` 之后，得到的是
**"要补一整个 Demonware 会话层"**，而不是某一处常量或某个回包格式。

### 44.1 `0xBBA6D0` 的内容：序列化 + 真实发送

```asm
BBA6D0  sub esp,0x518
BBA6F7  call 0xBC1C70                 ; 初始化序列化器（用 [ebp+8]）
BBA721  call 0xBC1C90                 ; 序列化 -> [ebp-0x50C], 长度 -> [ebp-0x510]
BBA726  cmp al,1 / jne 0xBBA763       ; 序列化失败即失败
BBA730  mov ecx,[esi]                 ; [esi] = 传输对象
BBA734  mov eax,[eax+0x18]            ; vtable+0x18 = 发送
BBA73F  push edi / push buf / push len
BBA740  call eax
BBA742  test eax,eax / jle fail       ; 返回值必须 > 0
BBA746  cmp eax,[ebp-0x510] / jne fail ; 且必须等于期望长度
BBA750  mov al,1                       ; 成功
```

即：**DW 要把报文序列化后，通过一个"传输对象"的虚表 +0x18 发出去；
发送返回 0 或长度不符即失败。**

### 44.2 失败链的性质

```text
0x7F4B70 STUN worker   -> ICMP ping（已证，且不是门）
0xBBAD10 DW 发报机     -> 每次尝试都失败（[dw+0x1A0] 恒 0）
  └ 0xBBA870 薄封装
      └ 0xBBA6D0 序列化 + vtable[+0x18] 发送
         ├ 0xBC1C90 序列化（必须回 1）
         └ [传输对象]->vtable[+0x18]（必须回 >0 且长度相符）
```

### 44.3 且已确认 DW 需要"远程配置 + OOB 通道"

本节新查到的两处关键字符串（都在同一个 dw 配置字符串表里）：

```text
0xDDFF24  'dw_disconnect_oob_always'    ; 0x7ED88D 起经 0x50BC70
                                         ; 从节名 dw_config 读取
0xDE01AC  'dw_disableExitPopup'         ; 0x7EE17C 起同样方式读取
```

配置读取的统一模式是
`0x50BC70(config=[0x33E6A00], 节名, 键名, 1)`：

```text
节名 'dw_config'       键 STUNPingEnabled / STUN_STN / STUN_TUB /
                              STUN_CTG / STUN_STG /
                              dw_disconnect_oob_always /
                              dw_disableExitPopup ...
节名 'tournament'      键 ...
节名 'cross_zone_%s'   键 'ping_address'      （按区服拼接）
```

**"OOB"（out-of-band）是 Demonware 在 UDP 之外维持的一条可靠控制通道。**
`dw_disconnect_oob_always` 这个键的存在说明客户端有
「OOB 断了就断开」的行为开关；这与发送链恒定失败、
最终置 `[dw+0x1F4] = -2` 完全吻合。

### 44.4 诚实结论

```text
第一档 ⑤ 无法在当前手段（只读采样 + 本地探针 + 配置文件）下闭合。

原因：DW（Demonware）不是 CODO 大厅协议的一部分，而是一整套独立子系统：
  1. 需要一个「远程配置服务」下发 dw_config / cross_zone_*；
     我们从未提供过，所以所有 STUN_* / dw_* 开关都拿不到值；
  2. 需要一条可用的 OOB（可靠控制）通道，客户端才会把
     [dw+0x1F4] 从 1 推到 2；
  3. 这两者都不是"补一条帧""回一个包"能解决的。

已完成且可信的部分（可直接复用）
  · CODO/IIPS 大厅链路全通：host/port 注入 -> 0x81 -> 0x82 -> 0x83 ->
    644==0 分支 -> 队列校验 lob1400=8900 / lob240=2 -> uA50=5
  · 断线路径完全定位：0x7EEBC1 -> 0x621810 -> cppOnDWDisconnected，
    关键字段 [0xE85C68+0x1F4]
  · 否证清单 23 条（手册 §5.3），含我自己的 4 处误判更正

若用户愿意放宽边界，唯一能"就地"解决问题的做法：
  在 [dw+0x1F4] 的写入点或 0xBBA6D0 的返回处做代码级干预
  （属改 .text，需明确授权）。
否则需要真正实现 DW 配置服务 + OOB 通道，规模远大于第一档。
```

## 46. DW 配置对象到底是"谁、用什么"建起来的 —— 机制已完全确定

顺着 §45.6 的线索继续，本轮把配置注册机制拆到了指令级。

### 46.1 谜题：`[0x33E6A00]` 从未被直接写入

精确搜索 5 种"立即数写入"与 6 种"寄存器写入"编码：

```text
mov [0x33E6A00], imm32        -> 0 处
mov [0x33E6A00], eax/ecx/...  -> 0 处
mov [0xC7AEAC0], imm8         -> 0 处
mov [0xC7AEAC0], al           -> 0 处
```

但 `0x50EAD5` 有一条 `mov ecx, 0x33E6A00`，随后
`0x50EADA call 0x50B910`。**答案就在这里：地址是被当作参数传出去的。**

### 46.2 注册函数 `0x50BC70` 的真实签名（读代码得出）

```asm
50BC70  push ebp / mov ebp,esp / push ecx
50BC7B  test eax,eax          ; eax = 配置容器
50BC83  mov edx,[ebp+8]       ; arg1 = 节名
50BC8E  cmp [ebp+0xc],0       ; arg2 = 键名
50BCAF  cmp byte [ebp+0x10],0 ; arg3 = 一个字节标志（我们一直传 1）
50BC99  mov ebx,[eax]         ; ebx = container[0]（哈希桶）
50BC9C  mov edi,[eax+4]       ; edi = container[1]
```

**它取 3 个栈参数、1 个 eax 寄存器参数。**
所以 `push 1 / push <键名> / push <节名> / call 0x50BC70`
与 `mov ecx,0x33E6A00 / call 0x50B910` **是两件不同的事**：

- `0x50BC70(container_in_eax, 节名, 键名, flag)` = **查找**
- `0x50B910(容器地址)` = **建立**（把 `0x33E6A00` 作为参数传进去）

### 46.3 建立点就是一个"注册表"函数

```asm
50EAB0  push ecx
50EAB1  mov eax,[0xC7AE9B0]        ; 工作缓冲
50EAB6  mov ecx,[0xC7AEAB8]        ; 长度
50EABC  mov byte [eax+ecx], 0xA    ; 追加换行
50EAC0  mov eax,[0xC7AE9B0]
50EAC5  mov edx,[0xC7AEAB8]
50EACB  mov byte [eax+edx+1], 0
50EAD0  mov eax,[0xC7AEAB8]
50EAD5  mov ecx, 0x33E6A00         ; <<< 传出配置对象地址
50EADA  call 0x50B910              ; <<< 建立
50EADF  call 0x7E9B00              ; DW 模块：读取自己的键
50EAE4  call 0x513A20
50EAE9  call 0x7FB950
50EAEE  call 0x4B8E30
50EAF3  call 0x4A9EC0
50EAF8  cmp byte [0xC7AEAC0],0 / je 0x50EB31   ; 配置已加载？
50EB01  cmp byte [0xC7AEAC1],0 / jne 0x50EB31  ; 且尚未用于 DW？
50EB0A  mov eax,[0x33E6A00] / push 1 / push 0xDB6EC8 / push 0xDB6EBC("dw_config")
50EB1B  call 0x50BC70                          ; 读 dw_config
```

即：**这段代码是"配置总入口"** —— 先建容器（`0x50B910`），
再让各子系统（DW 的 `0x7E9B00`、以及 `0x513A20`/`0x7FB950`/…）
各自把键注册进容器，最后才开始读 `dw_config` 下的键。

### 46.4 且这段注册代码按"模式编号"分派

在它之前的 `0x50E9E0` 起是一串同构分支：

```text
50E9E0  8bc6              mov eax,esi
50E9E2  e8a9f1ffff        call 0x50DB90
50E9E7  84c0 / jne ...    ; 该模式已处理则跳过
50E9EF  push 0x50DD20     ; <<< 注册函数指针
50E9F4  push 0xDBDEE0     ; <<< 模式名字符串
50E9F9  jmp 0x50EA6C
...     共 6 个同构分支（模式名在 0xDBDEE0 / 0xDBDEF0 / 0xDBDF00 /
        0xDBDF14 / 0xDBDF2C / 0xDBDF38）
50EA6C  imul edi,esi,0x130 / add edi,0xC7AE9A8
        call 0x66A650
```

即 **"当前模式"决定了哪一套注册函数被调用**。
我们的环境里这些分支全都没走，所以容器始终为空。

### 46.5 本轮结论

```text
已完全确定：
  · 配置容器地址 = 0x33E6A00，由 0x50B910 建立（在 0x50EADA 被建立）；
  · 建立时机 = 0x50EAB0 这个"配置总入口"，按模式分派调用各子系统注册函数；

        0x50DB60  imul eax,eax,0x130
```

## 49. 「实现资产注册」这条路的真实规模（本轮调研结论：不成立）

用户要求走「实现资产注册」。我按这个方向查了注册表的填充路径，
结论是**这条路在当前工程内不成立**，理由如下（全部有地址）。

### 49.1 注册表是三张联动的表，不是一张

```text
0x1E2D338   名字 -> 记录号（40 处引用）
0x239B120   记录表，stride 0x1C（75 处引用；+0x00 是类型码，
            +0x08 是名字指针，+0x11 是字节标志，+0x14 是 next 指针 <-- 链表）
0xE5C8C0    资产 reader 表（11 处引用）
```

从 `0x486B40` 这段可以读出记录的**结构**：

```asm
486B65  mov eax,0xC / call 0x49C870        ; 用类型码 0xC 取索引
486B6A  mov eax,[eax*4 + 0x1E2D338]        ; -> 记录号
486B75  lea ecx,[eax*8] / sub ecx,eax      ; *7
486B7E  cmp dword ptr [ecx*4 + 0x239B120], 0xC   ; 类型必须 == 0xC
486B8F  cmp dword ptr [eax+8], esi               ; 名字指针必须相符
486B94  mov eax,[eax+0x14]                       ; <<< 否则沿链表继续
486B99  test eax,eax / jne 0x486B75
```

即：**查询是"哈希 -> 桶 -> 链表遍历"**，而且 `0xE5C8F0`（reader）
必须已经给出正确的名字指针。这套结构由引擎的资产装载器建立。

### 49.2 填充点没有找到任何"可注入"的入口

```text
· 相关字符串只有 3 个错误名：WIN_LOAD_ASSET_ERROR / .1 / .2（0xDB63B8 起）
  —— 没有任何 manifest / 清单 / 卷 路径字符串可供我们提供。
· 全镜像里只有两处 .json 字符串：'mp/marketplace.json' 与 'the.json'，
  没有 *.ifs 之外的资产清单名。
· 0x26DF7AC 是另一个并行容器（75 处引用），由 0x4991B0 / 0x49D3XX
  一族的函数维护，与 0x239B120 相互配合。
```

**要"实现资产注册"，等于重新实现引擎的资产装载器（三张表 + 链表
+ reader + 名字哈希），并伪造 fastfile/zone 装载流程。**
这不是"补一个配置服务"级别的工程量。

### 49.3 与 §48.7 的实测互相印证

```text

```

### 49.4 本轮最终判断

```text

  · 要做的不是"注册"而是"实现装载器"。

```

**边界**：本节全部为只读分析；未改 `.text`、未写游戏内存。

## 51. zone 装载器的确切要求（解释 §50.11 的启动失败）

我用 `IWff0100` / `IWffu100` 两个魔数字符串反查，找到了 fastfile 装载器。

### 51.1 装载器入口 `0x483DB0`

```asm
483D8B  cmp dword ptr [ecx + 0xdb5ee0], ...
```

对应的完整逻辑：

```asm
483DDD  lea eax,[edi+8] / lea ecx,[ebp-0x10] / call 0x484940  ; 读 8 字节魔数
483DF0  loop:
483DF4    cmp edx, dword ptr [ecx + 0xDB5EE0]   ; 与 "IWff0100" 比较
483DFA    jne 0x483E09
483E09  ... 再与 [ecx + 0xDB5EEC]               ; 与 "IWffu100" 比较
483E1A    jne 0x483EDF                          ; 两个都不匹配 -> 失败退出

483E2B  mov eax,4 / call 0x484940               ; 读下一个 u32
483E38  mov eax,[ebp-0x40]
483E3B  cmp eax, 0x1CD
483E40  je 0x483E68                             ; <<< 必须 == 0x1CD
483E42  否则: push 0x1CD / push <实际值> / push <第2个魔数> / push 2(错误级)
        call 0x4F82E0                          ; 报 WIN_LOAD_ASSET_ERROR
```

**两个硬性要求：**

```text
1. 文件头 8 字节必须是 "IWff0100" 或 "IWffu100"；
2. 紧随其后的 u32 必须 == 0x1CD。（这正是 §50.10 在偏移 0x189
   读到的 "IWff0100 cd 01 00 00 ..."，0x1CD 也确实在那里。）
```

### 51.2 这解释了我为什么把客户端跑崩

```text
我从 .ifs 切出的三段，起点就是 "IWff0100" + 0x1CD —— 头部本身是合法的。
但 §50.11 把三个 .ff 放进 main\ 后，客户端 4/4 启动失败。

原因不在"头部不合法"，而在**装载顺序/索引**：
  · 0x483DD8 之前先 `mov [0x82C4878],[0x82C487C] = 0`（重置装载状态）
  · 装载是**由引擎按 zone 清单驱动的**，不是"扫目录里有多少 .ff"；
  · 我多放的 3 个 zone 让引擎按错误的名字/顺序去找配套资源
    （§50.8 的名字是 client_shipRetail/chinese/... 路径式），
    于是启动阶段就报 WIN_LOAD_ASSET_ERROR 并退出。
```

### 51.3 最终判断：zone 装载需要"清单驱动"，不是"文件放置"

```text
已确证：
  · .ifs 可解（工具已跑通）
  · 解出的 .ff 头部合法（IWff0100 + 0x1CD，与装载器要求一致）
  · 但 zone 装载必须由引擎的 zone 清单驱动；
    手工往 main\ 里加 .ff 会让引擎在启动阶段报错退出（4/4 实测）

因此"实现资产注册"需要：
  a) 找到引擎读取 zone 清单的位置（决定"要装载哪些 zone"的那张表）；
  b) 把 marketplace 的三个 zone 名加进去，并让 .ff 出现在它们被查找的路径；
  或者
  c) 走 IIPS 自己的挂载流程（若存在），而不是文件系统。

两者本轮都未定位到 —— 这是下一步的实际工作。
```

## 53. 补充核查：`0x49E160` 的 16 个调用点里没有"可外部触发"的入口

为把 §52 的结论钉死，我把 `0x49E160`（提交 zone 装载）的**全部 16 个
调用点**过了一遍，确认没有控制台命令 / 配置项 / 服务端响应能加 zone。

### 53.1 调用点分类

```text
0x4FCC7C / 0x4FCD32 / 0x4FCE4F   硬编码栈数组（§52，启动期 zone 清单）
0x4FE76C / 0x4FE951              引擎内部装载辅助
0x49E67B / 0x49EC93              0x49E160 同族内部
0x5BFBF9 / 0x5BFCBB / 0x5C2C23   引擎内部
0x59B212                         动态数组（见 53.2）
0x5C8448 / 0x5CB441 / 0x5CB451   动态单元素（见 53.3）
0x813D09                         启动一次性（见 53.4）
```

### 53.2 `0x59B212` 是动态的，但输入不是外部文件

```asm
59B201  call 0xBECB10              ; 分配/取缓冲
59B206  push 2                     ; 类型
59B210  push edi
59B211  push eax
59B212  call 0x49E160
59B223  inc dword ptr [0xE609680]  ; 计数
```

它遍历的是 `[ebp-0x3C10]` 起的数组，来源在同函数上游
（`0x59AF55` 附近的循环，`0x82CA590` 缓冲）。
**要素来自引擎已登记的资产表，而不是"再读一个文件"。**

### 53.3 `0x5C8448` / `0x5CB441` 每次只加一个元素

```asm
5C8433  call 0x49F970
5C843F  mov dword ptr [ebp-0x70], edi   ; 单个名字
5C8442  mov dword ptr [ebp-0x6C], edi
5C8445  mov dword ptr [ebp-0x68], ebx
5C8448  call 0x49E160                   ; push 1 项
5C8450  mov ecx,[0x8167ED0] / inc ...   ; 写进 0x8167ED8 表
5C8464  mov dword ptr [0x8167ECC], 0xdbc09c
```

同样是单元素追加，且写进的是引擎自己的表。

### 53.4 `0x813D09` 是启动期一次性

```asm
813CEE  call 0x49F970
813CF3  mov [ebp-0x10],0 / mov [ebp-0xC],0 / mov [ebp-8],6   ; 单一项
813D09  call 0x49E160
813D11  call 0x5C8A70
```

只提交一项，显然不是"加载 marketplace zone"的位置。

### 53.5 结论（与 §52 一致，且更硬）

```text
· 没有任何调用点从"我们可提供的输入"（配置文件 / HTTP 响应 /
  控制台命令）构造 zone 清单；
· 清单来源只有两类：.text 里的立即数（§52）与引擎已登记的资产表；
· `loadzone` / `addzone` / `load_asset` 等命令名在全镜像里 **0 命中**。

=> 再次确认：**不改 .text 就无法把 marketplace zone 加进装载清单**，
   因此第一档 ⑤ 在不改 .text 的前提下不可闭合。
```

## 52. **zone 清单是硬编码在 `.text` 里的栈数组 —— 「资产注册」路的终点**

顺着 §51 的"清单驱动"线索，我找到了决定"装载哪些 zone"的那个函数。

### 52.1 `0x4FCC00`：把 zone 名逐个压栈成数组

```asm
4FCC00  sub esp,0xa10
4FCC39  push 4                    ; <<< 数组长度 = 4（第 2 处是 5）
4FCC3B  push eax                  ; 数组基址 = [ebp-0xA10]
4FCC3C  mov dword ptr [ebp-0xA10], 0xDBD6E0   ; "patch_code_pre_gfx_mp"
4FCC46  mov dword ptr [ebp-0xA0C], ecx        ; 1（标志）
4FCC4C  mov dword ptr [ebp-0xA04], 0xDBD6F8   ; "code_pre_gfx_mp"
4FCC56  mov dword ptr [ebp-0xA00], ecx
4FCC5C  mov dword ptr [ebp-0x9F8], 0xDBD708   ; "patch_localized_code_pre_gfx_mp"
4FCC66  mov dword ptr [ebp-0x9F4], ecx
4FCC6C  mov dword ptr [ebp-0x9EC], 0xDBD728   ; "localized_code_pre_gfx_mp"
4FCC76  mov dword ptr [ebp-0x9E8], ecx
4FCC7C  call 0x49E160                         ; 提交这批 zone
```

紧邻的 `0x4FCCA0` 是同一模式的第二个函数：数组长度 5，

```text
0xDBD744  "code_post_gfx_default_mp"
0xDBD760  "patch_code_post_gfx_mp"
0xDB6350  "code_post_gfx_mp"
0xDBD778  "patch_localized_code_post_gfx_mp"
（+0xDBD79C "localized_code_post_gfx_mp"）
```

### 52.2 这意味着什么

```text
1. zone 清单**不是**从任何配置文件/服务端响应读的，
   而是**以立即数形式硬编码在 .text 的栈数组里**。
2. 全镜像里对 "code_pre_gfx_mp.ff"(0xDBD0A0) 的引用只有
   0x4F5B00 / 0x4F5EE8 —— 那是"文件系统按名找 .ff"的路径，
   与 0x49E160 的"按 zone 名提交装载"是两条不同的路。
3. 名单里**没有** marketplace 系列（common_marketplace_lite 等），
   所以引擎从启动起就不会去装载 marketplace 的 zone。
```

### 52.3 三条"补资产"路线到此全部封闭

```text
路线 1  放 mp/marketplace.json 普通文件        -> 实测无效（§48.7）
路线 2  解 .ifs 得到 .ff 放进 main\            -> 实测启动失败（§50.11）
        且已查明原因：装载器由硬编码清单驱动，扫目录不管用（§51）
路线 3  找到并修改 zone 清单                   -> 清单是 .text 里的立即数（§52.1）
        => 要改它**就是改 .text**，与路线 1/2 性质完全不同
```

### 52.4 最终结论

```text
在不修改 .text 的前提下，无法让引擎装载 marketplace zone，
因此无法让资产表登记 mp/marketplace.json，
因此 [0x82C4A88] 永远停在 0，
因此 [0x33E6A00] 永远不建立，
因此 DW 永远用硬编码默认值，
因此 [dw+0x1F4] 永远停在 1 并最终置 -2。

=> 第一档 ⑤ **在不改 .text 的前提下不可闭合**。
   这是本会话通过 3 条独立路线的实测/静证得到的确定结论，
   而不是"还没试到"。

唯一可闭合的路径：授权改 .text —— 最小改动是把
   0x4FCC00/0x4FCCA0 的栈数组各加一项 marketplace zone，
   或在 0x4A936E 处让"取不到资源"不再直接返回。
   **ACE已被多方证据证实并非安全软件，其内核为新加坡团队研发的间谍病毒软件，鉴于游戏已停服，并有国防风险，如不破解则为不可接受代价，如不对其修改则绝不推进至下一档，此为复活游戏的必备条件，如不具备则拒绝进行下一步。
```

**边界**：本节为只读反汇编；未改 `.text`、未写游戏内存；
