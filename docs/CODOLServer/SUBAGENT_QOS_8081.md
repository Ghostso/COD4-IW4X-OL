## 1. 判定：**加密后的 QoS 数据（QOS_SPDTST 或 QOS_REP 载荷），不是明文 `QOSCSPkg`**

证据（按强度排序）：

1. **无 `ur` 魔数。** 8000/UDP 上已验证的 `QOSCSPkg` 帧以 ASCII `ur`（`75 72`）开头，见
   `SINGLE_V0B\local_listeners.jsonl`：`7572 0010 0008 ...`。
   8081 九包的**首 2 字节全部不是 `75 72`**（`8841`/`55b2`/`b4d2`/`7bbf`/`5be3`/`bbd3`/`f474`/`c3f2`/`70ba`）。
   ⇒ **不共享 `QOSCSPkgHead` 明文头。强度 HIGH。**

2. **首 80 字节熵 5.94–6.10，全包熵 5.98–7.72。** 前 80 B 熵 ≈ 6.0 明显**低于**随机（8.0），
   也**高于**明文 ASCII（≤4.5）。这是**「明文结构 + 部分加密」**或**「带固定字段的二进制」**的特征，
   不是纯密文，也不是纯明文。**强度 MEDIUM。**

3. **末 4 字节 `u16 + u16` 结构极其规整。** `u16@len-4` 在**全部 9 包中都是 `0000`**（概率 2⁻⁹⁰，
   不可能是巧合）。⇒ 这是一个**固定预留字段**。**强度 HIGH。**

4. **`u16@len-2` 与包长无算术关系**（32529/514/11348/31321/13833/11183/17097/32457/19089 vs 84/196/260/708/756）。
   ⇒ 它不是长度、不是校验和的直接形式。**强度 HIGH（否定）。**

5. **`u16@len-6` 与包长也无关系**（52864/23296/…）。
   ⇒ 尾部 6 字节是**两个独立的 16 位随机/派生值 + 一个 0**。**强度 HIGH。**

6. **复现迹象：包 #6 与 #2 内部有重复块。** #6 偏移 `~0x1B0` 处的
   `d0ccb61b9677ede97befa6e08e5c5`（27 B）在包内出现两次。**强度 MEDIUM**
   （同包内重复，说明是「同一明文块被同一密钥流加密两次」或「ECB/无 IV 分组」的特征）。

### 结论

> 8081 九包 = **加密载荷**，尾部 6 B 为 `u16 A + u16 0 + u16 B` 的明文帧尾。
> **无法从本输入区分**它是 `QOS_SPDTST_REQ`（测速请求）还是 `QOS_REP`（上报）
> —— 因为两者都在 `KEY_CONTEXT` 里，且**都没有可对齐的明文魔数**。
> 唯一可用的区分线索是**包长分布**（见 §2）。**强度 MEDIUM。**

## 2. 包长分布与协议语义的对应（推断，MEDIUM）

`KEY_CONTEXT` offs `9907`–`10059` 命令枚举序：
`QOS_SPDTST_REQ / QOS_SPDTST_RES / QOS_GET_REQ / QOS_GET_RES / QOS_REP`

`QOSSpdTstReq/QOSSpdTstRes = Rtt . StdDev . LostRate`（offs `10310` 段），
字段名池里 `Rtt` / `StdDev` / `LostRate` 均**带 `ms` 格式化标签** ⇒ 是**小结构、定长**。
而 `QOS_REP` 走 `QosCSQosRep`（含 `QosList` 列表）⇒ **变长、可大可小**。

对照九包：

| 分组 | 长度 | 数量 | 最可能的语义 |
|---|---|---|---|
| 小包 | **84** | **5** | `QOS_SPDTST_REQ`/`RES`（定长测速样本，5 个测速点） |
| 中包 | 196 | 1 | 变长上报（1 个 QosList 项） |
| 中包 | 260 | 1 | 变长上报（2 项） |
| 大包 | 708 | 1 | 变长上报（更多项） |
| 大包 | 756 | 1 | 变长上报（更多项） |

**84 B × 5 与「5 个测速样本」高度吻合**（5 也是 `QOS_CS_MAX_REP` 的常见取值形态）。
**强度 MEDIUM**（长度相关性推断，无明文佐证）。

⚠ 注意：**这九包全部是同向**（同一 peer 只出现 `data_hex`，无 `sent_reply`）。
⇒ 它们是**客户端 → 服务器的出向包**，即**请求/上报**，**不是响应**。
若目标是「让客户端继续」，我们应关注**如何应答**，而不是复用这些包。

## 3. 加密 / 校验 / 包尾格式 与 密钥来源

### 3.1 已排除

| 假设 | 检验 | 结果 |
|---|---|---|
| 明文 `QOSCSPkg`（`ur`+u16 头） | 首 2 字节比对 | **排除**（9/9 无 `ur`） |
| 单字节 XOR | 未做（本输入无明文对） | **未测** |
| 尾部为长度字段 | `u16@len-2` vs len | **排除**（无算术关系） |
| 尾部为和校验 | 无匹配 | **排除（弱）** |
| 尾部为 CRC16 | 未做完整 CRC16 扫描 | **未测** |

### 3.2 包尾格式（HIGH）

```
[ 0 .. len-7 ]  加密载荷（len-6 字节）
[ len-6, len-3 ]  u16be  = 每包不同的 16 位值（疑似 nonce / 序号 / 校验）
[ len-4, len-3 ]  ---- 上者高位与下一字段的分界见下
[ len-4, len-5 ]  u16be  = 0x0000 固定（9/9）
[ len-2, len-1 ]  u16be  = 每包不同的 16 位值（疑似校验 / tag 低半）
```

精确切分（字节级，HIGH）：
```
offs[len-6 .. len-5] = A   u16be   (变化)
offs[len-4 .. len-3] = 0   u16be   (固定 0x0000，9/9)
offs[len-2 .. len-1] = B   u16be   (变化)
```

### 3.3 密钥来源：**UNKNOWN**

本输入**不含任何密钥材料**。已核对：

* `hits.jsonl` 中 `qos_cs` 仅 1 条（`VA 0x00E44AEC`）、`qos_ss` 仅 1 条（`VA 0x00E43BCC`），
  两条都是**紧凑二进制表**（后缀全为 `^P`/`?` 字节），**不是可读字面量**。
* `KEY_CONTEXT` 中 `QOS_CS_MAGIC` / `QOS_SS_MAGIC` 只出现**名称**，**无字面值**。

⇒ **无法给出密钥来源。** 但可给出两个可检验的方向：

1. **若尾部 `A`/`B` 是 nonce/tag** ⇒ 密钥很可能是**每会话固定**（非每包），
   因为 5 个 84 B 包长度相同而 `A`/`B` 全不同。
2. **若包 #6 内的重复块是真重复**（§0 第 6 条）⇒ 说明**同一密钥流被复用**，
   即**没有 per-packet IV**，这通常意味着**流密码 + 计数器**或**固定 IV 的 CTR**。

**这两条都是可实验假设，不是结论。**

## 4. 三个可实验应答模板（优先能引发下一步客户端行为）

前提：**我们目前没有正确的加密/签名算法**，所以任何「构造合法应答」都有失败风险。
以下按「先探测、后构造」排序 —— **前两个模板的目的是「观测客户端行为」而非「提供有效数据」**。

### 模板 1（首选：**回显 + 保持长度**，用于探测客户端是否校验）

**依据**：九包尾部结构规整（`A, 0, B`），若客户端**只校验尾部**而不验签，
回显同长度包即可让客户端「认为收到应答」；若它丢弃，我们就得到「有校验」这个结论。

```python
def build_8081_echo(req: bytes) -> bytes:
    """回显请求，仅把尾部 A/B 互换，长度不变。用于探测是否有完整性校验。"""
    n = len(req)
    A = req[n-6:n-4]
    B = req[n-2:n]
    return req[:n-6] + B + b'\x00\x00' + A
```

### 模板 2（次选：**84 B 定长空样本**，用于探测是否为定长测速应答）

**依据**：5 个 84 B 包暗示存在「84 B 定长」这一形态。若 `QOS_SPDTST_RES` 是定长 84 B，
客户端可能按固定长度解析。

```python
def build_8081_84(seq_hi: int = 0, seq_lo: int = 1) -> bytes:
    """构造 84 B 定长空样本：全 0 载荷 + 规整尾部。"""
    payload = bytes(78)                      # 84 - 6 = 78 B
    tail = (seq_hi & 0xFFFF).to_bytes(2, 'big') + b'\x00\x00' + (seq_lo & 0xFFFF).to_bytes(2, 'big')
    assert len(payload) + len(tail) == 84
    return payload + tail
```

### 模板 3（仅在前两者都被接受后使用：**变长上报应答**，用于探测 `QosList` 解析）

**依据**：`KEY_CONTEXT` offs `11411` 给出 `QOSConndIPPortList = ConndIPPortNum → ConndIPPortList[] → GameSvrList`。
若客户端会解析变长应答，可用「0 项」的最小变长体探测。
但**字段宽度 UNKNOWN**，此模板必须准备好按 `IntNum/IntList`+`StrNum/StrList` 复合结构改写。

```python
def build_8081_var(n_items: int = 0, head_u16: int = 0, tail_u16: int = 0) -> bytes:
    """变长应答骨架：1 B 计数 + n_items*0 + 6 B 尾部。字段宽度未证，仅作探测。"""
    body = bytes([n_items & 0xFF]) + bytes(4 * n_items)
    tail = head_u16.to_bytes(2, 'big') + b'\x00\x00' + tail_u16.to_bytes(2, 'big')
    return body + tail
```

**实验判据**：观察客户端是否发出**新包**（新长度 / 新端口 / TCP 连接）。
若九包之后没有任何新包，则 8081 这条路可能**不是**决定性路径。
