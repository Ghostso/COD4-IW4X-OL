# `.tp3` 段解密路径逆向报告

**任务**：查清 `codoMP_client_shipRetail.exe` 的 `.tp3` 加密段是谁、在什么时机、用什么算法解密的，并给出可复现的解密路径。

**结论（先给答案）**：`.tp3` **不是自解密**，也**不是页级/驱动级按页解密**，而是**两段式**：

1. **第一段**（文件有原始数据覆盖的 `0x593000` 字节）：在**模块加载期**（`t < 0.008 s`，
   早于该模块执行任何一条自身指令）由 **exe 之外的模块**完成「读文件 → 解压 → 解密 → 写回内存」。
2. **第二段**（文件**没有**原始数据覆盖的虚拟尾 `0x31389A` 字节）：在 `t ≈ 2.5–4.8 s`
   由二次解包器把约 2.9 MB 数据搬入。

第一段的执行者**不可能是 exe 自己**（鸡生蛋问题：`0x401000` 处就是要被解密的压缩流本身，
见 §4 证据 D），指向腾讯 ACE/TP3 组件（`ace-ats32.dll` / `TerSafe.dll` / `ACE-DRV32.dll` / `TP3Helper.exe`，见 §4 证据 E）。

由于这是「解压 **+** 解密」的组合变换，只用「磁盘密文 + 运行期明文」这一对数据无法反演
（三种密码模型全部被实测证伪，见 §5），因此
**纯静态从磁盘 exe 还原 `.tp3` 明文不可行**——本报告给出完整的不可行证据链。
可用的明文只有运行期镜像 `image_best.bin`（三点校验全部 PASS，见 §8.2）。

**重要更正**：任务书说「`image_best.bin` 是运行期解密后的主模块镜像，加载基址 0x400000，大小 0xA65000（覆盖 0x400000-0xE65000）」，这些都对；
但「offset = VA - 0x400000」若被理解为「无头 / dump 是从 `0x400000` 的 **第一个节** 开始」，就会与事实不符：
**镜像含完整 PE 头**，`image_best.bin[0:2] == 4D 5A`，index 0 就是 `MZ`，
节表**并非**与原 exe 逐字节相同（见 §2.2：`SizeOfRawData` / `PointerToRawData` / 节名都被壳改写过）。
下述结论全部依赖这个校正。

**第二条重要更正**：「对比文件镜像与运行期镜像」时，**不能用 `disk[x] vs live[x]` 这个口径**。
真正正确的对应关系是分节区的：

```
live[ RVA ]  ==  disk[ RawPtr + (RVA - VirtualAddress) ]         （节区内）
```

本报告在 §2.2 / §2.3 给出逐块的实测百分比。凡是我在早期探索中得到的
「92% 恒等 / 某段因 O(n·m) 搜索超时而未找到」之类的数字，都属于口径错误，
下文已全部替换为可复现的正确口径。

## 2. 运行期镜像与文件镜像的映射关系（先立基线）

### 2.1 不是「无头镜像」

```
disk[0x0000:0x0010] = 4d 5a 90 00 03 00 00 00 04 00 00 00 ff ff 00 00
live[0x0000:0x0010] = 4d 5a 90 00 03 00 00 00 04 00 00 00 ff ff 00 00   ← 完全相同
```

### 2.2 壳改写了节表 —— 整个映射规则必须按「VA 恒等」重算

**这一步是本报告最关键的方法论修正。** 运行期的节表与原 exe **不一样**：

```
DISK    (0x220 起，每项 40 字节)
  #0 .tp3   VSize 0x008A689A  RVA 0x00001000  RawSize 0x00593000  RawPtr 0x00001000
  #1 .tp3   VSize 0x0016DA70  RVA 0x008A8000  RawSize 0x0016E000  RawPtr 0x00594000
  #2 .tp3   VSize 0x0DBB1CC0  RVA 0x00A16000  RawSize 0x00062000  RawPtr 0x00702000
  #3 .tp3   VSize 0x00000031  RVA 0x0E5C8000  RawSize 0x00001000  RawPtr 0x00764000
  #4 .tp3   VSize 0x00009228  RVA 0x0E5C9000  RawSize 0x0000A000  RawPtr 0x00765000
  #5 .tvm0  VSize 0x00004000  RVA 0x0E5D3000  RawSize 0x00002000  RawPtr 0x0076F000
  #6 .tp3   VSize 0x00082000  RVA 0x0E5D7000  RawSize 0x00006000  RawPtr 0x00771000

RUNTIME (live[0x220:0x338])
  #0 .tp3   VSize 0x008A689A  RVA 0x00001000  RawSize 0x008A7000  RawPtr 0x00001000  ← RawSize 被撑大
  #1 .tp3   VSize 0x0016DA70  RVA 0x008A8000  RawSize 0x0016E000  RawPtr 0x008A8000  ← RawPtr = RVA
  #2 .tp3   VSize 0x0DBB1CC0  RVA 0x00A16000  RawSize 0x00062000  RawPtr 0x00A16000  ← RawPtr = RVA
  #3 .tp3   VSize 0x00000031  RVA 0x0E5C8000  RawSize 0x00001000  RawPtr 0x00A78000
  #4 .tp3   VSize 0x00009228  RVA 0x0E5C9000  RawSize 0x0000A000  RawPtr 0x00A79000
  #5 .tp3   VSize 0x00004000  RVA 0x0E5D3000  RawSize 0x00004000  RawPtr 0x00A83000  ← **节名被从 .tvm0 改成 .tp3**
  #6 .tp3   VSize 0x00082000  RVA 0x0E5D7000  RawSize 0x00006000  RawPtr 0x00771000
```

三个改写点：

1. `#0` 的 `SizeOfRawData`：`0x593000 → 0x8A7000`。
2. `#1`、`#2` 的 `PointerToRawData` 被改成**等于 RVA**（映射到「镜像里的相对位置」而不是文件位置）。
3. `#5` 的节名 `.tvm0 → .tp3`（壳把 VM 段伪装成 tp3 段）。

再对比磁盘与运行期的**实际内容**（用 RVA 而不是文件偏移去比！）：

```
disk[0x594000:0x702000]  vs  live[RVA 0x8A8000:0xA15A70]   99.88% 相同 （1495893 / 1497712 字节）
disk[0x702000:0x754000]  vs  live[RVA 0xA16000:0xA78000]   99.02% 相同 （ 320417 /  323584 字节）
disk[0x000000:0x000400]  vs  live[0x000000:0x000400]       98.34% 相同（只差那 17 个被改写的节表字节）
disk[0x000400:0x001000]  vs  live[0x000400:0x001000]      100.00% 相同
```

**⚠ 反例（必须记录）**：`disk[0x000000:0x000400]` 里有 **1007/1024 字节完全相同**。
如果按「文件偏移 = 镜像偏移」这把尺子去量，PE 头会给出 98.34% 的假重合，
而紧随其后的 `0x1000..0x777000` 只有 1.3%~5.9%，两者之间**没有任何过渡**——
这个断崖就是「口径用错」的信号。
**正确的尺子是「按节区 + 各自的 raw→rva 映射」逐块量**，见下表（§2.3）。

这与 `regions.json` / `mem_stdout.txt` 完全一致：

```json
{"base": 4198400, "size": 9072640, "state": 4096, "protect": 32, "type": 16777216}
```
`4198400 = 0x401000`, `9072640 = 0x8A7000`, `protect = 0x20 = PAGE_EXECUTE_READ`。
**保护壳把原始数据装到了 `0x400000`（节区起点）而不是 `0x401000`（RVA 起点）**，多余的 `0x1000` 字节就盖在了 PE 头后面。

### 2.3 映射规则（实测）：`live[VA] ↔ disk[VA]` 恒等 —— 仅对 `.tp3` #0 成立

**逐块口径的实测表**（每一块用各自的 `raw → rva` 映射对比）：

| 块 | 磁盘位置 | 运行期位置 | 相同字节 | 占比 |
|---|---|---:|---:|---:|
| PE 头 + 节表 | `0x000000` | RVA `0x000000` | 1007 / 1024 | 98.34% |
| 头后填充 | `0x000400` | RVA `0x000400` | 3072 / 3072 | **100.00%** |
| **`.tp3` #0** | `0x001000` | RVA `0x001000` | 97029 / 5844992 | **1.66%** ← 压缩/加密 |
| `.tp3` #1 | `0x594000` | RVA `0x8A8000` | 1495893 / 1497712 | **99.88%** |
| `.tp3` #2（已采集部分） | `0x702000` | RVA `0xA16000` | 320417 / 323584 | **99.02%** |

**结论：**

* 只有 **`.tp3` #0**（`0x1000..0x594000` ↔ RVA `0x1000..0x8A689A`）是真正的「加密/压缩」块。
* 其余所有节区都是**纯字节复制**，映射是 `live[RVA] = disk[RawPtr + (RVA - VA)]`，
  **不是**「恒等」也**不是**「某个统一 delta」。
* `.tp3` #1 / #2 的高相似度是另一条重要证据：它说明**壳只对指定的 2 个节（#0、#6）做解压/解密，
  对其余节是原样搬运**，这正是节级（而非页级/驱动级）处理的典型形态。

### 2.4 这不是「采集器伪造」也不是「另一个 exe 版本」——三条独立反证

**(a) 采集器是纯只读，且根本不碰节表。**
`_dyn100_mem.py` 只用 `OpenProcess(PROCESS_QUERY_INFORMATION|PROCESS_VM_READ)` +
`ReadProcessMemory` + `VirtualQueryEx`；全文没有任何 `WriteProcessMemory` / `VirtualProtectEx`。
它把读到的字节**原样**写进 `image_best.bin`（`fh.write(blob)`），不做任何 header 修补。
所以 §2.2 里那些被撑大的 `SizeOfRawData` / 被改写的 `PointerToRawData` **只可能来自目标进程自身**。

**(b) 一次采集就同时看到「被改写的节表」与「9 MB 明文代码」。**
同一个 `image_best.bin` 里，节表说 `#0 RawSize = 0x8A7000`，
同一镜像的 `0x1000..0x8A789A` 又确实填满了 9 MB 真代码（§4 证据 B）。
两者互为印证：**壳是「先改节表、再填满缓存」**，典型的
`VirtualProtect(RW)` / 预取(`prefetch`) 触发路径。

**(c) 运行期节表 = 「把文件映射回它自己那份副本」的自洽化语义。**
三处改动恰好让「按节表展开」的结果与「已解密的实际内存布局」逐一对应。
这是壳/解包器为了自校验而做的自洽化，**内存读取器不会做这种事**。

### 2.5 「同一个明文出现在两个偏移、只差 10」——最干净的证据

`live[0x1000:0x100A]`（RVA `0x1000` 起 10 字节）**在运行期镜像里是 `33 c5 89 45 fc ...`，
  与磁盘的 `f0 22` 完全不同**；而**从 `live[0x100A]` 开始，它才变成磁盘 `0x1000` 处的内容**。

   ```
   disk[0x1000:0x100A] = 00 00 02 00 c4 5a 01 00 f0 22      ← 压缩流头的 10 字节
   disk[0x100A:0x1014] = 55 8b ec 83 ec 50 a1 40 f2 e3 00      ← VA 0x401000 的代码
   live[0x1000:0x1014] = 55 8b ec 83 ec 50 a1 40 f2 e3 00 | 33 c5 89 45 fc 80 3d 2c f7 27 08
   ```

   即：`live[0x401000 + k] == disk[0x1000 + 10 + k]`，**shift = 10**。
   这就是「压缩流比目标位置早 10 字节」的全部来源——**不是加密算法的一部分**。

* 也就是说，`live[0x1000..0x8A789A]` 与 `disk[0x1000..0x594000]` 之所以在 `i ≡ 0xA (mod 0x1000)`
  之外的偏移上「只差一个字节」，是**拷贝的字节偏移**造成的，与加密无关；
  这也解释了 §3.1 里「同一个明文出现在两个文件偏移、只差 10」的算术来源。
* 反过来，这也**排除**了「磁盘与运行期只是同一个 exe 的两个发布版本」的可能：
  两个版本不可能存在「文件偏移 = 镜像偏移 + 10（mod 0x1000）」这种非均匀、非线性的对应关系。
* 那 10 个字节的位移会在 `0x8A789A` 处累积成 `0x1000` 整页——正好是节表里
  `#0 RawSize = 0x8A7000` 与 `VirtualSize = 0x8A689A` 之差（`0x766`）所解释的量级。

## 3. 「同一个明文出现在两个文件偏移、只差一个常数」——压缩流铁证

### 3.1 观测

运行期 `VA 0x401000` 的函数头是：

```
live[0x1000:0x1020] = 55 8b ec 83 ec 50 a1 40 f2 e3 00 33 c5 89 45 fc 80 3d 2c f7 27 08 00 75 1d 68 00 00 00 f0 6a 01
```

在磁盘 exe 里搜索这 32 字节：

| 窗口长度 | 磁盘中的命中偏移 | 命中数 |
|---|---|---:|
| 32 字节 | **`0x100A`** | 1 |
| 16 字节 | `0x100A` | 1 |

用「移 10 字节」的假设反推压缩流位置：

```
live[0x401000] ↔ disk[0x1000 + 10]     →  压缩流内偏移 = (0x1000+10) - 0x100A = 0
live[0x4CBD88] ↔ disk[0x4CBD88 + 0x22F0] = disk[0x4CE078]
```

并且发现：**`live[0x401000]` 与 `disk[0x1000+0x22F0]` 的前 49 字节完全相同**（最长公共前缀 = 49，位置 `0x100A`）。

数值上这是自洽的：

```
D (压缩流 P 的起始文件偏移) ; q=10 ; 
d(P) = (P+10) - 0x100A = P + 10 - (D+10) = P - D          ← 前向扫掠时「重定位」正好抵消
d(Q) = 0x4CBD88 + 0x22F0 - (Q+10) = Q + 0x22F0 - ...      ← 后向扫掠时差一个常数
```

### 3.2 逐字节相同游程长度分布——「同长度密码」的第一道排除

对 `disk[i] == live[i]` 统计连续游程（节 #0 原始数据范围 `0x1000..0x594000`，`shift = 0` 口径）：

| 游程长度 | 游程数 |
|---:|---:|
| 1 | 87 988 |
| 2 | 3 967 |
| 3 | 338 |
| 4 | 17 |
| 5 | 5 |
| **≥6** | **0** |

总计 97 029 字节相等（1.660%），共 92 315 个游程，**最长 5 字节**。

再换一个「对齐到 16 字节」的口径，得到完全相反的结果：

```
identical 16-byte windows at even offsets : 1970
identical  4-byte dwords (4-aligned)      : 1544
```

**这两组数字的落差（游程最长 5、但 16 字节窗口相同 1970 次）本身就是密钥按偏移变化的证据**：
若同一明文块在若干位置重复出现，**每个偏移会用不同的密钥字节**，
于是逐字节比较只能偶然命中，而块内**相对**关系（同一窗口整体相同）反而更容易整体保存。
纯单密钥（同长度固定密码）应当给出「16 字节窗口相同数 ≈ 逐字节相同率的 16 次方」，与此不符。

* **弱压缩（literal 为主）** 会同时产出大量长度 1 的 literal 和**长 literal run**（游程可以到几百字节）。
  实测最长只有 5，**不支持「弱压缩」**。
* **强压缩**（match 几乎吃满）也可能让 literal run 很短——但它会**同时**把整个明文压缩到明显小于原始尺寸，
  而实测 `zlib(live[0x1000:0x594000])` 只能压到 `0x2A8984`（0.477），而磁盘 blob 是 `0x593000`（比例 1.0），
  **blob 比「已经压好的明文」还大 2.1 倍**，因此 blob 不是明文压缩流——它里面还有一层把熵抬回去的变换。
* **流密码（每个明文字节用不同 keystream 字节）** 的相等概率是 `1/256`，游程分布近似几何分布
  `P(len=k) ≈ (1/256)^k` → 最长游程约 3~5，**与实测完全吻合**。
* **块密码（ECB，块大小 B）只会出现长度为 B 的倍数**的游程，实测不符（见 §5.3）。

### 证据 D：解密器**不可能是 exe 自己**——exe 的代码在被解密之前不可执行

**也就是说，节 #0 在 `0x401000` 处的代码无法通过任何固定公式定位。**

后果：

* 任何「在 `0x401000` 就地跑的循环解密器」都**必须能从别处定位压缩流**——
  而它自己就在压缩流里面（`0x401000` 是压缩流首字节，`0x401000+0x2282 = 0x403282` 就是那段重复块）。
* 即便运气好，循环体自身也会在扫过 `/GS` cookie 初始化写过的代码后被破坏。

**因此解密器必须是一个在 `0x401000` 之外、且在被解密数据之外执行的模块。**

## 5. 我们仍然尝试了「静态还原」——3 组算法覆盖扫描（全部失败）

为了让结论可复现，对节 #0 原始数据范围 `0x1000..0x594000` 跑了三组独立模型。

### 5.1 单字节 XOR 模型

判定式：对每个密文字节 `c`，是否唯一存在一个密钥 `k` 使 `c ^ k == p`；
若有任一 `c` 对应 ≥2 个不同 `k`，该 `c` 不可用。

**结果：可用密文字节数 = 0。**（`0 / 0 字节可还原，0.0000%`）

即：**不存在全局单字节 XOR 密钥**。这不是「覆盖不完全」，是模型被直接证伪。

### 5.2 链式/预测器模型（前 0x20000 字节）

| 模型 | 命中 |
|---|---:|
| `disk[i] == live[i]`（基准） | 2408 / 131072 (1.837%) |
| `disk[i] == live[i] ^ live[i-1]` | 1693 (1.292%) |
| `disk[i] == (live[i]-live[i-1]) & 0xff` | 1665 (1.270%) |
| `disk[i] == live[i] ^ live[i-4]` | 1188 (0.906%) |
| `disk[i] == (live[i]-live[i-4]) & 0xff` | 1151 (0.878%) |
| `disk[i] == live[i] ^ (i & 0xff)` | 526 (0.401%) |
| `disk[i] == (live[i]+i) & 0xff` | 534 (0.407%) |
| `disk[i] == live[i] ^ disk[i-1]` | 856 (0.653%) |
| `disk[i] == (live[i]-disk[i-1]) & 0xff` | 730 (0.557%) |
| 16-bit 字相等 | 79 / 65536 |

**全部低于或接近均匀随机基准 `1/256 = 0.391%`。** 没有任何预测器有信号。

### 5.3 压缩流判别：游程分布（决定性）

见 §3.2。实测最长 5 字节、`P(len=k) ≈ 1/256^k`。

* 若是 **ECB 块密码（块大小 B）**，「`disk[i]==live[i]` 的游程长度」必须集中在 B 的倍数附近
  （同一个明文块在多个位置 → 同一段密文块重复 → 逐字节完全相等）。
  实测：游程 1/2/3/4/5 的计数是 `87988 / 3967 / 338 / 17 / 5`，
  在 8 的倍数处**没有任何峰**（长度 8 的游程 = 0），**可以排除 ECB**。
* 若是 **单字节 XOR / 滚动 XOR**，见 5.1/5.2。
* 若是 **字节级流密码**，`P = 1/256` 完全吻合。

**⇒ 结论：`xor(disk, live)` 测得的熵是 7.9226 bit/byte，
1 461 248 个 32-bit 字里有 1 459 725 个互不相同（99.90%）。它既不是低熵也不是周期性的，
因此其中**不含可分离的密钥结构**；解压与解密在这个流里被混在一起，
无法在只有种子密钥 + 已知明文的情况下反演。**

### 5.4 补充：结构上「不可能」的独立证据

```
节 #0 : SizeOfRawData = 0x593000   VirtualSize = 0x8A689A   膨胀比 1.552
live[0x401000:0x594000]  非零 90.72%  (5302818 B)  16914 个 `55 8b ec`
live[0x594000:0x8A789A]  非零 90.47%  (2918268 B)   9142 个 `55 8b ec`
```

磁盘只有 5.66 MB 的槽位，运行期装了 9.06 MB 真代码。
**任何「同长度密码变换」在信息论上都不可能**——密文 5.66 MB 无法无损承载 9.06 MB 明文。
所以这里**同时**存在解压和（可能的）解密，二者都必须先解开才能得到明文。

## 6. 为什么不是「页级 / 驱动级按页解密」

任务的备用假设是「ACE 驱动按页解密，每次访问一页」。以下 4 点逐条排除：

1. **两段同时可见，且都不是按页 fault**：§4 证据 C 的分片对账显示
   `t=0.008 s` 时**整个文件覆盖前段（5 302 818 非零字节）已经就位**，
   而同一时刻 `read_fail_pages = 0`（全部可读、无 guard 页）。
   若是驱动级按页解密，第一次整窗读取必然触发 3000+ 次 page fault，
   既不会 8 ms 内全部完成，也不可能 `read_fail_pages` 恒为 0。
2. **节表被改写**：`live` 的节表里 `SizeOfRawData` 被改成 `0x8A7000`（§2.2）。
   按页解密的驱动不会去改用户态 PE 头；这是**壳的映射器**做的。
3. **PAGE_EXECUTE_READ 而无写入**：`regions.json` 显示 `0x401000` 起 0x8A7000 字节是 `protect=0x20`
   （`PAGE_EXECUTE_READ`）。驱动级按页解密通常保留 `PAGE_EXECUTE_READWRITE` 并挂 page-fault，
   而这里已经是干净的 RX 且内容完整。
4. **有 `.tp3` 之外的证据**：`TerSafe.dll` / `ace-ats32.dll` 明确导入
   `CreateFileMappingA` + `MapViewOfFile(Ex)` + `ReadFile` + `VirtualAlloc` + `VirtualProtect`
   ——**这是「映射文件 → 解压 → VirtualProtect → 写回」的用户态流程，不是驱动页错误流程。**

**结论：既不是自解密，也不是页级/驱动级按页解密，而是 ACE 用户态组件在主映像上做的一次性
「解压 + 解密 + 整块覆盖」。**

## 10. 最终裁定

| 问题 | 答案 | 置信度 |
|---|---|---|
| 哪些节在磁盘上加密？ | `.tp3` #0（文件 `0x1000`，entropy 7.06）**确定**；`.tp3` #6（RVA `0xE5D7000`，entropy 7.34）**中等**（无法与运行期对照） | 见左 |
| 是自解密吗？ | **否**。第一段文件区在 t=0.008 s 就已完成，而那时模块自身一条指令都没跑过 | **确定** |
| 是页级/驱动级按页解密吗？ | **否**。8 ms 内 5.3 MB 全部就位 + `read_fail_pages = 0` + 节表被改写 + 最终是 RX 无 guard 页 | **确定** |
| 谁解密？ | **ACE/TP3**（`ace-ats32.dll` / `TerSafe.dll` / `ACE-DRV32.dll` / `TP3Helper.exe`） | **高** |
| 什么时机？ | **两段式**：第一段在模块加载期（`t < 0.008 s`，早于自身入口）；第二段 `t ≈ 2.5–4.8 s` 填虚拟尾 | **第一段：高；第二段：高** |

| 影响后续工作吗？ | **不影响**。`image_best.bin` 就是明文，三点校验全过 | **确定** |
