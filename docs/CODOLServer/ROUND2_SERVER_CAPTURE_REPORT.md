## 2. `116.130.224.66` 的真正来源：DNS

本轮 PktMon 捕获到了决定性的一帧：

```
q: A? ied-tqos.qq.com.
A 116.130.224.66
```

即：

```
ied-tqos.qq.com  ->  116.130.224.66
```

这不是预置列表、不是 TCLS 下发、不是加密配置，而是**运行时 DNS 解析**。

`TQoS` = Tencent QoS（腾讯网络质量探测）。所以它承担的是 QoS/网络质量
探测职责，不是大厅服务。

## 6. 结论：`[100]` 的真实位置

到目前为止的证据一致指向：

1. `116.130.224.66` = `ied-tqos.qq.com`，TQoS 探测点，**不是大厅**。
2. 客户端在 `18:15:03` 收到它的 UDP 响应后，**没有再发起任何大厅连接**。
3. 唯一持续到后期的连接是 QoS 心跳 `182.50.14.56:8081`。
4. 游戏在 QoS 心跳停止后静默约 50 秒，然后集中 `closesocket` 并退出。

因此 `[100] 无法连接大厅服务` 不是"TQoS 没应答"造成的，而是：
**客户端认为它的启动前置条件没有满足，因此根本没有进入大厅连接阶段。**

最可能的判定位置是 QoS/IIPS 之后的**本地状态检查**，而不是某个远端
大厅地址返回了错误。下一阶段应转向：

1. 解析 `codoMP_client_shipRetailBase.dll` 里 `[100]` 错误码的引用路径；
2. 解析 `182.50.14.56:8081` 的 QoS 报文，确认它上报的是什么、期望什么响应；
3. 在内存中追踪客户端从 QoS 探测结果到"允许进入大厅"的状态变量。

## 7. 关于本地服务器

本轮 `-StartServer` 没有收到包，这不是服务器故障，而是**没有做重定向**。

在**不修改路由/网卡/DNS/防火墙**的约束下，可选的下一步是：

- **仅对 `ied-tqos.qq.com` 做单域名 hosts 覆盖**（`127.0.0.1`），
  这是单点、可回滚的改动，不会影响设备正常上网；但属于系统配置改动，
  执行前需要用户明确同意。
- 或者继续纯被动分析，先挖 `[100]` 的本地判定逻辑。
