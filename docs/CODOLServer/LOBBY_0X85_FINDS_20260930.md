# 大厅 0x85 本轮三项实获（2026-09-30 续）

## 1. 定位了 0x85 处理器的对象（此前一直缺失）

反汇编大厅消息分发器 **`0xBA4430`**（可读镜像
`_mainline\_dyn100_run_20260925_182324\live\image_best.bin`）：

```asm
00BA46AE  cmp al, 0x85          ; 阶段[esi+0x5E8]==3 且 opcode==0x85
00BA46C0  mov ecx, esi          ; this = 连接对象
00BA46C2  call 0xBA3710         ; 0x85 handler
```

⇒ `0xBA3710` 的 `edi` **就是大厅连接对象**。此前 SESSION 文档两次把
`[mgr+0x4F4]` 判为"采错对象"；实际 `[0x08269774]+0x4F4` **正是该对象**：
观察器读它的 `+0x5E8`（阶段）、`+0xC8`（状态）都成立，写 `+0x5E8` 也生效。

运行期实测（本轮新增采样）：

```
req = 0x3C15BF88   s9c=1 5e8=3 644=0 5ec=1
[req+0x620] = 75851563 d79ba3ef e9100a68 ed547a8b b2e9b6f8   ← 20B 握手密钥
```

## 2. `0x85` 校验 = keyed SHA1 MAC（HMAC），不是查表异或

```
0xBA38ED  call 0xBA02A0   ; key20 = codec(obj+0x620)
0xBA38FE  call 0xC73800   ; keyed-hash init，算法名指针 0xD40E7C = "sha1"
0xBA392C  call 0xC73760   ; update([obj+0xB0], [obj+0xAC]-4)
0xBA395A  call 0xC737A0   ; final -> 20B 摘要
0xBA398D  …… 摘要 与 报文末 20B 逐字节 XOR+OR，全 0 才通过 ……
```

`0xC77ED0` 中 `xor cl,0x5C`（HMAC opad）、密钥来自 `[ebx+0x328]`，
进一步确证是带密钥哈希。

## 3. ★ 找到并修正了一个确定性 bug

服务端 `lobby_plain_probe.py` 的 `_T02A0_IDX` **只有 19 项、缺 `0x10`**：

```
服务端(旧): 13 12 09 04 11 01 0A 08 0D 02 0F 03 0C    05 07 00 0E 06 0B   (19)
正确     : 13 12 09 04 11 01 0A 08 0D 02 0F 03 0C 10 05 07 00 0E 06 0B   (20)
```

`codec_02a0` 里 `_T02A0_IDX[... % len(_T02A0_IDX)]` 用 **%19** 取模，
⇒ 下标 ≥13 的 6 个输出字节全错。实测：

```
hs      = 75851563d79ba3efe9100a68ed547a8bb2e9b6f8
旧表算出 = 54b9ea6823b94def7bcec4c2ca488e0ba2c881d9   ← 前 14B 对，后 6B 错
正确算出 = 54b9ea6823b94def7bcec4c2cafe667f32f997cf
```

**已修正** `_T02A0_IDX`（补回 `0x10`，并在注释中记录来自 `0xBA02C2` 的 edx）。

⇒ 这是"`0xBA02A0` 复刻永远命不中"的**直接原因之一**：输入量 key20 本身就错了。

## 4. 仍差的一步（诚实）

用修正后的 key20，把 3 条真实 0x85 帧（386/194/468 字节）的**末 20 字节**当作
tag，对 `{key20, hs, key^0x5C}` × `{帧各切片}` 做 HMAC-SHA1 试算：**仍未命中**。

⇒ 说明除 key20 外，还差**消息语义**：

* handler 是对**收到**的帧做校验（`[obj+0xB0]` 流、长度 `[obj+0xAC]-4`）；
* 客户端**发出**的 0x85 是否用同一公式，尚未证实；
* `-5` / `-4` 这两个偏移的含义未读透。

下一步应直接从 handler 内部取**喂进 `0xC73760` 的真实指针/长度**（同一对象上），
即可一次性确定消息语义。

## 5. 0x85 帧格式（本轮实测钉清）

对 plain-probe 收到的 3 条真实 0x85 帧逐字节分析，帧结构为：

```
u32 frame_len | 0xAB | 0x85 | u32 seq | 8 字节 | ......数据...... | 20 字节 tag
   386          ab     85      1        623caf70…
   194          ab     85      2        7474b13c…
   468          ab     85      3        334fec79…
```

* `0xAB` = 帧类型（与握手期服务端 `sent_83` 的 `c8..00 83` 对应）
* `0x85` = opcode；`seq` 单调 1/2/3 —— 与 `[obj+0x5EC]` 收包计数器一致
* **末 20 字节的熵 4.2、20 字节互异 ⇒ 确是摘要**（非随机填充、非加密体）

## 6. MAC 试算：仍未命中（诚实记录）

用**修正后的 key20** 与多种 key/消息组合做 HMAC-SHA1，对 3 条帧的末 20 字节
逐一比对，**全部未命中**。已试：

| 维度 | 取值 |
|---|---|
| key | `hs`(20B) / `key20` / `key^0x5C` / `key^0x36` / 帧内派生段 |
| 消息 | 全文 / 去 tag / 去帧头 / `body[0:4]+body[8:]` / 各偏移切片 |
| 构造 | 标准 HMAC / `H(k^0x5c‖m)` / `H(m‖k^0x5c)` / `H(k‖m)` / `H(m)` |

⇒ 除 key20 外仍缺**消息语义或密钥来源**。两个未验证的可能：

1. 客户端**发出**的 0x85 与 handler **校验**用的公式不同（发/收两套）；
2. `[obj+0x620]` 不是唯一的密钥源，或 `0xBA02A0` 的 20B 只是中间量、还要与其他字段组合。

**下一步唯一可靠做法**：在 handler 的 `0xBA392C`（`call 0xC73760`）处取**实参指针与长度**
——但本环境禁用断点/调试器，只能用"高频采样 `[obj+0xB0]`/`[obj+0xAC]` 及其指向缓冲"
间接还原（观察器已具备采样能力，需把采样点对准 0x85 到达时刻）。

## 7. ★ 重试结论：`GetThreadContext` 在本环境返回全零（工具缺陷）

为执行"在 `0xBA4430` 下断点取 ecx"，把观察器 `--eip-trace` 改成
**全时段 20ms 采样**、捕获区间收窄到 `0xBA3000-0xBA5000`（该区间所有函数的
`ecx` 都是同一个连接对象），并加了 `EIP_TICK` 心跳。6 次运行：

```
EIP_TICK 确认在跑（threads=2~4）
EIP_HIT  = 0
独立采样器 91,874 次 → EIP 全部 0x00000000
```

三重对照实验（**结构体尺寸已核对为正确**）：

```
sizeof FLOATING_SAVE_AREA = 112   (正确)
sizeof CONTEXT            = 716   (x86 正确)

自检（本进程当前线程）: ok=1 err=0 flags=0x10007  eip=0 esp=0 eax=0 ecx=0 cs=0
对照 notepad          : ok=1 eip=0
游戏客户端            : 91,874 次采样全 0
```

⇒ **`GetThreadContext` 返回成功但寄存器全为 0**，与目标进程是否受保护无关
（连自己的线程、以及 notepad 都一样）。这是当前运行环境的行为，不是 ACE、
也不是结构体错位。

**两个直接后果**：

1. 观察器的 `EIP_HIT` 通道**任何目标上都永远不可能命中** —— 此前所有
   "0 命中"一直被解释为"采样时机不对"，**实际是该通道本身失效**（本轮更正）；
2. 依赖 EIP/寄存器的方法（含"在 `0xBA4430` 取 ecx"）**在当前环境不可用**。
