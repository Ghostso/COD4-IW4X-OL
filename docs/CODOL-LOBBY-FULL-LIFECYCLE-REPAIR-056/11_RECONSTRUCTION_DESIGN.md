## 一、为什么必须重构（而不是继续 R2-R6）

055 取证 + 056 R1 实测共同证明：断裂不是孤立缺陷，而是三层交叠：

### 层 1：入口路由缺损（客户端侧，最上游）

用户在 UI 选择"剧情任务"，客户端却走 `createRoom` 房间流程（056 五轮一致）。
真正的 PvE 直连路径（10-26 路径 A：无建房 → mmstart 带 map → roomChatChannelID=0）
当前**无法通过任何 UI 操作到达**。

### 层 2：房间态锁定（客户端状态机）

056 Run 122010 的新数据点打破了 055 记录的 H1/H2 共线：

| 数据点 | mmstart 带 map？ | 有 `_load.bk2`？ | 在房间里？ | 连接？ |
|---|---|---|---|---|
| 10-26 成功轮（firingrange） | ✅ | ❌ 无 | ❌ | ✅ |
| 056 122010（fav_tropical） | ✅ | ✅ 有 31MB | ✅ | ❌ |

⇒ **"mmstart 带 map + 视频存在"都不足以触发连接；唯一剩余变量 = 客户端是否处于房间态**（建过房 / roomChatChannelID≠0）。
客户端一旦建房，就走"等待房间事件（20 个订阅、成员同步、准备确认、StartGame 消费）"的分支，
而这些下行服务端**全部缺失**（BP-02/03/07），于是永远等不到 → 永不建 socket。

### 层 3：房间下行协议缺损（服务端侧）

- 20 个订阅事件零推送（BP-07）
- 成员列表无协议（BP-03）
- 下行推送从未证明被解析（BP-02，缺畸形对照）
- 准备按钮零上行且客户端本地无反应（BP-01，Flash/Scaleform 不可达）

**结论：单修任何一层都不闭合。** 必须同时：
- 让服务端具备完整的房间下行能力（事件推送、成员同步、状态机镜像），**并且**
- 解决入口路由/房间态锁定（客户端侧行为，见 §四的三条路线）。

## 二、重构目标（验收定义）

### G1 PvE 剧情路径恢复

```
大厅 → PvE 剧情任务 UI → 不建房 → findSessions(playlist=10)
    → mmbook → mmstart(map=<已安装且视频存在的剧情图>)
    → 客户端连 UDP 28960 → NAT/DTLS/connect → 进图 → 过场动画播放
```

### G2 房间路径恢复

```
大厅 → BOT/多人 UI → createRoom → 房间 UI 正常渲染（成员面板/准备按钮）
    → 点准备（本地状态变化 + 11/4 ready 批次）→ 服务端事件回执
    → 点开始 → mmbook → mmstart → 客户端连 UDP 28960 → 进图
```

### G3 状态恢复

退出房间 → 返回大厅 → 再入/切模式/重复进入，无状态残留。

## 四、技术路线（三线并行，各自独立可验证）

### 路线 A：PvE 直连恢复（服务端 + 资产，低风险）

1. **资产**：从外部来源获取 `coop_take_mp_fav_tropical` 等已有 `_load.bk2` 的剧情图
   ——**不需新资产**，只需让 PvE 流程路由到已有视频的图。
2. **大厅服**：`findSessions(playlist=10)` 回已有视频的剧情图（fav_tropical 等在
   `LOCAL_AVAILABLE_MAPS` 内的）。
3. **问题**：入口路由在客户端——用户选剧情仍建房。**需先做 §五.1 实验确认**：
   - 若客户端只在"从未建房"时走路径 A：设计"会话级重置"（大厅返回后清房间态）。
   - 若客户端无论何时都走房间：路径 A 已死，G1 只能靠 G2（房间内直连）实现。

### 路线 B：房间下行协议实现（服务端主体工程）

这是重构的核心工程量，分四个模块：

#### B1. ~~事件订阅解码器~~（**v1.0 作废**——M0/Q2 证明 6/5 是读排队消息，不存在事件编号列表）

#### B2. 事件推送引擎（**v1.0 提为第一优先**）

- 编码：`instant_push_body(kind=11)` 信封 + 位流 `readBits(3)+readData(8)` 格式。
- 路由：信封必须满足 `obj+8 == roomId_lo && obj+0xC == roomId_hi`（0x7E7C90 闸门）。
- **先做 E8 畸形对照**（055 判定的"最便宜、信息量最大的实验"）：
  发一条字段截断的推送，观察客户端行为是否变化。
  - 有变化 → 格式方向对，继续按解码器推。
  - 无变化 → 整段被忽略，需先查信封路由键，再查更外层。

#### B3. 成员同步（11/4 blob 解码，**v1.0 提为第二优先**）

- 解 26 种尺寸（103-245B）的 blob 内部结构。
- 成员列表按 blob 载体实现，**不发明新协议**。

#### B4. 房间状态机镜像

- 服务端维护 `ROOM_CREATED → INITIALIZED → WAITING → READY → START_ALLOWED →
  START_REQUESTED → START_CONFIRMED`（工程标签，实际状态对齐客户端 `0x63C5E0` 状态机）。
- 状态转换全部通过 B2 引擎下发。

### 路线 C：房间态连接解锁（关键假设实验）

**假设：客户端建房后不连 28960，因为它在等房间事件链完成（StartGame 消费/全员 ready/倒计时）。**

实验序列（每轮一个变量）：
1. **C1**：完整实现 B1+B2 后建房，观察是否出现 UDP 连接。
2. **C2**：若仍不连——在 mmstart 后让服务端对 `11/2 leaveRoom` 场景做会话重置
   （客户端退房重选），看退房后走 PvE 是否直连（验证"房间态锁定"）。
3. **C3**：NT 10 内存补丁思路（如 C2 证实锁定在客户端 dvar/标志）——定位
   `roomChatChannelID` 的客户端写点（已有 nt10 补丁框架，第 6 个补丁位置）。

## 六、重构工程结构（服务端）

```
lobby_server.py（重构后）
├── 保留：握手/KDF/bootstrap/档案/钱包/商城（不动，56/56 已验证）
├── 重构：reply_objects 的 21/5（路由到有视频的图）与 11/13（memberCount）
├── 新增 module: room_events.py
│   ├── 订阅表（Q2 解出的 20 编号）
│   ├── 位流编码器（readBits(3)+readData(8) 对称的写入器）
│   ├── 信封路由（roomId 高低 32 位绑定）
│   └── 事件生命周期（订阅→推送→确认）
├── 新增 module: room_members.py
│   ├── 11/4 blob 解析（26 种尺寸）
│   └── 成员表维护与下发
├── 新增 module: room_state.py
│   ├── 房间状态机（对齐客户端 0x63C5E0）
│   └── 状态转换 → 事件推送（调 room_events）
└── 保留：阶段日志（056 已实现的 LOBBY_* 系列，改挂 room_state 的状态转换）
```

每个新模块独立单测 + 与 10-26 成功字节对拍，再进实机。

## 九、本设计的边界

- 不修改战斗服内部（GameState/Snapshot/移动/碰撞/武器/伤害）——056 边界沿用。
- 不修改客户端二进制（除既有 nt10 运行时补丁框架的第 6 补丁候选，需单独授权）。
- 不伪造客户端响应；不用硬编码绕过状态机制造表面成功。
- 所有实机步骤沿用冻结链单发规则与提权 Agent。
