## Q2：6/5 的"20 个事件订阅"不存在 —— 055 BP-07 作废

**证据：** 成功轮与失败轮的 `lobby_tasks.bin` 中，6/5 payload 完全相同（13B）：

```
08 00 00 00 00 | 08 14 00 00 00 | 01 | 01 00
u32 offset=0     u32 maxResults=20  bool  terminator
```

**语义（ol-mod `InstantMessageService.cpp:25-54`，同类参考）：**

```cpp
registry.registerTask(0x06, 5, "Messaging::readQueuedMessages", ...)
task5: input.readU32(offset) || input.readU32(maximumResults) || input.readBool(consume)
// 归档环无插入点 → 两种分页模式在此构建中可观测为空 → 回空应答
```

**结论：**

1. 6/5 = **读排队消息**（分页：offset=0, maxResults=20, consume=true），不是事件订阅。
2. `0x14`=20 是**最大返回条数**，不是事件数量。payload 中**不存在事件编号列表**。
3. **055 的 BP-07（"20 个事件零推送"）基于误读，该断点不存在。**
4. 我们当前回空 ACK 与 ol-mod 行为一致，无需修改。
5. 房间事件推送的真实载体仍是 `11/4` 回显 + `instant_push_body(kind=11)`（BP-02），
   **不是** 6/5。重构路线 B 的事件引擎目标从"解 20 个编号"改为"解 11/4 blob + 位流 type 表"。

## Q1：成功轮与失败轮的完整结构 diff —— 分叉点与方向已定

**样本：** `ONCE_20261026_220815`（成功，69 任务）vs `ONCE_20261029_122010`（失败，100 任务）。

### 1. 完全相同的部分

| 项 | 结果 |
|---|---|
| S1 bootstrap 前 33 个任务（#0-#33 的 svc/task 序列） | **完全一致**（仅时戳类 payload 内容不同） |
| `28/4` 任务参数（519B，127 个 u32 dvar 能力清单） | **逐字节相同** — 它是 dvar-ID 能力表，不是每轮任务参数 |
| `21/5 findSessions` 请求（35B，playlist=10） | **逐字节相同** |
| `6/14 mmbook` 请求（45B） | **逐字节相同** |

### 2. 分叉点（唯一结构性差异）

```
成功：  #54 21/5 → #55 mmbook → #56 mmstart → #58 102/5 → #59 68/8 → 连接
失败：  #55 11/13 createRoom → #56 28/1 → #57 21/5 → #58 mmbook → #59 mmstart
        → #61/62 11/4 → （无 102/5、无 68/8）→ 零连接
```

**失败轮插入了 `11/13 createRoom` + `28/1`；成功轮直接 findSessions。**
分叉发生在 `93/1`（钱包查询）之后、`21/5` 之前——由**客户端本地决策**触发建房。

### 3. mmstart 内容 diff（成功 vs 失败）

### 4. 成功轮的独有尾部（连接触发链）

成功轮在 mmstart 之后多出**两条失败轮没有的请求**：

| 请求 | 成功轮 | 失败轮 | 含义 |
|---|---|---|---|
| `102/5`（10B：`08 02 00 00 00 03 01 03 02 00`） | ✅ #58 | ❌ 无 | storage 服务的某个确认/请求 |
| `68/8`（3B：`10 00 00`） | ✅ #59 | ❌ 无 | 10-26 八轮成功独有的请求（56 run 中仅 7 run 出现） |

**`68/8` 与 `102/5` 是客户端"决定连接"之后才发出的请求，不是连接的触发器**
（它们排在 mmstart 应答之后、NAT 探针之前）。它们的出现/缺席是**结果**不是原因。

## M0 综合结论（设计 v1.0 的修订依据）

1. **服务端没有可修的字段差异。** findSessions/mmbook 请求逐字节相同、
   28/4 相同、bootstrap 相同——分叉完全由客户端本地状态决定（是否发 11/13）。

2. **055 的问题清单需要修订：**
   - BP-07（20 事件零推送）**作废**（6/5 是读排队消息）。
   - "20 个事件编号"不存在，Q2 关闭。
   - 问题 2/3 的载体重新定位到 `11/4` blob 与位流 type 表（47 项分发表）。

3. **H1（mmstart 缺 map）被 056 122010 进一步削弱**（带 map + 有视频仍不连），
   H2（房间态）保持主嫌。但 Q1 显示失败轮与成功轮在 mmstart 之前还有一个
   **未被注意的差异：`2486`（成功=0，失败=1）与 `3265`（成功=18，失败=1）**。
   这两个字段与建房共线，但它们出现在 mmstart 的**同一条文本命令**里，
   是客户端对自己所处模式的自述——`2486 0` 可能正是"非房间直连模式"标志。

4. **重构路线修正：**
   - 路线 B 的第一优先从"事件订阅解码"改为 **`11/4` blob 结构解析**（BP-03）
     与 **E8 畸形对照**（BP-02）。
   - 路线 C（房间态解锁）的证据基础更强了：分叉=客户端本地决策，
     唯一可服务端影响的位置是 `21/5` 应答内容与房间下行链。
