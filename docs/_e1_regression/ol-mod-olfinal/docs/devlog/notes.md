## 后续回看

- 旧会话 `019fa07e-a763-7791-879d-f2d4f8cbcdd1`：项目最初研究阶段。只有在用户要求补写早期历程时再读取，届时用 Git、当时产物和运行证据校正文中的时间线，不直接把会话内容当成事实。
- server-owned snapshot 已从 request/reply 演进为主动 20 Hz server frame：单 EOF 曾让内层 snapshot parser 成功、外层 message parser 却拒绝整包，最终表现为 ack 回滚、reliable 积累、fragment 和 60 秒 timeout；补成嵌套双 EOF 后，可靠命令、snapshot ack 与 delta history 同时恢复。自然运行已达到 `1 full + 1210 delta`、零拒包，并正常渲染地图；相机仍落在 `origin.z + 8` 分支，后续成文要区分“世界可见”与“真实 playing spawn 可玩”。证据：`.runtime/natural-match/20260731_233232/summary.json`。
- 长流程曾在游戏已经自动关闭后仍只显示 `waiting for events`，说明自动点击还不等于完整自动化。`CodolNaturalMatchTrace.py` 现按 phase/heartbeat flush 进度，并在运行中原子更新 `summary.json`，让当前阶段和 terminal outcome 能在上下文压缩后直接恢复。
- usercmd 恢复不能只照着 BO1 猜结构：CODOL `0x005A1BE0` 使用三类 delta 分支、4-bit movement direction 和独立 bit/byte cursor；更容易忽略的是每包 baseline 来自 acknowledged snapshot，而不是固定零值或上一条 cmd。固定 wire bytes 与自然样本均已解出 `commandTime/angles/buttons/movement`，world 已消费最新 cmd，但在 `Pmove` 和真实 playing spawn 恢复前，“输入已进服务器”仍不等于玩家可以移动。
- 动态 yaw 首次进入 playerstate delta 后，客户端把本应结束于 field `18` 的包继续读成 field `19` 并 overflow。问题不在 field-index gap，而在 serializer 把 one-past-last 写成了 `20`；改为 `19` 后，同一自然链路连续接受 delta、ack 和 usercmd。这个故障适合作为后续成文案例：协议恢复不仅要确认字段值，还要锁住“哪些字段被宣告存在”的稀疏边界。
- script menu 首次按普通 configstring 发入 gamestate 时，客户端在 store 前报 `XBOXLIVE_CANTJOINSESSION`。CODOL parser 和运行表最终证明 `4291..4293` 属于 NCS type `8`：menu 名称来自客户端 constant asset，不能作为 raw override 发送。修正后自然 gamestate 恢复；自动化又在 watcher 尚存活时通过 native `Cbuf_AddText` 强制发送 `mr`，服务端闭环到 `changeclass_marines/custom1`。这段经历适合记录“协议字段有值”与“值应由哪一层拥有”之间的区别，以及为何强制调用必须单独标注证据等级。
- menu response 现在会驱动独立的 `WaitingForLoadout -> Playing`，并把 ground 从 none 切到 world；一次捕获中 predicted z 落在 spawn 附近，但相机仍只有 `origin + 8`。`pm_type` field `83` 后续 block 的错位最初被误判为 mixed cursor，固定 padding 只会把故障推到下一个边界；复核 CODOL reader 后才发现真正缺失的是 `changeHints==2` field `82` 的 second-pass zero marker。clean run `20260801_103324` 最终让真实客户端从 `pm_type=4/ground=2047` 稳定过渡到 `pm_type=0/ground=2046`，所有 snapshot block 零 overflow；这适合记录“字段正确不等于完整 reader 顺序正确”，以及运行证据如何迫使我们退出偶然有效的 padding。
- 2026-08-03 的 loadout 调试再次出现同一类教训：menu response 先进入 `Playing`、稍后才补武器，会让 playerstate delta 整段错位。改为 pending request、provider 完整解析、同帧提交 gameplay 与 weapon ownership 后，首次 `custom4` transition 的 25 个 packet 全部被客户端接受。随后发现 frontend resolver 的 `289/290` 只是 cgame 重建前的临时 modular index；完整 CCS 已把这些槽占给 AC130 武器，服务器写入时才会表现成炮艇/C4/空投信号弹。改为 frontend 只缓存配装描述、allocation 后从动态槽 `352+` 连续注册并 remap 后，M4 的身份、HUD、声音、主体和显式附件恢复，但枪管、弹匣、枪托等原版基底仍缺失。继续沿原生数据表查到 `mp/coWeapItemsWEA.csv` 才是默认组件的权威来源；把六个默认件与玩家装备的红点、握把按原生模型槽合并后，客户端 definition 读回 8 个 attachment、10 个 viewmodel，截图才真正显示完整整枪。这个案例适合记录同一个 asset index 在生命周期重建前后不一定拥有同一语义，也适合说明“主体和玩家附件出现”不能代替对默认装配数据的完整校验。
- `ClientSpawn` 的第一版又暴露了另一个容易混淆的生命周期：`loadoutSequence` 表示装备变化，不能兼任 respawn generation。独立 `spawnSequence` 后，world 只有在地图出生点和完整 loadout 同时有效时才原子替换 playerstate；失败不会消费请求，同一请求不会反复传送或补弹，换背包也不会增加 `spawnGeneration`。出生帧只把最新 usercmd 记作角度与按键基线，不执行此前积压的移动和开火输入。clean run `20260803_client_spawn_v1` 中 loadout 前保持 waiting/零 origin，提交后 snapshot 与 predicted 同时成为 generation `1`、weapon `356`，短 forward 的 71 个 packet 全部接受且 clip 始终为 `7`，给这条生命周期边界补上了真实客户端证据。
- 为确认 forced probe 使用的 `custom1` 是否只是临时命令残留，我们在 clean process 里做了只读内存扫描。加载后的 CODOL menu asset 不仅明确包含 `"scriptMenuResponse" "custom1"` 和 `class_custom_1`，还给出了完整范围 `custom1..5`、`class0..4`；据此保留有限 dispatch，同时撤掉原先未经本体证实的更大范围。最初无进度的全内存同步扫描也暴露了工具缺口，后来改为可取消边界更小、带阶段进度和结构化输出的 chunk scanner。
- 客户端回大厅后不会给当前链路发送可识别的 disconnect 命令，旧 server 因而永久保留 `Active/Playing` 并空发 full snapshot。新增 server-owned timeout 后，真实运行在最后入包后 240 秒边界释放完整 slot，snapshot 同 frame 停止；它解决的是可靠兜底，不应写成即时离场协议已经恢复。首次验证的 watcher 时长从 attach 而非 disconnect 起算，导致临界点前 26 秒结束；若这类验证需要重复，应把“armed -> trigger -> 从 trigger 计时 -> slot free 自动停止”纳入 lifecycle，而不是再拼固定时长 watcher。
- playerstate second pass 最初只因 field `83 pm_type` 暴露了 field `82`，完整 235-entry CODOL descriptor dump 后才确认同类字段共有 8 个。writer 因而从单字段补丁改为表驱动 marker 顺序，并借 field `191 delta_angles[2]` fixture 锁住全部 marker；同时 CODOL reader 证明 `delta_angles` 内存是 float、wire full branch 才是 signed short。这段适合记录“修复一个现场症状”怎样演进为可维护的完整协议边界，以及为何不能直接搬 BO1 layout。
- 一次黑屏初始化期的 QuickMatch 低地址崩溃曾被过度归因到 client connection state `0`，并把 PVP UI 导航误列为服务器恢复前置任务。i64 复核显示构造链实际依赖七个对象及 room/room-service vtable；稳定主大厅 state `0` 下验证这些内部依赖后，原生 `QuickMatch -> ready -> client-native allocation` 可以直接闭环。这个反例适合记录“相关状态值不等于安全前置条件”：自动化应验证目标函数真正消费的数据，而不是为了规避一次早调崩溃重新引入 UI 操作。
- 相机的“两个方向闪烁/轴歪”一度被旧 detector 漏报，因为它错误要求角度和位置同时两帧往返。修正检测后，分段 trace 把覆盖定位到 CODOL `sub_51D3B0 -> sub_51D2A0`：server snapshot angles 始终稳定，但未序列化的 11-bit `viewEntityNum/linkEntityNum` 从零 baseline 变成实体 `0`，后者周期性把 refdef 变换到 entity 0 的姿态。写入 none sentinel `2047` 后，真实 parser 和 predicted state 均读回 `2047`，443 帧里角度往返、大跳和 roll 全部归零；眼高仍只有 `8` 是独立的 view-height/Pmove 问题。证据：`.runtime/natural-match/20260801_183415/`。
