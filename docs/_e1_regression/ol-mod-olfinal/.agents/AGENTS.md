## 会话启动与上下文恢复

只有真正开始一个新的 task 时，才依次执行：

1. 完整阅读本文件。
2. 检查 `git status --short --branch` 和最近提交，识别用户改动、已完成工作与当前分支。
3. 跨模块任务先按 tag 查看 `pipelines/codol.dot`，再读取节点链接的 `modules/*.md`；单模块任务直接读取对应 module，仅在需要证据时读取 `research/*.md`。
4. 以当前文件、代码、测试和运行状态为准，不把聊天摘要或研究文档中的历史 `current` 当作实时事实。

### CODOL 恢复补充

上下文压缩、旧消息重放或当前消息明显承接压缩前操作时，先用 Codex App task history 恢复上下文：`list_threads` 只定位当前 task，然后以 newest-first、`limit=10..20` 调一次 `read_thread`；只有最新页从半句、未完成 tool call 或用户纠正中间开始时，才沿 cursor 再读一页。硬上限为两页和约 30 个高信号项，立即自行提炼“刚完成、最新纠正、运行中的命令、准确下一步”，不得请求整段 history、重复读取相同 cursor 或把原文整体注入上下文。聊天 history 是衔接依据；Git、handoff、文件、测试和日志只用于定向核验其中会漂移的事实，不要先反复重读整个仓库，也不要重新回应已经处理过的旧消息。history 接口若一次调用阻塞或超时，立即使用当前注入的压缩摘要或已有 checkpoint 继续，不能无界等待或反复调用。

只有聊天 history 无法表达的运行态，例如 PID、watcher 是否 armed、当前 run 目录和长命令 cell，才在 `.runtime/` 留轻量 checkpoint，并由生命周期工具自动更新。若全局 `AGENTS.md` 可用，其更详细的 task-history 规则继续适用；本段是项目内不可省略的最小动作。

用户只说“继续”时，继续本文件 handoff 中最新未完成工作，不回到会话开头、旧迁移或已证伪方案。

## 项目目标

恢复 CODOL 3.3.3.3 QA 客户端从认证、大厅、玩家状态、匹配、服务器分配到稳定局内游玩的完整链路，并逐步用可维护源码替代归档 Project Nova/Ayria 组件。

优先恢复游戏原生数据流、状态机和序列化边界。能让 UI 暂时前进的固定成功响应、硬编码 gamestate 或手工 snapshot 只能作为标明等级的探针，不能冒充完成实现。

## 决策优先级

出现冲突时按以下顺序权衡：

1. 用户当前明确的目标和知情后的决定。
2. CODOL 本体的 xref、反编译、wire bytes、运行跟踪和可重复测试。
3. 仓库现有模块边界、长期可维护性和数据安全。
4. BO1/KisakBlack、BO2、Ghosts、S1x、IW8、PDB 等参考实现。
5. 开发便利、短期演示效果和历史 workaround。

不能因为参考项目函数名相似就覆盖 CODOL 证据，也不能因为用户最初描述不完整就机械执行明显偏离最终目标的方案。

## 工程原则

- 优先源码化和原生链路，保留闭源组件只作为尚未替代的明确兼容边界。
- 优先复用 CODOL 自身函数、状态和序列化；相关 COD 代码是蓝本，不是可直接绑定的实现。
- 结构尽量接近 COD/BO1 可追溯命名，但以 CODOL 证据和当前代码清晰度为最终标准。
- 恢复 Pmove、snapshot/wire、weapon、collision、entity lifecycle 等 authoritative 核心 primitive 时，**实现或修改前必须同时核对 CODOL 本体、BO1 Windows x86 server 和 Ghosts PS4 x64 server**；不能只看 BO1 或只凭一份社区源码。比较算法、控制流、职责边界、状态所有权和原生代码组织，Ghosts 的 x64 ABI、offset 与 layout 不得复用。BO1/Ghosts 分歧、CODOL 位于两者之间或 Ghosts 平台差异妨碍判断时再加入 BO2。CODOL 已确认的差异必须定向保留；任一必查项不可用时只能标为未完成核对，不能声称已按原生方式恢复。详细执行和落库规则见 `modules/reverse_engineering.md`。
- 将控制面、玩家持久化和 authoritative gameplay 责任分清；是否同进程部署是实现阶段选择，不混淆逻辑边界。
- 不用字符串搜索单独支撑逆向结论。地址、offset、ABI、结构体和调用关系必须有 xref、反编译、动态跟踪或 wire 证据。
- 临时 hook、binary patch 和合成探针必须注明用途、适用 build、验证条件与退出路线。
- 修复规模与风险匹配测试覆盖。共享协议、持久化和跨模块契约需要自动化回归；不把“收到 success”当成 side effect 已恢复。
- 允许清理仓库内无价值的生成物、重复文档和过时实现；删除用户数据、外部参考库或不可再生文件前必须确认范围和价值。

## 证据等级与测试纪律

- **自然链路**：客户端原始 caller 在正常状态与后端消息下进入目标函数。
- **客户端原生强制**：Frida 在正确线程直接调用真实客户端函数，只证明入口之后的行为。
- **合成探针**：自行构造 descriptor、packet、gamestate、snapshot 或状态，只证明解析和协议边界。

运行记录必须注明等级。不能把“客户端进图”直接等同于 authoritative server 已恢复。

交互测试顺序：

1. 确认 PID、活动 EXE hash、加载模块和 baseline。
2. 启动持久日志、状态和 packet watcher，并看到 armed 标记。
3. 再触发自动化或请求用户操作。
4. 保持捕获直到明确成功、失败或超时。
5. detach 前读取最终状态并保存高信号证据。

多轮测试不必机械重启游戏。只有部署新 DLL、状态无法可靠复位、崩溃或测试要求 clean process 时才关闭。

## Git、文件与工具边界

- 当前仓库：`E:\codol_research\ol-mod`；常规开发分支：`v3.3.3.3`。当前 dedicated 实验按本 handoff 使用 `v3.3.3.3-dedicated`。
- 不 push。按完成边界创建清晰的本地提交；除非用户要求，不额外创建分支。
- 不覆盖或回滚未知用户改动。发现并发改动时先理解并与之协作。
- 不提交运行日志、缓存、IDA 数据库、完整游戏文件或随手备份。`distribution/legacy` 中四个固定哈希的 Project Nova x86 组件是明确例外。
- 游戏目录是部署和实验目标，必要时可以修改，但应由脚本或 manifest 记录，不制造层层备份。仓库根部已有原始备份不等于可以无记录覆盖玩家状态。
- CODOL 主 i64 在原路径维护；参考 i64/PDB/MAP 原地使用，不四处复制。各参考 PDB/MAP 的符号已加载进对应 i64，默认直接查询 i64，不重复搜索或导入 PDB。查询参考实现前先确认 build 日期、平台、32/64 位以及 client/server 属性；位宽或平台不同会降低 ABI、offset 和 layout 的参考优先级，但不自动否定算法与调用结构。BO1/Kisak 反编译源码以 BO1 PDB 为基础，但可能受旧版工具限制；出现差异时以当前 i64 的反编译、xref 和调用证据为主，源码为辅。参考库允许正常自动分析保存，手工类型、边界和命名修改保持最小且有证据。
- 当前 i64 自动分析的默认链路是 headless `idalib-mcp`，通过 `tools/reverse/IdalibMcpClient.py` 调用；不要误用需要 GUI 中 `Edit -> Plugins -> MCP` 的 `ida-pro MCP`，也不要要求用户为常规分析手动启动该插件。启动 `idalib-mcp` 时必须用参数数组把含空格的 i64 路径作为单个参数传入，不能拼接裸 PowerShell 命令。对高置信度结论应主动写入函数名、变量名、partial struct 和函数原型；一批 `declare_type/type_apply_batch/set_type/rename/set_op_type` 语义修改完成并校验后，统一执行一次空 `items` 的全库 `force_recompile`，再按需 `decompile`。该操作只清除 Hex-Rays cache，不会立即反编译全库，因此以少量成本避免遗漏 caller 或 type consumer；未修改 IDB 时不必无脑刷新。
- 跨 i64 比对时不得相信刚切换 worker 后未经验证的 strings cache。2026-08-03 已实证同一 idalib worker 在 BO1/CODOL session 之间保留旧字符串地址和内容；每次 `idb_open` 后先用 `server_health` 核对精确 `idb_path/module`，关键字符串必须再用当前 IDB 的 `get_bytes/find_bytes` 验证实际 bytes。优先为参考库使用独立 worker；`find_regex/entity_query` 的字符串结果若未通过 bytes 或当前代码 xref 复核，不得进入命名、文档或实现结论。
- 不确定命名必须分层，并同样适用于 IDA、源码 DTO、local、参数和诊断输出。只知道 offset/位置而不知道语义时使用中性 `unk_XXXX`、`unk_var_*` 或 `unk_flag_*`，不得把猜测写进名称；已有可检验的语义假设时才使用 `hyp_*`，并在相邻位置添加 `[HYP]`，写明当前证据、仍缺什么和可搜索的退出条件。试验命名先局部应用到单个函数或适配器，不能仅凭参考游戏猜测就修改 calling convention、函数边界、共享 global 或 canonical struct layout，也不能让不稳定名称进入 wire/持久化契约。只有 CODOL xref、disassembly、wire 或可重复运行证据闭合相应 producer/consumer 后，才能删除 `hyp_` 或把 `unk_*` 晋级为稳定名称；证伪后立即撤销。类型仍不确定或新 pseudocode 与控制流冲突时直接核对 disassembly。
- Python 用于自动化、探针、截图、状态和数据处理；C++/xmake/MSVC 用于运行时模块。选择工具以可靠性和维护成本为准，不受旧脚本形式约束。
- 当前 xmake CLI 一次只接受一个 target；多目标构建拆成独立命令，避免把第二个 target 误解析为非法参数。
- PowerShell execution policy 禁止脚本时，不要反复直接调用会解析成 `.ps1` 的全局 shim。npm CLI 优先显式调用同目录 `.cmd`，仓库 `.ps1` 继续通过 `powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -File` 和参数数组运行；把已验证入口固化到工具或文档，不让每个会话重新试错。
- Frida 临时文件只进入仓库 `.runtime/frida`，并按既定策略清理。

用户希望长期保留一份可以复盘和分享的中文开发历程。正文应像正常开发者写作一样自然、完整、专业，围绕“在做什么、为什么、最初如何判断、尝试了什么、结果如何、怎样解决、仍缺什么”组织；不写机械摘要、命令流水账、Agent 幻觉或没有改变项目认识的过程噪声。

- 可分享的文章和轻量素材统一放在 `docs/devlog/`，具体取舍与节奏以其 README 为准；它不承担 module、pipeline、research 或 handoff 的权威职责。
- 核心开发优先，不要求每轮即时写长文。只有出现新的已验证边界、改变方向的失败方案、重要工具链改进、值得保留的关键图片或用户明确指定的主题时，才先留一至五行素材；到达里程碑或用户要求整理时再扩写。
- 文章可以在新证据出现后重写和润色旧段落，不保留已经证伪的叙事。没有证据时不补造动机、对话和时间线。
