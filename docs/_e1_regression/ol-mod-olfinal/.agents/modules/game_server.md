## 责任

`src/game_server` 是 x86 dedicated gameplay server 实现，通过 `Com_Frame` hook 驱动网络和 server core，并复用已确认的 CODOL engine primitives。它负责局内 authoritative simulation，不负责 Auth3、仓库、档案、商城或匹配策略；`dedicated` 在本文只指这一职责，不是整个服务端系统的总称。它还不是完整 authoritative world。

实验分支 `v3.3.3.3-dedicated` 引入 `OLMOD_PROCESS_ROLE=combined|client|dedicated` 和 loopback versioned control channel。默认 `combined` 保留旧部署；`client` 只安装最小 `Com_Frame` hook 服务 session capture，不运行 gameplay server；`dedicated` 安装 gameplay hook、监听控制端口并在游戏线程消费 `SessionStart`，避免在 loader lock 或网络线程调用游戏函数。跨进程 descriptor v2 已迁移 authenticated identity、booking command、native playlist/rotation/map/gametype selection 和 item-ID loadout；dedicated 用自身资产表重新解析角色、武器及附件，不读取另一进程的指针、临时 registry slot 或当前角色内存。backend 现在先经 control channel 配置 dedicated session 并查询已绑定 endpoint，再由 `FIND_SERVERS` 向客户端下发该 endpoint；`.runtime/natural-match/20260808_dedicated_collision_world_v23_retry/` 已在真实 `mmstart` 后闭环客户端连接、CCS、gamestate、world spawn 与持续 snapshot。正式 `SessionStart` 路径直接以 descriptor 中的 playlist ID、rotation、map 和 gametype 解析 booking，不再要求 dedicated 读取本地 publisher playlist；只有未提供跨进程 selection 的旧 `combined/manual` 路径保留本地文件兼容读取。

`src/shared/RuntimeLog` 为 game-server 生命周期提供统一文件与可选控制台日志。记录 frame hook/control listener、`ConfigureSession`、`SessionStart`、map/world/CCS/loadout/booking 的关键状态转换，以及最多每五秒一次且仅在计数变化时输出的 client/packet/drop/snapshot/socket-error 聚合；禁止逐帧、逐 packet 或逐 snapshot 输出。文件继续写入 `Ayria/Logs/CodolGameServer.log`，标准 `launch-dedicated` 会为 client 与 dedicated 各自打开独立标题的控制台。

## Snapshot 与 world 链路

`ServerCore::runFrame` 现在以 20 Hz 编排 `SvServerWorld::beginFrame -> ClientThink -> endFrame`，持有 `serverTime`、每个 active slot 的最小 `playerstate`、`clientstate` 和 `ET_PLAYER` entity；`SvServerWorld::runFrame` 只保留给没有 dispatched command 的 lifecycle convenience。`ServerCore::onComFrame` 在每个新 world frame 后主动调用 `SV_SendClientMessages`，再由 `SvUdpTransport::NET_SendPackets` 发送 DTLS packet；active `SV_PacketEvent` 只消费 ingress，不再把 snapshot 绑定成客户端每个 packet 的即时 reply。`SvClientSystem` 为每个客户端维护 32 帧 ACK history，并独立保存首个 baseline frame。有效 ACK delta 同时使用对应 oldframe 和非零 outer delta distance；没有有效 ACK 时 outer delta byte 保持零，但后续 no-delta packet 的 clients/entities 可使用首帧缓存，换图时两套状态一并清除。

CODOL `CL_ParseSnapshot 0x0046D170` 证明 no-delta entity cache 与 playerstate baseline selector 是两套状态：首个 `snapFlags & 8` frame 保存 `unk_7996128`，后续 delta byte 仍为零时把该 cache 交给 packet client/entity parser；但 `MSG_ReadDeltaPlayerstate` 前另读一位，只有该 bit 为一才使用 cache，否则从零状态解码。BO1 没有 ACK oldframe 时同样从零写 playerstate；Ghosts 又明确把 playerstate oldframe 与 `hasAckedBaselineData/nextNoDeltaEntity` 分开。旧实现给 no-delta cached frame 写 playerstate baseline bit 一，第二包进入 `PlayerState_CopyAssign 0x0044F280` 的 `+0x218` embedded state copy 时触发 `0xC0000005`。源码现仅在 `deltaMessageDistance > 0` 时允许 playerstate baseline，同时保留 clients/entities 的 no-delta cache。clean run `.runtime/natural-match/20260811_scene_playerstate_baseline_fix_v5/` 为 parser snapshot/playerstate `11/11`、零 overflow，稳定窗口结束为 `3 full + 404 delta`、ACK `409`，客户端与 dedicated 均保持存活。

CODOL wire contract 已由客户端 parser 和运行 trace 确认：command `0` 后依次为 `serverTime`、delta distance、flags，首帧带 `0x08` server-count flag；随后为 playerstate、packet sound commands、packet clients、packet entities、client infos、glass section 和外层 server-message EOF。playerstate 后的一位由 `CL_ParsePacketSoundCommands 0x0046D060` 消费，并不是 BO1/BO2 的 `MatchState` presence；当前 server 在该 section 写空集合，模式语音后续必须走其真实 sound-command producer，不能把回合状态塞进这里。旧 serializer 没有显式 glass section，曾用两个 EOF 兼容 bit cursor：其中一个可能被 glass reader 当作空状态，另一个留给外层 command loop；只有一个时在 byte-aligned snapshot 上会令外层 parser 把整包判为 illegible，并回滚 `serverMessageSequence/reliableAcknowledge`。当前 writer 已正式写 glass section，再只写一个外层 EOF；所有既有 exact snapshot fixtures 已按实际 bit/raw cursor 对齐更新。

## Usercmd ingress

CODOL 客户端 `CL_WritePacket` caller `0x004602A0` 唯一调用 `0x005A1BE0` 写入 44-byte usercmd delta。CODOL-local xref 和反编译确认 key 为 `checksumFeed ^ messageAcknowledge ^ Com_HashKey(serverReliableCommand, 32)`；command stream 的 bit cursor 与 byte cursor 独立，move count 后依次为最多 32 条 delta usercmd、5 个 predicted-state dword 和外层 EOF。格式包含三种 trailer 为 `7/2/5` 的 unchanged/partial/full 分支；movement 两个 signed byte 在 wire 上量化为 4-bit direction mask，不照搬 BO1 的逐 byte 编码。

`Netchan_Process` 现在完整解码 `commandTime/buttons/angles/movement` 和其余条件字段，并在提交 netchan state 前拒绝 count `0` 或 `>32`、截断、错误 trailer/EOF 与单包非递增 command time。每次拒绝会保留 packet sequence、server/message/reliable ack、decoded command 长度与前 64 bytes、以及完整 reason；`CODOL_GameServerGetClientRejectStatus` 和 watcher 的 `last_reject` 暴露同一诊断状态，避免下一轮只看到累计 reject counter。每个 packet 的默认 usercmd 来自其 `messageAcknowledge` 对应的 server snapshot history：CODOL `sub_5A18E0` 会从 snapshot playerstate 初始化前两轴角度和三个 10-bit 字段，因此不能固定用零 baseline，也不能错误地用上一条 usercmd 代替。当前 field `39` 已为 `weapon` 提供 authoritative baseline；`offHandIndex/lastWeaponAltModeSwitch` 尚无非零 server 状态，继续以零传递。

## 2026-08-16 双客户端自然观察与后续归因

本轮人工自然测试中，客户端本地和远端看到的角色主体与基础运动动画肉眼正常；双客户端操作流畅、基本无回拉，多人同步相对旧故障显著改善。该结果只作为运行观察：尚未做逐骨骼/逐动画或长时延迟量化，偶发短卡暂不提高优先级，也不能据此把角色 producer 或动画链标为 complete。
