## 1. 四问四答（任务完成标准）

### Q1. `0x7FAA20` 如何分派到 `0x6376F0`？

**❌ `0x7FAA20` 与 `0x6376F0` 之间不存在分派关系。**

| 事实 | 证据 | 等级 |
|---|---|---|
| `0x7FAA20` 是**通用延迟激活/补发注册器**（106 个调用点），不含消息 ID | `0x7FAA56 call 0x7FA800`；注册表在 `0x7FA800`（表基 `0xE69CE0`，条目 0x50 字节） | CONFIRMED |
| 任务给的线索 `0x7F4477 mov ecx,0x6376F0 ; 0x7F447C call 0x7FAA20` **位于 `0x7F44B0` 的尾部** | `0x7F456E call 0x7FAA20`，在 `0x7F4503 call 0xB9B0B0` **之后** | CONFIRMED |
| 真正的传递者是 **`0x7F44B0`（出站消息发送器）**，全镜像**只有 2 个调用点** | `0x7F44BE call 0x803830`（transport 单例）→ `0x7F44CB call 0xB7A670`（get_state）→ `cmp eax,2`；调用点 `0x62932F`、`0x62DDF6` | CONFIRMED |
| `0xB9B0B0` **只存储回调、不调用** | `0x00B9B190 mov esi,[ebp+0x14]` … `0x00B9B1D8 mov [ebp-0x1c], esi`（**存入** `[ebp-0x1c]`，无 `call esi`） | CONFIRMED |

**⇒ 答案**：`0x7FAA20` 是**发送后的登记步骤**；
`0x6376F0` 是**随消息对象一同登记、由消息框架稍后调用**的回调。
**该"稍后调用"的具体位置（间接 `call`）本次未定位 —— 这正是剩余缺口。**

### Q2. 哪个消息分支传入 21/5 会话记录？

**✅ 消息分支已定位（2 条，全部确认）：**

| 消息 ID | 发送点 | 载荷 | 与 `0x6376F0` 的关系 |
|---|---|---|---|
| **0x26** | `0x62DDF6`（函数 `0x62DD5F`） | 由回调填充 | **`0x62DDE9 push 0x6376F0`** —— 回调 = 预约槽填充器入口 |
| **0x27** | `0x62932F`（函数 `0x6292AF`） | `mk+0x7470`（预约块整体） | 数据直接是槽数组；无回调 |

**⇒ 答案**：**没有单独一路"传入 21/5 会话记录"的消息分支被证实。**
`0x26` 携带的是**预约槽的序列化结果**（由 `0x6376F0` 填充），
`0x27` 携带的是**预约块本身**。
两者的**数据源仍是客户端的预约槽**，而不是"刚从 21/5 解析出来的记录"。

### Q3. A/B 分别从哪个源字段写入预约槽？

**❌ 未证明。**

本次把它从"未找到写入点"精确化为**结构性的构造事实**：

| 事实 | 证据 | 等级 |
|---|---|---|
| 预约槽由 `0x806B50` 构造，**`+0x168`/`+0x16C` 显式初始化为 0** | `0x00806BA7 mov [esi+0x168], ebx` / `0x00806BAD mov [esi+0x16C], ebx`（`ebx=0`） | **CONFIRMED** |
| 槽数组 B = `mk+0x7470`，**49**（0x31）个槽，步长 0x238 | `0x62C0C7 lea esi,[ebx+0x7470]`；`0x62C0CD mov [ebp+0xc],0x31`；`0x62C0DD add esi,0x238` | **CONFIRMED** |
| 另有数组 A = `mk+0x340`，同样 49×0x238 | `0x62C093 lea esi,[ebx+0x340]`；`0x62C099 mov [ebp+0xc],0x31` | **CONFIRMED** |
| 全镜像内 `+0x75D8/+0x75DC` 的位移**只有 2 次访问，全为读** | `r1_proof.py`（穷尽 `disp32`+SIB，操作码 88/89/C6/C7/FF/01/09/21/29/31/8B） | **CONFIRMED** |
| 访问槽数组 B（`lea [reg+0x7470]`）的位置**全镜像仅 4 处** | `0x62C0C7`（构造）、`0x62CD60`（重置）、`0x637746`（填充 dst）、`0x6379B0`（回调迭代） | **CONFIRMED** |
| 唯一能把数据写进槽的是 `0x637590`（`0x637752 call 0xC3C603`）与 `0x637720` | `0x637746 lea ecx,[esi+0x7470]` + `push [ebp+0xc]` | **CONFIRMED** |
| 二者的薄转发器 `0x6376F0`/`0x637930` 的 this **均为 `[0x82E13FC]`** | `0x637701` / `0x63793F mov ecx,[0x82E13FC]` | **CONFIRMED** |
| **A/B 在 21/5 会话记录中的偏移** | — | **UNKNOWN** |

**⇒ 答案**：**A/B 的来源结构偏移仍为 UNKNOWN。**
但因为槽被清零且无字段级写入，**A/B 的取值只能由"槽填充器的入参"决定**，
这个入参就是 21/5 会话记录 —— 所以缺口是**唯一且明确的**（见 §2）。

### 1.1 ★ 本次追加闭合：vtable 基址与三条派发链（E3 已解决）

**主 vtable 基址 = `0xDC7274`**（`0x62C023 mov dword [ebx], 0xDC7274` 是构造函数写入）。
NEXT-001 记录的两个"vtable"其实是**同一个连续表的两个视点**：

| 函数 | 主 vtable 偏移 | 证据 |
|---|---|---|
| `0x6391E0` | **+0x000** | `0xDC7274 slot0` |
| `0x62F840`（battle-booking 入口） | **+0x03C** | `0xDC72B0` = 基址+0x3C |
| `0x62CD30`（预约槽填充器） | **+0x044** | `0xDC72B8` = 基址+0x44 |
| **`0x632680`（accepted handler）** | **+0x13C** | `0xDC73B0` = 基址+0x13C |

**三条派发链（全部逐指令 CONFIRMED）：**

```
① accepted handler 的入口（与 NEXT-001 的 "+0x13C" 完全一致）：
   007F1554  mov ecx, [0x82E13FC]      ; 匹配对象单例
   007F155A  mov eax, [ecx]            ; vtable
   007F155C  mov eax, [eax + 0x13C]    ; ★ 0x632680
   007F156F  call eax

② 本地 mmbook 分派（"mmbook accepted" 的识别点）：
   007F153F  push 0xDC6724             ; "mmbook"
   007F1544  call 0xC3C678             ; strncmp(…, 6)
   007F154E  jne 0x7F1576              ; 不是 mmbook -> 试下一个命令

③ 预约槽填充器的调用（`0x62CD30` = vtable+0x44）：
   —— 经虚调用进入；本次未定位到该槽的具体 `call` 点（见 §2 缺口）
```

**⇒ 结论：`0xDC72B0` 不是"另一个 vtable"，而是主 vtable 的 +0x3C 视点。
NEXT-001 的 accepted handler 偏移 (+0x13C) 与本次完全吻合，结论不变。**

> ### 缺口 U2-G1″（最终形态）
>
> **待答的是非题**：`0x6376F0` / `0x637930` 这两条回调，
> 是**出站序列化时被调用**（则槽数据来自更早的入站解析），
> 还是**入站响应处理时被调用**（则槽数据就是 21/5 本身）？
>
> **已知**：`0xB9B0B0` 把回调**存入**消息对象（`[ebp-0x1c] = 回调`）而**不调用**；
> 因此调用点在这个消息对象被**投递/处理**的地方。
>
> **两条闭合路径，任选其一：**
>
> **路径 1（静态，约 1 跳）**：
> 从 `0xB9B0B0` 产出的消息对象（栈上 `[ebp-0x44]` 结构，含 `+0x1c` 回调槽）
> 反查它的**消费函数** —— 即谁读取 `[obj+0x1c]` 并 `call` 它。
> 判据：找到 `mov reg,[obj+0x1c]` + `call reg` 的配对。
>
> **路径 2（静态，判定 vtable 归属）**：
> 厘清 `0xDC7274` 与 `0xDC72B0` 的关系（前者由 `0x62C023` 写入，
> 后者的 `+0x100` 是 `0x632680`）。
> 这同时会回答"accepted handler 由哪个虚调用进入"。
>
> **路径 3（动态，最小配对抓包 —— 最快）**：
> 同一会话下取
> ① `21/5 findSessions` **响应字节**（尤其 field 2 的 u64、field 6 的 16B）；
> ② 紧接着的 `6/14 mmbook` **完整 payload**。
> 两者字节对齐即可**直接读出** A/B 在会话记录中的偏移，**绕过** `0xB9B0B0`。
> 既有抓包只有 ②，**缺同一会话的 ①** —— 这是需要补的**最小字段**。

## 6. 一句话实施门结论

> **传递机制已闭合（`0x7F44B0` 发消息、`0x6376F0` 是随消息登记的回调；
> 槽在构造时清零，只能由填充器整槽写入，填充器 this = `[0x82E13FC]`）。
> 但"A/B 在 21/5 会话记录中的偏移"未闭合，且新发现 vtable 归属矛盾（`0xDC7274` vs `0xDC72B0`）。
> 故本门判定：暂不实施。剩余工作收敛为两件小事：
> ① 找 `[obj+0x1c]` 回调槽的消费点；② 厘清 `0xDC7274`/`0xDC72B0`。
> 若可取得同一会话的 21/5 响应 + mmbook 配对抓包，可一步绕过 ①。**
