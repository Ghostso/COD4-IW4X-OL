## 1. 四问四答（任务完成标准）

### Q1. `[obj+0x1C]` 的真实消费点在哪里？

**❌ 前提被证伪：`[obj+0x1C]` 不是回调槽，而是 byte 标志。**

| 事实 | 证据 | 等级 |
|---|---|---|
| `0xBA72C0` 把**参数低字节**写进 `[esi+0x1C]`（`mov byte`，不是 dword） | `00BA7306 mov dl,[ebp+8]` → `00BA7309 mov byte [esi+0x1c], dl` | **CONFIRMED** |
| 相邻 `+0x1D` 同样是一个 byte | `00BA7318 mov byte [esi+0x1d], dl` | **CONFIRMED** |
| 消息对象 vtable = `0xD5A64C` | `00BA7312 mov dword [esi], 0xD5A64C` | **CONFIRMED** |
| 消息对象真正的回调槽是 **`+0x28`** | `00BA7328 mov dword [esi+0x28], eax`（初始 0）；`00B9B1D8 mov [ebp-0x1c], esi` | **CONFIRMED** |
| `call dword ptr [reg+0x28]` 的真实命中 = **0** | `x2_cb.py` 全量检索；两处命中逐指令复核为**反汇编错位假命中** | **CONFIRMED** |
| `[obj+0x28]` 的框架消费点 | — | **UNKNOWN** |

**⇒ Q1 答案：`[obj+0x1C]` 无消费点（它不是指针）；
`[obj+0x28]` 才是回调槽，其消费点本次未定位。**

### Q2. `0x6376F0` 与 `0x637930` 分别在什么上下文执行？

| 函数 | 上下文 | 消费点 | 等级 |
|---|---|---|---|
| **`0x637930`** | **消息 `0x27` 的完成/失败回调** | **`0x6292B0` 的 `0x62934C call ebx`（发送失败时同步调用）**；三个调用点 `0x632721`/`0x62F94A`/`0x62FBD0` 全部 `push 0x637930` → `call 0x6292B0` | **CONFIRMED** |
| `0x6376F0` | 消息 `0x26` 的回调（`0x62DDE9 push`）；另有延迟注册（`0x7F4477 mov ecx`） | **未定位** | **UNKNOWN** |

**⇒ Q2 答案：`0x637930` 的上下文已完全闭合；`0x6376F0` 仍未闭合。**

**两条链最终都汇聚到同一个槽写入器：**

```
0x637930 -> 0x637720  (dst = mk+0x7470, memcpy)
0x6376F0 -> 0x637590  (dst = mk+0x7470, memcpy)
```

### Q3. 预约槽 A/B 的实际源字段是什么？

**❌ 未确定**，但本次把缺口压缩并**排除了一条候选路径**：

| 事实 | 证据 | 等级 |
|---|---|---|
| A/B 在槽内位置 | `mk+0x75D8/+0x75DC + k*0x238`（= 槽 `+0x168/+0x16C`） | **CONFIRMED** |
| 构造时清零 | `0x806BA7` / `0x806BAD` | **CONFIRMED** |
| 字段级写入点全镜像 0 处 | 穷尽检索（disp32 + SIB） | **CONFIRMED** |
| 填充器只做整槽 memcpy | `0x637746` + `0x637752 call 0xC3C603` | **CONFIRMED** |
| **`0x62F840` 槽分支只读 A、不写**（本次新排除） | `0x62F9C8 lea eax,[..+0x75d8]` → `0x62F9D0 call 0x801600`（读） | **CONFIRMED** |
| 源记录字段偏移 | — | **UNKNOWN** |

**★ 关键推论（HIGH）**：
`0x6292B0` 的**失败**分支以 4 个 0 + 1 个 edx 调用回调
（`0x629343..0x62934C`）⇒ **失败路径不可能提供有效槽记录**。
⇒ **有效数据只可能来自"发送成功后的响应/超时路径"**
⇒ **A/B 来自消息 `0x27` 的响应负载**，而不是客户端本地计算。

### Q4. 是否有充分证据实施最小 accepted 响应修复？

**❌ 没有。** 三条理由：

1. **仍不知道服务端该回什么值**（A/B 在响应中的偏移未定位）。
2. **不得试填**（任务禁止）；本次**没有**任何证据把 A/B 绑定到 `SessionId`/`roomId`。
3. **即使知道了这两个值，也还不知道 accepted 体的确切字节布局** ——
   而 NEXT-002 已证否四种"改 envelope 元数据"的尝试。

## 3. 唯一剩余缺口（可静态闭合）

> ### 缺口 U2-G1⁗
>
> **待答**：**消息 `0x27` 的响应处理函数**（发送成功后由消息框架调用
> `0x7FAA20` 所注册表项的位置），以及其负载中对应槽记录的字段偏移。
>
> **为什么这是唯一缺口**：
> - 出站侧已定位到指令级：`0x7F44B0` 尾部
>   `0x7F4551 push 0x7F4330`（完成回调）+ `0x7F456E call 0x7FAA20`（延迟注册）；
> - 入站侧 = 由该注册表项触发；`0x7FA800` 是注册表实现
>   （表基 `0xE69CE0`，条目 `0x50` 字节，扫描 `0xE56FFE0..0xE5713E0`）。
>
> **下一步最小工作（纯静态，约 2 跳）**：
> 1. 解析 `0x7FA800` 的**条目结构**（`0x50` 字节）与**查找键**
>    （`0x7FA83E mov eax,[ecx*8+0xE4E20C]` + `shl eax,4` + `add eax,0xE69CE0`）；
> 2. 找出 `0x7F456E` 注册的处理器在响应到达时如何被调用，
>    并确认其负载 → 槽记录的映射。
>
> **该缺口是纯静态可闭合的** —— 出站登记点已在指令级；
> **只有在 `0x7FA800` 条目结构无法解析时**，才需要 §4 的配对抓包。

| 文件 | 位置 | 现状 | 待改为 |

**纪律**：① 单变量；② 独立开关、默认关、可回滚；③ **不碰 `SEC_KEY`**；④ **不猜字段**。

### 5.1 一个新增的实现风险（本次发现）

`0x6292B0` 在**发送失败**时会以 `(0,0,0,0,edx)` 调用回调 `0x637930` ——
而 `0x637930` 会把入参整槽 memcpy 进槽数组。
⇒ **若服务端不响应或响应失败，客户端可能把"全 0 记录"写进预约槽**，
从而让 A/B 变成 0。
**这意味着：实现修复时不仅要"回对值"，还要确认响应路径被真正走到**
（即 `0x629337 test al,al` 之后走成功分支，而不是 `0x62934C` 的失败分支）。
