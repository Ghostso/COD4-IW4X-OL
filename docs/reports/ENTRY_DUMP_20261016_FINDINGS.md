> 方法：只读。触发式全片转储（nt10 早期句柄）+ 50ms 定点时间序列采样 + 静态反汇编交叉验证。

## 0. 一句话结论

**在两次独立的实机运行中，客户端在入场后的内存里从未出现过我方快照的任何字节（连 16 字节明文前缀都 0 命中），
`client+0x3BE4`（`9→10` 的唯一门）在 50ms 采样下从未为 1。**

也就是说：**这不是"快照解析了但校验没过"，而是快照根本没有到达客户端的解析路径。**

## 1. 抓取方法（本轮改造）

上一轮 `memlinear_after=420` 实测是**进对局（stage 6）之后约 6.5 分钟**才抓的，早已错过跃迁。

本轮改为两级：

1. **触发式全片转储** —— 轮询 `cls.state`(VA `0x76446B0`)，首次 `>=9` 立刻转储，
   之后按 `0/+6/+12/+20s` 各再抓一份，夹住"进对局"的人工时间抖动。
2. **50ms 定点时间序列采样** —— 用 nt10 早期句柄高频只读 `cls.state` 与 `client+0x3Bxx` 一族字段，
   记录每次变化。这是唯一能区分"`+0x3BE4` 从未置位"和"置位后立刻被消费清 0"的手段
   （该标志是"置 1 → 立即清 0"的瞬时握手）。

### 2.3 快照"零出现"的精确定义

对每份转储做**递增长度的前缀搜索**（用快照 body 明文段，从偏移 8 起，避开每次不同的 netchan 头）：

| 搜索长度 | 133 / 120 / 96 / 80 / 64 / 48 / 32 / 24 / **16** 字节 |
| --- | --- |
| 命中 | **全部 0** |

掩码后的形态同样检索（`seq=4..12` × 两种 mask 变体）→ **0 命中**。

**对照**：gamestate 的明文 8 字节头**命中**（`0x9BD38 / 0x9BDA0 / 0x9DFE0 / 0x17CADC`）。
说明网卡/消息缓冲里残留的是 gamestate，而**我方快照连缓冲态都不存在**。

> 复核：上一轮报告里 `…ff0f05` 那个命中（本轮在 `0x15D351`）仍只是
> gamestate configstring 文本前的偶然字节序列；其**前 8 字节 0 命中**、周边无快照结构，**不是快照**。

### 2.4 ack 轨迹（注意口径，勿过度解读）

本轮服务端 `GAMESTATE TX` seq ∈ {1,2,3,29}，`SNAPSHOT TX` seq ∈ {4 … 9282}（数千条）。
客户端 **ack 只到 29**（= 最后一个 gamestate 的 seq）。

⚠️ **但 ack 本身不能证明快照被丢弃**：netchan 的 `ack` 只在处理**可靠(reliable)**消息时推进，
快照是**不可靠(unreliable)**消息、不进入 ack。所以 `ack=29` 只说明
"最后一条被完整处理的可靠消息是 gamestate 29"，**不能**推出"快照没到"。

本节仅作旁证；判定快照是否送达要靠 §2.3 的内存检索与 §3 的状态机证据。

## 3. 状态机侧：`9→10` 的门确实从未被满足

```
0x515F81  cmp ecx, 9                     ; cls.state == 9 ?
0x515F84  jne 0x5161F0                   ;   否 -> 返回
0x515F8A  cmp dword ptr [esi+0x3BE4], 0  ; 门
0x515F91  je  0x5161F0                   ;   ==0 -> 返回   ★ 我们卡在这里
0x515F98  mov dword ptr [esi+0x3BE4], 0
0x515FA2  call 0x515C30                  ;   内部 0x515D4E 置 0xA
```

`+0x3BE4` 全 `.text` 只有三处触及：`0x515B15`(清0) / `0x515F98`(清0) / **`0x472810`(唯一置1)**。
`0x472810` 位于函数 `0x471E90–0x47282A`（由 opcode 0 分派块 `0x473BFD` 调用）——
它的三个"提前返回"与三个"跳到尾声 `0x47281A`、跳过置位"的出口，
共同决定了 `+0x3BE4` 是否被置 1。

**实测：50ms 采样全程未观察到置位 → 该函数要么没被调用，要么每次都从跳过置位的出口返回。**

## 4. 附带发现：客户端持续重发 `qlive.tryclose`

本轮每个 netchan 包都携带同一条 reliable 命令（body 52B）：

```
4a 01 00 00 00 71 6c 69 76 65 2e 74 72 79 63 6c 6f 73 65 00 02 00 ...
              q  l  i  v  e  .  t  r  y  c  l  o  s  e
```

- 生成点 **`0x60D7A1`**（`cmp byte ptr [eax+0xdc6020], 0` 的扫描循环），
  从一个以 `0xDC6020` 为基址的逗号分隔命令表取出。
- 以 `relAck=1 / reliable=1` 持续重发（clientSeq 观察到 1154+），说明客户端在**等一个没等到的回应**。
- [推断，待证] 像入场失败后的重试/关闭路径。**尚未证明与快照被丢弃有因果关系**。

## 6. 结论与下一步

### 6.1 本轮确认（两次独立复现）

1. `cls.state` 在 stage 6 后约 6 秒到 9，并**稳定保持至少 100 秒**。
2. `client+0x3BE4` **从未置位**（50ms 采样 + 8 份转储，双重复现）。
3. **我方快照字节在内存中零出现**（连 16B 明文前缀都无）。
4. `ack` 停在 gamestate 的末序号（29）——但如 §2.4 所述，这只覆盖可靠消息，**不作为快照未送达的证据**。

### 6.2 诊断更新（重要）

原表述"客户端从未**解析**快照"可以收紧为：
**快照根本不在客户端的接收/解析路径上** —— 既不在消息缓冲，也不在解析态。

因此 **P1"补全快照五段"的优先级应下调**：内容正确性在"快照是否送达"之前是无关的。
先补内容，只会得到一个同样不被读取的帧。

### 6.3 建议的下一步（重排优先级）

- **P0**：确认**我方快照包是否真的发出并到达**客户端的 netchan 层。
  最小判据：把同一份转储里"服务端已发出的快照 seq"与"客户端 netchan 结构里能看到的上界"对照；
  或直接在服务端统计 `SendData` 的成功/失败（当前日志只有 `SNAPSHOT TX`，没有发送结果）。
- **P1**：查 `0x60D7A1` 的命令表选择条件，判定 `qlive.tryclose` 重发与快照被丢弃是否同源。
- **P2**：若确认快照确实未送达，回到**传输/分帧层**；若确认已送达但被丢弃，
  再回到 `0x473A50` 分派器与 opcode 0 的解析入口。
