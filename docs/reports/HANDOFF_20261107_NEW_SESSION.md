## 2. 已经查实、可以直接用的事实（不必重查）

**协议面（客户端已接受）**
- NAT(29B) / CT1 init(16B) / CT2 cookie(38B) / CT3 KX(219B) / CT4 ACK(114B) / CT6 数据帧（HMAC+SHA1 派生 + AES-CTR 解密）**全部通过**。
- OOB：`getchallenge` / `connect` / `stats` / `heartbeat` / `gamestateupdate` 全部被客户端接受并回应。
- 传输密钥真源：**客户端在 A-phase(`0x7F4630`) 现场生成 16B**，写进 `21/1` 请求体（marker `13 08 10 00 00 00` + 16B），**每次 createSession 都重新生成**。
  ⇒ 大厅必须**转发**它给战斗服；战斗服必须在**每次会话**重读（已在 `battle.c` 的 KX 前加，Release `40D07870…`，**未实机**）。

**客户端侧（静态，已双重核验）**
- `0x7BFD70` **无条件 return 1** ⇒ 客户端必然把「会话 id → 那 16B」插进 `N+0x40`。
- `0x7F5B50`（解析战斗服地址 + 挑槽）→ 要求 `0xBB2520` 返回 3 → 调 `0xBB2DD0` 登记；**`!=3` 只是跳过登记，两条路都继续返回成功** ⇒ 这条路是"宽进"的，**没有静默失败的窄门**。
- `[0x76446B0]` 在 exe 里**只有 5 个写点**，值 {0,3,4,7}（与**运行期 `.text` 内存捕获**逐字节比对一致：240/240 字节出现、同一批写点）。`Base.dll` 完全不引用它。
  ⇒ 推进到 9/10 的代码**不在我们能读到的原生代码里**。
- 加载页是 **Flash 影片**：exe 只按元素 id 喂值（276 项表 @ `0x5A99BC`，索引 = `id-30`；元素 **204** = 上面那句文案，取值器 `0x60C190` ← `0x477F50` 读 `[0x76446B0]`）。**"撤页"不在 exe 里。**

**booking**
- `6/14` 载荷 = `"mmbook <id> <AQAAAAAAA=> 0"` → 大厅命中 `mmbook` → 回 `'mmbook accepted'`。
- `mmbook accepted` 是 `0x632680`（**booking 超时检测**）的判据。
- `6/14` 只出现在 **coop/PvE 路径**（客户端先发 `findSessions`，大厅回 280B 单人 coop 房间，playlist=10 → `coop_training_mp_cargoship`）。
