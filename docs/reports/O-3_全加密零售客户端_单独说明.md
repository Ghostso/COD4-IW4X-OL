# O-3 单独说明（自包含，可独立交付）

> 本文不依赖任何其它对话。若你只拿到这一份文件，读它即可知道 **O-3 是什么、为什么重要、能对它做什么、不能对它做什么**。

## 0. 先解释 "O-3" 这个名字从哪来

"O-1 / O-2 / O-3 …" 是**本项目内部的对象编号**，不是 CODOL 官方术语，也不是任何公开资料里的叫法。

- 出处文件（唯一权威）：
  `D:\BaiduNetdiskDownload\使命召唤OL\FULL_ENCRYPTED_CLIENT_TARGET_ADJUDICATION.md`
- 出处位置：该文件 **§2.1「六类对象」表格**。

该表把和我们打过交道的**六种"客户端对象"**做了区分，因为历史上多次把它们的身份、哈希、用途混为一谈，导致过错误的结论和错误的补丁键值。**编号本身只是"第 N 个被登记的对象"**，没有其它含义。

六个对象速查（**完整定义见 §2**）：

| 编号 | 一句话定义 | 与本项目的关系 |
|---|---|---|
| O-1 | 历史**去壳**样本 `out.exe`（build 1649370） | 逆向来源对象，**不是**运行前提 |
| O-2 | 3.3.3.3 **QA 旧客户端** | 旧基线，其钩子**故意不装**在本客户端上 |
| **O-3** | **我们实际运行的、全加密的零售客户端** | **本文主题** |
| O-4 | **运行时映像**（进程内 PE 头 + 代码字节） | 门禁真正判定的对象，目前无证据 |
| O-5 | 哈希 `E3823FD6…F37B` | **归属未裁定**，三方说法互斥 |
| O-6 | `OL.exe` | 第三个零售对象，**本机没有**，仅登记 |

> **关键点**：O-3 是**磁盘上的那个文件**；O-4 是它**跑起来之后在内存里的样子**。二者不可混为一谈，这是本项目历史上最容易犯的错误。

## 3. 为什么 O-3 是唯一权威（本项目最核心的一句）

> **O-3 是我们唯一真正执行的对象，因此它是 3.19 线格式（wire format）与运行时行为的唯一权威。**

推论（每条都必须遵守）：

1. **服务端要"对得上"，就必须以 O-3 的实际行为为准** —— 不是以任何旧版服务端、任何开源重实现、任何历史样本为准。
2. **O-1（去壳 `out.exe`）派生的 145 个 RVA、82 处前缀守卫、25 个补丁点，全部只是"候选"**。它们**必须**在 **O-4（运行时映像）**上被逐字节验证，才能用于 O-3。
3. **O-2（3.3.3.3 QA）的 8 个钩子故意不装在 O-3 上** —— 因为那是旧基线，键值不匹配。
4. **不得**因为 O-3 与 O-1 的 `TimeDateStamp` 相同、`FileVersion` 相同，就宣称二者等价。该文件 **§2.2 明文禁止**这种推断。

### 3.1 O-3 与 O-1 的实测差异（同一张表）

| 字段 | O-3 实测 | O-1 期望值 | 比较 |
|---|---|---|---|
| `TimeDateStamp` | `0x6096930A` | `0x6096930A` | **相同** |
| `FileVersion` | `1649370` | `1649370` | **相同** |
| `SizeOfImage` | `0x0E659000` | `0x0E5D6000` | **不同**（差 `0x83000`） |
| 段表 | `.tp3`×6 + `.tvm0`（加壳） | 无这些段（去壳） | **结构性差异** |

**可支持的推断（标注为推断，不是结论）**：O-3 与 O-1 很可能属于同一构建。
**明文禁止由此推出的结论**：
- ❌ 不得宣称 O-3 的**运行时映像**通过门禁 A；
- ❌ 不得把 O-3 的 SHA-256 写成 `E3823FD6…` 或 `044c396c…`；
- ❌ 不得删除或放宽任何 RVA / 前缀 / 尺寸校验；
- ❌ 不得把"同 `TimeDateStamp`"当作"同一构建"的证明。

## 4. 为什么 O-3 不能在磁盘上反汇编

O-3 的代码段被 **`.tp3` 壳**替换。对磁盘文件直接反汇编，得到的是**壳的字节**，反汇编输出是垃圾（典型如 `daa`、`pop ss` 这类无意义指令），**看不到任何原始游戏逻辑**。

所以：
- **不能**直接对 `COD OL\codoMP_client_shipRetail.exe` 做静态反汇编来定位网络解包器、快照解析器等；
- **不能**指望用它来读 3.19 的线格式常量。

## 5. 应该用什么代替（O-3 的可反汇编替身）

**用 O-3 运行起来后的运行时映像（即 O-4 的一次成功快照）。**

落盘文件：

```
D:\BaiduNetdiskDownload\使命召唤OL\CODOLServer\_mainline\_dyn100_run_20260925_182324\live\image_best.bin
```

| 字段 | 值 |
|---|---|
| 大小 | `10,899,456` 字节（`0xA65000`） |
| **SHA-256** | `17CEF6E0A5E7B8D14FB97B5FDD846061187C6A722CFA3C5D432BEE37872FD045` |
| 身份交叉 | 与 `048` 报告登记的 **S-IMG** 一致 |

**必须使用的地址约定**：
- `file_offset == RVA`
- `VA = RVA + 0x400000`

（该约定已由三条独立证据交叉验证：`046` 的 TQOS 调用图 4/4 精确命中；5 处字符串偏移；进程快照 xref `0x14B5F7` 对应 `046` 记录的 `0x14B5F8`。）

**可用性结论**：
- 第一代码段**完整可读**，含 **26,056 个真实 `55 8B EC` 函数序言**；
- 第 2、3 段是数据（0 个序言）；
- **所有代码都在第 1 段**。
- 注：`048` 报告中的阻断项 `E-048-1`（"段 3 RVA `0xA16000+` 不可读，可能藏着对局内解析器"）是**误判** —— 段 3 有 0 个函数序言，那 `0x13000` 字节缺失是 C++ RTTI 字符串（`AVCodoCefClient`、`Scaleform`…），44% 为零。**不存在藏在段 3 的解析器。**

**红线**：`image_best.bin` 是**只读分析对象**。任何分析脚本只能读它。同时它**不是** O-3 本体的替代身份 —— 它是"O-3 某一次运行的内存映像"，用于静态分析，不用于证明磁盘文件身份。

## 7. 纪律红线（对 O-3 操作时）

### 7.1 绝对禁止

- ❌ 任何针对 **ACE / TenProtect** 的绕过、停止、配置修改或规避（历史上曾导致 BSOD `0x01010002`）。
- ❌ **Frida 注入**。
- ❌ 修改客户端 `.text`。
- ❌ 在游戏/平台进程上下断点。
- ❌ 修改 `COD OL\` 下的任何原件（**全部只读**）。

### 7.2 允许

- ✅ `ReadProcessMemory`（只读）。
- ✅ **早期句柄**只读转储（见 §7.3）。
- ✅ 静态反汇编（对 `image_best.bin` 等离线副本）。
- ✅ 全部离线测试、服务端逻辑、协议序列化、回环网络。

### 7.3 「早期句柄」关键事实（否则读不到内存）

**外部 `ReadProcessMemory` 在 ACE 起来之后必然失败**：`OpenProcess` 成功、`VirtualQueryEx` 成功，但 `ReadProcessMemory` 返回 **err=5（拒绝访问）** —— 连 `0x400000` 的 MZ 字节都读不到，即使句柄权限开到 `0x1F0FFF` 也没用。

项目源码（`REF_LOBBY_KIT\nt10.py:1584`、`:2141`）已记录：

> **必须使用早期句柄**：客户端受 ACE/TP3 保护，**后来打开的句柄会被拒绝（err=5）**，早期句柄实测在约 **t=6 秒**前仍可读/写。

**已验证可用的转储流程**：
1. 创建 `REF_LOBBY_KIT\memlinear.on`（空文件 = 开启）；
2. `memlinear_after.txt = 400~600`（进入对局后再开始）；
3. `memlinear_outdir.txt = <一个全新的目录名>`（**绝不要**指向已有的 `mem_linear_20261007_134406` 基线）；
4. 按固化启动链启动 → `nt10` 会用早期句柄转储全部内存。

切片命名规则：`r_<VA8>_<SIZE8>.bin`，**文件名第一个字段就是该块的绝对 VA**。

**必存的基线**：`REF_LOBBY_KIT\mem_linear_20261007_134406\`（42 GB，**用户要求保留**，不得覆盖）。

## 8. 常见错误（本项目已经犯过、必须避免）

1. **把 O-3 与 O-1 混为一谈**：O-1 的 RVA 只是候选，必须在 O-4 上验证。
2. **把 O-3 与 O-2 混为一谈**：O-2 是 3.3.3.3 QA 旧基线，钩子键值不同，故意不装。
3. **把"同 `TimeDateStamp`"当作"同一构建"的证明**：明文禁止。
4. **直接反汇编磁盘上的 O-3**：只会得到 `.tp3` 壳的垃圾指令。
5. **用 ACE 起来之后的句柄读内存**：必然 err=5；必须用早期句柄。
6. **拿 2697 / COD4x / IW4x / AlphaBuild 的格式当权威**：只可参考原理。
7. **把 O-5 的 `E3823FD6…` 当成 O-3**：O-5 归属未裁定，三方说法互斥。

## 9. 现在对 O-3 应该做什么（下一步方向）

1. **优先**：从实机内存转储中补齐 **O-4 运行时证据**（进程内 PE 头 + 关键 RVA 字节 + 绑定结果日志），这是门禁 A/B 真正判定的东西。
2. **其次**：在 `image_best.bin` 上继续静态分析（地址约定 `VA = RVA + 0x400000`），目标是定位：
   - `cls.state` 的**写入者**（`.text` 中只有 5 处直接写 `0x76446B0`，值为 3/7/4/0/7，**从不写 10** → 9→10 的跃迁是**间接**的）；
   - **顶层消息分发器**（负责 opcode `0=snapshot / 1=reliable / 3=gamestate / 6=EOF`；注意：本项目 C# 用的是 `Eof = 5`，与 `046` 注解的 6 **存在未解冲突**）。
   - 注意：静态扫 `E8` **看不到间接调用**；转储里有 **92,307 个候选指针表**可用于找间接调用目标。
3. **警惕**：不要用"最近的 `55 8B EC`"当函数起始 —— 本代码用 MSVC `/Oy`（省略帧指针），该启发式会把大片区域并成一个假函数。应使用 **`E8 rel32` 调用目标 ∪ `55 8B EC` 序言**（本项目实测得到 **35,798 个起点**）。
4. **注解库地址基准可能不一致**：某份 410 条注解文件只命中 **9/410**（约等于随机），基准不可用；而 `046` 的地址基准是 RVA，**可精确复现**。**两套来源必须分开对待。**
