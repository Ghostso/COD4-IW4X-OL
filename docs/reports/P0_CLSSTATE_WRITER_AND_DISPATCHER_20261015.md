# P0-A / P0-B 结论 —— `cls.state` 写入者 与 顶层消息分派器

> 生成时间：2026-10-15（本轮续做）
> 方法：**只读**。静态反汇编 `image_best.bin`（SHA256 17cef6e0…fd045）+ 对局态转储 `mem_linear_live_20261015` 交叉验证。
> 未注入、未断点、未改 `.text`、未触碰 ACE/TP3。
> 地址口径：`file_offset == RVA`，`VA = RVA + 0x400000`。转储切片名第一段为绝对 VA。

## 0. 一句话结论

`cls.state` **不是**由某个 `mov dword [0x76446B0], imm` 直接写的（所以上一轮静态穷举必然找不到 10）；
全部状态跃迁都走 **`base = idx<<5` 的数组形式** `mov dword [base+0x76446B0], imm`，并且它们是
**跨函数间接可见的**（同一段代码在多处出现，`lea` 后才 store）。

`9 → 10` 的**唯一**写点已定位：

```
0x00515D4E   mov dword ptr [edi], 0xA       ; edi = (idx<<5) + 0x76446B0
```

它的**门条件**也在同一函数里，且经活内存验证就是我们此刻卡住的原因：

```
0x00515F81   cmp ecx, 9                     ; cls.state == 9 ?
0x00515F84   jne 0x5161F0                   ;   否 → 直接返回
0x00515F8A   cmp dword ptr [esi+0x3BE4], 0  ; 客户端"快照已就绪"标志
0x00515F91   je  0x5161F0                   ;   ==0 → 返回（我们卡在这里）
0x00515F98   mov dword ptr [esi+0x3BE4], 0
0x00515FA2   call 0x515C30                  ; → 内部 0x515D4E 置 0xA
```

**活内存实测（对局态转储）**：

| 表达式 | 地址 | 实测值 |
| --- | --- | --- |
| `cls.state` | `0x076446B0` | **9** |
| `[0x76638F4]` | `0x076638F4` | `0x74EED103` |
| `client = [0x76638F4] ^ 0x6891D1C7` | `0x1C7F00C4` | — |
| `client+0x3BE4` | `0x1C7F3CA8` | **0** ← 阻塞点 |
| `client+0x3B8C` | `0x1C7F3C50` | `0`（bit1 必须为 0 才能进 `0x515C30`） |
| `client+0x3BE0` | `0x1C7F3CA4` | 0 |
| `client+0x3B90` | `0x1C7F3C54` | 0 |

→ 客户端**从未进入快照解析成功路径**，与"等待玩家数据"一致。

## 1. `cls.state` 全部写入点（完整、已穷举）

`lea reg, [... + 0x76446B0]` 共 **13 处**；其中真正把 `reg` 写回的是下面这些。
（`idx` = 客户端槽位，`base = idx<<5`。）

| # | 载入点 | 写回点 | 立即数 | 语义 |
| --- | --- | --- | --- | --- |
| 1 | `0x4732B2` | `0x4732EA` | **8** | gamestate 受理 → CA_LOADING/PRIMED 路径 |
| 2 | `0x5156E9` | `0x515722` | **8** | |
| 3 | `0x5157B6` | `0x5157E9` | **9** | → `CA_PRIMED` |
| 4 | `0x515AA0` | `0x515AD6` | **9** | 又一次 → `CA_PRIMED` |
| 5 | `0x515D06` | **`0x515D4E`** | **10** | → **`CA_ACTIVE`（唯一写 10 的地方）** |
| 6 | `0x5AA2F4` | `0x5AA327` | 1 | 连接态复位 |
| 7 | `0x5BE03B` | `0x5BE06E` | 寄存器 | 动态值 |
| 8 | `0x5BF68B` | `0x5BF6BE` | 0 | 复位 |
| 9 | `0x5C035A` | `0x5C038D` | 8 | |
| 10 | `0x5C1275` | `0x5C12A8` / `0x5C12F0` | 6 / 7 | |
| 11 | `0x5C12BC` | `0x5C12F0` | 7 | 断开/超时 |
| 12 | `0x5C7A02` | `0x5C7A3B` | 0 | 复位 |
| — | `0x515F4A` | （无直接写回） | — | 只读比较 |

另有绝对形式直接写 3 / 7 / 4 / 0 / 7 / 0 / 7（`0x470467, 0x5BE90A, 0x5BEA8B, 0x77C343, 0x813D34` 等）
—— 与上一轮结论一致，**均非 9→10**。

> 可信度：**高**。这解释了为什么上一轮"只扫 `c7 05 <G> imm32`"必然漏掉 10：
> 真正的 store 是 `lea edi,[edx+G]` + `mov dword ptr [edi], imm` 的**间接形式**。

## 2. `9 → 10` 的完整判据（可直接当修复依据）

函数边界：
- `0x515C30 – 0x515EED`：主状态推进函数（含 `mov [edi],0xA`）
- `0x515EF0 – 0x5161F4`：**入口判定函数**，每帧被调用

`0x515EF0` 逻辑（浓缩）：

```
515ef3  mov ecx, [cls.state]
515efc  cmp ecx, 7
515eff  jl  0x5161f0            ; state < 7 直接返回
515f05  esi = [0x76638F4] ^ 0x6891D1C7      ; client
515f11  cmp ecx, 0xA
515f14  je  515fee              ; 已是 CA_ACTIVE
...      (如果客户端已起本地"host/connect"分支, 走 515f42 的备用路径)
515f81  cmp ecx, 9              ; 必须正好是 9
515f84  jne 5161f0
515f8a  cmp [esi+0x3BE4], 0
515f91  je  5161f0              ; ★★★ 我们卡在这里
515f98  mov [esi+0x3BE4], 0
515fa2  call 0x515C30           ; 内部 0x515D4E: cls.state = 0xA
```

进入 `0x515C30` 后仍有**第二道门**：

```
515c58  test byte ptr [esi + 0x3B8C], 2
515c66  jne  0x515EDD           ; bit1 置位 → 整个函数提前退出，不写 0xA
```

因此跃迁条件 = **`cls.state==9` ∧ `client+0x3BE4 != 0` ∧ `(client+0x3B8C & 2) == 0`**。

**当前实测：`+0x3BE4 = 0` 且 `+0x3B8C = 0` → 第一个条件不满足。**

## 3. `+0x3BE4 = 1` 的唯一写入者 = 快照解析器尾部

`+0x3BE4` 全 `.text` 只有两处：`0x515B15`（清 0）、`0x515F98`（清 0）、
以及**唯一置 1 处**：

```
0x00472810  mov dword ptr [ebx + 0x3BE4], 1
```

它位于函数 **`0x471E90 – 0x47282A`**（`__chkstk` 帧 `0x3BE4`，`__security_cookie` 收尾）。
该函数把解析结果写进 `ebx+0x3B...` 一整族字段（`0x3B7C/0x3B80/0x3B84/0x3B88/0x3B8C/0x3B90/0x3B94/0x3B98/0x3B9C/0x3BA0/0x3BA4` …），
并在最后 `call 0x472830`（结构拷贝）+ 置 `+0x3BE4=1`。

→ **它的角色就是"快照解析成功"标志置位器**。我们从未置位，所以从未进入 `0x515C30`。

函数内 **3 个提前返回点**（这就是"快了我们帧但没解析成功"的候选原因）：

| 提前返回 | 条件 |
| --- | --- |
| `0x472267` | `ecx == edi` 且 `[0xC89E010] & 8 == 0`（首快照/基线判定不成立） |
| `0x4722E7` | `[edi+0x3B7C] == 0` 或 `[edi+0x3B88] != eax`（快照序号/基线不匹配） |
| `0x47234E` | 时间窗口越界（`[ebx+0x3C2C]-[edi+0x3BA8]`、`0x320`、`0x20`、`0x400` 等阈值） |

**下一步（P0-A 收尾）**：对着这三个返回点逐条比对
`firingrange_live.log` 的 TX 时序与我们的 `snapshot` 首帧字段
（`snapshotFlags`、`ack`/`serverTime`、以及"五段缺失"导致的 `[edi+0x3B7C]` 恒 0），
即可锁定是"基线/序号"还是"字段不全"。

## 4. P0-B：顶层消息分派器已定位（并且解决了 Eof 冲突）

**分派器函数：`0x00473A50`**（帧 `0x20044`，`__chkstk`）

```
473b61  edx = [ebp-0x20028]         ; 已读字节数
473b67  ecx = [ebp-0x20024]         ; 当前游标
473b6d  edx += eax
473b6f  cmp ecx, edx
473b71  jge 0x473c2b                ; 读尽 → 结束
473b83  movzx eax, byte ptr [edx+ebx]        ; ★ 取 1 字节 opcode
473ba3  inc ecx
473baa  cmp eax, 5
473bad  je  0x473c3e                ; ★ opcode 5 == EOF（直接结束）
473bb3  cmp eax, 3
473bb6  ja  0x473c1c                ; >3 → 协议错误
473bb8  jmp dword ptr [eax*4 + 0x473C50]     ; ★ 跳转表
```

**跳转表 `0x473C50`（已逐项读取并核对目标）**：

| opcode | 目标 | 处理函数 | 语义 |
| --- | --- | --- | --- |
| 0 | `0x473BF7` | **`0x471E90`** | **snapshot**（就是第 3 节那个解析器） |
| 1 | `0x473BBF` | `0x4737E0` | 读 4 字节 → 包类命令 |
| 2 | `0x473BCC` | `0x4738A0` | 读 4 字节 + 2 字节 → 包类命令 |
| 3 | `0x473BD9` | **`0x473260`** | **gamestate**（`0x4732B2` 处对 `cls.state` 读改写） |
| 5 | `0x473C3E` | — | **EOF**（函数尾） |
| 4 | — | — | **不在表内**（`cmp eax,3; ja` 直接判错），即**未使用** |

### 4.1 `Eof` 冲突裁决 —— **你们的 `Eof=5` 是对的**

046 注解写的 "opcode 6 = EOF" **在 3.19 这个映像上不成立**：
分派器显式 `cmp eax,5 / je 结束`，并且 `opcode>3` 直接进错误分支。
不存在 6 的合法路径。**C# 的 `Eof=5` 与目标客户端一致，无需改动。**

### 4.2 opcode 是**字节**，不是位域

`movzx eax, byte ptr [...]` —— 每帧 `1 字节 opcode`。
注意：客户端**发送方向**的命令读取器用的是 `r.Bits(3)`（3 位）另一套编码
（`ClientCommandReader.cs`），**两者不是同一套**，不要互相套用。

### 4.3 调用链（向上）

```
0x610911 → 0x515C30
0x515FA2 / 0x516033 → 0x515C30
0x5AC3F7 / 0x5B0DC9 / 0x5C2AD8 → 0x515EF0   （每帧入口判定）
0x473BFD (opcode0) → 0x471E90 (snapshot parser)
0x473A50 由 0x5AAB40 / 0x5C2434 调用
  0x5C2434 在 0x5C2260 内（cmp [cls.state],7 / 消费 netchan 消息的 CL_* 例程）
```

## 5. 对下一步的直接影响

1. **P0-B 可直接关闭**：分派器 `0x473A50` + 跳表 `0x473C50` + `Eof=5` 已确认，无需再找。
2. **P0-A 的剩余工作**从"找写入者"变成"**对齐 `0x471E90` 的三个提前返回条件**"，
   范围大幅收窄（见第 3 节表格）。
3. **P1 的地位上升**：第 3 节三个返回点的判定依赖 `[edi+0x3B7C]`/`[edi+0x3B88]`
   —— 这些正是"段序/基线"字段。**五段缺失很可能就是首快照未被接受的原因**，
   与 046 给的段序（playerstate → sound → clients → entities → clientinfos → glass）一致。
4. `0x515C30` 的第二道门 `(client+0x3B8C & 2) == 0` 目前满足（实测 0），**不是**当前阻塞点。
