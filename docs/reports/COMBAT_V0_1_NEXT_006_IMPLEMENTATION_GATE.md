## 1. 五问五答（任务完成标准）

### Q1. 谁调用 `0x63794F`？

**✅ 已闭合。唯一调用链：**

```
0x6379E0（转发器，无直接调用者）
   └─ 唯一引用 = 0x62DE9C  push 0x6379E0
        └─ 位于 0x62DE90（主 vtable 0xDC7274 的 +0x024）
             0062DEA0  push 0x32          ; timer id
             0062DEA2  call 0x6292B0      ; 注册为定时器回调
   └─ 由 0x7FA800 定时器泵在到点时调用：0x7FA9B0 call dword ptr [ebp-0x20]
        └─ 转发器 0x6379F4  call 0x637950   (= 0x63794F)
             └─ rep movsd 整块复制进 mk+0x7470
```

| 环节 | RVA | 等级 |
|---|---|---|
| `0x63794F` 正式入口 = `0x637950` | — | **CONFIRMED** |
| 唯一直接 `E8` 调用者 | `0x6379F4` | **CONFIRMED** |
| 转发器 `0x6379E0` 无直接调用者，唯一引用 = `0x62DE9C` | — | **CONFIRMED** |
| 注册为 timer id `0x32` 回调 | `0x62DEA0 push 0x32` | **CONFIRMED** |
| 回调调用点 | `0x7FA9B0 call [ebp-0x20]` | **CONFIRMED** |
| `0x637950`/`0x63794F` 不在任何 vtable | dword 引用 = 0 | **CONFIRMED** |

### Q2. EAX 指向的数组由谁创建和填充？

**❌ 未闭合。**

```
0x637950 的 eax  ←  0x6379E0 的 [ebp+0x18]（arg6）        CONFIRMED
0x6379E0 的 arg6 ←  回调的第 6 个参数                      CONFIRMED
回调只压入了 2 个参数（0x7FA9AA push 0；0x7FA9AC push [ebp-0x50]）
        ⇒ 参数 3–6 不在栈上，只能来自寄存器/条目内部偏移   HIGH
具体偏移                                            UNKNOWN
```

**★ 本次新增机制证据（CONFIRMED）**：`0x7FA800` 是**直通泵** ——
它把**自己调用者**传进来的 11 个参数**原样**搬进定时器条目（`0x7FA640` 入参 → 条目字段
的一一映射见 SOURCE_ARRAY §2.2），**不做任何加工**。

**⇒ 因此"数组的生产者"被精确定位为：`0x7FA800` 的调用者。**

**本次进一步核实了 7 个调用点（全部为"注册一个延迟任务"的通用用法）：**

| 调用点 | 函数 | 注册的处理器 | 延迟参数 | 备注 |
|---|---|---|---|---|
| `0x4A8E01` | `0x4A892F` 内 | `0x4A8EA0`（`0x4A8DEE push`） | `0x5E`（94） | 通用延迟任务 |
| `0x4AA8D8` | `0x4AA78F` 内 | `0x4AA620`（`0x4AA8C2 push`） | `0xA8`（168） | 通用延迟任务 |
| `0x4B56E1` | `0x4B55DF` 内 | `0x4B5740`（`0x4B56C8 push`） | `0x87`（135） | 通用延迟任务 |
| `0x7FAA56` 等 4 处 | `0x7FAA20` 族自身 | — | — | 注册器内部 |

**⇒ 关键判定：`0x7FA800` 是【通用延迟调用队列】，被 UI/游戏逻辑等**多个不相关子系统**使用
（三个业务调用点的处理器 `0x4A8EA0`/`0x4AA620`/`0x4B5740` 互不相关）。
因此**它本身不携带"预约"语义** —— 预约数组是**某个调用者**传进来的一个普通参数。**

**这使"数组生产者"的定位必须在【调用者侧】完成，
而不能在泵侧完成。**
**剩余唯一工作 = 在这三个（或其它）调用者中，找出哪一个传入了 `0x238` 记录数组。**

### Q4. A/B 的源字段能否逐字节证明？

**❌ 不能 —— 但本次把问题化简了一步。**

| 环节 | 状态 |
|---|---|
| 源字段 → 源记录偏移 | ❌ **UNKNOWN** |
| 源记录 → 槽（`0x63794F`） | ✅ CONFIRMED（`0x637997 rep movsd`，0x8E dwords） |
| **偏移保持（无重排/无转换）** | ✅ **CONFIRMED**（整块 memcpy + 直接 dword 载入，无 `bswap`） |
| 槽 `+0x168/+0x16C` → mmbook | ✅ CONFIRMED（`0x62F736`/`0x62F742`） |
| 槽 `+0x168/+0x16C` → accepted | ✅ CONFIRMED（`0x6326FB`/`0x632707`） |

**★ 化简结论（CONFIRMED）**：
由于复制是**整块、偏移保持**的，**源记录中的 A/B 就在其自身 `+0x168` / `+0x16C`**。
**因此只需拿到源数组基址，A/B 的位置即确定，无需再追任何变换。**

### Q5. 是否具备实施最小 accepted 响应修复的充分证据？

| # | 理由 |
|---|---|
| R1 | A/B 的**源数组基址**未定位 ⇒ 不知道源记录（进而不知道服务端该回什么） |

## 3. 唯一剩余缺口（唯一，可直接执行）

> ### 缺口 U2-G1⁽⁵⁾
>
> **待答**：定时器回调 `0x6379E0` 的 **arg6（源数组）**由谁提供？
>
> **由于偏移保持性已确证（Q4），闭合它 = 闭合 A/B 的整个映射。**
>
> **三条静态路径（任选其一）：**
>
> | 路径 | 目标 | 起点 |
> |---|---|---|
> | **P0（本次新增，优先）** | **`0x7FA800` 的 3 个业务调用点**（`0x4A8E01`、`0x4AA8D8`、`0x4B56E1`）中，哪一个传入的参数是 `0x238` 记录数组 | 这三个函数内 `call 0x7FA800` 前的参数装配；入参映射见 SOURCE_ARRAY §2.2 |
> | **P1** | `0x7FA640` 入参 → 条目字段的映射（**已闭合**，见 SOURCE_ARRAY §2.2） | — |
> | **P2** | `0x62DE90`（主 vtable `+0x024` = `0xDC7298`/`0xDC7738`）的虚调用入口 | 找 `call [reg+0x24]` 且 reg 的 vtable 为 `0xDC7274` |
> | **P3** | `0xE4E20C` 索引表的填充者 | 找 `mov [.. +0xE4E20C], ..` |
>
> **推荐顺序：P1 → P2 → P3。**
> P1 最直接：`0x7FA9B0` 前 `esi`/`edi` 都指向条目基址，
> 因此 arg6 必然来自条目内部偏移；枚举 `0x7FA640` 写入的 5 个 dword 即可定位。
