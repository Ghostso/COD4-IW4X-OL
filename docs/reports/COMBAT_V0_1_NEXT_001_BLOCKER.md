## 0. 首要阻断点（一句话）

**客户端不是"没有战斗代码"，也不是"没有 socket 代码"。
战斗连接的整条代码链在本镜像内**完整存在且已互相闭合**。
它停在 `0x632680`（mmbook-accepted handler）**入口处的 5 道闸门**上；
其中两道（`0x6326B9` / `0x6326C8`）要求"这条 accepted 消息自带的 u64"
必须等于"客户端为本次预约记下的 u64"，**不等就 `ret 0x14` 静默返回**，
于是 `0x63285A` 的桥接（→ 战斗连接）**永不执行**。**

```
0x632680  mmbook-accepted handler
  0x63268D  cmp byte  [esi+0x278], 0        -> je  0x6328EB (退出)
  0x63269B  cmp dword [0x76446b0], 3        -> jge 0x6328EB (退出)
  0x6326AA  cmp dword [esi+0xe360], edi     -> jl  0x6328ED (退出)
  0x6326B9  cmp dword [ebp+8],  [esi+0x3a048]     不相等
  0x6326C8  cmp dword [ebp+0xc],[esi+0x3a04c]   /  -> jne 0x632916 -> ret 0x14   ★★
  0x6326DF  call 0xC3C678  (strncmp "mmbook accepted", 0xF)
        ...
  0x63280B  mov byte [esi+0x288], 1        <- accepted 闩锁（只有 PASS 才写）
  0x632824  listener loop -> vtable+0x24(1,0)
  0x63285A  call 0x6293B0                  <- ★ 只有 PASS 才走"去连战斗服"
```

**`0x632916` 处只有 `pop/pop/pop/mov esp,ebp/pop ebp/ret 0x14` —— 没有任何日志、任何错误码、
任何 UI 提示。这就是"客户端什么都没发生"的原因：它在静默地拒绝。**

既有文档 `CLIENT-BOOKING-BATTLE-TRIGGER-014` 把 `[matching+0x288]` 的**读取点

|---|---|---|
| `0x63280B` | `mov byte [esi+0x288], 1` | 写 accepted 闩锁（**PASS 路径**） |

它比 `0x288` 更早、更靠前。这是本次相对既有结论的**修正**。

## 2.5 ★★ 追加闭合：u64 就是客户端自己 mmbook 请求里的那个值（U2/U3 已闭合）

在写完 §1-§2 后，本次继续追到了 `[esi+0x3a048]/[esi+0x3a04c]` 的写入点与 mmbook 的构造点，
**两个缺口当场闭合**：

### 2.5.1 mmbook **请求**构造器 = `0x62F6EF`

| RVA | 指令 | 说明 |
|---|---|---|
| `0x62F717`/`0x62F71D` | `mov [esi+0x3a048], ebx` / `mov [esi+0x3a04c], ebx`（`ebx=0`） | 先清零 |
| `0x62F736` | `mov ecx, [edi+0x168]` | **读预约项 +0x168** |
| `0x62F73C` | `mov [esi+0x3a048], ecx` | 写入 A |
| `0x62F742` | `mov edx, [edi+0x16c]` | **读预约项 +0x16c** |
| `0x62F748` | `mov [esi+0x3a04c], edx` | 写入 B |
| `0x62F7C1-0x62F7C7` | `push 8` / `push [edi+0x10]` / `call 0xB74410` | base64 编码预约数据 |
| `0x62F7E0`/`0x62F7E5` | `push "mmbook"` / `push "%s %d %s %d"` | **组装命令串** |
| `0x62F7EA` | `call 0x774980` | snprintf → `"mmbook <A 十进制> <base64> <B 十进制>"` |
| `0x62F7F9`/`0x62F809` | `mov ecx,[esi+0x3a04c]` / `mov ecx,[esi+0x3a048]` | 再次取出 A/B |
| `0x62F808`/`0x62F80F`/`0x62F810` | `push ebx` / `push ecx` / `push ecx` / `push eax` | 压参 |
| `0x62F801`/`0x62F819` | `mov edx,[edx+0x150]` / `call edx` | **把 mmbook 请求发出去** |

> 对照既有抓包（`BATTLE_SERVER_PROTOCOL` §9.6）：
> mmbook 载荷原文 = `0a 01 00..00 | 13 08 1d 00 00 00 | 19 00 00 00 | "mmbook 796 AQAAAAAAAAA= 0" 00`
> —— **格式与"mmbook %d %s %d"完全吻合**（`796` = A、`AQAAAAAAAAA=` = base64、`0` = B）。
> 本次静态反汇编与既有抓包**互相印证**。

### 2.5.2 accepted **校验**用的就是这两个值

```
0x6326B9  cmp [ebp+8],  [esi+0x3a048]      ; 消息里的 A  vs  我 mmbook 里发的 A
0x6326C8  cmp [ebp+0xc],[esi+0x3a04c]      ; 消息里的 B  vs  我 mmbook 里发的 B
          jne 0x632916 -> ret 0x14          ; 不等 = 静默丢弃
```

⇒ **U2 / U3 已闭合（CONFIRMED）：**

> **客户端在 mmbook 请求里用 `"mmbook %d %s %d"` 送出它自己的预约 id 对 (A, B)；
> 服务端的 `mmbook accepted` 推送必须把这**同一对 (A, B) 原样回传**，
> 否则 `0x6326B9`/`0x6326C8` 比较失败 → `ret 0x14` → 桥接 `0x6293B0` 永不执行 →
> 客户端从不向战斗服发起连接。**

**这解释了为什么"发一个固定内容的 accepted 会崩/会被忽略"**：
既有做法发的是**常量文本** `"mmbook accepted"`（`0xDC69B0`，长度 0xF），
它**不携带**客户端那对动态 (A, B)，所以无论怎么调 `replyId`/`seq`/`senderId` 都过不了这道闸门。

### 2.5.3 对"首要阻断点"表述的收敛

| 候选 | 状态 |
|---|---|
| ① `[esi+0x278] == 0` 跳过整条路径 | **仍未知**（U1：该字节的写入点未定位） |
| ② u64 对不上 → `ret 0x14` | **机制已完全闭合**；且已证实服务端当前发送的 accepted **不可能**携带正确的 (A,B) |

⇒ 候选 ② 从"机制成立但取值未知"升级为 **"机制与取值来源均已证实"**：
只要 accepted 里没有客户端自己那对 (A,B)，就必然失败。
**候选 ① 仍无法排除**（两者现象相同）。
