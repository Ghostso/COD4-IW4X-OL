## 2. 字段可恢复性的逐项判定（工作二 1–5）

| 步骤（任务原文） | 结论 | 依据 |
|---|---|---|
| 1. 用已有协议结构解析两份 payload | ⚠️ **只能解析请求侧** | 响应体字节缺失 |
| 2. 判断响应能否恢复 `0x238` 完整记录，或只能恢复部分字段 | ❌ **两者皆不能**（无字节可恢复） | 同上 |
| 3. 依整块复制偏移保持性，对照源记录 `+0x168/+0x16C` 与 mmbook A/B | ❌ **无法对照**（缺源记录字节） | 同上 |
| 4. 对每个映射给出原始字节区间与可复核证据 | ❌ **无映射可给** | 同上 |
| 5. 不因数值相同/字段相邻/名称相似认定业务语义 | ✅ **已遵守**（见 §3） | — |

### 2.1 即使做了"代码重建"，也不能替代抓包（说明为何不重建）

`21/5` 的响应对象由 `lobby_server.py` 的 `cc.build_mission_session_object()`
**确定性生成**，理论上可用已知参数重建 236 字节。
**但本次不重建，理由有三（必须记录）：**

1. **重建 ≠ 抓包**：任务要求"不伪造配对数据"。重建物是**服务端代码的输出**，
   不是**客户端实际收到的字节**；二者之间隔着加密/分帧/序号（`0x85 seq=47 replyId=47`）。
2. **重建无法回答核心问题**：A/B 是**客户端从响应解析后派生**的值。
   即使知道响应字节，仍需**客户端侧解析逻辑**才能把字节映射到 A/B ——
   而该逻辑正是 NEXT-001..007 未闭合的部分。
3. **NEXT-007 已证不存在字段级写入**：A/B 只随整条 `0x238` 记录被写入
   （PRODUCER §3），因此"哪两个字节"取决于**客户端如何构造该记录**，
   而非服务端发出什么。

**⇒ 因此本次如实停止字段恢复。**

## 4. accepted 响应格式的独立检查（工作三）

> 任务要求：**仅用现有静态证据**，且"不得将请求格式当作响应格式，
> 也不得假定 accepted 响应只需追加 A/B"。

### 4.1 `"mmbook accepted"` 的字符串判定

```
006326D4  mov  ecx, [ebp + 0x14]        ; 消息文本指针
006326D7  push 0xF                      ; ★ 长度 15
006326D9  push ecx
006326DA  push 0xDC69B0                 ; ★ "mmbook accepted"
006326DF  call 0xC3C678                 ; strncmp
006326E4  add  esp, 0xC
006326E7  test eax, eax
006326E9  jne  0x632876                 ; 不等 -> 另一分支
```

| 事实 | 值 |
|---|---|
| 比较函数 | `0xC3C678`（strncmp 形态） |
| 比较长度 | `0xF` = **15**（`"mmbook accepted"` 恰为 15 字符） |
| 被比较串地址 | `0xDC69B0` |
| **字符串常量中是否含 A/B** | ❌ **不含**（常量就是 `"mmbook accepted"`） |

**⇒ 结论（CONFIRMED）：accepted 的**识别**靠纯字符串比较，
A/B **不在**这个字符串里。**

### 4.2 A/B 比较发生的上下文与参数进入路径

```
[入口] 0x632680（accepted handler）
  0x63268D  cmp byte [esi+0x278], 0      ; 闸门1：预约使能
  0x63269B  cmp dword [0x76446B0], 3     ; 闸门2：尚未进入战斗连接
  0x6326AA  cmp dword [esi+0xE360], edi  ; 闸门3：有效槽索引
  ── A/B 比较 ──
  0x6326EF  mov  eax, [esi+0xE360]
  0x6326F5  imul eax, eax, 0x238
  0x6326FB  mov  edx, [eax+esi+0x75D8]   ; = 槽 +0x168 (A)
  0x632702  cmp  edx, [ebp+8]            ; ★★ 与"消息参数1"比较
  0x632707  mov  eax, [eax+esi+0x75DC]   ; = 槽 +0x16C (B)
  0x63270E  cmp  eax, ebx                ; ★★ ebx = [ebp+0xc]（消息参数2）
  ── 字符串比较 ──
  0x6326DF  call 0xC3C678 (strncmp "mmbook accepted", 0xF)
```

| 问题 | 结论 | 证据 |
|---|---|---|
| 参数如何进入比较？ | 由 **handler 的栈参数** `[ebp+8]`（→ `[ebp+0xc]`/`ebx`）进入 | 逐指令 |
| 参数来自谁？ | 由 `0x7F153F` 的**本地 mmbook 分派器**经 `vtable+0x13C` 调用时压入（NEXT-003 §1.1） | `0x7F1567`/`0x7F156B` |
| A/B 比较与字符串比较的**先后** | **先 A/B（`0x6326B9`/`0x6326C8`），后字符串（`0x6326DF`）** | 地址顺序 |
| 失败行为 | 不等 → `0x632916 ret 0x14`（**静默**，无日志） | NEXT-001 §0 |

### 4.3 当前服务端响应为何缺少已证实的动态字段

| 事实 | 证据 |
|---|---|
| 服务端推送体是**常量** `"mmbook accepted"`（`data=20`） | `lobby_srv.log` 行 211；`0xDC69B0` |
| 该常量**不含**任何动态值 | `0xDC69B0` 处的字节即 15 字符 + NUL |
| 因此它**不可能**携带客户端槽里的 A/B | 逻辑必然 |
| 四种"改 envelope 元数据"的尝试（replyId/seq/senderId/推送偏移）**全部失效** | NEXT-001 §9（9/9 断连实测） |

**⇒ 结论（CONFIRMED）：当前服务端的 accepted 响应**结构上缺失**满足
`0x6326B9`/`0x6326C8` 所需的动态字段。**

### 4.4 但**不能**据此推断 accepted 体的布局（遵守任务限制）

任务明确："**不得将请求格式直接当作响应格式，也不得假定 accepted 响应只需追加 A/B**"。

本次**未**确定 accepted 体的布局，理由：

| # | 理由 |
|---|---|
| 1 | `"mmbook accepted"` 只是**字符串识别**用；比较 A/B 的参数 `[ebp+8]/[ebp+0xc]` 的来源，**只追到 `0x7F153F` 的调用约定**，未追到"消息体里的哪个偏移" |
| 2 | 消息对象布局（`0xB9B0B0` 路径）中回调/参数槽已定位（`+0x20`/`+0x28`，NEXT-004），但**该对象是出站方向**；入库方向的 accepted 体是否复用同一结构 **未证** |
| 3 | 因此"只需在常量后追加 8 字节"是一**种假设**，本次**不采纳**为结论 |

**⇒ accepted 响应体布局：UNKNOWN。**
