## B. 已被推翻的历史结论（逐条真值，别再引用旧版）

- **房间位流**：`manifold` 是 **5 位 TLV**；位序 = **LSB-first**；`+0x21` 是**编解码总开关**；房间位流 = **41 位**（不是 49 位）。→ 169/175/176/179/180/242 等旧位流模型**全部作废**。
- **`11/4` 与 `6/5`** 是两层，`11/4` 的 batch = `[u32 len][inner]`。
- **`reply+5` 极性是服务私有的**，全库 6 处，**不得推广到其它 service**。
- **商城 SKU = 19 字段**：多插 2 个无证据字段会让其后全部错位（曾把整个 marketplace 服务打挂）。
- **`[0xC9113CC]` 是 `bad_items` 黑名单**，不是"已拥有表"（更正 249/250）。
- **段2 不是空洞**（非零 11.31%），且不是 ABC 字节码而是 AVM2 导出记录表（更正 139）。
- **166 卷"房间线静态清零"是错的**（全库扫漏 15 项）。
- **MMI 低区 `+0x00~+0x11F` = 本地状态**，不是网络字段。
- **`0x47/4` 不是安全键上报**：task 3/7 是明文模板串遥测、task 4 是机器指纹登录上报；对这些回空 ACK 是**正确行为**。
- **`0xBBE430` 是 CT6 收包，不是发送出口**（发送是 `0xBBDC00`→`0xBC2820`）。
- **`0xBBE110` 对内部状态 0 返回 3**（不是 0）；映射 `{0→3,1→1,2→1,3→2}`。
- **引擎只有一张 vtable** `0xD5AF94`；`0xD5AF9C`/`0xD5AFA4` 只是多重继承子对象视图。
- **`0xBB5260` 收包入口"不可达"的结论已撤回**（那次否定证明无效）。
- **`0x7F5E40` 是 `shared_ptr::operator=`**，不是 dwRoom 回调。
- **`0xBBFCC0` 是"从队列移除"**（计数器递减），不是"自动发起握手"。
- **`0x6F37E0/0x6F381B` 属于另一份同布局实现**（`0x6F37C0`），不是 `0xBBF040` 那条。
- **`ol-mod` 不是权威参照**：它明确针对不同构建（其头文件写明 "OLfinal ends it with 5"）。**不得抄它的常量/字段/协议值。**
- **参照层级**：3.19 本地逆向 > IW4X > CoD4X。**其它任何来源一律不得作为依据、不得提及。**

## C. 扫描/取证方法上的坑（工具必须先自检）

上一轮这四类误配**全部实际发生过**，且每次都导致过错误结论：

1. **`disp32` 误配**：用裸 4 字节地址搜，会命中**别的指令的位移**。
   例：`8D B0 B0 46 64 07` = `lea esi,[eax+0x076446B0]`（不同地址），我因此把 5 个写点虚报成 240 处引用。
   ⇒ 正确做法：**回溯对齐解码**（对每个出现点向前试 1..6 字节，用 capstone 解出完整指令并核对长度），或用 `ModRM` 显式判别基址寄存器。
2. **指令长度算错**：`got.size == k+4` 这类判据会**漏掉带尾随立即数的指令**（`C7 05 <addr> <imm32>` 是 10 字节），我因此一度得到"写点 0 处"。
3. **漏掉编码形态**：只扫 `C7 05`/`89 05` 会漏 `89 /r` 的其它 7 个寄存器、`A3`、字节宽的 `C6 05`/`88 /r`/`A2`、以及 `inc/dec/and/or/add` 这类读改写。
4. **按可执行属性过滤段**：`0xCA8000` 段被标为非可执行，**里面是真实代码**。按 `IMAGE_SCN_MEM_EXECUTE` 过滤会整段漏掉。
5. **线性反汇编全扫**（从段首开始）会被 `.text` 内嵌数据带偏，结果全空——**不要用它做权威判定**。

**前置自检**：任何"某地址无写点/无引用/不被调用"的结论，下之前必须
(a) 覆盖全部编码形态，(b) 覆盖全文件而非单段，(c) 检查是否存在**取地址后间接访问**，(d) 检查映像是否有洞（最长 0 串长度），(e) 有可能的话**与运行期内存捕获对照**（本项目有 22 万片 `r_<基址>_<长度>.bin` 可做这件事）。

**算术必须用脚本核**，不能心算（`0x1480C` 曾被误算成 `0x480C`，导致一整条错误结论）。

## D. 推理方法上的坑

1. **把一个局部可读到的事实当成整体判据** —— 上一轮四次错误的**共同根因**。每下结论先问：证据来自客户端还是只来自服务端日志？是一次 run 还是全部样本？
2. **用单次观察写通则**。`6/14`、`cancelConnect`、`clientState` 都栽在这里。写通则必须附**样本量与出处**。
3. **"错的更正比不更正更糟"**。发现自己错了就**就地标注作废并写清真值**，不要只写新结论、让旧的留在索引里。
4. **凡会变的数字不要写进散文**，只写"去看哪个命令/文件"。校验器文档曾写死"51 条：39 闭/12 未闭"，后来数字全错，还因此把已闭项报成未闭。
5. **不要用"需要运行时观测"当停手理由**（AGENTS.md 明文）。先把静态分解穷尽，并**把穷尽过程写下来**（试了什么、每次排除了什么）。
6. **不得声称"找到根因"**。上一轮四次声称、四次回退。在客户端真的进对局之前，不出现这个句式。
7. **不得把"我们在推数据"当成"客户端在接受"**。

## E. 运行 / 资产操作上的坑

- **受保护资产不可动**：`REF_LOBBY_KIT\*`（`run_all.py`/`nt10.py`/`lobby_server.py`/`fake_auth_tls.py`/`codol_crypto.py`/`write_dwauth.py`/`make_local_ca.ps1`/`_golden_hashes.json` 及其清单内一切）、`CODOL_VERIFIED_GOLDEN_20261019` 整体。**不改、不覆盖、不重命名、不删、不往里生成证书、不写运行期状态。**
- **必须走单次启动器**：`run_frozen_chain_once.py`（或带 `--allow-kit-divergence` 的 dynkey 版）**或**新建独立 run 目录；**先把文件复制过去再改行为**。
- **单次规则**：一次调用只允许创建一个客户端；早退后**不得自动重启**；用户明确要求才在新目录重试。
- **运行产物必须落在** `run_codol_001\runs\<RUN_ID>\` 下。
- **不得**因顺手修而改 IIPS / hosts / 证书 / 注册表策略 / 安全软件 / 游戏二进制。
- **elevated agent 是必需品**，缺了启动器直接 rc=2；启动器会校验它 `debug_privilege=true`。
- **3074 遗留监听**是提权 python，普通 `taskkill` 会 Access denied，**必须经 agent 的 `stop` 动作**杀。
- **单次令牌** `runs\.frozen_launch_used`：每次启动前要 `--authorize-next-launch`。
- **Release 构建不能当测试门**：`/DNDEBUG` 让 `assert()` 编译为空，断言型测试在 Release 下必然"失败"；**只有 Debug 的 ctest 有效**。
- **磁盘 `.ff` 不解密**；`.ifs` 已全定位。
- **`enable_iips=0` 是 6 秒必崩的根因**。
- **ACE 会挡调试**：cdb 拒绝 `0xC0000022`，须 6 秒内抢句柄。
- **不要用沙箱跑实验**：沙箱是残缺副本（129 文件/0.4GB vs 本体 3095 文件/24.7GB），且缺 `.local\`，加载的 `Base.dll` 与本体不是同一份。
