> **版本**：2026-10-17  
> **性质**：教学文档，不是可照抄的答案包  
> **适用对象**：第一次接手本项目的人类工程师或 AI Agent  
> **目标**：读完后能够**独立判断**问题出在哪一层，并能按证据设计下一步实验，而不是只会运行某个脚本

## 如何使用这本教程

这本教程故意**不**从“复制这几行命令”开始。原因很简单：

> 照着命令做成功一次，不等于理解了系统；命令一旦失效，照抄者就失去了方向。

每一章都按同一个节奏展开：

```text
问题 -> 心智模型 -> 证据 -> 实验 -> 自测 -> 常见错误
```

请按顺序阅读。每章末尾的自测题，**先自己回答，再看下一章**。如果你发现自己的答案只是“因为文档这么写”，说明还没有学会。

本书不会给出完整可运行源码。它教的是：

1. 如何把“进不了大厅”拆成可验证的假设；
2. 如何用日志、字节和状态变量区分根因与表象；
3. 如何设计只改一个变量的实验；
4. 如何把结论写成别人能复核的证据。

## 先做一次诊断：你现在是“会运行”还是“会理解”

请先不要查资料，用一句话回答下面五个问题：

1. 客户端窗口出现了，是否等于已经进入大厅？为什么？
2. 为什么认证服务用 `127.0.0.1:3074`，大厅服务却用 `127.0.0.2:3074`？
3. `0x81`、`0x82`、`0x83` 三帧分别在解决什么问题？
4. 日志里出现 `hmac=BAD`，可能是密钥错、帧错，还是两者都可能？你如何区分？
5. 客户端在握手成功约 52 秒后断线，为什么不能直接把“52 秒”写进协议常量表？

如果你只能回答“某个脚本会处理”，那说明你掌握的是操作记忆，不是系统模型。本书的目标就是把这五个问题变成可推导的结论。

# 第一部分 建立正确的心智模型

## 第 1 章 “进入大厅”不是一个开关，而是六道门

### 1.1 先区分三个容易混淆的现象

初学者最常犯的错误，是把下面三件事当成同一件事：

| 现象 | 实际含义 | 不能证明什么 |
|---|---|---|
| 游戏进程存在 | 操作系统成功加载了 exe | 不能证明启动链完成 |
| 游戏窗口出现 | 渲染和 UI 初始化到某一步 | 不能证明网络层可用 |
| 大厅界面出现 | 认证、握手、任务、UI 全部走通 | 不能证明后续功能稳定 |

**大厅是一个结果，不是一次调用。** 它是多个子系统按顺序全部成功后，客户端状态机到达的一个状态。

### 1.2 六道门

把整个链路拆成六层，每层都有自己的输入、输出和失败证据：

```text
G0 进程门
   客户端 exe 能被拉起，单实例互斥体不被占用，进程不立即退出

G1 启动链门
   IIPS / IFS2 初始化完成，客户端具备读取资源和进入网络层的前提

G2 地址与配置门
   hosts 把两个 CODOL 域名解析到本地；dwauth.ini 指向正确端口

G3 认证门
   TLS /auth/ 成功，客户端拿到票据和会话密钥

G4 大厅传输与握手门
   建立 127.0.0.2:3074 明文连接，完成 0x81 / 0x82 / 0x83

G5 任务与 UI 门
   0x85 加密任务帧可解可回；Publisher、档案等数据下发；大厅 UI 渲染
```

这六层是**串行依赖**的。下游失败时，不能先怀疑下游；必须先证明上游已经通过。

### 1.3 每层看什么证据

| 层 | 成功证据 | 典型失败证据 |
|---|---|---|
| G0 | 进程存活、窗口类出现 | `rc=1`、启动数秒即退出、`0xC0000005` |
| G1 | `IIPSHostApp.exe`、`iips.dll`、`ifs2.dll` 出现 | `初始化IIPS错误：8189fec` |
| G2 | hosts 两条记录、`dwauth.ini` 三行 | 客户端停在“连接服务器” |
| G3 | `TLS 就绪`、`200 task=10->11` | TLS 握手失败、证书不受信 |
| G4 | `=== 大厅连接建立 ===`、`0x83` 成功 | 连接不建立、握手复位 |
| G5 | `★ 试解命中`、`hmac=OK`、publisher 下发、大厅可见 | `hmac=BAD`、只解 4 条任务、缺文件弹窗 |

### 1.4 一个关键原则：不要跨层解释

例如：

- 看到“无法连接大厅服务”，不能立刻去改 `lobby_server.py`。先确认 G2（域名解析）和 G3（认证）。
- 看到 `hmac=BAD`，不能立刻怀疑加密算法。先确认 `nt10` 是否导出了**本会话**的密钥。
- 看到大厅 52 秒断线，不能立刻认为服务端少发了一个包。先确认客户端是否在读入站数据。

> **判断规则**：症状出现在哪一层，不等于根因就在哪一层。根因通常在上游，或者在一个被误认为“常量”的运行时条件里。

### 1.5 本章实验（不启动游戏）

拿一张纸，把下面症状分到 G0–G5：

```text
A. 双击 exe 后 3 秒退出
B. 游戏窗口出现，但一直显示“连接服务器”
C. 日志有 TLS 就绪，但没有“大厅连接建立”
D. 大厅连接建立，但 0x83 后立刻复位
E. 0x85 能解，但 52 秒后弹断线
F. 大厅能进，但 Publisher 文件报缺
```

**要求**：每个症状写出“最可能层”和“必须先排除的上游层”。不要写修复命令。

### 1.6 本章小结

- 大厅是六层串行链路的结果。
- 每层有独立证据，不能用下游现象反推上游已通过。
- 诊断的第一步不是修，而是定位层。

### 1.7 自测

1. 为什么“窗口出现”不能证明 G3 通过？
2. 如果 G4 失败，哪些 G3 证据必须先拿出来？
3. “52 秒断线”属于哪一层？为什么不能只看时间？

## 第 2 章 客户端是状态机，不是黑盒

### 2.1 为什么要建立状态机模型

“客户端不前进”是一个现象，不是原因。要定位它，必须知道客户端内部有哪些状态、状态之间靠什么事件迁移。

大厅链路的简化状态机：

```text
[进程启动]
    |
    v
[IIPS/IFS2 初始化] --失败--> [初始化错误 / 退出]
    |
    v
[DNS/配置就绪]
    |
    v
[/auth/ TLS 认证] --失败--> [认证失败 / 停在连接页]
    |
    v
[大厅 TCP 建立]
    |
    v
[0x81 发送] -> [0x82 接收] -> [0x83 校验]
    |
    v
[0x85 任务循环] -> [Publisher/档案/余额下发]
    |
    v
[大厅 UI]
```

注意：这张图是**逻辑状态机**，不是客户端源码里的全部状态。学习时要区分：

- **协议状态**：握手到第几步、任务序号是多少；
- **客户端内部状态**：例如请求对象上的状态字段；
- **可观测状态**：日志、窗口、进程、网络连接。

三者不是一一对应。一个常见的错误，是把“日志出现某行”当成“客户端内部状态一定到了某值”。

### 2.2 状态、事件、常量

把系统中的量分成三类，可以避免大量误判：

| 类型 | 例子 | 特点 |
|---|---|---|
| 状态 | 当前握手阶段、连接是否建立 | 会随事件变化 |
| 事件 | 收到 0x82、收到 0x83、连接断开 | 有先后顺序 |
| 常量 | 端口、帧魔数、域名 | 在同一版本内固定 |

初学者常把“状态”当“常量”。例如把某个超时时间、某个字段值写死，却没有验证它是否随环境变化。

### 2.3 为什么 challenge 不能从帧尾推断

握手中的一个关键值是 challenge。它用于 `0x83` 的校验。

错误做法：

> 看到 `0x82` 帧最后 8 字节像 challenge，就直接拿来用。

为什么错？因为帧尾是**线格式**的一部分，而 challenge 是**客户端运行时状态**。二者可能相同，也可能因为版本、会话或构造方式不同而不同。

正确做法：

1. 从协议帧中解析出候选值；
2. 用运行时观测确认客户端实际使用的值；
3. 只有在多轮实验中稳定一致，才把它写成规则；
4. 若不一致，保留“帧尾候选”和“运行时真值”两条证据，不强行合并。

这条原则适用于所有“看起来像”的字段。

### 2.4 事件顺序比单点值更重要

例如 `0x83` 使用过期 challenge 的竞态：

```text
错误顺序：
  收到 0x82 -> 用上一会话 challenge 构造 0x83 -> 客户端校验失败

正确顺序：
  收到 0x82 -> 等本会话 KDF 记录 -> 取本会话 challenge -> 构造 0x83
```

单看 `0x83` 的字节，可能完全正确；但它用的是**错误的会话**。所以必须记录事件顺序。

### 2.5 本章实验

给你一段日志（示意）：

```text
[00.0] process start
[08.1] iips.dll loaded
[09.2] ifs2.dll loaded
[15.2] splash
[16.0] TLS ready
[16.4] auth 200
[17.0] lobby connect
[17.3] 0x81 sent
[17.5] 0x82 received
[17.5] 0x83 sent
[17.6] reset
```

问题：

1. 哪些事件证明 G1 通过？
2. 哪些事件证明 G3 通过？
3. 0x83 后立刻 reset，最可能的问题类别是什么？
4. 如果 0x83 的字节校验正确，但 challenge 来自上一会话，日志上会看到什么差异？

**要求**：只根据事件顺序作答，不猜测修复方法。

### 2.6 本章小结

- 客户端是状态机，不是“能跑/不能跑”的二元开关。
- 状态、事件、常量必须分开。
- 顺序错误可能让“字节正确”的帧依然失败。

## 第 3 章 证据、因果与实验设计

### 3.1 证据分级

本项目使用四级标记，读文档时必须先看标记：

| 标记 | 含义 | 使用方式 |
|---|---|---|
| CONFIRMED | 有实机日志、字节级比对或可重复实验 | 可作为前提 |
| HIGH-CONFIDENCE | 有静态指令证据，缺逐条动态回放 | 可作为强假设，不可当铁律 |
| PARTIAL | 只证明了一部分 | 必须写清哪部分成立 |
| UNRESOLVED | 未解决 | 不得当作实现依赖 |
| NOT_FOUND | 现有材料中没有 | 不能推断“不存在” |

### 3.2 相关不等于因果

例子：

> 每次断线前都出现 `DELETE /queue`，所以 `DELETE /queue` 导致断线。

这个推理是错的。`DELETE /queue` 可能只是断线后的清理动作。要判断因果，需要：

1. 改变 `DELETE /queue` 的时机或是否发送，观察断线是否随之改变；
2. 找到更早的触发事件；
3. 检查断线是否在没有 `DELETE /queue` 时也发生。

本项目的历史结论正是：`DELETE /queue` 是断线的**结果**，不是原因。这个结论来自多轮对照实验，而不是日志顺序。

### 3.3 单变量原则

一个合格实验只改变一个变量：

```text
基线：不改任何东西，记录结果
实验：只改 A，其他保持完全一致
对照：只改 B，或改回基线
```

如果同时改了 hosts、证书和补丁，即使成功，也无法知道是哪一项起作用。

### 3.4 负对照

负对照用于排除“看起来成功”的假象：

- 不发 `0x81`，观察驱动是否仍打印 `SUCCESS`；
- 不启动大厅服务，观察客户端是否仍显示某个状态；
- 用错误密钥解密，观察是否必然 `hmac=BAD`。

如果负对照也“成功”，说明你的成功判据是假的。

### 3.5 可复现性

一个结论要可复现，至少记录：

```text
输入：客户端版本、exe 哈希、配置、数据文件
环境：操作系统、权限、端口、hosts
步骤：按顺序做了什么
观测：原始日志/字节，不只写结论
结果：成功/失败，重复次数
```

### 3.6 本章实验

设计一个实验，回答：

> “52 秒断线是否由服务端不发帧导致？”

要求写出：

- 基线条件；
- 实验组（服务端发帧的频率/内容）；
- 对照组；
- 成功/失败判据；
- 为什么不能只看断线时间。

### 3.7 本章小结

- 先看证据等级，再接受结论。
- 日志顺序不能直接证明因果。
- 单变量、负对照、重复性缺一不可。

# 第二部分 协议：从字节到会话

## 第 4 章 认证：TLS、证书与票据

### 4.1 认证层在解决什么问题

客户端启动后，需要知道“我是谁、我能拿到什么会话”。认证层负责：

1. 建立 TLS，确认服务端可信；
2. 接收 `/auth/` 请求；
3. 返回票据和会话材料；
4. 让大厅层能够用同一会话继续通信。

这不是“随便回 200”那么简单。TLS 证书、域名和票据内容都会影响后续握手。

### 4.2 为什么需要本地 CA

客户端使用系统证书信任链和游戏目录里的 `cacert.pem`。本地假认证服务要让它信任，必须：

1. 生成本地根 CA；
2. 把根 CA 加入 `LocalMachine\Root`；
3. 把根 CA 追加到游戏目录的 `cacert.pem`；
4. 让 leaf 证书的 SAN 包含客户端会访问的域名。

SAN 至少包括：

```text
localhost
formal-zone-auth.codol.qq.com
formal-zone-lsg.codol.qq.com
```

如果 SAN 缺一个，客户端可能只在某个连接阶段失败，表现为“认证能过但大厅连不上”或相反。

### 4.3 为什么 hosts 只劫持两个域名

需要劫持：

```text
127.0.0.1 formal-zone-auth.codol.qq.com
127.0.0.2 formal-zone-lsg.codol.qq.com
```

不要劫持：

```text
down.qq.com
intldlgs.qq.com
```

原因：ACE / TP3 等组件需要访问真实网络获取配置或 DLL。把它们也指向本地，会导致安全组件无法初始化，进而让游戏无法启动。这里的“少即是多”是硬约束。

### 4.4 票据与会话密钥

认证响应中包含票据。实测得到的关键事实：

```text
客户端真正使用的 24B 会话密钥 = ticket[97:121]
```

这个结论不是从“票据格式看起来像”推出来的，而是通过运行时观测与字节比对确认的。

票据不是密码，也不是随便的随机串。它承载了会话材料，后续 KDF 会用它派生四个子密钥：

```text
aes_out   服务端 -> 客户端 的 AES 密钥
aes_in    客户端 -> 服务端 的 AES 密钥
hmac_out  服务端 -> 客户端 的 HMAC 密钥
hmac_in   客户端 -> 服务端 的 HMAC 密钥
```

方向必须分清。把 `aes_in` 和 `aes_out` 弄反，帧可能“能解但校验失败”，也可能“校验对但内容错”。

### 4.5 KDF 的基本形式

一个可用的心智模型：

```text
secret     = HMAC-SHA1(key = transcriptHash, data = sessionKey)[...]
子密钥     = 从 secret 按标签扩展
```

不同实现可能在参数顺序、截断位置和标签上不同。学习重点不是背公式，而是理解：

- 输入必须来自**同一会话**；
- transcript 必须包含双方的握手材料；
- 参数顺序错误会导致“算法看似正确，结果全错”。

### 4.6 本章实验

1. 如果 leaf 证书 SAN 缺少 `formal-zone-lsg.codol.qq.com`，最可能在哪一层失败？
2. 如果把 `down.qq.com` 也劫持到 127.0.0.1，为什么可能连游戏都启动不了？
3. 如果把 `aes_in` 和 `aes_out` 对调，可能出现哪些症状？至少写两种。
4. 为什么服务端不能直接读游戏进程内存来拿会话密钥？

### 4.7 本章小结

- 认证层不只是“回 200”，还包括信任链、SAN、票据和会话材料。
- 会话密钥来自票据的特定字节区间。
- 四个子密钥有方向，不能混用。

## 第 5 章 大厅通道与握手

### 5.1 两条连接，不是一条

```text
127.0.0.1:3074   TLS      /auth/       认证
127.0.0.2:3074   明文     lsg          大厅
```

为什么用两个地址？因为客户端按域名和用途分别连接。把它们混成一个端口，可能让认证流量和大厅流量互相污染。

### 5.2 握手三帧

简化时序：

```text
客户端 -> 服务端   28B hello
服务端 -> 客户端   0x81
客户端 -> 服务端   0x82
服务端 -> 客户端   0x83
客户端 -> 服务端   0x85 任务帧
```

握手的目标不是“把三个包发出去”，而是让双方对以下内容达成一致：

- 会话标识；
- challenge；
- 票据/密钥配对；
- 后续帧的序号和方向。

### 5.3 0x81 的作用

`0x81` 是对客户端 hello 的应答。它通常包含：

- 帧长度/类型；
- 服务端随机材料；
- 与客户端 hello 相关的字段。

学习时不要只记“发 0x81”，要问：

> 客户端收到 0x81 后，用什么条件决定发送 0x82？

如果这个条件不满足，客户端会停在原地，而不是报错。

### 5.4 0x82 与 challenge

`0x82` 是客户端发来的 stage1 材料。服务端需要从中提取信息，构造 `0x83`。

关键点：

- challenge 必须来自**本会话**；
- 不能在 0x81 之前修改请求对象里的相关字段；
- 0x83 的回显值不能简单从帧尾推断。

### 5.5 0x83 的作用

`0x83` 是服务端对客户端材料的校验/确认。成功之后，客户端才进入任务循环。

常见错误：

| 错误 | 结果 |
|---|---|
| 用上一会话 challenge | 校验失败或立即复位 |
| 0x83 帧长度/字段错位 | 客户端解析失败 |
| 过早修改请求对象 | 服务端收到不一致的材料 |

### 5.6 本章实验

给定一个抽象帧描述：

```text
hello:  [len][len][type][type][flags][nonce8]
0x81:   [len][00][81][token4][random8][echo8]
0x82:   [len][AB][82][...stage1...]
0x83:   [len][00][83][challenge8]
```

问题：

1. 哪些字段是长度，哪些是类型？
2. 0x81 的 echo 与 hello 的哪一段相关？
3. 如果 0x83 的 challenge 来自上一会话，帧本身是否仍然“格式正确”？
4. 为什么不能只靠帧尾判断 challenge？

### 5.7 本章小结

- 两条连接承担不同职责。
- 握手是一个状态推进过程，不是三个孤立包。
- 会话一致性比单帧正确性更重要。

## 第 6 章 0x85：加密任务帧

### 6.1 为什么需要加密帧

握手完成后，客户端和服务端通过 `0x85` 交换任务。任务帧包含：

- 序号；
- IV；
- AES 密文；
- HMAC 前 8 字节。

它不是“普通 JSON 加个包头”，而是有明确密码学结构的二进制帧。

### 6.2 帧布局

一个可用的心智模型：

```text
u32 total_len
u8  0xAB
u8  0x85
u32 seq
u8  iv[16]
u8  cipher[...]
u8  hmac8[8]
```

计算关系：

```text
hmac8 = HMAC-SHA1(hmac_key, frame_without_last_8)[:8]
plain = AES-128-CBC-decrypt(aes_key, iv, cipher)
```

注意：

- HMAC 覆盖的是**去掉最后 8 字节的整帧**；
- AES 使用 CBC，IV 随帧；
- 两个方向使用不同的 key；
- 序号必须按会话维护。

### 6.3 解密后的明文结构

客户端 -> 服务端的任务帧，明文大体是：

```text
u32 declared
u8  0x86
u8  service
u8  0x03
u8  task
payload...
```

服务端 -> 客户端的应答，明文布局不同：

```text
u32 len
u8  0x01
TLV...
```

“请求明文”和“应答明文”不能套同一个模板。这是常见错误。

### 6.4 TLV 对象

应答中的对象使用“类型标签 + 值”的编码。一个简化例子：

```text
tag 10 + u64 replyId
tag 8  + u32 status
tag 3  + u8  task
tag 8  + u32 object_count
... objects ...
```

真实编码还要考虑长度、嵌套和对象类型。学习重点是：

> 先确定“这一段是标签还是值”，再确定“这个值属于哪个语义”。

不要从字符串猜字段。

### 6.5 hmac=BAD 怎么定位

`hmac=BAD` 只说明“校验不通过”，可能原因包括：

1. 密钥不是本会话的；
2. 方向用反；
3. 覆盖范围错（包含/不包含最后 8 字节）；
4. 帧被截断或拼接错；
5. 序号/IV 错。

区分方法：

- 用已知正确的帧做离线复算；
- 只改密钥，不改帧，观察是否恢复；
- 只改覆盖范围，观察是否恢复；
- 记录 `aes_in/aes_out/hmac_in/hmac_out` 四个值，不要只记一个。

### 6.6 本章实验

给定：

```text
frame_hex = <total><AB><85><seq><iv><cipher><hmac8>
key_a = ...
key_b = ...
```

要求写出伪代码：

1. 如何截取 HMAC 覆盖范围；
2. 如何验证 HMAC；
3. 如何解密；
4. 如何解析请求明文；
5. 如何判断失败发生在 HMAC 还是 AES 还是解析层。

**不要直接运行现成脚本。** 先在纸上写出步骤。

### 6.7 本章小结

- 0x85 是密码学帧，不是普通协议包。
- 请求和应答的明文布局不同。
- 定位 BAD 要分密钥、方向、覆盖范围、帧完整性四类。

## 第 7 章 任务、对象与“空应答”的语义

### 7.1 service/task 模型

客户端通过 `service` 和 `task` 区分业务：

```text
service=10, task=21   Publisher 配置下发
service=8,  task=1    公开档案
service=8,  task=2    私有档案
service=80, task=130  CP 余额
service=93, task=1    GP 余额
service=21, task=5    会话对象（靶场等）
service=6,  task=14   mmbook 推送
service=11, task=4    ready 推送
```

### 7.2 空应答不是“万能安全牌”

有些任务回空对象，客户端能接受；有些任务回空会导致：

- 大厅 UI 缺内容；
- 商城页面崩溃；
- Publisher 失败；
- 后续任务不再发送。

学习时要区分：

| 类型 | 例子 | 空应答是否安全 |
|---|---|---|
| 遥测/统计 | 71/3、68/3 | 通常安全 |
| 可选列表 | 好友、部分频道 | 视客户端实现 |
| 关键数据 | 10/21 Publisher | 不安全 |
| 档案 | 8/1、8/2 | 不安全 |
| 余额 | 80/130、93/1 | 不安全 |

判断依据不是“别人也回空”，而是**客户端收到空后是否继续发送后续任务**。

### 7.3 应答对象的语义

一个应答至少要回答：

1. 这是哪个请求（replyId/seq）；
2. 成功还是失败（status）；
3. 是哪个 task；
4. 携带几个对象；
5. 每个对象的类型和值。

如果 replyId 对不上，客户端可能丢弃整个应答；如果 status 错，客户端可能不再重试。

### 7.4 本章实验

给出症状，判断最可能缺哪个任务：

```text
A. 弹 EXE_DOWNLOAD_PUBLISHER_FILE_FAILURE
B. 大厅能进，但 CP/GP 显示 0
C. 大厅能进，但商城空白
D. 大厅能进，但玩家名不对
E. 握手后只解出 4 条任务就断
```

要求：写“任务号 + 需要什么数据 + 如何验证”。

### 7.5 本章小结

- service/task 是业务索引。
- 空应答的安全性取决于客户端是否依赖该数据。
- 应答必须能对上请求，否则等于没回。

## 第 8 章 会话密钥与 KDF

### 8.1 为什么服务端不能自己读游戏内存

一个自然的想法是：

> 服务端直接读游戏进程内存，拿到会话密钥不就行了？

现实中会遇到两个问题：

1. 权限：游戏由受保护进程拉起，普通服务端读不到；
2. 时序：密钥在握手过程中才产生，服务端启动时还没有。

所以本项目采用：

```text
注入器 nt10.py 在客户端进程内 hook KDF
  -> 把派生的 4 个子密钥写入 kdf_sessions.txt
  -> 大厅服务端读取该文件，按会话配对
```

### 8.2 会话配对

每个客户端会话有唯一的 24B 会话密钥。大厅服务端收到 `0x82` 后，从帧中读出票据片段，用 `ticket[97:121]` 去匹配对应的 KDF 记录。

如果配对错：

- 用错密钥解密 -> `hmac=BAD`；
- 用错 challenge -> 0x83 失败；
- 多客户端时互相污染。

### 8.3 多客户端为什么难

单客户端时，即使密钥配对不严格，也可能“碰巧”成功。多客户端时：

- 每个客户端有自己的会话密钥；
- 服务端必须按会话区分；
- 注入器必须为每个进程单独 hook。

这也是为什么“单客户端能进”不能直接证明“多客户端能进”。

### 8.4 本章实验

1. 为什么不能让大厅服务端在启动时读一次密钥就完事？
2. 如果 `kdf_sessions.txt` 里有多条记录，服务端如何知道用哪一条？
3. 如果 `nt10` 没有命中 KDF hook，日志上会缺什么？
4. 多客户端时，单实例互斥体会造成什么现象？

### 8.5 本章小结

- 密钥在运行时产生，必须由客户端侧导出。
- 会话配对依赖票据片段。
- 多客户端是独立问题，不是单客户端的简单复制。

# 第三部分 运行时：进程、补丁与数据

## 第 9 章 启动链、注入与补丁

### 9.1 客户端不是“双击就完事”

当前可用链路是：

```text
提权代理
  -> 清残留
  -> 起 auth + lobby
  -> nt10 拉起客户端
  -> 打 4 个补丁 + 装 KDF hook
  -> 观察日志
```

手工双击沙箱里的 exe，通常会遇到：

- 单实例互斥体被占用；
- 缺少启动上下文；
- 补丁未打；
- 读不到会话密钥。

### 9.2 四个补丁分别在解决什么

历史基线记录的补丁位置：

```text
补丁1 AuthGate       @0x00B9A78E  74 -> 75   (JE -> JNE)
补丁2 ClientTicket   @0x00B9A7C5  75 -> EB   (JNE -> JMP)
补丁3 ParseFallback  @0x00B9A7C7  E8 -> E9   (call -> jmp)
补丁4 LsgNonceCheck  @0x00BA3C1C  85 C0 75 44 -> 85 C0 90 90 (NOP)
KDF hook             @0x00BA0D20  trampoline
```

学习重点不是背地址，而是理解：

- 这些补丁改变的是**客户端的分支决策**；
- 每个补丁对应一个校验门；
- 地址与字节必须和客户端 build 严格匹配；
- 不同版本不能混用。

### 9.3 VirtualProtectEx 与 FlushInstructionCache

写代码段的基本步骤：

```text
OpenProcess
VirtualProtectEx(PAGE_EXECUTE_READWRITE)
WriteProcessMemory
FlushInstructionCache
VirtualProtectEx(恢复保护)
```

少一步都可能出现：

- 写入成功但执行旧指令；
- 进程崩溃；
- 补丁看似生效但行为不变。

### 9.4 残留进程与互斥体

客户端使用单实例互斥体。残留进程会导致：

- 新进程启动后立即退出；
- `0xC0000005`；
- 看起来“补丁没生效”。

因此每轮实验前必须清理：

```text
codoMP_client_shipRetail.exe
TP3Helper.exe
IIPSHostApp.exe
```

### 9.5 纪律边界

- 不绕过 ACE / TenProtect；
- 不修改原版安全组件；
- 不把“让安全组件认为正常”当作方案；
- 所有实验在开发副本上进行，原版只读。

这条边界不是技术问题，而是项目纪律。

### 9.6 本章实验

1. 为什么补丁地址必须绑定 build？
2. 只做 `WriteProcessMemory` 而不 `FlushInstructionCache` 会怎样？
3. 为什么“进程启动 3 秒退出”要先查残留进程，而不是先改补丁？
4. 如果补丁打错一个字节，最可能的症状是什么？

## 第 10 章 数据：Publisher、档案与“缺文件”故障

### 10.1 Publisher 不是独立程序

一个重要事实：

> Publisher 是客户端内部的下载子系统，不是独立 exe。

客户端通过 `service=10/task=21` 向大厅服务请求发行方配置。服务端从 `publisher_files\` 读取对应 `.info` 文件并下发。

### 10.2 关键数据

进大厅所需的最小数据集：

```text
publisher_files\
  activities_v1.info
  broadcast.info
  configs_s.info
  daily_challenge_config.info
  market-down.info
  market_ui.info
  MOTD.info
  tlogconfig.info
  whitelist_tester.info
  mp_playlists_shipRetail_1.0.0.info

player_profiles\
  public.result
  secure.result

user_files\
  the.json

player-account.json
```

`mkt_assets\`、`sku_arrays\` 主要影响商城/外观，不是进大厅的最小必需。

### 10.3 为什么“缺一个文件”会导致进不了大厅

客户端的 Publisher 下载有失败重试和错误弹窗。缺文件时：

- 客户端认为发行方配置不完整；
- 可能停在加载页；
- 可能弹出 `EXE_DOWNLOAD_PUBLISHER_FILE_FAILURE`；
- 即使进入大厅，部分 UI 也会空白。

这不是“服务端少回一个包”，而是**数据契约不完整**。

## 第 11 章 观测、诊断与失败分类

### 11.1 日志不是越多越好

先建立“问题 -> 证据”的映射：

| 问题 | 首选证据 | 不要先看 |
|---|---|---|
| 进程没起来 | 进程退出码、互斥体、残留进程 | 大厅日志 |
| 启动链失败 | IIPS/IFS2 日志、`iips.ini` | 0x85 帧 |

### 11.2 最小证据集

当你说“卡住了”，至少应提供：

```text

2. 当前阶段（G0-G5）
3. 最近 20 行相关日志
4. 本轮只改了什么
5. 期望现象 vs 实际现象
```

缺这些信息，任何诊断都会退化成猜。

### 11.3 失败分类表

| 症状 | 最可能层 | 区分实验 |
|---|---|---|
| 启动即退 | G0 | 查残留进程、退出码、互斥体 |
| 初始化 IIPS 错误 | G1 | 查 `enable_iips`、IIPSHostApp |
| 停在连接服务器 | G2/G3 | 查 hosts/dwauth；查 auth 日志 |
| TLS 失败 | G3 | 查 SAN、CA、cacert.pem |
| 大厅 TCP 不建立 | G4 | `netstat` 看 3074；查服务是否启动 |
| 0x83 后复位 | G4 | 查 challenge 来源、会话配对 |
| hmac=BAD | G5 | 查密钥方向、覆盖范围、会话 |
| 只解 4 条任务 | G5 | 查服务端实现是否完整 |
| 52 秒断线 | G5/运行时 | 查客户端是否读入站；不要先改服务端 |

# 第五部分 把知识迁移到新问题

## 第 12 章 如果版本变了，哪些结论还能用

可以把结论分成三类：

| 类别 | 例子 | 版本变化时 |
|---|---|---|
| 结构 | 两条连接、握手顺序、帧分层 | 大概率保留 |
| 常量 | 端口、域名、帧魔数 | 可能变化，需重新验证 |
| 地址/字节 | 补丁 VA、challenge 偏移 | 几乎一定变化 |

学习的目标是掌握“结构”，而不是背“常量”。

### 12.1 迁移检查表

遇到新 build，先问：

1. exe 哈希是否变化？
2. 端口/域名是否变化？
3. 握手帧长度/类型是否变化？
4. 补丁地址是否仍指向同一指令模式？
5. KDF hook 的调用点是否仍是同一函数？
6. Publisher 文件名是否变化？

### 12.2 不要做的迁移

- 直接套用旧补丁地址；
- 直接套用旧 challenge 偏移；
- 用旧日志证明新版本成功；
- 把“旧版本能进”当成“新版本也能进”。

## 第 13 章 常见“答案式理解”为什么是错的

| 答案式说法 | 为什么不够 |
|---|---|
| “起 run_all.py 就行” | 不知道失败时该看哪一层 |
| “回空对象最安全” | 关键任务回空会导致 UI/Publisher 失败 |
| “52 秒是协议常量” | 它是运行时行为，环境变化会变 |
| “hmac=BAD 就是密钥错” | 也可能是覆盖范围、方向、帧完整性 |
| “窗口出来就是进大厅” | 窗口只证明渲染到了某一步 |
| “把 down.qq.com 也劫持更彻底” | 会破坏 ACE/TP3 的真实网络依赖 |
| “驱动打印 SUCCESS 就是成功” | 已出现过假成功 |
| “改一个字节试试” | 没有单变量和回滚，无法形成结论 |

## 附录 C 课程设计说明

本教程刻意不提供“完整可运行答案”，原因有三：

1. **版本漂移**：地址、偏移、文件名会变，答案会过期；
2. **学习目标**：能诊断比能运行更重要；
3. **证据纪律**：照抄会绕过“验证”这一核心训练。

如果你需要执行层清单，请把它当作“实验记录”，而不是“教材”。教材训练的是判断力，清单训练的是手速，两者不能互相替代。

## 结语

真正学会的标志，不是你能背出 0x81、0x82、0x83，而是：

> 当链路在第 4 层失败时，你能说出为什么不是第 5 层；当有人给出一个“成功结论”时，你能问出它的证据等级、实验条件和反例。

这比任何一份可复制的脚本都更耐用。
