# §5 起：人工分析

## 5. ★ 最重要的一条：我们把字段写成 **XOR 增量**，三份参照全部写 **裸值**

`snapshot.c` 用 `bw_scalar_xor` / `put_f32_xor` 写的字段共 **11 个**：

```
3(weapon_time) 8(x) 10(z) 11(y) 13(vy) 14(vx)
17(weapon_state) 20(pm_flags) 39(weapon) 41(aim_fraction) 44(weapon_delay)
```

三份参照对**同一批字段全部写裸值**（`scalar(v,w)` / `Bytes(f32 v)`）。差别有两点：

1. **载荷**：我们写 `to ^ from`（`from` = 上一帧的值），参照写 `to`。
2. **存在位**：`bw_scalar_xor` 的 presence 位看的是 `to != 0`，参照看的是 `value != 0`
   —— 看起来一样，但配合第 1 点就不同了（见下面的演示）。

**为什么首帧看不出来**：首帧 `svc->snap_from` 是全零（`codol_snap_state_zero`），
`to ^ 0 == to`，于是首帧与参照**逐字节等价**。这也是为什么"首帧字节数对得上"
一直没暴露这个问题。

### 5.1 离线演示（`tests/probe_snapshot_size.c`，同一份输入、只换基线）

**改动前**（诊断证据，2026-10-24 记录）：

```
帧1  基线全零        len=125
帧2  from=帧1(XOR)   len=125
帧2  from=零(裸值)   len=125
帧1 首帧十六进制: ...00008044000040420000E8C200000FC491...
帧2 XOR   十六进制: ...00008044000000000000000000000000...
帧2 裸值  十六进制: ...00008044000040420000E8C200000FC491...
两者不同的字节数 = 8
```

读法：`000040420000E8C2` 就是 x=48.0 / z=-116.0 的 IEEE754 小端字节。
输入完全相同、只换 `from`：裸值式第 2 帧与第 1 帧一致；
XOR 式的 x/y/z 与 vx/vy 那几个 float 变成 **全 0** ——
因为 `put_f32_xor` 直接 `bw_bytes(to ^ from)`，**没有存在位**，
玩家一帧没动时 `to ^ from == 0`，**于是每个"没动"的帧都在告诉客户端位置 = (0,0,0)**。

**改动后**（同一探针，2026-10-24 修完）：

```
帧1 基线全零           len=125
帧2 from=帧1(非零基线) len=125
帧2 from=零(零基线)    len=125
帧2 两种基线之间不同的字节数 = 0   (载荷是裸值, 基线不参与编码)
帧1 与 帧2 不同的字节数       = 4   (只有头部 serverTime/first/flags)
```

⇒ XOR 路径删除后，基线不再影响任何字段载荷。

⚠️ 这只证明"我们发出去的东西是错的"。**没有**证明客户端怎么用它 ——
`HANDOFF_20261025_BINARY_BISECT.md` §13 的实测反而显示客户端**完全不采纳**这些运动字段
（两个相距数百单位的坐标、只发首帧或每帧都发，人物位置丝毫不动）。
所以现在有两条互相独立的嫌疑：**我们的运动字段从第 2 帧起就是错的**，
而且**客户端似乎根本没在用它们**。两条都指向"位置这条腿没通"。

### 5.2 这条能不能靠离线样本判定？

**不能。** `playerstate-motion-trace.json` 自己的 `scope` 字段写着：

```
"offline position branch trace; copy and security initialization omitted;
 not live packet validation"
```

—— 它是一次**离线解码演练**，不是抓下来的真实报文（Python 参照的注释把它当"实录"引用，
这一点需要打折）。它能定"读序 / 位宽 / 字段索引"（这些确实有用：trace 里字段索引的
跳号读数就是 **4 位一组**，支持我们编回 4 位的决定），**定不了"该不该 XOR"**。
判 XOR 只能靠"改一处、实机看"，或者从客户端二进制里读 f32 字段的读取路径。

| | 写法 | 锚点行 |

| **CSC** | `w.Scalar(opt != null && opt.OnGround ? 2046 : 2047, 16)` **动态** | `MotionSnapshot.cs:586` |

而 C# 那份**能玩**的配置 `verified_entry_snapshot = 1` 走的正是 **CSV**，
并且 `ClientLogic.cs:903` 明确把玩家的真实接地状态喂了进去：

```csharp
// [GROUNDFIX] 把玩家真实的地面状态传给快照（2046=地面 / 2047=空中）
currentOpts.OnGround = s.Player.OnGround;
```

`SnapshotOptions.OnGround` 自己的注释（`MotionSnapshot.cs:219-221`）：

> 实测: 站立 ground 2046，跳跃瞬间 2047。**之前恒写 2047 导致客户端认为永远在空中
> -> 悬空/无移动动画/不能跳。**

**我们 `snapshot.c:421-425` 的注释写的是"权威实现 CodolMotionSnapshot.cs 恒定写 2047"。
脚本锚点证明这句话是错的** —— 那一行源码里是 `opt.OnGround ? 2046 : 2047`。
我们照着一句被写错的注释，选中了参照明确标记为"会导致悬空/不能跳"的那个值。

> 这条与"人卡在房顶 / 不会落地"的症状**字面吻合**，是目前最值得先验证的一条。

## 7. 只有我们写的字段：62、107、162

```
snapshot.c:427  bw_index(62);  bw_scalar(0, 6)
snapshot.c:431  bw_index(107); bw_scalar(0, 16)
snapshot.c:432  bw_index(162); bw_scalar(0, 16)
```

三份参照都没有这三个字段。它们是零值，实际影响的不是"值"而是**索引游程的位流长度**
—— 多写一个索引就多几个位，后面所有内容整体位移。目前客户端收得下（快照能被 ack），
所以它们不是"立刻炸"的那类差异，但属于"没有任何依据的自造字段"。

## 8. 参照内部自己就互相矛盾 —— "照参照抄"这句话不成立

| 项 | PY | CSV（**能玩的配置选的是它**） | CSC |
|---|---|---|---|
| `num_fields` | 220 | 220 | **85** |
| idx 21-24 | 武器槽式（默认） | **旧式事件数组**（恒用） | 两种可切 |
| idx 83 | 不写 | 写 1 位 0 | 不写 |
| idx 219 | 仅开关打开时写 | **无条件写** | 仅开关打开时写 |
| index(84) 标记 | **有** | **没有** | **有** |

具体到两条最容易误导人的：

- **idx 21-24**：Python 的注释（`battle_server.py:1145-1158`）说旧式事件数组是**语义错位**
  ——"客户端会把事件号当成武器 id 解释"。**我们用的正是这个旧式写法**（`snapshot.c:398-406`），
  而能玩的 CSV 用的也是旧式。⇒ 两边都有依据，**不能据 Python 注释判我们对错**。
- **index(84) 标记**：Python 注释（`:1226-1229`）说漏写这个标记会让"整段错位"，
  "必须补上"。**但 CSV 也没写**，而 CSV 是能进图、能玩的那份。
  ⇒ 这条 Python 结论被 CSV 反证，**目前存疑**。

**结论**：Python 与 CSV 在至少 5 处互相矛盾，且各自都自称"对齐实录"。
所以"把我们的实现改成和参照逐字节一致"**不是**一个定义明确的目标 ——
必须先确定**以哪一份为准**。历史上有一次就是照着参照改了编码器，结果客户端反而卡住
（`HANDOFF_20261025_BINARY_BISECT.md` §15）。

### 11.2 本次改动**没有**碰的东西（已验证）

首帧的字段载荷与基线无关（基线全零时 `to ^ 0 == to`），所以：

- 改动前后的首帧**逐字节相同**（`tests/fixtures/snapshot_golden_20261024.txt` 钉住）；
- 更能说明问题的是：把 `ENTITY_SECTION_20261024_1320` 那轮（客户端进图并持续 ack）
  战斗服日志里的**线上第一帧**解掩码后，与我们现在的 `omit=1` 输出**逐字节相同**。
  ⇒ 客户端实际接受过的那条路径，一比特都没动。

### 12.3 开镜那一条：尚未归因，必须单变量验

开镜坏掉有两个候选，都可能：

1. **是 idx61 的连带后果** —— 客户端进了无碰撞/飞行状态，视角与动画状态机跟着异常；

## 13. ★★ 出生点的答案：我们一直跑在两份参照都明确否决的那个模式里（2026-10-24）

### 13.1 Python 参照的默认是"每帧发服务端积分位置"

`REF_LOBBY_KIT/battle_server.py:1300`：

```python
omit = bool(assoc["snapshot_sent"]) and os.path.exists(CLIENT_MOVEMENT_FLAG)
```

那个开关默认不存在 ⇒ **首帧与非首帧都 `omit=False`** ⇒ **每帧都发**。

而且它**从不积分 z**（`:698-699` 只有 `pos_x/pos_y += vel*dt`，没有重力、没有垂直模拟），
`pos_z` 恒为初值 `-116`（`:492`）。用户确认：**"Python 版服务器人物出生点是正确的。"**

⇒ **-116 这个 z 是对的**（不是"高了 11 单位"）。我们缺的不是正确的z，是**根本发出去**。

### 13.2 我们跑的 `omit=1`，正是两份参照都否决的模式

`CODOL-Combat-Server-v0.1/config/firingrange_live.cfg`：

```
client_movement = 0  # [FINAL] 该加壳客户端无法在"无位置快照"下完成世界初始化(卡设置游戏); 必须服务端权威
omit_motion = 0      # [NO-POS-ROLLBACK] 1 时客户端无碰撞会无限飘(实测 X 飘到 8740); 改回服务端权威位置
```

而 Python 参照把"不发位置"单独做成开关，并**写明了症状**（`battle_server.py:53-56`）：

> `spawn_from_map.on` 让客户端在**地图自带的几十个 `mp_tdm_spawn` 里自己挑**，
> **会挑到几何体/屋顶里 → 卡住走不动**。

我们当前是**全程 `omit=1`** —— 语义上等价于 `spawn_from_map.on`。
"**卡在房顶、按键无反应**"与这句注释逐字吻合。

### 13.3 为什么以前试"发位置"全都无效——那些实验测的是坏掉的编码器

`SPAWN_FIRSTFRAME` / `SPAWN_COOP` / `SPAWN_EVERYFRAME` 三轮都跑在**旧的 XOR 编码**上：
位置字段从第 2 帧起被写成 `to ^ from`，而位置没变 ⇒ **客户端每帧读到的都是 0**。
也就是说客户端**从来没有收到过一串连贯的位置**；
而且 `SPAWN_EVERYFRAME` 用的还是**基础图**的坐标 `(-44,-387,-83)`，不是本图的。

⇒ §13（旧文档）那句"客户端不采纳我们快照里的位置"**不能**用来否定"发位置"这个方向，
它测的是一个坏掉的编码器。该结论本轮作废。

### 13.4 本轮改动

镜像不可用那条分支 `omit = true` → **`omit = false`**。
即回到 Python 参照的默认：**每帧发服务端积分位置**（z 仍是 −116，与 Python 参照一致）。
idx61 维持 2047、字段载荷维持裸值。
