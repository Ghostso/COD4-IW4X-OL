## 2. 成功/失败怎么判

订阅回调（`0x4AA960`）：

```asm
0x4AA966  cmp  byte ptr [ebp+0xc], 0     ; 入参1 = 是否成功
0x4AA97E  je   0x4aa9bd                  ; 为 0 -> 失败
0x4AA980  test esi, esi / jne 0x4aa9bd   ; [0xc1b8020] != 0 -> 失败
0x4AA984  test edx, edx / jne 0x4aa9bd   ; [0xc1b8038] != 0 -> 失败
0x4AA988  ; 成功: 读 [eax+0x10] / [eax+0x14] 写入全局 0xc1b9590 / 0xc1b9594
```

**⇒ 成功 = `入参1 != 0` 且两个错误状态全局都为零。**

第二个回调（`0x4AAA10`）同样：

```asm
0x4AAA16  cmp  byte ptr [ebp+0xc], 0
0x4AAA1A  mov  edx, [0xc1b8008]
0x4AAA22  je   0x4aaa2c                  ; 入参1==0 -> al=0
0x4AAA24  test edx, edx / jne 0x4aaa2c   ; [0xc1b8008] != 0 -> al=0
0x4AAA28  mov  al, 1                     ; 否则成功
0x4AAA31  mov  [0x82c4af4], al           ; ★ 结果存进这个全局
```

## 3. ★ 状态码判定（关键）

`0x4AAC70` 起：

```asm
0x4AAC73  cmp  byte ptr [ebp+0xc], 0
0x4AAC77  jne  0x4aac96                  ; 入参1 != 0 -> 走另一支
0x4AAC79  mov  eax, [ebp+8]
0x4AAC7C  mov  ecx, [eax+0x28]
0x4AAC7F  call 0x927100                  ; ★ 返回对象 +0x38 的值
0x4AAC84  cmp  eax, 0x27DA               ; 11226
0x4AAC89  je   0x4aac90                  ; 等于 -> 接受
0x4AAC8B  cmp  eax, 0x6C                 ; 108
0x4AAC8E  jne  0x4aac96                  ; 都不是 -> 拒绝
```

`0x927100` 本体：

```asm
0x927100  mov eax, dword ptr [ecx + 0x38]
0x927103  ret
```

**⇒ 客户端把应答里的某个字段存进对象的 `+0x38`，然后要求它等于 `0x27DA` 或 `0x6C`。**

`0x6C` 与我们一直在用的 `T_ARRAY` 标签值相同（0x6C=108）—— 是否巧合**尚未确认**，
不要据此推断语义。

## 4. 对我们的意义

我们现在对 `71/3`（CreateRoom）、`71/20`、`71/15`、`71/7` 一律回**空 ACK**。
按上面的判定，空应答 ⇒ 状态码不会是 0x27DA/0x6C ⇒ `[0x82c4af4]` 保持 0
⇒ 订阅视为失败 ⇒ 打 `ChannelSubscriptionFail` ⇒ 客户端不进入下一步（不连战斗服）。

这与实测完全吻合：`mmstart` 之后客户端发了 `11/4`、`102/7`、`71/3`，
然后**战斗服一条包都没收到**，界面停在"战斗开始"。

## 5. 还没确认的（不要当成结论）

- `71/3` 的应答**整体结构**（几个对象、每个对象哪些字段）

## 7. ★ 完整判定（第二轮，已闭环）

### 7.1 四个状态码，不是两个

`0x4AA6F6` 这一段是**最完整的判定**：

```asm
0x4AA6F6  mov  ecx, [ebx+0x28]
0x4AA6F9  call 0x927100          ; 取状态码 = [obj+0x38]
0x4AA6FE  cmp  eax, 0x6C         ; 108
0x4AA701  je   0x4aa718
0x4AA703  cmp  eax, 0x27DA       ; 11226
0x4AA708  je   0x4aa718
0x4AA70A  cmp  eax, 0x4AA2       ; 19042
0x4AA70F  je   0x4aa718
0x4AA711  cmp  eax, 0x27D8       ; 11224
0x4AA716  jne  0x4aa740
0x4AA718  mov  byte ptr [0x82c4af4], 0     ; ★ 命中 => 标志清 0
```

**四个码：`0x6C`(108) / `0x27DA`(11226) / `0x4AA2`(19042) / `0x27D8`(11224)。**

### 7.2 `0x82C4AF4` 是"已订阅"标志，不是"成功"标志

读写点全部找到：

| 地址 | 动作 |
|---|---|
| `0x4AA71E` | 状态码命中上面四个 ⇒ **清 0** |
| `0x4AAA32` | `mov [0x82c4af4], al`（回调算出的结果） |
| `0x4AB4FD` | `mov [0x82c4af4], bl`（另一条路径） |
| **`0x4AABDB`** | `cmp byte [0x82c4af4],0` / `je 0x4aac07` ⇒ **为 0 才去发起订阅** |
| `0x4AB4EA` | `cmp byte [0x82c4af4],0` / `je 0x4ab517` |
| `0x5D2DE7` | 读进 bl 供别处用 |

**⇒ 语义 = "当前是否已处于订阅态"。为 0（未订阅）才会去发起；**
状态码落在那四个值上时会被**清 0**，即视为"未订阅/需重新订阅"。

### 7.3 对"卡在战斗开始"的解释

我们对 `71/3` 回**空 ACK** ⇒ 应答里没有能让状态码变成"非那四个值"的内容
⇒ 订阅态一直起不来 ⇒ 客户端不进入"对局已就绪" ⇒ **不去连战斗服**。

这与实测一致：`mmstart` 之后客户端发 `11/4`、`102/7`、`71/3`，
战斗服 `_c_battle_out.txt` **一条包都没有**。

### 7.4 仍然没定的（下一步）

1. **`[obj+0x38]` 这个状态码，是从应答的哪个字节写进去的** —— 还没追到写入点。
2. `71/3` 应答的整体结构（几个对象、哪些字段）。
3. 那四个码各自的含义（是"未加入/已离开/超时/无权限"之类？只能靠语义猜，**没有证据**）。

**下一步就做第 1 条**：从 `0x4AA6CC` 的 `mov esi,[ebx+0x28]` 出发，
追 `ebx+0x28` 指向的那个对象是谁创建的、它的 `+0x38` 在哪被赋值。

## 8. 第三轮：`0x4AA6C0` 那段是**打日志**，不是判定

把两个 helper 反汇编后确认：

| 地址 | 实际作用 |
|---|---|
| `0x477140` | 日志格式化：`sub esp,0xc14`（3KB 栈缓冲）、`rep` 式逐字节拷串、`call 0xc42de0`（memset）、`call 0x726d90` |
| `0xB83D70` | 纯 getter：`mov eax,[ecx+0x30]; mov edx,[ecx+0x34]; ret` |

⇒ `0x4AA6C0` 整个函数是**把订阅结果格式化成一条日志**，
里面那四个 `cmp eax,{0x6C,0x27DA,0x4AA2,0x27D8}` 决定的是**日志的措辞**，
不是"要不要连战斗服"。

**这条纠正很重要**：上一轮我把 `0x4AA6F6` 当成判定逻辑，是错的。
真正的判定仍然在 `0x4AA960` / `0x4AAA10` 两个回调里
（`入参1 != 0` 且错误状态全局为 0 ⇒ 成功），那部分结论不受影响。

## 9. 现状与下一步

**已经确定的**（都可以复跑脚本验证）：

1. 订阅结果回调的**成功条件**：`入参1 != 0` 且 `[0xc1b8020]==0` 且 `[0xc1b8038]==0`。
2. `[0x82C4AF4]` = "已订阅"标志；**为 0 才去发起订阅**（`0x4AABDB`）。
3. 四个状态码 `0x6C / 0x27DA / 0x4AA2 / 0x27D8` 只影响**日志措辞**。
4. 状态码读自 `[obj+0x38]`（`0x927100`）。

**还没确定的**：`71/3` 的应答到底长什么样。
`+0x38` 的写入点在 `0x4A0000-0x4B0000` 区间**一处都没有**（扫了 503 处
`mov [reg+0x38],reg`，该区间 0 处）⇒ 它在**别的模块**里写，很可能是网络层。

**下一步的正确做法**：不再从订阅回调往上爬，而是**从应答解析器往下找**——
即定位"收到 0x86 帧 → 按 service/task 分派 → 构造应答对象"这条链，
那里的对象就是 `[ebx+0x28]`。这条链的入口在 netchan/消息分派层，
可以先用 `service=71` 这个数字在分派代码里的比较去找。

## 10. 第四轮：分派层**没找到**，但找到了频道表结构

### 10.1 负面结果（如实记录）

- 全 `.text` 扫 `cmp eax, imm32`（imm ∈ 1..200）共 **245 处**，
  但 **`cmp eax, 71` 一处都没有** ⇒ service 号不是用立即数比较分派的。
- 试找 `{u32 service, u32 fnptr}` 表：列出 25 条，**全是误报**
  （把机器码字节当成了 id/fnptr，例如 `0x461A20` 的 `132 -> 0x848389` 明显是 `mov` 指令字节）。
- 试找同时含 71 与 102 的 u32 数组：**0 处**。

⇒ **分派层不在 `.text` 的静态表里**，可能是：
  ① 运行期构造的 map/vector；
  ② 用字符串名做 key 的注册表；
  ③ 在 `.tvm0`/其它加密段（那部分静态读不到）。

### 10.2 找到的东西：频道项 40 字节

订阅发起函数 `0x4AAB00` 起：

```asm
0x4AAB14  lea esi, [eax + eax*4]        ; esi = idx * 5
0x4AAB17  lea esi, [esi*8 + 0xc1b8188]  ; esi = idx*40 + 0xC1B8188   ★ 每项 0x28 字节
0x4AAB3E  mov eax, [esi + 0x10]
0x4AAB51  mov ecx, [esi + 0x14]
...
0x4AAB48  push 0x4aa960                 ; 注册回调
0x4AAB87  call 0x4aae20                 ; 发送
```

**⇒ 频道表在 `0xC1B8188`，每项 40 字节；`+0x10` / `+0x14` 是两个会被发出去的字段。**

这与订阅回调里"成功时读 `[eax+0x10]` / `[eax+0x14]` 写进 `0xC1B9590` / `0xC1B9594`"
（§2）**完全对上** —— 同一个结构的两端。

### 10.3 现在能确定到哪一步

| 已确定 | 依据 |
|---|---|
| 频道项大小 = **0x28** | `lea esi,[eax+eax*4]; lea esi,[esi*8+基址]` |
| 频道表基址 = `0xC1B8188` | 同上 |
| 每项 `+0x10` / `+0x14` 参与收发 | `0x4AAB3E` / `0x4AAB51` 与 `0x4AA988` 两头对上 |
| 订阅态标志 = `0x82C4AF4`，为 0 才发起 | `0x4AABD9` |

| 仍未确定 | 为什么 |
|---|---|
| `71/3` 应答的**字段序与宽度** | 需要应答侧的解析代码；分派层没定位到 |
| `+0x38` 状态码的写入点 | 扫 503 处 `mov [reg+0x38],reg`，订阅区 0 处 |

### 10.4 建议的下一步（不再盲扫）

改成**从已知数据反推**：客户端内存里那张频道表（`0xC1B8188`）在运行时是有内容的。
拿一次**真实对局**的内存转储，直接读 `0xC1B8188` 起若干项，
就能看到真实的频道项长什么样（`+0x10`/`+0x14` 是什么值）——
比在 230MB 里盲扫代码可靠得多。

## 14. ★ 第六轮：0x4AAE20 完整还原与根因定性（2026-10-24 终结闭环）

### 14.1 核心真相：71 不是订阅服务，而是遥测日志服务！

此前在 `71/3` 看到的 `ChannelSubscriptionFail`、`CreateRoom`、`ClientLogin` 等字符串，**全都带 `T_STRING(0x10)` 标签**。
**Service 71 是腾讯 Demonware 的客户端遥测/日志上报通道**（Telemetry / EventLogger）。
当客户端内部操作失败时，由 `0x477230` 格式化日志串后向 `71/3` 或 `71/7` 上报。
**真正的频道订阅与房间 RPC 根本不是 71 号服务！**

### 14.2 0x4AAE20 发送的真实目标：Service = 102, Task = 1

通过对 `0x4AAE20` 内部全指令反汇编：
1. `0x4AAE25: call 0x803830` 获取 Demonware 上下文。
2. `0x4AAE36: call 0xb7a670` 校验连接态（== 2）。
3. `0x4AAE46: call 0xb7a770` 获取服务对象。
4. `0x4AAE71: call 0xb8f370` 构建并发送任务：
   - `0xB8F486: push 0x66` (Service = 102)
   - `0xB8F481: push 1` (Task = 1)
   - 证明：**`0x4AAE20` 专用于发起 Service 102 Task 1 频道订阅/查询！**

### 14.3 请求与应答二进制结构完全解析

#### 请求格式（客户端发出，已在 `lobby_srv.log` 验证）：
- `T_U32` (0x08): array1_count
- array1 元素列表: 每个为 `T_U8` category + `T_U64` channelID
- `T_U32` (0x08): array2_count
- array2 元素列表: 每个为 `T_U8` category + `T_U64` channelID
- 尾部裸 `0x00`。
- 实测样本：`08 00 00 00 00 08 01 00 00 00 03 03 0a 00 00 00 00 00 00 00 00 00`（array1=0, array2=1, category=3, channelID=0）。

#### 应答格式（客户端反序列化链 `0xB840B0` -> `0xB841D0` -> `0xB9C430`）：
1. `0xB840FD`: `call 0xb761e0` 读 `T_U32 errorCode`（必须为 0 才能进入成功流，否则置 `[esi+0x14]=3`, `[esi+0x38]=4` 判废）。
2. `0xB84208`: `call 0xb761e0` 读 `T_U32 num_results`（数量 N）。
3. `0xB84227`: `call 0xb761e0` 读 `T_U32 total_results`。
4. 对每个频道元素（`0xB9C430`，共 8 个强校验字段）：
   - `T_U32`: category（回填请求的类目，如 3）
   - `T_U64`: channelID（回填请求的频道号，如 0）
   - `T_U32`: param1（置 1）
   - `T_U32`: param2（置 0）
   - `T_BOOL`: isMember / subscribed（置 True/1）
   - `T_U64`: ownerId（玩家 CODOID）
   - `T_STRING`: channelName（"channel\0"）
   - `T_STRING`: extraData（"\0"）
5. 尾部裸 `0x00`。

### 14.4 订阅成功标志 `[0x82C4AF4]` 的激活机制

- 当 102/1 应答被上述解析器吃下后，任务标记为 `BD_TASK_SUCCESS(2)`。
- 回调 `0x4AAA10`（在 `0x4AAC07` 注册）被触发，入参 `success == 1`。
- 执行 `0x4AAA28: mov al, 1; mov [0x82c4af4], al`。
- **`[0x82C4AF4]` 成功置 1！**
- 循环调用 `[0xc1b95a0]` 注册的所有状态监听器通知对局就绪，解除 20 秒超时拦截，避免触发 `0x5D2E30` 打出 `ChannelSubscriptionFail`。

### 14.5 关联阻断点：房间服务是 Service 4，不是 Service 11！

- 客户端发出的房间创建是 `Service 4, Task 13`（`0xB88701: push 0xd; push 4`）。
- 既有代码按 ol-mod 写成 `service == 11`，导致实机收到的 `4/13` 成了 UNMAPPED 空 ACK。
- `4/13` 的应答反序列化器为 `0xB88400`，严格要求 5 个字段：
  - `T_U64`: roomId
  - `T_I64`: createdTime
  - `T_U64`: ownerId
  - `T_STRING`: roomName
  - `T_U32`: roomType
- 修复方案：在 `lobby_server.py` 中将 `service == 4` 映射正确，并在 `102/1` 按上述协议返回结构化对象。
