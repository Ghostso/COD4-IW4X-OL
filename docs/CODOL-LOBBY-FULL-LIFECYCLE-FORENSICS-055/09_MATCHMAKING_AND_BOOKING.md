# 09 — 匹配与预约（mmbook）

---

## 1. 协议事实

| 项 | 值 |
|---|---|
| 通道 | `6/14`（Instant Message service） |
| 上行声明长度 | 31–209 B（8 种） |
| 上行内容 | **纯文本**：`mmbook 796 …` |
| 服务端应答 | push `mmbook accepted`（20 B） |
| 出现 run | 46 / 56 |

**`mmbook` 不是二进制协议，是文本命令。**

---

## 2. 时序位置

```
21/5 findSessions  →  6/14 mmbook  →  6/14 mmstart
        ↑                                    ↑
   查有哪些 session                    给出开局指令
```

实测全部 46 个含 mmbook 的 run，`mmbook` **必在 `mmstart` 之前**，且
**`mmbook accepted` 之后客户端立即发 `mmstart`**（同一秒内）。

这条因果关系是**本专项里唯一被证明的"下行→下一请求"链**。

---

## 3. `mmbook accepted` 的内容

服务端固定回 20 字节文本 `mmbook accepted`。

历史文档曾主张"必须回显客户端自己的 (A,B)"
（`COMBAT_V0_1_NEXT_001_BLOCKER §2.5`，八轮未闭合）。

**本审计的实测结论**：
- 10-26 成功轮回的是固定文本，客户端照样继续发 `mmstart`；
- 10-27/10-28/10-29 的房间轮也回同一文本，客户端也发 `mmstart`（B1）。

⇒ **"必须回显 (A,B)" 这个要求在实测中未被证实**：
固定文本已经足以让客户端进入下一步。

---

## 4. 与"战斗服地址"的关系

`mmbook` **不携带战斗服地址**。

地址在更早的 `21/5 findSessions` 应答对象里
（`build_mission_session_object(..., address67=True)`，对象 280 B 含 67 B 地址块）。

⇒ 流程顺序是：

```
21/5  → 客户端拿到地址
mmbook → 客户端预约（说"我要打这一局"）
mmstart → 客户端下令开局（带地图/模式）
→ 客户端用先前拿到的地址去连
```

**地址在 mmbook 之前就已经给了。**

---

## 5. 失败模式

| 模式 | 表现 | 出现 |
|---|---|---|
| mmbook 无应答 | 客户端不重发（6/14 是可靠通道之上的文本） | 未观测 |
| mmbook accepted 后无 mmstart | B2 形态（用户没点开始） | `ONCE_20261029_103202` |

---

## 6. 结论

| 问题 | 答案 |
|---|---|
| mmbook 是什么 | **文本预约命令**，走 6/14 |
| 它在流程里的位置 | `findSessions` 之后、`mmstart` 之前 |
| 服务端必须回什么 | 20 B 的 `mmbook accepted`（固定文本） |
| "必须回显 (A,B)" | **实测未证实**（固定文本即可） |
| 是否携带战斗服地址 | **否**（地址在 21/5 应答里） |
| 是否是匹配服务 | **不是**；它预约的是战斗服实例 |
