# 19 — 大厅根因分析

> 只分析**能解释"大厅流程为什么没走完"的根因**，不列所有缺陷。

---

## 1. 根因树

```
【为什么大厅流程没闭合】

├─ R1  客户端不连战斗服（BP-06）★ 唯一总开关
│       ├─ H1: mmstart 缺 map            ← HIGH_UNPROVEN
│       └─ H2: 在房间里(channelID≠0)     ← HIGH_UNPROVEN
│       （H1 与 H2 历史数据 100% 共线）
│
├─ R2  房间 UI 死（BP-01）★ 房间路径的第一块多米诺
│       ├─ H1: AS_* 未注册（LOW）
│       ├─ H2: 房间事件系统未建立（MEDIUM）
│       └─ 全部停在 Flash/Scaleform 层，不可达
│
├─ R3  下行未被消费（BP-02）
│       ├─ H1: 信封路由键不对       ← HIGH_UNPROVEN
│       ├─ H2: 整段被忽略           ← 未做畸形对照
│       └─ H3: 内容不足
│
└─ R4  MyEventHandler 状态未知（BP-04）
        └─ 证据陈旧，一次转储即可判定
```

---

## 2. R1 的完整证据

**现象**：客户端发出 `mmstart`，服务端收到，但客户端不建 UDP socket。

**为什么不能简单归因**：

| 候选 | 支持 | 反对 | 状态 |
|---|---|---|---|
| H1 缺 map | 8/8 成功都带 map；26/26 失败都不带 | 房间路径的 mmstart 也确实发出去了 | HIGH_UNPROVEN |
| H2 channelID≠0 | 8/8 成功都是 0 | 无法分离 | HIGH_UNPROVEN |
| H3 StartGame 推送 | 10-28 加了推送 | 10-26 不推却成功；10-27 不推也失败 | **排除** |
| H4 102/7 | 区间 C 有 | 区间 B 无 102/7 仍失败；区间 D 不处理仍失败 | **排除** |
| H5 memberCount | — | 区间 B 已=1 | **排除** |
| H6 服务未起/端口 | — | 失败轮日志头完整 | **排除** |
| H7 地址未下发 | — | 成功/失败轮 21/5 应答都是 280 B | **排除** |

**关键结构性事实**：
`mmstart` 的两种形态只差 **6 个字段**（map/gametype/difficulty/playlist/start_map_rotate/channelID），
其中 **`map` 与 `channelID` 是两个最可疑的**，且它们总是同时出现。

---

## 3. R2 的完整证据

**现象**：准备按钮点击无任何反应（无上行、无本地状态变化）。

**为什么这是根因而不是症状**：
- 它不是"服务端回错了"，是**客户端本地没有任何动作**。
- 也就是说，事件在客户端 UI 层就被丢弃了。

**三条候选**（见 `06_ROOM_READY_AND_START_FLOW.md`），全部停在不可达层。

---

## 4. R3 的完整证据

**现象**：推送发出、客户端无报错、UI 无变化。

**关键缺失**：**畸形对照**。
没有它，就无法区分"格式错"与"整段被忽略"。
这是本专项最便宜、信息量最大的一个实验（1 轮）。

---

## 5. 根因之间的关系

```
R4 (MyEventHandler) ──?──→ R2 (房间 UI 死)
                                │
R3 (下行未消费) ────────────────┘
                                │
                                ▼
                          R1 (不连战斗服)
                                ▲
                                │
        [PvE 路径绕过 R2/R3/R4，但仍在 R1 处失败]
```

**最重要的一点**：
**PvE 路径不需要 R2/R3/R4，却依然过不了 R1。**
这说明 R1 是**独立的**，不是被房间线拖累的。

---

## 6. 如果只允许做一个实验

**做 E2/PvE 复现**（在 PvE 入口、用正式 kit、记录是否出现 `TX_NAT_REPLY`）。

理由：
- 它绕开 R2/R3/R4 全部房间问题；
- 它直接检验 R1；
- 若成功 → 立刻拿到成功轮的内存转储与抓包（解锁 R4 与所有后续）；
- 若失败 → 说明"成功基线已不可复现"，需要先修环境。

---

## 7. 结论

**大厅流程未闭合的最早根因是 R1（客户端不连战斗服），
而它恰好是唯一已经被证明可以成功一次（10-26 八轮）的环节。**

这不是"从来没做对"，是"做对过一次，复现不了"。
