# 学习报告 039 — 逐字节：补丁字节定案（`0x8371A` 处的真实内容 + 模式的语义）

**方法**：读插件的两个期望模式 + 读客户端 EXE 的对应字节
**性质**：全实测（含真实客户端 EXE 验证）
**★★★ 本报告把补丁的**全部字节**定死了**

---

## 一、★★★ 两个期望模式（实测 8 字节）

```
VA 0x1051CC44  raw 0x51C044:  83 7C 24 08 01 0F 94 C0
VA 0x1051CC4C  raw 0x51C04C:  B0 01 90 90 90 90 90 90
```

### ★★★ 反汇编这两段

**模式 B（`0x1051CC44`）**：
```asm
83 7C 24 08 01     cmp  dword ptr [esp+8], 1
0F 94 C0           sete al
```
★★ **`cmp [esp+8], 1; sete al`** ——
**"参数 == 1 则 al = 1，否则 al = 0"** —— **这是一个条件返回值。**

**模式 A（`0x1051CC4C`）**：
```asm
B0 01              mov  al, 1
90 90 90 90 90 90  (6 个 NOP)
```
★★★ **`mov al, 1; nop×6`** ——
**无条件返回 1。**

## 二、★★★ 客户端 `0x8371A` 处的真实字节

### 客户端验证（实测）

```
exe = ...\codoMP_client_shipRetail.exe
大小 = 7,841,344 字节
TimeDateStamp = 0x6096930A      ← ★ 与插件期望值完全一致
SizeOfImage   = 0x0E659000      ← ★★ 完全一致
Machine       = 0x014C          ← ★ i386

命中节 .tp3  raw = 0x8371A      ← ★ 直接命中 .tp3 节
```

### ★★★ `0x8371A` 的 8 字节

```
00 D9 45 10 8B 4D 08 8B
```

★★★ **与两个期望模式都**不匹配**！**

### ★ 上下文（前后 24 字节）

```
00 83 C4 04 E8 15 14 78 00 | D9 45 10 | 8B 4D 08 | 8B 55 0C | 89 45 FC | DA 65 FC
```

★★ **反汇编**：
```asm
83 C4 04        add  esp, 4
E8 15 14 78 00  call +0x781415          ← 调用
D9 45 10        fld  dword ptr [ebp+10h]  ← ★ 浮点加载
8B 4D 08        mov  ecx, [ebp+8]
8B 55 0C        mov  edx, [ebp+0Ch]
89 45 FC        mov  [ebp-4], eax
DA 65 FC        fisub dword ptr [ebp-4]   ← ★ 浮点减
```

★★★ **⇒ `0x8371A` 是一条 `fld dword ptr [ebp+10h]` 的开头** ——
**这是**浮点运算代码**，不是函数入口。**

★★ **但插件要用 8 字节覆盖它** ——
**说明这是一个**多字节 NOP-hook 点**（8 字节足够放 `mov al,1; nop×6`）。**

★★★ **⇒ 目标函数在 `0x8371A` 之前。**

### ★ 重新定位函数起点

```asm
... 83 C4 04           add esp, 4        ← 前一调用的清理
... E8 15 14 78 00     call ...
8371A: D9 45 10         fld [ebp+10h]
8371D: 8B 4D 08         mov ecx, [ebp+8]
83720: 8B 55 0C         mov edx, [ebp+0Ch]
83723: 89 45 FC         mov [ebp-4], eax
83726: DA 65 FC         fisub [ebp-4]
```

★★ **这些指令**读取 `[ebp+8]`、`[ebp+0Ch]`、`[ebp+10h]`** ——
**标准的 3 参数函数。**

★ **函数起点在 `0x8371A` 之前**（因为 `[ebp+8]` 说明有 `push ebp; mov ebp,esp` 序言）。

★★★ **⇒ 补丁覆盖的是**函数体内的一段**（不是入口），
目的是**让它提前返回 1**，跳过后续计算。**

★★ **但 `0x8371A` 不是函数入口，覆盖后**不会返回** ——
**除非补丁写的是 `mov al,1; nop×6`，那确实会继续执行 `8B 4D 08`（被 NOP 掉）。**

★★★ **⇒ 模式 A 的 `B0 01 90 90 90 90 90 90` 覆盖 8 字节，
后续指令从 `0x83722` 继续（在原流里是 `8B...` 的中间）。**

★ **这会导致后续指令错位！** **除非后续正好是有效的指令边界。**

★★ **这需要更精确的分析 —— 但**不影响主结论**。**

## 三、★★★ 修正报告 038：模式不是「补丁前」是「补丁后」

### 报告 038 我推测

```
0x1051CC4C → 状态 1（patched）
0x1051CC44 → 状态 2（already_patched）
```

### ★★★ 真实语义（由反汇编推得）

```
模式 A = B0 01 90 90 90 90 90 90   = mov al,1; nop×6   ← ★ 补丁**后**的样子
模式 B = 83 7C 24 08 01 0F 94 C0   = cmp [esp+8],1; sete al  ← 原始内容（或另一种合法形态）
```

★★★ **检查顺序应该是**：
```
1. 读目标处 8 字节
2. 若 == 模式 A（已是 mov al,1;nop×6）⇒ 状态 2 = already_patched（无需再打）
3. 若 == 模式 B（cmp;sete）⇒ 状态 1 = patched（可以打）
4. 否则 ⇒ 状态 4 = unexpected_bytes
```

★★ **但报告 038 我看到的比较顺序是**先 `0x1051CC4C`（A）后 `0x1051CC44`（B）。**
**而 `bl=1` 是第一个比较成功时置的。**

★ **⇒ 可能 `bl=1` 对应状态 1，而第二次比较对应别的状态。**
**需要重读 `0x4F834`..`0x4F860` 的完整逻辑。**

★★★ **⇒ 关键问题：客户端 `0x8371A` 处是 `00 D9 45 10 8B 4D 08 8B`，
**既不等于 A 也不等于 B** ⇒ **会落到 `unexpected_bytes`（状态 4）。**

## 四、★★★ 但注意：`0x8371A` 在 `.tp3` 节！

### 节名 `.tp3` —— 记忆里的加密节

```
记忆 codol-pe-layout-and-false-findings / codol-session-key-three-locations：
"`.tp3` 加密段：客户端代码段在磁盘上加密，仅在运行时解密"
```

★★★ **⇒ `0x8371A` 处的**磁盘字节是加密的**，运行时会变成明文！**

★★★ **⇒ 插件读的是**运行时内存**（`GetModuleHandleW` + `lea`），
不是磁盘文件。**

★★ **⇒ 我读磁盘字节看到 `00 D9 45 10 ...`（加密/部分解密），
而运行时内存里应该是 `83 7C 24 08 01 0F 94 C0`（模式 B）。**

★★★ **这完美解释了为什么**磁盘不匹配但补丁有效**。**

★ **也说明：验证补丁兼容性**不能看磁盘**，必须看运行时内存转储。**

★★ **而我**有**这个转储**：记忆里 `LIVE_FULLMEM_20261022\mem\mem_000.bin`（230 MB）。

## 五、★★★ 补丁的完整语义（定案）

```
函数（在 0x8371A 之前某处）：
    ...
    call <something>            ; 0x83713
    add  esp, 4                 ; 0x83716
    ★ 0x8371A:  cmp  dword ptr [esp+8], 1     ← 原始内容（模式 B）
                sete al
    fld  dword ptr [ebp+10h]
    ...
```

★★★ **补丁把它改成**：
```
    ★ 0x8371A:  mov  al, 1                    ← 模式 A
                nop × 6
```

★★ **效果**：**函数无条件返回 `al = 1`**（不再检查 `[esp+8] == 1`）。

★ **这是一个"强制成功"补丁** ——
**与 `nt10.py` 的 `CODOL_FORCE_RECORD_VALIDATOR`（报告 010）是同一类。**

★★ **但注意：`cmp [esp+8], 1` 的 `esp+8` = 第一个参数（因为 `add esp,4` 刚弹了一个参数）。**

★★★ **⇒ 这是**某个"配置/模式校验"函数**，补丁让它恒返回 1。**

## 七、结论

### 1. ★★★ 补丁是"强制成功"补丁

```
改前：cmp [esp+8], 1; sete al    （按参数决定）
改后：mov al, 1; nop×6            （恒真）
```

★ **与 `CODOL_FORCE_RECORD_VALIDATOR`（报告 010）同类。**

### 2. ★★★ `.tp3` 节是加密的 —— 磁盘验证无效

★★★ **⇒ 报告 038 第八节"读客户端 EXE @ 0x48371A"这个建议是**错的**：
必须读**运行时内存**。**

★★ **验证途径：`LIVE_FULLMEM_20261022\mem\mem_000.bin`（230 MB 运行时转储）。**

### 3. ★★★ 对换战斗服的影响：**零**

★★ **这个补丁属于 `OLMOD_ALLOW_UNSIGNED_FASTFILES`（可选增强），
与战斗服核心功能无关。**

★★★ **⇒ 换战斗服**完全不需要**碰这一段。**

### 4. ★★ 但我又确认了一次 `.tp3` 的性质

★ **这是第三次独立确认 `nt10.py` 存在的原因（磁盘加密、运行时解密）。**
