## 一、latch（闭锁）机制 —— 本段的核心（行 677-691）

```python
done = set()
while time.time() - t0 < deadline and len(done) < 4:
    cur, notes = compat_patch_once(h)
    new  = cur - done
    done |= cur          # ← latch：只增不减
```

### 为什么必须 latch（行 674-676 的注释）

> 补丁3 会把 `0xB9A7C7` 的 `E8` 改成 `E9`，于是补丁2 的模式
> (`84 C0 .. 2A E8`) **再也匹配不到**；若每轮重新判定，
> 补丁2 就会"掉出计数"（**上一轮日志里 3/4 变 2/4 就是这个**）。

**机制拆解**：
1. 第一轮：补丁 2 成功（`0xB9A7C5` 75→EB），补丁 3 成功（`0xB9A7C7` E8→E9）
2. 第二轮：`compat_patch_once` 重新扫描
   - 补丁 2 的模式末字节是 `E8`，但现在已经是 `E9` → **匹配失败** → `cur` 里没有 2
   - 补丁 3 的模式开头 `E8/E9` 都接受 → 匹配成功 → `cur` 里有 3
3. 如果 `done = cur`（直接赋值），`done` 就变成 `{3}`，**补丁 2 丢失**
4. 用 `done |= cur` → `done` 保持 `{2,3}`

★ **这是一个真实的 bug 修复记录**，不是理论推演 —— 注释说"上一轮日志里 3/4 变 2/4 就是这个"。

## 二、轮询节奏（行 692）

```python
time.sleep(0.25)     # 每 250ms 试一轮
```

配合 `COMPAT_DEADLINE = 90.0` → 最多 **360 轮**。

**为什么是 0.25s**：
- 太密：频繁跨进程读（每次 `compat_patch_once` 读 ~110 字节×3 处）
- 太疏：解壳完成到补丁生效的窗口太长，可能错过客户端的关键时机

★ 实际补丁通常在 **0.0~0.5 秒**内完成（日志显示"用时 0.3s"），
因为解壳在 `t≈2s` 前就完成了，而补丁线程在 `t=0` 就启动。

## 三、收尾回读 —— 检测 TP3 还原（行 693-699）

```python
for i, ad, want in ((1, 0x00B9A78E, b"\x75"),
                    (2, 0x00B9A7C5, b"\xEB"),
                    (3, 0x00B9A7C7, b"\xE9"),
                    (4, 0x00BA3C1C, b"\x90\x90")):
    got = rpm(h, ad, len(want))
    log("回读#%d @0x%08X = %s 期望 %s %s" % (..., "OK" if got == want else "!! 不匹配"))
```

**四个回读地址**（与补丁点的关系）：

| 补丁 | 写入地址 | 回读地址 | 关系 |
|---|---|---|---|
| 1 | `base+i+2` | `0xB9A78E` | **直接是写入点** |
| 2 | `base2+i+2` | `0xB9A7C5` | **直接是写入点** |
| 3 | `base2+i` | `0xB9A7C7` | **直接是写入点** |
| 4 | `0xBA3C1C` | `0xBA3C1C` | **直接是写入点** |

★ 注意补丁 1 的回读是 `0xB9A78E`，而补丁 1 的搜索起点是 `0xB9A78C-16 = 0xB9A77C`。
`0xB9A78E = 0xB9A78C + 2`，说明**实际匹配位置就在参考点**（`i=16`，`base+16+2`）。

### 为什么要收尾回读

> 若被 **TP3 完整性检查还原**，这里会直接暴露

**TP3 会周期性检查关键代码段的完整性**。如果补丁被还原：
- 内存里是原始字节
- 补丁"写了但没留住"

★ **这解释了为什么要持续重试**：即使 4/4 成功，也可能**稍后被 TP3 改回去**。
但代码只在**开头** latch，收尾回读只**报告**不重打 —— 这是设计选择，意味着：
**如果 TP3 在运行中还原补丁，这套代码不会自动修复。**

## 四、失败诊断的分层（行 700-707）

```python
if len(done) == 4:
    log("4/4 全部成功 (用时 %.1fs)")
else:
    log("只完成 %d/4: %s (超时 %.0fs)")
    for i in (1,2,3,4):
        if i not in done:
            log("!! 补丁%d 的字节模式始终没出现(该段可能还没解壳)")
```

**失败的唯一解释**：`该段可能还没解壳`。

★ **这个判断是对的但不完整**。其他可能：
- 地址变了（不同 build）
- TP3 阻止了写入
- `_wpm_code` 的 `VirtualProtectEx` 失败

但代码**只给了"没解壳"这一种解释** —— 是简化，不是穷举。

---

## 五、这一块的结论

1. **latch 是必需的，不是优化** —— 补丁间有破坏性依赖（3 破坏 2 的模式）。
2. **0.25s × 360 轮**的节奏，实际 0.3s 内完成。
3. **收尾回读**能发现 TP3 还原，但**发现后不重打**。
4. **失败诊断只说"没解壳"**，实际可能更多原因 —— 这是代码的一个局限。
