**性质**：全实测
**★★★ 本报告揭示了客户端的加壳结构，并修正了"只有一个 .tp3 节"的认知**

## 二、★★★ 逐节分析

### 节 1：`.tp3` @ `0x1000`，VSize `0x8A689A`（**8.6 MB**），RawSize `0x593000`（5.6 MB）

```
Chars = 0x60000020 = CODE | EXECUTE | READ
                    （IMAGE_SCN_CNT_CODE | MEM_EXECUTE | MEM_READ）
```

★★★ **⇒ 这是**主代码段**，8.6 MB 虚拟 / 5.6 MB 磁盘。**

★★ **`VSize > RawSize`（8.6 > 5.6）⇒ 有 3 MB 是**解壳后展开**的。**

★★★ **⇒ 这就是 `.tp3` 加密的核心证据：磁盘 5.6 MB，内存 8.6 MB。**

### 节 2：`.tp3` @ `0x8A8000`，VSize `0x16DA70`（1.4 MB），Raw `0x594000`

```
Chars = 0x40000040 = INITIALIZED_DATA | READ
```

★ **只读数据段。**

### 节 3：`.tp3` @ `0xA16000`，VSize `0x0DBB1CC0`（**230 MB**），RawSize `0x62000`（400 KB）

★★★ **`VSize` 230 MB，`RawSize` 只有 400 KB —— 差了 **575 倍**！**

★★ **`Chars = 0xC0000040 = INITIALIZED_DATA | READ | WRITE`**

★★★ **⇒ 这是**巨大的可写数据区**（BSS / 堆初值 / 资源表），
绝大部分是**未初始化**（零填充）。**

★ **230 MB 与 `mem_000.bin` 的 241 MB 大小**呼应** ——
**内存转储的主体就是这一节。**

### 节 4：`.tp3` @ `0xE5C8000`，VSize `0x31`（49 字节）

★ **极小的段** —— 可能是**补丁/标记区**。

### 节 5：`.tp3` @ `0xE5C9000`，VSize `0x9228`（37 KB），Raw `0xA000`（40 KB）

★ **只读数据，RawSize > VSize**（磁盘上多）。

### 节 6：`.tvm0` @ `0xE5D3000`，VSize `0x4000`（16 KB），Raw `0x2000`（8 KB）

```
Chars = 0x60000020 = CODE | EXECUTE | READ
```

★★★ **`.tvm0` 是独立的节名** ——
**记忆 `codol-tvm0-is-pic-code` 说"`.tvm0` 是密钥化分支的派发器"。**

★ **16 KB 代码，8 KB 磁盘 —— 也是加密的（2:1 展开）。**

### 节 7：`.tp3` @ `0xE5D7000`，VSize `0x82000`（532 KB），Raw `0x6000`（24 KB）

```
Chars = 0xE0000020 = CODE | EXECUTE | READ | WRITE   ← ★★ 可写+可执行！
```

★★★ **`0xE0000020` 是 `RWX`** —— **极不寻常**（现代编译器不会生成 RWX 节）。

★★ **⇒ 这是**运行期自修改代码区**（解壳器 / 反调试 / 动态生成代码）。**

★★ **只有 24 KB 磁盘，532 KB 内存 ⇒ 22 倍展开。**

## 三、★★★ 运行时 `0x483700` 的完整反汇编（验证解壳）

```asm
00483700  C4 01                 les  eax, [ecx]          ← 伪（跨函数边界）
00483702  C7 44 24 2C 00 00 00 00  mov dword ptr [esp+2Ch], 0
0048370B  E8 21 4A 74 00        call 0xBC7B31            ← ★
00483710  83 C4 24              add  esp, 24h
00483713  85 C0                 test eax, eax
00483715  74 04                 je   +4                  ← 失败 → 0x48371B?
00483717  32 C0                 xor  al, al              ← ★ 失败路径返回 0
00483719  EB 08                 jmp  +8                  ← 跳过
--- 成功路径 ---
0048371B  83 7C 24 08 01        cmp  dword ptr [esp+8], 1    ← ★★★ 模式 B 在此
00483720  0F 94 C0              sete al
00483723  33 F6                 xor  esi, esi
00483725  89 35 9C B2 C2 01     mov  [0x1C2B29C], esi
0048372B  89 35 A0 B2 C2 01     mov  [0x1C2B2A0], esi
00483731  84 C0                 test al, al
00483733  0F 84 00 02 00 00     je   +0x200              ← al==0 跳远
00483739  B8 20 00 00 00        mov  eax, 20h
0048373E  B9 60 F8 C4 01        mov  ecx, 1C4F860h
00483743  8B 91 A4 BE FF FF     mov  edx, [ecx-415Ch]
00483749  3B 11                 cmp  edx, [ecx]
0048374B  0F 85 35 02 00 00     jne  +0x235
00483751  83 E8 04              sub  eax, 4
00483754  83 C1 04              add  ecx, 4
00483757  83 F8 04              cmp  eax, 4
0048375A  73 E7                 jae  -0x19              ← 循环（校验 8 个 DWORD）
0048375C  68 D0 1F 00 00        push 1FD0h
00483761  68 34 F7 C4 01        push 1C4F734h
00483766  68 24 B7 C4 01        push 1C4B724h
0048376B  E8 81 F0 7B 00        call 0xC428 ...
```

★★★ **注意：我读到的运行时字节是 `83 7C 24 08 01` 在 `0x48371A`，
但反汇编从 `0x483700` 起，指令边界推到 `0x48371B`。**

★★ **⇒ 这是因为我用 `0x48371A` 作为参考点，而实际指令边界是 `0x48371B`。**

★ **`mem_000.bin` 的读取显示 `0x48371A` 起是 `83 7C 24 08 01 0F 94 C0`，
若反汇编从 `0x483700` 顺序解码，`83 7C 24 08 01` 落在 `0x48371B`。**

★★★ **⇒ 偏移可能有 1 字节差异，需要更仔细的边界确认。**
**但**模式 B 的 8 字节 `83 7C 24 08 01 0F 94 C0` 确实存在** —— 这是核心。**

### ★★ 关键发现：`0x48371B` 前有 `test eax,eax; je; xor al,al; jmp`

```asm
00483713  85 C0              test eax, eax
00483715  74 04              je   0x48371B        ← 成功 → 跳到模式 B
00483717  32 C0              xor  al, al          ← 失败 → al = 0
00483719  EB 08              jmp  0x483723
```

★★★ **⇒ 完整逻辑**：
```c
if (some_check()) {              // 0x483713
    al = (arg == 1);             // 0x48371B（模式 B）
} else {
    al = 0;                      // 0x483717（失败）
}
*(0x1C2B29C) = 0;                // 0x483723
*(0x1C2B2A0) = 0;                // 0x48372B
return al;
```

★★★ **⇒ 补丁把 `0x48371B` 换成 `mov al,1; nop×6` 后**：
```c
if (some_check()) {
    al = 1;                      // ← 不再检查 arg==1
} else {
    al = 0;                      // ★ 失败路径仍然返回 0！
}
```

★★ **⇒ 补丁**只影响成功路径**！失败路径（`some_check()` 为假）仍然返回 0。**

★★★ **这是一个**精妙的**最小补丁 —— 只覆盖有条件的那一支。**

## 四、★★★ 后续的 8 DWORD 校验（`0x483739`..`0x48375A`）

```asm
00483739  B8 20 00 00 00        mov  eax, 20h           ← 32 字节 = 8 DWORD
0048373E  B9 60 F8 C4 01        mov  ecx, 1C4F860h      ← ★ 表 A
00483743  8B 91 A4 BE FF FF     mov  edx, [ecx-415Ch]   ← ★ 表 B（1C4B704h?）
00483749  3B 11                 cmp  edx, [ecx]
0048374B  0F 85 35 02 00 00     jne  +0x235             ← 不等 → 失败
00483751  83 E8 04              sub  eax, 4
00483754  83 C1 04              add  ecx, 4
00483757  83 F8 04              cmp  eax, 4
0048375A  73 E7                 jae  -0x19              ← 循环
```

★★★ **⇒ 循环比较 8 个 DWORD（32 字节）**：
```c
for (i = 0; i < 8; i++) {
    if (tableA[i] != tableB[i]) return 0;   // 校验失败
}
```

★★ **`ecx - 0x415C`** ——
```
0x1C4F860 - 0x415C = 0x1C4B704
```

★★★ **⇒ 比较 `0x1C4F860` 与 `0x1C4B704` 两处各 32 字节。**

★ **这是**完整性校验**（自校验或资源校验）。**

★★ **可能与"未签名资源"的校验有关（`OLMOD_ALLOW_UNSIGNED_FASTFILES`）。**

## 六、结论

### 1. ★★★ 客户端是**完整加壳**的（6 个 `.tp3` + 1 个 `.tvm0`）

★★ **没有标准节名，全部代码/数据装在伪装成 `.tp3` 的节里。**

★★★ **⇒ 任何静态分析**必须**用运行时转储。**

### 2. ★★★ 230 MB 的 `.tp3` 解释了内存转储的大小

```
节 3：VSize 230 MB（RawSize 400 KB）
mem_000.bin：241 MB
```

★ **⇒ 转储主体是这一节的零填充区。**

### 3. ★★★ 补丁只影响**成功路径**

★★ **`0x48371B` 是 `if (check())` 的真分支 —— 补丁只覆盖它。**
**失败分支（`0x483717` 的 `xor al,al`）不受影响。**

★ **⇒ 这是**最小侵入**设计。**

### 4. ★★ 有 8 DWORD 的完整性校验

★★ **`0x1C4F860` vs `0x1C4B704` 各 32 字节。**
**失败则返回 0。**

★ **这可能是**资源完整性校验**（与 `ALLOW_UNSIGNED_FASTFILES` 相关）。**

### 5. ★★★ `.tp3` 第 7 节是 **RWX**

★★ **`0xE0000020` = 可写 + 可执行 + 可读** ——
**运行期生成/修改代码（解壳器或反调试）。**
