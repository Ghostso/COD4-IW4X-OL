## 二、★★★ 修正报告 042 的"矛盾"

### 我之前的错误推理

```
我以为：0x483719 的 rel8 = 0x08，jmp 在 0x483718
        ⇒ 0x48371A 是 cmp opcode
        ⇒ je 0x48371B 跳到 cmp 中间（矛盾）
```

### 权威反汇编的真相

```asm
00483716  32c0    xor al, al
00483718  eb08    jmp 0x483722     ← ★ rel8 从 0x483719 算：0x48371A+8 = 0x483722
0048371A  837c240801  cmp [esp+8],1
```

★★★ **`jmp 0x483722` 的 rel8 = `0x08`，从 **`0x48371A`** 算：`0x48371A + 8 = 0x483722` ✓**

★★ **`je 0x48371a`（`0x483714` 的 `7404`）：`0x483716 + 4 = 0x48371A` ✓**

★★★ **⇒ 两条分支（`je` 和 `jmp`）的目标都在**正确的指令边界**上。**

★★ **我之前的推算把 `jmp` 的起点当成了 `0x483718` 而 rel8 的基准算成了 `0x483719`，
导致整体偏移 1 字节。**

## 三、★★★ 补丁的完整语义（权威定案）

### 函数结构

```c
// 伪代码（由反汇编还原）
int func(int arg) {
    // 0x4836DA: 第一次检查
    if (check1()) {          // call 0xbc7e70
        al = 0;              // 失败
    } else {
        // 0x4836E2..0x48370F: 第二次调用（9 个参数！）
        r = call_0xbc8130(0x1c4f760, 0x100, 0x1c4f740, 0x20,
                          1, esi, 8, &buf1, &buf2);
        if (r) {
            al = 0;          // 失败
        } else {
            // 0x48371A: ★ 补丁点
            al = (arg == 1);     // ★★★ 原语义
        }
    }
    // 0x483722: 汇合
    *(0x1C2B29C) = 0;
    *(0x1C2B2A0) = 0;
    if (al == 0) goto 0x483938;   // 失败出口
    // ... 8 DWORD 完整性校验 ...
    // ... 成功路径 ...
}
```

★★★ **关键**：
```
0x483722 是两个分支的汇合点（xor esi,esi 前）
0x48371A 的 cmp 只在"两次检查都通过"时执行
```

### 补丁效果

```
原:  al = (arg == 1)
补丁: B0 01 = mov al, 1
     90×6 = NOP 填满 8 字节
```

★★★ **⇒ 补丁后**：
```c
if (check1() == 0 && call_0xbc8130(...) == 0) {
    al = 1;                  // ★ 无条件真
}
// 其余不变
```

★★ **⇒ **仍然保留了前面两个检查**！补丁只强制"最后那一步"成功。**

★ **这是**最小侵入**：不解锁未通过 `check1` 或 `call_0xbc8130` 的情况。**

## 五、★★★ 8 DWORD 完整性校验的细节

```asm
00483738  mov  eax, 0x20             ← 32 字节 = 8 DWORD
0048373D  mov  ecx, 0x1c4f860        ← 表 A 指针
loop:
00483742  mov  edx, [ecx - 0x415c]   ← 表 B（0x1C4B704）
00483748  cmp  edx, [ecx]            ← 与表 A 比较
0048374A  jne  0x483985              ← 不等 → 失败
00483750  sub  eax, 4
00483753  add  ecx, 4
00483756  cmp  eax, 4
00483759  jae  loop
```

★★ **`ecx - 0x415C`：`0x1C4F860 - 0x415C = 0x1C4B704`**

★★★ **⇒ 比较内存中**两处相距 0x415C 的表**，各 8 个 DWORD。**

★★ **这是**自校验**（`0x1C4F860` 可能是运行期解密的表，
`0x1C4B704` 是磁盘上的原始表）。**

★ **两者相等 ⇒ 解壳成功。**

★★★ **⇒ 这是**反篡改校验**：如果补丁破坏了这段代码的数据，校验会失败。**

## 七、结论

### 1. ★★★ 撤销报告 042 的"1 字节矛盾"

★★★ **补丁目标 `0x48371A` 与指令边界**完全一致**。**
**`je` 和 `jmp` 两条分支都正确指向 `0x48371A` / `0x483722`。**

### 2. ★★★ 补丁是"最后一步强制成功"

★★ **保留前两个检查（`check1` / `call_0xbc8130`），
只强制 `arg == 1` 那一支返回真。**

### 3. ★★★ 有 8 DWORD 的反篡改校验

★★ **`0x1C4F860` vs `0x1C4B704`（相距 `0x415C`）** ——
**解壳完整性校验。**

★ **如果我们的补丁破坏了附近的数据，这个校验会失败。**

### 4. ★★★ capstone 是唯一的可靠路径

★★★ **我此前的 6 次手算错误，全部被 capstone 一次性解决。**

★★ **⇒ 后续所有客户端代码分析，必须用 `capstone`（已确认 5.0.7 可用）。**
