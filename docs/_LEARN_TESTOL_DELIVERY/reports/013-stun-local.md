## 一、这个模块解决什么问题（行 4-6）

> CODOL 客户端取"公网地址"走 UDP STUN 到 `stun1/2/3-tub.codol.qq.com`（见 `TESTOL\stun.ini`）。
> 坏启动的遥测是 `Address Fail|result = -3`（= `getPublicAddr` 失败），
> 且坏轮呈现 **UDP 重传超时形态（71/4 之后空转 29 秒）**。
> 把这三个域名指到 `127.0.0.1` 并由本程序确定性应答，即可把这条链路固定下来。

★ **症状链**：
```
getPublicAddr 失败 (result = -3)
    ↓
71/4 之后空转 29 秒（UDP 重传超时）
    ↓
t≈54s 致命错误
```

## 二、★★★ 最重要的部分：假设被自己否证（行 15-26）

### 第一版假设（错的）

> 同时回 `MAPPED-ADDRESS(0x0001, RFC3489)` 与 `XOR-MAPPED-ADDRESS(0x0020, RFC5389)`
> ——严格的 5389 客户端会忽略前者，3489 客户端会忽略后者。

★ **这是一个"标准 STUN"假设**：按 RFC 3489/5389 实现就对了。

### 实测否证（2026-10-07 03:0x）

> **客户端不发 RFC5389 STUN。**
> 它的 `getPublicAddr` 走的是 **Demonware 私有 STUN**，两种请求：
> ```
> 14 02 00 00   (类型 0x14，4 字节)
> 1e 03 00      (类型 0x1E，3 字节)
> ```
> 目标端口是 **3074**（UDP），**不是 3478/19302**

★★★ **这是本报告最有价值的一条**：
**"STUN"这个词让人以为是标准协议，实际是 Demonware 私有格式。**

### 抓包证据（好轮 vs 坏轮）

**好轮**（`99-Tmp\cap-nic-d6.pcapng`）：
```
客户端 192.168.5.11:22011  ->  185.34.107.128:3074
真服 200 ms 内回:  1502003afc12715210b9226b81020c   (15 字节)
⇒ 开局正常
```

**坏轮**（`99-Tmp\cap-stun-d5.pcapng`，回环）：
```
同样两发探针发往 127.0.0.1:3074
（hosts 把 stun1/2/3-tub.codol.qq.com 指到 127.0.0.1）
⇒ 0 回复
⇒ 71/3 UserWarning|…|Address Fail|result = -3
⇒ t≈54s 致命错误
```

### ★★ 结论：坏启动是**必然**而非概率

> 本脚本原先只听 3478/19302 ⇒ **一个探针都收不到**
> （这正是「STUN 假设被否证」的原因），**坏启动因此是必然而非概率**。

★★★ **这一句把"20-40% 坏启动率"（报告 007）的谜团解开了**：

- 如果 hosts 把 STUN 域名指到 127.0.0.1，而监听器只听 3478 → **100% 坏启动**
- 如果不指 hosts（走真实 `185.34.107.128:3074`，那个服务器还在）→ **100% 好启动**
- **"概率"来自 hosts 状态或 DNS 解析结果的差异，不是随机**

★ **报告 007 里"坏启动概率 20-40%"这个说法，现在有了物理解释。**

## 三、Demonware 私有 STUN 的应答格式（行 97-131）

### 布局（行 100-102）

```
<type+1> 02 00 <mapped_ip:4> <mapped_port:2 LE> <server_ip:4> <server_port:2 LE>
```

```
+0x00  1   type + 1      （0x14→0x15, 0x1E→0x1F）
+0x01  2   0x0002        （= socket.AF_INET，小端）
+0x03  4   mapped_ip     客户端源地址
+0x07  2   mapped_port   客户端源端口（小端）
+0x09  4   server_ip     本应答器地址
+0x0D  2   server_port   本应答器端口（小端）
共 15 字节
```

### 真实抓包实例（行 102-104）

```
15 02 00 | 3a fc 12 71 | 52 10 | b9 22 6b 81 | 02 0c
```

**逐字段解码**：
```
15        = 0x14 + 1        → 0x14 的应答
02 00     = AF_INET (LE)    → 2
3a fc 12 71 → 58.252.18.113   ← 客户端的公网地址（NAT 后）
52 10     = 0x1052 (LE)     → 4178   ← 客户端 NAT 后端口
b9 22 6b 81 → 185.34.107.129  ← 服务器地址
02 0c     = 0x0C02 (LE)     → 3074   ← 服务器端口
```

★★ **这是一个完整的 NAT 反射**：服务器告诉客户端"我看到你的地址是 `58.252.18.113:4178`"。

### 与老外归档的差异（行 106-109）

> 老外归档字节（`ServerTests.cpp:95-114`）**同布局**，
> 只是 mapped 填占位 `F0 00 00 01`、且 **0x1E 取 9 字节**（不带 server 字段）。
> 这里照**本机客户端实测接受过的 15 字节形态**（两种类型都 15 字节）。

★ **两处差异**：

| 项 | 老外 | 本包 |
|---|---|---|
| mapped 地址 | 占位 `F0 00 00 01` | 真实客户端源地址 |
| `0x1E` 应答长度 | **9 字节**（无 server 字段） | **15 字节**（含 server 字段） |

★★ **"照本机客户端实测接受过的"** —— 这是**实证优先于参照**的正确做法。

## 四、双协议并存的设计（行 64-95）

### `serve()` 的尝试顺序（行 152-155）

```python
resp, note = build_dw_response(data, addr, port)    # ★ 先试 Demonware 私有
if note is None:
    resp, note = build_response(data, addr)         # 再试标准 STUN
```

★ **私有协议优先，标准协议兜底。**

### `build_dw_response` 的判定（行 111-121）

```python
t = data[0]
if t == 0x14:   kind = "0x14 NAT"
elif t == 0x1E: kind = "0x1E ADDR"
else:           return None, None        # ← 不是 DW，交给标准 STUN
```

★★ **只认首字节 `0x14` / `0x1E`** —— 极简判定。

### ★ 两种类型的语义（我的推断）

| 类型 | 名字 | 我的理解 |
|---|---|---|
| `0x14` | **NAT** | 探测 NAT 类型 / 公网地址（标准 STUN 语义） |
| `0x1E` | **ADDR** | 探测服务器地址（拿到 server 的 IP:port） |

★ 两者应答**格式相同**，只是 `type+1`。

### 标准 STUN 部分（行 64-94）

```python
if len(data) < 20:
    return None, "短包 %d 字节" % len(data)
mtype, mlen = struct.unpack_from(">HH", data, 0)
if mtype != BINDING_REQUEST:      # 0x0001
    return None, ...
tx = data[4:20]                   # 128-bit txid 原样回显
cookie = struct.unpack_from(">I", data, 4)[0]
```

★ **注意**：`data[4:20]` 对 RFC 5389 = `[magic cookie:4][txid:12]`，
对 RFC 3489 = `[128-bit txid]`。**整体回显两种都成立**（注释行 11-12 说明了）。

### XOR-MAPPED 的计算（行 84-87）

```python
xport = port ^ (MAGIC_COOKIE >> 16)         # 0x2112
xip   = bytes(a ^ b for a,b in zip(ip_be, struct.pack(">I", MAGIC_COOKIE)))
```

★ **标准的 RFC 5389 XOR 算法**，正确。

### ★ 但这段**永远不会被执行到**（在交付包里）

因为客户端只发 `0x14`/`0x1E`，走 `build_dw_response` 就返回了。
**标准 STUN 部分是"万一"的兜底，实测用不到。**

### 多端口实现（行 172-177）

```python
ts = [threading.Thread(target=serve, args=(p, dump), daemon=True) for p in ports]
for t in ts: t.start()
while True: time.sleep(3600)

★ **每个端口一个线程，各自绑 `0.0.0.0`**。

## 七、★ 这一块的架构意义

### 它解掉的是一个**必要条件**

```
客户端启动
    ↓
getPublicAddr()  →  UDP 0x14 / 0x1E 到 stun*.codol.qq.com:3074
    ↓
必须收到 15 字节应答
    ↓                 ↓
收到                收不到
    ↓                 ↓
继续启动          Address Fail = -3 → 空转 29s → t≈54s 致命
```

★★ **它是一个"必须满足但很容易漏"的前置条件**，而漏掉它的表现
（**UDP 重传超时、空转 29 秒**）**完全不像"少了个 STUN 服务器"**。

### ★★★ 这解释了 GOLDEN 链为什么不用它

GOLDEN 链（我们自己的）**没有 `stun_local.py`**，但能进大厅。

**可能原因**：
- (a) GOLDEN 跑的时候 hosts **没有**把 stun 域名指到 127.0.0.1
     ⇒ 客户端连真实 `185.34.107.128:3074`（那台服务器还活着）⇒ 能通过
- (b) GOLDEN 有等效组件

★ **如果是 (a)**，那么 **GOLDEN 依赖一个外部公网服务器** ——
这是个**隐藏依赖**，一旦那台服务器下线，GOLDEN 也会失败。

★★ **这是一个必须验证的关键点。**

## 八、这一块的结论

### 学到的契约

1. ★★★ **"STUN"= Demonware 私有协议**，不是 RFC 5389。
   请求 `0x14 02 00 00`（4 字节）/ `0x1E 03 00`（3 字节），**端口 3074**。
2. **应答 15 字节**：`<type+1> 0200 <mapped_ip:4> <mapped_port:2LE> <server_ip:4> <server_port:2LE>`
3. **`type+1`**：`0x14→0x15`，`0x1E→0x1F`。
4. **mapped = 客户端自己的源地址**（NAT 反射语义）。
5. **监听端口必须含 3074**，只听 3478 会**一个包都收不到**。
6. **标准 STUN 部分是死代码**（客户端不发），保留作为兜底。

### 方法论价值（★ 最高）

**这是整个包里唯一记录了"假设 → 抓包 → 否证 → 修正"完整链条的模块。**

```
假设：标准 STUN (RFC5389/3489)
    ↓ 实测（抓包）
发现：客户端发 0x14/0x1E 到 3074
    ↓
结论：STUN 假设被否证
    ↓
修正：加 build_dw_response，端口加 3074
    ↓
结果：坏启动从"概率 20-40%"变成"可解释的必然"
```

★★ **"坏启动是必然而非概率"这句话，是本次学习中最硬的一条诊断结论。**

### 未解之谜

★ **GOLDEN 链没有 `stun_local.py` 却能进大厅** —— 它是靠真实公网 STUN 服务器吗？
**如果是，GOLDEN 有一个外部依赖，这在离线场景下是隐患。**
