## 三、★★★ 四个补丁的语义（由 `nt10.py` 注释还原）

★★★ **⇒ `nt10.py` 的补丁是**让客户端接受自签名 auth**（配合 `fake_auth_tls.py` 的本地 CA）。**

## 五、★★★ 但发现一个新问题：补丁目标差 1 字节

```
指令边界：0x48371B
补丁目标：0x48371A（由 `lea ebx, [edi+8371Ah]`）
```

★★ **如果确实写 `0x48371A`，会破坏：**
```
0x483719: EB 08    jmp +8      ← 这条指令的第 2 字节（08）会被覆盖
0x48371A: 83       ← 被覆盖成 B0
```

**结果：`0x483719` 变成 `EB B0`（`jmp -0x50`）—— 跳到 `0x4836CB`！**

★★★ **⇒ 这会导致**严重破坏**（跳到别处执行）。**

★★ **除非：**
- (a) 我算 `lea` 的偏移错了
- (b) 实际目标在运行时确实是 `0x48371B`（`0x8371B`）

★★★ **⇒ 需要重新精确读 `0x4F788` 的 `8D 9F 1A 37 08 00`（`lea ebx, [edi+0x8371A]`）。**

★ **`8D 9F` = `lea ebx, [edi+disp32]`，`disp32 = 1A 37 08 00 = 0x0008371A`** ✓

★★★ **⇒ 偏移确实是 `0x8371A`。**

★★ **那为什么补丁有效？可能：**
- **`edi` 不是 `0x400000`**（`GetModuleHandleW(NULL)` 可能返回别的）
- **或者 `0x48371A` 处确实是那条 `cmp` 的起点**（我的边界判断错）

★★ **关键：`je 0x48371B` 的目标是 `0x48371B`，但 `jmp 0x483723` 的偏移是 `08`（从 `0x48371B` 算，`0x48371B+8 = 0x483723`）。**

★★★ **⇒ 如果 `je` 目标是 `0x48371B`，那 `cmp` 就在 `0x48371B`。**
**但补丁写 `0x48371A`。**

★★ **⇒ 也许 `nt10.py` 或外部包用的是**运行时实际基址**，而不是 `0x400000`。**

★★★ **⇒ 必须读客户端实际加载基址（`mem_000.bin` 是 0x400000 起，但可能 ASLR）。**

★ **`mem_000.bin` 从 `MZ` 开始，说明转储就是按 `0x400000` 起算的。**
**⇒ 基址确实是 `0x400000`。**

★★★ **⇒ 那么 `0x48371A` 处是 `83`，`0x48371B` 处是 `7C`。**
**补丁写 `0x48371A` 会覆盖 `83`（正确）。**

★★ **但如果指令边界是 `0x48371A`（`83 7C 24 08 01` = 5 字节），
那 `je 0x48371B` 就跳到**指令中间**。**

★★★ **⇒ 这说明我对 `je` 目标的计算又错了。**

**重算**：
```
0x483715: 74 04      je +4
         下一条 = 0x483717
         目标   = 0x483717 + 4 = 0x48371B
```

★ **确实是 `0x48371B`。而 `cmp` 在 `0x48371A`。**

★★★ **⇒ `je` 跳到了 `cmp` 指令的**第 2 字节**（`7C`）！这是**故意的**。**
**`0x48371A` 处的 `83` 是 `cmp` opcode，`je` 跳过它，从 `0x48371B` 的 `7C 24 08 01` 开始...**

★★ **不，`7C` 不是有效 opcode 起点。**

★★★ **⇒ 唯一自洽的解释：`0x48371A` 处的 `83` **不是** `cmp` 的 opcode，
而是**上一条指令的末尾**，`0x48371B` 才是 `cmp` 的起点。**

★★ **但如果 `cmp` 在 `0x48371B`，那 `83 7C 24 08 01` 就是 `cmp [esp+8], 1` ✓**

★★★ **⇒ 那么 `0x48371A` 是 `jmp rel8` 的 rel8 字节（`08`）。**

★★ **而补丁写 `0x48371A` 会覆盖 `08`（rel8）→ 破坏 `jmp`。**

★★★ **⇒ 这与"补丁有效"矛盾。**

★ **⇒ 我需要重新核对 `mem_000.bin` 的 `0x483719` 和 `0x48371A` 两个字节：**
```
0x00483718: EB      jmp
0x00483719: 08      rel8 = +8
0x0048371A: 83      ← cmp opcode！
```

★★★ **⇒ `jmp` 在 `0x483718`，`rel8` 在 `0x483719`（`08`）。**
**`0x48371A` 是 `83` = `cmp` opcode ✓**

**重算 `je`**：
```
0x483715: 74 04    je +4
         下一条 = 0x483717
         目标 = 0x483717 + 4 = 0x48371B  ← ★ 跳到 cmp 的第 2 字节
```

★★★ **⇒ 这仍然矛盾。除非 `je` 的目标应该是 `0x48371A`，即 `rel8` 应该是 `03` 而不是 `04`。**

★★ **实测 `0x483715: 04`（rel8 = 4）。**
**`0x483715 + 2 + 4 = 0x48371B`。**

★★★ **⇒ `je` 确实跳到 `0x48371B`。**

★★ **而 `0x48371A` 的 `83` 是 `cmp` opcode。**

★★★ **⇒ `je 0x48371B` 是**跳到 `cmp` 的中间** —— 这在正确编译的代码里不可能。**

★★ **⇒ **我的指令边界解码仍然有误**。必须停止手算，改用更可靠的方法或承认限制。**
