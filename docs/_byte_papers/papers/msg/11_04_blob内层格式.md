## ★ 关键发现：blob 的首字节 = 长度

枚举 `11/4` 全部形态后，blob 开头高度一致：

| blob 长度 | 首 8 字节 | 首字节 |
|---|---|---|
| 16 | `0c 00 00 00 02 02 00 00` | `0c` = 12 |
| 20 | `10 00 00 00 02 02 00 00` | `10` = 16 |
| 21 | `11 00 00 00 18 1c 5a 98` | `11` = 17 |
| 30 | `1a 00 00 00 02 04 00 00` | `1a` = 26 |
| 63 | `3b 00 00 00 02 06 00 00` | `3b` = 59 |
| 129 | `7d 00 00 00 02 02 00 00` | `7d` = 125 |
| 245 | `f1 00 00 00 02 04 00 00` | `f1` = 241 |
| 267 | `07 01 00 00 02 06 00 00` | `07 01` = 263 |

**每一个形态都满足**：

```
首 4 字节（u32 小端）= blob 长度 - 4
```

- 长度 16 → 首 u32 = 12 = 16-4 ✓
- 长度 20 → 16 = 20-4 ✓
- 长度 21 → 17 = 21-4 ✓
- 长度 267 → 263 = 267-4 ✓

**这不是巧合，是协议规则。**

## 内层结构

```
blob := u32 内容长度 | <内容长度字节的数据>
```

**这是一种"自带长度前缀的裸数据"格式，完全不使用类型标签。**

---

## 为什么它看起来不像 TLV

因为**它真的不是 TLV。**

外层（payload）是 Demonware ByteBuffer（每个值带类型标签）。
内层（blob 内容）是**另一个层次的格式**，用简单的长度前缀。

**这是我之前判断失误的根本原因**：
我一直用外层的文法去解内层。

---

## 内容里的可辨识结构

剥掉 4 字节头后，内容开头常见：

| 内容开头 | 出现次数 |
|---|---|
| `02 02 00 00 ...` | 最多 |
| `02 04 00 00 ...` | 次多 |
| `02 06 00 00 ...` | |
| `02 08 00 00 ...` | |
| `18 1c 5a 98 ...` | 少数 |

**`02 XX 00 00` 这个模式极稳定。**

其中 `XX` ∈ {02, 04, 06, 08} —— **全是偶数**。

可能的解释：

- `02` = 某个类型码
- `XX` = 某个长度或计数（2, 4, 6, 8）
- `00 00` = 保留

**如果 `XX` 是"元素个数 × 2"，那这些是数组。**

---

## 与 `28/4` 的对照

`28/4` 的 blob 数据也是裸 u32 序列，但**没有长度前缀**。
说明**数组标签 `0x6c` 和 blob 标签 `0x13` 的内层格式不同**：

- `0x6c`：直接是 u32 序列
- `0x13`：先是 u32 长度，再是数据

**这解释了为什么它们需要两个不同的标签。**

## 修正后的完整结构

```
11/4 payload :=
    u64 0x1122334455667788
    blob  (13 08 <N> <u32 N-4> <N-4 字节>)
    u32 1
    00
```

其中内层 blob：

```
<u32 内容长> <内容>
```
