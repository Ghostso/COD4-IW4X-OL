# 报文 `10/20` · 探讨：三个 0x00 与一次失败的诊断

> 对应：`msg/10_20_发布者参数.md`

---

## 一、这条报文最初是"解析失败"的

在 v4 解析器上：

```
10/20   ok=0   bad=88   <<<
```

88 条全部失败。

报错：`unknown op 06`。

---

## 二、第一反应：是不是被截断了

看到 `10/20` 的末尾：

```
... 06 00 00 00
```

三个 0x00。

第一反应：**"最后两个 0x00 是 u16 的值，最后一个是终止符"** —— 对。
但同时也怀疑：**会不会是 u16 的值被吃掉了？**

如果是这样，解析器就会认为"u16 = 0，然后终止"，
而实际是"u16 = 0，然后终止" —— **恰好一样**。

所以这个报文**没有**触发第 1 卷的陷阱，
因为它末尾的 u16 值恰好是 0。

---

## 三、真正的失败原因

不是"三个 0x00"，是 **`0x06` 这个标签根本不在表里**。

v4 的 FIXED 表：

```python
FIXED = {0x01: 1, 0x03: 1, 0x07: 4, 0x08: 4, 0x0a: 8}
```

**没有 `0x06`。**

所以解析器在偏移 0x07 遇到 `06` 时，直接报 `unknown tag`。

---

## 四、怎么发现它是 2 字节的

这一步是**纯算术**：

```
总长 14
已知：10 00 (2) + 08 xxxxxxxx (5) + 终止 (1) = 8
剩余：6 字节
报文里有：06 20 00 和 06 00 00
如果每个 06 + 2 字节 = 3 字节
两个 = 6 字节 ✓ 完全吻合
```

**这就是"算总长"的力量**：不需要知道 `0x06` 是什么，
只需要知道它占多少字节。

---

## 五、一个有意思的细节

`06 20 00` 后面紧跟着 `06 00 00`，然后终止。

如果按大端读，`0x2000 = 8192`，`0x0000 = 0`。
如果按小端读，`0x0020 = 32`，`0x0000 = 0`。

**两个值在两种读法下都是"整数"，报文本身无法区分。**

这就是第 4 卷为什么要写"字节序靠同族推定"。

---

## 六、方法论收获

> **算术能定宽度，不能定语义，也定不了字节序。**

`0x06` 的宽度是 3 字节（标签 + 2 字节载荷），这是纯算术结论，非常可靠。

但：
- 它是 u16 还是两个 u8？—— 需要对照同族（`0x08` 是 u32，所以 `0x06` 是 u16）
- 它是小端还是大端？—— 需要外部锚点（`71/18` 的 build 号）

**不同层次的问题需要不同的证据。
算只能解决第一层。**

---

## 七、这个报文后来成了标准用例

`10/20` 只有 14 字节，结构简单：

```
空串 + u32 + u16 + u16 + 终止
```

它同时用到了：
- `0x10`（字符串，且是空串）
- `0x08`（u32）
- `0x06`（u16）
- 三个连续 0x00 的边界

**是一个很好的"边界情况测试用例"。**

如果解析器能正确处理 `10/20`，说明它对"空字符串 + 多字节整数 + 连续终止符"都处理对了。
