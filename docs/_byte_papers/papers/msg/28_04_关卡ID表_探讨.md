# 报文 `28/4` · 探讨：两条报文互证的力量

> 对应：`msg/28_04_关卡ID表.md`

---

## 一、单独看，两条都是谜

### `28/1`（11~19 字节）

```
6c 08 <N> <数据> <M> 00
```

M 是什么？不知道。

### `28/4`（519 字节）

```
6c 08 fc 01 00 00 <127 个 u32> <263> 00
```

127 个数是什么？不知道。

**两条报文结构相同，内容完全不同，各自都解不出语义。**

---

## 二、放在一起，答案就出来了

关键操作：**把 `28/1` 的每个 M 值，拿去 `28/4` 的表里查**。

结果：

| M | 在 `28/4` 表里 |
|---|---|
| 0, 1, 9, 131, 190, 203, 214 | ✓（按类型 1） |
| 4, 5 | ✗（按类型 2） |

**这不是"大致吻合"，是"完全按类型分裂"。**

---

## 三、这个发现为什么重要

因为它把一个"猜测"变成了"可实现的规则"。

原来的表述：

> "`28/1` 可能带着玩家选了哪一关的线索"

现在的表述：

> "`28/1` 的数据第一个 u32 是类型码。
>  类型 = 1 时，尾字段 M 是关卡 ID，取值必在 `28/4` 的 126 个 ID 内。"

**后者可以直接写成代码。**

---

## 四、这个方法的普遍性

"两条报文互证"在协议逆向里是最强的手法之一。

原理：

- 报文 A 提供一个**未知的标识符**
- 报文 B 提供一个**已知的标识符集合**
- 如果 A 的标识符大量落在 B 的集合里 → 两者描述同一个对象

类似的手法还在用：

1. `21/5` 的 `-695030357` —— 想找它在哪张表里
2. `28/1` 的 M —— 已成功
3. `102/1` 的 u64 值 —— 想找它在 `102/7` 的 0..49 里吗

**第 3 个可以直接试**：`102/1` 的 u64 都很大（20 位），
`102/7` 的是 0..49。**大概率不重合**，但值得确认。

### 实测结果（已跑）

```
102/1 的 u64 集合：{0}          （只有 1 个值）
102/7 的 u64 集合：{0..49}      （50 个值）
交集：{0}
```

**结论：除 0 外无交集。** 这说明 `102/1` 和 `102/7` 虽然同属
service 102，操作的是**不同的 ID 空间** —— 或者更可能，
`102/1` 里的 u64 是"字段编号 0"这一个特定字段，而 `102/7` 是批量读。

**互证在这个方向上失败了**，但失败也是有价值的：
排除了"`102/1` 的操作对象是 `102/7` 的字段编号"这个假说。

---

## 五、一个反直觉的点

**如果 9/9 全中，反而更可疑。**

为什么？

因为 9/9 全中会让我认为"M 是关卡 ID"，
从而**错过"类型码"这个结构**。

正是因为那 2 个不中的，而且它们恰好是"数据首元素 = 2"的样本，
才让我发现：**类型码决定了 M 的含义**。

**部分失败比完全成功更有信息量。**

这条经验在逆向里非常宝贵：
- 100% 吻合 → 可能只是巧合，也可能真的对
- 90% 吻合 + 有规律的 10% 例外 → **几乎必然藏着结构**

## 六、还剩什么

1. 类型 2 的 M（4、5）是什么？
2. `28/4` 里为什么是 126 个而不是 127 个
3. 尾字段 263 是什么

这三个问题都需要**更多类型的样本**才能推进。

## 七、对项目的直接影响

现在可以回答 `lobby_server.py` 注释里的问题了：

> "如果能在这一步就拿到关卡/地图，就能让 `21/5` 一次回对图，
>   不用靠'上一轮记住、这一轮才对上'的自校正。"

**答案**：可以。

规则是：

```python
if kind == 1:
    selected_level = M
```

只要服务端解析 `28/1` 的数组首元素和尾字段，就能在
`21/5` 之前知道玩家选了什么关卡。

**这是一条可以直接落地的结论。**
