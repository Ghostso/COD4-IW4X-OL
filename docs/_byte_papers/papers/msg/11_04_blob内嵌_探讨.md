## 二、五条失败路径的过程

### 路径 1：直接 TLV

```
0c 00 ...
↑
0x0c 不在标签表
```

一秒钟失败。

### 路径 2：前 4 字节当长度

```
0c 00 00 00 = 12
剩余 = 12 ✓
```

**长度对上了！** 这是唯一一条"算术吻合"的路径。

然后对 12 字节的体做 TLV 解析：

```
02 02 00 00 00 08 00 00 00 80 08 00
↑
0x02 不在标签表
```

**又失败。**

### 路径 3：类型-长度-值

按 `02 02 <2字节>` / `08 <4字节>` 读：

```
02 02 00 00       类型2 长度2 值
08 00 00 00 80    类型8 值
08 00             类型8 ...
```

`4 + 5 + 2 = 11 ≠ 12`。差 1 字节。

### 路径 4：u8 序列

`0x02` 作为 u8 标签是错的（u8 是 `0x03`）。失败。

### 路径 5：定长结构体

四个 u32：

```
12, 514, 2048, 557056
```

`2048 = 2^11` 很整齐，但其余三个无规律。

**没能找到合理解释。**

---

## 三、路径 2 的启示

`0x0c 00 00 00` = 12，恰好是剩余字节数。

**这不是巧合。**

如果内层结构是「u32 长度 + 数据」，那它就是一个**完全不同的序列化器** ——
一个不带类型标签的、简单的长度前缀格式。

这可以解释为什么内层的第一个字节是 `0x0c` 而不是标签：
**内层根本不使用标签。**

---

## 四、一个大胆的猜测

如果内层是"不带标签的长度前缀格式"，那它可能是：

```
u32 长度
<长度字节的裸数据>
```

而裸数据 `02 02 00 00 00 08 00 00 00 80 08 00`（12 字节）
可能是**另一个协议层**的字节（例如战斗服的、或某个子系统的）。

**这解释了为什么它不像 TLV：因为它本来就不是 TLV。**

---

## 五、这个发现的重要性

如果这个猜测成立，那意味着：

> **大厅协议不是一个单一序列化器，而是多层序列化器的叠加。**

- 外层：Demonware ByteBuffer（带标签）
- 内层：某个不带标签的定长/长度前缀格式

这对写服务端有直接影响：**不能假设所有字节都是 TLV。**

---

## 六、怎么验证

最直接的办法：**改变一个已知输入，看内层变不变、怎么变。**

例如：

- 改变房间名 → 内层哪几个字节变？
- 改变地图 → 内层哪几个字节变？

如果内层是结构化数据，就会呈现"部分字节变、部分不变"的模式。

**这需要主动实验。**

---

## 七、方法论收获

> **"长度对上了"是最强的信号，即使内容解不开。**

路径 2 里，`0c 00 00 00 = 12 = 剩余字节数`。
这个吻合度（4 字节整数恰好等于剩余长度）随机出现的概率极低。

即使后面内容完全解不开，**"这里有一个长度前缀"这个结论是站得住的**。

这和前面的方法论相反但互补：

- 前面说"不要只看长度"
- 这里说"长度吻合本身也是证据"

区别在于：**长度吻合能证明"存在一个长度字段"，但证明不了"字段的语义"。**
