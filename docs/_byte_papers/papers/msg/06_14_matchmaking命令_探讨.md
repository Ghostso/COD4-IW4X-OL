# 报文 `6/14` · 探讨：整个协议里最重要的一处"明文"

> 对应：`msg/06_14_matchmaking命令.md`

---

## 一、这是本卷集合里最大的发现

前面 14 卷都在研究"标签怎么切、字段多宽"。
`6/14` 不一样：**它的内容是可以直接读的英文。**

```
mmstart sv_resetServer; 2486 0; 3265 18; 2489 0; 2574 0; 2500 0;
        g_gametype coop;  g_difficulty 1; ;
        map coop_train_mp_firingrange;2654 ;
        roomChatChannelID 0;
```

**客户端在告诉服务端：**
- 开什么模式（`coop`）
- 什么难度（`1`）
- 哪张图（`coop_train_mp_firingrange`）

---

## 二、这解决了项目里的一个大问题

`lobby_server.py` 的注释反复提到"猜地图"：

> "猜错地图客户端就不去连战斗服"

以及 `28/1` 那一节的：

> "如果能在这一步就拿到关卡/地图，就能让 `21/5` 一次回对图，
>   不用靠'上一轮记住、这一轮才对上'的自校正。"

**现在有了两个来源**：

1. `28/1` 的尾字段 M（第 28 卷已解：类型 1 时是关卡 ID）
2. **`6/14 mmstart` 里的 `map <地图名>`**

第 2 个是**直接的地图名**，不需要 ID 映射。

---

## 三、为什么之前没看到

三层原因：

### 1. 藏在两层里面

`6/14` payload → blob → blob 内层 → 明文命令

如果不剥开 blob，就看不到。

### 2. blob 内层有长度前缀

```
u32 内容长度 | ASCII 文本
```

如果不知道这个前缀，就会把前 4 字节当成文本的一部分，
读出来是乱码。

### 3. 内容本身不像"命令"

`mmbook`、`mmstart`、`mmban` —— 这些词如果不知道是命令，
可能被当成随机字符串。

**但对本项目来说，`mmstart` 这个词在 `lobby_server.py` 里出现过多次。**

---

## 四、`mmbook` 里又出现了那个哨兵

```
"AQAAAAAAAAA=" → 01 00 00 00 00 00 00 00
"iHdmVUQzIhE=" → 88 77 66 55 44 33 22 11
```

第二个就是 `0x1122334455667788`，与 `11/4` 的房间 ID 完全相同。

**这证实了一件事**：客户端在这个 build 上，"房间/会话 ID"被固定成一个测试哨兵。

**这是不是缺陷？**

可能不是 —— 因为在单机/离线环境下，房间没有真实 ID，
客户端就用了一个占位值。服务端如果回显这个值，就能对上。

**但如果服务端需要真实的房间 ID（例如多房间），就必须自己生成。**

## 五、对我之前结论的修正

### 修正 1：`6/14` 的定位

第 13 卷我写：

> `6`（matchmaking 事件订阅）只回空 ACK... 是当前大厅功能的**最大功能缺口之一**。

**部分错误。**

`6/5` 是事件订阅（确实缺口）。
`6/14` 是 **matchmaking 命令**，内容是完整的启动指令。

**服务端的"空 ACK"对 `6/14` 是致命的** ——
因为这条命令告诉服务端"开什么图"。

如果服务端不解析它，就不知道客户端要开什么。

### 修正 2：`6/14` 不是"未解"

第 14 卷的清单里，`6/14` 在"结构已解、语义未知"里。

**现在它应该升级到"语义已知"** ——
至少 `mmstart` 这一支完全可读。

## 六、还能从 `6/14` 里挖什么

### 1. 那 5 个 dvar 编号

```
2486 0
3265 18
2489 0
2574 0
2500 0
```

如果项目的 dvar 表能查到这些编号，就能知道 `mmstart` 还设置了什么。

### 2. `mmbook` 的第三个参数 `0`

125 条里恒为 0。可能是"是否等待匹配"。

### 3. `mmban`

`mmban` 44 条，内容只有 `mmban\x00\x00\x00`。

可能是"取消预订"或"禁止匹配"。

### 4. `u64 = 76561201696194782`

这是 `0x10FF...` 之类的值吗？需要看具体字节。

（`76561201696194782` = `0x010FFF...`，看起来像一个真实的会话 ID，
与测试哨兵 `0x1122334455667788` 不同。）

## 七、方法论收获

> **不要在找到"结构"后就停下 —— 内容可能比结构更重要。**

`0x13` 的结构我在第 9 卷就解出来了：标签 + 长度 + 数据。

**但真正有价值的信息在数据里。**

本卷集合前面 14 卷都在研究"怎么切"，`6/14` 提醒我：
**切片是为了读内容，不是为了切片本身。**
