## ID 表内容

508 字节 = **127 个 u32**。

实测前 20 个：

```
127, 0, 1, 2, 3, 9, 10, 12, 14, 18, 20, 21, 22, 23, 24, 27, 29, 31, 38, 75, ...
```

值域：**0 ~ 262**，127 个不重复的值。

---

## ★ 首个 u32 = 127 是计数，不是 ID

实测核对：

```
127 个 u32
首个值 = 127
剩余 126 个，范围 0..262，严格递增
```

**关键**：如果把首值去掉，剩下 126 个值**严格递增且无重复**，
最大 262。

而 `127` 这个数**大于表里其余任何值的位置关系** ——
它被放在最前，且恰好等于"数组 u32 总数"。

**但 126 ≠ 127。** 所以不是"count + count 个元素"。

### 三种可能

1. **count = 127 表示"ID 总数"，但实际列了 126 个**（少一个）
2. **首个 127 是第一个 ID，恰好等于元素数**（巧合）
3. **数据是 "count, id[count-1]" 结构**（off-by-one）

**证据偏向 (3)**：因为 126 = 127 - 1，这个 off-by-one 太整齐。

如果客户端写的是：

```c
writeU32(count);           // 127
for (i = 0; i < count - 1; i++) writeU32(ids[i]);   // 126 个
```

就会出现这个形态。

**这是一个可能的客户端 bug，也可能是有意的"去掉自身"。**

## 尾字段

偏移 `0x006 + 508 = 0x202`：

```
07 01 00 00 00    00
```

两种读法（第 10 卷讨论过）：

- **(a) 无标签 u32**：值 = `0x00000107` = 263，然后 `00` 终止
- **(b) i32 字段**：`07` 是标签，值 = 1，然后 `00` 终止

**证据偏向 (a)**：因为 `28/1` 的尾部有 `05 00 00 00` 和 `83 00 00 00`，
其中 `0x05`、`0x83` 都不是已知标签。

所以 `28/4` 的尾部是 **u32 = 263**。

---

## 263 是什么

观察：

- `28/1` 的 M 值范围：0, 1, 4, 5, 9, 131, 190, 203, 214
- `28/4` 的 ID 表最大值：262
- `28/4` 的尾字段：**263 = 262 + 1**

**263 恰好是"表最大值 + 1"。**

这可能意味着：
- 尾字段是"下一个可用 ID"
- 或者"表的容量"

**但没有更多证据。**

## ★ 这张表的意义：它让 `28/1` 可以被解释

单看 `28/4`，它是一串递增的 ID，不知道是什么。

单看 `28/1`，它有一个尾字段 M，不知道是什么。

**把两者放在一起**：
- `28/1` 的 M（类型 1 时）100% 落在这张表里
- 所以 M 是"这张表里的某个 ID"
- 表是"可选关卡/任务"的集合

**这是本卷集合里"两条报文互证"的最好例子。**

## 数据性质

### 递增但跳号

`0,1,2,3,9,10,12,14,18,...`

不是连续整数，中间跳过了 4..8、11、13、15..17 等。

**跳号意味着**：这是一张"已解锁/已存在"的**子集**，
不是"完整 ID 空间"。

### 首个 u32 = 127（见上文"计数"一节）

结论：`127 = u32 总数`，实际 ID 有 126 个（off-by-one，或首值即计数）。

## 完整结构

```
6c 08 <N=508> <u32 count=127> <u32 id[126]> <u32 263> 00
```

尾字段 `263` 与 `count 127` 无关，是独立字段。
