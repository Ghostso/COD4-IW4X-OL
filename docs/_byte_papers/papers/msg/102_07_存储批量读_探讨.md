# 报文 `102/7` · 探讨：一条报文如何成为解析器的基准用例

> 对应：`msg/102_07_存储批量读.md`

---

## 一、为什么选它做基准

`102/7` 有四个特点，使它成为"验证解析器"的最佳样本：

1. **长度固定**：556 字节，371 条全部相同
2. **结构规整**：1 + 50×11 + 1
3. **每个字节都有明确归属**
4. **重复性强**：50 个完全同构的块

**如果解析器对它的输出有任何偏差，立刻能看出来。**

## 三、这个表格说明了什么

### 说明 1：`u32 = 50` 是计数

50 个块，不多不少。

**这条证据强度极高**：如果 50 是"别的什么"，那它应该偶尔与块数不符。
371 条样本全部吻合。

### 说明 2：`u8 = 1` 是恒定值

50 个块里，每一块的 u8 都是 1。

**这不是"序号"** —— 序号在 u64 里（0..49）。

所以 u8 是**每块都相同的"类型"或"操作码"**。

### 说明 3：`u64` 是序号

0, 1, 2, ..., 49 严格递增。

**这是整个语料里最清晰的"序号序列"。**

---

## 四、这个基准用例能抓什么错

### 错误 1：把 `03` 当成分组容器

第 3 卷讨论过这个错误。
如果解析器把 `03 01` 当成"组，1 个元素"，那 `0a <u64>` 会被当作第一个元素，
然后下一个 `03` 就成了组外的内容 —— 导致解析在 50 个块之间错位。

**用 `102/7` 可以立刻抓到：输出块数 ≠ 50。**

### 错误 2：把 `0a` 当成两个 u32

如果解析器把 `0a` 读成 8 字节但拆成两个 u32，那"序号"会变成
`(0,0), (1,0), (2,0)...` —— **第二个 u32 恒为 0**。

这会让"序号"语义丢失。

**用 `102/7` 可以抓到：第 50 个块的序号应该是 49，而不是 (49, 0)。**

### 错误 3：把终止符当成数据

如果解析器在末尾多吃/少吃一个字节，块数或尾部会错。

## 五、方法论收获

> **选一个"最规整"的样本做回归测试。**

在一个有 55 个 task 的协议里，不可能每个 task 都手工核对。
但**只要一个 task 被彻底核对过**，就能用它来发现解析器的系统性错误。

`102/7` 就是这样的样本：

- 它用了 u32、u8、u64 三种标签
- 它有明确的计数与重复
- 它的长度足够大（556 字节），能暴露累积性错误

**这相当于给解析器装了一个"标准砝码"。**
