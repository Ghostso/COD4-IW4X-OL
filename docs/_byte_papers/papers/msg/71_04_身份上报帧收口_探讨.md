# 71/4 收口 · 探讨：一个「猜错了」的字段，和一个「猜对了也白猜」的字段

> 配套：[117 · `71/4` 身份上报帧收口](71_04_身份上报帧收口.md)
> 性质：方法论复盘。**重点是两个字段的对比——一个能定、一个必须诚实放弃。**

## 一、为什么我盯着 `71/4` 不放

116 卷把 `102` 定名后，请求侧的「服务名」黑箱清零了。剩下的纯本地可攻的黑箱里，`71/4` 的 `31902622` 是最显眼的一个——它是 110 卷列的「高频未定值」，160 次出现、只在一个 task。

但真正让我动手的，是重读 `71/4` 旧卷时看到一句**含糊的猜测**：

> blob1「最可能的身份：**会话 ID / 会话令牌**」

「最可能」四个字是危险信号。旧卷没有证据，是**形状联想**（16 个随机-looking 字符 → 会话 ID）。这和 115 卷把 `102` 猜成 `Leaderboard` 是同一种错误。**于是我把它当假设去证伪——结果一枪打穿。**

## 二、`nQlo` 的证伪：从「猜」到「反汇编」

### 2.1 第一步：它到底是随机还是固定？

我先问了一个更弱但更根本的问题：**它跨 run 变不变？** `confirm_714.py` 一跑：160 条、83 个 run，`nQloP0oCVWR6RDJS` **一个字都没变**。

**会话 ID 不可能跨 83 次登录完全一样。** 仅此一条，旧卷的「会话 ID」猜测就已经死了。但「跨 run 固定」还可能是「这台机器第一次登录生成后缓存」——所以我继续挖。

### 2.2 第二步：它在二进制里吗？

`find_31902622_img.py` 顺手把 `nQlo` 串也搜了——**E 镜像 `0x9B6B68`、磁盘 EXE `0x6A2B68` 各一处**。

**固定字符串 + 在 .rdata 里 = 编译期常量。** 到这里已经 90% 确定。但我不满足于「在字符串池里」——字符串池里也可能是「默认值模板，运行时被覆盖」。

### 2.3 第三步：谁在用它？（反汇编收尾）

`nqlo_refs.py` 找指向 `0xDB6B68` 的指针，唯一一个落在**代码段** `0x4A6389`：

```asm
mov edx, [0xDB6B68]   ; 直接读 .rdata
mov eax, [0xDB6B6C]
mov ecx, [0xDB6B70]
mov edx, [0xDB6B74]
```

**没有中间变量、没有条件覆盖，直接 `mov` 读常量写进报文。** 到这一步，**「会话 ID」彻底判死**——它就是一个 `.rdata` 常量，每次都一样。

**方法论：证伪一个「最可能」的猜测，最有力的不是「找到更好的解释」，而是「找到它的生成点，发现根本没有生成」。「没有生成」比「生成方式不同」更致命。**

## 三、`++++` 的意外收获

反汇编里 `mov eax, 0x2B2B2B2B` 连写 4 次——`+` 不是「客户端没值填占位」，是**编译器把 16 字节 `+` 当常量压进栈**。

这跟 111 卷的「空串 `10 00` 占位」是**同一条约定**：协议要求字段必在，客户端宁可填常量占满长度也不省略。**两个卷从两个方向撞到同一条规则**——这种「独立路径汇合」是可信度最高的信号。

## 四、`31902622`：一个必须诚实放弃的字段

对比之下，`31902622` 我穷举了几乎所有本地能做的手段：

- 跨 run 恒定 ✅（机器级，非会话级）
- 全镜像立即数：LE/BE/32/64 **全 0 命中**
- 12 种哈希 × 多拼接 × 两端序：**全不中**
- MAC 字节算术、时间戳、与 build/titleId/zoneId 的整数关系：**全不中**

**结论：它是运行时值，本地静态不可定名。**

这里最容易犯的错，是**继续硬凑**——比如「31902622 是不是 base64 解码后 XOR 某个数」之类。我试了 base64（`nsvmAQ==` / `AebLng==`），无意义，就停了。

**方法论：穷举要「有边界地穷举」。** 112 卷「先算术枚举再起名」是对的——但它的前提是「枚举能穷尽」。当枚举穷尽仍无解，**正确的动作是标「运行时值 + 需要什么证据才能定」，而不是无限加码凑一个名字。** `31902622` 就是后一种情况：要定它，需要「换一台机器抓 71/4 看这个值变不变」——那是**授权动作**（跑客户端），本地做不到。

## 五、两个字段的对照表（本卷的核心）

| | `nQlo` | `31902622` |
|---|---|---|
| 跨 run | 恒定 | 恒定 |
| 在二进制 | ✅ `.rdata` 常量 | ❌ 无立即数 |
| 生成方式 | 编译期硬编码 | 运行时计算/下发 |
| 能否定名 | ✅ 已定（硬编码常量） | ❌ 本地不可定 |
| 需要什么才能定 | 已定 | 换机抓包 / 读服务端逻辑 |

**同一帧里两个「恒定值」，一个能定、一个不能——区别只在「它在不在二进制里」。** 这就是「本地逆向能做什么、不能做什么」的分界线。

## 六、对旧卷的教训

`71/4` 旧卷写于早期，那时还没建立「先验跨 run 恒定、再查二进制」的习惯，所以把常量猜成了会话 ID。

**这不是旧卷的错——是那时的工具链还没到位。** 现在有了 `find_*_img.py`（二进制立即数搜索）+ `confirm_*.py`（跨 run 一致性），任何「疑似 ID」的字段都应该先过这两关：

1. **跨 run 恒定？** 恒定 ⇒ 机器级/常量，不可能是会话级。
2. **在二进制？** 在 ⇒ 编译期常量，直接定；不在 ⇒ 运行时值，诚实标注。

**这条两问流程，应该成为以后每个「未定值」的标准第一步。**
