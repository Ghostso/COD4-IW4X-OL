## 1. 外层结构

```
6/14 payload := u64 <会话> | blob | 00
```

- 最常见：`u64 = 1`（125 + 44 + 26 + ... 条）
- 少数：`u64 = 76561201696194782`

blob 内层规则：**首 4 字节 = 内容长度**，内容为 ASCII 文本。

## 2. ★ 内层是明文命令

### `mmbook`（125 + 2 条）

```
mmbook 796 AQAAAAAAAAA= 0
```

| 字段 | 值 | 解释 |
|---|---|---|
| 命令 | `mmbook` | 预订 |
| 参数 1 | `796` | **playlist 版本号**（项目常量 `PLAYLIST_VERSION = 796`） |
| 参数 2 | `AQAAAAAAAAA=` | **Base64** |
| 参数 3 | `0` | 某个标志 |

**Base64 解码实测**：

```
"AQAAAAAAAAA=" → 01 00 00 00 00 00 00 00   (u64 = 1)
"iHdmVUQzIhE=" → 88 77 66 55 44 33 22 11   (u64 = 0x1122334455667788)
```

**★ 第二个解码值是 `0x1122334455667788`** —— 与 `11/4` 的房间会话 ID 完全相同。

这说明：`mmbook` 的第二个参数就是**房间/会话 ID**，
而客户端在这条路径上用了同一个测试哨兵。

## 3. 这意味着什么

### 结论 1：客户端自己知道要开什么图

`mmstart` 命令里明确写着 `map coop_train_mp_firingrange`。

**这推翻了"服务端需要猜地图"的假设** ——
客户端已经在 `6/14` 里告诉服务端了。

### 结论 2：匹配命令是纯文本，不需要解析二进制

`mmbook` / `mmstart` / `mmban` 都是空格分隔的文本。

**服务端只需要按空格切开就能读。**

### 结论 3：`mmstart` 里的 dvar 编号是数字

`2486 0; 3265 18; 2489 0; 2574 0; 2500 0`

这些数字很像 **dvar 的哈希/编号**。
本项目已知 `dvar 3291`、`3292`、`1760` 是脚本 dvar。
`2486/3265/2489/2574/2500` 是同一类东西。

---

## 4. 与 `lobby_server.py` 的现有判断对照

服务端代码里有一条注释：

> 靶场：`6/14 mmbook -> push 'mmbook accepted'`
> `6/14 mmstart -> 空应答`

**服务端目前只 ACK，没有解析 mmstart 的内容。**

但 `mmstart` 里已经包含了：
- 游戏类型（`coop`）
- 地图（`coop_train_mp_firingrange`）
- 难度（`1`）

**这些正是服务端"猜"的东西。**

## 5. 为什么这条报文之前没被发现

因为：
1. 它藏在 `0x13` blob 里
2. blob 内层的第一层是长度前缀
3. 内容看起来像"随机字节"，直到被当成 ASCII 读

**正确读法**：

```
blob 内容 = u32 长度 | ASCII 命令文本
```
