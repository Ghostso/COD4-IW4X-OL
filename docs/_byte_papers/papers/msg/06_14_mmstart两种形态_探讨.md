# 报文 `6/14` `mmstart` 两种形态 · 探讨：会话 ID 里的 DEADC0DE

> 对应：`msg/06_14_mmstart两种形态.md`

---

## 一、第一次看到这串数字

```
u64 = 76561201696194782
```

十进制看不出来。转十六进制：

```
0x1100001DEADC0DE
```

一眼就看出两段：

```
0x1100001   DEADC0DE
```

- 后半段 `DEADC0DE` 是 **"dead code"** —— 程序员常用的填充哨兵
- 前半段 `0x1100001`

---

## 二、`0x1100001` 与项目常量的关系

项目里有一个常量：

```python
ROOM_HOST_UID = 1000001
```

而 `0x1100001` = 17825793。

**两者不相等**，但字形极度相似：

```
1000001     （十进制 1000001）
0x1100001   （十六进制 = 17825793）
```

如果把 `1000001` 加上一个 `1` 变成 `1100001`，再当十六进制读，就是 `0x1100001`。

**这不是巧合，但也不是"完全一致"。**

### 三种可能

1. **客户端写的是 `0x1100001`（十进制 17825793）**，
   而项目常量 `1000001` 是另一回事（从 ol-mod 抄来的，可能错）。

2. **客户端写的是十进制 `1100001`**，恰好等于 `0x10CAE1`……
   不，`1100001` 十进制 = `0x10CAE1`。而报文里是 `0x1100001`。
   **不等。**

3. **客户端把 `1000001` 写成 `0x1100001`** —— 这是个打错的常量？

**最可能的是 1**：`0x1100001` 是客户端真实的 host UID，
而项目里的 `1000001` 来自 ol-mod，**与本 build 不同**。

**这正好印证 AGENTS.md 的警告：**
> "Never copy its constants... ol-mod targets a different build."

---

## 三、`DEADC0DE` 的意义

这是**调试哨兵**，说明这个会话 ID 不是真实的。

客户端在"没有真实会话"时，用
`<某种前缀> + DEADC0DE` 填充。

**这与 `11/4` 的 `0x1122334455667788` 是同一类做法** ——
用可识别的、非随机的值标记"这是占位"。

---

## 四、两种会话 ID 的三种形态

语料里见过三种：

| 值 | 出处 | 性质 |
|---|---|---|
| `1` | `6/14` 多数样本 | 简单占位 |
| `0x1122334455667788` | `11/4`、`6/14 mmbook` | 递增序列哨兵 |
| `0x1100001DEADC0DE` | `6/14` 少数样本 | **host UID + DEADC0DE** |

**第三种是最"有信息量"的** —— 它至少透露了 host UID 的值。

---

## 五、`roomChatChannelID` 的一次巧合

形态 B 的 `roomChatChannelID = 1800154382 = 0x6B4C2D0E`。

而 `11/4` 的另一个会话 ID 是 `0x0E2D4C6B00000000`
（从 `msg/11_04` 的形态表里：`u64` = `0e2d4c6b00000000`）。

**`0x6B4C2D0E` 正好是 `0x0E2D4C6B` 的字节反转。**

这说明：
- `11/4` 存的是 **大端序** 或
- 某个字段被翻转了

**这是一个字节序问题，需要单独核对。**

---

## 六、方法论收获

> **十六进制是逆向的母语。**

`76561201696194782` 这个十进制数，没有任何意义。

`0x1100001DEADC0DE` 一眼就能看出两段结构，
还能认出 `DEADC0DE` 这个程序员梗。

**遇到大整数，先转十六进制。**
