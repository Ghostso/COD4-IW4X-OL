# 报文 `6/5` · 探讨：一个被"订阅了但没推"的空白结构

> 对应：`msg/06_05_事件订阅.md`

---

## 一、这个 13 字节为什么值得单独一篇

因为它虽然小、虽然 100% 解出，**却是整个大厅当前最大的功能断点**。

结构解出 ≠ 功能可用。
`6/5` 是一个典型案例：客户端在正确的位置、用正确的格式、
发出了正确的订阅请求，服务端也正确 ACK 了。

**但没有事件被推回来。**

---

## 二、字节层面已经没有疑点

13 个字节：

```
u32 0 · u32 20 · bool true · term
```

160 条样本，一个字节都不变。

**这不是"大致解出"，是"完全确定"。**

所以问题不在格式，在**服务端的实现缺失**。

---

## 三、缺失的是什么结构

服务端需要能推送事件。推送的格式：

**完全未知。**

原因很直接：语料来自"服务端 → 客户端"的反方向时，
只有我们自己的服务端发的那些字节（而且全是空 ACK 或简单回显）。

**从来没有真正服务端推过事件**，所以没有样本。

这意味着：

- 无法用语料统计法解出事件推送格式
- 必须从**别的途径**获得

可能的途径：

1. **客户端侧**：找到接收事件的代码，看它怎么解析
2. **参照实现**：IW4X / CoD4X 里有没有等价机制
3. **主动实验**：构造一个猜测格式推给客户端，看它是否响应

按 AGENTS.md 的权威序，途径 1 最高（本地逆向），
但客户端被 `.tvm0` 加壳，静态分析困难。

---

## 四、一个可以做的推理

虽然推送格式未知，但可以推出**它必须遵守的约束**：

1. **必须走同一个序列化框架** —— 因为客户端用同一个反序列化器。
2. **必须以事件类型开头** —— 客户端需要知道收到的是哪种事件。
3. **必须带 roomId 或类似定位符** —— 否则不知道该更新哪个房间。

这三条约束把可行空间缩得很小：

```
push := <事件类型> <定位符> <事件体> 
```

其中"事件类型"很可能是 `0x03`（u8）或 `0x08`（u32），
因为订阅的 20 个事件需要编号。

**这是一个有价值的推断：推送的第一个字段应该是事件编号。**

---

## 五、这暴露的方法论问题

**语料统计法的盲区：只能解"发生过的事"。**

如果某个报文类型从未被发出/推送过，
语料里就是空的，无论怎么统计都得不到。

这提醒一件事：

> 本卷集合的"100% 闭合"限定在**已发生的 6848 条**上。
> 协议里可能存在**从未触发过的结构**，它们不在台账里。

这一点在第 14 卷的"台账边界"里提到了，
但 `6/5` 是它最具体的实例。
