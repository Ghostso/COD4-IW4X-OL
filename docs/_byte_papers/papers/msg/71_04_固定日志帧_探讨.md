# 报文 `71/4` · 探讨：`++++++++` 与 16 位会话标识

> 对应：`msg/71_04_固定日志帧.md`

---

## 一、16 个 `0x2b`

第一次读 `71/4` 时，第二个 blob 是：

```
2b 2b 2b 2b 2b 2b 2b 2b 2b 2b 2b 2b 2b 2b 2b 2b
```

`0x2b` = `+`。

16 个加号。

**这不是随机数据，也不是加密 —— 是填充。**

---

## 二、为什么用 `+` 而不是 0

三种可能：

1. **客户端填充逻辑写错了** —— 用了可打印字符而不是 0。
2. **协议要求** —— 长度固定为 16，无内容时填 `+`。
3. **它是某种"加密后的空值"** —— 换个方式表示空。

第 3 条可以排除：16 个相同的字节不可能是密文。

第 1 条最可能：某个代码路径在"没有会话 token"时，
用了 `memset(buf, '+', 16)`。

---

## 三、第一个 blob `nQloP0oCVWR6RDJS`

16 个字符，大小写混合 + 数字。

**字符集**：`A-Z a-z 0-9` —— 典型的"字母数字随机串"。

这种格式通常来自：
- Base62 编码
- 随机 token 生成器
- 会话 ID

**关键观察**：160 条样本、83 个 run，全部相同。

如果是每会话随机，应该每次不同。
如果是每机器固定，那它就是**本机的客户端 ID**。

**我倾向"客户端 ID"**，但无法证实。

---

## 四、这条报文在协议里的位置

`71/4` 是 `71` 系列的第一个 task。

结合 `71/7`（ClientReconnect / ClientLoadTime 日志）、
`71/18`（build 号上报），整个 `71` 系列是**客户端 → 服务端的混合上报**：

- `71/3` 大日志串
- `71/4` 身份 + 令牌
- `71/7` 事件日志
- `71/18` build 号

**这解释了为什么 `71` 有 11 个 task** —— 它是一组"客户端信息上报"的集合。

---

## 五、为什么服务端"空 ACK"也没问题

客户端发这些，服务端只回 ACK。

这说明：**客户端不依赖服务端对这些上报的回应**。

但有一个例外：如果服务端需要"知道这是哪个客户端"，
就必须解析 `71/4` 的前两个 blob。

**目前的实现没有解析，所以服务端不知道客户端 ID。**

---

## 六、方法论收获

> **填充值是可识别的。**

16 个相同的可打印字符（`+`），一眼就能看出是填充。
这在逆向里是好事：填充不会伪装成数据。

盘点语料里的"填充模式"：
- `+ × 16`（`71/4`）
- `2b` 开头
- 全 0 块（`0x13` 长度 0）

**识别填充模式，能快速剥离"无信息"的部分，聚焦真实数据。**
