# 第 2 卷 · 探讨：一个"显然"的结论也可以是错的

> 对应论文：`02_布尔标签0x01.md`

---

## 一、这个结论有多可信

`0x01` 是 bool，看起来不言自明。但"看起来"在逆向里不算证据。

真正让这个结论站得住的，是三个独立事实同时成立：

1. **宽度恰为 1**（用全量语料闭环验证，不是挑样本）
2. **值域恰为 {0,1}**（329 个实例无一例外）
3. **同族里另有 1 字节标签 `0x03`，值域是 {0,1,2,3}**

第 3 条最关键。如果只有前两条，我无法排除"`0x01` 是个
取值恰好只有两种的枚举" —— 比如协议版本号、性别、状态位。

有了第 3 条，可以论证：**同一个 1 字节宽的位置，客户端用了两种标签**。
如果标签本身不携带类型信息，就没必要用两个不同的字节。
所以标签必须有类型含义。而 `0x01` 的值域又恰好是布尔值域。

三条合起来，`0x01` = bool 的置信度才够高。

## 二、被排除的其它解释

### 解释 B1：`0x01` 是"字段存在标志"

有些协议用"是否存在"前缀，`00` = 无，`01` = 有。

**排除理由**：如果 `0x01` 是存在标志，那它后面必定还跟着值。
但在 `6/5` 里我们看到：

```
... 01 01 00
      ↑  ↑
   标签  值?   终止
```

`01 01` 后直接终止，没有额外数据。
所以 `0x01` 后面那 1 个字节**就是它带的值**，不是"存在标志 + 值"。

（如果它是存在标志，格式应是 `01 <value>`，那 `01 01 00`
读作"存在，值为空" —— 但这与其它 hundreds 条一致行为冲突。）

### 解释 B2：`0x01` 是"小整数"，只是恰好没出现过 2

**排除理由**：只有 329 个实例，确实不算多。
但 `0x03` 在 18970 个实例里出现过 0/1/2/3 四个值。
如果客户端偶尔会把 2 塞进 `0x01`，在 329 个样本里零命中是可接受的巧合，
可是服务器端构造代码在 `codol_crypto.py` 里也只对 `T_BOOL` 写 0/1 ——
**两侧都没有出现过 2**。

置信度：高，但不是绝对。

### 解释 B3：`0x01` 属于外层帧头，不是 payload 的一部分

**排除理由**：语料是"解密后的 payload"，帧头
（`u32 declared | 0x86 | service | 0x03 | task`）已经被剥掉。
`0x01` 出现在 payload 内部任意位置（首次出现于偏移 0 到 200+ 之间都有），
不可能是帧头残留。

## 三、那 3 个 `00` 是怎么回事

这是我最不放心的地方。

3 个样本：

- `93/131` 两个（`val=00`）
- `80/154` 一个（`val=00`）

这三个 task 在语料里分别只有 2 条和 1 条样本。
也就是说：**这两个 task 全部都写了 false**。

两种可能：

**可能性 1**：这些 task 的业务语义就是"发一个 false 过去"，
例如"取消某个状态"。

**可能性 2**：`00` 不是 false，而是某种"缺省"表示 ——
客户端在某些路径上把布尔写成 0 表示"没设置"。

目前无法区分。

**但这个不确定性不影响主结论**：无论 `00` 是 false 还是"缺省"，
`0x01` 标签后面读 1 个字节、值域极小，这两点是稳固的。

## 四、方法论收获

> **"显然"的结论必须能被反例攻击。**
> 找一个同宽度、不同标签的兄弟，用它们的差异来反证。

这一卷的 `0x01` vs `0x03` 就是范例。
这种"兄弟标签对照"后面还会反复用：

- `0x07`(i32) vs `0x08`(u32) —— 第 5、6 卷
- `0x6b` vs `0x6c` —— 第 10、11 卷

对照的意义在于：**差异本身就是证据**。
两个标签如果语义相同，客户端就没理由区分它们。
