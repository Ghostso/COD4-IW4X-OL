# 第 7 卷 · 64 位整型标签 `0x0a`（与 `0x09` 的缺席）

> 覆盖：`0x0a` 标签及其 8 字节载荷；`0x09`（i64）的存在性
> 证据：`_byte_papers/evidence/ev_value_stats.txt`（tag 0a 段）
> 复跑：`tools/lobby_value_stats.py`

---

## 1. 结论

```
0x0a <8 字节小端 无符号 uint64>
```

语料中出现 **20525 次**，54 个不同值。

### 关键反证：它不是浮点

先把最容易被想到的解释排除掉。

**如果是 f64**：
- `0x1122334455667788` 读作 f64 = 1.348e+228（无意义）
- `16701785630074219790` 读作 f64 = 8.89e-315（次正规数，无意义）
- 1758 个样本里只有 262 个产生"合理"的 f64 值

**如果是 u64**：
- `0x1122334455667788` = 0x1122334455667788（教科书哨兵常量）
- `16701785630074219790` = 服务端代码里的 `owner` 常量
- 全部 20525 个值都有明确的整数语义

**结论：u64，无争议。**

## 2. 值分布

| 值 | 次数 |
|---|---|
| 0 | 850 |
| **16701785630074219790** | **820** |
| 1 | 691 |
| 2 … 49（每个） | 371 |
| 其余 | 少量 |

### ★ `16701785630074219790`

这个值在服务端代码 `lobby_server.py` 里被定义为 `owner` 常量，
在 `_pack_public_result(raw, tail=(), owner=16701785630074219790, ...)` 的签名里。

它是**玩家唯一 ID**（CODOID）。

**实证价值**：和 `1649370`（第 6 卷）一样，这是一个
"外部有定义 → 报文里出现"的锚点，直接把 `0x0a` 的类型锚定为 u64。

### ★ `0x1122334455667788`

`11/4` 的报文里：

```
0a 88 77 66 55 44 33 22 11
```

小端读作 `0x1122334455667788`。

**这是一个人为构造的测试常量**（`11 22 33 44 55 66 77 88` 递增序列）。
它出现在真正的协议流量里，说明客户端/服务端在某个槽位用了
"可识别的占位值"，而不是加密随机数。

### 0..49 的递增序列

`102/7` 里的 50 个 `(u8=1, u64=N)`，N 从 0 递增到 49。

**这批值直接证明 `0x0a` 能承载小整数** ——
它不仅有 20 位的 CODOID，也有 0..49 这样的序号。

## 3. 报文逐字节

### 3.1 `11/4`（37 字节，261 样本）

```
偏移  字节                          解释
00    0a 88 77 66 55 44 33 22 11    u64 = 0x1122334455667788
09    13 08 10 00 00 00 0c 00 00 00 blob，16 字节
12    <16 字节>                     （blob 内容）
22    02                          u8 = 2
23    02 00 00 00                 u32 = 2
27    08 00 00 00 80             u32 = 0x80000000
2c    08 00                 
...
```

**逐字节算术校验**（37 字节）：

```
9  (u64)
+ 6 + 16 (blob)
+ 1 + 1 (两个 u8)
+ 4     (u32 = 2)
+ 5     (u32 = 0x80000000)
+ ... = 37
```

`0x0a` 在报文最开头，承载会话标识 `0x1122334455667788` ——
**这是一个明显的测试哨兵**：`11 22 33 44 55 66 77 88` 递增序列。

它出现在每一份 `11/4` 里（261/261），说明是固定值而非随机会话号。

### 3.2 `102/7`（556 字节，371 样本）

```
00    08 32 00 00 00      u32 = 50
05    03 01               u8 = 1
07    0a 00 00 ... 00     u64 = 0
10    03 01               u8 = 1
12    0a 01 00 ... 00     u64 = 1
...
```

50 对 `(u8=1, u64=N)`，N = 0..49。

## 4. `0x09`（i64）缺失

`codol_crypto.py` 的对照表里定义了 `T_I64 = 0x09`。
但在 6848 条样本、1343713 个标签实例中，**`0x09` 出现 0 次**。

### 可能的解释

1. **客户端在这一方向从不发 i64**
   —— 服务端有 `i64` 方法，但实际路径没用到。
2. **i64 只在服务端 → 客户端方向发**
   —— 本语料只含客户端发出的报文，所以看不到。
3. **客户端根本没有 i64 类型**
   —— 服务端表是照着外部项目抄的，抄多了。

**无法区分。** 需要抓一次客户端真正需要 64 位有符号值的场景
（例如负的经验值、负的时间差）才能验证。

---

## 5. `0x0a` vs `0x09` vs `0x08` 的关系

| 标签 | 宽度 | 符号 | 实测 |
|---|---|---|---|
| `0x08` | 4 | 无 | 6369 例 |
| `0x09` | 8 | 有 | **0 例** |
| `0x0a` | 8 | 无 | 20525 例 |

`0x0a` 的数量远多于 `0x08`，这本身值得注意 ——
说明 64 位无符号是大厅协议的主力数值类型，
很可能因为 CODOID、会话 ID、时间戳都用它。

---

## 6. 字节覆盖

| 字节 | 语义 | 证据强度 |
|---|---|---|
| `0x0a` | u64 标签 | 强（20525 例） |
| 载荷 8 字节小端 | 无符号 | 强（哨兵常量 + CODOID 双重锚定） |
| `0x09` | i64 | **零样本**（结构存在，用法未知） |

**盲区**：

1. `0x09` 的实际用法完全未知。
2. 54 个 distinct 值里，低频值（出现 1~2 次）的语义未解。
3. `16701785630074219790` 与具体玩家绑定 ——
   换账号后是否变化，无法从本语料判断（语料始终是同一账号）。
