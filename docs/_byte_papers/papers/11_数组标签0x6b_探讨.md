# 第 11 卷 · 探讨：两个标签、同一结构，为什么

> 对应论文：`11_数组标签0x6b.md`

---

## 一、最反常的观察

`0x6b` 和 `0x6c` 的**编码结构完全一样**：

```
标签 08 <u32 N> <N 字节> <u32>
```

只有第一个字节不同。

在一个类型标签系统里，**如果两个标签的编码相同，它们通常只是
"同一个类型的两个名字"** —— 就像 C 的 `int` 和 `signed int`。

但这里的用法完全不同：

| | `0x6b` | `0x6c` |
|---|---|---|
| 出现在 | 21 族 | 28 族 |
| 数据 | 恒定 `[1]` | 递增 ID 表 |
| 尾部 | 恒 0 | 变化 |

**如果是同一个类型，为什么用法差这么多？**
**如果不同，为什么要用两套标签？**

---

## 二、四种解释

### 解释 1：元素类型不同

`0x6b` = `array<uint32>`，`0x6c` = `array<某种结构体>`。

**反驳**：如果是 `array<结构体>`，那 N 应该总是结构体大小的倍数，
但 28/4 的 N=508，如果元素是 4 字节就是 127 个；
28/1 的 N=4 或 8 也都能被 4 整除。**看不出结构体**。

不过，也可能结构体本身就是 4 字节。

### 解释 2：一个是"读"一个是"写"

`0x6b` 用在**请求**里（21/5 是客户端发起的查询），
`0x6c` 用在**另一个方向**。

**反驳**：语料全部是客户端 → 服务端的请求，两者都在请求里。

### 解释 3：协议演进留下的两个版本

早期用 `0x6b`，后来改用 `0x6c`（或反之），
旧标签保留兼容。

**这是最符合工程现实的一种。**

如果这样，`0x6b` 是"老式数组"，`0x6c` 是"新式数组"。
新代码用 `0x6c`，老代码路径还在用 `0x6b`。

### 解释 4：尾部 u32 的语义不同

`0x6b` 的尾部恒为 0，`0x6c` 的尾部变化。

如果尾部是"关联 ID"，那 `0x6b` 的 0 表示"无关联"，
`0x6c` 的非零表示"关联到某个对象"。

**这个解释能同时说明两种标签的用法差异。**

---

## 三、倾向哪个

我倾向"解释 3 + 解释 4 的组合"：

- `0x6b` 和 `0x6c` 是**同一个类型的两个代号**（不同版本）
- 尾部 u32 是**关联 ID**，0 表示无关联

但没有直接证据。**所以论文里只写"结构已知，语义未定"。**

---

## 四、这对写服务端有什么影响

**目前没有影响** —— 因为服务端只需要回 ACK，
不需要构造这两种数组。

但一旦要实现"返回会话列表"或"返回关卡列表"，就必须知道：

- 用哪个标签？
- 尾部 u32 填什么？

**现在不知道。** 这是一个明确的功能阻塞点。

---

## 五、方法论收获

> **两个结构相同的标签，差异本身就是线索。**

如果只看一个标签，会以为"数组就是这样"。
把 `0x6b` 和 `0x6c` 放在一起，才看出：

- 它们的用法完全不同
- 这暗示了协议内部存在"两套体系"

**对照是发现结构的手段，不只是验证结构的手段。**

---

## 六、怎么才能解开

需要三类证据，按可获得性排序：

1. **同会话的连续样本**：如果某个会话里既有 `0x6b` 又有 `0x6c`，
   可以对比它们的上下文。
2. **主动改输入**：改变游戏类型/关卡，看哪个标签变。
3. **客户端代码**：找到写这两个标签的调用点。

第 1 条最容易 —— 检查现有的 6848 条里，
**有没有同一条报文里同时出现 `0x6b` 和 `0x6c`**。

（快速检查：没有。`0x6b` 只在 21/5，`0x6c` 只在 28/1、28/4，
两条路径从未在同一条报文里共存。）

第 2、3 条需要实验或客户端逆向。
