# 第 8 卷 · 字符串标签 `0x10`

> 覆盖：`0x10` 标签及其 NUL 结尾载荷
> 证据：`_byte_papers/evidence/ev_value_stats.txt`（tag 0x10 段）
> 复跑：`tools/lobby_value_stats.py`

## 1. 结论

```
0x10 <字节序列> 0x00
```

无长度前缀，**以 NUL 结束**。长度可以为 0（空串，写作 `10 00`）。

语料中 5006 次出现：

| 类别 | 样本数 |
|---|---|
| 空串 | 2789（55.7%） |
| 非空 | 2217 |
| 其中 distinct 值 | 489 |

## 2. 宽度判定

### 为什么不是"u32 长度 + 数据"

如果 `0x10` 是 `0x13` 那种"标签 + 长度 + 数据"，格式应为
`10 <u32 len> <len 字节>`。

**反例**：`71/4` 的

```
10 44 34 2d 39 33 2d 39 30 2d 31 38 2d 35 35 2d 31 30 00
   ↑ "D4-93-90-18-55-10"
```

`44` = 'D'，不是长度 0x44 = 68。
按"长度前缀"读会要求 68 字节，但只到终止符 00。

**所以 `0x10` 是无长度前缀、NUL 结束的。**

### 为什么不是定长

`D4-93-90-18-55-10` 长 17 字节；
`the.json` 长 8 字节；空串长 0。
长度完全可变，NUL 是唯一的分界。

## 4. ★ 语义边界：`0x10` 不保证可打印

这是本卷必须写清楚的一条：

2217 个非空串中，**只有 1889 个（85.2%）是可以打印的 ASCII**。
剩下 328 个（约 15%）含有不可打印字节。

但看具体样本：

```
b'CreateRoom|${TIMESTAMP_OFFSET(-5)}|16701...'
```

头部是标准日志格式，**后面接了二进制**。

这说明：

> `0x10` 只保证"到下一个 NUL 为止"，
> **不保证内容是文本**。客户端把日志串和二进制数据直接拼接，
> 中间没有转义或长度保护。

### 这条对写服务端有直接影响

如果要构造带 `0x10` 的响应，**必须确保载荷里没有 NUL**，
否则客户端会在 NUL 处截断。

反过来：解析客户端的 `0x10` 时，若内容含不可打印字节也不要假定解析错误 ——
那是客户端真实写出来的。

## 5. 空串占比

2789 / 5006 = **55.7%** 是空串。

这解释了第 1 卷的观测：连续多个 `0x00` 非常常见。
`10 00` + 终止符 `00` = 两个连续 0x00，这是分布里第二多的形态。

**但 9 个连续 0x00 仍然需要 8 个尾部空串**，
这个现象在第 1 卷列为未解，此处再次确认无新证据。

| `0x10` | 字符串标签 | 强（5006 例） |
