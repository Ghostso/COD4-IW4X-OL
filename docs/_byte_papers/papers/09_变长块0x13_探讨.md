# 第 9 卷 · 探讨：为什么 blob 要自带"长度字段的类型"

> 对应论文：`09_变长块0x13.md`

---

## 一、一个多余的设计

`0x13` 的格式是：

```
13 08 <u32 len> <data>
      ↑↑
   长度字段自己的类型标签
```

这个 `08` 看起来**完全多余** —— 长度当然是整数，谁都知道要读 4 个字节，
为什么还要写一个 `0x08` 告诉别人"这是个 u32"？

三种解释：

### 解释 1：统一序列化框架的副作用

Demonware 的 ByteBuffer 对所有值都写 "类型 + 值"。
"blob 的长度"本身就是一个 `writeU32()` 调用，自然带标签。

这是最自然的解释：**实现层面的一致，不是协议层面的冗余**。

### 解释 2：允许长度用别的类型

如果框架允许 `13 0a <u64 len> ...`（用 64 位长度），那 `08` 就有意义 ——
它告诉你该读几字节。

但实测 1749 例**全部是 `08`**，从未出现 `0a` 或其他。
所以"允许变体"这条在当前 build 上没有被使用。

### 解释 3：自描述以便跳过未知字段

如果解析器遇到不认识的标签，可以通过"读类型标签 → 知道值宽度 → 跳过"
来实现向前兼容。

`13 08 <len> <data>` 正好允许：看到 `13` 就知道"先读一个类型标签，
再按该类型的宽度读长度，再跳过长度字节"。

**这是最有说服力的设计理由。**

---

## 二、这个细节为什么值得写进论文

因为它是一个**可复用的模式**：

`0x6b`、`0x6c` 也是 `标签 + 08 + u32 长度` 的形态。
三者共享同一套"变长结构"骨架：

```
变长标签 = 标签字节 | 长度字段的类型(08) | 长度值(u32) | 数据
```

一旦认出这个骨架，任何新的 `0x6X`/`0x1X` 标签都能快速归类。

**这是本卷集合里第一次出现"可推广的结构模板"。**

---

## 三、为什么是 `0x13` 而不是别的数

标签值本身没有可推的规律（`0x10` 字符串、`0x13` blob、`0x6b`/`0x6c` 数组）。

但有个观察：

```
0x10 = 16
0x13 = 19
0x6c = 108
```

`0x0a`(10)、`0x10`(16)、`0x13`(19) —— 和 Demonware 的枚举值可能有关。
这属于"外部知识"，不在本卷的实证范围内，
所以**不写结论，只记为观察**。

---

## 四、16 字节块的困惑

437 个 16 字节块，出现在 `11/4`、`4/13` 等报文里。

16 字节 = 128 位，恰好是：
- MD5 摘要
- UUID
- AES-128 密钥

在 `11/4` 里，它与 `0x1122334455667788`（测试哨兵）相邻。
如果哨兵是"测试用的会话 ID"，那 16 字节块很可能是**配套的密钥或哈希**。

但**无法证实**。语料里没有"已知内容的 16 字节块"可以作为对照。

**这提醒一件事**：不是所有字段都能靠语料解出来。
有些字段需要"改变一个输入，看输出变不变"的**主动实验**。

## 五、`0x13` 与 `0x10` 的选择规则

一个实际的问题：服务端在构造应答时，
什么时候该用 `0x10`（字符串），什么时候用 `0x13`（blob）？

从语料看：

| 内容类型 | 用的标签 |
|---|---|
| 文件名、ID、日志串 | `0x10` |
| 二进制、压缩数据、哈希 | `0x13` |

**规则**：如果需要保证"含 NUL 也能传"，必须用 `0x13`。

这条对项目有直接价值：`lobby_server.py` 的 `blob()` 方法
已经正确处理了这一点（`T_BLOB` + `T_U32` + 长度 + 数据）。

## 六、方法论收获

> **当看到一个"多余"的字段时，问"它在什么情况下有用"。**

`13 08 <len>` 里的 `08` 在今天的语料里完全多余
（1749 例全是 08）。但它的存在说明框架支持"长度类型可变"。

这类"当前未用但设计保留"的字段，是理解**框架设计意图**的窗口。
它们告诉你：这个协议当初是为什么场景设计的。
