# 第 0 卷 · 字节级逆向总纲与方法论

> 项目：使命召唤OL 整大厅同步推进（build 1649370 / 3.19）
> 日期：2026-10-29
> 证据基线：`_byte_papers/corpus/corpus.json`（83 个 run，6848 条真实客户端 payload）
> 复跑入口：`tools/lobby_grammar_v5.py`

---

## 1. 这份文档集是什么

本目录（`_byte_papers/`）是对**整个大厅协议**的字节级逆向后备
记录。目标不是"能跑起来"，而是**每一个字节都有归属**。

组织方式：

| 路径 | 内容 |
|---|---|
| `corpus/corpus.json` | 从 83 次真实运行抽取的 6848 条完成任务帧，逐字节十六进制 |
| `corpus/corpus_stats.txt` | 按 (service, task) 的样本量 / 长度 / 重复度 |
| `corpus/grammar_v5_result.txt` | 文法闭合验证结果（6848/6848） |
| `evidence/` | 每篇论文引用的原始统计产物，可复跑 |
| `papers/` | 论文本体 |

---

## 2. 证据等级（按 AGENTS.md 的权威序）

本项目强制要求按可信度取信：

1. **本地逆向** —— 从真实客户端抓到的字节。**本卷全部属于此级。**
2. IW4X
3. CoD4X
4. 其他外部项目（ol-mod 不在权威序列，仅作同族旁证）

`corpus.json` 里的每一条记录都是 `lobby_server.py` 在**真实客户端会话**中
解密成功、HMAC 校验通过（`hmac=OK`）后才落盘的 payload。
这意味着：

- 它不是协议文档复述，不是参照实现生成，而是**客户端真正写出来的字节**。
- 任何与本卷推论冲突的外部项目文档，一律以本卷为准。

---

## 3. 语料的构造方式

`lobby_tasks.bin` 的记录格式（`lobby_server.py:1447` 的写点）：

```
u8  service
u8  task
u32 payload_len            (小端)
u8  payload[payload_len]
```

连续拼接，无文件头，无对齐。`tools/lobby_corpus_build.py` 遍历
`run_codol_001/runs/**/kit/lobby_tasks.bin`，按 mtime 排序后逐条解出，
并给每条打上来源 run 标记。

**这一步的意义**：把 83 次互不相关的运行合并成单一可统计语料，
才能做"某个字节在所有样本中是否恒定"这种统计——这是字节级逆向的基本功。

规模：

```
files=83  records=6848  pairs=55
```

55 个 (service, task) 二元组，即 55 类不同的请求/响应体。

---

## 4. 核心方法：三遍扫描

### 第一遍 · 位置统计

对每个 (svc,task)，取样本最多的那个长度，逐字节统计取值分布
（`tools/lobby_byte_field_stats.py`）。

判定规则：

- **该位置在所有样本中取值恒同** → 结构字节（标签、长度、常量）
- **该位置取值变化** → 数据字节

这是把"一串十六进制"切成"结构 / 数据"的唯一客观手段。
不靠猜字段，靠样本间的差异性。

### 第二遍 · 假设-证伪

对每个疑似标签，写出**可证伪的断言**，然后在全部样本上跑：

> 断言 = "若字节 X 是标签 T，则从它开始按 T 的格式步进，
> 解析出的边界必须与样本总长度吻合。"

例子（第 4 卷详述）：

```
断言 H1: 0x6c | 08 | u32 N | N 字节 | u32 M | 00
结果:   203/203 命中          → 假设成立
断言 H4: 0x6c | 08 | u32 N | 4N 字节 | 00
结果:   0/203 命中            → 假设证伪
```

**这是本卷最重要的方法论**：一个文法如果不能在所有样本上闭合，
它就是错的，哪怕它在几条手工样本上"看着对"。

### 第三遍 · 全量闭合

把全部文法写进一个解析器（`tools/lobby_grammar_v5.py`），
在 6848 条样本上跑到底。

**结果：6848 中 6848 通过，0 失败（100.00%）。**

闭合是本次逆向后备的合格线。任何"通过了 97%，剩下 3% 大概是特例"
的结论，都视为未完成。

## 5. 文法的最终形态（结论先行）

大厅任务 payload 不是 protobuf，不是 JSON，而是
**Demonware ByteBuffer 风格的类型标签流**：

```
payload := element* terminator
element := tag value
terminator := 0x00 (可重复 1 至 9 次)
```

| tag | 语义 | 载荷 |
|---|---|---|
| `0x00` | 终止 | — |
| `0x01` | bool | 1 字节 |
| `0x03` | u8 | 1 字节 |
| `0x06` | u16 | 2 字节 |
| `0x07` | i32 | 4 字节 |
| `0x08` | u32 | 4 字节 |
| `0x09` | i64 | 8 字节 |
| `0x0a` | u64 | 8 字节 |
| `0x10` | 字符串 | 到 NUL，可空 |
| `0x13` | blob | `08` + u32 长度 + 数据 |
| `0x6b` | 数组 | `08` + u32 字节长 + 数据 + u32 元素数 |
| `0x6c` | 数组 | `08` + u32 字节长 + 数据 + u32 元素数 |

---

## 6. 为什么这套文法可信

三条独立证据同时成立：

1. **闭合率 100%** —— 6848 条无一例外。
2. **长度自洽** —— 每个变长标签的长度字段都与实际步进量严格相等，
   不是"大概能对上"。
3. **与项目内已实机验证的构造器一致** ——
   `codol_crypto.py` 的 `Buf` 类在 2026-10-03 已被实机验证过
   （任务应答路径），它写的正是同一套标签。
   本卷的贡献是：**把读方向也闭合了**。

---

## 7. 本卷的边界（诚实声明）

- 本卷回答"**字节怎么切分**"，不回答"**每个字段业务含义是什么**"。
  字段语义（例如某个 u32 是房间号还是地图号）属于后续各卷，
  且必须以服务端应答与客户端反应为证据，不能凭命名猜。
- 语料来自**一条服务端实现路径**。客户端可能发出的、但该路径
  从未触发的报文类型，不在语料内 —— 这类盲区在各卷末尾单列。
- 本文不引用 ol-mod 的任何常量。凡出现"对照"，均已注明对照物
  是否服务本 build。

## 8. 后续卷的推进顺序

按"字节覆盖率 × 业务重要性"排序：

- 第 1 卷 终止符（0x00）
- 第 2~3 卷 定长标量（0x01 / 0x03）
- 第 4~7 卷 整型（0x06 / 0x07 / 0x08 / 0x0a）
- 第 8 卷 字符串（0x10）
- 第 9 卷 变长块（0x13）
- 第 10~11 卷 数组（0x6b / 0x6c）
- 第 12 卷 长度前缀的分层与嵌套规则
- 第 13 卷 按 service 的整体语义分区
- 第 14 卷 全通道字节覆盖台账

每一卷配一篇"探讨"文档（`*_探讨.md`），记录推导过程、
证伪掉的假设、以及仍然存疑的地方。
