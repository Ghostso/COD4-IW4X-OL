# 第 5 卷 · 探讨：负值才是这类字段的钥匙

> 对应论文：`05_有符号整型0x07.md`

---

## 一、问题：4 字节怎么可能是"有符号"和"无符号"两种

`0x07` 和 `0x08` 都是 4 字节。
它们读出来的位模式完全一样 —— 区别只在**如何解释**。

如果只看正数，你永远分不清它们：

```
07 64 00 00 00  → 100（当作 i32）
07 64 00 00 00  → 100（当作 u32）
```

**正数完全不提供区分度。**

那凭什么说 `0x07` 是有符号的？

---

## 二、三个独立判据

### 判据 1：`-1` 的位模式出现 117 次

`FF FF FF FF` 作为 u32 是 4294967295。

在 6848 条真实报文里，`0x08` 的 129 个不同取值中**没有一个**是 4294967295；
而 `0x07` 里有 117 个 `FF FF FF FF`。

如果 `0x07` 是有符号的，"这个字段等于 -1"是一个常见的
"未设置 / 无效"语义，非常合理。
如果 `0x07` 是无符号的，"这个字段等于 42 亿" 就毫无道理。

### 判据 2：407 个负值集中在同一个 service

全部负值都出现在 `21` 族（21/1、21/5、21/12）。

`21` 是什么？根据 `lobby_server.py` 的处理注释，
`21/5` 是 findSessions 的应答，内容是会话（session）描述对象。

会话描述里出现负数，最自然的解释是：
**某些字段是"带符号的容量 / 差值 / 偏移"**，
或者是 hash 值被按 int32 处理。

无论哪种，"那里应该有负数"是一个可预期的现象；
而它们确实出现了，且全部在 `21` 族 —— **位置集中**。

### 判据 3：服务端构造代码的实测教训

`codol_crypto.py` 里有一行注释（2026-10-03 的实测结论）：

> `★ 关键: matchmaking 的 query-criterion 字段是 SIGNED，必须用 I32(0x07)；
>   写成 U32(0x08) 会被客户端逐值类型检查拒绝`

这条教训来自**真实运行**：服务端曾用 `0x08` 写这个字段，客户端拒绝。
换成 `0x07` 后通过。

这是行为层面的证据（客户端做了类型检查），比字节统计更硬。

**三条合起来，`0x07` = int32 的置信度足够高。**

---

## 三、被排除的解释

### 解释 E1：`0x07` 是 u32，只是恰好出现大数

如果 `0x07` 是无符号的，那 407 个"负值"实际上是 40 亿量级的正数。

**排除理由**：`-1`（即 4294967295）出现 117 次，且全部在 `21` 族。
一个会话描述里，某个字段恒为 4294967295 —— 这不可能是正常数据，
只能是哨兵值。而 4294967295 作为"全 1 位模式"的哨兵，
在有符号语义下正好是 -1。

### 解释 E2：`0x07` 是 float

**排除理由**：`FF FF FF FF` 作为 float 是 NaN。
而 `0x07` 有 12634 个实例，如果它是 float，
应该出现大量小数（例如 `0x3f800000` = 1.0）。
实测所有值都是整数，没有一个小数。

### 解释 E3：`0x07` 与 `0x08` 是同一个类型的两种写法

**排除理由**：客户端做了类型检查（判据 3）。
如果两者等价，服务端写哪个都该通过。实测不是。

## 四、仍然想不通的地方

### `-695030357` 是什么

它在 `21/5` 的 159 条样本里恒在同一位置，跨 83 个 run 不变。

`-695030357` 的十六进制是 `0xD692ADAB`。

反过来看：`0xABAD92D6` 如果倒序…… 就是 `d6 92 ad ab`。
而语料里实际字节序是 `ab ad 92 d6`（小端存储），
即逻辑值 `0xD692ADAB`。

**`AB AD 92 D6` 这个字节序列看起来很眼熟** —— 它包含 `AB AD`，
像是 `BAD` 的变体。会不会是个凑出来的"坏值"哨兵？

但它在**每一个** 21/5 样本里都出现，不是偶发。
如果是"坏值"，说明客户端每次都报同样的错 —— 不太可能。

更可能：它是某个**固定的 session 类型标识或 security key 的半段**。

我倾向于"固定标识"，但**没有证据**，所以不下结论。

### `21/1` 与 `21/12` 的关系

两者都有 `-1`、`-695030357`、`-1924013160`，但长度不同（269 vs 288）。

可能是因为：`21/12` 是 `21/1` 的应答（带更多字段），
或者两者是不同查询参数的同一结构。

**需要把它们逐字段对齐才能确定。** 列为待办。

## 五、方法论收获

> **要区分"同一宽度的两种类型"，去找那个只在一种类型下合理的值。**

`FF FF FF FF` 就是这样的值：

- 作为 u32 → 4294967295（无意义）
- 作为 i32 → -1（标准哨兵）

一旦找到这样的值，类型判别就从"猜"变成"证"。

这条规则可以推广：

| 要找 | 找什么值 |
|---|---|
| 有符号 vs 无符号 | 高位全 1 / 出现负数 |
| 整数 vs 浮点 | 出现小数 / 出现 NaN 位模式 |
| 定点 vs 整数 | 出现"看似无规律但范围极小"的值 |
