# 第 14 卷 · 探讨：台账的诚实边界

> 对应论文：`14_全通道字节覆盖台账.md`

---

## 一、这张台账证明了什么，没证明什么

### 证明了的

1. **客户端发往服务端的所有已知报文，字节结构 100% 可解析。**
   - 6848 条，55 个 task，零失败。
   - 这是**可复跑**的：`python -I tools/lobby_grammar_v5.py`。

2. **每个标签的宽度、字节序、边界规则都经过全量样本验证。**
   - 不是抽样，不是"看着像"。

3. **部分字段的语义被外部锚点固定。**
   - `1649370` = build 号（88 例，全在 71/18）
   - `16701785630074219790` = CODOID（820 例）
   - 文件名字符串可直接读

### 没证明的

1. **服务端 → 客户端方向的字节结构。**
   本卷只覆盖客户端发出去的。
   服务端的应答/推送格式，虽然有 `codol_crypto.py` 的实现，
   但**没有对应的字节级台账**。

2. **约 15 个 task 的业务语义。**
   结构清楚，但不知道是干什么的。

3. **每个字段的"为什么"。**
   例如 `102/7` 里 u8 恒为 1 —— 结构上知道它是 u8，
   但不知道为什么是 1。

4. **帧头与加密层。**
   `u32 declared | 0x86 | service | 0x03 | task` 这个帧头，
   以及 AES-CBC + HMAC 的封装，都属于传输层，
   本卷没有独立验证（依赖 `lobby_server.py` 的现有实现）。

## 二、为什么"100% 闭合"不意味着"完全理解"

这是本卷集合里最容易被误读的一点。

一个类比：

> 你可以 100% 正确地切分一篇外语文章的单词边界，
> 但完全不认识任何一个词的意思。

本卷做到的是**切分**（结构），
语义是另一层工作。

**"字节级逆向"这个名字容易给人一种"全解了"的错觉。
实际做到的是"字节边界全解了，字节含义解了约一半"。**

这个区分必须写在最显眼的地方。

## 三、台账最有价值的用法

不是"查阅"，而是**"定位"**。

场景：某个功能不工作（例如"点开始游戏没反应"）。

用这张台账可以：

1. 找到该功能对应的 task（例如 `21/5`）
2. 找到该 task 的字节结构（35 字节，`u32×3 + i32 + array + u32`）
3. 找到每个字段的取值分布（`-695030357` 恒定、`array=[1]` 恒定）
4. 判断"哪个字段可能是闸门"

**没有台账时**，这个过程是"猜字段"；
**有台账时**，是"排除已知、聚焦未知"。

## 四、一个具体的例子：`0x09` 的处理

`codol_crypto.py` 的表里有 `T_I64 = 0x09`，语料里 0 例。

台账里我怎么处理的？

- **不写"客户端支持 i64"**
- **不写"客户端不支持 i64"**
- **写"零样本，存在性未知"**

这是台账该有的态度：
**没证据的地方留白，不猜测。**

因为如果我写了"客户端支持 i64"，将来别人照着实现，
可能会造出一个客户端根本不认的字段。

## 五、还要补什么

按优先级：

### 优先级 1：服务端方向的字节台账

现有 `codol_crypto.py` 里有 `build_task_reply_objects` 等函数，
它们生成的字节**没有经过本卷这样的验证**。

需要：把服务端发出的字节也收集起来，做同样的 55 个 task 级别的分析。

**难点**：服务端字节是我们自己生成的，不是客户端"自然产生"的。
所以它只能验证"我们发的格式对不对"（通过客户端反应），
不能验证"协议本来该是什么"。

### 优先级 2：激活 `0x09` 的路径

要确认 i64 是否存在，需要：
- 找一个业务上需要 64 位有符号值的场景
- 或者从客户端侧找到 `0x09` 的读取代码

### 优先级 3：15 个未解 task 的语义

这些需要主动实验或更多语料。

## 六、方法论收获

> **台账的价值在于"什么没解"，而不是"什么解了"。**

一份好的台账，读的人应该能立刻知道：
- 哪些可以用（已验证）
- 哪些不能用（未验证）
- 哪些是推测（标注了）

本卷的每一节都试图做到这一点：
每条结论后面都有"证据强度"。

**这是这份文档集能长期使用的唯一原因。**
