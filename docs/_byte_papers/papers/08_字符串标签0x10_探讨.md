# 第 8 卷 · 探讨：客户端把日志直接扔到了大厅通道上

> 对应论文：`08_字符串标签0x10.md`

---

## 一、这一卷最大的意外

`0x10` 的结论——"NUL 结尾的可变长字符串"——本身平淡无奇。
真正让人意外的是**里面的内容**。

489 个 distinct 字符串里，最大的那一批长这样：

```
ClientLoadTime|${TIMESTAMP_OFFSET(-5)}|16281043470933576704|16701785630074219790|${CODOID(16701785630074219790)}|101.24.255.88:9147|Windows 10|AMD Ryzen 7 5800H with Radeon Graphics|...
```

**这是客户端日志。**

它包含：事件名、时间戳占位符、两个 20 位 ID、玩家 IP、端口、
操作系统版本、CPU 型号……

而且它**直接从客户端发到了服务端**，长度 8058 字节。

### 这不是"协议字段"，这是"日志上报"

服务端目前对这类报文的处理是：

```
-> UNMAPPED service=71 task=3 payload=435B -> 空 ACK (功能未实现)
```

即：**原样吞掉，回一个空 ACK**。

这意味着两件事：

1. **服务端不需要解析它** —— 客户端不在意回什么，只要 ACK 到。
2. **但它每天在上报隐私信息** —— CPU 型号、IP、OS 版本。

第 2 点不是安全漏洞，但值得记录：
**大厅协议里有一条完整的客户端遥测通道**，
而且通道里的内容是明文日志串。

---

## 二、为什么这些串会被当成"字符串"发出去

推测：客户端内部的日志系统会把日志行格式化成「竖线分隔的字段串」，
然后某个上报模块直接把它塞进 `0x10` 字段发走。

**这解释了为什么会有不可打印字节**：

如果日志行后面拼了二进制（例如调用栈地址、内存快照片段），
直接用 NUL 结尾的字符串承载它，就会出现"看似文本、后接二进制"的现象。

这也解释了为什么最长能到 8058 字节 ——
日志行没有被截断。

---

## 三、`${TIMESTAMP_OFFSET(-5)}` 是什么

这个占位符出现在几乎每一个日志串里。

`${...}` 是**客户端模板引擎**的语法。
`TIMESTAMP_OFFSET(-5)` 的意思是"当前时间减 5"（单位可能是秒或帧）。

`${CODOID(16701785630074219790)}`、`${ZONEID(...)}` 同理。

**关键问题：谁负责展开？**

两种可能：

1. **客户端展开** —— 发之前把 `${...}` 替换成实际值。
   如果是这样，我们收到的应该是 `TIMESTAMP_OFFSET` 展开后的结果 ——
   但实际收到的是**原样的占位符**，说明它没有被展开。

2. **服务端展开** —— 客户端把模板发过来，服务端替换后再存。

**实测支持第二种**：收到的是原文。

这意味着服务端有一个**未实现的职责**：展开这些模板。

但服务端目前的处理是"空 ACK 吞掉"，客户端也没报错 ——
说明**客户端并不检查上报是否被处理**。

---

## 四、不可打印字节：一个必须记住的坑

85.2% 的字符串是纯可打印 ASCII，剩下 14.8% 含二进制。

我最初以为这 14.8% 是"解析错误"—— 但检查样本后发现，
它们开头全是对的日志格式，只是后面接了非文本。

**这不是解析错误，是客户端的真实行为。**

这条对后面做服务端极重要：

> 解析 `0x10` 时，**只能信 NUL 分界**，不能信"内容是文本"。
> 构造 `0x10` 时，**绝不能把 NUL 塞进载荷**（会截断）。

## 五、这批数据对项目的实际价值

### 价值 1：确认了 service 71 的用途

`71/3`、`71/7` 的 8000+ 字节串，
全部是 `xxxEvent|...` 格式的日志。

`71` 是 **客户端日志/遥测通道**。

这样一来，第 13 卷做 service 语义分区时，`71` 就有了明确定位：
**它不是业务逻辑，而是日志上报**。

### 价值 2：拿到了客户端环境信息

从这些串里能读出：

- 操作系统：`Windows 10`
- CPU：`AMD Ryzen 7 5800H with Radeon Graphics`
- IP：`101.24.255.88:9147`
- 分辨率：`1680x1050`
- 刷新率：`60 Hz`
- 显卡分类：`Default`

这些是**客户端上报的真实环境**，对理解"为什么某些路径行为不同"有帮助。

### 价值 3：看到了客户端内部的事件名清单

从所有日志串的首段提取事件名，得到一份**客户端内部事件清单**：

```
ClientLoadTime, ClientLoadout, ClientReconnect, ClientOffline,
ClientLogin, ClientSettingsGpu, CreateRoom,
TimerError, ChannelSubscriptionFail, ...
```

**这个清单的价值**：它是客户端用自己语言写下的"我会做什么"。
比从 RTTI 反推类名更直接。

## 六、方法论收获

> **字符串字段的价值不在"它是字符串"，而在"它写了什么"。**

`0x10` 的结构（NUL 结尾）一分钟就能确定。
但把 489 个 distinct 值当真读一遍，能拿到：

- service 71 的语义
- 客户端环境
- 客户端内部事件名

**结构分析给骨架，内容分析给血肉。**

## 七、未解

   中间可能有更有价值的信息。
2. 占位符 `TIMESTAMP_OFFSET(-5)` 的单位（秒？帧？）未定。
3. `-5`、`-4`、`-7` 这些偏移量的含义未解。
4. 长度 1~6 的短数字串（`1625160`）是什么 ID。
