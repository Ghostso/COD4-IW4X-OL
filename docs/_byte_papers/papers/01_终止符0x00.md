## 2. 为什么不是"一条记录的填充"

先排除最平凡的解释：这会不会只是记录格式本身的对齐填充？

不是。原因：记录格式是

```
u8 service | u8 task | u32 len | payload[len]
```

`len` 是精确的 payload 长度，后面直接接下一条记录，**没有对齐要求**。
所以 payload 尾部的 `0x00` 属于 payload 内部，是客户端写进来的。

---

## 3. 终止符的两种来源

连续多个 `0x00` 有两种可能来源，必须分开：

### 来源 A：真正的协议终止符

每条 payload 至少有一个 `0x00` 表示"字段流结束"。
这是语料中 `1 个 0x00`（1362 条）的主力。

### 来源 B：空字符串 `0x10 00` 的尾巴

字符串标签 `0x10` 的格式是"标签 + 到 NUL 为止的内容"。
**空字符串**就写成 `10 00` —— 它自己带一个 `0x00`。

于是：

```
... 10 00 00
      ↑    ↑
   空串   终止符
```

产生 2 个连续 0x00。

**验证**：`2 个 0x00` 是最大宗（2562 条），
与"空字符串极常见"的观测一致——第 8 卷会给出空串的统计。

---

## 4. 更长的连续 0x00 怎么解释

按来源 B 的推理，若报文尾部连续 N 个空字符串字段，叠上终止符，
就得到 N+1 个 `0x00`。

但**这个解释只在"空串恰好是最后几个字段"时成立**。
9 个连续 0x00 = 8 个尾部空串，这个数量在具体报文里是否真的出现，
尚未逐条核对（见第 0 卷探讨的待办第 1 条）。

## 5. 终止符在解析中的实际作用

在 `tools/lobby_grammar_v5.py` 里，终止逻辑是：

```python
if b[buf.i] == 0x00:
    while buf.i < len(b) and b[buf.i] == 0x00:
        buf.i += 1
    if buf.i < len(b):
        return False, out, "trail %dB"     # 终止符后还有内容 = 错
    return True, out, ""
```

即：**吃掉所有尾部 0x00，然后必须恰好到达 payload 末尾**。
若终止后仍有非零字节，整条判为失败。

这个判据在全量语料上 6848/6848 通过。

## 6. 与长度字段的关系

`0x13` 和 `0x6b/0x6c` 这些变长标签**自带字节长度**，
不依赖终止符界定边界；终止符只界定**整条 payload**。

这两层是独立的：

```
payload := element* 0x00+
element := tag value           # value 内部自带长度, 不靠 0x00
```

因此 payload 里出现的 `0x00` 只有两种身份：
- 空字符串的 NUL
- payload 终止符

**不存在"某个字段内部 0x00 被误当终止符"的风险** ——
定长字段不可能是 0x00 标签，变长字段自带长度不吃终止符。
