# `0x13` blob 的两种内层格式

> 重大修正：blob 不是单一格式，而是**按 task 严格分裂为两类**
> 证据：`tools/lobby_blob_prefix_stats.py`（全语料 1749 个 blob）

---

## 1. 统计事实

| task | blob 数 | 首 u32 == 长度-4 | 比例 |
|---|---|---|---|
| `6/14` | 235 | 235 | **100%** |
| `11/4` | 261 | 261 | **100%** |
| `8/3` | 84 | 0 | **0%** |
| `21/1` | 84 | 0 | 0% |
| `21/3` | 13 | 0 | 0% |
| `21/12` | 108 | 0 | 0% |
| `68/3` | 162 | 0 | 0% |
| `71/4` | 640 | 0 | 0% |
| `71/15` | 162 | 0 | 0% |

**这不是概率分布，是二分。**

九个 task，无一例外地落在 100% 或 0%。

---

## 2. 两类 blob

### 类型 A：带内层长度前缀（`6/14`、`11/4`）

```
blob 内容 := u32 内容长度 | <内容长度 字节的数据>
```

**验证**：无论是 16、20、21、30、63、129、245、267 字节，
首 u32 都严格等于 `长度 - 4`。

### 类型 B：裸数据（`8/3`、`71/4`、`21/*`、`68/3`、`71/15`）

```
blob 内容 := <任意数据>
```

- `8/3`：zlib 流（`78 01 ...`）
- `71/4`：ASCII 字符串（`nQloP0oCVWR6RDJS`）
- `21/1` / `21/12`：二进制
- `68/3`：以 `00 00 ...` 开头

---

## 3. 这个发现推翻了我之前的两个结论

### 推翻 1：第 12 卷"嵌套未使用"

`11/4`、`6/14` 的 blob 内部是**有结构的**（长度前缀 + 内容）。

### 推翻 2：`msg/11_04_blob内嵌.md` 的"五条路径全失败"

那五条路径失败，是因为**我没意识到内层的第一层就是长度前缀**。
发现后，`0c 00 00 00` = 12 = 剩余字节 —— 完全吻合。

---

## 4. 内层内容的结构（`11/4` 与 `6/14`）

剥掉 4 字节长度头后，`11/4` 的内容开头：

| 内容开头 | 出现形态数 |
|---|---|
| `02 02 00 00 ...` | 最多 |
| `02 04 00 00 ...` | 次多 |
| `02 06 00 00 ...` | |
| `02 08 00 00 ...` | |
| `18 1c 5a 98 ...` | 少数 |

`02 0X 00 00` —— 第二字节 ∈ {2,4,6,8}，全偶数。

**假说**：`02` 是类型码，`0X` 是"元素数 × 2"或"字节长度的倍率"。

---

## 5. 为什么会有两种格式

最可能的解释：**`0x13` 只是"不透明字节块"，客户端在里面装什么由业务决定。**

- `11/4`（房间数据）：装的是"再带一层长度前缀的结构体"
- `8/3`（档案）：装的是"zlib 压缩流"
- `71/4`（身份上报）：装的是"ASCII 字符串"

**所以 `0x13` 本身没有"内层格式"，内层格式属于业务。**

这是一个重要的认知修正：
**不能假定所有 `0x13` 都能用同一种方式继续解析。**

---

## 6. 对解析器的影响

`tools/lobby_grammar_v5.py` 的处理是**正确的** ——
它把 `0x13` 当作不透明块，读长度、取数据、不继续解。

如果试图"深入解析 `0x13` 内容"，必须**按 task 分别实现**。
