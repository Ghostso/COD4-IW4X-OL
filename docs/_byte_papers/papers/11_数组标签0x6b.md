# 第 11 卷 · 数组标签 `0x6b`

> 覆盖：`0x6b` 标签
> 证据：`tools/lobby_array_stats.py`、`tools/lobby_grammar_v5.py`
> 样本：21/5（159 条），全部同形

---

## 1. 结论

```
0x6b 0x08 <u32 字节长度 N> <N 字节数据> <u32 计数>
```

与 `0x6c` 结构**完全相同**，但标签不同。

实测：`N = 4`，`数据 = 01 00 00 00`，`计数 = 0`。

---

## 2. 报文逐字节

`21/5` 的最短形态（35 字节，129 样本）：

```
偏移  字节                              解释
00    08 01 00 00 00                    u32 = 1
05    08 00 00 00 00                    u32 = 0
0a    08 0a 00 00 00                    u32 = 10
0f    07 ab ad 92 d6                    i32 = -695030357
14    6b 08 04 00 00 00                数组头，N = 4
1a    01 00 00 00                       数据：u32 = 1
1e    00 00 00 00                       计数 = 0
22    00                                终止
```

**算术**：`5 + 5 + 5 + 5 + 6 + 4 + 4 + 1 = 35` ✓

### 75 字节形态（30 样本）

前面 5 个字段相同，然后在偏移 `3c` 处又出现一个 `6b`：

```
3c    6b 08 04 00 00 00                N = 4
42    01 00 00 00                      数据：u32 = 1
46    00 00 00 00                      计数 = 0
4a    00                                终止
```

**所以 21/5 有两个数组字段**，中间隔着别的 TLV 字段。

---

## 3. 与 `0x6c` 的对照（本卷核心）

| 项 | `0x6b` | `0x6c` |
|---|---|---|
| 结构 | `08 + u32 N + N B + u32` | 同 |
| 出现位置 | **只在 21/5** | 只在 28/1、28/4 |
| N 值 | 恒 4 | 0, 4, 8, 508 |
| 数据 | 恒 `01 00 00 00` | 递增 ID 表 / 小序列 |
| 尾部 u32 | 恒 0 | 变化（1~263） |

**关键观察**：
- `0x6b` 的数据**恒为 u32 = 1**
- `0x6b` 的尾部计数**恒为 0**
- `0x6b` 只出现在 `21` 族（matchmaking）
- `0x6c` 只出现在 `28` 族（任务参数）

**这说明它们是两套不同用途的"数组"类型**，
虽然编码格式相同，但业务角色不同。

---

## 4. `0x6b` 的语义推测

`21/5` 是 findSessions 的应答体。
报文里有：

```
u32 = 1
u32 = 0
u32 = 10
i32 = -695030357
array<u32> = [1]      ← 0x6b
```

结合 `lobby_server.py` 里对 21/5 的处理
（构造 session 对象，包含 game_type、max_players、
current_players、map_name、security_key 等），
这个 `array<u32> = [1]` 很可能是**"允许的 game type 列表"或"地图 ID 列表"**。

尾部计数恒为 0，说明客户端在这个请求里**没有传筛选条件**
（或者传了一个空条件集）。

**这是推测，不是实证。**

---

## 5. 为什么数据恒为 1

159 条样本，跨 83 个 run，`01 00 00 00` 一次都没变。

这排除了"随机数据"和"会话相关数据"。
它要么是：
- 某个固定枚举值（game_type = 1）
- 某个"列表长度为 1"的暗示

第一种更可能 —— 因为如果是长度，应该有别的值才对。

---

## 6. 结构验证

在 v5 解析器里，`0x6b` 按
`6b 08 <u32 N> <N B> <u32>` 解析，全语料 159 条全部通过，
无一条因 `0x6b` 失败。

这与 `0x6c` 的验证方式一致（第 10 卷）。

---

## 7. 字节覆盖

| 项 | 语义 | 证据强度 |
|---|---|---|
| `0x6b` | 数组标签（第二变体） | 强（159 例） |
| 结构 | 与 `0x6c` 相同 | 强（算术闭合） |
| 数据含 u32 = 1 | 恒定的枚举/长度 | 强（159/159） |
| 尾部 u32 = 0 | 恒定的空值 | 强（159/159） |
| 业务语义 | 疑为 game type 列表 | **弱（纯推测）** |

**盲区**：

1. `0x6b` 的语义完全未解 —— 只是"结构已知"。
2. 为什么数据和尾部计数都是固定值？说明这条路径从未被改变过输入。
3. `0x6b` 与 `0x6c` 的差异是否对应"元素类型"？还是"业务系列"？
   语料无法区分。
