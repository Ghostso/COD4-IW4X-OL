# 第 12 卷 · 探讨：解析器的边界就是协议的边界吗

> 对应论文：`12_长度前缀与嵌套.md`

---

## 一、一个藏在解析器里的假设

我的 v5 解析器这样处理 `0x6b`/`0x6c`：

```python
if t == 0x6C:
    if buf.take(1) != b"\x08": fail
    bl = buf.u32()
    body = buf.take(bl)
    cnt = buf.u32()        # ← 尾部这个 u32
    return (t, (cnt, body))
```

这里有一个**未声明的假设**：

> `0x6b`/`0x6c` 的管辖范围**包括**数据之后那个 u32。

为什么这么假设？因为如果不包含，解析器会在 u32 的第一个字节上
尝试读新标签 —— 而那个字节是 `0x00`、`0x01`、`0x83` 之类，
全部是未知标签，会失败。

**所以这个假设是"被迫"的：只有这样才能闭环。**

但这不等于"这就是协议规定"。

## 二、两种可能的协议形态

### 形态 A：数组标签管辖到 u32 为止

```
数组 := 6c | 08 | N | 数据 | u32
```

这是我实现的方式。

### 形态 B：数组标签只管数据，u32 是独立字段

```
数组 := 6c | 08 | N | 数据
字段 := u32（无标签）
```

如果协议是形态 B，那序列化器的写法应该是：

```
writeArray(xs); writeU32NoTag(m);   // 但框架没有"无标签"的写方法
```

**B 不太可能** —— 因为整个框架都是"每个值都带标签"。
一个"无标签 u32"是反设计的。

### 形态 C：u32 是数组元素类型的描述符

```
数组 := 6c | 08 | N | 数据 | u32 元素类型
```

如果尾部 u32 是"元素类型"，那它应该是一个小的枚举值（0,1,4,8...）。
实测有 263、131、203 —— **超出合理的类型范围**。

排除。

**结论：形态 A 最合理。** 但这是推理，不是直接证据。

---

## 三、这为什么重要

如果将来要实现"构造一个数组字段"，就必须知道：

- 尾部 u32 填什么
- 它属于数组头还是外部

目前的处理是"原样回显客户端发来的数组"（服务端 `28/1` 是回显）。
**回显不需要理解语义，所以问题被掩盖了。**

一旦要主动构造（例如返回一个"可用关卡列表"），就必须回答这个问题。

**这是第 10、11 卷留下的技术债。**

## 四、嵌套：为什么实测没有

`0x13` 的数据部分完全可以装另一个 TLV 流。
为什么客户端不用？

可能原因：

1. **不需要**：所有嵌套需求都用"扁平化 + 长度前缀"解决了。
2. **框架不支持**：序列化器没有"写一个子 buffer"的方法。
3. **有但没触发**：本语料覆盖的操作路径不包含嵌套场景。

**从 `codol_crypto.py` 看，框架里没有"嵌套写"的方法** ——
`Buf` 只有标量、字符串、blob、数组这几种。
如果要在 blob 里放 TLV，需要手动拼接字节。

**这也解释了为什么 `8/3` 的 764 字节 blob 是一个 zlib 流而不是 TLV 流** ——
因为框架不支持嵌套，客户端选择了"自己压缩一个结构化档案"。

## 五、分层的实际意义

把 payload 理解成"两层平坦结构"，对写服务端有直接影响：

### 影响 1：可以逐字段回显

服务端可以做到"不理解的 tag 就原样回显"，
因为每个元素是独立的，不需要理解整体。

`lobby_server.py` 的 102/7 处理正是这样：
"回显 50/50 个字段（值=0）"。

### 影响 2：字段顺序可能重要

如果客户端按"第 N 个字段"取值，顺序就重要；
如果按"标签 + 位置"匹配，顺序仍重要。

**目前假设顺序重要**（服务端是逐字段构造的）。

### 影响 3：未知标签必须能跳过

因为 `0x08` 作为"长度类型标签"的存在，
解析器可以做到：看到不认识的标签 → 若后面跟 `08` 就按长度跳过。

**这是向前兼容的基础。**

## 六、方法论收获

> **解析器的"被迫假设"要单独标出来。**

当解析器为了闭环而不得不采用某种读法时，
这个读法**可能是对的，也可能只是"恰好能跑"**。

本卷标出的被迫假设：

1. `0x6b`/`0x6c` 管辖尾部 u32
2. `0x10` 的空串与终止符的区分

这两条都在各自的卷里写了"证据强度"，这是必要的诚实。
