# 第 12 卷 · 长度前缀的分层与嵌套规则

> 覆盖：所有带长度前缀的标签（`0x13`、`0x6b`、`0x6c`）的共同规则，
> 以及嵌套是否可能
> 证据：`tools/lobby_grammar_v5.py`（100% 闭环）+ 语料的嵌套实例

---

## 1. 共同模板

三个变长标签共享同一个骨架：

```
变长标签 := 标签字节 | 0x08 | u32 长度 | 长度字节的数据
0x13 → blob
0x6b → 数组（尾部多一个 u32）
0x6c → 数组（尾部多一个 u32）
```

**关键点**：中间那个 `0x08` 不是长度值的一部分，
而是"长度字段自身的类型标签"。

---

## 2. 为什么必须是 `0x08`

如果允许变体（例如 `13 0a <u64 len>`），解析器就要处理两种情况。
实测 1749 个 `0x13`、159 个 `0x6b`、203 个 `0x6c`：

**全部是 `0x08`，零例外。**

这是一个**实现约束**：客户端只会写 `08`。
服务端如果需要构造这类字段，也必须写 `08`。

---

## 3. 嵌套是否可能

### 已有实例

`8/3` 的报文：

```
08        u32 = 5
08        u32 = 1
08        u32 = 1
08        u32 = 0x1b97d354
13 08 <764> <764 字节 zlib>
<125 × (07 + u32)>
00
```

`13` 里的 764 字节是 zlib 流，解压后 32768 字节。

**zlib 流里是否含有同样的 TLV 结构？** 不是 ——
它是压缩后的 profile 档案（32768 字节固定大小），
有自己的格式（CRC + 233 + 1248641861 魔数）。

所以 `0x13` 只是"不透明容器"，里面可以是任何东西。

### 嵌套的可能性

从结构上说，`0x13` 的数据部分完全可以再放一个 TLV 流 ——
没有任何字节规则阻止它。

但从语料看，**没有一个实例真的这样做**。

**结论**：嵌套在结构上允许，在实测中未使用。

---

## 4. 长度字段与数据的确切关系

对每个变长标签，验证：

```
解析出的数据起始位置 + 长度 = 下一个标签的位置
```

在所有 6848 条样本上成立。

**这意味着：长度字段是精确的字节数，不是元素数、不是字节数的倍数。**

（第 10 卷讨论过 `0x6c` 尾部的 u32 —— 那个不是长度，是独立字段。）

---

## 5. ★ 分层：payload 的结构层级

整个 payload 是一个**两层**结构：

```
层 1: 记录头（已剥离，不在语料里）
        u32 declared | 0x86 | service | 0x03 | task

层 2: payload
        element* 0x00+
        element = tag | value
        value 可能是定长（1/2/4/8 字节）
                  或 变长（NUL 结尾 / 长度前缀）
```

**层 2 内部没有第三层** —— 也就是说，
payload 里的元素是"平铺"的，不会嵌套子结构。

**但有一种例外**：`0x13` 的数据部分可以装任意数据，
包括另一个完整的 TLV 流。只是本语料里没有这样用。

---

## 6. 终止符的分层

`0x00` 只出现在**层 2 的末尾**，不会出现在：
- 定长字段内部（值是普通数据）
- 变长字段内部（`0x13`/`0x6b`/`0x6c` 靠长度界定）
- `0x10` 字符串内部（字符串自己的 NUL 是内容的一部分）

**唯一的歧义**：`0x10` 的空串 `10 00` 会产生一个 0x00，
它与终止符连在一起，看起来像"两个 0x00"。

这是第 1 卷讨论的问题，此处再次确认：
**解析时必须按标签走，看到 `0x10` 就吃掉一个 NUL，
而不是"看到 0x00 就终止"。**

---

## 7. 长度前缀的边界保护

`0x13` 的 u32 长度理论上可以到 4GB。
但语料里最大是 8058（日志串，走 `0x10` 而非 `0x13`），
`0x13` 最大是 764。

**保护规则**：
- 解析 `0x13` 时，若 `长度 > 剩余字节数`，立即判错
- 不要尝试"按长度分配内存"（会有 OOM 风险）

`tools/lobby_grammar_v5.py` 的 `take()` 已经做了边界检查。

---

## 8. 字节覆盖

| 项 | 结论 | 证据强度 |
|---|---|---|
| 变长标签共同骨架 | `标签 + 08 + u32 N + N B` | **强（2111 例全一致）** |
| 长度单位 | 字节 | 强（算术闭合） |
| 中间 `08` | 恒为 0x08 | 强（0 例外） |
| 嵌套 | 结构允许，实测未用 | 中 |
| 层数 | 2 层（记录头 + 平坦 payload） | 强 |

**盲区**：

1. `0x6b`/`0x6c` 尾部那个 u32 属于"层 2 的普通字段"还是
   "数组头的一部分"？—— 结构上说它紧跟在数据后面，
   但在字节层面**属于数组标签管辖范围**（因为如果按 TLV 读，
   它会变成一个未知标签）。
   **这个边界问题目前只在解析器里解决（按数组头处理），没有语义上的证明。**
2. 嵌套未使用 —— 但这只是"没看到"，不是"不可能"。
