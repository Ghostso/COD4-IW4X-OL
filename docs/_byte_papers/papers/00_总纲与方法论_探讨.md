# 第 0 卷 · 探讨：为什么必须做字节级，以及我推翻过的三次判断

> 对应论文：`00_总纲与方法论.md`
> 本篇记录推导过程、被证伪的中间假设、未解决的疑点。

## 一、为什么"能进大厅"不等于"懂了协议"

本项目当前状态：大厅链路能解出 64 条任务，某些路径能进图。
这很容易被误读成"协议已经吃透"。

但实际情况是：服务端代码里到处是
`ob.u64(ROOM_ID); ob.u32(0); ob.u32(18); ...` 这种**照着外部项目抄的字段序**。
它能跑，是因为客户端对某些字段不敏感，不是因为字段被理解了。

这正是要做字节级的原因：
**抄来的字段序能跑通，但一旦某字段是"错了就崩"的闸门，抄错的地方就会
以"莫名其妙卡住"的形式暴露出来，而你没有工具定位它。**

字节级台账的价值在于：当某个行为异常时，你能回答
"这条报文第 37 字节是谁写的、值域是多少、客户端读到它会做什么"。

## 二、被推翻的假设清单（按时间顺序）

记录这些是因为：**不记录证伪过程，下一个人会重复走一遍。**

### 假设 A：`0x03` 是"成组容器"

**怎么想到的**：在 102/7 里看到
`03 01 0a <u32> 03 01 0a <u32> ...` 重复 50 次，
第一反应是"03 后面跟个数，然后跟 N 个元素"，这是很多 TLV 变体的做法。

**怎么证伪的**：写出解析器，在 102/1 的 22 字节样本上跑：

```
08 00 00 00 00  08 01 00 00 00  03 03  0a <u64>  00
```

按"03 是组，03 后面是 count=3"解析，需要 3 个元素，
但 `0a <u64>` 只贡献 1 个，随后就撞上终止符 00 —— **长度对不上**。

改按"03 是 u8，值就是后面那 1 个字节"解析：
`5 + 5 + 2 + 9 + 1 = 22`，**严格相等**。

**结论**：`0x03` = u8，值域实测只有 0/1/2/3。
`03 01 0a ...` 应读作"u8 值 1，然后 u64 字段"，不是"组内 1 个元素"。

**教训**：重复出现的模式最容易让人以为是容器。
判据只有一个——**长度闭环**。看着像不算数。

### 假设 B：`0x0a` 是 f64（双精度浮点）

**怎么想到的**：CODOID `16701785630074219790` 是 20 位十进制，
一看到 8 字节就想到浮点。而且 `11/4` 里 `0a 88 77 66 55 44 33 22 11`
字节序列看起来"很随机"，像浮点尾数。

**怎么证伪的**：把 corpus 里全部 1758 个 `0x0a` 载荷拿出来，
按 u64 / f64 / (u32,u32) 三种解释统计（`tools/lobby_tag_semantics.py`）：

```
作为 f64 : 合理值 262/1758（大量 -8.79e+191、5e-324 这种无意义值）
作为 u64 : 范围 [0, 16701785630074219790]
```

`16701785630074219790` 正是服务端代码里的 `owner` 常量。
而且 `11/4` 里那个"随机"的 8 字节 `88 77 66 55 44 33 22 11`
读作 u64 是 `0x1122334455667788` —— **教科书式的测试常量**。

**结论**：`0x0a` = u64。

**教训**："看起来随机"的 8 字节，先试 0x1122334455667788 这种哨兵值。

### 假设 C：`0x6c` 是"变长字节块"

**怎么想到的**：`6c 08 00 00 00 00 ...` 长得像 `13 08 <len> <data>`，
只是标签不同，所以最初按"6c 是另一种 blob"处理。

**怎么证伪的**：穷举 6 种结构假设，在 28/1 和 28/4 的全部 203 条上跑
（`tools/lobby_6c_hypotheses.py`）：

```
H1: 6c 08 <u32 N> <N B> <u32 M> 00    →  203/203 命中
H2: 6c 08 <u32 N> <N B> 00            →    0/203
H3: 6c <u32 N> <N B> 00               →    0/203
H4: 6c 08 <u32 N> <4N B> 00           →    0/203
H5/H6 各种无尾变体                     →    0/203
```

**结论**：`0x6c` = 数组，尾部那个 u32 M 在全部 203 条里恒等于 N/4，
即**元素个数**（元素宽度 4 字节）。

**教训**：长度字段有两种可能的单位（字节 / 元素）。
必须两个都试，用样本判定，不能"取看起来顺眼的那个"。

## 三、没能完全解决的地方（诚实列出）

### 1. 终止符为什么可以是 1~9 个 `0x00`

实测分布：

```
1 个 0x00 : 1362 条
2 个 0x00 : 2562 条
3 个 0x00 :  359 条
4 个 0x00 : 1071 条
5 个 0x00 :  749 条
8 个 0x00 :  530 条
9 个 0x00 :  215 条
```

**目前解释**：空字符串字段（`10 00`）本身就以 0x00 结尾，
紧跟着真正的终止符 0x00，就变成两个。
连续多个空字符串就叠出更多。

但这个解释**没有完全对上**：9 个连续的 0x00 意味着
连续 8 个空字符串字段，这在哪些报文里出现、为什么，
尚未逐条核对。**列为待办。**

### 2. `0x09`（i64）在语料中零出现

`codol_crypto.py` 的对照表里有 `T_I64 = 0x09`，
但 6848 条样本里一个都没有。可能是：
- 客户端从不在这个方向发 i64
- 或者服务端路径从未走到需要 i64 的报文

**列为待办**：需要覆盖更多客户端操作路径才能验证。

### 3. `0x6b` 与 `0x6c` 为什么是两个标签

两者结构完全相同（`08 + u32 字节长 + 数据 + u32 元素数`）。
实测差异：

- `0x6c` 出现在 28/1、28/4，载荷是递增整数序列（0..511），元素宽 4
- `0x6b` 出现在 21/5，载荷恒为 `01 00 00 00`，count 恒为 4

**当前假说**：两者分别对应不同的数组元素类型
（可能是 int32 数组 vs 某种定长结构数组），
但**没有足够样本证伪或证实**。**列为待办。**

## 四、方法论沉淀

三条可以复用的规则：

1. **长度闭环是唯一判据。**
   任何"看起来对"的字段解释，必须在全部样本上产生精确的边界吻合。
   97% 等于 0%。

2. **证伪优于证实。**
   每提出一个结构假设，同时写下它的否定形式，一起跑。
   只跑正例的人永远发现不了自己在自我确认。

3. **常量是最好的路标。**
   `0x1122334455667788`、`16701785630074219790`、递增的 0..511
   这些"不像真实业务数据"的值，是逆推字段宽度和类型的最强证据。
   一旦在报文里看到它们，立刻反向确认字段解释。
