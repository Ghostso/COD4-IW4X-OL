# 229 探讨 · 找到了第二个调用点，然后发现服务端根本不是那台

## 一、227 卷我说"唯一调用点"，229 卷自己推翻了

227 卷结论：`0x632680` 只有一个调用点（FrameUpdate `0x632FC4`），传 `"mmbook timedout"`。

于是我说"它是 booking 超时检测，`mmbook accepted` 路径无调用点，服务端推它没用"。

**229 卷：从 `[0x82E13FC]`（228 卷枚举的 302 处）里，`+0x13C` 命中 1 处 —— 是另一个调用点。**

`0x7F156F`，在 `0x7F1110` 里。

## 二、这次我学乖了：先读调用者的入口

227 卷的教训是"没读调用者传的参数"。

所以这次我先看 `0x7F1110` 的**入口**：

```asm
0x7F1113  mov ecx, [0x84ABB08]   ; ← 这个全局是什么？
0x7F111D  mov ecx, [0x84ABB14]   ; ← 这个呢？
```

**`[0x84ABB14]` —— 我在 151/152 卷已经定名过：HTTPS/TLS 客户端，域名 `formal-zone-auth.codol.qq.com`。**

⇒ `0x7F1110` **不是大厅 3074 的处理器**，是**腾讯认证服务器的 HTTPS 应答处理器**。

## 三、然后才读参数

```asm
0x7F153F  push 0xDC6724          ; "mmbook"
0x7F1544  call 0xC3C678          ; strcmp(应答串, "mmbook")
0x7F155C  mov eax, [eax+0x13C]   ; 0x632680
0x7F1566  push edx               ; 参3 = edi = 栈上解析出的字符串
0x7F156F  call eax
```

**参3 = HTTPS 应答里解析出来的字符串。**

⇒ 若服务端在 HTTPS 应答里返回 `"mmbook accepted"`，门6 就过。

## 四、结论翻了个个儿

227 卷：**"服务端推 mmbook accepted 没用"**。

229 卷：**"服务端必须推 —— 但推的不是 3074 的 `6/14`，是 HTTPS 的应答"**。

| | 227 卷以为 | 229 卷实际 |
|---|---|---|
| 通道 | 大厅 3074 `6/14` | **HTTPS**（腾讯认证服务器） |
| 服务端 | 我们的 `lobby_server.py` | **腾讯 `formal-zone-auth.codol.qq.com`** |
| 能否本地提供 | 能 | **不能**（除非劫持 HTTPS） |

## 五、这一轮我到底在干什么

回头看这条线（213→216→226→227→229），我**推翻了三次**：

1. 213-216：`0x632680` 是开局闸门 → 服务端补 u64
2. 226：它没有调用点（**扫描器缺陷**）
3. 227：它是超时检测（**只读了一个调用点**）
4. 229：它是通用 booking 处理，成功路径走 HTTPS

**四轮，四次结论，三次自我推翻。**

每次都发现"上一轮的前提没验证"：
- 226：扫描器没验证（disp8/disp32）
- 227：调用者参数没读
- 229：调用者**入口**没读（连它属于哪台服务器都不知道，就在讨论"服务端要怎么改"）

## 六、值得记住的一条

**★★★★★ 讨论"服务端要怎么改"之前，必须先确认"这个服务端是不是我们那台"。**

我前面四轮一直在讨论"改 `lobby_server.py`"，而 229 卷发现这条路径的对方是**腾讯的 HTTPS 服务器**。

**改动方向从头到尾就是错的。**

## 七、现在的真实状态

- `0x632680` = **通用 booking 状态处理器**，两个调用点：
  - FrameUpdate（超时，传 `"mmbook timedout"`）
  - HTTPS 应答（成功，传应答串）
- **booking 应答走 HTTPS ⇒ 本地无法提供**
- 服务端侧（3074）**已无待改项**（至少在 booking 这条线上）

★ 下一步如果还要在"房间开局"上推进，得先解决 **HTTPS 劫持**，而不是继续读二进制。
