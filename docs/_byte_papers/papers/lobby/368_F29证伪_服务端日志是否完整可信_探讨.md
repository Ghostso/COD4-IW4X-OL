# 368 · 探讨：为什么「日志看起来什么都记了」，却漏了一条真实的处理失败

> 编号：368（room64 证伪路 F29）副篇 · 方法论与误判链
> 主篇：`368_F29证伪_服务端日志是否完整可信.md`

---

## 1. 误判链是怎么长出来的

假设「日志是完整可信的」有三层诱因，逐层剥开才知道它在哪里破：

**第一层（观感层）**：`lobby_srv.log` **每一帧**都有 `★ 解密成功 #N seq=… service=… task=…`，
外加 `payload(N): <hex>`，再外加 `-> 0x85 应答 …`。这种「三段式」密度让人觉得
**只要收到就一定有记录、一定有结论**。

**第二层（结构层）**：读源码会看到 `log()` 调用散布在分支里，像 `findSessions`、`mmstart`、
`购买失败` 这些「重要路径」都专门打了一条。于是自然推论：「重要的都记了，没记的是不重要的」。

**第三层（因果层）**：本轮绝大多数请求**确实**有来有回（#1–#58 全部 `-> 0x85 应答`）。
58/59 = 98.3% 的「看起来完备」，足以让人放过那 1 条。

错的地方不在逻辑，而在**计数口径**：读者数的是 `解密成功`（59），真相在 `0x85 应答`（58）。
一个字的差异，把「处理失败」整个藏起来了。

---

## 2. 判定「日志是否完整」只需三个正交问题

| 问题 | 本卷答案 | 证据 |
|---|---|---|
| Q1. 收到的每一帧都在日志里吗？ | **是** | rx 帧 59 ↔ 解密行 59 ↔ tasks.bin 59，差 0 |
| Q2. 每一帧都有处理结果记录吗？ | **否** | 应答行 58；seq=59 只有收包、无结果 |
| Q3. 漏的原因是「分支选不记」还是「异常没记」？ | **异常** | AST 48/48 return 带 note；L1105 NameError |

**Q1 成立、Q2 不成立、Q3 是异常** ⇒ 「日志完整可信」作为一个整体命题**不成立**，
但要对得精确：破在「处理结果」这一层，不在「收包」这一层。

---

## 3. ★ 这条线里最容易踩的三个坑

### 3.1 「有 `解密成功` 行」≠「服务端处理了」

`解密成功` 只证明**解密成功**，它发生在 `reply_objects()` **之前**。
真正的「已处理并已回包」信号是 `-> 0x85 应答 seq=…`。
本卷现场里 seq=59 恰恰是「解密成功之后立刻炸」，于是成了**半条记录**：
前半（收包）在、后半（结果）不在。

> 教训：引用 `lobby_srv.log` 当「服务端处理了 X」的证据时，**必须配 `应答 seq=X` 行**。
> 只有 `解密成功` 的引用是**不充分**的，而且恰好会漏掉崩溃点。

### 3.2 「文件没写错」≠「文件没被截断」

`lobby_srv.log` 最后一行是一个**没有换行结尾的 payload hexdump 片段**，看起来像「日志正常写到这」。
但正常结束会有 `=== 大厅连接结束 … ===`。**缺这一行**就是硬信号：线程不是正常退出，而是中途死亡。
把「文件里最后一行是什么」当成「程序走到最后一行」，是本次差点漏判的关键。

### 3.3 「分支都不静默」≠「不会有静默失败」

脚本 `static_branches.py` 证明 48/48 个 return 都带 note —— 这本来可以让人下结论
「没有分支不打日志，所以日志完整」。但这只排除了**控制流选不记**，排除不了
**控制流根本没走到 return**（异常）。「静态枚举覆盖所有 return」是必要条件，不是充分条件。

---

## 4. 为什么这条缺陷值得单独立卷（而不是当噪声）

1. **它命中房间线**：seq=59 是 `11/4 setRoomData`，room64 的核心房间动作入口（175 卷定位）。
   它没回包 = 一条真实的房间请求在服务端被吞了。
2. **它是「一行删除引入全局崩溃」**：REF 谱系有 `ch, batch, tp = _parse_set_room_data(plain)`，
   实跑 kit 删了它却留下三处消费者 ⇒ **任何** 11/4 请求都会 NameError，不是偶发。
3. **它解释了「日志看起来正常」的错觉**：崩溃点没有 traceback 落盘
   （`run_all.py:452` 启动 lobby_server 时不重定向 stderr），读者无从知道线程已死。

---

## 5. 给后续卷的一条硬规则

> **服务端「处理过 X」的权威判据 = `-> 0x85 应答 seq=X` 行存在且对象/字节数自洽。
> `解密成功 seq=X` 只说明收到了；`payload(X)` 只说明解码了。三者缺一，都不能说「处理了」。**

本卷把这条规则连同三个计数器（rx 帧 = 解密行 = tasks 记录 = 59）固化成可复跑脚本，
后续任何「日志说处理了」的引用都可以先用它验一遍。
