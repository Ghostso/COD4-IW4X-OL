## 二、分桶宽度这件事，值得单开一节

156 卷我用了 **1 MB 桶**，得到：

```
RVA 0x03116000  nz 88.5%
RVA 0x03216000  nz 96.4%
RVA 0x03316000  nz 96.8%
...
```

于是写下「`0x31xxxxx..0x38xxxxx` 96% 非零 ⇒ 32 MB Flash 资源」。

157 卷我换成 **256 KB 桶**，同一段变成：

```
0x03100000  nz=  0.2%
0x03140000  nz=  2.7%
0x03280000  nz=  2.0%
0x03300000  nz= 11.4%
0x03380000  nz= 43.1%
0x035C0000  nz= 95.9%   ← 从这里才开始 96%
```

**同一个物理区域，桶宽从 1 MB 缩到 256 KB，结论从「整段 96%」变成「只有后 1/3 是 96%」。**

### 为什么会差这么多

因为 1 MB 桶是**右端对齐**的：`0x03116000` 这个桶覆盖的是 `0x03116000..0x03216000`，而真正的数据区可能是 `0x03380000` 起。**一个桶里的 96% 会把结论「污染」到相邻桶**，而我没检查桶边界与结构边界是否对齐。

### 教训（升级版）

> **★ 分桶宽度必须小于待测结构的尺度。** 判断「某项是不是资源」，先确认桶边界与内容边界对齐，否则「96%」可能只是桶里有一个 96% 的子段。

这条比我 156 卷写的「先数非零字节」更进一步：**数了，但数错了粒度，等于没数。**

## 三、`0xE57A70`：我把「混淆」当成了「校验」

156 卷看到：

```asm
mov edx,[0xE57A70]
xor edx,[edi-0x50]
shr/shl 循环移位
xor eax,[edi]
rol eax,8
```

我判断：**这是完整性校验**（和 121 卷的 HMAC 类比）。

157 卷我做了两件 156 卷没做的事：

1. **穷举写点** —— `A3`/`89 05`/`C7 05`/ALU-to-mem **全部 0 命中** ⇒ 它从不被写。
2. **看下游** —— 还原出的 `eax` 立刻 `push` 进 `"%d"` / `"|%d"` 格式化。

**一个「校验值」不会被拿去 `%d` 打印。** 只有**被还原的业务字段**才会。

所以它是：**从记录里解出一个混淆的整数字段，打印出来。**

### 完整性 vs 可读性

| 属性 | 完整性校验（如 HMAC） | 字段混淆（本处） |
|---|---|---|
| 目的 | 判断数据有没有被改 | 不让内存扫描读出明文 |
| 失败后果 | 拒绝/断开 | 读出乱码，程序照跑 |
| 有无比较 | **必须** 与预期值比较 | **没有**比较，解出即用 |
| 输出去向 | `if (calc != recv) reject` | `printf("%d", calc)` |

**判据：`xor` 之后有没有 `cmp`。有 `cmp` 才是校验；直接 `push` 进格式化就是解码。**

这条我记下：**看到一串 `xor`/`rol`，先找 `cmp`。没有 `cmp`，就不是校验。**

## 七、方法论（本卷新增六条）

1. **★ 分桶宽度必须小于结构尺度。** 「96%」可能只是桶里有个 96% 的子段。
