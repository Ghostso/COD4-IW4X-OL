# 编码器 v2 接类型号 · 探讨：一个字节的差别，一条消息的生死

> 对应：`lobby/95_编码器v2接类型号.md`

---

## 一、v1 到 v2 只改了一个值，但性质变了

**v1 的 `MemberList` 首二字节：`18 05`**
**v2 的 `MemberList` 首二字节：`18 75`**

**差的这一个字节，是类型号 0 → 14。**

**⇒ v1 输出的是"格式对、类型错"的字节串。
客户端看到它，会当成"类型 0 的消息"（基类），按基类去解析。**

**⇒ 基类只有 13 位（一个 u8），后面 62 位全是垃圾 ⇒ 必然解析失败。**

**⇒ 所以 v1 的东西**发出去一定不会生效**，而这**看不出来**——
字节长度对、tag 对、什么都不报错。**

---

## 二、这就是"能生成"和"能生成对的"的区别

**`lobby/93` 我给 `MemberList` 算 63 位（错的），
`lobby/90` 改成 775 位（对的）。**

**`lobby/93` 我填类型号 0（错的），
`lobby/94` 改成 14（对的）。**

**⇒ 两次都是"数字看着合理，但错了"。**

**⇒ 长度错会立刻显形（客户端读到一半没数据），
类型号错**不会显形**（客户端照基类解析，然后静默失败）。**

**⇒ 后者更危险。**

---

## 三、逐位验证为什么重要

**我没有满足于"字节看起来对"，而是把 `18 75` 拆成位：**

```
0x18 = 00011000
0x75 = 01110100

bits[0:5]  = 00011     = 3   ✓
bits[5:13] = 00001110  = 14  ✓  （00011|000 跨字节）
bits[13:18]= 10101     = 21  ✓  (0x15)
```

**⇒ 三个字段全对，而且它们**跨了字节边界**。**

**⇒ 如果位序是 LSB-first，这 13 位会被拆成完全不同的东西 ⇒ 立刻能看出来。**

**⇒ 所以这一次逐位验证**顺带**确认了位序。**

**这比单独做一次"位序测试"更经济。**

## 四、`P2PInfo` 那段我说了"三种分解"，这是诚实的边界

**67 字节 = 1+2+64 或 3+64 或 2+1+64 —— 我列了三种，但都没定。**

**有人可能会说"你随便挑一个呗"。**

**⇒ 不行。**

**因为 67 不是一个"自然"的数（不是 2 的幂、不是 32 的倍数）。
如果我挑一个分解写进文档，下一个人会当成事实用。**

**⇒ 所以我就停在这里：长度确定、结构未定。**

**⇒ 这是"知道多少说多少"的具体做法。**

## 五、P2PInfo 的发现方式本身就值得记

**它是 `tools/dwall_vtables.py` 枚举 vtable 区时捞出来的。**

**不是从 `dwroom_serializers.py` 里"看"出来的。**

**⇒ 那把脚本按"COL → 指针"去搜，搜漏了一个。
而枚举法（遍历地址区间，读每个 dword，看是不是 COL 指针）不漏。**

**⇒ 两种搜索方式的差别：
- 正向搜索（我知道要找什么，去找）→ 会漏
- 反向枚举（这个区域里有什么）→ 不漏**

**⇒ 以后凡是"这个区域里一共有 N 个 X"这类问题，必须用枚举。**

---

## 六、方法论收获（三条）

> **① 类型号错了不会报错，长度错了才会报错。
> 静默失败的错误最危险。**

> **② 逐位拆解能同时验证多个假设（字段值 + 位序）。**

> **③ "区域里有什么"用枚举；"找某个东西"用搜索。混用会漏。**

## 七、v2 的遗留

**v2 的手抄 spec 有 5 处错（Vote/ChangeTeamRequest/RoomInfo/4 条缺失）。**

**⇒ 这是 `lobby/96` 改用自动生成的原因。**

实际可靠的是 v3 的"45 条，35 条对账"。**

**⇒ 不要拿 v2 的数字当成果。**
