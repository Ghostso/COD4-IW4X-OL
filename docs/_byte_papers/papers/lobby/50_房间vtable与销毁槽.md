> 承接 `lobby/49`

## 1. vtable 在 `0xdc7274`

**从构造函数 `0x62c000` 的 `mov [ebx], 0xdc7274` 得到。**

**实测前 20 项全为有效代码地址：**

```
[ 0] 0x006391e0    [10] 0x0062dfe0
[ 1] 0x0062ca80    [11] 0x0062e410
[ 2] 0x0062d5d0    [12] 0x0062e4e0
[ 3] 0x0062d7e0    [13] 0x0062e0a0
[ 4] 0x0062da10    [14] 0x0062f640
[ 5] 0x0062db50    [15] 0x0062f840
```

**⇒ 房间对象有数十个虚函数。**

## 2. 已确认的两个 slot

| slot | 偏移 | 地址 | 对应命令 |
|---|---|---|---|
| — | `+0x38` | `vtable[14]` = `0x62f640` | **`room.startgame`** |
| — | `+0xC0` | `vtable[48]` = ? | **`room.changemap`** |

**`+0x38 / 4 = 14` ⇒ slot 14。**

**`+0xC0 / 4 = 48` ⇒ slot 48。**

---

## 3. 销毁函数在 slot 155

```
0xdc74e0 − 0xdc7274 = 0x26C
0x26C / 4 = 155
```

**⇒ 析构函数是 `vtable[155]` = `0x63a460`。**

**⇒ vtable 至少有 156 项。**

---

## 4. 销毁函数 `0x63a460` 的形态

**无直接 `call` 引用，只有 1 处 vtable 引用。**

**⇒ 它是"通过虚表调用的析构"，不是"被代码直接调用的清理"。**

**⇒ 只有当某个地方调用 `obj->vtable[155]()` 时，
房间对象才会被销毁。**

---

## 5. 对"对象为 0"的最终判断

**两条路径：**

### 路径 A：从未创建

```
0x7e98f0 没被调用  →  0x639d00 没执行  →  0x82e13fc = 0
```

### 路径 B：创建后被析构

```
0x7e9933 → 创建
某处调 vtable[155] → 0x63a460 → 0x82e13fc = 0
```

**从证据看：**

- `0x63a460` 只通过虚表调用，没有任何直接调用点
- **⇒ 要触发它，必须先有对象**（才能读到 vtable）
- **⇒ 如果对象从一开始是 0，路径 B 不可能发生**

**⇒ 结论偏向路径 A：`0x7e98f0` 没被调用，或 `0x639d00` 内部失败。**

---

## 6. 再回到 `0xc3e9f5`

**上一卷确认它是 CRT 锁函数，几乎总是成功。**

**⇒ `0x639d00` 内部失败的可能性很低。**

**⇒ 最可能是 `0x7e98f0` 整段没被调用。**

---

## 7. 最终待验证项

| 项 | 方法 |
|---|---|
| `0x7e98f0` 是否被调用 | 查 `0x808658` 是否可达 |
| `0x808658` 在哪个函数 | 反汇编 |
| 该函数是否在启动路径 | 查它的调用者 |

**这是整条链的最后一环。**

---

## 8. 本轮（40–49）总结

**十卷把房间逆向从报文推到 vtable。**

| 层 | 落点 |
|---|---|
| 报文 | `11/13` `11/4` `11/2` `6/5` `6/14` |
| 命令 | 25 个，已提取 4 个 handler |
