# 服务 80 与 102 · 探讨：把「未解」写成可核验的任务，而不是一句「需要抓包」

> 对应：`lobby/222_服务80与102_证据链与边界.md`

---

## 一、这一卷真正想做的事

**不是再多知道几个地址，而是：**

> **把所有「未解」从「主题词」翻译成「地址/字节范围级的可核验任务」。**

**AGENTS.md 明令：**

> **「需运行时 / 无样本」不得作停手理由；每项须是可独立核验任务；推进靠依赖图 + 严格验证。**

**所以我逼自己给每条边界写三样东西：**
1. **具体是什么没解（地址级）；**
2. **我做了哪些机械扫描（穷尽了什么）；**
3. **排除了什么可能。**

## 二、一个反例：如果我只写「发送点未找到」

**这会是不合格的边界——它说得太软，无法核验，也给不出下一步。**

**我实际写的是：**

```
边界 1：102/1·102/7 的发送点未定位
  已做：扫全部 E8→写器(0xB766B0/0xB76620) 调用点；
        按 push imm 值(0x32/0x3e8/1/2) 筛；
        扫静态表 0xC1B7xxx。
  排除：不是「常量立即数」形式（值来自内存，所以 push 常量筛全空）。
  结论：静态不可达（构造点未定位）。
```

**⇒ 这样别人能**照着复现**，也能接着往下走（下一步该扫「内存来源」而不是常量）。**

## 三、差点翻车：把「巧合同值」写成「因果」

**`102/7` 的首字段 `08 32`（=50），而读器 `0xB76220` 里有一句 `cmp [ebp-0x14], 0x32`。**

**两者都是 0x32 = 50。太诱人了。**

**第一反应：「看，读器就是为 102/7 写的！」**

**但我去找两者的**调用边**：`0xB76220` 是被 `0xB76310`（读 tag 0x16 的分支）调的，而 `102/7` 的报文首字节是 `08`（tag 8），**根本不进 tag 0x16 分支**。**

**⇒ 没有调用边。同值 = **候选巧合**。**

**我把它写成边界 3：「候选巧合，未证实」。**

**★ 教训：两个数相等，只是「可能相关」；要成立因果，**必须有调用边/数据流边**。这和 220 卷「值域已知 ≠ 语义已定」是一体两面。**

## 四、边界 4 的自我加压

**任务里有人提过「102/1 的 82 字节对象」。**

**我全库扫了两种可能的「82」写法：**

```
6A 52 E8            (push 0x52 + call)      → 0 命中
push 0x52 → 0xB74220 (alloc 82)              → 0 命中
```

**⇒ 本镜像里**没有**任何「分配 82 字节」的点。**

**我没有含糊过去，而是写：「疑为内存态而非线形态，本镜像无对应分配点」。**

**★ 「查不到」+「我把查法写出来」 > 「查不到」+「大概是内存态吧」。**

## 五、证据总账的意义

**220/221/222 三卷，我刻意让 222 只做「索引 + 边界」，不复述。**

**因为项目已经踩过「一个假数字生出一窝假结论」的坑（134 卷自批）。**

**账本的每条都标：**
- **地址；**
- **权威层级（本地逆向 = 最高）；**
- **验证方式（vtable 槽 / E8 调用边 / 字节常量 / RTTI 字符串）。**

**⇒ 任何人可从账本任取一条，独立复核。**

## 六、方法论价值

> **① 边界要写成「地址/字节范围 + 已穷尽扫描 + 排除项」，不能写成主题。**
> **② 两值相等只是「可能相关」；成立因果必须有调用边/数据流边。**
> **③ 「查不到」必须连「查法」一起写出来，否则等于没查。**
> **④ 证据总账只做索引与边界，不复述结论——避免复述中悄悄放大误差。**
