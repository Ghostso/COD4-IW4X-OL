# ★★★★★ 死结的解法：`0x808650` 有一条独立入口

> **`lobby/78` 的死结被解除**
> 证据：`0x808650` 的调用者是 `0x4fd287`，不经过 `0x808261`

---

## 1. 两条通往 `0x7e98f0` 的路

```
路 A（受闸门约束）：
  0x808240
    → 0x808261  cmp [0x849ba30], 3
    → 0x808268  jne 0x80852c（返回）
    → 0x808650
    → 0x7e98f0

路 B（独立）：
  0x4fd287
    → 0x808650          ★ 直接调用，无闸门
    → 0x7e98f0
```

**⇒ 路 B 绕过了 `[0x849ba30]==3`。**

**⇒ 死结不成立。**

---

## 2. 路 B 的上下文

**`0x4fd287` 紧邻 `0x4f8ad0`——那是主循环里的帧更新。**

**⇒ 路 B 大概率在"初始化阶段"被调用一次，
而路 A 在"每帧"被调用。**

**⇒ 首次初始化走 B，之后每帧走 A。**

---

## 3. 完整启动模型（修正版）

```
启动
  ↓
0x4fd287 → 0x808650 → 0x7e98f0     ★ 首次初始化（无条件）
                       ├─ 0x6212c0(1) → [0xe59d20] = 5
                       └─ 0x639d00    → [0x82e13fc] 房间对象 ★ 创建
  ↓
此后每帧
  ↓
0x808240 → 0x808261（需要 [0x849ba30]==3）
            → 0x808650 → 0x7e98f0
```

**⇒ 房间对象在**首次初始化**时就已经创建了。**

**⇒ `[0x849ba30]==3` 只影响**后续每帧**的重复初始化。**

---

## 4. 这与实测矛盾吗

**实测 `[0x82e13fc] = 0`。**

**如果启动时无条件创建了房间对象，它应该是非 0。**

**⇒ 两种可能：**

### A. `0x4fd287` 也没被调用

**`0x4fd287` 所在函数可能也在某个条件里。**

### B. 房间对象创建后又被销毁

**`lobby/50` 提到 `vtable[155]` 是析构，但需要对象存在。**

**⇒ 如果创建后又销毁，说明有清理路径。**

### C. 这份 dump 抓得太早

**`0x4fd287` 还没执行。**

**⇒ 与 `memory: codol-memdump-timing-critical`（t+23.8s 成功）吻合。**

---

## 5. C 最可能

**`client_runtime.bin` 是在某个时间点抓的。**

**如果抓的时候还没到 `0x4fd287` 那一步，
所有状态都是初始值。**

**⇒ 那这份 dump 无法证明"运行时也起不来"。**

**⇒ 必须用**更晚**的 dump 验证。**

---

## 6. 这一轮的净结论

**确认了三件事：**

1. **`[0x849ba30]` 只有 1 个写入点（同步点）**
2. **`0x7e98f0` 有两条入口：受闸门约束的（`0x808240`）和无条件的（`0x4fd287`）**
3. **`enable_iips` 是 `iips.ini` 的键，当前已是 1**

**⇒ 死结解除，但"房间对象为什么是 0"仍未定。**

**⇒ 最可能是"dump 抓得太早"。**

---

2. 确认 `client_runtime.bin` 的抓取时间点
3. 用更晚的 dump 验证 `[0x82e13fc]` 是否非 0

**如果更晚的 dump 里它仍为 0，那才是真问题。**
