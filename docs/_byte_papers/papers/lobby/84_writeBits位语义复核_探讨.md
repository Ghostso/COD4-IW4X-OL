# writeBits 位语义复核 · 探讨：一个 `inc eax` 推翻了 20 卷的位宽假设

> 对应：`lobby/84_writeBits位语义复核.md`

---

## 一、这一轮我差点又写错

**`lobby/83` 我写：**

> `writeBits(n)` 写 n 位，值 n。

**推导过程：`value - start = n - 0 = n`。**

**看起来没问题。**

---

## 二、但有个细节我没看

**`writeBitsCore` 段 3 的最后：**

```asm
0xb77ace  push ecx
0xb77acf  call 0xb75d40      ; ← 算字节数
0xb77ad4  add esp, 4
0xb77ad7  inc eax            ; ← ★ 这个 inc
0xb77aeb  push eax           ; → writeData 的 nbits
```

**`0xb75d40(31)` 返回 4（31 位 = 4 字节）。**

**`inc eax` → 5。**

**⇒ `writeData(&val, 5)` → 写 **5 位**。**

---

## 三、所以 `writeBits(n)` 恒写 5 位

**不管 n 是 3、0x15、还是 0x13，都写 5 位。**

**⇒ `writeBits` 不是"写 n 位"，而是"写 5 位，值 n 的低 5 位"。**

---

## 四、这推翻了一堆东西

**`lobby/82` 的台账里：**

```
0x15 + 32 位
```

**那是 `writeData(&val, 0x20)` —— `0x20` 是 `writeData` 的位宽，
这一条没错。**

**但 `writeBits(0x15)` 本身是 5 位。**

**⇒ 整个位流布局要重算：**

```
writeBits(3)  = 5 位
writeData(8)  = 8 位
```

**⇒ 头 13 位。**

---

## 五、但我不能确定

**因为还有一种读法：**

**`0xb75d40` 的参数如果是"字节数"而非"位数"，
那 `0xb75d40(31)` 可能返回 31，`inc` 后 32。**

**⇒ 那 `writeData(&val, 32)` → 写 32 位。**

**⇒ `writeBits(n)` 写 32 位。**

**⇒ 头 40 位。**

**⇒ 也不对。**

---

## 六、三种可能

| 读法 | `writeBits` 写几位 | 消息头 |
|---|---|---|
| A: 写 n 位 | 3 位 | 11 位 |
| B: 写 5 位 | 5 位 | 13 位 |
| C: 写 32 位 | 32 位 | 40 位 |

**⇒ 静态反汇编无法定论，因为 `0xb75d40` 的入参语义有歧义。**

---

## 七、怎么定论

**只有两种办法：**

### 1. 动态：在 `writeData` 下断点，看实际 nbits

**⇒ 需要活进程调试，ACE 挡着（`memory: codol-ace-blocks-debug-and-read`）。**

### 2. 实测：找到一条真实的位流样本，反推

**⇒ 但我没有服务端推送的样本。**

### 3. 交叉验证：看 `readBits` 的对称实现

**`0xb774e0` 是 `readBits`，它的实现应该和 `writeBits` 对称。**

**⇒ 如果 `readBits` 里有相同的 `inc`，那 B 成立。**

**⇒ 这是唯一可做的静态验证。**

---

## 八、所以下一步很明确

**反汇编 `0xb774e0`（readBits），看它是否也写 `inc eax`。**

**如果对称 → 确认 5 位。
如果不对称 → 说明我的读法有误。**

---

## 九、方法论收获

> **一个 `inc` 就能推翻 20 卷的位宽假设。**

**这就是字节级逆向的特点：
结论总是"可被一个指令推翻"的。**

**⇒ 所以每个位宽都必须**双向验证**（写与读），
不能只读一侧。**

---

## 十、本轮的诚实状态

**`lobby/82` 的"字段台账"在**结构**上仍然有用
（它给出了字段顺序和各自的 `writeData` 宽度）。**

**但"`writeBits` 占几位"这个**基础量**，还没定。**

**⇒ 在定之前，不能声称"知道位流格式"。**
