# 循环依赖解开 · 探讨：一个变量，两条路

> 对应：`lobby/76_循环依赖解开.md`

---

## 一、上一卷的困境

`lobby/75` 我发现一个循环：

```
[0x849ba30]==3 → 0x7e98f0 → [0xe59d20]=5
                              ↓
                      [0xe59d20] ∉ {4,6}
                              ↓
                      [0x849ba30] 到不了 3
```

**死锁。**

---

## 二、怎么解的

**我没有继续推理，而是把 `[0xe59d20]` 的**所有写入点**列出来。**

**结果：6 处。**

**其中 4 处我之前已经知道（0、6、4、3/5）。**

**剩下 2 处是变量写入：**

```
0x6217dd  mov [0xe59d20], eax
0x621ac0  mov [0xe59d20], edi
```

**⇒ 这两条路我漏了。**

---

## 三、`0x621ac0` 的发现

```
0x621ac0  mov [0xe59d20], edi
0x621ac6  call 0x6212c0
```

**它先写，再调。而且它在 `0x621810` 里。**

**`0x621810` 的唯一调用者是 `0x7eebc1`，也就是 `0x7eebc0`。**

**而 `0x7eebc0` 是状态机每帧调用的函数。**

**⇒ 这是一条**常规**路径，不是"启动时的一次性设置"。**

---

## 四、这意味着什么

**`[0xe59d20]` 不是一个"只在初始化时写一次"的变量。**

**它是**每帧都可能被更新**的界面状态。**

**⇒ 状态机在运行时不停地把它推到 3/5/4/6。**

**⇒ 我之前的"12 层链"模型太静态了。**

---

## 五、修正后的模型

**不是"一次性走完 12 层"，而是：**

```
每一帧：
  状态机 0x7ef1xx 跑
    → 0x7eebc0 → 0x621810 → [0xe59d20] = edi（界面状态）
    → 0x6212c0(bool) → [0xe59d20] = 3/5
    → 下一帧 0x62186b: 3→4（大厅）或 5→6（游戏）
```

**⇒ 这是一个持续运行的状态机，不是"启动序列"。**

---

## 六、这个修正很重要

**因为它改变了"怎么修复"的判断：**

**如果是一次性序列 → 某个条件没满足，卡住。**
**如果是每帧状态机 → 它可能一直在跑，只是某个输入是 0。**

**⇒ 后者更符合"6 秒后崩溃"的描述：
它跑了 6 秒，一直没拿到正确输入，然后超时。**

---

## 七、方法论收获

> **一个变量有多个写入点时，不要只看到一个就下结论。**

**我最初只扫了 `mov [mem], imm` 和 `mov [mem], reg` 的一部分，
漏了 `0x621ac0`。**

**⇒ 这次我把所有 83 处引用按"前一字节"分类，
才发现完整的 6 个写入点。**

**⇒ "穷举"比"找到第一个"可靠。**

---

## 八、下一步

**反汇编 `0x621810`，看 `edi` 从哪来。**

**那是"界面状态"的真正来源 —— 
可能来自 UI 系统、服务器，或者本地配置。**

**这一条确定后，就能回答"为什么它是 0"。**
