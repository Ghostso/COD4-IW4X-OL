# 170 · 探讨：51 卷未解的东西，是「固定前缀」四个字害的

> 配套论文：`170_房间类最后阻塞项闭合_0x13第二层长度分帧.md`

---

## 一、119 卷那句话

> 「`V=04/06/08` 的数据体几乎全部以**同一个固定前缀**开头：`68 ab 5b ab 63 ab 03 ...`
> 这个前缀与 `V=0x02` 的部分数据体是同一组字节 ⇒ `04/06/08` 不是"另一种头部"，而是"`02` 族数据体里再嵌了一层"。」

**「固定前缀」这四个字，是这 51 卷卡住的直接原因。**

因为它把这三个 u16 当成**魔数**了。既然是魔数，那就只能"记住它"，不可能"解释它"。

---

## 二、真相

```
68 ab 5b ab 63 ab 03
│  │     │     │
│  └─────┴─────┴── ab5b=43867, ab63=43875（差 8）—— 是**两个长度**
└── 0x68 = 104 —— 是**第三个长度**（或段数）
```

而实际结构是（`0xB76220`）：

```asm
call 0xB761E0 → len1     ; 8 位
call 0xB761E0 → len2     ; 8 位
call 0xB761E0 → len3     ; 8 位
call 0xB74220(len3)      ; 分配
call 0xB74220(len2)      ; 分配
```

**⇒ 那不是"前缀"，那是「三段长度」的头。**

**「固定」是因为样本里这三段的长度恰好稳定，不是因为它是常量。**

---

## 三、为什么这次能找到

因为换了问法。

| 旧 | 新 |
|---|---|
| 「`V=04/06/08` 的序列化格式是什么？」 | 「**谁在读 `0x13` blob？**」 |
| 没有独立样本 → 无解 | `0x6371F0` → `0xB76AF0` → `0xB76310` → `cmp ecx,0x16` → `0xB76220` |

**一条调用链，四个函数，20 分钟。**

而 119 卷当时手里**有全部样本**（195 条 room 族记录），就是没往"谁读它"这个方向走。

---

## 四、一条更硬的判据

**`0xB76354 cmp ecx, 0x16`** —— 这一条指令把 `0x13` blob 分成了两路：
- `sub == 0x16` → 三段长度分帧（就是"第二层"）
- `sub != 0x16` → 普通读取

**⇒ 「第三套序列化」不是第三套，是 `0x13` 的**一个子类型分支**。**

`0x16` = 22。而 45/5 卷记录过：**P2PInfo 类型号 = 19 (`0x13`)**。
**⇒ `0x13` 是 P2PInfo 的 tag，`0x16`(22) 是它的子类型 —— 一条消息里套了另一条。**

**这就解释了为什么按 `dwRoomMessage` 位流去解会"撞非法 tag"**：因为外层是 `0x13`(P2PInfo)，内层才是 `0x16` 的分帧，中间还夹着长度头。

**0 项。**

全库只剩 4 条命中 —— 3 条是已闭合的陈述，**第 4 条就是本卷这条**。

## 六、方法论（本卷新增三条）

1. **★★★ 「固定前缀」要立刻怀疑是「变长字段的稳定取值」。** 一旦写成"魔数"，就永远解释不了它。
2. **★★ 「没有样本」→「谁读它」。** 这条已经救了我三次（6/5、vt[0x58]、现在这个）。
3. **★ 调用序列能反推结构。** 读 3 次长度 → 分配 2 次缓冲 ⇒ 第三段是元数据、前两段是负载。
4. **★ 「另一套序列化」往往是「一个子类型分支」。** `cmp ecx,0x16` 一条指令而已。
