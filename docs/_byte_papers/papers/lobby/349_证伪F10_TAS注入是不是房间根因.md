| 断言 | 判定 | 一句话证据 |
|---|---|---|

## §1 TAS 注入原本做什么（`nt10.py:384-506 / 2133-2159`）

`build_tas_image()` 生成一块名为 **`TCLS_SHAREDMEMEMORY<pid>`** 的共享内存镜像，格式 = `魔数0x40 + table[key-1]=偏移 + (len,value)`；消费方是 TenProxy 的 **`CTclsProxy`** 对象。

**镜像里的东西（全部是"登录票据"）：**

| tag | 内容 | 消费点 |
|---|---|---|
| 服务器条目 `(seq<<16)\|tag` | `2=名称 / 4=host / 3=端口DWORD / 5,6,7,8` | TenProxy `vtable[0x34]=0x13ED` 读 tag2/4，`vtable[0x38]=0x1226` 读 tag3/5/6/7 |
| 全局 `tag 4` | `LoginKey 128B` | `CTclsProxy 0x6310-0x6680` 段 |
| 全局 `tag 22/24` | 16B/128B 票据 | exe `0x641600` 段 |
| 全局 `tag 25` | `OpenID "10001"`（16B） | 格式串 `0xDC7104 = "OpenID LoginKey: %s"` |
| 嵌套 `key20 / E1` | tag5/7/8 的 `(len,value)` | TenProxy `vtable[12]=0x8250` / `vtable[14]=0x8510`（嵌套结构，**不是** `(seq<<16)\|tag`） |

**实测 TenProxy 确实在消费它**（`tp_runtime.bin`，基址 `0x12800000` 反推自 `chain.txt`）：
```
RVA 0x6176  push 0x12820f70        ; string = L"TCLS_SHAREDMEMEMORY"   (tp_strings.py 实测)
RVA 0x619B  call 0x12801393        ; sprintf "%s+%d" -> L"TCLS_SHAREDMEMEMORY<pids>"  (0x20F00 实测)
RVA 0x61DB  push 0
RVA 0x61DD  push 0xF001F
RVA 0x61E2  call [0x12826398]      ; = OpenFileMappingW
RVA 0x61EB  mov  [ecx+0x18D4], eax ; 保存映射句柄
RVA 0x61F4  cmp  dword [edx+0x18D4], 0
RVA 0x61FB  jne  ok    ;  ==0 -> RVA 0x61FD 走错误日志 "[CTclsProxy::Initialize] OpenFileMapping TCLS_SHAREDMEMORY+%d fail!Error code = %d"
```
`chain.txt` 也记录到了这次调用：`#0 参数='TCLS_SHA' 调用者 TenProxy.dll+0x61E8`（hook 只截到前 8 字节）。

**★ 一个已知风险（与本卷结论无关但值得记）：** `nt10.py:2151` 建的是
`"TCLS_SHAREDMEMEMORY%d" % pid`（**数字 pid**），而 TenProxy 的格式是 `TCLS_SHAREDMEMEMORY` **+ 十六进制**（`%d` 后接什么分隔由 `0x20F00` 处的格式串决定，实测为 `...EMORY<pids>`）。两者只在 pid 为纯十进制且恰好匹配时才重合。**即使启用 `--tas`，若名字不精确一致，`CTclsProxy` 仍会 OpenFileMapping 失败。**

### 3.1 补丁 5 的真实语义（本轮新解）

```
原: 0x62FE80  80 B9 14 06 01 00 00   cmp byte [ecx+0x10614], 0
    0x62FE87  0F 95 C0               setne al
    0x62FE8A  C3                     ret                       ; = (obj->+0x10614 != 0)
改: 0x62FE80  B0 01 C3               mov al,1; ret              ; 恒 true
```
vtable 槽位（本轮新解，纠正我第一版的误读）：
- `0xDC7270` 存 COL 指针 `0xDF96D8`；`0xDF96D8+12` 的类型描述符 = `0xE6F8C4`，其 `+8` 是名字 **`.?AVdwRoomImp@@`**
- 因此主 vtable 起点 = `0xDC7274`，slot0 = 析构 `0x6391E0`（`push esi; call 0x637c00` 后 `test [ebp+8],1` 决定是否 `call 0xC3E8D0` 释放）
- `0x62FE80` = **(0xDC72D8 − 0xDC7274)/4 = 第 25 槽**

★ 教训复现：`0xDC72D8` 之前一个 dword 是函数 `0x62FDE0`，若按"vtable[-1]=COL"的习惯读会得到"slot 0"，本卷第一版就栽在这里。**索引必须从真正的 COL 位置算。**

`+0x10614` 的**全部写点**（镜像里 `0F95C1 / 88...14060100` 共 2 处，再加补丁本身）：
```
0x62CB0C  call 0x637ab0
0x62CB11  mov eax, [0x8269818]        ; = dvar "3291" 对象
0x62CB16  cmp dword [eax+0xc], 0      ; dvar 当前整数值
0x62CB20  setne cl
0x62CB23  mov [ebx+0x10614], cl       ; == (dvar_3291 != 0)

0x6300CB  mov eax, [0x8269818]
0x6300D0  cmp dword [eax+0xc], 0
0x6300DA  setne cl
0x6300E0  mov [edi+0x10614], cl       ; 同式
```

`0x8269818` 的**唯一写点** `0x80884F`。这里有一个极易读错的"store 在 call 之前"布局：
```
0x808825  push 0xdae091        ; 描述串(空)
0x80882A  push 0x2000          ; flags
0x80882F  push ebx             ; 默认值 = 0
0x808830  push 0xde6954        ; 名字 "3291"
0x808835  mov  [0x826982c], eax ; <- 这是**上一次** call(0x80881D, 名字 "1756") 的返回值
0x80883A  call 0x770890        ; <- 注册 "3291"，返回值在本条之后才落盘
0x80883F..0x80884A  push 0xde695c "1758"
0x80884F  mov  [0x8269818], eax ; <- eax = **0x80883A 的返回值** = dvar "3291" 对象
0x808854  call 0x770890        ; 注册 "1758" -> 落到 [0x8269788]
0x808860  push 0xde6964 "xblive_privatematch"  -> 落到 [0x8269848]
```
`read_dvar_name.py` 实测相邻字符串：`3291 / 1758 / xblive_privatematch / 3292 / splitscreen`。

⇒ **补丁 5 = 把 dvar `"3291"`（flags `0x2000`，boot 时默认值 0）门强行置 1。**
这与 `codol-iips-must-be-enabled` 记忆里"`0x63C5E0` 闸门B = (dvar `3291` != 0)，3291 是 GSC dvar，全镜像无写点"**完全吻合** —— 正因为 `3291` 没人写、恒为 0，才需要补丁 5。
它与 TAS **没有任何数据依赖**：`3291` 是本地 dvar，不由共享内存提供。

### 3.2 补丁 1–4 的边界

它们只改 `0xB9A7..0xBA3C`（认证/LSG 区）。**与 TAS 共享内存无关**：TAS 的消费点是 TenProxy `0x1280xxxx`（DLL）和 exe `0x641xxx`（登录读取段），两者都不在补丁地址区间内。

## §4 TAS 对象在跳过注入时的真实状态（`chain_obj.bin`）

`chain_obj.bin` = `[0x82E1580]` 指向的 `CTclsProxy` 对象前 `0x1900` 字节（`nt10.py:3047-3055`，写于 15:17:16）。

| 偏移 | 值 | 含义 |
|---|---|---|
| `+0x00` | `0x128205D0` | vtable 有效（TenProxy 运行时构建） |
| `+0x04/+0x08` | `0x128205A0 / 0x1282059C` | 成员指针 |
| `+0x18C0` | `0` | — |
| `+0x18C4` | `0` | TAS 记录基址（未设置） |
| `+0x18C8` | `0` | TAS table 指针（未设置） |
| **`+0x18D4`** | **`0`** | **`OpenFileMappingW` 返回的映射句柄 = NULL** |

`+0x18D4 = 0` 与 `tp_runtime.bin:0x61EB` 的 `mov [ecx+0x18D4], eax` 完全对应 ⇒ **TAS 镜像从未被映射，因为 `tas_off.flag` 让 nt10 不建这个命名共享内存。**

★ **这证明的是"TAS 没生效"，不是"TAS 生效后能修好房间"。** 两者不能混为一谈：
若启用 TAS，副作用是 `auth_task` 从 10 变 32、走 DSA 签名路径，`run_all.py:682` 明确记载会**卡住**；且 §1 的名字格式不一致会让映射仍然失败。

**对象只有 15/1600 个 DWORD 非零** ⇒ 它是"构造完成、票据未注入"的空壳，但这不影响后续任何房间调用（见 §5）。

## §5 房间代码是否依赖 TAS → 不依赖（分母明确）

对 `0x82E1580`（CTclsProxy 全局）在镜像里做全量绝对地址扫描：

| 区间 | 引用数 | 说明 |
|---|---|---|
| **房间区间 `0x62C000–0x640000`** | **0** | 房间虚拟表 `0xDC73B0`、`0x632680`、`0x6398A0` 等全部在此区间 |
| 全局总数 | 22 | `0x64162A..0x641C11`（exe 登录读取段，14 处）、`0x754CAB..0x754CE1`（`0x754CA0` 析构/清理）、`0x77EEAD`（启动期一次性） |

对照：`0x82E13FC`（AS 单例，房间/UI 注册链的宿主）在**同一区间被引用 120 次**（全局 302 次）。
⇒ **不是"扫不到"，而是"房间代码根本不碰 TAS 对象"。**

`0x641xxx` 的 14 处引用就是 §1 里"登录信息收集段"（`chain.txt:60` dump 的 `chain_exe_login.bin` = `0x00641300`，2304 字节）。它们是**认证期**，不是房间期。

## §7 仍开 / 未证

1. **TAS 名字格式**（§1 ★）：`nt10.py:2151` 用 `%d` 拼 pid，TenProxy 用 `%s+%d`（实测格式串在 `0x20F00`）。**启用 `--tas` 很可能仍失败**，需要一次专门的运行期验证（本轮 `tas_off.flag` 存在，无法观察）。
2. **`xblive_privatematch` dvar 的真值**：本轮补丁 5 已把它绕过，无法区分"原本为 0/1"。要判断补丁 5 是否必要，需在**不打卡 5** 的一轮里读 `chain_obj` 同源对象（或在 `0x62CB16` 下断点）。
3. **房间仍不可用的真正原因**：本卷只证伪"TAS 被跳过"这一条；`21/12` 空应答（`lobby_srv.log:247`）、`leader=0` 等仍开（由其他 F 路负责）。
4. **`0x82E1580` 在 `0x77EEAD` 的启动期读写**：本卷未逐条展开（只确认它是一次性初始化，不在房间路径）。
