# 236 探讨 · 从"发送面"倒推，比从"服务面"正推容易十倍

> 配套：`236_97通道128发送函数_大厅服务面索引.md`

---

## 一、232–235 卷我一直在"正推"，很费劲

- 232：找 service id → 从 `0xB78C10` 的 `push` 立即数反推
- 233：找第二个构造器 → 从 `80/70` 已知样本反查
- 234：找宿主工厂 → 靠 SEH cookie 指纹
- 235：找响应判据 → 扫 `cmp byte [reg+5],0`

**每一步都要先猜对"目标长什么样"。** 猜错就得重来（233 卷猜错了一次，234 卷范围断言错了一次）。

## 二、这一卷换了个方向：找"所有出网的必经之路"

**不管服务号怎么编号、task 怎么分布、构造器有几个模板 —— 任何消息要发出去，都必须经过出口漏斗。**

出口漏斗就 4 个函数：`0x7FA800` / `0x7FAB70` / `0x7FABE0` / `0x7FAA20`。

抓它们的调用点：**136 个**。
按函数分组：**128 个函数**。
按通道号分组：**97 个通道**。

**一次扫描，整个大厅的发送面就出来了。**

---

## 三、为什么这个方向"容易十倍"

| 方向 | 需要先猜对什么 | 失败代价 |
|---|---|---|
| 正推（服务号 → 构造器） | 构造器的签名/位置/参数约定 | 猜错就 0 结果（233 卷猜错 190KB） |
| **倒推（漏斗 → 所有发送点）** | **只要知道漏斗地址**（已知） | **不可能失败，漏斗调用点是机械可数的** |

★ **倒推不依赖任何假设。** 漏斗地址是既定事实（154 卷已定），`call` 指令是机械可搜的。

## 四、但这份索引有一个我没验的地方

**通道号是从「漏斗 call 前最后一个 `push imm8`」取得的。**

```python
def chan_before(x):
    # 在 call 前 0x40 内找 push imm8 或 mov eax,imm8
    ...
    if v is not None and 0x01 <= v <= 0xFF:
        ch = v     # ← 取最后一个
```

**这个启发式会出错**，比如：

```asm
push 0x400      ; 缓冲大小
push 7          ; 某个字段值
push 0x800420?  ; 真实通道
call 0x7FA800
```

如果真实通道是通过 `mov eax, imm` 传的，而中间又有别的 `push imm8`，我就会取错。

**已知的对照点**（`0x59`=89 / `0x5A`=90 / `0x5D`=93 / `0x6B`=107 / `0x16`=22 / `0x3A`=58）**全部正确**，说明启发式在这 6 个上是准的。但 **97 个里只验了 6 个。**

★ **这和 234 卷"验了 1/24 就说 24 个同构"是同一个毛病。** 我必须明确标注：**这张表 97 行里只有 6 行经过对照验证，其余 91 行是启发式输出。**

## 五、通道号 vs 服务号：一次真实的险情

234 卷我看到 `0x7FF57F push 0x3A` 就写「这是 svc 58」。

236 卷的通道表显示：**`0x3A` 是通道号，`0x7FF500` 这个函数确实属于 Clan，但依据是「它的函数体里有 `svc 58` 的 `0xBA72C0` 构造点」，不是 `push 0x3A`。**

**两个不同的东西数值相同，我差点用错的理由得出对的结论。**

★ **结论对 ≠ 推理对。** 这是本项目反复出现的模式（记忆里 `codol-room-two-ready-judgements-wrong-161`：「读了两边 ≠ 两边对得上」）。

## 六、这份索引的真正价值

不是"知道有 97 个通道"这个数字，而是：

**它给了「逐 svc 定响应判据」一个可行的遍历顺序。**

235 卷我说下一步是「逐 svc 找 `reply+N`」，但不知道从哪开始。现在有了：

```
对每个通道函数（128 个）：
  ① 反汇编，找它注册的 reply 回调（push <cb> 在漏斗前）
  ② 在回调查 cmp byte [reply+N], 0
  ③ 记录 N、极性、后果分支
```

**这是一个有限、可枚举、可验证的任务。** 不再是"逐 svc 找"这种无边界表述。
