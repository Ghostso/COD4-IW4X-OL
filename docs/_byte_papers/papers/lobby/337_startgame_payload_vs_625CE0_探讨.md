# 337 探讨 — 为什么"逐段全对"仍可能开不了局

## 0. 一句话

`build_startgame_payload` 与客户端 `0x625CE0` **逐段 100% 对上**（含 1 位头），
所以若开局失败，锅**不在这 109 字节里**。本文讨论它上面的两层、以及"全对但无效"的几种可能。

## 1. 对账为什么能这么干净

关键在于找到了**读侧的 ctor**（`0xB779A0`），而不是只看 `0x625CE0` 本体：

- `0x625CE0` 自己只从 `readTag(3)` 开始，看起来"没有头"。
- 但 ctor 里 `0xB77A2F call 0xB772E0` 的参数是 `push 1` + `push edi`（`edi=[esi+0x21]`），
  即构造时就**吃掉 1 位**写入 `+0x21`，并把 `+0x21` 当 useDataTypes 开关。
- 服务端 `BitWriter.__init__` 恰好写这一位。⇒ 两边都在"tag 之前"处理同一 1 位。

★ 方法论教训：**只读反序列化函数本体 = 必然误判"头哪来的"**。要连同 ctor/调用者一起读。

## 2. 一个看似矛盾、其实不是的矛盾

`0x625BE0`（同消息的写侧）**不写** 1 位头，只从 `0xB77B10`（writeTag）开始。
如果拿它跟服务端比，会得出"服务端多写 1 位 = 错"的结论 —— 这是**假阳性**。

原因：读/写侧都是"容器写了头、成员函数从 tag 起"。`0x625BE0` 的上游 ctor 才是写头的地方。
所以**对账必须读侧对读侧、写侧对写侧**；交叉对比（服务端写 vs 客户端写函数）会误判。
（这也提醒：`0x625BE0` 无直接 `E8` 调用者，是按 vtable 调用的成员，单独看不完整。）

## 3. "全对"之后，开局还可能死在哪

按依赖顺序，`0x625CE0` 之前还有三道：

1. **外层信封**：`build_room_push` 用 `Buf(True)`（字节标签 `08/0A/10/13`）把 109B 包起来，
   而 `0x625CE0` 读的是**位标签**（`0x13/0x08`）。两种是不同的编码层。
   客户端要把字节信封解出 blob 后，**再新建一个 bit reader**（带 1 位头）才能进 `0x625CE0`。
   若信封的字节标签与客户端 `0x7E7970`/`0x7F1060` 期望不符，109B 根本到不了 `0x625CE0`。
   —— 本卷只验证了 109B 本身；外层信封是对账的**下一站**（见论文 T1）。
2. **前置 tag3/u8（已闭合）**：`0x634870` 入口 `[ebx+0x1C]!=0` 时先 `readTag(3)+readBits(8)`，
   得到 u8 后 `0x6348D8 mov esi,[0x82E1458+eax*4]` 分派（无专用则落 `0x636F3C[eax]`），
   紧接着 `0x6348D1 mov [edx+0x1c],1` **复位游标到 bit 1** ⇒ `0x625CE0` 再把同一 u8 读一遍。
   **结论**：这个 u8 就是字段1（opcode），服务端写一次（=3）即命中 `0x636F3C[3]=0x634AC2`，
   不需要额外字段。原来的"前置字段是否缺失"疑虑 **不成立**。
3. **`securityKey` 的内容**：长度 16B 对，但值是 `ECDH 派生`（163/272 卷）。
   本卷只确保"16 字节在位"，**不保证数值正确**。若服务端仍写 `00*16` 或写错派生值，
   客户端拿到长度对的 key 也会在后续握手失败。

## 4. 尾部 4 位补零：真无害吗

服务端 109B = 872 bit，字段只用 868 bit，末 4 bit 为 0。
- `0x625CE0` 读满 16B blob 立即 `ret 4`，**不检查剩余位**。
- 外层若按"字节长度"传（109B），4 bit 补零天然被吞进最后一字节，无需对齐。
- 唯一风险：若客户端对"消息消耗位 == 缓冲位长"做**严格相等**校验（本路径未见），
  会因 868≠872 报错。本卷在 `0x625CE0`/`0x634870` 内未见此校验。

⇒ 判断：补零无害，但它是"服务端写法不是最省"的痕迹，不是缺陷。
