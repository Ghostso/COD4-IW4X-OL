# 256 探讨 · 方法、批判与自我更正

## 一、方法：先定"归属"，后问"调用"

面对 `0x7F1400`，旧卷（229/244/246）一直在问"**谁调用它**"，得到的答案是"没找到 `E8` 调用点"。
本卷换问法："**它属于哪个对象**" —— 读它的 vtable 基址写点。

- 手段：`0x7F1400` 的 dword 出现在 `0xDE080C`；`0xDE080C` 距某基址 = 某已知槽偏移。
- 猜 `0xDE07B4`（229 卷认为的表头）不对；改搜"哪个地址的 dword == 基址候选" ⇒ 命中 `0x7F097F mov [0xE39B6E8],0xDE07A4`。

★ 这与记忆里 `「没有样本→谁读它」`、`「vtable 槽也是调用边」` 同源：
**vtable 槽是"对象 + 偏移"的调用边，没有 `E8` 不代表没有调用者。**

## 二、本卷与 246 卷的关系（重要）

246 卷的核心结论是"`0x7F1110` 不是 booking 入口，`0x7F1400` 才是分派器"。
本卷进一步发现：**`0x7F1110` 与 `0x7F1400` 是同一条 vtable（`0xDE07A4`）的两槽（`+0x20` vs `+0x68`）**
⇒ **它们是同一个"房间/会话协议处理器"对象的两个虚方法**。

这解释了 246 卷的困惑："为何 `0x7F1110` 读了 HTTPS 全局却不是入口" ——
因为它本来就不是"入口"，而是**同一对象上的另一个回调槽**（`ret 0x14` 的连接身份通知）。
**框架**（同一对象）比**函数级**（两个孤立函数）更本质。

## 三、批判本卷

1. **"注册进 srpc"这条最初最弱 → 已在本轮补强**：我原先只按"`push 0xE39B6E8; call 0xB7A400`"推断语义，
   后来**读了 `0xB7A400` 函数体**：`mov [ecx+0x4F0],eax; ret 4` ⇒ 它是**纯 setter**，
   `0xE39B6E8` 被写进 `srpc+0x4F0`。**教训：推断"某调用是注册"之前，先读被调函数体（3 条指令而已）。**
2. **上游派发未定**：`0xE39B6E8` 的 `vt+0x68` 谁来调？静态无 `E8` 边（vtable 槽）。
   我只给出"对象 + 槽"，没给出"srpc 内部如何按命令字选中 `+0x68`"。
   ★ 已知 `[srpc+0x4F0]=0xE39B6E8`、`0x7F0AF0` 会驱动它走 `0x7FAA20` 漏斗，但"入方向"（收包→选槽）仍未读。
3. **`0xDE07A4` 是基址还是 `0xDE07A4` 的前一项**：`0xDE07A4[0]=0x7F0A00`、`0xDE07A4[4]=0x92E880`。
   `0x92E880` 与 `0x9F1D10` 反复出现（可能是同一 thunk 或多个槽指向它），未确证 `0xDE07A4` 就是 slot0。

## 四、下一步可独立核验任务

1. 反汇编 `0xB7A400`（控制台里 3 条指令即可判断是 setter 还是 list-add）。
2. 读 `0x92E880`/`0x9F1D10`，判断 `0xDE07A4` 是不是 vtable 头部。
3. 追 `0x7F0AF0`（`0x7EED28 call 0x7F0AF0`，另一处操作 `0xE39B6E8`）—— 可能是"处理一条命令"的分派器。

## 五、边界重申

本卷解决的是**"归属"问题**（`0x7F1400` / `0x7F1110` 同属 `0xE39B6E8`），
**不解决**"运行期这条槽是否被触发"（需要实机或抓到真实 `mm*` 消息）。
按 GPT-6A 原则，这已翻译为可独立核验任务（见 §四），不是停手理由。
