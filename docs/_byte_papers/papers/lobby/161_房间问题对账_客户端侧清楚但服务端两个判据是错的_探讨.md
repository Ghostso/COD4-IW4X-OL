# 161 · 探讨：我问「清楚了吗」，然后就把它问清楚了

> 配套论文：`161_房间问题对账_客户端侧清楚但服务端两个判据是错的.md`

---

## 一、我本来准备怎么回答

你问「现在房间问题清楚了吗」。

我第一反应是想说：「客户端侧闭了，服务端在 160 卷读了，**应该算清楚了吧**。」

**「应该算了吧」——这四个字就是危险信号。**

160 卷我只做了「读服务端源码」，**从来没做过「客户端 × 服务端逐项对账」**。

读了两边 ≠ 两边对得上。

于是我去对了一下，一小时后拿到了硬结论：**服务端两个关键判据都是错的。**

---

## 二、最刺的那条

服务端判「准备」用的是：

```python
has_ready = (bytes(batch) == cc.ROOM_READY_BATCH       # 16 字节常量
             or (len(plain) > 11 and plain[11] == 0x15))
```

我去把客户端的 Ready 序列化器（`0x6287D0`）逐条指令拆开：

```
WriteBits(3,  type & 7)      →  3 位
WriteBits(8,  type)          →  8 位
WriteBits(1,  1)             →  1 位（存在位）
WriteBits(1,  ready?0xFF:0)  →  1 位
                          ─────────────
                            13 位 = 2 字节
```

`type=0x10` ⇒ 位串 `0000001000011` ⇒ 打包成 **`02 18`**。

**服务端在拿 16 个字节（`0c 00 00 00 02 02 00 00 00 08 00 00 00 80 08 00`）去和 2 个字节比。**

永远不相等。这条分支从来没生效过。

### 为什么挂了这么久

因为源码里写着 `# —— 照抄 ol-mod Unknown0BService.cpp:98-101`。

**一旦标上「照抄」，它就不再被质疑了。** 大家都以为「别人验证过」。

而 AGENTS.md 明明写着 ol-mod 服务的是 3.3.3.3，不是我们这份 3.19。

---

## 三、第二条更隐蔽

兜底判据 `plain[11] == 0x15`。

源码注释里，这条判据**被推翻过一次，又被加回来过**：

- `788-796`：「★ 更正 ready 判据：**不是** `payload[11]==0x15`。那个字节其实是 blob 长度的低字节」
- `799-802`：「★ 实机更正: 客户端 PvE 发来的 ready 批次是 21B, 其中 `plain[11]==0x15`」⇒ 重新启用

**两次都没有去查本地字节。**

我查了。按服务端自己的解包格式：

```
0A <u64 channelId> | 13 08 <u32 len> <batch> | 08 <u32 type>
 1    8               1  1    4
```

`batch` 从 **第 15 字节**开始。

**`plain[11]` 落在 `channelId` 里面（channelId 的第 3 个字节）。**

所以：
- 「是 blob 长度低字节」—— 错（blob 长度在 `+12..+15`）
- 「是 ready 子类型」—— 错（它在 channelId 里）

**它读的是房间频道 ID 的一个字节。**

---

## 四、这两条错误为什么能一直存在

因为**「实机试」是唯一的验证手段时，你会接受任何能让流程往下走的巧合**。

- 某次试通了 → 记下「这个字节有用」→ 写死。
- 换一个场景不通了 → 推翻。
- 又试通了一次 → 再加回来。

**而真正的判据一直在本地镜像里**：`0x6287D0` 那 12 条指令，逐条 `WriteBits` 累加就是答案。

### 教训

> **★★ 当你有第一权威（本地逆向）时，就不该用「实机试通」当验证手段。**
> 试通只能证明「这一次碰巧对」，不能证明「判据正确」。

这和 157 卷那条「`bind_world` 已接上但记忆没更新」是同一类：**信息在手上，但没去看。**

---

## 五、所以「房间问题清楚了吗」

**清楚了。而且清楚得很具体：**

| | |
|---|---|
| 客户端发什么 | ✅ 精确到位（`02 18` / `02 10`） |
| 服务端判什么 | ✅ 精确（16 字节常量 / `plain[11]`） |
| 两边对得上吗 | ❌ **对不上，两个判据都错** |
| 能跑通吗 | ❌ 所以跑不通 |

**「清楚」的正确含义不是「已经能跑了」，而是「已经知道为什么跑不通、以及怎么修」。**

这个区别很重要。我上一轮如果回答「清楚了」，你可能会以为房间已经能用了。

## 六、三处可以立刻改的

```python
# 1) ready 判据改成位流判据（来源：客户端序列化器 0x6287D0）
def _is_ready_bitstream(batch):
    if len(batch) < 2: return False
    return (batch[0] >> 5) == 0 and \
           (((batch[0] & 7) << 5) | (batch[1] >> 3)) == 0x10

# 2) 删掉 plain[11]==0x15（它读的是 channelId 内部字节）

# 3) GAME_START_PAYLOAD（162B 三方抓包常量）源码自承未验证 ⇒ 默认不发
```

三条都不是猜的，都有本地依据。

## 七、方法论（本卷新增两条）

1. **★★ 「读了两边」≠「两边对得上」。** 对账必须逐项做，不能因为都读过了就假设一致。
2. **★★ 有第一权威时，不要用「实机试通」当判据。** 试通只证明这一次对，本地逆向才能证明永远对。
