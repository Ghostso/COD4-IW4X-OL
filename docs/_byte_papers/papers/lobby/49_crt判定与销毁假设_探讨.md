# CRT 判定与销毁假设 · 探讨：把"闸门"排除掉，本身就是进展

> 对应：`lobby/49_crt判定与销毁假设.md`

---

## 一、上一卷的猜测被推翻了

上一卷我写：

> "`0xc3e9f5` 可能在检查会话/资源，离线时不创建房间对象。"

**这一卷反汇编证明：它是 CRT 的锁函数。**

```
0xc3d2c5  call [0xca82e8]     ; IAT 调用（不是业务代码）
0xc4b5bf  call [0xca82f0]     ; IAT 调用
```

**两个都是"取函数指针再调用"，配合 `0x19697c8` 这类全局句柄，
是标准的多线程锁写法。**

**⇒ 它几乎总是成功，`0x639d25`（失败分支）几乎不会走。**

---

## 二、排除一个假设的价值

**如果我继续相信"它是闸门"，就会去查 `0x3a128` 是个什么资源。**

**那会浪费很多时间。**

**反汇编 40 行代码就否定了这个方向。**

**这就是"追到函数体"的价值。**

---

## 三、新假设：对象被销毁了

**在追 `0x82e13fc` 的所有写入点时，我发现第三处：**

```
0x63a59a  mov dword ptr [0x82e13fc], edi    (edi = 0)
```

**它在一个"销毁"函数里：**

```asm
mov ecx, [0x82e13fc]
cmp ecx, edi
je  0x63a59a           ; 已经是 0 就跳过
mov edx, [ecx]
call [edx]             ; 调用虚析构
mov [0x82e13fc], edi   ; 置 0
```

**⇒ 如果这个函数在创建之后跑了一次，对象就变 0。**

---

## 四、为什么这个假设更可能

**假设 A（没创建）需要：**

- `0x7e98f0` 整个没被调用
- 或 `0xc3e9f5` 返回 0

**第二个已被排除。
第一个需要"启动路径断在最前面"，那是很大的前提。**

**假设 B（创建后销毁）需要：**

- `0x63a583` 那段在某处被调用

**这是很常见的模式（例如"重新初始化前先清理"）。**

---

## 五、一个具体的场景

**客户端启动流程可能是：**

```
1. 初始化 A 阶段 → 创建房间对象
2. 检测到大厅未就绪 → 重新初始化
3. 初始化 B 阶段 → 先销毁旧的（0x63a59a）→ 再创建
4. 但 B 阶段的创建被某个条件挡住
```

**⇒ 最终状态：0。**

**这个场景能同时解释"创建代码存在但对象为 0"。**

## 六、方法论收获

> **排除一个假设，和确认一个假设，价值相同。**

**这一轮没有"找到答案"，但把可能性从 2 个减到 1 个（其实是换了方向）。**

**在逆向里，每次"这不成立"都是向答案靠近一步。**
