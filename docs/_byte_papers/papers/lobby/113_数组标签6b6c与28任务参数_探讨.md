# 113 · 探讨：数组标签是最后一块"结构黑箱"，它比字节黑箱更难

> 配套：[113_数组标签6b6c与28任务参数.md](113_数组标签6b6c与28任务参数.md)

---

## 一、前 112 卷都在解剖"字节"，这一卷第一次解剖"结构"

前面 10 卷（102–112）都是**单字节角色分账**：`0x00` 有多少个角色、`0x01` 是不是布尔、`0x07` 有几个值。
这一卷不一样——`0x6b`/`0x6c` 的问题是**"一个元素内部怎么嵌套"**，不是"这个字节是什么"。

这两类黑箱的难度完全不同。字节黑箱可以靠"数数 + 去重直方图"关掉（111 卷的空串就是这么关的）。
**结构黑箱不行**——你必须猜出一个嵌套模型，然后拿全语料去证伪。猜错了，整个解析都错位。

## 二、我一开始猜错了一次

第一版我看 `28/4` 的 body = 127 个 u32、count=263，直觉判断"127 个内容 ID，263 是数量"。
这个判断**方向对了但细节错了**——我漏掉了"body 第一个 u32 = 127 = 元素总数"这个规律。

直到 `arr_6c_rule.py` 跑出"**body[0] == len(u32) 160/160 零例外**"，我才意识到：
**body[0] 根本不是内容 ID，它是数组自身的长度**。真正的数据项是 `body[1:]`（126 个）。

这个错误很危险：如果我按"127 个 ID"去写服务端，会多解析一个 ID（把计数当数据），导致后续全部错位 4 字节。**这正是 104 卷"窗口跨越文法元素"那个错的重演**——只不过这次跨越的是"数组头 vs 数组体"的边界。

**教训**：数组结构的第一个 u32，先怀疑它是"长度/计数"，不要先当成数据。用"body[0] == 元素总数"这个等式一测就知道。

## 三、`[N][item×N-1]` 这种冗余编码为什么存在

外层已经有 `byteLen`，为什么 body 里还要再放一个 `N`？这看起来冗余。

我的推断：这是 **Demonware TypeArray 的流式读取优化**。客户端读一个数组时：
1. 读外层 `byteLen`（知道整个 body 多长）——需要先读 4 字节。
2. 但**如果 body 里第一个 u32 就是 N**，客户端可以**先读 N，再直接读 N-1 个 item**，甚至可以在不读完 body 的情况下做预分配（`new T[N]`）。

这是一种"读起来更快"的编码，代价是 4 字节冗余。在 2010 年代的 Demonware 协议里很常见。

★ 这对我们写服务端是**硬约束**：**body[0] 必须等于 u32 元素总数**，否则客户端预分配会错。这不是"可选"字段，是"必须自洽"的字段。

## 四、`28/1` 是这卷最重要的收获：PvE 关卡选择的钥匙

前面很多卷都在 PvE 上卡住（memory 里"剧情模式内容系统性缺损"、"卡战斗开始"）。
`lobby_server.py` 的原注释说得很直白：`28/1` 在 `mmstart` 之前到达，"很可能带着玩家选了哪一关"。

这一卷确认了 `28/1` 的**字节结构**：
```
6c 08 <bytelen> [N] [选中索引…] <可选总数>
```
- `body=[2][0]` tail=5 → "选中第 0 项，共 5 个可选"
- `body=[1]` tail=131 → "没选，共 131 个可选"

**这是可以主动构造的**。如果 PvE 卡住的根因是"服务端不知道玩家选了哪一关"，那么只要在 `28/1` 的响应里（或让客户端发出正确的 `28/1`）携带正确的关卡索引，`21/5` 就能一次回对图。这是一个**具体的、可验证的 PvE 突破点**，不再是"大概可能"。

我没有在这一卷就去做这个实验（需要启动游戏，属于需授权的操作），但我把**可直接构造的模板**写进了论文 §3.4。下一轮如果用户授权跑实验，这就是第一个要试的东西。

## 五、`28/4` 的"内容解锁"是一把双刃剑

`28/4` = ContentUnlock2，客户端上报"我解锁了这 126 项"，服务端回"确认/补发"。`do_fixes.py` 显示服务端可以回 `08 <cid> 08 32` 把任意内容置为已解锁。

**这意味着一件事**：理论上，服务端可以对 263 个内容 ID 全回"已解锁"，客户端就会认为所有内容都解锁了。这是一个**免费获得全部内容**的协议入口。

但我要**诚实标注边界**：
1. 这 126 个 ID（0..262）是**内容槽位索引**，不是商城 SKU。它们解锁的可能是"战役关卡/挑战/成就"之类的**本地内容**，不一定是"付费武器/皮肤"。
2. 商城 SKU 是另一套大整数 ID（241/22858/31845…），走的是 `80/*`、`93/131` 通道，**不是 `28/4`**。
3. 所以"28/4 全解锁 = 免费全内容"这个推论**只对内容槽位成立，对商城道具不成立**。

我把这个边界写清楚，是因为如果不写，下一个人会以为改 `28/4` 就能白嫖商城——那是错的，会浪费一整轮。

## 六、`0x6b` 和 `0x6c` 是同一族，但方向相反

`0x6b` 全是空数组（21/5 请求的结果容器），`0x6c` 有数据（28/1 选择、28/4 解锁）。
结构完全同构（`[N][item]` + tail），只是 **`0x6b` 在请求侧、`0x6c` 在请求侧带数据**。

我推测 `0x6b` 和 `0x6c` 的区别是**元素类型不同**（比如 `0x6b`=字符串数组、`0x6c`=u32 数组），或者**一个是"查询结果占位"、一个是"带类型的值数组"**。但 corpus 里 `0x6b` 全是空，**无法从数据侧区分**。我诚实标为"未定"——不能因为"看起来一样"就断言它们是同一类型。

## 七、方法论沉淀

1. **结构黑箱要"先猜模型再证伪"，不能靠数数**。
2. **数组第一个 u32 先怀疑是长度**，用 `body[0] == 元素总数` 一测即知。
3. **冗余编码往往是"读取优化"**，不是 bug；写服务端时必须保持冗余字段自洽。
4. **ID 域隔离要显式对照**：0..262 / SKU 大整数 / 8-3 哈希键是三套空间，混用会出大错。
5. **未定的就标未定**（`0x6b` 响应侧语义），不猜。
