## 1. 已严格证明（可复跑）

### 1.1 RSA 密文的位置

```
mp_playlists.ff 偏移 0x15，256 字节
→ RSA 私钥（PKCS#1 v1.5）解密成功
→ 40 字节明文密钥材料
```

**命令**：`python -I tools/rsa_scan_ff.py "COD OL\main\mp_playlists.ff"`

**结构证明**：不是"看着像"，而是 `rsa_decrypt_key` 的 PKCS#1 v1.5 填充
（`00 02 <≥8 非零> 00 <数据>`）严格校验通过。

材料：`da135e91c7981459a13ddc2aed3050ae6dd9a7ce619bb6c5ff6c10c6db65 0000 149c1f01 03000000`

### 1.2 数据起点 = 0x115

```
IWff 头   0x00–0x14    (16 字节)
RSA 块    0x15–0x114   (256 字节)
密文数据  0x115–...    (49,216 字节)
```

`u32@8 = 461` 与整包结构吻合。

### 1.3 AES 密钥与 IV

```
key = 材料[0:24]   = da135e919c7981459a13ddc2aed3050ae6dd9a7ce619bb6c5
iv  = 材料[24:40]  = ff6c10c6db650000149c1f0103000000
```

**RFC 结构**：材料后 16 字节中的后 8 字节是 `149c1f01 03000000`，
像是固定的版本/尾标记，符合"前 24 密钥 + 后 16 IV"的排布。

### 1.4 解密结果的头部

```
CFB128 / OFB / CTR 三种模式都能解出：
  b'IWffs100\x00\x00\x00\x00o\x9e\x1d\x0c'
```

**并且磁盘密文 ≠ 明文**（`b2 2d ee f2 ...` ≠ `IWffs100...`），
**证明这 16 字节是真正解密出来的，不是碰巧**。

### 1.5 从代码确认的算法身份

| 函数 | 身份 | 证据 |
|---|---|---|
| `0xbc8780` | `find_cipher` | 遍历 `0xe87850` 注册表 + strcmp |
| `0xbca340` | `cipher_is_valid` | 索引 < 0x20 且表项非空 |
| `0xbc8d70` | **AES `setup`** | `cmp esi,0x10/0x18/0x20`（接受 16/24/32）+ S-box 表 |
| `0xbc9230` | AES `encrypt` | 调 `0xbcd060` + `0xbccbc0` |
| `0xbc9720` | AES `decrypt` | 同上结构 |
| `0xbc7e70` | `rsa_import` | DER 解析 + 长度校验 |
| `0xbc8850` | `rsa_decrypt_key_ex` | padding 参数必须 1 或 2 |
| `0xbc7c40` | SHA-256 init | `0x6a09e667` 等魔数 |
| `0x4834f0` | 块解密主循环 | 8192 字节块 + SHA-256 校验 |

注册表入口 `0xe87850`（0x68 字节/项）：
`+0x18 = 0xbc8d70`（setup）、`+0x1c = 0xbc9230`（encrypt）、
`+0x20 = 0xbc9720`（decrypt）、`+0x28 = 0x8435d0`（done）。

## 2. 尚未打通的一步

### 现象

解密后**只有前 16 字节正确**（`IWffs100`），从第 16 字节起全是高熵随机。

### 已排除的可能

| 假设 | 排除依据 |
|---|---|
| 密钥错 | 头 16 字节能解出精确的 `IWffs100`，概率 2^-64 |
| IV 错 | 换 5 种字节序（raw/rev32/rev16/u32le↔be），头 16 字节都变，只有 raw 命中 |
| 模式不是 CFB | CFB8/CFB64/CFB128、OFB、CTR、ECB 全试过，只有 CFB128/OFB/CTR 能回头 |
| 是块链（CBC 式） | 用块 0 尾密文/尾明文作块 1 的 IV，块 1 仍解不出可识别内容 |
| 每块独立重置 | 每 8192 重置后，块 1 仍是随机 |
| 正文是压缩 | 全文件扫 zlib/gzip/bzip2 头，无一个能解压 |

### 最可能的原因

**我对 `0x483a50` 的参数映射有一个错位。**

`cipher_setup` 调用点（`0x483af3`–`0x483b14`）的压栈序列里夹了
`call 0xbc8780` + `add esp,4`，导致"哪些 push 属于哪个 call"需要重排。
当前我假定的是：

```
cipher_setup(idx=eax, key=[ebp-0x14], keylen=?, ...)
```

而实际**很可能**是：

```
cipher_setup(idx=eax, key=[ebp-0x2c] /*RSA输出*/, keylen=24)
```

两种解释都能让前 16 字节解对（因为 `[ebp-0x14]` 可能就是 `[ebp-0x2c]` 的
前 16 字节的副本），但后续密钥调度不同，导致第 2 块之后全部错。

**下一步必须精确解出 `cipher_setup` 的 6 个参数各自来自哪里。**

## 3. 这次尝试的净收获

即使正文没解开，这一轮**新增了 4 条硬结论**：

1. **RSA 密文在 `.ff` 偏移 0x15**，不在文件头也不在尾部
2. **40 字节密钥材料，前 24 是密钥、后 16 是 IV**
3. **AES 是 CFB 族**（不是 ECB/CBC）—— 因为前 16 字节完美、后续全乱
4. **`.ff` 明文头是 `IWffs100`**（磁盘上是 `IWff0100`，说明"已加密"标记）
