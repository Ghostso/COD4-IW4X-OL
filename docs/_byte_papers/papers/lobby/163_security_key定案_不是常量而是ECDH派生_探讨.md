# 163 · 探讨：我问「0x00 还是 0x01」，答案是两个都不对

> 配套论文：`163_security_key定案_不是常量而是ECDH派生.md`

---

## 一、上一卷我把问题问错了

162 卷我写：

> 「待验证的唯一一项：**客户端期望 `security_key` 是 `0x00…` 还是 `0x01…`？**」

这是一个二选一。

我去查了，结果是：**选项之外。**

`security_key` 在客户端根本不是常量 —— 它是 **ECDH 共享秘密**，由 `0xBA0D20` 那次 EC 运算实时算出来，然后喂给带标签的 KDF。

**⇒ 正确的问题不是「哪个值」，而是「战斗服有没有用同一个算法」。**

而答案是：**没有。算法都不一样。**

---

## 二、证据链

```
0xBA1F6B  push 0xD5A4E0        ; "BDDATA"
0xBA1F70  lea edx,[ebp-0x4C]   ; 输入 = shared secret
0xBA1F76  call 0xBA13D0        ; KDF(shared, tag, taglen, out, outlen)

[ebp-0x4C] 的唯一写点：
0xBA1E88  lea ecx,[ebp-0x4C]
0xBA1E96  call 0xBA0D20        ; ← EC 运算（内部 0xC73800/0xC73760/0xC737A0）
```

而战斗服：

```c
codol_sha1( buf = shared_x28 || 0x01×16 , 44 );
```

**⇒ 客户端：`KDF(shared, "BDDATA")`；战斗服：`SHA1(shared || 常量)`。**

这已经不是「值不一样」，是「公式不一样」。**任何值都救不了。**

---

## 三、`0x01` 那个常量是怎么来的

```c
/* securityKey: 客户端 build 1649370 的 live 映射对 ID 1 保留 0x01 默认值 */
memset(b->security_key, 0x01, sizeof(b->security_key));
```

「live 映射对 ID 1 保留 0x01 默认值」—— 听起来像从客户端内存里看到的。

**但如果客户端那 16 字节是 ECDH 派生的，那"看到 0x01"只能是：**

- 某个中间态（还没算出来）
- 或者看错了位置

**⇒ 这条注释的出处现在可疑。** 它把一个运行时派生值当成了静态默认值。

## 五、我现在能说的和不能说的

**能说（已确证）**：
- 客户端用带标签 KDF（`BDDATA` 6B / `CLIENTCHAL` 10B），输入是 ECDH 共享秘密
- 战斗服用裸 SHA1 拼接全 `0x01`
- **两者必然算出不同的 key ⇒ HMAC 必然失败**

**不能说（待定）**：
- `BDDATA` 输出 72 字节、`CLIENTCHAL` 输出 16 字节 —— **哪一个对应 `transport_key`**
- 这需要继续解 KDF 两个输出的消费者

**⇒ 但这不是黑箱，是有明确下一步的待定项。**

## 六、方法论（本卷新增）

1. **★★ 「A 还是 B」这种提问要警惕。** 162 卷我问「0x00 还是 0x01」，实际答案在两个选项之外。
   **先问「它是什么」，再问「它是哪个值」。**
2. **★★ 比"值"之前先比"算法"。** 值不同可能是参数差异，算法不同才是根本分歧。
3. **★ KDF 标签是最强的算法指纹。** 有 `"BDDATA"`/`"CLIENTCHAL"` 就是标准 KDF；没有标签的拼接就是自制。
4. **★ 源码注释里的"默认值"要验出处。** 「保留 0x01 默认值」可能是把运行时派生值误当成常量。
