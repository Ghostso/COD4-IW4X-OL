---

## 一、这是本轮最难受的一次

`RawSize=0x62000` 这个数字，我看了十几遍。139 卷写「覆盖 0.2% ⇒ 文件空洞」，150/153/154 卷都在这句话下面加了一句「所以段2 的值不可信」，然后**绕开段2 走**。

而段2 里躺着 **25 KB 明文配置 + 几十 MB Flash 资源 + playlist 明文**。

最刺的是：**`VA = file_offset + 0x400000` 这个公式，我每一卷都在用，而且每一次都对**。139 卷却在同一篇论文里既用这个公式把 `0xDC7274` 映射到 vtable（成功），又说段2 的磁盘值是空洞（失败）。

**同一个文件，同一条公式，不能一半有效一半无效。**

### 为什么会犯

因为我先看到 `VSize/RawSize = 3540` 这个**比值**，被它吓到了。「3540 倍」在直觉上就等于「99.97% 是假的」，于是我去找证据支持这个直觉（找 `RawSize` 定义、找 VMProtect 惯例），而不是去数非零字节。

**正确做法只需要一行：`sum(1 for x in d[0xA16000:0xE5C7CC0] if x)`。**

我没跑这一行，跑了 15 卷。

### 教训（写给自己）

> **任何「这块是空的」的结论，都必须由一个非零字节计数器支撑，不能由节表比值支撑。**

## 二、`RawSize` 到底是什么

我这次把它想清楚了：

- 标准 Windows 加载器：`memcpy(ImageBase+RVA, file+RawPtr, RawSize)`，其余 `memset 0`。
- **`RawSize` 是给标准加载器看的。**
- 一个自研/混淆过的加载器，完全可以 `memcpy(ImageBase, file, file_size)` 一把梭。
- 而本镜像 `RawPtr == RVA`（段2 的 `RawPtr=0xA16000` 恰等于 `VirtualAddress=0xA16000`）—— **这本身就是「整体映射」的指纹**。标准编译器产出的 PE，`RawPtr` 几乎从不等于 `RVA`（通常 0x200 或 0x400 对齐）。

**`RawPtr == RVA` 是一个可以批量扫的判据：**

> **若某段的 `PointerToRawData == VirtualAddress`，则该段极可能被整体映射，`RawSize` 无意义。**

这条判据值得写进方法论，因为它是**结构性的**，比「熵」「可打印率」都硬。

## 三、这次的两个「意外收获」

### 3.1 `tcls_zone_map` 直接给了 zone_id

用户很早说过一句话：

> 「这三项直接在游戏客户端文件里找，本地客户端肯定有，如果没有他要怎么知道什么是正确的」

我当时（143 卷）的结论是「**客户端确实知道正确值，但那是运行时计算，磁盘无明文**」。

**现在我必须修正一半**：

- **通用映射**（zone 名 → zone_id、超时、开关、匹配参数）→ **磁盘明文，就在 `0x331D420`**。
- **本账号/本会话的具体值**（ticket、cnonce、实际分配的 zone）→ 运行时才有。

`stnd=83886082`、`tubd=419430402`、`stgd=754974722`、`ctgd=1090519042` —— 这几个数，**四个大区的身份**，明明白白写在可执行文件里。

而且它们的结构是自证的：低 16 位全是 `0x0002`，高 16 位步进 `0x14`。**这不是巧合，这是 `[zone_index << 16 | 2]` 的编码。** 一个随机值不会这么整齐。

### 3.2 `dw_task_timing_overrides` 5/5 命中

154 卷我从 `0xE69CE0` 逐行读出「25000/25000/2000/5」「25000/25000/2000/10」……

磁盘明文：

```
0=25000,25000,2000,5
1=25000,25000,2000,10
2=25000,25000,2000,5
3=60000,60000,2000,5
4=60000,60000,2000,10
```

**一行不差。**

这一处让我对 150–154 卷的所有「从 `.rdata` 读表」的结论都更放心了 —— 至少这一条，代码和磁盘互相印证。

而且它顺手关掉了 154 卷的最后一个未闭合项：**`0x7FA560` 读的 dvar `dw_task_timing_overrides`，默认值不是外部 config，而是编译进 exe 的这段明文**。

## 四、`[dw_service_info]` 解释了 141 卷的一个悬案

141 卷我发现 srpc 有 14 张哈希表、68 个注册点、每表 1 条目（空串主键）。当时留下的疑问是：

> 注册了 68 个服务，为什么运行时只有少数几个在活动？

`[dw_service_info]`：

```
matchmaking=1  messaging=1  profiles=1  storage=1  stats=1
其余 14 个全 0
```

**只有 5 个是 1。**

⇒ **「注册」与「启用」是两层。** 注册是代码结构（编译进去就有），启用是配置。这解释了 102 卷（Messaging2 活跃，因为 `messaging=1`）、129 卷（stats 相关遥测活跃，因为 `stats=1`）。

这条对我理解整个 lobby 的「为什么很多代码从不执行」非常关键：**不是死代码，是开关关着。**

## 五、我这次又差点只写一半

读配置块的时候，我从 `[dw_task_timing_overrides]`（`0x331E6E3`）开始往下读，读到 61 个 section 就以为是全部。

**「`[dw_task_timing_overrides]` 在最前面」这件事本身就可疑** —— 一个配置文件不会以最冷门的超时覆盖表开头。我向上回溯到 `0x331D420`，才看到真正的头是 `[version] g_dwConfigVersion=1`。

结果：**61 → 80 个 section**，多了 `tcls_zone_map`、`ds_title_zone`、`dw_config`、`dw_service_info`、`cross_zone_*` —— **恰恰是最有价值的那批**。

### 教训

> **从中间某处开始读文本块，一定会低估它。** 正确做法：找到锚点后，**向两个方向扫到「非文本字节」为止**（我这次是向回扫到连续的 `\x00`，向前扫到连续的非可打印）。

这和 154 卷「地址相邻 ≠ 同表」是同一枚硬币的两面：
- 154：「看起来连着的东西可能不是一张表」
- 155：「看起来是开头的东西可能不是开头」

两句话合起来：**边界必须由内容决定，不能由位置推断。**

## 六、还剩什么

本卷开了三个新口子，都没做：

1. **`[Whitelist]`**（`0x330C0C8`）—— 反作弊白名单，是进程列表还是模块列表？
2. **playlist 明文**（`0x07716000` 一带）—— 大量 `1011 1;3265 4;...` 形式的 id+dvar 对，需要单独一卷逐行对表。
3. **段2 里其他明文块** —— `0x07216000` 的 `[activities]`、`0x08016000` 的 `M7-E8S6Client`、`0x0BE16000` 的腾讯登录 URL。这些都能像本卷一样直接 dump。

按用户的「每个字节都要写一篇论文」的标准，**段2 至少还能再挖 3–5 卷**。

但更重要的是：**段2 = 219 MB，现在已知有 25 MB 非零。这是一个从未被系统扫过的区域。** 本卷只是从里面捞了一块 25 KB。系统扫一遍段2 的 ASCII run 分布，可能会把之前所有「找不到」的问题一次性解决。

## 七、方法论（本卷新增四条）

1. **★ 「这块是空的」必须由非零字节计数器支撑，不能由节表比值支撑。**
2. **★ `PointerToRawData == VirtualAddress` ⇒ 整体映射，`RawSize` 无意义。**
3. **★ 读文本块要双向扫到非文本边界，不能从锚点单向下读。**
4. **★★ 前卷的「不查」会连锁压缩后续卷的范围。** 139 卷对段2 弃权 → 143 卷只看两段 → 15 卷后才发现明文。**每卷的弃权都要写成显式待办，并在下一卷回检。**
