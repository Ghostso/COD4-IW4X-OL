**★ 与 `0x07`（i32）对照：`0x08` 标签:非标签 = 6,369 : 4,238 ≈ **1.5 : 1**。

（`13 08 …` / `6b 08 …` / `6c 08 …`），实测 1,749 + 159 + 203 = **2,111 个**。
`L` 总数 2,185 − 2,111 = **74** 个是长度前缀或计数字节恰好等于 0x08。**

## 3. ★★ 更正 `109` 卷：`1800154382` = 账号 ID 的低 32 位

**`109` 卷我把 `1800154382`（`0x6B4C2D0E`）写成"另一个频道 ID"，并误记 hex 为 `0x6B4E6E0E`。**

**本卷复核（一次算术即定案）：**

```
账号 ID = 0xE7C8A98A6B4C2D0E
低 32 位 = 0x6B4C2D0E = 1800154382    ← 完全相等
```

**★ 交叉证据（`61` 卷早已记录的字节）：`4/13` 的 u64 存为
  `0a 0e 2d 4c 6b 8a a9 c8 e7`，其**低 4 字节 `0e 2d 4c 6b`** = `0x6B4C2D0E`。**

**⇒ 所以 `11/4` 的 `[u64 roomId]` 有两个可能取值：**
- `0x1122334455667788`（默认/靶场频道，298 次）
- `0x6B4C2D0E`（= **账号 ID 低 32 位**，54 次）

**★ 它不是"独立变量"，是**从账号 ID 截断而来**的。
  ⇒ 教训：看到"新魔数"第一步先做"与已知常量的算术比对"（截断/移位/与），
  再决定要不要起语义名。本卷正是这样纠错的。**

**★ 这个 32 位截断只出现在 3 个 run（`ONCE_20261029_000806` / `_001513` / `_002046`），
  且这 3 个 run **都建过房**（有 `11/13`）。但 47 个建过房的 run 用的是默认 ID
  ⇒ 不是"建房就用 ACClo"，只是"这 3 次会话选了它"。见 §8。**

## 5. ★ `31902622` = `71/4` 的硬件指纹 u32（不是时间戳）

**`71/4`（81 字节，160 条完全同形）的 u32 = `31902622` = `0x01E6CB9E`，恒定 160/160。**

**报文结构（`71_04` 卷已解）：**

```
13[16]"nQloP0oCVWR6RDJS" | 13[16]"++++++++++++++++" | 08=<31902622> | 13[0] | 13[0] | 10"D4-93-90-18-55-10"
```

**★ 我穷举了 5 种哈希（FNV1a/FNV1/djb2/sdbm/Java）+ 3 种摘要（md5/sha1/sha256）
  对 MAC 的 4 种写法（带横线/去横线/小写/原始 6 字节）做前 4 字节截断 —— **全部不匹配**。**

**⇒ `31902622` **不是** MAC 的常规哈希。它更像一个独立的"机器/会话 ID"
  （可能与 `"nQloP0oCVWR6RDJS"` 这个 16 字符 ID 同源，由服务端或本地随机生成后固化）。**

**★ 两个 16 字节 blob 我也试了 base64：**
- `"nQloP0oCVWR6RDJS"` → base64 解码 = `9d 09 68 3f 4a 02 55 64 7a 44 32 52`（12 字节）
- `"++++++++++++++++"` → base64 解码 = `fb ef be fb ef be fb ef be fb ef be`（12 字节）

**⇒ 都能解码成 12 字节，但**没有可识别结构**（第二个是 0x2b 重复 ⇒ 是占位填充）。
  所以 `31902622` 与它们的关系**未定**。**

**★ 结论：`31902622` = 机器指纹 u32，语义"未定"，但它是**全语料 160 次完全恒定**的
  客户端标识 —— 若服务端要做"机器级识别"，这是入口。**

## 6. `932`（0x3A4）：`4/13` + `4/4` 的主值，语义未定

```

**★ `4/13` 与 `4/4` 是同一族（service 4 只有这两个 task，290 + 89 条）。**
**★ 唯一的"变量"是 `4/13` 的首 u32：常态 932，但在 `ONCE_20261029_143736` 这个 run 里
  出现了 `100/108/113/118/123/135/148` 七个值（每个 2~4 次）。**

**该 run 里 `4/13` 的记录按 idx 排列：**

```
idx 38,49,50      -> 932
idx 72,73,76,77   -> 100
idx 78-81         -> 108
idx 82-85         -> 113
idx 86-90         -> 118
idx 91-94         -> 123
idx 95-98         -> 135

**⇒ 这像一个"按某种 ID 逐个请求"的序列（同一 ID 连发 2~4 次），
  但 `932` 为何是常态值、`100..148` 为何只在这一次出现 —— **未定，不猜**。**

**★ 已知的边界：`4/13` 的 u64 = 账号 ID（100%），`4/4` 的 u64 = 1。

### 7.1 ★★ `80/119` 的 #3 = **"现在 + 365 天"的时间戳**（本卷最硬的发现）

**`80/119` 的第 3 个 u32 每个 run 都不同（83 个 run，83 个不同值）。**

**把它当 Unix 时间戳（按 UTC+8 解释）与 run 目录名的时间对比：**

```
run=ONCE_20261026_143143   ts_local=2027-10-26 14:32:22   Δ=+31536039s
run=ONCE_20261026_153238   ts_local=2027-10-26 15:33:16   Δ=+31536038s
run=ONCE_20261026_154327   ts_local=2027-10-26 15:44:02   Δ=+31536035s
…（全部 26 个有对齐样本，Δ 全部落在 31536033..31536039）
```

**★ `31536000` = 365 × 86400 = **整一年**。**
**⇒ 每个 Δ 都 ≈ 31536000 + 33~39 秒。**

**★ 那 33~39 秒是什么？正是"run 开始 → 发出 `80/119`"的会话内耗时。**

```
run 开始 14:31:43  →  ts 14:32:22  =  +39 秒  →  而 Δ − 31536000 = 39
```

**★★ 因此 `80/119` 的 #3 = **"该报文发送时刻 + 365 天"**。
  语义 = 一个**一年后到期的时间戳**（目录缓存有效期 / 凭证过期时间）。**

**⇒ 这是本卷唯一一条"可以自己算出来"的字段：
  构造 `80/119` 时，`#3 = int(time.time()) + 365*86400` 即可。**

## 10. `0x08` 与 `0x0a`/`0x07` 的分工（三兄弟对比）

| 标签 | 字段数 | 值种数 | {0,1} 占比 | 典型角色 |
|---|---|---|---|---|
| `0x07` i32 | 12,634 | 59 | 14.2% 零 | **配置键/枚举/负哨兵(-1)** |
| `0x08` u32 | 6,369 | 129 | **53.9%** | **量/序号/页大小/ID** |
| `0x0a` u64 | 20,525 | 54 | 4.1% 零 | **账号/房间/序号(0..49)** |

**★ 规律：宽度越小，`{0,1}` 占比越高（u32 53.9% > i32 14.2% > u64 4.1%）。
  ⇒ 因为 u32 被大量用作"开关/计数"，而 u64 只装"长 ID"，i32 装"有符号枚举"。**

**★ 三者里只有 `0x07` 会出现负数（-1 哨兵），`0x08`/`0x0a` 是无符号 ⇒ 不会有哨兵负值。
  所以"未设置"在 u32 里只能用 `0` 表示（`0xFFFFFFFF` 只在 `0xFF` 卷里作为 -1 出现）。**

## 11. 可落地结论

**① `1649370` = build 号（`71/18` 上报）。这是语料来自本客户端的铁证。**

**② `80/119` 的 #3 = `now + 365天` 时间戳（Δ 精确 = 31536000 + 会话内耗时）。
  构造时直接算，不要抄旧值。**

**③ `80/154`/`93/131` 的元素 #2 = 购买 SKU（28845 / 22858 / 241）。
  要"买什么"就改这个 u32。**

**④ 商城族 `80/*` 的"页大小" u32：2000/1000/700/10 各对应一个 task，
  改大它可能一次拉更多目录项（未实机验证）。**

**⑤ `6/5` 的 maxResults=20、`21/5` 的 playlist=10/50 是**唯一两个能改的请求参数**。**

**⑥ `1800154382` 不是独立频道 ID，是**账号 ID 低 32 位**。改账号 ID 会连带改它。**

**⑦ `31902622`/`932` 语义未定，但都是**恒定值**（160/160、352/352 主值）
  ⇒ 是"身份码/分类码"，服务端若做识别可用，但不要臆测其含义。**
