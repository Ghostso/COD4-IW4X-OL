# 159 · 探讨：我说了「100% 闭合」，然后被一句「大厅房间呢」戳破

> 配套论文：`159_房间专线剩余黑箱审计_五项当场闭三项说明.md`

## 一、这是我这轮最该被骂的一次

158 卷结尾我写得很硬：

> 「至此：协议 / 房间 / 大厅 / 配置 / playlist / Flash 符号 / 段2 内容，**客户端侧静态逆向全部闭合**。」

**房间这个子系统，我当时一项都没审。**

我为什么敢那么写？因为 157/158 那两轮我在**段2、playlist、GFx、战斗服**上连赢四项，产生了「已经收尾了」的错觉。然后**用大厅的结论去覆盖房间**——这两条线从 138 卷起就是分开的，我却当成一条。

### 教训

> **★★ 「全部闭合」必须逐子系统列举并各自给依据。**
> 不能因为「我最近几项都很顺」就推断「剩下的也顺」。

这和 134 卷「完整性≠正确性」是同一类错误的另一个面：**那次是数量对内容错，这次是一个子系统的结论覆盖另一个子系统。**

## 二、审计一开，8 项里 6 项能当场闭

把 138–154 各卷「未闭合」小节拉出来，房间线剩 8 项。**其中 6 项我一小时内全闭了。**

这说明什么？**说明它们本来就不难，只是从来没被回头看。**

| 项 | 闭的代价 |
|---|---|
| `0x639D00` 调用者 | 一次 `callers()` = 1 处 |
| `0x7FA800` 槽 `+0x28` | 看一眼 `AddRef/Release` 就知道不是回调 |
| `0x7FA640` `+0x38..+0x40` | 一段 disasm = 8 个字段拷贝 |
| `0xE69D30` | 读 7 个指针 + 2 块数据 |
| 通道 `0x02/0x03` | 已有数据，只需判「预留」 |
| srpc 7 张表 | 一次构造序列扫描 = 17 行 |

**六项加起来不到一小时。**

对比一下：我在 154 卷给 `0xE69D30` 判了「类 5 参数行」，157 卷判「函数指针表」，159 卷才判对「(getter,data) 对」。

**三卷都在同一张表上打转，因为每次都是「看形状猜」，没有一次是「逐条读出键指向什么」。**

> **★ 教训：「未闭合」清单里躺着的东西，往往比新开的方向便宜得多。**
> 这是反直觉的——人本能地觉得「已经查过还没查出来的东西很难」，实际恰恰因为「已经查过」所以只要再补一刀。

## 三、第 6 项教了我一个新词：「构造期清空」

141/142 卷说「另 7 张表由谁注册未追」。

我的第一反应（写在 157 卷草稿里）是：「`srpc+4` 恒 0 ⇒ 每表最多 1 条 ⇒ 若为空表就没注册点可找」。**这还只是「猜它是空的」。**

159 卷我做了实证：

1. 找真构造函数 —— `0xD599DC` slot[0] 是**析构**，真 ctor 在 `0xB824F0`（因为它 `mov [esi],0xD599DC`）。
2. 扫出 17 个 `lea ecx,[esi+OFF] → call`，14 张表全在。
3. 看被调者 `0xB80CA0` **干什么** —— 它遍历桶、`call 0xB74240`（free）、最后 `mov [ecx],0`。

**⇒ 这不是「初始化一张空表」，这是「清空一张表」。**

### 为什么这个区别重要

- 「构造空表」⇒ 后面**应该有**注册点。
- 「构造期清空」⇒ 表在 ctor 里就是**被清干净的**，注册只可能发生在**运行期**（141 已证 68 个注册点）。

**同一个「找不到注册点」，两种答案对应完全不同的结论。**

> **★ 教训：判「表为空」要读的不是 count 的值，而是构造函数里对它的最后一个动作。**
> 写 `mov [ecx],0` 和写 `call <hash_init>` 是两回事。

## 四、`0xB76E50` 那个字节很有意思

`[esi+0x460]` 的构造器全长 **7 字节**：

```asm
0xB76E50  mov dword ptr [ecx], 0xDEADBEEF
0xB76E56  ret
```

**`DEADBEEF`。**

我在 45/5bit 卷里见过它（P2PInfo 槽的销毁哨兵）。这里是**未初始化哨兵**。

同一个魔数，两个用途：**销毁后标记** 和 **未初始化标记**。都是「这块内存不许被当真」。

这个细节本身不重要，重要的是：**它证明 14 张表的构造序列我把「特殊的那一个」也认出来了** —— 如果我只统计「14 个 call 到 0xB80CA0」，就会漏掉 `0x460`（`0xB76E50`）和 `0x220`（`0xBAEA50`，装 vtable `0xD5AA14` 的子对象）。

## 五、房间线现在的真实状态

**闭的：**
- 消息类型 / 43 类 vtable / 序列化器
- 入站五层门 / 双 blob / 47 表
- 出站两入队路 / 五通道 / UDP 漏斗
- 子系统构造（含上游 `0x7E98F0` 大厅初始化第 8 步）
- 容器（延迟环 / 主队列 / 槽结构 / 智能指针）
- 通道参数表 / `0xE69D30` / srpc 14 表构造

**没闭的只剩 1 项：4 字节服务名。**

而它不是「不会」，是**没有样本**：

> 我们手里 6848 条报文 **100% 是客户端→服务端**。服务端回包里那个 4 字节服务名，一次都没抓到。

**这一项用纯静态逆向永远闭不了。** 必须启动客户端抓包——那是需要授权的动作。

## 六、所以「大厅有黑箱吗」的准确答案

**协议方向**：
- 客户端**发出**的每一条：已全解（6848 条 100%）。
- 服务端**回**的：**只有 corpus 里那部分样本**；`6/5` 推送格式空白、4 字节服务名未知 —— **都是同一类：我们没抓过服务端主动发包。**

**框架层**：
- `.ff` 解密链路：**256 字节 RSA 密文来源未确定**（唯一缺口）。
- `ui_mp.ff` 内部结构：未解。

**房间**：客户端侧全闭，服务端应答侧空。

**结论**：
> 大厅不是「全黑」，也不是「全白」。
> **凡是「客户端自己产生/自己解析」的字节，全解了。**
> **凡是「必须看服务端怎么发」的字节，都空着 —— 而这一类只能靠抓包，不能靠静态。**

## 七、方法论（本卷新增四条）

1. **★★ 「全部闭合」必须逐子系统列举 + 各自给依据。** 一个子系统的绿灯不能照亮另一个。
2. **★ 「未闭合清单」里的项比新方向便宜。** 已查过 = 地形熟，往往只差最后一刀。
3. **★ 判「表为空」要读构造函数最后的动作**：`mov [ecx],0`（清空）vs `call <init>`（构造）——含义完全不同。
4. **★ 构造序列要列全表并标注特例**（17 个里 2 个是特例：`0xDEADBEEF` 哨兵 / 子对象 vtable）。
5. **★ 方向性缺口单独成类**：C→S 齐 ≠ 协议齐。
