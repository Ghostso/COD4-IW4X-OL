## 一、把大厅拆成两半

做完这一卷，我发现大厅可以清楚地分成两层：

### 内容层（服务端下发，明文）

```
模式列表      mp_playlists_*.info
公告          MOTD.info
活动          activities_v1.info
每日挑战      daily_challenge_config.info
商城排序      market_ui.info / sku_tags.info
广播          broadcast.info
```

**这些决定了"大厅里显示什么"。**

### 框架层（客户端本体，部分加密）

```
页面布局      ui_mp.ff
菜单定义      ui/default.menu
大厅逻辑      code_post_gfx_mp.ff
```

**这些决定了"大厅长什么样、怎么运作"。**

---

## 二、这个划分的意义

**"内容"和"框架"是可以分开改的。**

| 需求 | 改哪层 | 难易 |
|---|---|---|
| 换个公告 | 内容层 | 改 147 字节的 INI |
| 加个活动 | 内容层 | 改 417 字节的 INI |
| 加模式按钮 | 内容层 | 改 playlist |
| 改按钮位置 | 框架层 | 需要 AES |
| 加全新控件 | 框架层 | 需要 AES |

**用户说"加按钮删按钮" —— 如果按钮指的是"模式入口"，那在内容层。
如果指的是"页面上的某个 UI 控件"，那在框架层。**

**这两件事的难度差一个量级。**

## 三、一个具体的编码陷阱

我在写脚本打印文件内容时，Python 报错：

```
'gbk' codec can't encode character '\xe4' in position 6
```

**这在 Windows 上是常见问题** —— 控制台默认 GBK。

但这次它暴露了一个真实信息：`\xe4\xbd\xbf` 是 UTF-8 的"使"。

**于是我知道 `MOTD.info` 是 UTF-8。**

而 `playlist` 里的中文（`ÊµÕ½¶Ô¿¹`）是 GBK。

**同一个大厅系统，两套编码。**

这不是设计上的合理选择，而是**不同模块不同时期开发的遗留**。

**改文件时必须逐个确认编码，不能统一处理。**

## 四、`configs_s.info` 是个异常

所有 `.info` 里，只有它是二进制：

```
34 FE 6F 2C 4C D2 EC 77 ...
```

25KB，不是 zlib，不是文本。

**它可能是：**
- 加密的配置（有密钥）
- 某种自定义二进制格式
- 打包后的资源

**目前未解，但不影响主要路线**（模式/公告都不依赖它）。

---

## 五、方法论收获

> **先分清"内容"和"框架"，再决定投入。**

如果一开始就去啃 `ui_mp.ff`（框架层，加密），
会花很大力气，而且不一定成功。

而先做内容层（`publisher_files`），
**一天之内就能把"能改什么"全部摸清，而且全部可行。**

**"先做容易的，再决定难的要做到什么程度" 是合理的顺序。**
