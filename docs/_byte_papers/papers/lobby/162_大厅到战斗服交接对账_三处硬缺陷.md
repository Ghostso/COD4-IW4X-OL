## 三、🔴 硬缺陷 1（致命）：`security_key` 两边不一致，且**根本没人读**

### 3.1 大厅侧

```python
# lobby_server.py:460-462
SEC_KEY = b"\x00" * 16                     # ★ 全零常量
SEC_KEY_FILE = os.path.join(OUTDIR, "battle_security_key.txt")

# lobby_server.py:1400
with open(SEC_KEY_FILE, "w", encoding="ascii") as f:
    f.write(SEC_KEY.hex())                 # 写出 "00000000000000000000000000000000"
```

### 3.2 战斗服侧

```c
// battle.c:41-43
void codol_battle_init(codol_battle_t *b) {
    memset(b, 0, sizeof(*b));
    /* securityKey: 客户端 build 1649370 的 live 映射对 ID 1 保留 0x01 默认值 */
    memset(b->security_key, 0x01, sizeof(b->security_key));   // ★ 全 0x01！
```

### 3.3 而战斗服**从来不读那个文件**

全 `src` 搜 `battle_security_key` / `security_key`：

```
src/battle/battle.c:43    memset(b->security_key, 0x01, ...)      ← 唯一写点
src/battle/battle.c:155   codol_derive_transport_key(shared, b->security_key, ...)
src/crypto/p224.c:314,319 (参数声明与 memcpy)
```

**⇒ 没有 `fopen`/`read` 读 `battle_security_key.txt`。大厅写它，战斗服不读它。**

### 3.4 后果

```
大厅认为  security_key = 00 00 ... 00
战斗服实际 security_key = 01 01 ... 01
```

`codol_derive_transport_key(shared, security_key, transport_key)` 用它对 ECDH 共享秘密做派生。

**⇒ 如果客户端期望的是 `0x01` 那套，战斗服能通；如果期望 `0x00`，永远 HMAC 失败。**
**而大厅写的那个 `0x00` 文件是死文件 —— 两个组件在用两套不同的假设，没人发现。**

### 3.5 而 `0x00` 还是"暂用"标记

```python
SEC_KEY = b"\x00" * 16    # 16B securityKey; 真游戏服要配对的另一半, 暂用全 0
```

**源码自己写着「暂用全 0」。这个"暂用"值就一直留在了发布路径上。**

## 四、🟠 硬缺陷 2：`21/5` 回的会话对象里，`127.0.0.1:28960` 是常量

```python
# lobby_server.py:454-457
# 21/5 findSessions 的会话对象要用到的"权威服务器地址"。停服后我们本地没有真游戏服务,
# 先按配方里的既定值填 127.0.0.1:28960(与 SHARED.md 记的"21/5 含 127.0.0.1:28960"一致)。
GAME_IP   = (127, 0, 0, 1)
GAME_PORT = 28960
```

**问题**：

1. 大厅监听在 `127.0.0.2:3074`（`--lobby-bind` 默认 `127.0.0.2`），**战斗服却让客户端连 `127.0.0.1`**。
2. 注释说「与 SHARED.md 记的『21/5 含 127.0.0.1:28960』一致」—— **那是抓包观测到的历史值，不是我们主动选的。**

**⇒ 这个地址是"抄观测值"，不是"按我们自己的部署填"。** 如果战斗服绑在别的网卡/端口，这里就错。

## 五、🟠 硬缺陷 3：战斗服启动是"三条件与"，且默认不满足

```python
# lobby_server.py:1355-1369  （注释自承"逐条照抄 C# CodolLocalLobbyServer.cs:900-940"）
def maybe_start_battle_server(bind, port, lobby_bind):
    if lobby_bind != "127.0.0.2":           # 条件①
        return None
    if not os.path.exists(FR_BATTLE_FLAG):  # 条件②  firingrange-battle.enabled
        return None
    if not os.path.exists(script):          # 条件③
        return None
```

**三个条件任一不满足就静默不起**（只写日志，不报错）。

而 `run_all.py` **默认也会起一份战斗服**（源码注释自己警告）：

> 「⚠️ 注意: run_all.py 默认也会起一份战斗服; 若两处同时起会抢 28960 端口」

**⇒ 存在「两处抢端口」或「都不起」两种失败模式，且都不报错。**

## 八、可立即验证的一条（纯静态/纯本地，不需启动游戏）

**问：客户端期望的 `security_key` 是 `0x00…` 还是 `0x01…`？**

判据在客户端镜像里 —— 找 `codol_derive_transport_key` 对应的客户端实现，看它在哪取那 16 字节。

- 若客户端从**大厅下发的某个字段**取 ⇒ 大厅必须真的把 key 发下去（现在只写文件，没发）
- 若客户端**内嵌常量** ⇒ 该常量是什么值，战斗服就该用什么值

**这条一查，`security_key` 到底该是 0x00 还是 0x01 就定案了。**

## 九、方法论

1. **★★ 两个组件之间「传递了参数」不等于「传到了」。** 大厅写文件、战斗服不读 —— 这种「单向写入」最隐蔽（两边代码都没错，只是没接上）。
2. **★★ 占位值（`暂用全 0`）必须被追踪到落实为止。** 它躺在发布路径上，比缺代码更危险，因为它看起来像"已完成"。
3. **★ 抓包观测值不等于部署值。** `127.0.0.1:28960` 是"曾经观察到"，不是"按我们部署算出来的"。
4. **★ 静默不启动比启动失败更糟。** `maybe_start_battle_server` 三个条件任一不满足就 `return None`，只写日志。
5. **★ 这是第 4、5 次「写好了没接线」。** 同一模式反复出现，说明应该建立一个「组件间参数传递清单」而不是逐次发现。
