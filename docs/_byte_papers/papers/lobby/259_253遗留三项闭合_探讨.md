# 259 · 探讨：一个"越界运行期地址"是怎么被指令缝隙造出来的

> 配套：`259_253遗留三项闭合_wildcard表与伪造地址_5E3760记录链.md`

---

## 一、253 的这条记录读起来毫无破绽

253 卷 §6 边界表里写：

> `0x8269D40` 由 `0x80B450` 写入时用的源 `[eax*4 + 0x663D74C0]`，
> `0x663D74C0` **超出镜像范围**（镜像 0xE659000），说明那是**运行期地址**，
> 我无法静态看到它的内容。

它甚至**做了正确的边界判断**（镜像末地址 0xE659000 与 `0x663D74C0` 比较），
并且由此**诚实地标注为"未定"**，而不是编一个来源。

这正是最危险的一类记录：**证据看起来自洽，结论看起来克制，方法看起来严谨。**

唯一的问题是：**那条指令根本不存在。**

## 二、真相：四条指令的字节被缝成了一个 disp32

`0x663D74C0` 的字节序（小端）是 `C0 74 3D 66`。全库只有 3 处出现这 4 个字节。

逐处对齐反汇编后发现，三处**全都落在某条指令的中间**。以 `0x80B42B` 为例，
那里的真实指令是：

```asm
0x80B427  83 C4 04    add  esp, 4
0x80B42A  85 C0       test eax, eax
0x80B42C  74 3D       je   0x80b46b
0x80B42E  66 ...      (下一条指令的前缀)
```

`C0`（test 的 ModRM）、`74 3D`（je 的字节）、`66`（下一条的 66 前缀）
**首尾相接**，恰好拼出 `C0 74 3D 66`。

而从 `0x80B428` 起读（`C4 04 85` → `les eax,[eax*4+disp32]`），
capstone 忠实地把 `C0 74 3D 66` 当成了位移 —— **`0x663D74C0` 就此诞生。**

**它不是"超出镜像的运行期地址"，它是"跨越四条指令的字节巧合"。**

## 三、为什么 253 会从 `0x80B428` 起读

253 的脚本 `a11_other_tables.py` 里：

```python
st = s - 0x28                     # s = 0x80B450
for ins in md.disasm(blob[st-BASE: s-BASE+0x40], st):   # st = 0x80B428
```

它取了兴趣点前 0x28 字节作为窗口起点 —— 而 `0x80B428` 不是任何指令的边界。
**"从目标往上退 N 字节"是一个没有对齐保证的启发式。** 于是窗口的第一条就已经是幻影，
后面整条链全乱（`mov edx,[eax]` 读的是假指针）。

对照本卷的读法：从**函数起点 `0x80A630`**（其前 8 字节是 `... c3 cc cc`，
`CC CC` 填充确认它是函数边界）线性扫到 `0x80B450`，得到的是：
`mov ecx,[edi+0xc]; imul eax,ebx; mov eax,[ecx+eax*8]` —— 一个**运行期容器的字段索引**，
与"越界常量基址"毫无关系。

## 四、教训

**当结论是"这个地址落在镜像外面"时，先别急着解释它是运行期地址 ——
先问：这条指令真的从那里开始吗？**

- **地址越界是"不可能的先兆"，不是"结论"。** 一个 disp32 落在镜像外，在 PE 里
  通常意味着**你读错了**，而不是"软件用了固定高地址"（那需要 reloc 或特殊分配器，
  真发生时附近一定有线索）。
- **"从目标上退 N 字节"读到 `ret`/`int3` 才回退** ——本项目的读法应该是
  **找到函数起点（`CC CC` 或 `push ebp;mov ebp,esp`）再线性扫**，任何"窗口"都从函数起点算。
- 这条与 AGENTS.md 已经写明的「反汇编从函数起点读到 `ret`/`int3`」是**同一条规则**，
  只是 253 在"读点上下文"这种小脚本里**放松了它** —— **方法论不会因为脚本短就失效。**

（换句话：253 在论文正文里严格遵守了"从函数起点读到 ret"，却在辅助脚本里为了方便
"退 0x28 字节"——**严格性一旦被脚本的便利性侵蚀，幻影就会从脚本里爬进论文。**）

## 五、这一卷的另一半：把疑问句变成 grep

253 留的第一项是「**谁调用数组重建器 `0x5DE440`？`0x7EC650` 是不是唯一调用者？**」

这个问题的答案是一次全库 `E8 rel32` 扫描：**是**，且只有它一个。

值得记的是：**253 已经有工具做这件事**（它自己的 `a10_indexrefs.py` 就在扫全库），
但它把这个问题**当成了"待查"**而不是"跑一下"。**疑问句写下来时，
应当顺手判断它是不是已经可以被现有工具直接判定** —— 能判就立刻判，别留成"开项"。
