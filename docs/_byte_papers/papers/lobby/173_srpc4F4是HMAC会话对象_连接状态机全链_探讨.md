# 173 探讨 · 我上一轮把一个对象指针当成了开关

## 一、172 卷的错误，一句话说完

上一轮我写了：

> `srpc+0x4F4` 是状态闸门，`0xB7A670` 返回 1 当且仅当 `[srpc+0x4F4] != 0`……

这句话**逻辑上没错**，但**语义全错**。`!= 0` 不是"标志被置位"，是"**这个指针非空**"。

我犯的具体错误是：看到一个 `test ecx,ecx / je`，就默认它是布尔。没有问"这个 ecx 是从哪来的"。

## 二、怎么查出来的

上一轮我说"16 个候选写点，无一可静态归属"。这句话本身就说明我没查透 —— 一个偏移的写点怎么会数不清？

这一轮换了写法：**先用 ModRM 精确筛（`mod==10` 才是 disp32），再对每条 `mov [X+0x4F4], reg` 反解这个 reg 的最近赋值**。

结果：

```
7 个写点
├─ 0x847155  ebx = 0   (xor ebx,ebx)
├─ 0x8B3F89  edx = 0   (xor edx,edx)
├─ 0xB81EA3  ebx = 0
├─ 0xB81FFD  esi = call 0xBA2800 的返回值   ← 唯一的非零
├─ 0xB82404  ebx = 0
├─ 0xBA92C6  edi = 0   (0xBA923C xor edi,edi)
└─ 0xBA9339  eax = 0   (0xBA9312 xor eax,eax)
```

六个清零，一个对象。**这不是"无一可归属"，这是"一目了然"。**

## 三、这个对象是什么

`0xBA2800` 的 vtable 是 `0xD5A4F4`。我本来想追 RTTI，但那次 RTTI 解析失败了（COL 落在 `.rdata` 之外）。

**转念去看这个 vtable 旁边的字节**：

```
0xD5A4E8: "CLIE"
0xD5A4EC: "NTCH"
0xD5A4F0: "AL"
0xD5A4FC: "HMAC"
0xD5A500: " mis"
0xD5A504: "matc"
0xD5A50C: "HMAC"
0xD5A510: " cal"
0xD5A514: "cula"
0xD5A518: "tion"
```

`CLIENTCHAL` —— 这正是 163 卷记录的客户端 KDF 标签。然后是 `HMAC`、`Hmac mismatch`、`Hmac calculation`。

**结论直接掉出来了：`srpc+0x4F4` 是一个绑定 `CLIENTCHAL` 的 HMAC 会话对象。**

## 四、这意味着什么

`0xB7A670` 的真实语义：

```
if (srpc->hmac_session == NULL) return 0;
return (srpc->force_flag || hmac_session->query_state() == 2);
```

翻译成人话：**"客户端有没有建立且认证过 HMAC 会话"**。

于是"房间里点准备/改阵营/投票没反应"的解释变成：

> 客户端的 srpc HMAC 会话没建起来（或没认证到状态 2），
> 所以 `0x7E8300` 出口前的三道门全挡住，消息根本没上网。

**不是服务端少分支，也不是某个 flag 忘了置。**

## 五、上溯把整条链也串上了

追 `0xB81FFD` 的唯一上游：

```
0x7F26C0  大厅状态机（[0x84ABA50]）
  └ 0x7F276A → 0x7F3800   连接状态机（[0x84ABA7C] 0→1→2）
      ├ 0 → 0x7F3890 → 0x803830(取srpc单例) → 0xB82070 → 0xB81EF0(建会话)
      └ 1 → 0xB838A0(投递链) → 0xB7A670(查会话) → 跳表 5 case
              case1 → [0x84ABA7C] = 2   （成功）
              case0 → [0x84ABA7C] = 0   （失败重来）
```

这条链与记忆里的 `codol-lobby-boot-chain-12-layers` 一字不差：

```
[0xe59d20] → [0x8269774] → +0x4F8 → 0xb7a670()==2 → [0x84aba50]==5
```

**那条记忆里写的 `0xb7a670()==2`，现在有了实体：HMAC 会话认证状态 == 2。**

## 六、还开着的

诚实说，只有一条真的还开，而且是位流层的：

**`[obj+0x21]`**（`0xD59838` 位流写器对象的第 0x21 字节）。

- `0xB77B30` 是它的 ctor，只写 vtable，**不碰 `+0x21`**
- 基类 ctor `0xBC18B0` 只写 `0xD5B094`，也不碰
- 全镜像 16 个 `mov byte [reg+0x21], …`，没有一个落在这条构造链上

所以 `0xB77B10` 到底是"写 n 个 0 位"还是"什么都不写"，取决于一个我在静态里定位不到的初始化点。

**这条我留着，不假装闭合。**

其余的（`0xBA0780` 的 `[+0x644]`/`[+0xC8]` 语义、`0x84ABB08/0C` 两个全局、实机是否走完 0→1→2）都是"已定位到地址，语义没展开"，不是黑箱。

## 七、这轮方法上得到的

1. **看到一个 `test reg,reg / je` 先问 `reg` 从哪来。** 布尔和指针在这一条指令上长得一模一样。
2. **偏移的写点必须精确筛 ModRM。** 我上一轮的"16 个候选"里至少 9 个是错位反汇编出来的假指令。
3. **RTTI 解析失败不要放弃，去看 vtable 旁边的字符串。** 这次 `CLIENTCHAL` 是直接摆在那里的，一行都不用算。
4. **"逐条反解写入值"是必须做的一步**，不能因为"写点太多"就跳过 —— 事实是只有 7 个。
