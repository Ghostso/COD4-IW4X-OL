# `IWff0100` 分支的完整追踪

> 承接 `lobby/35`
> 本篇给出这条分支**到底做了什么**的完整答案。

---

## 1. 分派器的完整控制流（`0x483db0`）

```
0x483dd8  call 0x484b70        ; 读文件（Buffer 初始化）
0x483de3  call 0x484940        ; read 8 bytes -> [ebp-0x10]
0x483df0  cmp [ebp+ecx-0x10], "IWff0100"    ; 4 字节对比 ×2
0x483dfa  jne 0x483e09
0x483e07  jmp 0x483e2b         ; ★ IWff0100 → 直接汇合

0x483e09  cmp [ebp+ecx-0x10], "IWffu100"
0x483e1a  jne 0x483edf         ; 都不是 → 报错

0x483e2b  read u32 -> [ebp-0x40]   ; 版本
0x483e3b  cmp eax, 0x1cd (461)
0x483e40  je  0x483e68         ; 版本匹配 → 继续
0x483e42  ... 打印 "283/284 %s %d %d" 错误并返回

; ★★ 两条路径在此**完全汇合**，后面的代码不区分魔数
0x483e68  read 1 byte  -> [ebp-0x39]
0x483e75  read 4 bytes -> [ebp-0x44]
0x483e82  read 4 bytes -> [ebp-0x48]
0x483e8f  read 8 bytes -> [ebp-0x10]

0x483e94  cmp [ebp-0x10], "IWffu100"    ; ★ 这里再次判断
0x483ea4  jne 0x483ee4                   ; 不是 IWffu100 → 跳过
0x483ed3  call 0x483b40                  ; 只有 IWffu100 才解密
```

---

## 2. `IWff0100` 的实际处理

**它走 `0x483e2b` → `0x483e68` → `0x483ee4`，即：**

```
读版本(461) → 读 1+4+4+8 字节头字段
→ 比较 [ebp-0x10] 与 "IWffu100" → 不等 → 跳过解密
→ 进入链接阶段
```

**结论：`IWff0100` 在加载时不做任何解密。**

---

## 3. 跳过解密后做什么（`0x483f18` 起）

```
0x483f18  lea eax,[ebp-0x38]; mov ecx,0x28; call 0x484a00   ; 分配 0x28
0x483f2c  call 0x49a4d0                                     ; 某个注册
0x483f3a  call 0x49a4d0                                     ; 再次
0x483f41  mov [0x2f79af4], [ebx]
0x483f49  mov [0x2f79af8], [ebx+8]
0x483f52  mov [0x2f79afc], [ebx+0x10]
0x483f5d  mov [0x2f79b00], [ebx+0x18]
0x483f68  mov [0x2f79b04], [ebx+0x20]
0x483f71  mov [0x2f79b08], [ebx+0x28]
0x483f7a  mov [0x2f79b0c], [ebx+0x30]
0x483f82  mov [0x2f79b10], [ebx+0x38]
```

**这是把 `[ebx]` 起始的 8 个 u64 复制到全局表。**

`[ebx]` 是 `0x49ed40` 加载器里的一个结构，**不是 `.ff` 文件头**。

---

## 4. 关键否证：那 8 个 u64 不是文件内的偏移

实测 `mp_playlists.ff` 的 `+0x14` 起 8 个 u64：

```
0xe2c1d35735ed9100   16,339,573,294,597,247,232
0xc8c8390f770741c6   14,467,876,541,511,975,366
0x55b1fe33ffad1327    6,174,996,063,387,980,583
...
```

**全部 ≫ 文件长度 49,493。**

**⇒ 这些不是指针/偏移，是密文字节。**

**⇒ `.ff` 的载荷从 `+0x14` 起就已经是密文了。**

## 5. 全量交叉验证

对 6 个不同来源的 `.ff` 做同样检查：

| 文件 | 大小 | magic | ver | f12 | f16 | 熵 |
|---|---|---|---|---|---|---|
| `mp_playlists.ff` | 49,493 | IWff0100 | 461 | 1 | 0 | 7.947 |
| `common_mp.ff` | 77,605,093 | IWff0100 | 461 | 1 | 0 | 7.950 |
| `common_loadscreen.ff` | 24,885 | IWff0100 | 461 | 1 | 0 | 7.959 |
| `localized_common_mp.ff` | 192,434 | IWff0100 | 461 | 1 | 0 | 7.959 |
| `code_pre_gfx_mp.ff` | 74,085 | IWff0100 | 461 | 1 | 0 | 7.958 |

**五个文件、跨 3 个目录，头字段完全一致（`ver=461, f12=1, f16=0`），
每 4KB 熵全部 7.95–7.96。**

**这说明它们是同一套加密，且加密覆盖整个载荷。**

---

## 6. 那 8 个 u64 的真实含义

`0x483f41`–`0x483f82` 复制的是 `[ebx+N]`，而 `ebx` 来自 `0x49ed40` 的
参数 —— **那是"加载器对象"，不是文件头。**

所以这 8 个值来自加载器的运行时状态
（例如：文件句柄、映射基址、大小），与 `.ff` 内的字节无关。

---

## 7. 一个反向推论

既然 `IWff0100` 在加载时不解密，而载荷确实是高熵的：

**两种可能：**

### A. 解密在别处（尚未找到）

`.ff` 读取时先解密再交给这个分派器。
**那我们要找的是"读文件 → 解密 → 交给分派器"这一段。**

### B. 客户端从头到尾不解密，载荷始终是密文

那么 `.ff` 的内容由**别的组件**（可能是 TP3 保护层）在
**内存中**解密，磁盘上永远是密文。

**第 B 种与项目已有记录一致：**
`iiips` 的 `IIPSVFS.dll` 提供内存映射，TP3 可能在映射后解密。

---

## 8. 结论

| 项 | 状态 |
|---|---|
| `IWff0100` 分支流程 | **完全确定**（不调用 `0x483b40`） |
| 版本字段 | 必须 `461` |
| 头后 8 个 u64 | 是密文，不是偏移 |
| 全部 `.ff` 是否同构 | **是**（5 个样本） |
| 解密在哪 | **未找到** |

**本轮把"这条分支做什么"彻底查清楚了：
它只做"校验 + 注册 + 链接"，不做解密。**

**解密必然发生在它之前（读文件时）。**
