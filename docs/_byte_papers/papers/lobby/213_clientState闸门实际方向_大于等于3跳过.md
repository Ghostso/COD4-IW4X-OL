## §2 更正 138 卷

138 卷记忆写：「`[0x76446B0]` = clientState(CA_*)，**开局闸门 <3**」。

★ "闸门 <3" 这个表述**容易被理解成"<3 才放行"**。

**实际代码是 `>=3 时跳过`**，即：
- `clientState < 3` → **继续走这个路径**（构造 StartGame 发给对端）
- `clientState >= 3` → **跳过**（因为已经在房间里，不需要再发）

★★ **语义正确理解**：`0x632680` 是"**通知对端我准备开局**"的路径，
只在"还没进房间（clientState<3）"时才需要发。

★ 这与 190 卷的 `StartGame` vs `StartGameFailed` 逻辑**一致**：
- `clientState == 0`（未进）→ 构造 `StartGame`（190 卷）
- `clientState != 0` → 构造 `StartGameFailed`

★ 但 213 卷这里是 `>= 3` 才跳过，`1..2` 仍继续 —— 比 190 卷的 `!= 0` 更细。

## §3 其余五道门的语义

| 门 | 字段 | 语义 |
|---|---|---|
| 1 | `[esi+0x278]` | 某开关（布尔） |
| 3 | `[esi+0xE360]` | 槽索引 ≥ 0 |
| 4 | `[esi+0x3A048]` | **对端 ID 低 32 位** |
| 5 | `[esi+0x3A04C]` | **对端 ID 高 32 位**（u64 分成两半） |
| 6 | `strcmp(参数, 0xDC69B0)` | 某字符串匹配 |

★★ **门 4/5 合起来是"对端 u64 ID 必须匹配 `[esi+0x3A048..4C]`"** ——
这是**目标房间/会话的 ID 校验**。

⇒ **StartGame 只能发给"ID 匹配的那个对端"。**

## §5 对服务端的直接意义

★★★ **StartGame 发送必须满足 6 个条件，其中门 4/5 是"对端 ID 匹配"。**

⇒ **服务端若发 StartGame，客户端的 `[esi+0x3A048/4C]` 必须等于服务端提供的 ID。**
   而这个 ID 是**客户端自己记录的**（来自之前的握手/房间创建）。

★ 这解释了"服务端随便发 StartGame 无效"。

## §6 方法论

1. **★★★★ `cmp [全局],N / jge <skip>` 的方向必须精确记录。** "闸门 <3" 这种模糊表述会导致完全相反的结论。
2. **★★★ 一个函数开头的连续 `cmp/je` 是"准入条件表"，必须全部列出。**
3. **★★ u64 ID 分成 `[X]` + `[X+4]` 两个 dword 比较，是 x86 的常见模式。**
