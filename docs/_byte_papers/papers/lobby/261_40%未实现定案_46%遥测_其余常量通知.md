## §0 结论

**232 的「40.4% 流量未实现」不是一个"坏"的比例 —— 本卷把它拆开：
46.4% 是遥测（服务端本就不该应答），其余绝大多数是"常量通知"消息（无需数据应答）。**

1. **★★★★★ 复算逐字命中**：`corpus.json` 6848 条，服务端覆盖 31 个 (svc,task)，
   未覆盖 **2767 条 = 40.4%**（与 232 **完全一致**）。
2. **★★★★★ 最大一片 = 遥测**：`svc 71` 合计 **1285 条 = 未覆盖的 46.4%**（占总流量 18.8%）。
   载荷是**明文 ASCII 事件日志**（`ClientOffline|...` / `TimerErrors|...` / `ClientLogin|...`）或
   其 zlib 打包（`71/15`）。**这类消息语义上不需要服务端返回数据 ⇒ "空 ACK"是正确行为。**
3. **★★★★ 其余未覆盖 = 常量"通知/订阅"消息**：绝大多数 (svc,task) 的载荷**只有 1 个不同取值**
   （见 §3 表）⇒ 是固定格式的"我在这里/我订阅了"，服务端无需返回内容。
4. **★★★★ `4/13`（未覆盖第二大，290 条）载荷携带账号核心 ID `0xE7C8A98A6B4C2D0E`**
   （u64 字段，载荷偏移 11）—— 与记忆里"三核心 ID"的账号 ID 逐字节相同。
5. **★★★ 结论用一句话**：**「40.4% 未实现」里没有证据显示"客户端在等数据"**；
   按载荷可变性分类，需要服务端实现的是**可变载荷**的少数（`71/15` 是遥测，仍不需 ACK）。

## §4 ★★★★ `4/13` 载荷 = 账号核心 ID

## §5 ★★★★ 这一卷真正改写的东西

232 的措辞是「**40.4% 流量未实现（功能未实现）**」。本卷把它改写成：

```
40.4% UNMAPPED
  ├── 46.4%（占未覆盖） 遥测 svc71     → 空 ACK 是协议正确行为（无数据契约）
  └── 其余          常量通知/心跳      → 空 ACK 不破坏（无数据契约）
       ★需要复核的只有"可变载荷且非遥测"的：本卷未发现（71/15 是遥测）
```

**"未实现"这个词暗示了"应该实现而没实现"。真正的判据是"客户端是否在等返回数据"。**
本卷用**载荷可变性**做代理判据：**常量载荷 ⇒ 客户端不依赖服务端字段**（一个固定串，回什么都不影响它解析自己的常量）。

★ **与 235 的边界一致**：235 警告「空 ACK 判据是服务私有，勿外推」——
本卷**不外推任何极性**，只做"载荷可变性 + 是否需要数据"的**语义分类**，
这两件事不冲突（235 讲"怎么判失败"，本卷讲"该不该有数据"）。

## §8 方法论

1. **★★★★★ "未实现率"不是"故障率"，先按"是否需要数据"分类。**
   40.4% 这个数在 232 里读起来像"四成功能是坏的"，但拆开后 **46% 是遥测**——
   **一个比例数字要先拆成"有数据契约"和"无数据契约"两桶，再谈好坏。**
2. **★★★★ 「载荷可变性」是"是否需要服务端数据"的静态代理判据。**
   客户端发**常量** ⇒ 它不期待服务端字段（否则字段会变）；发**变量** ⇒ 可能期待。
   **不需要运行时就可用语料做这个分类。**
3. **★★★ 名字（"UNMAPPED"/"未实现"）会框住后续推理。** 服务端代码里的措辞
   `"UNMAPPED ... 功能未实现"` 是**作者的一句话**，不等于"客户端需要它"。
   **读到"未实现"要立刻问：谁判定它"应该实现"？**
4. **★★★ 跨材料对账（语料 ↔ 建造器 ↔ 服务端）比单一材料可靠。** 本卷三材料互指：
   语料给"发了什么"，建造器给"怎么发的"，服务端给"回了什么"。
