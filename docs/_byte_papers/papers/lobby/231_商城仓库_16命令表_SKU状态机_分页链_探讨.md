# 231 探讨 · 商城仓库为什么"有 3 万件库存，商城却是空的"

> 配套：`231_商城仓库_16命令表_SKU状态机_分页链.md`
> 本篇不重复结论，只讨论**判据、误区、以及这次差点又走错的三处**。

---

## 一、先摆事实：一组自相矛盾的实机数据

同一份日志、同一秒（`23:50:41`）、同一个客户端 PID：

```
80/230 玩家资产 193579 字节        ← 我们下发了 35741 件库存
80/70  空应答
80/107 空应答
80/119 空应答
80/173 空应答
80/174 空应答
80/232 空应答
```

`marketplace-inventory.json` 里 `Items` 有 **35741** 条。

**如果我们只看服务端，会得出「服务端有数据，客户端不显示 ⇒ 服务端格式错」。**

这个推论在过去几轮里反复出现过，并直接导致了「自编 SKU 页」的实验——然后服务被打挂（160 卷记载）。

**但这个推论的前提是错的。** 本卷给出的证据是：客户端**根本没在等我们的目录页**。

---

## 二、为什么"根本没在等"——状态机的单向性

`[0x82C4A88]` 全库有 **9 个写点、7 个 `==3` 读点**。这说明它是一个被**广泛消费**的状态量。

关键在于写入值分布：

| 写入值 | 写点数 | 含义 |
|---|---|---|
| **3** | **1**（`0x4A7E37`） | 目录就绪 |
| 2 | 6 | 错误 / 未认证 |
| 1 | 1（`0x4A9443`） | init 完成 |
| 变量 | 1 | — |

而 `0x4A7E37` 所在的函数 `0x4A7E20` 第一句就是：

```asm
0x4A7E20  cmp dword ptr [0x82C4A88], 1
0x4A7E27  jne 0x4A7E56        ; ★ 不是 1 就直接返回
```

**⇒ `state=3` 的唯一入口要求「当前恰好是 1」。**

而 `state=1` 的唯一写点 `0x4A9443` 前面有三道门：

```asm
0x4A941F  test esi, esi         ; srpc 单例非空
0x4A9421  je   0x4A9455         ; → 直接返回
0x4A942A  cmp  eax, 2           ; 0xB7A670() 必须 == 2
0x4A942D  jne  0x4A9455         ; → 直接返回
0x4A9436  call 0xB81250         ; 空串查对象
0x4A943D  je   0x4A9455         ; → 返回 0 也直接返回
0x4A9443  mov  [state], 1       ; ★ 只有三道门全过
```

**这三道门和 172/173 卷的房间类完全相同**（`srpc+0x4F4` 是 HMAC 会话对象，认证状态 == 2）。

**⇒ 房间类和商城类卡在同一个地方。** 这不是巧合——它们都走 `0x803830` → `0xB7A670` → `0xB81250` 这条 srpc 认证链。

### 2.1 ★★★★★ 但真正的杀手是第二道门：我们自己回的空页

写完上面那一段之后我又追了一步，发现**认证门不是主要矛盾**——日志证明客户端**已经**发出了 6 个目录请求（能发出 ⇒ 认证必过）。真正的死锁在**响应判定**：

三个响应回调用的是**逐字相同**的判据：

```asm
; 0x4A7FB0（0x5a 分页回调）
0x4A7FBE  cmp  byte ptr [eax + 5], 0      ; reply+5
0x4A7FC2  je   0x4A7FCD                   ; ★ ==0 → 失败
0x4A7FDE  mov  [0x82C4A88], 2             ; ★ state = 2

; 0x4A8200（0x59 getskus 回调）
0x4A820D  cmp  byte ptr [eax + 5], 0
0x4A8234  mov  [0x82C4A88], 2

; 0x4A8400
0x4A83FC  cmp  byte ptr [eax + 5], 0
0x4A841B  mov  [0x82C4A88], 2
```

**我们回的「空页」= `reply+5 == 0`（无数据）⇒ 客户端判定失败 ⇒ `state=2`。**

然后 `state=2` 有自己的定时重试：

```asm
0x4A9850  mov  eax,[0x82C4A88]
0x4A985E  sub  eax, 2
0x4A9861  jne  0x4A98DD          ; 非 2 跳过
0x4A9886  fld  dword [0x849B800+0xC]   ; 重试间隔
0x4A98CC  je   0x4A98DD          ; 未到时间
0x4A98D8  call 0x4A93E0          ; ★ 重新 init → state=1
```

**闭环：`state=1` → 发请求 → 我们回空 → `state=2` → 等定时器 → `init` → `state=1` → …**

**这就是日志里 6 个 task 周期性重复的原因。** 我一直把「客户端还在请求」当成「客户端在工作」，实际上那是**失败重试**。

### 2.2 一句话把因果钉死

| 环节 | 实际 | 我们以为 |
|---|---|---|
| 客户端发请求 | ✅ 有（认证已过） | 有 |
| 我们回空页 | ✅ 有 | 「安全」 |
| 客户端判定 | ❌ `reply+5==0` ⇒ 失败 | 「不炸就是对的」 |
| state | **2（失败）** | 以为 3 |
| 商城 UI | **不渲染** | 以为是格式问题 |
| 日志重复请求 | **失败重试** | 以为「客户端在正常工作」 |

**⇒ 「回空页安全」是过去所有商城/仓库实验里最贵的一个误判。它让每个实验都得到了「不崩但也没用」的结果，而我们把原因归到「字段序错」。**

## 三、由此推翻的两个旧判断

### 3.1 「自编 SKU 页打挂服务 ⇒ 我们的字段序错了」

160 卷把「发 3 条自编 SKU 就把整个 marketplace 打挂」归因为**字段序错**，并据此把方向定为「必须拿到真实 SKU 页字节」。

本卷看这个结论**不完整**：

- 字段序错**确实**会导致崩溃（21 个槽位，多两个 CODOL 专有字段，错一字节就崩）；
- 但**回空页也不显示**，且**空页让 state 走成 2**，说明还有一层前置条件；
- 前置条件就是 `reply+5 != 0` 且条数 > 0。

**⇒ 正确表述是：先让 `reply+5 != 0` 且条数 > 0（进 `state=3`），再谈字段序。** 顺序反了会一直在「猜格式」上打转。

★ 而且现在能解释「为什么自编 3 条会打挂」：**那 3 条让 `reply+5 != 0`、条数 = 3 > 0，`state` 真的走到了 3，UI 真的去渲染了**——于是 21 个槽位的字段错立刻炸。**空页和自编页的差别不在"安全"，而在"前者不渲染所以不炸，后者渲染了所以炸"。**

### 3.2 「`marketplace` 服务 enable=0 却高频发请求」

221 卷说「enable 位 ≠ 发不发请求」，并把它当方法论。

本卷给出机制：`enable` 影响的是 `0xB81250(空串)` 能否取到对象，而对象取不到 ⇒ 三道门最后一道 `je 0x4A9455` 直接返回 ⇒ **state 永远到不了 1**。

★ **更准确的判据**：`enable` 不是「协议开关」，也不是「状态上报开关」，而是**「对象可否实例化」**。

## 四、这次差点又错的三处（方法论价值高于结论）

### 4.1 差点把控制台命令表当成网络 task 表

`0xDB6CE0..0xDB6E88` 有 16 条 `marketplace.*` 字符串，紧跟 `0xE6E640` 的 `MarketEventHandler` RTTI。

**第一直觉（错误）**：这是 `80/70`、`80/107`… 的 task 名表，可以拿来做 task 号映射。

**实际（正确）**：旁边是 `0x4A9A60`，它对每个名字 `call 0x4F37A0`。反汇编 `0x4F37A0`：

```asm
0x4F37A0  mov eax,[0x33303B0]
0x4F37B0  mov edx,[eax+4]        ; 节点里的名字
0x4F37B5  mov bl,[ecx]           ; 逐个字符比较
...
0x4F37DA  test ecx,ecx
0x4F37DC  je   0x4F37E6          ; 找到 → 返回非 0
```

**这是线性链表的字符串查重**，标准 `Cmd_AddCommand` 前置检查。网络 task 派发表是 `0xE4E8F8`（服务名+enable）和 `0xE4E20C→0xE69CE0`（通道号→重试策略），结构完全不同。

★ **判据**：**看「调用者用哪张表判断重复」。** 用链表 = 控制台命令；用固定索引表 = 网络服务。

### 4.2 差点把 `0x4A7E80` 当成写 `state=3` 的函数

我用「`blob.find(u32(state_addr))` → 从 `hit-7..hit-1` 逐个尝试解码」的办法找引用点，得到：

```
0x004A7E38  add eax, 0x82c4a88
```

然后看到 `0x4A7E37 mov [state],3`，就以为函数是 `0x4A7E80`。

**错在哪**：`0x83 3D 88 4A 2C 08 01` 是 `cmp dword ptr [0x82c4a88], 1`，7 字节。绝对地址在指令的 **+2** 位置。我从 `hit-1` 开始解，`C3 83 3D ...` 被解成 `add eax, 0x82c4a88`——**指令边界错位了一个字节**。

**正确做法**：按 x86 编码形式建表：

```python
FORMS = [(b"\x83\x3d", 2, "cmp dword,imm8"), (b"\xc7\x05", 2, "mov dword,imm32"), ...]
# 对每个 hit，用 ref - offset 回推指令起点，再看前缀字节是否匹配
```

★ **这不是第一次犯**。记忆里 `codol-mmi-lowregion-vs-networkregion` 写着「反汇编必须从函数起点且遇 ret/int3 即停」；`codol-208` 写着「零数据引用先查 EH unwind 表」。**同一个病，第四次发作。**

### 4.3 差点漏掉 `0x4A7E18..1F` 的 8 个 `CC`

修正 §4.2 之后，我以为 `0x4A7E20` 和 `0x4A7E80` 是同一个函数的两个位置（中间只隔 0x60 字节）。

**实际**：`0x4A7E18..0x4A7E1F` 是 **8 个 `0xCC`**，明确是两个函数的分界。`0x4A7E20` 是独立函数，`0x4A7E80` 是另一个。

**⇒ 「距离近」不等于「同函数」。** 必须扫 `CC CC` 边界。

## 五、真正该问的问题变了

旧问题：**「SKU 页的字节格式是什么？」**

新问题：**「怎么让 `reply+5 != 0` 且条数 > 0？」**

这是一个第一次**有了明确判据**的问题。三条可静态推进的路：

| 待查 | 方法 | 可判定性 |
|---|---|---|
| **`reply` 对象是谁构造的**（`reply+5` 谁写） | 反汇编 `0xB86A40` 的调用链上游 / `0x7FAB70` 的 `0x7FA800`；找 `mov byte [reg+5], imm` 且 imm≠0 的点 | 纯静态，**最高优先级** |
| 条数容器 `+0x44`/`+0x24` 谁填 | 反汇编 `0xB83D50`/`0xB83D20` 的写侧（`+0x44`/`+0x24` 的 setter） | 纯静态 |
| `0xB81250(0xDAE091)` 查的是哪个对象 | 反汇编 `0xB81250` 后半段（`0xB812A4` 之后） | 纯静态 |
| `0x4A9850` 是 FrameUpdate 吗 | 唯一调用者 `0x7EEC8D`，在 `0x7EEBF0`（帧回调批）里 | 已定位，可确认 |
| `0x849B800+0xC` 重试间隔变量 | 找 dvar 名（`dw_marketplaceInitRetryInterval` 在 `0xDDF648`） | ★ 已有线索！ |

★ **`0xDDF648` = `"dw_marketplaceInitRetryInterval"`** —— 这就是 `0x4A9886` 读的那个重试间隔。**221 卷没有把它和状态机联系起来。**

**这些全部可以在不启动客户端的情况下继续追。** 按 AGENTS.md 的 GPT-6A 原则，「需要实机」不能当停手理由。

## 六、这次的方法论：三个「以为安全」的假判据

| 假判据 | 为什么当时觉得对 | 为什么会错 |
|---|---|---|
| **「回空页不崩 ⇒ 安全」** | 实测确实不崩 | 不崩 ≠ 正确；空页让 state 走失败分支 |
| **「日志里请求在重复 ⇒ 客户端在正常工作」** | 有周期、有规律 | 那是**失败重试环**，不是正常轮询 |
| **「仓库有 35741 件数据 ⇒ 服务端数据是对的」** | JSON 里数字确实在 | 目录页（`80/70`）和库存页（`80/230`）是**两条不同的链**，前者空不影响后者 |

★ **共同点：三个判据都是「没有负面信号」⇒ 判定「正确」。这是本卷最值得记住的一条——负面信号的缺失不是正面证据。**

---

## 七、一句话总结本篇

**「有 3 万件库存但商城空」不是格式问题：我们自己回的「安全空页」让客户端 `reply+5==0` ⇒ `state=2` ⇒ 永不进 `state=3` ⇒ UI 不渲染 ⇒ 定时重试 ⇒ 日志看着像"在工作"。修法不是猜 SKU 字节，是先让 `reply+5 != 0` 且条数 > 0——而这一条现在有了明确的机器指令判据（`0x4A7FBE`/`0x4A820D`/`0x4A83FC`）。**
