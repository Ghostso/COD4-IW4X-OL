## 一、这条"未独立验证"是什么意思

`INDEX §七 #3` 写：「帧头 / 加密 / CRC 层**未独立验证**」。

意思是：**我们所有关于帧结构的认识，都来自三方 C# 参考**（`codol_crypto.py` 开头就写"逐字段照抄三方 CodolLocalLobbyServer.cs"）。三方说帧是 `u32 len | 0xAB | 0x85 | seq | iv | cipher | hmac8`，我们就照着实现——**但我们从没在客户端里证明过它真是这样。**

按 `AGENTS.md` 的可信度分级：**本地逆向 > IW4X > CoD4X > 其他**。三方 C# 参考属于"其他外部项目"，**最低可信度**。这条黑箱不闭，整个帧层就一直挂着"可能被三方误导"的风险。

## 二、怎么验证：不是读代码，是找"表"

我一开始想"找个反汇编窗口看 AES 怎么调用"。那个方向又慢又脆（虚拟化壳，`.text` 都不在）。

**换了思路：AES 一定有 T-table 或 S-box。它们是不会骗人的字节模式。**

如果客户端真的实现 AES，就一定有一张 256 项的标准表，逐字节不变。**我不需要理解代码，我只需要问："这张表在不在？"**

结果：
- 前向 S-box 原始 256 字节 —— **不在**（0 命中）
- 但 **Te0 / Td0（T-table）在**，前 8 项逐项匹配（`a5 63 63 c6` = `0xc66363a5` 小端）

**"不在"和"在"都很有信息量：**
- S-box 裸表不在 ⇒ 客户端不是"查表式"简单实现；
- T-table 在 ⇒ 客户端是**优化版 AES**（4 张 T 表代替 S-box+列混合），这是业界最常见的写法。

**⇒ 客户端确实实现 AES，而且是标准优化实现。三方没骗我们。**

## 三、同一个办法，验 SHA-1

SHA-1 有四个轮常量 `0x5A827999` / `0x6ED9EBA1` / `0x8F1BBCDC` / `0xCA62C1D6`。**这些数字只可能在 SHA-1 实现里出现。**

一搜：77 / 77 / 61 / 45 次命中，成簇。**SHA-1 真在客户端。**

**⇒ 帧完整性用 HMAC-SHA1，有三方说的那回事。**

## 四、最关键的一步：错误串

表和常量证明"原语在"，但**证明不了"原语被用在这个帧上"**。比如客户端可能用 AES 去加密别的什么，不一定是帧。

所以我继续找**错误串**——帧层出错时客户端打的日志。找到四条：

```
'Bad frame/payload size'   ← total_len / payload_len 校验
'HMAC mismatch'            ← HMAC 校验
'Bad recv counter'         ← seq 校验
'HMAC calculation'         ← HMAC 计算异常
```

★★ **这四条把"帧层到底校验什么"钉死了**：长度、HMAC、序号。**和三方 `codol_crypto.py` 的 `decrypt_task_frame` 逐项对应。**

**⇒ 不是"客户端碰巧有 AES"，是"客户端用 AES+HMAC 校验这个帧，且校验失败会报这几句"。**

## 五、一个纠正：帧层没有 CRC

`INDEX §七 #3` 写的是"帧头 / 加密 / **CRC** 层"。

**本卷确认：没有 CRC。** 完整性是 `HMAC-SHA1(key, frame[:-8])[:8]`，错误串是 `HMAC mismatch`，不是 `CRC mismatch`。

**"CRC"这个词是早期凭印象写的。** 本卷把它改正。**这种"早就写在清单里、但其实是错的词"，不查就永远错下去。**

## 六、顺带又确认了一遍地址映射

这一卷所有换算都依赖 `VA = file + 0x400000`。我没有假设它，而是**用三个互相独立的锚点证**：

1. `lobby_server` 说 `0x8435D0` 是"被编空的断言 = `c3`"。反推 file `0x4435D0` → **实测正好 `c3`**，而且前面是 `jmp + int3 填充`，正是函数尾部 `ret` 的样子。
2. `CLIENTCHAL` file `0x95A4E8` → VA `0xD5A4E8`，与记忆里 `codol-auth3-lsg-shim-contract` 的记录**一字不差**。
3. Te0/Td0 在此映射下内容逐项正确。

**三锚点全中，我才敢用这个映射。** 一个锚点可能是巧合，三个不可能。

## 七、附带捡到：客户端自带 UPnP/STUN 打洞

在帧层字符串旁边，出现了完整的 NAT 穿越栈：

```
stun.au/jp/eu.demonware.net
239.255.255.250:1900 / M-SEARCH * HTTP/1.1
WANPPPConnection:1 / WANIPConnection:1
AddPortMapping / DeletePortMapping / GetExternalIPAddress
<NewPortMappingDescription>DemonwarePortMapping</NewPortMappingDescription>
```

**客户端会自己 STUN 拿公网地址 + UPnP 开端口。** 对"建房/联机"这是直接的可用信息。

**又是"副产品"，又是顺手捡的。** （`119` 卷捡到 `127.0.0.1:28960`，这卷捡到 UPnP 栈。）

## 八、诚实的部分

- **AES-128 还是 AES-256？** 本卷只证"是 AES"（T-table 对 128/256 通用）。**密钥长度要读 key schedule 的轮数（10 vs 14），本卷没做，标为未定。**
- **"原语在"≠"用在帧上"**——我靠错误串补了这一环，但错误串只能证明"帧层做 HMAC/长度/序号校验"，**没证明 cipher 一定是 CBC 而不是别的 AES 模式**。CBC 依据仍是三方 + `iv[16]` 字段的存在（结构强证据，但非独立证）。

**我没有为了"完整收口"把 AES-128 和 CBC 说成已证**——那超出本卷证据。**规律成立的范围，就是能证的范围。**

## 九、方法论（可迁移）

1. **验证一个算法是否真在客户端：找它的表/常量，不找调用点。** S-box、T-table、SHA-1 轮常量、CRC 多项式——这些字节模式不会骗人。
2. **"原语在"和"原语被用"是两件事。** 用错误串把两者接上。
3. **清单里的词也可能是错的。** §七 #3 的"CRC"本卷改正为 HMAC。
4. **地址映射用多锚点证，不用单锚点假设。**
