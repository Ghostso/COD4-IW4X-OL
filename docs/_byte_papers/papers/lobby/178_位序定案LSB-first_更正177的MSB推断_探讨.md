查到日志里有这么一行：

```

```

我第一反应是：**这就是真实 ready 位流！** 终于能验证模型了。

| 模型 | 预期 | 实测 |

2. **先查这 5 个字节是谁生成的**

我选了 2。查到了：

```python
# run_codol_001/kit_E8_OK_20261029/lobby_server.py
def frame_room_message(msg_type, fields, subtype=0):
    w.write(msg_type, 8)      # ← 8 位 type
    w.write(subtype, 3)       # ← 3 位 subtype
    for value, tag in fields:
        w.write(value, 8)     # ← 8 位值
        w.write(tag, 3)       # ← 3 位标签
```

**这是服务端自己造的。** 一个叫 `kit_E8_OK` 的对照实验，用来测"推一条格式正确的 ready 会不会改变客户端行为"。

它用的模型是 `8 位 type + 3 位 subtype + (8 位值 + 3 位标签)*` —— **第三个模型，也是错的**（是当时猜的）。

## 二、如果我当时没查来源

我会得出"两个模型都错"，然后去构造第三个、第四个模型，全都基于 `10 08 40 00 00`。

**而它是错的。** 用错误样本校准模型，只会得到错误模型，而且会显得"有实机数据支撑"，比纯静态推断更有欺骗性。

## 三、位序这次是硬推出来的

`0xB777C0` 里这段掩码生成：

```asm
0xB77832  or   dl, 0xFF
0xB77835  shl  dl, cl        ; cl = k + (offset%8)
0xB7783E  sar  eax, 0xFF >> (8 - offset%8)
0xB77844  or   dl, al        ; dl = (0xFF << (k+off)) | (0xFF >> (8-off))
```

代入 `offset=0, k=5`：

```
dl = (0xFF << 5) | (0xFF >> 8) = 0xE0 | 0x00 = 0xE0
```

`0xE0` 保留 bit5..7。数据经 `shl al, 0` 落在 bit0..4。

**两者不重叠 ⇒ 数据在低位 ⇒ LSB-first。**

如果是 MSB-first，数据应占 bit3..7，那保留位必须是 `0x07`。**实测是 `0xE0`。**

这条不是猜的，是算术。

## 四、177 卷错在哪

177 卷我写"MSB-first 是弱推断（只看 `shl` 方向）"。

当时我看到 `shl al, cl` 就认为"左移 = 高位对齐 = MSB"。

**错在只看了移位，没看掩码。**

`shl al, cl` 里 `cl = offset%8`，是把数据移到"当前位位置"——在 LSB-first 下，当前位置 0 就是低位，左移 0 位不动。这跟 MSB 没有任何关系。

**移位方向 ≠ 位序。掩码才是。**
