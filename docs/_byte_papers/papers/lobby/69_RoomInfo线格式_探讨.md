# RoomInfo 线格式 · 探讨：从"缺两张表"到"缺一个函数"

> 对应：`lobby/69_RoomInfo线格式.md`

## 一、上一卷说缺两张表

`lobby/67` 我判断要构造 `6/5` 应答，缺：

1. **类型码表**
2. **位流字节化规则**

---

## 二、第一张表：不需要了

**我反汇编了基类的 `deserialize`（`0x627ce0`）：**

```asm
readBits(3)
readData(&[obj+4], 8)
```

**没有分派、没有表。**

**⇒ 3 位只是版本号，不是类型码。**

**⇒ "类型"由**对象本身的 vtable** 决定，
不需要在线格式里编码。**

**⇒ 第一张表根本不存在。**

---

## 三、第二张表：部分解决

**我解出了 `RoomInfo::serialize` 的完整结构：**

```
3 位  版本
8 位  [obj+4]
16 位 字符串类型标签
len*8+8 位  字符串 1
16 位 字符串类型标签
len*8+8 位  字符串 2
1 字节  [obj+0xC]
...
```

**⇒ `RoomInfo` 的线格式已经清楚了。**

**⇒ 只剩"位如何变成字节"这一层。**

---

## 四、`writeBits(0x10)` 的巧妙

**我一开始以为 `0x10` 是长度。**

**但紧接着的数据长度是 `len*8+8`，不是 `0x10`。**

**⇒ `0x10` 是"字符串类型标签"。**

**⇒ 而 ByteBuffer 里 `T_STRING = 0x10` —— 同一个值。**

**⇒ 两套序列化共用类型码常量。**

**这是一个很有说服力的旁证：
说明它们出自同一个设计者/框架。**

---

## 五、`len*8+8` 的含义

```
len 个字符 × 8 位 + 8 位 NUL
```

**⇒ 字符串以 NUL 结尾，长度自动算出。**

**⇒ 不需要显式长度字段。**

**⇒ 这是"长度由内容决定"的编码。**

## 六、现在缺什么

**只剩一件事：`writeBits` 如何把位写进字节缓冲。**

**`0xb77b10` 的实现会告诉我：**

- 当前位偏移怎么维护
- 什么时候 flush 到字节

**⇒ 反汇编 100 行就能确定。**

## 八、方法论收获

> **"缺两张表"往往是"缺一个误解"。**

**我以为需要"类型码表"，实际上是"类型不走线格式"。**

**⇒ 反汇编基类，发现它压根没有分派。**

**⇒ 这张表是我想象出来的。**

**⇒ 真正的缺口比想象的小。**
