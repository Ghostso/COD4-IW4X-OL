# 171 · `11/4` batch 与 `6/5` Manifold 是两层 —— 房间动作分派定案，并证明 168–170 卷判据失效

> 卷次：171（房间类 · 抓包回归）
> 第一权威：`run_codol_001\runs\*\kit\lobby_srv.log` 全部 33 个 run 的 251 条 `11/4` 明文
> 第二权威：`E:\codol_re\client_image_20261027.bin` 反汇编
> §0 结论有三条是**推翻性**的，直接作废前面几卷的部分结论，见 §0.3。

## §0 结论

1. **`11/4` 的 batch = `[u32 innerLen][inner]`**，`inner` 首字节**只有两种值**：`0x02`（房间数据块，188 条）与 `0x18`（ready 记录，63 条）。**全世界 251 条真实 `11/4` 里没有任何一条以 `0x10/0x14/0x15/0x1A` 开头。**
2. **`dwRoomMessageReady` 的 13 位位流（`02 18`/`02 10`）不在 `11/4` 里**，它在 `6/5` 拉取队列（Manifold）。`11/4` 的 ready 是 `inner[0]==0x18` 的 17 字节记录。
3. **现网 `_is_ready_bitstream()` 是死代码**：251/251 真实 batch 全部判 `False`（`batch[0]>>5` 分布 `{0:151,1:11,2:6,3:17,4:44,5:7,7:15}`，type 永不为 `0x10`）。
4. **"加入阵营 / 投票"在客户端侧从未被发出**：全部 33 个 run 里 `service=11` 只有 task `2/4/13`。`ChangeTeam(0x14)`、`ChangeTeamRequest(0x15)`、`Vote(0x1A)` **一次都没有出现过**。

## §1 `11/4` 的真实报文结构

### 1.1 逐字节（`ONCE_20261029_161336`，明文 170 字节）

```
0a 88 77 66 55 44 33 22 11      0A + u64 channelId = 0x1122334455667788
13 08 95 00 00 00               tag 0x13 / sub 0x08 / u32 batchLen = 0x95 = 149
   91 00 00 00                     ← ★ u32 innerLen = 0x91 = 145
   02 04 00 00 00 30 00 00 00 e0 68 ab 5b ab 63 ab 03 ...   ← room 族
08 01 00 00 00                  tag 0x08 / u32 type = 1
```

★★ **`batch` 的前 4 字节是内层长度**，`inner = batch[4:]`。这条在 251 条里 `165/251` 精确成立；剩下 86 条不成立的原因是那些 run 撞上了旧版服务端的应答错位（前缀值等于另一个数，例如 `0x91` vs 实测 `145`），**但内层首字节 `0x02`/`0x18` 在 251/251 上全部成立**——族判定与长度前缀是否吻合无关。

### 1.2 两族在真实流量中的分布

| inner[0] | 条数 | 结构 |
|---|---|---|
| `0x02` | **188** | `[02][变体 V][u32 …][u16 …][数据体]`，V ∈ {02,04,06,08} |
| `0x18` | **63** | `18 1c 5a 98 d6 14 53 91 cf 01` + u16 计数 + 1B 标志 + `00 00 00 00` = 17B |
| 其他 | **0** | — |

V 的实测分布：`0x02`×113、`0x04`×53、`0x06`×12、`0x08`×10。

### 1.3 常见样本

```
room V=02 : 02 02 00 00 00 18 00 00 00 a8 10 00 00 00 00 00        (16B)
room V=02 : 02 02 00 00 00 08 00 00 00 80 08 00                    (12B)
room V=06 : 02 06 00 00 00 30 00 00 00 e0 68 ab 5b ab 63 ab 03 ... (59B)
ready     : 18 1c 5a 98 d6 14 53 91 cf 01 1a da 00 00 00 00 00     (17B)
```

★ 注意 `V=06` 里出现了 170 卷说的"固定前缀 `68 ab 5b ab 63 ab 03`"——它不是长度，是**房间数据体里的子结构**，170 卷的"三段长度"读法在本卷不重复主张（直接反驳需要单独取证，见 §5 诚实边界）。

## §2 `6/5` 才是 Manifold，`11/4` 不是

### 2.1 `6/5` 的真实报文

```
payload(13): 08 00 00 00 00 | 08 14 00 00 00 | 01 01 00
             tag 0x08 + u32 0   tag 0x08 + u32 20   ...
```

即 `(offset=0, maxResults=20, consume=true)` —— **"从队列取最多 20 条"**。这是拉取请求，应答才是 Manifold 位流。

### 2.2 Manifold 分派器 = `0x634870`

```asm
0x634870  sub esp, 0xdbc
0x6348A7  mov ecx,[ebp+0x1c] ; push 3 ; call 0xB774E0     ; 读 3 位 tag
0x6348B7  push 8 ; lea ecx,[ebp-0xa88] ; call 0xB772E0    ; 读 8 位 type
0x6348C7  movzx eax, byte [ebp-0xa88]                     ; eax = type
0x634949  cmp eax, 0x2e                                   ; ★ 0..46
0x63494D  ja  0x636eba
0x634953  jmp dword ptr [eax*4 + 0x636f3c]                ; ★ 47 槽跳表
```

★★ **这就是 138 卷那张 47 种类型表的本体**——它是 **Manifold 位流的分派器**，不是 `11/4` 的解析器。

### 2.3 序列化器的归属（由 xref 定死）

| 函数 | 角色 | 调用点 | 所在容器 |
|---|---|---|---|
| `0x6287D0` | **写** Ready（`0xB77B10` WriteBits 3 + `0xB777C0` WriteBits 8） | **0 处 call** | 只有 5 个 vtable 数据引用 `0xDC7624` 等 5 处 |
| `0x629090` | **读** Ready | 5 处，全在 `0x634870` 内 | — |
| `0x628260` | 读 ChangeTeam | 1 处 @`0x636455`（`0x634870` 内） | — |
| `0x625DB0` | 读 ChangeTeamRequest / Vote | 7 处，全在 `0x634870` 内 | — |
| `0x625520` | 读 Manifold | 1 处 @`0x6337AD`（`0x632D90` = FrameUpdate 内） | — |

> `0x6287D0` 的 vtable 引用在 `0xDC7624`，恰好是 153 卷记录的 `SendReady` 对象 vtable 槽位区。

**⇒ 结论**：这五个函数全都是 **Manifold（`6/5`）的读写两端**。`11/4` 的 batch 与它们无关。

## §3 现网判据失效的三个证明

### 3.1 `_is_ready_bitstream()` 恒 False（251/251）

```python
tag = b[0] >> 5                          # 真实值 ∈ {0,1,2,3,4,5,7}
typ = ((b[0] & 0x1F) << 3) | (b[1] >> 5) # 因 b[0] 是长度字段低字节，毫无语义
return tag == 0 and typ == 0x10
```

实测：**251 条真实 batch 全部返回 False**。这条路径自 171 卷修复以来**从未命中过**。

### 3.2 16 字节常量 `ROOM_READY_BATCH` 恒不匹配

真实 ready 是 17 字节且内层首字节 `0x18`。旧的 16 字节常量是 ol-mod 对 3.3.3.3 的抓包，与 3.19 无关。

### 3.3 `plain[11]` 读的是 channelId 内部

`payload[0]=0x0A` + 8 字节 channelId ⇒ `plain[11]` 是 channelId 的第 3 字节。日志里它恒为 `0x33`（`0x1122334455667788` 的第 3 字节），而注释却把它当"blob 长度低字节"解释。

## §4 房间动作的真实通路（据客户端语义）

```
Flash 按钮
   → AS_SetReadyState → 0x7CF850 → dwRoomImp vt[33] = 0x6301A0
   → 构造 dwRoomMessageReady → 0x62C5A0 入队（+0x3A098）
                                  ↓
                          客户端侧出站队列
                                  ↓
        ┌─────────────────────────┴─────────────────────────┐
        │                                                   │
   [A] 11/4 setRoomData                         [B] 6/5 拉取应答
   room 状态同步（0x02 族）                      Manifold 消息（0x10 Ready 等）
   ready 记录（0x18 族，17B）                    ← 47 类型跳表 0x636F3C
```

★★ **两条路都要通，客户端才认为"准备成功"**：
- `[A]` 抓包已证客户端**确实发** `0x18` 记录；
- `[B]` 需要服务端在 `6/5` 应答里回 **Manifold 位流**，把这条 Ready 广播回该连接。

现网 `[A]` 的 `0x18` 判据是错的（§3.1），`[B]` 回的是 `count=0` 空位流 —— **两条都不通**。

## §5 诚实边界

1. `0x6287D0`（写 Ready）**0 个 call 点**，只通过 vtable 调用。谁在什么时刻用它、拼进哪一段，本卷未取证到位——只知道它在 `0xDC7624` 的 vtable 里，紧邻 153 卷的 `SendReady`。
2. `68 ab 5b ab 63 ab 03` 到底是"三段长度"（170 卷）还是房间数据体子结构，本卷不给结论。**170 卷的"三段长度"读法在 `V=06` 样本上无法直接验证**（长度 59 的样本里这三段若按 8 位读为 104/91/99，与剩余字节数不合）。
3. `0x634870` 的分支只解到 `case 0x02`（`0x63495A` 起），其余 46 个 case 未逐个展开。
4. `11/4` 的 86 条"长度前缀不吻合"样本未逐条归因。

## §6 方法论

1. **★★★ 先证"判据能不能命中真实报文"，再谈分派。** 一条判据在 251 条真实样本上恒 False，说明它描述的是另一个协议层。
2. **★★ 同一族函数（同 vtable 区、同 WriteBits/ReadBits 对）的 xref 会一次性给出归属。** `0x6287D0/0x629090/0x628260/0x625DB0/0x625520` 五个函数聚集在 `0xDC74F8..0xDC76F4`，全部指向 Manifold。
3. **★★ "客户端发了什么"直接查日志明文，不要从类型表反推。** 47 类型表存在 ≠ 这 47 种都会在 `11/4` 出现。
4. **★ 反汇编里 `cmp eax,0x2e` + `jmp [eax*4+…]` 是分派器的签名。** 找到跳表就找到了"谁按类型号分流"。
