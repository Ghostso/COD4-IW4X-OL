# `.ff` 载荷加密判定 · 探讨：熵不是判据，七条合起来才是

> 对应：`lobby/13_ff载荷加密判据.md`

---

## 一、最容易犯的错：只看熵

熵 7.96 → "这是加密的"。

**这个推理有漏洞。**

高熵也可能是：
- 已经压缩过的数据（图片、音频本身）
- 加密
- 经过编码的随机数据

`.ff` 里的载荷在概念上可能已经是"压缩过的资源包"。

**所以熵只能作为"否证明文"，不能作为"是加密"。**

---

## 二、怎么把"加密"从猜测变成结论

需要找**只有加密才会出现的特征**：

### 特征 A：zlib 解不开

如果它是压缩的，用 zlib/raw-deflate 一定能解开。
**实测两个都失败。** → 排除压缩。

### 特征 B：0x00 与 0xFF 等量

| 状态 | 0x00 占比 | 0xFF 占比 |
|---|---|---|
| 未压缩文本/结构 | 高（填充） | 低 |
| zlib 压缩后 | 略高 | 低 |
| **加密后** | ≈0.39% | **≈0.39%** |

**实测 0.39% / 0.40%** —— 两者相等，这正是"均匀随机映射"。

### 特征 C：16 字节块零重复

如果是 ECB，重复明文块会产生重复密文块。
**262143 个块，0 重复** → 不是 ECB。

### 特征 D：16 列分布全都均匀

ECB 会让某些列偏斜。**实测 16 列全部 0.44–0.50%**（基线 0.39%）。

### 特征 E：跨块无相关

测了 7 个块长（256~16384），全部接近随机基线。

### 特征 F：4 字节词几乎全唯一

262132 个词里只有 11 个重复。

### 特征 G：`IWff0100` 头里 `u32@+12 = 1`

一个"看起来像标志位"的 1。

---

## 三、七条的作用不是"相加"，而是"互相排除"

单看任何一条都不够：

| 判据 | 单独能排除什么 |
|---|---|
| A（zlib 失败） | 排除 zlib 压缩 |
| B（00/FF 相等） | 排除"压缩"和"未压缩结构" |
| C（块零重复） | 排除 ECB |
| D（列均匀） | 再证不是 ECB |
| E（跨块无关） | 排除"分块重复" |
| F（词唯一） | 排除"明文与密文混杂" |
| G（标志位） | 提供独立旁证 |

**七条合起来，"加密"是唯一剩下的解释。**

---

## 四、为什么这值得花一整篇

因为它是**整个大厅改造路线的分水岭**。

- 如果 `.ff` 只是"压缩"，那解开后就能直接改菜单、加模式
- 如果 `.ff` 是"加密"，那必须先拿到密钥

**判错方向，后面所有工作都会白费。**

项目历史上已经吃过这个亏：
"mp_firingrange clipmap 解析失败"那条记忆里写着
"曾误把 xmodel 浮点数据当平面表（指针 100% 吻合也骗人）"。

**判据不够多，就会被"看起来对"的东西骗。**

---

## 五、还缺什么

### 缺 1：一个 `u32@+12 = 0` 的样本

如果那个字段是加密标志，应该存在明文样本。

找法是继续扫全部 974 个文件里的 `IWff` 头。

### 缺 2：明文对照

如果能找到一个**应该相同**但一个加密一个明文的东西，
就能用差分。

### 缺 3：解密函数

`CCoderRWFilter` 的实现还没读完。
`CoderFilter.cpp` 里的 `[obj+4]` 16 字节表和 `2*size+10` 特征码
是唯一的线索。

---

## 六、方法论收获

> **判定"加密"需要找只有加密才有的特征，不能只靠熵。**

熵高只能说明"不像明文"。

真正的判据是：
- 0x00 与 0xFF 等量（均匀随机映射）
- 密文块零重复（非 ECB）
- 解密器全部失败（非压缩）

**这三条合起来，才敢说"是加密"。**
