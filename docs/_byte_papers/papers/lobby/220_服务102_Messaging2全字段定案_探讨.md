# 服务 102 (Messaging2) · 探讨：两次解析器误判与一次「槽位即视角」

> 对应：`lobby/220_服务102_Messaging2全字段定案.md`

---

## 一、这一卷我差点在第一步就全错

**第一版解析器我写的是：**

```
0x10 = string，格式 = [长度字节][数据]
0x0a = u64，   格式 = [长度字节 0x08][8 字节]
```

**跑出来 `80/70` 的尾部是：**

```
10 31 36 32 35 31 36 30 00 00
= string(len=0x31=49, ...)   ← 荒谬
```

**`0x31` 是 `'1'`。长度 49 却只有 7 个字符。**

**⇒ 如果我「相信解析器」，整条语料全错。**

---

## 二、我是怎么发现的：**手数字节**

**我没重跑，我先肉眼数列：**

```
10 00                                  → 空串（2 字节）
...
10 31 36 32 35 31 36 30 00             → "1625160" + NUL（10 字节）
```

**⇒ 没有长度字节。`0x10` 是 NUL 结尾。**

**然后我回到镜像找读器 `0xB76A30`：**

```
loop:
  push 1
  call 0xB75E80        ; 读 1 字节
  test cl,cl
  je   跳出            ; ← 遇 NUL 停
```

**⇒ 读器循环自己证明「NUL 结尾」。**

**★ 教训：编码判定必须落到「读器本体」，不能从样本反推——样本里的 NUL 可能被当成数据。**

---

## 三、第二次误判：把「写器」当成「读器」

**追 `0xB8F370` 时我看到它内有一段：**

```
push edi
call 0xB766B0
```

**我先认定 `0xB766B0` 是 u32 读器（因为它在 `0xB76xxx` 区、和读族挨着）。**

**⇒ 于是 `0xB8F370` = 反序列化器。**

**但同一段前面又是 `push 0x2c; call 0xB74220`（分配）+ `call 0xB9BEB0`（构造）——读器为什么要先分配再构造？**

**我去把 `0xB766B0` 的头读完：**

```
0xB766CA  push 8
0xB766CC  call 0xB75F30      ; ← 0xB75F30 内部 cmp [ecx+0x18],0 → 写门控
0xB766D5  push 4
0xB766DD  call 0xB75E00      ; ← 写 N 字节
```

**`0xB75E00` 是「写 N 字节」，`0xB75E80` 才是「读 N 字节」。一字之差。**

**⇒ `0xB766B0` 是写器。`0xB8F370` 是序列化器。**

**★ 教训：`0xB75E00` vs `0xB75E80`——读/写底层函数地址只差 0x80，靠「它在哪个区」推断必翻车，必须看函数体里是 `call 0xB75E00` 还是 `call 0xB75E80`。**

---

## 四、这一次真的没解开：`vt[0]` 到底是读还是写

**我读 `0xB8FB90`（类族 vtable 槽 `0xD59CE8`）全函数：**

```
call 0xB76890   ; readU8
cmp byte [ebp-0xd],1
call 0xB769A0   ; readU64
call 0xB761E0   ; readU32
```

**明确是「读」。**

**而静态表 `0xC1B7EC4`（步进 0x28）每个元素 `+8 = 0xD59CE8`（主 vtable）⇒ 元素 `vt[0] = 0xB8FB90 = 读`。**

**但 `0xB8F370` 对同类元素调 `vt[0]`，而它自己是序列化器（刚证明）。**

**⇒ 冲突。我卡在这里。**

**我试了：**
- 读 `0xB8FC90`（`0xD59CE4` 的 `vt[0]`）→ 是 scalar deleting dtor，不是序列化器。
- 读构造器 `0xB8FAE0` → 设 `[esi]=0xD59CE8`；`0xB8FCC0` → 设 `[esi]=0xD59CF4`。

**⇒ 同一对象有两个相邻 vtable（`0xD59CE8` / `0xD59CF4`，差 0xC），`0xB8F370` 引用的是一个「混合视角」。**

**我没能把这一层彻底拆开。诚实地写进边界（§7-2 / §8）。**

**★ 但这不阻止结论：读器 `0xB8FB90`/`0xB8FD60`、序列化器 `0xB8F370` 各自的**函数体**都验证过了，只是「谁在什么时候调 `vt[0]`」没闭合。**

---

## 五、方法论价值

> **① 解析器出错时，先「手数字节」再改代码——不要用「看起来对」的代码去解释数据。**
> **② 读/写底层函数地址往往只差几字节（`0xB75E00`/`0xB75E80`）——必须看函数体，不能靠邻接猜。**
> **③ 一个「函数体已验证」的结论，不依赖「它的 vtable 槽语义」是否闭合——把两层分开，能救回大部分价值。**
