# `01 01 01 01 01 01 01 01` 的语义：它是"无效/空槽"哨兵

> 承接 `lobby/98` §4、`lobby/99` §4、`lobby/100`
> **★ 本卷把那个常量从"魔数"判定为"哨兵值"，并给出第三处独立使用点**

---

## 1. 之前它只是一个"确定的 8 字节"

**`lobby/98`：`0xc7341d0` = `01×8`，被 `memcpy` 进 P2PInfo 的 `+0x4F`。**
**`lobby/99`：槽 `+0x09..+0x10` 实测也是 `01×8`。**

**⇒ 那时我只能说"这是 8 个确定的字节"。**

**⇒ 不知道它**是什么**。**

---

## 2. 第三处使用点：`0x7f5ab0`（★ 本卷核心）

```
0x7f5ab0  push ebp / mov ebp,esp
0x7f5ab3  push ebx
0x7f5ab4  mov ebx, [ebp+8]
0x7f5ab7  push 0xc7341d0         ; ★★ 哨兵常量
0x7f5abc  mov ecx, ebx           ; this = [ebp+8]（要检查的对象）
0x7f5abe  call 0xb74090          ; bytes_equal(this_id8, SENTINEL, 8)
0x7f5ac3  test al, al
0x7f5ac5  jne 0x7f5b45           ; 相等 → 直接返回（什么都不做）
0x7f5ac7  push esi / push edi
0x7f5ac9  push 0x81a5558
0x7f5ace  call [0xca819c]        ; EnterCriticalSection
0x7f5ad4  xor edi, edi           ; 索引 = 0
0x7f5ad6  xor esi, esi
0x7f5ae0  loop:
0x7f5ae0    mov eax, [esi + 0xe3f4db0]  ; ★ 全局表，步长 0x18
0x7f5ae6    test eax,eax
0x7f5ae8    je 0x7f5b05                 ; 空槽 → 跳过
0x7f5aea    push ebx
0x7f5aeb    lea ecx, [eax+8]
0x7f5aee    call 0xc61360               ; 取该项的 ID
0x7f5af3    mov ecx, eax
0x7f5af5    call 0xb74090               ; 再比 8 字节
0x7f5afa    test al,al
0x7f5afc    je 0x7f5b05                ; 不等 → 跳过
0x7f5afe    mov ecx, edi
0x7f5b00    call 0x7f5060              ; ★ 找到 → 处理
0x7f5b05    add esi, 0x18              ; 步长 24
0x7f5b08    inc edi
0x7f5b09    cmp esi, 0xeb8             ; ★ 上限 0xEB8 = 3768 → 157 项
0x7f5b0f    jb 0x7f5ae0
...
0x7f5b45  5b / 5d / c3               ; ★ 就是 pop ebx; pop ebp; ret（空返回）
```

**⇒ 这是一个"**按 8 字节 ID 在全局表里查对象**"的函数，
且**入口先判哨兵**：**

```c
if (bytes_equal(id, SENTINEL_01x8)) return;   // 未设 ID → 什么都不做
lock(); for (i=0; i<157; i++) if (bytes_equal(table[i].id, id)) handle(i); unlock();
```

## 3. `0xb74090` 是什么（★ 返回值极性已精读）

```
0xb74090  cmp dword [ecx], [edx]     ; 逐 dword 比较，共 8 字节
...
0xb74106  xor eax, eax               ; ★ 全等分支：eax = 0
0xb7410d  sete al                    ; ZF=1 → al = 1   ⇒ **相等返回 1**
0xb74112  ret 4

0xb740f3  sar eax, 0x1f              ; ★ 不等分支
0xb740f6  or  eax, 1                 ; eax = -1（0xFFFFFFFF）
0xb740fe  sete al                    ; ZF=0 → al = 0   ⇒ **不等返回 0**
0xb74103  ret 4
```

**⇒ 它**不是** `memcmp` 三值语义，而是 `bytes_equal(a,b,8) -> bool`。**

**⇒ 相等 → 1；不等 → 0。**

---

## 3.1 ★ 因此 `0x7f5ab0` 的分支方向是**"不等才干活"**

```
0x7f5ab7  push 0xc7341d0            ; 哨兵 01×8
0x7f5abe  call 0xb74090             ; ← 但注意：this(ecx)=[ebp+8]，第二参=哨兵
0x7f5ac3  test al, al
0x7f5ac5  jne 0x7f5b45              ; al=1（相等）→ 跳去 0x7f5b45
0x7f5b45  5b / 5d / c3              ; ★ 就是 pop ebx; pop ebp; ret —— 空返回
```

**⇒ 完整语义：**

```c
if (bytes_equal(obj_id8, SENTINEL_01x8, 8))   // 对象 ID 还是哨兵（未设置）
    return;                                    // ★ 直接返回，什么都不做
// 否则：遍历全局表 0xe3f4db0，找 ID 匹配的项，调 0x7f5060 处理
```

**⇒ ★★ 这是"哨兵"最标准的用法：**
**"未设置"的对象**不参与**查表分发——直接静默返回。**

**⇒ 于是 `01×8` 的语义确定为：**"该对象还没有分配有效 ID"**。**

**⇒ 与我 §2 的直觉一致，但**依据完全反过来了**：
不是"相等时干活"，而是"不相等时干活"。**

---

## 4. 所以 `01×8` 的语义是**"空/无效 ID"**

**三条独立证据都指向同一结论：**

| 证据 | 说明 |
|---|---|
| `0xb74060` 写 `0x01010101` 两遍 | 构造**默认值**（未设置时） |
| `0xc7341d0` 常量被 memcpy | 初始化/复位到默认 |
| `0x7f5ab0` 用 memcmp 与它比较 | 判定"是否未设置" |

**⇒ 一个值如果同时被"写入默认"和"比较是否未设置"使用，
它就是**哨兵**（sentinel / invalid marker）。**

**⇒ `0x0101010101010101` 是一个不可能作为真实 ID 出现的值。**
**（真实 ID 是 CODOID 类的大 u64，不会恰为 0x01 循环。）**

---

## 5. 这解释了 `P2PInfo` 为什么发 `01×8`

**P2PInfo 的 8 字节 blob 源 = 槽的 `+0x4F`。**

**而槽的 `+0x4F` 在 `lobby/99` §4 实测里……**

**等一下，上一卷我记的是 `+0x54` 起有 `01`。`+0x4F` 是 blob 的第 2 段。**

**⇒ 让我重新对一下偏移（见 §6）。**

**如果 `+0x4F` 那 8 字节等于哨兵，那 P2PInfo 发出去的
"8 字节 blob"就是**"我这个 peer 的 ID 尚未设置"**。**

**⇒ 这在"单机/离线/未连接"场景下完全合理。**

**⇒ 也与 memory 里"`[0x8269774]` 连接单例 = 0"的状态吻合。**

**★ 但这是"合理"，不是"证明"。见 §7。**

## 6. 偏移核对（`+0x4F` 落在 67 字节区的末尾）

**`lobby/99` §4 实测槽内非零区：**

```
+0x09 .. +0x10   01 × 8
+0x54 .. +0x57   01 × 4
+0x58 .. +0x63   01 × 12
+0x11 .. +0x53   全零（67 字节）
```

**注意：`+0x4F` 落在 `+0x11..+0x53` 这个 67 字节区**内部**（倒数第 4 字节起）。**

**⇒ 但 `lobby/99` 的实测第 0 项在 `+0x4F..+0x53` 是 `00 00 00 00 00`。**

**⇒ 这说明：**

**① `+0x11` 那 67 字节是**子表**（默认全零，等内层打包器填）。**
**② `+0x4F` 起 8 字节虽然**物理上**在这个 67 字节区内，**
**但在**消息对象**里是独立的第 2 个 blob —— 因为消息对象有自己的布局。**

**★ 这里必须严格区分"槽的布局"与"消息对象的布局"：**

```
槽（0xe36e4d0 + i*0x88）
  +0x09  8B   ID 槽（哨兵默认）
  +0x11  67B  对等玩家子表
  +0x54  4B   
  +0x58  12B  

P2PInfo 消息对象
  +0x0C  67B  ← 由 0xb74bc0 填充（源 = 槽 +0x11）
  +0x4F  8B   ← 由构造函数写哨兵 / 或由 ID 赋值
  +0x58  4B
  +0x60  8B
```

**⇒ `0x4F = 0x0C + 0x43` 在**消息对象**里是"67 字节之后的下一字段"。**

**⇒ 在槽里则不是同一语义（槽的 `+0x4F` 落在子表内部）。**

**⇒ 这是"同一数字、两个对象、不同含义"的第二个实例
（第一个见 `lobby/100` 探讨 §三）。**

**★ 教训再强调一次：偏移只在同一对象内标识字段。**

## 7. 已核实：67 + 8 字节是**连续的一块**

**回查 `0x627fc0` 的两处 `lea`：**

```
0x62802e  lea ecx, [esi + 0x0C]   ; ★ 第 1 个 blob 源
0x628031  push ecx
0x628034  call 0xb777c0           ; writeData(67 字节 = 0x218 位)

0x628063  lea eax, [esi + 0x4F]   ; ★ 第 2 个 blob 源
0x628066  push eax
0x628069  call 0xb777c0           ; writeData(8 字节 = 0x40 位)
```

**而 `0x0C + 0x43 = 0x4F`。**

**⇒ ★★ 两段**首尾相接**，合起来是 `+0x0C .. +0x57` 共 75 字节的连续区。**

**⇒ 这解释了为什么拆成两个 blob 发：
前 67 字节「对等玩家子表」+ 后 8 字节「本 peer 的 ID 槽」。**

**⇒ 与 `lobby/100` 的结论吻合：前 67 字节的源就在槽的 `+0x11`
（`0x7bfb32` 实证），而在**消息对象**里它落在 `+0x0C`。**

**⇒ 同一块数据、两个对象、两套偏移 —— 正是 `lobby/100` 探讨的主题。**

## 7.1 已读：`0x7f5b45` 是**空返回**

```
0x7f5b45  5b    pop ebx
0x7f5b46  5d    pop ebp
0x7f5b47  c3    ret
```

**⇒ 只有三条指令，没有其他逻辑。**

**⇒ 所以"是哨兵"⇒ 立刻返回，连锁都不进。**

**⇒ 这是最省事的"未设置就不处理"写法。**

**★ 至此 §2 的语义完全闭合，无遗留分支。**
