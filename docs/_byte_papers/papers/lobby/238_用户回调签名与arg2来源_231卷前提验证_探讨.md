# 238 探讨 · 隔了七卷才去验证的那一个前提

> 配套：`238_用户回调签名与arg2来源_231卷前提验证.md`

---

## 一、231 卷我写下了一个前提，然后当成结论用

231 卷原文：

```asm
0x4A7FB4  cmp  byte ptr [ebp + 0xc], 0
0x4A7FB9  jne  0x4A7FE7
0x4A7FBE  cmp  byte ptr [eax + 5], 0
```

我看到了 `[ebp+0xc]`，但**没追它从哪来**。然后在结论里直接写：

> 「服务端回空页 ⇒ `[reply+5]==0` ⇒ `state=2` ⇒ 商城永空」

**中间那个 `[ebp+0xc]` 我默认它是 0。**

如果它是非 0，代码会 `jne 0x4A7FE7` 跳到"有数据"分支，**根本不会读到 `reply+5`**。

**我的整个根因结论挂在一个我从没验证过的字节上。**

---

## 二、七卷之后才回头验

237 卷我做判据普查时，看到 20 个回调都在查 `[ebp+0xc]`，这才意识到：**这是个框架参数，我得知道它是谁给的。**

于是有了 238 卷的追踪：

```
0x7FAF50  ← 用户回调派发
  mov eax, [ebp + 8]      ; status
  mov ecx, [esi + 0x30]   ; cb
  push eax
  push esi
  call ecx                ; cb(reply, status)
```

再往上追 `arg2` 的三个来源：

```
0x7FAFC2  push 0                    ; 无数据 → status = 0
0x7FAFE9  push 0                    ; 超时   → status = 0
0x7FB052  movzx edx, byte [esi+4]   ; 正常   → status = reply+4
0x7FB056  push edx
```

**⇒ 空 ACK 时 status = 0。前提成立。231 卷结论保住了。**

## 四、一个意外收获：`+4/+5/+6` 的真实分工

追 `arg2` 的过程中，我顺手看到：

```asm
0x7FB052  movzx edx, byte ptr [esi + 4]   ; status = +4
0x7FAF7D  mov byte ptr [esi + 6], 1       ; +6 = 1 (回调中)
0x7FAF86  mov byte ptr [esi + 6], 0       ; +6 = 0
0x4A7FBE  cmp byte ptr [eax + 5], 0       ; +5 = 数据有无
```

**三个相邻字节，三种完全不同的用途。**

这直接解释了 237 卷我没想通的事：`0x684D93` 为什么同时查 `+6`/`+0x64`/`+5`/`+4`？

**因为它查的是四个不同含义的标志。**

也解释了 235 卷那个"极性相反"的怪现象：`0x4B5610` 查的 `[edi+5]` 和商城查的 `[eax+5]`，**看起来同偏移，但如果对象类型不同，`+5` 可能是不同字段**。

★ **235 卷我用"同偏移不同极性"来描述它，本卷证明更可能是"不同对象的不同字段"。** 235 卷的观察没错，解释错了。

## 五、237 卷的结论也要改一半

237 卷我写：

> 「主流判据是 `[ebp+0xc]`，由**调用方**传入"成功/失败"标志 —— 最通用」

**"由调用方传入"是错的。** 它由**框架**在 `0x7FAF50` 处决定：

- 正常 → 取 `reply+4`
- 超时/无数据 → 填 0

**⇒ 它不是"调用方想传什么就传什么"，而是「框架算出的结果码」。**

而 `reply+4` 是**服务端应答内容解析出来的**。

★ **所以 237 卷 §4 的推论「只有商城空 ACK 才会失败」也是错的** —— `[ebp+0xc]` 判据的服务**同样会**因为空 ACK 而拿到 `status=0`。

**正确表述**：**几乎所有服务都会在空 ACK 时收到 `status=0`；区别在于各服务拿到 `status=0` 后怎么办。**
