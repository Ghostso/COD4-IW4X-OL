# 5 位前缀即字段 ID · 探讨：我上一轮的"定长"是怎么骗过自己的

> 对应：`lobby/89_5位前缀即字段ID.md`

---

## 一、先说最难看的一条

**`lobby/88` 里我写了"`MemberList` = 63 位，这是最容易验证的预测"，
还建议"下次抓到 8 字节推送先看前 5 位"。**

**这是错的，错的根源是：我用了一个越界的反汇编窗口。**

---

## 二、错误的发生过程（诚实地复盘）

**我的提取器是这么写的：**

```python
for ins in md.disasm(b[o:o + 0x200], va):
    ...
```

**两个问题：**

**1. 窗口 0x200 是"猜"的长度。**
**2. 没在 `ret` 处停。**

**于是 `0x627d80` 的函数在 `0x627df4` 就 `ret` 了，
窗口还继续往前，把 `0x627eb7` 那条 `push 3/call writeBits`
（属于 `RoomInfo::serialize`）算进了 MemberList。**

**⇒ 63 = 50 + 一条从隔壁借来的 13 位。**

---

## 三、为什么我当时"觉得"它是对的

**因为 63 位 ≈ 8 字节，看起来非常合理。**

**而这就是最危险的地方：一个错的结论，如果它"看着合理"，
就没人会去验证。**

**⇒ 教训：越是"看起来漂亮的数字"，越要去找它的每一条来源。**

---

## 四、这一轮真正的收获不是位长，是那个 `cmp`

**我在查 `0xB774E0` 时以为它只是 `readBits(5)`。**

**结果反汇编出来：**

```
0x00b7751a  cmp esi,eax     ; 实读 vs 期望
0x00b7751c  sete bl
0x00b77521  jne 0xb7754b
0x00b77523  call 0x8435d0   ; 不等 → 报错
```

**⇒ 它读 5 位，然后断言"必须等于 X"。**

**这一下就把整件事的性质变了：**

**如果读侧断言"第 3 个字段的标签必须是 0x15"，
那写侧必须在那个位置写 0x15。**
**⇒ 5 位前缀不是"可选的类型标记"，而是"协议里的字段编号"。**

---

## 五、于是验证方式变得非常硬

**不用猜。只需要问：**
**同一类消息的 ser 和 der，标签序列是否逐项相同？**

**43/44 相同。**

**剩下 1 个（RoomInfo）只差一个位置，而那个位置的**
**断言函数 `0x8435D0` 只有一个字节 `c3`（ret）。**

**⇒ 意思是：客户端在这个位置根本不检查。**

**⇒ 这是"D 侧代码与 S 侧代码不同步，但因为断言被编空了，
所以线上不出问题"——非常典型的零售版遗留。**

---

## 六、我一开始以为 DIFF 是工具缺陷

**第一次跑出 3 个 DIFF，我以为是工具的 `seen` 去重错了，
改了。剩 2 个，我以为还是工具错，又改了。**

**改到 1 个还是 DIFF 时，我去看了那个地址的原始字节：**

```
0x624b80  6a 03 ...   ser 写 3
0x62530f  6a 02 ...   der 读 2
```

**⇒ 不是工具错。是客户端自己两侧不一样。**

**⇒ 这里差点犯了"把不利于结论的数据当噪声"的错。**

---

## 七、方法论收获（三条）

> **① 反汇编窗口必须以 `ret` 收尾；固定窗口长度是 bug 源头。**

> **② 遇到"看起来合理的漂亮数字"，先怀疑它最不合理。**

> **③ 差集不能默认归因于工具；先看原始字节，再改工具。**
