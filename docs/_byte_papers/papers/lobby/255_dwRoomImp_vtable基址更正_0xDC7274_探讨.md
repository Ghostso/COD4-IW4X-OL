# 255 探讨 · 方法、批判与自我更正

## 一、这个"更正"值不值得单独成卷

**值得**，因为它是个**坐标系**错误，会污染所有引用 vtable 槽的结论：
- 227/229/244 写"`vt+0x13C = 0x632680`"——**数值对，但没说基址**；
- 191–216 写"dwRoomImp vtable = `0xDC73B0`"——**把槽地址当基址**；
- 若有人拿 `0xDC73B0` 当基址去算别的槽（如 `+0x148`），会读到 `0xDC73FC`（错），而不是 `0x62C580`。

★ **一条 vtable 的"基址"错了 0x13C，所有非零槽引用都会偏 0x13C。** 这正是记忆里
`「比 disp 前先确认 this 偏移」`、`「vtable 位置给出 this 偏移」`（`codol-mmi-lowregion-vs-networkregion`）的同类错误。

---

## 二、我是怎么发现的

1. 先按旧卷假设"`0xDC73B0` 是基址"，读 `0xDC73B0+0x148` 得 `0x625520`（Manifold::serialize）——
   **但 254 卷的语境里 `+0x148` 该是"发送"，不是"序列化"**，产生矛盾；
2. 于是改找"**谁往对象里写 vtable 指针**"：搜 `0x632680` 的 dword 位置 ⇒ 得 `0xDC73B0`/`0xDC7850`；
3. 再算 `0xDC73B0 - 0x13C = 0xDC7274`，搜 `0xDC7274` 的 dword 引用 ⇒ 命中 `0x62C025`（构造函数）；
4. 读构造函数确认 `mov [ebx],0xDC7274`；再读 `[0xDC7274+0x148] = 0x62C580`（=发送）——**矛盾消失**。

★★ **触发点是"语义矛盾"**：旧基址导出的 `+0x148` 身份与上下文不符。**发现错误常靠"两个独立来源对不上"，而不是靠"再确认一遍"。**

---

## 三、批判本卷

1. **"`0xDC73B0` 是 191–216 卷的假设"** —— 我未逐字核对 191–216 卷原文，只按记忆索引的摘要。
   若其原文其实也写"基址 = `0xDC7274`"，则本卷是**确认**而非更正。**这一点降低本卷的"更正"分量，但不降低"基址 = `0xDC7274`"的正确性。**
2. **两条 vtable（`0xDC7274`/`0xDC7714`）的关系未确证**：
   我推断是"多继承主/次"，但没读 RTTI COL（`0xDE07A0` 附近）确认是同一个类的两个基类子对象。
3. **`+0x20` 是 MMI** 这条只凭"`0x62C02C call 0x806B50`"，未核对 `0x806B50` 确为 MMI 构造函数（依赖 198 卷）。

## 四、下一步可独立核验任务

1. 读 `0xDE07A0`（可能是 COL 指针）→ 顺藤读 RTTI 名，确认 `0xDC7274`/`0xDC7714` 同属 `dwRoomImp`。
2. 对 `+0x20` 的 MMI：找 `lea [reg+0x20]` 的引用，确认它就是 P1 的 `[this+8]`（若 `0x625CE0` 的 `[this+8]` 指向 `dwRoomImp+0x20`，则 P1 已闭合）。
3. 把旧卷里所有 `vt+0xNN` 断言统一重算（基址 `0xDC7274`），列差异表。
