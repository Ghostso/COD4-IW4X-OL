# 遥测与小服务：证据链与边界（服务 71 + 3/4/6/8/9/12/28/29/68/93）

> 卷次 225 · 方法：capstone 反汇编 + 全量明文日志（7645 条解密记录）+ 台账逐字节对照 · 结论：**读侧（客户端解析器）已到函数地址级铁证（11 个类型读取器 + 1 个类型校验器）**；**写侧**由台账字节精确对照锁定，但**客户端侧写函数未逐函数隔离**（负结论，已穷尽，见 §3）；**"数字 service id → 服务名"映射未恢复**（负结论，见 §4）。

## §1 证据链总览

```
帧        [u32 declared][0x86][service][0x03][task][payload]      declared=3+len(payload)
payload   Demonware ByteBuffer 值流：<tag><value>*
读侧库    0xB76310(tag 校验) + 11 个读取器（0xB761E0…0xB76BE0）   ← 本卷最强证据
写侧库    台账 codol_crypto.Buf 逐字段字节精确（与实测 wire 1:1）  ← 客户端侧写函数未隔离
服务名表  [dw_service_info] 19 名 @0xDE0B78..0xDE0C04 + 描述符表 @0xE4E8F8
```

## §2 读侧库（地址级铁证）

**入口 `0xB76310(reader, expectedTag)`**：`0xB76313 sub esp,0x6c`；`0xB76334 push 1 / lea eax,[ebp-0x55] / call 0xB75E80`（读 1 字节）；`0xB76430 mov eax,[ebp+8] / cmp ecx,eax / sete bl`（**与期望 tag 比较**）；不等则 `0xB7643C..0xB7645F` 两次 `call 0xB773D0`（名字表格式化）后失败。`0xB76354 cmp ecx,0x16 / jne 0xB76430` 是 **P2PInfo 子类型（0x16）特例**（呼应 170/178 卷）。

| tag | 类型 | 读取器 | 首行证据 |
|---|---|---|---|
| 0x01 | bool | `0xB76850` | `0xB76855 push 1`；`0xB76877 cmp byte[ebp-1],0/setne cl` |
| 0x03 | u8 | `0xB76890` | `0xB76895 push 3`；`0xB768B9 mov byte[ecx],dl` |
| 0x06 | u16 | `0xB768D0` | `0xB768D5 push 6`；`0xB768FA mov word[ecx],dx` |
| 0x07 | i32 | `0xB76910` | `0xB76915 push 7`；`0xB76939 mov [ecx],edx` |
| 0x08 | u32 | `0xB761E0` | `0xB761E5 push 8`；`0xB76209 mov [ecx],edx` |
| 0x09 | i64 | `0xB76950` | `0xB76957 push 9`；8B 拷贝 |
| 0x0A | u64 | `0xB769A0` | `0xB769A7 push 0xa`；8B 拷贝 |
| **0x0D** | **f32** | `0xB769F0` | `0xB769F5 push 0xd`；`0xB76A13 fld dword/fstp [ecx]`（**台账类型表无此类型，本 build 独有**）|
| 0x10 | string | `0xB76A30`（定长）/`0xB76A90`（动态） | `0xB76A34 push 0x10`；`0xB76A50` 逐字节读到 NUL |
| 0x13 | blob | `0xB76AF0`（定长）/`0xB76B60`（分配） | `0xB76AF5 push 0x13` → `0xB76B11 call 0xB761E0`（内层 tag=0x08 长度）→ `0xB76B35 call 0xB75E80` |
| 0x17 | 可选 u32 包装 | `0xB76BE0` | `0xB76BE5 push 0x17` 后转 `0xB761E0` |

**`13 08 <u32 len>` 的分层证明**：`0xB76AF0` 自己 `push 0x13` 校验后，立刻 `call 0xB761E0`；而 `0xB761E0` 的首行就是 `push 8; call 0xB76310`。⇒ blob 的 `08` 是**长度字段自身的 u32 tag**，不是"第二个标签"。

**读取器调用者清单（= 反序列化函数全集，地址级）**：以 `call 0xB761E0`(u32) 为索引共 **191 个调用点 / 87 个函数**，全部落在 `0x4AC040`、`0x6BFAA0`、`0x71D8B0`、`0x7F6330`、`0x7FC0F0`、`0x806F20`(MMI)、`0xB76xxx`(库内)、`0xB7B210…0xBAB0xx`(DW 服务反序列化群，约 80 个函数)。这类"同一批读取器被 80+ 函数复用"正是 §224 能一次解完所有小服务的根据。

## §3 写侧：结论与已穷尽的定位尝试

**写侧格式由台账字节精确锁定**（与实测 wire 逐字节一致）：
- `codol_crypto.py:262-264`：`T_BOOL=01,T_U8=03,T_U16=06,T_I32=07,T_U32=08,T_I64=09,T_U64=0A,T_STRING=10,T_BLOB=13,T_ARRAY=6C`；
- `codol_crypto.py:311-316` `blob()`：带 tag → `13 08 <u32 len> data`；`u32array()`：`6c 08 <u32 byteLen><u32 count><count×u32>`。
- 台账明写"客户端运行时读取器 `0xB76910`"（= 本卷 i32 读取器地址，双方对上）。

**客户端侧写函数的定位尝试（全部负结论，已穷尽）**：
1. `mov byte [reg], 08`（C6 /0 imm）全镜像扫描：1891 命中/1304 簇，`0xB6..0xBA` 段仅 11 处——逐条反汇编**多为 `81 C6`/`89 C6`（add/mov 的 ModRM 字节 0xC6）假阳**，非 tag 写。
2. capstone 指令对齐版重扫 `0xB70000..0xB7A000`：`mov byte ptr [...], <tag imm>` **0 命中**。
3. `mov al,<tag>; mov [reg],al`（`B0..B3 XX … 88`）全镜像 113 命中——绝大多数是 `b0 01`（布尔真，通用），非 TLV 写。
4. `push <tag>; call X` 反查：`push 0x10; call 0xAF98A0`(142×) 等一度似"写侧库"，但反汇编 `0xAF98A0` 证明其为**定长环/日志登记例程**（写 `[esi+0x44]`/`[esi+0x104]` 编码字段），`0xAF9290` 为 CRT 初始化 → **假阳**。
5. 结论：**客户端写路径未以"独立 tag 立即数写"形态出现**，很可能每个服务的序列化器直接调"值写入器（tag 由参数传入）"，或写侧就是 `Buf` 这类对象方法，静态上未形成可枚举的写侧函数族。
   ⇒ **本卷把"写侧"定性为：格式已定（台账字节精确 + 读侧对偶），客户端写函数族未隔离（负结论）**。

## §4 服务名：全量表与"数字绑定"负结论

**`[dw_service_info]` 全名表**（连续 ASCII，VA 起始）：
`0xDE0B78 reward` · `0xDE0B80 titleutilities` · `0xDE0B90 tencent` · `0xDE0B98 teams` · `0xDE0BA0 storage` · `0xDE0BA8 profiles` · `0xDE0BB4 pooledstorage` · `0xDE0BC4 messaging` · `0xDE0BD0 matchmaking` · `0xDE0BDC marketplace` · `0xDE0BE8 eventlog` · `0xDE0BF4 non_critical` · `0xDE0C04 critical`；另有 `0xDB8C5C friends`·`0xDBDBB8 group`·`0xDCA00C mail`·`0xDBDEA4 tags`·`0xDBFE38 stats`·`0xDADDE0 none`。

**描述符表 `0xE4E8F8..0xE4E990`（16B/项，`{ptr, enabled}`）** 与配置文件 `[dw_service_info]`（`0x331E5xx`）**逐位吻合**：
```
0xE4E940 matchmaking p=0xDE0BD0 enabled=1
0xE4E948 messaging   p=0xDE0BC4 enabled=1
0xE4E950 pooledstorage p=0xDE0BB4 enabled=0
0xE4E958 profiles    p=0xDE0BA8 enabled=1
0xE4E960 storage     p=0xDE0BA0 enabled=1
0xE4E978 tencent     p=0xDE0B90 enabled=0
0xE4E990 stats       p=0xDBFE38 enabled=1   ...（与 [dw_service_info] 5 个 =1 完全一致）
```
⇒ 这是**配置解析后的结构体**，**不含 wire id 字段**。

**"数字 wire id → 名字"映射：负结论（已穷尽）**：
1. 搜"名字指针与 id 的 dword 邻接"（`id|ptr` / `ptr|id` 两种序，6 个已知服务名 ×2）→ **0 命中**。
2. 帧 marker 定位：`cmp al,0x86`(`3c 86`) 124 命中全为 `8d 3c 86`(lea `[esi+eax*4]`) 假阳；`cmp eax,0x86`(`3d 86 00 00 00`) **1 命中=0x2600DE0**（在数据区）；`c6 ?? 86` 4 处为全局状态写。
3. 服务描述符表无 id 字段（见上）。
⇒ 已确认的绑定仅来自**台账/语义**：`6=messaging`、`8=profiles`、`21(0x15)/138(0x8A)=matchmaking`、`71=tencent`、`80/93=marketplace`、`102=storage`、`10=publisher`、`11=room`。`3/4/9/12/28/29/68` **未绑定**。

## §6 方法论

1. **"是假的"要靠"是谁"证伪**：写侧扫描 4 项里 3 项是"编码假阳"（`81 C6`/`b0 01`），不是"没找到"，而是**逐条反汇编证明那些字节属于别的指令**——负结论必须有正面归属。
2. **读侧对偶胜过字面搜写侧**：写侧难找，但写格式被"读侧两跳结构 + 台账字节精确"双重锚死，格式结论不必依赖写侧函数地址。
3. **配置表 ≠ 协议表**：`0xE4E8F8` 与 `[dw_service_info]` 逐位吻合 ⇒ 它是**配置**，不能拿它当 wire-id 表用；"名字就在文件里"不代表"能反推编号"。
4. **地址级证据优先给"库/基础设施"**：11 个读取器 + 1 个校验器覆盖全部 7645 条样本，比"逐 task 找发起者"更省力且更普适。
5. **口径要能对账**：事件名数、写点候选数，全部带分母与"假阳归属"，方便后来者基于同一事实重判。
