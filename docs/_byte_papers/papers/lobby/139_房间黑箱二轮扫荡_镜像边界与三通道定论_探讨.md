## 一、版本演变：三个版本，全都"当时证据充分"

| 版本 | 结论 | 当时依据 | 结局 |
|---|---|---|---|
| V1（138 卷） | 房间消息走 **opcode 6** | `0xB838A0` 里 `0xB7B210` 挂在 op6，且它是唯一读 blob 的 | **错** |
| V2（139 初稿） | 房间消息走 **op7/8**，op6 是邀请弹窗 | `0x7E7C90` 读出 `rec+0x25B8`=0x6371F0 | **半对** |
| V3（139 终稿） | **op6/op7 都走 `0xB7B300`**，经 vtable slot[6] → `0x7F1060` → `0x7E7C90` | `0xB7B428 mov edx,[edx+0x18]` | ✅ |

**关键：V1 和 V2 并不是"瞎猜"，它们每一步都有真实的反汇编依据。**

V1 的依据是"op6 → `0xB7B210`"——我读到了 `0xB82DF7 call 0xB7B210`，而 76 项表里 **op5** 才是 `0xB82DDD`。我把 `0xB82DDD` 的 call 目标记成了 op6 的。

★ **一个 3 字节的表格错位（0xB82DDD vs 0xB82E03），让整条链错了一层。**

V2 的依据是"`0x7E7C90` 读 `rec+0x25B8`"——这是对的。但我**没有往上追一层**：`0x7E7C90` 是由 `0x7F1060` 调的，而 `0x7F1060` 是 `dwLobbyEventHandler` 的 **vtable slot[6]**，谁调 slot[6] 才决定 opcode。

★★ **教训一：只查到"函数被谁用指针调用"不够，要查到"那个指针在哪个表里、那个表被哪个 opcode 索引"。**

## 二、第二次自我推翻：`0x82E1458` 的"无写点"

139 初稿写"`0x82E1458` 47 项描述符表全镜像 0 写点，是死表"。

**这个结论本身没错（确实 0 写点），但它的"证明力"被我高估了。** 后来挖到：
- 段2 覆盖率 0.2% ⇒ **任何"全镜像扫描 0 命中"都可能是"该地址在文件里没有数据"**
- 我只扫了 `mov [reg+off], imm` 和 `mov [imm], reg` 两种形态

★ **教训二："0 命中"必须先排除"扫描目标本身不在可扫描区域"。** 这次侥幸结论仍成立（表在段2，且 `if(esi) call esi` 的语义在代码里，代码在段0），但推理路径本来是坏的。

## 三、第三次：`rec+0x01` 的"没有写点"

初稿说：`rec+0x00/+0x01` 两个启用字节，`0x7E7941 mov word [rec],1` 只写 +0x00，+0x01 写成了 0，而三条派发都要求 +0x01 != 0 ⇒ **矛盾，必有漏写点**。

**我搜了 `mov byte [reg+1], imm`（53 处），没结果。** 然后我去看谁调 `0x7E7936`——**0 个调用者**（因为 `0x7E7910` 末尾 fall-through 进去的）。

最后是在 `0x7E7FA0`（一个**回调函数的地址被 push 进去**，而不是被 call）里找到的：

```
0x7E7F38  push 0x7E7FA0        ; ★ 注册回调，不是 call
0x7E7F5E  call 0x7FAA20        ; 真正发起订阅
...
0x7E7FAA  mov ecx,[eax+0x40]
0x7E7FB0  mov byte [ecx+1], 1  ; ★ 这里
```

★★★ **教训三：`push <函数地址>` 是"回调注册"，用 `E8 call` 扫描永远找不到它，用 `mov [reg+1]` 扫描也找不到——因为它写的是 `[ecx+1]`，而 `ecx` 在静态分析里只是一个寄存器。**

**这条和 138 卷"构造器写在栈上所以扫不到"是同一族教训的第二次发作。**

## 四、真正的收获：一个"四层门"的注册模型

把所有碎片拼起来，`srpc` 订阅是这样四层递进的：

```
第1层  0x62DEE0 (dwRoomImp ctor)
        call 0x7E7910        → 分配槽 (rec+0x00=1, rec+0x01=0, 五个回调槽清零)
        mov [room+0x1C], eax
        mov [rec+0x25C8], room      ← 反指
        call 0x7E7EE0(svc, task)    ← 真正注册
                     ↓
第2层  0x7E7EE0
        call 0x803830        → srpc 单例；空 ⇒ 失败
        call 0xB7A670        → 状态；!=2 ⇒ 失败
        call 0xB7A770        → 会话对象；0 ⇒ 失败
        mov [rec+0x10], svc  ← ★ key.lo 在这里写！
        mov [rec+0x14], task ← ★ key.hi 在这里写！
        call 0xB8FAB0        → 发起订阅，返回 handle
        push 0x7E7FA0        → 注册成功回调
        call 0x7FAA20        → 提交
                     ↓
第3层  0x7E7FA0 (回调)
        mov ecx,[eax+0x40]   → 槽记录
        mov byte [ecx+1], 1  → ★★★ 这里才 rec+0x01=1
                     ↓
第4层  0x633FE0 (room → 回调)
        rec+0x25B8 = 0x6371F0   ← 收到 dwRoom 报文
        rec+0x25BC = 0x6374E0   ← 成员对账
        rec+0x25C0 = 0x637520   ← 房间激活
        rec+0x25C4 = 0x633D50   ← 状态码
        call 0x633DF0
                     ↓
第5层  0x633DF0
        cmp byte [room+0x284],0 → 一次性
        cmp byte [rec+0x01],0   → 必须已激活
        push 0x634240; call 0x7E8120  → 订阅 opcode 0x13 的消息流
```

★★★ **结论：任何一层没走通，`rec+0x01` 就永远是 0，而三条派发函数都会在第一条指令 `cmp byte [rec],0 / je skip` 处静默跳过。**

**这就是"房间按钮点了没反应，但客户端不报错"的最完整的机制解释**——一个五层串联守卫，任一环断开都是完全静默的。

## 六、方法论（本卷新增，与旧卷合并）

1. ★★★★ **查函数调用者，要区分三种边**：`E8 call`（直接）、`dword 表项`（vtable/跳转表）、`push <addr>`（回调注册）。**第三种是最大的盲区**——本卷 `rec+0x01` 的唯一写点就藏在第三种里。
2. ★★★★ **"磁盘实测值"必须先做段归属判定**（`VSize >> RawSize`）。
3. ★★★ **opcode ↔ handler 必须双向查**：先 `表[op] → handler`，再 `handler → call 目标`，两边对上才算。**只看一边就会像 V1 那样错一层。**
4. ★★★ **多层门控要全部列出**：本卷五层里，任一层都能让整条链静默失效。**只报告最外层会误导修复方向。**
5. ★★ **"0 写点"要同时排除"扫描形态"和"扫描区域"两个盲区。**
6. ★★ **同一个结论改三次不是失败**——V1→V2→V3 每次都更细，最后才落到 `mov edx,[edx+0x18]` 这种不可再分的机械事实上。

## 七、给下一步的硬约束（写给修复）

1. **不要再猜 opcode**：房间消息 = **op6 或 op7**，消息体 = `u64 key + u64 A + char[0x40] + blob`。
2. **blob 里必须是"两个子 blob"**，blob#1 = 47 表位流报文，blob#2 = 文本（可为空但字段要在）。
3. **key 必须是运行时注册写入的那对值**，不是磁盘里的 `0x55667788/0x11223344`。
4. **发之前先验证客户端的 `rec+0x01` 已经为 1**——否则发了也白发，且完全静默。
5. **最便宜的验证**：先查 `[dwLobbyImp+0x4F0]` 是否非空、srpc 状态是否为 2（`0x4F8` 是否为 0）。这两个任一不满足，后面全部不必做。
