## §2 ★★★ 这个索引解决了什么

### 2.1 232 卷「40.4% 未实现」现在有了**双向定位**

之前只知道「服务端没实现 `71/7`」。现在知道：

- **`71/7` 的客户端发送函数入口**（从通道号反查 `0x800420` 区）
- **它的响应处理判据**（从 235 卷的方法：找 `reply+N` 的 `cmp`）

**⇒ "缺什么" + "怎么判失败" 两端都通了。**

### 2.2 通道号 ≠ 服务号（再次确认）

231/232 卷已证出口漏斗的立即数是**通道号**，不是服务号。本卷给出完整对照：

| 通道 | 对应服务（已知） |
|---|---|
| 0x59(89) | 80 getskus |
| 0x5A(90) | 80 分页 |
| 0x5D(93) | 80/93 类别 |
| 0x6B(107) | 80 的 700 查询 |
| 0x3A(58) | **58 Clan**（数值巧合！不是同一编号体系） |
| 0x87(135) | 未定 |
| 0x16(22) | 房间类 |

★ **`通道 0x3A` 与 `服务 58` 数值相同纯属巧合** —— 234 卷我差点把 `0x7FF57F push 0x3A` 当成 svc 58，本卷证明 `0x3A` 只是通道号，而 `0x7FF500` 确实属于 Clan 是通过另一条路径（svc 58 的构造点在同一个函数）确定的。

## §6 方法论

1. **★★★★★ 「发送面」比「服务面」更容易穷举。** 服务号散落在各种构造器里，而**所有出网必须经过同一族漏斗函数** —— 抓住漏斗的 136 个调用点，就拿到了完整的发送面。
2. **★★★★ 通道号是独立编号体系，与 svc 号数值巧合会误导。** 234 卷我差点把 `push 0x3A` 当 svc 58，本卷给出完整通道表避免了这类错误。
3. **★★★ 「一个函数多个漏斗调用」说明它能发多种消息**（`0x7E7E30` 发通道 0x12/0x13）。这与房间类 172 卷的"唯一出口 `0x7E8300`"不矛盾 —— 是同一子系统内的多个发送点。
