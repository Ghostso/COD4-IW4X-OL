## 一、这一卷的意义不在编码器，在"对账"

**前面六卷（89–95）我一直在**说**：
"字段顺序是这样""位宽是那样""循环体 725 位"。**

**但这些都是**我一个人的判断**。如果我在 `lobby/92` 里把第 17 个字段
记成了 16 位而实际是 8 位，后面所有卷都会跟着错，而且**看不出来**。**

**⇒ 这一卷给了第一条独立校验。**

## 二、为什么对账能成立

**因为两条路径**信息源不同**：**

| 路径 | 输入 | 方法 |
|---|---|---|
| 反汇编 | `client_runtime.bin` | 递归下降，逐条识别 `call writeBits/writeData` |
| 编码器 | `msg_spec.py` | 读我写的字段表，累加位宽 |

**⇒ 如果我在抄表时把某个 `writeData(8)` 写成 16，
编码器就会算出 +8 的差，而对账立刻暴露。**

**⇒ 34 条全 0 差 ⇒ 这 34 条的字段表没有转录错误。**

**（P2PInfo 补上后为 35 条，见下。）**

## 三、但我要说清楚 35/45 不意味着"45 条都对"

**剩下 10 条差 24/32/160 位，我判为"字符串载荷记账差异"。**

**这个判断**是解释**，不是验证**。**

**⇒ 诚实表述：**
**- 34 条：双重独立确认。**
**- 10 条：单次判断 + 差值的自洽解释。**

**⇒ 不能把两者混为一谈。**

## 四、那个"24 vs 32"其实是个真发现

**我在对账时发现字符串差有两种：24 和 32。**

**起初以为是 bug。**

**查下来发现：**

**两个字符串读器：**
- `0x4f3de0`：**工具递归进去了**，记了第一轮 `readData(8)` ⇒ 差 24（=32−8）
- 另一个：工具没进去 ⇒ 差 32（=32−0）

**⇒ 也就是说，代码里有两套字符串读取实现。**

**⇒ 这可能对应"短串直读"和"长串带缓冲"两种路径——
在 `MemberInfoEXT`（24）和 `Text`（32）之间出现。**

**⇒ 这是一个"从错误里长出来的发现"。**

## 五、最大的教训：去重方向搞反

**`spec_gen.py` 第一版：**

```python
seen = set()
if va in seen: continue
seen.add(va)
```

**逻辑上"每个 serialize 只算一次"，没问题。**

**但 8 个类共用 `0x628320`，于是只有第一个类拿到 spec，
其余 7 个什么都没输出。**

**⇒ 输出从 44 条掉到 30 条。**

**⇒ 改成：**

```python
cache = {}          # va -> spec
if va in cache:
    out[name] = cache[va]     # ★ 复用，但仍然输出
    continue
```

**⇒ 44 条全回来。**

**⇒ 教训：去重应该作用于"计算"，不能作用于"输出"。
两者混在一起，就会丢数据。**

## 六、方法论收获（三条）

> **① 任何"我读出来的结构"，都要有第二条独立路径复算一遍。
> 否则错误不可见。**

> **② 解释差异 ≠ 验证正确。要把"已确认"和"已解释"分开标注。**

> **③ 去重作用于计算，不作用于输出。**
