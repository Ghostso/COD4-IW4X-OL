# 116 探讨 · 「定名」到底靠什么：三条链、两个陷阱、一条方法论

> 配套：[116 · `102` 定名 Messaging2](116_102定名Messaging2.md)
> 性质：方法论复盘 + 反面清单。**记录我这一轮差点翻车的地方，给后续字节卷立规矩。**

---

## 一、这一轮的真正难点：不是「找不到名字」，是「名字找到了但不敢用」

115 卷停在「`102` 语义名未定」。当时手里的候选是 `Leaderboard`——纯靠「50 个序号 = 排行榜 50 名」的**形状联想**。这一轮我先拿到 ol-mod 的 `// Messaging2 (102)`，**几乎是瞬间就能「定名」的**。但我没有立刻写结论，而是花了十几步去本地找证据。为什么？

因为 AGENTS.md 有一条硬规则：

> ol-mod **does not meet the bar for primary study**……Never copy its constants, field layouts, or protocol values into our implementation.

如果我直接写「102 = Messaging2，因为 ol-mod 这么说」，那就犯了项目已经翻过车的老错（实体段照抄 ol-mod）。**定名本身可以借 ol-mod，但必须被本地证据兜住。**

## 二、三条链，缺一不可

### 链 A：本地二进制「服务开关表」——证明 `messaging` 是真实且启用的服务

发现过程值得记：我本来在找 `{u32 id, char* name}` 的服务号表（115 卷卡住的方向），扫遍了也没找到。转折点是**换了个问题**——不问「102 叫什么」，而问「客户端自己怎么组织服务名」。于是做了「服务名 C 串的指针反查」，在 `0xA4E8F8` 撞出一张 `[name_ptr][flag]` 表。

**这张表的杀手级特征是：顺序与 `configs_s.info [dw_service_info]` 逐项一致、flag 逐项同值。**
- `configs_s.info` 是客户端**读**的资产；
- 二进制表是客户端**内建**的；
- 两者独立产生、结果同序同值 ⇒ 不可能是巧合。

**教训：找「服务号→名」，不如找「客户端怎么用服务名」。** 前者在虚拟化壳里被抹了（`.tp3` 节，静态无直表），后者以字符串+指针形式活得好好的。

### 链 B：RTTI + 状态绑定——证明 `messaging` 是 bd 层 DW 服务

`bdMessagingGroup` 和 `bdMatchMakingInfo`/`bdProfileInfo`/`bdRichPresenceData` **并列**，这是「同类」的强信号。再加 `ChattingController` 绑 `data.messaging.status → DWServiceStatus`，就把「messaging 是一个有在线状态的 DW 服务」钉死。

**教训：RTTI 类族的「邻居」比类名本身更有信息量。** 一个类单独出现可能是噪声；它和已知服务类排成一片，就是服务族。

### 链 C：ol-mod 载荷逐字段——证明「102 这个号」对应「Messaging2 这个名字」

这是唯一直接给出「102 ↔ Messaging2」绑定的来源。我做的不是「信它」，而是**逐字段对账**：

```
ol-mod 注释 1: (u32 0, u32 1, u8 3, u64 0)  ←→  语料 08 00 00 00 00 08 01.. 03 03 0a 00×8
```

四个 task **全部逐字段一致**，连 `102/2` 的「整帧 `04 00 00 00 86 66 03 02`」都和我们 `declared=3 / service=0x66 / ver=0x03 / task=0x02` 对上。

**为什么这足以「借名字」？** 因为 ol-mod 描述的**不是它自己的猜测，而是它观测到的一个真实客户端的载荷**——而这个载荷与我们抓到的**是同一份字节**。同一份字节 ⇒ 同一个客户端行为 ⇒ 它给这份行为起的名字，可以采信。**这不是「抄 ol-mod 常量」，是「用 ol-mod 的观测记录去命名我们自己的观测」。** 边界很清楚：字节我们自己是验证过的，没抄一个。

## 三、两个陷阱（都差点踩）

### 陷阱 1：`str-Alwaysoffline.txt` 里的 `Messaging2::task1`

我一度以为这是「原版客户端二进制解出的字符串」，差点当成**独立本地证据**引用。直到看见同表里有：

```
RecoveredEmpty::0x66/0x01
```

`RecoveredEmpty::` 是 **ol-mod 自己的命名**（它的 RecoveredCatalog 风格）。⇒ 这张串表来自 **ol-mod 派生的服务器二进制 `Alwaysoffline.Localnet32`**，不是原版客户端。**它只能算「ol-mod 的第二份转述」，不构成独立证据。**

**规矩：看到「解出的字符串表」，先问它从哪个二进制来的。** 交付包里的 `.exe` 不一定是原版。

### 陷阱 2：`0x722EC00` 的「130 项表」

扫「同时含多个已知服务号的密集 u32 表」时，`0x722EC00` 命中 `[8,10,11,21,93,102]`，看起来像服务号表。dump 出来是 0..129 的**带重复**序列（`min=0 max=129 unique=111`，不是全排列）。它是**字符串哈希桶 / 字典序索引**，不是服务号表。`102` 出现在里面纯属数值巧合。

**规矩：密集 u32 表要先验「是不是全排列 / 是不是单调 / 有没有重复」，再谈语义。** 数值命中 ≠ 语义命中——这就是 112 卷「魔数先做算术枚举再起名」的同一条教训的又一例。

## 四、`Leaderboard` 为什么必须作废（反面推理的价值）

115 卷的推理是「50 个槽位 → 排行榜前 50」。这一轮我列了四条反证：

1. 排行榜查询**必然带玩家 ID / 榜 ID / 时间窗**，不会是恒定 0..49 索引枚举；
2. `102/1` 的 `u8 3`、`102/5` 的 `[1,2]` 是**类别枚举**，与榜无关；
3. 排行榜类叫 `bdCODOReadCCPLeaderboardRequest`，**不叫 messaging**；
4. `configs_s.info` 里**没有 leaderboard 开关项**，`messaging` 却有且=1。

**方法论：候选作废要给出「为什么它不可能」，而不只是「有更好的候选」。** 只写「换成 Messaging2」是弱论证；写「Leaderboard 的 50 是表面巧合」才是强论证。**一个结论的可信度，一半来自正面证据，一半来自对旧候选的证伪。**

## 五、还差什么（诚实边界）

1. **静态没有 `{102, "messaging"}` 直表**——我穷举过（`svc_id102_bind.py`），不存在。这说明客户端把号↔名的绑定放在**运行时**（服务注册时由配置字符串填），静态面天然看不到。**这不是「找不到」，是「本来就不在静态面」。**
2. **102 各 task 的业务级语义**（比如 `102/1` 的 `u8 3` 到底是「未读」还是「系统」类别）——只能到「信箱轮询」这一层，再细需要**真实应答样本**（要跑客户端，需授权）。
3. **`messaging` 与 `Messaging`（服务 6）的分工**——6 是「即时消息发送」（sendInstantMessage），102 是「信箱批量拉取」，两者是**发 vs 收**的两代协议。这个分工是从 task 形态推的，**无服务端应答佐证**。

## 六、一句话总结

> **定名 = 本地证据钉住「名字是真的服务」，语料钉住「号是真的服务」，ol-mod 的观测记录把两者接上——而接上的那一刻，必须能逐字节对账。**
> 三缺一，都不能叫「定名」，只能叫「候选」。
