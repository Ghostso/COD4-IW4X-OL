1. `0xB778E0` —— ctor，看到 `push 1` / `call 0xB777C0` ⇒ 「写 1 位」✅
2. `0xB779A0` —— 读侧 ctor，看到 `push 1` / `call 0xB777C0` ⇒ 「两侧对称」✅

```asm

```

**`+0x21 == 0` 时，`W_TAG` 一位都不写。**

★ **我在 242 卷里明确写了「`+0x21` = ctor 的第 2 参」（173 卷的结论），也知道房间是 `push 0; push 0` ⇒ `+0x21 = 0`。但我没有把这两件事和 `W_TAG` 连起来。**

**我把 `+0x21` 当成了「1 位头的值」，而它实际上是「整个标签编码的开关」。**

## 四、`+0x21` 到底是什么（本卷的真正收获）

它在三个地方被读，三种作用：

| 位置 | 读法 | 作用 |
|---|---|---|
| `0xB778E0` ctor | `mov [esi+0x21], al`（写） | 存 flag |
| `0xB779A0` ctor | `mov [esi+0x21], al`（al 恒 0） | 读侧恒 0 |
| `0xB77B10` `W_TAG` | `cmp byte [ecx+0x21],0` / `je` | **写标签的总开关** |
| `0xB774E0` `R_TAG` | `cmp byte [ecx+0x21],0` / `je` | **读标签的总开关（返回成功）** |
| `0xB77A70` `W_TAG` 内部 | `cmp byte [esi+0x21],0` / `je` | 跳过 8/32 位前缀 |

★ **一个字节，五个读点，两种语义（"存值"和"当开关"）。**

★★ **最关键的是读侧**：

```asm
0xB774F0  cmp  byte ptr [ecx + 0x21], 0
0xB774F4  mov  al, 1              ; ← 默认"成功"
0xB774F6  je   0xB7754F           ; ← +0x21==0 就返回成功，一位不读
```

**`+0x21 == 0` 时，客户端"校验通过"了，但根本没读标签。**

★ **这意味着：如果服务端按"有标签"的格式发包，客户端在读侧会以「不读标签」的方式去解析 —— 它会把标签字节当成数据字段读。**

**这是"格式对不上但不报错"的典型 —— 最难查的一类 bug。**

## 五、175 卷「7 字节」也要改

175 卷说「`6/5` 应答必须 **7 字节**（不是 6）」。

按本卷：

- `+0x21 == 0` ⇒ 41 位 ⇒ **ceil(41/8) = 6 字节**
- `+0x21 != 0` ⇒ 51 位 ⇒ **ceil(51/8) = 7 字节**

**175 卷的 7 字节是按 51 位算的，而房间是 41 位 ⇒ 6 字节。**

★ **但我不改 175 卷的结论，只标注冲突。** 因为：
1. 没有真实 `6/5` 样本
2. `0x636FF0` 那个函数是 `R_TAG(3)` 读第一个标签 —— 如果 `+0x21==0` 那 R_TAG 直接返回成功，**后面的 `0xB772E0`（`0x63705D`）读 8 位就变成读第 1 个字节**，整个解析起点都变了

**这是一个必须实测的分歧，静态无法收敛。**

## 六、我现在能说什么、不能说什么

### 能说（有机器指令证据）

- `+0x21 == 0` ⇒ `W_TAG`/`R_TAG` 完全不读写标签位 ✅
- 房间类 3 个写侧构造点全 `push 0` ⇒ 写侧 `+0x21 = 0` ✅
- 读侧 `0xB779A0` 的 `+0x21` 恒 0（`xor eax,eax`）✅
- 因此房间位流 = 41 位（若不考虑标签）✅

### 不能说

- ❌ 「服务端改 41 位就能通」—— 无样本
- ❌ 「175 卷的 7 字节是错的」—— 见 §5 的分歧
- ❌ 「41 位向上取整一定是 6 字节」—— 需确认位流的起始偏移是否对齐
