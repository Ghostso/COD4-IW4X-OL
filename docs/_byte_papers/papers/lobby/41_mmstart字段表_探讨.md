# `mmstart` 字段表 · 探讨：房间参数不在"房间协议"里

> 对应：`lobby/41_mmstart字段表.md`

---

## 一、一个反直觉的结论

**做房间逆向，我没在 `11/*`（房间服务）里找到房间参数，在 `6/14`（匹配服务）里找到了。**

```
11/13  createRoom      1 字节（空）
11/4   setRoomData     恒定模板（除 2 字节）
11/2   queryRoom       只有 roomId
6/14   mmstart         16 个键、6 种地图、playlist、难度、模式
```

**⇒ 房间的"内容"由匹配服务定义，房间服务只负责"会话容器"。**

---

## 二、这个设计的合理性

**在 CoD 的架构里：**

- **房间（lobby）** = 一个会话，有 ID、有成员、有状态
- **对局（match）** = 一局游戏，有地图、有模式、有规则

**`11/*` 管前者，`6/*` 管后者。**

**当用户"创建房间并开始游戏"时，客户端：
1. `11/13` 建房间（拿到 roomId）
2. `6/14 mmstart` 告诉匹配服务"开什么局"
3. `11/4` 把房间设成"准备打这个局"**

**所以房间参数是"挂在房间上的匹配请求"，不是"房间自己的属性"。**

---

## 三、`playlist 37` 是核心

20 条 playlist 形态里，**`playlist 37` 是唯一的值**。

**这和项目里已有的工具 `tools/resolve_playlist37.py` 对上了 ——
之前的会话就在追这个 37。**

**`playlist 37` 是一个"对局套餐"：
- 包含若干张地图
- 每张图配一个 gametype
- `start_map_rotate_once N` 选第 N 张**

**⇒ 如果能在 `mp_playlists` 里找到第 37 条，就知道这 20 个 mmstart 指的是什么对局。**

## 四、`roomChatChannelID` 又出现了那个哨兵

```
1234605616436508552 = 0x1122334455667788
```

**这是第三次遇到这个值：**

1. `11/4` 的 u64（房间 ID）
2. `11/2` 的 u64（房间查询）
3. **`6/14` 的 `roomChatChannelID`**

**⇒ 客户端把"房间 ID"和"聊天频道 ID"用同一个值。**

**这很可能是一个"单房间模式"的设计：
整个客户端只有一个房间、一个聊天频道。**

## 五、六个数字 dvar 的价值

```
2486 / 2489 / 2500 / 2574 / 3265 / 2810
```

**它们在两种形态里的翻转是同步的：**

| 形态 | 2486 | 2489 | 2500 | 2574 | 3265 |
|---|---|---|---|---|---|
| A（map） | 1 | 0 | 0 | 0 | 1 |
| B（playlist） | 1 | 1 | — | 2 | 6 |
| 靶场 | 0 | 0 | 0 | 0 | 18 |

**`2486` 在 A/B 都是 1，在靶场是 0 ⇒ 可能是"是否多人"。**
**`2489/2574` 在 A/B 翻转 ⇒ 可能是"地图来源"。**
**`3265` 三档 ⇒ 可能是"地图类型"。**

**如果能在客户端 dvar 表里找到这些编号对应的名字，就全解了。**

**项目里已有 dvar 表读法（memory: `codol-dvar-table-in-memdump`）：
名字串 VA 搜指针 → 对象 +0xC 是值。**

## 六、这条线索的可行路径

**`mmstart` 的 dvar 编号 → 名字**，可以通过：

1. **内存 dump**：在 dvar 表里找编号 2486/2489/2500/2574/3265 对应的条目
2. **但 dvar 表按名字索引，不一定有"编号"字段**

**另一种可能：这些数字不是 dvar 编号，而是"某个枚举表的索引"。**

**那就要先找到那张表。**

## 七、方法论收获

> **"服务名"不等于"内容所在"。**

`11` 是房间服务，但房间**内容**在 `6`（匹配服务）。

**如果我一开始就认定"房间数据在 11 里"，会一直找不到。**

**正确的做法是：先穷举所有相关 service，看哪个的数据是"变化的"。**

**`11/4` 恒定，`6/14` 变化 —— 这就指明了方向。**
