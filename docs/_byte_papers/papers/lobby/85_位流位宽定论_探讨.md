## 一、上一卷的三种可能

`lobby/84` 我列了三种：

| 读法 | 头长 |
|---|---|
| A: `writeBits` 写 n 位 | 11 位 |
| B: 写 5 位 | 13 位 |
| C: 写 32 位 | 40 位 |

**我当时说"静态反汇编定不了"。**

---

## 二、但对称性定住了

**我反汇编了 `readBitsCore`，发现：**

```asm
sub ecx, edi
call 0xb75d40
inc eax          ← 一模一样
push eax         ← 当 nbits 传
call readData
```

**⇒ 写和读**完全对称**。**

**⇒ `inc eax` 不是 bug，是设计。**

**⇒ 那么问题只剩"`0xb75d40(31)` 返回几"。**

---

## 三、追踪 `0xb75d40` 的逻辑

**它是一个"求最高有效位索引"的函数：**

```
n = 31 = 0b11111
0xffff0000 & n = 0 → 不移 16
0xff00 & n = 0 → 不移 8
0xf0 & n = 0x10 ≠ 0 → ecx |= 4, n >>= 4 → 1
0xc & n = 0 → 不移 2
0x2 & n = 0 → 不移 1
```

**⇒ 累计 `ecx = 4`（最高位在索引 4）。**

**`inc eax` → 5。**

**⇒ 写 5 位。**

---

## 四、为什么这个结论可信

**三条独立证据：**

1. **`0xb75d40` 的逻辑**：确实返回最高位索引
2. **对称性**：write/read 用同一套
3. **标签值域**：`0x10/0x13/0x15` 都在 0..31，正好 5 位

**⇒ 5 位这个结论，三条证据同时支持。**

---

## 五、我前面错在哪

**`lobby/83` 我说：**

> `writeBits(n)` = `writeBitsCore(n, 0, 31, 0)`
> → 截取 `value - start = n` 位

**这个推导**忽略了** `0xb75d40` 那一步 —— 
`writeBitsCore` 不是"写 n 位"，而是"写 `floor(log2(width))+1` 位"，
用 `value` 填进去。**

**⇒ 现在明白：`width` 参数是"值的上界"，不是"要写多少位"。**

---

## 六、这个更正的意义

**如果按 `lobby/83` 的"写 n 位"去构造消息，**

**`writeBits(0x15)` 会写 21 位 —— 而实际只写 5 位。**

**⇒ 差 16 位，整条消息全错位。**

**⇒ 这是一个会导致"构造的推送客户端完全不认"的错误。**

**⇒ 幸好在这轮发现了。**

---

## 七、方法论收获

> **同一个函数，写侧和读侧必须都反汇编，才能定语义。**

**如果我只读 `writeBitsCore`，会得到错误结论。**

**读了 `readBitsCore` 才发现"两边都有 `inc`"，
从而确认它是设计而非偶然。**

**⇒ "对称验证"应成为位流/协议逆向的标准动作。**

---

## 八、修正后的完整位流模型

```
位流 = 连续位序列
写入单元：
  writeBits(v)          5 位，v & 0x1F
  writeData(ptr, n)     n 位，直接拷贝
消息 = 
  5 位标签 + 8 位 + …（按 serialize 脚本）
```

**⇒ 一条 MemberList = 5 + 8 + 5 + 32 = **50 位 = 7 字节**（进位）。**
