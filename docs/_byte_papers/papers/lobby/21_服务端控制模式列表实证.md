# ★★★ 实证：服务端下发完全控制大厅模式列表

> **这是"完全自定义大厅"的实证闭环**
> 证据：`CODOL_LOCAL_CHAIN_V2\publisher_files\` 下的两组 `.info` 文件

---

| 文件 | 压缩大小 | 解压大小 | 内容 |

## 3. 这证明了什么

### 证据 A：客户端接受替换

客户端在大厅初始化时请求 `mp_playlists_shipRetail_1.0.0.info`
（第 `8` 卷的 `10/21` 请求，payload 实测：

```
10 00 10 "mp_playlists_shipRetail_1.0.0.info" 00 00
```

）。

服务端从 `publisher_files/` 读这个文件、压缩、下发。

**客户端拿到的是服务端给的那份，不是磁盘上 `mp_playlists.ff` 里那份。**

### 证据 B：项目已经成功替换过

`bak_dummy` 的存在 + 注释"rebuilt 2026-10-06"，
说明当时**有人把官方 112KB 版本换成了自制 4.4KB 版本，并且跑通了**。

（否则不会有"bak_before_playlists"这种备份命名。）

### 证据 C：`buildversion 1649370` 写进了自制版

```
buildversion 1649370
```

这正好是**目标 build 号**（第 6 卷已锚定）。

**客户端会校验这个字段**，所以自制版必须写对。

---

## 4. ★ 结论：大厅模式列表完全由我们控制

```
客户端 ──10/21 请求──> 服务端
                        │
                        ├─ 读 publisher_files/mp_playlists_shipRetail_1.0.0.info
                        ├─ zlib 压缩
                        └─ 下发
客户端 ──解析──> 构建模式列表 / 对局列表
```

**磁盘上的 `mp_playlists.ff`（AES 加密）被绕过了。**

| 目标 | 操作 | 需 AES？ |
|---|---|---|
| **新增模式按钮** | `.info` 里加 `catinfo` + `playlist` | **否** |

| **改模式名字** | 改 `name chinese`（GBK） | **否** |
| **改可用地图** | 改 `mp_xxx,type,1` 行 | **否** |

**前 6 项（也就是用户最关心的"增删模式/按钮"）全部不需要密钥。**

## 7. 还剩下的边界

### 边界 1：`catinfo` 与 `playlist` 的 category 对应

官方版 `category 1` → `catinfo 1`（冲锋团队竞技）。
自制版 `category 0` —— **0 是个特殊值**，可能是"不分组"。

### 边界 2：`script <name>` 指向的脚本必须存在

自制版用 `script war`，而官方 `gametype tdm` 也是 `script war`。
**说明 `war` 是 TDM 的通用脚本。**

如果写一个不存在的 `script xyz`，加载会失败。

### 边界 3：地图必须在本地 `.ifs` 里存在

自制版注释："Maps verified present in the local IIPS packages."
**用了 12 张确认存在的地图。**
