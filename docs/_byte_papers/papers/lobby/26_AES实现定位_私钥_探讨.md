# AES 私钥定位 · 探讨：从"静态反汇编失败"到"内存里捞到私钥"

> 对应：`lobby/26_AES实现定位_私钥.md`

---

## 一、拐点在哪

前 25 卷，我一直卡在"`.ff` 是 AES 加密，但拿不到密钥"。

尝试过：
- 黑盒统计（第 13 卷）→ 确认是加密，但拿不到密钥
- 反汇编 `IIPSVFS.dll` 的 `CCoderRWFilter`（第 15 卷）→ 证明了不是它
- 读 `IFS2.dll` 的 libtomcrypt（第 16 卷）→ 只有 hash/公钥，没有对称加密

**然后我发现磁盘 EXE 的 `.tp3` 段线性反汇编错位（第 25 卷）。**

这是关键转折 —— **不是说"反汇编错了"，而是说"反汇编这个工具在这里不适用"。**

---

## 二、换工具

项目里有两个内存转储：

```
DEDRUN_RUNTIME_0x810000.bin       348 MB
client_runtime.bin                230 MB（CODOL_LOCAL_ENGINE_CHAIN_20261019）
```

`client_runtime.bin` 里能搜到 `dwRoomMessageStartGame`、`ClientLogin`。

我做了两件事：

1. **验证映射**：`aes` 字符串在 dump 偏移 `0x9b5ed4`，其 VA 是 `0xdb5ed4`。
   **差值恰好 0x400000。**
   再用 `common_gametype_mp` 验证第二个点。**两处都对。**

2. **用 push imm32 找引用**：不用反汇编，直接搜 `68 d4 5e db 00`。

**结果：5 处命中（磁盘上只有 3 处）。**

---

## 三、为什么内存里多了 2 处

磁盘上的 3 处是静态代码里的 `push 0xdb5ed4`。

内存里多出的 2 处（`0x83b06`、`0x36ab72`）……

**等等，`0x83b06` 对应 VA `0x483b06`，这就是 `0x483a50` 函数里的那一条！**

**磁盘上为什么没有？**

因为磁盘上对应的位置是 `0x5c042`（VA `0x45c042`）——
**同一个函数，在磁盘和内存里 VA 不同。**

**这说明 `.tp3` 在加载时被重定位/重排了。**

（第 25 卷观察到"错位"，根因可能就是这个。）

---

## 四、反汇编 `0x483a50`

从内存镜像反汇编，一切正常：

```
push ebp / mov ebp,esp / sub esp,0x15c
mov eax, [0xe3f240] / xor eax, ebp     ← 栈保护 cookie
...
push 0xd5b2e0    ← 算法表
call 0xbc80d0
...
push 0xdb5ec0    ← "sha256"
...
push 0xdac4b0    ← 1187 字节数据
push 0x4a7       ← 1191 = 1187 + 4
...
push 0xdb5ed4    ← "aes"
...
push 0x1c51734   ← 输出缓冲
call memcpy
```

**结构清晰：查算法 → 导入密钥材料 → 设置 AES → 拷贝到全局。**

---

## 五、1187 字节数据

`0xdac4b0` 开头：

```
30 82 04 a3 02 01 00 02 82 01 01 00 bd 7e d6 e2 ...
```

作为 ASN.1：

- `30 82 04 A3` = SEQUENCE，长度 1187
- `02 01 00` = INTEGER 0（version）
- `02 82 01 01` = INTEGER 257 字节
- `00 BD 7E D6 E2...` = 模数（2048 位，有前导 0）

**接着是 8 个 INTEGER：`n, e, d, p, q, dP, dQ, qInv`。**

**这是 PKCS#1 的 RSA 私钥。**

---

## 六、我不敢直接相信

看到 8 个 INTEGER，第一个反应是"像私钥"。

**但"像"不等于"是"。**

我做了两个数学检查：

```python
p * q == n                              → True
(e * d) % ((p-1)*(q-1)) == 1            → True
```

**两条都通过。**

**这才是"是私钥"的证明。**

如果不做这两个检查，可能会把一个"碰巧有 8 个整数"的数据段当成私钥，
后面所有推导都建立在沙子上。

---

## 七、这解决了什么

**`.ff` 的 AES 密钥，不再是一个黑箱。**

```
私钥在里面  →  AES 密钥可以派生  →  .ff 可以解
```

而且因为**私钥在客户端**（不是服务端），
说明这套加密**根本不打算阻止客户端解密** ——
它只是防"随便改盘上文件"，不防"有人会逆向"。

---

## 八、方法论收获（最重要的一卷）

### 收获 1：静态反汇编失败时，换内存镜像

磁盘上的代码可能是重定位的、加壳的、指令变体的。
**内存镜像里的代码是"已经准备好执行"的形态，反汇编可靠得多。**

### 收获 2：不要用线性反汇编找引用

`push imm32` = `68 <4 字节>`，**6 字节固定模式，不依赖指令对齐。**

用它找字符串引用，永远有效。

### 收获 3：看到"像私钥"必须做数学验证

`p*q == n` 和 `e*d ≡ 1 (mod φ)` 是 RSA 的**定义性**检查。

**不做这两步，"私钥"只是"8 个大整数"。**

### 收获 4：映射关系要两个点验证

我只用 `aes` 一个点得出了 `off = va - 0x400000`。

**但一个点可能巧合。**

用 `common_gametype_mp` 第二个点验证后才敢用。

## 九、还剩什么

1. `0x483a50` 里 `[ebp-0x2c]` 那 24 字节中间值
2. AES 模式（CBC/CTR/CFB）和 IV
3. `0x1c51734` 在这份 dump 里是 0 —— 需要更晚的 dump
4. 实际解密一次 `.ff` 验证

**第 4 条是最终的判定标准。**
