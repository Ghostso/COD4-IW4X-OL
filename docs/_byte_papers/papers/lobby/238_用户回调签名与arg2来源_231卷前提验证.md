## §0 结论

**★★★ 大厅服务的用户回调签名是 `cb(reply, status)`，两个参数。`status` 不是"有无数据"，而是"请求是否成功"；它有三个来源，其中正常路径来自 `reply+4`。**

1. **★★★★ 231 卷的未验证前提成立**：空 ACK / 超时时 `status == 0`。
2. **★★★★ `reply+4` / `+5` / `+6` 分工定案**（见 §4）。
3. **★★ 更正 237 卷**：`[ebp+0xc]` 不是"调用方随便传的标志"，而是 `reply+4` 的值（正常路径）。

| # | 证据 | 强度 |

| ① | `0x7FAF7B push eax` / `0x7FAF7C push esi` / `0x7FAF81 call ecx` | ★★★★★ |

## §1 ★★★★★ 用户回调派发：`0x7FAF50`

```asm
0x7FAF50  push ebp / mov ebp,esp / push esi
0x7FAF54  mov  esi, eax                ; esi = 响应对象
0x7FAF56  call 0x7FA3F0                ; 前置处理
0x7FAF5B  cmp  byte ptr [0x82CA046], 0 ; 某开关
0x7FAF62  je   0x7FAF75
0x7FAF64  mov  eax, [esi]              ; 消息类型
0x7FAF66  cmp  eax, 0x7F / 0x1B / 0x1A ; ★ 三种特殊类型也直接回调
0x7FAF73  jne  0x7FAF8A
0x7FAF75  mov  eax, [ebp + 8]          ; ★★ 参数2 = status
0x7FAF78  mov  ecx, [esi + 0x30]       ; ★★ 用户回调地址
0x7FAF7B  push eax                     ;   push status
0x7FAF7C  push esi                     ;   push reply
0x7FAF7D  mov  byte ptr [esi + 6], 1   ; ★ 置 "+6 = 1"（回调进行中）
0x7FAF81  call ecx                     ; ★★★ cb(reply, status)
0x7FAF83  add  esp, 8
0x7FAF86  mov  byte ptr [esi + 6], 0   ; ★ 清 "+6 = 0"
0x7FAF8A  mov  dword ptr [esi], 1      ; 状态归 1
0x7FAF90  call 0x7FA450                ; 释放
```

**⇒ 回调签名 = `cb(reply_object, status_byte)`。**

★ **`[esi+0x30]` 是用户回调，`[esi+0x2C]` 是内部派发（0x7FA733 写入 `0x7FADC0`）。** 两个槽分工不同。

## §2 ★★★★★ `status` 的三个来源

`0x7FAF50` 有 **3 个调用点**，每个的 `arg2` 来源不同：

| 调用点 | `arg2` 来源 | 触发条件 | 语义 |
|---|---|---|---|
| `0x7FAFC4` | **`push 0`**（`0x7FAFC2`） | `[esi+0x10] != 0` 且 `[esi+0x18] == 0` | **无数据 / 流结束** |
| `0x7FAFED` | **`push 0`**（`0x7FAFE9`） | `[esi+0x1C] >= [esi+0x20]`（缓冲满） | **超时 / 满** |
| `0x7FB059` | **`movzx edx,[esi+4]`**（`0x7FB052`） | 内部派发 `0x7FADC0` 返回真 | **正常完成** |

```asm
; 正常路径（0x7FB03D）
0x7FB041  mov  byte ptr [esi + 6], 1      ; 置 +6 = 1
0x7FB045  call ecx                        ; [esi+0x2C] = 0x7FADC0 内部派发
0x7FB04A  mov  byte ptr [esi + 6], 0      ; 清 +6
0x7FB04E  test al, al
0x7FB050  je   0x7FB061                   ; 失败 → 不回调
0x7FB052  movzx edx, byte ptr [esi + 4]   ; ★★★ status = reply+4
0x7FB056  push edx
0x7FB057  mov  eax, esi
0x7FB059  call 0x7FAF50                   ; cb(reply, reply+4)
```

**⇒ 正常时 `status = reply+4`；超时/无数据时 `status = 0`。**

## §3 ★★★★★ 231 卷前提验证通过

231 卷的根因链条：

```
服务端回空页
  → 回调 0x4A7FB0 的 [ebp+0xc] == 0 ?
  → 是 → 查 reply+5 == 0 → 是 → state = 2
```

**231 卷没有验证「空 ACK 时 `[ebp+0xc] == 0`」。**

**本卷验证**：

- 空 ACK / 超时 ⇒ `arg2 = push 0` ⇒ 回调收到 `[ebp+0xc] == 0` ✅
- 有数据 ⇒ `arg2 = reply+4`

★ **⇒ 231 卷的根因结论成立。**

### 3.1 而且链条更完整了

```
服务端回空 ACK
  → 0x7FAFC2 push 0        (无数据分支)
  → cb(reply, status=0)
  → 0x4A7FB4 cmp [ebp+0xc], 0   → 等于 0 → 继续
  → 0x4A7FBB mov eax, [ebp+8]   (reply)
  → 0x4A7FBE cmp byte [eax+5], 0 → 等于 0（空页没数据）→ 失败
  → 0x4A7FDE mov [0x82C4A88], 2  → state=2 ★ 死锁
```

★★ **现在的每一步都有机器指令证据，不再有未验证前提。**

## §4 ★★★★ `reply+4` / `+5` / `+6` 分工定案

结合本卷与 235/237 卷：

| 偏移 | 语义 | 证据 |
|---|---|---|
| **`+4`** | **请求成功/结果码** —— 作为 `status` 传给用户回调 | `0x7FB052 movzx edx, byte [esi+4]` |
| **`+5`** | **数据有无** —— 商城用它判"空页" | `0x4A7FBE cmp byte [eax+5], 0` |
| **`+6`** | **回调进行中标志** —— 派发前置 1、返回后置 0 | `0x7FAF7D` / `0x7FAF86` / `0x7FB041` / `0x7FB04A` |

★★★ **这解释了 237 卷的困惑**：`0x684D93` 同时查 `+6`/`+0x64`/`+5`/`+4`，是因为**这四个是不同含义的标志**，不是"同一状态字节的不同副本"。

★ **也解释了 235 卷的"极性相反"** —— 商城查的是 `+5`（数据有无），通道 135 那处查的是别的字段；**不是同一字段的不同极性。**

## §5 更正 237 卷

237 卷说：

> 「主流判据是 `cmp byte ptr [ebp+0xc], 0`（第二个参数）…… 由**调用方**传入"成功/失败"标志 —— 最通用」

**部分正确**：

- ✅ 主流确实是 `[ebp+0xc]`
- ❌ 但**不是"调用方随便传"** —— 它由**框架**在 `0x7FAF50` 处决定：正常时取 `reply+4`，超时/无数据时填 0

★ **⇒ 更准确的说法**：`[ebp+0xc]` 是**框架给出的「本次请求结果码」**，来源是 `reply+4` 或常量 0。**服务端应答内容会影响它**（通过 `reply+4`）。

★★ **这意味着 237 卷 §4 的推论「只有商城空 ACK 才会失败」需要修正**：

| 判据形态 | 服务端能否影响 | 结论 |
|---|---|---|
| `[ebp+0xc]`（主流） | ✅ **能**（`reply+4`） | 空 ACK ⇒ status=0 ⇒ 可能失败 |
| `reply+5`（商城） | ✅ 能 | 空 ACK ⇒ 失败（已证） |
| 全局开关 | ❌ 不能 | 与服务端无关 |

**⇒ 「回空 ACK 会不会失败」不能按判据形态一刀切，要看该服务对 `status==0` 的处理。**

## §8 方法论

1. **★★★★★ 「未验证前提」必须显式列出并优先验证。** 231 卷的根因依赖「空 ACK 时 `[ebp+0xc]==0`」，我隔了 7 卷才验证它。**结论对不等于推导完整。**
2. **★★★★ 回调参数必须追到「谁压栈」，不能停在「回调读了它」。** `[ebp+0xc]` 在 35 个回调里都被读，但只有追到 `0x7FAF50` 才知道它来自 `reply+4`。
3. **★★★ 一个对象的相邻字节往往是不同含义。** `+4`=结果码、`+5`=数据有无、`+6`=回调中 —— 把它们当"一个状态字节"会得出 235 卷那种"极性相反"的错误结论。
