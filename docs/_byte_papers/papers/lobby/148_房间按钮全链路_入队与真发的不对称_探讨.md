# 148 探讨 · 把前端挖开之后，问题变成了「谁把队列送出去」

> 配套：[148 · 房间按钮全链路](148_房间按钮全链路_入队与真发的不对称.md)
> 主题：**我七卷都在挖"入站"，这一卷第一次挖"出站"。挖开之后，问题的形状完全变了。**

---

## 一、我之前的思路有个大盲区

139–147 卷，我一直在问：

> **服务端发什么，客户端才能正确响应？**

这是一个**入站**问题。

`AS_SetReadyState`、`AS_ChangeTeam`、`AS_VoteMap` 这些**出站**接口，
我从来没查过它们**发不发、发什么**。

★★★ **用户点按钮没反应，最直接的可能就是"客户端根本没把请求发出去"。**

---

## 二、第一步就排除了一个假设

枚举 `AS_*` RTTI：**678 个**，其中房间相关 **33 个**。

```
AS_SetReadyState   AS_ChangeTeam   AS_VoteMap
AS_StartMatch      AS_ChangeRoomInfo  AS_ChangeRoomOptions
AS_SendVoteRequestToDS  AS_CurrentPlayerCanVote  ...
```

**⇒ 按钮不是"没有回调"。** 这一步只花了 3 分钟。

★★ **排除法比证明法便宜。**

---

## 三、顺着路径挖，一路都通

```
Flash 按钮
 → AS_SetReadyState handler 0x7CF850
     0x7CF859  mov ecx,[0x82E13FC]     ← 房间对象
 → dwRoomImp::vt[33] = 0x6301A0
     0x6301AE  type = 0x10 (Ready)
     0x6301B5  vtable = 0xDC7624
     0x6301BF  call 0x62C5A0           ← ★
```

而且我查了 `[0x82E13FC]` 在三个 dump 里的值：**全部非 0**，vtable `0xDC7274` = `.?AVdwRoomImp@@`。

**⇒ 房间对象存在，按钮路径完整打通。**

★★★ **这推翻了我之前"房间对象未创建"的猜测**（那是另一个项目里的旧结论，我不该沿用）。

---

## 四、转折点：`0x62C5A0` 不是网络发送

我以为 `0x62C5A0` 是"发送"，直到看它的函数体：

```asm
0x62C5BF  add edi, 0x3A098        ; 容器基址
0x62C5D4  call 0x654CD0           ; 查容器
0x62C63D  call edx                ; 消息 vt[0] = 序列化自己
0x62C651  call 0x654BF0           ; 插入
```

**没有 `0x7E8300`，没有网络调用。它只是"放进一个本地容器"。**

然后我找到真正的网络发送：`0x62C870` 内部调 `0x7E8300`。

**而 `0x62C870` 的调用者用的是 `kind=4`；房间动作用的 `0x62C5A0` 是另一条路。**

---

## 五、不对称才是本卷的核心

| 消息 | 路径 |
|---|---|
| 用户点"准备"（Ready 0x10）| `0x62C5A0` **入队** |
| 用户点"改阵营"（ChangeTeamRequest 0x15）| `0x62C5A0` **入队** |
| StartGame（0x3）| `0x62C870(kind=4)` **真发** |
| MemberInfoAdd（0xA）| `0x62C380(kind=4)` **真发** |

★★★ **同一个 `dwRoomImp`，用户动作走"入队"，状态广播走"真发"。**

**这就是新的问题形状：入队的消息，谁把它真发出去？**

---

## 六、我这一卷的教训

### 6.1 一直挖一个方向，会形成盲区

我七卷都在挖入站。**出站一次没查。**

★ 而且每一卷都有收获，所以从没觉得方向有问题。

★★★ **教训：连续几卷挖同一侧时，主动去挖另一侧。**

### 6.2 旧结论不能直接沿用

我一开始担心"房间对象可能没创建"——那是**别的项目**（`codol-myhandler-never-created-root-cause`）里的结论。

**一查 dump：`[0x82E13FC]` 非 0。**

### 6.3 「函数名像什么」不等于「它做什么」

`0x62C5A0` 我之前标为"序列化器"，就默认它在发送。**读函数体才发现它只入队。**

## 七、还剩最后一段

**「入队 → 真发」的桥接点。**

已知：
- 入队容器的分发在 `0x6330xx`（FNV 哈希查表）
- 真发入口是 `0x62C870(kind=4)`

**没找到的是：谁从入队容器取出消息，交给 `0x62C870(4)`。**

候选线索（未分析）：
- `0x62C72E` / `0x62C82F` / `0x62CA1D` —— 三处 `add eax, 0x3A0D4`，在 `0x62C870` 附近
- `0x6331BD` 之后的 `+0x3A118` 队列处理

★★ **这是下一个要挖的点，而且它就在 `0x62C8xx` 这 2 KB 内。**

---

## 八、方法论

1. ★★★★ **前端接口先枚举**：678 个 `AS_*`，3 分钟排除"缺回调"。
2. ★★★★ **出站也要挖**：只挖入站会形成系统性盲区。
3. ★★★★ **`kind` 参数决定路径**：同一个发送函数，`kind` 不同行为不同。
4. ★★★ **容器基址用 `add reg, imm32` 算**，只搜 `lea` 会漏。
5. ★★★ **230 MB 镜像必须用 `bytes.find`**，逐字节 Python 循环会超时。
