## 二、★★ 更正 139 卷：段2 不是「0.2% 文件空洞」

### 2.1 139 卷的原判据与它的缺口

139 卷 §1 写：

> 段2 `.tp3` `VSize=0xDBB1CC0`(230MB) / `RawSize=0x62000`(401KB) ⇒ **覆盖 0.2%**。段2 的"磁盘实测值"一律是文件空洞。

**`RawSize=0x62000` 这个数字没错**（PE 节表实测，本卷复核一致）。错的是从它推「文件里没东西」。

**`RawSize` 是「标准 PE 加载器从这里拷多少」**，不是「文件里这里有多少」。当一个文件被自研加载器整体映射（或 VMProtect 自解）时，`RawSize` 与文件的物理长度毫无关系。

### 2.2 实测：RawSize 边界外 20% 非零

```
section3 RVA 0xA16000..0xE5C7CC0  VSize 219.69 MB  RawSize 400 KB
file 物理长度 0xE659000 (230.4 MB)  ⇒ 段2 的 RVA 范围整段都有物理字节
```

| 度量 | 值 |
|---|---|
| 段2 范围内非零字节 | **25,849,974** |
| 占 VSize | **11.31%** |
| `RawSize` 窗口内(0xA16000..0xA78000) 非零 | 207,105 / 401,408 = **51.6%** |
| `RawSize` 边界外 32 MB 非零 | 6,884,196 / 33,554,432 = **20.52%** |

⇒ **RawSize 边界之外有大量真实数据**。139 卷「一律空洞」的表述必须作废。

### 2.4 为什么 VMProtect 文件会这样

`RawPtr == RVA`（段2 的 RawPtr `0xA16000` 恰等于 RVA `0xA16000`）⇒ **该段的 `PointerToRawData` 与 `VirtualAddress` 相等**，这是「文件尾部大块数据直接从同一偏移起铺」的写法。自研加载器按 `VA = off + ImageBase` 直接映射即可，完全绕开 `RawSize`。

> **这正是我在 139–154 卷一直在用的映射公式 `VA = file_offset + 0x400000`。** 这个公式对本镜像**一直是对的**——139 卷却用 `RawSize` 推翻了它，自相矛盾。本卷把这个矛盾消掉：**映射公式对，`RawSize` 判据错。**

### 4.1 数值结构自证（不是巧合）

`83886082 = 0x0500_0002`、`419430402 = 0x1900_0002`、`754974722 = 0x2D00_0002`、`1090519042 = 0x4100_0002`。

**低 16 位恒为 `0x0002`，高 16 位是 `0x05/0x19/0x2D/0x41`** —— 步进 `0x14`（20）。

⇒ **zone_id 的高字是「大区序号」、低字是「平台/环境标记 2」**。这与 `[cross_zone_*]` 里的 `zone_id=` 完全一致（`cross_zone_stgd` 的 `zone_id=754974722`）。

## 十、方法论

1. **★ `RawSize` ≠ 文件物理长度，只等于「标准加载器映射窗口」。** 判断「文件里有没有」必须**直接读字节数非零**，不能看节表。
2. **★ 一个映射公式被用了 15 卷且从未失败，就不该被一个节表字段推翻。** 139 卷用 `RawSize` 推翻 `VA = off + ImageBase`，是「理论压过实测」的错误；本卷用 25 MB 非零字节把它纠正回来。
3. **★ 明文配置块用 `[section]` 正则找边界，再向上回溯找真正的头。** 从中间某节起读会低估长度（本卷 B 块从 `0x331E6E3` 回溯到 `0x331D420` 才完整）。
4. **★ 两条独立路径得出同一张表 ⇒ 这是最高级别的确认。** 154 卷（代码读 `0xE69CE0`）与 155 卷（磁盘明文）5/5 吻合。
5. **配置面就是协议面。** `[dw_config]` 的超时值与代码里的 `0x3A98`/`0x7D0` 同量纲；`[dw_service_info]` 的开关决定了哪些 srpc 服务真的会发请求。
6. **前卷的「弃权」会连锁压缩后续卷的范围。** 139 卷对段2 弃权 ⇒ 143 卷只看两段 ⇒ 直到今天才发现段2 有明文。**每卷的「不查」都要写成显式待办。**
