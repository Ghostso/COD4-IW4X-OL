## 二、`msg/11`：一个挂了 155 卷的"未解"，其实是抄错了版本

`msg/11` 卷说：

> 「内层的 16 字节，结构未知。5 种假设全部失败。这是本卷集合里**唯一一个『外层完全解出、内层完全未解』的地方**。」

它记录的字节：

```
0c 00 00 00 02 02 00 00 00 08 00 00 00 80 08 00
```

**这个字节串，和我们服务端 `codol_crypto.py:803` 的 `ROOM_READY_BATCH` 逐字节相同。**

而 `ROOM_READY_BATCH` 的注释写着：

```python
# 房间 ready 批次的 16 字节常量 —— 照抄 ol-mod Unknown0BService.cpp:98-101。
```

**⇒ 这 16 字节是 ol-mod 对着 3.3.3.3 版本客户端抓的。**

**而 161 卷已证：本 build（1649370）客户端真正发的 ready 是 13 位位流 = 2 字节 `02 18`。**

### 所以"未解"的真相是

> **`msg/11` 抓到的是另一个版本客户端的报文。用本 build 的文法去解，当然解不开。**

**这不是"解不出来"，是"解错了对象"。**

而且它反过来印证了 161 卷：**拿这个 16 字节做判据，必然失败。**

## 三、`room.changemap` 和 `maxResults=20`：问题本身问错了

### `room.changemap` 对应报文

我原来以为有一个"changemap 专属 task"。

**实际：所有房间动作都走 `11/4 setRoomData` 的 blob batch。**（161 卷已证 ready 走这里）

**⇒ 没有"changemap 报文"这个东西 —— 它是 `11/4` 里某一种 batch 内容。**

### `6/5` 的 `maxResults=20`

`6/5` = service 6, task 5。**服务端全源码读过，没有这个分支 ⇒ 我方从不发。**

**⇒ 客户端也就不可能有对应的读侧字段。**

**⇒ "20 是否硬编码"这个问题，前提就不成立。**

## 四、`<<10` 那个怪数字：其实是跨字段误读

119 卷为它纠结过：

> 「`u32@[4:8] == (len-10) << 10`，等价 `u16@[5:7] == (len-10) × 4`。为什么是 `<<10` 而非 `<<3`（=×8，真位长），本卷不下结论。」

**本卷看明白了**：

```
u32 = u16 << 8        ← 这才是那个 <<8 的来源
u16@[5:7] = (len-10) × 4
```

**⇒ `[4]` 是 u16 的高字节，`[7]` 恒 0。所谓 `<<10` 只是「u16 值乘 4，再被当成 u32 读时左移 8 位」。**

**⇒ 那个字段就是 `(len-10) × 4`，一个 u16。`×4` 的含义：数据体按 4 字节（u32）计数的元素个数。**

**"为什么是 `<<10`"这个问题的答案是：它不是 `<<10`，它是 `×4` 加一次跨字段误读。**

## 五、`[0x82E1400]` 是 `dwPartyImp` —— 这改变了对房间子系统的理解

152 卷说：`0x639D00` 创建 3 个单例，其中 `[0x82E1400]`「身份未定」。

本卷 RTTI 一解：

```
0xDC73DC → .?AVdwPartyImp@@
0xDC7474 → .?AVdwPartyImp@@
0xDC7714 → .?AVMyRoomImp@dwPartyImp@@
0xDC787C → .?AVMyRoomEventHandler@dwPartyImp@@
```

**⇒ 它是 `dwPartyImp`（组队），继承 `dwRoomImp`，内含 `MyRoomImp`。**

**所以房间子系统不是"三个平行的单例"，而是：**

```
dwRoomImp（房间）
dwPartyImp（组队）—— 继承 dwRoomImp，内含 MyRoomImp + MyRoomEventHandler
dwInvitationImp（邀请）
```

**"队伍里的房间"是一个独立实现**，这解释了为什么 `0xE36E4D8` 那个 0x730 状态块会被**两个对象各 memset 一次**——它们是同一块共享状态。

## 六、还剩的那 1 项

`6/5` 的消息类型码表 / 位流容器。

**它不是"解不出"，是"我方服务端从不发 `6/5`，所以没有样本可对"。**

**⇒ 只要我方服务端推一次 `6/5`，客户端能不能解就知道了。**
**⇒ 这是工程动作（改服务端），不是逆向动作。**

## 八、方法论（本卷新增三条）

1. **★★ 「证明它不存在」是最彻底的闭合。** `changemap` 没有独立报文、`6/5` 没有客户端读侧、`msg/11` 的 16 字节不属于本 build —— 三个"未解"都是问题提错了。
2. **★★ 跨字段误读会造出"神秘常数"。** `<<10` 其实是 `×4` + u16/u32 混读。**遇到怪标度，先查是不是读错了宽度。**
3. **★ RTTI 一次解析胜过猜测十次。** `[0x82E1400]` 挂了三卷"身份未定"，`vftable[-4] → COL → type_info → +8` 一次就到 `dwPartyImp`。
