## 1. 双向联合统计（最硬的证据表）

```
            SER                            DER
tag 0x01    1 位 × 41                      1 位 × 41
tag 0x02    8 位 × 3                       8 位 × 5
tag 0x03    8 位 × 98                      8 位 × 96
tag 0x05    16 位 × 1                      16 位 × 1
tag 0x06    16 位 × 22                     16 位 × 22
tag 0x07    32 位 × 2                      32 位 × 2
tag 0x08    32 位 × 17                     32 位 × 17
tag 0x0a    64 位 × 8                      64 位 × 8
tag 0x0d    32 位 × 14                     32 位 × 14
tag 0x10    变长 × 19                      8 位 × 19（内部循环）
tag 0x13    blob × 6                       blob × 6（内部循环）
tag 0x15    8/16/32/64 × 149              8/16/32/64 × 149
```

**除 `0x10`/`0x13`（helper 内部循环）与 `0x02`（见 §4），
两侧 11 个标签的位宽组合逐一吻合。**

## 2. 语义判定（两个层级）

### 2.1 编号 = 类型（窄类型专用通道）

| tag | 语义 | 依据 | 实例 |
|---|---|---|---|
| `0x01` | `bool` | 41 次全是 1 位，值只 0/1 | `UpdateCreditRating` 尾 |
| `0x03` | `u8` | 98 次全是 8 位 | 几乎所有消息首字段（消息类型号） |
| `0x05` | `u16` | 1 次 16 位 | `AvatarInfo` 内部 |
| `0x06` | `u16` | 22 次全是 16 位 | `AvatarInfo`、`MemberDetails` |
| `0x07` | `i32` | 2 次 32 位 | `MyPartyInvitation` |
| `0x08` | `u32` | 17 次 32 位 | `UpdateWarGodData`、`MemberDetails` |
| `0x0a` | `u64` | 8 次 64 位 | 账号 ID（CODOID） |
| `0x0d` | `float32` | 14 次 32 位，源为 `fld dword` | `RoomInfo` 坐标 |
| `0x10` | 字符串 | 写 `(len+1)*8` 位 | 房间名/昵称 |
| `0x13` | blob | `0x13 0x08 u32n n*8位` | `StartGame` 三块 |

### 2.2 `0x15` = **无类型通道**（位宽随行）

**这是本卷最重要的判定。**

**`0x15` 出现 149 次，位宽 8/16/32/64 全有。同一个函数里可以连续 28 个。**

**⇒ 它不可能是"某一种类型"。**

**⇒ 它是"这里有一个字段，类型由下一个 32 位立即数决定"的通用标记。**

**源码层面的原型很可能是：**

```c
WriteField(uint32_t value, int nbits);
//   -> writeBits(0x15); writeData(&value, nbits);
```

**而 `0x03`/`0x06` 等是这个函数被内联展开的特化版本：**

```c
WriteU8 (uint8_t v){ writeBits(0x03); writeData(&v,8); }
WriteU16(uint16_t v){ writeBits(0x06); writeData(&v,16); }
```

**⇒ 词表就是"常用宽度留了专用编号，其余走 0x15"。**

## 3. `0x0d` 是 float32 的实证

**`RoomInfo::serialize` 里 `0x624788`：**

```
0x624788  d9 46 30        fld  dword ptr [esi+0x30]    ← x87 加载 float
0x62478b  6a 0d           push 0x0d
0x62478d  d9 5d f8        fstp dword ptr [ebp-8]       ← 存回 float
0x624790  e8 ...          call 0xb77b10                ← writeBits(0x0d)
0x624795  d9 45 f8        fld  dword ptr [ebp-8]
0x624798  6a 20           push 0x20
0x62479a  8d 45 f4        lea  eax,[ebp-0xc]
0x62479d  d9 5d f4        fstp dword ptr [ebp-0xc]
0x6247a0  50              push eax
0x6247a1  8b cb           mov  ecx, ebx
0x6247a3  e8 ...          call 0xb777c0                ← writeData(32 位)
```

**⇒ `fld dword` → `writeBits(0x0d)` → `writeData(32)` = IEEE-754 float32。**

**⇒ `RoomInfo` 里有 7 个 `0x0d` 字段，且集中在**同一段连续的坐标/角度区域**：

```
... 0x0d:32 0x06:16 0x03:8 0x03:8 0x03:8 0x03:8
    0x0d:32 0x0d:32 0x0d:32 0x0d:32 0x0d:32
    0x06:16 0x06:16 0x0d:32 ...
```

**⇒ 5 个连续 float32 + 2 个 u16 夹在中间，
非常像"3 个位置向量 + 2 个角度"或"5 个玩家槽的某属性"。**

## 4. `0x02` 的唯一异常

**`0x02` 只在 `RoomInfo`/`Join` 各出现一次，
SER 侧对应位置写的是 `0x03`，DER 侧读 `0x02`。**

**而该位置的断言 `0x8435D0` = `c3`（ret）。**

**⇒ 这是 D/S 代码的一处遗留不同步，客户端不检查。**

**⇒ 所以 `0x02` 在线上从未被真正"期望"过，语义无法从代码判定。**

**⇒ 诚实标注：`0x02` 语义未知。**

## 5. 与 ByteBuffer TLV 词表的对照

| TLV（`INDEX.md`） | 位流 | 一致？ |
|---|---|---|
| `0x00` 终止 | 无 | ✗（位流靠长度定界） |
| `0x01` bool | `0x01` bool | ✓ |
| `0x03` u8 | `0x03` u8 | ✓ |
| `0x06` u16 | `0x06` u16 | ✓ |
| `0x07` i32 | `0x07` i32 | ✓ |
| `0x08` u32 | `0x08` u32 | ✓ |
| `0x09` i64 | — | ✗（位流零样本） |
| `0x0a` u64 | `0x0a` u64 | ✓ |
| `0x10` 字符串 | `0x10` 字符串 | ✓ |
| `0x13` blob | `0x13` blob | ✓ |
| `0x6b`/`0x6c` 数组 | — | ✗ |
| — | `0x02`/`0x05`/`0x0d`/`0x15` | 位流独有 |

**⇒ 9 个编号完全同构。**

**⇒ 两套序列化是同一个人写的两代实现：**
**TLV 版用标签 + 终止符定界；位流版用 5 位字段 ID + 显式位宽。**

**⇒ `0x0d`(float) 和 `0x15`(通用) 是位流版新增的**
**——因为位流要在有限带宽上省掉终止符，就必须自带位宽。**
