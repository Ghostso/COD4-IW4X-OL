## 一、为什么这张表重要

之前我说"房间动作入队后没出网"，但那只是**没见过**。

**现在我能对照了**：

| 类 | vtable | 序列化 | 谁构造 | 谁发 |
|---|---|---|---|---|
| `dwRoomMessageReady` | `0xDC7624` | `0x6287D0` | `AS_SetReadyState` | **?** |
| `dwRoomMessageChangeTeamRequest` | `0xDC7654` | `0x628320` | `AS_ChangeTeam` | **?** |
| `dwRoomMessageStartGame` | `0xDC751C` | `0x625BE0` | `0x634340` | **`0x634626`(kind=4)** |
| `dwRoomMessageMemberInfoAdd` | `0xDC7540` | `0x6260A0` | `0x634340` | **`0x634677`(kind=4)** |

★★★ **Ready 和 ChangeTeamRequest 是"有序列化函数、有构造点、但没找到发送点"。**

**这两个类是"半条链"** —— 头在（构造），尾不在（发送）。

## 二、MSVC RTTI 链是"一次导出全表"的钥匙

```
vtable[-1] → COL（.rdata 内）→ COL+12 → type_info → type_info+8 → 名字
```

**这一步把 43 个类一次全导出来了。** 而且过滤条件（`vtable[-1]` 必须是合法 COL）能挡掉假阳性。

★ 这个方法在 141 卷就用过（对 srpc），但当时只用来验一个 vtable。
**这次是把它当成"批量导出工具"用。**

## 三、顺手更正 138 卷一处

138 卷说：

> ChangeTeam 0x14 / Vote 0x1A / ChangeTeamRequest 0x15 → `0x628320`（写）

**实际**：
- `dwRoomMessageChangeTeam`(`0xDC7648`) → **`0x6281D0`**（不同的函数！）
- `0x628320` 被 **5 个类共用**：StartGameFailed / MemberDetailsQuery / StartCountingDown / ChangeTeamRequest / Vote

★★ **"一个 type 一个序列化器"是我的隐含假设，错了。** 形态相同的类会复用同一个写法。

## 四、帧更新：容器遍历的顺序

```
0x63307F  +0x3A0D4   ← 容器 1
0x6330C7  +0x3A098   ← 容器 2（房间动作入队的）
0x6331BD  +0x3A118   ← 容器 3
0x63346E  call 0x634340   ← 房间状态广播（多个 kind=4 真发）
```

**⇒ 每帧依次处理三个容器，最后广播房间状态。**

★ 容器 1 和 2 的遍历都只做"取出/摘链/释放"（`0x6330B2 call vt[0]` 是引用计数释放，
`0x63316D call 0xB74240` 是 free），**没有把内容交给 `0x62C870(4)`**。

## 五、主机可达性：一个我没想到的前置

`0x632D90` 开头就是：

```asm
0x632DD8  call 0x7F4F10          ; host 状态 0..3
0x632DE5  jmp [eax*4+0x633D10]
状态 0/3 → 0x632DEC → push "EXE_HOSTUNREACH"
状态 2   → 0x6295A0（重置计时器 + 日志）
```

★★★ **"主机不可达"会打日志，但不阻止后续流程**（打完日志就 jmp 到 `0x632E32` 继续）。

★ 这也是一个"静默失败"的候选：**如果 host 不可达，客户端可能选择不发。**

## 六、这一轮的诚实结论

**我没找到发送点，但我把搜索空间压缩到了极致：**

- ✅ 43 个出站类全部定名（表在手）
- ✅ 帧更新入口与容器遍历顺序（`0x632D90`）
- ✅ 唯一的出网函数（`0x62C870(kind=4)`）
- ✅ 唯一的网络出口（`0x7E8300`，全镜像 1 个调用者）
- ❌ **Ready / ChangeTeamRequest 的发送点**

★★★ **现在的问题是：这两个类的实例，除了 `+0x3A098` 之外，有没有被放到别的容器？**

**下一步该做的**：不是继续扫 `+0x3A098`，而是**从 `dwRoomMessageReady` 的 vtable `0xDC7624` 反查**：
**全镜像有多少处引用这个 vtable？** 每一处都是一个"构造点"。

如果只有 `0x6301B5` 一处 ⇒ 只可能走 `0x62C5A0`（已排除）。
如果有多处 ⇒ 还有别的构造点，可能通向发送。

★ **这是"从类反查构造点"的扫描，比继续读函数体更可能命中。**

## 七、方法论

1. ★★★★★ **MSVC RTTI 链可以批量导出整族类的 vtable** —— 不要一个一个人工找。
2. ★★★★ **"一个 type 一个序列化器"是错的**：形态相同的类复用同一个函数。
3. ★★★★ **"半条链"是重要信号**：头在（构造）、尾不在（发送）⇒ 要么还有别的构造点，要么设计如此。
4. ★★★ **帧更新是"每帧都跑"的地方** —— 状态机、容器遍历、广播都在这里。
5. ★★★ **`vtable[-1]` 校验（必须是 .rdata 内的合法 COL）是过滤假 vtable 的机械判据**。
