## 一、先认错

这一卷我写完之后自查，发现**两处数字是凭空写的**：

| 位置 | 我先写的 | 实测 | 错在哪 |
|---|---|---|---|
| §六 通道 0x02/0x03 | 「`push 0x02` 共 1 处、`push 0x03` 共 0 处」 | **都是 0 处** | 「1 处」是我凭印象填的 |
| §三 记录数 | 「实测 3 条」 | **12 条**（3 是 userid 行数） | 把「文本行数」当成「表项数」 |

两处都不是笔误，是**思维偷懒**：
- 第一处：我知道结论是「几乎没调用点」，于是写「1 处」让句子更自然 —— 这是**为了叙事顺畅而编数字**。
- 第二处：我看到 `[Whitelist]` 有三行 `userid`，就顺着写成「3 条记录」，**没有做 `(end−base)/step` 这一步除法**。

134 卷的教训原文是「**写完工具之前不许写数字**」。这次我工具写了，但**数字是先键入的、后跑的**。所以教训应该升级：

> **★ 数字必须先出现在工具输出里，再出现在论文里。顺序颠倒一次都不行。**

## 二、`[Whitelist]` 是什么，我怎么绕了一圈

第一眼看它：

```ini
[Whitelist]
userid=4503607658266846
userid=11376448412308544053
userid=5655630139569513483
```

「Whitelist」+「userid」= 我第一反应是**反作弊白名单**（哪些账号允许进游戏）。

**错。** 真相靠两处证据翻出来：

1. `0x7F85C0` 的循环扫的是 `0x330B978` 起、步进 `0x9C` 的记录区，扫到 `0x330C0C8` 结束 —— 说明 **userid 文本不是被解析的对象，它只是紧邻的一块文本**。
2. `0x50FDF0` / `0x5100E0` 里的格式串是 **`characterClasses` / `slots` / `emotes` / `perks`** —— 这是**外观/配装槽位**的字段名。

合起来：**这是一张「哪些 userid 被授权使用哪些外观类/槽位/表情/特长」的表。**

### 教训

**「Whitelist」这个词是陷阱。** 它在游戏里至少有三种含义：
- 反作弊进程白名单
- 服务器白名单（允许登录的 IP）
- **DVAR/资产授权表**（本处）

**词义不能替代读码。** 我必须看「谁读它、读出来干什么」，而不是看它叫什么。

## 三、那个 `DEADC0DE` 很有意思

```
4503607658266846 = 0x00100001DEADC0DE
```

低 32 位恰好是 **`DEADC0DE`** —— 这是程序员最爱的「死咖啡」魔数。

也就是说：

> **第一条 userid 不是真实账号，是一个占位/调试账号，作者故意把低 32 位写成 `DEADC0DE`。**

而另两条（`0x9DE1438E55351A35`、`0x4E7CD5A5AA08A40B`）是真账号 ID 的形态（高熵）。

这解释了一个我一直没想通的问题：**为什么一个正式发行版里会有「白名单」这种通常是运营后台配的东西？**

答：**这是开发期的授权表，正式运营时由 `0x84ABB14` 的 HTTPS 客户端从腾讯服务器拉最新版覆盖。** 磁盘上留着的 `DEADC0DE` 就是**没被覆盖过的开发默认值**。

`0x7F9090` 的代码印证了这一点：

```asm
0x7F9096  mov eax, [0xE59D20]      ; 只是 4 或 6 时才刷新
0x7F90A8  mov ecx, [0x84ABB08]  /  [0x84ABB14]
0x7F90E9  call 0x7F8E10            ; 用服务端数据覆盖
```

**⇒ 磁盘值 = 默认；运行时 = 服务端权威。** 这与 143/155 卷「通用默认值磁盘有、本账号值运行时算」完全一致。

## 四、playlist：113 条，一次全中

这一项我原本以为会很难（155 卷写了「量太大，需单独一卷」）。结果**一条正则就全捞出来了**：

```python
re.compile(rb'\r?\nplaylist [0-9]+\r?\n')
```

123 个匹配，113 个是完整块。

### 为什么这次不难

因为 **playlist 文件是纯文本 `.arena` 脚本**，不是二进制 blob：

```
// @LOGAS="Charge - Skirmish"
playlist 1
displayorder 1
category 1
name chinese "
description english "Charge TDM with bots."
...
rule scr_cha_scorelimit 50
mp_nuked,cha,1
```

**它长得就像配置文件。** 155 卷我以为它「密排」，是因为我只看了一小段 `1011 1;3265 4;...` 的片段 —— 那是 `rule` 行，不是全部。

### 教训

> **★ 一次只读 200 字节会严重误判数据结构。** 155 卷我看到 `1011 1;3265 4;...` 就下结论「密排文本」，实际那是多行 `rule xxx yyy` 被我的采样窗口挤在了一起。

## 五、`0xE69D30` 第三次定案

154 卷我把它当「类 5 参数行」（错），155 卷作废，本卷定身份：**函数指针哈希表**。

```
0xE69D30: 0xDE1404  →  [0xDE1404] = 0x7FC0F0  (push ebp; mov ebp,esp; sub esp,0x204)
0xE69D38: 0xDE1410  →  [0xDE1410] = 0x7FBF00  (push ebp; mov ebp,esp; sub esp,0x208)
```

三个卷、三次判定，最终结论是「它离通道表只有 0x50 字节，但完全无关」。

> **同一块地址我看了三次才对。** 这说明「地址相邻」这个陷阱有多深 —— 它不是看一眼就能避开的，**它会反复诱惑你**。

现在我的规则改成：

> **★ 判「是不是同一张表」时，必须先列出两张表的「写者」和「读者」两组集合，集合不相交才算两张表。**

本卷就是用这招确认的：`0xE69CE0` 的读者是 `0x7FA83E`/`0x7FA5D4`；`0xE69D30` 的写者是 `0xC95B50`、读者是 `0xC95B59`/`0xC95B77`。**零交集 ⇒ 两张表。**

## 六、通道 0x02/0x03：0 调用点也是答案

我最初的判断是「`0x02/0x03` 是高可靠通道，属于大厅主信道」。

实测：**`push 0x02` = 0 处，`push 0x03` = 0 处。**

但直方图里有 **2 处 `push eax` / `push ecx`** —— 通道号走寄存器。

所以正确表述是：

> **`0x02/0x03` 在一级表里有定义（类 1，高可靠），但代码里没有立即数硬编码的调用点；它们要么是预留，要么由运行时动态传入。**

这是一个**「负面结论」也算结论**的例子。之前 143 卷我写过「磁盘无明文」也是这样 —— 当时是错的（155 卷翻了），这次是**对的**（有 0 调用点的硬证据）。

**区别在于：这次我给出了计数器（0/106），而 143 卷只是「我没找到」。**

## 九、方法论（本卷新增五条）

1. **★★ 数字必须先出现在工具输出里，再出现在论文里。** 顺序颠倒一次都不行（本卷犯两次）。
2. **★ 表项数 ≠ 文本行数。** 必须用 `(end−base)/step` 算，不能数行。
3. **★ 词语不能替代读码。** 「Whitelist」有三种含义，只有读 `0x7F85C0` 才知道是哪种。
4. **★ 判「同一张表」要列「写者集合」与「读者集合」，零交集才算两张。**
5. **★ 负面结论（0 调用点）必须有分母。** 「0/106」是结论，「我没找到」是借口。
6. **★ 「清完文本」不等于「清完区域」。** 措辞必须与覆盖范围匹配。
