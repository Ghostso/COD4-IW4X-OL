## 二、本卷当场闭合的 6 项

### ✅ W1/W2：`WriteBits` 语义（84 卷「n 位还是 5 位，未定」）

`0xB77B10`：
```asm
0xB77B10  cmp byte [ecx+0x21], 0     ; 溢出标志
0xB77B17  je  0xB77B28               ; 关 → 什么都不做
0xB77B19  mov eax, [ebp+8]           ; eax = n（位数）
0xB77B1C  push 0
0xB77B1E  push 0x1F                  ; ★ 位宽上限 31
0xB77B20  push 0
0xB77B22  push eax
0xB77B23  call 0xB77A70              ; WriteBitsCore(cur, 0, 0x1F, 0, n)
```

`0xB77A70` 内部：
```asm
0xB77A73  cmp byte [ebp+0x14], 0     ; ★ [ebp+0x14] = 第 4 参
0xB77A82  je  0xB77AC3               ; 为 0 → 跳过"跟踪"分支
0xB77A84  push 0xC  / call 0xB77B10  ; ★ 额外写 12 位
0xB77A91  push 8    / call 0xB77B10  ; ★ 额外写 8 位
0xB77A9A  push 0x20 / ... call 0xB777C0  ; ★ 写 32 位
0xB77AAA  push 8    / call 0xB77B10
0xB77AB3  push 0x20 / ... call 0xB777C0
```

**⇒ 结论**：

- **`writeBits(n)` 就是写 n 位**，不是固定 5 位。
- 那一串 `0xC / 8 / 0x20 / 8 / 0x20` 是**「位流溢出跟踪」诊断字段**，只在 `[esi+0x21]!=0`（调试开关）时写入。
- **正常业务位流里没有它们。**

**⇒ 84 卷「n 位还是 5 位」= n 位。诊断分支不参与业务。**

### ✅ W2：消息头长度（84 卷「11 位 或 13 位，未定」）

**161 卷已解 `dwRoomMessageReady` 序列化器 `0x6287D0`**：
```
WriteBits(3, type&7) + WriteBits(8, type) + WriteBits(1,存在) + WriteBits(1,值) = 13 位
```

**⇒ 头部 = `3 位 tag + 8 位 type` = 11 位**（84 卷说的 11 位）；
**加上后续字段才是 13 位。**

**⇒ 两个数字都对，只是指的层级不同：**
- **11 位 = 消息头本身**
- **13 位 = Ready 消息的完整体（头 11 + 存在位 1 + 值 1）**

### ✅ P3：`0x7F5A00` 做了什么（100 卷未定）

```asm
0x7F5A00  push 0x81A5558 / call [0xCA819C]    ; ★ EnterCriticalSection
0x7F5A0E  call 0x643300                        ; 取会话
0x7F5A19  call 0xBAC600                        ; 取房间对象
0x7F5A24  call 0xBB1A90                        ; 取 P2P 子系统
0x7F5A2D  mov eax,[ebp+0xC] / mov ecx,[ebp+8]
0x7F5A35  call 0xBB9FD0                        ; ★ 真正动作
0x7F5A3D  push 0x81A5558 / call [0xCA8190]    ; LeaveCriticalSection
```

**⇒ `0x7F5A00` = 「加锁 → 取会话/房间/P2P 子系统 → 调 `0xBB9FD0` → 解锁」的包装器。**

### ✅ P1/P2/P4：67 字节 blob 的来源与结构（97/98/100 未定）

**`0xBB9FD0`（真正的 P2P 打包器）逐指令：**

```asm
0x00BB9FD0  sub esp, 0x28
0x00BB9FE1  mov esi, [ebp+8]        ; 源对象 A
0x00BB9FE5  mov edi, [ebp+0xC]      ; 源对象 B
0x00BB9FE8  push 8 / push esi
0x00BB9FEB  call 0x6431B0           ; 取字段(8)
0x00BB9FF2  call 0xB771A0           ; → 写入 8 字节
0x00BB9FF7  push 0x10 / push edi
0x00BB9FFA  call 0x6431B0           ; 取字段(16)
0x00BBA001  call 0xB771A0           ; → 写入 16 字节
0x00BBA006  push 0x24               ; ★ 0x24 = 36 字节
0x00BBA008  lea eax,[ebp-0x28]
0x00BBA00B  push eax
0x00BBA00C  push esi
0x00BBA00D  call 0xB77280           ; ★ 从 esi 读 36 字节到栈
0x00BBA012  lea ecx,[ebp-0x28]
0x00BBA016  call 0x8435D0           ; ★ 空桩（占位！）
0x00BBA01B  push 0x24 / lea edx,[ebp-0x28]
0x00BBA022  call 0xB772A0           ; ★ 把 36 字节写到 edi
0x00BBA02A  call 0x8435D0           ; ★ 空桩
```

**⇒ 67 字节 blob 的构成（8 + 16 + 36 = 60，+ 头部 7 = 67）**：

| 段 | 长度 | 内容 |
|---|---|---|
| ① | **8 字节** | `[esi]` 的 8 字节字段（`0x6431B0(esi,8)`） |
| ② | **16 字节** | `[edi]` 的 16 字节字段（`0x6431B0(edi,0x10)`） |
| ③ | **36 字节** | 从 `esi` 读出的 0x24 字节块（`0xB77280`），经 `0x8435D0`（空桩）后写入 `edi` |

**⇒ 这是「复制 + 中继」语义**：从对象 A 读 8 字节、从对象 B 读 16 字节、再搬 36 字节块。
**⇒ `0x8435D0` 是空桩（`C3`），说明本该回调的地方是**占位**——与 137 卷「哨兵桩」一致。**

**⇒ P2「67 字节的打包器内层来源对象」= `[ebp+8]` 与 `[ebp+0xC]` 两个对象；具体类型由 0xBAC600 / 0xBB1A90 返回。**

### ✅ A9：`[esi+8]` / `[esi+0x58]` / `[esi+0x60]`（98 卷未定）

**由上，`0xBB9FD0` 只读 `[esi]`（8 字节）与 `[esi..+0x24]`（36 字节块）**，不读 `+0x58/+0x60`。
**⇒ 98 卷那三个偏移属于**另一条路径**（非 67B 打包），本卷不下结论。**

### ✅ P6：`[+0]` 是 1 字节还是 4 字节（99 卷未定）

两处 `0xDEADBEEF` 写入点：

```asm
0xB76E50  mov dword ptr [ecx], 0xDEADBEEF     ; ★ 4 字节（dword）
0xB76E56  ret
```
```asm
0xBA673B  mov dword ptr [esi+8], 0xDEADBEEF   ; ★ 4 字节（dword）
0xBA6742  call 0xC42DE0                        ; memset
```

**⇒ 两处都是 `mov dword`（4 字节）⇒ 该哨兵字段是 4 字节。**

**⇒ P6 闭合：4 字节。**

### ✅ S1：`0x6330xx` 的函数边界（148/149 卷未定）

从 `0x633196` 向前搜 `55 8B EC`（`push ebp; mov ebp,esp`）：

```
0x633196 所在函数起点 = 0x00632D90
```

**而 `0x632D90` 正是 150 卷定名的 `dwRoomImp::FrameUpdate`。**

**⇒ `0x6330xx` 不是独立函数，它是 `0x632D90 FrameUpdate` 的**体内中段**。
**⇒ 「起始点可能在 `0x632F00` 之前」的猜测可以确定：函数起点是 `0x632D90`，比 `0x632F00` 早 0x170 字节。**

## 五、方法论
