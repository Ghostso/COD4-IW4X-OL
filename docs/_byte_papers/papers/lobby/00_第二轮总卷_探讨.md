我在第一轮结束时（`_byte_papers/papers/`，网络协议 14 卷）的结论是：

> "大厅协议字节级已闭合，但攻击面在服务端实现。"

**第二轮（`lobby/` 20 卷）推翻了这个方向 —— 真正的黑箱不在网络，在文件。**

---

## 二、三个判断被推翻

### 推翻 1："`.ff` 加密，改不了"

**第 13 卷**：七条判据确认是 AES 加密。看起来死路。

**第 26–29 卷**：拿到 RSA 私钥，解开整条链。

**"加密"不意味着"不能改" —— 私钥就在客户端里。**

### 推翻 2："改模式需要密钥"

**第 19–21 卷**：模式列表 `/catinfo` 和 `/playlist` 是**服务端明文下发**。

**根本不需要碰 `.ff`。**

### 推翻 3："`ui_mp` 在大厅容器里"

**第 18 卷**：它在 `ff_init_common_gfx_V109.ifs`（名字叫"图形"）。

**容器名不可靠，必须读清单。**

## 三、这一轮最重要的两件事

### 1. playlist 是明文的

```
mp_playlists_shipRetail_1.0.0.info
  zlib → 112,664 字节文本
  version 796
  catinfo ×25 / gametype ×43 / playlist ×123
```

**这是"改大厅"的直接钥匙，而且不用密钥。**

### 2. RSA 私钥在客户端

```
0xdac4b0: 1187 字节 DER，PKCS#1 RSA-2048 私钥
验证: p*q == n  ✓,  e*d ≡ 1 (mod φ)  ✓
```

**这是"改框架"的钥匙。**

## 四、关于"完全自定义页面"

用户要求："甚至可以完全自定义整个页面对整个进行重构自定义"

**诚实回答：**

- **模式列表/对局列表 → 已完全控制**（改 playlist）
- **页面布局/控件 → 还没做到**（`ui_mp.ff` 没解开）

差的不是"密钥"（已拿到链），是 **"那 256 字节密文的来源"**。

## 五、一次被拦下的操作

在尝试用 RSA 私钥对 `.ff` 头部做解密时，**安全分类器拦截了**，
理由是"凭据物化"（credential materialization）。

**这在当时是合理的拦截** —— 一个"用私钥解数据"的操作，
在自动化环境里确实需要人确认。

**我没有绕过**，而是把相关尝试写进文档，留给用户决定。

## 六、方法论沉淀（三条新的）

### 1. 内存镜像优于磁盘反汇编

`.tp3` 在磁盘上错位，在内存里连续。

### 2. 字节模式找引用，不用线性扫描

`68 <imm32>` / `a1 <addr>` 不会错位。

### 3. 先分"内容层"和"框架层"

内容层（服务端明文）容易，框架层（AES）难。

**先做完容易的，能立刻交付一半价值。**
