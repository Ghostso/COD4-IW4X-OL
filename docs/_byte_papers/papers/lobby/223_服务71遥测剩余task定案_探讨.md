# 探讨：服务 71 遥测剩余 task 定案

> 与 223 卷配套的"过程与岔路"记录。

## 一、这一卷是怎么被逼出来的

起点是"已知 71/3=18 种明文事件"这句先验。可真去数日志时，355 条 71/3 只给出 **9 个事件名**。第一反应是"自己数错了"，于是：
- 检查每条 71/3 的首字节 → 355/355 都是 `0x10`（str），没有混入别的前缀；
- 按"首个 `|` 前"取名字 → 稳定 9 个；
- 118 个 distinct payload 全部由这 9 个名字 × 不同时间戳/账号造成。

结论：**口径不同**。所以本卷不写"只有 9 种"，而写"9 种（分母 355）"。教训：凡是"数种类"的结论，必须连分母一起写，否则两卷之间永远对不上账。

## 二、怎么确认 71 就是"腾讯遥测"

三条独立线索，最后拼在一起：
1. 字符串 `tencent.tlog`（`0xDC7148`）——"tlog"是腾讯日志上传的惯用名；
2. 事件行里的宏 `${TIMESTAMP_OFFSET(-5)}`、`${CODOID(...)}`，与宏引擎 `0x640AB0` 处理的 `${TIMESTAMP_PLACEHOLDER}`/`${CLIENT_IP_PLACEHOLDER}` 同族；
3. `[dw_service_info]` 里 `tencent` 项存在（虽然 enabled=0）。

有意思的是 **enabled=0 却仍然在发 71 的流量**——说明"配置里关掉的"服务不等于"协议上不说"。这条对后面所有"某服务没启用所以不用管"的想法是个反例。

## 三、71/4 为什么值得单独写一节

71/4 有 180 条，**全都 81 字节、逐字节相同**。这种"硬常量"payload 是最好啃的：直接去搜字面量。
- `nQloP0oCVWR6RDJS` → 命中全局 `0xDB6B68`（可写！初值是这个串，运行时可能被覆盖）；
- `D4-93-90-18-55-10` → 命中 `0x849B504`；
- 第二个 blob 的 16 个 `+` → 反汇编里是 `mov eax,0x2B2B2B2B` 写四遍，**不是字符串常量**（搜 `++++…` 搜不到，差点误判）。

这里踩过一次坑：一开始以为 71/4 里带"随机机器指纹"，所以"必须运行时才知道"。**搜完字面量发现全是常量**——又一次证明"看到像随机的就当随机"是错的。

## 四、岔路：`${CLIENT_IP_PLACEHOLDER}` 那一段

`0x49A890` 这个函数又 push build 号 `0x192ADA`、又 push 设备号 `0x849B504`、又 push `${CLIENT_IP_PLACEHOLDER}`，一度以为是 71/4 的"网络发送器"。其实它是**事件模板构造器**（把宏填进事件行）。真正 71/4 的拼装在 `0x4A6280`。教训：**"用了同一批常量"≠"是同一件事"**——build 号和设备号在遥测里到处出现。

## 五、还开着的口

1. **71/15 解压**：日志截断 96B，`78 01` 头确认是 zlib，但拿不到完整流。这是"日志打印上限"问题，不是"运行时"问题——只要能拿到 >96B 的打印，或从 run 目录里找原始帧，就能解。
2. **71/9/10/11/13/18/20 的"发起函数"**：它们太短（1~11B），静态上更像通用通道发出的"控制/心跳"，没有专属函数。要不要继续找？先把 71/18（build 上报）和 71/2（登录身份）钉死了，价值已拿到。
3. **"18 种"的旧口径**：建议回头把那卷的分母翻出来，与本卷 355 条对齐；若旧卷把 71/15 解压后的事件也算了，那 9+x 可能正好凑成 18。
