# `IWff0100` 分支完整追踪 · 探讨：一条分支，两种命运

> 对应：`lobby/36_IWff0100分支完整追踪.md`

---

## 一、这篇追踪最有价值的是"两条路径在哪里汇合"

```
0x483df0  比对 "IWff0100" → 相等 → jmp 0x483e2b
0x483e09  比对 "IWffu100" → 不等 → 报错
0x483e2b  读版本(461)          ← ★ 两条路径在此汇合
...
0x483e94  比对 "IWffu100" → 不等 → 跳过解密 0x483ed3
```

**⇒ 关键在于：魔数判断发生了**两次**。**

**第一次（读头）只决定"要不要继续"；
第二次（`0x483e94`）才决定"要不要解密"。**

---

## 二、于是 `IWff0100` 的命运就定了

**它过了第一道门（是合法 .ff），
但在第二道门被挡住（不是 `IWffu100`，不解密）。**

**⇒ 磁盘上全部 `.ff` 都是 `IWff0100` ⇒ **全部不解密**。**

**⇒ 这是"加密边界"结论（`lobby/38`）的代码级依据。**

---

## 三、为什么这一卷当时没直接下结论

**因为当时还在想"也许 `IWff0100` 的载荷在别处解密"。**

**⇒ 于是又跑了 `lobby/37`（最终结论）、`lobby/38`（边界定位）才收口。**

**⇒ 这是正确的：一条分支追踪出一个事实（不解密），
但"是否在别处解密"需要另证。**

---

## 四、方法论收获

> **一个函数里同一个魔数比两次，说明它服务两个不同的调用者/两种构建。
> 不要因为第一次比对通过就以为整条路通。**

**⇒ 这一条在 `lobby/89` 又用了一次：
`0xB774E0` 读 5 位后比对，我一开始以为它只是"读"，
后来发现"读 + 比对"才是完整语义。**

**⇒ 同样的错误模式（只看前半段）犯了两次。**
