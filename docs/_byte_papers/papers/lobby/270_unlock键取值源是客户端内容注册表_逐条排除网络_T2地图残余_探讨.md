# 270 探讨 · 「服务端/网络能不能设 loadout4enable」的追问

## 协调者的三条线索，逐条回应

**线索 1「值是被写进去的 → 找写点」** —— 成立，且找到唯一写点：
`[0x84ABB38] ← 0x80A4C0 ← 0x660B00("loadout4enable")`。链条再往前是 `0x660B00` 的注册表 `[0x779583C]`。徽章表同理：填充循环 `0x80B2CE` 读的也是 `0x660B00` 的查表结果，**查表结果的来源就是这张注册表**。

**线索 2「0x774980 / 0x660B00 是什么系统」** —— 两个不同的东西：
- `0x774980`：从 `fs:[0x2c]`(TEB) 取 SEH，再取 `[+0x10]`，返回一个字符串或空串 `0xDAE091`。像「取当前地图/用户名」的小工具，与本问题无关。
- `0x660B00`：`hash→bucket→strcmp` 的名字查找，表在 `[0x779583C]`（堆）。**不是 dvar**（dvar 是 `0x76F190`/`[0x80F8E30]`，名@+0），**不是 configstring**（indexed）。命名空间全是内容/unlock 键。

**线索 3「clientState 5/8 触发 ⇒ 那时网络已经能改」** —— 顺序属实（第二入口无单次标志，clientState 5/8 时跑）。**但**两个入口读的是同一批输入（注册表+CSV+硬编码名），**都不读库存**。所以「网络改过输入」这个可能性，落回到「注册表能不能被网络改」—— 也就是 §3.3 的残留。

## 我的答案为什么不是干脆的 YES/NO

我把 8 条通道逐条排除干净了（对 lobby 无通路），但**注册表自身的 loader 没找到**。这不是偷懒 —— 全镜像：
- 没有一条指令写 `[0x779583C]`（基址）；
- bucket 常量 `0x1387` 只在查找函数里；
- 没有 `Dvar_Set*`/`Cvar_Set*`/`Register` 的脚本绑定（只有 `Dvar_Get*`）。

一个 26.7k 条目的表，**填充者却不在任何直接寻址里** ⇒ 它多半是「一次性大块初始化 + 拷贝」，或者填充者在镜像构造时没被完整覆盖（堆没进镜像）。

**所以诚实结论**：`loadout4enable` 的值来自客户端本地内容表，对 lobby 无已证通路；但「网络能不能在别的时机改这张表」我没有穷尽 —— 提出为独立任务。

## 为什么 267 的操作结论不受影响

267 证的是「**库存不喂 `0x8269FC8`**」（写者唯一 + 反例）。270 问的是「**unlock 键能不能被网络设**」（另一条链）。**两条链互不否定**：即使 unlock 键哪天被证可设，267 的「发库存没用」仍成立；反过来说，本卷没找到 unlock 键的网络通路，267 的结论更稳。

## 一个可能被忽略的点

`pl10` 实测要 `coop_take_mp_fav_tropical`（剧情图），而文件里 `playlist 10 = Survival Normal`（生存图）。如果**客户端的 `_pl` 编号与 .arena 的 playlist 编号不是同一命名空间**，那 `PVE_PLAYLIST_IDS` 里的 id 也可能对不上客户端实际发的 id —— 这是 268 卷 T2 的一个**潜在结构性风险**，值得在抓到真机请求时一并核。
