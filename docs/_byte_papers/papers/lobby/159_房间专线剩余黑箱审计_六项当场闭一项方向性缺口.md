## 二、✅ 闭 1：`0x639D00` 的调用者 = 大厅初始化序列 `0x7E98F0`

```
callers of 0x639D00 : 1 处 = 0x7E9933
0x7E9933 属于函数 0x7E98F0
```

`0x7E98F0` 是大厅**一次性初始化序列**，逐行：

```asm
0x7E98F9  call 0x7E84A0            ; 前置：UI/AS 初始化
0x7E98FE  cmp byte [0xE85C28], 0   ; 一次性守卫
0x7E9909  call 0xB76D80            ; 初始化
0x7E9913  call 0x6212C0            ; 初始化
0x7E991B  call 0x7FA4C0            ; ★ 网络通道槽表初始化（见闭 2）
0x7E9920  call 0x7EF830            ; Demonware 服务初始化
0x7E9925  mov byte [0xE374650], 0
0x7E992C  mov byte [0xE376C20], 0
0x7E9933  call 0x639D00            ; ★★ 房间子系统（dwRoomImp/dwRoomImp2/dwInvitationImp）
0x7E9938  call 0x4A1F60
0x7E993D  call 0x642620            ; 遥测
0x7E9942  call 0x4AB840
0x7E9947  push 0x18 / call 0xB74220 ; 新建一个 0x18 对象 → [0x82C4A78]
0x7E9978  call 0x801020
0x7E997D  call 0x4A9A60
0x7E9982  call 0x4A3300
0x7E9987  call 0x7F9F60
```

**结论**：`0x639D00` 是**大厅初始化链的第 8 步**（在 `0x7EF830` Demonware 服务初始化之后、遥测之前）。房间子系统**晚于网络层、早于 UI 首帧**建立 —— 这与 152 卷「dwRoomImp 总是存在」完全一致。

## 三、✅ 闭 2：64 槽的 `+0x28` **不是回调，是引用计数智能指针**

153 卷写：

> 「`0x7FA800` 的 64 个通道槽 `0xE56FFE0..+0x50*64` 各自的 `+0x28` 回调（`0x7FA6CD` 处拷贝）尚未解出。」

**「回调」这个词是我猜的。** 实测 `0x7FA6CD` 起的代码：

```asm
0x7FA6CA  lea edi, [esi+0x28]        ; 目标 = 槽+0x28
0x7FA6CD  lea eax, [ebp+0xC]         ; 源 = 参数
0x7FA6D0  cmp eax, edi / je 0x7FA709 ; 自赋值保护
0x7FA6D4  mov eax, [edi]             ; 旧值
0x7FA6D6  test eax, eax / je 0x7FA6F6
0x7FA6DA  add eax, 4
0x7FA6DD  push eax
0x7FA6DE  call dword ptr [0xCA8114]  ; ★ Release（COM 风格）
0x7FA6E4  test eax, eax / jne 0x7FA6F6
0x7FA6E8  mov ecx, [edi]
0x7FA6EE  mov edx, [ecx]
0x7FA6F0  mov eax, [edx]             ; vt[0] = Release
0x7FA6F2  push 1
0x7FA6F4  call eax
0x7FA6F6  mov ecx, [ebp+0xC]
0x7FA6F9  mov [edi], ecx             ; 存新值
0x7FA6FF  add ecx, 4
0x7FA702  call dword ptr [0xCA8128]  ; ★ AddRef
```

**`AddRef`/`Release`（`0xCA8114`/`0xCA8128`）⇒ 这是标准 COM/引用计数智能指针赋值**，与 `0x656A10`（链表插入）、`0x6567C0` 里的同款代码一致。

⇒ **`+0x28` = 「本次发送关联的引用计对象」**（很可能是 bdByteBuffer 或会话对象），**不是函数指针**。

**闭 3 同理**：`0x7FA640` 的 `+0x30..+0x48` 全是**普通字段拷贝**，不是回调：

```asm
0x7FA715  mov [esi+0x30], edx        ; = [ebp+0x10]
0x7FA71B  mov [esi+0x34], eax        ; = [ebp+0x14]
0x7FA721  mov [esi+0x38], edx        ; = [ebp+0x18]
0x7FA727  mov [esi+0x3c], eax        ; = [ebp+0x1C]
0x7FA72D  mov [esi+0x40], edx        ; = [ebp+0x20]
0x7FA73A  mov [esi+0x44], eax        ; = [ebp+0x24]
0x7FA73D  mov [esi+0x48], ebx        ; = [ebp+0x2C]
0x7FA740  fild dword [edx]           ; ★ 对 [ebp+0x28] 取值做浮点换算
```

⇒ **槽记录 = {8 个发送上下文参数 + 1 个浮点时间换算}**。`0x7FA740` 处：

```asm
fild dword [edx]           ; 整数
cmp eax,0 / jns / fadd [0xDE7BC0]   ; 负数补偿
fdiv qword [0xDE7B98]      ; 除以常数
fstp [ebp+0x30]
fcom qword [0xDE8068]      ; 与上限比较
```

**⇒ 这是「整数 tick → 秒」的换算 + 钳位**，与 121/110 卷的 tick/时间换算同款。

## 四、✅ 闭 4：`0xE69D30` 是**时间戳环表的索引表**，不是「函数注册表」

155/157 卷我判它是「函数指针哈希表」（因为键指向 `0x7FC0F0`/`0x7FBF00` 等代码）。**那只对了一半**。

### 4.1 键值的真身

```
[0xDE1404] = 0x007FC0F0   → 一个函数
[0xDE1408] = 0x007FC2D0   → 一个函数
[0xDE140C] = 0x00E0836C   → ★ 数据区
[0xDE1410] = 0x007FBF00   → 一个函数
[0xDE1414] = 0x00B87DA0   → 一个函数
[0xDE1418] = 0x00E08358   → ★ 数据区
[0xDE141C] = 0x007FB4A0   → 一个函数
```

`0xE0836C` 与 `0xE08358` 的内容：

```
0xE08358: 00 00 00 00 | 50 02 00 00 | 00 00 00 00 | 8c 73 e7 00 | 94 83 e0 00
                                    ↑            ↑ 指向自身区的指针
0xE0836C: 00 00 00 00 | 08 00 00 00 | 00 00 00 00 | 8c 73 e7 00 | 94 83 e0 00
```

`0x50 02 00 00 = 592`、`0x08 00 00 00 = 8` —— **都是小整数 + 自指指针**，不是代码。

### 4.2 定案

`0xE69D30` 这张表的**键**是「**成对**的 (代码指针, 数据块)」：

- 4 组：`(0x7FC0F0, …)` / `(0x7FBF00, 0xE0836C)` / `(0xB87DA0, 0xE08358)` / `(0x7FB4A0, …)`
- 值区在 `0xE69D50`（桶，容量 `0x100`），计数 `0xE69F84`
- 建表者 `0xC95B50`

**⇒ 这是「4 个可调参数集」的注册表**：每个参数集 = 一个访问器函数 + 一块数据。**不是「通道参数表」，也不是「纯函数表」，而是「(getter, data) 对」。**

> 这是我第三次判它（154「类5 参数行」→ 157「函数指针表」→ 159「(getter,data) 对」）。
> **教训：只有把「键指向什么」逐条读出来，才知道表是什么。前两次都是看形状猜的。**

## 五、✅ 闭 5：通道 `0x02/0x03` —— 确认「预留」而非「业务通道」

156 卷已测：106 个漏斗调用点里 `push 0x02`/`push 0x03` **各 0 处**，但 2 处是寄存器传参。

本卷补一层验证：**一级表 `0xE4E20C` 的 `0x02/0x03` 项在磁盘上确实是类 1（高可靠，25000ms/重试 10）**，且它们是**唯一两个**用类 1 的槽（除 `0x02/0x03` 外没有别的通道用类 1）。

⇒ **表里专门留了两个「高可靠」槽位，但代码从不用立即数引用它们。**
**判定：预留。** 若将来需要「必须送达的房间关键消息」，这就是现成的两个槽。

## 六、✅ 闭 6：srpc 另 7 张表 —— 原来是「构造期清空」，本就没有注册者

141/142 卷：14 张表，7 张确认由 handler 侧注册，另 7 张（`+0x08/+0x20/+0xD4/+0xF4/+0x15C/+0x1A4/+0x1D4`）的注册者「未追」。

### 6.1 先找到真正的构造函数

`srpc vtable 0xD599DC` 的 slot[0]（`0xB82850`）只是**析构/标量删除**（`call 0xB824F0` + `call 0xB74240` 释放）。真构造函数是 **`0xB824F0`**（它 `mov dword [esi],0xD599DC` 装 vtable）。

### 6.2 构造序列全表（17 个 `lea ecx,[esi+OFF] → call`）

```
0xB82564  [esi+0x460] -> 0xB76E50     ; 特例: mov dword [ecx],0xDEADBEEF
0xB82573  [esi+0x220] -> 0xBAEA50     ; 特例: 装 vtable 0xD5AA14
0xB82582  [esi+0x204] -> 0xB80CA0
0xB825A0  [esi+0x1EC] -> 0xB80CA0
0xB825BE  [esi+0x1D4] -> 0xB80CA0     ; ★ 141 说的「未追」之一
0xB825DC  [esi+0x1BC] -> 0xB80CA0
0xB825FA  [esi+0x1A4] -> 0xB80CA0     ; ★ 未追
0xB82618  [esi+0x18C] -> 0xB80CA0
0xB82636  [esi+0x174] -> 0xB80CA0
0xB82654  [esi+0x15C] -> 0xB80CA0     ; ★ 未追
0xB82672  [esi+0x144] -> 0xB80CA0
0xB82690  [esi+0x12C] -> 0xB80CA0
0xB826AE  [esi+0x114] -> 0xB80CA0
0xB826CC  [esi+0x0F4] -> 0xB80CA0     ; ★ 未追
0xB826EA  [esi+0x0D4] -> 0xB80CA0     ; ★ 未追
0xB82708  [esi+0x020] -> 0xB7F900     ; ★ 未追
0xB82720  [esi+0x008] -> 0xB80CA0     ; ★ 未追
```

### 6.3 关键：`0xB80CA0` 是**清空函数**，不是填充

```asm
0xB80CA0  mov [ebp-4], ecx
0xB80CAA  cmp dword [ecx+4], ebx(=0) / jbe 0xB80CFA   ; 容量为 0 就跳到「清 count」
0xB80CB1  mov eax, [ecx+0x10]        ; 桶数组
0xB80CB4  mov esi, [eax+ebx*4]       ; 遍历每个桶
0xB80CC0  ... mov esi,[esi+8] / call 0xB75AC0 / call 0xB74240   ; ★ 释放节点 + 释放字符串
0xB80CED  mov dword [ecx], 0         ; ★★ count = 0
0xB80CFA  mov [ecx], ebx             ; 空表路径: count = 0
```

`0xB7F900` 同构（少一次字符串释放）。

**⇒ 这两个函数做的事是「遍历桶 → 释放所有节点 → count=0」= 哈希表的 `clear()` / 析构。**

### 6.4 定案

> **这 14 张表在 srpc 构造时全部被「清空/初始化」，没有一张在构造期被「注册」内容。**
>
> 141/142 卷说「另 7 张表由谁注册未追」—— **答案是：没有注册者，因为在构造期它们就是空的。** 内容只会在**运行期**由 handler 注册（141 已证 68 个注册点全部 key=空串 ⇒ 每表最多 1 条）。

**⇒ 该项闭：不是「找不到」，是「构造期本就没有」。**

（附带修一个 153 卷的判断：`0xB76E50` 是 `mov [ecx],0xDEADBEEF` —— **单指令**，这是「**未初始化哨兵**」，与 45/5bit 卷的 `DEADBEEF` 销毁哨兵同一族。）

### 6.5 ❌ 仍开唯一一项：4 字节服务名（方向性缺口）

140 卷：注册时 key 全是空串 `0xDAE091`，但**消息里出现的 4 字节服务名**仍未知。

**为什么闭不了**：需要**动态读 srpc 哈希表**（看运行时填进去的 key），或**从真实服务端报文**取。

**这是协议方向性问题**：我们只有客户端发出的报文（6848 条 100% C→S），服务端回包的 4 字节服务名没样本。

⇒ **必须抓包**（需授权启动客户端）。

## 八、方法论

1. **★★ 「100% 闭合」这种断言必须按子系统分别给依据。** 我 158 卷把房间并进「客户端侧全闭」，是拿大厅的结论覆盖房间。
2. **★ 「回调」这个词不能瞎用。** 看到 `+0x28` 被拷贝就写「回调」，实际是 `AddRef/Release` 智能指针。
3. **★ 同一张表判三次才对**（`0xE69D30`：类5 → 函数表 → (getter,data) 对）。
   **判据：必须逐条读出「键指向什么」，不能看形状猜。**
4. **★ 「找不到注册点」有三种含义**：①真的没有；②表是空的；③它在**构造期被清空**。
   本卷第 6 项就是第 ③ 种 —— 必须先读构造函数的被调用者**干什么**（清空 vs 填充）。
5. **★ 协议方向性缺口要单独列。** C→S 齐 ≠ 协议齐。
6. **★ 构造序列要给「全表」**：17 个 `lea→call` 一次列完，7 个「未追」当场变成「已知偏移 + 已知被调者」。
