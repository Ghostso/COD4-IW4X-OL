# 342 · 探讨：一个"启动了"的证明，是怎么被一张清单作废的

> 配套：`342_证伪F03_改的代码真的被执行了吗.md`

---

## 一、这道题的陷阱在哪

任务是"证伪：我们改的代码真的被执行了吗"。

最容易走的错路是：**看见 `lobby_srv.log` 里有新版字符串，就下结论**。那条日志确实只有新版写得出来，看起来已经够了。

但"日志里有"只证明**某个进程运行了这段代码**，不证明**它跑的是我们以为的那份文件**。两者之间隔着：
- 文件在复制后被改吗？
- import 解析到别处了吗？
- `.pyc` 用的是旧的？
- 启动器有没有在复制前/后动过它？

所以我把它拆成四道独立的锁，每道都要机器级证据：

| 锁 | 问的是 | 本卷答案 |
|---|---|---|
| 复制后没被改 | 启动器写点审计 | 0 个写点 |
| import 没跑偏 | `find_spec().origin` | 指向 work kit |
| 字节码不陈旧 | `.pyc` 头 `(mtime,size)` | 3/3 VALID |
| 确实是新版行为 | 同一位点前后对照 | 15:08 vs 15:15 |

四道锁全开，才能说"被执行了"。**任何一道只靠推理，结论都是脆的。**

---

## 二、最值钱的不是"是"，是那两处"不是"

题目问的是一个文件；通读启动器后，真正的发现是**它还改了另外两个文件**：

- `run_all.py` —— 整体替换 `start_battle_server` 函数体；
- `nt10.py` —— `range(1, 6)` → `range(1, 2)`。

如果我们只验"lobby_server 是不是我们的"，这两个替换永远查不出来，**而它们恰恰改变了战斗服是怎么起来的**（`codol_battle_server.exe` 而不是旧 Python 骨架）。

### 教训

**"这个文件有没有被改"应该先被问成"这套 kit 里有没有文件被改"。**
先做全量，再回答单点。反过来做，默认答案就是"Yes it's fine"，因为没人去看别处。

顺带一提，这两处改写都**只落在副本**上，源 kit 只读、哈希不变 —— 设计上是干净的。
"被改写"本身不是问题，**"被改写且没人知道"才是**。

## 三、证书：一个每次都会变、却被拿来当指纹的东西

我一直以为证书是固定的。实际是 `run_all.py` 默认每次都 `make_certs()` 重签。

后果很具体：`postflight.json` 与 `source_manifest.json` 一对照，`_rsa.txt`、`_ca.pem`、`_leaf2.*` 五项的 sha **全部不同**。

如果任务只问"两份清单为什么对不上"，第一次看的人会顺着这个不符，去怀疑"kit 被换了/跑的不是 source"——
**方向完全错**，代码一个字节都没差。

### 教训

**校验哈希之前，先问"这个文件在正常流程里会不会变"。**
会变的东西（证书、日志、运行时 flag、令牌）不能当版本指纹；把它们放进同一张差异表，等于自己制造假阴性。

## 四、更隐蔽的一层：基准清单是事后重建的

`_golden_hashes.json` 和 `_run_once_hashes.json` 的 mtime 都是 **15:14:40**，而 golden 的 `lobby_server.py` 是 **15:14:15**。

也就是说：**清单是从"当时磁盘上的文件"生成的，然后启动器拿同一批文件去比对。**
三绿（protected OK / kit==mirror / manifest 匹配）当然会绿 —— 它绿在**同一性**上，而不是**审计**上。

271 卷花了很大篇幅讲"校验对象 == 执行对象"。这卷补上下一句：

> **"校验对象 == 执行对象"之后，还要问"这个执行对象是什么时候、由谁、被什么流程写进来的"。**

启动器自己改的是 `run_all.py`/`nt10.py`，但它改的是**副本**，源不变。
源在 15:14:15 被换了一版 —— 那是**构建动作**（`_BUILD_LOG.txt` 的 overlay 步骤），不是启动器的动作。
构建 → 重签清单 → 启动，这条序列本身没错；错的是**它让"清单通过"看起来像"代码被审计过"**。

## 五、跨 run 对照是白捡的证据

我本来打算只凭单次 run 下结论，直到发现 golden 的 `lobby_server.py` 在 143840→151503 之间从 `AD6A3ADA` 变成了 `5652EC58`。

这个变化正好是**同一个功能点的前后两版**：

```
旧 run 15:08  line 38: -> 6/5 空应答(payload=13)
新 run 15:15  line 38: -> 6/5 拉取(...) -> Manifold 位流 count=0 (6 字节)
```

**位点相同，行为不同** —— 这比任何静态分析都硬。而且它还回答了一个没人问的问题：
**这个修复到底是不是在 151503 才第一次跑起来的？** 是的。

### 教训

**先看同一目录下还有没有别的 run。** 一个 run 是快照，一串 run 是实验记录；后者能给出前者给不了的"变化量"。

## 六、这道题没回答的部分，也必须写下来

本卷只证明了"代码被执行"。它**不**证明：
- 新版 6/5 Manifold 的行为是对的（那是房间仍不可用的真正问题所在）；
- `nt10.py`（golden 版）与 R20/R21 后的 cryptolib 兼容；
- 客户端 PID 在整个窗口里始终是 1912（只有末态）。

**证伪一条假设，不等于证实它的反面。** 房间为什么还不可用，仍然开着，而且本卷没有靠近它一步。

这符合 AGENTS.md 的那条推论：把问题拆成能独立核验的任务，每条给出分母和证据，
**不因为"排除掉一条解释"就宣称问题在别处解决了**。
