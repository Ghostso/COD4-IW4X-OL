# 房间成员记录：725 位 + 1 字符串的逐字段结构

> 承接 `lobby/90`、`lobby/91`
> 产物：`_byte_papers/member_record_fieldmap.txt`，`tools/field_map.py 0x623880`

---

## 1. 这是什么

**`dwRoomMessageMemberList` 的循环体 = `0x623880` = 一个"房间成员"记录。**

**这是整个大厅里最常出现、也最直接影响"玩家名单显示"的结构。**

**⇒ 一条 `MemberList` = 50 位头 + N × (725 位 + 名字串)。**

## 3. 字段分簇（结构上的自然分组）

**从偏移看，有 4 个明显分簇：**

```
簇 A  [0x00 .. 0x0C]   账号 ID + 槽位（第 1–3 字段）
簇 B  [0x8C .. 0xBA]   基本信息（第 4–18 字段，连续）
簇 C  [0x1A0 .. 0x1C8] 扩展信息（第 19–26、33–36 字段）
簇 D  [0x1B1 .. 0x1B7] 6 个连续布尔（第 27–32 字段）
```

**★ 簇 D 是最直接的证据：`0x1B1,0x1B2,0x1B3,0x1B4,0x1B5,0x1B7`
六个相邻字节各写 1 位——这是典型的"位域（bitfield）"或
"6 个独立 bool 成员"的序列化。**

**⇒ 注意 `0x1B6` 缺席，`0x1B7` 在。说明 0x1B6 不是 bool（可能是补齐字节）。**

## 4. 725 位是怎么构成的（逐条加）

```
5 位 tag × 36 个 = 180
定长 payload:
  64+8+1                                  = 73
  16+16+8+8+64+32+1                       = 145
  8+8+16+16+16+16+16+8                    = 104
  16+8+32+32+8+32+32+8                    = 168
  1+1+1+1+1+1                             = 6
  32+8+8+1                                = 49
  --------------------------------------------
  73+145+104+168+6+49                     = 545
180 + 545 = 725 ✓
```

**⇒ 36 个字段（含 1 个变长串的 tag），725 位，精确闭合。**

## 5. ★ 更正：记录**没有**名字串，就是 725 位

**我最初以为循环末尾 `0x623dc7` 那条 `writeData` 是名字串。**

**反汇编对齐后（`0x623d8f` 起）：**

```
0x623d8f  mov  bl, byte ptr [edi + 0x1be]   ← 一个 bool
0x623d95  push 1 / call 0xB77B10             ← tag 0x01
0x623d9e  push 1
0x623da0  test bl,bl
0x623da2  je   0x623dbb
0x623dab  mov  byte [esp+0x10], 0xff
0x623db0  call 0xB777C0                      ← 真分支：写 1 位 = 1
0x623dbb  mov  byte [esp+0x10], 0x00
0x623dc7  call 0xB777C0                      ← 假分支：写 1 位 = 0
```

**⇒ 这是 **一个 bool 的两条分支**，不是我上一版以为的"变长字符串"。**

**⇒ 工具把两条分支各记一次（一条记 1 位、一条记 None），
实际线上只走其中一条 ⇒ 计 1 位。**

**⇒ 所以成员记录 = **精确 725 位，无字符串**。**

**⇒ 昵称不在 `MemberList` 里。名单位置见 §5.1。**

### 5.1 昵称在哪里

**带 `0x10` 字符串的消息只有 4 个：**

```
ClanNameChange    0x03, 0x10        ← 战队名
MemberInfoEXT     0x03,0x15:64,0x10,0x15:32,0x03,0x03,0x01
MemberInfoAdd     0x03,0x0a:64,...(725 位记录)...,0x10
JoinRequest       0x03,0x10,0x15:32,...
Text              0x03,0x10,0x15:64,0x02
```

**⇒ 昵称在 `MemberInfoAdd` 的**末尾**（725 位记录之后跟一个 `0x10` 串）。**

**⇒ `MemberInfoAdd` = `0x03:8 + 0x0a:64 + 725 位记录 + 0x10 名字串`
= 738 位（不含名字）+ 名字。**

**⇒ `MemberList` 只发"名单骨架"，名字靠 `MemberInfoAdd` 单独补。**

**这是 `dwRoom` 协议的一个真实设计取舍：高频广播不带长字符串。**

## 6. 与 TLV 语料交叉：账号 ID 字段

**TLV 语料里 `0x0a`(u64) 有 20525 例，其中最著名的是
`16701785630074219790`（= `0xE7C3...`），已锚定为 CODOID。**

**位流 `MemberList` 成员记录的第一个字段就是 `0x0a`(u64)，源 `[edi+0]`。**

**⇒ 高度可确定：这是成员账号 ID。**

**⇒ 这给了我们一个"自洽性检查"：
如果实抓一条 `MemberList`，第一个成员的 u64 应该等于该玩家的 CODOID。**

## 7. 构造一条合法 MemberList（可执行方案）

**已落成代码：`tools/dwroom_codec.py`。**

**以 2 个成员为例：**

```
5 位   0x03    ← 消息类型号（具体值见 lobby/90）
8 位   <类型值>
5 位   0x15
32 位  2       ← 成员数 N
—— 成员记录 × 2，每条精确 725 位 ——
5 位  0x0a / 64 位 账号 ID
5 位  0x03 /  8 位 槽位
5 位  0x01 /  1 位 标志
5 位  0x15 / 16 位
...（按 §2 全表顺序，36 个 tag）
5 位  0x01 /  1 位 末位 bool
```

**总长 = 50 + 725 × N 位。**

**N=1 ⇒ 775 位 = 96.875 → 97 字节。**
**N=8 ⇒ 5850 位 = 731.25 → 732 字节。**

**⇒ 这是精确的、可直接生成的字节数。**

**若还要显示昵称，再单独发 `MemberInfoAdd`（见 §5.1）。**
