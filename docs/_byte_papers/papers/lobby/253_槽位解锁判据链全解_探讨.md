## 一、先说翻车

这一卷我犯了本轮最不该犯的错：**先写论文，后跑脚本。**

稿子写到 §2.1 时，我凭记忆填了两行数：

```
| 徽章表 0x8269B18 | 0x38015688 0x38032219 0x379102CE … | 0x3791..0x3803 |
| 已拥有表 0x8269FC8 | 0x3822EEFD 0x382330A4 0x3823724B … | 0x3822..0x382C |
```

两行数字**本身都不是编的**，但它们是我用**步进 8** 读 `0x8269FC8` 得到的 ——
而这张表的写入指令明明白白是：

```asm
0x80B5CA  lea esi, [esi + esi*2]      ; esi = count
0x80B5CD  lea esi, [esi*4 + 0x8269FC8] ; => count*12 + base
```

**`3 * 4 = 12`。** 我把 `0x3822EEFD`（它是某条记录的 `[+0]`）当成了"前一条的 `[+8]`"，
于是"已拥有表的 A 值区间"整体错位。

**这不是算错，是"没读那两行 `lea`"。** 而这两行 `lea` 就在我**上一轮**已经反汇编过的窗口里。

### 教训

**只要断言里出现"某张表的字段取值落在某区间"，就必须先跑一次逐条 dump，不能凭上一轮的印象拼。**

数字看着"很专业"恰恰最危险 —— `0x3822EEFD` 长得就像个合法的表项，
所以它不会触发任何"这不对劲"的直觉。

## 二、这一卷真正的方法论收获：边界要用"代码引用"而不是"数据形状"

250 卷遇到过一模一样的问题，并且**自己写下了正确的教训**：

> 「表长度必须用「字段值域」界定，不能按固定步进一直读。徽章表读 27 项后 `[+4]` 变成 100（ASCII 字符）……
> 一改就是干净的 27 项。」

它用"`[+4]` 只能是 0/1"当表尾判据，得到 **27 项**。

**27 也是错的。真长是 7。**

为什么"值域判据"会失效？因为 **`0x8269B18` 后面紧跟的 `0x8269B6C` 是一张同构表**——
同样的步进 12、同样的 `{A, 标志, B}`、同样的 `[+4] ∈ {0,1}`、同样的解码式。
值域判据读不出"我跨过界了"，因为**界那一边长得一模一样**。

真正硬的边界在这条指令里：

```asm
0x80A6C7  lea esi, [edi + 0x8269b6c]   ; 下一张表的基址被代码独立引用
```

**"哪张表在哪结束"这个问题，代码里通常有答案（谁引用下一张表的基址）；
数据里往往没有。** 值域判据只是数据形状的启发式，同构表相邻时必然失效。

这与 250 卷自己写下的「分桶宽度须小于结构尺度」是同一条法则的不同切面：
**当"结构"被复制粘贴成邻居时，任何基于形状的分界都失效。**

## 三、这一卷最漂亮的一步：用「地址区间零重叠」代替「元素重合」

252 卷的推理是：

> 已拥有表与徽章表的 item **高度重合**（`10001/10010/10015/60043/60040/60137/60049/60038/60214` 都在两边）
> ⇒ 已拥有表是从徽章表一类"源表"搬运来的。

这个推理**不成立**，而且 252 卷自己也犹豫过（写了"一类'源表'"这个模糊措辞）。

本卷换成机械判据：

```powershell
# 扫全库所有 lea reg,[reg*4+disp32] 且 disp32 落在表区
```

结果只有 **4 张表**，引用点分布：

```
0x8269B18 (徽章)   4 点：0x50CB8D 0x7D74EF 0x7D7577 0x80BD2B
0x8269FC8 (已拥有) 18 点：0x80B5CD … 0x80BB8C
```

**两组地址区间零重叠。**

**⇒ 两张表在机械上不可能有搬运关系**，与 item 重合与否无关。

**要素材重合与否，是概率证据；地址区间重叠与否，是结构证据。**
前者会被"同一批物品被多处引用"解释掉，后者不能。

## 四、一个更隐蔽的读法错误：`edi` 从哪来

252 卷读到：

```asm
0x5E37F8  mov word ptr [edi + 4], bx     ; bx = 0
```

判定为「**命中 → 把黑名单条目标志写成 0**」。

本卷把这个函数（`0x5E3760`）**从头读到 `ret`**：

```asm
0x5E3760  push ebp
0x5E3761  mov  ebp, esp
0x5E3763  mov  ecx, [0xC9113D4]     ; 计数
...
0x5E37D0  mov  dword [edi], esi     ; ← edi 第一次出现，是"被写"
```

**`edi` 在整个函数里从未出现在目的操作数左侧之前的赋值中 ⇒ 它是调用者传进来的出参指针。**

于是 `0x5E37F8` 的真身是：**在填一条 0x30 字节的结果记录**（"该物品不可用"），
而不是往某个全局黑名单数组里插项。同一个 `[edi+4]`，语义从"数据库写入"变成"函数返回"。

**教训：要把 `mov [reg+X], imm` 解读成"写全局状态"之前，先看完整个函数确认 `reg` 从哪来。**
寄存器参数是 x86 里最容易被"位置"骗过去的东西 —— 它长得跟"某个全局数组的指针"一模一样。

（顺带：`0x5E3550` / `0x5E3580` 恰好印证了这一点——这两张表的扫描函数用 `ecx-8` / `ecx-4` / `ecx`
的相对寻址，是为了让 `ecx` 从"末字段指针"起步；如果只看 `[edi+4]` 而不管基址相对谁，必错。）

## 五、这一卷的答案为什么"更好用"

原来的问法是：**「60220/60221 被哪个条件滤掉了？」**
——这个问法预设了"它们会经过那条装配路径，只是被拦住了"。

真相是：**徽章表与已拥有表是两条永不交汇的链。**

```
链 A（该槽需要哪个 item）：  索引 → 徽章表 0x8269B18 → 60220
链 B（玩家是否拥有）：       0x5E3550 → 0x80A5E0 → 0x8269FC8 → false
```

**链 A 只回答"该要什么"，链 B 只回答"有没有"。它们之间没有"过滤"这一步。**

这个改写带来直接后果：
- 旧问法的修法是"找到那个过滤条件并改掉它" —— **不存在这个条件，所以修不了**。
- 新问法的修法是"**让链 B 为真**"，即服务端直接授予 item 60220/60221 —— **可落地**。

（这正是 250 卷 §4 给出的修法。250 的表长读错了，但修法方向反而对 ——
因为修法只依赖"60220/60221 没被拥有"这一个事实，与表长无关。
**一个结论可以为真，而支持它的证据是错的。**）
