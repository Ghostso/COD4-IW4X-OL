## 一、一个"读表"的常见陷阱

徽章表在 `0x8269B18`，步进 12 字节。第一步我按固定步进读了 40 项，结果：

```
[14] A=0x37A16C8E E=1  B=0xAA1CB267 -> item=60137     ← 正常
[27] A=0x000000C0 E=100 B=0x00000101 -> item=3185558132  ← 荒谬
[28] A=0x514C2D8C E=67  B=0x00000101 -> item=4059205157  ← 荒谬
```

**item id 解出了 31 亿。**

如果我就此把它当"表末有异常项"记下来，就会带着一堆垃圾数据往下走。

**实际原因**：第 27 项的 `[+4]` = **100**，那是 **ASCII 字符 `'d'`** —— 表**已经结束**，后面是**字符串数据**。

★ **判据**：表项的 `[+4]` 是**存在标志**，值域只有 `{0, 1}`。**一旦出现 0/1 以外的值，就是表结束。**

改完后：**27 项、22 项有效**，全部解出干净的 item id（10001 / 60043 / 60220…）。

## 二、"整齐的缺口"是证据

核对 60027/60028 时发现：

```
catalog 里 Item ∈ [60000, 60300] 的：60001..60026, 60038, 60040..60050, 60064, 60066, 60070...
                                     ↑            ↑
                                  60027/60028 在这里被跳过
```

**不是随机缺失，而是正好跳过 60027、60028 两个连号。**

再叠加上"库存里没有 / mkt_assets 里没有"，三条独立证据指向同一个结论：

**这四个 item（60027/60028/60220/60221）不是"商品"，是"槽位解锁物品"。**

★ 如果只是"catalog 里碰巧没有"，那说明数据不全；**但"正好跳过两个连号"说明编译期就知道它们是另一类**。

## 四、一个还在的隐患，我标出来了

解码式里两次出现 `[0xE4DD90]`：

```asm
0x7D7587  xor edi, dword ptr [0xE4DD90]
0x7D74FE  xor eax, dword ptr [0xE4DD90]
```

**如果这个全局会在运行时被改写，那静态解出的 item id 就只在特定时刻成立。**

我没有去找它的写点，所以**在论文 §6 把它列为"未验证"**，没有当成结论。

★ 这和 249 卷的 `xor cx, ax`（指针低 16 位）是同类隐患 —— **凡是"解码依赖运行时状态"的地方，静态结论都要打折**。
