## §2 共用写侧 `0x628320` 的真实位流

被 **7 个类**共用（StartGameFailed / MemberDetailsQuery / StartCountingDown / **ChangeTeamRequest** / **Vote** / QQMembership / NetcafePrivileges）。

```asm
0x628320  mov al,[esi+4]        ; ★ 类型号
0x62832D  push 3 / call 0xB77B10                            ; [1] WriteBits(3, ____)
0x62833C  push 8 / lea [ebp+8] / push / call 0xB777C0       ; [2] WriteBits(8, type)
0x62834B  push 0x15 / call 0xB77B10                         ; [3] WriteBits(21, ____)
0x628354  push 0x20 / lea [esi+8] / push / call 0xB777C0    ; [4] WriteBits(32, [+8])
```

**注意第 4 个参数**：`0xB777C0` 内部 `mov eax,[ebp+0xC]`，即栈上第一个参数 = 从 `lea [esi+8]` push 进去的**指针**。所以 `0xB777C0(bits, ptr)` 是**写指针指向的数据**，不是写 `bits` 的数值。

⇒ `WriteBits(32, [+8])` = **把对象 `+8` 处的 32 位字段写出去**。

### 2.1 `0x6281D0`（ChangeTeam 专用写侧）

```asm
[1] WriteBits(3,  ____)
[2] WriteBits(8,  type)
[3] WriteBits(21, ____)
[4] WriteBits(32, [+8])
[5] WriteBits(21, ____)
[6] WriteBits(8,  [+0x10])
[7] WriteBits(21, ____)
[8] WriteBits(32, [+0x0C])
[9] WriteBits(21, ____)
[10] WriteBits(64, ...)      ; push 0x40
```

⇒ **ChangeTeam 的线格式 = 4 个字段：`u32 [+8]`、`u8 [+0x10]`、`u32 [+0x0C]`、`u64`。**
字段语义未定，但**布局是确定的**，服务端可以直接按此解析/回填。

## §3 ★★ `0xB77B10` 的真正语义（更正 169 卷的边界）

```asm
0xB77B10  cmp byte ptr [ecx+0x21], 0
0xB77B17  je  0xB77B28            ; ← 为 0 就什么都不写
0xB77B19  mov eax, [ebp+8]        ; n
0xB77B1C  push 0
0xB77B1E  push 0x1F
0xB77B20  push 0
0xB77B22  push eax
0xB77B23  call 0xB77A70           ; core(cur, 0, 0x1F, 0, n)
0xB77B28  ret 4
```

```asm
0xB77A73  cmp byte ptr [ebp+0x14], 0    ; 第 4 个参数
0xB77A77  je  0xB77AC3                  ; ==0 跳过跟踪块
   ...（跟踪块会递归调 0xB77B10，但 [esi+0x21]==0 时立刻返回，不会无限递归）
0xB77AC3  mov ecx, ebx ; sub ecx, edi   ; ebx=n, edi=0 ⇒ ecx = n
0xB77ACF  call 0xB75D40                 ; ★ 0xB75D40 = 位宽（bit length）计算
0xB77AEF  mov [ebp+0x14], ecx
0xB77AF5  call 0xB777C0                 ; ★ WriteBits(width=n, value=0)
```

★★ **所以 `0xB77B10(buf, n)` = `WriteBits(n, 0)`（把 `n` 个 0 位写出去），前提是 `[obj+0x21] != 0`。**

**169 卷的两处边界需要更正：**

| 169 卷说法 | 本卷更正 |
|---|---|
| 「`WriteBits(8)` 什么都不写」 | 仅在 `[obj+0x21]==0` 时成立；非 0 时**写 8 个 0 位** |
| 「`push 0x13` 是字段类型码」 | 169 已自行更正为 P2PInfo tag；本卷确认 `push 0x15` 是**位宽 21**，不是类型码 |

★ 剩余未定（诚实边界）：`[obj+0x21]` 的写点在本镜像里**找到 16 处 `mov byte [reg+0x21], imm/reg`，但没有一处能静态确认作用于同一个位流对象**。该标志是运行时状态 —— 属于"证明它是 0"做不到，也"证明它不是 0"做不到。**但它不改变 §4 的结论**，因为 §4 的闸门在更外层。

## §4 ★★★ 唯一出口 `0x7E8300` 的三道闸门

全镜像扫描：**`0x7E8300` 只有 1 个调用点 —— `0x62C93D`（在族 A `0x62C380` 内，`kind==4` 分支）。**

```asm
0x7E8305  call 0x803830            ; ★ 门 1
0x7E830C  test esi,esi / je  → 返回
0x7E8316  call 0xB7A670            ; 门 2
0x7E831B  cmp  eax, 2 / jne  → 返回
0x7E8326  call 0xB7A770            ; 门 3
0x7E832B  test eax,eax / je  → 返回
0x7E8353  call 0xB8EE70            ; 构造
0x7E8382  push 0x16                ; ★ 通道号 0x16
0x7E8388  call 0x7FAA20            ; ★ 投递漏斗
```

### 门 1：`0x803830` = **srpc 单例 `[0x8269774]` 的惰性构造器**

```asm
0x803830  mov eax,[0x8269774]
0x803835  test eax,eax
0x803837  jne 0x8038A7            ; 已存在 → 返回它
0x803839  push 0x1618 / call 0xB74220      ; 分配 0x1618 = 5656 字节
0x80384C  call 0xB82130                     ; ctor
0x803851  mov [0x8269774], eax
```

★★★ **这就是记忆里"房间逆向断点：`[0x8269774]`=0"的那个量。** 它**不是常量闸门**，是 srpc 单例的惰性创建 —— `0x803830` 被调用时若还未创建就现建。所以门 1 本身**总能通过**（只要堆分配成功）。

### 门 2：`0xB7A670` = `srpc+0x4F4` 状态闸门

```asm
0xB7A670  mov ecx,[esi+0x4F4]
0xB7A679  test ecx,ecx / jne ok
0xB7A67D  xor eax,eax / ret          ; 0x4F4 为 0 → 返回 0
ok:       call 0xBA0780
0xB7A686  cmp byte [esi+0x4F8], 0
0xB7A68D  jne 0xB7A699               ; 0x4F8 != 0 → 保持 eax
0xB7A68F  cmp eax, 2
0xB7A692  jne 0xB7A699
0xB7A694  mov eax, 1
```

★★ **返回 1 当且仅当 `[srpc+0x4F4] != 0` 且（`[srpc+0x4F8] != 0` 或 `sub()==2`）。**
与记忆条目 "真闸门是 `srpc+0x4F4`，且开着" **完全吻合**。

### 门 3：`0xB7A770` = 同一判据的包装（内部先 `call 0xB7A670`，再 `cmp eax,2`）

⇒ **`dwRoomMessage` 的所有"真发"必须同时满足：srpc 已创建 + `srpc+0x4F4 != 0` + 状态判据。**

## §5 通道号 `0x16`

`0x7E8300` 里 `push 0x16 → call 0x7FAA20`，与 154 卷记录的「五通道 `0x13/0x14/0x15/0x16/0x17`」一致。

★ 154 卷把 `0x16` 标为"空桩"。**本卷更正：`0x16` 不是空桩** —— `0x7FAA20` 的第 3 参 `push 0x8435D0` 确实是空回调，但主路径 `call 0x7FA800` 才是投递，`0x16` 是**房间动作专用通道**。

## §6 结论：哪些还开、哪些已闭

| 项 | 状态 |
|---|---|
| 43 类的**写侧**地址 | ✅ **本卷闭**（§1 全表） |
| `ChangeTeam` 线格式（4 字段） | ✅ **本卷闭**（§2.1） |

| `0xB77B10` = `WriteBits(n, 0)` | ✅ **本卷闭**（§3，含 169 两处更正） |
| 唯一出口 + 三道闸门 | ✅ **本卷闭**（§4） |
| 通道号 `0x16` | ✅ **本卷闭**（§5） |
| `[obj+0x21]` 运行时取值 | ⬜ **仍开**（16 个候选写点，无一可静态归属） |
| `ChangeTeam` 4 个字段语义 | ⬜ **仍开**（布局已知、含义未知） |
| 谁触发 `vt[0]` 写出 | ⬜ **仍开**（`0x62C93D` 之上是哪个 UI 回调） |
| 服务端为何收不到 `11/14` | ⬜ **仍开** —— 但现在知道**不是协议没定义，而是被 `srpc+0x4F4` 闸门挡住** |

★★★ **最重要的结论：`dwRoomMessage` 的发送链完整存在（写侧全有、出口唯一、通道明确），但出口前有三道运行时闸门。** 客户端在房间里点"准备/改阵营/投票"没反应，最可能是 **`srpc+0x4F4` 状态未满足**，而不是"服务端少了分支"。

## §7 方法论

1. **★ vtable 的 `[+0]/[+4]` 是「写/读」一对。** 只看读侧会得出"只能收不能发"的错误结论。
2. **★ `WriteBits(n)` 的第二个参数是指针时，写的是指针指向的数据。** 看 `mov eax,[ebp+0xC]` 就知道。
3. **★★ 追发送链要追到 `socket`/服务层，不要停在"入队"。** 入队→出口→闸门，三段都要看。
4. **★★ 闸门函数要读它的返回值条件，不要只看函数名。** `0xB7A670` 一行 `cmp byte [esi+0x4F8],0` 就决定了整个状态机。
