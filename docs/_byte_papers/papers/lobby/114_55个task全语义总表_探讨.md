# 114 · 探讨：从"字节黑箱"到"语义黑箱"，以及为什么必须收尾

> 配套：[114_55个task全语义总表.md](114_55个task全语义总表.md)

---

## 一、这一卷的性质变了：不再解字节，而是"点名"

113 卷之前，每一卷都在问"这个字节是什么"。这一卷不一样——55 个 task 里 **41 个是固定 payload**
（全语料每条都逐字节相同），它们的问题不是"字节怎么解"，而是"**这条报文在游戏里干什么**"。

对固定 payload 的 task，字节早就解完了（v5 文法 6848/6848 全过）。缺的是**名字**。
而名字的来源只有两个：`reply_objects` 的源码注释（我们的冻结参考实现）和 `_lobby_data_audit.py` 的语义表。
这一卷就是把这 55 个名字**系统地填进去**。

## 二、"语义黑箱"比"字节黑箱"更难彻底关掉，因为缺应答样本

字节黑箱可以用语料自己关掉（数数、去重、验证结构）。但**语义黑箱缺一半数据**——
corpus 只有**请求**（108 卷：6848 条 100% 客户端→服务端），**没有一条应答**。

这意味着：`9/5` 我只知道"客户端发 `08 100`"，但我**永远不知道服务端回什么好友列表**。
`80/203` 我只知道"客户端请求库存"，但不知道库存的字节布局。这些的语义只能从**源码注释**里读，不能从数据里推。

★ 这是必须诚实承认的边界：**"请求语义"已 100% 定名，"应答语义"仍然只有源码级证据**（`reply_objects` 是最低可信度的"照抄 ol-mod/C#"）。要真正闭环应答，必须跑一次真实客户端抓包——那需要授权。

## 三、`932` 的升级：从"无名魔数"到"统计类别"

110 卷把 `932` 写成"未定"，我当时的理由是"68 种哈希全不匹配"。但这一卷换了个角度：
不问"932 是哪个值的哈希"，而问"932 出现在哪、和谁一起出现"。

结果发现：`932` 是 `4/13`(290 条) 和 `4/4`(89 条) 的**共同首字段**，而且 `4/13` 在某个 run 里
从 `100→108→113→118→123→135→148` 递增。**递增序列 = 经验/等级/计数**，`932` = 类别/赛季号。

**教训**：魔数的语义不一定能从"值本身"解出来（哈希、算术都失败时），但**可以从"共现和变化模式"解出来**。
`932` 恒定 + 另一个字段递增 ⇒ `932` 是"类别"、递增字段是"值"。这个推理不需要知道 932 具体是啥，就能定它的**角色**。

我把它标为"半定名"（类别号确定、具体含义待应答），而不是"定名"——因为我不知道 932 对应哪个赛季/哪类统计。**这种克制的边界必须保留**。

## 四、`102/*` 是唯一没关掉的，我为什么不硬关

`102/1`、`102/2`、`102/5`、`102/7` 是唯一 4 个语义未定的 task。
- `102/7` 的结构很清楚：`08 50 | [03 1 | 0a i]×50 | 00`，50 个序号 0..49。
- 但"50 个 (1, 序号) 对"在游戏里代表什么？资源下载？CDN 状态？成就进度？**没有源码注释，没有应答样本**。

我本可以猜一个名字（比如"资源池状态"），但那样就违反了前面反复强调的纪律：**假的定名比诚实的未定危害大**。
所以我只写结构（50 元素数组，已确定），不写语义名（未定）。

`102` 这个服务号本身可能就是"未使用的/内部调试的"——它不在 `_lobby_data_audit.py` 的任何映射里。
**它很可能是可以安全忽略的**（像 `71/*` 遥测一样），但我没有证据说它"无 UI 影响"，所以不下这个结论。

## 五、`21/3` 是第四个频道 ID 编码路径

`21/3` 的 payload 是 `13 08 08 000000 <频道ID>` —— 频道 ID `0x1122334455667788` 以 **blob** 形态携带。
这已经是 `roomChatChannelID` 的**第 4 条独立编码路径**（前三条：`0x0a` u64、`6/14` 明文、mmbook base64）。
同一个 ID 用四种方式编码，说明协议里"频道"这个概念到处出现——**改频道 ID 时必须同时改四处**，否则会不一致。这是一个实操上极容易踩的坑，值得单独记。

## 六、商城页的"打挂"教训值得反复强调

源码 747-763 有一句血泪注释：**只发 3 条自编 SKU 就把整个 marketplace 服务打挂**（仓库变红叹号、角色被锁、按钮点不动）。
原因：CODOL 的 SKU 记录**不是** MW19 的 `bdMarketplaceSku`（多两个字段），照抄兄弟作品的字段序就炸。

这一卷把 `80/70/107/119/173/174/232` 全列出来了，但**我不会去编 SKU 页**——
因为要编对，必须先拿到**真实 SKU 页的字节**（官方响应样本），或把客户端反序列化器逆到字段级。
这是"**不知道就别碰**"的典型：乱改会打挂整个商城，比不改还糟。

## 七、方法论沉淀

1. **固定 payload 的 task，字节早解完，缺的是名字**——从源码注释填名字，成本低、收益高。
2. **魔数语义可从"共现+变化模式"推**，不必从值本身解（`932` 恒定 + 邻居递增 ⇒ 类别）。
3. **没有应答样本 = 应答语义永远只能到"源码级"**，要闭环必须真实抓包（需授权）。
4. **同一 ID 多编码路径要显式记录**（频道 ID 四条），改一处必须改四处。
5. **不知道就别碰**（商城 SKU 页），乱改会打挂服务。
6. **未定就标未定**（`102/*`），不猜。

## 八、下一步

55 个 task 语义表完成后，协议层（主线 A）基本**收口**：6848 条报文、55 个 task、12 个标签全部有定名或明确标注。
剩下的黑箱只在两个地方：
1. **应答侧**（corpus 无应答）—— 需真实抓包，属授权范围。
2. **`102/*`**（4 个 task）—— 结构与 `71/*` 遥测类似，可能是可忽略的内部服务。

如果要继续"直到结束全部黑箱"，那么**请求侧已经没有黑箱了**——剩下的要么需要授权跑客户端，要么是低价值的遥测/内部服务。这是一个应该向用户明确汇报的**阶段性终点**。
