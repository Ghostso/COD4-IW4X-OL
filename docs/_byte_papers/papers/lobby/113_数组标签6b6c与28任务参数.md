## §1 `0x6b`：只有 21/5 用的"空结果容器"

`tools/arr_census.py` 结果：`0x6b` 全语料 **159 次，100% 在 `21/5`**，body 恒为 4 字节 `01000000`、tail(count) 恒 0。

- `21/5` = findSessions（找房间）。客户端发查询时带一个 `0x6b` 数组作为**结果容器**。
- 因为是**查询请求**（corpus 全是入站请求，108 卷），结果容器**必然为空**（cnt=0），body=`[1]` 表示"1 个 u32 元素（就是计数本身）"。
- ⇒ `0x6b` 与 `0x6c` 是**同一编码族的两个 tag**（一个请求侧、一个响应侧），只是 `0x6b` 在本语料里恰好全是空数组。

★ 注意 `0x6b` 的 body 同样遵守 `[N][...]` 规律：`body=01000000` = `[1]`，N=1=元素总数（只有计数自身，无数据项）。**与 `0x6c` 完全同构。**

## §2 `0x6c` 的精确结构（160 样本全验证）

### §2.1 外层

```
6c 08 <u32 byteLen> <byteLen 字节的 body> <u32 tail>
```
- `08` 是子标记（与 `0x13` blob 的 `13 08` 同构）。
- `byteLen` = body 的字节数，**恒为 4 的倍数**（203/203 验证，`arr_struct.py`）。
- `tail` 是 body 之后的独立 u32。

### §2.2 内层 body = `[N][item…]`

`tools/arr_6c_rule.py`：**body 第一个 u32 == body 的 u32 总数**，**160/160 全中，0 例外，43 个空 body 除外**。

| 样本 | body u32 | 验证 |
|---|---|---|
| `28/4` | `[127, 0,1,2,…,262]`（127 个 u32） | body[0]=127 == 127 ✅ |
| `28/1` `6c080800000002000000000000000500000000` | `[2, 0]`（2 个 u32） | body[0]=2 == 2 ✅ |
| `28/1` `6c0804000000010000008300000000` | `[1]`（1 个 u32） | body[0]=1 == 1 ✅ |
| `28/1` `6c08000000000000000000` | `[]`（0 个） | 空 ✅ |

⇒ **body 是一个自描述长度的数组：第一个 u32 是元素总数，后面是 (N−1) 个数据项。**

★ 这个编码在协议上是**冗余的**（外层已有 `byteLen`），但它给了客户端一个**快速跳过**的能力（读第一个 u32 就知道要读多少个元素），不必先算 `byteLen/4`。这是 Demonware TypeArray 的典型写法。

## §3 `28/1` = 任务参数（任务选择）

### §3.1 权威命名

`lobby_server.py:918-934`：
> ★★ 2026-10-07: `28/1` 特别标注 —— 它是"任务参数"，实测在 `mmstart` **之前**到达，
> 很可能带着"玩家选了哪一关"的线索。

`_lobby_data_audit.py:95`：`("28/1,28/4,29/10", "任务参数", "未映射", "任务/活动")`

### §3.2 全语料 109 条形态

`tools/arr_28_1_full.py`：9 种 payload，全部是 `0x6c` 数组：

| body `[N][items]` | tail | 次数 | 解读 |
|---|---|---|---|
| `[0]`（空） | 0 | 43 | 无选择（首次查询/清空） |
| `[2][0]` | 5 | 24 | 选中第 0 项，共 5 个可选 |
| `[2][0]` | 4 | 1 | 选中第 0 项，共 4 个可选 |
| `[1]` | 131 | 25 | 无选中项，共 131 个可选 |
| `[1]` | 203/214/190/9/1 | 各 1 | 无选中项，可选数变化 |

### §3.3 `tail` 语义判定

- `body=[2][0]` 时 tail=5 或 4：**选中索引 0 < 可选数 5/4** ✅
- `body=[1]`（无选中）时 tail=131/203/214：**只报总数，不报选中项**
- 唯一 12 次 `body=[1] tail=1`：可选数=1 且无选中（边界）

⇒ **`tail` = 该任务下的"可选项总数"**（关卡/难度/角色等下拉项的数量），**`body` 的 items = 用户当前选中的索引**。
当用户没选（`body=[1]` 只有计数）时，tail 仍报总数。

### §3.4 与 21/5 playlist 的交叉

`tools/arr_cross.py`：`28/1` 的 tail 与 `21/5` 的 playlist **无固定对应**（playlist=10 与 50 下 tail 都出现过 0/1/5/131/203/214）。
⇒ `28/1` 的 tail **不是 playlist ID**，而是**独立的"任务内选项数"**。这符合"任务参数"而非"模式参数"的定位。

★ **PvE 关键线索**：`28/1` 在 `mmstart` 之前到达且带"选中索引 + 可选总数"。如果我们能让 `28/1` 的 `body` 携带正确的关卡索引，就能让 `21/5` 一次回对图（`lobby_server.py` 注释的原话）。本卷确认了它的**字节结构**，为后续"PvE 关卡选择"提供了可直接构造的模板：
```
28/1 payload = 6c 08 <bytelen=4+4k> [k+1] <idx0> <idx1> ... <tail>
```

## §4 `28/4` = ContentUnlock2（内容解锁查询）

### §4.1 权威命名

`do_fixes.py:9-32`：
> `if task == 4:  # ContentUnlock2::task4: 完整对齐 TypeArray (0x6C 0x08)`
> 逐项 `content_ids` → 生成 `08 <cid> 08 32` 的解锁响应。

⇒ `28/4` 的 `0x6c` 就是 **ContentUnlock2 的 TypeArray**，`body` 里的 u32 是**内容 ID 列表**。

### §4.2 全语料 94 条，body 完全恒定

`tools/arr_28_4_ids.py` + `arr_6c_model.py`：
- **127 个 u32，body[0]=127**（= 元素总数），后 126 个是**内容 ID**。
- 126 个 ID 在 **94 条报文里逐字节完全相同**（distinct=1）。
- ID 集合：`{0,1,2,3,9,10,12,14,18,20,…,262}`，min=0 max=262，非连续（137 个槽位未列）。
- `tail = 263`。

### §4.3 语义

- **126 个 ID = 客户端当前"已解锁"的内容项**（本地存档里的解锁状态）。
- **tail=263 = 该 build 的内容总容量**（0..262 共 263 个槽位）。
- 客户端的意图：**"我解锁了这 126 项，请服务端确认/补发其余 137 项"**。

★ **对我们写服务端的意义**：`28/4` 是我们能**主动"送"内容解锁**的通道。要解锁全部内容，服务端只需对 263 个 ID 全回 `08 <cid> 08 32`（如 `do_fixes.py` 所示，32 = "已解锁"状态值）。**这是"免费获得所有武器/皮肤/道具"的协议入口**（若内容 ID 与商城 SKU 同域——但本卷证实 ID 域是 0..262，与 SKU 的大整数域不同，见 §5）。

## §5 ID 空间对照：28/4 的 0..262 vs 商城 SKU vs 8/3 配置键

| 来源 | ID 域 | 性质 |
|---|---|---|
| `28/4` 内容解锁 | **0..262**（小整数，263 槽） | 内容槽位索引 |
| 商城 SKU（`80/154`、`93/131`） | 241 / 22858 / 28845 / 31816…（大整数） | 商品编号 |
| `8/3` 配置键 | 10001..10010 / 30059..30061（哈希化） | 配置项键 |

⇒ **三个完全不同的 ID 空间**。28/4 的"内容解锁"不等于"商城购买"，它是**本地内容槽位的开关**（可能对应"战役关卡解锁/挑战解锁"等）。
