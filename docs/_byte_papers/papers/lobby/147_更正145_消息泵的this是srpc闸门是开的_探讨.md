## 二、为什么错得这么自然

我在 141 卷把 `0xE39B6E8` 命名为「dwLobbyImp 单例」，又把它当成"消息泵对象"。

到 145 卷，我看到 `0xB838A0` 里 `cmp [esi+0x4F4],0`，就去读 `0xE39B6E8+0x4F4` —— **读出 0，正好"符合"我的假设**。

★★★ **这就是最危险的情况：错误的前提 + 巧合的证据 = 一个自洽的假结论。**

★ 而且 `0xE39B6E8+0x4F4` 真的是 0 —— **它"验证"了我的猜想**，我因此完全没有怀疑。

## 四、真相

```
srpc+0x4F4 = 0x3ACD38A0   ★★ 非 0，闸门是开的
handler+0x4F4 = 0          ← 我上一卷读的是这个
```

而 `0x3ACD38A0` 的 vtable 是 `0xD5A4F4`，正是 `0xBA2800` 构造连接对象时写的那个值。

**⇒ 连接对象存在，闸门开着，消息泵正常工作。**

★ 「野指针 ⇒ 闸门关闭」这条链，**从第二步起就全错了**。

## 五、我在这一卷真正学到的

### 5.1 `this` 的身份要先钉死

**同一个偏移 `+0x4F4`，在 `srpc` 上是闸门，在 `dwLobbyEventHandler` 上是无关字段。**

★★★ **判据：任何 `mov ecx, X` 之后调用，都要往上追 `X` 从哪来。**

### 5.2 巧合的验证比没有验证更危险

`handler+0x4F4 = 0` **恰好**符合我的假设，所以我没有再查第二遍。

★★ **教训：如果一个证据"太符合预期"，反而要去查它是不是读错了对象。**

### 5.3 一个字节的偏移错误会连锁

`0xB8392C` 这个地址我是读对的，指令也是对的。**错的只是 `esi` 指向谁。**

★★ **地址对 ≠ 语义对。**

## 六、我的搜索脚本也错了一处

第一次搜 `0xB838A0` 的调用者，得到 **0 命中**。

原因：
```python
# 错误：把 file offset 当 VA 用
if (i + 5 + rel + IB) == TARGET
```

`i` 是 file offset，`rel` 是 VA 空间的位移，两者相加无意义。

**正确：**
```python
here = off2va(i)           # file offset → VA
if here + 5 + rel == TARGET
```

修正后立刻拿到 3 个调用者。

★★★ **这也是一个"判据错误导致 0 命中"的实例** —— 和 142 卷那个 ModRM 判据错误同类。
