# 140 · 消息类型号终极定案：`0xB83744` 是「类型号-1」索引表

> 前序：139（房间投递 / 五层注册门）、138（dwRoom 协议层）
> 性质：**逐指令逆向 + 表长机械自证**。本卷**推翻 139 卷 §3 的唯一一处「更正」**，
> 并给出消息泵从「4 字节服务名」到「handler」的完整解码链。

---

## §0 十条结论

1. ★★★★★ **`0xB83744` 的索引 = 类型号 − 1**（`0xB82D42 dec eax`），**主表恰 75 项**（`0xB83870 − 0xB83744 = 0x12C = 75×4`，两张表首尾相接，表长机械自证）。
2. ★★★★★ **房间消息 = 类型号 7 或 8**（表项 `0xB82E03` → `0xB7B300` → vtable slot[6] → `0x7F1060` → `0x7E7C90` → `rec+0x25B8` = `0x6371F0`）。
3. ★★★★★ **类型号 6 是邀请弹窗**（`0xB82DDD` → `0xB7B210` → slot[10] → `0x7F20C0` → `0x808DC0`）。
   **139 卷把这一条改错了；138 卷原本的「opcode 6 → `0xB7B210`」是对的。**
4. ★★★ **类型号 9 / 10** → `0xB7B4B0` → slot[4] → `0x7F1040` → `0x7E7A50`（定向 / 成员同步）。
5. ★★★ **类型号 31 / 32** → `0xB7B650` / `0xB7B820` → **slot[7] / slot[8]**（`0x7F10C0` / `0x7F1160`），
   槽 8 = `0x7F1160` 内含「读 0x800 blob + 读文本」结构，与 `0x6371F0` 同族。
6. ★★★ **类型号 1001 走独立分支**（`0xB82D3C je 0xB83547` → `0xB7CCE0`），**不查主表**。
7. ★★★ **类型号 1002..1010** 走第二表 `0xB83870`（9 项，`add eax,0xFFFFFC16` 即 `−1002`）。
8. ★★★ **类型号来自「4 字节服务名」的 FNV-1a 哈希查表**：`0xB7FAD0` 用 `imul 0x1000193 / xor` 算 4 字节 key，
   在 `0xB7F950` 建的哈希表里查节点，`节点[0]` = 类型号。
9. ★★ **类型号按注册顺序 1..N 顺序分配**（注册函数 `0xB7A550` 每次取 `++counter`）。
10. ★★ **`0x82E1458`（47 项描述符表）直接按类型号索引（无 `dec`）**，与 `0xB83744` 规则**不同** ——
    这是两张完全独立的表，不能互相套用。

## §1 表长机械自证（推翻 139 的唯一一处）

```
0xB83744 + 75×4 = 0xB83870   ← 与第二表起始地址完全重合
0xB82D42  dec eax            ; eax = 类型号 − 1
0xB82D43  cmp eax, 0x4A      ; 74 ⇒ 类型号 1..75
0xB82D46  ja  0xB836CC       ; 越界兜底
0xB82D4C  jmp [eax*4 + 0xB83744]
```

**⇒ 主表 75 项覆盖类型号 1..75；`0xB83870` 起的 9 项是另一张表。**

139 卷此前按「索引即类型号」读，把 `0xB82DDD`（索引 5）记成类型号 6 的邻居，
实际它**就是**类型号 6；`0xB82E03`（索引 6）**就是**类型号 7。

## §3 类型号的来源：4 字节服务名 → FNV → 哈希表

### 3.1 消息泵的解码

```asm
0xB82CCA  lea ecx,[edi+0x20]          ; 消息体对象
0xB82CD2  call 0xB80D30               ; 取类型号
0xB80D37  call 0xB7FAD0               ; FNV 查哈希表
0xB80D40  mov ecx,[eax]               ; ★ 节点[0] = 类型号
0xB80D45  mov [edx],ecx               ; → [ebp-0x78]
0xB82D1D  mov ecx,[ebp-0x78]          ; 类型号
0xB82D2C  cmp eax,0x3E9               ; 1001
0xB82D42  dec eax                     ; ★ 索引 = 类型号-1
0xB82D4C  jmp [eax*4+0xB83744]
```

### 3.2 哈希函数（`0xB7FAD0`，读侧）

```asm
0xB7FADB  movzx eax,[edx]      ; 取消息里 4 字节 key 的 byte0
0xB7FADE  imul  eax,0x1000193  ; FNV-1a 质数
0xB7FAE5  movzx esi,[edx+1] / xor eax,esi / imul
0xB7FAEB  movzx esi,[edx+2] / xor eax,esi / imul
0xB7FAF7  movzx esi,[edx+3] / xor eax,esi
0xB7FB06  dec esi ; and esi,eax  ; 桶 = hash & (cap-1)
0xB7FB14  mov edx,[edx]          ; ★ 4 字节整体作为 key
0xB7FB16  cmp edx,[eax+4]        ; 比对节点[1]
0xB7FB1B  mov eax,[eax+8]        ; 冲突链
```

### 3.3 哈希插入（`0xB7F950`，写侧）

```asm
0xB7F995  movzx edx,[ecx+eax]     ; 遍历字符串全部字节
0xB7F999  imul  ebx,0x1000193
0xB7F9A0  xor   ebx,edx
0xB7F9D4  inc   dword [edi]       ; 计数器++
0xB7F9D6  push 0xc ; call 0xB74220 ; 分配节点
0xB7FA01  mov [ebx],ecx           ; 节点[0] = 类型号（来自参数）
0xB7FA07  call 0xB75980           ; 节点[4] = 名字字符串
0xB7FA0F  mov [ebx+8],eax         ; 节点[8] = 冲突链
```

### 3.4 ★ 关键：注册表是**空**的

`0xB80D90`（`dwLobbyImp` 的服务名注册函数）的 25 个调用者**全部** push 的是
`0xDAE091`（空串哨兵），而不是 `room`/`team`/`vote` 之类的名字。

**⇒ `dwLobbyImp` 自己的名字表在静态下没有任何 4 字符服务名。**

`room`（`0xDAE3E8`）、`team`（`0xDBFDD8`）、`vote`（`0xDBA93C`）这三个字符串
唯一的 `push` 点是 **`0x7C76F0..0x7C782E`**，而那是 **GFx/Flash 的 `SetVariable`**
（`mov edx,[edx+0x14]` = `ActionScript 的 setMember`），与消息泵无关。

## §5 完整解码链（从网络字节到 handler）

```
网络帧
  └ 0xB838A0  dwLobbyImp::handleMessage
      └ 0xB82CCA  lea ecx,[edi+0x20]
          └ 0xB80D30 → 0xB7FAD0   ; 4 字节服务名 → FNV-1a → 哈希表 → 类型号
      └ 0xB82D2C  cmp 1001 / je  → 0xB83547 → 0xB7CCE0
      └ 0xB82D31  jg  → −1002 → 第二表 0xB83870（1002..1010）
      └ 0xB82D42  dec eax
      └ 0xB82D4C  jmp [eax*4+0xB83744]   ; 类型号 1..75
          ├ 6  → 0xB82DDD → 0xB7B210 → slot[10] 0x7F20C0 → 0x808DC0  【邀请】
          ├ 7/8→ 0xB82E03 → 0xB7B300 → slot[6]  0x7F1060 → 0x7E7C90 → 0x6371F0 【房间】
          ├ 9/10→0xB82E29 → 0xB7B4B0 → slot[4]  0x7F1040 → 0x7E7A50        【定向】
          ├ 31 → 0xB82E53 → 0xB7B650 → slot[7]  0x7F10C0
          └ 32 → 0xB82E79 → 0xB7B820 → slot[8]  0x7F1160
```

### 5.1 房间消息（类型号 7 / 8）的包体

```asm
0xB7B34B  call 0xB769A0  → u64 A
0xB7B372  call 0xB76A30  → char[0x40]
0xB7B39B  call 0xB769A0  → u64 key
0xB7B3E5  call 0xB76AF0  → blob(0x800)
0xB7B41F  mov ecx,[edi+0x4F0]
0xB7B428  mov edx,[edx+0x18]   ; slot[6]
0xB7B459  call edx             ; 7 参
```

`0x7E7C90` 用 (arg1=key.lo, arg2=key.hi) 匹配 `rec+0x10/+0x14`；
`rec+0x25B8` 的 `0x6371F0` 用 **arg6=ptr / arg7=len** 建位流，再读**两个子 blob**。

## §6 诚实边界

1. **「类型号 7 还是 8」未做动态区分**：两者 handler 完全相同，区别只能靠运行时观测
   （或从服务端下发时的名字反推），静态无法再细分。
2. **4 字节服务名的实际值**（`room`? `ROM1`? 别的?）**静态拿不到** ——
   `dwLobbyImp` 的注册调用点全部 push 空串哨兵 `0xDAE091`，名字表在静态下是空的。
   这是 140 的**主要未闭合项**。
3. **`0xB7B650`(type31) 与 `0xB7B820`(type32) 的完整字段格式未逐条展开**（已知 32 走 slot[8]，含双 blob 结构）。
4. **第二表 1002..1010 的语义未定**（handler 地址已全列）。
5. **`0xB7CCE0`（类型号 1001）未展开**。

## §8 方法论

1. ★★★★★ **看到跳转表，先算表长再读表**：`表2首址 − 表1首址 = 表1长度`，一条减法就能证伪「76 项」。
2. ★★★★ **`dec`/`sub`/`add` 出现在 `jmp [eax*4+表]` 之前，索引就不是原值** —— 这是本卷全部错误的根源。
3. ★★★ **「0 调用点」先问「该不该有 call 边」**：`0xB7A550` 的注册调用者全是空串哨兵，
   说明名字不是静态常量，而是**运行时**从某处灌入。
4. ★★★ **两张表规则不同要分开验**：`0xB83744` 有 `dec`，`0x82E1458` 没有。
5. ★★ **更正别人之前，先算出「谁的表长能自证」**：139 的错就在于没有做 §1 那条减法。
