## §3 第 3 问：有没有「房间被 ACE 标记」的迹象 —— 用服务端一票否决

### 3.1 59/59 帧连续，零缺口

`kit\lobby_srv.log`（24,539 字节 / 250 行）逐帧记录服务端解密结果：

```
解密成功 59 次，seq = 1,2,...,59
gaps = 0     duplicates = 0     missing = 0
marker=0x86 ver=0x03 全 59 帧一致
```

**任何一个「本地丢弃/降级」机制都会在服务端留下缺口**（seq 跳号、重复、或帧数少于客户端发送计数）。
**零缺口 ⇒ 从握手（seq1）到 11/4（seq59）客户端一帧没丢、一帧没改、一帧没降级。**

### 3.2 房间四连全部到达

| seq | svc/task | 服务端处理 |
|---|---|---|
| 54 | **11/13** | `createRoom -> roomId=0x1122334455667788 secondId=0x42706516032933CB (37 字节)` |
| 57 | **21/1** | `createSession -> sessionId=0x1122334455667788 (对象 14 字节)` |
| 58 | **21/12** | `matchmaking 21/12 空应答(payload=288)` |
| 59 | **11/4** | 收到 170B payload（`0a 88 77 66 55 44 33 22 11 …`） |

### 3.3 ★★★ 应答被客户端消费（不是只到了服务端）

`seq=58`（21/12）的请求 payload 前 14 字节：

```
序号(0-based) 00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D
字节          13 08 08 00 00 00 88 77 66 55 44 33 22 11
                              ^^^^^^^^^^^^^^^^^^^^^^^^^
                              payload 偏移 0x06..0x0D = 0x1122334455667788 (LE)
```

**这 8 个字节正是服务端在 `seq=54` createRoom 应答里下发的 roomId。**
`seq=59`（11/4，170B）的 payload 同样以它开头：

```
0a 88 77 66 55 44 33 22 11 13 08 95 00 00 00 …
   ^^^^^^^^^^^^^^^^^^^^^^^^^ 再次回显 roomId
```

⇒ 客户端**收到了** `11/13` 的应答、把它解出来、并在**两条不同的后续消息**里带回来了。
这是一条**不依赖 hook 完整性**的端到端证据：roomId 完成了「服务端→客户端→服务端」的往返。

### 3.4 反例关键词扫描

`lobby_srv.log` 与 `chain.txt` 全文扫描：

```
drop / reject / deny / block / DROP = 0
拦截 / 丢弃 / 阻止 / 降级 / 检测 / 封禁 / 非法 = 0
```

`_battle_err.txt` = `securityKey <- battle_security_key.txt (00000000...) 与大厅下发客户端的 16B 一致`。

## §4 结论与分母

**判定：ACE 无关（ACE-irrelevant）。**

| 假说 | 判据 | 结果 |
|---|---|---|
| ACE 拦截房间 socket | 22 条 ACE 网络记录，0 条指向 `127.0.0.2:3074`；ace-ats32 无 WS2_32 导入 | **否证** |
| ACE 在客户端丢弃/降级房间帧 | 服务端 59/59 连续、零缺口 | **否证** |
| ACE 标记房间请求后本地吞掉 | `seq=58`(21/12) 与 `seq=59`(11/4) 两次回显 `seq=54` 下发的 roomId | **否证** |
| ACE 内核 WFP 静默过滤 | 若过滤，服务端必现缺口；实测零缺口 | **否证（本次运行）** |
| ACE 在时间上与房间阶段重叠 | ACE 网络活动 t≈2.8–12.9s，房间 t≈45s+ | **否** |

**仍开 / 需要说清的两条边界：**

1. **hook 分母不全**：`WSASend/WSARecv/ConnectEx` 未 hook，`127.0.0.2:3074` 的连接建立过程没被观测到。
   「ACE 没调 connect 到 3074」这句话只能覆盖 **19 条已记录的 connect**。
   —— 但 §3 的服务端证据不依赖 hook，故结论不变。
2. **内核驱动状态未知**：chain.txt 看不见驱动。本次运行中 ACE-SSC 的 WFP 若在，也必须解释零缺口；
   它要么没装、要么装了对 3074 放行。**下一条要闭的是「ACE-SSC 是否加载」**（设备枚举 / 驱动服务状态），
   但那属于「ACE 自身状态」，不是「ACE 阻断房间」——后者已被本次运行否证。

**房间功能坏在别处。** 本次现场里房间线的可观测断点是 `21/12` 回空对象（`对象=0 (66 字节)` =
空 ACK）、`11/4` 收到后日志无应答记录（120s 窗口内）。这两条与 ACE 无关，归房间线其他卷。

## §6 方法论

1. **「观测不到」≠「没发生」，但「对端收到了」＝「本地没吞」**。
   hook 是不完整的分母，所以证否要用**对端**（服务端 seq 连续 + roomId 回显），
   而不是用「hook 里没看到 ACE 调 sendto」。
2. **回显是最强的单点证据**：一个由服务端下发、客户端在后续消息里带回的随机值，
   同时证明了「下行收到」「解析正确」「上行发出」三件事，且不依赖任何 hook。
3. **ACE 用户态看导入表，内核态只看实测**。ace-ats32 无 WS2_32 导入是决定性的（它根本不能建 socket）；
   WFP 则只能靠「零缺口」这种不可伪造的运行期事实来否证。
