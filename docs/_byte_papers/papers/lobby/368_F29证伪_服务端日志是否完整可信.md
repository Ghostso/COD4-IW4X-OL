## §0 判定（一句话）

**「日志完整记录『收到了什么』」——成立（59/59）。**
**「日志完整记录『处理结果』」——不成立：差 1 条（seq=59）。**
缺的不是「收包记录」，而是**「处理结果」**：`11/4 setRoomData` 分支在 `lobby_server.py:1105`
抛 `NameError: name 'batch' is not defined`，异常在 `reply_objects` 内**未捕获**，
于是**既没有 `-> …` 结果行，也没有 `-> 0x85 应答` 行，更没有 traceback**（见 §4）。

对任务三选一：**「日志有遗漏，遗漏的是 X」**，其中
**X = seq=59（service=11 task=4 setRoomData）这一条请求的「处理结果/应答」**，
而不是「收包」。收包层零遗漏。

## §2 静态：所有「会回包」的分支与它们的日志

### 2.1 日志模型是**两层**，不是「每个分支各打各的」

`handle_lobby()` 主循环（L1620–1687）对**每一条成功解密的 0x85**无条件打三层通用日志：

1. `★ 解密成功 #N seq=… service=… task=… declared=…`（L1630）
2. `payload(K): <hex>`（L1645，`if r["payload"]`）
3. **若 `note` 非空**：`-> <note>`（L1654）
4. 发送后：`-> 0x85 应答 seq=… service=… task=… 对象=N (B 字节)`（L1672）

所以「某分支打不打日志」=「它的 return 是否带回**非空 note 字符串**」。

### 2.2 枚举 `reply_objects()` 的全部 48 个 return

脚本 `static_branches.py` 用 AST 枚举（`reply_objects` 定义于 L807–1363）：

```
total return statements in reply_objects: 48
  ... (逐条打印) ...
branches WITHOUT a loggable note: 0 []
if-statement branch headers: 57
```

**48/48 个 return 都带回非空 note**（`ack("…")` 或三元组第 2 位）——没有「静默 ACK」分支。
即**纯静态**看：不存在「分支主动选择不打日志」。漏掉处理结果的唯一机制只能是
**根本没走到 return**（异常）。

### 2.3 主循环里「收到但不进 `reply_objects`」的路径（同样都记）

| 路径 | 是否记日志 |
|---|---|
| keepalive 帧 | `<- keepalive`（L1707） |
| 0x82 stage1 | `<- 0x82 stage1 (…)`（L1713） |
| 0x85、密钥未就绪 | `<- 0x85 (…) 会话密钥还没就绪, 先攒着`（L1779） |
| hmac=BAD | `(hmac=BAD -> 不回, 塞回 pending …)`（L1642） |
| 解密失败 | `!! 0x85 解密失败`／`!! 解密异常`（L1624–1627） |
| `len(fr) < 6` 的帧 | **静默 `continue`（L1709–1710），不打日志** ← 唯一静默丢弃点 |
| `parse_frames()` 尾部不完整帧 | 留在 `buf`，**不打日志** |

后两条是「静默丢弃」，但**都不回包**，且本卷实跑中两份计数证明未发生（§3）。

## §4 漏掉的那一条：seq=59（11/4 setRoomData）——分支内 NameError

### 4.1 日志的客观形状

`lobby_srv.log` 共 250 行，末 3 行（第 249–250 行）是：

```
[15:15:57]   ★ 解密成功 #59 seq=59 hmac=OK marker=0x86 service=11 ver=0x03 task=4 declared=173
[15:15:57]        payload(170): 0a 88 77 66 55 44 33 22 11 13 08 95 …
[15:15:57]        payload(170): … (截断，文件到此结束)
```

- **有** `解密成功 #59` 与 `payload(170)` ⇒ 收包已记录。
- **没有** `-> …` 结果行。
- **没有** `-> 0x85 应答 seq=59`。
- **没有** `11/4 batch 族=…`（该分支 L1107 本应打的行）。
- **没有** `=== 大厅连接结束 ===`（L1787 本应打的行）。
- 全文 `Traceback|NameError` = **false**（`crosscheck.py`）。

### 4.2 机读定位

`reply_objects()` 的 11/4 分支（L1086–1146）：

```python
if task == 4:
    ...
    _fam, _inner = _parse_11_4_batch(batch)   # L1105  ← 第一个可执行语句
```

`batch` 在 `reply_objects` 作用域**从未被赋值**：它只是 `_parse_set_room_data()` 内的局部名
（L1458 `ch, batch, tp = 0, b"", None`），而该函数在此分支**没有被调用**。
对照组 `REF_LOBBY_KIT\lobby_server.py:787` 是 `ch, batch, tp = _parse_set_room_data(plain)`，
实跑 kit 把这一行删了却保留了 L1105/L1119/L1139 对 `batch/ch/tp` 的引用。

**实跑复现**（`prove_11_4_nameerror.py`，喂入 seq=59 的真实 96B payload）：

```
EXCEPTION TYPE=NameError ARG="name 'batch' is not defined"
  at lobby_server.py:1105 in reply_objects
```

### 4.3 为什么「连 traceback 都没有」

1. L1653 `objs, note, pushes = reply_objects(...)` 在 `try` 块**之外**（`try` 从 L1656 才开始，
   只包应答构造/发送）。⇒ `NameError` 不被捕获，直接冒到 `handle_lobby` 线程顶层。
2. `handle_lobby` 线程无外层 `except`，也未注册 `threading.excepthook`。
3. `run_all.py:452–455` 用 `subprocess.Popen(...)` 启动 lobby_server，
   **不重定向 stdout/stderr**（无 `stdout=`/`stderr=` 参数） ⇒ 默认 traceback 输出到哪里取决于
   run_all 自身控制台，**未落进任何 run 目录文件**。
4. 结果：连接线程静默死亡 → 不再 recv → 不再写 `lobby_srv.log` → 文件停在 payload 半行。

这与「`decrypt #59` 有、其后全无、且没有『连接结束』」的现场**逐项吻合**，
且**预测**了「不应出现 `11/4 batch 族`」——实测确无。

### 4.4 影响边界

seq=59 的 `payload(96)` 是 11/4 的 **room 族**批次（`…02 04 …`，`13 08 95 00 00 00 | 91 00 00 00 | 02 04 …`）。
这是**房间动作（setRoomData）**，正是 room64 关心的房间线。它**未回包**，客户端拿不到该次
房间数据应答；但本卷仅判定「日志完整性」，房间语义另卷。

## §5 「日志有遗漏」的精确表述

| 命题 | 判定 | 证据 |
|---|---|---|
| 收到的请求都在日志里？ | **是，59/59** | §3 三份产物同数，差 0 |
| 每个收到的请求都有处理结果记录？ | **否，58/59** | seq=59 无 `->`、无应答行 |
| 遗漏的是「某个分支主动不打日志」？ | **否** | AST：48/48 return 都带 note（§2.2） |
| 遗漏的是「收包」？ | **否** | rx/ tasks / log 解密行 三向差 0 |
| 遗漏的是「异常导致的处理结果丢失」？ | **是** | L1105 NameError，未捕获（§4） |
| 日志对「没回包」是显式的吗？ | **否（这是真缺陷）** | 无 traceback、无「连接结束」行，读者无法区分「处理中」与「已崩溃」 |

**⇒ 结论：「日志有遗漏，遗漏的是 X」；X = `service=11 task=4`（seq=59，setRoomData）这条请求的
「处理结果/应答记录」——因为该分支在 `_parse_11_4_batch(batch)` 处抛 NameError 未捕获，
而服务进程的 stderr 未被 run 目录收集。收包层零遗漏。**

## §6 对「我以为服务端处理了、其实没处理」的判定

命题担心的失败模式确实**在本轮发生过一次**，但机制不是「某些分支不打日志」，
而是「**异常没有日志**」。两种失败模式的区分证据很干净：

- 若是「分支静默不打日志」：日志里会**没有**该条的任何痕迹（连 `解密成功` 都没有）。
  实测：seq=59 **有** `解密成功` 与 `payload` ⇒ 不是这一类。
- 若是「异常未记录」：会**只有收包、没有结果、且文件/连接突然中断**。
  实测：完全符合 ⇒ 是这一类。

因此，「看到 `解密成功`」**不能**推出「已处理并已回包」；必须看 `-> 0x85 应答` 行。
本卷把这条判据固化为可机读规则：

> **日志中「已回包」的权威计数 = `-> 0x85 应答 seq=` 行数（本轮 58），
> 而不是 `解密成功` 行数（本轮 59）。**

## §10 方法论

1. **「收包计数」和「回包计数」是两个不同的分母。** 本卷 59 vs 58；只看前者会误判「全部已处理」。
2. **静默失败 ≠ 静默分支。** 先看有没有收包痕迹，再判断属于「分支不打日志」还是「异常未记录」；
   两者留下的日志指纹截然不同。
3. **日志的末尾形态是证据。** 「无『连接结束』行 + 末行是半条 hexdump」= 进程/线程非正常终止，
   这是 `NameError` 假设的**事前预测**（应无 `11/4 batch 族` 行），实测命中。
4. **对照受保护基线与实跑 kit 的同一分支。** REF 有 `_parse_set_room_data(plain)` 调用，
   实跑 kit 没有但保留了其消费者 ⇒ 一行删除制造全局 NameError。这是「基线比对」能一眼看出的缺陷。
