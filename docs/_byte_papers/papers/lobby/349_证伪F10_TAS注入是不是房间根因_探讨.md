# 349 · 探讨：为什么「跳过 TAS ⇒ 房间坏」看起来成立，其实不成立

> 编号：349（room64 证伪路 F10）副篇 · 方法论与误判链
> 主篇：`349_证伪F10_TAS注入是不是房间根因.md`

---

## 1. 误判链是怎么长出来的

这个假设有三层"看起来对"的支撑，逐层剥开才能看到它错在哪：

**第一层（现象层）**：`chain.txt:4` 有一行醒目的 `★ 跳过 TAS 注入`。
`★` 在 kit 的日志约定里通常表示"异常/重要"，读日志的人自然会把它当成"故障点"。

**第二层（结构层）**：TAS 确实是**唯一**通过共享内存把"服务器地址 + 账号票据"塞进客户端的通道。
一旦它被跳过，"客户端怎么知道大厅地址"就变成一个必须回答的问题。

**第三层（因果层）**：房间功能确实需要联网状态。如果登录票据缺失 ⇒ 在线对象不成立 ⇒ 房间不可用，
这条链**在纯逻辑上完全成立**。

错的地方不在逻辑，而在**前提没验证**：本链到底有没有用别的方式提供登录票据？
答案是**有，而且已经提供了**（§2）。所以"票据缺失"这个前提是假的，整条因果链就悬空了。

---

## 2. 判定这件事只需要三个正交问题

一个功能"缺了某个注入"是不是根因，必须同时满足：

| 问题 | 本卷答案 | 证据 |
|---|---|---|
| Q1. 这个注入提供的东西，别处能替代吗？ | **能** | hosts + dwauth.ini + 未签名认证（auth_task=10） |
| Q2. 目标功能的代码读这个注入的产物吗？ | **不读** | `0x82E1580` 在房间区间引用 **0** 次 |
| Q3. 跳过后目标功能的可观测前置条件满足吗？ | **满足** | `5E8=3`、`C8=2`、连上 `127.0.0.2:3074` |

**三个都是"否/能"**，所以"是根因"不成立。
重要的是：**Q2 是决定性的**。即使 Q1/Q3 都成立，如果房间代码真的读 `CTclsProxy`，那它就是根因。
本轮把 Q2 做成了**可数的分母**：全镜像 22 处引用，房间区间 0 处；对照 AS 单例在同一区间 120 处。

## 3. ★ 这条线里最容易踩的两个坑

### 3.1 "TAS 没生效" ≠ "TAS 失效是根因"

`chain_obj.bin` 显示 `+0x18D4 = 0`、`+0x18C4/+0x18C8 = 0` —— **这确实是 TAS 没生效的铁证**。
但"证明了 A 没生效"和"证明 A 是根因"是两个不同强度的命题。前者只需要一次内存读，后者需要
**反事实**：A 生效后目标功能会变好。本卷无法做反事实（`tas_off.flag` 在场），
但有 **`run_all.py:682` 的反向记载**："否则 auth_task=32 走签名路径会卡住"——
即 A 生效后反而更糟（在名字不一致的前提下）。

这是 264 卷"错的更正比不更正更糟"的同类：**把"某物缺失"当成"某物缺失导致故障"，少一步反事实检查。**

### 3.2 补丁数是 5 不是 4

Memory 里记的是"4 补丁 + latch + TAS 镜像"。实测 **5 个**（`chain.txt:36-40` 全 5/5 回读 OK）。
第 5 个 `GateB @0x62FE80` 是**房间虚拟表 `0xDC72D8` 的 slot 0**，看上去"最像房间补丁"，
本节把它解到底：它是 `xblive_privatematch` **dvar 门**，恒置 1，与 TAS 无数据依赖。
⇒ 即使有人想"补丁 5 需要 TAS 提供某字段"，也被 `0x8269818` 的唯一写点否掉了。

---

## 4. 那 TAS 到底该不该开？

**短期：不该，且默认关是对的。** 理由：
- `auth_task=10` 路径已实测走通（2239B 应答、`5E8=3`）；
- `auth_task=32` 路径官方记载会卡住；
- TAS 名字格式（`%d` vs `%s`+十六进制）很可能让 OpenFileMapping 仍失败。

**长期（若要做"完全原样登录"）：** 需要先修名字格式，再做一次**独立 run**（新 run 目录、
`--tas`、且不依赖 hosts/dwauth）来观察 `auth_task` 和 `+0x18D4` 是否非 0。那是另一件事，
与"房间修复"不同路。

## 5. 给其他 F 路的交接

- **不要**再把"TAS 被跳过"列为房间待查项——本卷已关闭。
- **`21/12` 空应答**（`lobby_srv.log:247`，`payload=288`）仍是房间线的第一个未闭合点；
  它发生在 `createSession (21/1)` **之后**、`21/12` **返回空**，而 `21/12` 的入口在
  `0x626xxx` 段（不在 TAS 引用清单里）。
- **`xblive_privatematch` dvar 真值**：若要判断补丁 5 是否必要，需在未打卡 5 的一轮里读
  `[0x8269818]+0xc`；本轮补丁已绕过，无法区分 0/1。
