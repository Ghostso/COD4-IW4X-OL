## 二、它确实起到了压力测试的作用

**写编码器的时候，我被迫回答了一些"读论文时不会追问"的问题：**

**- `MemberList` 的 36 个字段，到底谁是第一个？**
**- 那个 `0x01` 末尾 bool 在不在循环里？**
**- 725 位里有没有我算重的？**

**结果：**

**1. 一开始我把名字串放在 `MemberList` 里 → 反汇编核对后发现没有 ⇒ 改了论文。**
**2. 一开始我把 `MemberInfoAdd` 写成 `0x03+0x0a+记录` → 重复了记录里的 `0x0a` ⇒ 改了代码。**
**3. 位长算成 812 而不是 775 ⇒ 找到了名字串那个多余项。**

**⇒ ★ 写代码比读代码更容易发现自己错。**

## 三、位序这件事我不敢打包票

**我看到 `msb_index` + `inc`，推断是 MSB-first。**

**但这只说明"定位起始位时从高位算起"，
不必然等于"写入时先写高位"。**

**⇒ 所以编码器做了 `--lsb` 开关。**

**这不是偷懒，这是**诚实地把不确定性暴露给使用者**。**

**⇒ 如果我硬写"MSB-first 是对的"，将来错了，
使用者会以为是客户端问题。**

---

## 四、最难承认的一条：我不知道"消息类型号"

**每条消息第一个字段是 `0x03:8` = 一个 u8。**

**它是"这是哪条消息"的编号。**

**但它的取值我完全不知道。**

**⇒ 我只知道"MemberList 的第一字节是 u8 类型"，
不知道"MemberList 的 u8 值应该是几"。**

**⇒ 这就像知道信封上要写邮编，但不知道邮编是几位数。**

**⇒ 这个必须从实测里拿（发一条，看客户端当它是哪种消息）。**

---

## 五、有一样东西是意外收获

**手解前两个字节时，我发现：**

```
0x18 = 00011 000   → 前 5 位 = 3 ✓
0x05 = 0000 0101
0x40 = 0100 0000
```

**8 位类型值按 MSB-first 读 = `0000 0101` = 5。**

**⇒ 如果这个位流的类型号恰好是 5，那 MSB-first 就被"顺带"验证了。**

**⇒ 但这是"如果我填的 0 恰好变成 5"的巧合，不能当证据。**

**⇒ 不能拿巧合当证据，这是我这一轮反复提醒自己的。**

---

## 六、方法论收获（三条）

> **① 逆向的最终验收标准不是"论文写得漂亮"，
> 而是"能不能生成一个至少格式合法的样本"。**

> **② 写编码器是发现读漏字段的最好方法——
> 因为每个字段都必须落到具体位。**

> **③ 未知的东西要在代码里显式暴露（`--lsb`），
> 不要在文档里含糊过去。**
