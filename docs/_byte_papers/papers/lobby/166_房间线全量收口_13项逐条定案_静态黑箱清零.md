## 二、各项证据

### B1 `[0x82E1400]` = `dwPartyImp`

`0x638210` 构造器：

```asm
0x638230  mov dword [ebx],   0xDC73DC    ; vt1 → .?AVdwPartyImp@@
0x638236  mov dword [ebx+0x10], 0xDC7474 ; vt2 → .?AVdwPartyImp@@
0x63823D  call 0x62C000                  ; ★ 基类 dwRoomImp 构造
0x638242  mov dword [esi],   0xDC7714    ; 内嵌成员 → .?AVMyRoomImp@dwPartyImp@@
0x638254  mov dword [edi],   0xDC787C    ; 内嵌成员 → .?AVMyRoomEventHandler@dwPartyImp@@
```

**RTTI 解析（`vftable[-1]` → COL → type_info → +8）**：

| vtable | 名字 |
|---|---|
| `0xDC73DC` | `.?AVdwPartyImp@@` |
| `0xDC7474` | `.?AVdwPartyImp@@` |
| `0xDC7714` | `.?AVMyRoomImp@dwPartyImp@@` |
| `0xDC787C` | `.?AVMyRoomEventHandler@dwPartyImp@@` |
| `0xDC7D4C` | `.?AVEventHandler@dwRoom@@` |

**⇒ 这是 `dwPartyImp`（组队），它继承 `dwRoomImp`，并内嵌一套"队伍里的房间"实现。**

**意义**：房间子系统不是 3 个独立单例，而是 **`dwRoomImp`（房间）+ `dwPartyImp`（组队，内含房间）** 两层。

### A1 `b8-b9` 的 7 个值

```
0x0078=120  0x0080=128  0x00A0=160  0x00A8=168
0x00B8=184  0x00D0=208  0x00E0=224
```

**全部是 8 的倍数**，且 `(v-0x78)/8 ∈ {0,1,2,3,5,6,8}`。

**⇒ 它是一个 8 字节对齐的槽位/标志计数**，不是任意长度。

**与 `len` 的关系**：119 卷说「与长度不完全线性」—— 与本结论一致：它数的是**槽位数**，不是字节数。

---

### A5 `<<10` 的真正含义

```
u32@[4:8] == (len-10) << 10
u16@[5:7] == (len-10) × 4
```

两个关系**等价**，因为 `u32 = u16 << 8`。

**⇒ 这个"u32"实际是「u16 值在 [5:7]，后面 [7] 是 0」**，即：
```
[4:5] = (len-10)*4 的高字节
[5:7] = (len-10)*4 的低 16 位
[7]   = 0
```
**`<<10` 不是"位长标度"，而是「值本身就在 [5:7]，读 [4:8] 时被当成 u32 导致左移 8 位」的错觉。**

**⇒ 该字段 = `(len-10) × 4`，一个 u16。`×4` 的含义：数据体按 4 字节（u32）计数的元素个数。**

### ✅ A8：`msg/11` 的「内层 16 字节」= `ROOM_READY_BATCH`（同一个字节串）

`msg/11_04_blob内嵌.md` 记录 `11/4` 的 blob 内层 16 字节：

```
0c 00 00 00 02 02 00 00 00 08 00 00 00 80 08 00
```

**与 `codol_crypto.py:803` 的 `ROOM_READY_BATCH` 逐字节相同。**

```
ROOM_READY_BATCH = bytes.fromhex("0C00000002020000 0008000000800800")
                 = 0c 00 00 00 02 02 00 00 00 08 00 00 00 80 08 00   ✓
```

### 这个"未解"的真正含义

`msg/11` 自己分析：

```
u32@0 = 12  →  后面正好剩 12 字节 ✓（长度自洽）
[4:16]  = 02 02 00 00 | 00 08 00 00 | 00 80 08 00
```

而 161 卷已证：**本 build（1649370）客户端真正发出的 ready 是 13 位位流 = 2 字节 `02 18`**。

**⇒ 结论**：

> 这个 16 字节**不是本 build 客户端的 ready 格式**。
> 它是 **ol-mod 对着 3.3.3.3 版本抓到的 `CapturedReadyMessage` 常量**。
> `codol_crypto.py` 注释里也写着「照抄 ol-mod Unknown0BService.cpp:98-101」。

**⇒ `msg/11` 的"内层未解"是**：**它捕捉到的是另一个版本的客户端报文**，
与本 build 的 13 位位流格式不同 ⇒ 用本 build 的文法去解，自然解不开。

**⇒ 该项闭合，且顺带证明了 161 卷的结论**：拿这个 16 字节去做判据必然失败。

## 六、方法论

1. **★★ 「问题问错了」也是一种闭合。** `room.changemap` 和 `6/5 maxResults` 都是"不存在独立报文/字段"——**证明不存在 = 闭合**。
2. **★★ `<<10` 可能只是"u16 被当成 u32 读"的错觉。** 遇到"奇怪的标度"，先看是不是跨字段误读。
3. **★ 值域全为 8 的倍数 ⇒ 对齐槽位计数，不是字节长度。**
4. **★ RTTI 缺失（无 COL）要如实标为"边界"，不要硬猜名字。** `[0x84ABB08]` 就是这种情况。
5. **★ 早期卷的"未解"要先和后续卷对账**，`msg/11` 的内层 16 字节早已被 119 卷解掉。
