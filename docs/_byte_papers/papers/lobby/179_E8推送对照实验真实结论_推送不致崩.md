# 179 · 房间类黑箱：E8 推送对照实验的**真实结论**（首次有行为数据）

> 卷次：179（房间类 · 首次拿到"推送 → 客户端行为"的对照证据）
> 方法：按 run 逐个对齐"发了什么 / 客户端随后做了什么"
> 结论：**房间里推 `dwRoomMessageReady` 不会让客户端崩溃；崩溃另有原因。**

---

## §0 结论

1. **`10 08 40 00 00` 不是客户端真实报文，是服务端 `kit_E8_OK` 自造常量**。用它当"第一权威"会得出错误模型（我试过，两个候选模型都对不上）。
2. **唯一真发过它的 run 是 `ONCE_20261029_161336`（3 次）。客户端没有崩溃** —— 16:14:34 发完，`对端关闭` 出现在 **16:17:00**（2.5 分钟后，是正常退出）。
3. **对照 run `ONCE_20261029_162109`（不发 E8-OK）反而在 16:24:44 收到 `10054`（连接被强制关闭）**。
   ⇒ **E8-OK 推送不是"同秒 reset"的原因。**

## §1 E8-OK 的真实来源

`run_codol_001\kit_E8_OK_20261029\lobby_server.py:244` 内嵌：

```python
def frame_room_message(msg_type, fields, subtype=0):
    w.write(msg_type, 8)      # 8 位 type
    w.write(subtype, 3)       # 3 位 subtype
    for value, tag in fields:
        w.write(value, 8)     # 8 位值
        w.write(tag, 3)       # 3 位标签

def build_ready(member_id=1, is_ready=1, subtype=0):
    return frame_room_message(0x10, [(member_id & 0xFF, 0), (is_ready & 0xFF, 0)], subtype)
```

算出来：`type=0x10`(8位) + `subtype=0`(3位) + `1`(8位) + `0`(3位) + `1`(8位) + `0`(3位)
= `00010000 00000000 10000000 00...` = **`10 08 40 00 00`** ✓

★ 这是**第三个模型**（8 位 type + 3 位 subtype），和 169/175/176 的位宽模型、177 的 5 位标签模型都不同。
⇒ 三套模型并存，说明当时没人用真实样本校过。

## §3 这条证据推翻了什么

### 3.1 推翻"推送会让客户端同秒 reset"

前几卷（160 卷）写过：

> 11/4 推 16B 常量 ⇒ **同秒 reset ×4**

★ 那是**推 16 字节常量**（`ROOM_READY_BATCH`），不是推 `10 08 40 00 00`。
本卷证明：**推 5 字节的 `10 08 40 00 00` 不会崩。**

两者不是同一个实验，不能混为一谈。

### 3.2 说明 `dwRoomMessage` 推送本身不是致命项

`161336` 连推 3 次，客户端全程正常工作 2.5 分钟。

⇒ **房间里推 ready 消息，客户端会接收，不会崩。**

★ 这直接支持 172/173 卷的结论方向：**问题不在"推送格式"，在"更外层的闸门/状态"**。

## §4 但仍未闭合的（诚实）

1. **`10 08 40 00 00` 是错的格式，客户端"没崩"不等于"理解了"。** 它可能只是被静默丢弃。
2. **没有"推送后客户端真的进入房间/开始游戏"的证据。** `161336` 的后续应答（102/7 等）是聊天/存储服务，不是房间状态。
3. **`162109` 的 10054 原因不明**，可能与 mmstart 推送的 `dwRoomMessageStartGame`（109 B）有关 —— 那个 109 B 用的是 `build_startgame_payload`，同样没有真实样本校过。
4. **`E8-OK` / `E8-BAD` 两组对照实验从来没跑成**：
   - `kit_E8_OK` / `kit_E8_BAD` 目录里 `lobby_srv.log` 只有 5 行（未跑）
   - `160922` 因缺模块没发
   - 只有 `161336` 发了，但没有配对的 BAD 组

⇒ **A/B 对照从未成立。** 这是房间类最大的实验缺口。

## §5 为什么"房间类永远有大型致命黑箱"这个判断是对的

用户说"房间类黑箱用不置空，房间类永远有大型致命黑箱"。本卷给出具体理由：

**因为房间动作的验证必须 A/B 对照，而 A/B 对照需要两次实机运行。**

静态逆向能给出：
- ✅ 结构（字段、位宽、标签）
- ✅ 调用链（谁调谁）
- ✅ 闸门位置（`srpc+0x4F4`）

静态逆向**不能**给出：
- ❌ 客户端收到 X 之后的反应（需要实机 + 抓包）
- ❌ 格式对不对（需要真实样本）
- ❌ 闸门开没开（需要运行时状态）

★★ **`10 08 40 00 00` 这一条已经把这件事演示得很清楚**：
三个模型并存，服务端推了，客户端没崩，**但没人知道它到底被解析了还是被丢了**。

## §6 方法论

1. **★★★ 日志里的字节必须先查来源。** `10 08 40 00 00` 出自 `kit_E8_OK` 的内嵌 `frame_room_message()`，不是客户端数据。
2. **★★★ 时间差是证据。** "发完 → 2.5 分钟后才断开" ≠ "同秒 reset"。必须看两次事件的时间戳间隔。
3. **★★ 对照实验要成对。** 只有 OK 组没有 BAD 组，等于没有对照。
4. **★★ "客户端没崩" ≠ "客户端理解了"。** 前者只能否定"格式会崩溃"，不能肯定"格式被解析"。
5. **★★ 前卷的"同秒 reset"要核清实验条件。** 160 卷那个是 16B 常量，不是 5B 位流。
