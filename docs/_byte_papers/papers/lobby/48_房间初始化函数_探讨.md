## 一、这一轮的终点

从报文追到对象，从对象追到创建，从创建追到初始化，
从初始化追到唯一调用者。

```
0x82e13fc  房间对象 = 0
   ↑ 0x639d00 创建（12 条指令）
   ↑ 0x7e9933 无条件调用
   ↑ 0x7e98f0 初始化函数
   ↑ 0x808658 唯一调用者
```

**再往上就是启动总入口了。**

---

## 二、一个意外：那个开关不是房间的闸门

我一开始以为 `[0xe85c28]` 是关键。

```asm
cmp byte ptr [0xe85c28], 0
jne 0x7e9911
```

**但仔细看跳转：它只跳过了 `0xb76d80` 这一句。**

**后面的 `0x6212c0` / `0x7fa4c0` / `0x7ef830` /
以及 `0x639d00`（创建房间）全部照常执行。**

**⇒ `[0xe85c28]` 只控制一个子步骤，不是房间的开关。**

**这是一个"差点误判"的地方。**

---

## 三、真正的疑点回到 `0xc3e9f5`

```asm
0x639d08  call 0xc3e9f5
0x639d12  cmp eax, edi
0x639d14  je  0x639d25    ; = 0 就走失败路径
```

**`0xc3e9f5` 返回 0 ⇒ 房间对象不创建。**

**上一卷我判断它是 CRT 函数。**

**如果不是，那它就是"检查某状态"的门。**

**这一步必须精确确认。**

---

## 四、一个更可能的解释：离线状态

**`0xc3e9f5(0x3a128)` 很可能在检查"是否已登录/有会话"。**

**如果是这样，那结论是：**

> **离线大厅下，房间对象本就不创建 —— 这是设计如此。**

**这解释了为什么项目里所有"房间功能"都失效，
而且和"网络协议能跑但房间不动"完全一致。**

---

## 五、这一轮的价值

**即使没找到"修复方法"，也把问题缩小到了一个函数调用：**

```
0xc3e9f5(0x3a128) 是否返回非零
```

**这比"房间对象是 0"具体得多。**

**而且给出了两个可验证的假设：**

1. 它是 CRT 函数 → 创建应当无条件 → 那 `0x7e98f0` 没跑
2. 它是会话检查 → 离线不创建 → 需要先建立会话

## 六、诚实地说

**这一轮我做了 9 卷（40–48），把房间逆向从"报文"推到了"启动初始化"。**

**但我没有解决"房间对象为什么是 0"。**

**我能说的是：**

- 它在哪个函数里创建（`0x639d00`）
- 谁调用（`0x7e9933`）
- 在哪一层条件（`0xc3e9f5` 的返回值）
- 唯一调用者（`0x808658`）

**剩下的问题是"`0xc3e9f5` 返回什么、为什么"。**
