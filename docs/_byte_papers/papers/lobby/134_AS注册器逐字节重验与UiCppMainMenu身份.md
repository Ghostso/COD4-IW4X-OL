## §一 838 个注册器：逐字节重验

133 的 838 是"vtable 立即数 → 向上找最近 `cc cc`"。**这个判据有 bug**：如果 vtable 地址出现在**数据区**（如 `[count][ptr]` 表），向上找 `cc cc` 会撞进**无关函数的函数体**。

逐字节重验判据（四条同时成立）：

```
① 函数入口前两字节是 cc cc（int3 对齐填充）
② 函数体内（前 0x300 字节）存在 `mov [reg], <本对象 vtable>` 且 <reg> ∈ {eax,ecx,edx,ebx,esp,ebp,esi,edi}
③ 该 vtable 是 829 个之一
④ 写入点距函数入口 ≤ 0x400（排除数据区误撞）
```

结果（集合差，`tools/as_registrar_enum.py`）：

```
133 版 838  →  实为 828 真 + 10 假
仅在 133 版存在的: 恰好那 10 个（仅在 134 版存在的: 0 个）
```

10 条假注册器的身份证：

| 假地址 | 真因 |
|---|---|
| `0x00693DD0` | **标量删除析构 shim 本身**，被误当成"某个对象的注册器" |
| `0x00A08BE0` / `0x00ABA330` | 落在数据段旁，字节凑巧像 `55 8b` |
| `0x00C414AC` `0x00C42162` `0x00C473E5` `0x00C4749F` `0x00C586D6` `0x00C5A411` `0x00C5A491` | **7 个全是同一段代码的中部**，起始字节 `00 00 eb 11` —— 前面那个 `00` 让"向上找 cc"跑到了更早的位置 |

★★ **7 个假注册器共享完全相同的 12 字节前缀 `00 00 eb 11 50 e8 ...` —— 这是同一份模板内联展开 7 次**（`eb 11` 是短跳转，`50` 是 push eax，`e8` 是 call）。它们是**某个函数的多个内联副本的中段**，不是 7 个函数。

★ 判据教训：**"向上找最近 `cc cc`"必须加上"函数体内有特征动作"这一条**。`.tp3` 段里 `cc` 不只出现在函数间对齐处，也出现在**大函数内部的数据跳转表区**。

## §二 覆盖率重算：828 / 829，1 个缺口有确切解释

收紧判据后重算（工具 `tools/as_registrar_enum.py`）：

```
覆盖对象 828 / 829
唯一未覆盖  .?AVFunctionHandler@GFx@Scaleform@@   (vtable 0xDC7BA4)
```

★★ **这 1 个未覆盖不是缺口，是父类。**

| 事实 | 证据 |
|---|---|

★ 这也解释了 132 §三 的"`0x693DD0` 体内写 `0xDC7BA4`"：那是**回填父类 vptr**，第 2 步（`0x693DE1 test`）才判断要不要 `operator delete`。**父类虚表在这里被引用是唯一合理的位置。**

## §三 2 个"漏覆盖"对象的真相：函数头不是 `55 8b ec`

收紧判据后第一次跑，报 2 个未覆盖：

```
00dce16c  .?AVAS_GetHeadSeason@@   h=006a9ba0
00dd516c  .?AVAS_ListContact@@     h=00726550
```

追查它们的注册器：

| 对象 | 注册器 | 函数头字节 |
|---|---|---|
| `AS_GetHeadSeason` | `0x6AEBD0` | **`57 8b f8`** ← `push edi; mov edi,eax` |
| `AS_ListContact` | `0x728350` | **`53 bb 01 00 00 00`** ← `push ebx; mov ebx,1` |

★★ **两个注册器都合法，只是函数头不是标准的 `push ebp; mov ebp,esp`。**

★ 我第一版的过滤器写了 `if d[f]!=0x55 or d[f+1]!=0x8b: continue` —— **把人肉写的"标准序言"当成了必要条件**。MSVC 对**叶子函数**（不调子函数的）会省略 `push ebp; mov ebp,esp`，直接 `push edi`/`push ebx`。

★★ **⇒ 判据"函数入口必须是 `55 8b ec`"是错的。正确判据是"入口前是 `cc cc`"，序言形态不作为条件。**

★ `0x728350` 的 `mov ebx,1` 后紧跟 `84 1d 44 86 7b 0e`（`test byte [0x0E7B8644], bl`）—— 这是一个**一次性守卫**（`static bool inited`），正是"只注册一次"的典型写法。★ 这也解释了 133 §五 里 `0x728350` 与 `GetMutInfo`/`RequireRecentmetData` 同块的现象：它是**该模块的惰性初始化函数**。

## §四 "9 个双注册"是伪缺口：829 对象 / 828 注册器 是 1:1

133 §八 4 说"9 个对象被两个注册器注册，主/别名未区分"。

★★ **本卷证明这句话错了。**

```
829 对象
828 注册器（真）
829 − 828 = 1  ← 就是抽象父类 FunctionHandler（无注册器）
```

**⇒ 829 个对象中 828 个各有唯一注册器，第 829 个是父类。没有任何对象被两个注册器注册。**

★ 我上一稿按"829 对象 / 838 注册器 ⇒ 差 9"推"9 个双注册" —— **这个推理把 10 个假注册器当成了真注册器**。修正 838→828 后，差值从 9 变成 1，而 1 已经有确切身份（父类）。

★★ **教训（本卷最重要的一条）：用"两个总数的差"去推断"有 N 个特殊项"，必须先确认两个总数各自的口径。** 一个掺假的分子会制造出一整批不存在的特殊项。

### 唯一"注册两次"的实情

§三 那两个对象确实各有**两个写入点**，但它们不是"两个注册器"：

| 对象 | 写入点 A | 写入点 B |
|---|---|---|
| `AS_GetHeadSeason` | 标准注册器 | `0x6AEBD0`（叶子 + 一次性守卫） |
| `AS_ListContact` | 标准注册器 | `0x728350`（同上） |

★ 这两个 B 是**同一函数的第二个入口/内联副本**，扫描时归入同一注册器记录 —— 所以**没有增加注册器计数**。

★ **诚实边界**：`0x6AEBD0` / `0x728350` 与各自的标准注册器是否**互斥执行**（`if !inited` 分支），本卷**未逐字节确认**。

## §五 `UiCppMainMenu` 的真实身份（更正 132 的隐含推断）

132 §八·补 列了 7 个 `UiCppXxx::Init`，并写"未见 `UiCppMainMenu` ⇒ 走另一条路径"。

本卷查清：

### 5.1 `UiCpp*` 有 34 个**字符串**，但只有 1 个 **RTTI 类**

```
.?AVUiCpp*  RTTI 类:  只有 1 个  →  .?AVUiCppUserData@@

```

★★ **7 个 View 类（MainMenu/ItemListView/MatchSelectView/ChallengesView/NewItems/NewModes/Onboarding/SuggestedLoadoutView）都没有自己的 RTTI。**

**⇒ 它们是被编译成"无虚表的普通类"，`::Init` 是普通成员函数，因此没有 `?AV...` 符号可查。**

★ **这就是 133 §八 3 "29 个外层函数仅 1 个映射到类名"的根本原因 —— 不是我没找到，是它们根本没有符号可对。**

### 5.2 那批 `codo.cpp.UiCppXxx` 是**源文件路径**，不是类名表

```
0xDD8230  "codo.cpp.UiCppMainMenu"
0xDD8248  "codo.cpp.UiCppItemListView"
0xDD8280  "codo.cpp.UiCppMatchSelectView"
...
```

★★ **`codo.cpp.` 前缀 ⇒ 这是 `__FILE__` 字符串**（编译期路径泄漏），全部落在 `0xDD81FC..0xDD8300` 一个连续块里。**零指针引用是正常的** —— `__FILE__` 只被断言宏/日志格式化用，永远不被"查找"。

★ 这和 `codol-tconnd-protocalhandler` 的"编译期源路径泄漏定身份"是同一手法，只是那次用来定第三方库身份，这次用来**确认类确实存在**。

### 5.3 `UiCppMainMenu` 没有 `::Init` 局域类 = 真实结构事实

全镜像 `?N@??Init@UiCpp<View>@@` 形态的局域类名只有 **62 条**，分布：

```

UiCppOnboarding              6
UiCppSuggestedLoadoutView    5
UiCppChallengesView          5
UiCppNewItems                4

```

★★ **`UiCppMainMenu` 零条。** 这不是漏检（正则已覆盖全部 `UiCpp[A-Za-z]+`），是**它确实没有在 `::Init` 里注册局域类 handler**。

### 5.4 那主菜单的交互怎么走？

查 816 短名表里含 `Menu` 的 10 个：

```
AS_GetZHuntHelpMenuInfo      AS_GetZHuntPauseMenuInfo   AS_SpyMode_GetPauseMenuTips
AS_ToggleLoadoutMenu         AssignUIKeyCatcherToDotMenu  DropDownMenuItemSelected
AS_MainMenuWillReload        AS_RequestRaisePauseMenu   AS_ScriptMenuResponse
AS_ScriptMenuResponseReady
```

★★ **没有一个是"主菜单按钮"** —— 全是**子菜单/弹窗/暂停菜单**。

★ **`MainMenuWillReload`（`0x68EC20`）是唯一与主菜单相关的**，且它是**事件（被通知）**，不是**动作（被点击）**。

★★ **⇒ 正确表述：`UiCppMainMenu` 是一个"只监听、不暴露接口"的 View。** 它的按钮回调走 **Flash 内部 ActionScript**，不经过 AS_ 原生接口面。

★ 这**更正 132 §八·补 的隐含推断**：我当时写"主菜单走另一条（未闭合的批量注册器）"——**错。主菜单不走任何注册路径，因为它不注册任何原生接口。**

## §六 对本项目工程的实际结论

1. **829 个接口 = 整个 Flash↔C++ 面，已 100% 闭合**，无遗漏、无第二个注册机制。
2. **`UiCppMainMenu` 不需要服务端配合** —— 主菜单是纯 Flash 侧视图。
3. **`AS_MainMenuWillReload`（`0x68EC20`）= 主菜单刷新事件**：如果服务端改了 playlist/商城/公告，客户端靠它触发重载。**这是"改服务端数据后如何让 UI 生效"的关键钩子。**
4. **838 个注册器中有 2 类形态**（启动即注册 / 惰性一次性守卫），说明部分模块支持**热重载**。
