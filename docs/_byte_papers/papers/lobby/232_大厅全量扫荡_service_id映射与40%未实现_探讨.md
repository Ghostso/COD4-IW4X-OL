## 一、七次解析，六次错

要找「客户端发 service=71 task=7 时，代码在哪」，我写的解析器连续失败了六版：

| 版本 | 做法 | 错在哪 |
|---|---|---|
| v1 | 从 `hit-0x40` 起向后解，收集 push imm | 窗口跨过了函数边界，解出一堆 `sal byte ptr [edx+ecx-0x7d], 0xc0` 这种垃圾 |
| v2 | 从函数入口（扫 `CC CC`）正向解，状态机记 pending push | 分组把相距 0x1000+ 的多个调用点并进一个"函数"，状态机丢状态 |
| v3 | 从 call 处向前找可解码起点 | 遇到第一个 `CC` 就 break，跳过了真正的起点 |
| v4 | 固定窗口，取「最后两个 imm8」 | 取到 `push 0x2C`（分配大小）当 svc |
| v5 | 反向取最近两个 imm8 push | 同上，`push 0x2C` 污染 |
| v6 | 匹配 `push/lea/push/push` 四连 | 只成功 9 个 |
| **v7** | **同上 + 修 `int(x,16)` → `int(x,0)`** | **成功 33/37** |

### v7 的 bug 有多蠢

```python
# v6（错）
if ins.op_str.startswith("0x"):
    v = int(ins.op_str, 16)
```

capstone 对 `push 0x66` 输出 `"0x66"`，但对 `push 5` 输出 **`"5"`（十进制，无前缀）**。于是 `push 5`（task=5）、`push 9`、`push 2` 全部被跳过。

**6/5 这个最常见的 task 就是因为 `5` 没前缀而漏掉的。**

改成：
```python
v = int(ins.op_str, 0)   # 让 int() 自己判断 0x 前缀
```

★ **这一条和 231 卷的"绝对地址必须按编码前缀解码"是同一类错误：把"格式假设"当成了"事实"。** 231 卷我假设 `find(u32)` 命中点前面就是指令起点；本篇我假设 capstone 的立即数一定带 `0x`。**两次都是"没去验证工具的输出格式"。**

## 二、为什么「参数顺序」必须靠语料验证

`0xB78C10` 反汇编出来是清楚的：

```
0xB78C1F  call 0xB75E00   ; writeN(*holder, &[ebp+0xC], 1)
0xB78C2A  call 0xB76620   ; u8(*holder, [ebp+0x10])
```

读完这两条，我知道**先写 `[ebp+0xC]`、后写 `[ebp+0x10]`**。但协议头的实际字节顺序是 `[len][AB][svc][task]...`，所以先写的是 svc。

**这里有一个我没法从这段代码排除的可能**：也许 `[ebp+0xC]` 是 task、`[ebp+0x10]` 是 svc，而协议头是 `[task][svc]` 顺序——毕竟我从没直接读过一个完整的 `0x85` 帧头。

**唯一能排除的办法**：拿 15 个 (svc,task) 去对语料。结果：

- 读成 `(svc=[ebp+0xC], task=[ebp+0x10])` ⇒ **15/15 命中**
- 读成 `(svc=[ebp+0x10], task=[ebp+0xC])` ⇒ **0/15 命中**

★ **这不是"更可能"，这是"唯一可能"。** 15 个独立样本全错的概率可以忽略。

**方法论**：**反汇编给出"可能是"，语料交叉给出"是"。** 单靠任何一边都不够。

## 三、我差点再次接受「已穷尽」这个说法

224/225 卷写着：

> 「其余服务名（3/4/9/12/28/29/68/93）**未在客户端内找到"数字 id→名字"映射**（已穷尽，见 225 卷 §4）」

**"已穷尽"三个字让我差点不去碰它。** 但我这次做了一件不同的事：**不问"名字在哪"，问"客户端在哪写这个数字"。**

一换问法，`0xB78C10` 就在那儿，37 个调用点，一目了然。

### 这次学到的

| 旧问法 | 新问法 | 结果 |
|---|---|---|
| 「service id → 名字」映射表在哪？ | 客户端在哪**写**这个 id？ | `0xB78C10`，33/37 解析成功 |
| 名字表 `0xE4E8F8` 怎么绑 id？ | 名字表**被谁消费**？ | `0x7EEF2C` 配置循环，根本不碰 id |
| 语料里没出现 ⇒ 客户端不发？ | 代码里**有没有**它的构造点？ | 服务 58 整片存在 |

★ **"已穷尽"只在「问法不变」的前提下成立。问法一换，「已穷尽」就作废。** 这和记忆里 `codol-room-open-7-after-fullscan-167`（「文件名含房间」的扫描漏一半）是同一个病。

## 四、「零引用」作为正面证据

这次有一个不太常见的推理：**用"零引用"证明"不可能是映射源"**。

```
marketplace   0xDE0BDC   表外代码引用 = 0
matchmaking   0xDE0BD0   表外代码引用 = 0
profiles      0xDE0BA8   表外代码引用 = 0
...（共 13/20 个为 0）
```

如果这张表是 id→名字映射，那**必然**有代码拿 id 索引它、然后拿返回的名字去比对或上报。但表基址 `0xE4E8F8` 只有**一个**代码引用（`0x7EEF2C`），而这个引用只取 `[ebx*8+0xE4E8F8]`（name 指针），从不碰 `+4` 的 `enabled`。

**⇒ 表是自足的打印/配置数据，与协议 id 无因果关系。**

★ **方法论：「零引用」通常是负面结论，但当你要否证某个对象是"某机制的来源"时，零引用是最强的正面证据。** 前提是：扫描必须覆盖 disp8/disp32/`mov reg,imm`/`push imm` 全部寻址形态（231 卷的教训）。

## 五、40.4% 这个数字该怎么读

我算出 2767/6848 = 40.4% 走 UNMAPPED。

**但这个数字有个陷阱**：它是按**条数**算的，而条数被 `71/7`(355)、`71/3`(328)、`4/13`(290) 三条高频轮询拉高了。按**任务种类**算，是 24/55 = 43.6% —— 巧合地接近，但性质不同。

更重要的是：**40.4% 不等于"40.4% 的功能坏了"。**

- 有的 task 是纯查询，空 ACK 客户端能容忍（如 `12/6` payload 只有 1 字节 `00`）；
- 有的 task 是状态机驱动，空 ACK 会像商城一样死锁（231 卷）；
- 有的 task 是遥测上报，写失败了客户端也不管。

**⇒ 正确的下一步不是"把 40.4% 全填上"，而是「逐 svc 找空 ACK 的后果判据」。** 这是 §6 边界 4 的内容。
