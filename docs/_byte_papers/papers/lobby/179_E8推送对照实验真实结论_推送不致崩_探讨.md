# 179 探讨 · "房间类永远有致命黑箱"——这句话我原来以为是在施压，现在觉得是事实描述

## 一、先给结论

这轮我拿到了房间里第一个**行为级证据**（不是静态推断）：

> `ONCE_20261029_161336` 连推 3 次 `dwRoomMessageReady`，客户端**没有崩**，之后继续正常收发 2.5 分钟。

同时：

> `ONCE_20261029_162109` **没有**推 ready，却在 6 分钟后收到 `10054`。

**推送不是崩溃原因。** 这条我原来不敢说，现在敢了。

## 二、但这条证据同时也证明了另一件事

它证明了**我根本不知道那次推送有没有被读到。**

客户端没崩，有两种可能：

- **A**：它读到了，认为这是一条格式不对的 ready，静默丢弃
- **B**：它根本没读到，消息在更外层就被拦下了

**这两种在日志里长得一模一样。**

要区分，必须做 A/B 对照：
- A 组：推格式正确的
- B 组：推格式错的（或者不推）
- 如果两组行为相同 ⇒ 说明根本没被读取

而这件事我**一次都没做成**：

| 组 | 状态 |
|---|---|
| `kit_E8_OK_20261029` | 目录里 `lobby_srv.log` 只有 5 行 —— **从未运行** |
| `kit_E8_BAD_20261029` | 同上 —— **从未运行** |
| `ONCE_20261029_160922` | 想发 OK，但 `ModuleNotFoundError: room_push_encoder` → **实际没发** |
| `ONCE_20261029_161336` | **真发了 3 次**，但没有配对的 BAD 组 |

**A/B 对照从未成立。**

## 三、为什么"房间类永远有致命黑箱"是对的

我先前把这句话理解成"你要求我承认做不到"。现在我觉得它是在陈述一个结构事实：

**房间动作的每一个判断，都需要"客户端收到 X 之后做了什么"这个信息。**
**而这个信息静态逆向原理上给不出来。**

具体到三层：

| 层 | 静态能给 | 静态给不出 |
|---|---|---|
| 结构（字段/位宽/标签） | ✅ 能给 | — |
| 调用链（谁调谁） | ✅ 能给 | — |
| 闸门位置 | ✅ 能给 | — |
| **客户端反应** | ❌ | 需要实机 |
| **格式对不对** | ❌ | 需要真实样本 |
| **闸门开没开** | ❌ | 需要运行时状态 |

前三条我已经做到地址级。后三条**不是我不努力，是类别不同**。

## 四、这轮踩到的坑值得单独说

我一开始看到日志里：

```
★ E8-OK 推送 dwRoomMessageReady (5 字节 body=10 08 40 00 00)
```

**第一反应是"终于有真实样本了"。**

拿它去套两个模型：

- 位宽模型（3+8+1+1）→ type 应该是 0x10，实测 0x80 ✗
- 5 位标签模型（5+8+5+1）→ tag 应该是 3，实测 2 ✗

**两个都错。** 正常人的下一步是"都不对，找第三个模型"。

我停下来查了这 5 个字节是谁生成的，结果是：

```python
# kit_E8_OK_20261029/lobby_server.py
def frame_room_message(msg_type, fields, subtype=0):
    w.write(msg_type, 8)   # 8 位
    w.write(subtype, 3)    # 3 位
    for value, tag in fields:
        w.write(value, 8)
        w.write(tag, 3)
```

**是服务端自己造的第三个模型。** 而且这个模型也是错的。

★★ 如果我没查来源，我会用这个假样本去"校准"出一个第四、第五个错误模型，而且会以为它有实机支撑。

**"日志里有字节" ≠ "客户端发/收过这些字节"。** 这条要刻在脑子里。

## 五、顺手查出的另一件事：位序

这轮还从 `0xB777C0` 的掩码生成式推翻了 177 卷的 MSB-first：

```asm
dl = (0xFF << (k+off)) | (0xFF >> (8-off))
   = (0xFF << 5) | (0xFF >> 8)      [off=0, k=5]
   = 0xE0 | 0x00 = 0xE0
```

`0xE0` 保留 bit5-7 ⇒ 数据在 bit0-4 ⇒ **LSB-first**。

**移位方向 ≠ 位序，掩码才是。** 177 卷只看了 `shl` 就判 MSB，错了。

这条同样没有实机样本验证，但它是算术推出来的，比 177 的"看方向"硬。

## 六、现在的账

房间类：

| 项 | 状态 |
|---|---|
| 43 类写侧 / 线格式 | ✅ 静态闭合 |
| `srpc+0x4F4` = HMAC 会话 | ✅ 静态闭合 |
| 状态机 5 路输出 | ✅ 静态闭合 |
| Manifold 5 位标签 + LSB-first | ✅ 静态闭合（无样本） |
| 推送不会导致崩溃 | ✅ **本轮首个行为级结论** |
| **推送是否被客户端解析** | ❌ **需要 A/B 实机** |
| **格式对不对** | ❌ **需要真实样本** |
| **闸门开没开** | ❌ **需要运行时** |

**用户的判断是对的：这三条不解决，房间类就永远有致命黑箱。**

而且它们不是同一类问题 —— 前两个需要**一次设计良好的 A/B 实机实验**，第三个需要**内存/状态读取**。

## 七、下一轮如果继续

我会先做一件不依赖实机的事：**把 `dwRoomMessageStartGame`（109 B）也查一遍来源**。

因为 `162109` 那轮的 `10054` 出现在 `mmstart → StartGame(109B)` 之后。如果那个 109 B 也是自造常量，那 `162109` 的崩溃很可能就是它造成的 —— 这会成为**第二个**"推送导致崩溃"的候选，而且这次有对照（`161336` 也推了 109B？要核）。

★ 这是纯静态能做的下一步，不需要实机。
