## 一、最刺眼的一条

`run_frozen_chain_once.py` 里并排写着两行：

```python
DEFAULT_KIT    = ROOT / "CODOL_VERIFIED_GOLDEN_20261019"   # 跑这个
PROTECTED_ROOT = ROOT / "REF_LOBBY_KIT"                    # 校验这个
```

`verify_protected_baseline()` 认认真真地比对 `REF_LOBBY_KIT` 的 6 个 launch_core 文件、
逐字节核对 sha256、连两个零字节 flag 文件都不放过 —— 而且它**一直是绿的**。

但它证明的只有一件事：**一套 10-07 的旧快照没人动过。**

真正跑起来的那套（golden，10-27）里，`lobby_server.py` 差了 11.7 KB、`nt10.py` 差了 882 B、
`battle_server.py` 差了 1.2 KB。**没有任何检查覆盖它们。**

这不是"检查写错了"——`verify_protected_baseline()` 完全按设计工作。错的是**设计假设**：
它假设"受保护的那套"就是"要跑的那套"。这个假设曾经成立，后来 `DEFAULT_KIT` 被改成 golden 时，
**没有任何东西会因此报错。**

### 教训

**一堵很严的墙，如果立错了地方，只会让人更安心。**

配套的操作规则：**给完整性检查加一条会失败的断言 —— 「校验对象 == 执行对象」。**
一行 `assert DEFAULT_KIT == PROTECTED_ROOT`（或显式的路径映射表），就能让这次脱钩在发生的那一天就报警。

## 二、`if is_file()` 是最安静的失败模式

`CORE` 白名单第 58 行明明白白写着 `market_skus.py`。复制循环是：

```python
for n in CORE:
    if (kit / n).is_file():
        shutil.copy2(kit / n, work / n)
```

golden 里没有这个文件 ⇒ **跳过，无日志，无警告。**

后果不是崩溃，而是：

```python
try:    import market_skus
except: market_skus = None      # ← 商城目录回空页
```

**程序照常启动、照常进大厅、照常连 IW4X，只是商城永远是空的。**

这与 231 卷写下的那句一模一样：
> 「服务端刻意回空页正是商城/仓库全空的根因」

——我们花了很大力气去解"服务端为什么回空页"（`reply+5` 判据、`state=2` 写点、重试环），
**而运行链上的真实原因是一行 `import` 失败。**

### 教训

**白名单 + `is_file()` 是"缺了就当没有"的语义，而缺文件通常是"根本没打算有"。**
两者必须能区分。具体做法：
- 复制循环对**必需文件**用 `if not (kit/n).is_file(): raise`；
- 对**可选文件**记一行日志（`SKIP n: not in kit`）；
- 启动后**主动断言**关键模块 `is not None`，而不是让 `except` 把降级吞掉。

`except: X = None` 这种写法在本项目里出现多次（`market_skus`、`ms`、`marketplace_store`），
它们每一个都是一个**静默降级点**。**降级必须留痕。**

## 三、我给 agent 的提示，制造了这次血缘分裂

我给两个修复 agent 的提示里，这两句挨得太近：

> 「受保护资产只读：`REF_LOBBY_KIT\run_all.py` / `nt10.py` / `lobby_server.py` …」
> 「所有改动只能落在你新建的 run 目录…**先把要改的 kit 复制进去，再改副本**」

结果：
- **房间修复** agent 选了 **MRKFIX kit**（血统 B）→ R20/R21 落在 B 上；
- **大厅修复** agent 选了 **`REF_LOBBY_KIT`**（血统 A）→ PVE 37 条与 SKU 19 字段落在 A 上。

两条改动**无法直接拼接** —— B 比 A 多了三周的修复，A 的改动得重新打到 B 上。

**这不是 agent 判断失误**：提示里确实没有一个"唯一复制源"的句子。

### 教训

**并行分线时，"唯一复制源"必须是一句显式的、写死的路径，不能靠 agent 从上下文里挑。**

正确写法应该是：

> 「复制源**唯一且固定**为 `run_codol_001\runs\ROOMFIX_20261103_1239\kit\`（血统 B 顶，已含 R20/R21）。`REF_LOBBY_KIT` **只是校验基准，不是复制源**。」

——把"哪个是源、哪个是基准"写成两行并列的硬事实，而不是让它们在同一段话里争夺解释权。

## 四、我把 D 盘写爆了

第一次尝试"全量备份两个受保护目录"，写到 31273 个文件时报 `[Errno 28] No space left on device`。

一查：`REF_LOBBY_KIT` = **178,162 文件 / 128 GB**，其中：
- `mem_linear_20261007_134406` = 40.9 GB
- `mem_marketplace` = 14.0 GB
- 后面还有一排 4–6 GB 的 `mem_linear_entryfix_*`

**它不是"链"，是内存 dump 归档。** 我当时脑子里把"受保护资产"和"启动链"画了等号，
于是 `shutil.copytree` 一个 128 GB 的目录。

处置：删掉我自己几分钟前建的半成品备份（22.35 GB），D 盘恢复 22.36 GB。

**代价**：我唯一的全量备份机会没了 —— 现在只能"只镜像 launch_core 那十来个文件"。

### 教训

**备份前先量体积，尤其是"受保护"这种听起来很轻的词。**
一条 `Measure-Object -Sum` 只要 3 秒；一次写爆磁盘要花掉一个更重要的机会。

**而且：`REF_LOBBY_KIT` 这个名字本身在骗人** —— 叫 "KIT"，实际 99.96% 是 dump。
命名与内容不符，是这次误判的起点。

## 五、这次整合真正做成的事

一句话：**把"分散在四条血缘上的、各自验证过的修复"合并成一条可以跑的链，并第一次发现它此前根本不可运行。**

在整合之前，如果有人直接跑链：
- 用 golden ⇒ 商城**必然空页**（缺 `market_skus.py`）
- 用 MRKFIX/ROOMFIX ⇒ 直接 `SystemExit`（**缺 5 个数据目录**）
- 用 LOBBYFIX ⇒ 同上
- 用 REF ⇒ 商城回退（`market_skus` 为 21 字段旧版）+ 无任何 10-27 之后的修复

**⇒ 四条候选，没有一条是可运行的。** 而所有 agent 的报告都是"验证 ALL PASS" ——
因为它们各自验证的是**自己那一小块**。

**"局部 ALL PASS" 与 "整链可运行" 之间，缺的正好是这次整合。**
