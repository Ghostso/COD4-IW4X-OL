# 探讨：小服务 3/4/6/8/9/12/28/29/68/93 定案

> 与 224 卷配套的过程记录。

## 一、为什么能"一次解 10 个服务"

一开始以为每个服务要单独逆。后来发现：**它们全都用同一套 Demonware 值流读取器**（223/225 卷 §2 的 11 个函数）。于是策略变了——先把"类型表"钉死，再写一个通用解析器，把 7645 条 payload 一次性全部解出来。结果是：除了被日志截断的（blob-overflow / str-noterm），其余 **100% 可解**。

这带来一个反直觉的结论：**服务级差异只在"字段序 + 取值域"，不在编码**。所以 §224 的核心是"结构表"，而不是"每个服务的协议"。

## 二、踩过的坑

1. **`10 00` 到底是"空字符串"还是"两个字节的别的字段"**：纠结了很久。最后确认 = `tag 0x10 + NUL`（空串）。判据：`3/46` 里 `10 00` 出现两次，且整体能被"str/u64/str/u32/u32"不剩字节地吃掉。
2. **payload 尾部那个孤零零的 `00`**：是**终止符**（tag 0x00），不是空字符串。`3/53` 以 `10 00 00` 结尾 = 空串 + 终止；`71/10` 整条就是 `00` = 只有终止。
3. **`declared = payload + 3` 的 3 是什么**：一开始算不平（4 字节头却差 3）。看清帧 = `[len][0x86][svc][ver][task]` 后明白了：`declared` 从 `service` 起算，**不含 `0x86`**，也不含长度本身 = `svc+ver+task=3`。

## 三、服务 28 的数组：`6c` 是怎么定的

`28/4` 一条 105 次全同、96B 被截。头是 `6c 08 fc 01 00 00 7f 00 00 00 …`。
- 若按 u32array：`6c 08 <byteLen=0x1FC=508> <count=0x7F=127> <values>`；
- **508 = 127 × 4** 自洽；值是 0,1,2,3,9,10,12,…（playlist id 域）。
不需要任何样本外信息，**byteLen=count×4** 就是它的自证明。这也顺带说明 `28/*` 是"清单/参数"类（与 160 卷 remark 的"28/1 在 mmstart 前到达、带关卡线索"吻合）。

## 四、服务名：为什么我拒绝"猜名字"

有 19 个候选名（`reward/friends/group/mail/tags/teams/titleutilities/eventlog/pooledstorage/stats/…`）。`68/3` 看着像 friends、`3/xx` 看着像 stats、`12/6` 像 pooledstorage——**但全是"像"**。

我去找"数字 id ↔ 名字"的硬表：
- 名字指针旁有没有 id？两种邻接序，0 命中；
- 有没有一个"注册"表把 (id,name) 配对？只找到 `0xE4E8F8` 那张 `{ptr, enabled}`，与配置文件逐位吻合 ⇒ **那是配置，不是协议**。

既然拿不到硬表，就**只写结构、不写名字**，把三个猜测显式标成"候选（勿当结论）"。这与 AGENTS.md 的"结论须可核验"一致：结构可核验，名字不可。

## 五、还开着的口

1. **3/4/9/12/28/29/68 的名字**：需要"客户端注册服务"的那张表（也许在 `dwall`/`bdService` 初始化里，用名字注册并分配 id）。下一步可以搜"按字符串名注册服务"的初始化函数。
2. **4/13 的 u32 id 域**（932/100/108/113/118/123/135/148）：像 item/sku/邮件 id，但缺一个对照表，暂不定名。
3. **68/3 的 u8（1/2）**：看着像 public/private 或版本号，未定。
