## 一、129 卷那个 case 归属，我是怎么错的

129 卷我写：

> 跳转表 @`0x5D3C6C`：case0→`0x5D3A1F`，case1→`0x5D3AD1`，case2→`0x5D3B11`，case3→`0x5D3B4B`。
> Case 3 called `0x6411E0` (UIPage at `0x5D3B07`)；cases 0/1 called `0x641180`.

这句话里**每一块都是真的，拼起来是错的**。

`0x5D3B07` 确实调 `0x6411E0`，但 `0x5D3B07` **不在 case 3 里**。case 3 的体从 `0x5D3B4B` 开始，而 `0x5D3B07 < 0x5D3B4B`。

### 1.1 我当时怎么想的

我按**跳转表顺序**读：表里第 4 项 → 我以为是第 4 个 case 的体 → 我看到 `0x5D3B4B` 后面还有代码 → 我以为 `0x5D3B07` 属于它。

**跳转表只是给出四个入口地址，它不告诉你每个体的结束在哪**。体与体之间是**代码顺序**，不是表顺序。

### 1.2 本卷的做法

我改用**反推**：不问「case 3 里有什么」，问「`0x6411E0` 被谁调用」。

```
callsite_finder 0x6411E0 → 0x1D3B07   （唯一）
callsite_finder 0x641180 → 0x1D3AB1, 0x1D3AC4   （两个）
callsite_finder 0x641340 → 0x1D3B34   （唯一）
```

然后只做一件事：**这三个地址分别落在哪个跳转目标之后、下一个目标之前**：

- `0x1D3AB1`、`0x1D3AC4` ∈ `[0x1D3A1F, 0x1D3AD1)` ⇒ **case 0**
- `0x1D3B07` ∈ `[0x1D3AD1, 0x1D3B11)` ⇒ **case 1**
- `0x1D3B34` ∈ `[0x1D3B11, 0x1D3B4B)` ⇒ **case 2**

★★ **⇒ 从"调用目标"反推"谁在分支里"，比从"分支入口"正推可靠。** 因为反推只需要「调用点落在哪个区间」，这是一个不需要理解语义的机械判断；正推需要我猜"体到哪结束"。

### 1.3 教训

**跳转表给出的是"入口集合"，不是"区间的定义"。** 四个入口排序后，区间边界才是体边界 —— 但**只有当体在内存里按入口地址顺序排列时**才成立。这次成立，所以反推结果干净。

★ 如果体不是顺序排列呢？那反推依然成立，正推依然不成立。**⇒ 反推在两种布局下都对。**

## 二、页名：我把「找不到」升级成了「不存在」

这是本卷最重要的判断。

124 卷记了：UIPage 505 次、页号 28 种、2..154。129 卷记了：「页号→页名 未闭合」。

**我的默认假设是：页名一定在某张表里，只是我还没找到那张表。**

### 2.1 我先做了穷举，而不是继续找

我写了 `page_table_hunt.py`：扫全镜像，找**任何** `[u32 id][u32 ptr→ASCII]` 或 `[u32 ptr→ASCII][u32 id]` 的连续 ≥8 项。

结果是 **12 段，全部与 UI 无关**。

### 2.2 穷举之后，我才敢说"不存在"

★★ **「没找到」和「穷举后没有」是两个不同强度的结论。** 前者是搜索失败，后者是判据覆盖。

但**穷举有效的前提是判据正确**。如果页名表不是 `{id,name}` 形态（比如是两个平行数组 `[ids...]`、`[names...]`），我这个判据就漏了。

### 2.3 所以我还要第二条证据

第二条证据在代码里：**页号是 `get(0)` 从运行时对象读的，不是编译期常量**。

```
0x5D3ADC  lea esi,[esp+0x20]   ; 出参
0x5D3AE3  call edx             ; get(this, 0, out)
0x5D3AFB  mov esi,[esp+0x30]   ; 页号 = 写回 out 的值
```

★★ **⇒ 页号是一个 UI 属性值，它在编译期根本不存在。** 那"页号→页名"这张表在编译期也不可能存在 —— **不是我没找到，是它不会以那个形态存在于 EXE 里。**

### 2.4 诚实边界

页名**可能**存在于 `.ifs` 资产或服务端 playlist。**这两者都不在当前可读面内。** 所以我的结论是：

> 在**当前可读面（客户端 EXE 静态数据 + 明文协议）**内，不存在页号→页名的映射。

我**不写**「页名不存在」—— 那是过强的。我写的是**在什么面内不存在**。

★ 这与 `8/3` 32 KB 字段映射边界是**同一条**：字段语义在结构体里，名字在别处。

## 三、`0xDAE091`：我**自己**造出来的第三个"假阳性"

这一节是本卷最值得写的部分，因为**我先写错，再推翻了自己**。

### 3.1 第一版我怎么想的

`rawdump.py` 读出 `cstr(0x9AE091) == b''`。我立刻联想前两卷的教训：
- 124 卷 `wfUD3"` —— ASCII 正则误捕魔数 C；
- 126 卷 3 字母标识符族 —— 正则误捕二进制。

**⇒ 我把 `b''` 归进了"同一族假阳性"，写成「它指向数据中部，不是字符串，列入防火墙」。**

### 3.2 为什么这个判断是错的

`cstr` 返回 `b''` 的**唯一**直接原因是 `d[0x9AE091] == 0`。

而 `0x9AE090..0x9AE093` 是**连续四个零字节**。所以从 `0x9AE091` 开始，**读什么都是空串** —— 这是**合法的空 C 字符串**，不是错位。

### 3.3 推翻它的证据（不在字节里，在调用方）

我去看谁 push 它：

```
0x77ECD7  ClientLogin        push 0 / push 0xdae091 / push 0 / push 0 / push 1
0x5E34FD  fn 0x1E3400        push 0 / push 0xdae091 / push 0 / push eax / push 4
0x6BBEBC  fn 0x2BBD70        push 0 / push 0xdae091 / push 0 / push edi / push 4
0x612601  fn 0x2122D0        push 0 / push 0xdae091 / push eax / push esi / push 0xe
```

★★ **四处都是"没有字符串可报"的位置** —— 同伴参数全是 0。**这就是空字符串哨兵的用法。**

### 3.4 我这次犯的错，类型比前两次更隐蔽

| 卷 | 错在哪 | 检测手段 |
|---|---|---|
| 124 | 把二进制当文本（正则误捕） | 按字节串全库对账 |
| 126 | 同上（3 字母标识符） | 同上 |
| **130（第一版）** | **把合法空串判成错位** | **必须有调用方证据** |

★★ **⇒ 前两次的错是"读错了字节"；这次的错是"读对了字节，读错了含义"。** 字节层面完全正确（`b''` 是真的），错在**把"空"当成了"没有"**。

### 3.5 正确的规则

> **`cstr` 读出 `b''` 有两种可能：①地址处是 NUL（合法空串）；②地址错位/越界。**
> **区分它们不能靠读字节（两种情况下读出来都是空），只能靠"谁在用它"。**

★ 这条规则和前两卷的「假阳性防火墙」**不是同一条**。我在第一版里把它们合并了 —— **那是过度概括**：前两次防的是"字节误捕"，这一次防的是"空值误判"，方向正好相反。

★ 这也解释了为什么我第一版的"新防火墙规则"（读 4 字节看是否落记录中部）**是错的建议**：`0xDAE091` 确实"落在名字池的零串里"，但**这不影响它是合法的空串**。位置分析在这里是**误导**，调用方分析才是答案。

## 四、我以为挖到"第五个遥测入口"，其实是我自己的猜测

这是本卷第二个"我先说错、再撤回"的地方。

### 4.1 猜测是怎么来的

查 `0x477910` 的调用点，看见它被 **`ClientLogin` / `ClientDisconnect` / `MatchMakingJoin`** 这几个遥测事件的日志函数调用。

★★ **⇒ 我的第一反应："这是第二套遥测入队入口！129 卷的'四入口'其实是五入口。"**

这个猜测很顺：调用方全是遥测日志函数，函数体又是个大函数，看起来完全像。

### 4.2 我核对了一个能让猜测成立或作废的条件

问题只有一个：**它体内到底调不调那四个入口？**

我把 rel32 扫描写对（`next_insn + rel32 == target`，而不是拿 `E8` 后面跟绝对地址去搜），然后统计：

```
0x640190 : 7 处     0x6404B0 : 56 处     0x640FD0 : 2 处     0x63FC60 : 7 处
落在 [0x477910, 0x4784C4) 内的： 全部 NONE
```

★★ **⇒ 它一个都不调。猜测当场死。**

### 4.3 顺带得到两个副产品

1. **这段扫描独立复现了 129 卷的 7/56/2/7** —— 129 的"四入口"模型**得到交叉验证**，不是我又"发现"了什么。
2. **`0x477910` 的真面目**：`f(flag, v1, v2, str, str)`，10 个调用点，flag 值 `{1,4,0x0E,0x10,0x12,0x13,0x17}`。

### 4.4 这次教训与第一次相反

- `0xDAE091` 那次：**我读字节读对了，含义读错了**；
- 这次：**我连字节都没读**，只在"调用方像遥测"上做了推断。

★★ **⇒ "谁调它"是必要线索，但绝不是充分证据。** 遥测日志函数调用一个函数，只能说明"两者在同一个业务流程里"，**不能说明"这个函数就是入队口"**。

### 4.5 一个写代码时差点埋下的 bug

我第一次写扫描脚本时用的是：

```python
d.find(b'\xe8' + struct.pack('<I', target))
```

**这是错的**：`E8` 后面跟的是 **rel32 位移**，不是绝对地址。它一个都没命中，`total=0`。

★ 如果我当时没发现"总数怎么会是 0"，直接拿 `total=0` 当"没有调用点"，我就会得出**完全相反的结论**。

★★ **⇒ "总数=0" 是最该怀疑的数字。** 一个本来应该有 7 个调用点的目标报 0，先怀疑自己的扫描，不是先下结论。

## 五、「绝对立即数 0 引用 ⇒ 数据是死的」——这条推理在本镜像被证伪

我本来想用一条很漂亮的推理：

> 枚举表 `0xA4E9A0` 没有任何代码用绝对立即数引用它 ⇒ 它是死数据。

**我做了个对照**：拿**已知是活的**服务开关表 `0xA4E8F8` 去扫 —— **0 次引用**。

★★ **⇒ 判据被自己的对照打死了。**

### 5.1 为什么

这些表**不是**通过 `mov eax, 0xA4E8F8` 访问的。它们通过：
- 别的结构里的**指针成员**；
- **运行时计算的基址**（`lea eax, [base + constant]` 里 base 本身是运行时的）。

### 5.2 但同一条判据在别处是对的

UIPage 的 5 槽环 `0x76456FC`：扫出来 4 个引用，**全在 `0x2411E0..0x2412F2` 之间**。这个结论是可信的，因为目标被**直接寻址**。

★★ **⇒ 判据的有效性依赖目标是否被直接寻址 —— 不能一刀切。**

### 5.3 教训

**每一条"0 命中 ⇒ 不存在"的判据，都必须拿一个"已知为真"的对照跑一遍。** 对照要是 0，判据当场作废。

这一条跟 126 卷的「假阳性防火墙」是同一族：**任何检测方法都要先证明它能检出真阳。**

## 六、`UIInitialGameMode` 的载荷，是"邻居串"给的

`0x641420` 调用点全在 `0x2B0230`，函数里压了 `'un_sp_onboard'` / `'un_mp_onboard'` / `'un_zm_onboard'`。

★★ **⇒ `UIInitialGameMode` 载荷 = 新手引导所属模式（sp/mp/zm）。**

这里的关键是：**载荷语义不是从模板读出来的**（模板 `…|%d` 只有个位域），是**从这个函数里其它串推出来的**。

★ 这属于 122 卷「dvar 语义名只到邻居+值域推断级」的同一类：**邻居串定语义，值域定范围，两者交叉才敢挂名。**

但 **我不能说 "载荷就是这个串"** —— 模板是 `%d`，压进去的**是 int**，而 `un_*_onboard` 是字符串。**⇒ 串是"分支选择的依据"，int 是"映射后的模式号"（0/1/2）。** 我写的是载荷语义，不是载荷字节。

★★ **这是本卷第二个"差一步就写错"的地方**：如果我为了"语义闭合"直接写「载荷 = `un_sp_onboard`」，那就是把**控制流依据**写成**数据**。这跟 124 卷 `CreateRoom` 是 TLog 打点不是真建房，是同一类错误。

## 七、我差点以"纠正 116 卷"的名义，把自己的一段记忆偏差写成论文

写 §6 时我脑子里想的是：「116 卷把顺序写反了，我要更正它」。

**我先去读了 116 卷原文，才发现它写的是 `[ptr→服务名][flag]` —— 完全正确。** 读反的是**我自己**（我在别处把它转述成了 `[name_ptr][enabled]`）。

★★ **⇒ 如果没有"先查原文再动笔"这一步，我会以"更正"的名义在论文里造一个 116 卷并不存在的错误。** 这比单纯记错危险得多：**记错会被自己将来纠正，而"论文里写了别人错了"会把错固化成档案。**

### 7.1 一个仍然要保留的技术判据

我确实在复核时踩过"按 `[flag][ptr]` 读"的岔路：那样读时 flag 全是 `0x00DE0xxx`（前一项的指针高位），下一个 ptr 全为 0。

★ **判别方法**：`[ptr][flag]` 读法下 flag 只有 `{0,1}`；`[flag][ptr]` 读法下"flag"全是 `0xDE0xxx` 形态 —— **值域本身就是判据**。

★★ **多字段记录，"对齐成功"不等于"顺序正确"。要在两种顺序下都读，看哪种的值域合理。** 这条判据是真实的、可迁移的；只是它这次用来**确认** 116 卷，不是用来推翻它。

★ 启用 5 个 = `matchmaking/messaging/profiles/storage/stats`，独立复核了 116 卷三链交汇里 messaging 的那一环 —— **本卷是加固 116，不是更正它。**

### 7.2 新增一条流程规则

> **凡是要写"某卷错了"，先打开那一卷的原文，逐字确认它到底写了什么。** 记忆里的转述不是证据。

## 八、方法论（可迁移）

1. **跳转表给的是"入口集合"，不是"区间"。** 分派归属要从**调用目标反推**，不要从**分支入口正推**。
2. **「穷举后没有」≠「没找到」；但穷举前要先写清判据。** 结论要挂在"在 X 判据 + Y 面内"，不挂在绝对。
3. **`cstr` 读出 `b''` 有两种可能，读字节分不开。** 合法空串 vs 地址错位 —— **只能看调用方**。我曾把 `0xDAE091`（合法空串哨兵）判成"指向数据中部"，方向反了。
3b. **"谁调用它"是必要线索，不是充分证据。** 遥测日志函数调用某函数，只说明同一业务流程。`0x477910` 就是这样被我误判成"第五入口"，直到确认它体内 **0 处**调四入口才撤回。
3c. **扫描结果为 0 时，先怀疑扫描本身。** rel32 必须按 `next_insn + rel32 == target` 判，拿 `E8 + 绝对地址` 去搜会静默返回 0。
4. **每条"0 命中 ⇒ 不存在"的判据，拿一个已知为真的对照跑一遍。** 对照为 0 ⇒ 判据作废（本卷 `0xA4E8F8` 就是这样打死"绝对立即数引用"判据的）。
5. **判据有效性与目标的寻址方式相关，不能一刀切。** 直接寻址的目标可以用绝对立即数扫描；表基址不行。
6. **多字段记录要在两种顺序下都读，看值域。** 本次 `{0,1}` vs `{0xDE0xxx}`。
7. **载荷语义可以从邻居串推，但不能把"控制流依据"写成"载荷数据"。** `un_*_onboard` 是分支依据，`%d` 是模式号。
8. **凡是要写"某卷错了"，先打开那一卷的原文逐字确认。** 本卷差点把 116 卷的正确记录当成错误来"更正" —— 记忆里的转述不是证据。
