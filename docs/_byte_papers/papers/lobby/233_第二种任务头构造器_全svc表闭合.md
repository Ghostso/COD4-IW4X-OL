## §1 ★★★★★ `0xBA72C0` = TaskBuilder（带缓冲大小版）

### 1.1 函数体前半（关键 6 条）

```asm
0xBA72E6  mov  esi, ecx
0xBA72EB  mov  ecx, [ebp + 0x10]      ; 参数3
0xBA72EE  mov  edi, [ebp + 0x14]      ; 参数4
0xBA72F3  mov  [esi + 4], ecx
0xBA72F6  mov  [esi + 8], edi
0xBA72F9  mov  byte ptr [esi + 0xC], 1
0xBA7306  mov  dl, [ebp + 8]          ; 参数1
0xBA7309  mov  [esi + 0x1C], dl       ; ★★ svc 存进 +0x1C
0xBA730C  mov  dl, [ebp + 0xC]        ; 参数2
0xBA7318  mov  [esi + 0x1D], dl       ; ★★ task 存进 +0x1D
0xBA7312  mov  dword ptr [esi], 0xD5A64C   ; vtable
```

★ **`+0x1C` 与 `+0x1D` 是相邻的两个 byte** —— 正是协议头的 `[svc][task]` 两字节。

### 1.2 调用约定（四 push + lea ecx）

```asm
push 0x80000        ; 参数5 = 保留量（固定常量）
push 0x400          ; 参数4 = 缓冲大小（固定 1024）
push <task>         ; 参数3
push <svc>          ; 参数2
lea  ecx, [ebp-0x44]; 参数1 = this（栈上临时对象）
call 0xBA72C0
```

★ **注意 `esi` 是 this，`ecx` 也是 this** —— 这是 MSVC 的 `__thiscall` + 栈上临时对象模式。

### 1.3 ★ 校准（四个已知样本逐一验证）

## §7 方法论

1. **★★★★★ 找"第二种实现"要用「函数签名」而不是「地址邻近」。** 我猜 `0xB78C10` 的兄弟在前后 0x400 内，实际在 `0xBA72C0`（相隔 190KB）。正确的判据是"写 svc + 写 task 两个连续字节"。
2. **★★★★ 调用约定必须用「已独立确认的样本」校准。** 四个校准点（`80/70`/`80/130`/`80/203`/`80/1`）来自 221 卷的独立逆向，不是从本函数反推的 —— 否则就是循环论证。
3. **★★★ 一个 svc 的全部 task 命中，比多个 svc 各中一个更有说服力。** `80` 的 10/10 命中直接锁死了参数顺序。
4. **★★ 「push 顺序 ≠ 参数顺序」**：`push 80000; push 400; push task; push svc` 对应 `(p1=svc, p2=task, p3=400, p4=80000)`，因为 x86 cdecl 从右往左压栈。**只看 push 顺序会读反。**
