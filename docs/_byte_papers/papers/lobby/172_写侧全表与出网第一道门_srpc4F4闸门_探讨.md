# 172 探讨 · "还是黑箱"这句话，本轮该被削掉多少

## 一、起点：我上一轮的说法是"客户端不发，所以没得修"

这个说法在**现象层**是对的（抓包确实一条 `11/14` 都没有），但它把问题截断得太早。

AGENTS.md 的 GPT-6A 条款写得很直白：**「没有样本」不是停手理由，必须先做函数级拆解并写明排除了什么。** 我上一轮没有做这一步。

本轮补上之后，房间动作这条线的黑箱变小了一大块 —— 但**没有清零**，而且新暴露出来的东西比原来的诊断更准确。

## 二、本轮真正削掉的四块

### 1. 43 个类的写侧，全部存在

之前 142/150 卷只列了 `vtable[+4]`（读）。我据此（隐含地）认为这批消息"只能收"。

实际的 vtable 是三槽 `[写][读][下一个COL]`。把 `[+0]` 全展开后：

```
dwRoomMessageReady           写 0x6287D0
dwRoomMessageChangeTeam      写 0x6281D0
dwRoomMessageChangeTeamRequest 写 0x628320
dwRoomMessageVote            写 0x628320
...
```

**43 个类，43 个写侧，一个不缺。**

所以"客户端有没有能力发"这个问题的答案是**有**，而且是完整的一套。

### 2. 线格式能直接读出来

`0x628320` 被 7 个类共用，逐指令是：

```
WriteBits(3,  ____)
WriteBits(8,  type)
WriteBits(21, ____)
WriteBits(32, [+8])
```

`0x6281D0`（ChangeTeam 专用）是这一串的加长版，4 个字段：`u32 / u8 / u32 / u64`。

**这意味着服务端其实可以先按布局写解析器**，哪怕字段语义还不知道。

### 3. 出口只有一个，通道号是 0x16

全镜像扫下来，`0x7E8300` **只有 1 个调用点**：`0x62C93D`，在族 A 的 `kind==4` 分支里。

这修正了 154 卷的一个说法 —— 154 卷把通道 `0x16` 标成"空桩"。实际上 `0x7FAA20` 那个 `push 0x8435D0` 只是**回调参数**为空，主投递走 `0x7FA800`。`0x16` 是房间动作专用通道，不是桩。

### 4. 三道闸门里，第一道根本不是闸门

这是本轮最有价值的一条。

我记忆里一直挂着"房间逆向断点：`[0x8269774]`=0"。本轮反汇编 `0x803830`：

```asm
mov eax,[0x8269774]
test eax,eax
jne 已存在
push 0x1618 ; call malloc ; call ctor
mov [0x8269774], eax
```

**它是 srpc 单例的惰性构造器，不是判据。** 只要堆分配成功，它永远通过。

真正的闸门是门 2 —— `0xB7A670`：

```asm
mov ecx,[esi+0x4F4]
test ecx,ecx / je → 返回 0
call 0xBA0780
cmp byte [esi+0x4F8], 0
jne 保持
cmp eax, 2 / jne 保持
mov eax, 1
```

**`srpc+0x4F4` 才是那个开关。**

## 三、这改变了什么

原来的诊断：

> 服务端缺 changeteam 分支 ⇒ 补分支。

新诊断：

> **发送链完整，出口唯一，但出口前被 `srpc+0x4F4` 状态挡住。**
> 客户端点"准备/改阵营/投票"没反应，最可能是这个状态没满足。

这两条指向的排查方向完全相反：
- 前者让我去改 Python 服务端；
- 后者让我去查客户端的 srpc 状态机。

**如果我只按前者做，会白改一轮。**

## 四、本地图的诚实边界

还有四条是开的，我不打算说"闭合了"：

| 项 | 为什么还开 |
|---|---|
| `[obj+0x21]` 取值 | 镜像里有 16 处 `mov byte [reg+0x21], …`，但**没有一处能证明作用于同一个位流对象**。它是运行时状态。 |
| ChangeTeam 4 字段语义 | 布局读出来了（`u32/u8/u32/u64`），但这个 u8 是 team 还是 slot、这个 u64 是账号还是 session，静态读不出来。 |
| 谁触发 `vt[0]` | `0x62C93D` 往上是哪个 Flash 回调，本轮没追。 |
| `11/14` 为什么一条都没有 | 现在知道闸门在哪，但**没证**客户端在实机上确实卡在 `srpc+0x4F4`。 |

最后一条尤其要说清楚：**我推断的因果链没有被实测验证。** 这不是"已闭合"，是"有了一个可检验的假设"。

## 五、关于 `0xB77B10` 那次更正

169 卷说"这个 `WriteBits(8)` 什么都不写"。本轮读全了：

```asm
cmp byte [ecx+0x21],0
je  ret          ← 为 0 → 真的什么都不写
...
call 0xB77A70    ← 非 0 → 走 core
```

两条都是真的，只是 169 卷把条件当成了结论。core 里的 `call 0xB75D40` 是个**位宽计算**（找最高有效位），所以 `0xB77B10(buf, n)` 的语义是 **写 n 个 0 位**。

这条更正不推翻 169 的位流结构（`[3][8][8][32]` 的位数加起来仍然对），但它确实意味着：**当 `[obj+0x21] != 0` 时，线上的字节会比 169 卷推算的多出 21 位。**

## 六、一句话

黑箱没清完，但**黑箱的形状变了**：从"服务端少写了一个分支"变成"客户端发送链被运行时状态挡住"。

前者是猜的，后者有地址级证据。
