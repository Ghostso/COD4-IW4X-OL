# 184 · `StartGame` 的第 1 段 blob = **dwRoomImp 内嵌结构 `+0x7238` 的 `+0x18` 缓冲区**

> 卷次：184（房间类 · 182/183 卷追问的最终答案）
> 方法：从 `Manifold` 分发器的 StartGame 分支（`0x634B09`）反推消息对象 `[this+8]` 的真实地址
> 结论：**三个 blob 全部来自 `dwRoomImp + 0x7238` 这块内嵌结构，不是外部数据。**

---

## §0 结论

```asm
0x634AED  lea edi, [ebx + 0x7238]        ; ★ ebx = dwRoomImp
0x634AF9  mov [ebp-0xc94], 3
0x634B03  mov [ebp-0xc98], 0xDC751C      ; vtable = dwRoomMessageStartGame
0x634B0D  mov [ebp-0xc90], edi           ; ★★ [this+8] = dwRoomImp + 0x7238
0x634B25  lea ecx, [ebp-0xc98]           ; this = 栈上临时消息对象
0x634B2B  call 0x625CE0                  ; StartGame::deserialize
```

★★ **`[this+8]` 不是堆对象，是 `dwRoomImp + 0x7238` 的内嵌结构。**

### 0.1 结构布局（由两个函数共同确定）

| 偏移 | 用途 | 证据 |
|---|---|---|
| `+0x10` | blob#2 数据（8 字节） | `0x625C60 add eax,0x10` / `0x625D5F add ecx,0x10` |
| `+0x18` | blob#1 数据（256 容量） | `0x625C17 add eax,0x18` / `0x625D2C add eax,0x18` |
| `+0x118` | blob#1 实际长度 | `0x625C0F mov edx,[eax+0x118]` / `0x625D45 mov [ecx+0x118],edx` |
| `+0x1CC` | blob#3 数据（16 字节） | `0x625CA2 add esi,0x1CC` / `0x625D86 add eax,0x1CC` |

☆ `0x118 - 0x18 = 0x100 = 256` ⇒ **blob#1 缓冲区容量恰好 256 字节**，与读侧 `mov [ebp+8], 0xff`（255）吻合（留 1 字节终止）。

## §1 三个 blob 的真实语义

| # | 容量 | 内容来源 | 语义（推断） |
|---|---|---|---|
| 1 | 255/256 | `dwRoomImp+0x7238+0x18` | **一段 256 字节的原始数据块**（长度在 `+0x118`） |
| 2 | 8 | `dwRoomImp+0x7238+0x10` | **一个 8 字节值**（`u64`） |
| 3 | 16 | `dwRoomImp+0x7238+0x1CC` | **一个 16 字节值**（128 位，`security_key` 形状） |

★★ **blob#3 = 16 字节 = 128 位，与 `security_key` 的形状完全吻合**（`build_startgame_payload` 传的就是 16 字节）。
★★ **blob#2 = 8 字节 = 64 位，与 `session_id`（u64）吻合**。

### 1.1 所以我们的实现"部分正确"

| 段 | 我们 | 客户端 | 判定 |
|---|---|---|---|
| #1 | 67 字节 `bdCommonAddr` | `dwRoomImp+0x7238+0x18` 的 256B 缓冲（长度存 `+0x118`） | ⚠️ **内容不同** |
| #2 | 8 字节 `session_id` | `+0x7238+0x10` 的 u64 | ✅ **结构吻合** |
| #3 | 16 字节 `security_key` | `+0x7238+0x1CC` 的 128 位 | ✅ **结构吻合** |

★ **#2/#3 的结构完全对。#1 的容量差 4 倍（67 vs 255），内容也不同。**

## §2 谁填 `+0x7238+0x18`

`+0x18` 是 **256 字节缓冲**，`+0x118` 是它的长度字段。

三种可能来源：
1. 对端收到 StartGame 时由 `0x625D2C` 写入（**转发路径**）
2. `dwRoomImp` 构造时初始化
3. 别的消息（如 `RoomInfo`）填充

★ 本卷只确认了 (1) 存在 —— `0x625D45` 会写。
(2)(3) 未追。

## §3 位宽与我们的 109 字节

```
bits = 13 + (42 + len1*8) + (42+64) + (42+128) = 331 + len1*8
len1=67 → 867 位 → 109 字节
```

★ 我们用的是 **len1=67**（自拼的 bdCommonAddr）。客户端实际 len1 是 `+0x118` 的值，**不一定是 67**。

## §5 为什么这很重要

★★★ **如果服务端要"构造一条 StartGame 发给客户端"，那么 blob#1 该装什么，取决于客户端期望它装什么。**

而客户端在**接收**方向（`0x625CE0`）只是"读进 `+0x18` 缓冲、长度写 `+0x118`"。
**它不校验内容。**

⇒ 这解释了 179 卷的现象：`161336` 推送后客户端没崩 —— **因为读侧只做拷贝，不做语义校验**。

⇒ 也说明：**推送"格式对"只是第一步，客户端拿到后怎么用 `+0x18` 那块数据才是关键。**

## §6 方法论

1. **★★★ 从"消费方"反推"生产方"最快。** 从 `0x634B09`（Manifold 分发器构造 StartGame）一眼看到 `[this+8] = ebx+0x7238`，比从 ctor 追快得多。
2. **★★ 内嵌结构 vs 堆对象，看 `lea reg,[base+disp]` 还是 `call new`。** `lea edi,[ebx+0x7238]` 明确是内嵌。
3. **★★ 容量差 4 倍（67 vs 255）是强信号：** 说明我们猜的内容不对，而不是"恰好够用"。
4. **★★ 读侧不校验内容 —— 只拷贝。** 这解释了"推送不崩但也没用"。
