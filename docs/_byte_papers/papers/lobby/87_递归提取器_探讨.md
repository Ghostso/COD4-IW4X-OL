# 递归提取器 · 探讨：两次修正，两个不同的错

> 对应：`lobby/87_递归提取器.md`

---

## 一、这一轮修了两个错

**错 1：不跟进子函数 → `RoomInfo` 只算 18 位。**
**错 2：把定长 `writeData(ptr, imm)` 判成变长 → `MemberList` 只算 15 位。**

**两个错方向相反：一个漏算，一个少算。**

---

## 二、错 1 是"结构性的"

**`RoomInfo::serialize` 只写头，主体在 `0x624510`。**

**这种"主函数只调度、子函数干活"的模式，在 C++ 里非常常见。**

**⇒ 任何静态分析工具都必须能跟进。**

**⇒ 我用 `depth <= 3` 的限制跟进，
且只跟进 `0x625000–0x62A000` 段（serialize 密集区）。**

---

## 三、错 2 是"逻辑性的"

**我写了：**

```python
kind = "var" if ptr[0] != "imm" and ptr[0] != "mem" else "data"
if ptr[0] == "reg":
    kind = "var"          # ← 错
```

**我把"指针是寄存器"当成"变长"。**

**但 `writeData(&[obj+4], 8)` 里，指针是寄存器（`lea ecx,[obj+4]`），
位宽是立即数 8。**

**⇒ 指针来源与是否变长**无关**。**

**⇒ 应该看**位宽**是不是立即数。**

**修正后：`MemberList` 从 15 位变 63 位。**

---

## 四、这个错说明了什么

**我把两个正交的维度混在一起：**

| 维度 | 取值 |
|---|---|
| 指针来源 | 立即数 / 内存 / 寄存器 |
| 位宽来源 | 立即数（定长）/ 寄存器（变长）|

**⇒ 正确答案只看第二列。**

**⇒ 第一列对"变长"判断毫无用处。**

---

## 五、方法论收获

> **判断"变长"只看位宽，不看指针。**

**这是位流 API 的基本性质：
`writeData(ptr, nbits)` 的 `nbits` 决定长度，
`ptr` 只决定数据从哪来。**

**⇒ 我把"数据从哪来"和"数据多长"搞混了。**

---

## 六、现在的可信度

**修正后：**

- 纯定长消息 → 长度精确（`MemberList` 63 位）
- 含变长字段 → 标 `+`，给出下界（`RoomInfo` ≥ 853 位）

**⇒ 这是诚实的表述。**
