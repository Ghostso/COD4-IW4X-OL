# 135 探讨 · 判据窗口跨函数：一个假条目如何连锁制造两条假结论

> 配套：[135 · AS 注册链三层归属闭合：3 个容器类 + 44 个分批函数 + GFx 转发器表](135_AS注册链三层归属与GFx转发器表.md)
> 性质：机制复盘 + 一处对 134 卷的实质性更正。
> 主题：**这一卷真正新学到的，不是"又知道了什么"，而是"134 的一个判据在**向下**方向没有设防，于是同一个窗口里长出了假条目、假解释、假数字"。**

## 一、起点：133/134 留了一句"诚实保留"

133 §三 写：

> `0x830BC0` 容器语义未解。

134 §边界 也照抄了这条。**两卷都把它记为"未解"**，谁也没回去看它那 17 个字节长什么样。

本卷第一件事就是把这 17 字节打开：

```
0x00830BC0  55            push ebp
0x00830BC1  8bec          mov ebp,esp
0x00830BC3  8b490c        mov ecx, dword ptr [ecx+0xc]
0x00830BC6  8b01          mov eax, dword ptr [ecx]
0x00830BC8  8b80c0000000  mov eax, dword ptr [eax+0xc0]
0x00830BCE  5d            pop ebp
0x00830BCF  ffe0          jmp eax
```

**它根本不是"容器"，是一个 vtable 转发器（thunk）。**

★★ **教训 A：连续两卷把"未解"往下传，是因为没人愿意为一个"只是被调用一次的地址"付一次反汇编的成本。** 这个地址在 133 里出现过（注册器体内 `call 0x830BC0`），在 134 里出现过（`mov [eax],<vtable>` 旁边），**两卷都跳过了它**。

★ **"未解"不是中性的——它会传染。** 我把"未解"当成了一个结论抄下来，而它其实只是一个"我还没查"的标记。

## 二、顺着这一跳，整条链自己展开了

打开 `0x830BC0` 之后，往回追调用者 `0x64F620`，在它的头部看到 `mov ecx,[0xe778dc]` 和一个**巨大的常数字符串**在函数尾：

```
0x0064F6A2  683027dc00   push 0xdc2730   ; 'JoinRoom'
```

顺手把 `0xDC2730` 周围的字符串 dump 出来（`str_range_135.py`），得到的是一整条 **AS 短名带**：`CancelList / CreateRoom / JoinRoom / QuickMatch / EnableRoomListEvent / … / GetServerTime`。

再往上一跳：谁调 `0x64F620`？→ `0x5D4483`，在一个**很长很规律的函数** `0x5D43B0` 里，体内全是 `push esi; call <注册器>; add esp,4`。

再往上一跳：谁调 `0x5D43B0`？→ `0x5EBBCE`，在一个更长更规律的函数 `0x5EBB90` 里，**同一个"push esi; call"形状**，而且开头是 `mov edi,0xdc41b4` + `call 0x730690`。

`0xdc41b4` 是什么？→ `'codo.common.CFunctionContainer'`。**旁边还并排着两个同族名字**：

```
0x00DC418C  codo.common.CFunctionCommonContainer
0x00DC41B4  codo.common.CFunctionContainer
0x00DC41D4  codo.common.CFunctionInGameContainer
```

★ **这几个字，是整卷的钥匙。** 133 花了一整卷论证"名字→对象映射表不存在"——结论是对的，但那只是**否定式**的。这三个类名给出了**肯定式**的答案：

> **映射不在 C++ 侧，在 AS3 侧。** 客户端做的是"用 `flash.utils.getDefinitionByName` 把 `codo.common.CFunctionContainer` 这个 SWF 类取出来，再往它身上一个个定义属性（属性名 = AS 短名，属性值 = 一个 handler 对象）"。

★★ **教训 B：一个"穷举后不存在"的结论，必须配一个"那么它在哪"的答案，否则只是半闭合。** 133 的"不存在"如果没有 135 的"在 AS3 里"，读起来就像一个死胡同。

## 三、134 的两条结论，我这一卷要撤回

134 §0-⑤ 写：

> 2 个"漏覆盖"是过滤器 bug：`AS_GetHeadSeason` 注册器 `0x6AEBD0` 头 `57 8b f8`、`AS_ListContact` 注册器 `0x728350` 头 `53 bb 01 00 00 00` ⇒ MSVC 叶子函数省略 `push ebp` ⇒ **"函数头必须 55 8b ec"是错的判据**。

这一条读起来很漂亮——"我发现了自己的判据过严"。**但它错了两层**。

### 3.1 `0x6AEBD0` 是分批函数

工具 `as_batch_prologue_135.py` 按"统一序言 `57 8b f8 56`"普查，`0x6AEBD0` 在列。打开它：

```
0x006AEBD0  57 8bf8 56    push edi; mov edi,eax; push esi
0x006AEBD4  e8e7000000    call 0x6aecc0
...                       26 组 "push esi; call <注册器>; add esp,4"
0x006AECBD  5f            pop edi
0x006AECBE  c3            ret
```

**总长 0xEE，体内 26 组 `push esi; call`，尾 `pop edi; ret`。** 这是**分批函数**，不是注册器。注册器的形状是 `push ebp; mov ebp,esp; sub esp,0x28; mov ecx,[0xe778dc]…`（0x64F620 那样），尾是裸 `ret` 或 `c2 04 00`。

### 3.2 `0x728350` 是惰性初始化

```
0x00728350  53            push ebx
0x00728351  bb01000000    mov ebx,1
0x00728356  841d44867b0e  test byte ptr [0xe7b8644],bl
0x0072835C  7518          jne 0x728376              ; 做过就跳
0x0072835E  091d44867b0e  or dword ptr [0xe7b8644],ebx
0x00728364  e8c75dd8ff    call 0x4ae130
0x00728369  68005dca00    push 0xca5d00
0x0072836E  e811655100    call 0xc3e884
0x00728376  881d09637b0e  mov byte ptr [0xe7b6309],bl
0x0072837C  5b            pop ebx
0x0072837D  c20400        ret 4
```

全函数 **0x2D 字节，无一条 vtable 写入**。它是"首次调用时做一次初始化"的守卫。真正的分批函数是**紧跟在它后面的 `0x728380`**。

### 3.3 外层根因：**判据窗口向下的那一侧没有设防**

134 的判据之一是：

> 体内**前 0x300 字节**内有 `mov [reg],<vtable>`，且 vtable 属于 829 个。

对 `0x6AEBD0`（长 0xEE）和 `0x728350`（长 0x2D），**这个 0x300 的窗口都越过了函数末尾，伸进了下面那个函数**，于是：

- `0x6AEBD0` 的窗口吃到了 `0x6AECC0`（它自己调的第一个真注册器）的 vtable 写；
- `0x728350` 的窗口吃到了 `0x728380`（下一个函数）体内 28 个注册器的 vtable 写。

⇒ **它们被"补"进了注册器集合。**

★★ **教训 C（本卷最重要）：134 已经学会了"向上找最近 `cc cc` 会撞进数据区"，但只在"向上"方向设了防。"体内前 N 字节"是一个**向下**的窗口，它同样会跨函数——而这一侧没人管。**

**这条可以写成一句通用检查：**
> **凡是"N 字节窗口"的判据，先问一句："如果窗口比函数本身还长，会发生什么？"**
> **答：它会读到下一个函数的字节，并把邻居的性质当成自己的。**

### 3.4 更贵的那一层：134 为假条目发明了解释

`0x6AEBD0`/`0x728350` 被误判成注册器之后，134 需要解释"为什么它们的函数头不是 `55 8b ec`"，于是发明了：

> MSVC 叶子函数省略 `push ebp; mov ebp,esp`，所以"函数头必须 55 8b ec"是错的判据。

**这个解释本身是正确的 C++ 事实**（叶子函数确实可能省略帧指针），但它被用在**两个根本不是注册器的函数**上。

★★ **教训 D：为反常现象发明解释时，先重验"现象本身是否真实"。** 解释越精巧、越需要额外知识（"叶子函数"、"一次性惰性守卫"），越应该回头问"**我是不是把两个东西看成同一个了**"。

★ 134 §十 自己写过：**"教训不免疫，只缩短发现时间。"** 134 头上刚写完这句，脚上就犯了一个同族错误——只不过换了个方向。**这一卷的价值就是把"方向"补齐。**

## 四、数字的连锁污染

`tools/as_regfns_v2.json`（134 的产物，828 条）经本卷重验（`as_reg_vfy_135.py`），至少含 **3 个非注册器**：

| 地址 | 真相 | 证据 |
|---|---|---|
| `0x6A7650` | 普通小函数（0x1D 字节，`call 0x4f7150/0x4ad5f0`） | 无 vtable 写、无短名 push |
| `0x6AEBD0` | **分批函数**（26 个注册器） | 序言 `57 8b f8 56`、尾 `pop edi; ret` |
| `0x728350` | **惰性初始化** | 0x2D 字节，无 vtable 写 |

⇒ **真注册器 ≤ 825**，134 的"828 覆盖 828/828"要读成"828 条候选，其中 ≥3 条不是注册器"。

★★ **教训 E：一个假数字会连锁。** 134 自己在 §十 写过"一个假数字会生出一窝假结论"——**这一卷又生了一窝**，而且是从"补两条漏覆盖"这个看起来最负责的动作里长出来的。

★ **附带一个反面教训**：本卷的重验工具（`as_reg_vfy_135.py`）报"体内找不到短名 push"的共有 7 条，其中 `0x650FA0`（=`AS_ShowShoutcastAndUpdateBypassMouseInput`）、`0x6AF380`（=`AS_TryToUpdatePrimaryWeaponCountToPartyMember`）**是真注册器**。⇒ **我自己的新过滤器同样偏严，不能单独用它下"是假的"结论**——真假都要**打开反汇编看一眼**（"假阳性防火墙"的双向版：**假阴性也要防火墙**）。

## 五、顺带闭合的两个旧点

### 5.1 `test al,0x8F; cmp al,0x0A`（134 边界 1）

现在能逐字节写出来了：

```
0x0064F682  8b470c        mov eax,[edi+0xc]     ; 容器.flags
0x0064F685  8b4f08        mov ecx,[edi+8]
0x0064F688  8b11 / 8b5214 mov edx,[ecx] ; mov edx,[edx+0x14]
0x0064F68D  258f000000    and eax,0x8f
0x0064F692  3c0a          cmp al,0xa
0x0064F694  0f94c0        sete al
0x0064F697  0fb6c0        movzx eax,al
0x0064F69A  50            push eax              ; arg4 = bool((容器.flags & 0x8F)==0x0A)
```

⇒ 它是**"容器标志位（掩码 0x8F）== 0x0A"的布尔值**，作为第 4 个实参传给"定义属性"。**`0x0A` 的确切含义仍未定**（诚实边界保留），但**"这是个 bool 实参"现在是逐指令确证的**。

★ 另：`0x830BC0` 之后的 `test al,0x8f / je`（`0x64F67E`）用的是**同一个掩码 0x8F**——同一个 handler 值类型标志在两个地方被检查。**同一掩码两次出现，是"这两个检查管的是同一件事"的强提示。**

### 5.2 GFx 转发器表：`0x830AC0..0x830BC0` 共 9 个

一发现"`0x830BC0` 是 17 字节模板"，就顺手扫了同形（`gfx_fwd_scan.py`）：**9 个，全部连在一起**，slot 覆盖 `0xB0..0xC8` + `0xE4/0xE8`。

★★ **教训 F：认出"一个字节模板"，就立刻扫它的全族。** 一个 thunk 值 17 个字节，一张表值 9 条 slot 映射——**成本几乎为零，收益是把"一个未解地址"变成"一张接口表"。**

★ 这里也第一次出现了"**同一个数字由不同证据类型独立给出**"的最好例子——但那是 §六 的事。

## 六、28 这个数，第一次有了两条独立的腿

132 卷从 RTTI 拿到：`?N@??Init@UiCppMatchSelectView@@` 局域类 **28 个**（数据侧）。
133 卷从调用图拿到：`0x73DF20` 调 **28** 次（代码侧）。
**133 当时已经标注"次数对齐推断，非直接证据"。**

本卷 `as_batch_135.py` 从**第三路**（注册器→分批函数归属）又得到 `0x73DF20` = **28 个注册器**（调用图侧）。

⇒ 现在 **28** 有：RTTI 名（数据）、直接调用次数（代码）、注册器归属（代码+数据）三路一致。

★★ **教训 G：同一个数字被不同**类型**的证据独立复现时，它的可信度不是"三次相加"，而是"换了一层"。** 133 把它标成"推断"是对的（当时只有两路，且都是"数出来的"）；本卷把它推到"机制一致"。

★ 顺带，`0x5CEB10` 的 133 §七 记录"调 220 次"，本卷分解为 **217 个注册器 + 3 个非注册器调用 = 220**。**旧卷的观测数被分解成"有用部分 + 噪声部分"——这比"重新数一遍"信息量大。**
