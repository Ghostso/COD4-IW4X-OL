# 67 字节 blob 的来源实证：就是槽的 `+0x11` 起 67 字节

> 承接 `lobby/98` §6、`lobby/99` §8 的遗留问题
> **★ 本卷把一个"猜"变成了"证"，同时否证了自己的一个错误假设**

---

## 1. 上一卷我猜错了一次

**`lobby/99` 探讨里我写：**

> **"槽的 `+0x11` 到 `+0x53` 正好是 67 字节，
> 而 P2PInfo 的 blob 也是 67 字节。如果成立，就把空白填上了。"**

**同时我注意到一个矛盾：**
**P2PInfo 打包时传的源是 `[esi+0x0C]`，不是 `[esi+0x11]`。**

**⇒ 我当时的结论是"巧合被否定"。**

**★ 那个结论**错了一半**：`[esi+0x0C]` 传的是**输出缓冲**，
而 `[esi+0x11]` 是**另一个调用点的输入源**。**

---

## 2. 关键反汇编：`0x7bfb32`

**函数入口 `0x7bfa70`，在 `0x7bfb32` 处：**

```
0x7bfab7   test eax,eax
0x7bfab9   jns 0x7bfb1f            ; 成功分支
...
0x7bfb1f   mov ecx, [ebp-8]
0x7bfb22   test ecx, ecx
0x7bfb24   jne 0x7bfb32
...
0x7bfb32   lea edx, [edi + 0x11]    ; ★★ 源 = 槽 +0x11
0x7bfb35   push edx
0x7bfb36   call 0xb74bc0           ; ★★ 同一个打包器
0x7bfb3b   lea eax, [edi + 0x54]
0x7bfb3e   lea ecx, [edi + 9]
0x7bfb41   push eax
0x7bfb42   push ecx
0x7bfb43   call 0x7f5a00          ; 处理 +0x09 与 +0x54 两块
0x7bfb48   lea eax, [edi + 0x54]
0x7bfb4b   push eax
0x7bfb4c   lea eax, [edi + 9]
0x7bfb4f   push eax
...
```

**⇒ `0xb74bc0`（那个 67 字节打包器）的输入源是 `[edi+0x11]`。**

**⇒ 输出缓冲在哪？`0xb74bc0` 的第一个参数（`[ebp+8]`）在 `0x7bfaae` 传入：**

```
0x7bfaa2  lea eax, [ebp-8]
0x7bfaa5  shl esi, 4
0x7bfaa8  mov edi, [esi + 0xe36dba0]   ; ★ 槽指针（索引表）
0x7bfaae  push eax
0x7bfaaf  call 0x7f5970                ; 取得槽对象
```

**⇒ 这里 `edi` 是**槽的基址**，`[edi+0x11]` 就是 67 字节数据区。**

---

## 3. ★★ 一行代码坐实了数组身份

**`0x7bfabb`：**

```
0x7bfabb  cmp edi, 0xe36e4d0        ; ★★ 与已知数组基址比较
0x7bfac1  jne 0x7bfacc
0x7bfac3  mov dword [ebp-4], 0
0x7bfaca  jmp 0x7bfaf6
0x7bfacc  lea esi, [esi + 0xe36db94]
0x7bfad2  mov dword [ebp-4], 2
```

**⇒ `0xe36e4d0` 正是我在 `lobby/99` §4 里从镜像读出的
对等玩家槽数组的基址。**

**⇒ 这个函数**明确地在操作同一个数组**。**

**⇒ ★ 所以 `[edi+0x11]` 就是这个数组里某一项的 "+0x11"。**

**⇒ ★★ 结论成立：67 字节 blob 的输入 = 对等玩家槽的 `+0x11` 起 67 字节。**

---

## 4. 于是 67 字节区域有了确切含义

**槽布局（`lobby/99` §4 实测）：**

```
+0x00 .. +0x08   状态头（8 字节，含 0xDEADBEEF 标记位置）
+0x09 .. +0x10   8 个 01
+0x11 .. +0x53   67 字节 ← ★ P2PInfo 的 blob 就是这一段
+0x54 .. +0x57   4 个 01
+0x58 .. +0x63   12 个 01
+0x64 .. +0x87   零
```

**⇒ 67 字节不是"独立缓冲"，是**槽内固定区域**。**

**⇒ 它的填充逻辑在 `0xb74bc0`：遍历**源数组**（`[edi+0x10]` 项数、
`[edi+8]` 基址、步长 `0x88`、上限 `0x550`）→ 结果写进 `+0x11` 那块。**

**★ 等等 —— 这里有两个"对等玩家表"？**

**必须澄清（见 §5）。**

---

## 5. 澄清：两层数组，不是同一个

**`0xb74bc0` 内部循环用的是 `[edi+0x10]` / `[edi+8]` / 步长 `0x88` / 上限 `0x550`。**

**而 `0x7bfb32` 传进来的是**一个槽**（`edi` = `0xe36e4d0 + i×0x88`）。**

**⇒ 所以结构是两层的：**

```
外层：对等玩家槽数组  基址 0xe36e4d0，10 项 × 0x88 = 0x550
       每项含：
         +0x00 状态
         +0x09 8 个 01
         +0x11 ★ 67 字节"子表"← 由内层打包器填
         +0x54 / +0x58 更多 01

内层：0xb74bc0 遍历的数组（[edi+8] 基址、[edi+0x10] 项数、步长 0x88）
```

**★ 但内层也用 0x88 步长 —— 这引出一个必须诚实标注的问题：**

**`0xb74bc0` 的 `edi` 到底指向**外层槽**还是**另一个容器**？**

**从 `0x7bfb32` 看，传进去的是 `[edi+0x11]`（一个缓冲地址），
而不是槽指针本身。**

**⇒ 所以 `0xb74bc0` 的 `[ebp+8]`（输出缓冲）是 `[edi+0x11]`，
它的 `edi`（内部来源对象）是**另一个**参数。**

**⇒ 我需要再看 `0xb74bc0` 读 `[edi+8]` / `[edi+0x10]` 时 `edi` 从哪来。**

---

## 6. 诚实标注：内层来源对象未定

**`0xb74bc0` 的签名（按 `[ebp+8]` 起）：**

```
[ebp+8]   输出缓冲（= 槽的 +0x11）
[ebp+0xc] ...
[ebp+0x10] ...
[ebp+0x14] ...
edi = ecx = this（成员函数）
```

**⇒ `[edi+8]` / `[edi+0x10]` 里的 `edi` 是 **this 指针**，
不是 `[ebp+8]` 那个输出缓冲。**

**⇒ 所以内层来源是"打包器所属的对象"，不是"外层槽"。**

**★ 那这个对象是什么？本卷**没有**确定。**
**⇒ 下一卷必须查 `0x7bfa70` 里 `ecx`（this）是怎么来的。**
**但本卷的核心结论（67 字节 = 槽 +0x11）**不依赖**它。**
**因为它只依赖 `0x7bfb32` 那一行 `lea edx,[edi+0x11]`。***

## 7. 同时确认了 `+0x09` 和 `+0x54` 的用途

```
0x7bfb3e  lea ecx, [edi + 9]
0x7bfb41  push eax              ; +0x54
0x7bfb42  push ecx              ; +0x09
0x7bfb43  call 0x7f5a00
```

**⇒ `+0x09`（8 字节）与 `+0x54`（4 字节起）被**配对**传给另一个函数。**

**⇒ 这正是 `lobby/99` §5 里那两簇 `01`。**

**⇒ 它们不是"顺手填的"，而是**成对参与**某个计算（很可能是地址/端口组合）。**
