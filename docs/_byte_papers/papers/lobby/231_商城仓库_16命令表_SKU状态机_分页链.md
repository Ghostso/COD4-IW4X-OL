## §0 结论（一句话）

**`80`(Marketplace) 的 SKU 目录刷新是一条 7 状态机全链：`init(0x4A93E0)` 置 `state=1` → `getskus(0x4A80C0)` 发 `0x59` 分页请求 → 回调按 `reply+5` 判定 → 有数据才置 `state=3`；回空则置 `state=2` 并进入定时重试环。缺任一环，仓库/商城全空。**

★★★★★ **本卷根因结论**：**服务端「刻意回空页」正是商城/仓库全空的直接原因。** 回空 ⇒ `[reply+5]==0` ⇒ `[0x82C4A88]=2` ⇒ 永远到不了 `state==3` ⇒ 商城 UI 不渲染 ⇒ 客户端按定时器重发 ⇒ 日志里请求周期重复 ⇒ 误判为「客户端在正常请求」。**「空页安全（不炸）」和「空页正确（能显示）」是两件事，过去把它们混为一谈。**

★★★ **本轮最重要更正**：`marketplace.*` 是 `0x33303B0` 上的**控制台命令注册表**（16 条，`0x4F37A0` 查重 / `0x4F3820` 注销），**不是网络 task 派发器**。之前把它当 task 映射会走错方向。

### 1.1 判定：这是控制台注册表，不是网络 task 派发

```
0x4A9A60  由唯一调用者 0x7E997D 调用
0x7E9942  call 0x4AB840            ; 命令表初始化
0x7E997D  call 0x4A9A60            ; ★ 注册 marketplace.*
0x7E9982  call 0x4A3300
0x7E9987  call 0x7F9F60
```

`0x4F37A0(name)` 是**线性链表字符串查重**（返回 0 = 未注册），`0x4F3820(name)` 是**从链表摘除**。这是标准的 Cmd_AddCommand/Cmd_RemoveCommand 模式，**不是** `0xE4E8F8` 服务表 / `0x7FAA20` 出口漏斗那条网络链。

### 2.3 ★ 状态机全图

```
state=0 (未初始化)
   ↓ 4A9850: state==0 → call 4A93E0
state=1 (init 完成，已发首页请求)   ← 4A9443 唯一写 1
   ↓ 4A7E20: state==1 且 [0x8536F64]!=0
      → 写 state=2 (先), 再写 state=3 (0x4A7E37)
state=3 (SKU 目录就绪)   ★ 全库唯一写 3 = 0x4A7E37
   ↓ 7 个消费点，其中 5E6A20 才真正渲染商城
state=2 (错误/未认证)
   ↓ 4A9850: state==2 → 浮点定时器重试 (0x849B800+0xC 与 0)
```

★ **推论**：`4A7E20` 的身份不是「设置成功」，而是「**失败检测 + 唯一成功出口**」：
```
4A7E20:
  cmp [state], 1        ; 只在 state==1 (刚 init) 时动作
  jne ret               ; ★ 其它状态直接返回，什么都不做
  or  [flags], 6        ; 0x82C4AA4 |= 6
  state = 3             ; ★ 唯一写 3
  for obj in [0x8536F64] 链表:
      call [obj->vt + 8]  ; 通知所有监听者
```

### 2.4 ★★★★★ 回空应答 ⇒ `state=2` ⇒ 死循环重试（本卷最重结论）

分页响应回调 `0x4A7FB0`（由 `0x4A7F49 push 0x4A7FB0` 注册）开头：

```asm
0x4A7FB0  push ebp / mov ebp,esp / push ecx
0x4A7FB4  cmp  byte ptr [ebp + 0xc], 0     ; 第二参数
0x4A7FB8  push esi
0x4A7FB9  jne  0x4A7FE7                    ; 非 0 走"真实数据"分支
0x4A7FBB  mov  eax, [ebp + 8]              ; ★ reply 对象
0x4A7FBE  cmp  byte ptr [eax + 5], 0       ; ★★ reply+5
0x4A7FC2  je   0x4A7FCD                    ; ★ ==0 → 判定失败
0x4A7FC4  cmp  byte ptr [0x82C4A72], 0
0x4A7FCB  jne  0x4A7FE3                    ; 已有请求在飞 → 直接返回
0x4A7FCD  or   dword ptr [0x82C4AA4], 4
0x4A7FD4  mov  eax, 2
0x4A7FD9  mov  [0x82C4AEC], eax
0x4A7FDE  mov  [0x82C4A88], eax            ; ★★★ state = 2
```

**同一套判据在另外两个回调里逐字重复**：

| 回调 | `[reply+5]` 判定 | `state=2` 写点 |
|---|---|---|
| `0x4A7FB0`（`0x5a` 分页） | `0x4A7FBE cmp byte [eax+5],0` | `0x4A7FDE` |
| `0x4A8200`（`0x59` getskus） | `0x4A820D cmp byte [eax+5],0` | `0x4A8234` |
| `0x4A8400` | `0x4A83FC cmp byte [eax+5],0` | `0x4A841B` |

★ **对象字段（本节初稿有一处错，已按 `0xB83DD0` 构造函数更正）**：

```
0xB83DD0 = 事务对象 ctor（vtable 0xD59A08，字符串 0xDB6AE4）
  0xB83DFD  mov [esi],    0xDB6AE4
  0xB83E0C  mov [esi],    0xD59A08        ; 二次写 vtable（派生类）
  0xB83E12  call 0xB75DD0                 ; 子对象 +8 构造
  0xB83E17  fld  [0xD59A04] / [esi+0x10]  ; 浮点初值
  0xB83E20..3C  [esi+0x14/18/1C/20/24/28/2C/30/34/38/3C] = 0
  0xB83E52  mov  [esi+0x44], eax          ; ★ eax = [0xE85C5C]
  0xB83E55  inc  eax
  0xB83E56  mov  [0xE85C5C], eax          ; ★★ +0x44 = 全局自增事务号
```

**⇒ `+0x44` = 单调递增的事务序号，不是「条数」。** 回调里的用法正对：

```asm
; 请求时（0x4A7F0D）：
0x4A7F0D  call 0xB83D50              ; eax = txn+0x44
0x4A7F12  mov  [0x82C4A9C], eax      ; ★ 记下本次事务号

; 响应时（0x4A7FFC）：
0x4A7FFC  call 0xB83D50              ; eax = 响应里的事务号
0x4A8001  cmp  [0x82C4A9C], eax      ; ★★ 事务号必须匹配
0x4A8007  jne  0x4A7FE3              ; 不匹配 → 静默丢弃
```

★ `+0x24`（`0xB83D20 mov eax,[ecx+0x24]`）在本层 26 个写点里**全部写 0**，但回调用它累加后与 dvar 页大小比较（`0x4A801A add [0x82C4A94],eax` / `0x4A8028 cmp eax,esi`）⇒ **它是「本次返回条数」，属于响应侧的对象类（非上面的 0xD59A08 事务类）**。该类构造函数未定位。

★ **重要**：`+0x05`（`reply+5`）在上述事务对象 ctor 里**完全没有被写**（`0xB83E20..3C` 那段只写 dword 字段）。⇒ **`reply+5` 属于另一个对象**，其 ctor 尚未定位。

### 2.5 ★★★ 死循环重试链（解释了日志里的重复请求）

```
state=2 后，下一帧 0x4A9850 被调用：
0x4A9850  mov  eax,[0x82C4A88]
0x4A9858  sub  eax, ebx          ; ebx=0
0x4A985C  je   0x4A98D8          ; state==0 → call 0x4A93E0 (init)
0x4A985E  sub  eax, 2
0x4A9861  jne  0x4A98DD          ; 非 2 → 跳过
         ; state==2 分支：浮点定时器
0x4A987D  mov  eax,[0x849B800]
0x4A9886  fld  dword [eax+0xc]   ; ★ 重试间隔（秒）
0x4A988B  fucompp                ; 与 0 比较
0x4A9894  mov  ecx,0xE9C6458 ; call 0xB75DA0   ; 取当前计时
0x4A98BD  fcompp                 ; 当前 >= 间隔 ?
0x4A98CC  je   0x4A98DD          ; 未到 → 返回
0x4A98CE  mov  ecx,0xE9C6458 ; call 0xB75D90   ; 重置计时
0x4A98D8  call 0x4A93E0          ; ★★★ 重新 init → state=1
```

**⇒ 闭环：`state=1` → 发请求 → 回空 → `state=2` → 等定时器 → `init` → `state=1` → …**

### 2.6 ★ 重试间隔是 dvar `dw_marketplaceInitRetryInterval`

`0x4A987D mov eax,[0x849B800]` / `0x4A9886 fld dword [eax+0xC]` 读的那个全局：

```
[0x849B800] = 0x0810B118          ; dvar 对象指针
0x7EAE55 push 0xDDF648            ; "dw_marketplaceInitRetryInterval"
0x7EAE5A push 0xDB6EBC            ; "dw_config"  ← dvar 分类
0x7EAE5F call 0x50BC70            ; Dvar_RegisterFloat
0x7EAE67 cmp  eax, ebx
0x7EAE6B mov  esi,[0x849B800]     ; ★ 结果存回 0x849B800
```

★ **`[0x849B800]+0xC` = `dw_marketplaceInitRetryInterval` 的浮点值**（MSVC dvar 对象布局：`+0xC` 是 current value float，与 `0x4A9886 fld dword [eax+0xC]` 一致）。

★ **⇒ 这个重试环是客户端设计内的行为，可以用 dvar 改间隔，但改间隔不能让 `state` 进入 3** —— 只有让 `reply+5 != 0` 才行。

★ 顺带确认了什么不是：`[0x849B7F0]` 是另一个 dvar（`enable_wild_card_slot_...`），`[0x849B7FC]` 也是（`dw_roomCODTeamBalance` 相邻注册）。**`0x849B7E0`/`0x849B80C`/`0x849B818` 是不同的 dvar 对象**，221 卷把它们笼统当「分页表」是不准确的。

### 5.1 ★★ 关键观察：31741 件物品换不来一个非空目录页

**我们下发了 35741 件库存（`80/230` 193KB 玩家资产），6 个目录 task 全部回空 ⇒ 客户端进了大厅、仓库有数据，但商城/仓库 UI 是空的。**

对照 §2.3 状态机：**`state=3` 需要 `0x4A7E37` 被走到，而它只在 `0x4A7E20` 内、且只在 `state==1` 时执行。** `state=1` 由 `0x4A9443`（init）写，条件是：

```
0x4A941F test esi,esi          ; srpc 非空
0x4A9425 call 0xB7A670
0x4A942A cmp  eax, 2           ; ★ 必须 == 2（已认证）
0x4A942D jne  0x4A9455         ; 否则 init 直接返回，state 保持 0
0x4A9436 call 0xB81250         ; 空串查对象
0x4A943D je   0x4A9455         ; ★ 返回 0 也直接返回
0x4A9443 mov  [state], 1       ; ★ 只有到这里才置 1
```

**⇒ 结论：`state` 卡在 0 或 2 时，客户端永远不会请求 SKU 目录，我们回什么格式都没用。** 这解释了为什么「自编 SKU 页打挂服务」和「回空页安全」两种实验都没产生正向结果——**实验前提（客户端已发请求）可能从未成立。**

### 5.2 与 221 卷 `enable=0` 的关系

221 卷 §2.2 的 `marketplace` 服务项 `enabled=0`，本卷给出机制解释：**`enabled` 位影响的是 `0xB7A670()==2` 之后的 `0xB81250(空串)` 是否能取到对象**，而不是「发不发请求」。

## §11 方法论

1. **★★★★★ 先问「这张表是谁注册的」。** `marketplace.*` 出现在 `0xDB6CE0` 附近，第一直觉是「网络 task 名表」，实际是 `0x33303B0` 控制台链表。**判据：查注册函数用的是 `0x4F37A0`（链表查重）还是 `0xE4E8F8`（服务表）/`0x7FAA20`（出口漏斗）。**
2. **★★★★ `state==3` 只有 1 个写点、7 个读点 ⇒ 先看写点是否可达，再看读点。** 若写点前置条件（`state==1` + 认证==2 + 对象非空）不成立，所有读点的行为分析都是空谈。
3. **★★★ 「回空页安全」≠「回空页正确」。** 实机日志证明 6 个目录 task 全回空、仓库 35741 件、UI 仍空 ⇒ 空页只保证「不炸」，不保证「能显示」。
4. **★★★ 绝对地址搜索必须按编码形式解码，不能用 `find(u32)` 猜指令起点。** 同一条 `83 3D xx xx xx xx 01` 从不同偏移反推会解出完全不同的指令。
5. **★★ 「函数起点」必须用 `CC CC` 边界验证，不能靠「看起来像入口」。** `0x4A7E18..1F` 的 8 个 `CC` 被我跳过了一次，导致结论挂错函数。
