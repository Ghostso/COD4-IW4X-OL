# 245 · 复核 239 卷并更正 242 卷：`+0x21` 是**整个编解码的开关**，41 位 / 51 位取决于它

> 卷次：245（第七轮·独立复核二）
> 被复核：`239`（子代理：41 位(flag=0) / 51 位(flag=1)）
> 被更正：`242`（我方上一卷：笼统写「51 位」）

---

## §0 结论

**★★★★★ 239 卷对，242 卷错（我上一卷只看到了写侧 `flag=1` 的那条路径）。**

**`[obj+0x21]` 不只是"1 位头的值"，它是整个位流编解码的`总开关`：**

| `+0x21` | `W_TAG`(`0xB77B10`) | `R_TAG`(`0xB774E0`) | 位宽 |
|---|---|---|---|
| **0** | **直接 ret，1 位都不写** | **直接返回 `al=1`（成功），1 位都不读** | **41 位** |
| **非 0** | 写 5 位标签 + 值 | 读 5 位标签 + 比对 | **51 位** |

★ **⇒ 房间类（服务端应答侧）`+0x21 == 0` ⇒ 41 位。242 卷说「51 位」是错的。**

| # | 证据 | 强度 |
|---|---|---|
| ① | `0xB77B13 cmp byte [ecx+0x21],0` / `0xB77B17 je 0xB77B28`（写侧，0 就跳过） | ★★★★★ |
| ② | `0xB774F0 cmp byte [ecx+0x21],0` / `0xB774F6 je 0xB7754F`（读侧，0 就 `al=1` 返回） | ★★★★★ |
| ③ | `0xB77A8B cmp byte [esi+0x21],0` / `0xB77A8F je 0xB77AC3`（`W_TAG` 内部也用它） | ★★★★★ |
| ④ | `0x637026 push 1` 是 0xB779A0 的**第 3 参**，`0xB77A02 mov [esi+0x21],al` 里 `al` 来自 `0xB779CD xor eax,eax` = **0** | ★★★★★ |

## §1 读侧 `0xB779A0` 的参数（修正 242 卷）

```asm
0x637009  push 0x24 / call 0xB74220          ; 分配 36 字节
0x637019  mov  ecx, [ebp + 0x24]             ; 参数6
0x63701C  lea  edx, [ecx*8]                  ; edx = 参数6 * 8 = 位长
0x637023  mov  ecx, [ebp + 0x20]             ; 参数5 = 源缓冲
0x637026  push 1                             ; ★ 第3参 = 1
0x637028  push edx                           ; 第2参 = 位长
0x637029  push ecx                           ; 第1参 = 源缓冲
0x63702A  mov  ecx, eax                      ; this
0x63702C  call 0xB779A0                      ; ★ 位流读对象 ctor
```

对应 `0xB779A0` 内部：

```asm
0xB779EC  mov  ebx, [ebp + 0xC]      ; 第2参 = 位长
0xB779EF  lea  edi, [esi + 0x21]
0xB779CD  xor  eax, eax              ; ★ eax = 0
0xB77A02  mov  byte ptr [edi], al    ; ★★ [esi+0x21] = 0   ← 不是第3参！
0xB77A04  cmp  byte ptr [ebp + 0x10], al   ; 第3参 == 0 ?
0xB77A07  je   0xB77A36              ; 是 0 → 走默认分支
0xB77A09  cmp  ebx, eax
0xB77A0B  je   0xB77A36
0xB77A36  push 1 / lea ecx,[ebp-0xD]
0xB77A3E  mov  byte ptr [ebp - 0xD], al    ; 源 = 0
0xB77A41  call 0xB777C0              ; 写 1 位 0
0xB77A46  push ebx / push [ebp+8] / call 0xB777C0   ; 拷贝 ebx 位
```

★★ **关键更正**：`0xB77A02 mov [esi+0x21], al` 里的 `al` 是 `0xB779CD xor eax,eax` 的结果 = **0**。
**第3参（`push 1`）只用于 `0xB77A04 cmp [ebp+0x10],0` 这个分支选择，不写进 `+0x21`。**

★ **⇒ 读侧对象的 `+0x21` 恒为 0，与传入的 `push 1` 无关。242 卷说"读侧也写 1 位 0"是对的，但把它当成"51 位的证据"是错的 —— 那 1 位只是 `0xB77A41` 拷贝前的占位。**

## §2 ★★★★ `+0x21` 的双向总开关（本卷最重要）

### 2.1 写侧 `0xB77B10`（`W_TAG`）

```asm
0xB77B10  push ebp / mov ebp,esp
0xB77B13  cmp  byte ptr [ecx + 0x21], 0    ; ★★ 总开关
0xB77B17  je   0xB77B28                     ; ★★ ==0 → 直接返回，一位不写
0xB77B19  mov  eax, [ebp + 8]               ; 标签值
0xB77B1C  push 0 / push 0x1F / push 0 / push eax
0xB77B23  call 0xB77A70                     ; 写 5 位
0xB77B28  pop ebp / ret 4
```

### 2.2 读侧 `0xB774E0`（`R_TAG`）

```asm
0xB774E0  push ebp / mov ebp,esp
0xB774F0  cmp  byte ptr [ecx + 0x21], 0     ; ★★ 总开关
0xB774F4  mov  al, 1                        ; ★ 默认"成功"
0xB774F6  je   0xB7754F                     ; ★★ ==0 → 直接返回 al=1，一位不读
0xB774F8  push 0 / push 0x1F / push 0 / lea eax,[ebp-0x58]
0xB77509  call 0xB77630                     ; 读 5 位
0xB7750E  test al, al / je 0xB7754F
0xB77512  mov  eax, [ebp + 8]               ; 期望值
0xB7751A  cmp  esi, eax
0xB7751C  sete bl                           ; ★ 比对结果
...
0xB7754C  mov  al, bl
```

★★ **`+0x21 == 0` 时 `R_TAG` 无条件返回 `al=1`（成功）** ⇒ 客户端认为"标签匹配"，**但没读任何位**。

★★★ **⇒ 这解释了 175 卷「6/5 应答必须 7 字节」的真相**：
- `+0x21 == 0`：R_TAG 不读标签，只读 `W_VAL(8)` + `W_VAL(32)` 的实际字段
- 服务端应答**不需要标签**，只需要 `[1位][8位 maxResults][32位 count]`

## §3 位宽对照（41 / 51 两个值都对）

| 场景 | `+0x21` | 组成 | 位数 |
|---|---|---|---|
| **房间类服务端应答** | **0** | 1(ctor 前置) + 0(W_TAG 跳过) + 8 + 0 + 32 = 41 | **41** |
| **flag=1 的消息** | 非 0 | 1 + 5 + 8 + 5 + 32 = 51 | **51** |

★ **两者的最小字节数都是 ceil(n/8)：41→6 字节，51→7 字节。** 这就是 180 卷「867 和 868 都是 109B」的成因 —— **位数差 10 位，字节数可能相同。**

## §4 对 242 卷的更正

| 242 卷说法 | 更正 |

| 「房间位流 = `[1 位=0][Manifold 头 50 位]` = **51 位**」 | ❌ **应为 41 位**：`+0x21==0` ⇒ `W_TAG` 一位不写，所以是 `1 + 8 + 32 = 41` |
| 「读侧 `0xB779A0` 也写 1 位 0 ⇒ 两侧对称」 | ⚠ **部分对**：读侧确实写 1 位，但那是 `0xB77A41` 的占位，**且读侧 `+0x21` 恒 0** |

★ **242 卷的错因**：我只反汇编了 `0xB778E0`（ctor）和 `0xB779A0`（读侧 ctor），**没有反汇编 `0xB77B10`（`W_TAG`）**，所以没看到那个 `je` 会把 5 位标签整个跳过。

★ **本卷补上了这一步，结论从"51 位"修正为"41 位 / 51 位两个值"。**

## §5 服务端可实现的具体结论

**若要让客户端 `6/5` 应答被正确解析（`+0x21==0` 路径），payload 应为：**

```
[1 位 0]  [8 位 maxResults]  [32 位 count]
= 41 位 = 6 字节（向上取整）
```

★ **注意**：41 位向上取整是 **6 字节**，不是 7。**175 卷的"7 字节"是按 51 位算的。** 这两个值的区别需要在服务端落地时确认。

★★ **但本卷不给"改了就通"的结论** —— 因为 33 个 run 的 `6/5` payload 全是空 TLV，**没有真实样本可以端到端验证**。本卷只给"客户端怎么读"。

## §8 方法论

1. **★★★★★ 一个字段（`+0x21`）在一个子系统里是"3 个不同东西"**：写侧 1 位头的值 / 编解码总开关 / 读侧恒 0。**只看一个函数必然误判。**
2. **★★★★ 位宽必须"把编码路径上每一次写位都列出来"，包括被 `je` 跳过的那些。** 我 242 卷只列了 `0xB778E0` 里的，漏了 `0xB77B10` 里的 `je`。
3. **★★★ 子代理结论与主对话冲突时，主对话要独立重跑全部相关函数，不能只验冲突点。** 我 242 卷只验了 ctor，就断言"51 位"，**漏了 `W_TAG`**。
4. **★★ "位数差 10 但字节数相同"是位流分析的常态，不能拿字节数当位数验证。**
