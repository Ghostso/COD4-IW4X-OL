## 一、先认错

上一轮我写给用户的是：

> 「**`battle_security_key` KDF 对齐**（163 卷）—— 进战斗服的唯一硬阻断，**可纯静态做**」

这句话有两处过头：

1. **"唯一硬阻断"** —— 我没有验证过它是不是"唯一"。
2. **"可纯静态做"** —— 我当时只有 163 卷的一条结论（"客户端带标签 KDF vs 战斗服 SHA1，公式不同"），
   **没有自己反汇编过任何一处**，就把它当成可执行项排进了计划。

真做下去之后，结论变成了：**这条不是机械修复，而且 163 卷的前提本身很可能站错。**

---

## 二、为什么"公式不同"这个说法值得怀疑

163 卷的推理是：

> 客户端 `security_key` 来自 ECDH（`0xBA1E96 call 0xBA0D20`），
> 而战斗服 `p224.c:313` 用 `SHA1(shared_x28 ‖ security_key16)`
> ⇒ 不是「值不同」是「公式不同」，HMAC 必然失败。

我照它给的地址去读，读到的是：

```
0xBA1E5B call 0xC73D20      ; 造一个 20 字节量 (长度变量初值 0x14)
0xBA1E7A call 0xBA0750      ; 造 24 字节会话密钥
0xBA1E96 call 0xBA0D20      ; 20B + 24B -> 20B
0xBA1EF2 call 0xBA13D0      ; KDF(label="CLIENTCHAL", len=10, out=16)
0xBA1F76 call 0xBA13D0      ; KDF(label="BDDATA",     len=6,  out=72)
```

这串东西——**24 字节会话密钥 + 20 字节 transcript hash + HMAC 出 20 字节 secret +
CLIENTCHAL→16 / BDDATA→72**——正是 `codol_crypto.py` 里给**大厅**用的 `derive_session_keys`。

而战斗服的 `codol_derive_transport_key(shared_x28, security_key16)` 是**另一个形状**：
28 字节 ECDH 共享 X + 16 字节 security key → SHA1 → 24 字节。

**两条不同形状的链，被判成"公式不一致"。**

### 这是一个我在这个项目里犯过的老毛病的变体

项目里反复出现的一类错误是 **"名字相同/位置相近 ⇒ 同一条链"**：
- 138/142 卷的「两个'类型号'同名不同义」；
- 235 卷的「同偏移 ≠ 同语义」；
- 253 卷的「两张表元素重合 ≠ 来源相同」。

这次是 **"两段都跟密钥有关 ⇒ 是同一段密钥"**。

**判据本该是：先确认两条链处理的是同一类报文。** 而 `0xBA1E96` 附近那段是在
构造**会话记录/握手报文**（有一个 0x44A 容量的报文缓冲、逐字段 append），
和战斗服 UDP 通道的 DTLS 式握手根本不是一个流程。

## 三、第二个线索：`0xBA0D20` 根本不是 EC 运算

163 卷写「`0xBA0D20` = EC 秘密计算」。我把它的函数体读完：

```
0xC73800  ← 用 (ptr, len) 构造一个字符串/缓冲对象
0xC73760  ← assign
0xC737A0  ← 取 20 字节
```

**全是缓冲操作，没有一次 EC 域运算**（没有模乘、没有大数、没有 P-224 常量）。

⇒ 163 卷那一条是**从调用位置猜的语义**（"它在 ECDH 之后被调用，所以它是 ECDH"），
不是从函数体读出来的。而**它的下游确实能推出「HMAC 出 20 字节」**这个更合理的解释。

**教训与 201 卷那条一样：只读开头/只读调用点 = 必然误判，要读到 `ret`。**

## 四、第三个线索：那份 KDF 自己写着"照抄"，而且自附"没对上"

`codol_crypto.py:571-573`：

> ★ 本轮借鉴 ol-mod 的核心: 逆出密钥派生…
> 出处: ol-mod src/backend/Demonware/Crypto.cpp:153-216

而 AGENTS.md 明写 **ol-mod 非权威、禁止照抄其常量/字段布局/协议值**。

更关键的是它**自己**的实测注记（2026-10-03）：

> 4. **但这个配方的输入与我们的 build 不同**: 用票据的全部 24B 窗口 × 12 种 transcript
>    × 2 种 HMAC 参数序 × 2 种 label 序 = **5040 组穷举, 与真实内存密钥全部不命中**。
>    => 所以本文件提供的派生函数目前只用于**诊断/互校**；生效的密钥来源仍是 nt10 内存快照。

**⇒ 一份被标注"未对上、仅供参考"的实现，在后续卷里被当成权威结论引用了。**

这和 248 卷的 `unknown_skus.txt`（2026-10-10 的旧日志，错误串在当前代码里早已不存在）
是同一类错：**旧材料被当作现况**。

★ 配套纪律：**引用任何实现前，先读它自己的"已知不成立"注记。**

## 五、那到底修了什么

不是 KDF 公式，而是**两个占位值互相不一致**：

| | 值 | 是否发给客户端 |
|---|---|---|
| 大厅 `SEC_KEY` | `0x00*16` | ✅ 经 21/5 会话记录第 6 个记录尾字段 |
| 战斗服 `b->security_key` | `0x01*16` | ❌ 硬编码 |
| `battle_security_key.txt` | 由大厅写 | ❌ **战斗服从不读** |

**不管正确答案是 0x00 还是别的东西，「两侧必须一致」是无条件成立的。**
所以修复方向是**确定的**：让战斗服使用大厅下发的那个值。

这也是这条缺陷**能修而 KDF 公式不能修**的原因：
- 修"两侧一致"——**不需要知道正确答案**，只需要消除分歧；
- 修"KDF 公式"——**需要知道正确答案**，而那需要证明两条链是同一条。

**判断一个修复能不能动手，标准不是"看起来对不对"，而是"我需不需要一个我还不知道的事实"。**

## 六、这次修得比上次谨慎的地方

1. 改前**备份**了 `battle.c`（`_rev_analysis/_p253/srcbak_battle_c/`）。
2. 先确认**链里的 exe 与已构建的 exe 同哈希**（`275B165F0A79`）⇒ 源码与运行体对应，改了才有意义。
3. **保留回退分支**并**打日志**——不静默。
4. 新断言**两个方向都实测**（改受保护侧 → exit 2；改 kit 侧 → exit 3；还原 → exit 0）。
   ★ 第一次测"受保护侧"时被旧清单先拦住（exit 2），**没有就此宣称新断言有效**，
   而是补测了 kit 侧才确认 exit 3 确实由新断言产生。

第 4 条是这几卷反复吃到的一个教训：
**"我改了 X，然后测试通过了"不等于"我测的是 X"。** 断言的验证也要有对照组。

## 七、还没验的（不许写成结论）

- 战斗服装了新 exe 之后，**帧解密/HMAC 是否真的通过** —— 完全未验，必须实机。
- `SEC_KEY = 0x00*16` 全零是否被客户端接受 —— 未验（全零在密码学上可用，但如果客户端把
  全零当作"未设置"的哨兵值，行为可能不同）。
- 战斗服 transport_key 公式与客户端是否一致 —— **未定**，本卷只是**拒绝在没有依据时改动它**。
- 战斗通道与大厅通道到底共不共用密钥材料 —— 未定，这正是 §2/§4 那条范畴问题的核心。
