# 162 · 探讨：链路上每一步都写好了，参数在中间掉了

> 配套论文：`162_大厅到战斗服交接对账_三处硬缺陷.md`

---

## 一、我以前会怎么回答

「大厅到战斗服的连接」这条线，我从 138 卷起陆续写过：
- 138 卷：`[0x76446B0]` clientState 闸门 <3
- 121/122 卷：帧层 AES + HMAC
- 战斗服那边：NAT / DTLS / PCDH

**每次都是「这一层清楚了」。但从来没有人把「大厅发出的参数」和「战斗服要的参数」摆在一张桌子上。**

这次摆了。半小时后发现 `security_key` 两边不一样。

---

## 二、最刺的一处

```python
# 大厅
SEC_KEY = b"\x00" * 16    # 注释: "真游戏服要配对的另一半, 暂用全 0"
open("battle_security_key.txt","w").write(SEC_KEY.hex())   # 写出 00...00
```

```c
// 战斗服
memset(b->security_key, 0x01, sizeof(b->security_key));   // 全 0x01
```

**而战斗服从来不读那个文件。** 全 src 搜 `battle_security_key`：零个 `fopen`。

### 这意味着什么

- 大厅以为自己把 key 传下去了（**写了文件**）。
- 战斗服以为自己用的是对的（**注释写着「客户端 build 1649370 的 live 映射对 ID 1 保留 0x01 默认值」**）。
- 两者从没对上过。

**这套 `security_key` 参与 `SHA1(shared_x28 || security_key16)` 派生 `transport_key`，也就是帧加密和 HMAC 的根。**

⇒ **只要这个值错了，后面全错，而且表现为「握手看起来成功，但 HMAC 一直 BAD」。**

---

## 三、为什么这种错最难发现

因为**两边代码都没错**。

- 大厅：`SEC_KEY` 有值、文件写出了、日志打出来了（`已写出 battle_security_key.txt = 0000...`）。看起来完全正常。
- 战斗服：`security_key` 有值、注释有出处、派生函数用了它。看起来也完全正常。

**错的地方在「中间那一跳」，而中间那一跳没有任何代码。**

### 这类缺口有个共同特征

> **A 往通道里放东西，B 从通道里拿东西，但 A 放的位置和 B 拿的位置不是一个。**

我在 158 卷给这个模式起过名：「写好了没接线」。现在这是第 4 次（`bind_world` / `model_index` / `netchan` / `security_key`）。

**四次都不是"不会做"，是"做了但没对上"。**

## 四、`127.0.0.1:28960` 也是同一个毛病

```python
# 大厅
GAME_IP = (127,0,0,1); GAME_PORT = 28960
# 注释: "先按配方里的既定值填…与 SHARED.md 记的『21/5 含 127.0.0.1:28960』一致"
```

「与 SHARED.md 记的一致」= **与抓包观测到的一致**。

但抓包观测到的是**当年那个服务端**发的值。**我们现在的大厅监听在 `127.0.0.2`，战斗服绑 `0.0.0.0:28960`。**

- 地址能通（0.0.0.0 包含 127.0.0.1）✅
- 但**它是抄来的，不是算出来的**

如果哪天战斗服换端口，这里就会静默出错 —— 因为没有任何代码校验「我告诉客户端的地址」==「战斗服实际监听的地址」。

## 五、第三个：静默不启动

```python
def maybe_start_battle_server(bind, port, lobby_bind):
    if lobby_bind != "127.0.0.2": return None      # 只写日志
    if not os.path.exists(FLAG):  return None      # 只写日志
    if not os.path.exists(script): return None     # 只写日志
```

**三个条件任一不满足，战斗服就不起，且不报错。**

而 `run_all.py` 默认也会起一份。源码自己警告「两处同时起会抢 28960 端口」。

⇒ **有两种失败模式（都不起 / 抢端口），都只留一行日志。**

## 六、所以「清晰了吗」

**链路清晰，参数不清晰。**

| 层 | 状态 |
|---|---|
| 协议格式（NAT/DTLS/ECDH/帧加密） | ✅ 清楚（121/122 卷 + battle.c 实读） |
| 交接时序（21/5 → 21/1 → 6/14 → 28960） | ✅ 清楚 |
| **参数传递（key / 地址 / 启动）** | ❌ **三处对不上** |

这个区分很重要：

> **我把「协议搞清楚了」当成了「连接问题搞清楚了」。**
> 协议是「怎么说话」，参数是「说什么」。前者我挖得很深，后者从没系统查过。

## 七、我现在最想验证的一条（不需要启动游戏）

**客户端到底期望 `security_key` 是 `0x00…` 还是 `0x01…`？**

战斗服注释说「客户端 build 1649370 的 live 映射对 ID 1 保留 0x01 默认值」——**这句话有出处吗？还是也是猜的？**

判据：
1. 在客户端镜像找 `codol_derive_transport_key` 的等价实现（`SHA1(shared || key16)` 这个形状）
2. 看它那 16 字节从哪来（内嵌常量 / 大厅下发 / KDF 派生）

**这条一查，0x00 还是 0x01 就定案。** 而且这是**纯静态**，不用跑游戏。

## 八、方法论（本卷新增四条）

1. **★★ 「协议清楚了」≠「连接清楚了」。** 协议是「怎么说话」，参数是「说什么」。
2. **★★ 两个组件之间「有代码」≠「接上了」。** 要查的是 A 的写点与 B 的读点是不是同一个位置。
3. **★★ 占位值必须追到落实。** 「暂用全 0」这种注释，等于承认「这里没做完」，但它长得像做完了。
4. **★ 抓包观测值 ≠ 部署值。** 抄来的地址在换端口时会静默失效。
5. **★★ 第 4 次「写好了没接线」⇒ 应该列一份「组件间参数传递清单」，而不是逐次发现。**
