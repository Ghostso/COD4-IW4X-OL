## 一、231 卷我说了什么，这一卷推翻了什么

231 卷我写：

> 「三个响应回调用的是逐字相同的判据：`cmp byte [reply+5], 0` ⇒ `==0` 就 `state=2`。
> **我们回的"空页"= `reply+5 == 0`（无数据）⇒ 客户端判定失败。**」

这句话在**商城的上下文里是对的**（我验了三个回调：`0x4A7FBE`/`0x4A820D`/`0x4A83FC`）。

然后 232 卷我顺势推广：

> 「**同样的风险适用于上表每一项**：空 ACK 会让客户端走失败分支。」

**这一句没有验证。** 它是从"一个服务成立"推到"40.4% 都成立"。

本卷找到了 `0x4B55E0`：

```asm
0x4B5610  cmp byte ptr [edi + 5], 0
0x4B5614  jne 0x4B5729        ; ★ 非 0 就跳过，== 0 才继续
```

**和商城完全相反。**

| | `reply+5 == 0` | `reply+5 != 0` |
|---|---|---|
| 商城 | 失败 → state=2 | 正常处理 |
| 通道 135 | **正常处理** | **跳过** |

★ **同一偏移、同一指令形态、相反极性。**

## 二、这个错误有多危险

如果我按 232 卷的说法去做服务端修复：

> 「40.4% 都是空 ACK 导致失败，需要逐项填充真实数据」

那么对通道 135 这类服务（`==0` 才继续），**填充真实数据反而会让它跳过**。**修反了。**

而且这种错误极难发现 —— 客户端不会崩，只是"没反应"，和服务端没实现时的表现**一模一样**。

★ **这是本卷最值钱的一条：一个"已确认"的机制被外推到未经确认的服务上，产物是"看起来正确、实际反向"的修复。**

## 三、「+5」到底是什么

`0x684D93` 给了我线索：

```asm
0x684D75  cmp byte ptr [edi + 6], 0
0x684D83  jne 0x684E6D
0x684D89  cmp byte ptr [edi + 0x64], 0
0x684D8D  jne 0x684E6D
0x684D93  cmp byte ptr [edi + 5], 0
0x684D97  jne 0x684E6D
0x684D9D  cmp byte ptr [edi + 4], 0
0x684DA1  je  0x684E6D
```

**它同时查 `+6`、`+0x64`、`+5`、`+4` 四个字节。**

⇒ `+4/+5/+6` 不是"一个状态字节"，而是**一个三元标志组**（加上 `+0x64` 是第四个）。各服务按自己需要的位判定。

这和 DML 对象头部的常见设计一致：几个 bool 挤在同一 dword 的低字节。

**⇒ 231 卷把它叫"数据有无状态字节"是过窄的定性。** 正确说法：**`reply` 对象头部 `+4/+5/+6` 是标志组，语义由消费方定义。**

★ **这和 176 卷「同偏移读写两侧可不同值」是同族，但更进一步：同一偏移在不同服务可以是不同含义。**

## 四、234 卷也被我推翻了

234 卷我写：

> 「这类函数在 `0xB80xxx~0xB81xxx` 区密集排列」

本卷发现的第三个 getter 是 `0xB7A9B0` —— **在 `0xB7Axxx`**。

★ **两个样本（`0xB80D90`/`0xB81250`）→ 归纳出一个范围 → 第三个样本就在范围外。**

这和 233 卷的"猜兄弟函数在附近，实际隔 190KB"是同一个毛病：**从 1–2 个样本归纳出的"规律"，在第三个样本上就崩。**

正确做法：**扫 SEH cookie `0xC8B753` 拿全族**（234 卷自己提出的方法），而不是靠地址范围断言。

**我提出了正确的方法，却没有用它来做那个范围断言。** 这是本卷最该记住的一条。

## 七、一句话
