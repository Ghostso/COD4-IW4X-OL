## §3 ★★★★★ 断点锁定：`dwLobbyImp+0x4F0` 从未被赋非零值

### 3.1 全镜像写点穷举

```
0x008B3F7D  mov [r0+0x4F0], r1     (别处对象)
0x00AD8EDC  mov [r3+0x4F0], r0     (别处对象)
0x00B7A406  mov [r1+0x4F0], r0     ★ 0xB7A400：srpc+0x4F0 = dwLobbyImp
0x00B823FE  mov [r6+0x4F0], r3     ★ dwLobbyImp ctor：= 0（ebx）
0x00BA92C0  mov [r6+0x4F0], r7     ★ dwLobbyImp dtor：= 0（edi）
0x00BA9333  mov [r1+0x4F0], r0
```

**对 `dwLobbyImp+0x4F0` 而言，只有 `0xB823FE`（ctor）和 `0xBA92C0`（dtor）两处，
且都是写 0。**

### 3.2 三个 dump 一致

| dump | `+0x4F0` | `+0x278` | srpc |
|---|---|---|---|
| `DUMP_20261031_194250` | **0** | 0 | `0x397D3978` |
| `DUMP_20261031_200456` | **0** | 0 | `0x3AE3A110` |
| `DUMP_20261031_221458` | **0** | 0 | `0x3AC89CB8` |

**⇒ 与 139 卷的五层门完全对应：第 1 层（`dwLobbyEventHandler` 存在）就没过。**

### 3.3 因果链

```
dwLobbyImp+0x4F0 == 0
  ⇒ 0xB838A0 消息泵里 cmp dword [edi+0x4F0], 0 / je 0xB836DC  ⇒ 所有 opcode 直接跳过
  ⇒ 0xB7B210 / 0xB7B300 永远不被调用
  ⇒ 0x6371F0 房间消息处理器永远不执行
  ⇒ rec+0x01 永远为 0
  ⇒ 三条派发函数静默跳过
  ⇒ 房间内按钮全部无反应，且客户端不报错
```

★ **这就是用户描述的「准备/改阵营/投票点了没反应，但客户端不报错」的完整机制。**

## §5 诚实边界

1. **哈希桶数组未捕获**：`0x3ABC8990` / `0x3ABC9890` 落在 dump 的 64 KB 页间隙，
   无法读出「名字→类型号」的具体条目。
2. **`0x3AC89CB8` 之前的 srpc 头部（`+0x00..+0x1EC` 之外）未全读**。
3. **dump 时未进房间**（`+0x278 = 0`、成员数 = 0），
   因此房间内的运行时状态（`rec+0x90` 等）无法验证。
4. **`dwLobbyEventHandler` 为何没被创建** —— 只知道它从未被赋值，
   不知道创建函数在哪、为什么没执行。**这是下一个要追的目标。**

## §7 方法论

1. ★★★★★ **静态推断必须用运行时验证**：vtable、表偏移、字段语义，
   三类都能在 dump 里一次性对账。
2. ★★★★ **"字段恒为 0"要穷举写点**：`+0x4F0` 只有 ctor/dtor 两个清零写点，
   这就是"从未创建"的机械证明。
3. ★★★★ **dump 的采样粒度决定能看到什么**：64 KB 页粒度会漏掉页间的桶数组。
4. ★★★ **三个时间点的 dump 互相印证**：三次都是 0，排除"dump 太早"的可能。
5. ★★★ **断点在"对象未创建"，不在"逻辑错误"** ——
   与记忆 `codol-myhandler-never-created-root-cause` 是同一类故障。
