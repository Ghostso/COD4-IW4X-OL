# 136 探讨 · 「下界」是怎么变成「精确值」的：三个数字怎样互证

> 配套：[136 · AS 面静态收口：825 个注册器（精确）+ 62 个 Flash 回调全表 + 类型标签判据](136_AS面静态收口_825注册器与62个Flash回调全表.md)
> 性质：方法论复盘 + 对 135 的一处精度修正。
> 主题：**上一卷我给出的是"≤825"；这一卷它是"825"。差别不在推理，在**我自己的一个常数上限**。**

---

## 一、`≤825` 与 `825` 之间，隔着一个 `maxlen=40`

135 卷我写过：

> ⇒ `tools/as_regfns_v2.json` 的 828 至少含 3 个非注册器（`0x6A7650`/`0x6AEBD0`/`0x728350`）⇒ **真注册器 ≤ 825**。

当时我用的是自己的重验过滤器：**"体内（到首 `ret`）是否存在 `push <可打印短名>`"**，报"找不到短名的共 7 条"，我逐一打开看了 3 条（`0x6A7650`/`0x6AEBD0`/`0x728350`）确认不是注册器，剩下 4 条（`0x650FA0`/`0x69D040`/`0x69D340`/`0x6AF380`）我**在上一卷里明确写了"它们是真注册器，说明我的过滤器偏严"**——但**我没有回头去改那个过滤器**，于是结论停在"≤825"。

这一卷只做了一件事：

```
cstr(va, maxlen=40)   ->   cstr(va, maxlen=200)
```

结果：

```
总数 828; 体内找不到'短名 push'的: 3
   0x006A7650 / 0x006AEBD0 / 0x00728350
```

那 4 条**全都找回了名字**，而且它们的长短正好说明问题：

| 注册器 | 名字 | 长度 |
|---|---|---|
| `0x650FA0` | `AS_ShowShoutcastAndUpdateBypassMouseInput` | 41 |
| `0x69D040` | `AS_GetTimeInMillisecondsUntilNextBatchOfItemsExpire` | **49** |
| `0x69D340` | `AS_UnequipItemByIDFromAllCharacterLoadouts` | 41 |
| `0x6AF380` | `AS_TryToUpdatePrimaryWeaponCountToPartyMember` | 45 |

**40 个字符**：4 个里 3 个超一点点（41/45/49），一个 41。而 **39 个字符以内**的短名有八百多个，全都安全。

★★ **教训：一个常数上限制造了一个"看起来诚实"的不精确值。**
"≤825"读起来像是谨慎（留了余地），实际上是**我的工具参数在替我做判断**。
**"未找到"的第一步永远是：查我自己传进去的那个数字。**

★ 这条与 124 卷「长度本身就是结构证据」是一枚硬币的两面：长度足够时它是**证据**，长度设错时它是**过滤器**。

## 二、为什么上一卷只敢说"下界"，这一卷可以说"精确"？—— 因为判据的**两端都有界**

上一卷（135）说的"窗口会跨界"是针对 134 的错：

> 134 的判据是「体内**前 0x300 字节**内有 vtable 写」——对只有 0x2D 字节的 `0x728350`，这个窗口**伸进了下一个函数**。

135 我吸取教训的方式是"再加一条判据"。但这一卷真正有用的一句话是：

> **判据的窗口上界应当是函数自己的 `ret`。**

因为：
- 上界 = **`ret`** ⇒ 不会读到邻居（治 134 的病）；
- 下界 = **入口** ⇒ 不会读到"块首对象之前"（治 132 的病）。

两个界都钉死之后，判据的输出就**只有两种可能**：命中 / 不命中，而**不命中就真的不存在**。
⇒ 这才敢把"≥3 条不是注册器"变成"**恰好 3 条**"，把"≤825"变成"**825**"。

★★ **教训：判据的精确度，取决于它的边界在哪；边界不明确时，只能说下界。**

## 三、62 这个数，为什么值得单独立一节

本卷最"贵"的结果不是 825，是 **62**。

原因：**同一个数被三种不同性质的东西独立打出。**

| 路 | 性质 | 数 |
|---|---|---|
| ① RTTI 局域类名（`._SF_Handler@?<n>??Init@UiCpp<View>@@`） | **数据** | 28 / 11 / 6 / 5 / 5 / 4 / 3 |
| ② 分批函数体内的 `push esi; call <注册器>` 计数 | **代码** | 28 / 11 / 6 / 5 / 5 / 4 / 3 |
| ③ 132 卷独立枚举的 RTTI 计数 | **数据（另一轮）** | 28 / 11 / 6 / 5 / 5 / 4 / 3 |

★★ **注意 ①③ 是"同类"（都是 RTTI），所以严格说互证强度靠 ①⊗② 这一对异质证据。**
上一卷我说过"28 三路独立复现"——**这句话要精确一点**：三路里有两路是同一类证据（RTTI），真正跨层的是"**数据层（RTTI 名）⊗ 代码层（调用计数）**"。

★ 这条观察还顺手闭合了 135 §6 的一个模糊：
135 我把 `0x748A70 → 28` 记为"上层 = `0x748A70`"，标注"VA 来自近似锚定（弱证据）"。
本卷给出**不依赖那个 VA 的旁证**：**28 的 handler 数**由 RTTI 名独立给出，且**每个 View 的分批函数计数与它逐一相等**。
⇒ **弱证据（VA）被强证据（数字一一对应）托住了。** 这正是"命名要落在结构上"的另一种写法：**允许弱证据存在，但要让强证据去检验它。**

## 四、用「重复」否证「索引」

序号 `?<n>` 前后我犯过两种相反的错：

- **132**：把 `?N@` 说成声明顺序 ⇒ **对**，但没说清"什么在按顺序"。
- 本卷：我一度想把它读成"该 View 的 handler 序号"。

否证只用了一条**极便宜**的观察：

> **`?P@`（=25）同时出现在 `UiCppMatchSelectView` 和 `UiCppItemListView`。**

一个**全局/跨 View 的索引不可能在两个 View 里取同一个值**。
再加一条量级反证：**MatchSelectView 的最大序号是 337，而它只有 28 个 handler**。

⇒ 两条否证合起来，只剩一个解释：**序号索引的是「`Init` 内全部局域类型」的声明序号**，handler 只是其中一部分。

★★ **教训：要否证一个"索引假设"，只要找到"同一个索引值指向了两个不同对象"。一个反例就够了。**
★ 反面也一样灵：**如果要证明"索引是各容器独立的"，就去找"同一个值出现在两个容器"——找到了就否证"全局序"；找不到，反而支持它。** 这是**可判定的**，不需要读编译器源码。

★ 附带发现一个**反直觉**的事实：**序号在地址上倒挂**（序号大的字符串存在更低地址）。
⇒ **不能用地址顺序去推声明顺序**。我第一版笔记里正是这么推的，靠这条才没写进结论。

## 五、把「没有」说成「没有」——"类型名未定"是怎么定的

135 §边界 我写的是：**`0x0A`（掩码 0x8F 后）语义未定**。
本卷我能把它从"未定"推进到"**确定地拿不到**"，靠的是两步：

1. **证明它是类型标签**（而不是业务标志）：
   `and eax,0x8F` 出现 **2801** 次，其后 `cmp al,imm8` 的取值**只有 5/6/9/10 四种**，另有 `cmp eax,1`。
   一个"业务标志"不会在全镜像里被**八百多个不同函数**用同一个掩码与同一个常量反复比较 ⇒ **它是通用判据**。
   （旁证：`mov [reg+0xC], imm32` 的 imm 主值恰好是 0..10 的小枚举。）
2. **证明类型名不可达**：
   按关键字穷举 RTTI —— `Scaleform` 133 条 / `GFx` 86 条，但 **`Interpreter`/`Movie`/`Sprite`/`Loader`/`GFxPlayer`/`AVMP`/`ASVM` 全 = 0**。
   ⇒ **AS3 虚拟机类没进 RTTI 表**。
   ⇒ 所以"类型 0x0A 叫什么"**在这份镜像的数据面不存在**，不是我没找到。

★★ **教训：「未定」要分两种——"我还没找到"与"这里没有"。前者是待办，后者是结论；把后者写成前者，会让下一卷（或下一年的我）白跑一趟。** 而区分它们的方法就是：**先穷举一遍，把"全 0"写进结论。**

★ 这也解释了本卷 §8-1/§8-2 两条边界为什么**不必再花力气**（至少静态面不必）——它们不是"缺口"，是**边界**。

## 六、一个意外收获：`RefCountImplCore` 与 `FunctionHandler` 不是同一个"父类"

133/135 两卷都写：

> `mov [eax],0xDC7AF4`（父类 vptr）→ `mov [eax+4],1` → `mov [eax],<自身 vtable>`

本卷用 `vtable[-1] → COL → type_info(ti+8)` 这条链一查：

```
0xDC7AF4 -> .?AVRefCountImplCore@Scaleform@@
0xDC7BA4 -> .?AVFunctionHandler@GFx@Scaleform@@
```

⇒ **ctor 写的是 `RefCountImplCore` 的 vtable，`[+4]=1` 是引用计数；dtor shim 写的才是 `FunctionHandler`。**
⇒ 两卷把它们都叫"父类 vptr"，**不算错**（都是基类子对象），但**丢掉了信息**：`RefCountBase` 三段式 ctor 的痕迹（基类 vptr + refcount + 派生 vptr）被压成了一个模糊词。

★★ **教训：把"基类 vptr"当一个词用时，会顺手丢掉"这是引用计数对象"这一整类信息。** 而**只要把 vtable 反查成类名，模糊词自动变成精确词** —— 成本是 6 字节的 COL 链。

★ 而且这条链**顺手给了 133 的 `as_name_to_vtable.json` 一个完全独立的交叉验证路径**：任何 vtable 都能反查出 `AS_*` 名，**不再依赖注册器体内的那个字符串常量**。
⇒ **同一结论有了两条独立的证据链（字符串侧 / 结构侧），这才是"闭环"。**

## 七、这一卷的形状

| 项 | 上一卷的状态 | 本卷 |
|---|---|---|
| 真注册器数 | **≤825**（下界） | **825（精确）** |
| View 站点 | 数字 28/11/6/5/5/4（VA 弱证据） | **62 个回调全表 + 7 个分批函数一一对应** |
| `?<n>` 序号 | "声明顺序"（未追问） | **= `Init` 内全部局域类型的序号；不能当 handler 序号** |
| `0x0A` 判据 | 语义未定 | **= 全局值类型判据（2801 处，值域 {5,6,9,10,1}）；类型名"这里没有"** |
| 非唯一调用者 | 10 个未解释 | **8 个跨容器注册 + 2 个非注册器** |
| 父类 vptr | "父类 vptr" | **ctor=`RefCountImplCore`(refcount=1) / dtor=`FunctionHandler`** |
| 聚合对象 `[0xc77bb98]` | 只知"被读写" | **创建点/销毁点/生产者（`manager->vt[0x60]`）** |

★★ **一句话：本卷没有发现新的"C++ 层秘密"，它把上一卷的每个"大约/至少/未定"都推进到"精确/恰好/这里没有"。**
上一卷是**开口**（找到三层、找到 62、找到 828 的 3 条假），本卷是**收口**（把每个口都合上，或者明确地钉上"到此为止"）。

★ 与 135 的关系正是我上一卷写的：
> **「完整性 ≠ 正确性」；「一个假数字会生出一窝假结论」。**
本卷补一句：
> **「精确性 ≠ 谨慎」——写"≤"不等于安全，可能只是工具上限在替我保守。**

## 八、方法论（本卷新增 / 修订）

1. ★★ **"未找到"先查自己的过滤器常数**（`maxlen=40` 制造了 4 个假阴性）。
2. ★★ **判据的两端都要有界**：上界 = 函数自己的 `ret`，下界 = 入口 ⇒ 才能从"下界"升到"精确值"。
3. ★★ **异质互证才算互证**：同类证据数两遍 ≠ 两路证据。
4. ★ **否证"索引假设"用"重复值"**；**反证"独立序"也用"重复值"** —— 可判定，不需要读编译器。
5. ★ **"未定"要分"没找到"与"这里没有"**：先穷举，把全 0 写进结论。
6. ★ **把"基类 vptr"这类模糊词换成"vtable 反查类名"，模糊信息自动变精确**（6 字节 COL 链的成本）。
7. ★ **同一结论要有两条独立证据链**（字符串侧 ⊗ 结构侧）才算闭环。
