# 120 · `0x6b`/`0x6c` 尾部 u32 语义收口 —— `body首u32` 是**恒等于 `byteLen/4` 的重复字段**

> 项目：使命召唤OL 大厅（build 1649370 / 3.19）
> 前卷：`113_数组标签6b6c与28任务参数.md`（§"`0x6c` body 首 u32 恒等于 u32 元素总数"）、`INDEX §七 #5`（"尾部 u32 语义未定"）
> 本卷：把 `0x6b`/`0x6c` 的 **`body` 首 u32** 与 **尾部 u32** 各自定性，闭掉 §七 #5 的主体
> 证据：`array_tail_u32.txt`、`array_tail_close.txt`

---

## §0 结论

| 字段 | 语义 | 验证 | 可信度 |
|---|---|---|---|
| `byteLen`（`08` 后的 u32） | **body 字节长度** | **362/362** 精确 | ★★★★★ |
| `body[0:4]`（body 首 u32） | **恰好等于 `byteLen / 4`**（= body 的 u32 元素总数） | **`0x6b` 159/159；`0x6c` 160/160** | ★★★★★ |
| **尾部 u32**（body 之后的 u32） | **`0x6b`：恒 = `body首u32 - 1`（159/159）；`0x6c`：不是元素总数，是"另一维度容量"** | 见 §2 | ★★★★（6b）/ ★★★（6c） |

★ **一句话**：`0x6b`/`0x6c` 的结构是 `[tag][08][u32 byteLen][body][u32 tail]`，其中 **body 首 u32 是同义重复的"元素数 = byteLen/4"**（不是数据结构的一部分，是**冗余的校验/自描述字段**）。**尾部 u32 不是"元素数"，是另一个量**——两家语义不同。

## §1 `byteLen` 与 `body首u32` 都已 100% 钉死

`array_tail_u32.txt`：

```
byteLen(声明 u32) == len(body) : 362/362
```

`array_tail_close.txt`：

```
tag=0x6B: bl==bodylen 159/159, bf==bl/4 159/159
tag=0x6C: bl==bodylen 203/203, bf==bl/4 160/160
```

★★ **`body首u32 == byteLen/4` 在 `0x6b` 全 159 条、`0x6c` 全 160 条（有 body 的）零例外。**

这是 `113` 卷结论的**精确化**：`113` 说"body 首 u32 恒等于 u32 元素总数"，本卷补上**分母**——它等于 `byteLen/4`。

**为什么它是"冗余字段"而不是"数据"**：
- 若 body 是 u32 数组的数据，首 u32 应该是数组的**第 0 个元素**，值应随业务变；
- 但实测它 **恒等于 `byteLen/4`**，与业务内容无关 ⇒ **它是序列化器自己写的自描述头**（"我这里有 N 个 u32"），数据从 `body[4:]` 才开始。

★★ **⇒ `0x6b`/`0x6c` 的 body 真结构是 `[u32 N=byteLen/4][N-1 个元素]`，不是 `[N][N 个]`。** `113` 卷写的 `body=[N][item×N-1]` 是**对的**，本卷给出更硬的等式（`N==byteLen/4`）。

## §2 尾部 u32：两族语义不同（本卷新结论）

### 2.1 `0x6b`（159 条，全在 `21/5`）

```
bl=4, bodyFirst=1, tail=0   ×159
tail == bodyFirst - 1        : 159/159
```

`21/5` 是 findSessions 的**空结果容器**。body 只有 4 字节 = `01 00 00 00`（"1 个 u32"），tail = 0。

★★ **`tail = bodyFirst - 1`，159/159 零例外** ⇒ 对 `0x6b`，尾部 u32 = **"元素数减一"** = **最后一个元素的索引**（0-based 末尾下标）。

**语义**：`tail` 存的是**末元素下标**，与 `N = bodyFirst` 天然相差 1。这是"长度-1"式的**索引**字段，不是长度本身。

### 2.2 `0x6c`（203 条，`28/1` 和 `28/4`）

| 用例 | byteLen | bodyFirst | tail | 次数 | 含义 |
|---|---|---|---|---|---|
| `28/1` PvE 关卡选择 | 0 | — | 0 | 43 | **空数组**：无 body，tail=0 |
| `28/1` | 4 | 1 | **131** | 25 | 1 个元素（选中索引），**tail=可选总数=131** |
| `28/1` | 4 | 1 | 1 | 12 | 1 个元素，tail=1 |
| `28/1` | 4 | 1 | 203/214/190/9 | 各 1 | 各局可选总数不同 |
| `28/1` | 8 | 2 | **5** | 24 | 2 个元素，tail=可选总数=5 |
| `28/1` | 8 | 2 | 4 | 1 | |
| `28/4` 已解锁内容 | 508 | 127 | **263** | 94 | 127 个已解锁 ID，**tail=总容量 263** |

★★ **对 `0x6c`，`tail` 是"可选空间的总容量"**（PvE 关卡总数 131/5、内容槽总数 263），**与 `bodyFirst`（已选/已解锁数）是两个不同的量**。

**⇒ `tail` 在 `0x6c` = 容量上限（capacity / domain size），不是元素数。** 与 `0x6b` 的"索引-1"完全不同。

### 2.3 为什么同标签两种语义？

`0x6b` 和 `0x6c` 语法相同（`08 + u32 len + body + u32`），但尾部 u32 语义**由业务决定**——这与 `09` 卷"`0x13` 内层格式属于业务"是同一个规律：

> **Demonware 的容器标签只保证"怎么读"，不保证"尾部字段是什么"。**

★★ **⇒ 不能给 `0x6b`/`0x6c` 的尾部 u32 起一个统一名字。** 本卷钉死的是：
- `0x6b`：`tail = N - 1`（索引语义）
- `0x6c`：`tail` = 业务容量（领域大小）

**一个标签，两个语义。写解析器时，`0x6b` 的 tail 可以用 `N-1` 校验，`0x6c` 的 tail 不能。**

## §3 对"改大厅"的可落地结论

1. **`28/1`（PvE 关卡选择）可直接构造**（`113` 卷已给模板，本卷补全字段语义）：
   ```
   6c 08 <u32 4> <u32 1> <u32 选中关卡id> <u32 可选总数>
   6c 08 <u32 8> <u32 2> <u32 id1> <u32 id2> <u32 可选总数>
   ```
   ★ 注意：**body 里第 0 个 u32 是 `N=byteLen/4`，不是第一个数据元素**。手工构造时必须先写 N。
2. **`28/4`（内容解锁）**：`6c 08 <508> <127> <126 个已解锁ID> <263>`。服务端回 `08 <cid> 08 32` 置解锁（`113` 卷）。
3. **`0x6b` 的 `N-1` 校验可用**：收到 `0x6b` 时若 `tail != bodyFirst-1`，说明解析错位。
