## 2. ★ 两种标签：`0x10` 与 `0x15`

| 标签 | 值 | 用法 |
|---|---|---|
| `writeBits(3)` + `writeData(u8)` | 3+8 | **无标签的裸字段** |
| `writeBits(0x10)` + 字符串 | 16 | **字符串** |
| `writeBits(0x15)` + 值 | **21** | **数字字段（8 或 32 位）** |

**`0x15 = 21`，而 ByteBuffer 里 `T_STRING = 0x10`。**

**⇒ 位流里 `0x10` 也是字符串 —— 与 ByteBuffer 同值。**

**⇒ 位流里 `0x15` 是"带长度前缀的整数"？**

**看 `0x15` 后跟的：**

```
writeBits(0x15)   → 21
writeData(&[obj+0x1c], 0x20)    → 32 位
```

**⇒ `0x15` 后跟 32 位值。**

```
writeBits(0x15)   → 21
writeData(&[obj+0x24], 8)       → 8 位
```

**⇒ `0x15` 后跟 8 位值。**

**⇒ 同样的 `0x15`，宽度不同！**

**⇒ `0x15` 不是"类型"，而是一个**字段序号**或**固定标记**。**

---

## 3. 判断：`0x15` 是字段序号

**21 在序列里反复出现，后面跟着不同宽度的值。**

**⇒ 它是"字段 ID 21"，而不是类型。**

**⇒ 位流的编码是：`writeBits(字段ID)` + `writeData(值, 宽度)`。**

**⇒ 而宽度由**写入方自己决定**（在 serialize 里硬编码）。**

**⇒ 读取方必须知道每个字段 ID 的宽度 —— 这就解释了为什么
`deserialize` 和 `serialize` 必须成对。**

## 4. 4 个字符串的位置很怪

**字符串出现在 `[+0x00]`、`[+0x08]`、`[+0x10]`、`[+0x18]`、`[+0x04]`。**

**注意最后一个：`[+0x04]` —— 它在 `[+0x00]` 之后。**

**⇒ 说明对象不是"按序排列"的，
而是按"字段 ID"访问的。**

**⇒ `[+0x04]` 是第 5 个字符串，但物理位置在第二个。**

**⇒ 这是一个"结构体 + 字符串池"的布局：
字符串对象（`std::string`，32 字节）交错存放。**

**每个 `std::string` 占 32 字节（MSVC 的 SSO 布局）：**

- `[+0x00]` 字符串 1
- `[+0x20]` 字符串 2（但这里用的是 `+0x08`？）

**矛盾。需要重新看。**

**更可能：这是一个 `std::string` 数组，
每个元素 8 字节（指针），所以 `+0x00/+0x08/+0x10/+0x18` 是 4 个连续指针。**

**⇒ 4 个字符串指针 + `[+0x04]` 是另一个指针？**

**`+0x04` 在 `+0x00` 和 `+0x08` 之间，说明对象布局不是 8 字节对齐。**

**⇒ 或者 `[+0x04]` 是一个独立的 32 位字段，
被当成字符串指针用了。**

**（这可能是反汇编里的寄存器复用造成的误读。）**

## 5. 保守结论

**确定的部分：**

- **5 个字符串字段**（各自 `len*8+8` 位）
- **8 个 u8 字段**（3+8 位）
- **2 个 u32 字段**（21 + 32 位）
- 标签 `0x10`（字符串）与 `0x15`（数字字段 ID 21）

**不确定的部分：**

- 字符串的物理布局（`+0x04` 的位置可疑）
- `0x15` 到底是字段 ID 还是类型
