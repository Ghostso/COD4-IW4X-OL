## 一、第一次：以为"房间消息走 6/5"

起点很自然：`6/5` 叫 `ReadQueuedMessages`，语义上就是"读排队消息"，房间事件当然是排队消息。

**推翻它用了两路独立证据：**

1. **类型域**：`6/5` 的 `0x7FE600` 只覆盖 type **1..0x15**，而 `RoomStateUpdated=0x17`、`Vote=0x1A` **都越界**（`0x7FE673 ja 丢弃`）。
2. **全局变量**：`6/5` 用 `0xE5716C0`（队伍数组）/`0xE5713EC`（观察者链），房间用 `[ebx+0x105D8]`/`+0xE368`/`+0x10768` —— **两套完全不相交**。

★ **教训一：名字像 ≠ 语义是。** `ReadQueuedMessages` 这个英文名是我自己从 ol-mod 对来的，而 ol-mod 不是这个 build。

## 二、第二次：以为"房间消息在 11/4 的 blob 里"

理由看起来很硬：`11/4` 是 `setRoomData`，房间数据当然在里面；而 `0x6371F0` 要两个 blob，`11/4` 正好有个 blob。

**推翻只用了一个测试** —— 拿真实 `11/4` 数据喂 `0x637000` 的判据：

```
ready族 18 1c 5a 98…  首5位 = 3 ✓  但后续 3位 = 4 ✗
room族  02 02 00 00…  首5位 = 0 ✗
TLV外层 0a 88 77 66…  首5位 = 1 ✗
```

**全部走不通。**

★ **教训二：在"改服务端"之前，先用真实数据验证你的格式假设。** 这个测试只花了 5 分钟，却挡住了一整轮白改。

★ 而且它顺带揭示了一个更大的事实：**`dwRoom` 是比 srpc 更上层的一层，语料里从未出现过**。所以"语料里找不到"不是"我搜得不对"，是**它本来就不在语料里**。

## 三、第三次：以为"VERIFIED 修好了"

这是最痛的一次。

我当时的推理链是：
1. 发现 `lobby_server.py` 有两个版本（GOLDEN `D7EEB456` / VERIFIED `FF473204`）
2. VERIFIED 里有 `build_startgame_payload`（注释写"严格对齐 `0x00625BE0`"）
3. 而我独立逆出来的序列化器正好是 `0x625BE0` —— **两个独立来源给出同一结构**
4. 所以用它应该能修好

**跑了，无效。**

★ 但要注意：**第 3 步的互证是真实的**。VERIFIED 的注释和我逆出的结构确实一致。**错的是"注释一致 ⇒ 实现正确"这个跳跃** —— 注释说的是"对齐序列化器"，但 `build_room_push` 的信封（`u32(8)+u64+str+u64+blob`）根本不是客户端要的 `tag 0x13` 双 blob 结构。

★★ **教训三：代码里的注释说的是"我打算做什么"，不是"我做对了什么"。**

★ 更深的教训：**"两个来源一致"只能证明"设计意图一致"，不能证明"这条路径能走通"。** 我把"意图吻合"当成了"功能可用"。

## 五、字节级逆向这个方法的两次"自我修正"

### 第一次：位流写入器的位序

我按 `0xB777C0` 逐指令还原了写入器，写自测：

```python
bw.write_bits(0b101, 3); bw.write_bits(0b11010, 5)
# 我断言 = 0xBC，实际 = 0xBA
```

**是我的断言写错了，代码是对的**（`101` + `11010` MSB-first = `10111010` = `0xBA`）。

★ 但这次"失败"有价值：它逼我手算了一遍位序，确认了 `shr al,cl` + `shl bl,cl` 是 **MSB-first**。

### 第二次：47 type 全表扫不出来

早期扫 `mov [reg],imm32` 找构造器，**全部落空**。真因：

```
构造写在栈上：mov dword ptr [ebp-0x2014], 0xdc7528
不是：        mov dword ptr [eax], 0xdc7528
```

★★ **教训五：扫描的"寻址形态"决定了你能找到什么。** 这和 138 卷"判据窗口要双向设防"、137 卷"判据两端都要有界"是**同一族**——**判据的形式本身就是盲区**。

★ 这条最后靠 `0x628320` 的 `mov al,[esi+4]` 反向锚定才破：从"序列化器怎么读"反推"构造器怎么写在哪"，而不是正面扫。

## 六、三个新发现的"硬规则"

这一卷挖出来的不只是"某个地址是什么"，而是**三条会让服务端直接失效的规则**：

| 规则 | 违反后果 |
|---|---|
| dwRoom 消息首个 u64 必须是 `0x1122334455667788` | `0x7E7C90` 不命中 ⇒ 消息丢弃 |
| Manifold 条目 64 位必须是 `0` 或本机账号 ID | `0x637166` 摘链释放 ⇒ 元素丢弃 |
| 位流字段码必须逐位对齐（客户端 `cmp` 断言） | 类型错误 |

★★ **这三条是"静默失败"型的**：不崩、不断连、无报错，**就是没反应**。

★ 这解释了整个排查为什么这么难：**我们之前所有"推送了但没用"的尝试，很可能都撞在这三条上，而客户端一声不吭。**

★★ 由此得出一条通用判据：**当"发了东西但完全没反应"时，优先怀疑"格式对但路由键/归属字段错"，而不是"格式错"。** 路由错是静默的，格式错通常会断言。

## 八、给下一卷的硬约束

1. **动手前先 hash 版本 + 报出来**（不只校验受保护文件，要校验**实际跑的**那份）
2. **最外层的格式假设，先用一个真实样本喂给判据**（5 分钟 vs 一轮）
3. **"发了没反应"优先查路由键/归属字段**，不是查格式
4. **注释是意图，不是证明**；两个来源一致只证明设计一致
5. **扫描前先问"这个值可能被写在哪几种寻址形态里"**（栈/堆/寄存器/结构体）
6. **对照实验 > 相关性推断**（删一个开关 vs 看到两个现象同时出现）
