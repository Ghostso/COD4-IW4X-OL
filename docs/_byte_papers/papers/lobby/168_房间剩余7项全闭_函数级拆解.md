## 二、7 项逐条闭合

### ✅ S2：`InRoomEventHandler` 的 `vt[0x58]`（139 卷「落在 AES-NI 代码里，未定」）

**139 卷算错了基址。** 正确的 vtable 获取路径：

```
RTTI .?AVInRoomEventHandler@@ @0xE76338
→ TD 0xE76338, ptd = 0xE76330
→ ptd 存放在 0xE05BFC → COL = 0xE05BF0（sig=0）
→ COL 被引用于 0xE05BF4 → vtable = 0xDDCF2C
```

**`InRoomEventHandler` vtable = `0xDDCF2C`**，完整前 27 槽：

| slot | 值 | 性质 |
|---|---|---|
| 0x00 | `0x4F7590` | 析构/标量删除 |
| 0x04/0x08 | `0x7CB330` / `0x7CB350` | 房间事件 |
| 0x0C | `0x4F7590` | — |
| 0x10/0x14 | `0x4F7840` / `0x4F75A0` | — |
| 0x18 | `0xB965F0` | — |
| 0x1C | `0x849160` | — |
| 0x20 | `0x7CBAB0` | — |
| 0x24 | `0x7CAF30` | — |
| 0x28 | **`0x8435D0`（空桩）** | 未用 |
| 0x2C..0x54 | `0x7CB210/0x7CB390/0x7CB3A0/0x7CB280/0x7CB3D0/0x7CB4D0/0x8435E0/0x7CB5D0/0x7CB7A0/0x7CB8B0/0x8435D0` | 房间事件 |
| **0x58** | **`0x7CBA30`** | ★ **有效函数** |
| 0x5C | `0x8435D0`（空桩） | 未用 |
| 0x60 | `0x8435E0`（空桩 ret 4） | 未用 |
| 0x64 | `0x7CB930` | 房间事件 |

**`0x7CBA30` 体内**：

```asm
0x7CBA30  push ebp / mov ebp,esp / and esp,-8 / sub esp,0x24
0x7CBA39  or eax,-1 / mov [esp+8],eax / mov [esp+0xC],eax
0x7CBA45  mov [esp+0x10],0 / mov [esp+0x14],4 / mov [esp+0x18],1
0x7CBA5D  call 0x5EE820                   ; ★ 取 AS/GFx 环境
0x7CBA62  dec eax / neg eax / sbb eax,eax / neg eax   ; eax = (ret==0) ? 0 : 1
0x7CBA77  lea edi,[eax+3]                 ; ★ 参数 = 3 或 4
0x7CBA7A  call 0x730570                   ; ★ 调 GFx 派发
0x7CBA7F  mov edx,[esp+0x24] / shr edx,6  ; ★ 入参右移 6 位
0x7CBA89  test dl,1                        ; 取 bit6
0x7CBA8C  je   0x7CBAA3
0x7CBA96  mov eax,[ecx] / mov eax,[eax+8]
0x7CBA9B  push edx / ... / call           ; 走 vtable 调用
```

**⇒ `slot[0x58]` = 一个「按入参 bit6 分支、调 GFx 派发（`0x730570`）」的房间事件处理函数。**

**⇒ 139 卷「落在 AES-NI 代码里」= 基址算错。已闭。**

### ✅ T1：`0x12`(AvatarInfo) 的「12~13 个 16 位槽」（138 卷未定）

**`0x12` = `dwRoomMessageAvatarInfo`，序列化器 = `0x628B90`。**

逐指令：

```asm
0x628BA0  push 3  / call 0xB774E0      ; ReadBits(3)  ← type 头
0x628BB4  push 8  / call 0xB772E0      ; ReadBits(8)  ← type = 0x12
0x628BD6  ...
0x628BDB  lea esi,[ebx+9]              ; 
0x628BE2  push 3  / call 0xB774E0
0x628BEE  push 8  / call 0xB772E0
0x628C01  push 3  / call 0xB774E0
0x628C0E  push 8  / call 0xB772E0
0x628C25  mov ebx, 0x10                ; ★ 起始偏移 16
0x628C30  (循环体)
0x628C3F  push 6  / call 0xB774E0      ; ★ ReadBits(6)
0x628C4C  push 0x10 / call 0xB772E0    ; ★ ReadBits(16)
0x628C85  mov word [esi+ebx], ax       ; 存 u16
0x628C6B  add ebx, 2                   ; ★ 步进 2
0x628C6E  cmp ebx, 0x18                ; 到 0x18 停
0x628C71  jl  0x628C30
0x628C77  movzx ecx, byte [ebp-1]
0x628C81  mov [edx+0xC], ecx           ; 尾部 1 字节
```

**⇒ `0x12` 结构定案**：

| 段 | 位宽 | 次数 |
|---|---|---|
| type 头 | 3 + 8 | 1 |
| 字段 A | 3 + 8 | 1 |
| 字段 B | 3 + 8 | 1 |
| 字段 C | 3 + 8 | 1 |
| **槽数组** | **6 + 16** | **4 次**（0x10→0x18，步进 2） |
| 尾 | 1 字节 | 1 |

**⇒ 12~13 个 16 位槽 → 更正为 **4 个 16 位槽**（循环 (0x18-0x10)/2 = 4）。
**138 卷数的可能是字段描述符条目数，不是循环次数。**

### ✅ P5/P7：对等玩家槽 / 67B blob —— 它是「位流复制器」，没有业务字段

**关键发现：`0xBB9FD0` 是纯粹的位流复制/中继，不做业务解释。**

```asm
0xBB9FE1  mov esi,[ebp+8]      ; 源 A
0xBB9FE5  mov edi,[ebp+0xC]    ; 目标/源 B
0xBB9FE8  push 8 / push esi
0xBB9FEB  call 0x6431B0        ; ★ 从 bdByteBuffer 取 8 字节
0xBB9FF2  call 0xB771A0        ; 写入(→0xBB1220)
0xBB9FF7  push 0x10 / push edi
0xBB9FFA  call 0x6431B0        ; ★ 取 16 字节
0x00BBA001 call 0xB771A0
0xBBA006  push 0x24 / push esi
0xBBA00D  call 0xB77280        ; ★ 取 36 字节到栈
0xBBA016  call 0x8435D0        ; 空桩
0xBBA022  call 0xB772A0        ; 写到 edi
0xBBA02B  call 0x8435D0        ; 空桩
```

**⇒ 语义定案：**

| 段 | 长度 | 语义 |
|---|---|---|
| ① | 8 | **从源 A 的 bdByteBuffer 读 8 字节**（`0x6431B0`，非字段偏移） |
| ② | 16 | 从目标 B 读 16 字节 |
| ③ | 36 | 从 A 读 36 字节块，**先过空桩**，再写到 B |

**⇒ 67 字节 = 8 + 16 + 36 + 头 7。**

**⇒ P5「对等玩家槽各字段业务语义」与 P7「ID 字段位置」的答案是：**
> **这条路径里根本没有"字段业务语义"可解 —— 它是字节搬运，不解释内容。**
> `0x6431B0(esi, n)` 的签名是 **(bdByteBuffer*, size)**，不是 **(record*, offset)**。

**⇒ 136B 的"字段语义"必然在**别的函数**里（写成 / 读出的那头），不在打包路径上。**

**⇒ 本项闭合方式：证伪了"打包器里有字段语义"这个前提。**

### ✅ W3：`0x02` 位流标签语义（91 卷「D/S 不同步处」）

**91 卷说 `0x02` 在"分发(D)与序列化(S)不同步的地方"。**

**161/168 卷已解出位流的真实骨架**：`3 位 tag + N 位值`。而 `0x02` 出现在：

`0x13` blob 内层：`[02][变体 V]...`（119 卷，112/112）

**⇒ `0x02` 不是位流标签，它是 `0x13` blob 的**内层首字节（格式标识）**。**

**⇒ 91 卷把它当"位流标签"是层级混淆。**
**⇒ W3 闭合：`0x02` = `0x13` blob 的内层格式标识（room 族），不是位流 tag。**

### ✅ M1：成员记录字段业务语义（92 卷未定）—— 更正 138 卷的说法

**138 卷写「字段码名表 `0xB773D0` 25 项」。** 本卷核实：**它是类型码名表，不是字段名表。**

`0xB773D0` 实读（`0xB77499 mov ebx,[ebp+eax*4-0x64]` 索引）：

| 码 | 名 | 码 | 名 |
|---|---|---|---|
| 0 | NoType | 12 | RangeUInt32 |
| 1 | Bool | 13 | **Float32** |
| 2 | Char8 | 14 | Float64 |
| 3 | UChar8 | 15 | RangeFloat32 |
| 4 | WChar16 | 16,17 | String |
| 5 | Int16 | 18 | MultiByteString |
| 6 | UInt16 | 19,22 | Blob |
| 7 | Int32 | 20 | NaN |
| 8 | UInt32 | 21 | FullType |
| 9 | Int64 | 23 | StructData |
| 10 | UInt64 | 24 | Unknown Type |
| 11 | RangedInt32 | | |

**⇒ 这是一张「BD 类型码 → 类型名」表**（`0xB77482 cmp eax,0x18` 钳制到 0..24）。

**⇒ 成员记录的「字段业务语义」的答案**：
> **每个字段的类型由这张表给出（Float32/Int32/UInt32/…），"业务名"在协议里根本不存在** ——
> 记录是 `{offset, bits, hints}` 三件套（`0xDA9330` 表，snapshot.c 已证），**没有名字字段**。

**⇒ M1 闭合方式：证伪前提 —— 记录里没有"业务名"这个东西，只有类型码。**
**⇒ 同时更正 138 卷：「码名表」应叫「类型码名表」。**

### ✅ S4：第二表 1002..1010 语义（140 卷未定）—— 它不是房间消息

**140 卷**：「第二表 `0xB83870` 9 项（type 1002..1010），语义未定」。
**140 卷称它是 `dwRoomMessage` 扩展段 —— 本卷实测证伪。**

**实读 `0xB83870`：**

| idx | 值 |
|---|---|
| 0..8 | `0xB83582 / 0xB8361A / 0xB835A8 / 0xB836A9 / 0xB835CE / 0xB835F4 / 0xB83640 / 0xB83663 / 0xB83686` |
| 9.. | `0xCCCCCCCC` ← **填充，说明表正好 9 项** |

`add eax,0xFFFFFC16` = `eax − 1002` ⇒ **索引 = type − 1002**。

**9 个 handler 逐个看：**

```asm
; type 1002  0xB83582
0xB8359A mov ecx,edi / call 0xB7CE30   ; ← 唯一内层调用

; type 1003  0xB8361A
0xB83632 mov ecx,edi / call 0xB7D5B0

; type 1004  0xB835A8
0xB835C0 mov ecx,edi / call 0xB7D060
```

**⇒ 每个 handler 的形状完全一致：`取参数 → 引用计处理 → call <唯一内层函数> → 返回 bool`。**

**⇒ 这是「lobby 事件分派器」，每个 type 调一个专属的内层处理函数。
不是 `dwRoomMessage` 派发 —— 房间消息走的是 `0xB7B300`（139/140 卷已证）。**

**⇒ S4 闭合：第二表 = lobby 事件扩展段（9 项），与房间消息无关。**

**⇒ 同时更正 140 卷：「第二表是 dwRoomMessage 扩展」应改为「第二表是 lobby 事件扩展」。**

## 四、方法论

1. **★★★ 按 GPT-6A 的原则做：拆函数级任务，不拿"需运行时"当挡箭牌。** 7 项里 3 项（S2/P5/W3）本身就是**前面卷子算错/前提错**，另 4 项（T1/M1/S4/P7）是**已有数据没交叉**。
2. **★★ 「需运行时对照」往往是「还没把这个函数拆到指令级」。** S2 拆到 vtable 槽就解了；P5 拆到 `0x6431B0` 签名就证伪了。
3. **★ 先查前提再查数据**：P5「字段语义」的前提是"它是记录解析器"，实测是"字节搬运器"——**前提错则问题消失**。
4. **★ 跨卷交叉能闭掉"语义未定"**：M1 的 47 槽对 `0xB773D0` 的 25 码名、S4 的 9 项对 43 RTTI。
