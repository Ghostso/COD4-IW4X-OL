# `configs_s.info` · 探讨：一个"给什么都行"的文件

> 对应：`lobby/23_configs_s_only_binary.md`

---

## 一、它看起来很重要

`configs_s.info` —— 名字叫"配置"，25KB，高熵二进制。

**第一反应：一定是核心配置，加密的。**

---

## 二、然后我看到了 `bak_dummy`

```
configs_s.info.bak_dummy    311 字节
54 BD F1 C2 C7 04 8C 32 ...
```

**311 字节的随机数据，不是原文件的子串。**

**这个文件存在的意思：有人试过用垃圾替换它。**

---

## 三、这说明什么

如果替换垃圾就崩，就不会留下这个备份。

**备份的存在 = 替换成功过 = 客户端不校验内容。**

---

## 四、对比其它 publisher 文件

看谁有 `bak_dummy`：

```
configs_s.info.bak_dummy        311B   ← 垃圾
market_ui.info.bak_dummy         16B   ← 几乎空
market-down.info.bak_dummy       45B   ← 略小
tlogconfig.info.bak_dummy        92B   ← 略小
whitelist_tester.info.bak_dummy  30B   ← 略小
mp_playlists_*.info.bak_dummy   976B   ← **结构完整，只是精简**
```

**只有 playlist 的 dummy 是"结构正确的精简版"，其它都是"随便写点"。**

**因为这符合逻辑：playlist 被解析（需要结构），其它只是被读取/忽略。**

---

## 五、这个发现的实用价值

**"给什么都行"的文件，可以完全不用管。**

不用去解 `configs_s.info` 的格式，不用找它的密钥，
直接给个空文件或随机字节就行。

**这减少了一大块"不必要的逆向工作"。**

---

## 六、一个反例警告

但我要标注清楚：**"bak_dummy 存在"不等于"一定没影响"**。

可能是：
- 替换后大厅能进，但某个功能（商城/活动）坏了没被注意到
- 或者只在某个场景下才校验

**所以我的结论是"看似可以"，不是"确定可以"。**

---

## 七、方法论收获

> **`bak_*`、`*_dummy`、`*_off` 这类文件是实验日志。**

它们记录了"什么被替换过"。
**替换成功的留下了（因为要 restore），失败的删掉了。**

所以：

```
存在 bak_dummy  →  这个文件曾被替换过，且实验继续下去了
```

**这是判断"某文件是否可替换"最快的线索。**
