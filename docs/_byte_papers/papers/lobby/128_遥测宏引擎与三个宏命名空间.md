# 128 · 遥测宏引擎与三个宏命名空间 —— `${...}` 到底谁在替换

> 项目：使命召唤OL 大厅（build 1649370 / 3.19）
> 前卷：`123`（71/3·71/7）、`124`（71/15）、`126`（模板总表）、`127`（54 条模板 + 统一信封）
> 本卷：**126/127 一直挂着的"宏引擎实现地址未定位"，本卷定位并解剖**
> 证据：`tools/dis_640fd0.py`、`tools/macro_ref_search.py`、`tools/macro_engine_report.py`、`tools/macro_placeholder_hits.py`、`tools/codo_macro_table.py`

## §0 结论（五句）

1. **替换 `${TIMESTAMP_PLACEHOLDER}` / `${CLIENT_IP_PLACEHOLDER}` 的引擎 = `0x640AB0`（file）/ `0x0040AB0+`VA `0x640AB0`→** 实际 VA `0x00640AB0`，它是**遥测专用**的。
2. **`${TIMESTAMP_OFFSET(%d)}` 只被它引用一次**（`0x240B87`）——这就是 127 卷 §3 里 `call 0x2404b0` 之后真正干活的那一段。
3. **调用约定已实证**：`0x49AA26 push ${TIMESTAMP_PLACEHOLDER}` → `0x49AA2B push <ClientLoadTime 模板>`，**模板是 arg1（fmt），占位符是 arg2，填模板的第 1 个 `%s`** ⇒ 每条事件的第 2 字段都必然变成 `${TIMESTAMP_OFFSET(-N)}`。
4. **`${CODOID(...)}` / `${ZONEID(...)}` 只存在于模板字面量里，客户端里没有它们的独立串**（`${ZONEID(%llu)}` 独立串引用数 = 0）⇒ **遥测引擎不解释它们，原样透传**。
5. **`${CODO_*}` 是同名的另一套系统**：6 条在腾讯配置替换器（`0xB6A70`/`0xB6D10`，表在栈上），5 条在腾讯 TLog 消息替换器（`0xA567xx`，表在栈上）。**和遥测不是同一套。**

## §1 引擎 `0x640AB0`：逐字节解剖

```
0x640AB0  push ebp / mov ebp,esp / sub esp,0x13c
0x640AC9  mov edi, ecx            ; ★ 这是 __thiscall: ecx = 输出缓冲指针
0x640AC4  mov ebx, [ebp+8]        ; in  = 输入格式串
0x640ADD  call 0xc74510           ; 取串长度
0x640B00  ← 循环头
0x640B00  push 0xdbb744           ; '${TIMESTAMP_PLACEHOLDER}'   (0x9BB744)
0x640B05  push esi
0x640B06  call 0xc3c990           ; strstr
0x640B0B  push 0xdb4cf8           ; '${CLIENT_IP_PLACEHOLDER}'  (0x9B4CF8)
0x640B11  ...                     ; strstr
0x640B2F  je 0x640BFF             ; 没有 TIMESTAMP 占位符 → 走 IP 分支
0x640B35  test ebx,ebx
0x640B39  cmp eax,ebx / jae 0x640BFF   ; ★ TIMESTAMP 出现在 IP **之后** → 交给 IP 分支
0x640B41..0x640B6E                ; 取"本条目的基准 tick"([in+0x14] 或 [in+0x10])
0x640B74  mov eax,0x10624dd3 / imul / sar edx,6 / shr eax,0x1f / add
                                   ; ★ 精确的 "除以 1000" 魔数 → 毫秒转秒
0x640B86  push 0xdc6fc4           ; '${TIMESTAMP_OFFSET(%d)}'   (0x9C6FC4)
0x640B91  push 0x100              ; ★ 时间串缓冲 256 字节
0x640B97  call 0x774900           ; snprintf
0x640BB9  call 0xc3c740           ; memmove 前置段
0x640BDC  call 0xc3c740           ; 写入时间串
0x640BFA  jmp 0x640B00            ; 继续找下一个占位符
0x640BFF  test ebx,ebx / je 0x640C80
0x640C06  push 0x16 / lea edx,[ebp-0x1c] / call 0x77be30   ; ★ 长度参数 0x16 = 22
0x640C14..0x640C1E                ; 结果串长度（到 NUL）
0x640C37  call 0xc3c740 / 0x640C5D call 0xc3c740   ; 用 IP 串替换
0x640C80  收尾: memmove + 终止 NUL
```

### 1.1 两个占位符的分工

| 占位符 | 串地址 | 替换成 | 规则 |
|---|---|---|---|
| `${TIMESTAMP_PLACEHOLDER}` | `0x9BB744` | `${TIMESTAMP_OFFSET(-N)}`，N = `(条目tick − 基准tick)/1000` | 取**负偏移**（早于基准则为负） |
| `${CLIENT_IP_PLACEHOLDER}` | `0x9B4CF8` | 客户端 IP 串（长度上限 `0x16`=22 字节，够 `255.255.255.255`） | 直接插值 |

★★ **"除以 1000" 的魔数 `0x10624dd3 + sar 6` 是标准 `/1000`**，所以 N 的单位是**秒**。
语料里 `UIPage|${TIMESTAMP_OFFSET(-21)}|…` 的 21 就是**21 秒**。

★ `0x640B39 cmp eax,ebx / jae` 说明**优先级**：若 TIMESTAMP 出现在 CLIENT_IP 之后，先处理 IP（`0x640BFF` 分支），再回头循环。**两个占位符都处理，顺序按出现位置**。

### 1.2 前传：`0x6404B0` 建立的"时间基准"

引擎要算 `条目tick − 基准tick`，而条目本身只存了事件发生时的秒数。基准来自 `0x6404B0`：

```
0x6404C4  cmp byte [0xe5735b],0       ; 全局"遥测使能"
0x6404EF  cmp dword [0x849b5cc],0     ; 是否已初始化
0x6404F8  call esi                    ; 取当前 tick → [0x81aa118]
0x6404FF..0x64051E                    ; 取另两个时间基准 → [0x81aa110]/[0x81aa114]
0x64052A  imul edx,edx,0x3e8          ; ★ 秒 × 1000 → 毫秒
0x640546  imul eax,eax,0x3e8
0x640555/58/5B  add edx/ecx/eax, ebx  ; + 当前tick 偏移
0x64055E  call 0x640100               ; 建条目
0x64057E  push '${CLIENT_IP_PLACEHOLDER}'
0x640584  call 0xc3c990               ; strstr
0x640590..0x6405A0                    ; 命中 → 用 [0xc911f4c/50] 那组
0x6405A7..0x6405B6                    ; 否则 → 用 [0xc8e4054/58] 那组
0x6405BE  cmp ecx,-1
0x6405C3  mov ecx,0x1388              ; ★ 缺省偏移 5000 ms
0x6405CB  cmp eax,[0xe69bdc] / 取较小者
```

**语义**：`0x6404B0` = "登记一个带时间戳的遥测条目"，秒→毫秒（×1000），并把 4 个时间基准写进条目；缺省偏移 `0x1388` = **5000 ms**。

## §2 调用约定实证：模板 = arg1，占位符 = arg2

★ 本卷最有价值的一条证据，在 `ClientLoadTime` 的日志函数里：

```
0x49AA04..0x49AA25   若干 push（各字段实参）
0x49AA1B  push 0xdb4cf8   ; '${CLIENT_IP_PLACEHOLDER}'
0x49AA1E..0x49AA25   push eax / ecx / eax / ecx / edi / esi
0x49AA26  push 0xdbb744   ; '${TIMESTAMP_PLACEHOLDER}'
0x49AA2B  push 0xddbbd0   ; 'ClientLoadTime|%s|%llu|%llu|${CODOID(%llu)}|%s|%d|%d|%s|%s|%s|%s|%s|%u|%s|%d|%d'
0x49AA30  lea eax,[ebp-0x408]
0x49AA36  push 0x400 / push eax
0x49AA3B  call ...        ; snprintf(缓冲, 1024, 模板, ……)
```

cdecl 从右往左压栈 ⇒ **最后一个 push 的是 arg1**。所以：

| 位置 | 实参 |
|---|---|
| **arg1** | **模板串**（`ClientLoadTime|%s|...`） |
| **arg2** | **`${TIMESTAMP_PLACEHOLDER}`** |
| arg3.. | 字段值（`push esi`/`edi`/`ecx`/`eax`…） |

**⇒ 模板第 1 个 `%s` 就是 arg2，也就是那句字面量 `${TIMESTAMP_PLACEHOLDER}`。**

**这解释了 127 卷 §5 对账里"为什么第 2 字段永远是时间表达式"**：不是巧合，是**每条事件的第二个参数都固定传这个占位符**。
`81 个 `${TIMESTAMP_PLACEHOLDER}` 引用点** = 45 个日志函数（其中若干函数压多次）**，分布在 `0x06FF30`~`0x3F7BA0`。

### 2.1 例外：8 个函数用 `${TIMESTAMP}`（绝对时间）

`${TIMESTAMP}`(`0x9B48E4`) 有 9 个引用点，其中 8 个正是下列事件的日志函数：

| 引用点 | 事件函数 | 对应事件 |
|---|---|---|
| `0x0759C6` | `0x75EF0` | `LoadoutChangeEvent` |
| `0x0E7170` | — | `UIClickCount` |
| `0x27577B` | — | `STUNServerPingResult` |
| `0x32BA57` | — | `QuestionnaireResult` |
| `0x35614C` | — | `TencentCrossInit` |
| `0x357AF7` | — | `GameMomentsEdit` |
| `0x37C23F` | — | `ComError` |
| `0x37DB0C` | — | `ClientException` |
| `0x0B7DD6` | — | **未定**（不在这 54 条模板的引用点里） |

★★ **语料直接印证**：
```
LoadoutChangeEvent|${TIMESTAMP}|16701785630074219790|${CODOID(...)}|…
```
**这条的第 2 字段就是字面量 `${TIMESTAMP}`，不是 `${TIMESTAMP_OFFSET(-N)}`。**
⇒ **遥测有两种时间口径**：这 8 个事件记**绝对时间**，其余记**相对偏移（秒）**。

## §3 第二个引擎 pass：谁处理 `${TIMESTAMP_OFFSET(%d)}`

`${TIMESTAMP_OFFSET(%d)}`(`0x9C6FC4`) 全镜像 **1 个引用点：`0x240B87`** —— 就在本节这个函数里。

而同一个函数还引用 `${CLIENT_IP_PLACEHOLDER}`（`0x240B0C`）。所以：

```
0x640AB0   第一遍:  ${TIMESTAMP_PLACEHOLDER} → ${TIMESTAMP_OFFSET(-N)}
                   ${CLIENT_IP_PLACEHOLDER} → IP 串
0x240?      第二遍:  ${TIMESTAMP_OFFSET(%d)} → 实际偏移量
```

**诚实边界**：第二遍函数的入口我还没用 `55 8b ec` 定位到（`0x240B87` 附近是循环体，函数可能更大或用了别的序言）。**只确认了"它引用 `${TIMESTAMP_OFFSET(%d)}`"与"它和第一遍不是同一个函数"**。

★ 但有一个更省的解释要先排除：`0x640AB0` 自己**已经**用 `${TIMESTAMP_OFFSET(%d)}` 做 snprintf 的格式（`0x640B86` 就是 `push 0xdc6fc4`）。所以那 1 个引用点**很可能就是引擎自己的 snprintf 格式参数**……可是引擎里的 push 在 `0x240B86`，而搜到的是 `0x240B87`。

**逐字节核**：`0x240B85 push eax` / `0x240B86 push 0xdc6fc4`。`0xdc6fc4` 的字节序列 `c4 6f dc 00` 从 `0x240B87` 开始 —— **`0x240B87` 正是那条 push 的立即数位置，不是新的引用点。**

★★ **⇒ 本卷撤回"第二遍引擎"的假设。`${TIMESTAMP_OFFSET(%d)}` 的 1 个引用点 = 引擎自己 snprintf 的格式参数，没有第二遍。**

这条必须写出来：我的"引用点搜索"用 `struct.pack("<I", ptr)` 匹配的是**立即数字节**，而 `push imm32` 的立即数就长这样。**"引用"二字把两种完全不同的东西（真指针数据 vs 指令立即数）混在了一起。** 127 卷用同样方法得出的"48/54 单引用点"要按这个理解复查：那批引用点本来就是 `push` 指令，结论（内联，无表）不变，但推理链要写清。

## §4 `${CODOID}` / `${ZONEID}`：客户端不解释它们

| 宏 | 独立串引用数 |
|---|---|
| `${CODOID(%s)}` (`0x9B4CD0`) | 1（`0x775ED`，`MissingLocalizedString` 函数） |
| `${CODOID(%llu)}` (`0x9B4CE0`) | 2（`0x77642`、`0x214F2B`） |
| **`${ZONEID(%llu)}`** | **0（不存在独立串）** |
| `${ZONEID(...)}` 其它形态 | 0 |

★★ **⇒ `${ZONEID(%llu)}` 从来没被单独引用过** —— 它只出现在模板的**中间**（如 `MissingLocalizedString|...|%s|${ZONEID(%llu)}`）。
**客户端里没有任何代码去查找这个子串。** 所以结论是：

- `${CODOID(x)}` / `${ZONEID(x)}` **只是模板文本的一部分，引擎不解释，原样发出去**；
- 语料里看到的 `${CODOID(16701785630074219790)}` **是 printf 填充 `%s`/`%llu` 之后的产物**，不是替换出来的。
- **⇒ 服务端的 TLog 解析器必须自己认这两个宏。** 这是**协议契约**，不是客户端行为。

★ 顺带：`${CODOID(%s)}` 与 `${CODOID(%llu)}` **两种形态并存**（前者用于字符串参数、后者用于整数 ID）—— 模板里哪个字段是 `%s`/`%llu` 就配哪种，**说明宏是"跟着 printf 类型走的文本"**，进一步佐证"它不被解释"。

## §5 `${CODO_*}` 与 `CODOID` 无关 —— 是腾讯配置系统

6 条 `${CODO_*}` 全部只被 **2 个函数**引用：

| 宏 | 串 | 引用点 |
|---|---|---|
| `${CODO_OPENID}` | `0x9B79D8` | `0xB6A8C` / `0xB6D32` |
| `${CODO_JUMP_SIGNATURE}` | `0x9B79E8` | `0xB6B0C` / `0xB6D64` |
| `${CODO_ZONE}` | `0x9B7A00` | `0xB6B9B` / `0xB6D3C` / `0x1A8034B` |
| `${CODO_TCLS_ZONE}` | `0x9B7A10` | `0xB6BF3` / `0xB6D46` |
| `${CODO_NAME}` | `0x9B7A24` | `0xB6C50` / `0xB6D50` |
| `${CODO_LEVEL}` | `0x9B7A34` | `0xB6C9D` / `0xB6D5A` |
| `${TITLE_ID}` | `0x9B7A68` | `0xB6F2C` / `0xB7034` |

### 5.1 替换器 `0xB6A70` = `if/else if` 链

```
0xB6A8B  push '${CODO_OPENID}' / push esi / call 0x774710(strstr)
0xB6A9D  jne → 0xB6B0B
        …取 OPENID：cmp dword[0x331c5c0],1 ⇒ 调 0x641560(0x331c5c4) 填 0x3ff 字节…
0xB6B0B  push '${CODO_JUMP_SIGNATURE}' … jne → 0xB6B9A … 填 0x1ff 字节
0xB6B9A  push '${CODO_ZONE}' … jne → 0xB6BF2 … sprintf('%d', [0x81a9eb8])
0xB6BF2  push '${CODO_TCLS_ZONE}' … jne → 0xB6C4F … sprintf('%d', [0x331caf8])
0xB6C4F  push '${CODO_NAME}' … jne → 0xB6C9C … strncpy 自 [[0x8269854]+0xc]，0x400
0xB6C9C  push '${CODO_LEVEL}' … jne → 0xB6CF3 … 0x50c550 → sprintf('%d')
0xB6CF3  都不匹配 → 原样返回长度
```

### 5.2 批量替换器 `0xB6D10` = 栈上 6 项数组 + 指针扫描

```
0xB6D2C  mov [ebp-0x42c], 0xdb79d8   ; ${CODO_OPENID}
0xB6D36  mov [ebp-0x428], 0xdb7a00   ; ${CODO_ZONE}
0xB6D40  mov [ebp-0x424], 0xdb7a10   ; ${CODO_TCLS_ZONE}
0xB6D4A  mov [ebp-0x420], 0xdb7a24   ; ${CODO_NAME}
0xB6D54  mov [ebp-0x41c], 0xdb7a34   ; ${CODO_LEVEL}
0xB6D5E  mov [ebp-0x418], 0xdb79e8   ; ${CODO_JUMP_SIGNATURE}
0xB6DD6  cmp eax,6 / jl 循环        ; 6 项
        → 取"最靠前出现的那个宏" → 调 0xB6A70 递归替换
```

★★ **⇒ 宏表是"栈上临时数组"，不是静态数据表。** 这解释了为什么在 `.rdata` 里找不到 `{宏名, 值}` 配对 —— **配对在代码里，一次 6 个 `mov`。**
这是 127 卷"没有注册表"结论的**同一种模式的第二次出现**：**这张客户端里，配置项普遍被编译期摊平，运行时不建表。**

### 5.3 第三个命名空间：腾讯 TLog 消息宏

5 条只被 `0xA567xx` 一个函数引用：

```
0x9CED84  ${CODO_MSG}
0x9CED90  ${CODO_CODE}
0x9CEDA0  ${CODO_EVENTTIME}
0x9CEDB4  ${CODO_TASKID}
0x9CEDC4  ${CODO_SCENEID}
```

引用点 `0xA56744/40/3C/38/34` —— **相邻的 5 个 `mov`**，同一模式（栈上局部数组）。

**⇒ 三个宏命名空间，三套实现，互不相干：**

| 命名空间 | 宏 | 实现 | 载体 |
|---|---|---|---|
| **遥测 TLog** | `${TIMESTAMP_PLACEHOLDER}` / `${CLIENT_IP_PLACEHOLDER}` / `${TIMESTAMP_OFFSET(%d)}` | `0x640AB0` | 硬编码 strstr 两遍 |
| **腾讯配置** | `${CODO_OPENID}` `${CODO_JUMP_SIGNATURE}` `${CODO_ZONE}` `${CODO_TCLS_ZONE}` `${CODO_NAME}` `${CODO_LEVEL}` `${TITLE_ID}` | `0xB6A70` / `0xB6D10` | if/else 链 + 栈上 6 项数组 |
| **腾讯 TLog 消息** | `${CODO_MSG}` `${CODO_CODE}` `${CODO_EVENTTIME}` `${CODO_TASKID}` `${CODO_SCENEID}` | `0xA567xx` | 栈上 5 项数组 |

## §6 遥测队列家族

`0xC911F4C..0xC911F60` 有 6 个相邻全局：

| 全局 | 角色 | 证据 |
|---|---|---|
| `0xC911F4C` | 队列 A 基址 | `0x640597` 把地址传给替换器 |
| `0xC911F50` | 队列 A 长度 | `0x640590 push [0xc911f50]` |
| `0xC911F54` | 队列 A 计数 | `0x640F44 sub [0xc911f54], edi` |
| `0xC911F58` | 队列 B 基址 | `0x6410E0 mov esi,[0xc911f58]`（冲刷） |
| `0xC911F5C` | 队列 B 附加 | `0x64001E mov edi,[0xc911f5c]` |
| `0xC911F60` | 队列 B 计数 | `0x640FE2 cmp [0xc911f60],0x400` |

另有 `0xC8E4054`/`0xC8E4058`/`0xC8E405C` 一组（断线/退出时专用队列，127 卷 §4 的 `0x640F5B call 0x6407F0` 就是它的条件判断）。

★ **同一个开关 `[0xe5735b]` 控制引擎、登记器、冲刷器、断线转储** ⇒ 这是**一个总开关**。

## §7 缓冲尺寸一览

| 尺寸 | 用途 | 出处 |
|---|---|---|
| `0x400` = 1024 | 队列上限；信封冲刷缓冲 | `0x640FE2`/`0x641112` |
| `0x400` = 1024 | `${CODO_NAME}` 拷贝上限 | `0xB6C69` |
| `0x400` = 1024 | `${CODO_TCLS_ZONE}` 输出上限 | `0xB6C13` |
| `0x100` = 256 | `${TIMESTAMP_OFFSET(%d)}` 时间串 | `0x640B91` |
| `0x3FF` = 1023 | `${CODO_OPENID}` 输出上限 | `0xB6AD3` |
| `0x1FF` = 511 | `${CODO_JUMP_SIGNATURE}` | `0xB6B1D` |
| `0x16` = 22 | `${CLIENT_IP_PLACEHOLDER}` 值上限 | `0x640C06` |
| `0x1388` = 5000 ms | 遥测默认时间偏移 | `0x6405C3` |
