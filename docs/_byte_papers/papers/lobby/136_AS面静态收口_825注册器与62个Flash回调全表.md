## §0 结论（八条）

1. **真注册器 = 825（精确，不再是下界）**。`as_regfns_v2.json` 的 828 条里，**恰好 3 条不是注册器**（`0x6A7650` / `0x6AEBD0` / `0x728350`）。判据换成**双向有界**的"函数自身范围内有 `push <短名串>`"，一次给出精确值。
2. **7 个 View 的 Flash 回调全表 = 62 个**，名字**直接写在镜像里**（零猜测）：
   `UiCppView` 3 / `UiCppMatchSelectView` 28 / `UiCppItemListView` 11 / `UiCppOnboarding` 6 / `UiCppSuggestedLoadoutView` 5 / `UiCppChallengesView` 5 / `UiCppNewItems` 4。
3. ★★★ **三方独立互证同一组数字**（62 = 28+11+6+5+5+4+3）：
   ① RTTI 局域类名计数（本卷）⊗ ② 分批函数的注册器计数（135）⊗ ③ 132 的 RTTI 计数。
   ⇒ **View 注册站点 = 7 个分批函数，一个 View 一个**；`0x7396F0`（3 个注册器）= 基类 `UiCppView` 三件套。
4. **序号语义收口**：`?<n>` 是 **MSVC 局域类序号**。证据：**同一序号在多个 View 里重复**（`?P@` 同时出现在 MatchSelectView 与 ItemListView）⇒ 不是跨 View/全局索引；且 MatchSelectView 的序号**最大到 337 而它只有 28 个 handler** ⇒ 序号索引的是「`Init` 内**全部局域类型**的声明序号（含非 Handler 的局域类型）」。
   ⇒ **132 的"`?N@` = 声明顺序"成立，但不能当作 handler 的序号来用。**
5. ★★ **类型标签判据收口（135 的 B3）**：`and eax,0x8F` 全镜像 **2801 处**，其后 `cmp al,imm8` 的取值域 = `{0x0A:2457, 0x09:9, 0x06:1, 0x05:1}`，另有 `cmp eax,1` 分支。⇒ `(x & 0x8F) == 常量` 是**全局通用的"值类型判据"**（不是业务标志）。旁证：`mov dword ptr [reg+0x0C], imm32` 直方图（1088 处）主值恰为 **0..10 的小枚举**（0×416 / 2×215 / 3×114 / 1×92 / 4×40 / 6×37 / 5×28 / 7×10 / 9×5 / 0x0A×4 / 8×3）⇒ `+0xC` 是**小枚举字段**。**0x0A 对应的类型名仍未定**（镜像里没有 Scaleform AS VM 的 RTTI）。
6. **非唯一调用者收口（135 的 B5）**：10 个 = **8 个注册器被 2–3 个分批函数调用**（= 同一 handler 注册到**多个容器**，如 `AS_IsInClan` 被 3 处调用）+ **2 个即已确认的非注册器**。⇒ 不是假条目；同时解释了 133 观察到的"同名多对象"（`AS_OnInit`/`AS_ShowView`/`AS_HideView` 在**每个 View 各注册一次**）。
7. ★★ **注册器身份机械闭环**：`mov [eax],<vtable>` → `vtable[-1]`(COL) → `type_info`(`ti+8`) → **RTTI 名 = `AS_<短名>`**。逐例验证通过（见 §6）。
   ★ 并**精确化 133/135 的字段描述**：ctor 的第一次写 `0xDC7AF4` 是 **`Scaleform::RefCountImplCore`** 的 vtable（引用计数基类），紧接的 `[+4]=1` 就是 **refcount=1**；写 `Scaleform::GFx::FunctionHandler` 的是**析构 shim**（`0x693DD0`），不是 ctor。
8. **全局聚合对象与 `GFx::Value` 布局（135 的 B4 收口）**：`[0xc77bb98]` 的**创建点** = `0x5EB9D0`（一次性，门 = `[0xc7ae9a0]`/`[0xc77bb98]` 双零），体内 `[0xc77bb98] = 0x4F70A0(manager) = manager->vt[0x60](&ctx16, 0, 0)`；**销毁点** = `0x5ED804`/`0x5EDA5F`（`mov [0xc77bb98], 0` + 析构 `0x830BE0`）。`GFx::Value`(32 位本 build) = **20 字节**（`+0xC` = 类型/标志字，`+0x10` = 附加——`0x730690` 里那格放的是**类名字符串指针**）。★ **各转发器 slot 的方法名仍未定**（无 RTTI）。

## §1 825：精确计数怎么得到的

判据（**双向有界**，专治 134 的跨界假阳性）：

> **一个真注册器 = 在 `[入口, 首条 ret)` 区间内存在 `push <指向可打印短名(≥3 字符)的 imm32>`。**

`tools/as_reg_vfy_135.py`（把 `cstr` 上限从 40 提到 200）在 828 条上跑：

```
总数 828; 体内找不到'短名 push'的: 3
   0x006A7650  (首 ret 在 +0x1D)
   0x006AEBD0  (首 ret 在 +0xEE)
   0x00728350  (首 ret 在 +0x2D)
```

**828 − 3 = 825。**

★ **为什么上一轮（135）只敢说"≤825"**：135 的同一工具用 **40 字符**上限，于是把 4 个**长名**注册器误判成"无短名"：

| 地址 | 真名 | 长度 |
|---|---|---|
| `0x650FA0` | `AS_ShowShoutcastAndUpdateBypassMouseInput` | 41 |
| `0x69D040` | `AS_GetTimeInMillisecondsUntilNextBatchOfItemsExpire` | **49** |
| `0x69D340` | `AS_UnequipItemByIDFromAllCharacterLoadouts` | 41 |
| `0x6AF380` | `AS_TryToUpdatePrimaryWeaponCountToPartyMember` | 45 |

⇒ 7 个"无短名"里 **4 个是假阴性（我的上限截断）+ 3 个是真非注册器**。**修正 135 的"下界"为精确值。**
★ 而 3 个真非注册器各自的性质上一卷已定：`0x6A7650` = 普通小函数、`0x6AEBD0` = 分批函数（尾 `pop edi; ret`）、`0x728350` = 惰性初始化。

**因此"825"是精确值，不是下界** —— 因为该判据的窗口**上界是函数自己的 `ret`**，不可能读到邻居。

## §4 序号（`?<n>`）到底是什么 —— 用**重复值**证伪"局部序号"

```
?1..?9      : 9 个（MatchSelectView 的 AS_* 命令族）
?L@ ?N@ ?P@ : 21,23,25（AS_GetWarGodPlaylist / OnRootModeClick / OnPveModeClick）
?BB@..?CP@  : 297,299,...,337（step=2，18 个 On* 回调）
```

两条否证：

1. **同一序号值出现在多个 View**：`?P@`(=25) 在 `UiCppMatchSelectView` 与 `UiCppItemListView` **都有**；`?1` 在 7 个 View 里都出现。
   ⇒ 序号**不是全局索引**，也不是跨 View 共享的编号。
2. **MatchSelectView 的最大序号 = 337，而它只有 28 个 handler**。
   ⇒ 序号索引的对象**远大于**"该 View 的 handler 数"。

⇒ **序号 = 「该 `Init` 内全部局域类型」的声明序号**（handler 只占其中一部分；其余是 SF 适配层/visitor 之类的局域类型）。
⇒ **132 说"`?N@` 是声明顺序"是对的，但要读作"局域类型的声明顺序"，不能当 handler 序号。**
★ 附带：序号在**地址上倒挂**（序号大的存在更低地址），所以**不能用地址顺序推声明顺序**。

### 未定案（诚实边界）
**两种 mangled 形态并存**：`@?<n>??Init@` 与 `@?<n>@??Init@`（多一个 `@`）。且 `OnSortClick` 在 ItemListView 里以 **25 与 300 两个序号各出现一次**。
⇒ 同一 `Init` 内存在**两种父作用域/mangling 路径**；**具体是什么未定案**（我没有把它写成结论，只记录现象 + 数字互证的**计数**不受影响：62/28/11/… 全部由两种形态一起数出，且与 135 的调用计数逐一吻合）。

## §5 类型标签判据：`(x & 0x8F) == 0x0A`

工具 `static_136.py` 扫 `and eax,0x8F`（`25 8F 00 00 00`）全镜像 **2801 处**，取其后的 `cmp al,imm8`：

```
{0x0A: 2457, 0x09: 9, 0x06: 1, 0x05: 1}
另有形态:  and eax,0x8F ; cmp eax,1 ; je ...    (83 F8 01 74 ...)
```

⇒ **`(x & 0x8F) == 常量` 是一个贯穿全镜像的"值类型判据"**，取值域只有 `{1,5,6,9,10}`，其中 **0x0A 占 99.6%**。
135 的 `(容器.flags & 0x8F) == 0x0A → bool` 只是这 2457 个实例中的一个 —— **它不是一个业务标志，而是"这个 `GFx::Value` 是不是 0x0A 类型"**。

旁证（`typefield_136.py`）：`mov dword ptr [reg+0x0C], imm32` 共 **1088 处**，imm 分布集中在 **0..10**：

```
0×416  2×215  3×114  1×92  4×40  6×37  5×28  7×10  9×5  0x0A×4  8×3   (其余偶发大值)
```

⇒ **`+0xC` 是一个小枚举字段**（与"类型标签"的位置一致）。

★ 掩码 `0x8F = 0x0F | 0x80` 的形状 ⇒ **低 4 位 = 类型，bit7 = 一个标志位**（本判据要求 bit7 = 0）。
★ **诚实边界**：**每个数值对应的类型名未定**。原因可查证：按关键字扫 RTTI（`Scaleform` 133 个 / `GFx` 86 个）**没有** `Interpreter`/`Movie`/`Sprite`/`Loader`/`GFxPlayer`/`AVMP`/`ASVM` 任何一个 ⇒ **Scaleform 的 AS3 虚拟机类没进 RTTI 表**，所以"类型名"这条路在静态面**不可达**（不是没找，是没有）。
★ 能拿到的名字只有：`Value`/`ObjectInterface`/`FunctionHandler`/`ASUserData`/`RefCountImplCore`（见 §6）。

```

★★ **这张表把 133/135 的两处字段描述精确化了**：

| 指令 | 133/135 的写法 | 本卷实测 |
|---|---|---|
| `mov [eax],0xDC7AF4` | "父类 vptr" | **`Scaleform::RefCountImplCore`** 的 vtable（**引用计数基类**） |
| `mov [eax+4],1` | "= 1" | **引用计数 = 1**（RefCountBase ctor 的典型内联） |
| `mov [eax],<自身 vtable>` | "自身 vtable" | ✓ 且该 vtable 的 RTTI 名 = **`AS_<短名>`** |

⇒ 133 的 `tools/as_name_to_vtable.json`（816 短名表）由此获得**完全独立**的交叉验证路径：**任一 vtable 都能反查出 `AS_*` 名**，无需依赖注册器体内的字符串。

★ 附带纠错：`RefCountImplCore` 是**基类子对象 vtable**，与"每对象共享的析构 shim `0x693DD0`"是**两个不同函数**（ctor vs dtor），133/135 把两者的"父类"写成了同一个类。⇒ **ctor 写 RefCountImplCore，dtor 写 FunctionHandler。**

0x4F70D6  mov eax,[ecx]; mov eax,[eax+0x60]      ; manager vt[0x60]
0x4F70DF  push 0; push 0; lea edx,[ebp-0x3c]; push edx; call eax
0x004F70F8 ret                                   ; 返回该调用的 eax
```
⇒ `[0xc77bb98] = manager->vt[0x60](&ctx(0x2000,-1…,size=0x10), 0, 0)`。

### 7.2 销毁
`0x5ED804` / `0x5EDA5F`：`mov [0xc77bb98], ebx(0)`，之前 `call 0x830BE0` 析构。同处把 `[0xc7ae9a0]` 也清零（`call 0x82F420`）。

### 7.3 `GFx::Value` 布局 = 20 字节
- 注册器的 Value：`[ebp-0x24] [ebp-0x20] [ebp-0x1c] [ebp-0x18] [ebp-0x14]` = **5 个 dword = 20 字节**（前 2 个 init 为 `-1`，后 2 个为 `0`，第 5 个由 `0x830BC0` 填）。
- `0x730690` 的局部 Value：`[-0x20..-0x10]` = `{-1,-1,0,6,"codo.common.CFunctionContainer"}` ⇒ **`+0xC` 格 = 6（类型），`+0x10` 格 = 类名字符串指针**。
▶ ⇒ **`+0xC` = 类型/标志字**（与 §5 的 `+0xC` 小枚举一致），**`+0x10` = 附加数据（字符串指针）**；`0x730690` 把类型写成 **6** 且载荷是字符串 ⇒ **类型 6 = 字符串**（这一条是"旁证级"，见 §8）。

★ `GFx::Value` 的对象接口类型在 RTTI 里**有名字**：`.?AVObjVisitor@ObjectInterface@Value@GFx@Scaleform@@`（`0xE730F0`）⇒ 注册器的 `[[edi+8]]->vt[0x14]` 是**对象接口的方法槽**（`setMember`/`invoke` 一类），**具体槽名未定**。

## §8 诚实边界

1. **`0x0A`/`0x09`/`0x06`/`0x05`/`1` 的类型名未定** —— 静态面不可达（AS VM 类不在 RTTI 表里，已用关键字扫证）。
2. **GFx 转发器 9 个 slot 的方法名未定**（同一原因：`[global+0xC]` 的对象类无 RTTI）。
3. **`?<n>@` 与 `?<n>??` 两种 mangled 形态的成因未定案**（现象 + 计数已固定；同名 `OnSortClick` 出现两个序号）。
4. **"类型 6 = 字符串"是旁证级**：来自 `0x730690` 一处（类型字段 = 6 且载荷为字符串指针），**未见第二处独立确认**。
5. **825 的前提**：`as_regfns_v2.json`（828 条）本身是 134 的产物。本卷只证明了"其中 3 条不是注册器"，**未用独立方法重算"真注册器集合"**。若 828 还含别的跨界条目（且恰好也压了短名），本卷的判据也会漏掉——但我没有找到这样的例子。
6. 所有结论只对**本镜像（3.19 / 1649370）**成立。

## §10 方法论（本卷新增）

1. ★★ **"下界"要回头查自己的**工具参数**：135 的 `cstr(maxlen=40)` 把 4 个长名注册器变成假阴性 ⇒ 一个常数上限制造了"≤825"这个不精确值。**凡"未找到"，先查自己的过滤器参数。**
2. ★★ **判据要有界的两端**：134 补了"上界"，本卷的判据把窗口**上界钉在函数自己的 `ret`**，于是既不受邻居污染，也不受数据区污染 ⇒ 一次得到**精确值**。
3. ★★ **数字互证要"异质"**：62 由 **数据（RTTI 名）** 与 **代码（调用计数）** 两路给出，且逐 View 全部一致 ⇒ 强度远超"同一方法数两遍"。
4. ★ **用"重复值"证伪"索引假设"**：如果序号是全局/跨 View 索引，它就不能在两个 View 里重复出现。**一个反例即可否证一类解释。**
5. ★ **"类型名未定"要说清是"没有"而不是"没找"**：先按关键字穷举 RTTI，确认 `Interpreter/Movie/Sprite/…` 全 0 ⇒ 才能写"静态面不可达"。
6. ★ **vtable 名可反查 ⇒ 把"字符串证据"升级为"结构证据"**：`vtable[-1]`(COL) → `ti+8` 一条链，独立于注册器体内的字符串。
