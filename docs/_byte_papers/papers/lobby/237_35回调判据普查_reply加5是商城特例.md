## §2 ★★★ 商城回调的完整判据顺序（补全 231 卷）

`0x4A7FB0` 的真实开头是：

```asm
0x4A7FB0  push ebp / mov ebp,esp / push ecx
0x4A7FB4  cmp  byte ptr [ebp + 0xc], 0      ; ★ 第一步：第二参数
0x4A7FB8  push esi
0x4A7FB9  jne  0x4A7FE7                     ; 非 0 → 走"有数据"分支
0x4A7FBB  mov  eax, [ebp + 8]               ; 第一步为 0 → 才看 reply
0x4A7FBE  cmp  byte ptr [eax + 5], 0        ; ★ 第二步：reply+5
0x4A7FC2  je   0x4A7FCD                     ; ==0 → 失败
0x4A7FC4  cmp  byte ptr [0x82C4A72], 0      ; ★ 第三步：请求在飞？
0x4A7FCB  jne  0x4A7FE3                     ; 是 → 直接返回
0x4A7FCD  or   dword [0x82C4AA4], 4
0x4A7FD4  mov  eax, 2
0x4A7FD9  mov  [0x82C4AEC], eax
0x4A7FDE  mov  [0x82C4A88], eax             ; state = 2
```

★ **231 卷只写了 `cmp byte [eax+5],0` 那一步，漏了前面的 `cmp byte [ebp+0xc],0`。**

**⇒ 完整判据是三步，不是一步：**

| 步 | 判据 | 含义 |
|---|---|---|
| ① | `[ebp+0xc] == 0?` | 第二参数（可能是"是否有错误"标志）—— 非 0 直接走数据分支 |
| ② | `reply+5 == 0?` | 数据有无 —— `==0` 判失败 |
| ③ | `[0x82C4A72] == 0?` | 是否有请求在飞 —— 非 0 静默返回 |

★★ **231 卷的根因结论不变**（空页 ⇒ `reply+5==0` ⇒ `state=2`），但**判据描述不完整**：第一步 `[ebp+0xc]` 才是最先判断的。

## §3 ★★ 修正 235 卷的错误推广

235 卷我写：

**本卷证明这是错的。** 正确的是：

| 说法 | 对错 |
|---|---|
| `cmp byte [reg+5],0` 在全库出现 6 次 | ✅ 事实 |
| 其中 3 个是商城回调（同一函数体的 4 处） | ✅ 事实 |
| ⇒ 它是"大厅通用判据族" | ❌ **推广错误** |
| ✅ 正确表述 | **`reply+5` 是商城私有；主流判据是 `[ebp+0xc]`（第二参数）；另有大量全局开关判据** |

★ **235 卷的"极性相反"观察仍然成立**（`0x4B5610` 的 `jne` vs 商城 `je`），但那两个用的是**不同对象的不同字段**，不是"同一判据的不同极性"。**235 卷把两件事混成一件了。**

## §4 ★ 三种判据形态的意义

| 形态 | 例子 | 含义 |
|---|---|---|
| **参数判据** `[ebp+0xc]` | 20 个回调 | 由**调用方**传入"成功/失败"标志 —— **最通用** |
| **对象字段判据** `[reply+N]` | 商城 3 处 | 由**服务端应答内容**决定 |
| **全局开关判据** `[0x8xxxxxx]` | 约 10 个回调 | 本地状态（是否在飞、是否已初始化） |

★★ **⇒ 服务端"回空 ACK"到底会不会失败，取决于该服务的回调用的是哪种判据：**

- **参数判据**（主流）：由**发送方**（客户端自己）决定 `[ebp+0xc]` 的值 —— **服务端回什么不影响**
- **对象字段判据**（商城）：由**服务端应答**决定 —— **回空就会失败**
- **全局开关**：与服务端无关

★★★ **这是一个可执行的结论**：**只有用「对象字段判据」的服务，服务端空 ACK 才会导致失败。按本卷普查，35 个回调里只有商城 3 处是这样。**

## §7 方法论

1. **★★★★★ 「全库出现 N 次」不等于「通用」——要看这 N 次是不是同一个函数体。** `[eax+5]` 出现 6 次，其中 4 次是商城同一函数的复制（其实只有 3 个入口），另外 2 次是无关模块。**235 卷被"6 次"误导成了"通用"。**
2. **★★★★ 判据有「参数/对象字段/全局开关」三种形态，只有对象字段判据与服务端应答内容相关。** 这直接决定了「空 ACK 会不会失败」。
3. **★★★ 反汇编必须读到"第一个业务判据"，不是读到"我关心的那个判据"。** 231 卷读到 `cmp [eax+5],0` 就停，漏了前面 3 条指令的 `cmp [ebp+0xc],0` —— 判据顺序完全颠倒。
4. **★★ 一个函数里的多处判据是「顺序」不是「并列」，不能只取其中一条当全部。**
