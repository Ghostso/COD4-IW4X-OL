## §1 方法更正：capstone 立即数**无 `0x` 前缀**

232 卷已记「capstone 立即数可能无 `0x` 前缀」。本卷**第一次真正踩上它**：

```python
# 错：push 9 的 op_str 是 "9"，startswith("0x") 为 False ⇒ 被当成寄存器 ⇒ None
if op.startswith("0x"): v=int(op,16)
# 对：
try: v=int(op,0)
except: v = regs.get(op)      # 寄存器/其它
```

只这一个修正，就把 **36 个 svc==None 的调用点**全部还原成 svc 3（`push 9` → 9 → 不对；
真正的是 `push 3`，op_str `"3"`；修正后 svc=3）。

★ **教训：解析器里"看着对但漏一种写法"的 bug，会把一整族数据静默归到 `None` 桶里，
而不是报错。** 36 个点全落进 `None` 桶时，"None" 看起来很合理（"大概是经寄存器"），
**这个合理外观正是它藏了两卷的原因。**

## §3 ★★★★ 宿主三段式骨架 + 建造器词汇表

### 3.1 宿主（如 `0x7FF500`）

```asm
0x7FF506  call 0x803830          ; srpc 单例
0x7FF50D  test esi,esi / je ret
0x7FF513  call 0xB7A670          ; ★ == 2 ?
0x7FF518  cmp  eax,2 / jne ret
0x7FF51D  push 0xDAE091          ; ★ 空串
0x7FF524  call 0xB80D90          ; ★ svc3 宿主 getter（234 的那种）
0x7FF529  ...
0x7FF551  call 0xB92140          ; 建造器
```
**⇒ 与 234 的模板逐字节同构**（`0x803830 → 0xB7A670()==2 → getter → 建造器`），
再次证明 `0xB7A670()==2` 是**所有 srpc 服务公共前置**，不是房间/商城私有。

### 3.2 建造器词汇表（以 task30 `0xB92140` 为样本）

```asm
0xB921AD  push 0x80000 / push 0x400 / push 0x1e / push 3
0xB921BE  call 0xBA72C0          ; 建头（svc=3, task=0x1e=30）
0xB921CE  call 0xBA7250          ; 写「带标签 dword」（源 = [ebx+8]）
0xB921D9  call 0xBA75D0          ; 写字符串/字节块（源 esi, 上限 0x40）
0xB921E5  call 0xBA71C0          ; 写「对象」（源 = [ebp+0x14]）
```

助手逐个反汇编：

| 助手 | 行为（反汇编证据） |
|---|---|
| `0xBA7250` | `push 1; push 0x10` → 写 **1 bit + 类型标签 0x10(16)**，再写值（源 `[ebp+8]`） |
| `0xBA75D0` | `call 0xC3FF30`(strnlen) → 写 **长度 + 字节**（`push edi; push 0; push len`） |
| `0xBA71C0` | 经 vtable 写 **对象**（`0xB85D20` 求串长，`0xB86000` 写出） |
| `0xBA74B0` | 经 vtable 写 **指针/对象**（有 `push 0`） |
| `0xBA7660` | 写 **字节块**（`call 0xB767D0`，`lea ecx,[edi+5]`） |
| `0xBA7120` | TaskBuilder **析构**（置 vtable `0xD5A64C`，释放 `[esi+0x2c]`） |
| `0xBA7300` | TaskBuilder **构造**（置 `[+0x1C]=svc` / `[+0x1D]=task`，与 233 一致） |
| `0xB76120(val,mask)` | `push 0xA; call 0xB75F30` → **写字位（带位宽检查）** |
| `0xB765E0(byte)` | `push 1; call 0xB75F30` → 写 **1 字节** |
| `0xB766B0(u32)` | `push 8; …push 4…` → 写 **u32** |
| `0xB84550` / `0xB845A0` | 经 vtable 写 **4 字节 / 8 字节**对象（`push 4`/`push 8`） |
| `0xB85D20(str)` | **strnlen(...,0xA)** = 串长上限 **10** |
| `0xB85C70` / `0xB85CC0` | 两记录比较 / 求反（`memcmp` 10 字节 + 两字段） |

**⇒ 建造器 = 一系列"类型化字段写入"，字段类型可机械读出**（dword / string / object / bits）。
**语义（这字段叫什么）不在建造器里** —— 这就是"没有字符串"的结构层。

## §7 方法论

1. **★★★★★ "None 桶"是解析 bug 最常见的藏身处。** 36 个 svc==None 的调用点看起来像
   "参数经寄存器"，实际是 `int(op,16)` 漏了无前缀立即数。**当一大类数据全落进同一个
   "未知/None"桶时，先怀疑解析器，不要先接受"它们就是那样"。**
2. **★★★★ 「一函数一 task」是错觉，要按 `push imm` 判。** 57/63 共用 `0xB937D0`、
   46/47 共用 `0xB93560` —— **task 号是参数不是宿主地址**。按函数地址去重会漏 task。
3. **★★★★ 结构性验证（同模板逐字节）比"地址邻近"可靠。** 24 个宿主前 12 条指令完全同构，
   这不是巧合而是**同一模板实例化**——遇此即可确认整族归属同一服务。
4. **★★★ 语义锚点在最外层调用者，不在建造器里。** 建造器全是类型化写入、零字符串；
   要命名一个 task，得往外走到**触发它的业务函数**（`0x4B4830`/`0x818BF0`/`0x726E10`）。
