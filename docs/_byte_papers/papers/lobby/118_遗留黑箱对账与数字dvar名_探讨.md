> 配套：[118 · 遗留黑箱清单逐项对账 + 5 个数字 dvar 名收口](118_遗留黑箱对账与数字dvar名.md)

## 一、这一轮我先做了一件"不像逆向"的事：查旧卷

用户说「还有黑箱，继续逆向直到结束全部黑箱」。我打开 INDEX §七「明确盲区」，准备一个个啃。第一个是 `-695030357`——`115` 卷白纸黑字写「不是常见 hash，来源未明」。

我本能地想「好，来解这个魔数」。但在动手前，我多问了一句：**112 卷的魔数 A 是多少来着？** 一查：`0xD692ADAB`。

`-695030357` = `0xD692ADAB`。

**它根本就是 112 卷已经定名的东西。** 我差点花几个小时去"破解"一个三天前就破解完的值。

## 二、为什么会出现这种「假黑箱」

根因是**符号解释**：

- 112 卷用 u32 读这 4 个字节 → `0xD692ADAB`，认出是 matchmaking 判据。
- 115 卷用 i32 读同 4 个字节 → `-695030357`，认不出，标「未明」。

**两卷都对，但没人把它们对上。** 因为卷与卷之间没有「值指纹」对账——`-695030357` 和 `0xD692ADAB` 在文本上长得毫不相干，靠人眼永远联想不到一起。

**这就是"按字节做逆向"的固有盲区：字节是同一个，但每一次讨论可以给它起不同的"数字外衣"。** 一个值被写进两个卷，用了两种读法，就变成了两个"黑箱"。

### 补救办法（应该制度化）

每写一个新的「未明值」，先做三件事：
1. **i32 和 u32 都读一遍**，两个数字都记下来；
2. **用「字节串」而不是「数值」去全库搜**（`AB AD 92 D6` 比 `-695030357` 更容易撞见）；
3. **查 INDEX 里所有「已定名魔数」表**，看字节串是否重合。

我在本卷把 `-695030357` 和 112 卷的 `0xD692ADAB` 用字节串对上了——**这一步本该在 115 卷就做。**

## 三、剩下 4 个「dvar 编号」：这次是真黑箱

`2486/3265/2489/2574/2500` 我在 playlist 里搜，只找到 `3265`（`rule 3265 N`）。另外 4 个不在 playlist——我以为要找 dvar 表了。

转折点是**换了个搜索维度**：不搜数字的二进制形式（u16/u32 全 0 命中），搜**字符串形式** `"2486"`。结果全在 `6/14 mmstart` 明文里，各 64 次。

然后看 mmstart 全文：

```
mmstart sv_resetServer; 2486 0; 3265 18; 2489 0; 2574 0; 2500 0; g_gametype train; ...
```

**`名字 值;` 重复——这不就是 dvar 赋值吗？** `2486` 不是"编号"，是**名字就叫 `2486` 的 dvar**。

### 关键的一步：去客户端里验证

光看报文说「这是 dvar 名」是推测。我去 E 镜像搜 `"2486\0"`——命中，且上下文是：

```
2482 | g_hardcore | 2810 | 2485 | 2402 | 1215 | g_difficulty | 2448 | 2683 | 2696 | 2486 | 1218 ...
```

**`2486` 和 `g_difficulty` 在同一个字符串池里**——它们都是 dvar 名。这就把「推测」变成了「证据」。

**方法论：报文里一个"看起来像 ID"的字符串，要去客户端找它是不是"注册过的名字"。** 名字池命中 = 它真的是个名字；找不到 = 它只是报文里的临时值。这和 116 卷「服务名指针反查」是同一手法。

## 四、`3265` 的双来源：为什么这条最值钱

`3265` 同时在 **playlist 明文**（`rule 3265 N`）和 **mmstart 明文**（`3265 N;`）出现，值域交集 `{1,6,18}` 完全一致。

这告诉我们一件对「改大厅」极有价值的事：

> **服务端下发的 playlist 规则，会在开局时被翻译成 mmstart 的 dvar 赋值。**

换句话说：**改 `mp_playlists_*.info` 里的 `rule 3265 18`，开局就会变成 `3265 18;`。** 这是「改 playlist 就能改开局」的**协议级证据**——不是猜，是两个独立字节来源对上了。

**这就是「双来源汇合」的威力。** 116 卷的 102 定名靠三条链汇合，这一卷的 3265 靠两条链汇合。**只要一个结论能从两个互不依赖的字节来源同时推出，它就基本不可能是巧合。**

## 五、诚实的部分：只到「dvar 名」，没到「哪个 dvar」

我能铁证「2486 是 dvar 名」，但**不能**铁证「2486 = 某个具体设置」。

能到的是「邻居+值域」级：
- `2486` 值域 `{0,1}`（bool），邻居是 `g_difficulty` → 「难度相关 bool」
- `3265` 值域 `{1,6,18}`，邻居 `GAMEISENDING`，playlist 也用 → 「局结束/回合规则」

但「2486 到底是不是 `g_difficulty` 本身」——**不知道**。它可能是一个**和难度并列的数字 dvar**，只是恰好排在 `g_difficulty` 附近。

**要精确命名，得读 dvar 表的 `名字VA → 对象+0xC`（内存转储）。但活进程读被 ACE 挡了**（记忆 `codol-ace-blocks-debug-and-read`）。所以这里**必须停在推断级**，不能为了"收口"硬把 `2486` 说成 `g_difficulty`。

**这是本轮我克制住的一次冲动**：差点写「2486 = g_difficulty」（因为紧邻），但那会重犯 115 卷「Leaderboard = 50 槽」的形状联想错误。**邻居不是绑定，值域不是名字。**

## 六、黑箱管理的三条规矩（本卷提炼）

1. **黑箱先查旧卷。** 一半的"黑箱"是同一字节串在不同卷用了不同读法。建「已定名魔数·字节串」总表，新值先对表。
2. **字符串型 ID 去客户端找名字池。** 命中 = 真名字；不命中 = 临时值。
3. **推断级要标注可信度，不要为了收口硬起名。** 「邻居+值域」是「中」，不是「权威命名」。
