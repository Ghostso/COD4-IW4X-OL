# 176 探讨 · "还开着"的四种不同含义

## 一、这轮闭掉的四项，其实是四种不同的"没做完"

复盘上一轮我列的四个开项，它们的性质完全不同：

| 项 | 上一轮的说法 | 实际情况 |
|---|---|---|
| `0xBA0780` 状态枚举 | "只知返回 2=已认证" | **根本没读全**，读了 18 条指令就全出来了 |
| 谁触发 `vt[0]` | "上游未追" | **追到了，但终点是 vtable，没有 call** |
| Manifold item 布局 | "只解到 header" | **就在 `0x4F3EB0`，30 条指令** |
| ChangeTeam 字段语义 | "布局已知，含义未知" | **确实不知道，而且静态不可能知道** |

也就是说：

- 前两项是**我上一轮偷懒**（读了够用就停）
- 第三项是**我上一轮没找到入口**（不知道从哪读起）
- 第四项是**真不知道**，而且这个"不知道"是合理的

把这四种混在一起说"还有 4 项未闭合"，是不诚实的 —— 因为它们需要的工作量差 10 倍。

## 二、`0xBA0780` 那 18 条指令

上一轮我写"只知返回 2=已认证"。这轮读全后：

```
[+0x644] != 0:
    [+0xC8] == 1 或 2  -> 2
    [+0xC8] == 其它    -> 原值
[+0x644] == 0:
    [+0xC8] != 2       -> 原值
    [+0xC8] == 2:
        [+0x5E8] == 3  -> 2
        [+0x5E8] != 3  -> 1
```

**5 种输出路径。** 上一轮"只记一种"会直接导致误判：如果 `[+0x644]!=0` 且 `[+0xC8]==1`，也会返回 2，但那时其实还没到 `==2` 状态。

这种错误在排查"为什么闸门不过"时是致命的——你会以为它要求 `[+0xC8]==2`，实际上有个前置标志能放宽。

## 三、`vt[0]` 那条：我上一轮该早点想到

上一轮写"谁触发 `vt[0]` 写出：上游未追"。

这轮一查：

```python
0x6301A0 (SendReady)  数据引用 2 处: 0xDC72F8, 0xDC7798
                      0 处 call
```

**`0x6301A0` 根本没有 call 边 —— 它是 vtable 槽。**

我的 `calls_to()` 只扫 `E8 rel32`。对 vtable 里的函数，这个扫描必然返回 0。上一轮我看到 0 就写"未追"，其实是**方法没覆盖**。

正确做法：查调用者要同时查两种边：

```python
# 1. 直接调用
E8 rel32
# 2. 数据引用（vtable 槽 / 函数指针表）
dd <addr>
```

这条 172 卷其实已经吃过一次教训（`0x6287D0` 0 处 call、5 处 vtable 引用），我却又犯了一次。

## 四、Manifold item：就是我上一轮没找到入口

上一轮说"`0x6257D5` 起是变长块解析，未逐字段展开"。

这轮直接反汇编 `0x4F3EB0`：

```asm
push 0x13 / call 0xB774E0     ; 读 13 位
push 8    / call 0xB774E0     ; 读 8 位
push 0x20 / call 0xB772E0     ; 读 32 位 = 长度
...
add eax, eax  ×3              ; ★ 长度 ×8 = 位数
call 0xB772E0                 ; 读载荷
```

30 条指令看完。上次我把"`0x4F3EB0` 是什么"当成拦路虎，实际它就在调用点里明摆着。

## 五、ChangeTeam 字段语义：这个真的闭不了

`0x6281D0` 的线格式是：

```
WriteBits(3)  WriteBits(8,type)  WriteBits(21)  WriteBits(32,[+8])
WriteBits(21) WriteBits(8,[+0x10]) WriteBits(21) WriteBits(32,[+0x0C])
WriteBits(21) WriteBits(64)
```

四个字段：`u32[+8]`、`u8[+0x10]`、`u32[+0x0C]`、`u64`。

**哪个是队伍号、哪个是槽位号、那个 u64 是账号还是 session —— 静态读不出来。**

要定这个，必须找**写这些字段的 UI 代码**：

```
Flash"加入阵营"按钮 → AS_SetTeam(team) → C++ 写 [+0x10] 和 [+0x0C]
```

而这条链的终点又回到 vtable —— 和 §3 一样，**静态止于 vtable 槽**。

所以这项的正确表述是：

> **布局已定，语义需要运行时或 Flash 侧证据。静态到此为止，且已穷尽。**

不是"我还没查"，是"静态查不到"。

## 六、这轮的账

| 项 | 状态 |
|---|---|
| `0xBA0780` 5 种输出路径 | ✅ 闭 |
| `+0x644` 初值 0 / 唯一置 1 点 `0xBA35EB` | ✅ 闭 |
| `+0xC8` / `+0x5E8` 初值 | ✅ 闭 |
| SendReady 的 vtable 槽 `0xDC72F8`/`0xDC7798` | ✅ 闭 |
| FrameUpdate → 0x634340 定时广播 | ✅ 闭 |
| Manifold item = `[13][8][32][len×8]` | ✅ 闭 |
| ChangeTeam 字段语义 | ⬜ **静态不可达**（已穷尽） |

**从"7 项未闭合"变成"1 项静态不可达"。**

## 七、我该改的

**以后列开项时，必须标注它属于哪一类：**

1. **没查够**（读了就停）→ 下一轮必须查完
2. **找不到入口**（不知道从哪读起）→ 需要换维度
3. **方法没覆盖**（比如只扫 E8 不扫 vtable）→ 需要补工具
4. **静态不可达**（需要运行时/Flash 侧）→ 明确写"到此为止"，不再重复列

把 4 项混成一句"还有 4 项未闭合"，等于把 1 天的工作和 1 小时的探测混在一起，对下一步规划毫无帮助。
