# P2PInfo 背后的数据结构：136 字节的对等玩家槽

> 承接 `lobby/98`
> 产物：本卷新增的 `0x88` / `0x40` 两套结构判别，`0xDEADBEEF` 销毁哨兵

---

## 1. 本卷要解决上一卷留下的问题

**`lobby/98` §5 说了"67 字节 = 对等玩家数组上循环，步长 0x88、上限 0x550"，
但没说"那 136 字节里是什么"。**

**⇒ 本卷从**数据结构**这一侧切入，不读打包器那 6 个形参。**

---

## 2. 先排除一个陷阱：`0x40` ≠ `0x88`

**在追 P2PInfo 构造调用点（`0x62ab85`）的上游时，
我遇到 `0x7c0410` 这个函数，它看起来也在遍历"玩家槽"：**

```
0x7c0424  lea eax, [ecx + 2]
0x7c0427  shl eax, 6              ; ★ ×64
0x7c0439  cmp dword [eax+edi+0x88], esi   ; 比较"句柄"
0x7c0442  mov eax, [eax+edi+0x8c]         ; 比较"地址"
...
0x7c0476  add eax, 0x40           ; ★ 步长 64
0x7c0479  cmp ecx, 0x13           ; ★ 上限 19
```

**⇒ 这是**另一套结构**：步长 0x40（64 字节）、上限 19 项。**

**⇒ 与 P2PInfo 用的 0x88（136 字节）/ 上限 10 项**不同**。**

**★ 差一点把它们当成同一个。**
**判据：`shl eax,6` 是 ×64，不是 ×136；`cmp ecx,0x13`(19) 不是 10。**

---

## 3. 两套结构对照

| | 对等玩家槽（P2PInfo 用） | 会话网格槽 |
|---|---|---|
| 结构大小 | **0x88 = 136 字节** | **0x40 = 64 字节** |
| 容量上限 | **0x550 / 0x88 = 10** | **0x13 = 19** |
| 首字段 | 空 | `[+0]` 有效标志（`cmp byte [eax],0`） |
| ID 字段 | 未知 | `[+0x88]` 句柄 + `[+0x8C]` 地址（在 base 偏移外） |
| 消费者 | `0xb74bc0`（P2PInfo 打包） | `0x7c0410`（会话查找） |
| 语义 | **对等玩家（P2P peer）** | **网络会话/连接槽** |

**⇒ 10 = 5v5 满员；19 = ？ （可能 16 玩家 + 3 观战/预留）**

---

## 4. 对等玩家槽的实例：镜像里的真实内容

**数组基址 `0xe36e4d0`，10 项 × 136 字节。**

**第 0 项（本机玩家）实测：**

```
+0x00 .. +0x08   00 00 00 00 00 00 00 00
+0x08            00
+0x09 .. +0x10   01 01 01 01 01 01 01 01   ← ★ 正是那 8 个 01
+0x11 .. +0x53   00（全零）
+0x54            01
+0x55            01
+0x56            01
+0x57            01
+0x58 .. +0x63   01 ×12
+0x64 .. +0x87   00（全零）
```

**第 1–9 项：全零（未使用）。**

**⇒ ★★ 这直接解释了 `lobby/98` 那 8 个 `01`：**
**它们不是独立常量，而是**对等玩家槽 `+0x09` 起的 8 字节**，
并且这个槽**默认就被填 `01`**（构造函数把整块初始化成 `01` 再逐字段覆盖）。**

**⇒ 8 个 `01` 的语义可以从"槽的初值"反推：**
**8 个按位标志，默认全开。**

---

## 5. 槽里的三簇 `01`（不是一簇）

**实测第 0 项有三段非零：**

```
+0x09 .. +0x10   01 × 8     ← 8 字节标志
+0x54 .. +0x57   01 × 4     ← 4 字节
+0x58 .. +0x63   01 × 12    ← 12 字节
```

**合计 8 + 4 + 12 = 24 个 `01`。**

**⇒ 如果这些是"按位布尔"，那这个槽有 24 个默认 true 的标志位。**

**⇒ 如果它们是"字节型默认值"，则是 24 个初值为 1 的 u8。**

**⇒ 两者都说得通，代码层面无法区分。
**★ 本卷只交付"这三段的偏移与长度"，语义不下结论。***

## 6. `0xDEADBEEF`：这个结构的销毁标记

**`0xb76e50` 整个函数只有一条指令：**

```
0xb76e50  mov dword ptr [ecx], 0xDEADBEEF
0xb76e56  ret
```

**它被 `0xb74e12`（释放对等玩家表时逐项调用）使用：**

```
0xb74e04  mov eax, [edi+8]        ; 项数
0xb74e07  mov esi, [edi]          ; 数组基址
0xb74e10  mov ecx, esi
0xb74e12  call 0xb76e50           ; ★ 标记 0xDEADBEEF
0xb74e17  add esi, 0x88           ; 步长 136
0xb74e1d  dec ebx
0xb74e1e  jne 0xb74e10
```

**⇒ 释放时把每项首 4 字节写成 `0xDEADBEEF`。**

**★ 这是一个可用于**实测**的判据：**
**如果能在内存里搜到 `EF BE AD DE`（小端），
就说明对等玩家表曾被释放过。
⇒ 可用于判断"P2PInfo 有没有被构造过/是否已被销毁"。**

## 7. 副本构造：`0xb76e60` 是 132 字节的 POD 拷贝

```
0xb76e60  mov eax, ecx
0xb76e67  mov ecx, 0x21           ; 33 个 dword = 132 字节
0xb76e6c  lea esi, [ebp+8]
0xb76e71  rep movsd
0xb76e76  ret 0x84                ; ★ 参数区 0x84 = 132 字节
```

**⇒ 这个结构的 POD 部分 = 132 字节（不是 136）。**

**⇒ `0x88`(136) − `0x84`(132) = 4 字节 ⇒ 开头 4 字节不在 POD 拷贝范围。**

**⇒ 与 `[+0]` 是"有效标志/状态"（`0xDEADBEEF` 写这里）
和 §2 里会话槽 `cmp byte [eax],0` 的形态吻合。**

**⇒ 结构 = `[+0] 4 字节状态头` + `[+4] 132 字节 POD` = 136。**
**（但也可能是 `[+0]` 1 字节标志 + 3 字节补齐 —— 见 §8）**

## 8. 诚实边界

| 项 | 状态 |
|---|---|
| 对等玩家槽 = 136 字节 / ≤10 项 | **精确（数组实例已读出）** |
| 会话网格槽 = 64 字节 / 19 项 | **精确（另一个结构，别混）** |
| 槽内 `01` 的三段偏移 | **精确（0x09/0x54/0x58）** |
| `0xDEADBEEF` 销毁标记 | **精确（单指令函数）** |
| POD 部分 132 字节 | **精确（rep movsd 0x21）** |
| 各字段语义（除状态位） | **未定** |
| `[+0]` 是 1 字节还是 4 字节 | **未定**（POD 从 +4 起，但写 0xdeadbeef 是 4 字节） |
| 67 字节 blob 每项位布局 | **仍未定**（`lobby/98` §6 的边界不变） |
