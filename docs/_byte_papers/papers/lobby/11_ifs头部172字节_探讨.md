# `.ifs` 头部解剖 · 探讨：一个指针的语义怎么会随文件大小变

> 对应：`lobby/11_ifs头部172字节.md`

---

## 一、我一开始以为 8 个指针是同一套语义

看到头部有 8 个 u64，第一反应是找统一规律：

- `[4]` 满足 `+tail_len = L`（974/974）
- `[3] == [0]`（974/974）

这两条很干净。于是我以为 `[0]` 也是某种统一的东西。

---

## 二、`[0]` 的两面

### 16KB 小文件

```
size = 16417
[0]  = 0x4000 = 16384
```

清单区从 0xac 开始，到 `0xac + tbl[0] = 0x40ac` 结束 ——
而 0x40ac 之后正好是 `[4]=0x4020`（16416）和最后 1 字节。

**所以 `[0]` 在这里 = "清单区长度"**，且等于块大小 0x4000。

### 34MB 大文件

```
size = 34819339
[0]  = 0x212C000 = 34,783,232
```

如果 `[0]` 是"清单区长度"，那清单区会有 34MB。
但 0xac 处只是 `.lst` + 两个 `.ff` 路径，156 字节后就是 `IWff0100`。

**不可能。**

---

## 三、问题出在哪

两种可能：

### 可能 A：`[0]` 在大文件里指的是"载荷区终点"

`0x212C000` 落在载荷区内（34,783,232 < 34,819,339）。
从 0x148 到 0x212C000 是 34,782,904 字节的载荷。

**这说得通。**

### 可能 B：`[0]` 恒指"清单区 + 载荷区的总终点"，但小文件里清单区恰好占满

16KB 文件：清单区 0xac..0x40ac，载荷区为空。
所以"总终点" = 0x40ac ≈ `[0]`+0xac。

**也说得通。**

---

## 四、我倾向 A，但证据不足

因为：

- 大文件：0x148 后是 `IWff0100` + 随机数据（载荷），一直到 `[0]`
- 小文件：0xac 后是清单文本，一直填到 `[0]` 边界

**两者在 `[0]` 处都"停下"**，只是停下的东西不同。

最可能的统一解释：

> `[0]` = **"主数据区终点"**。
> 主数据区的内容由文件类型决定 ——
> 小文件是清单，大文件是载荷。

---

## 五、这为什么值得写一篇

因为**一个指针的语义不统一**，是很危险的事。

如果我假设 `[0]` 永远是"清单长度"，写解析器会在所有 >100MB 的文件上崩掉。
如果我假设 `[0]` 永远是"载荷终点"，16KB 文件就解不出清单。

**必须两种都处理。**

---

## 六、方法论收获

> **"974/974 成立"的关系可以直接用；"只在部分文件成立"的必须有分支。**

这次确定的可信关系：

| 关系 | 覆盖率 | 可用性 |
|---|---|---|
| `[4] + tail_len == L` | 974/974 | **可直接用** |
| `[3] == [0]` | 974/974 | **可直接用** |
| `[0]` 语义 | 因文件大小而异 | **必须分支** |

**"几乎全部成立"的经验规则，比"全部成立"危险得多。**

因为前者不会让你警觉，后者才逼你去找原因。
