# 344 — 房间动作是否发出：证伪路 F05

**结论（一句话）**：**「客户端根本没发房间动作」不成立，证伪失败。**
真实原因是**服务端对房间通道 11/4 的处理函数抛 `NameError`**，客户端动作已发出、服务端未应答；
最新一轮的两个 run 就在 11/4 处**永久停住**（连接保持 ESTABLISHED 87 秒、无任何后续帧）。

## 2. 有没有「房间动作」？—— 有，但最新一轮被服务端吞掉

日志到此**结束**（全文件 250 行，最后 3 行即上面），**没有 `-> 0B/4 ...`、没有 `-> 0x85 应答`**。

### 相关性（47/47 单向依赖）

`corr.py` 逐 run 统计：
- 有 room 记录的 run：49；其中**被应答 47**。
- 有 ready 记录的 run：47；**前置 room 记录被回显的 47，未回显的 0**。
- 47 个 run 全部满足 `ready_index > room_index`。

⇒ 客户端的 ready 是**对上一条 room 记录被服务端确认后的后续动作**。
服务端一停，客户端就停在 room 那一步，ready 永远不会来。

## 3. 为什么没发（最新一轮）：服务端 `NameError`，不是客户端门

`reply_objects()` 的 11/4 分支第 1105 行：
```python
_fam, _inner = _parse_11_4_batch(batch)      # batch 在该作用域从未赋值
```
`LobbyServer...` 只捕获 `Exception` 并 `continue`（第 1621–1625 行只包住解密，
`reply_objects` 在 1653 行**没有 try**）。异常上抛到 1693 行 `except Exception` → `break`，
于是**这条连接再也不会发任何帧**——日志表现为「#59 之后什么都没有」。

实测复现（`_f64_05\prove_fix.py`，直接 import 现场 kit 的 `lobby_server.py`）：

```
===== STOCK (run kit) =====
  151503 #59 room V=04   -> RAISED NameError: name 'batch' is not defined
  132700 #61 room V=04   -> RAISED NameError: name 'batch' is not defined
  132700 #62 ready 16B   -> RAISED NameError: name 'batch' is not defined
```

**回归来源**：历史版 `ONCE_20261027_132700\kit\lobby_server.py:890` 有
`ch, batch, tp = _parse_set_room_data(plain)`；当前版把这一行删了，只留下游引用。
（`batch` 修好后还会撞第二个未绑定名 `ch`——同一处删改的连带。）

### 修复证明（只改本地副本，未动 kit）

`_f64_05\patched_lobby_server.py` 恢复上游那一行 `ch, batch, tp = _parse_set_room_data(plain)`：

```
===== PATCHED (local copy) =====
  151503 #59 room V=04   -> OK note='0B/4 ... [room族 V=0x04]' pushes=0
  132700 #61 room V=04   -> OK note='0B/4 ... [room族 V=0x04]' pushes=0
  132700 #62 ready 16B   -> OK note='0B/4 ... [ready族 17B]'   pushes=0
```

三例全部通过，ready 族能被正确识别。**这就是本轮房间故障的直接根因。**

## 4. 客户端侧的门（静态，供修复后仍不通时排查）

`0xB7A670`（所有 svc 宿主工厂的前置门，`0xB80D90` 等 `call 0xB7A670; cmp eax,2; je`）：

```
00B7A670  mov esi,ecx
00B7A673  mov ecx,[esi+0x4F4]
00B7A679  test ecx,ecx
00B7A67B  jne 0xB7A681        ; [srpc+0x4F4]==0 -> eax=0 (门关)
00B7A681  call 0xBA0780        ; 状态机
00B7A686  cmp byte [esi+0x4F8],0
00B7A68D  jne 0xB7A699        ; [srpc+0x4F8]!=0 -> 直接用状态机返回值
00B7A68F  cmp eax,2
00B7A692  jne 0xB7A699
00B7A694  mov eax,1
00B7A699  ret
```
门开条件：`[srpc+0x4F4]!=0` **且**（`[srpc+0x4F8]!=0` 或 `0xBA0780(srpc)==2`）。

全镜像**没有一处** `[reg+0x4F8]` 写指令（`disp2.py` 扫遍 `0x400000..0xE659000`：
`refs to [reg+0x4F8]: 0`；同法扫 `0x4F4` 得 1 处 `00B8255A mov dword [esi+0x4f4],0`，
证明扫描器有效）。所以这道门在当前镜像里恒由 `0xBA0780(srpc)==2` 决定。

Ready 序列化器 `0x6287D0`（`WriteBits(3,type)` + `WriteBits(8,type)` + `WriteBits(1,flag)`）
**无直接 `E8` 调用点**（`callers.py`：0 处），只以 vtable 形式存在：
`0xDC7600` 起的 `[写][读][COL]` 12 字节步进表，槽 `+0x24/+0x9C/+0xA8/+0xB4/+0xD8`。
唯一代码引用 `0x62A1BF`（`mov dword [ebp-0x10],0xDC7600`，type id `0xd`），经 `vt[0x144]` 注册。
⇒ Ready 是**间接经表调用**，不能靠 xref 判"没被调用"。

## 5. 结论与处方

- **证伪失败**：客户端确实发出 `11/4 room`（163 条）与 `11/4 ready`（57 条）。
- **当前故障点**：服务端 `reply_objects` 11/4 分支 `NameError: batch`（连带 `ch`），
  异常 break 掉连接，客户端动作到 room 即被饿死，ready 永远发不出。
- **处方**（需用户批准后改 kit）：在 `reply_objects` 的 `if task == 4:` 分支开头恢复
  `ch, batch, tp = _parse_set_room_data(plain)`；跑新 run 验证日志出现
  `0B/4 ... [room族 V=0x04]` → `0B/4 ... [ready族 17B]` → `-> 0x85 应答` 连续三段。

### 仍开
1. 修复后 ready 被应答，是否足以让客户端推进到 `6/14 mmbook / mmstart`——
   `ONCE_20261103_151503` 全 run `6/14=0 / mmbook=0 / 21/5=0`，这三条**从未在本 run 出现**。
2. `0xBA0780(srpc)` 的 5 种输出（176 卷）在实跑中的取值未取；若修复后仍卡在门，需要抓这个值。
3. `11/4 room` 的前 80 条 `innerLen` 不吻合（163 条里 80 条 `len_mismatch`）——
   `_parse_11_4_batch` 注释说"族判定不依赖长度"，成立，但长度语义仍未定。
