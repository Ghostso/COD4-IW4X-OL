# 字节 `0x01` · 探讨：3 个 false 比 326 个 true 值钱

> 对应：`lobby/105_字节01全解剖.md`

---

## 一、这一卷最有价值的不是 25,187，是那 3 个

**`0x01` 出现 25,187 次。其中 22,039 次是"整型字段值 = 1"。**

**如果只看这个数字，结论会是"0x01 就是 1，没什么可说的"。**

**但真正的信息在**反例**里：**

```
bool = 1 : 326
bool = 0 :   3
```

**⇒ 3 个 false，全部在 `93/131` 与 `80/154` 的元素 #5。**

**★ 这 3 个 false 是全语料**唯一**能证明"这个字段是布尔"的证据。**

**⇒ 如果没有它们，我无法排除"0x01 是一个恒为 1 的常量标记"。
  有了它们，我知道它**可以是 0**，所以它是**真的可变状态**。**

---

## 二、"恒为 X" 和 "从不为 X" 哪个更有信息

**这一卷同时出现了两个极端：**

```
0x03 u8 : 98.9% 的值是 1
0x06 u16: 0% 的值是 1
```

**⇒ 这两个都是**强信息**，但方向相反。**

**`0x03` 98.9% 是 1 —— 说明它是**枚举**（取值域只有 4 个）。**

**`0x06` 0% 是 1 —— 说明它是**连续量**（1 是一个"不该出现"的值）。**

**★ 一个字段"从不为某个值"，比"总是某个值"更能说明它的类型。**

**⇒ 如果 `0x06` 是"标志/序号"，1 一定会出现。
  1 一次都不出现 ⇒ 它不是标志，它是"量"。**

**⇒ 这条判据可以直接迁移：
  判断一个字段是"枚举"还是"量"，看它是否**覆盖小整数**。
  覆盖 0..3 ⇒ 枚举；从不取 1 ⇒ 量。**

## 三、我一开始差点把 `0x03` 当成"类型码"

**看到 `0x03` 在 `102/1` 里取值 1、2、3，我第一反应是
"这是元素类型码，1=xx、2=yy、3=zz"。**

**但 `102/7` 推翻了这个想法：**

```
102/7: [03=01 0a[u64]] × 50
```

**⇒ 50 个条目的 `0x03` **全部等于 1**。
  如果它是"元素类型码"，50 个条目应该有多种类型。全 1 说不通。**

**⇒ 所以 `0x03` 不是"元素类型"，而是"这个 task 的固定标志 = 1"。
  而 `102/1` 里出现的 1/2/3，是**另一个 task 的**序号。**

**★ 教训：一个字节的"取值域"必须在**跨 task** 的层面看。
  只在 `102/1` 里看，会以为 `0x03` 是 1..3 的序号；
  加上 `102/7`，才知道它是"按 task 固定的标志"。**

**⇒ 这正是"全语料"和"抽样"的区别。**

---

## 四、`0x01` 的"标签 vs 值"歧义，是这一卷最实用的发现

**`0x01` 既可以是标签（bool，329 次），也可以是值（24,858 次）。**

**⇒ 比例 1:75。**

**★ 这意味着：**
**解析器看到 0x01，必须知道"当前是不是在期待标签"。**
**如果是，它就是 bool；如果不是，它就是值 1。**

**⇒ 这不是歧义，这是"上下文决定语义"的典型。**

**★ 对我们的实践意义：**
**构造报文时，如果你在"值的位置"写 0x01，它是值；
  如果你在"标签的位置"写 0x01，它会开启一个 bool 字段。
  两者差 1 个字节，但解析结果完全不同。**

**⇒ 这也是为什么 `lobby_grammar_v5` 的解析器必须严格按"期待标签"状态推进，
  不能"看到 0x01 就当标签"。**

## 五、那 3 个 false 的"可操作性"

**`93/131` 和 `80/154` 的元素 #5（共 13 个元素）是 false。**

**⇒ 这两个 task 的报文结构相似（都是 13 个元素），
  第 6 个字段是一个 bool，本次会话里是 0。**

**★ 如果我想找一个"可安全修改的开关"，这是最好的候选：**
**- 它是真的 bool（有 true 也有 false，不是常量）**
**- 它只在 2 个 task 里出现**
**- 它位于固定的元素位置（#5）**

**⇒ 把它的 0 改成 1，观察客户端行为变化，
  是一个**低风险、可观测**的实验。**

**★ 但我**不**现在就说"改它能开启什么功能" —— 我没有证据。
  我只说"它是一个可改的、会变的布尔"。**

## 六、与 0x00 / 0x70 / 0xFF 的横向对照

**四个字节放一起，规律就出来了：**

| 字节 | 主导角色 | 语义 |
|---|---|---|
| `0x00` | 整型高位零（71.6%） | 结构冗余 |
| `0x01` | **整型值 1（87.5%）** | **枚举/布尔** |
| `0x70` | 字符串字母 p（66.1%） | 无 |
| `0xFF` | blob 空槽（78.1%） | 哨兵 |

**★ 一条规律：**
**"主导角色"决定了这个字节的信息价值：**
**- 主导角色是"字符串" ⇒ 无（0x70）**
**- 主导角色是"整型值" ⇒ 有（0x01）**
**- 主导角色是"结构填充" ⇒ 低（0x00、0xFF）**

**⇒ 所以下一个该做的字节，应该是"主导角色是整型值"的。
  按 `102` 的表，`0x0a`（u64 标签）和 `0x07`（i32 标签）都是。**

## 七、方法论收获

> **① 反例比正例值钱。3 个 false 证明了 326 个 true 的字段是"可变布尔"，
>    而不是"恒真常量"。**

> **② "从不为某值" 是强类型判据。`0x06` 从不为 1 ⇒ 它是"量"不是"标志"。**

> **③ 取值域必须在跨 task 层面看。
>    只看一个 task 会把"固定标志"误判成"序号"。**

> **④ 同一字节值在不同上下文里语义不同（0x01 既是标签又是值），
>    解析器必须按状态推进，不能按字节值硬判。**
