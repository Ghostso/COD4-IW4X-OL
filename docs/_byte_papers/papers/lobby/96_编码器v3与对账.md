## 2. v3 的做法：spec 由程序生成

**`tools/spec_gen.py` 读 `serialize_extract6` 的逆向结果，直接吐 Python 字典。**

**关键修正（也是这一卷唯一的技术点）：**

**同一份 serialize 会被多个类共用。** 例如：

```
0x628320  被 Vote / ChangeTeamRequest / StartCountingDown /
          StartGameFailed / MemberDetailsQuery /
          NetcafePrivileges / QQMembership / MemberDetailsNoUpdated
          共 8 个类共用
0x6287d0  被 Ready / UpdateCreditRating /
          DMZLeagueTicketStateChange / InRoomStateChange /
          PlayerPrimaryWeaponCountChange 共 5 个类共用
0x627d30  被 Leave / JoinWithMe 共用
0x626650  被 RequestMemberList / LeaveWithMe / MemberDetailsNoUpdated 共用
```

**第一版用 `seen` 去重，导致"共用者的 spec 全部丢失"（只出 30 条）。**

**⇒ 改成"缓存 VA → spec，命中就复用" ⇒ 45 条全部生成。**

**⇒ 这是一个纯粹的"去重方向搞反了"的 bug：
该去重的是**计算**，不该去重的是**输出**。**

## 4. 剩下 10 条的差，全部是字符串载荷

```
ClanNameChange      asm  18   codec  50   差 32
Join                asm 969   codec 1129 差 160
JoinRequest         asm 938   codec 994  差 56
MemberInfoAdd       asm 751   codec 775  差 24
MemberInfoEXT       asm 164   codec 188  差 24
MessageText         asm 106   codec 138  差 32
MyPartyInvitation   asm 124   codec 156  差 32
RoomInfo            asm 937   codec 1097 差 160
SyncPartyPending    asm 230   codec 262  差 32
Text                asm 100   codec 132  差 32
```

**这些差不是错误，而是**两边对"字符串"的记账方式不同**：**

| 差 | 成因 |
|---|---|
| **32** | codec 写 5 位 tag + 4 字节（"Bob"+NUL = 32 位）；asm 只记 5 位 tag |
| **24** | codec 写 5+32；asm 记 5+8（它递归进了字符串读器，记了第一轮 8 位） |
| **160** | 5 个字符串 × 32（RoomInfo / Join 各有 5 个 `0x10`） |
| **56** | 1 个 32 + 1 个 24（JoinRequest 有两个 `0x10`，走两种不同的读器） |

**⇒ 24 vs 32 的差别，恰好证明**字符串读器有两个版本**：
一个被工具递归进去了（记 8 位），一个没有（记 0 位）。**

**⇒ 这是一个副产品发现，不是缺陷。**

## 7. 这一卷真正验证了什么

**验证的不是"编码器能跑"，而是：**

> **两条完全独立的路径（读汇编 / 读表）算出同一个位长。**

**⇒ 说明 spec 表没有转录错误，
也说明 `lobby/92`~`94` 的字段顺序与位宽没抄错。**

**⇒ 这是这六卷（89–95）第一次得到"内部一致性"的证明。**
