# 房间对象创建函数 `0x639d00` · 探讨：12 条指令决定了整条链的生死

> 对应：`lobby/46_房间对象创建函数.md`

---

## 一、这一卷是一个"边界更正"卷

**上一卷 `lobby/45` 把起点弄错了（`0x639cf5` vs `0x639d00`）。**

**⇒ 本卷用 `int3` 填充（`0x639cf2–0x639cff`）证明了真正的函数边界。**

**⇒ `int3` 填充是 MSVC 的函数分隔标记，这是硬证据，不是推断。**

---

## 二、真正的价值在 `0x639d03` 那个立即数

```
push 0x3a128        ; = 241,960
call 0xc3e9f5       ; 查找（RTTI / 类工厂）
```

**⇒ `0x3A128` 是一个 241,960 字节的对象尺寸请求。**

**⇒ 这个数字非常有意思：241,960 ≈ 236 KB，一个巨大的房间对象。**

**⇒ 它比 `0x1D0`（成员记录 464 字节）大 500 倍。**

**⇒ 说明房间对象里塞了大量东西（可能包括成员数组 500 槽）。**

**验算：`0x1D0 × 512 = 237,568`，非常接近 `241,960`。**

**⇒ 高度可能：成员数组 = 512 槽 × 464 字节 ≈ 237 KB + 头。**

**⇒ 这是"成员上限 512"的一个旁证（但未实测）。**

---

## 三、失败路径的处理很说明问题

```
0x639d14  je 0x639d25       ; 查找失败
0x639d25  mov [0x82e13fc], edi   ; edi = 0 ⇒ 存 NULL
```

**⇒ 构造函数返回 NULL 时，全局指针写 0。**

**⇒ 这与 memory 里"`[0x82e13fc]=0` 是断点"完全一致。**

**⇒ 也就是说：我们观察到 `[0x82e13fc]=0`，
不是"房间对象被销毁了"，而是"房间对象从来没有创建成功"。**

**⇒ 这一条直接支持 `codol-room-reverse-conclusion-connection-bound` 的结论。**

---

## 四、方法论收获

> **`int3` 填充是最可靠的函数边界标记。**
> **对象尺寸立即数是推断"容量上限"的免费线索。**
