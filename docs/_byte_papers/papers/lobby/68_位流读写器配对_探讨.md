# 位流读写器配对 · 探讨：这一卷说"`0xb774e0` = readBits"，后来被推翻了

> 对应：`lobby/68_位流读写器配对.md`
> **★ 本卷的表格有一处关键错误，`lobby/89` 已更正。**

---

## 一、四件套的配对是对的

```
写  writeBits  0xb77b10
写  writeData  0xb777c0
读  readBits   0xb774e0    ← ★ 名字错，见 §2
读  readData   0xb772e0
```

**⇒ "四件套对称"这个结构判断是正确的。**

---

## 二、错误：`0xb774e0` 不是 `readBits`，是 `readBitsExpect`

**本卷写的是"读 3 位"。**

**`lobby/89` 读了完整函数后：**

```
0xb7750e  test al,al
0xb77512  mov eax,[ebp+8]     ← 期望值（调用方 push 的那个数）
0xb77517  mov esi,[ebp-0x58]  ← 实读 5 位
0xb7751a  cmp esi,eax
0xb7751c  sete bl
0xb7751f  test bl,bl
0xb77521  jne 0xb7754b
0xb77523  call 0x8435d0       ← 不等 → "断言"
```

**⇒ 它**读 5 位然后比对**。`push 3` 的含义不是"读 3 位"，
而是"**期望读到的值是 3**"。**

**⇒ 本卷的"0x627cec push 3 / call readBits(3) → 读 3 位"是误读。**

**⇒ 真实语义：读 5 位，断言它等于 3。**

---

## 三、为什么这个误读会传播

**因为它"看起来成立"：**

**`writeBits(3)` 写 3、`readBits(3)` 读 3，读写对称，很自然。**

**⇒ 但 `writeBits(3)` 的 "3" 是**要写出去的值**，
`readBitsExpect(3)` 的 "3" 是**期望收到的值**。**

**⇒ 两个 3 指的是同一件事：字段 ID 是 3。**

**⇒ 一旦换成"字段 ID"视角，读写完全对称——
但"读 3 位"这个说法就错了。**

---

## 四、这个错误的代价

**它让后续几卷（`lobby/82`–`88`）把 `push N` 一律记成"写 N 位/N 个"，
导致 `writeBits` 的位宽全部算错（这是 `lobby/85` 才纠正的）。**

**⇒ 一个"看起来合理"的误读，污染了 6 卷。**

**⇒ 这是本项目最典型的一类事故：
不是算错，而是**定义错了**，然后一贯地算对了一个错的东西。**

---

## 五、方法论收获

> **`push N; call F` 里，N 的语义必须从 F 内部读出来，
> 不能从 F 的名字猜。**

**⇒ `readBits` 这个名字是我自己起的，不是程序给的。
它误导了我 6 卷。**

**⇒ 教训：临时函数名要带问号，不要当事实用。**
