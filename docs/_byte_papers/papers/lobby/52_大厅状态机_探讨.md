# 大厅状态机 · 探讨：所有已知问题都汇到一个返回值

## 一、这一卷做了什么

上一卷找到房间闸门 `[0x849ba30] == 3`。

这一卷问：**谁来写它？**

答案出乎意料：

```
[0x849ba30]  ←  每帧从 [0x849ba34] 同步
[0x849ba34]  ←  有 12 个写入点，值域 1–10
```

**⇒ 房间闸门不是一个孤立条件，
而是一个 10 态状态机的某个状态。**

---

## 二、12 个写入点的意义

我把它们按值排了一遍：

```
1 → 进大厅开始        (0x7ef1b8)
2 →                     (0x7ef224)
3 → ★ 房间初始化所需   (0x7ef411)
5 → ×4                 (0x640d0f 0x7eeba3 0x7eedfb 0x7ef3ee)
6 → ×2                 (0x7ef2e1 0x7ef36e→8? 需再核)
7 →                     (0x7ef325)
8 →                     (0x7ef36e)
9 →                     (0x7ef347)
10 →                    (0x7eea4b)
```

**这是一个典型的分阶段初始化状态机。**

## 三、最关键的那个判断

```asm
0x7ef1cd  call 0x7f25b0
0x7ef1d2  mov esi, eax
0x7ef1de  cmp esi, 3
0x7ef1e1  jne 0x7ef210
0x7ef1e3  call 0x803780      ; 是 → 继续
```

**`0x7f25b0()` 返回 3，才继续。**

**而 `0x7f25b0` 在主循环里也出现过：**

```asm
0x4f8adb  call 0x7f25b0
0x4f8ae0  cmp eax, 1
0x4f8ae3  je  0x4f8ad1      ; == 1 → 循环等待
```

**⇒ 它是一个"连接/登录状态机"的查询函数：
1 = 进行中，3 = 完成。**

---

## 四、这条链解释了所有已知现象

| 现象 | 解释 |
|---|---|
| 6 秒必崩（`enable_iips=0`） | 连接状态到不了 3 |
| 改 1 后能进大厅 | 状态机 1→3 |
| 31 个 service 全应答 | 状态 3 之后才发起 |
| 房间对象 = 0 | 状态 3 才初始化 |
| MyEventHandler 零实例 | 同上 |
| 大厅"战斗开始"无响应 | 同上 |

**⇒ 六个现象，一个根因。**

## 五、这一卷的价值

**之前的记录都是"某个对象是 0"。**

**现在是"状态机停在 0，所以一切下游都不存在"。**

**⇒ 从"症状清单"变成了"单一状态"。**

**这是从"知道哪里坏了"到"知道为什么坏"的一步。**

## 六、诚实的边界

**我没有验证 `0x7f25b0` 实际返回什么。**

**只是从代码里读到"必须 == 3"。**

**⇒ 下一卷要做的是反汇编 `0x7f25b0`，
看它依据什么返回 3。**

**那才是"如何修"的答案。**

## 七、方法论收获

> **追"谁写这个变量"，往往能发现一个完整的状态机。**

**我只想找 `[0x849ba30]` 的写入点，
结果发现了 12 个写入点、10 个状态。**

**这些状态构成了大厅的初始化流程。**

**⇒ 这是本轮最有价值的结构性发现。**
