# 5 位前缀不是"标签"而是**字段 ID**：读写两侧逐项同一

> 承接 `lobby/88`
> 本卷**推翻 `lobby/88` 的位长表**，并给出 5 位模型的**第四、第五条证据**

---

## 1. 起因：一个地址对不上

上一轮 `lobby/88` 说 `MemberList` = 63 位。我把它台账最后一条
`writeBits(0x3) @0x627eb7` 拿去反汇编核对，发现：

```
0x627df4  c2 04 00    ret 4        ← MemberList::serialize 到这里就结束了
0x627df7  cc ...       int3×9
0x627e00  55 ...       push ebp     ← 这是下一个函数 deserialize 的开头
...
0x627eb7  e8 54 fc 54 00  call 0xb77b10   ← 这条属于 RoomInfo::serialize
```

**⇒ `0x627eb7` 根本不是 MemberList 的指令。**

旧的提取器用 `b[o:o+0x200]` 线性反汇编，**窗口越过了 `ret`**，
把邻居函数的写入当成自己的，还"凑"出了 63 位这个假数字。

---

## 2. 真正的 MemberList 长这样

```
0x627d9e  push 3  / call 0xB77B10    tag 0x03
0x627da4  push 8  / call 0xB777C0    u8
0x627db7  push 0x15 / call 0xB77B10  tag 0x15
0x627dc4  push 0x20 / call 0xB777C0  u32   ← 成员数
0x627dc9  mov eax,[ebx]; test; jle →循环外
0x627dd5 ... add ebx,0x1d0; dec; jne  ← ★ 循环！
0x627ddd  call 0x623880              ← 每个成员写一条
```

**⇒ MemberList = 5+8+5+32 = 50 位头 + N × (成员记录)。**

**⇒ 成员记录 = `0x623880` = 725 位 + 1 个变长字符串。**

**⇒ 63 位是错的。**

---

## 3. 顺带修的第 4、5、6、7 个工具缺陷

| # | 缺陷 | 后果 |
|---|---|---|
| D3 | 窗口越 `ret` 串邻居 | MemberList 假 63 位（`lobby/88`） |
| D4 | 条件分支两臂都 `push`，位宽取到污染的 `pend` | 一堆 0x15 位宽错 |
| D5 | 递归无门槛 | 把无关函数算进来（RoomInfo 假 853） |
| D6 | 已访问集合去过重 | 同一子函数调用两次只算一次 |
| D7 | 只扫到第一条 `ret` | MSVC 冷块在 `ret` 之后被整段丢掉 |

**⇒ 全部修完后写了 `tools/serialize_extract6.py`（递归下降遍历基本块）。**

## 4. ★ 最强的一条证据：读写序列逐项相同

`deserialize` 侧用的是 `0xB774E0`。反汇编：

```
0x00b774f8  push 0
0x00b774fa  push 0x1f
0x00b774fc  push 0
0x00b774fe  lea eax,[ebp-0x58]
0x00b77501  push eax
0x00b77509  call 0xb77630        ← readBitsCore(min=0,max=0x1f) = 读 5 位
0x00b7750e  test al,al
0x00b77512  mov eax,[ebp+8]      ← 期望值
0x00b77517  mov esi,[ebp-0x58]   ← 实读值
0x00b7751a  cmp esi,eax          ← ★ 比对
0x00b7751c  sete bl
0x00b7751f  test bl,bl
0x00b77521  jne 0xb7754b         ← 相等就走
0x00b77523 ... call 0x8435d0     ← 不等就调"断言"
```

**⇒ `0xB774E0` 不是"读 5 位"，是"读 5 位并断言它等于 X"。**

`0x8435D0` 反汇编只有一个字节：`c3` = `ret`。

**⇒ 断言在零售 build 里被编空了。**

## 5. 于是可以做一条无人能反驳的检验

**如果 5 位前缀真是"每类消息里硬编码的常量字段 ID"，
那么同一类的 serialize 与 deserialize 写/读的标签序列必须逐项相同。**

我扫了全部 36 个消息类的 vtable[1]（ser）和 vtable[2]（der）：

```
SAME=43   DIFF=1   EMPTY=6
```

**⇒ 43 / 44 完全逐项相同。**

那 1 个 DIFF 是 `dwRoomMessageRoomInfo`（`Join` 也含同一段），
差异只有**一个位置**：

```
ser 写 tag 0x03，der 读 tag 0x02
```

而 `0x8435D0` 是空桩 ⇒ **客户端根本不检查这个位置。**

## 7. ★★ 5 位模型的第五条独立证据

前四条在 `lobby/85`。这一条是**新的、且更硬**：

**读写两侧的 (tag → 位宽) 联合分布完全相同。**

```
SER:  0x01→1×41  0x03→8×98  0x06→16×22  0x07→32×2  0x08→32×17
      0x0a→64×8  0x0d→32×14  0x10→VAR×19  0x15→8/16/32/64
DER:  0x01→1×41  0x03→8×96  0x06→16×22  0x07→32×2  0x08→32×17
      0x0a→64×8  0x0d→32×14  0x10→8×19(见下)  0x15→8/16/32/64
```

**除了 `0x10`（字符串，读侧内部另走变长循环，工具记为 8），
两侧 11 个标签 × 全部位宽组合逐一吻合。**

## 8. `writeBits` 到底几位——这次读的是完整函数

`0xB77B10` 是 `writeBits(value)`，它调 `0xB77A70`：

```
0x00b77af0  push 0              ← min
0x00b77af2  lea edx,[ebp+0x14]
0x00b77af5  call 0xb777c0       ← writeDataCore
```

等等，重看入口：

```
0x00b77b1c  push 0        ← pad
0x00b77b1e  push 0x1f     ← max = 31
0x00b77b20  push 0        ← min = 0
0x00b77b22  push eax      ← value
0x00b77b23  call 0xb77a70
```

`0xB77A70` 里：

```
0x00b77ac3  mov ecx, ebx      ; ebx = max = 0x1f
0x00b77ac5  sub ecx, edi      ; edi = min = 0
0x00b77ac7  mov eax, 0
0x00b77acc  je  0xb77ad8      ; 范围 0 ⇒ 位宽 0
0x00b77ace  push ecx
0x00b77acf  call 0xb75d40     ; msb_index(0x1f) = 4
0x00b77ad4  add esp,4
0x00b77ad7  inc eax           ; ★ 4+1 = 5
0x00b77ad8  mov ecx,[ebp+8]   ; value
0x00b77adb  cmp ecx, ebx
0x00b77add  jbe 0xb77ae3
0x00b77adf  mov ecx, ebx      ; 夹到 max
...
0x00b77af5  call 0xb777c0     ; writeDataCore(ptr, 5 位)
```

**⇒ 5 位，值域 0..31，超界夹到 31。**

**⇒ 与 `lobby/85` 的结论一致，但这次是读了完整入口 + 完整实现。**
