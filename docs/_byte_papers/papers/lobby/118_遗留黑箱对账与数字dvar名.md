## §1 假黑箱 #1：`-695030357` ≡ `0xD692ADAB`（同一个值的两种读法）

### 1.1 事实

`tools/verify_m695.py`：

```
-695030357 (i32)  ==  0xD692ADAB (u32)   同一 4 字节小端串  AB AD 92 D6
```

该字节串全语料 **237 次**，分布：

| task | 次数 |
|---|---|
| `21/5`（findSessions） | 159 |
| `21/1`（createSession） | 42 |
| `21/12` | 36 |

**237 = 112 卷记录的魔数 A 的 237 次，逐 task 完全一致。**

### 1.2 为什么会出现「两个卷各说各话」

- `112` 卷按 **u32** 读：`0xD692ADAB` → 认出是 matchmaking query criterion（`SessionDescriptor.cs:147` 权威命名）。
- `115` 卷按 **i32** 读：`-695030357` → 认不出，标「不是常见 hash，来源未明」。

**同一个字节串，一个有符号读、一个无符号读，结论分裂。** 这是字节逆向里最隐蔽的陷阱之一：**符号解释改变了一个值的"身份"，但它还是同一串字节。**

### 1.3 收口

`-695030357` **不是新黑箱，是 `0xD692ADAB` 的 i32 别名**。112 卷的定名直接覆盖它。

★★ **方法论**：任何「来源未明」的整数，第一步应该**同时按 i32 和 u32 看**，并检查是否与已定名的魔数同字节串。这一条应该写进字节卷的标准流程。

## §2 真收口：5 个「数字 dvar 名」

### 2.1 它们出现在哪

INDEX §七 曾把 `2486/3265/2489/2574/2500` 列为「5 个 dvar 编号未对应」。`tools/find_dvars.py` 定位：**全部在 `6/14` 的 mmstart 明文里**（`2486/2489/2574/3265` 各 64 次，`2500` 44 次）。

### 2.2 mmstart 的真面目：`dvar value;` 赋值串

`tools/mmstart_full.py` 抓到一条完整 mmstart（233 字节）：

```
mmstart sv_resetServer; 2486 0; 3265 18; 2489 0; 2574 0; 2500 0; g_gametype train;
  2810 0; sv_post_options AAAA...AQAAAAAAAA==; map mp_nuked; roomChatChannelID 0;
```

★★ **语法是 `名字 值;` 的重复**——`sv_resetServer`（命令）后跟一串 `dvar名 dvar值;`。所以 `2486`、`3265` 等**是 dvar 的名字**，只不过名字是纯数字。**它们不是「编号」，是「数字形式的 dvar 名」。**

### 2.3 客户端里确认是 dvar 名字符串

`tools/dvar_names_img.py` 在 E 运行时镜像里搜 `"2486\0"` 等——**各命中 1 处**，且都落在**dvar 名字符串池**里（数字名与语义名混排）：

```
0x9B8F00  2482 | g_hardcore | 2810 | 2485 | 2402 | 1215 | g_difficulty | 2448 | 2683 | 2696 | 2486 | 1218 ...
0x9D8C50  ... 3301 | 2574 | 2819 | sv_onboardBonus | 2588 | 2654 | 3225 | scr_clash_mode_flag | mp_ranked | profileReady ...
0x9B59D8  ... GAMEISENDING | 1011 | 3265 | 3266 | 1014 | 3267 | 3268 | 3269 | 3270 | 1019 | 1020 ...
```

★ 这些数字与 `g_difficulty`/`g_hardcore`/`sv_onboardBonus`/`scr_clash_mode_flag` 等**语义 dvar 名同池**，证明它们就是**同级的 dvar 名**（数字命名只是别名体系）。

### 2.4 值域（决定 dvar 类型）

`tools/verify_dvar3265.py`（64 条 mmstart）：

| dvar | mmstart 值域 | 类型推断 |
|---|---|---|
| `2486` | `{0,1}`（51×1 / 13×0） | **bool** |
| `2489` | `{0,1}`（44×0 / 20×1） | **bool** |
| `2574` | `{0,2}`（44×0 / 20×2） | **枚举（0/2）** |
| `2500` | `{0}`（44×0，恒定） | **常量 0** |
| `3265` | `{1,6,18}` | **枚举/整数** |

### 2.5 `3265` 的双来源交叉（最强证据）

`3265` **同时**出现在两个**独立来源**：

| 来源 | 形态 | 值域 |
|---|---|---|
| **playlist 明文**（`mp_playlists_*.info`，解压后） | `rule 3265 N` | `{1,4,6,8,9,10,12,18}` |
| **`6/14` mmstart 明文**（客户端下发） | `3265 N;` | `{1,6,18}` |

★★ **交集 `{1,6,18}` 完全一致**，且 mmstart 值域是 playlist 值域的子集 ⇒ **`3265` 是 playlist 规则与开局命令共享的同一个 dvar**。这是「两个独立字节来源汇合于同一结论」——可信度最高的信号（同 116 卷 §3.2 的手法）。

★ 另 4 个（`2486/2489/2574/2500`）**只在 mmstart，不在 playlist** ⇒ 它们是**开局专用的 dvar**（每局 mmstart 时按局况设定），不是 playlist 级规则。

### 2.6 语义映射（从同池邻居 + 值域推断，标注可信度）

| dvar | 同池邻居 | 推断语义 | 可信度 |
|---|---|---|---|
| `2486` | 紧邻 `g_difficulty` | **难度相关 bool**（0/1） | 中（邻居+bool 值域） |
| `2489` | 同段 `g_difficulty` 区 | 难度/规则 bool | 中 |
| `2574` | 紧邻 `sv_onboardBonus` | 新手奖励/引导相关（0/2） | 中 |
| `2500` | 同段 | 恒 0 的开关（默认关） | 弱 |
| `3265` | 紧邻 `GAMEISENDING` | **局结束/回合规则**（playlist 也用它） | 中高 |

★★ **诚实边界**：**「是 dvar 名」是铁证（语法 + 字符串池 + 双来源）；「具体哪个 dvar」只能到「邻居+值域」推断级，不能到「权威命名」级。** 要精确命名，需在 dvar 表里读 `名字VA→对象+0xC`（内存转储），但活进程读被 ACE 挡（见记忆 `codol-ace-blocks-debug-and-read`）。

## §3 为什么「数字 dvar 名」这件事重要（对改大厅）

1. **`6/14 mmstart` 是「开局命令串」**，里面每个 `名字 值;` 都是一条 dvar 赋值。**要改开局行为（难度、奖励、回合规则），就是改这些数字 dvar 的值。**
2. **`3265` 双来源**说明：**playlist 规则（`rule 3265 N`）会转成 mmstart 的 `3265 N;`** —— 服务端下发 playlist → 客户端开局时把规则翻译成 mmstart。**这给「改 playlist 就能改开局」提供了协议级证据**（与 21 卷「服务端控制模式列表」呼应）。
3. **数字 dvar 名 = 反查表**：有了 `2486→g_difficulty 区`、`3265→GAMEISENDING`，**改 mmstart 时能定位该动哪个数字**。
