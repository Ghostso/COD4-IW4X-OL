### 2.2 findSessions（21/5）—— 最容易出错的一条

```python
if service in (0x15, 0x8A) and task in (5, 16):
    # 从请求里解析 playlist（第 3 个 u32）
    _pl = _vals[2] if len(_vals) >= 3 else None
    is_pve = _pl in PVE_PLAYLIST_IDS
    objs = [cc.build_mission_session_object(not is_pve, playlist=_pl, ...)]
```

**关键**：服务端**回填客户端请求里的 playlist**，不是写死。
- 靶场：`GameType=0x1000007, MaxPlayers=1`
- PvE 剧情：`GameType=0x1000003, MaxPlayers=4`
- 无开关：`session_objects(qk)` → 258 字节 session 记录

**⇒ 这里有一条重要因果**：协议里 `playlist` 是客户端发的，服务端回显。所以 **157 卷的 116 条 playlist 明文，服务端是能读懂的**（虽然我们现在只把它当数字回填）。

### 2.3 房间 ready（11/4）—— 服务端只回空 ACK，但可选回显

```python
has_ready = (bytes(batch) == cc.ROOM_READY_BATCH or plain[11] == 0x15)
if ch and os.path.exists("ready_push.on"):
    pushes.append((2, cc.instant_push_body(1, "Player", plain, kind=11)))   # 回显
    if has_ready:
        pushes.append((2, cc.instant_push_body(0,"Server",cc.GAME_START_PAYLOAD,kind=11)))
```

**⇒ 房间 ready 的应答有两种模式：**
- **默认（`ready_push.on` 不存在）**：只回空 ACK
- **开启后**：把客户端 payload 原样回显成频道广播 + 若识别为 ready 再推 game start

### 3.2 这直接违反 AGENTS.md 的强制规则

AGENTS.md 原文：

> **ol-mod is NOT authoritative.** It is usable only as a "similar game of the same family" cross-reference.
> Never copy its constants, field layouts, or protocol values into our implementation.
> Its own header states it targets a different build: `net_chan_mp.hpp` — "3.3.3.3 ends a server message with 6; **OLfinal** ends it with 5".

**而 `lobby_server.py` 里有 60 处「照抄 ol-mod / 三方」的实际拷贝。**

### 3.3 源码自己已经记录了拷贝的后果

源码注释里有**三处**「照抄导致的失败」，是我们自己踩过的坑：

| 位置 | 失败现象 | 原因 |
|---|---|---|
| 商城 70（SKU 页） | 「客户端反序列化不了的应答会让**整个 marketplace 服务死掉**（STORE/INVENTORY 变灰且本次会话不再恢复）」 | CODOL 的 SKU 记录**比 MW19 多两个字段**，照抄兄弟作品字段序就炸 ⇒ 现在坚持回空页 |

## 五、这改变了我必须做的事

159 卷我说「剩下的都需要抓包」。**错了。** 正确的下一步是：

### 5.1 服务端应答要按权威等级重审

对每个 `(service, task)` 分支，分三类：

| 类别 | 判据 | 动作 |
|---|---|---|
| **A 已用本地字节验证** | 该分支的字节布局能在**客户端镜像**里找到对应的解码器，且逐字段对上 | ✅ 可信 |
| **B 纯照抄 ol-mod/三方** | 只有「照抄 XXX.cpp:NNN」注释，没做过客户端侧验证 | ⚠ **必须重审** |
| **C 空 ACK / 空页** | 刻意不发内容（如商城 70） | ✅ 安全（不炸） |

**A 类**（有本地证据的）：
- `21/5 findSessions` 的 `playlist` 回填 —— **157 卷 116 条 playlist 明文提供了 ground truth**
- `11/13 createRoom` 的对象布局 —— 需核 139/138 卷的 dwRoom 结构
- `6/x mmbook` 的 `mmbook accepted` —— 122 卷已解 mmstart 全键

**B 类**（纯照抄，待审）：
- `11/1,2,4,5,9,10,11` 的空 ACK 语义
- `21/1 createSession` 的 `blob 8B sessionId`
- `0x47/2` Tencent 用户名
- 全部商城对象布局

### 5.2 关键：客户端镜像里**有**这些应答的解码器

服务端发什么，客户端就得能解什么。**解码器在客户端镜像里，这是本地逆向（第一权威）。**

⇒ 正确做法：**对每个服务端应答对象，去客户端镜像找它的反序列化函数，逐字段核对。**

这不是抓包，是静态逆向 —— 完全可做。

## 七、方法论

1. **★★ 分清「逆向别人」和「检视自己」。** 前者需要样本/抓包；后者**源码就是台账**。
   我把 15 卷的第三方逆向习惯套到自研服务端上，白挂了一项「必须抓包」。
2. **★ 自研代码的「不是黑箱」≠「是对的」。** 有源码只解决「知道发了什么」，不解决「发得对不对」。后者要靠**对齐客户端解码器**。
3. **★★ AGENTS.md 的「ol-mod 非权威」不是形式条款。** 这份服务端 60 处照抄，且已有 3 次实测翻车（商城整服务死、房间 reset、购买点了没反应）。**照抄的成本已经付过了。**
4. **★ 源码注释里的「失败记录」是最贵的证据。** 那三处翻车记录，比任何成功路径都值钱 —— 它们标出了「不能照抄」的具体位置。
5. **★ 服务端应答的正确性判据：客户端有解码器 + 字段逐一对上。** 缺任一条就是「未验证」。
