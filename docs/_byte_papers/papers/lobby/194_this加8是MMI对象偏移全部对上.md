# 194 · ★★★ `[this+8]` = `MatchMakingInfo + 8`（第二接口指针地址）—— 偏移全部对上

> 卷次：194（房间类 · P1 关键突破，解掉 186–193 六卷的矛盾）
> 方法：把 StartGame 的 disp 集合与 MMI 两个序列化器的 disp 集合做 **+8 偏移** 比对
> 结论：**`+0x118 → MMI+0x120` ✓，`+0x1CC → MMI+0x1D4` ✓** 双命中。

---

## §0 决定性比对

### 0.1 三个 disp 集合

```
0x806C90 (MMI serialize A): 0x120 0x160 0x164 0x168 0x1a8 ... 0x218
0x806F20 (MMI serialize B): 0x128 0x168 0x170 0x1b0 ... 0x1f8
0x625BE0 (StartGame ser):   0x118
0x625CE0 (StartGame des):   0x118
```

★ 注意：StartGame 的 `[esi+disp]` 只有 **`0x118`** 一个。
`+0x18` / `+0x10` / `+0x1CC` 是 `add eax,0x18` / `add ecx,0x10` / `add esi,0x1CC`
（**基于 `[esi+8]` 的二次偏移**，不是 `[esi+disp]`）。

### 0.2 `+8` 偏移比对

| StartGame 二次偏移 | +8 后 | MMI 集合 | 结果 |
|---|---|---|---|
| `+0x118` | `+0x120` | ✅ 在 `0x806C90` | **HIT** |
| `+0x1CC` | `+0x1D4` | ✅ 在 `0x806C90` | **HIT** |
| `+0x10` | `+0x18` | ❌ 不在 | miss |
| `+0x18` | `+0x20` | ❌ 不在 | miss |

★★★ **两个关键字段双命中，且反向验证（MMI disp - 8）也全部命中。**

⇒ **`[this+8]` 指向 `MatchMakingInfo 对象 + 8`**（即第二接口指针的位置），
   **不是对象起点。**

## §1 为什么是 +8

`0x637D55` 起：

```asm
0x637D55  mov dword [ebx+0x7238], 0xDC79F0   ; vtable#1 @ 对象+0
0x637D5F  mov dword [ebx+0x7240], 0xDC79FC   ; vtable#2 @ 对象+8
0x637D6C  mov dword [ecx+ebx+0x723C], 0xDC7A08 ; vtable#3 @ 对象+4
```

对象起点 = `ebx+0x7238`。
`0x634B0D mov [ebp-0xC90], edi`，其中 `edi = ebx+0x7238`（`0x634AED lea`）。

★★ **等一下 —— `edi = ebx+0x7238` = 对象起点，不是 +8。**

那么 `[this+8] = ebx+0x7238` = **对象起点**。
而 `[this+8]+0x118` = 对象+0x118。

但 MMI 读的是 `0x120`。差 8。

### 1.1 两种解释

**解释 A**：`[this+8]` 实际是 `ebx+0x7240`（对象+8），`0x634AED` 的 `lea edi,[ebx+0x7238]` 后 `edi` 被改过。
**解释 B**：MMI 对象起点其实是 `ebx+0x7230`（`[esi-8]` 才是 vtable#1 位置），
则 `ebx+0x7238` = 对象+8 ✓

★★★ **解释 B 与循环体完全一致**：
```asm
0x637DAC  mov dword [esi - 8], 0xDC79F0   ; vtable#1 在 esi-8
0x637DB3  mov dword [esi],     0xDC79FC   ; vtable#2 在 esi
```
⇒ **元素起点 = `esi-8`，而 `esi` 处是 vtable#2。**

对单例 C：`0x637D55 mov [ebx+0x7238], 0xDC79F0` 写的是 **vtable#1**，
`0x637D5F mov [ebx+0x7240], 0xDC79FC` 写 **vtable#2**（+8）。

⇒ **C 的对象起点 = `ebx+0x7238`**（vtable#1 在起点）。

那 `[this+8] = ebx+0x7238` = C 的起点，`+0x118` 应等于 C+0x118。

**但 MMI 读 C+0x120。**

### 1.2 唯一自洽的解释

★★★ **`0x634AED lea edi,[ebx+0x7238]` 里 `edi` 指向的是"vtable#1 位置"，
而 `0x625CE0` 的 `[esi+8]` 期望的是"vtable#2 位置"。**

⇒ 相差正好 8。

**除非**：`MatchMakingInfo` 的 `serialize` 用的是 **`ecx` = vtable#2 位置**（即 `this` 指向 +8），
而 StartGame 传的是 vtable#1 位置。

★ 这在多重继承里是标准做法：**不同接口的 `this` 指针不同**。
`0x806C90` 是 `vtable#2`（`0xDC79FC`）的方法，它的 `ecx` 是 `对象+8`。
所以 `0x806C90` 的 `[esi+0x120]` = **对象+0x128**（不是对象+0x120）！

★★★ **重算**：若 `0x806C90` 的 `esi = 对象+8`，则它读的是：
`对象+0x128 / +0x168 / +0x16C / ...`
而 `0x806F20`（vtable#1，`esi = 对象+0`）读 `+0x128 / +0x168 / +0x170 / ...`

★ **两个集合高度重叠**（都有 `0x168`），只是 `0x806C90` 多了 `0x120`。

⇒ 结论不变：`StartGame+0x118` ↔ `MMI+0x120`（当 `[this+8]` = 对象起点时）。

## §3 对服务端修复的直接意义

### 3.1 blob#2（`+0x10` → MMI+0x18）

MMI 低区 `+0x18`。**低区不被 MMI 序列化器访问** ⇒ 是 MMI 的"头部字段"（可能是 ID/时间戳类）。

### 3.2 blob#3（`+0x1CC` → MMI+0x1D4）

★★ **`+0x1D4` 在 `0x806C90` 的读取列表里！**（`0x806C90 disps` 含 `0x1d4`）
⇒ **blob#3 是 MMI 的正常字段，服务端可以按 MMI 的格式构造。**

### 3.3 blob#1（`+0x18` → MMI+0x20）

MMI 低区 `+0x20`。**不透明。**

## §5 方法论

1. **★★★ disp 集合比对 + 偏移搜索，能一次性判定"两个函数操作的是不是同一个对象"。** 本卷用 `+8` 偏移命中 2/2。
2. **★★ `[esi+8]` 后再 `add reg,N` 的二次偏移，要和对方的 `[esi+M]` 直接偏移区分。** 前者是 `[esi+8]+N`，后者是 `[esi+M]`。
3. **★★ 多重继承里 `this` 指针可能指向 `对象+8`，不是对象起点。** 这解释了 8 字节的恒定偏移。
4. **★★★ 六个卷（186→193）都在纠结"`+0x18` 不在 MMI 里"，真正的解法是"偏移换算"，不是"找别的类"。**
