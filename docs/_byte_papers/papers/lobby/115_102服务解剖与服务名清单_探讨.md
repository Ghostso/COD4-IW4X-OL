# 115 · 探讨：`102` 是"该停手的地方"，也是"该诚实的地方"

> 配套：[115_102服务解剖与服务名清单.md](115_102服务解剖与服务名清单.md)

---

## 一、这是全语料唯一没有名字的服务，我想关掉它

114 卷把 55 个 task 里 51 个定名了，剩 4 个全是 `102/*`。用户说"继续逆向直到结束全部黑箱"，
所以这一卷的目标就是关掉 `102`。我做到了**结构层面完全关掉**，但**语义名关不掉**——
而我想诚实地讲清楚为什么。

## 二、结构关掉：`102/*` 是"静态槽位声明"

`102/7` = `08 50 | [03 1 | 0a i]×50`，i 从 0 到 49，**371 条报文里序列 distinct=1**（完全相同）。
`102/1` = `08 0 | 08 N | [03 key | 0a 0]×N`，值全 0。

这个模式太清楚了：**它不携带任何动态数据**。所有值要么是固定序号（0..49），要么是 0。
如果是"查询排行榜"，值应该是玩家 ID / 分数（会变）；如果是"上报统计"，值也会变。
但这里**全语料一个变值都没有** ⇒ 它只能是**声明性的**：声明"我有 50 个槽位""我有 N 个键位"。

这就像 HTTP 的 `OPTIONS` 请求——客户端问"你支持哪些能力"，服务端回"这 50 个"。
至于这 50 个槽位代表什么（50 个排行榜？50 个成就？50 个资源），**字节里没有线索**。

## 三、语义名关不掉：三个候选，一个证据都没有

我从三个角度找 `102` 的名字：

1. **EXE 服务名清单**（`task_svc_names.py`）：`Leaderboard` 出现 35 次（19 大写 + 16 小写），
   与"50 个序号槽位"（排行榜前 50 名）吻合度最高。但 EXE 里**没有服务号→服务名的映射表**，
   无法证明 `Leaderboard` 就是 `102`。
2. **Web 搜索**：环境不支持实时搜索（返回的是"我无法联网"）。Demonware 服务号是 Activision 私有协议，
   公开资料里没有权威的"102 = X"映射。**不能编。**
3. **ol-mod 参考**：搜到的全是 SKU 表（`productId:102` 之类），与协议服务号无关。

三个角度都**指向"Leaderboard 最可能，但无证据"**。我把它写成"最强候选，未定"，而不是"确定是排行榜"。

**为什么这么较真**：如果我写"`102` = 排行榜服务"，下一个人会基于这个假设去实现排行榜协议——
如果错了，会浪费一整轮实验，甚至因为发了格式错的应答而打挂客户端。**一个假的定名，代价是一整轮工作。**

## 四、最有价值的一条：空应答安全，这是实测的

日志 `lobby_srv.log:168-199` 显示，我们的服务端对 `102/7`、`102/1`、`102/5` **全部回空 ACK**（`UNMAPPED`），
而**大厅能正常进**（`5E8=1→3`、31 个 service 全应答，见 memory「enable_iips」那条）。

这是一个**比语义名更有用的结论**：**`102/*` 是可安全空应答的**。
- 如果它是排行榜，空应答 = "暂无排行榜数据"，客户端不会崩。
- 如果它是能力声明，空应答 = "我不支持"，客户端也不会崩（因为它不是关键路径）。

所以对我们写服务端来说：**`102/*` 不需要实现**。这比"知道它叫排行榜"更实用——
知道名字只能满足好奇心，知道"可以空着"才能让服务端跑起来。

## 五、客户端服务名清单本身是个副产品

`task_svc_names.py` 从 EXE 里扒出了完整的 Demonware 服务名清单：Matchmaking、Marketplace、
Leaderboard、Presence、Messaging、Task、Stats、Reward、Friends、Notification、Session、Lobby、Party、Room、Clan。

这份清单本身有价值：**它告诉我们这个 build 支持哪些服务**。对照我们的 55 个 task：
- 已定名的：Matchmaking(21)、Marketplace(80/93)、Messaging(6)、Task(28)、Stats(4)、Friends(9)、Room/Party(11)、Lobby(21)。
- **未在语料里出现的服务名**：Presence、Notification、Reward、Clan。
  ⇒ 这些服务**这个 build 有代码，但我们的抓包里没有调用**。要么是本次会话没触发（比如没加战队就没 Clan 请求），
  要么是走了别的通道（比如 CEF 浏览器）。

★ 这是一个**新的调查方向**：`Reward` 出现 116 次（最多的几个之一），但语料里没有对应 task。
它可能藏在 `28/4 ContentUnlock2`（113 卷）里——"解锁奖励"和"Reward"语义接近。但同样，这是推测。

## 六、方法论沉淀

1. **"值全恒定"本身就是强结论**：`102/*` 所有值恒定 ⇒ 声明性而非数据性。这比逐个猜值快得多。
2. **空应答安全 = 最实用的结论**：比语义名更有用。写服务端只需要知道"能不能空着"。
3. **三个独立角度都只到"候选"，就诚实地停在候选**：EXE 名、Web、ol-mod 都没证据，不写死。
4. **服务名清单是副产品但有价值**：暴露了 build 支持但语料未触发的服务（Presence/Notification/Reward/Clan）。

## 七、这一卷之后：请求侧真的没有黑箱了

到这里，我要向用户明确汇报一个**阶段性终点**：

- **6848 条报文、55 个 task、12 个标签**：全部有**结构**定名（字节层面 100% 闭合）。
- **51/55 个 task**：有**语义**定名（从源码注释 + 行为证据）。
- **4/55 个 task（`102/*`）**：**结构完全解出**，语义名未定，但**行为上可安全空应答**。

**请求侧（客户端→服务端）已经没有"字节黑箱"了。** 剩下的黑箱只在两个地方：
1. **应答侧**：corpus 无应答样本，应答语义只能到源码级（`reply_objects` 最低可信度）。要闭环必须**真实抓包**——需授权。
2. **`102` 的语义名 + Presence/Notification/Reward/Clan 等未触发服务**：需**反汇编客户端读侧**或**跑客户端触发**。

这两条都超出"读语料"的能力边界。要继续，必须**启动游戏客户端**（AGENTS.md：需授权）。
所以我在这里停手，把"请求侧全闭合"作为一个可以交付的结论，而不是硬猜 `102` 叫什么。
