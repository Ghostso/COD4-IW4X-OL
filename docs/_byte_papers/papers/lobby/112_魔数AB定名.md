## §0 结论（先给答案）

| 魔数 | 值 | 身份 | 证据等级 |
|---|---|---|---|
| **A** | `0xD692ADAB` = -695030357 | **matchmaking query criterion（查询判据）** | ★★★★★ 权威命名 |
| **B** | `0x8D51E398` = -1924013160 | **session 记录尾的固定字段**（紧随 `0xDEADC0DE` 家族） | ★★★★ 位置+邻接实证 |

两者**都不是**账号 ID / 频道 ID 的哈希（本卷用 8 种字节形态 × 9 种哈希算法实测 0 命中，证伪）。

## §1 魔数 A 的权威定名

`CODOL-Combat-Server-v0.1/src/Codol/SessionDescriptor.cs:147`：

```csharp
ob.String(mapName);                                                   // 3 地图名
ob.I32(unchecked((int)0xD692ADAB));                                   // 4 query criterion
for (int i = 0; i < 6; i++) ob.I32(0);                                // 5
```

这是 258B session 记录（`build_session_record`）里，**紧跟在 `mapName` 之后的固定 i32**，
注释直接写 `query criterion`。它与 ol-mod 的 `MatchmakingService.cpp:614-629` 同源。

### §1.1 我们语料里的 A 完全同构

`tools/dump_215.py` 抓到的 `21/5` findSessions 请求（4 条全同）：

```
08 01 | 08 00 | 08 0a | 07 D692ADAB | 6b <array>
#00 u32 = 1        ← queryKind（findSessions(queryKind=1)）
#01 u32 = 0
#02 u32 = 10       ← playlist 候选数（与 lobby_server.py:581 注释一致）
#03 i32 = A        ← ★ query criterion 0xD692ADAB
#04 0x6b array     ← 结果容器
```

⇒ **A 是客户端发起 findSessions 时携带的固定筛选判据**。它不是"数据"，而是"查询条件"。

### §1.2 ★ A 的值随 build 变化（关键副产物）

ol-mod 3.3.3.3 的真实抓包黄金向量里，同位置的值是 **`0xD6F01F9B`**（`tools/magic_golden.py` 解出 `#03`）。
我们 3.19 是 `0xD692ADAB`。两者**高 16 位同为 `0xD6`，低 16 位不同**。

- 全语料搜 `0xD6F01F9B`：**0 命中**（`magic_adjacency.py`）。
- 全语料所有 `0xD6??????` 高位 i32：**只有 `0xD692ADAB` 一种**（×237）。

⇒ 这是 **build 派生的判据常量**：不同 build 的客户端用不同的 `0xD6????` 作为 query criterion。
**这是"不能照抄 ol-mod 常量"的又一铁证**——照抄 `0xD6F01F9B` 会被我们 3.19 客户端判为非法查询。

## §2 魔数 B 的定位

`0x8D51E398` 在全语料出现 36 次，全部在 `21/1`(createSession) 与 `21/12`。
`tools/magic_adjacency.py` 给出它的**邻接指纹**（前一个元素 / 后一个元素）：

```
prev=0x07:0x0  next=0x0a:0x1122334455667788  x21   ← 后接频道 ID (u64)
prev=0x07:0x0  next=0x0a:0x6B4C2D0E          x15   ← 后接账号 ID 低32位
```

即 **B 永远紧跟在"值为 0 的 i32"之后，且后面紧跟一个 u64（频道 ID 或账号 ID）**。

### §2.1 与 ol-mod 黄金向量逐字段对照

`tools/magic_golden.py` 解析 ol-mod 的 `FULL_DESCRIPTOR_HEX`（176B，26 元素）：

```
#21 0x07 = 0
#22 0x07 = 0x8D51E398   <<< MAGIC B
#23 0x0a = 0xDEADC0DE   ← 8 字节 0xDEADC0DE
#24 0x07 = 0
#25 0x07 = 0
```

⇒ **ol-mod 3.3.3.3 里 B 也是 `0x8D51E398`，且后面紧跟 `0x0a 0xDEADC0DE`。**
B 在**两个 build 完全相同**——这与 A（build 派生）形成鲜明对比。
B 是一个**跨 build 稳定的协议常量**，位置固定在"会话描述符尾部、账号/频道 ID 之前"。

### §2.2 我们语料里 B 后面的 u64

- 21 次后接 `0x1122334455667788`（= **`roomChatChannelID`**，见 107 卷魔数 C）。
- 15 次后接 `0x6B4C2D0E`（= **账号 ID 低 32 位**，见 110 卷 §3 更正）。

⇒ B 与"频道/账号"是**邻接但不同**的字段。B 本身是会话描述符里的一个固定尾字段，
**不是**频道 ID 也不是账号 ID（它们各自是后面的独立元素）。

## §3 证伪：B 不是 ID 的哈希

`tools/magic_hash2.py`（本卷新建并运行）测试 B / A 是否为下列输入的哈希：

- 输入 8 种：`acc_le8`、`acc_be8`、`acc_le4`、`acc_str`、`acc_str_hex`、`user="M7-E8S6Client"`、`chan_le8`、`chan_str`。
- 算法 9 种：crc32 / fnv1a / fnv1 / djb2 / java / sdbm + md5/sha1/sha256 前/后缀截断。

**结果：命中 = 0。** ⇒ A、B 都不是账号/频道/用户名任何字节形态的常见哈希。
