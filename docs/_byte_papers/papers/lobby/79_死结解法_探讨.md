# 死结解法 · 探讨：两条入口，一个时间问题

> 对应：`lobby/79_死结解法.md`

---

## 一、我怎么发现第二条入口的

**上一卷我用全镜像扫 `[0x849ba30]`，确认只有 1 个写入点，
于是判定"死结"。**

**这一卷我换了个角度：**

> **不查闸门，查 `0x7e98f0` 有几个入口。**

**结果：**

```
0x808650 → 0x7e98f0     （受闸门）
0x4fd287 → 0x808650     ★ 独立调用
```

**⇒ `0x808650` 自己也有两个调用者。**

**⇒ 死结解除。**

---

## 二、这说明什么

**我之前的假设是"`0x7e98f0` 只在 `0x808240` 里被调用"。**

**但 `0x808240` 只是**其中一个**调用者。**

**⇒ 我漏了 `0x4fd287`。**

---

## 三、为什么漏了

**因为 `lobby/47` 我只查了 `0x7e98f0` 的**直接**调用者（`0x808658`）。**

**而 `0x808658` 是 `0x808650` 内部的一条指令。**

**⇒ 我没往"`0x808650` 的调用者"再查一层。**

**⇒ 少查了一层，就漏了一条路。**

---

## 四、教训

> **追调用链时，要追到"函数入口"，而不是"函数内的第一条指令"。**

**`0x808658` 是 `0x808650` 函数体内的指令，
不是函数入口。**

**⇒ 查它的调用者没有意义。**

**⇒ 应该查 `0x808650`（函数起点）的调用者。**

**这次我做了，才发现 `0x4fd287`。**

---

## 五、但问题还没完全解决

**如果 `0x4fd287` 无条件调用 `0x808650`，
那房间对象应该在启动时就创建了。**

**⇒ 但实测是 0。**

**⇒ 剩下的解释是"dump 抓得太早"。**

---

## 六、这个解释的可验证性

**`memory: codol-memdump-timing-critical` 记录：**

> t+23.8s 成功 / t+32.2s 失败（err=5）

**⇒ 抓 dump 有时间窗。**

**⇒ 如果 `client_runtime.bin` 是 t+20s 左右抓的，
而大厅初始化的调用点在 t+30s 之后，
那就解释得通。**
