> 十卷（89–97）的收口。所有数字都有工具可复跑。
> 产物索引：`_byte_papers/msg_spec.py`、`msgtype_FINAL.tsv`、

## 1. 一条 dwRoomMessage 是怎么变成一个字节串的

```
┌─────────────────────────────────────────────────────────┐
│ 五层封装                                                  │
├─────────────────────────────────────────────────────────┤
│ L5  Demonware 报文（service/task 头）   ← lobby/60、61     │
│ L4  dwRoomMessage 消息体（本条）                          │
│ L3  位流（BitWriter，MSB-first）                          │
│ L2  字节对齐（补位到 8 的倍数）                            │
│ L1  传输层（连接单例 [0x8269774]）      ← lobby/55        │
└─────────────────────────────────────────────────────────┘
```

**本十卷只解 L3 + L4。L5 在 `lobby/60`–`61` 已解，L1 在 `lobby/55` 已解。**

## 2. L4 结构（每条消息都一样）

```
msg :=  field*
field := 5 位 tag  +  payload(tag)

payload(0x01) = 1 位
payload(0x02) = 8 位
payload(0x03) = 8 位                 ← ★ 第一个 0x03 字段是消息类型号
payload(0x05) = 16 位
payload(0x06) = 16 位
payload(0x07) = 32 位
payload(0x08) = 32 位
payload(0x0a) = 64 位
payload(0x0d) = 32 位（IEEE-754 float32）
payload(0x10) = (len+1)×8 位（UTF-8 字节 + NUL）
payload(0x13) = 5 位 0x08 + 32 位长度 + 长度×8 位
payload(0x15) = 8 / 16 / 32 / 64 位（★ 位宽随行）
```

**⇒ 没有终止符、没有自描述长度 —— 消息靠"字段表固定"定界。**

**⇒ 这与 ByteBuffer TLV（靠 `0x00` 终止）是两代设计（`lobby/91` §5）。**

## 3. 每条消息的身份 = 前 13 位

```
bits[0:5]   = 00011     恒为 3（tag 0x03）
bits[5:13]  = 类型号     0..46（lobby/94）
```

**这 13 位唯一确定"这是哪条消息"。**

**⇒ 45 个类 → 45 个类型号 → 2 个保留空位（11、25）。**

**⇒ 编号连续 0..46 是对"枚举完整"的强证据。**


## 5. 成员记录 725 位的字段序列（构造 MemberList 必读）

**36 个 tag，顺序严格固定。前 4 个：**

```
0x0a:64   账号 ID（= TLV 里的 CODOID）
0x03:8    槽位
0x01:1    标志
0x15:16   …
```

**中间 28 个 `0x15`（位宽 8/16/32/64 混合）+
6 个连续 bool（源 `0x1B1..0x1B7`）+ 尾部 2 个 u8 + 1 个 bool。**

**完整表见 `_byte_papers/member_record_fieldmap.txt`。**

## 7. 十卷的方法论沉淀

| 卷 | 核心教训 |
|---|---|
| 89 | 反汇编窗口必须以 `ret` 收尾；"漂亮数字"要怀疑来源 |
| 90 | 循环要写成 ×N，不能压成常数 |
| 91 | "哪些没对上"比"哪些对上了"信息量大 |
| 92 | 序列化给"结构"不给"语义"，要分开交付 |
| 93 | 编码器是逆向结论的压力测试 |
| 94 | 宽窗口高命中 = 可疑；连续编号本身就是验证 |
| 95 | 逐位验证优于字节级"看起来对" |
| 96 | 去重作用于计算，不作用于输出；解释≠验证 |
| 97 | 本卷 |

## 8. 明确的剩余黑箱（诚实清单）

| # | 项 | 为什么还没解 |
|---|---|---|
| 1 | **位序 MSB/LSB** | 有三条强证据指向 MSB，但**没有真实抓包** |
| 2 | **字段的业务语义**（34/36 个） | 序列化代码不携带名字；需 UI/GSC 或实测 |
| 3 | **`0x02` 的语义** | D/S 不同步且断言已编空，无法从代码判定 |
| 4 | **P2PInfo 的 67 字节 blob 内容** | 固定长度已知，结构未知 |
| 5 | **`0x15` 各实例的字段名** | 同上（`lobby/92` 已给偏移） |
| 6 | **N 的实际取值** | 头部 u32 已定位，需实测确认范围 |
| 7 | **封包层如何装载本条位流** | L5 层，`lobby/60`/`61` 有部分 |

**⇒ 1–4 全部需要**同一个东西**：一次真实抓包，或者一次成功发包。**

## 9. 为什么说到这里就该停了

**静态分析能回答的问题类型是有限的：**

**能答：**
- 有哪些消息（45 条）
- 每条多长（35 条精确）
- 字段顺序与位宽（全部）
- 类型号（全部）

**不能答：**
- 字段叫什么
- 值该是多少
- 客户端收到会不会接受

**⇒ 后三个问题的共同点是：它们都是**运行时的**，而代码里没有。**

**⇒ 继续读汇编，只是在同一份信息上重复推理。**
