## 二、真正有价值的是 R13

R13 是本轮唯一"如果做错就会全盘失效"的地方。

`build_manifold()` 是生成 `6/5` 应答的。它头部是：

```
[3 位 tag][8 位 type][8 位 ?][32 位 count]
```

那个 8 位产生过三种说法：

| 卷 | 说法 |
|---|---|
| 67 | 是"字段类型码" |
| 169 | 是"零填充"，正常路径什么都不写（所以 7 字节里那 8 位其实不存在） |
| 174 | `+0x21==0` 时不写 ⇒ 房间路径 6 字节 |

**169 和 174 是一致的：写侧 `+0x21==0`，不写。**

但 6/5 应答是**服务端生成、客户端读**。我这次去读了客户端的**读取器**：

```asm
0x637026  push 1            ← ★ 读侧 ctor 第 3 参 = 1
0x63702C  call 0xB779A0
```

```asm
0xB774F0  cmp byte ptr [ecx+0x21], 0
0xB774F6  je  0xB7754F      ← 为 0 就跳过，en al=1 直接返回 True
```

**读侧 `+0x21 == 1` ⇒ 不跳过 ⇒ 真的读那 8 位。**

再核对读侧完整头部：

```asm
0x625721  push 8  / call 0xB774E0     ; 读 8 位
0x62572E  push 0x20 / call 0xB772E0   ; 读 32 位 count
```

**3 + 8 + 8 + 32 = 51 位 = 7 字节。**

结论：**服务端必须写 7 字节。** 当前代码已经是 7 字节，不用改 —— 但注释必须改，因为 169 卷那句"调试态才写 8 个 0"会让人下次把它删掉。

## 三、这件事的一般形式

**同一个二进制里，同一个偏移，读侧和写侧可以取不同的值。**

`[obj+0x21]`：

| 对象 | 值 | 谁构造的 |
|---|---|---|
| 写侧 Manifold 序列化器 | 0 | `0x62C3AA push 0` |
| 读侧 Manifold 解析器 | **1** | `0x637026 push 1` |

因为 `0x637009` 那段是**客户端解析服务端应答**用的，`+0x21=1` 的意思是"我这边要严格按格式读"。而 `0x62C380` 是**客户端自己拼消息**用的，`+0x21=0` 意思是"我自己拼的，不需要额外标记"。

**所以：服务端生成应答时，必须模拟"客户端读侧"的期待，而不是"客户端写侧"的输出。**

这条如果搞反，症状是：客户端不报错，但把 type 的低位当成了那 8 位，count 读成垃圾，然后认为队列里有天文数字条消息 —— 要么卡死要么崩。
