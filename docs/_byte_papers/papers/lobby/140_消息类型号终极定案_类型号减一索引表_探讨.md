# 140 探讨 · 我花了一整轮去「更正」一个本来正确的结论

> 配套：[140 · 消息类型号终极定案](140_消息类型号终极定案_类型号减一索引表.md)
> 主题：**139 卷最自信的那条「更正」，在 140 卷被一条减法推翻。错的不是 138，是我。**

---

## 一、发生了什么

**138 卷说**：`opcode 6 → 0xB7B210`（邀请/队列消息）。

**139 卷说**：不对，`0xB7B210` 是 **op5**；房间消息走 **op7/8**，并把这个当成「本卷对 138 的第二处实质更正」。

**140 卷说**：138 是对的。139 错在把**表索引**当成了**类型号**。

---

## 二、错误的完整生成过程

我当时的推理是：

1. 读出 76 项表：`0xB83744[0..75]`
2. 发现 `0xB83744[5] = 0xB82DDD`，而 `0xB82DDD` 里 `call 0xB7B210`
3. 结论：`0xB7B210` 属于「op5」

**每一步都"看起来对"。错在没有任何一步去问：表索引和 opcode 是同一个数吗？**

真值就在跳转前 2 个字节：

```
0xB82D42  dec eax
0xB82D4C  jmp [eax*4+0xB83744]
```

**我读过 `0xB82D4C` 这一行，甚至把它写进了 139 卷的 §2.1，但没有读它上面那行 `dec`。**

★ **这是最痛的一种错误：不是没看到证据，而是看到了证据却没读它前面那条指令。**

---

## 三、一条减法就够了

140 卷推翻 139 用的是：

```
0xB83870 − 0xB83744 = 0x12C = 300 = 75 × 4
```

第二张表的起始地址，减去第一张表的起始地址，**正好是第一张表的长度**。

而代码里 `cmp eax, 0x4A`（74）—— 索引上界 74，即 **75 项**。

**两个独立数字对上了。** 而 139 卷报的「76 项」直接与之矛盾。

★★ **教训：表长永远可以自证 —— 「表首址之差」和「cmp 的上界」是两个独立来源，
两者不一致时，一定有一方是错的。**

---

## 四、这一卷真正的收获不是"更正"，是"解码链"

把错误修正之后，整条链第一次完整了：

```
网络帧
 → 0xB838A0 handleMessage
 → 0xB80D30 / 0xB7FAD0     4 字节服务名 → FNV-1a → 哈希表 → 类型号
 → 0xB82D2C cmp 1001 / jg  特殊分支
 → 0xB82D42 dec eax        索引 = 类型号−1
 → 0xB82D4C jmp [表]       类型号 1..75
 → handler → vtable slot → 真正的业务函数
```

**这条链第一次解释了「为什么一个消息会走哪个 handler」的完整因果。**

---

## 五、但链上有一个洞，而且这个洞比 139 的错更重要

`dwLobbyImp` 注册服务名用的是 `0xB80D90`。它有 **25 个调用者**。

我把 25 个调用点的 `push imm32` 全抽出来 —— **全部是 `0xDAE091`**。

`0xDAE091` 是什么？**空串哨兵**（记忆里 `codol-uipage-pageid-and-ui-dispatcher` 已记录：`0xDAE091` = 空串）。

**⇒ `dwLobbyImp` 的名字表在静态下是空的。类型号 1..75 对应的 4 字符服务名，
不是编译期常量。**

这不是"我没找到"，而是**代码本身就指向"运行时注入"**。

★★★ **这正是 139 探讨里那条教训的第二次发作**：
「查调用者要分三种边」—— 这次是第四种情形：**调用者全都在，但参数是空的**。
空参数本身就是结论：**名字来自别处**。

## 七、方法论（并入 140 §8）

1. ★★★★★ **表长永远可以自证**：`表2首址 − 表1首址` 与 `cmp 上界` 必须一致。
2. ★★★★★ **`jmp [eax*4+表]` 之前 5 个字节必须读完**：`dec`/`sub`/`add`/`shl` 任意一条都会改变索引语义。
3. ★★★★ **「更正」别人之前，先做一次能自证的减法**。如果做不出来，先不要更正。
4. ★★★ **调用者全在但参数全是哨兵 ⇒ 参数是运行时注入的**，这本身就是结论。
5. ★★ **两张表规则不同要分开验**：`0xB83744` 有 `dec`，`0x82E1458` 没有。

---

## 八、给下一步

1. **类型号 7 还是 8** 静态已无法区分（handler 相同），只能动态观测或从服务端名字反推。
2. **4 字节服务名的真实值**是 140 的主要未闭合项 —— 需要动态读哈希表，或从注册时的
   `0xB7F950` 调用点参数（运行时）取。
3. **不要再基于「op6」做任何修复** —— 6 是邀请弹窗，发了只会弹对话框。
