# 报文方向判定 · 探讨：为什么"方向"比"字节"更重要

> 对应：`lobby/108_报文方向判定.md`

---

## 一、上一轮我留了一个坑，这一轮必须填

**`107` 卷结尾我写：**

> "本卷暴露了一个比逐字节更重要的事：报文方向（谁发给谁）还没定。
> 如果不知道方向，逐字节分析就只是'知道字节是什么'，不能'利用它'。"

**⇒ 这一卷就是来填这个坑的。**

**★ 而且填的方式很朴素：**去读生成 corpus 的那个脚本的源码**。**
  **不用逆向、不用转储、不用断点 —— 只需要看 `lobby_tasks.bin` 在哪里被写。**

**⇒ 结果：唯一写入点在 `decrypt_task_frame` 之后。**

**⇒ 一句话结论：corpus 全是客户端发来的。**

---

## 二、这个结论为什么"值钱"

**因为在此之前的 6 卷（102–107），我一直默认"这些字节是协议的一部分"，
但没分清是**请求**还是**应答**。**

**⇒ 这两者的差别是致命的：**

**如果 corpus 是**请求**（客户端说的），那我们分析的字段是"客户端告诉我什么"。
  ⇒ 我们要做的是**读懂并应答**。**

**如果 corpus 是**应答**（服务端说的），那我们分析的是"服务端该说什么"。
  ⇒ 我们要做的是**照抄格式发出去**。**

**★ 这两条路的工程做法完全不同。
  分不清方向，就会犯"抄着请求去当应答"的错。**

**⇒ 而项目记忆里其实已经踩过这个坑：
  `lobby/74` 把推断写成"实测 0"，导致 77–79 三卷作废。
  方向不明就写结论，就是同一类错误的温床。**

---

## 三、证据链：我为什么敢说"100% 入站"

**我没有满足于"看注释里有'客户端发的'这几个字"。**

**我做了三级证据：**

**① 代码级：唯一写入点。**
```
第 1142 行：open(...lobby_tasks.bin, "ab").write(...)
```
**它上面第 1116 行是 `r = cc.decrypt_task_frame(fr, ...)`。
下面第 1147 行是 `reply_objects(...)`（构造应答）。
⇒ 写入发生在"解密之后、构造应答之前" ⇒ 写的是**收到的明文**。**

**② 结构级：函数签名。**
```
reply_objects(service, task, plain) -> (objects, note, pushes)
```
**`plain` 是输入，`objects` 是输出。**名字就叫"reply"**。
⇒ 输入是客户端说的，输出是我们要回的。**

**③ 内容级：请求形态。**
**- `11/13` 是空 payload（建房间请求无参数）**
**- `21/5` 带 playlist 查询条件**
**- `6/14` 带 `mmstart ... map X`（客户端告诉服务端它选了哪张图）**
**- 每个 run 里 `21/5` 出现 11 次（轮询）**
**⇒ 全是"请求"的特征，没有一条像"应答"。**

**★ 三级证据互相独立，全部指向同一结论。
  这比"我看注释说是客户端发的"强得多。**

## 四、附带收获比主结论更值钱

**这一卷的**主结论**是"方向 = 入站"。**

**但**附带收获**是：`reply_objects` 里有 **22+ 条 service/task 的语义与布局注释**。**

**⇒ 这相当于拿到了一份"协议字典"，而且是**受保护资产里的**（可信度高）。**

**★ 它把前 6 卷的字节级结论全部**升格**了：**

| 前几卷说的 | 现在知道的 |
|---|---|
| "8/3 = u32×4 + blob + i32×125" | **8/3 = 客户端上传玩家档案，125 个 i32 是档案尾清单** |
| "21/1 = 30 元素玩家档案" | **21/1 = createSession，进/出房间时发** |
| "21/5 = 有 playlist 参数" | **21/5 = findSessions，第 3 个 u32 就是 playlist** |
| "11/13 = 空 payload" | **11/13 = createRoom（无参请求）** |
| "6/14 = mmstart 明文" | **6/14 = 即时消息，且主流是 mmbook 不是 mmstart** |

**⇒ 逐字节分析是"看到树叶"，`reply_objects` 是"看到树的名字"。
  两者结合，才是完整的。**

## 五、但我没有无条件相信 `reply_objects`

**`AGENTS.md` 明确规定可信度分级：**
```
本地逆向 > IW4X > CoD4X > 其他外部项目
```

**`reply_objects` 的注释明说是"照抄 ol-mod / 三方 C#"。**
**⇒ 按分级，它是**最低档**。**

**★ 所以我在论文 §8 明确写了：
  "它的布局注释可以用作线索，但不能当权威。"**

**⇒ 具体做法：**
**- 它说的"service/task 语义"（如"8/3 是上传档案"）—— 可以用，因为我能用
  corpus 的字节独立验证（125 个 i32 确实存在）。**
**- 它说的"应答对象布局"（如 `createRoom 对象 = u64+u32+u32+u64+bool+bool+u32`）
  —— **不能直接用**，因为 corpus 里**没有应答样本**可以对照。**

**★ 这是"分级"的实际操作：同源材料，不同部分可信度不同，
  要按"能否本地验证"来分别对待。**

## 六、实测把参考实现的一条说法**改了**

**`reply_objects` 第 842 行说：**

> "真实客户端发的是 `mmbook 1 <base64> 0`，**不是** `mmstart <token>`。"

**我没照抄，而是去 corpus 实测。**

**结果：**
```
mmbook  : 127 条   ← 主流
mmstart :  64 条
mmban   :  44 条   ← 参考实现完全没提
```

**⇒ 参考实现说的"主流是 mmbook"**对了**。
  但它说"不是 mmstart"**错了** —— 有 64 条 mmstart。
  而且它**漏了 mmban**（44 条）。**

**★ 这正说明为什么不能照抄第三方：
  它的观察基于**某几次抓包**，不是全语料。
  我们有了 6848 条全语料，就比它更全。**

## 七、★★ 最大的收获：`mmbook` 的 base64 就是魔数

**实测 `mmbook` 只有两种：**

```
mmbook 796 AQAAAAAAAAA= 0    ×107   → base64 解码 = 01 00 00 00 00 00 00 00  = u64 1
mmbook 796 iHdmVUQzIhE= 0    ×20    → base64 解码 = 88 77 66 55 44 33 22 11  = u64 0x8877665544332211
```

**★ 而 `0x8877665544332211` 小端读出来就是 `0x1122334455667788` ——
  正是 `107` 卷解出的 `roomChatChannelID` 魔数！**

**⇒ 三条完全独立的路径，指向同一个常量：**
1. **`107` 卷：二进制 u64 `0x0a` 字段（298 次）**
2. **`107` 卷：`mmstart` 明文 `roomChatChannelID 1234605616436508552`（47 次）**
3. **本卷：`mmbook` 的 base64 `iHdmVUQzIhE=`（20 次）**

**★ 三条路径 = 铁证。而且它揭示了 `mmbook` 的第二个参数就是"频道 ID"。**

**⇒ 这意味着 `mmbook <token> <base64(u64 channelId)> 0` 的语义是：
  "我（token=796）要在频道 <channelId> 上预约/占位"。**

**⇒ `AQAAAAAAAAA=` = 频道 1，`iHdmVUQzIhE=` = 频道 `0x1122334455667788`。**
  **前者是靶场/训练（单机默认频道 1），后者是线上默认频道。**

**★ 这是一个**可直接操作的字段**：
  如果我们想让客户端在"我们的"频道上预约，改这个 base64 就行。**

## 八、`6/14` 的内层结构：4 字节长度前缀

**这一卷还实测出一个之前没注意的结构：**

```
blob 内容 = [u32 长度][命令串]
```

**验证：235/235 个样本，首 4 字节 u32 == `len(blob) - 4`。**

**⇒ 这是**完全确定**的结构（235/235，没有例外）。**

**★ 而 `lobby_grammar_v5` 把整个 `0x13` 的 body 当作一个 blob，
  没解析内层的这个长度前缀。**
  **⇒ 这是一个可以补进文法的细节：`0x13` 在 `6/14` 里是"嵌套的 TLV"。**

**⇒ 更准确地说：`6/14` 的 `0x13` body = 一个**内层报文**，
  它自己也是 `[len][data]` 格式。**

## 九、`roomChatChannelID` 有三个值，不是两个

**实测 `mmstart` 里的 `roomChatChannelID`：**

```
1234605616436508552  ×47   ← 魔数 0x1122334455667788
0                    ×13   ← 未设置
1800154382           ×4    ← ★ 一个新值！
```

**⇒ 出现了一个 `1800154382`（= `0x6B4E6E0E`），4 次。**

**★ 这个值**不是**易读魔数，看起来像**真实分配的频道 ID**。**
**⇒ 说明在某些场景（可能是特定的 playlist 37 组队模式），
  客户端拿到的是**真实频道 ID**，不是默认魔数。**

**★ 这条对"自定义大厅"很重要：
  **说明频道 ID 是**服务端分配**的，不是客户端写死的。**
  **⇒ 我们能控制它！**

**⇒ 但注意：`1800154382` 只在 4 条里出现，
  不足以确定它是"服务端给的"。标注为**待验证的推测**。**

## 十、方法论收获（三条）

> **① 判断方向不要猜，去读"写日志的那行代码"。
>    写入点在上游（解密后）还是下游（应答前），就是方向。**

> **② 附带收获常常比主结论值钱。
>    这一卷主结论是"入站"，但真正的金子是那份 22 条的语义表。**

> **③ 第三方参考实现的说法必须**全语料实测复核**。
>    `reply_objects` 说"不是 mmstart"是错的（有 64 条），还漏了 mmban（44 条）。**

**⇒ 下一个问题变成："客户端请求了之后，服务端该回什么？"**
