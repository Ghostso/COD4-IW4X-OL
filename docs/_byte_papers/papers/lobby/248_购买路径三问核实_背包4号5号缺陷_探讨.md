## 一、第一眼看到的"证据"是假的

查第一个问题时，我扫到 `unknown_skus.txt`：

```

39039	Unsupported SKU/currency/quantity
```

**第一反应**：这就是"购买失败"的铁证，156 次失败。

**如果我就此下结论**，我会回答："组合包/军牌/徽章都买不了，有 156 条失败记录"。

## 二、但我查了那个错误串还在不在

```powershell
Select-String -Path "marketplace_store.py","lobby_server.py" -Pattern "Unsupported SKU"
→ （空）
```

**当前代码里没有这个字符串。**

再看时间戳：
- `unknown_skus.txt` = **2026-10-10**
- `marketplace_store.py` = **2026-10-16**

**⇒ 那 156 行是旧版遗留。** 当前代码的购买逻辑在 10-16 被重写过（`parse_purchase` 改成结构化解析、加了 `_extra_sku_map` 自动映射）。

★ **拿一份 6 天前的日志当"当前故障"，会得出完全反向的结论。**

## 四、但"能解析"也不等于"修好了"

我差点在这里停手 —— "111/122 能查到，Q3 解决了"。

**再往下看一层**：`purchase()` 拿到 SKU 之后做什么。

于是发现了 4/5 号背包的真实缺陷：**两个 SKU 指向同一 item，非 stackable 分支只在 `owned == 0` 时授予。**

★ **"查得到" ≠ "给得对"。** 这是本卷最重要的一条。

---

## 五、离线模拟：不启动游戏也能拿到硬证据

4/5 号背包的缺陷需要"买两次"才能暴露。我没有实机权限，但可以：

1. 复制合法的 `player-account.json` + `marketplace-inventory.json` + `secure.result` 到**临时目录**
2. 调真实的 `ms.purchase()`
3. 观察 `Items` 与余额

结果（本卷 §2.2）：

```
buy 241 (4号)  → Items[121]=1, 扣 1880
buy 242 (5号)  → Items[121]=1, 不扣款、不加量
```

**并且真实库存文件同构**：`Items["121"]=1`、`Items["241"]=1`、`Items["242"]=1`。

★ **这个手段值得记住**：购买逻辑是纯 Python，**不需要游戏就能端到端验证**。
过去遇到"购买"类问题我总想"要实机"，**其实只有"显示"才需要实机**。

## 六、为什么之前没人发现

因为**两个 SKU 指向同一个 item** 这件事，藏在 `item_sku_arrays.csv` 的两行里：

```
121,241,1880,30
121,242,9680,0
```

而 `purchase()` 的判定是"按 `Item` 计已拥有"。**两者相隔两个文件**。

★ 和 247 卷同一个毛病：**跨文件对照缺失**。247 是 `_sku_schema_as.py` vs `market_skus.py`；248 是 `item_sku_arrays.csv` vs `marketplace_store.py`。

---

## 七、这次我没有动手修，为什么

因为修复方案取决于一个我**不知道的**事实：

> **客户端按什么键显示"第 N 个背包"？按 `Item`(121) 还是按 `Sku.Id`(241/242)？**

- 若客户端按 `Item` 计数 → 方案 B（槽位型允许累加）
- 若客户端按 `Sku.Id` 判拥有 → 方案 A（改用 SKU 做库存键）

**猜错方向就会把能用的东西改坏** —— 235 卷就是这个教训（把商城 `reply+5` 的结论外推到别的服务，极性正好相反）。

★ **所以本卷只给判定 + 方案，不动手。** 要动手，需要**一个真实库存样本**或一次实机对照。
