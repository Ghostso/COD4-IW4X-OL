# 132 · 12 字节行的结构定案：AS_* 是 829 个单虚函数对象，不是一张派发表

> ★★ **137 卷更正**：本卷「**真实步进 17 字节**」「131 按 12 ⇒ 每 4 个对象错位一格」**作废** —— 实测 `0x693DD0` 字面量相邻间隙 **803/830 = 12**，`0xDC8910`/`0xDC8988` 直读亦确认 `[COL][vf0][vf1]` **12 字节紧排**。本卷其余结论（COL 判据 / 829 对象 / `0x693DD0` = 共享标量删除析构 shim / Flash 经 `vtable[1]` 间接调用 / 63 个 `?N@??Init@UiCppXxx@@` 局域类）**不受影响**；137 §3 已独立复核 `0xDC7BA4`=2 槽、`0xDC7AF4`=1 槽、AS_* 各 2 槽。

> 前作：[131 · AS_* 原生函数登记表定名](131_AS原生函数登记表定名UserComplaint与sendGpuLatchedSettings.md)
> 任务：闭掉 131 §十三 遗留的「12 字节单元是虚表还是描述符行 · 不定案」。
> 结论：**两者都不是**。是 **829 个独立对象的虚表**，每个对象只有 **1 个虚函数**。
> 性质：结构性结论 + 一处对 131 的**数据层更正**（行数 / 名字 / 槽语义）。

## §0 本卷九条结论

1. 12 字节单元的**真实结构** = `[COL][vftable 槽0=0x693DD0][vftable 槽1=handler]`，即 **MSVC 标准虚表布局**，`vftable[-1]` 就是它自己的 Complete Object Locator。
2. 每个对象**只有一个虚函数**。131 卷看到的"多槽表"是**逐对象虚表首尾相接**造成的视觉错觉。
3. 因此 `0x693DD0` 不是"表头哨兵"，是**每一行共享的标量删除析构函数（scalar deleting destructor shim）**。
4. 全镜像这类对象共 **829 个**（不是 806）。
5. **131 卷的 806 行里有 18 行是假行** —— 原因是 131 的正则 `[A-Za-z0-9_@?$<>,\-]*` 遇到模板名里的 `,` 截断，导致"同一对象被记成两条"。本卷用 COL 反查，一个对象一行。
6. ★★ **本卷补齐 131/130 的页名缺口**：829 个对象里有 **63 个**的类名是 `?AU<Handler>@?N@??Init@UiCpp<View>@@QAE…` 形态 —— **注册它的 View 类和局域编号直接写在 RTTI 名里**，不需要全局映射表（§八·补）。其中 `UiCppMatchSelectView::Init` 一个函数注册 **28 个**（含整条房间入口链 + `OnRoomsListed`/`OnRoomListExpired` 房间列表回调）。
7. **132 卷不推翻 131 的定名**：`0x5D3790`=AS_TencentReportBadLanguage、`0x5D39E0`=AS_SetRecommendedSetting、`0x5D3CB0`=AS_IIPS_Response 全部用**四个独立锚点**在本卷复核通过（见 §五）。
8. `0x8435E0`（`c2 04 00`）被 **22 个对象**共用 ⇒ 131 卷"一址三名"实际是"一址二十二名"，这个 build 里 **22 个 Flash 接口被整体禁用**，不是 3 个。
9. 派发形态定案：Flash 调用 `obj->vftable[1]`（`0x5D2E00` 给出逐字节证据），**所以 `callsite_finder` 对任何 AS handler 都必然报 0** —— 131 卷"0 是正确结果"的判断是对的，且现在有了形态级证明。

## §一 12 字节单元的逐字节解剖

以 `0xDC8904` 为起点，16 字节实际排布：

```
VA            bytes                含义
0x00DC8900    98 2d df 00          COL 指针 -> .?AVAS_CreateRoom@@
0x00DC8904    d0 3d 69 00          vftable[0] = 0x00693DD0   标量删除析构 shim
0x00DC8908    70 2e 5d 00          vftable[1] = 0x005D2E70   AS_JoinRoom 的 handler
0x00DC890C    3c 2d df 00          COL 指针 -> .?AVAS_JoinRoom@@
0x00DC8910    d0 3d 69 00          vftable[0] = 0x00693DD0
0x00DC8914    00 2f 5d 00          vftable[1] = 0x005D2F00   AS_EnableRoomListEvent
```

★★ **17 字节一个对象，不是 12 字节。** 131 卷按 12 步进，所以每 4 个对象就错位一格；错位后 `[COL][thunk][handler]` 被读成了 `[thunk][handler][COL]`，这正是 131 §十三"两种读法都讲得通"的根源。

★★ **判据（可复用）：`vftable[-1]` 是不是一个合法 COL。** 合法 COL 的定义在本 build 里是四段零：

```
+0x00 signature   = 0
+0x04 offset      = 0
+0x08 cdOffset    = 0     ← 注意：不是 MSVC 标准的 1
+0x0C pTypeDescriptor -> ".?A....@@"
+0x10 pClassHierarchy
+0x1C = 6
```

实测 `806/806` 的第三字段、以及 `829/829` 的 `vftable[-1]`，均满足这个判据。**虚表不可能含数据指针**，这一步就排除了"虚表"读法。

## §二 131 卷 806 与 829 的差：正则截断

131 用 `rb"\.\?A[VU][A-Za-z0-9_@?$<>,\-]*@@"` 抽名字。这个字符类**不含 `,`**（虽然写了 `,\-` 在类里，但 `-` 在前面已被当作范围，`\` 转义后实际匹配的是 `-` 和 `\`）。

后果：

- `.?AV?$UiCppUserDataTyped@UUiCppUserData@@` 这类名字含 `@` × N，能过；
- 但 131 扫到的 806 条里，有若干是**同一对象的 COL 被匹配了两次**（一次从 type_info 名、一次从别处）。
- 反查 COL 得到的 **829 个对象**是唯一解 —— 因为"每个 COL 只属于一个对象"是编译期事实。

★★ **教训：用正则抽 C++ 修饰名，字符类必须按"修饰名的合法字符全表"写，不能凭印象。** `$ ? @ < > , -` 六个都要，且 `-` 必须放在类末尾。

## §三 `0x693DD0` 的身份：不是表头，是共享析构

```
0x693DD0  55                push ebp
0x693DD1  8b ec             mov  ebp, esp
0x693DD3  56                push esi
0x693DD4  8b f1             mov  esi, ecx
0x693DD6  c7 06 a4 7b dc 00 mov  dword [esi], 0xDC7BA4   ← 写父类 vftable
0x693DDC  e8 cf 2f 19 00    call 0x826DB0                ← 父类析构
0x693DE1  f6 45 08 01       test byte [ebp+8], 1
0x693DE5  74 0e             je   0x693DF5
0x693DE7  8b 0d dc 78 e7 00 mov  ecx, [0xE778DC]
0x693DED  8b 01             mov  eax, [ecx]
0x693DEF  8b 50 30          mov  edx, [eax+0x30]
0x693DF2  56                push esi
0x693DF3  ff d2             call edx                     ← operator delete
0x693DF5  8b c6             mov  eax, esi
0x693DF7  5e 5b 5d c2 04 00 pop esi / pop ebp / ret 4
```

这是 **MSVC 标量删除析构函数**的标准形状。`0xDC7BA4` 是父类（`Scaleform::GFx::FunctionHandler`）的虚表。

★★ **`0xDC7BA4` 自身的 `vftable[-1]` = `.?AVFunctionHandler@GFx@Scaleform@@`** —— 父类确认。

★★ **所以 `0x693DD0` 出现在 829 个对象里 829 次，是"每个对象都继承同一父类、都用自己的删除析构"的必然结果，不是"表头"或"哨兵"。**

131 卷 §十三 说"`0x693DD0` 是 dtor shim 却出现在 806 行 slot0，裂缝" —— **裂缝现在闭合了**：它不是 slot0，它是每个对象自己的 slot0，因为每个对象都只有一个虚函数。

## §四 派发形态：为什么 callsite_finder 必然报 0

`0x5D2E00`（`AS_CancelList` 的调用约定样本）逐字节：

```
0x5D2E00  10                ...（前置指令省略）
         8b 11             mov  edx, [ecx]          ← 取 vftable
         8b 52 08          mov  edx, [edx+8]        ← 取 vftable[1]  ← ★
         50                push eax
         56                push esi
         ff d2             call edx                 ← 间接调用
```

★★ **`[edx+8]` 就是 vftable[1]（第二个槽，字节偏移 8）。** 这是 Flash 侧调用原生接口的唯一形态。

**后果**：任何 `E8 rel32` 都**不会**指向 `0x5D2E70` 等 handler。所以：

- `callsite_finder 0x5D39E0` = 0 ✔（131 卷判断正确）
- `ptrref_scan --calls 0x5D3790` = 0 ✔

★★ **这是形态级证明，不是"猜"**。131 §三 给出的"先问该不该有 call 边"的启发式，本卷升级为**机械判据**：*目标是否是 `vftable[-1]` 为合法 COL 的对象的槽 ≥1 ⇒ 必然无 rel32 调用边。*

## §八·补 ★★ 63 个对象的类名里直接写着"谁注册的、第几个"

829 个对象中，有 **63 个**的 RTTI 修饰名是 **函数内定义的局域类**：

```
.?AUOnPvpModeClick_SF_Handler@?BH@??Init@UiCppMatchSelectView@@QAEXAAVValue@GFx@Scaleform@@@Z@
                  └── 局域类名 ──┘ └序号┘ └──── 宿主函数 ────┘ └──── 参数表 ────┘
```

## §九 与 127/129 遥测链的关系（重要修正）

131 卷把 `0x5D39E0` 定为 `AS_SetRecommendedSetting`，四分支分别调 `0x641180`(UIClick)/`0x6411E0`(UIPage)/`0x641340`(UIKeySetting)/`0x477910`(通用)。

本卷确认：**这四个都是遥测入口，`0x5D39E0` 是它们的上游调用者，不是派发器**。语义链：

```
Flash: "推荐设置" 按钮
   → AS_SetRecommendedSetting  (0x5D39E0)
      → 应用设置（真动作）
      → + 顺带打 3 条遥测（UIClick / UIPage / UIKeySetting）
```

★★ **"顺带打日志"不是"身份"。** 131 卷已经写进方法论；本卷追加一条**结构判据**：

> **凡 `vftable[-1]` 为合法 COL 的对象，其槽1 的语义是"Flash 暴露的一个动作"，绝不是"日志派发器"。** 因为 Scaleform 的外部函数表是**动作面**，不是**事件面**。

★ 这条能防止下一次同样的误判：只要先跑 `iscol(vftable[-1])`，就知道"这是一个 Flash 动作对象"，再也不会把它当派发器。

## §十 诚实边界

1. **短名 → 对象的映射表本体未找到**（§八）。只知道名字池和注册点，不知道表在哪。**但 §八·补 用 63 个局域类名补上了"哪个 View 注册哪些 handler"，缺口收窄为"主菜单那条路径"。**
2. **829 的族谱里 `AS_` 的确切数量** = 678（本卷工具全量统计，非抽样）。
3. **`0x5D2E00` 的完整函数体**只反汇编了首 48 字节，`[edx+8]` 之外是否还有第二处间接调用未穷举。
4. **CEF 对象（`0xD569xx`）与 AS 对象的边界**按"槽0==0x693DD0"切分，但同一镜像里是否存在既非 CEF 也非 AS 的第三族未统计。
5. **`0x693DD0` 写入的 `0xDC7BA4` 是父类 vftable** —— 这证明 829 个对象都继承 `FunctionHandler`，但**父类是否还有更多槽**（即"对象是否其实有 2 个虚函数，槽1 只被覆盖"）**未验证**。若父类有 N 个槽，则本卷"只有一个虚函数"应改成"只覆盖了一个"。
