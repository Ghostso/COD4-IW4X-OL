# 226 · ★★★★ 更正 213–216：`0x632680` 在 `dwRoomImp` vtable `+0x13C`，但**全镜像无调用点**

> 卷次：226（**房间类 · 第七次更正**）
> 方法：定 vtable 起点 → 算槽号 → 字节搜索该槽的所有读取
> 结论：**`0x632680` 是 `dwRoomImp` 的孤立 vtable 条目，静态无调用点。**

---

## §0 vtable 起点定案

```
0xDC7270: 0x00DF96D8   ← COL 指针（RTTI）
0xDC7274: 0x006391E0   ← vtable[0]（MyRoomImp@dwPartyImp 的 ctor）
0xDC7278: 0x0062CA80
...
0xDC73B0: 0x00632680   ← ★ 槽 +0x13C
...
0xDC73D0: 0x00A09910
0xDC73D4: 0x00000000   ← vtable 结束
```

★ **COL `0xDF96D8` 的类名 = `.?AVdwRoomImp@@`**（读 `[COL+12]` → TypeDescriptor `0xE6F8C4`）。

⇒ **vtable 起点 = `0xDC7274`**（COL 在 `-4`，标准 MSVC 布局）
⇒ **`0x632680` 槽号 = `0xDC73B0 - 0xDC7274` = `+0x13C`**
⇒ vtable 长度 = `0xDC73D4 - 0xDC7274` = `0x160` = **88 槽**

## §1 槽 `+0x13C` 的所有读取 = 零

字节搜索 `disp32 == 0x13C` 的全部指令（11 处），**没有一处是读取 vtable 槽**：

```
0x540C40  jmp 0x540D81
0xA09D30  add eax, 0x13c        ← 别的类
0xA13CDE  add eax, 0x13c
0xA9B7E3  mov eax, 0x13c
0xB04F14  jmp
0xB05D7F  push 0x13c
0xB1031D  push 0x13c
0xB4792B  push 0x13c
0xB47E0B  jmp
0xBB30CF  jmp
0xC5EB54  push 0x13c
```

★ **没有 `call dword ptr [reg+0x13C]`，也没有 `mov reg, [reg+0x13C]`。**

### 1.1 扫描器的正确性

`call [reg+0x13C]` 的编码是 `FF /2` + ModRM(`mod=10`) + `disp32`。
我的条件 `blob[i]==0xFF && (modrm>>6)==2 && ((modrm>>3)&7)==2 && disp==0x13C` —— 覆盖 `call [eax+0x13C]`(FF 90)、`call [edx+0x13C]`(FF 92) 等**全部**寄存器形式。

**结果为 0 ⇒ 确实没有虚调用。**

## §3 可能的解释

1. **死代码**：该 vtable 槽是历史遗留，实际开局走别的路径。
2. **调用点在未映射区**：客户端 `.text` 有 VMProtect 加密段（143 卷：熵 7.140），如果调用点在那里，静态搜不到。
3. **通过数据驱动的分发表调用**：不是 `call [reg+slot]`，而是把 `0x632680` 存进某个表再 `call`。但那样会有 `0x632680` 的**第二次数据引用** —— 实际只有 2 处（都是 vtable），所以排除。

★ 结合 143/146 卷（`.text` 被 VMProtect 加密、`client_image` 是解包后但导入表未重建）：
**解释 2 最可能** —— 调用点在加密段或未重建区。

## §5.5 ★★★ 更大的发现：`+0x80` 以上 **87 个槽全部没有 `call [reg+disp]`**

### 5.5.1 扫描器修正（本卷第二次踩同族坑）

第一版扫描器只覆盖 **mod=10（disp32）**，漏掉 **mod=01（disp8）**。
修正后统计全 88 槽：

| 区间 | 有虚调用的槽 |
|---|---|
| `+0x000 ~ +0x07C` | **30 个**（如 `+0x050`=566 次、`+0x068`=571 次） |
| **`+0x080 ~ +0x15C`** | **0 个**（含 `+0x084` SendReady、`+0x13C` 0x632680） |

★★★ **`+0x80` 以上（disp ≥ 0x80，只能用 disp32）**的 87 个槽，`call [reg+disp32]` **全部为 0**。**

### 5.5.2 这与 154 卷冲突

154 卷记录：`AS_*` 33 回调 → `vt[33]` = `0x6301A0`（SendReady）。
`33×4 = 0x84` ⇒ **`vt[33]` = `0x6301A0`** —— 就在"无虚调用"区间里。

⇒ **要么调用形式不是 `call [reg+disp]`，要么 154 卷的槽号有误。**

### 5.5.3 可能的调用形式

```
形式 1（两跳，我的扫描覆盖不到"第二跳的基址来源"）:
    mov  eax, [obj]                 ; eax = vtable
    mov  edx, [eax + 0x84]          ; ★ 载入函数指针（mov 统计命中）
    call edx                        ; ★ 间接调用（不是 call [reg+disp]）
形式 2: 函数指针表（`0x632680` 无第二处数据引用 ⇒ 排除）
```

★ `mov reg,[reg+disp]` 统计显示 88 槽**全部**有命中，但那个统计**无法区分"是哪个类"**
（`[reg+0x84]` 这类偏移几乎所有类都有）⇒ **不能作为证据**。

### 5.5.4 结论

★★★ **虚调用的确切形式未能静态确定**，需要**带基址来源的数据流分析**（跟踪 vtable 指针从哪个对象来）。

⇒ **本卷对 `+0x13C` 的"无调用点"结论仍然成立**（`0x13C ≥ 0x80`，只需 disp32，已扫）；
但**不能推广**到"整个 vtable 都没被调用"。

## §6 方法论

1. **★★★★ 定 vtable 起点：找 `vtable[-4]` 是合法 COL（`[COL+12]` → TypeDescriptor，`[TD+8]` 是 `.?A`）。**
2. **★★★★ `call [reg+disp]` 的 disp < 0x80 用 disp8（mod=01），≥ 0x80 用 disp32（mod=10）。扫描器必须同时覆盖。**
3. **★★★ 「有 vtable 引用」≠「被调用」。** 一个槽可以被登记而从不调用。
4. **★★★★ 偏移统计（`mov reg,[reg+disp]`）不能区分类 —— 常见偏移几乎每类都有。必须限定基址来源。**
5. **★★★ 与前几卷结论冲突时，先怀疑"关键前提未验证"。** 213–216 卷整条链都建立在"`0x632680` 会被调用"这个未验证前提上。
