# 153 · 探讨：为什么「入队」这件事骗了我们五卷

> 配套论文：`153_房间动作入队到出网全链关闭_三层队列与clientState闸门.md`

---

## 一、五卷都在同一个坑里

从 148 卷开始，反复出现同一种句式：

> 「发送链静态上止于 `0x62C5A0` 入队 `+0x3A098`，该容器遍历只做『摘链 + 释放 + count--』。」

148、149、150、151、152 五卷都这么写。这个观察**本身没错**——`0x3A098` 的遍历确实什么都不干。错的是**推论**：把「遍历什么都不干」推出「所以链在这里断了」。

真实的因果是：**`+0x3A098` 不是出站队列，它是延迟环。** 谁从它里面「摘链就释放」，那是在**去重合并**：同键消息被后来的覆盖、旧的被释放。真正搬东西的是 `0x632FD1` 那一段——它把 `+0x3A098` 里的节点**提升**到 `+0x3A0D4`。

一句话：**我们一直在数「出货口」，但那是「垃圾回收」。**

### 教训

「遍历只做 A」永远不能推出「这个容器只有 A 用途」。必须找**所有**写 `count` 的点：
- `0x633176 dec [ebx+0x3A098]` ← 我们看到的（去重）
- `0x62C651 / 0x654BF0` ← 我们没细看的（插入）

插入点才是「谁往里放」，**提升点才是「谁从里拿」**。148–152 卷只做了前者。

## 二、`0x3A0D4` 与 `0x3A098`：两个容器只差 0x3C 字节

```
+0x3A098  哈希表（count / cap / buckets）  ← 延迟环
+0x3A0D4  链表（head / tail / count）      ← 主出站队列
```

差 `0x3C = 60` 字节。而且 `0x62C5A0` 与 `0x62C380` 的入队分支**代码形状几乎一样**：

```asm
; 0x62C5A0（→ +0x3A098）
0x62C5BF  add edi, 0x3A098
0x62C5D4  call 0x654CD0          ; 哈希查找

; 0x62C380（→ +0x3A0D4）
0x62C533  lea eax, [edi+edi*2+0xE82F]
0x62C53E  lea eax, [ecx+eax*4]   ; = +0x3A0D4
0x62C547  call 0x656A10          ; 链表插入
```

两个函数的「入队」长得像，但进的是**不同层**。如果我只看 `0x62C5A0` 就断言「房间消息都进 `+0x3A098`」，那 149 卷的「三入队一真发」框架就会永远缺一块。

**这就是为什么必须做 `xref` 全扫，而不是从某个函数往下顺。** 顺着走只能走一条路。

## 三、clientState 闸门的三个数值：3 / 10 / 阈值 0x200

`0x633196..0x633493` 这一段是全卷信息密度最高的地方，因为它同时出现了**三个**和 `[0x76446B0]` 相关的常数：

| 地址 | 比较 | 语义 |
|---|---|---|
| `0x633292` | `cmp esi, 0xA` | `>=10` ⇒ 走「投递分支 A」（`0x675260`，6 dword） |
| `0x63335D` | `cmp esi, 3` | `>=3` ⇒ 走「投递分支 B」（`0x675260`，3 dword） |
| `0x63342A` | `cmp [ebx+0x3A120],0` | 广播开关 |

138 卷说「`[0x76446B0]` = clientState，`<3` 拒绝本地开局」。这里 `<3` 时也**什么都不发**。同一全局、同一阈值、两个完全不同的后果——**这就是为什么两个卷可以都对，而看起来像矛盾**。

### 反思

我一度以为 138 卷和 153 卷在讲同一个闸门。不是。138 卷的闸门在「开局」路径，153 卷的在「房间消息投递」路径。**共享变量 ≠ 共享语义。** 这是本次最值得记住的一条：以后看到「同一个地址」不要合并结论，要**按调用点分栏登记**。

## 四、`0x62ACD0` 六道门：把「静默丢弃」解释清楚了

139 卷留下一个悬案：

> 「Manifold 归属者 ID：0=广播、=账号ID=定向、**其他 ⇒ 静默丢弃**」

为什么是「静默」？因为这个丢弃发生在 `0x62ACD0` 里，而它的**每一个失败分支都是 `je 0x62AE59`（直接 ret）**，中间没有任何日志、没有任何返回值传播。从调用方（`0x6335D7`）看，就像什么都没发生。

六道门：
1. `[room+0x1C] != 0`
2. `[[room+0x1C]+1] != 0`（已连接）
3. srpc 单例存在
4. `srpc->state == 2`
5. `srpc->session != 0`
6. `[room+0x283] == 0`（不在拆房）

再加上「收件人必须在成员表里」（`+0x40`、步进 `0x60`、`+0x18` 计数）。

⇒ **调试建议（若将来实测）**：房间动作不发，第一件事看 `[dwRoomImp+0x283]`、`[room+0x1C]`、`[[room+0x1C]+1]`、`[0x76446B0]` 这四个值。这四个一变，就能定位到六道门里的哪一道。

## 五、`0x8435D0` 这个哨兵桩，第三次出现

137 卷：B9 双命令表 + 哨兵桩（`0x8435D0` = `C3`）。
本卷：`0x7FAA20` 把它 `push 0x8435D0` 当「回调」传下去；`0x62C5A0` 也 `push 0x8435D0`。

同一个 3 字节函数被全镜像几百处 `call`（实测 800+ 调用点）——**它不是「没实现」，它是「统一的空回调占位符」**。这意味着 `0x7FA800` 的「完成回调」参数在很多路径上就是「不需要回调」。

这提醒一件事：**看到一个 `ret` 桩被大量调用，不要判它「死代码」，它是活跃的默认实现。**

## 六、还剩什么

本卷把「主链」关掉了。剩下两块**不是黑箱、是细化**：

1. `0x7E7xxx` 里 6 个直接调 `0x7FAA20` 的函数，`push` 的 type 是 `0x13`(19=P2PInfo)、`0x22`(34)、`0x16`(22) 等。这些是**不同的传输语义**（P2P / 房间频道 / 主信道）。要逐条对上「哪个按钮走哪条」，需要把 `0x7E7000..0x7E8600` 这 0x1600 字节全部按 `push imm` 建表。
2. `0xE56FFE0` 起 64 个通道槽 × `0x50`，每个 `+0x28` 是回调。这是**发送完成后**的分层统计/重传层。

这两块做不做，取决于下一步是「继续静态」还是「转实测」。按用户一贯标准（「还有黑箱，继续逆向直到结束全部黑箱」），两块都该做，但主链已通，可以先交付一轮。

## 七、方法论的自我修正

本卷有两条是**推翻自己**的：

1. **「入队 = 链路终点」是错的。** 入队只是第一层。以后写「止于 X 入队」，必须同时给出「X 的出队点在哪」；给不出，就不要写「止于」。
2. **「唯一真发点」这类断言必须扫 vtable 和 `.rdata` 常量表，不能只扫 E8。** `0x7E8240` 有 3 个 E8 调用点，如果只扫 `0x7E8300` 的调用点（1 个），就会漏掉 `0x633839` 这条 FrameUpdate 批量包路径——而那条路径正是房间状态广播的主力。

第 2 条已经在卷 151 的「方法 6」里埋过伏笔（`0x656A10` 用 `inc [ebx+8]` 自证），本卷把它上升为**强制规则**：

> **断言唯一性前，先数三种引用：E8 rel32、`mov/lea` 的 disp32、`.rdata` 里的 4 字节常量。三种全扫才叫穷举。**
