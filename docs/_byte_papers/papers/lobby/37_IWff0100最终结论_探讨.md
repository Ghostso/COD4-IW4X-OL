## 三、这轮是怎么验证的

### 第一步：找门

`0x4834f0`（AES 解密循环）有两个调用点。
两个点的前面都是：

```
cmp dword ptr [0x1c4b700], 0
jne  <跳过>
```

**一个全局变量当门。**

### 第二步：查谁开门

全镜像搜索 `0x1c4b700` 的写入点：

```
0x483b49  push 0x6044 / push 0 / push 0x1c4b700 / call memset
```

**只有一处。而它在 `0x483b40` 里。**

### 第三步：查谁会进 `0x483b40`

`0x483ed3` 调用它，前置：

```
0x483e94  cmp [ebp-0x10], "IWffu100"
0x483ea4  jne 0x483ee4          ← 不是 IWffu100 就跳过
0x483ed3  call 0x483b40
```

**磁盘上全是 `IWff0100`。**

**⇒ 门永远关着。**

---

## 四、这个论证的强度

它不依赖任何"统计推断"，是**控制流事实**：

1. `0x4834f0` 被调用前必须 `[0x1c4b700] != 0`
2. `[0x1c4b700]` 只在 `0x483b49` 被 memset（清 0）或写入
3. 写入点只有 `0x483b40` 内部
4. `0x483b40` 只在 `IWffu100` 时被调用
5. 磁盘上所有 `.ff` 都是 `IWff0100`

**五步，每步都可以在反汇编里逐条核对。**

**这比任何"熵/统计"都硬。**

---

## 五、还有一个反向证据

`.ifs` 内嵌的 `common_mp.ff` 与磁盘独立的同名文件：

```
.ifs 内：77,817,667 字节，MD5 b6ec57...
磁盘独立：77,605,093 字节，MD5 14f1ee...
差 212,574 字节
```

**同一份内容，两个版本，大小不同。**

**如果 `.ifs` 只是容器，应该完全相同。**

**⇒ `.ifs` 里的不是"打包的 `.ff`"，而是"另一种形态的 `.ff`"。**

**两者都是熵 7.95，说明没有一个是明文。**

## 六、这个结论的价值

**它把"解密在哪"从"某个未知参数"变成了"某个未知层"。**

具体排除了：

- ❌ 不在 `IWff0100` 分支
- ❌ 不在 `0x4834f0`（被门挡住）
- ❌ 不在 `.ifs` 容器层（两份字节不同但都是密文）
- ❌ 不在 `CCoderRWFilter`（已读，是半字节表）
- ❌ 不在 `CZlibRWFilter`（已读，是 zlib）

**剩下三个候选，都还没查：**

- `IFS2.dll` 的扇区读取函数
- TP3 保护层
- 运行时内存（挂载后解密）

## 七、方法论收获（最重要的一条）

> **在调参数之前，先确认这个函数会被调用。**

**一个不会被执行的函数，参数怎么调都是错的。**

这条如果早做，能省掉 `lobby/26`–`lobby/34` 九卷的弯路。

**具体的检查方法：**

1. 找全局/对象的状态位
2. 找它的写入点
3. 找写入点的前置条件
4. 用真实数据验证前置条件是否满足

**四步，反汇编能做完。**
