## 一、229 卷我是怎么错的

229 卷我写：

> 「`0x7F1110` 的入口读 `[0x84ABB08]`/`[0x84ABB14]` = HTTPS/TLS 客户端 ⇒ booking 应答走 HTTPS」

**这两个读是真的**（我今天复核也看到了，在 `0x7F1113` / `0x7F111D`）。

**但结论错了。**

今天我读完了整个函数：

```asm
0x7F1110  push ebp / mov ebp,esp
0x7F1113  mov ecx,[0x84ABB08]      ; 读 HTTPS 会话 ✅ 我看到了
0x7F111D  mov ecx,[0x84ABB14]      ; 读 HTTPS 会话 ✅ 我看到了
0x7F1127  call 0xB9A0F0            ; ← 我没看
0x7F112D  mov ecx,[eax+0x20]       ; ← 取连接 id 高
0x7F1133  mov eax,[eax+0x24]       ; ← 取连接 id 低
0x7F1137  cmp [edx+8], ecx         ; ← ★ 身份比对
0x7F113C  cmp [edx+0xC], eax       ; ← ★ 身份比对
0x7F114C  call eax                 ; ← 虚调用槽 0x38
0x7F1159  call eax                 ; ← 虚调用槽 0x08
0x7F115C  ret 0x14                 ; ← ★★★ 短函数，就这些
```

**它是一个「HTTPS 连接身份匹配后发两个通知」的回调。`ret 0x14`，总共 20 条指令。**

**不是 booking 分派器。**

## 二、错误的性质

我不是"看漏了"，是**看到感兴趣的东西就停了**。

| 我看到 | 我推断 |
|---|---|
| 读了 `[0x84ABB08]`（HTTPS 会话） | 「这是 HTTPS 客户端相关」 ✅ |
| 读了 `[0x84ABB14]` | 「肯定是处理 HTTPS 应答」 ❌ **跳步** |

**"读了 HTTPS 会话" 只能推出 "它与 HTTPS 有关"，推不出 "它处理 booking 应答"。**

★ **必须读到函数体内的 `cmp` 和 `call`，才知道它在做什么。** 我今天读了，才看到那两条 `cmp [edx+8]/[edx+0xC]` 是**连接 id 比对**，两个 `call eax` 是**通知**。

## 六、我也纠正了子代理一处

子代理 244 卷说：

> 「门 6 `strcmp(参3, "mmbook accepted")` 的参3 是 `0x7F3440` 填的动态应答串」

**我独立反汇编后发现**：

```asm
0x7F3440  mov ecx, 0xDE0A0C        ; = "HostUser"
0x7F3447  mov dl, [eax] / cmp dl,[ecx] / jne ...
```

**`0x7F3440` 是拿应答文本跟 `"HostUser"` 比对的 strcmp 封装**，不是解析器。

而 `0x7F1562..0x7F156F` 的压栈顺序显示：**应答文本在栈缓冲 `[esp+0xB0]`（`ebx`）作为参4**，参3 是 `edi`。

★★ **所以子代理把一个 strcmp 当成了应答解析器，还把参4 说成参3。**

★★★ **但它的机制性结论（客户端拿应答文本比常量，不回精确值就失败）是对的** —— 只是**比对常量是 `"HostUser"`，`"mmbook accepted"` 的比对在 `0x632680` 门 6 里，是两个不同的门。**

## 七、本轮最终账（232–246 共 15 卷）

### 已稳的结论

- service id 双来源（`0xB78C10` / `0xBA72C0`），19 svc / 86+ task 全表
- 97 通道 × 128 发送函数服务面索引
- 回调签名 `cb(reply, status)`，`status` 来自 `reply+4` 或常量 0
- 231 卷「空 ACK ⇒ state=2」前提已验证
- **位流 41 位（`+0x21==0`）/ 51 位（flag≠0）**，读写两侧对称
- 44 张 vtable + 线上类型号 ≠ 序号
- ChangeTeam 四字段 + 客户端从不主动发
- `0x7F1110` 不是 booking 入口（是 HTTPS 身份通知回调）

### 仍未闭合（且静态已尽）

- **腾讯 HTTPS 实际回什么** —— 对端 `formal-zone-auth.codol.qq.com`，本地不可得
- **真实 `6/5` 位流样本** —— 33 个 run 全空 TLV
- **41 位 vs 175 卷 7 字节** —— 冲突未决，无样本

### 服务端修复的唯一可靠方向

**在拿到"腾讯 HTTPS 应答"或"真实 `6/5` 样本"之前，任何对 `lobby_server.py` 的修改都是盲改。**

这不是"需运行时"的托词 —— 是**静态已经把能确定的都确定了**：
- 客户端要 41 位（不是 50/51）
- booking 走腾讯 HTTPS（不是本地 3074）
- 门 6 期望 `"mmbook accepted"`，本地代码不产生它

**剩下的缺口在"对端"和"样本"，不在这份二进制里。**
