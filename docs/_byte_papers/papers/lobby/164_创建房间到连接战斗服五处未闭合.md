```
① 11/13 createRoom      → 大厅回 roomId / memberCount / maxPlayers / secondId
② 21/5 findSessions     → 大厅回 session 记录（含 HostAddress 127.0.0.1:28960 + 16B securityKey）

⑦ 战斗服派生 transport_key → 帧加密/HMAC
```

## 二、五处未闭合（逐条给证据）

### ❌ 未闭合 1：`roomId` 两处表示不一致

| 位置 | 值 | 形式 |
|---|---|---|
| `11/13 createRoom`（`lobby_server.py:774`） | `ROOM_ID = SESSION_ID = 0x1122334455667788` | **u64 二进制** |
| `21/5 session record`（`codol_crypto.py:366`） | `(session_id & 0x7FFFFFFF) \| 1 = 0x56667789` = `"1449428873"` | **十进制字符串** |

```python
# codol_crypto.py:366
room_id = (int(session_id) & 0x7FFFFFFF) | 1        # 强制非零
ob.string(str(room_id))                             # ① 十进制串
```

**⇒ 同一个房间，客户端从两条路径拿到两个不同的 roomId。**

**影响**：`11/13` 返回的 `roomId` 被客户端用作**本地房间标识**；`21/5` 的 `roomId` 用于**匹配/踢人判断**（源码注释：「否则 `_strtoui64(room.id) == last_kick_room_id` → 每次加入都被判被踢」）。

**⇒ 两者不等，最坏情况是「进房后立刻被判被踢」。**

**未闭合点**：客户端是否要求两者一致？**没有验证过。**

# lobby_server.py:774

**房主自己创建的房间里，人数是 0。**

**⇒ 这是一条「从房间创建就开始错」的源头，且从未验证。**

### ❌ 未闭合 3：`21/5` 的 `securityKey` 与战斗服硬编码不一致（163 卷遗留，**本卷收窄了它的边界**）

```python
# lobby_server.py:486
return [cc.build_session_record(SESSION_ID, GAME_IP, GAME_PORT, ...,
                                security_key=SEC_KEY)]     # SEC_KEY = b"\x00"*16
```
```python
# codol_crypto.py:381
ob.blob((security_key or b"")[:16].ljust(16, b"\x00"))    # 第 6 个尾字段 = 全 0
```

**⇒ 大厅通过 `21/5` 下发给客户端的是 `00 00 ... 00`。**

而战斗服：`battle.c:43` `memset(b->security_key, 0x01, 16)` ⇒ **`01 01 ... 01`**。

#### 本卷新查的两条（重要）

**(a) 客户端的 ECDH 输入是硬编码曲线参数，不是会话里那 16B**

`0xBA1E7A call 0xBA0750` → `0xBA0754 jmp 0xBA05A0`，而 `0xBA05A0` 开头就是：

```asm
0xBA05CC  mov dword [ebp-0x1C], 0x90F542AD   ┐
0xBA05D3  mov dword [ebp-0x18], 0xE621A488   │ 24 字节
0xBA05DA  mov dword [ebp-0x14], 0x0289C93B   │ 曲线/基点参数
0xBA05E1  mov dword [ebp-0x10], 0xDC02FF39   │ （硬编码）
0xBA05E8  mov dword [ebp-0x0C], 0xFF770411   │
0xBA05EF  mov dword [ebp-0x08], 0x0D6288EE   ┘
0xBA05F6  mov dword [ebp-0x7C], 8            ┐
0xBA05FD  mov dword [ebp-0x78], 0x12         │ 6 个索引
0xBA0604  mov dword [ebp-0x74], 9            │
0xBA060B  mov dword [ebp-0x70], 0x0E         │
0xBA0612  mov dword [ebp-0x6C], 5            │
0xBA0619  mov dword [ebp-0x68], 0x14         ┘
```

**⇒ 这条路径完全不读会话里的 16B securityKey。**

**(b) 但会话记录里确实有那个 16B 字段，且大厅在填**

`build_session_record` 的第 6 个尾字段明确是 `security_key[:16]`。

**⇒ 现在有两个候选解释，本卷无法二选一：**

| 解释 | 含义 |
|---|---|
| **H1**：那 16B 是给别处用的（如房间内 P2P），与战斗服 ECDH 无关 | 战斗服的 `0x01` 仍需与客户端 ECDH 结果对齐 |
| **H2**：客户端另有一条 KDF 路径用那 16B | 大厅必须发对值 |

**⚠ 无法静态定案的硬原因（本卷实测）**：
- 会话记录里的 `0xD692ADAB`（query criterion）在镜像中 **0 命中**
- 会话记录里的 `0x0C0DE001`（room id 标记）在镜像中 **0 命中**

**⇒ 258 字节会话记录没有常量锚点 ⇒ 客户端是按位流/变长解码的 ⇒ 无法用魔数定位它的解码器。**

**这条未闭合点的准确表述**：
> **「会话里的 16B securityKey 客户端到底用不用」——静态上暂时定不了，因为会话记录的解码器无常量锚点可定位。**

（这不是「没查」，是「查了，确认没有可用锚点」。下一步只能靠动态观察或按位流结构硬解。）

## 三、这五处的因果关系（重要）

```
未闭合 2（memberCount=0）
      ↓ 房间状态从创建就异常
未闭合 1（roomId 两个表示）
      ↓ 进房判断可能误判
未闭合 4（ready 判据错）
      ↓ 点准备，服务端识别不到
      ↓ 不推 game start
未闭合 5（game start 载荷是抓包常量）
      ↓ 即使推了，内容也不对
未闭合 3（security_key 不一致）
      ↓ 就算客户端连上 28960，HMAC 也过不去
      ↓ 战斗服 0 收包
```

**⇒ 这是一条「五道闸门串联」的链：任何一道关着，都到不了战斗服。**
**而目前五道全是关着的。**

## 六、方法论

1. **★★ 分段查清 ≠ 整链清楚。** 五个环节各自「清楚」，串起来才发现**五道闸门全关**。
2. **★ 把「未闭合」按数据流排序，才能看出哪一环是源头。** 本段源头其实是 `memberCount=0`（最早出错的那一环）。
3. **★ 源码自承「未验证」的常量要当红线。** `GAME_START_PAYLOAD` 的注释写了「不是已验证」，但代码仍在用。
4. **★ 客户端拿到的值和服务端用的值要成对核。** `securityKey` 是「大厅发 0x00 / 战斗服用 0x01」，`roomId` 是「u64 vs 十进制串」—— 两处都是成对才看得出的错。
