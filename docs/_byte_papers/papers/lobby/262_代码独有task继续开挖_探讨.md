# 262 · 探讨：命令名挂在哪一层

> 配套：`262_代码独有task继续开挖_svc9Friends_svc80商城_svc191mgroup.md`

---

## 一、这一卷最省力的三个发现，都来自"字符串挂在哪"

svc 9、svc 191 的服务身份，**一次都没靠"猜协议语义"**，而是靠一句话：

```
bdFriends::proposeFriendship
mgroup.bigSpeaker
```

它们出现在**宿主调用者**的字符串常量里。

回看这条链的层级：

```
task 号(push 立即数)
  └─ 建造器 0xB92xxx        ← 零字符串，全是类型化写入（260 已证）
       └─ 宿主 0x7FFxxx     ← 薄壳，三段式骨架
            └─ 宿主调用者    ← ★命令名在这里：bdFriends::* / mgroup.*
```

**建造器回答"怎么发"；宿主回答"发不发送"；宿主调用者回答"这是什么动作"。**

260 把这条叫"逐层外溯"，本卷**第三次**验证它。它的价值在于：
**命名不需要理解二进制格式**，只需要把外溯走到挂着业务字符串的那一层。

## 二、反面：为什么不能靠建造器的字节去"猜"语义

如果只看建造器，svc9/task1 是：

```asm
push 0x80000 / push 0x400 / push 1 / push 9 ; call 0xBA72C0
call 0xBA7250   ; 写带标签 dword
call 0xBA75D0   ; 写字符串
call 0xBA71C0   ; 写对象
```

"一个 dword + 一个字符串 + 一个对象" —— 这可以套成**任何**"带一个 id + 一个名字 + 一个对象"的请求。
**从字节反推语义，等于从"主语+谓语+宾语"反推"这句话是什么场合说的"。** 信息不够。

而 `bdFriends::proposeFriendship` **直接就是命令名** —— 因为它是开发者**为了让代码可读**写下的。

**结论：能被命名的东西，开发者通常已经命名过了；反汇编的任务是找到那个名字，不是重新发明它。**

## 三、另一条：`0xB78C10` 假桶 —— 一个方法边界，不是一个数据结论

本卷的 `a40_codemap.py` 第一次跑出：

```
svc 0  ( 7 tasks): [6, 8, 11, 12, 58, 71, 102]
```

`svc 0` 是**假的**。它来自 `0xB78C10`，而后者的调用约定不同（232 卷：
`push task; lea buf; push svc; push buf; call`），我的"取最后两个 push"恢复法在这里失效。

**危险不在于出错，而在于它在我的地图里显得很合理** —— 7 个 task 排成一列，
和别的 svc 桶长得一样。**如果不核 232 的表，这 7 个会以 `svc 0` 的身份进论文。**

这与 260 的"None 桶"是**同一类陷阱**：
> **恢复器（recover）产生一个"看起来像结果的假桶"时，它不会报错，只会污染下游。**

**教训：一个解析器/恢复器，必须对"它的输入约定"显式建模。**
`0xBA72C0` 的恢复器不该被拿去跑 `0xB78C10` —— 本卷是**因为 232 的表在旁边**才发现，
**如果没有那张表，`svc 0` 会成为一个新卷的"新发现"。**
