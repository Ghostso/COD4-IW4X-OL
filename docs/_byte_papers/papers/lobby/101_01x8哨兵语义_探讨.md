# `01×8` 哨兵语义 · 探讨：一个常量，三种用法，才叫证据

> 对应：`lobby/101_01x8哨兵语义.md`

---

## 一、为什么"三处"比"一处"强这么多

**`lobby/98` 时我知道 `0xc7341d0 = 01×8`，被 memcpy 一次。**

**那时它只是"一个被拷进去的字节串"。**

**`lobby/101` 找到第三处：`0x7f5ab0` 用 `memcmp` 拿它与对象 ID 比较。**

**⇒ 一个值如果**只被写入**，它可能是任意数据。
⇒ 一个值如果**被写入又被比较**，它就是**语义标记**。**

---

## 二、具体到这三处

| 位置 | 动作 | 说明 |
|---|---|---|
| `0xb74060` | `mov ecx,0x01010101` ×2 | **写默认值** |
| `0xc7341d0` | 被 memcpy | **初始化的来源** |
| `0x7f5ab0` | `memcmp(id, 0xc7341d0, 8)` | **判定"是不是默认/未设置"** |

**⇒ 三处连起来读：**

**"这个对象第一次创建时填 `01×8`；
查询时若发现它还是 `01×8`，说明**还没被赋过真实 ID**。"**

**⇒ 这就是哨兵（sentinel）的完整定义。**

---

## 三、`0x7f5ab0` 的分支方向：我读了两遍，第一遍是**反的**

**第一眼：**

```
0x7f5ac3  test al, al
0x7f5ac5  jne 0x7f5b45
```

**⇒ 我写下了："`jne` = 不相等就跳走 ⇒ 相等时继续 ⇒
相等（是哨兵）时去遍历表"。**

**那是错的。**

---

## 3.1 为什么错

**我以为 `0xb74090` 是 `memcmp`（三值：负/0/正）。**

**实际它是 `bytes_equal -> bool`：**

```
0xb74106  xor eax,eax        ; 全等路径
0xb7410d  sete al            ; → al = 1     ★ 相等返回 1

0xb740f3  sar eax,0x1f
0xb740f6  or  eax,1          ; → eax = -1
0xb740fe  sete al            ; → al = 0     ★ 不等返回 0
```

**⇒ `al = 1` 表示**相等**（与 memcmp 的 `al=0` 恰好相反）。**

**⇒ 所以 `jne 0x7f5b45`（al==1 就跳）的含义是：**

**"**相等时**跳去空返回"。**

**⇒ 最终语义：**

```c
if (id == 01×8)  return;      // 未设置 → 什么都不做
else             /* 遍历全局表查找 */
```

**⇒ 与我第一遍写的**完全相反**，而且方向不同（不是"相等时干活"，
而是"相等时**不**干活"）。**

---

## 3.2 这里的教训比结论更值钱

**`test al,al / jne` 这种组合，单看一处永远读不准。**
**必须回头去读**被调函数**的返回值极性。**

**⇒ 我当时的做法是：打开 `0xb74090`，一路读到两个 `ret`，
看到两处 `sete al` 才定下来。**

**⇒ 如果只读 `0x7f5ab0`，我会把整个语义写成反的，
而且"反的版本"读起来同样通顺——这是最危险的一类错误。**

**⇒ 它不会报错，只会让后面所有引用它的结论都朝反方向长。**

## 四、这一卷真正的收获：P2PInfo 的两段 blob 是**连续**的

**`0x0C + 0x43 = 0x4F`。**

**这个算式一旦立起来，"两个 blob"就变成"一块 75 字节被截成两段发"。**

**⇒ 为什么要截？**

**因为语义不同：**
- 前 67 字节 = **对等玩家子表**（变长逻辑在那儿）
- 后 8 字节 = **本 peer 的 ID 槽**（定长 8）

**⇒ 序列化时分成两个 `0x13` blob，各带自己的长度头。**

**★ 这个"截成两段"的写法，在 `StartGame` 里也有（3 段 blob）。
⇒ 说明这是这套协议处理"一块混合数据"的通用手法。**

---

## 五、我这一卷**没有**做的两件事

**① 没有断言"`01×8` 在线上一定表示未设置"。**

**因为它也可能是"**另一个**哨兵值"，比如"本机/回环"。
代码只说"它被比较"，没说"比较失败意味着什么"。**

**⇒ 需要读 `0x7f5b45` 才知道另一半。
⇒ 本卷老实标了"未读"。**

**② 没有把"`+0x11` 那 67 字节的内部布局"补出来。**

**因为 `lobby/100` §6 已经标了"打包器内层来源对象未定"。
⇒ 上游未定，下游我不硬算。**
