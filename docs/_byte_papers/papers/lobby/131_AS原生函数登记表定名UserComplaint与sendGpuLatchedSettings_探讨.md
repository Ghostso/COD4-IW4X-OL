## 一、我上一轮记下的那个函数，根本不存在

上一轮我在会话末尾写：

```
0x5D39B6  call 0x63fc60     ← D entry, inside UIException logger
0x5D39D2  ret 4
```

并且推论"这是 UIException 日志器，函数起点在 `0x5D3940`"。

本卷打开镜像，从 `0x5D3790` 起反汇编，看到的是：

```
0x5D3790  55            push ebp
0x5D3791  8bec          mov ebp,esp
0x5D3793  83e4f8        and esp,-8
0x5D3796  81ecec070000  sub esp,0x7ec      ← 2028 字节帧
```

`0x5D3940` 不在函数头,而在**函数中部**。

### 1.1 为什么从中间读也能读通？

因为 **x86 是变长指令**。从任意字节开始，都有很大概率解出一串"像样"的指令。我上一轮从 `0x5D3915` 起读，解出来的是：

```
0x5D3915  mov ecx,[eax+0x10]
0x5D3918  mov [esp+0x1c],ecx
0x5D391C  call 0x5ee820
...
0x5D39D2  ret 4
```

**读起来完全合理** —— 有取字段、有存栈、有调用、有 `ret 4`。但它不是我所以为的那个函数的一部分，而且**它是一个更长的函数的后半段**。

### 1.2 判据：找 `int3` 填充

唯一可靠的边界判据，是编译器的对齐填充：

```
VA 0x5D378D  cc cc cc      ← 3 字节
VA 0x5D3790  push ebp      ← 真入口
```

★★ **⇒ 反汇编窗口的起点必须用 `int3` 串 / 前一条 `ret` 来锚定，不能用"我看着像函数头"。**

★ 这条和 130 卷 §一 的教训是**同一族**（"跳转表给入口集合，不给区间"），但方向相反：130 卷是"我按表的顺序猜体的边界"；本卷是"我按指令流的顺滑度猜函数的边界"。**两次都是拿"看起来对"当判据。**

**正确的判据永远是结构性的：`int3` 填充、`ret` 后的对齐、cookie 写入位置。**

## 二、"事件名"和"类名"是两条独立的命，缺一条就闭不上

上一轮我拿到事件名就以为够了。本卷拿到的是：

| 来源 | 值 | 位置 |
|---|---|---|
| 格式串字面量 | `UserComplaint` | `.rdata` `0xDC2458` |
| RTTI mangled 名 | `. ?AVAS_TencentReportBadLanguage@@` | `.data` typeinfo 内嵌 |

**两者都不在代码里。** 代码里只有 `push 0xdc2458` 和一次 `call 0x63fc60`。

★★ **⇒ 光有事件名，我知道"上报什么"，不知道"谁触发"；光有类名，我知道"哪个 UI 动作"，不知道"上报什么"。**

这是本卷最实在的一条：**遥测事件的完整身份 = 事件名 + 触发者**，而这两样**分别存在两个完全不同的数据区**（`.rdata` 字面量池 / `.data` RTTI 描述符）。任何"只挖一边"的做法都会停在半闭合。

★ 这与 123 卷「TaskEvent 词表」的做法一致，但 123 卷是**从语料侧**拿事件名；本卷是**从客户端侧**拿事件名，并且**第一次**拿到了"类名"这一路。同一事件在两个独立面被独立确认，这是最高强度的证据。

## 三、`callsite_finder` 报 0，我上一轮判"工具坏了" —— 判错了

上一轮结尾：

```
callsite_finder 0x1D3940 → call rel32 ???: []
file 0x-22C6C0
```

我当时把它记成"工具没解析输入"。本卷用 `ptrref_scan --calls` 复核，得到的是：

```
target 0x5D39E0 : 0 处 -> NONE
target 0x5D3790 : 0 处 -> NONE
```

两个不同的扫描器、两种不同的输入形式（file 偏移 / VA），**都是 0**。

### 3.1 真正的原因

这两个函数是 **AS_* 类的成员/虚拟方法**。它们只能经"对象 → 函数指针"间接调用：

- 若 12 字节行是虚表 ⇒ `call [vtable+4]`，**没有 `E8 rel32` 指向函数体**；
- 若是描述符行 ⇒ 运行时取指针后 `call eax`，**同样没有 `E8 rel32`**。

★★ **⇒ 对这类目标，"0 个 rel32 调用点"是**正确且必然**的结果，不是工具故障。**

### 3.2 我差点为此改工具

上一轮我甚至写下"`callsite_finder.py` 对 `0x1D3940` 未解决"，把它列为待办。**如果我当时去"修工具"，会花掉一轮，而且修不好 —— 因为没坏。**

★★ **⇒ 排查"扫描结果为 0"的正确顺序，必须是：**

1. **先问"这个目标本来该不该有 call 边"**（它是不是虚函数 / 表内函数 / 回调）；
2. 再看它有没有被 `[表]` 引用（`ptrref_scan` 的"疑似表项"分支）；
3. 最后才怀疑扫描逻辑本身。

130 卷 §八 3c 条我写的是"扫描结果为 0 时先怀疑扫描本身"。**这条要加一个前提，否则会把正确结果当成 bug。**

### 3.3 一个补充判据

`ptrref_scan` 的"疑似 `[count][ptr]` 表项"分支，本卷对 `0x5D3900` 报了 `0x2124CC3` —— 那次是**错误输入**（把 file 偏移当 VA 用）导致的越界命中，不可信。

★ **VA 和 file 偏移必须严格区分**：`ptrref_scan` 吃 **VA**；`callsite_finder`/`dis_640fd0` 吃 **file 偏移**。本卷至少有两次把两者搞混（一次让它算出 `file 0x-22C6C0`，一次让它在 `.rdata` 里找到"表项"）。**工具签名不统一，是这个项目反复踩的坑**，应当统一成"一律 VA，内部减 0x400000"。

## 四、`0xE6C72C` 读出乱码 —— 这次"乱码"是结构头，不是空串

上一轮 `0xDAE091` 的教训是：`cstr` 读出 `b''` 可能是合法空串。本卷遇到的是它的**近亲**：

```
cstr(0xE6C72C)  →  b'\x18x\xd7'
```

我第一反应又是"地址错位 / 假阳性"。**又错了。**

字节事实：

```
0xE6C72C:  18 78 D7 00 | 00 00 00 00 | ".?AVAS_TencentReportBadLanguage@@\0"
```

- 前 4 字节 = dword `0x00D77818`（**另一个指针**）；
- `0x00` 是那个指针的**高位零**，不是字符串终止符；
- 名字从 **+0x08** 开始。

### 4.1 判据：读出的 3 字节 == 该 dword 自身的低 3 字节

★★ **⇒ 若"字符串"的前几字节正好构成一个**看起来像地址**的值，就说明这里是结构体头，不是 C 串起点。**

`18 78 D7` 作为 24 位值 = `0xD77818`，正好落在镜像里（`0x400000` 起）⇒ 它是指针，不是文本。

### 4.2 与 130 卷的区别（不能合并）

| 卷 | 现象 | 真因 | 判据 |
|---|---|---|---|
| 130 `0xDAE091` | `b''` | **合法空串** | 调用方把它当"无字符串"占位 |
| 131 `0xE6C72C` | `b'\x18x\xd7'` | **结构体头 + 高位零截断** | 前 3 字节 = 一个镜像内有效地址 |

★★ **两者共同点：`cstr` 的结果不可直接当语义。不同点：一个要问"谁在用它"，一个只要"把前 4 字节当 dword 看一眼"。**

★ 我现在把这条上升为一条通用规则：

> **`cstr` 的返回值在 3 类情况下都不可信：①空串；②跨指针高位零被截；③落在二进制里。**
> **区分方法：先按 dword 读一遍（看是否像地址），再按字节串全库对账，最后才看调用方。**

## 五、我给 130 卷做了实质性更正 —— 这次不是"加固"，是"推翻"

130 卷 §0 第 3 条写的是：

> UI 遥测派发器 `0x1D39E0` 四分支：0=UIClick / 1=UIPage / 2=UIKeySetting / 3=通用采样

本卷证明：

```
.?AVAS_SetRecommendedSetting@@   0x00DC897C   0x005D39E0
```

**`0x5D39E0` 是 Flash 侧「应用推荐设置」的原生回调，不是"UI 遥测派发器"。**

### 5.1 四分支的归属仍然正确

130 卷那四条归属（UIClick/UIPage/UIKeySetting/通用）**字节级全对**，本卷复核一致：

```
0x5D3A0C  mov ecx,[eax+0x10] ; 0x5D3A0F cmp ecx,3
0x5D3A18  jmp dword ptr [ecx*4+0x5d3c6c]
0x5D3AB1/0x5D3AC4 → 0x641180 (UIClick)
0x5D3B07          → 0x6411E0 (UIPage)
0x5D3B34          → 0x641340 (UIKeySetting)
0x5D3C38          → 0x477910 (通用)
```

**⇒ 错的是函数名，不是分支内容。** 这是"局部证据对、整体定性错"的典型。

### 5.2 错在哪一步

130 卷的推理链是：

> switch 的每个 case 都调不同的遥测日志器 ⇒ 这个函数是遥测派发器。

★★ **⇒ 这是从"下游副作用"反推"上游身份"。** 一个"设置推荐值"的 UI 回调，在执行时会顺带打三条日志，**并不因此变成日志派发器**。

**正确做法：函数身份必须由**命名证据**（RTTI / 导出表 / 字符串注册）给出，日志调用只是它的**行为**。**

★ 这和 124 卷 `CreateRoom` 是 TLog 打点不是真建房，**是同一类错误**：把"打了什么日志"当成"做了什么动作"。**这是我在这个项目里犯的第二次。**

### 5.3 这条要写进方法论

> **凡是要给函数起名，先找命名证据；找不到命名证据时，只能写"某函数，行为是 X"，不写"X 函数"。**

130 卷当时如果写的是"`0x1D39E0` 是一个 switch，三个分支分别打 UIClick/UIPage/UIKeySetting"，就不会错。它错在**多加了一个名字**。

## 六、`UiCppXxx`：130 卷"页名不存在"，本卷给出另一半

130 卷花了一节论证"协议面内不存在页号→页名映射"。那结论**仍然成立**。

本卷发现客户端里有 33 个 `UiCpp*` 屏幕类名：

```
UiCppMainMenu / UiCppOnboarding / UiCppMatchSelectView / UiCppChallengesView
UiCppItemListView / UiCppSuggestedLoadoutView / UiCppNewItems / UiCppNewModes / ...
```

★★ **⇒ 130 卷的"不存在"要限定为"在协议面不存在"。** 二进制面**有**屏幕命名，只是它的形态是"每类一个 `Init`，在 `Init` 里现场注册 SF 回调"，而不是"一张 `{id,name}` 表"。

### 6.1 这条为什么重要

`page_table_hunt.py` 的判据是 `[u32 id][u32 ptr→ASCII]` 连续 ≥8 项。**在这个判据下，"每类一个 Init"的形态永远扫不到** —— 因为它根本没有"表"。

★★ **⇒ 穷举的判据决定了"不存在"能推多远。** 130 卷写"在 X 判据 + Y 面内不存在"是对的；本卷把 Y 面从"协议面"精确到"协议面（不含二进制结构）"。

★ 这条与 130 卷 §八 第 2 条完全一致，本卷只是**执行它**：结论要挂在判据和面上。

### 6.2 一个防止自我欺骗的细节

`UiCpp0codo / 8codo / 9codo / Acodo / Ccodo / Dcodo / Ecodo / Gcodo` —— 这些是**带产品名（codo）的混淆类名**。

★★ **⇒ 不能数成"8 个不同的屏幕"。** 命名里带产品名，说明它们是**同一模板的实例化**（或混淆器插入的重复）。这条我写进论文的诚实边界里，**没有把它们算进"33 个屏幕"**。

★ 这正是 126/124 卷"假阳性防火墙"的同族：**先看命名规律，再决定它是不是一个独立实体。**

## 七、`AS_UILog` 是 `c2 04 00` —— 三字节的"不存在"

本卷在同一张表里看到 `0x8435E0` 出现 3 次：

```
handler 0x008435E0:  c2 04 00     ret 4
```

它对应 `AS_UILog`、`AS_QuickMatch`、`AS_setdvar` 三个名字。

★★ **⇒ 三个接口在本 build 都是空实现。**

这一条的价值在于：**"接口存在" ≠ "功能存在"。** 名字在 RTTI 里、地址在表里，**函数体三个字节**。

★ 判据：**遇到 `c2 04 00`（或 `c3`）这种"恰好一条 `ret`"的函数体，先怀疑它是被禁用的占位**，不要试图解它的"行为"。

★ 这与我上一轮的另一个错误对照：上一轮我怀疑 `0x477910` 是"第五入口"，因为它被遥测函数调用。**本卷的 `AS_UILog` 说明：名字像遥测入口、被登记、被引用，仍可能什么都不做。**

## 八、`sendGpuLatchedSettings`：一条命令，不是一个事件

`AS_IIPS_Response` 的函数体里：

```
0x5D3D18  push 0xdbcf88   ; "Cbuf_AddText: overflow\ntext: %s\nlength: %d\ncmd_text->cmdsize: %d\ncmd_text->maxsize: %d\n"
0x5D3D13  push 0xdc24cc   ; "sendGpuLatchedSettings\n"
```

★★ **⇒ `Cbuf_AddText` 是引擎的控制台命令缓冲入口，格式串是它自己的溢出报错。**

这件事如果按"字符串像什么"来归，会归到"遥测事件"里（因为它在 UI 事件处理函数里，名字是动词短语）。**但它是控制台命令。**

★ 判据：**看它往哪写** —— 写进 `[0x76595ac]/[0x76595a8]`（cmdsize/maxsize）就是命令缓冲；写进遥测四入口之一才是事件。

★ 诚实边界：我没找到 `sendGpuLatchedSettings` 的**命令处理器注册项**。`ptrref_scan` 只命中 `0x9C740B` 一处，反汇编确认是 x87 浮点里的**偶然字节重合**（`d9 45 38` 之类）。

★★ **⇒ 这里我又差点犯错**：如果我不去看 `0x9C740B`，就会写"命令名有指针引用 ⇒ 命令存在"。**假阳性防火墙要求：每一个命中都要落到具体指令上看一眼。**

## 九、方法论（本卷新增/修订）

1. **反汇编窗口起点必须结构性锚定**：`int3` 串、前一条 `ret`、cookie 写入位置。**"指令流读起来顺"不是判据。**
2. **事件身份 = 事件名 + 触发者，二者分居 `.rdata` 与 `.data`。** 只挖一边只能半闭合。
3. **「扫描结果为 0」的排查顺序**：先问目标该不该有 call 边（虚函数/表内/回调），再查表引用，最后才查扫描逻辑。**130 卷 §八 3c 条必须加这个前提。**
4. **VA / file 偏移必须在工具层统一**。本卷因两者混用产生了两次假命中。
5. **`cstr` 结果不可信有三种形态**：空串 / 跨指针高位零被截 / 落在二进制里。**先按 dword 读一遍看是否像地址。**
6. **函数起名必须有命名证据（RTTI/导出/注册）。** 没有命名证据时只能写"行为是 X"，不能写"这就是 X 函数"。这是本卷对 130 卷的实质性更正。
7. **"接口存在" ≠ "功能存在"**：`c2 04 00` 三字节函数体 = 禁用占位。名字、登记、被引用，都不能证明有功能。
8. **穷举判据决定"不存在"的推多远**：130 卷"页名不存在"只在 `{id,name}` 表 + 协议面内成立；本卷用 `UiCppXxx::Init` 形态给出了二进制面的另一半。
9. **每一个指针命中都要落到具体指令上确认**（`0x9C740B` 是 x87 浮点里的偶然重合）。

## 十、这一卷我最大的收获

**四次"我以为"，四次都错在起点：**

| # | 我以为 | 实际 | 错因 |
|---|---|---|---|
| 1 | `0x5D3940` 是函数头 | 函数从 `0x5D3790` 起 | 按"读得通"判边界 |
| 2 | `0xE6C72C` 是错位/假阳性 | 是结构体头，名字在 +8 | 按"前 3 字节乱码"判错位 |
| 3 | `callsite_finder` 坏了 | 0 是正确结果 | 按"应该有调用点"判工具故障 |
| 4 | `0x5D39E0` 是遥测派发器 | 是 `AS_SetRecommendedSetting` | 按"下游行为"判上游身份 |

★★ **共同点：我把"看起来应该如此"当成了判据。** 每一次推理本身都没错 —— 错的是**推理的起点**。

★ 这与 124 卷"长度对齐是最便宜的证伪"、126 卷"假阳性防火墙"、130 卷"穷举后没有 ≠ 没找到"是**同一条主线**：**在这个项目里，任何一次"我觉得"的出现，都意味着我还缺一个机械判据。**

★ 而这一卷的正面收获，恰好全部来自**机械判据**：`int3` 定位函数头、dword 判断地址、`c2 04 00` 判断空实现、RTTI 名判断类身份、`Cbuf_AddText` 格式串判断写入目标。**没有一条是靠"看起来像"。**
