# 350 · 探讨：怎样才算"证否了一条嫌疑"

> 对应：`lobby/350_ACE不影响房间_26条记录2114分母.md`

---

## 一、这个任务最容易做的两个错

### 错法 A：数一数 hook 记录，发现 ACE 少，就说「ACE 无关」

这很诱人：2114 条记录里 ACE 只占 26 条（1.23%），看起来一眼就能下结论。

问题是**分母本身是残缺的**。这次挂的钩子是：

```
OpenFileMappingW, CreateFileMappingW, MapViewOfFile,
connect, sendto, WinHttpConnect, WinHttpOpenRequest, WinHttpSendRequest
```

`WSASend` / `WSARecv` / `WSASendTo` / `WSARecvFrom` / `ConnectEx` / `AcceptEx` **一个都没挂**。
而现代 Windows 客户端走 IOCP 时几乎必然用 `WSASend`。所以「ACE 没调用网络」这句话，
**只能覆盖它碰巧用到的那 8 个 API**。

更有意思的是现场自带的证据：`chain.txt:130` 明明写着
`[net] 游戏 TCP 连接 = … ; 127.0.0.2:3074 [ESTABLISHED]`，
可是 19 条 `connect` 记录里**没有一条**是发往 `127.0.0.2:3074` 的。
⇒ **游戏到大服务器的那条 socket，hook 根本没看见它建立。**
既然连"正常连接"都漏了，"ACE 的异常连接"当然也可能漏。

所以"数记录"这条路，**证明力上限很低**。

### 错法 B：看 ACE 很吓人，就顺着说「很可能是 ACE 拦的」

`HANDOFF_ACE_REVERSE.md` 里 ACE 的形象相当凶：5 个内核驱动、`KeBugCheckEx` 自毁、
`ACE-SSC-DRV64.sys` **导入 fwpkclnt（WFP 网络过滤）**、`MmMapIoSpace`、NMI 回调……
读完确实会想"这玩意儿要拦点什么太容易了"。

但这正是**"能力"不等于"行为"**。有 WFP 过滤驱动 ≠ 本次运行里它过滤了东西。
把"它有这个能力"写成"它这么干了"，就是本项目反复吃过的亏
（26x 卷：`[100]` 弹窗链、`bad_items` 黑名单，都是先有可怕的机制、后有错的归因）。

## 二、所以我换了证否的方向：不看客户端，看对端

关键的一句话是：

> **客户端可以在本地吞掉任何东西，但它吞不掉"服务端已经收到的字节"。**

于是把判决权交给服务端日志。这有个额外好处：**服务端是我们自己写的**，
它的 `seq` 计数、解密成败、payload 内容全部可信，而且**与钩子无关**。

### 结果比我预想的干净

```
59 次解密成功，seq = 1..59
gaps = 0   duplicates = 0   missing = 0
```

没有任何缺口。**任何"本地丢弃/降级"都会在这里留下跳号。**

然后是这个任务里最漂亮的一条：

`seq=54` 服务端下发 `roomId = 0x1122334455667788`；
`seq=58` 客户端发来的 payload 第 6–13 字节是
`88 77 66 55 44 33 22 11` —— **就是它，小端序**。

这一个 8 字节序列，同时证明了：

1. 下行应答到了客户端（否则它不会有这个数）
2. 客户端解析对了（否则它不会原样摆回）
3. 上行发出去了（否则服务端收不到）
4. 中间没有人截胡（否则字节会变）

而且**完全不依赖任何 hook**。这是我最想要的那种证据：不可伪造、不靠分母。

## 三、还有一条我自己都意外的硬证据

`ace-ats32.dll` 的导入表里 **WS2_32 是 0 个函数**。

它导入的 7 个 DLL 是 KERNEL32 / ADVAPI32 / SHLWAPI / VERSION / PSAPI / **WINHTTP** / IPHLPAPI。
没有 ws2_32，就意味着**它连 `socket()` 都没有**——它在用户态物理上无法创建或操作
一个到 `127.0.0.2:3074` 的 socket。它唯一能做的网络动作是 WinHttp（HTTP 栈），
而 chain.txt 里它的三条 WinHttp 记录指向的是和 GDPLoader 同一族的 `down.qq.com / iedsafe` 串。

这条证据的价值在于**它是"结构性的"而不是"统计性的"**：
统计性的结论（26/2114）会被"分母不全"削弱，结构性的结论（没有导入 = 不能调用）不会。

### 但我也得说清楚它的边界

- PolicyProbe 和 BugTrace **是有** ws2_32 的（19 / 31 个函数，含 connect/sendto/send/recv）。
- PolicyProbe 有 **5.39 MB 的 `.vmp0` 段**（占文件 78%），是 VMProtect。
  我用 `FF 15 <IAT_VA>` 扫出了它 1 处 `connect`、2 处 `sendto`，但**这是下界不是全部**——
  VM 里虚拟化的代码不会以明文 `FF 15` 出现。
- 也就是说：**"从导入表和 call site 看不出 ACE 会连 3074" 是一个弱结论**；
  真正扛事的是服务端的零缺口。

## 四、关于内核那一条，我只能给到这个程度

`ACE-SSC-DRV64.sys` 导入 fwpkclnt，这是全套 ACE 里唯一能**在内核层按五元组丢包**的东西。
用户态的 `connect/sendto` hook 是**观测**，不是**拦截**——就算我把用户态全排干净，
理论上 WFP 仍然可以在更底下把包吃掉。

这一点我没法用 chain.txt 解决，因为 **chain.txt 完全看不见内核**。

但反过来：**WFP 丢包也会在服务端留下缺口。** 服务端零缺口 ⇒ 本次运行中它没有丢。
这是一个"无论机制多强都得遵守"的事实。所以我不需要去证明驱动没装，
只需要说"装了也没干活"——对本次现场，这已经够了。

**下一条该闭的**：ACE-SSC 到底加载了没有（设备枚举 `\Device\ACE-SSC-DRV64` / 服务状态）。
这不是为了回答"ACE 阻不阻断房间"（已答），而是为了把"ACE 的活动面"画完整。
注意 `HANDOFF_ACE_REVERSE.md` 的红线：**不要 `sc stop/config/delete` 驱动，会蓝屏 `0x01010002`**。
只做只读枚举。

## 五、那么房间到底坏在哪

本次现场里，房间线的两个可观测断点，**都与 ACE 无关**：

1. `21/12` 回了 `对象=0 (66 字节)` —— 空 ACK。而 `11/4` 的应答大小应该在 roomId 那条链上。
2. `11/4`（seq59）的 payload 被完整记录了（170 字节），但日志到此为止，
   没有该请求的应答行 —— 文件本身在 250 行处完整结束（24539 = 24289 + 250×`\r`），不是截断。

这两条要交给房间线其他卷。我这条支线只负责把 ACE 从嫌疑人名单里划掉。

---

## 六、留给以后的一句话

**怀疑一个"有能力的组件"时，先去它的对端找账。**
对端有没有收到、收到的是什么、字节对不对得上——这三问比在客户端里翻一千行 hook 记录都管用，
而且不受钩子覆盖面、加壳、内核层这些"观测盲区"的影响。
