## 4. 循环体里的"记录"才是真结构

| 消息 | 循环体 | 含义 |

| `MemberList` | 725 位 + 1 串 | 每个房间成员一条 |
| `JoinMemberInfos` | 725 位 + 1 串 | 同上 |

| `PlaylistWeights` | 37 位 | 每个 playlist 权重 |

## 5. 成员记录（725 位）的字段表

见 `_byte_papers/member_record_fieldmap.txt`。摘要：

```
tag 0x0a  64 位   账号 ID（u64）
tag 0x03   8 位   槽位/序号
tag 0x01   1 位   标志
tag 0x15 × 28     各字段（8/16/32/64 位混合）
tag 0x01 × 6      6 个布尔
tag 0x03 × 2      2 个 u8
tag 0x01   1 位   末位
+ 1 个变长字符串（名字）
```

**★ 关键：`0x15` 在同一记录里出现 28 次，位宽 8/16/32/64 都有。**

**⇒ 这坐实了 `0x15` 不是"类型"，而是"无类型字节串 / 原始块"标记。**

**⇒ 与 `lobby/89` 的"字段 ID"说法兼容：它是"编号 0x15 的变长容器"。**

## 6. ser/der 的差值全部是**工具未展开 helper 内部**，不是真不一致

**先给出结论：没有任何一类消息在"真实线格式"上 ser/der 不同步。**

**证据：三个 helper 的内部都读/写了等价的数据，只是工具只记了第一轮。**

### 6.1 字符串读器 `0x4f3de0`（`0x10`）

```
0x4f3deb  push 0x10 / readBitsExpect   ← 0x10
0x4f3e13  push 8   / readData           ← 读 1 字节
0x4f3e76  test bl,bl
0x4f3e78  je  0x4f3e80                  ← 读到 0 就停
0x4f3e7e  jne 0x4f3e10                  ← ★ 循环读下一字节
```

**⇒ 读侧等价于 `while (c = read(8)) != 0`。**

**写侧（`0x624539` 附近）是：**
```
call 0xb759a0        ; strlen
lea  eax,[eax*8+8]   ; (len+1)*8
push eax / writeData
```

**⇒ 写侧等价于 `writeData(str, (len+1)*8)`。**

**两者位数相同 ⇒ 工具只记了读侧第一轮 8 位，造成"差 +8"。**

### 6.2 blob 读器 `0x4f3eb0`（`0x13`）

```
0x4f3eb4  push 0x13 / readBitsExpect
0x4f3ec6  push 8    / readBitsExpect(0x08)
0x4f3ed5  push 0x20 / readData(&n, 32)      ← 读长度
0x4f3efe  mov edx,[ebp+0xc] / mov eax,[edx] ; cap
0x4f3f04  cmp eax,esi / mov eax,esi         ; min(cap, n)
0x4f3f0a  add eax,eax ×3                    ; ×8
0x4f3f14  call readData(buf, min(cap,n)*8)  ← ★ 按 n 读数据
```

**⇒ 读侧 = `0x13 0x08 <u32 n> <n×8 位>`。与写侧 `0x625be0` 的构造完全一致。**

### 6.3 于是 `StartGame` 也不是"不一致"

```
写侧 0x625be0:
  0x03:8
  0x13 0x08 <u32 来自 [eax+0x118]> <n×8 位>
  0x13 0x08 <u32 = 8>              <64 位>
  0x13 0x08 <u32 = 0x10>           <128 位>

读侧 0x625ce0:
  readBitsExpect(3) / readData(8)
  blob(&buf, cap=0xff)     ← 读 u32 = n1，读 n1×8
  blob(&buf, cap=8)        ← 读 u32 = 8，读 64 位
  blob(&buf, cap=0x10)     ← 读 u32 = 0x10，读 128 位
```

**⇒ 三块完全对应。工具的 `pre` 差异（346 vs 154）= 192 位数据段没被读侧算进去。**

### 6.4 唯一真正的座位不一致

**只要 `RoomInfo` / `Join` 里的那一个位置：**

```
ser 写 tag 0x03，der 读 tag 0x02
```

**而该位置的断言函数 `0x8435D0` = 单字节 `c3`（ret）。**

**⇒ 客户端真的不检查它。这是 D 侧代码与 S 侧代码的遗留不同步，
但因为没有断言，线上无影响。**

**⇒ 这也解释了为什么把它放到"字段 ID"框架里必然对不上：
它是唯一一处 D/S 不同步点，而不是我们工具的问题。**
