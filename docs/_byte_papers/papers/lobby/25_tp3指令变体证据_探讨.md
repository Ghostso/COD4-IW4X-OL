# `.tp3` 指令变体 · 探讨：线性反汇编在加壳代码上必然失败

> 对应：`lobby/25_tp3指令变体证据.md`

---

## 一、这是一次工具失败的复盘

我用 capstone 写了 `xref.py` / `xref2.py`，想找"谁引用了 `aes` 这个字符串"。

跑了两次，结果都是：

```
=== 0xdb5ed4  refs=0
=== 0xdb60c8  refs=0
=== 0xdb6154  refs=0
=== 0xdb62b4  refs=0
```

**零引用。**

---

## 二、我差点就信了

如果信了，结论会是：

> "`aes`、`common_gametype_mp`、`ui/default.menu` 这些字符串在 EXE 里
>  **没有任何代码引用**。"

**这是错的。**

---

## 三、转折：原始字节搜索

我换了个方法：不反汇编，直接搜字节。

`push imm32` 的编码是 `68 <4 字节小端立即数>`。

搜索 `68 d4 5e db 00`（= `push 0xdb5ed4`）：

**找到 3 处。**

```
文件偏移 0x5c042
文件偏移 0x22aeab
文件偏移 0x57889f
```

**代码确实引用它。**

---

## 四、为什么 capstone 漏了

看 `0x5c042` 附近的字节：

```
6a 18          push 0x18
39 00          cmp dword ptr [eax], eax
b0 55          mov al, 0x55
ec             in al, dx
52             push edx
68 d4 5e db 00 push 0xdb5ed4
e8 70 4c 20 00 call 0x660cbc
0x660cbc call
```

**`in al, dx` 是特权指令，用户态代码不可能有。**

**说明这几条是"错位解码出来的假指令"。**

真实的指令边界不在那里。

---

## 五、为什么会错位

**`.tp3` 不是一个普通的代码段。**

证据：
- 节名是 `.tp3`（不是 `.text`）
- 段三的 virtual size (0xdbb1cc0) 远大于 raw size (0x62000)
- 段内出现特权指令

**这是腾讯 TP3 保护体系的代码段。**

**可能的原因：**

1. **段内混杂数据**（跳转表、对齐填充，线性扫描会跑进数据区）
2. **自解密代码**（磁盘上是密文，运行时才还原为真实指令）
3. **自定义指令编码**

无论哪种，**线性反汇编都不可靠**。

---

## 六、方法论收获（这卷最重要）

> **在非常规命名的代码段上，线性反汇编不可信。必须用原始字节模式验证。**

具体做法：

| 找什么 | 用什么 |
|---|---|
| 字符串引用 | `68 <imm32>`（push） |
| 全局变量访问 | `mov reg, [imm32]` = `a1`/`8b 0d`/`8b 15` |
| 函数调用 | `e8 <rel32>`，但 rel32 要算 |

**这些模式的字节长度是固定的，不会因错位而失败。**

---

## 七、这也解释了一个更大的问题

如果 `.tp3` 是自解密代码，**那么磁盘上的 EXE 不能直接当"真实代码"来逆向**。

**必须用运行内存转储。**

而项目里已经有内存转储（`DEDRUN_RUNTIME_0x810000.bin`，
以及 `LIVE_FULLMEM_20261022\mem\mem_000.bin` 230MB）。

**下一步应该转向内存分析，而不是继续啃磁盘 EXE。**
