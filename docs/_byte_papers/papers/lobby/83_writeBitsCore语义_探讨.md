# `writeBitsCore` 语义 · 探讨：那 5 位是怎么来的

> 对应：`lobby/83_writeBitsCore语义.md`
> **补充：本卷结论在 `lobby/89` §8 已被完整函数读法再次确认，并修正了"位宽由谁决定"的措辞。**

---

## 一、本卷写对的部分

**`pad != 0` 会额外写 `12 + 8 + 32` 位封装头——这一点是对的，
而且解释了为什么"我们不走这条路"。**

**`pad == 0` 是主路径——这也是对的。**

---

## 二、本卷没说清的部分：位宽到底谁给的

**本卷写的是"`width - start` 算位宽"。**

**但 `lobby/89` 读了完整入口后发现：**

```
0xB77B10 (writeBits):
  push 0      ← pad
  push 0x1F   ← max   ★ 恒定
  push 0      ← min   ★ 恒定
  push value
  call 0xB77A70
```

**⇒ `width = 0x1F`、`start = 0` 是**调用方写死的常量**，
不是从参数传进来的。**

**⇒ 所谓 `writeBits(n)`，真名应该是 `writeValue5(value)`：
把 `value` 用 5 位写出去，超出 31 就夹到 31。**

**⇒ 本卷的"签名"写对了，但"语义"写得含糊。`lobby/89` 收口了。**

---

## 三、为什么当时会含糊

**因为我只看了 `0xB77A70`（内层），没看 `0xB77B10`（入口）。**

**内层代码 `sub ecx,edi / msb / inc eax` 看不出这两个常量从哪来。**

**⇒ 教训：先读调用方，再读被调方。
入口处的 `push` 常量是语义的最强线索。**

---

## 四、这一卷留下的最有价值的一句

> **`pad == 0` ⇒ 不写封装头。我们的所有房间消息都走这条路。**

**⇒ 这条让我们后来能把 5 位前缀直接当"字段 ID"看，
而不是当成"嵌套容器"。**

**⇒ 如果走 `pad != 0`，每条字段都要套 `12+8+32` 位外壳，
那 `lobby/89` 的 43/44 逐项相同就不成立了——因为多了一层。**

**⇒ 所以本卷是 `lobby/89` 的前提。**
