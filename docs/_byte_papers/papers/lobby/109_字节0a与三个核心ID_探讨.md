# 字节 `0x0a` · 探讨：54 种值意味着"可以逐个点名"

> 对应：`lobby/109_字节0a与三个核心ID.md`

---

## 一、这一卷能写得"确定"，是因为值域窄

**`0x07`（i32）有 59 种值、12,634 个字段。`0x0a`（u64）有 54 种值、20,525 个字段。**

**⇒ 两个的值域宽度差不多，但 `0x0a` 的字段数是 `0x07` 的 1.6 倍。**

**★ 这意味着 `0x0a` 的"平均每个值被用 380 次" —— 极高重复度。**

**⇒ 高重复度 = 这些不是"数据"，是"引用"。
  20,525 个 u64 里，绝大多数是在反复引用同一个 ID。**

**★ 所以这一卷的写法必须是"点名"：把 54 个值列出来，逐个说它是谁。
  而不是像 `0x07` 那样只能给分布。**

---

## 二、三个 ID 是怎么被"认出来"的

**我没有靠"猜哪个数字像 ID"。**

**方法是：**把每个值按 task 拆开，看它的"task 分布指纹"。**

**结果一目了然：**

```
账号 ID  0xE7C8A98A6B4C2D0E  →  4/13(290) 10/12(166) 68/3(162) 8/1(124) 21/1(42) 21/12(36)
频道 ID  0x1122334455667788  →  11/4(228) 21/1(35) 21/12(26) 11/2(9)
频道 ID2 0x6B4E6E0E          →  11/4(33) 21/12(10) 21/1(7) 11/2(4)
```

**★ 两个指纹完全不同：**
- **账号 ID 横跨"档案/文件/会话"六类 task ⇒ 它是"身份"**
- **频道 ID 只出现在"房间/会话"四类 task ⇒ 它是"房间属性"**

**⇒ 这个判断不需要任何语义知识，纯粹是"分布聚类"。**

**★ 这是逐字节分析里最可靠的一类推理：
  **不看值像什么，看值在哪些 task 里出现。**
  一个值如果只在"房间类" task 出现，它必然是房间相关的东西。**

## 三、`1800154382` 从"疑似"到"确认"（**结论在 110 卷被推翻并纠正**）

> **⚠️ 本节结论已被 110 卷推翻。保留原文以记录"我当初怎么想的、错在哪"。**
> **真相：`1800154382 = 0x6B4C2D0E` 就是账号 ID `0xE7C8A98A6B4C2D0E` 的低 32 位，
> 不是"另一个频道 ID"。**

**`108` 卷我看到它在 `mmstart` 明文里出现 4 次，写了"疑似服务端分配，待验证"。**

**本卷它在 u64 字段里出现 **54 次**，而且关键是：**

```
11/4 的元素序列：
  0a=1234605616436508552  13[145]  08=1
  0a=1234605616436508552  13[21]   08=1
  ...
  0a=1800154382           13[...]  08=1     ← 同一位置！
```

**⇒ 它和 `0x1122334455667788` **占据同一个字段位置**（`11/4` 的第 1 个元素）。**

**★ 一个字段位置，两个不同取值 ⇒ 这个字段是"变量"，不是"常量"。**

**⇒ 因此 `1800154382` 不是一个"特殊魔数"，它只是**这个变量在某次会话里的值**。**

**★ 这条推理很关键：
  如果我只看到 `0x1122334455667788` 出现 298 次，我会以为它是"常量"。
  但看到同一位置还有另一个值，我就知道它是"变量"。**

**⇒ 而"变量"意味着**我们能控制它** —— 这是可用性的前提。**

**★★ 但我在这里犯了一个推理错误：我"看到一个字段位置有两个取值"，
  就跳到了"这是同一个变量的两个取值"。而实际上第二个值根本不是"另一个房间 ID"，
  它是**账号 ID 被截断成 32 位**的结果。**

**⇒ 错在哪：我没有先做"这个值是否和已知常量有算术关系"这一步。
  只要做一次 `1800154382 == 0xE7C8A98A6B4C2D0E & 0xFFFFFFFF` 的检查，
  这个误判就不会发生。**

**★ 教训（写进方法论）：看到一个"新魔数"，第一步永远是拿它和**已知常量**
  做加/减/与/移位/截断的枚举比对，而不是急着给它起语义名字。
  110 卷就是这么纠正的。**

## 四、这一卷意外证明了参考实现是**对的**

**前几卷我一直在"推翻"参考实现（`108` 卷推翻了"不是 mmstart"）。**

**这一卷反过来：`11/4` 的结构实测是 `[u64 channelId][blob][u32]`，
而 `reply_objects` 的注释写的是 `setRoomData(u64 roomId, blob batch, u32 type)`。**

**⇒ **逐字段吻合**。**

**★ 这是第一次"参考实现与本地实测完全一致"。**

**⇒ 说明 `reply_objects` 不是不可信的 —— 它的**语义描述**通常是准的，
  只是**细节**（如"不是 mmstart"）会因为抓包不全而出错。**

**★ 所以正确的用法是：**
**- 用 `reply_objects` 的**语义**做假设**
**- 用 corpus 的**字节**做验证**
**- 两者冲突时，信 corpus（本地实测 > 第三方）**

## 五、blob 长度前缀：一个"task 专属"的精确结构

**这一卷最漂亮的数据是这张表：**

| task | `首4B == len-4` 命中率 |
|---|---|
| `11/4` | **261/261 = 100%** |
| `6/14` | **235/235 = 100%** |
| 其他 7 个 task | **0%** |

**★ 100% 对 0% —— 没有任何中间态。**

**⇒ 这不是"大概有"或"多数有"，这是**结构性的**：
  这两个 task 的 blob 一定是嵌套报文，其他的一定不是。**

**★ 为什么只有这两个？我的解释是：**
**- `11/4` 的 blob 要**转发给房间其他成员** ⇒ 需要自带边界**
**- `6/14` 的 blob 要**转交给另一个子系统**（mmbook 预约）⇒ 需要自带边界**
**- `21/1`、`8/3` 的 blob 是**自己消费的档案数据** ⇒ 不需要**

**⇒ 但我必须承认：这是**解释**，不是**证明**。
  真正的证明要看客户端代码怎么读这两个 blob。**

**★ 所以我在论文里把"为什么"标成解释，把"100% vs 0%"标成事实。**

## 六、`plain[11] == 0x15` 这个"神话"被彻底解开

**`108` 卷参考实现里有一句很有名的话：**

> "参考 C# 的自动开局判据正是这一条（`pushData[11] == 0x15`）"

**当时参考实现自己也怀疑过（注释里说"那个字节其实是 blob 长度的低字节"）。**

**本卷实测把这件事算清楚了：**

```
外层 payload = 0a <8B u64> 13 08 <4B len> <blob>
                 [0]  [1..8] [9][10] [11..14]  [15..]

plain[11] = len 的**最低字节**
blob 长度 21 = 0x15 ⇒ plain[11] == 0x15
```

**⇒ 所以 `plain[11] == 0x15` **严格等价于** "blob 长度 == 21"。**

**★ 而 21 字节的 blob 里 `blob[4] == 0x18`。**

**⇒ 真正的语义判据是："房间消息的 blob 长 21 字节，且第 5 字节是 0x18"。**

**★ 这个发现的价值：**
**如果照抄 `plain[11]==0x15`，那只要任何一个 blob 长度是 21 就会被误判为 ready。
  而实际上"长度 21"只是必要条件，还要看 `blob[4]==0x18`。**

**⇒ 参考实现的判据是"偶然正确"的 —— 因为它观察到的所有 ready 批次恰好都是 21 字节。
  但这不是因果，是巧合。**

**★ 这正是 `AGENTS.md` 说的"照抄第三方会踩坑"的具体形态。**
  **正确做法是理解字节的**来源**（这里是长度字段），而不是记住"第 11 字节是 0x15"。**

## 七、`DEADC0DE` 与 `DEADBEEF` 必须分清

**本卷发现 `6/14` 里有 `0x01100001DEADC0DE`。**

**而项目记忆里有一条"销毁哨兵 `0xDEADBEEF`（`mov [ecx],0xDEADBEEF`）"。**

**★ 两个魔数：**
```
0xDEADBEEF  ← 内存销毁哨兵（本地逆向，0xb76e50 那条 mov）
0xDEADC0DE  ← 报文里的"无效 ID"（6/14，4 次）
```

**⇒ 它们长得很像，但**完全不同用途、完全不同层**。**

**★ 如果我看到 `DEAD` 就联想到"销毁"，那会把"报文里的占位 ID"误判成
  "某个对象被销毁了"。**

**⇒ 教训：魔数要**记全 8 个十六进制位**，不能只看前缀。
  `DEADBEEF` ≠ `DEADC0DE`，就像 `0x11223344` ≠ `0x1122334455667788`。**

## 八、`102/7` 的"50 个序号"意味着什么

**`102/7` 贡献了 90.4% 的 u64，值是 0..49 的序号。**

**⇒ 这说明 `102/7` 不是"请求 50 个具体对象"，而是"请求编号 0..49 的全部条目"。**

**★ 一个固定 50 的编号空间，很像：**
- **一个 50 格的资源槽**
- **或者一个 50 项的表（如 50 个成就/50 个解锁项）**

**⇒ 未定，因为 `102` 这个 service 不在 `reply_objects` 的映射表里。**

**★ 但"50"这个数字是硬事实，且它出现在 `102/7` 的 `08 32 00 00 00`（=50）里。
  这是一个可以拿去和游戏内容对表的线索：**游戏里什么系统恰好有 50 项？****

## 九、方法论收获（四条）

> **① 值域窄的标签要"点名"，值域宽的标签要"分布"。**
>    54 种值就逐个列，59 种以上就只给 top。**

> **② 识别 ID 的最可靠方法是"task 分布指纹"，不是"值长得像什么"。**
>    横跨档案类 task = 身份；只在房间类 task = 房间属性。**

> **③ 一个字段位置有两个取值 ⇒ 它是变量 ⇒ 我们能控制它。**
>    这是"可用性"的判据。**

> **④ 结构 100% vs 0% 比"多数/少数"强得多。**
>    它说明是"设计如此"，不是"碰巧如此"。**
