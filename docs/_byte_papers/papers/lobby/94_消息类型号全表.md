## 1. 为什么这一卷能把上一卷的最后一个未知量填掉

`lobby/93` 结尾写着：

> **"我不知道消息类型号。我知道 MemberList 的第一字节是 u8 类型，
> 不知道它的 u8 值应该是几。"**

**这一卷把它填上了。**

**而且填法不是猜，是三级证据链：**

```
[obj+4] 是类型号  →  构造函数里写入常量  →  serialize 前 8 位就写这个字节
```

## 2. 定位过程：三次失败，第四次对

### 尝试 1：按 `[reg+4]=imm` 全扫

`tools/msgtype_scan.py`：扫出 16 处。

**为什么失败：只覆盖构造函数，而 45 个类里多数构造函数被内联或不存在独立的。** 命中 2/50。

### 尝试 2：从 vfptr 装填点向后 0x80 找

`tools/msgtype_exact.py`：命中 8/50。

**为什么失败：窗口里经常夹着别的寄存器的写，且 vfptr 的字节模式我一开始判断错了
（`C7 /0` 的 modrm 对 `mod=00` 是 `0x00..0x07`，不是 `0x40..0x47`）。**

### 尝试 3：栈上消息头

关键突破在 `0x62b6d0` 附近看到：

```
0x62b6d7  c7 45 f0 0c 76 dc 00   mov dword ptr [ebp - 0x10], 0xdc760c
0x62b6d0  c7 45 f4 0e 00 00 00   mov dword ptr [ebp - 0xc],  0x0e
```

**`[ebp-0x10]` 与 `[ebp-0xc]` 相差 4 —— 正是 `obj+0` 与 `obj+4`。**

**⇒ 这是把消息对象**构造在栈上**：先填类型号，再填 vfptr。**

### 尝试 4（成功）：相邻指令配对

`tools/msgtype_stack2.py`：**只在同寄存器、displacement 相差 4、
且在相邻 ±8 条指令内**配对。

**⇒ 命中 43/50。加上人工补正 2 个 = 45/45。**

## 4. ★★ 决定性闭环：类型号就是线上前 8 位

**每个 `serialize` 的开头（逐字节）：**

```
0x627d80 (MemberList):
  8a 46 04        mov al, byte ptr [esi+4]    ← ★ 取 obj+4
  6a 03           push 3
  8b cf           mov ecx, edi
  88 44 24 14     mov [esp+0x14], al
  e8 6d fd 54 00  call 0xB77B10               ← writeBits(0x03)
  6a 08           push 8
  8d 4c 24 14     lea ecx, [esp+0x14]
  51              push ecx
  8b cf           mov ecx, edi
  e8 0f fa 54 00  call 0xB777C0               ← writeData(ptr, 8)
```

**`0x627ea0`(RoomInfo)、`0x625be0`(StartGame)、`0x6261c0`(MemberDetails)、
`0x627fc0`(P2PInfo) 全部有 `8a 46 04`（或 `8a 47 04`）。**

**⇒ 线上一条 dwRoomMessage 的位流前 13 位是：**

```
5 位  = 0x03        （字段 ID：u8 通道）
8 位  = [obj+4]     （★ 消息类型号）
```

**⇒ 这解释了一个之前没解释的现象：为什么所有消息的第一个 tag 都是 `0x03`。**

**⇒ 因为它写的是"类型号"这个 u8 字段。**

## 5. 字节级：13 位头 + 类型号，逐位展开

**以 `MemberList`（类型号 14 = `0x0E`）为例，头 13 位：**

```
位序（MSB-first）:
  00011       = 0x03  (5 位 tag)
  00001110    = 0x0E  (8 位类型号)

拼成 13 位:  00011 00001110
补到 16 位:  0001 1000 0011 1000  ... 
第一个字节 = 0001 1000 = 0x18
第二个字节 = 0011 1000 → 后续位继续填
```

**⇒ ★ 与 `lobby/93` 编码器输出的首字节 `0x18` **完全吻合**。**

**⇒ 这是编码器与类型号表的第一次交叉验证。**

**⇒ 而且它反过来确认了 MSB-first 是对的（否则 5 位 tag 会落在字节低位，首字节不会恰好是 0x18）。**

## 6. 新发现：`dwRoomMessageP2PInfo`（19 号）

**它不在 `tools/dwroom_serializers.py` 的 50 类里，
因为那个脚本 grep 的是 `.?AVdwRoomMessage` 前缀，
而 P2PInfo 的 RTTI 名是 `.?AVdwRoomMessageP2PInfo@@`，本该命中——
真正原因是它的 vtable 在 `0xdc7638`，而脚本按 COL→指针搜索时漏了。**

**用 `tools/dwall_vtables.py` 直接枚举 vtable 区 `0xdc74e0..0xdc7c40`，
按 COL 反查 RTTI 名，就把它捞出来了。**

### 6.1 P2PInfo 的序列化（840 位定长）

```
0x627fc0 (serialize):
  tag 0x03 /  8 位   类型号 (=0x13)
  tag 0x15 / 32 位
  tag 0x13 /  8 位             ← blob 起始
      tag 0x08 / 32 位 (长度=67)
      data 536 位              ← ★ 67 字节 = 536 位
  tag 0x13 /  8 位             ← blob 起始
      tag 0x08 / 32 位 (长度=8)
      data 64 位               ← 8 字节
  tag 0x15 / 32 位
  tag 0x15 / 64 位
```

**总长 = 5×7 + 8 + 32 + 8 + 32 + 536 + 8 + 32 + 64 + 32 + 64 = 840 位 = 105 字节。**

**读侧（`0x6280b0`）标签序列 `03 15 13 08 13 08 15 15` —— 完全一致。**

### 6.2 那个 67 字节 blob 是什么

**长度 67 一次写死在序列化里（不是运行期算的）——`data 536` 位是立即数。**

**⇒ 它是一个 **固定 67 字节的结构**，很可能是 P2P 连接参数
（ICE/STUN 候选、密钥、地址列表）。**

**⇒ 这是"房间内 P2P 直连"的协议载体。**

**⇒ 与 memory 里 `codol-lsg-never-listening`（外部插件接管 ws2_32 失败）
直接相关：如果 P2P 协商靠这条消息，那它失败会导致 P2P 不通。**

**⇒ 这是一条新的、之前完全没看到的线索。**

## 7. 为什么 11 和 25 是空的

**全镜像搜过：没有任何 vtable 指向这两号对应的位置（其实它们根本没有位置）。**

**⇒ 两种可能：**
**A. 开发期删掉了两个类（版本演进）。**
**B. 编号是硬编码在某个枚举里（enum 显式赋值）。**

**⇒ 无论哪种，线上不会出现 11/25 号消息。**

**⇒ 这是"枚举留洞"的典型 —— 也是反过来说 45 个类不是"碰巧 45 个"的证据。**
