## §1 装配族的触发入口

`0x8269FC8` 由大函数 **`0x80A630`** 装配（254 卷已识其「源表→已拥有表」关系）。本轮把**入口**推全：

```
0x4FE120  cmp byte [0x84abb2f],0 / jne skip     ; 单次初始化标志
          push "code_post_gfx_mp" / call 0x49f180 ; ★ 资产加载检查
          call 0x80A360                          ; → 0x80A630
...
0x80A360  cmp byte [0x84abb2f],0 / jne ...       ; 同一标志
          mov  byte [0x84abb2f],1                ; 置位
          call 0x80A630                          ; ★ 建已拥有表
          call 0x80A4C0                          ; loadout4/5enable
          call 0x80A550                          ; supply_basic/advanced/limited
          call 0x811ce0
```

另一入口：

```
0x5C0310  cmp [0x76446b0],8 / jge ...
          cmp [eax+0x76446b0],5              ; ★ clientState(clientState 指针 = 0x76446B0)
          call 0x7F9090                      ; Whitelist/HTTPS 刷新(156 卷)
0x5BFCE0  call 0x809140 / ...
          call 0x80A400
0x80A400  call 0x80A630 / call 0x80A4C0 / call 0x80A550 / jmp 0x811ce0
```

**⇒ 两个入口：**
1. `0x4FE120` —— **`code_post_gfx_mp` 资产加载后**的单次初始化（UI/资源装载）。
2. `0x5BFCE0`←`0x5C01C0`/`0x5C0310` —— **clientState 前进到 5/8 时**（连接/状态机驱动）的重建。

**两者都不在 marketplace/库存处理路径上。**

## §3 `0x80A630` 的输入（无库存）

`0x80A630` 调用的子函数（去重）：

```
0x76B7A0  (path,&out): push 0x25 ; push path ; call 0x49CF30   ; ★ 装载 CSV
0x49CF30  资产/文件装载器（code_post_gfx_mp 同款）
0x660B00  (name)->ptr: 按名查 dvar/配置表 [0x779583C]           ; dvar 查表
0x810B20  (esi=entry, eax=item): 写入 {key,exists,init,value} 编码项
0x80A5E0  (item)->bool: 查已拥有表(去重用)
0x8435D0  空桩 C3（无副作用）
```

关键字符串（`push imm32`）：
- `0x80A63F push 0xDE6D1C` = **`"mp/coStartingLoadoutSetting.csv"`** —— 逐行读该 CSV 的列名，再 `0x660B00(名)` 求值，写入源表 `0x8269B6C` 族。
- 硬编码名（经 `0x660B00`）：`cha_INFbaseA`/`heg_composite`/`fja_leathersuits`/`ret_default`/`sco_none`/`uav`/`predator_missile`/`helicopter`/`badge_unlock_%d`/`defaultknife_mp`/`emp`/`armor_locker`/`umbrella_system`/`pci_default`/`pcb_default`/`pct_default`/`m4t2_mp` …
- `loadout4enable`/`loadout5enable`（在 `0x80A4C0`，写 `[0x84ABB38]/[0x84ABB3C]` = 60027/60028）。

`0x660B00` 读全局表 `[0x779583C]`（75 个函数引用它，是全客户端通用的 name→entry 表，条目 `[entry+8]`=名字）。**该表是客户端 dvar/配置注册表，不由 lobby 网络消息驱动。**

**⇒ `0x80A630` 的全部数据来源是：客户端 CSV 资产 + 客户端 dvar + 编译期硬编码名。它没有读取 80/203、80/230 任何库存负载的代码路径。**

复现：`t1b_entry.py`（结构）+ `t1d_strings.py`（字符串）+ `t1f_config_src.py`/`t1g_config2.py`（`0x660b00`）。

## §7 方法论

1. **★★★★★ 「服务端能不能让客户端拥有」要落到「谁写那张表」。** 判据函数（`0x5E3550`）只读一张表，就只问一个函数：**谁写这张表**。写者唯一 ⇒ 判据链的唯一输入源就被钉死。
2. **★★★★ 写者要用「任意操作数编码」的字节搜索穷举，不能只搜 `mov [T],eax`。** `lea esi,[esi*4+BASE]`（SIB）这种索引形式才是本表的写入形；只搜 `89 05` 会漏全部。
3. **★★★ 函数输入看它 push 的字符串与它 call 的子函数。** `0x80A630` push 的是 CSV 名与硬编码名、call 的是 dvar 查表与 CSV 装载 ⇒ 数据来源一目了然；「它有没有读库存」= 「它的子调用里有没有库存解码器」。
4. **★★★ 「反例」优先于「正面证据」。** 252 卷 `121 在库存不在表` 一条，就把「库存=已拥有」证伪；本卷只补上机械原因。
5. **★★★ 触发入口决定「时机」而不是「来源」。** 两个入口（资产加载后 / clientState 5/8）说明表在**启动/状态推进**时建一次；即使重建，重建的输入仍是 CSV/dvar。
