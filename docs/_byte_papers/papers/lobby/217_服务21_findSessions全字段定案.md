### 1.2 ★ 必须先说的边界：日志截断 96 字节

`CODOL_VERIFIED_GOLDEN_20261019\lobby_server.py:1445`

```python
log("       payload(%d): %s" % (len(r["payload"]), hexd(r["payload"][:96])))
```

`len(...)` 是全长，`hexd(...)` 只吃前 **96** 字节。所以：

- `payload(269)` / `payload(288)` 的**真实长度是 269 / 288**，但日志里只有 96 字节的十六进制。
- 所有 ≤96 B 的任务（`21/3`、`21/5`、`10/*`）是**完整样本**。
- `21/1`、`21/12` 只能定案前 96 B —— 这是**证据缺口，不是协议结构**。见 §6.4 / §9 开项 O-1。

### 1.3 消息体的公共文法（本节定案，§2 给地址）

```
message := field* 0x00
field   := <tag:1B> <value>
```
- 字符串=**裸字节 + 0x00**（非长度前缀）。
- blob/数组=**两级**：外层 tag，内层 `0x08` + `u32`。
- 整个消息**以一个单独的 `0x00` 结束**。这条把此前所有"结尾莫名多一个 0"的账全对上（§5.3）。

## §2 类型标签表：从客户端写侧函数逐条读出（铁证）

`0xB7xxxx` 是 Demonware 字节缓冲（非位流）一族。缓冲对象布局（ctor `0xB76480`）：

| 偏移 | 含义 | 证据 |
|---|---|---|
| `+0x00` | vtable `0xDB7154` | `0x4AB13C mov [esi],0xDB6AE4` → `0x4AB149 mov [esi],0xDB7154` |
| `+0x08` | 容量 | `0xB7649C mov [esi+8],edi` |
| `+0x0C` | 缓冲基址 | `0xB764A0` |
| `+0x10` | **读游标** | `0xB75E80 … add [esi+0x10],size` |
| `+0x14` | **写游标** | `0xB75E00 … add [esi+0x14],size` |
| `+0x18` | **useDataTypes（是否写标签）** | `0xB75F33 cmp byte [ecx+0x18],0` |
| `+0x19` | 标签开关的保存槽 | `0xB76C86 mov [esi+0x19],al` |

**基础原语**：`0xB75F30` 只在 `[+0x18]!=0` 时写 1 字节（标签）；`0xB75E00` 写 n 字节；`0xB75E80` 读 n 字节。

> ★ **与 223 卷（服务 71 遥测）独立互证**：223 卷从**读侧**列出同一张表（`01`=bool@`0xB76850`、`03`=u8@`0xB76890`、`06`=u16@`0xB768D0`、`07`=i32@`0xB76910`、`08`=u32@`0xB761E0`、`09`=i64@`0xB76950`、`0A`=u64@`0xB769A0`、`0D`=f32@`0xB769F0`、`10`=string@`0xB76A30/B90`、`13`=blob@`0xB76AF0/B60`），**与本卷从写侧读出的表逐条一致**（并且 223 卷证明了 `13` 后面的 `08` 就是"长度字段自身的 u32 标签"）。两卷**互不知道对方**，却给出同一张表 —— 这是本表最强的证据。

| tag | 类型 | 写侧函数 | 内部证据 |
|---|---|---|---|
| `0x00` | null（第二种） | `0xB760A0` | `push 0; call 0xB75F30` |
| `0x01` | bool/u8 | `0xB765E0` | `push 1` + 1 字节 |
| `0x03` | i8 | `0xB76620` | `push 3` + 1 字节 |
| `0x05` | i16 | `0xB76000` | `push 5` + `movzx word` + 2 字节 |
| `0x06` | **u16** | `0xB76040` | `push 6` + 2 字节 |
| `0x07` | **i32** | `0xB76660` | `cmp edi,0x7FFFFFFF` → `push 7` + 4 字节 |
| `0x08` | **u32** | `0xB766B0` | `cmp edi,-1` → `push 8` + 4 字节 |
| `0x09` | i64 | `0xB760C0` | `push 9` + 8 字节 |
| `0x0A` | **u64** | `0xB76120` | `push 0xA` + 8 字节 |
| `0x0D` | f32 | `0xB76180` | `push 0xD` + 4 字节 |
| `0x10` | **string** | `0xB76700`（writeString）/ `0xB767A0`（writeCString=+1 再写） | `push 0x10`；先 `call 0xC3FF30` 求长度；末尾 `push 1; mov byte[ebp+0xB],0; call 0xB75E00` |
| `0x13` | **blob** | `0xB767D0` | `push 0x13` → `call 0xB766B0`(写 u32 长度) → 写数据 |
| `0x14` | null（第一种） | `0xB76080` | `push 0x14` |
| **`0x64+T`** | **array（元素类型 T）** | `0xB76C70` + `0xB75E70` | 见下 |

### 2.1 数组编码（`0x6B` 的来历）

```asm
0xB76C70  mov cl,[ebp+8]        ; T = 元素类型 tag
0xB76C79  mov al,[esi+0x18]
0xB76C7C  add cl,0x64           ; ★ 数组 tag = 0x64 + T
0xB76C86  mov [esi+0x19],al     ; 存旧标签开关
0xB76C89  mov byte [esi+0x18],0 ; ★ 关标签
0xB76C8D  call 0xB76620         ; 把 (0x64+T) 当"值"写 1 字节 → 输出就是裸 0x6B
0xB76C95  mov byte [esi+0x18],1 ; 开标签
0xB76C9F  imul eax,edi,[ebp+0x10]  ; byteLen = count × elemSize
0xB76CA6  call 0xB766B0         ; 写 08 + u32 byteLen
0xB76CB5  mov byte [esi+0x18],0 ; 关标签
0xB76CC0  call 0xB766B0         ; 写 u32 count（裸）
0xB75E70  mov al,[ecx+0x19]; mov [ecx+0x18],al   ; 恢复标签开关
```

⇒ `T=0x07`（i32）→ 数组 tag **`0x6B`**；`T=0x08`（u32）→ `0x6C`。
⇒ 编码：`[0x6B][0x08][u32 byteLen][u32 count][count×elem 裸写]`，且 `byteLen = count × 4`。
⇒ **这解释了 91 卷以来 "0x6B/0x6C 不明"**：它们不是独立类型，是"数组头 = 0x64 + 元素类型"。

## §4 客户端的查询类（地址级）

### 4.1 RTTI → vtable → ctor → serialize 全表

RTTI 名字串（`.?AV…@@`）在 `0xE6ED30..0xE6EEB8`，用 `name-8=TypeDescriptor` → 找 `COL(+0xC==TD)` → 找 `[-1]==COL` 得 vtable。

| 类（RTTI 地址） | vtable | ctor（写 vtable + `+0x48`） | serialize |
|---|---|---|---|
| `MatchMaking_FIND_SERVERS_Query`（`0xE6EE68`） | `0xDC7A28` / `0xDC7A3C` | **`0x807450`**（`+0x48=1`） | **`0x8074D0`**：1 个 i32 + 数组 |
| `…FIND_LOBBIES_BY_MAP_Query`（`0xE6EE34`） | `0xDC7A44` / `0xDC7A58` | **`0x807520`**（`+0x48=2`） | `0x8075B0`：6 个 i32 + 数组 |
| `…FIND_LOBBIES_BY_PLAYLIST_Query`（`0xE6EDF8`） | **`0xDC7A60`** / `0xDC7A74` | **`0x807640`**（`+0x48=3`） | **`0x8076D0`**：9 个 i32 + 数组 |
| `…FIND_LOBBIES_BY_CHANNEL_Query`（`0xE6EDC0`） | `0xDC7A7C` / `0xDC7A90` | — | `0x8078xx` |
| `…BY_GAME_TYPE_Query`（`0xE6ED78`） | `0xDC7A98` / `0xDC7AAC` | — | `0x807Axx` |
| `…BY_NAME_Query`（`0xE6ED30`） | `0xDC7AB4` / `0xDC7AC8` | — | `0x8079xx` |
| `MatchMakingQuery`（`0xE6EEB8`） | `0xDC7A10` / `0xDC7A20` | 基类 | — |
| `bdMatchMakingInfo`（`0xE6EED8`） | `0xDDCB98..` | — | — |
| `MatchMakingInfo`（`0xE6EEF8`） | `0xDC79F0`/`0xDC79FC`/`0xDC7A08` | MMI ctor `0x806B50`（198 卷） | **反序列化** `0x806F20`/`0x806C90` |

**`+0x48` 就是 queryType 的铁证**：

```asm
0x807450 … 0x807485  mov dword [esi+0x48],1        ; FIND_SERVERS
0x807520 … 0x807565  mov dword [esi+0x48],2        ; BY_MAP
0x807640 … 0x807685  mov dword [esi+0x48],3        ; BY_PLAYLIST
```
而日志里 35 B 的第 1 个 u32 = `1`、75 B 的第 1 个 u32 = `3` —— **一一对应**。

### 4.2 字段偏移 → 载荷位置（`FIND_LOBBIES_BY_PLAYLIST`）

`0x8076D0` 的写序是 `+0x4C, +0x54, +0x50, +0x58, +0x5C, +0x60, +0x64, +0x68, +0x6C`（注意第 2、3 个是 `+0x54` 在 `+0x50` **之前**），与 75 B 的 9 个 i32 一一对齐。

赋值点（构造现场 `0x62D8C3` 附近，`esi = esp+0x20` 即查询对象）：

```asm
0x62D8C3  call 0x807640                 ; 构造 BY_PLAYLIST 查询
0x62D8D2  mov eax,0x800000 (仅当 [0x82CA044]!=0)
0x62D8DD  mov edx,[ecx+0xC] ; ecx=[0x7ACE410]
0x62D8E8  or  edx,0xD692ADA0            ; ★ 魔数基
0x62D8EE  xor edx,eax
0x62D8F4  mov [esp+0x6C],edx            ; obj+0x4C = magic
0x62D8FA  mov [esp+0x74],eax            ; obj+0x54 先写
0x62D908  push esi; call [edx+0xF8]     ; ★ 虚函数"填充查询条件"，收 &query
0x62D90B  mov [esp+0x74],ebx            ; obj+0x54 = 覆盖值
0x62D904  mov [esp+0x78],ecx            ; obj+0x58
0x62D926  mov [esp+0x7C],eax            ; obj+0x5C = [edx+0xF8] 返回值
0x62D92A  mov [esp+0x80],ecx            ; obj+0x60 = [0x7B25A38]
0x62D91D  mov [esp+0x84],esi            ; obj+0x64 ← 见 0x62D897（0x761740() 结果）
0x62D931  mov [esp+0x88],edx            ; obj+0x68 = [edi+0x10750]
0x62D938  mov [esp+0x8C],0              ; obj+0x6C（另有条件置 1，见 0x62D989）
```

`0x62D8F4` 的 `[esp+0x6C]` = `esi+0x4C`（因 `esi=[esp+0x20]`）⇒ **`obj+0x4C` 就是载荷 `+15`**，直接对上。

> `obj+0x50`（载荷 `+25`，恒 255）在 `0x62D8C3` 段内**没有**写点；ctor 把它置 `0x7FFFFFFF`。它必在 `0x62D908` 那条 `call [edx+0xF8]`（以 `&query` 为参数）内被写 —— 这是本卷**未闭合的一小点**（O-5）。

### 4.3 35 B 变体的构造现场

```asm
0x6292D0  call 0x807450                 ; 构造 FIND_SERVERS 查询
0x6292EA  mov ecx,[0x7ACE410]
0x6292F0  mov edx,[ecx+0xC]
0x6292F3  or  edx,0xD692ADA0            ; ★ 同一魔数基
0x6292F9  xor edx,eax                   ; eax = 0 或 0x800000
0x6292FD  mov [esp+0x5C],edx            ; obj+0x4C（esi=esp+0x10）
```

### 4.4 数组：`0x8073B0` = 16 槽过滤器

```asm
0x8073B0  ; 统计 [edi..edi+0x40] 中 16 个 dword 的非零个数 → ecx
0x8073E6  push 4
0x8073E8  inc ecx                       ; count = 非零数 + 1
0x8073E9  push ecx
0x8073EA  push 7                        ; 元素类型 = i32
0x8073EE  call 0xB76C70                 ; → 数组头 6B 08 <byteLen=count*4> <count>
0x8073F7  push 0; call 0xB76660         ; 首元素恒 0
0x807410..0x807432                      ; 16 个 dword，非零者逐个写入
0x80743B  call 0xB75E70                 ; 结束数组（恢复标签开关）
```
⇒ count=1 当且仅当 16 槽全 0 ⇒ 载荷 `+20/+60` 的 `6B 08 04 00 00 00 01 00 00 00` + 元素 `00000000`。**与日志逐字节吻合**。

## §5 魔数 `0xD692ADAB` 的来源（本次真正的新发现）

### 5.1 常量在镜像里**不存在**

全镜像搜 `ab ad 92 d6`（u32 LE）→ **0 命中**；`0x8D51E398`（魔数 B）→ **0 命中**。
⇒ 不是编译期常量。

### 5.2 它是"ID 低位 + 掩码"

```asm
0x6292EA  mov ecx,[0x7ACE410]     ; → 0x80FB5F0（镜像实读）
0x6292F0  mov edx,[ecx+0xC]       ; → 0x0B（镜像实读：[0x80FB5F0+0xC]=0x0000000B）
0x6292F3  or  edx,0xD692ADA0      ; 0x0B | 0xD692ADA0 = 0xD692ADAB
0x6292F9  xor edx,eax             ; eax=[0x82CA044]?0x800000:0；镜像实读 [0x82CA044]=0 ⇒ 不变
```

**实读验证**（`python -I`，`image.read(0x7ACE410)=0x80FB5F0`，`read(0x80FB5F0+0xC)=0x0B`）：

| 项 | 值 |
|---|---|
| `[0x7ACE410]` | `0x80FB5F0` |
| `[0x80FB5F0+0xC]` | `0x0B` |
| 掩码常量 | `0xD692ADA0` |
| 或运算结果 | **`0xD692ADAB`** = 日志 161/161 条的第 4 个 i32 |

⇒ 该字段 = **"实例/租户 ID（低 4 位 = 0x0B）嵌进固定掩码 `0xD692ADA0`"**，是一个**位域打包值**，不是哈希、不是校验和、不是时间戳。
⇒ `0x82CA044` 是"把 bit21 置 1"的开关（某些 UI 状态下），当前镜像为 0。

### 5.3 这同时否掉了"整数字段混淆"假说

157 卷提出"0xE57A70 静态种子 = 整数字段混淆"。本卷看到的是 **`or` 打包**，不是 `xor` 混淆；`0x7FC0F0` 才真的用了 `xor [0x82693A4]` + `rol 8` 的混淆（那条属于别的服务）。**同一份报文中，"打包"和"混淆"是两种不同手法，不能混为一谈。**

## §11 方法论

1. **先读"写侧函数"再读报文**：类型标签表不是猜出来的，是从 `0xB76000..0xB767D0` 这一族写函数里 `push <tag>` 直接读出来的。报文与代码**互为校验**（报文里出现的 tag 必须都能在写侧找到，且宽度一致）。
2. **`push imm8` 不一定是位宽，也不一定是类型**：`0x6B` 根本不是独立类型，是 `0x64 + 元素类型`（`0xB76C7C add cl,0x64`）。**看到"奇怪 tag"先找它和已知 tag 的算术关系**。
3. **"常量不在镜像里"要立刻转成"它是算出来的"**：搜字面量 0 命中 → 直接去找 `or`/`xor`/`shl` 的组合点，比继续搜更省时间（本卷因此抓到 `or 0xD692ADA0`）。
4. **日志长度 ≠ 协议长度**：`payload(269)` 只代表长度，`hexd([:96])` 才代表内容。**看到"某任务 payload 都是 96 B"先怀疑日志截断，而不是先怀疑协议固定 96 B**。
5. **`imul count, elemSize` 一把给出 `byteLen`**：数组头的两个 u32（byteLen / count）之间是乘法关系，能互相验证；单看一个会得出"4=4"的无意义巧合。
6. **RTTI 的 COL 有 5 字段形态**（x86 VC：sig/offset/cdOffset/pTD/pClassDesc，无 pSelf）。按 6 字段找会全部失败 —— 本卷第一版就是这样全空，改成 `COL+0xC==TD` 才对上。
7. **`COMDAT folding` 会让一个类的 vtable 连续出现两次**（`0xDC7A60` 与 `0xDC7A74` 同属 `BY_PLAYLIST`），**取第一个槽当"方法 0"**，否则会把 serialize 认错。
