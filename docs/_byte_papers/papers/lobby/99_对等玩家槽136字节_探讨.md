# 对等玩家槽 136 字节 · 探讨：差一点把两个结构当成一个

> 对应：`lobby/99_对等玩家槽136字节.md`

---

## 一、这一卷最值钱的不是结论，是一次"差点翻车"

**追 P2PInfo 构造调用点的上游时，我看到 `0x7c0410` 在遍历玩家槽：
`shl eax,6`、比 `[+0x88]`、`cmp ecx,0x13`。**

**第一反应：这就是 P2PInfo 打包时用的那个数组。**

**⇒ 如果我这么写了，整卷就错了。**

---

## 二、为什么错

**`P2PInfo` 打包器 `0xb74bc0` 的循环是：**

```
0xb74c7a  add esi, 0x88
0xb74c80  cmp esi, 0x550
```

**而 `0x7c0410` 是：**

```
0x7c0476  add eax, 0x40
0x7c0479  cmp ecx, 0x13
```

**⇒ 步长 136 vs 64；上限 10 vs 19。**

**⇒ 两个**完全不同**的数组。**

---

## 三、我靠什么发现的

**我没有"凭直觉"，我做了一件很土的事：**
**把两处的常量并列写出来。**

```
0x88 = 136        0x40 = 64
0x550/0x88 = 10   0x13 = 19
```

**⇒ 并列之后，"这不可能是一个东西"是自明的。**

**⇒ 如果我只读了一处就下笔，永远发现不了。**

---

## 四、这件事的方法论价值

> **凡是"步长 / 上限"这种数字，必须写成算式并列。
> `0x550/0x88=10` 和 `19` 摆在一起，一眼就不对。**

**⇒ 这比"读完两个函数再回忆"可靠得多。**

**⇒ 这是这一轮第三次靠"写出来并列"抓住错误
（前两次：`lobby/89` 的地址不连续、`lobby/90` 的 StartGame 192 位差）。**

---

## 五、但也因此发现了一个真的东西

**两条线索虽然指两个数组，但都有用：**

- `0x88/10` 是对等玩家表（P2PInfo 用）
- `0x40/19` 是会话网格（连接层用）

**⇒ 第二个是意外收获，而且它和 memory 里的连接线有关。**

**`0x7c0410` 里的比较是 `[+0x88]` 句柄、`[+0x8C]` 地址——
这正是"按句柄+地址配对查会话"的典型写法。**

**⇒ 后面要查"连接单例 `[0x8269774]`"时，这个函数可能是入口之一。**

---

## 六、`0xDEADBEEF` 是这一卷的第二个礼物

**`0xb76e50` 只有一条指令，但意义重大：**

**它把"释放"这件事变成了**可搜索的信号**。**

**⇒ 如果将来抓到一份内存转储，在里面搜 `EF BE AD DE`，
就能回答"这个数组有没有被销毁过"。**

**⇒ 而 memory 里 `codol-room-reverse-conclusion-connection-bound`
一直在纠缠"对象存在/不存在"。
**⇒ `0xDEADBEEF` 提供了一个比"看指针是否为零"更硬的判据：
指针为零可能是从未创建，也可能被清空；
但 `0xDEADBEEF` 只会在"曾经存在、后被释放"时出现。***

---

## 七、8 个 `01` 的谜底：解了一半

**`lobby/98` 我只能说"这是常量 `0xc7341d0`"。**

**这一卷我看到了它在**源槽**里的位置：`+0x09` 起 8 字节。**

**⇒ 它不是"独立的 8 字节常量"，而是"槽的一个字段"。**

**⇒ 但仍不知道这 8 字节表示什么。**

**⇒ 而且发现 `+0x54/+0x58` 还有 16 个 `01`。**

**⇒ 槽里一共 24 个 `01`，比原来以为的多两倍。**

**⇒ 这是"越挖越深"的典型：
一个结论引出三个新问题。但每个新问题都比原来的更精确。**
