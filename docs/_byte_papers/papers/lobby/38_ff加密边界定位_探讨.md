用户让我"继续挖 `IWff0100` 那条分支"。

**这个结论不是猜的，是从控制流读出来的。**

---

## 二、为什么这个结论可信

### 论证结构

```
1. AES 解密函数 0x4834f0 被调用前，必须 [0x1c4b700] != 0
2. [0x1c4b700] 只在 0x483b49 被 memset 清零
3. 只有 0x483b40 内部会写它
4. 0x483b40 只在 0x483ed3 被调用
5. 0x483ed3 的前置是 [ebp-0x10] == "IWffu100"
6. 磁盘上所有 .ff 都是 "IWff0100"
∴  解密永远不会执行
```

**六步，每步都能在反汇编里指着看。**

**这不是"熵高所以是加密"那种统计推断，
是"这段代码不会走"那种事实。**

## 四、一个具体的教训

`0x1c4b700` 这个全局变量，在整个镜像里只出现 5 次：

```
0x483b49  push 0x1c4b700   (memset 参数)
0x484a20  cmp  [0x1c4b700], 0
0x4a0cb0  cmp  [0x1c4b700], 0
0x483d24  cmp  [0x1c4b700], 0
```

**五处引用，一处写、三处读。**

**找到"写"的那一处，就看懂了整个门控。**

**这个动作花了不到 2 分钟，比前面 9 轮的调参都有效。**

## 五、还剩下什么

三个候选，按可能性排序：

1. **TP3 保护层** —— 最可能
   - `.tp3` 段在磁盘上反汇编错位，内存里正确
   - 说明磁盘代码被变换过
   - **同理，`.ff` 载荷也可能在内存中才解密**

2. **VFS 组合过滤器** —— 可能
   - `ICreateCoderRWFilter` 和 `ICreateZlibRWFilter` 是工厂
   - 可能有"组合"实例

3. **运行时内存** —— 未验证
   - 现有 dump 里 `0x1c51734` 是 0
   - 需要更晚的 dump
