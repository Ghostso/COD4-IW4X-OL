## 二、★ 硬结论 1：`ROOM_READY_BATCH` 不是客户端会发的东西

### 2.1 客户端 Ready 的**精确**线上位流（本卷新解）

`dwRoomMessageReady` 的序列化器 = **`0x6287D0`**（vtable `0xDC7624` 的 slot[0]）。逐指令：

```asm
0x6287DD  mov al, byte [esi+4]       ; this+4 = type (0x10)
0x6287E0  push 3
0x6287E7  call 0xB77B10             ; ★ WriteBits(3)    → 3 位
0x6287EC  push 8
0x6287F1  lea ecx,[ebp+8] / push ecx
0x6287F4  call 0xB777C0             ; ★ WriteBits(8, &type) → 8 位
0x6287FB  mov bl, byte [esi+8]      ; this+8 = ready 布尔
0x6287FE  push 1
0x628802  call 0xB77B10             ; ★ WriteBits(1)    → 1 位（bool 存在位）
0x62880B  test bl,bl / je
0x628812  mov byte [ebp+0xB], 0xFF  ; 真 → 写 0xFF
0x628827  mov byte [ebp+0xB], 0x00  ; 假 → 写 0x00
0x62882B  call 0xB777C0             ; ★ WriteBits(1)    → 1 位
```

**总位宽 = 3 + 8 + 1 + 1 = 13 位。**

| ready | 位串（13 位） | 打包（2 字节） |
|---|---|---|
| 1 | `0000001000011` | **`02 18`** |
| 0 | `0000001000010` | **`02 10`** |

（`esi+4 = 0x10` ⇒ 前 3 位 `0x10&7 = 0`，接下来 8 位 `0x10`。）

### 2.2 服务端常量 `ROOM_READY_BATCH`

```python
# codol_crypto.py:802
# 房间 ready 批次的 16 字节常量 —— 照抄 ol-mod Unknown0BService.cpp:98-101。
ROOM_READY_BATCH = 0c 00 00 00  02 02 00 00  00 08 00 00  00 80 08 00   (16 字节)
```

### 2.3 对不上，而且是根本性的

| | 客户端实际 | 服务端常量 |
|---|---|---|
| 长度 | **2 字节**（13 位打包） | **16 字节** |
| 首字节 | `02` | `0C` |
| 结构 | `[3位tag][8位type][1位存在][1位值]` | 完全不同的 4 段定长 |

**⇒ 服务端拿一个 16 字节的**ol-mod 常量**去和客户端发的 2 字节位流做 `==` 比较。永远不相等。**

```python
has_ready = (bytes(batch) == cc.ROOM_READY_BATCH       # ← 永远 False
             or (len(plain) > 11 and plain[11] == 0x15))  # ← 退化的兜底
```

**所以「点准备」实际只靠 `plain[11] == 0x15` 这一条兜底判据在起作用。**

### 2.4 而源码自己也怀疑 `plain[11]==0x15`

`lobby_server.py:788-796` 的注释：

> 「★ 2026-10-04 更正 ready 判据：**不是** `payload[11]==0x15`。
>  · 三方的 `pushData[11]==0x15` 是**误读**：那个字节其实是 blob 长度的低字节（0x15=21），不是子类型」

**两天后又（`799-802`）把它加回来了**：

> 「★ 2026-10-07 实机更正: 客户端 PvE 剧情任务发来的 ready 批次是 21B, 其中 `plain[11]==0x15`」

**⇒ 这是一条被推翻又重新启用的判据，两边的理由都没用本地字节验证过。**

## 三、★ 硬结论 2：`plain[11]` 的正确含义，本地镜像能直接判定

### 3.1 `plain[11]` 是什么

`_parse_set_room_data` 的解包格式（源码自己写的）：

```
0A <u64 channelId> | 13 08 <u32 len> <batch...> | 08 <u32 type>
```

按这个格式，`batch` 的起点 = `1 + 8 + 6 = 15`，**`plain[11]` 落在 `channelId` 内部**（第 3 字节），**不是 batch 的字节**。

**⇒ `plain[11]==0x15` 读到的是 channelId 的一个字节，与「ready」毫无关系。**

这正好印证 `0x0B/4` 的注释里那句「那个字节其实是 blob 长度的低字节」——**两种说法都不对，它是 channelId 的第 3 字节**。

### 3.2 正确的判据（用本地镜像）

**判 ready 应该判位流本身**：

```
batch 至少 2 字节，且
  (batch[0] >> 5) == 0            # 前 3 位 tag = 0
  ((batch[0] & 0x07) << 5 | (batch[1] >> 3)) == 0x10   # 8 位 type == 0x10
  (batch[1] & 0x04) != 0          # 存在位
```
或更直白：**`batch[:2]` ∈ {`02 18`, `02 10`}**（分别为 ready=1 / ready=0）。

**这个判据来自客户端序列化器（第一权威），不是照抄。**

## 五、可立即修的三处（都基于本地权威）

### 修 1：ready 判据改成位流判据

```python
def _is_ready_bitstream(batch: bytes) -> bool:
    """Ready 位流 = [3位tag=0][8位type=0x10][1位存在][1位值]
       来源：客户端序列化器 0x6287D0（本地逆向，第一权威）"""
    if len(batch) < 2:
        return False
    tag = batch[0] >> 5
    typ = ((batch[0] & 0x07) << 5) | (batch[1] >> 3)
    return tag == 0 and typ == 0x10

has_ready = _is_ready_bitstream(batch)
```

### 修 2：删掉 `plain[11]==0x15`

它读的是 `channelId` 内部字节，与 ready 无关。

### 修 3：game start 载荷标注为未验证

源码已经写了「不是已验证的 coop 开局数据」，但代码仍在用。应改为**默认不发**，或明确标注 `UNVERIFIED`。

## 六、方法论

1. **★★ 「清楚」不等于「能跑」。** 房间问题现在**完全清楚**，但清楚的内容是「服务端有三条错」。
2. **★★ 照抄的常量必须与本地逆向做过 `==` 对账。** `ROOM_READY_BATCH`(16B) vs 客户端位流(2B)，一眼就能否掉，却挂了很久。
3. **★ 同一条判据被推翻又启用（`plain[11]`），说明两次都没用本地字节验证。** 有本地镜像就该查序列化器，不该靠"实机试"。
4. **★ 位流格式要从序列化器逐条 `WriteBits` 累加得出**，不能从抓包长度倒推。
5. **★ `_parse_set_room_data` 的字段偏移要自己算一遍**：`1+8+6=15` 起点 ⇒ `plain[11]` 在 channelId 里，不在 batch 里。
