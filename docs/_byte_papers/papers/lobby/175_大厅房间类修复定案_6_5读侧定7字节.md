## §1 ★★★ 为什么是 7 字节：读侧才是权威

### 1.1 客户端读取器的构造参数

```asm
0x637009  push 0x24 / call 0xB74220     ; alloc(0x24)
0x637019  mov  ecx,[ebp+0x24]           ; 参数 = 每条 item 的位宽
0x63701C  lea  edx,[ecx*8]              ; ×8
0x637023  mov  ecx,[ebp+0x20]           ; 缓冲
0x637026  push 1                        ; ★★★ 第 3 个参数 = 1
0x63702C  call 0xB779A0                 ; 读侧 ctor
```

⇒ **读侧对象的 `+0x21` = 1**。

### 1.2 `+0x21` 决定读不读那 8 位

`0xB774E0`（读原语）第一件事：

```asm
0xB774F0  cmp byte ptr [ecx+0x21], 0
0xB774F4  mov al, 1
0xB774F6  je  0xB7754F                ; ★ 为 0 → 直接返回 True，什么都不读
```

⇒ 读侧 `+0x21 == 1` ⇒ **走完整路径，真的读**。

### 1.3 读侧的完整头部（`GeneralManifold` 反序列化 `0x6256C0` + 容器 `0x637000`）

```asm
; 容器层 0x637000
0x637048  push 3   / call 0xB774E0    ; 读 3 位
0x637055  push 8   / call 0xB772E0    ; 读 8 位
0x637062  movzx eax,[ebp-1]
0x63706E  cmp  eax, 1 / jne ...       ; ★ 8 位 != 1 → 走另一分支（无 count）
; 有 count 的分支：
0x63707D  lea ecx,[ebp-0x20] / mov [ebp-0x20],0xdc74f8
0x637090  call 0x6256C0               ; GeneralManifold::deserialize

; 0x6256C0 内部
0x6256E4  push 3 / call 0xB774E0      ; 再读 3 位（tag）
0x6256F9  push 8 / call 0xB772E0      ; 再读 8 位（type）
0x625721  push 8 / call 0xB774E0      ; ★ 读 8 位
0x62572E  push 0x20 / call 0xB772E0   ; ★★ 读 32 位 count
```

★★★ **合计 `3 + 8 + 8 + 32 = 51 位 = 7 字节`。**

### 1.4 为什么不能照写侧

写侧 `0x625520` 的第三个 `WriteBits(8)`（`0x62555A push 8 / call 0xB77B10`）在**写侧对象 `+0x21 == 0` 时不写**。

**但读侧 `+0x21 == 1`，恒读。**

⇒ 服务端若按写侧的"不写"省略这 8 位，**客户端会错位读**：把 type 的低位当成这 8 位，把 count 读成垃圾。

⇒ **服务端必须以读侧为准，写 7 字节。**

> ★ 这是"发送方和接收方是同一个二进制里的两个不同对象，参数不同"的典型案例。
> 174 卷的 `[obj+0x21]=ctor 第 2 参` 正好解释了这个差异的来源。

## §6 方法论

1. **★★★ 服务端应答格式以「客户端读取器」为准，不以「服务端/客户端写侧」为准。** 同一二进制里读侧 `+0x21=1`、写侧 `+0x21=0`，两侧不一致时**读侧赢**（因为断的是接收方）。
2. **★★ ctor 的参数差异会变成线上字节差异。** 必须看每一处 `call <ctor>` 前面 push 了什么。
3. **★★ 修复前先确认"旧代码到底做了什么"，别凭记忆写修复说明。** 我在 R10 上就写错了（旧代码是无条件回显）。
4. **★ 注释也是代码。** 四轮叠加的矛盾注释会让下一次判断从错误前提出发，必须收敛。
