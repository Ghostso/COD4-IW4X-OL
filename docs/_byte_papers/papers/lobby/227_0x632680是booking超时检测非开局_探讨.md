# 227 探讨 · 一条链错了六卷，只因为我从没读过"调用者传了什么"

## 一、这条链是怎么搭起来的

- **190 卷**：发现 `0x634B0D` 把 `ebx+0x7238` 挂到 `[this+8]`，推断是 StartGame 路径。
- **213 卷**：读 `0x632680` 开头 6 条 `cmp`，判定它是"开局闸门"，列了 6 道门。
- **214 卷**：发现 `0xDC69B0` = `"mmbook accepted"`，把它当成门6 的"期望值"，画出完整开局链。
- **215 卷**：确认它在 `dwRoomImp` vtable 里。
- **216 卷**：推断服务端必须补 u64，否则门4/5 不过。

**六卷、一套完整因果链、一个可直接指导改服务端的结论。**

## 二、这一轮我是怎么推翻它的

先从 226 卷开始找"`0x632680` 的调用点"。

第一次我扫 `call [reg+disp]` —— 找到 0。差点下结论"从没被调用"。

但统计整个 vtable 时发现 `+0x80` 以上 87 个槽全 0，觉得不对——修正扫描器（补 disp8），低槽变成 30 个有调用，高槽仍 0。

于是换思路：**扫两跳形式** `mov reg,[X+0x13C] / call reg`。找到 7 处。

其中只有 `0x632FC4` 的 `ecx` 是 `dwRoomImp`。

然后**读了它 push 的参数**：

```asm
0x632FAF  push 0xF
0x632FB1  push 0xDC69D4      ← 我没读过的那个地址
```

读 `0xDC69D4`：**`"mmbook timedout"`**。

## 三、差在哪里

门6 是：

```asm
0x6326DA  push 0xDC69B0        ; "mmbook accepted"
0x6326DF  call 0xC3C678        ; strcmp
```

**期望 `"mmbook accepted"`，实际传 `"mmbook timedout"`。**

⇒ 永远不等 ⇒ 永远走 timeout 分支。

**我 214 卷看到 `0xDC69B0` = `"mmbook accepted"` 时，
默认了"这就是调用者传的值"，从没去读调用者真正 push 的是什么。**

## 四、还有一处：门 4/5 恒真

```asm
0x632FBD  mov  ecx, [ebx + 0x3A048]   ; 参数1 ← 自己的字段
0x632FCA  push ecx
...
0x6326B9  cmp eax, [esi + 0x3A048]    ; 门4：参数1 == 自己的字段
```

**传进去的是自己的字段，再和自己比 ⇒ 恒等。**

所以我 216 卷说"服务端必须提供其 u64 让门4/5 通过"——**这个门根本不需要通过，它恒过**。

## 五、教训

**★★★ 看到 `strcmp(参数, 常量)`，必须两边都读：常量是什么、参数实际是什么。**

- 常量：`0xDC69B0` = `"mmbook accepted"` ✓ 我读了
- 参数：`0xDC69D4` = `"mmbook timedout"` ✗ **我从没读**

**★★★ "参数 == 自己的字段" ⇒ 该门恒真，不能当校验条件。**

**★★★ 六卷链能搭起来，是因为每一卷都只验证了"这一环看起来对"，没有回头验证"上一环的输入是哪来的"。**

## 六、现在的真实状态

`0x632680` = **booking 超时检测函数**：
- FrameUpdate 每隔一段时间调一次
- 超时就调它，参数 `"mmbook timedout"`
- 门6 恒不等 ⇒ 走 `0x632876`
- 门1/2 不满足 ⇒ 清 booking 状态（`0x6328EB`）

**"mmbook accepted" 这条成功路径，在当前 build 里没有调用点。**

⇒ **服务端推 `"mmbook accepted"` 不会触发开局。**
