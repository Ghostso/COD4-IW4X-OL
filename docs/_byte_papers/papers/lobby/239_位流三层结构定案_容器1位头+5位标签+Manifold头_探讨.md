# 239 探讨：为什么「50 位」骗过了三卷，以及位级对账的正确做法

## 判据

1. **位宽必须从「谁写、写几位」读出，不能从「总共几字节」反推。**
   我在 `0x625520` 上数出 `3/8/8/32` 四个 `push`，加了 4 次得到 51。177 卷得到 50，是因为它**只读了序列化器**、并且把某个 5 位标签算成 0（`+0x21==0` 时 `W_TAG` 是空操作）。两边都「自洽」，因为**两边看到的都是同一个序列化器，谁也没去看构造函数**。

2. **构造函数里的写，属于「同一次编码」。** 判据：`0xB778E0` 返回后 `[esi+0x1C]==1`（`0xB7797E`），而 `0xB77B10`/`0xB777C0` 的游标就是 `[esi+0x14]`/`[esi+0x1C]`。也就是说**构造函数写的 1 位进入了同一块 buffer、同一个游标**。这是「它在同一条位流里」的机器指令级证据，不是猜测。

3. **写侧和读侧对同一个头位的处理方式必须分别读。**
   - 写侧 `0xB778E0`：`push 1` → 无条件 `call 0xB777C0`
   - 读侧 `0xB779A0`：先 `0xB77710` 整块按位拷入，再 `push 1; call 0xB772E0` 读走那 1 位
   两边都是「1 位」，但**路径不同**（写是「写值」，读是「整块拷+读回 `+0x21`」）。如果只看写侧，会以为读侧会跳过；只看读侧，会以为写侧可能不写。

## 误区与自我推翻记录

- **第一版：以为 `0xB77B10` 的 `push 3` 是位宽。** 被 177 卷纠正过，这次复核仍然成立：`0xB77A70` 的 `push 0x1F` 是 `max`，`bits=bitwidth(max-min)=bitwidth(31)=5`。
- **第二版：以为 Manifold 就是 50 位，于是 7 字节。** 本卷推翻。我做的第一件事是写了个逐位仿真（`sim3.py`），发现 count=0 只有 41 位 —— **41 ≠ 50 ≠ 51**，三个数字都对不上，才回去找漏项，找到了构造函数那 1 位。
- **第三版：以为 `0xB779A0` 的 `cmp [ebp+0x10],0` 就是「是否带头」的开关，所以读侧可能不带。** 读完全函数发现：不管带不带，`0xB77A36` 那条无头分支**也先 `push 1` 写一位 0**，再整体写。所以**头永远在**，`[ebp+0x10]` 只决定「整体是拷贝还是重写」。
- **差点犯的错：用「50 和 51 都补到 7 字节」验证。** 这正是 178 卷被坑的地方。**总字节数对 ≠ 内部位宽对**。判据必须是**逐标签位数相加**。

## 方法论

- **只读序列化器 = 必漏容器头。** 一个「往缓冲区写」的函数，它的第一个写操作很可能是**在构造函数里**完成的（容量分配 + 头部）。查位流协议要同时读：构造函数（头）→ 序列化器（体）→ 发送器（外包装）。
- **「两个不同的总数却都对」是危险信号，不是安慰。** 41/50/51 三个数字里我对了两个（41 实测、51 相加），第三个（50）是旧卷的。**必须让仿真给出确定值，不能接受「两种都说得通」**。
- **`push imm` 先看它被谁消费。** `push 0x1F` 是 max 不是位宽；`push 3` 是 tag 值不是位宽；`push 1` 这次终于是位宽 —— 判据是**它最终进到 `0xB777C0` 的第 2 个参数**。
- **不对称要写下来。** 写侧「无条件写」/ 读侧「无条件读」看起来对称，但中间路径完全不同（重写 vs 拷贝+读回）。这种不对称往往是后来修 bug 的关键。
