# 182 · `dwRoomMessageStartGame` 逐字段定案：blob#1 是**运行时缓冲区**，不是硬编码地址

> 卷次：182（房间类 · StartGame 载荷结构定案）
> 方法：把 `0x625BE0` 每一个 `push N / call` 按序还原成"标签 + 值 + 数据来源"
> 结论：三个 blob 的**长度来源全部不同**，我们的实现只在长度上巧合对，**语义全错**。

---

## §0 客户端真实结构（`0x625BE0 StartGame::serialize`）

```
W_TAG(3)                             5 位
W_VAL(type, 8)                       8 位     type = [this+4]

-- blob #1 --
W_TAG(19)                            5 位
W_TAG(8)                             5 位
W_VAL(len1, 32)                     32 位     ★ len1 = [[this+8]+0x118]
W_VAL(data1, len1*8)               动态       ★ data1 = [this+8]+0x18

-- blob #2 --
W_TAG(19)                            5 位
W_TAG(8)                             5 位
W_VAL(8, 32)                        32 位     ★★ **硬编码长度 8**
W_VAL(val2, 64)                     64 位     ★★ **固定 64 位** = [this+8]+0x10

-- blob #3 --
W_TAG(19)                            5 位
W_TAG(8)                             5 位
W_VAL(0x10, 32)                     32 位     ★★ **硬编码长度 16**
W_VAL(val3, 128)                   128 位     ★★ **固定 128 位** = [this+8]+0x1CC
```

## §1 我们的实现错在哪

`build_startgame_payload` 现在写的是：

```python
w.write_tag(3)
w.write_data(bytes([3]), 8)
w.write_blob(addr_67)                              # 67 字节，自己拼的
w.write_blob(struct.pack("<Q", session_id_int))    # 8 字节
w.write_blob(security_key_16)                      # 16 字节
```

### 1.1 差异表

| 字段 | 客户端 | 我们 | 判定 |
|---|---|---|---|
| blob#1 长度 | `[[this+8]+0x118]`（运行时） | 硬编码 67 | ❌ 来源错 |
| blob#1 内容 | `[this+8]+0x18` 缓冲区 | 自拼 `bd_common_addr` | ❌ 内容可能错 |
| blob#2 长度 | **立即数 8** | 8 | ✅ |
| blob#2 值 | **W_VAL(64)** 固定 64 位 | 8 字节 = 64 位 | ✅ |
| blob#3 长度 | **立即数 0x10=16** | 16 | ✅ |
| blob#3 值 | **W_VAL(128)** 固定 128 位 | 16 字节 = 128 位 | ✅ |

★★ **blob#2 / blob#3 我们的实现是对的。blob#1 是错的。**

### 1.2 长度巧合

若 `len1 = 67`：

```
5 + 8 + (5+5+32+536) + (5+5+32+64) + (5+5+32+128)
= 13 + 578 + 106 + 170 = 867 位 = 109 字节
```

**与我们的 109 字节完全一致** —— 因为 len1 恰好也是 67。

⇒ **字节数对，但 blob#1 装的东西不是客户端要的。**

### 1.3 blob#1 应该是什么

`len1 = [[this+8]+0x118]`，`data1 = [this+8]+0x18`。

`[this+8]` 是 StartGame 消息对象的子对象。`+0x18` 是缓冲起点，`+0x118` 是长度字段（**0x118 - 0x18 = 0x100 = 256 字节容量**）。

★★ **这是一个 256 字节容量的变长缓冲区**，运行时填充。

**不是"本端地址"** —— 至少不能假定它就是 67 字节的 `bdCommonAddr`。

★ 这条需要看 `[this+8]` 那个子对象是什么类、`+0x18` 装什么，才能定。

## §2 位宽合计（一般式）

```
bits = 5 + 8
     + (5+5+32 + len1*8)
     + (5+5+32 + 64)
     + (5+5+32 + 128)
     = 45 + 42 + len1*8 + 42 + 42
     = 171 + len1*8

len1=67 → 171 + 536 = 707？
```

★ 等一下，重算：

```
5 + 8 = 13
blob#1: 5+5+32 = 42，+ len1*8
blob#2: 5+5+32 = 42，+ 64
blob#3: 5+5+32 = 42，+ 128
合计 = 13 + 42 + len1*8 + 42 + 64 + 42 + 128
     = 331 + len1*8

len1=67 → 331 + 536 = 867 ✓
```

**与 `verify9.py` 的 867 位一致 —— 算术没错，错的是 blob#1 的语义。**

## §3 结论

| 项 | 状态 |
|---|---|
| StartGame 三段结构（tag/len/val） | ✅ 定案 |
| blob#2 = 固定 8 字节 / 64 位 | ✅ 与我们一致 |
| blob#3 = 固定 16 字节 / 128 位 | ✅ 与我们一致 |
| **blob#1 = 运行时 256B 缓冲区前 len1 字节** | ⚠️ **我们硬编码了 67 字节地址，语义未确认** |
| 位宽公式 `331 + len1*8` | ✅ 定案 |

★ **本卷不修改代码** —— 因为 blob#1 到底该装什么，需要先定 `[this+8]` 的子对象类型。
盲目改成"256 字节零缓冲"会从"语义可疑"变成"确定错误"。

## §5 诚实边界

1. **`[this+8]` 子对象类型未定**（本卷只追到"它是子对象指针"）。
2. **`+0x118` 与 `+0x1CC` 的写点未追**。
3. **blob#2 的 `[+0x10]` 与 blob#3 的 `[+0x1CC]` 都是同一个子对象的字段** —— 说明三段都来自同一个子对象，这点值得注意。
4. 无真实样本。

## §6 方法论

1. **★★★ 「长度页」要追到"立即数还是内存读取"。** blob#2/#3 是 `mov dword[ebp+8],8` 立即数；blob#1 是 `mov edx,[eax+0x118]` 内存读取。**这一条就区分了"常量字段"和"运行时字段"。**
2. **★★ 三段 blob 来自同一个子对象（`[this+8]` 的 +0x10 / +0x18 / +0x1CC）** —— 说明它们是同一块状态的三个切片。
3. **★★★ 字节数一致不能证明语义一致。** len1 恰好等于 67 时两者都得 867 位/109 字节。这是第二次踩同类坑（180 卷 867/868 同理）。
4. **★★ 发现语义可疑时，先不改成"另一个猜测"，而是继续追来源。** 改错比不改更糟（181 卷教训）。
