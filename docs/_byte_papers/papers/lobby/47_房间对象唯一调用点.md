# ★★★★ 房间对象的唯一调用点：`0x7e9933`（启动初始化序列）

> 承接 `lobby/46`
> **追到了根：房间对象在启动时由一段固定初始化序列创建。**

---

## 1. 调用点上下文

```asm
0x7e9907  push 1
0x7e9909  call 0xb76d80        ; ①
0x7e990e  add esp, 4
0x7e9911  push 1
0x7e9913  call 0x6212c0        ; ②
0x7e9918  add esp, 4
0x7e991b  call 0x7fa4c0        ; ③
0x7e9920  call 0x7ef830        ; ④
0x7e9925  mov byte [0xe374650], 0    ; 标志清零 ⑤
0x7e992c  mov byte [0xe376c20], 0    ; 标志清零 ⑥
0x7e9933  call 0x639d00        ; ★★★ 创建房间对象 ⑦
```

**这是启动阶段的初始化序列，7 步依次执行。**

---

## 2. 全镜像只有一个调用者

```
call 0x639d00 : 1 处  [0x7e9933]
imm 引用    : 2 处  [0x7a1055f, 0x7a10573]
```

**⇒ `0x639d00` 只被调用一次，就在启动序列里。**

**⇒ 如果这段没执行，房间对象永远不会被创建。**

---

## 3. 那 2 处 imm 引用

```
0x7a1055f
0x7a10573
```

**两者都在 `0x7a1055f` 附近，间隔 0x14（20 字节）。**

**⇒ 很可能是一个跳转表/函数指针表的两项。**

**这两个位置可能是"另一个入口"（例如某个表驱动调用）。**

**需下一轮确认。**

---

## 4. 这解开了什么

**之前的所有疑问，现在有了统一答案：**

| 现象 | 解释 |
|---|---|
| `[0x82e13fc]` = 0 | **`0x7e9933` 这段没执行** |
| `room.startgame` 会崩 | handler 依赖这个对象 |
| MyEventHandler 实例 = 0 | 房间对象不存在，回调无从注册 |
| `[0x82E1518]` = 0 | 同上 |
| 大厅卡"战斗开始" | 整条房间链从未启动 |

**⇒ 所有"对象为 0"都指向同一个根：启动序列没跑到 `0x7e9933`。**

---

## 5. 为什么这段没执行

**三种可能：**

### A. 这段属于"某个模式"的初始化

`0x7e9907` 和 `0x7e9911` 都 `push 1`。

**参数 1 可能是"模式号"或"阶段号"。**

**⇒ 也许只在特定模式下才走到 `0x7e9933`。**

### B. 前面有异常/提前返回

**如果 `0x7e9909`–`0x7e9920` 里任何一个失败并返回，
`0x7e9933` 就不会执行。**

### C. 这段根本没被调用

**需确认 `0x7e98xx` 所在函数是否被调用。**

---

## 6. 判定方法（下一轮）

1. 找 `0x7e98xx` 所在函数的**起点**
2. 找它的**调用者**
3. 看调用者是否在启动路径上

**这是把"房间子系统为什么不启动"一路追到底的最后一步。**

---

## 7. 与 `.ff` 加密的呼应

**如果 `0x7e9933` 前面那几步（`0xb76d80` / `0x6212c0` /
`0x7fa4c0` / `0x7ef830`）里有一步依赖 `.ff` 里的资源，
而 `.ff` 解密失败 —— 那整条启动序列就断在这里。**

**⇒ `.ff` 加密和房间不可用，可能是同一根因的两端。**

**这条假设可以用"读那 4 个函数"来验证。**

---

## 8. 本轮总结

**房间逆向从"报文"一路追到"启动序列的第 7 步"：**

```
报文层：11/13 建房间(空) → 11/4 模板 → 6/14 mmstart(16字段)
命令层：25 个 room/party/match 命令 → handler 是 vtable 转发
对象层：[0x82e13fc] = 0
创建层：0x639d00（12 条指令）
调用层：0x7e9933（启动序列第 7 步，全镜像唯一）
```

**五个层次全部打通，只剩"这段启动序列为什么没跑"。**

---
