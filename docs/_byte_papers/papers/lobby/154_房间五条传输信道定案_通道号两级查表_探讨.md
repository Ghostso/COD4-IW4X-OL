# 154 · 探讨：一个 `push 0x13` 骗了我一整卷

> 配套论文：`154_房间五条传输信道定案_通道号两级查表.md`

---

## 一、153 卷那句话我写得太快了

153 卷我写：

> 「`0x7E7EE0`（`push 0x13` = 传输 type 19 = P2PInfo）等 6 个函数」

`0x13 = 19`，19 恰好是 45/5 卷记录的 **P2PInfo 类型号**，于是「19 = P2PInfo」看起来天衣无缝。**这就是错的开始：数字巧合 + 已有知识 = 假结论。**

真相是 `0x13` 是**通道号**，进 `0xE4E20C + 0x13*8` 查表。P2PInfo 是**消息类型号**（在消息体 `+4` 处），这两个数字**属于完全不同的两层协议**，撞在 19 上纯属巧合。

### 这个错误是怎么被抓住的

我对六条通道全部做了 `callers()` + `push imm` 提取，得到：

```
0x13 0x14 0x15 0x16 0x16 0x17
```

**「0x16 出现两次」不合常理**——如果 `push imm` 是消息类型号，两条不同的建包器（5 段 / 6 段）不该共用一个类型号，因为消息类型号与序列化结构是 1:1 的。

正是这个「不合常理」逼我去翻漏斗：`0x7FAA20` 的 `[ebp+8]` 直接进 `0x7FA800`，而 `0x7FA800` 第一件事就是 `mov eax,[ecx*8 + 0xE4E20C]`。

**⇒ 如果 `push imm` 是类型号，它不该被拿去当数组下标。**

这一条判据比任何寄存器追踪都硬：**一个值被当数组下标用，它就是这个数组的键，不管它在别处叫什么名字。**

## 二、「两级查表」是 Demonware 的指纹

```
通道号 --[0xE4E20C, stride 8]--> 类(0..5) --[0xE69CE0, stride 0x10]--> {25000,25000,2000,5}
```

这个形状我在 IW4X 里见过（`bdUDPConnection` 的 channel config），但按 AGENTS.md 的分级，**本地字节优先**——本卷的结论完全由 `0xE4E20C` / `0xE69CE0` 两张表的实际内容支撑，不依赖任何外部项目。

四元组 `{发超时, 收超时, 间隔, 重试}` 的解释是**从数值反推**的：
- `0x61A8 = 25000` 和 `0xEA60 = 60000` 是 ms 量级的整秒数
- `0x7D0 = 2000` 是 2 秒重发间隔
- 第 4 字段只有 5 和 10 两个值 → 只能是「次数」

**如果第 4 字段是超时，它不该只有 5/10 两个值。** 这是「值域证明语义」的一个实例。

## 三、类 5 那一行——我差点把两张表缝成一张

初稿我写了「类 5 = 四个指针 `0xDE1404/0xDE1420/0xDE1410/0xDE1428`」，理由是 `0xE69CE0 + 5*0x10 = 0xE69D30` 那行确实长这样。

**这是错的。** 两条硬证：

1. `0x7FA5CF cmp eax, 4 / ja 0x7FA570` —— **类号 > 4 直接跳过**。类 5 永远不会被索引。
2. 一级表 139 项穷举，**最大类号 = 4**（`0x58..0x5B`）。

那 `0xE69D30` 是什么？`0xC95B50` 这个函数：

```asm
0xC95B58  mov ecx, 0xE69D30
0xC95B60  mov dword ptr [0xE69F84], 0
0xC95B66  call 0xB91EC0                     ; 哈希表构造
0xC95B75  mov dword ptr [0xE69D30], 0xDE1404
0xC95B7F  mov dword ptr [0xE69D38], 0xDE1410
0xC95B92  mov dword ptr [ecx+0xE69D34], 0xDE141C   ; ← 注意是 0xDE141C 不是 0xDE1420
0xC95B9C  call 0xC42DE0                      ; memset [0xE69D50], 0x100
```

这是**另一张哈希表**（计数 `0xE69F84`、桶 `0xE69D50`、容量 `0x100`），只是**恰好紧接在 `0xE69CE0` 表后面 0x50 字节**。

### 教训：相邻 ≠ 同表

我犯的错是「地址连续 ⇒ 同一结构」，这在 `.rdata` 里是**最不可靠的推论**。正确做法：

> **先找写入者和读取者，再判断归属。** `0xE69CE0+i*0x10`（`i<=4`）由 `0x7FA83E`/`0x7FA5D4` 读；`0xE69D30` 由 `0xC95B50` 写、`0xC95B59/0xC95B77` 引用。两组代码互不相干 ⇒ 两张表。

这和 134 卷「`.tp3` 里向上找 `cc cc` 会撞进数据跳转表」是同一类陷阱：**地址相邻是假朋友**。

### 顺手挖到的 dvar：`dw_task_timing_overrides`

查 `0xE69CE0` 的写入者时发现 `0x7FA560`：

```asm
0x7FA593  push 0xDE1190                 ; "dw_task_timing_overrides"
0x7FA598  call 0x50BB90                 ; 读 dvar（字符串）
0x7FA5B6  push 0xDB0CA4                 ; "%d"
0x7FA5BF  call 0xC3EAE3                 ; sscanf 取「类号」
0x7FA5CF  cmp eax, 4 / ja               ; 类号必须 0..4
0x7FA5EE  push 0xDE11AC                 ; "%d,%d,%d,%d"
0x7FA5F4  call 0xC3EAE3                 ; 取四个值
0x7FA604  mov [esi+0xC], ecx            ; ← 写表！
0x7FA60F  mov [esi+8], edx
0x7FA61A  mov [esi+4], ecx
0x7FA628  mov [esi],    edx
```

**⇒ 通道类的四个超时/重试参数是运行时可被 dvar 覆盖的。**

这条比「类 5」重要得多：它意味着**如果服务端想调整超时行为，改 dvar 就够了**；也意味着**我们在实测里看到的超时值可能不是本卷读出的默认值**。

这是一个很好的「打通两个层」的例子：静态读表 → 发现写者 → 发现配置面。如果我只满足于「表内容是什么」，就永远不知道它是可配的。

## 四、0x17 用空回调，这是个强信号

五条通道里，**只有 0x17 的完成回调位是 `0x8435D0`（`C3`）**。

153 卷我已经确认 `0x8435D0` 是全镜像几百处共用的空桩。这里它出现在「完成回调」位置上，含义明确：

> **0x17 通道发出去就不管了。没有 ACK、没有重试、没有失败回调。**

对照 0x13/0x14/0x15/0x16 都有真实回调（`0x7E7FA0` / `0x7E8090` / `0x7E81D0` / `0x7E8210`），可以断定：

- **有回调 = 等对方确认（可靠传输）**
- **空回调 = fire-and-forget（可能带超时但不重试）**

再看 `0x7E83D0` 的调用者 `0x6384A0`：

```asm
0x6384B3  mov word ptr [ecx+0x290], 0    ; 清零两个房间标志字节
0x6384BC  call 0x7E83D0                  ; 通道 0x17 发出去
```

**先清标志、再发一次、不等回执** —— 这是「房间状态上报」的典型写法：本地状态已经改了，把新状态扔出去，服务端收到没收到都不影响本地继续跑。如果这条消息丢了，下一次状态变更会再带一次。

**这个模式解释了 138 卷「房间消息有时发得出有时发不出」的大半**：如果 0x17 这条 fire-and-forget 丢了，客户端不会重发，本地也不报错——从外部看就是「点了没反应」。

## 五、64 槽 × 15 秒硬截止

```asm
0x7FA84D  mov esi, 0xE56FFE0
0x7FA85E  cmp esi, 0xE5713E0
```

`(0xE5713E0 - 0xE56FFE0) / 0x50 = 64`。

`0x7FA640` 填槽时：

```asm
0x7FA6A5  add eax, 0x3A98     ; 15000
0x7FA6A9  mov [esi+0xC], eax  ; 截止时刻
```

**64 个槽 + 每条 15 秒** —— 这是「同时在途的包上限 64 个、每个最多活 15 秒」。

想想看：房间里有 12 个人、每人每秒发 2 条消息 = 24 条/秒。如果服务端全不回执，64 个槽在 2.7 秒内塞满。塞满后走 `0x7FA920` 分支——**不再分配新槽，直接原地调 `0x7FA640`？**

不，`0x7FA920` 是「找不到空槽」的路径，它绕过槽表直接构造参数再调 `0x7FA640`（`0x7FA958 call 0x7FA640`，传的是 `esi`=表尾）。这看起来是**复用最后一个槽**——也就是**队满时覆盖最旧的包**。

如果这个判断成立，那么：**房间里消息一多，旧包会被新包挤掉，服务端看到的就是「部分消息丢失」。** 这是一个可以实测的预测，但本卷不追（属实测范畴）。

## 六、`0x7E7D30` 的 100 × 0x60 是跨卷互证

```asm
0x7E7D39  push 0x2580              ; = 100 * 0x60 + 0x30 - ... 实际 0x2580 = 9600
0x7E7D3E  lea esi, [ebx+0x38]
0x7E7D44  call 0xC42DE0            ; memset
0x7E7D50  mov edi, 0x64            ; 100
0x7E7D62  add esi, 0x60            ; ★ 步进 0x60
```

`0x2580 = 0x60 * 0x64` 正好 100 项 × 96 字节。

而 153 卷我从**完全不同的路径**（`0x62ACD0` 的收件人过滤）得到：成员表基址 `+0x40`、**步进 0x60**、计数在 `+0x18`。

**两条独立路径给出同一个 `0x60`。** 这是本卷最踏实的一处——不是推理，是两处字节的巧合。

> 方法论：**同一结构常数从两条不相关路径得到相同值 ⇒ 结构假设成立**。这比任何单点证据都强。

## 七、我这一卷又差点犯的错

写 §四时我一度想写「0x17 = 房间离开」，因为「fire-and-forget + 清标志 + 0x6384A0 是 `0x638370` 附近」。

停下来查了一下：`0x6384A0` 的调用链上 `0x63` 段是**房间成员管理**（`dwInvitationImp` 在 `0x82E1404`）。所以 0x17 最可能是「成员信息变更广播」而不是「离开」。

**结论：本卷不猜 0x13..0x17 各自的业务语义。** 只写「通道号 — 发送函数 — 段数 — 回调」这条硬链，业务名留白。

135/136 卷的教训：**先起名后验证，一定会翻车。** 本卷就到此为止。

## 八、给下一轮的三个具体入口

1. **`0xE69D30` 那张哈希表的键值语义** —— `0xC95B50` 建表，`0xDE1404..0xDE141C` 四个指针做初值，`0xE69F84` 计数、`0xE69D50` 桶（容量 0x100）。
2. **`0x7FA920` 是否覆盖最旧槽** —— 看 `0x7FA640` 收到「表尾指针」时的行为，验证「队满丢包」假设。
3. **dvar `dw_task_timing_overrides` 的实际取值** —— 磁盘上查 `dw_task_timing_overrides` 在 config 里的默认值；这决定了上表 25000/60000/2000/5/10 是不是真的生效值。
4. **五条通道的业务名** —— 反查各发送函数的**上游**：`0x7E7EE0` ← `0x62DF84`（`0x62DEE0` 建连接后）、`0x7E7FD0` ← `0x633EEC`（房间状态机）、`0x7E8120` ← 六个房间状态函数。这三条上游分别对应「入房 / 状态同步 / 状态变更」，但要按 150 卷的 vtable 表逐条对上才敢写。
