## 一、上一卷留下的方向是错的

232 卷 §6 边界 1 我写了：

> 「这 9 个 svc 一个都不命中 `0xB78C10` —— 它们可能走 `0xB78Bxx` 兄弟函数或不同封装。
> **下一步：扫 `0xB78C10` 前后 0x400 字节内的同类函数**」

**实际答案在 `0xBA72C0`，相隔 `0xBA72C0 - 0xB78C10 = 0x2E6B0` = 190,128 字节。**

我的假设是「同一模块的函数会挨着」。这个假设在这份二进制里不成立 —— `0xB78C10` 是一组极简 setter 的成员（旁边 `0xB78C40 mov ecx,[ecx+0x44]; jmp 0xBA07F0` 这种 thunk），而 `0xBA72C0` 是带 SEH + 分配 + 校验的"重"函数，编译器把重函数放到了远处。

### 正确的判据

不该找"地址邻近"，该找**函数签名**：

```
特征：函数体内有 连续两字节写 [esi+0x1C] 和 [esi+0x1D]
     且 0x1C/0x1D 的值分别来自 [ebp+8] / [ebp+0xC]
```

我实际用的搜索是「`call 0xB75E00`(writeN,1) 后跟 `call 0xB76620`(u8)」，只命中了 `0xB78C10` 一个 —— **因为 `0xBA72C0` 根本不调用这两个写器**（它把 svc/task 存进对象字段，真正的写字节发生在后续 `Append/Serialize` 里）。

**⇒ 连"函数签名"这个判据也不对，因为两个函数的实现方式不同：**
- `0xB78C10`：**立即写**（直接 writeN + u8）
- `0xBA72C0`：**先缓存**（存 `+0x1C/+0x1D`，稍后序列化）

我是靠 `0xB86AEE` 处 `push 0x46 / push 0x50 / call 0xBA72C0` 这个**已知样本反查**才找到的 —— 不是靠扫描。

## 三、push 顺序骗了我一次

第一次解析，我按 push 出现顺序读：

```
push 0x80000   → 我以为是 svc?
push 0x400     → 我以为是 task?
push 0x46      → 我以为是 ...
push 0x50      → 我以为是 ...
```

得到一堆 `svc=0x400`、`task=0x1024` 的垃圾。

直到我读了函数体：

```asm
0xBA7306  mov dl, [ebp + 8]        ; 第 1 个参数（最后 push 的）
0xBA7309  mov [esi+0x1C], dl
0xBA730C  mov dl, [ebp + 0xC]      ; 第 2 个参数
0xBA7318  mov [esi+0x1D], dl
```

**`[ebp+8]` 是最后 push 的那个**（x86 从右往左压栈）。所以：

```
push 0x80000 → [ebp+0x14] (第4参)
push 0x400   → [ebp+0x10] (第3参)
push 0x46    → [ebp+0x0C] (第2参 = task)
push 0x50    → [ebp+0x08] (第1参 = svc)
```

**⇒ `svc=0x50`, `task=0x46` = `80/70` ✅**

★ **这条和 232 卷的「参数顺序必须语料交叉」是同一类：push 顺序 ≠ 参数顺序 ≠ 字节顺序，三者都不同。**

## 四、两个新 svc：139 和 191

我挖出了 `svc 139 (0x8B)` 和 `svc 191 (0xBF)`。**在 232 卷的语料覆盖表里，这两个数字根本不存在。**

这说明一件事：**语料（6848 条，来自登录 + 房间流程）远不是完整的协议面。**

对照：
- 语料覆盖 **17 个 svc**
- 代码侧覆盖 **19 个 svc**（多 139、191）
- 服务端实现了 **31 个 (svc,task)**，代码侧有 **86+ 个**

★ **所以「40.4% 未实现」这个数字是下限，不是上限。** 真实的"没有实现的功能面"远大于 40.4% —— 只是客户端在这些流程里没走到。

## 五、服务 3：21 个独有 task，最大的盲区

`svc 3` 代码侧有 24 个 task，语料只有 3 个（46/48/53）。

21 个没见过：`30,31,32,33,34,35,36,37,38,47,50,51,52,57,63,64,65,66,91,92,128`

**这是全大厅最大的单点盲区。** 而且注意到：`0xB921BE / 0xB922DE / ... / 0xB92C2B` 这些调用点**连续排列**，说明它们是一组同构的构造器（可能是同一类对象的不同字段查询）。

★ **下一册的第一优先不是"填 40.4%"，而是先搞清 svc 3 是什么服务。** 21 个 task 的密集度说明它是核心服务。

## 六、一句话

**我猜"兄弟函数在附近"，它隔了 190KB；我猜"和 `0xB78C10` 一样调 writeN+u8"，它的实现完全不同（先缓存后序列化）。两次全靠 `80/70` 这个已知样本反查才找到。所谓"扫描穷尽"，在没有至少一个已知实例时，是不成立的。**
