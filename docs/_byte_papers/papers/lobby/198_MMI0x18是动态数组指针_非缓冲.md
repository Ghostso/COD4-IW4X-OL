# 198 · ★★★ `MMI+0x18` 定案：它是**动态数组的指针**（`+0x18`ptr / `+0x1C`size / `+0x20`cap）

> 卷次：198（房间类 · P1 最终答案）
> 方法：`0x4F4480` 是 MMI 的**析构函数**，它对每个动态数组做"遍历→free→清零"三连
> 结论：**`+0x18` 不是 256 字节缓冲，是一个动态数组的指针**；`+0x118` 才是那个 256B 缓冲。

---

## §0 析构函数 `0x4F4480` 完整

```asm
0x4F4480  push ebx / push esi / mov esi,ecx / push edi
0x4F44A5  lea ecx, [esi+0xD8] / call 0xB76E50      ; 析构子对象 @ +0xD8
0x4F44B0  lea ecx, [esi+0x24] / call 0xB76E50      ; 析构子对象 @ +0x24

; ---- 动态数组 #1：元素大小 0x84 ----
0x4F44B8  mov eax, [esi+0x20]      ; ★ count
0x4F44BB  mov edi, [esi+0x18]      ; ★ ptr
0x4F44BE  test eax,eax / je
0x4F44C2  mov ebx,eax
0x4F44C4  mov ecx,edi / call 0xB76E50   ; 逐个析构（步进 0x84）
0x4F44CB  add edi, 0x84
0x4F44D1  dec ebx / jne
0x4F44D4  mov eax,[esi+0x18] / push eax / call 0xB74240   ; free(ptr)
0x4F44DF  mov dword [esi+0x18], ebx(=0)    ; ★ ptr = 0
0x4F44E2  mov dword [esi+0x20], ebx(=0)    ; ★ count = 0
0x4F44E5  mov dword [esi+0x1C], ebx(=0)    ; ★ cap = 0

; ---- 动态数组 #2：元素大小 4 ----
0x4F44E8  mov eax, [esi+0x10]      ; ★ count
0x4F44EB  mov edi, [esi+0x08]      ; ★ ptr
0x4F44F3  jbe
0x4F44F5  mov ebx,eax
0x4F44F7  mov ecx,edi / call 0xB75AC0   ; 逐个析构（步进 4）
0x4F44FE  add edi, 4
0x4F4501  dec ebx / jne
0x4F4504  mov ecx,[esi+0x08] / push / call 0xB74240   ; free(ptr)
0x4F4511  mov dword [esi+0x08], ebx(=0)    ; ptr = 0
0x4F4514  mov dword [esi+0x10], ebx(=0)    ; count = 0
0x4F4517  mov dword [esi+0x0C], ebx(=0)    ; cap = 0
```

## §1 两个动态数组的布局

| 数组 | ptr | size | cap | 元素大小 | 元素析构 |
|---|---|---|---|---|---|
| **数组 A** | `+0x18` | `+0x20` | `+0x1C` | **`0x84`** = 132 | `0xB76E50` |
| **数组 B** | `+0x08` | `+0x10` | `+0x0C` | **`4`** | `0xB75AC0` |

★★★ **`+0x18` 是"元素 132 字节的数组指针"，不是缓冲！**

### 1.1 这解释了 197 卷的拷贝构造

`0x806A70` 复制 `+0x18` 时只 `mov` 4 字节 —— **复制的是指针**（浅拷贝），不是 256 字节。

⇒ 197 卷说"`+0x18` = 256B 缓冲起点"**不准确**。正确说法：
**`+0x18` 是一个 `{ptr, size@+0x20, cap@+0x1C}` 动态数组，元素 132 字节。**

---

## §2 那 `+0x118` 是什么

★★ **`+0x118` 在低区之外（`0x118 < 0x120`，仍在低区但不在上面两个数组里）。**

从 `0x625CE0`：
```asm
0x625D45  mov dword [ecx+0x118], edx    ; edx = 读到的声明长度
```

★ 而 `0x625D2C add eax,0x18` —— **目标缓冲是 `[this+8]+0x18` = MMI+0x18**。

★★★ **矛盾**：`MMI+0x18` 是"数组指针"，`0x4F3EB0` 却把 255 字节数据写进去？

### 2.1 唯一解释

★★ **`0x4F3EB0(buf, &cap)` 的 `buf` = `MMI+0x18`，而 `cap` 是指向 `MMI+0x118` 的指针！**

回看 `0x625CE0`：
```asm
0x625D18  mov dword [ebp+8], 0xff      ; ★ 局部变量 cap = 255
0x625D28  lea edx, [ebp+8] / push      ; &cap（栈上）
0x625D2C  add eax, 0x18 / push         ; buf = MMI+0x18
0x625D30  call 0x4F3EB0
0x625D3F  mov edx, [ebp+8]             ; 读回 cap（= 实际长度）
0x625D45  mov [ecx+0x118], edx         ; 存到 MMI+0x118
```

★★★ **`cap` 是栈上的局部变量，不是 `MMI+0x118`！**

⇒ **`MMI+0x18` 确实被当作"256 字节缓冲"使用**，
   而 `MMI+0x118` 只是**存"上次读到的长度"的一个独立字段**。

★★ **这意味着 `dwRoomMessageStartGame` 复用 `MMI+0x18` 这块内存做临时缓冲 ——
但 `MMI+0x18` 本身是"元素 132 字节的数组指针"！**

⇒ **这是类型混淆/复用**：同一块内存，MMI 当数组用，StartGame 当缓冲用。

---

## §3 这是否合理

★ 在 C++ 里这**不合理**（类型不匹配），除非：

1. **`MMI+0x18` 实际是个 `union`**
2. **或者 `0x625CE0` 是死代码**（`clientState==0` 时才跑，如 190 卷所述）
3. **或者我算错了 `[this+8]`**

★★ 结合 190 卷结论：`0x634B0D` 那条路径**只在 `clientState==0`（未进大厅）时跑**。
⇒ **它是"垃圾数据吸收"路径** —— 收到 StartGame 但还没进大厅，就读进一个临时缓冲然后丢弃。

⇒ **`+0x18` 在这里被当缓冲用，是"反正要丢弃，随便找块内存"**。

## §6 方法论

1. **★★★ 析构函数是"字段表"的第二个最佳来源**（第一个是拷贝构造）。它揭示 ptr/size/cap 三件套。
2. **★★ `{ptr, size, cap}` 的判定：`free(ptr)` 后三个字段连续清零。** `0x4F44DF/E2/E5` 就是。
3. **★★★ 元素大小从 `add reg, N` 的步进读出。** `add edi,0x84` ⇒ 元素 132 字节。
4. **★★★ 同一块内存被两种类型使用 ⇒ 优先怀疑"死代码路径"或"union"。** 结合 190 卷的 `clientState==0` 条件，判定为死代码路径。
