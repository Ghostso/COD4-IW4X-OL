## §0 结论

1. **★ 服务 71 = 腾讯遥测 / TLog 服务**（不是"未知上传"）。证据三重：
   - 字符串 `tencent.tlog`（VA `0xDC7148`，其邻串 `0xDC7124`=`tencent.verif*`、`0xDC7134`=`tencent.sanit*`）；

2. **★ 帧格式（两个方向一致）**：`u32 declared ‖ 0x86 ‖ service ‖ 0x03 ‖ task ‖ payload`，其中 `declared = 3 + len(payload)`（3 = service+ver+task 三字节，**不含 0x86**，也不含 4 字节长度本身）。证据：台账 `lobby_server.py:775-777` 与日志 `declared=paylen+3`（例：71/4 `declared=84, payload(81)`；全量 5851/5851 命中，见 §1）。

## §1 帧与 payload 分层

```
帧   = [u32 declared][0x86][service u8][ver u8][task u8][payload]
payload = ByteBuffer 值流：  <tag><value>*

其中 declared = 3 + len(payload)        # 3 = service‖ver‖task
日志证据：71/4 declared=84 且 payload 打印 81 字节 → 84-81=3 ✔
         71/2 declared=19  且 payload 打印 16 字节 → 19-16=3 ✔
         4/4  declared=28  且 payload 打印 25 字节 → 28-25=3 ✔
台账证据：lobby_server.py:892  frame = pack("<I",declared)+bytes([0x86,service,0x03,task])+plain
```
- 该分层在**全部未被日志截断的记录**上 100% 成立：本卷脚本 `extract.py` 逐条核对 `declared==paylen+3`，**5851 条命中 / 0 反例**；另 1794 条因日志把 payload 打印上限截到 96B（`paylen=96 < declared-3`）而**无法核对长度**（不是反例）。

## §2 payload 值流的类型表（带**客户端读取函数地址**）

**读取入口 `0xB76310(reader, expectedTag)`**：读 1 字节，与 `expectedTag` 比较；不等则调 `0xB773D0` 打印名字表后失败；读到 `0x16` 走 P2P 子类型特例（`0xB76354 cmp ecx,0x16 / jne 0xB76430 / 0xB76433 cmp ecx,eax; sete bl`）。**这是全协议唯一的值类型校验闸门。**

| tag | 类型 | 值宽 | 客户端读取函数 | 证据（函数体关键行） |
|---|---|---|---|---|
| 0x01 | bool | 1 | `0xB76850` | `0xB76877 cmp byte[ebp-1],0 / setne cl / mov [edx],cl` |
| 0x03 | u8 | 1 | `0xB76890` | `0xB76895 push 3` + `0xB768B9 mov byte[ecx],dl` |
| 0x06 | u16 | 2 | `0xB768D0` | `0xB768D5 push 6` + `0xB768FA mov word[ecx],dx` |
| 0x07 | i32 | 4 | `0xB76910` | `0xB76915 push 7` + `0xB76939 mov [ecx],edx`（台账/`codol_crypto.py:262` 明示 7=i32）|
| 0x08 | u32 | 4 | `0xB761E0` | `0xB761E5 push 8` + `0xB76209 mov [ecx],edx` |
| 0x09 | i64 | 8 | `0xB76950` | `0xB76957 push 9` + 8B 拷贝（`mov [eax],ecx;[eax+4],edx`）|
| 0x0A | u64 | 8 | `0xB769A0` | `0xB769A7 push 0xa` + 8B 拷贝 |
| **0x0D** | **f32** | 4 | `0xB769F0` | `0xB769F5 push 0xd` + `0xB76A13 fld dword[ebp-4] / fstp [ecx]` ← **本 build 独有，ol-mod 类型表无此项** |
| 0x10 | string | NUL 结尾 | `0xB76A30`(定长缓冲) / `0xB76A90`(动态) | `0xB76A34 push 0x10`；`0xB76A50` 逐字节读到 0 |
| 0x13 | blob | `13 08 <u32 len> data` | `0xB76AF0`(定长) / `0xB76B60`(分配) | `0xB76AF5 push 0x13` → `0xB76B11 call 0xB761E0`（**内层就是 tag=0x08 的 u32 长度**）→ `0xB76B35 call 0xB75E80` 读 len 字节 |
| 0x6C | array | `6c 08 <u32 byteLen><u32 count><count×u32>` | 依据 `codol_crypto.py:319 u32array`（写侧一致） | 28/4 实测 `byteLen=508=127×4,count=127` 自证 |
| 0x17 | 可选 u32 包装 | `17 08 <u32>` | `0xB76BE0` | `0xB76BE5 push 0x17` 后再调 `0xB761E0`（tag=8）|
| 0x00 | 终止 | 1 | 解析循环终止 | 各 payload 尾部 |

> ★ `blob = "13 08 <u32 len> data"` 的 `08` **不是第二个标签语义，而是"长度字段"自身的 tag（u32）**——由 `0xB76AF0` 先 `push 0x13` 校验、再 `call 0xB761E0`（其首行 `push 8` 校验）两跳结构直接证明。

## §3 71/2 与 71/4 逐字节

**71/2（n=75，1 种）**
```
10 4d 37 2d 45 38 53 36 43 6c 69 65 6e 74 00 00
└tag10└"M 7 - E 8 S 6 C l i e n t"──────────┘NUL end
```
= `str "M7-E8S6Client"`。字面量 `M7-E8S6Client` @ VA `0xE7B6310`，默认写者函数 `0x4A4490`（`0x4A4498 push 0xe7b6310`）。语义=客户端/机器名上报。

**71/4（n=180，1 种，恒 81B）**
```
13 08 10 00 00 00  6e 51 6c 6f 50 30 6f 43 56 57 52 36 52 44 4a 53   ← blob16 "nQloP0oCVWR6RDJS"
13 08 10 00 00 00  2b×16                                              ← blob16 "++++++++++++++++"
08 9e cb e6 01                                                        ← u32 0x01E6CB9E
13 08 00 00 00 00                                                     ← blob0
13 08 00 00 00 00                                                     ← blob0
10 44 34 2d 39 33 2d 39 30 2d 31 38 2d 35 35 2d 31 30 00 00           ← str "D4-93-90-18-55-10"
```
- blob1 从**可写全局** `0xDB6B68` 读出 16 字节（`0x4A6387 mov edx,[0xdb6b68]` ×4 次读到 `[ebp-0x24..-0x18]`），初值即 ASCII `nQloP0oCVWR6RDJS`（`0xDB6B68` 处 16B + 4×0x00）；即"机器 GUID 全局缓冲"，运行时可能被覆盖。
- blob2 由代码内**立即数**生成：`0x4A63AD mov eax,0x2B2B2B2B` 写 `[ebp-0x14..-8]` = 16 个 `'+'`。
- 设备号字符串 `D4-93-90-18-55-10` @ `0x849B504`（`0x4A633C push 0x849b504`、`0x4A6398 push 0x849b504`）。
- 构造器函数 `0x4A6280`（`0x4A6362/0x4A63DF call 0xB897B0`、`0x4A636F call 0x7F5E40`）。
- ⇒ 71/4 = **完全由常量拼装的客户端指纹**（不含运行时随机项），180 条 100% 逐字节相同，与"1 种 payload"完全吻合。

## §6 边界（静态不可达 / 未闭合）

- **71/15 压缩批内容**：日志把 payload 截断到 96B，`13 08 <u32 len>` 的 len 常 >90 ⇒ 无完整 zlib 流可解。**已穷尽**：全库日志中 71/15 无一条 len≤90；`0x78 01` 头已确认。→ 只有拿到完整帧（>96B 打印）才能解压。**这不是"需运行时"，而是"日志本身的打印上限"**（见 225 卷 §5 边界）。
- **逐 task 的专属构造器地址**：71/2、71/4 已定位（`0x4A4490`/`0x4A6280`）；71/3/7/9/10/11/13/18/20 的**专属"发起"函数未逐个钉死**——它们共用同一批**通用写入/读取原语**（§2 表 + 225 卷写侧），"发起"多由通用 `send(service,task,payload)` 通道完成，静态上未出现"一个 task 一个函数"的形态。已穷尽手段见 225 卷 §3。

## §7 方法论

1. **先分层再下结论**：帧头（`declared=payload+3`）与 payload（Demonware 值流）是两层，混在一起会算错长度（本卷两处都逐条核对过）。
2. **一个 `push imm` 不一定是"类型号/位宽"**：`13 08 <u32>` 的 `08` 是**长度字段自身的 tag**，靠"读侧两跳（`0xB76AF0`→`0xB761E0`）"才分清。
3. **读侧函数地址是"类型表"的最强证据**：11 个读取器 1:1 对应 11 个 tag，比任何字符串/注释都硬；且能反查出**本 build 独有的 `0x0D=f32`**（台账类型表没有）。
4. **常量 payload 要去找"常量来源"**：71/4 恒 81B 且逐字节相同 ⇒ 直接去搜字面量，命中 `nQlo…`@`0xDB6B68`、`D4-93…`@`0x849B504`、`0x2B2B2B2B` 立即数，一眼看出"全是常量"。
5. **口径必须带分母**：事件名统计写"9（分母 355）"，而不写"只有 9 种"，避免与旧口径对撞时无法对账。
