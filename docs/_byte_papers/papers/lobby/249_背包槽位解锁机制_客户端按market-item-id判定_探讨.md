## 三、顺理成章的 5 步

有了函数名，剩下是机械的：

```
RTTI 名 → COL → vtable → 实现函数 → 读全局 → 初始化 → 拥有检查
```

每一步都是"地址 → 下一条地址"，没有判断，没有猜：

| 步 | 得到 |
|---|---|
| RTTI `0xE6C3C8` → COL → vtable `0xDC8A78` | impl = `0x7D7470` |
| 反汇编 `0x7D7470` | index3 → `[0x84ABB38]`，index4 → `[0x84ABB3C]` |
| 读全局 | **60027 / 60028** |
| 全局写点 `0x80A4C0` | 来自配置名 `"loadout4enable"`/`"loadout5enable"` |
| `0x7DBB60`（解锁判定） | `0x5E3760` 查已拥有列表 |

**半小时拿到确定答案，比 248 卷纠结一整轮还快。**

## 四、一个容易看错的坑

`0x7DBB60` 的两条出口：

```asm
0x7DBBA2  xor eax, eax        ; eax=0, ZF=1
0x7DBBA6  test al, al
0x7DBBA8  sete al             ; al = 1     ← 返回 1

0x7DBBB0  mov eax, 1          ; eax=1, ZF=0
0x7DBBB7  test al, al
0x7DBBB9  sete al             ; al = 0     ← 返回 0  ！
```

**`mov eax,1` 之后的 `sete al` 返回 0，不是 1。**

如果我不逐条算，只看到 `mov eax,1` 就以为"这条返回真"，就会把**解锁判定整个读反**。

★ 这和 231 卷「`reply+5` 判据顺序读反」是同一类：**`sete`/`setne` 的语义取决于上一条 `test` 的操作数**，不能只看助记符。

## 五、这一卷更正了 248 卷

248 卷我说根因是：

> 两个 SKU 同指 item 121，非 stackable 分支只授予一次 ⇒ 第 5 个背包拿不到

**这一卷证明那是表象**：

- 真实根因是**两个槽位各自要一个不同的 item id**（60027 / 60028）
- 而服务端**两个都给了 121** ⇒ 两个 item id **都查不到**
- 所以不只是"第 5 个拿不到"，而是**第 4 个也拿不到**

★ **248 卷的结论方向是"数量累加"，249 卷是"id 映射"。两者都能解释"买 242 没反应"，但只有后者能解释"买 241 也没用"。**

## 六、还留着一个更麻烦的可能

解码链里有一句：

```asm
0x0080A4DB  xor cx, ax      ; cx ^= 指针低 16 位
```

**如果配置存储的地址不是静态的，那 60027/60028 只在当次会话成立。**

我在论文 §8 把这条列为**待确认**，没有当成结论用。

★ 判断依据是：`0x660B00` 最终返回的是**表项指针**（`[0x779583C] + idx*0x28 + 8`）—— 表是静态的，所以指针静态、解码确定。**但这只是推断，不是验证。**

**写论文时我把它标成"需确认"，而不是"已确定"。**
