## 一、这一轮真正解决的两个问题

### 1.1 `kind` 到底是什么

我之前一直模糊地说"`kind=4` 是真发"。这一轮读到了函数头：

```asm
0x62C876  cmp dword [ebp+0x14], 4
0x62C881  jne 0x62C99F
```

**一行指令,语义完全确定。** 而且 `kind != 4` 的分支也读全了：

| kind | 行为 |
|---|---|
| 4 | 构造 bdByteBuffer → `0x7E8300` **真发** |
| ≠4 | 序列化 → 插入 `+0x3A0D4` 链表 **入队** |

### 1.2 三条入队路径

```
0x62C5A0          → +0x3A098（哈希表）  ← 房间动作用
0x62C800          → +0x3A0D4（链表）
0x62C870(kind≠4)  → +0x3A0D4（链表）  ← 0x62CA60 包装
```

**三条独立的入队路径，我原以为只有一条。**

## 二、一个强收敛点：`0x7E8300` 只有一个调用者

```
0x7E8300（网络发送）全镜像调用者: [0x62C93D]
```

**⇒ 所有出网流量必经 `0x62C870(kind=4)`。**

★★★ **这条约束极强**：如果房间动作要出网，它必须在某个时刻走到 `0x62C870(4)`。
而我把 `+0x3A098` 的**全部 5 个访问点**（构造/入队/遍历×2/析构）都读了，**没有一处调用它**。

★ 同样地，`0x62C5A0` 的**全部 4 个调用者**都是房间动作虚函数，而它体内只有"序列化+插入"。

## 三、所以剩下的未知变得非常精确

之前是"房间按钮为什么不工作"——一片黑。

现在是：

> **`+0x3A098` 里的消息，如何变成 `0x62C870(4)` 的调用？**

★ 这是个**可以证伪**的问题。只有几种可能：

| 可能 | 特征 |
|---|---|
| (a) 经由 `0x6330xx` 的分发 | 但我在匹配分支只看到"摘链+释放" |
| (b) 经由某个我还没识别的消费者 | 需要继续扫 `0x656A10` / `0x654D60` 的调用者 |
| (c) **设计如此**：本地总线只做本地状态同步，出网由服务端驱动 | 与"服务端不下发⇒客户端无动作"一致 |

★★ **(c) 值得认真对待** —— 因为用户描述的症状是"按钮点击后本地状态变了（加入阵营按钮变灰）但服务端不知道"。
**这正是"本地总线生效、网络未发送"的表现。**

## 四、我这一轮的方法论收获

### 4.1 函数头的 `cmp` 比正文更有信息量

我前面几轮都在读正文,猜 `kind` 的含义。**读开头两行就定了。**

### 4.2 "唯一调用者"是最好的收敛工具

`0x7E8300` 只有 1 个调用者 ⇒ 出网路径唯一 ⇒ **排除法变得极强**。

★★ 如果一开始就查这个，能省两轮。

### 4.3 容器要把"生命周期"看全

`+0x3A098` 的访问点是：构造 → 入队 → 遍历 → 遍历 → **析构**。
**五个点都看了，才敢说"没通向网络"。**

## 五、下一步的唯一目标

**确认 `+0x3A098` 的遍历（`0x6330xx`）到底做什么。**

具体做法：
1. 反汇编 `0x632F00..0x6331C0` 全段，确定函数边界
2. 逐条读匹配分支（`0x633131`..`0x633176`）
3. 如果确实只有"摘链+释放" ⇒ 走 (c)：**设计如此，本地总线不出网**

★ 如果是 (c)，那么**用户的房间按钮问题就不在客户端**，而在：
- 服务端没下发驱动消息（上游），或
- 客户端的动作应该触发别的路径（需要重新审视 `0x6301A0` 的调用上下文）
