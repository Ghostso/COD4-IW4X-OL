# 125 · `8/3` 档案上传 = zlib 压缩的 32KB 固定档案块

> 项目：使命召唤OL 大厅（build 1649370 / 3.19）
> 前卷：`104`（`8/3` 结构 u32×4 + blob + i32×125）、`114`（`8/3`=档案上传）、`09`（blob=zlib）
> 本卷：**第一次真正解压 `8/3`**，确认它是**固定 32768 字节的档案块**，并定位其顶层结构
> 证据：`m83_zlib.txt`、`m83_profile_structure.txt`；旁证 `m65_push_ctx.txt`（zlib 错误表）

---

## §0 结论

| 项 | 结论 |
|---|---|
| `8/3` blob 是否 zlib | ✅ **`78 01`，84/84 解压成功** |
| 解压后长度 | ✅ **恒为 32768 字节**（84/84 完全一致） |
| payload 里的 u32 ↔ 解压首 u32 | ✅ **payload u32 = `0x1b97d354` = 解压 `dec[0:4]`**（84/84） |
| 32KB 内容 | **固定模板**（`[12:3862)` 有 3850 字节恒定）+ 穿插的 **2 字节可变字段**（计数器/时间戳） |
| 含 CODOID / ASCII | ❌ **0 个**（纯二进制数值档案，非文本） |
| zlib 是否真在客户端 | ✅ 镜像里有 zlib 完整错误表（`invalid window size` / `oversubscribed … tree` / `incompatible version`） |

★★ **一句话**：`8/3` 不是"不透明 blob"，是 **zlib(32768) 的档案块**。它**每次解压都是同样 32768 字节**——说明客户端把档案序列化成**固定大小的结构体**再压缩上传。payload 里的一个 u32 存的是解压首 u32（= 内容 ID/校验）。

## §1 为什么"固定 32768"极重要

`m83_zlib.txt`：84 条 `8/3`，每条的 blob 长度不一（761~1262 压缩后），但**解压后统统是 32768 字节**。

★★ **32768 = 32KB = 一个固定大小的结构体序列化结果。**

如果它是"变长的字节流"，解压后长度会随内容变。**长度恒为 32768 ⇒ 它是一个定长结构的内存 dump**：
- 客户端有一个固定 32KB 的档案结构（大概率是 `sizeof(profileStruct) == 32768` 的一个内存块，或一个固定槽数组）；
- 序列化 = 直接把这块内存 zlib 压缩。

★ 这也解释了为什么 payload 长度 1413~1914 波动：**压缩率随内容变**（数值档案压缩率不固定），但**解压后 32KB 不变**。

## §2 payload 顶层结构

`m83_zlib.txt` 首样本（payload 1416B）：

```
08 05 00 00 00       tag08 + u32 5            ← 版本/类型?
08 01 00 00 00       tag08 + u32 1
08 01 00 00 00       tag08 + u32 1
08 54 d3 97 1b       tag08 + u32 0x1b97d354   ← = 解压 dec[0:4]（内容ID/校验）
13 08 fc 02 00 00    blob(0x2fc=764)          ← zlib → 32768B
78 01 …              zlib(deflate)
…                    （blob 之后还有 i32×125 等，见 104 卷）
```

★ **payload 里的 `0x1b97d354`（第 4 个 u32）== 解压后的首 4 字节**——这是 `104` 卷「u32#4 ↔ blob 内容 ID」的**第一次直接证据**（此前只知"一一对应"，本卷给出生效机制：它就是解压首 u32）。

★ 注意 TLV 偏移：每个值前有 `08` 标签，所以 u32 在偏移 1/6/11/16（不是 0/4/8/12）——**读 TLV 时别按裸 u32 偏移取**。

## §3 32KB 档案块的内部形态

`m83_profile_structure.txt`——把 84 条解压结果逐字节比对（同一账号，故大部分相同）：

### 3.1 恒定/可变区段（1160 段）

```
[    0..    5) VAR     ← 前 5 字节随样本变（含 dec[0:4]=0x1b97d354 等）
[    5..    8) CONST
[    8..   12) VAR
[   12.. 3862) CONST   ← ★ 3850 字节完全恒定（大模板）
[ 3862.. 32768)  CONST 为主, 穿插大量 2 字节 VAR 槽
```

★★ **`[12:3862)` 这 3850 字节是铁板一块的模板**——档案的前段是**固定结构**（配置/默认值），后段（3862..32768）是**"模板 + 每格 2 字节可变字段"**（计数器/时间戳/状态），共 1160 个区段。

### 3.2 非零 u32 值分布

首样本非零 u32 Top：`0x1`(239) / `0x10000`(230) / `0x1000000`(120) / `0x100`(62) / `0xea61*`(24-25) / `0xea8c*` / `0xeaea*` / `0x2711*` / `0x272c*` / `0xffffffff`(14)…

- `0x1`/`0x100`/`0x10000`/`0x1000000` 是**单位标志/移位值**（每字节位置不同）；
- `0xea61`/`0xea8c`/`0xeaea`/`0x2711`/`0x272c` 等是**数据项 ID**（稀疏）。

### 3.3 无 CODOID / 无 ASCII

- 解压里**不含 CODOID `0xE7C8A98A6B4C2D0E`**（0/84）；
- **无任何 ≥6 的可读 ASCII 串**。

⇒ **档案是纯二进制数值结构，账号身份不在这个 32KB 块里**（可能在别处 u64 字段或压缩外面）。

## §4 zlib 在客户端的旁证

`m65_push_ctx.txt`：查 `subscribe` 时命中 `0x9DC200` 区，实为 **zlib 库的完整错误表**：

```
'invalid window size'
'incorrect header check'
'need dictionary'
'incorrect data check'
'oversubscribed dynamic bit lengths tree'
'incomplete dynamic bit lengths tree'
'oversubscribed literal/length tree'
'incomplete literal/length tree'
'oversubscribed distance tree'
'incomplete distance tree'
'empty distance tree with lengths'
'incompatible version'
```

★★ **这是 zlib 1.x 的标准 `z_errmsg[]` 表**（inflate.c 里那 12 条错误串）。⇒ **客户端静态链入了 zlib**。这给 `8/3`（本卷）和 `71/15`（`124`）用 zlib 提供了直接依据——**不是猜，是客户端里就有 zlib 库**。
★ 附带：这 12 条也是"哪些串是假命中"的证据——`0x9DC25C` 的 "subscribe" 是 `oversubscribed` 的子串，不是真 `subscribe`。
