## §2 ★★★★★ Q2：4/5 号背包 —— 有实测数据的硬缺陷

### 2.1 事实：两个 SKU 指向同一个 item

```
item_sku_arrays.csv:  121,241,1880,30     ← SKU 241 -> item 121, 1880, 30天
item_sku_arrays.csv:  121,242,9680,0      ← SKU 242 -> item 121, 9680, 永久
catalog: SKU 241 -> Sku(Id=241, Item=121, Price=1880, Category=0, Stackable=False, Grant=1, Days=30)
catalog: SKU 242 -> Sku(Id=242, Item=121, Price=9680, Category=0, Stackable=False, Grant=1, Days=0)
```

★ **两个 SKU 都是 `Stackable=False`，都指向 `Item=121`。**

### 2.2 离线模拟（复制合法 account/inventory 到临时目录，绝不碰受保护资产）

```
start            Items[121]=None  CP=963849
buy 241 (4号)    Items[121]=1     CP=961969   <- 扣 1880
buy 242 (5号)    Items[121]=1     CP=961969   <- 未扣款、数量未加
```

### 2.3 真实库存文件同构

```
marketplace-inventory.json:  Items["121"]=1   Items["241"]=1   Items["242"]=1
```

**两个 SKU 都记了"已购"，但背包物品 121 只有 1 个 ⇒ 第 5 个背包没生效。**

### 2.4 根因（`marketplace_store.py:566-600`）

```python
key = str(sku.Item)
owned = int(state["Items"].get(key, 0))
if sku.Stackable:
    charge += sku.Price * qty
    state["Items"][key] = owned + sku.Grant * qty
elif owned == 0:                 # ★★★ 非 stackable 只在"未拥有"时授予
    charge += sku.Price
    state["Items"][key] = 1
# owned != 0 时：不扣款、不加数量、不报错
```

★ 对**唯一性物品**（枪械，已拥有就不该再买）这是对的；
★ 对**槽位型物品**（背包，每买一次应 +1）就是错的。

### 2.5 附带问题：租用被当永久

SKU 241 的 `SelectedDays=30`（30 天租用），但 `inventory_object()` 恒写"无过期"：

```python
w = _u32(w, 0)    # no expiration   （marketplace_store.py:659）
```

⇒ **30 天租用被发放为永久**（过度授予，不是阻塞）。SKU 242 的 `Days=0`（永久）与此一致，所以只有 241 受影响。

### 2.6 修复方向（未实施）

| 方案 | 说明 |
|---|---|
| A. 按 SKU 记库存键 | `key = str(sku.Id)` 而非 `str(sku.Item)` —— 但会与客户端读取的 item 语义冲突，**需先确认客户端按 Item 还是按 Id 计** |
| B. 槽位型白名单 | 对 `Item` 属于"可叠加槽位"的物品（如 121）允许 `owned+1` 并扣款 |
| C. 分档映射 | 把 241/242 映射到两个不同 item id |

★ **A 与 B 的取舍取决于「客户端按什么键显示第 N 个背包」**，这需要实机或真实库存样本，**不能凭猜**。

   `{0:3089, 1:29315, 2:225, 3:4283, 4:127, 5:721, 6:74}` —— **Category 7（组合包类）0 条**。

   ```python
   sku = vals[1]; quantity = vals[3]      # 只取第 2/第 4 个 u32
   ```
   若组合包帧携带多个 SKU，**其余被丢弃**。

但对**购买**无影响。**此点未验证**（无真实 SKU 页样本）。

## §4 Q3：军牌/称号/徽章 —— 大部分已解决，有残留

### 4.2 那批失败 SKU 现在的解析率

### 4.3 Category 门槛当前不拦任何东西


## §7 方法论

1. **★★★★★ 「能解析」≠「授权正确」。** 111/122 能查表，但真正决定成败的是 `purchase()` 的授予逻辑 —— **查表只是第一步**。
2. **★★★★ 同一条 item 被多个 SKU 指向时，非 stackable 语义会失效。** 唯一性物品的规则不能套用到槽位型物品。
3. **★★★★ 旧日志必须先验证"错误串是否还在当前代码里"。** `unknown_skus.txt` 的 156 行是 2026-10-10 的旧版遗留，直接拿它当"当前故障"会得出完全错误的结论。
4. **★★★ 离线模拟可以给出确定结论。** 复制合法 account/inventory 到临时目录 → 跑真实 `purchase()` → 观察 `Items` 与余额，**不碰受保护资产、不启动游戏**。
