# 编码器 v2：接上类型号，第一条真正完整的 dwRoomMessage

> 承接 `lobby/93`、`lobby/94`
> 产物：`tools/dwroom_codec2.py`

---

## 1. 与 v1 的唯一差别，但它是决定性的

**v1 输出：**

```
MemberList (N=1)  首字节 0x18，第二字节 0x05   ← 类型号 = 5（错的，那是 0 被夹出来的位）
```

**v2 输出：**

```
MemberList (N=1)  首字节 0x18，第二字节 0x75   ← 类型号 = 14 = 0x0E（正确的）
```

**⇒ 就是这一位之差，一条消息从"格式对但类型错"变成"格式和类型都对"。**

---

## 2. ★ 逐位验证（这是本卷的核心证据）

**`MemberList`（类型号 14），N=1，位长 775：**

```
位流（MSB-first）：
  bits[0:5]    = 00011          = 3      ← tag 0x03
  bits[5:13]   = 00001110       = 14     ← ★ 类型号 = 0x0E
  bits[13:18]  = 10101          = 0x15   ← tag 0x15
  bits[18:50]  = 000...001      = 1      ← 成员数 N=1
  bits[50:775] = 725 位成员记录
```

**实际字节：**

```
18 75 40 00 00 00 54 00 ...
↑  ↑
|  └─ 0111 0100 → bits[8:16] = 01110100，其中 bits[8:13] = 01110，
|      接 bits[5:8]=000 ⇒ 00001110 = 14 ✓
└─ 0001 1000 → bits[0:5] = 00011 = 3 ✓
```

**⇒ 首两个字节 `18 75` 唯一确定了 tag=3、type=14。**

**⇒ 与 `lobby/94` §4 的 `8a 46 04` 反汇编证据完全一致。**

## 3. 三种成员数的精确字节长

```
N=1  →  775 位 =  96.875  →  97 字节
N=2  → 1500 位 = 187.5    → 188 字节
N=8  → 5850 位 = 731.25   → 732 字节
```

**⇒ `tools/dwroom_codec2.py encode MemberList --members 8` 直接给出 732 字节。**

**⇒ 这可以直接贴进 poke/发包工具里试。**

## 5. 为什么 `P2PInfo` 值得单独说

**它 840 位里，有 **536 位 = 67 字节** 是一个固定的 blob。**

**`0x627fe4` 处的反汇编是：**

```
push 0x20        ; 32
call writeData   ; 写 blob 长度字段
push 0x218       ; ★ 536 = 0x218
```

**⇒ 536 是立即数，不是算出来的 ⇒ 编译期就定死 67 字节。**

**⇒ 一个 P2P 消息里有一个 67 字节的固定结构，
最可能是：**

```
67 = 1 + 2 + 64      (类型 + 端口 + 32 字节哈希?)
67 = 3 + 64          (标志 + 密钥)
67 = 2 + 1 + 64      (族 + 类型 + 32 字节候选)
```

**⇒ 我给了三种分解，但都不足以定论。**

**⇒ 这是"结构已知、语义未知"的又一例。**

---

## 6. 编码器现在能做什么

**能：**
- 生成 32 条消息的合法位流（含类型号）
- 任意 N 个成员的 MemberList
- MSB / LSB 双模式
- 精确字节数

**不能：**
- `RoomInfo`（53 个字段，需要单独的 spec 表，未完）
- 变长串内容（现在填 "Bob"）
- 真实业务值（全是 0）

**⇒ 第三条仍然是"必须有真实样本"才能解决。**
