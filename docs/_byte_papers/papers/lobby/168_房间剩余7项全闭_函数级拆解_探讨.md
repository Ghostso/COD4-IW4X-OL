# 168 · 探讨：七项里没有一项真的需要"运行时对照"

> 配套论文：`168_房间剩余7项全闭_函数级拆解.md`

---

## 一、先说这句话为什么管用

> **大型游戏复原可以拆成大量独立函数任务，再通过依赖关系和严格验证机制持续推进。** —— GPT-6A

我上一卷把 7 项都标成"静态到此为止"，其中 4 项写的是「结构已知、业务名未知，需要运行时对照」。

**按这句话拆到函数级，7 项全部闭合，零运行时依赖。**

---

## 二、7 项各自的真相

| 我上卷的说法 | 实际原因 |
|---|---|
| S2「`vt[0x58]` 落在 AES-NI 代码里」 | **139 卷基址算错**，正确 vtable 是 `0xDDCF2C`，`slot[0x58]=0x7CBA30` 完全正常 |
| T1「12~13 个 16 位槽」 | **138 卷数成了字段描述符数**，实测循环 4 次 |
| P5「对等玩家槽字段语义需运行时」 | **前提错**：那个打包器是字节搬运器（`0x6431B0(buf, n)`），**没有字段语义可解** |
| P7「ID 字段位置」 | 同上 |
| W3「`0x02` 标签需完整位流样本」 | **层级混淆**：它是 `0x13` blob 的内层首字节，不是位流 tag |
| M1「成员记录字段业务语义」 | **前提错**：记录是 `{offset,bits,hints}`，**协议里根本没有名字字段** |
| S4「第二表语义」 | 实测 9 个 handler 各调一个 lobby 函数 ⇒ **根本不是房间消息** |

**⇒ 四项是「前提错」，三项是「前卷算错」。没有一项是真的"缺数据"。**

---

## 三、这暴露了一个模式

我反复用「需要运行时对照」当停手理由。但回头看，**每一次都是我没把一个函数拆到指令级**：

- **S2**：拆到 vtable 槽就解了（半小时）。
- **P5**：拆到 `0x6431B0` 的签名（`(bdByteBuffer*, size)`）就证伪了。
- **M1**：拆到 `0xDA9330` 的 12 字节记录（`{offset,bits,hints}`）就发现没有名字。
- **S4**：拆到 9 个 handler 的内层调用就发现是 lobby 事件。

**⇒ 「需要运行时」= 「我没拆到底」。**

GPT-6A 那句话的意思正是：**能不能拆成函数级任务，是能不能推进的分水岭。**

## 四、连带更正了三处

| 卷 | 原结论 | 更正 |
|---|---|---|
| 138 | 「字段码名表 `0xB773D0` 25 项」 | **是类型码名表**（NoType/Bool/Char8/…/FullType），不是字段名 |
| 138 | 「`0x12` 有 12~13 个 16 位槽」 | **实测 4 个** |
| 140 | 「第二表 1002..1010 是 dwRoomMessage 扩展」 | **是 lobby 事件扩展** |

**⇒ 三处都是「前卷数字没复核」的残留。**

## 五、房间线的最终账

| | |
|---|---|
| 累计闭合 | 12（166）+ 8（167）+ 7（168）= **27 项** |
| **仍开** | **1**（`6/5` 消息码表） |
| 那 1 项的性质 | **我方服务端从不发 `6/5`，无样本** |

**⇒ 但按 GPT-6A 的原则，「无样本」也不能当停手理由。**

**`6/5` 该怎么拆？**
1. `6/5` 是 `service=6, task=5`，属于 `InstantMessageService`。
2. 客户端侧一定有对应的**发送/接收**函数（因为客户端要能发 `6/5`）。
3. **拆法**：在客户端找 `service==6 && task==5` 的分派点，读它的解码器。
4. 这**完全静态可做** —— 只要找到分派表。

**⇒ 这是下一轮的入口，不是"到此为止"。**

## 六、方法论（本卷新增三条）

1. **★★★ 「需要运行时对照」= 「还没拆到函数级」。** 7 项实测，全部静态可解。
2. **★★ 先验证前提，再查数据。** P5/M1 都是「前提本身错了」，查数据是白费。
3. **★ 前卷的数字要复核才用。** 138/140 三处数字，本轮全部更正。
