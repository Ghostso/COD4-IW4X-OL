# 264 探讨 · 41 位 / 49 位之争，以及"恢复被删的位"为什么也算修复

> 配套卷：`264_房间类修复落地_Manifold41位与BitWriter头位.md`
> 本文只谈**为什么**、**哪里没把握**、**下一步怎么判**，不重复证据表。

---

## 一、五卷对同一个问题给了三个答案

房间 Manifold 位流到底是 41 / 50 / 51 位，历史上写过五卷，结论三变：

```
175 -> 51 位（读侧 push 1 当 +0x21=1）
177 -> 50 位（把 push 3/8 当位宽加错）
239 -> 41(flag=0) / 51(flag=1)
242 -> 51 位（只看了 ctor）
245 -> 41 位（+0x21 是总开关）
```

这不是"越写越乱"，而是**每卷都只读了一部分代码**：
175 把 ctor 第 3 参当地 2 参；177 把 tag 值当位宽；242 漏了 `W_TAG` 里那个 `je`。
245 之所以对，是因为它把 **读侧 + 写侧 + 两个 TAG 原语 + ctor** 四块拼齐了。

**教训**：一个字段（`+0x21`）在同一子系统里扮演三种角色
（写侧的 flag 值 / 编解码总开关 / 读侧恒 0）。
**只看一个函数，必然得到三种答案中的一种错答案。**

## 二、我为什么敢把 7 字节改成 6 字节

改这个数最怕"改完更错"。本轮的护栏是**独立复算**：
不引用任何一卷的加法，而是自己把 `0x625520` 的执行序抄一遍，
再去读 ctor 确认头位，再去读 `W_TAG` 确认跳空条件。
三段各自独立，拼起来只有一个答案：`1 + 8 + 32 = 41`。
然后再用 **239 卷的逐位仿真向量**（`16 00 00 00 00 00`）交叉验证——
那是另一条独立路径（子代理写的 sim3.py），数值吻合。

**两条独立路径给出同一个数**，才敢落地。这比"哪卷卷号大听哪卷"稳。

## 三、BitWriter 那条：删一个 bit，测试全绿

R19 把 `write_bits(1,1)` 删掉，理由是"无 1 位头"。
删完之后 StartGame 从 868 位变 867 位——**都是 109 字节**，
`ceil(867/8) == ceil(868/8) == 109`，所以任何"字节数断言"都发现不了。

这正是 242 卷说的"藏了四卷"的同款陷阱：
**用一个粗粒度指标（字节数）去验证一个细粒度结论（位宽/对齐）**。
破解办法只有一个：**逐位读**。用 867 的读法去读 868 的字节，
tag3 位置读到 7 而不是 3，错位立刻现形。

**"删了一行还能全绿"的修复，最危险。**

## 四、容器信封（41 vs 49）——**已解，且是主对话一度读错的一卷**

这一条一度是本轮**最大的不确定性**，现在有了结论，且过程本身是个方法论标本。

- 客户端**唯一**能解 Manifold 的函数是 `0x6256C0`。
- 它的**唯一**调用者是 `0x637000`（`E8` 全库扫描，恰好 1 处）。
- `0x637000` 先读 `R_TAG(3) + R_VAL(8)` 并 `cmp eax,1`，才进 `0x6256C0`。

**主对话**据此判：「容器多读 8 位 ⇒ 线上 = `[H][8 u8][8 type][32]` = 49 位」，
并要求照此回改 R20。**我驳回了**：

> `0x63706B`（原始字节 `b9 01 00 00 00` `89 4e 1c`）把**读游标重置回第 1 位**，
> 紧接着才 `cmp eax,1`。`0x6256C0` 于是从第 1 位**重读同一个 8 位**。
> 容器那层 `R_TAG(3)+R_VAL(8)` 是 **peek**，不是消费。⇒ **没有外层字段，仍是 41 位。**

**主对话已接受驳回并确认自纠**（2026-11-03）：「你是对的，我错」——
它重看 `0x63706B/0x6370C6` 两处同为 `mov [eax+0x1c],1`，确认是回卷。
⇒ **R20 保持 41 位，我上一轮的 49 位作废。**

### 这条为什么值得单列

它同时踩中三个已知陷阱：
1. **「读了两边」≠「两边对得上」**——主对话读了写侧也读了读侧，但漏了中间的游标回卷。
2. **关键指令只有 3 字节**——`89 4e 1c`，夹在 `movzx`/`cmp` 之间，不专门看就会滑过去。
3. **「多一层」的直觉最容易误导**——看到容器先读 8 位，就默认它是独立字段，
   而不去问「读完这位以后，游标停在哪」。

**判据**：`0xB772E0` 的 `0xB773A6 add [edi+0x1c],esi` 证明 `[obj+0x1C]` 是**会前进的读游标**。
所以「把 `[obj+0x1C]` 置 1」= 回卷 = peek 语义。**先确认游标是不是会前进，再判是不是独立字段。**

## 五、R22：那 8 位 type 该不该是 1（**静态不可达**）

容器对 peek 到的 type 分流：**`type==1` 才走 Manifold 读器 `0x6256C0`**，
`type!=1` 走 `0x634870`（它自己也 peek+回卷，再走**两级分派**）。

- 一级 `0x82E1458[type]`：**运行期填表（BSS，静态前 12 项全 0）** ⇒ 静态读不出「type→handler」。
- 二级 `0x636F3C[type]`：**磁盘里的静态跳转表**（`[0]=0x636F02` 仅清理）。
  一级槽为空时回落到它。**171 卷记的正是二级，有效；本轮找到一级是新增，非替代。**
  （早期口述「更正 0x636F3C 归属」是过度更正，已作废。）
- ⇒ **type=0 的落点取决于运行期 `0x82E1458[0]` 是否为空**：为空则落 `0x636F3C[0]=0x636F02`
  （仅清理）⇒ **若回包真走此路，type=0 回包运行时可能被静默丢弃**。此为事实补充，非改动依据。
- 0x6256C0 是**唯一** Manifold 读器 ⇒ **若回包被当 Manifold 读，type 必须是 1**；
  而现用 0 ⇒ 走 `0x634870[0]`（一个非读器 handler）。
- **但**「6/5 回包是否经由 `0x637000`」**静态没证死**：`0x637000` 的父级 `0x6371F0`
  是注册在 `[roomObj+0x25B8]` 的房间报文处理器，任务回包→该处理的绑定只有间接证据。

⇒ **判定为「静态不可达」，不改值。** 写清条件：**若回包走容器，type 必须为 1，0 即「回包被丢弃」级缺陷**；
是否走容器需**真实样本/实机**。**不用猜的改。**
