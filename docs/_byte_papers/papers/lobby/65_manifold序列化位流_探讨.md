# Manifold 序列化位流 · 探讨：字节对齐掩盖了位结构

> 对应：`lobby/65_manifold序列化位流.md`

---

## 一、这一卷的核心发现

**所有 `dwRoomMessage` 共用一个消息头：**

```
writeBits(3)  +  writeData(8)      ← 3 位 + 1 字节
writeBits(8)  +  writeData(0x20)   ← 8 位 + 4 字节
```

**这解释了 `lobby/40` 里 `11/4` 的恒定结构：**

```
02 02 00 00 | 00 08 00 00
```

**如果按字节读，它是 `u32`；
如果按位读，前 3 位可能是类型码。**

---

## 二、一个必须承认的矛盾

**我算了一下：**

```
0x02 = 0000 0010
前 3 位 = 000 = 0
```

**但消息头要求 `writeBits(3)` 写的是**写死的 3**。**

**⇒ 如果 `11/4` 的 blob 从 `02` 开始，前 3 位应该是 `011`（=3）。**

**⇒ 不是。**

**⇒ `11/4` 的 blob 不是 `dwRoomMessage` 的位流。**

---

## 三、那它是什么

**三种可能：**

### A. `11/4` 的 blob 是"已字节对齐的中间形态"

**位流写完后被填充到字节边界。**

**3 位 + 1 字节 = 11 位，会跨字节。**

**如果序列化器把每个字段单独对齐，就会变成字节序列。**

**⇒ 这能解释为什么 `11/4` 的 blob 看起来像字节字段。**

### B. `11/4` 的 blob 是另一种协议（不是 dwRoomMessage）

**它可能是 Demonware 的"通用对象序列化"，与房间消息体系并列。**

### C. `11/4` 的 blob 是加密的

**但 `lobby/40` 已证明它是恒定模板，
如果是加密的，不同会话应该不同。**

**⇒ 排除 C。**

**不 —— 我只读了前 100 字节的反汇编。**

**`0x625578` 之后还有很多。**

## 六、方法论收获

> **"按字节看"和"按位看"是两种完全不同的视角。**

**同一个 145 字节，按字节是"36 个 u32"，
按位是"一个 1160 位的消息流"。**

**⇒ 遇到"恒定但看不懂"的数据，先试按位切。**
