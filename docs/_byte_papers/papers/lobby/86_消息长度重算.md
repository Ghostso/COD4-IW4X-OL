## 2. ★ 缺陷 1：RoomInfo 明显不对

**`0x627ea0` 算出 18 位（2.25 字节）。**

**但 `lobby/71` 我用人工读法得到 28 个字段（5 个字符串 + …）。**

**⇒ 原因：`0x627ea0` 只写头，主体交给 `0x624510`。**

```asm
0x627ead  mov al, [esi+4]
0x627eb7  call writeBits(3)       ← 只读到这
0x627ec4  call writeData(&[esi+4], 8)
0x627ec9  mov ecx, [esi+8]
0x627ece  call 0x624510           ← ★ 主体在这里
```

**⇒ 提取器没跟进 `0x624510`。**

**⇒ 这解释了 18 位 vs 人工读出的 28 字段。**

---

## 3. ★ 缺陷 2：变长字段无法静态计算

**凡是 `writeData(ptr, reg)`（而非立即数），我的工具标 `?`。**

**⇒ 涉及字符串/blob 的消息，位长无法静态确定。**

**⇒ 上表标 `?` 的 14 个类，都是含变长字段的。**

## 4. 哪些数字是可信的

**纯定长、无子调用的消息，位长可信：**

| 类 | 位长 | 字节 |
|---|---|---|
| `MemberList` | 55 | 6.88 → **7 字节** |
| `UpdateDlcLevel` | 26 | 3.25 → **4 字节** |
| `RoomStateUpdated` | 100 | 12.5 → **13 字节** |
| `Vote` 族 | 89 | 11.12 → **12 字节** |
| `ChangeTeam` | 169 | 21.12 → **22 字节** |

**⇒ 这些是"可预测的长度"，将来抓到真实推送就能比对。**

---

## 5. 对 5 位模型本身的影响

**缺陷 1、2 都是"提取器不完整"，不是"5 位模型错"。**

**5 位模型的证据（`lobby/85`）：**

1. `0xb75d40(31) = 4`，`inc` → 5
2. write/read 完全对称
3. 所有标签 ≤ 0x1F

**⇒ 5 位模型仍然成立。**

**⇒ 上面的长度只要"字段序列完整"，就可信。**

---

## 6. 一个可验证的预测

**`MemberList` = 55 位 = 7 字节（含 1 位填充）。**

**如果将来抓到一条 `MemberList` 推送，它应该是 7 字节。**

**⇒ 这是本卷第一个"可现场验证"的数字。**

---

## 7. 修正提取器

**需要两处改进：**

1. **跟进 `call 0x624510` 等子函数**（RoomInfo 主体）
2. **对 `writeData(ptr, reg)` 记录"变长"标记清楚**

**⇒ 下一轮做。**
