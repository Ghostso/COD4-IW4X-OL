# 服务端控制模式列表 · 探讨：证明"能改"的那份文件

> 对应：`lobby/21_服务端控制模式列表实证.md`

---

## 一、我要证明什么

前面我写了"`catinfo` 加一行就能加模式"。

**但那是推理，不是证据。**

推理链是：
1. 客户端请求 `.info`
2. 服务端下发 `.info`
3. `.info` 里有 `catinfo`
4. 所以改 `.info` 就能改模式列表

**第 3 步到第 4 步之间，缺一个"客户端真的会用"的证明。**

---

## 二、证据在哪

在 `CODOL_LOCAL_CHAIN_V2\publisher_files\` 里：

```
mp_playlists_shipRetail_1.0.0.info              21,412 字节  ← 官方
mp_playlists_shipRetail_1.0.0.info.bak_dummy       976 字节  ← 自制
mp_playlists_shipRetail_1.0.0.info.bak_before_playlists_20261006_215009   262 字节
mp_playlists_shipRetail_1.0.0.info.bak_before_playlists_20261006_215606   658 字节
mp_playlists_shipRetail_1.0.0.info.bak_before_playlists_20261006_220758   716 字节
...（还有更多，尺寸递增）
```

**这些 `bak_before_playlists_*` 的文件名，说明有人反复改过这个文件并保存了每一版。**

**尺寸从 262 → 658 → 716 → 822 → 976 递增** —— 是一步步建立起来的。

---

## 三、最关键的一份

`bak_dummy`（976 字节，解压 4,428 字节）的第一行：

```
// CODOL local lobby playlists (rebuilt 2026-10-06).
```

**"rebuilt" = 重建。**

**这不是原厂的，是本项目自己写的。**

---

## 四、它的内容证明了三件事

### 1. 字段可以精简

官方版一个 `playlist` 块有 30+ 行。
自制版只有：

```
playlist 1
name english "Team Deathmatch"
description english "Team Deathmatch"
category 0
teambased 1
maxparty 6
buildversion 1649370
mp_village war 1
...
```

**客户端接受这种精简。**

### 2. 地图行可以用空格分隔

官方：`mp_nuked,cha,1`（逗号）
自制：`mp_village war 1`（空格）

**两种都能解析。**

### 3. `buildversion` 必须是 1649370

自制版特意写了 `buildversion 1649370` —— 就是目标 build 号。

**说明客户端会校验它。**

---

## 五、这份证据为什么强

因为它是**己方做过的事**，不是"理论上可行"。

- 有 `bak_before` 备份 → 说明改过
- 有"rebuilt"注释 → 说明重写过
- 有递增的尺寸 → 说明逐步调试
- 有 `buildversion 1649370` → 说明踩过坑

**这是实验记录，不是推测。**

---

## 六、还差的一环

**我没有亲眼看到"改完之后模式列表变了"。**

但即使没有这一步，`bak_dummy` 的存在本身已经证明：

> **有人成功让客户端接受了一份自制 playlist。**

因为如果客户端拒绝，就不会有一连串递增尺寸的版本迭代。

---

## 七、方法论收获

> **项目里已有的实验产物，是最强的证据。**

我没有做新的实验，是在文件系统里找到了**别人（可能是我自己在前几次会话里）留下的实验痕迹**。

`bak_before_*` 这种命名是"改过"的直接证据。

**在开始新实验之前，先扫一遍磁盘，找有没有历史的实验产物。**

这一条以后要变成常规动作。
