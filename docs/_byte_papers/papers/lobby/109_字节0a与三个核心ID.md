## 3. ★★ 三个核心 ID 定位（全部跨 task 验证）

| ID | 值 | 出现 task | 总次数 |

**★★ 更正（110 卷）：`1800154382 = 0x6B4C2D0E` 是**账号 ID 的低 32 位**，

## 4. ★★ `1800154382` 的真相：**账号 ID 的低 32 位**（110 卷更正）

**`108` 卷我在 `mmstart` 明文里看到 `roomChatChannelID 1800154382` 只出现 4 次，
当时标"疑似服务端分配"。本卷先误判为"另一个 channelId"，**110 卷已证伪**。**

**★ 硬事实：`1800154382` = `0x6B4C2D0E` = `0xE7C8A98A6B4C2D0E & 0xFFFFFFFF`。**

```
账号 ID = 0xE7C8A98A6B4C2D0E
  └─ 低 32 位 = 0x6B4C2D0E = 1800154382   ← 就是这个值
```

**★ 交叉证据（`61` 卷早已记录的字节）：`4/13` 的 u64 存储为
  `0a 0e 2d 4c 6b 8a a9 c8 e7`，其**低 4 字节 `0e 2d 4c 6b`** 正是 `0x6B4C2D0E`。**

**本卷实测：它在 u64 字段里出现 **54 次**，分布：**

```
11/4  : 33
21/12 : 10
21/1  :  7
11/2  :  4
```

**★ 而在 `11/4` 里，它和 `0x1122334455667788` **占据同一个字段位置（元素 #0）**：**

```
11/4 元素序列（示例）：
  0a=1234605616436508552  13[145]  08=1      ← 默认频道 ID
  0a=1800154382           13[21]   08=1      ← 账号 ID 低 32 位
```

**⇒ `11/4` 的完整结构 = `[u64 roomId][0x13 blob][0x08 u32]`，
  与 `108` 卷从 `reply_objects` 拿到的
  "`11/4` = setRoomData(u64 roomId, blob batch, u32 type)"**逐字段吻合**。**

**★★ 关键关联（110 卷）：ACClo 只出现在 83 个 run 里的 **3 个**
  （`ONCE_20261029_000806` / `_001513` / `_002046`），且这 3 个 run **都建过房**（有 `11/13`）；
  但反向不成立（47 个 run 也建过房却用默认频道 ID）。⇒ 详见 110 卷 §5。**

**⇒ 对我们的目标：**默认房间 ID 是 `0x1122334455667788`（可控）；
  账号派生 ID = `账号ID 低32位`，我们也能算出来。**

## 5. `21/1` 的 u64 只有两个位置 —— 档案骨架

**实测 `21/1` 里 u64 元素的**位置**（元素序号）只有两处：**

```
元素 #4  : 16701785630074219790 (账号ID)   ×42  ← 100%
元素 #25 : 1234605616436508552 (频道ID) ×35
           1800154382           (频道ID) ×7
```

**⇒ 这是 `21/1`（createSession）的**骨架**：**

```
#04 0a = 账号ID      ← "我是谁"
#25 0a = 频道ID      ← "我在哪个频道"
```

**★ 两个 u64 之间的 21 个元素（#5..#24）全是 `0x07` i32 与两个 blob ——
  那就是 `107` 卷解出的"玩家档案"（等级、统计、装备等）。**

**⇒ 所以 `21/1` = 完整玩家档案 + 两个 ID。**
**⇒ 如果我们想让客户端"以为自己"是另一个玩家/另一个频道，改 #04 和 #25 即可。**

## 6. ★★ 重大结构发现：`11/4` 与 `6/14` 的 blob 有内层长度前缀

**全语料扫描"`0x13` blob 的首 4 字节是否 == `len(blob)-4`"：**

| task | 命中率 |
|---|---|
| **`11/4`** | **261 / 261 = 100.0%** |
| **`6/14`** | **235 / 235 = 100.0%** |
| `71/4` | 0 / 320 = 0.0% |
| `71/15` | 0 / 162 = 0.0% |
| `68/3` | 0 / 145 = 0.0% |
| `21/12` | 0 / 108 = 0.0% |
| `8/3` | 0 / 84 = 0.0% |
| `21/1` | 0 / 84 = 0.0% |

**★ 这是**精确的 task 专属结构**：只有 `11/4` 和 `6/14` 有内层长度前缀，
  其余 task **一个都没有**。**

**⇒ 这不是"普遍规律"，是"这两个 task 的 blob 是嵌套报文"。**

**★ 为什么？因为 `11/4` 和 `6/14` 的 blob 里装的是**另一条完整报文**：
  - `11/4` 装的是**房间频道消息**（要转发给其他成员）
  - `6/14` 装的是**即时消息命令串**（`mmbook`/`mmstart`/`mmban`）

**⇒ 要转发/转交的东西，需要自带长度 ⇒ 有长度前缀。**
  **而 `21/1`、`8/3` 的 blob 是"自己消费的数据"，不需要长度前缀。**

**★ 这条规律可以直接用于**判断一个 blob 是"数据"还是"嵌套报文"**：
  看首 4 字节是否等于 `len-4`。**

## 7. `11/4` 的内层结构（b0 只有 2 和 24 两值）

**`11/4` 的 blob 去掉 4 字节长度前缀后，首字节 `b0` 只有两个取值：**

```
b0 = 2   ×195
b0 = 24  × 66
```

**★ `b0 = 2` 时，紧跟的 u32 是 `2/4/6/8`（小偶数）：**

```
b0=2  u1=2  : 112
b0=2  u1=4  :  56
b0=2  u1=6  :  17
b0=2  u1=8  :  10
```

**⇒ 这像一个"消息类型 = 2，子类型/长度 = 2/4/6/8"的房间消息头。**

**★ `b0 = 24`（0x18）时，是 **21 字节的 ready 批次**：**

```
11 00 00 00 | 18 | 1c 5a 98 d6 | 14 53 91 cf | 01 | ac b5 01 00 00 00 00
  len=17        b0   └── 8 字节时间戳/ID ──┘   ↑   └── 后续 ──┘
```

**★ 21 字节 = 4(len) + 1(b0=0x18) + 8(时间戳) + 1(0x01) + 7(尾)。**

**⇒ 这正是 `108` 卷参考实现提到的"21B ready 批次，`plain[11] == 0x15`"。**
  **（`plain[11]` 在这个 blob 里 = 第 12 字节 = `0x91`... 让我核对：
  外层 payload = `0a <8B> 13 08 <4B len> <21B>`，
  所以 payload[0]=0x0a，payload[9]=0x13，payload[10]=0x08，
  payload[11..14]=len，payload[15]=blob[0]... 嗯，`plain[11]` 是 len 的**首字节**。
  21 = 0x15 ⇒ `plain[11] == 0x15` **正是 blob 长度 21 的低字节**！）**

**★★ 这印证了 `108` 卷参考实现自己的更正：
  "`pushData[11] == 0x15` 那个字节其实是 **blob 长度的低字节**（0x15=21），
  不是子类型"。**

**⇒ 也就是说：所谓"ready 判据 `plain[11]==0x15`" = "blob 长度 == 21"。
  而 21 字节的 blob 里 `b0 = 0x18 = 24`。**

**★ 所以真正的判据应该写成：**`11/4` 的 blob 长度 == 21 且 `blob[4] == 0x18`。**
  **这比"`plain[11]==0x15`"清晰得多，而且不依赖外层布局。**

## 8. `6/14` 的 `0x01100001DEADC0DE`

**`6/14` 里有一个 u64 = `76561201696194782` = `0x01100001DEADC0DE`，出现 4 次。**

**它的原始位置（len=45 的报文）：**

```
0a de c0 ad de 01 00 10 01 13 08 1d 00 ...
   └────── u64 = 0x01100001DEADC0DE ──────┘
```

**★ 小端存的是 `de c0 ad de 01 00 10 01` ⇒ 值 = `0x01100001DEADC0DE`。**

**⇒ 它含 **`DEAD C0DE`** 这个经典调试魔数（dead code）。**

**★ 这是**开发者故意放的哨兵值**。
  `0xDEADC0DE` 是 Windows/内核里表示"已释放/无效"的经典填充值。**

**⇒ 它在 `6/14`（即时消息）里出现 4 次 ⇒ 某条即时消息带了一个"无效 ID"标记。
  这可能是"还没有分配会话 ID"时的占位。**

**★ 注意与 `memory` 里记的"销毁哨兵 `0xDEADBEEF`（`mov [ecx],0xDEADBEEF`）"
  区分开：**
- **`0xDEADBEEF`** = 内存销毁哨兵（本地逆向，`0xb76e50`）
- **`0xDEADC0DE`** = 报文里的无效 ID（本卷，`6/14`）

**⇒ 两个不同的魔数，两个不同的用途，不能混。**

## 9. `102/7` 的 50 条目：u64 是序号，不是 ID

**`102/7` 有 18,550 个 u64，值 0..49 各 371 次。**

**结构（`102` 卷已解）：**

```
08 32 00 00 00 | [03 01 | 0a <u64 序号>] × 50 | 00
```

**★ u64 值是 **0,1,2,...,49** —— 是**序号**，不是真实 ID。**

**⇒ 所以 `102/7` 是"请求 50 个编号为 0..49 的条目"，不是"请求 50 个具体对象"。**

**★ 结合 `108` 卷的语义表：`102` 是哪个 service？未在 `reply_objects` 里映射。
  但它的形态（50 个序号 + 每项带一个 `03 01` 标志）很像"批量查询某类资源"。**

**⇒ 具体是什么资源，**未定**。但它的"50"是固定值，说明资源池大小是 50。**

## 10. `6/14` 的 `0x0a` 与 `0x13` 的分工

**`6/14` 里 u64 只有两种值：**

```
1                    ×231   ← 与 0x1122334455667788 无关
76561201696194782    ×  4   ← 0x01100001DEADC0DE
```

**⇒ `6/14` 的 `0x0a` 字段不是频道 ID，是一个"序号/标志"。**

**★ 而 `6/14` 的频道 ID 在 **base64 里**（`mmbook 796 iHdmVUQzIhE= 0`，见 `108`），
  不在 `0x0a` 字段里。**

**⇒ 同一个 task 里，同一个"频道 ID"概念用**两种载体**：
  ① `0x0a` u64（在 `11/4`、`21/1`、`21/12` 里）
  ② 字符串 base64（在 `6/14` 的 mmbook 命令里）

**★ 这是"同一语义、多种编码"的典型例子。
  ⇒ 改频道 ID 时必须**同时改两处**，否则不一致。**

## 11. 可落地结论

**① 账号 ID `0xE7C8A98A6B4C2D0E` 是"我是谁"的唯一标识。**
**⇒ 它横跨 6 个 task。改它会让客户端"变成另一个玩家"。**
**⇒ 但风险高：服务端可能用它做鉴权，改了会失败。**

**② 房间/会话 ID 有两个取值：默认 `0x1122334455667788`，
  以及**账号 ID 的低 32 位**（`0x6B4C2D0E` = 1800154382，仅 3 个 run 用）。
**⇒ 默认 ID 我们可自由指定；账号派生 ID 由账号 ID 决定。**

**③ `11/4` / `6/14` 的 blob 有 `[u32 len]` 前缀（100%），其他 task 没有。**
**⇒ 构造这两个 task 的 blob 时必须带长度前缀，否则客户端读错位。**

**④ `11/4` 的 ready 判据应写成"blob 长度 21 且 `blob[4]==0x18`"。**

**⑤ `102/7` 的 u64 是序号 0..49，不是 ID。资源池大小 = 50。**
