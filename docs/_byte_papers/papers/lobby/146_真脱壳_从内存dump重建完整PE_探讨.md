# 146 探讨 · 你说"这不是脱壳"，我一开始没听懂

> 配套：[146 · 真脱壳](146_真脱壳_从内存dump重建完整PE.md)
> 主题：**把"读内存"当成"脱壳"，是一个概念混淆。纠正之后发现：我一直在分析的东西本来就已经解包了。**

---

## 一、我原来做的是什么

144 卷我写：

> **脱壳成功**：`DUMP_20261031_221458` 覆盖到 `0x3ACF3000`，
> srpc 单例 `0x3AC89CB8` 与 dwLobbyImp `0xE39B6E8` 都可读。

**这不是脱壳。** 这只是**按地址读了几段内存**。

★ 我当时甚至写下「"脱壳"可以只是"读运行时内存"」——**这句话本身就把概念搞混了**。

---

## 二、脱壳的定义

**脱壳 = 产出一个可被静态工具完整加载的模块镜像。**

不是"读到几个字段"，而是：
- 有完整 PE 头
- 节表正确（`SizeOfRawData` 与内存态一致）
- 全模块数据铺满
- 任何工具（IDA / Ghidra / objdump）能直接加载

**判据：产物是一个 `.exe`/`.dll` 文件，不是一个 JSON。**

---

## 三、做完之后，发现一个更重要的事

重建出的 PE 与 `E:\codol_re\client_image_20261027.bin` 在关键地址**逐字节一致**。

然后我回去看那个镜像的段表：

```
.tp3#1  VA=0x1000  VSize=0x8A689A  RawSize=0x8A7000   覆盖 100%
熵 6.776 / 0xCC 3.04%
```

**⇒ 那个镜像本来就已经是解包后的。**

★★★ **我从 139 卷开始，一直分析的就是脱壳后的代码。**

| 文件 | 覆盖率 | 熵 | 状态 |
|---|---|---|---|
| 磁盘 exe | 64.44% | 7.140 | **未脱壳** |
| `client_image.bin` | **100%** | **6.776** | **已脱壳** |
| 146 脱壳 PE | 100% | 6.761 | 已脱壳（重建为 PE） |

## 四、那 146 到底新增了什么

**真正的增量只有一个：`.tp3#3`（230 MB BSS）。**

- `client_image.bin` 的 `.tp3#3` 覆盖率 **0.17%**（空洞）
- 146 的 dump **把它填满了**

★★★ **这就是为什么 144 卷能读到 srpc 单例和 handler 单例 —— 那些对象在 `.tp3#3` 里。**

★ 而代码分析（139–142 卷）根本不需要 146，因为镜像里的代码一直是明文的。

---

## 五、我这一卷承认的三件事

### 5.1 概念混淆

**"读内存" ≠ "脱壳"。** 产物形态不同（JSON vs PE），可复用性不同，判据不同。

### 5.2 术语误用传播

144 卷标题写「脱壳成功」，145 卷继续沿用。**一个错误的术语，会把后续所有讨论带偏。**

### 5.3 但结论没受影响

139–145 的**结论**全部成立，因为：
- 代码分析用的是已解包的镜像
- 运行时字段用的是 dump

**错的只是"我给它起的名字"。**

---

## 六、真正的脱壳还差什么

严格意义的脱壳（VMProtect 那种）还包括：

| 步骤 | 状态 |
|---|---|
| 找 OEP（原始入口点） | ❌ 未做 |
| dump 内存镜像 | ✅ 已做 |
| 修正节表 | ✅ 已做 |
| **重建导入表（IAT）** | ❌ **未做** |
| **修正重定位** | ❌ 未做 |
| **清除 VM 残留** | ❌ 未做 |

★★ **我做的是「内存镜像冻结」，不是「完整的 VMProtect 脱壳」。**

★ 但对本项目的目的（静态分析房间消息链路）来说，**已经够用**——
因为我们要看的是代码逻辑，不是要让这个 exe 重新能跑。

---

## 七、方法论

1. ★★★★★ **术语要用准**：脱壳的产物必须是可加载模块。
2. ★★★★ **"成功"之前先问产物形态对不对**。
3. ★★★★ **重建后与已有镜像逐字节比对**，能立刻发现"我一直在用的东西是什么"。
4. ★★★ **熵 + `0xCC` 比例是"解没解包"的机械判据**。
5. ★★★ **承认术语错误，但不要否定已得的结论** —— 两者是分开的。
