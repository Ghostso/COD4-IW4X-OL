## 三、最严重的是 84 卷

84 卷留着：

> 「`writeBits` 写 n 位还是 5 位：**两种读法都有依据，未定**」
> 「消息头长度：**11 位 或 13 位，未定**」

**这两条悬着，意味着所有房间消息的位宽都不可靠。**

本卷查了 `0xB77B10`：

```asm
cmp byte [ecx+0x21], 0
je  ret                    ; 调试开关关 → 什么都不做
mov eax, [ebp+8]           ; n
push 0
push 0x1F                  ; 位宽上限 31
push 0
push eax
call 0xB77A70              ; WriteBitsCore(buf, 0, 0x1F, 0, n)
```

**⇒ `writeBits(n)` 就写 n 位。** 那一串 `0xC/8/0x20/8/0x20` 是**溢出跟踪诊断**，只在 `[esi+0x21]!=0` 时写，**不进业务位流**。

**⇒ 84 卷的"两种读法"里，n 位那种是对的。**

**而"11 位 或 13 位"也解了**：
- **11 位 = 消息头**（3 位 tag + 8 位 type）
- **13 位 = Ready 消息完整体**（头 11 + 存在位 1 + 值 1）

**两个数字都对，只是层级不同。**

## 四、67 字节 blob 也解了

`0xBB9FD0`（真正的 P2P 打包器）：

```asm
push 8  / push esi → 0x6431B0 → 0xB771A0    ; ① 8 字节
push 0x10 / push edi → 0x6431B0 → 0xB771A0  ; ② 16 字节
push 0x24 / lea [ebp-0x28] / push esi
call 0xB77280                               ; ③ 从 esi 读 36 字节块
call 0x8435D0                               ; ★ 空桩（占位）
push 0x24 / lea [ebp-0x28] / push edi
call 0xB772A0                               ; ④ 把 36 字节写到 edi
call 0x8435D0                               ; ★ 空桩
```

**结构 = 8 + 16 + 36 = 60，加头部 7 = 67。**

**⇒ "67 字节 blob" = 两段定长字段 + 一段 36 字节块的**复制中继**。**

**注意那两个 `0x8435D0`——空桩。** 这和 137 卷的"哨兵桩"是同一个函数。
**⇒ 打包路径上有两个"本该回调却没接"的位置。**

## 七、方法论（本卷新增三条）

1. **★★★ 「文件名含关键词」的扫描会漏掉一半。** 房间协议的核心在 `P2PInfo`/`对等玩家槽`/`writeBits` 这些**不含"房间"二字**的卷里。
2. **★★ 绝对断言（"清零""全部"）必须先做机械全库扫。** 说"在我扫到的范围内"不算丢人，说"清零"然后被推翻才丢人。
3. **★ 底层卷（writeBits/位流）决定上层全部消息的解读。** 84 卷一条"n 位还是 5 位未定"，悬着会影响所有房间消息。
