# 字节 `0x08` · 探讨：一个"算出来的时间戳"教会我怎么对待未知字段

> 对应：`lobby/110_字节08全解剖.md`

---

## 一、这一卷最值得说的，不是 `0x08` 本身

**`0x08` 是一个"平庸"的标签 —— 它就是 u32，没什么神秘。**

**但这一卷里有三件事比 `0x08` 本身更重要：**

1. **一个"我上一卷写错了"的更正（`1800154382`）。**
2. **一个"可以自己算出来"的字段（`80/119` 的 `now + 365天`）。**
3. **一个"穷举了 40 种哈希都不匹配"的诚实失败（`31902622`）。**

**★ 逐字节分析的价值，往往不在"这个字节是什么"，而在**这三类副产品**。**

---

## 二、更正：我是怎么把"账号 ID 的低 32 位"误判成"另一个频道 ID"的

**`109` 卷我看到 `1800154382` 和 `0x1122334455667788` 占同一个字段位置，
就下结论"这是同一个变量的两个取值 ⇒ 频道 ID 会变"。**

**★ 错在哪？错在**跳过了算术检查**。**

**只要做一步：**
```
0xE7C8A98A6B4C2D0E & 0xFFFFFFFF = 0x6B4C2D0E = 1800154382
```
**这个误判就不可能发生。**

**⇒ 我犯的是一个"模式匹配过早"的错误：
  看到"同一位置、两个值"，就套用"变量"这个模板，
  而没有先问"这两个值之间有没有确定关系"。**

**★ 而且更尴尬的是：`61` 卷**早就记录过** `4/13` 的字节
  `0e 2d 4c 6b 8a a9 c8 e7`，那低 4 字节 `0e 2d 4c 6b` 就是 `0x6B4C2D0E`。
  证据一直在，我只是没把它和 `1800154382` 联系起来。**

**⇒ 教训两条：**
> **① 新魔数第一步：和已知常量做算术枚举（&、>>、<<、+、-、×）。**
> **② 旧卷里的"字节串"要定期和"十进制大数"对一遍 —— 同一个值的两种写法很容易擦肩而过。**

## 三、`80/119` 的时间戳：这是"逆向"和"猜"的分水岭

**这一卷最有成就感的一处，是 `80/119` 的第 3 个 u32。**

**我没有猜它是什么，而是：**
1. 发现它**每个 run 都不同**（83 个 run，83 个不同值）。
2. 把它当 Unix 时间戳，和 **run 目录名里的时间**比。
3. 发现差值**恒等于 31536000 + 33~39 秒**。
4. `31536000 = 365 × 86400`。

**⇒ 结论：`#3 = 发送时刻 + 一年`。**

**★ 那 33~39 秒为什么是"会话内耗时"？**
```
run 目录名 14:31:43  →  ts(减一年) 14:32:22  →  差 39 秒
```
**run 目录名是"启动时刻"，`80/119` 是"会话进行中发出的"。
  所以差值 = 从启动到发这条报文的时间，几十秒，完全合理。**

**⇒ 这条推理链的每一步都有数据支撑，没有一步是猜的。**

**★ 这正是"字节级逆向"该有的样子：
  **不是"我觉得这是时间戳"，而是"它减去 run 时间恰好是整一年加几十秒"。**

## 四、诚实失败：`31902622` 穷举 40 种哈希都不匹配

**我一开始的假设是：`71/4` 里既有 MAC 又有这个 u32，那 u32 大概是 MAC 的哈希。**

**于是我把能想到的都试了：**
- 5 种字符串哈希：FNV1a、FNV1、djb2、sdbm、Java hashCode
- 3 种摘要：md5、sha1、sha256（取前 4 字节 / 后 4 字节，大小端）
- MAC 的 4 种写法：带横线、去横线、小写、原始 6 字节

**4 × (5 + 3×4) = 4 × 17 = 68 种组合，全部不匹配。**

**★ 我也可以"挑一个看起来像的"硬凑，但我没有。**

**⇒ 论文里写的是"非 MAC 哈希，语义未定"。这是诚实的。**

**★ 为什么"未定"比"猜一个"更好？**
- **如果我猜"这是 MAC 的 CRC32"，写进服务端代码，客户端可能不认。**
- **如果我写"未定"，后来的人看到会去查，不会被我误导。**
- **项目记忆里已经有过"把推断写成实测"导致整卷作废的教训（`lobby/74`）。**

**⇒ 所以"未定"不是偷懒，是**纪律**。**

## 五、`932` 也是"未定"，但我知道它的**边界**

**`932` 出现 352 次，是 `4/13`+`4/4` 的主值。**

**我没有解释它是什么，但我把它的**边界**画清楚了：**
- 它只在 `4/13`、`4/4` 出现（别的 task 一次都没有）。
- 它是 `4/13` 首 u32 的**常态值**（264/290）。
- 在唯一一个 run 里，它被 `100/108/113/118/123/135/148` 替代。

**⇒ "未定"但"边界清晰"，这是可以接受的状态。**

**★ 对比"完全未知"：如果我只知道"932 出现 352 次"，那没什么用。
  但我知道"它只在 service 4 出现，且是一个可变的首字段"，
  这就给了后来人一个明确的搜索方向：**service 4 是什么？****

**⇒ 未知字段也要给出"搜索边界"，不能只留一个数字。**

## 六、`0x08` 的"平庸"本身也是一条结论

**这一卷证明了 `0x08` 就是普通的 u32，没有隐藏结构。**

**但"平庸"值得写，因为：**
- **`0x08` 占 0.663% 的字节，是第四高频的标签。**
- **53.9% 是 0 或 1 ⇒ 它主要当"开关/序号"用。**
- **连续簇最多 4 个 ⇒ 它不是数组（数组走 `0x6b`/`0x6c`）。**

**★ 这三条一起，回答了"`0x08` 会不会像 `0x6c` 那样藏数组"这个问题 —— 不会。**

**⇒ 逐字节分析的很多结论是"排除法"：
  **"它不是数组""它不是哈希""它不是时间戳" —— 这些"不是"和"是"一样有价值。**

## 七、这一卷对"能写服务端"的贡献

**用户的目标是"能改大厅"。那这一卷给了什么可改的东西？**

**★ 三个"可改的请求参数"：**
1. `6/5` 的 maxResults=20（读更多排队消息）
2. `21/5` 的 playlist=10/50（找不同列表的房间）
3. `80/154`/`93/131` 的 SKU（买不同东西）

**★ 一个"可算的字段"：**
4. `80/119` 的过期时间戳 = now + 365 天

**★ 一个"不要乱改的字段"：**
5. `1800154382` 是账号 ID 派生 —— 改它必须连账号 ID 一起改。

**⇒ 这就是逐字节分析的产出：**不是"知道 932 是什么"，而是"知道哪些能动、哪些不能动、怎么动"。**

## 八、方法论收获（四条）

> **① 新魔数先做算术枚举（&/>>/<</+/-），再起语义名。**
>    `1800154382 = 账号ID 低32位` 就是这样定案的。**

> **② 时间戳类字段的验证方法：和 run 目录名的时间比，看差值是否恒为整数天/年。**
>    `80/119` 的 31536000 秒就是这样算出来的。**

> **③ 穷举失败也要写进论文，并写清"我试了哪些"。**
>    `31902622` 试了 68 种组合，全失败 ⇒ "未定"是结论，不是逃避。**

> **④ 未知字段要给"搜索边界"（只在哪个 task 出现、是固定还是可变）。**
>    `932` 就是这样：不知道它是什么，但知道去哪找答案。**
