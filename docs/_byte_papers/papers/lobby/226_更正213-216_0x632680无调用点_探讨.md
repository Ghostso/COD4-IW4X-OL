# 226 探讨 · 我这一轮两次踩了同一类坑：扫描器本身没验证

## 一、先说结论

这一轮（226）我做了一件"反悔"的事：**推翻自己 213–216 卷的整条开局链**。

推翻的理由不是"发现了新证据"，而是**"发现我的扫描器是坏的"**。

## 二、第一次：226 卷主线

从 190 卷起，我一直在说 `0x632680` 是"开局虚函数"，213 卷还列出了它的 6 道门。

这一轮我想找它的**调用点**（确认 `[ebp+8]`/`[ebp+0xC]` 从哪来）。

步骤：
1. 定 vtable 起点：从 `0xDC73B0` 往前找，得到 `0xDC7270`，发现那里是 COL 指针 → 真起点 `0xDC7274`
2. 读 COL 名 → `.?AVdwRoomImp@@`
3. 算槽号 → `0xDC73B0 - 0xDC7274 = 0x13C`
4. 扫 `call dword ptr [reg+0x13C]` → **0**

于是写论文说"`0x632680` 无调用点，213–216 的链是死的"。

## 三、第二次：写完论文后自查，发现扫描器有洞

写完 226 我认为可以收尾了。但顺手统计了"整个 vtable 88 个槽各自被调用几次"，结果：

```
+0x000 ~ +0x07C   30 个槽有虚调用（多的几百次）
+0x080 ~ +0x15C   0 个槽有虚调用
```

**87 个槽全部 0 次**——这显然不对。一个被大量使用的房间子系统，vtable 不可能只有头几个槽被调用。

于是我发现：**`call [reg+disp]` 的 disp < 0x80 时用 disp8（`mod=01`），只有 ≥ 0x80 才用 disp32（`mod=10`）**。

我的扫描器只扫了 `mod=10`。

**`+0x84`（SendReady）和 `+0x13C`（0x632680）都 ≥ 0x80，所以"只需 disp32"——对这个具体结论不影响。** 但"87 槽全 0"的整体统计在修正后变成了"30 槽有调用"（低槽）。

## 四、这暴露的更大问题

修正后仍然：**`+0x80` 以上 87 个槽的 `call [reg+disp]` 全为 0**。

包括 154 卷记录的 **SendReady `vt[33]` = `+0x84` = `0x6301A0`**。

所以要么：
- 调用形式不是 `call [reg+disp]`，而是 `mov edx,[eax+0x84] / call edx`（两跳）
- 要么 154 卷的槽号错了

我又试了统计 `mov reg,[reg+disp]`——88 个槽**全部**有命中。但这个统计**没用**：`[reg+0x84]` 这种偏移几乎所有类都有，无法区分是哪个类。

**所以"虚调用的确切形式"我没定下来。**

## 五、两次踩坑的共同点

| 轮次 | 扫描器缺陷 | 后果 |
|---|---|---|
| 206 卷 | 正则 `dc[0-9a-f]{4}` 只匹配 4 位（实际 6 位） | 得出"零 vtable 写入"的错误结论 |
| 226 卷 | 只扫 `mod=10`（disp32），漏了 `mod=01`（disp8） | 得出"87 槽全无调用"的错误统计 |

**两次都是同一个毛病：我没有先验证扫描器本身，就直接相信了扫描结果。**

★★★ **这应该成为一条硬规矩：任何"扫描结果为 0/全空"的结论，必须先用一个"已知非空"的样本来验证扫描器。**

226 卷的案例里，我本可以用"`+0x000` 应该被调用"（对象析构/构造一定调）来验证——它确实非空，所以扫描器至少对那一部分是好的；但低槽 0 就该触发怀疑。

## 六、诚实交代：现在还开着什么

1. **`0x632680` 的调用形式未定**（两跳？函数指针表？）→ 需要**带基址来源的数据流分析**
2. **`+0x80` 以上 87 槽的调用形式未定** → 与 154 卷冲突未解
3. **`[ebp+8]`/`[ebp+0xC]` 来源未定** → 216 卷的"服务端必须提供 u64"前提未验证

**这三条都属于"需要数据流分析"，不是"扫一遍就能定"。**

## 七、对服务端修复的直接影响

213–216 卷的推理链是：

```
0x632680 是开局虚函数（前提1）
  → 它有 6 道门（前提2：会被调用）
  → 服务端必须补 u64（结论）
```

**前提 2 未验证。** 所以"补 u64 就能开局"这个结论**现在是悬的**。

★ 在验证调用路径之前，**不应该按 216 卷的建议去改服务端**。
