# serialize 全台账 · 探讨：自动化把"92% 盲区"变成一张表

> 对应：`lobby/82_serialize全台账.md`

---

## 一、这一轮做了什么

**上一轮我说"50 个类只有 28 个 serialize，逐个人工读太慢"。**

**这一轮我写了个提取器：**

```python
扫描函数体内的 call 0xb77b10 / call 0xb777c0
往上追溯紧邻的 push 参数
输出 writeBits(n) / writeData(ptr, nbits)
```

**⇒ 30 个函数一次跑完，343 行脚本。**

---

## 二、自动化的关键点

**难点是"push 参数归属"：**

```asm
push 3            ← 给 writeBits 的位宽
mov ecx, ebx      ← 中间插了 mov
call 0xb77b10     ← writeBits
```

**我的处理：维护一个 `pend` 列表，遇到 `call` 就消费；
遇到 `mov` 就清空（因为它可能改变 ecx）。**

**⇒ 不完全精确，但足够读出"写了几位、什么宽度"。**

---

## 三、读出来的结构

**最有价值的三个发现：**

### 1. 统一头部

**28 个函数**全部**以 `writeBits(3) + writeData(&[obj+4], 8)` 开头。**

**⇒ 这是基类贡献的 11 位头。**

**⇒ 任何位流解析都可以"先读 11 位"。**

### 2. `0x15` 不是类型

**它后面跟 8/32/64 三种宽度。**

**⇒ 只能是"段标记"或"字段序号"。**

**⇒ 这与 `lobby/71` 从 `RoomInfo` 得出的判断一致 —— 
两处独立得出同一结论。**

### 3. 三个变长家族

```
0x10 + (len*8+8)     字符串
0x13 + 8 + 32位 + n*8  blob
1 位 + 变长           可选字段
```

**⇒ 和 ByteBuffer 的 `0x10`/`0x13` 完全同构。**

**⇒ 再次印证：两套序列化出自同一设计。**

---

## 四、这一卷的实际价值

**现在可以构造任何一条房间消息了：**

```
1. 选一个消息类（vtable 已知）
2. 按 serialize 脚本填充字段
3. 调 serialize
4. 位流字节化（ceil(bits/8)）
5. 装进 6/5 应答
```

**⇒ 缺的只剩"每个字段填什么值"。**

---

## 五、但"填什么值"仍是问题

**28 个 serialize 告诉我"写几位什么宽度"，
但没告诉我"这个数字代表什么"。**

**⇒ 业务语义仍需实机或报文对照。**

**⇒ 但这是"可现场试错"的层次，不是"结构未知"。**

---

## 六、方法论收获

> **把重复的阅读工作自动化，是提高逆向效率的关键。**

**28 个函数，人工读要 3 小时，写脚本 20 分钟 + 跑 2 分钟。**

**⇒ 而且脚本可复跑、可审计。**

**⇒ 这正是项目里"工具要可复跑"的要求。**
