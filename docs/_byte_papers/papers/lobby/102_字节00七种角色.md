# 第 102 卷 · 字节 `0x00` 的七种角色（全语料实测）

> 承接 `papers/01_终止符0x00.md`（那份只统计了"末尾连续 0 的个数"）
> 本卷把它升级为**按文法角色分账**，每个 0 都能说出它是谁。

## 2. 七种角色（互斥分账，覆盖 100%）

| 角色 | 含义 | 0x00 个数 | 占全部 0 | 覆盖字节数 |
|---|---|---|---|---|
| **T** | 终止符（payload 尾部那串） | **6,848** | 2.66% | 6,848 |
| **S** | 字符串内容的 NUL 结尾 | **5,006** | 1.95% | 1,067,971 |
| **F** | 整型字段载荷里的 0 | **184,074** | **71.59%** | 319,139 |
| **B** | blob / 数组载荷里的 0 | **53,483** | 20.80% | 187,761 |
| **L** | 长度前缀 / 子标记里的 0 | **7,715** | 3.00% | 14,114 |
| **H** | 标签字节本身 | 0 | — | — |

**⇒ 最大的来源不是"终止符"，而是"整型字段载荷"（71.6%）。**

**这一条直接把旧认知推翻了：0x00 的主要身份是"小整数的三个零字节"，不是"记录结束"。**

---

## 3. 角色 T：终止符 —— 6,848 次，一条不多一条不少

**6848 条 payload，每条的最后一个字节都是 `0x00`（100%）。**

**⇒ 终止符是"每条恰好一个"的协议常量。**

**★ 但注意 §7：尾部连续多个 0 时，只有最末那个是纯终止符。**
**其余的是"字段值恰好为 0"叠上去的。**

---

## 4. 角色 S：字符串 NUL —— 5,006 次

**字符串（`0x10`）是"直到 NUL 结束"的格式，所以每个非空字符串恰好贡献 1 个 0x00。**

```
5,006 个 0x00 = 5,006 个字符串字段（与 01_终止符 卷的"0x10 = 5006 次"逐字吻合）
```

**⇒ 这是一条双向校验：字符串出现次数 == 字符串 NUL 个数。**
**⇒ 两者独立统计却完全相等，说明文法解析没有任何遗漏。**

**★ 空字符串 `10 00` 也占 1 个 NUL，含在这 5006 里。**

---

## 5. 角色 F：整型字段载荷 —— 184,074 次（最大来源）

**按标签分开统计"整个字段值全零"的比例：**

| 标签 | 宽度 | 全零次数 | 非零次数 | 全零率 |
|---|---|---|---|---|
| `0x01` bool | 1B | 3 | 326 | 0.9% |
| `0x03` u8 | 1B | 3 | 18,967 | **0.02%** |
| `0x06` u16 | 2B | 88 | 179 | **33.0%** |
| `0x07` i32 | 4B | 1,788 | 10,846 | **14.2%** |
| `0x08` u32 | 4B | 1,725 | 4,644 | **27.1%** |
| `0x09` i64 | 8B | 0 | 0 | —（零样本） |
| `0x0a` u64 | 8B | 850 | 19,675 | **4.1%** |

**⇒ 规律极其干净：宽度越大，全零率越高。**

**⇒ 因为值域小的字段都用 `0x03`（u8），它们几乎不会是 0（0.02%）。**
**而 `0x06`/`0x07`/`0x08` 装着"有时为 0 的玩家数据"（击杀数、配置值），
所以三分之一是 0。**

**★ 推论：如果某个 u32 字段的全零率**低于** 27%，说明它承载的是"恒非零"的量
（如 ID）；如果**高于** 27%，说明它多数时候闲置。**

## 6. 角色 B：blob / 数组载荷 —— 53,483 次

**blob（`0x13`）内部 28.48% 是 0x00 —— 比整型字段的 57.68% 低。**

**分布（blob 内 top10）：**

```
00: 28.48%   01: 1.56%   20: 1.53%   2b: 1.43%   ff: 1.02%
02: 0.87%    08: 0.86%   40: 0.84%   80: 0.84%   41: 0.79%
```

**⇒ `0x20`(空格)、`0x2b`(＋)、`0x41`(A)、`0x40`(@) 高频
⇒ 大量 blob 是 base64 文本（`sv_post_options AAAA...==`）或序列化结构。**

**★ 关键反证：0x70（'p'）在 blob 里出现 622 次，
接近均匀期望 733 —— 说明 blob 载荷**没有**对 0x70 的任何偏好。
它只是一个普通字节值。**

## 7. 尾部连续 0 串的真实构成（把角色串接起来看）

**旧版论文说"连续 N 个 0 = N-1 个空字符串 + 终止符"。这个解释只对了一部分。**

**实测：把末尾连续 0 串按"角色序列"归类，前 8 类：**

```
ST          ×2329   ← ★ 空字符串的 NUL + 终止符   （旧论文的解释，占最多）
T           ×1362   ← 纯终止符（前一个字段非零）
FFFT        ×961    ← 3 字节整型字段恰好为 0 + 终止符
FFFFT       ×732    ← 4 字节整型字段恰好为 0 + 终止符
FFFFFFFT    ×371    ← 7 个 0 = 102/7 的 u64 零值 + 终止符
FFT         ×265
FFFFFFFFT   ×172    ← 8 字节 u64 零值 + 终止符
BBBLLLLT    ×159    ← blob 数据尾 + 长度/计数 + 终止符
```

**⇒ 八类里只有 `ST` 和 `T` 是"纯协议"；
其余六类都是"字段值恰好为 0"的假象。**

**★ 这解释了旧论文为什么会被误导：
它看到"末尾 2 个 0 最多（2562）"，就归因为"空字符串常见"。
其实 2562 里 2329 是 ST（确实如此），
但 7 个 0（18327 次）它完全没法解释 —— 那就是 `102/7` 的 u64 零值。**

## 8. 角色 L：长度前缀里的 0 —— 7,715 次

**`0x13 08 <u32 len>` 与 `6b/6c 08 <u32 blen> <body> <u32 cnt>` 的长度字段是 u32。**

**小长度 ⇒ 高 3 字节全 0。**

```
0x13/6b/6c 共 1749+203+159 = 2111 个元素
每个贡献 3 个必零字节（u32 高三位）≈ 6333
再加上 <u32 cnt> 的 3 个 ≈ 700
⇒ 合计约 7000，与实测 7715 吻合
```

**⇒ L 类的 0 是"小端 u32 的高位"，属于结构性冗余。**

## 11. `0x00` 能作为"标签"出现吗

**能，但只有一种情况：终止符本身。**

**文法里 `0x00` 是保留字：遇到它就"吃掉后面所有连续的 0 并结束解析"。**

**⇒ 因此 `0x00` 在所有数据位置（S/F/B/L）都是**被动**的，
唯一**主动**的用法是 T。**

**★ 这条很重要：如果我在构造 payload 时在数据中间插入一个 0x00，
客户端会把它当终止符 —— 这就是"字段值含 0"必须用定长编码而不是字符串的原因。**
