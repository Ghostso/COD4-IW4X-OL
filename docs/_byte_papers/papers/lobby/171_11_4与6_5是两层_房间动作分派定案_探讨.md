# 171 探讨 · 为什么"分派缺失"这个诊断一开始是错的

## 一、被问的是什么

用户问："目前房间问题全部修复了吗？例如准备，加入阵营，投票选图。"

上一轮我给出的诊断是：`lobby_server.py` 里没有 `changeteam`/`votemap` 分支，服务端"没有分派"，所以这三件事都没修好。

**这个诊断有两处站不住。**

## 二、第一处：把"客户端没发"当成"服务端没派"

我先 grep 了服务端源码，找到"没有 change team 分支"，据此判定缺陷在服务端。

但真正的问题是：**客户端到底发没发这条消息？** 我没查。

查了 33 个 run、全部明文日志之后：

```
service=11 出现过 329 次，task 只有 2 / 4 / 13
service=11 task=14  —— 0 次
service=11 task=15  —— 0 次
service=11 task=26  —— 0 次
```

客户端**从来没有发出过**任何一条"改阵营"或"投票"的请求。服务端没有对应分支，是因为**根本没人发过**，不是因为服务端写漏了。

> ★ 教训：「服务端缺少 X 分支」和「客户端需要 X 分支」是两个独立命题。
> 前者可以靠 grep 证实，后者必须靠抓包证实。**只做前者就把结论写死，是越权。**

## 三、第二处：把"类型表存在"当成"这条报文里一定出现"

138 卷整理出 47 种 `dwRoomMessage` 类型号，我据此推断 `11/4` 的 batch 里会出现 `0x10/0x14/0x15/0x1A`。

**全量 251 条真实 `11/4` 的 batch 内层首字节只有 `0x02`（188）和 `0x18`（63）。**

47 类型表是存在的，但它挂的容器是**另一个**：`6/5` 的 Manifold 位流。反汇编里 `0x634870` 那段

```
cmp eax, 0x2e
jmp dword ptr [eax*4 + 0x636f3c]
```

就是 47 槽跳表本身 —— 它在读 `6/5` 应答的位流，不在读 `11/4` 的 batch。

> ★ 教训：**"表存在"≠"这张表在我要分析的那层上生效"。**
> 类型号是从哪里读出来的（`push 3` → `push 8` 两个 ReadBits），决定了它属于哪一层。

## 四、这轮真正带回的东西

### 1. 一个恒为 False 的判据

我上一轮刚写进 `lobby_server.py` 的 `_is_ready_bitstream()`：

```python
tag = b[0] >> 5
typ = ((b[0] & 0x1F) << 3) | (b[1] >> 5)
return tag == 0 and typ == 0x10
```

在 251 条真实 batch 上**全部返回 False**。

原因很朴素：真实 `batch` 的开头是 4 字节内层长度，`batch[0]` 是 `0x91`/`0x7b`/`0x8d`/`0x11` 这类值。用它们做"3 位 tag + 8 位 type"的解码，得到的当然永远是垃圾。

**我上一轮把这条写进去时，"验证"是拿我自己构造的 `b"\x02\x18"` 测的 —— 那个字节串是我从位流格式推出来的，不是从抓包里拿的。** 用推导值验证推导值，测了等于没测。

### 2. 真正的 ready 判据

```
batch[0:4] = u32 innerLen
inner      = batch[4:]
ready ⟺ inner[0] == 0x18 且 len(inner) == 17
room  ⟺ inner[0] == 0x02
```

251/251 成立，零例外。简单到不需要位运算。

### 3. 两层协议必须分开修

- `11/4`（setRoomData）：房间状态同步。服务端要**广播**给同一房间的其他连接。
- `6/5`（pull messages）：消息队列拉取。服务端要在应答里回 Manifold 位流。

现在两层的代码都在，但都没通：`11/4` 的 ready 判据是死的，`6/5` 回的是 `count=0` 空位流。

## 五、诚实的部分

"加入阵营"和"投票"我**没法说修好了**，因为：

1. 客户端一次都没发过 —— 没有样本可对齐；
2. 客户端侧的 vtable 槽位（`0x628260` 读 ChangeTeam）确认存在，但**写侧在哪、由哪个 UI 回调触发**，本卷没查到；
3. 47 类型表里 `0x14`/`0x15`/`0x1A` 的分派槽（`0x636F3C + n*4`）未逐个展开。

这三条都得等有真实流量才有意义。**在客户端不发的前提下，服务端"补一个分支"是纯粹的空转。**

## 六、方法上值得留下的两条

1. **任何"判据/修复"，落地前必须先在全部真实样本上跑一遍命中率。** 命中率 0 就说明它描述的不是这层协议。
2. **反汇编里找 `cmp reg, N` + `jmp [reg*4 + 表]`，一次就能把"分派器"和"表"绑在一起。** 比按类名 grep 可靠得多。
