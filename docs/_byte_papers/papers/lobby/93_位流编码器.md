## 2. 位序：这是唯一还没定的东西

**`writeDataCore`（`0xB777C0`）的实现里用 `msb_index` 定位起始位：**

```
0xb77acf  call 0xb75d40     ; msb_index(range)
0xb77ad7  inc  eax
...
0xb77af5  call 0xb777c0     ; writeDataCore
```

**⇒ 位是从**高位往低位**填的（MSB-first）。**

**⇒ 但这是**静态推断**，我没有一条真实位流对照。**

**⇒ 编码器默认 MSB-first，同时提供 `--lsb` 开关。**

**★ 第一次实测时，两个模式各发一次，看哪个客户端能认——这是最省事的验证。**

## 3. 生成的样本（MemberList，N=1）

**输入：1 个成员，全零字段。**

```
总位长 775 = 50 + 725
76 位 = 96.875 → 97 字节
hex:
18 05 40 00 00 00 14 00 00 00 00 00 00 00 00 30 00 aa 00
01 50 00 0a 80 54 02 a0 00 00 00 00 00 00 00 15 00 00 00
00 0a a0 15 00 a8 00 05 40 00 2a 00 01 50 00 0a 80 00 54
02 a0 00 15 00 a8 00 00 00 05 40 00 00 00 2a 01 50 00 00
00 0a 80 00 00 00 54 00 20 82 08 20 aa 00 00 00 00 30 01
80 04
```

**手解前两个字节验证：**

```
0x18 = 0001 1000
       00011  ← 前 5 位 = 0x03  ✓ 消息类型号
       000    ← 后 3 位 = 接下来 8 位的高 3 位

0x05 = 0000 0101
0x40 = 0100 0000
接起来：000 0000 0101 0100 0000 ...
              ↑ 前 8 位 = 0x05？还是 0x2A？
```

**⇒ 这里就暴露了位序问题：如果 MSB-first，8 位类型值是
`0x00`（从 0000 0101 0100 0000 取前 8 位 = `0000 0101` = 5）。**

**⇒ 看起来合理（类型值 5）。这也侧面支持 MSB-first。**

## 4. 编码器与逆向表的对账

| 消息 | 逆向表位长 | 编码器输出 | 差 |
|---|---|---|---|
| `ChangeTeam` | 169 | 169 | 0 |
| `Score` | 161 | 161 | 0 |
| `Card` | 118 | 118 | 0 |
| `UpdateWarGodData` | 100 | 100 | 0 |
| `UpdateDlcLevel` | 26 | 26 | 0 |
| `SetPilot` | 26 | 26 | 0 |
| `Leave` | 82 | 82 | 0 |
| `RequestMemberList` | 13 | 13 | 0 |
| `MemberList` N=1 | 50+725 | 775 | 0 |
| `MemberList` N=8 | 50+5800 | 5850 | 0 |

**⇒ 9/9 精确吻合。**

**⇒ 这本身也是一次"表自洽性"验证：
如果表里有加减错误，编码器算出来不会刚好等于解码器算出来的。**

## 5. 这个编码器能做什么、不能做什么

**能：**
- 生成任何定长消息的精确位流
- 生成任意 N 个成员的 MemberList
- 双位序（MSB/LSB）切换
- 逐字段注释

**不能：**
- **不知道"消息类型号"的真实取值**（现在写 0，实际要填对）
- **不知道字段的真实业务值**（坐标、等级、状态等）
- **不知道封包层**（这条位流怎么塞进 Demonware 的报文里）

**⇒ 前两个必须实测，第三个见 `lobby/60`/`61`（ByteBuffer 层已全解）。**
