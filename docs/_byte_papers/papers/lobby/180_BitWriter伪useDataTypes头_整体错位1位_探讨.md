# 180 探讨 · "109 字节"这个数字骗了我四卷

## 一、这次找到的 bug 藏了四卷，原因是算术巧合

`build_startgame_payload` 一直产出 **109 字节**。
所有卷（169/175/176/177/178）都用"109 字节"当"结构正确"的证据。

这轮算清楚了：

```
无伪头：5 + 8 + 578 + 106 + 170 = 867 位 → ceil(867/8) = 109 字节
有伪头：      868 位 → ceil(868/8) = 109 字节
```

**两个都是 109。**

这就是为什么四卷都没发现——**字节数不变，只有内部错位 1 位**。

★ 这和 175 卷"51 位和 50 位都补到 7 字节"是同一类陷阱，我又踩了一次。

## 二、这次怎么发现的

不是靠"109 字节"这个数字，而是靠**读第一条业务指令**。

写侧 `0x625520`：

```asm
0x625533  mov al,[edi+4]    ; type
0x625536  push 3            ; ★ 第一条业务指令
0x625542  call 0xB77B10
```

读侧 `0x6256C0`：

```asm
0x6256E4  push 3            ; ★ 第一条业务指令
0x6256F0  call 0xB774E0
```

**两侧都直接 `push 3`，中间没有任何 `write(1)` / `read(1)`。**

而 `lobby_server.py` 里是：

```python
if use_data_types:
    self.write_bits(1, 1)   # ← 客户端没有这个
```

## 三、这个"头"是怎么被编出来的

我查了 `0xB77A70`，里面**确实有一段包装头代码**：

```asm
0xB77A73  cmp byte ptr [ebp+0x14], 0
0xB77A82  je  0xB77AC3          ; == 0 跳过
0xB77A84  push 0xC  / call 0xB77B10   ; W_TAG(12)
0xB77A91  push 8    / call 0xB77B10
0xB77A9A  push 0x20 / call 0xB777C0
0xB77AAA  push 8    / call 0xB77B10
0xB77AB3  push 0x20 / call 0xB777C0
```

看起来非常像"数据段包装头"。

但再看 `0xB77B10` 怎么调的：

```asm
0xB77B1C  push 0        ; ← 第 4 个 push
0xB77B1E  push 0x1F
0xB77B20  push 0
0xB77B22  push eax
0xB77B23  call 0xB77A70
```

**第 4 个参数 = 0。** cdecl 从右往左压栈，`push 0` 是最右边的参数，对应 `[ebp+0x14]`。

⇒ `cmp byte [ebp+0x14], 0 / je` ⇒ **直接跳过。**

★ **原作者看到了这段代码，但没查它有没有被启用。**

## 四、这条错误的实际后果

如果这个 bug 存在：

- `dwRoomMessageStartGame` 的 109 字节，从第 0 位就是错的
- 客户端 `R_TAG(3)` 读前 5 位，读到的是"伪头 1 位 + tag 3 的高 4 位"
  - 实际读到 `00001` = 1，期望 3 → **失败退出**
- 所有基于它的推送全废

**而日志里看起来一切正常**：`推送 109 字节`、`应答成功`。

## 五、这一串更正的规律

从 169 到 180，Manifold 位流被改了四次：

| 卷 | 更正的什么 | 根因 |
|---|---|---|
| 177 | 位宽模型 → 5 位标签 | 只读了 `0xB77B10` 前 6 条 |
| 178 | MSB → LSB | 只看了 `shl`，没看掩码 |
| 180 | 去掉伪头 | 只看了"有这段代码"，没看"启用条件" |

**三次都是同一个毛病：读得不够深，或者读到了但没查条件。**

## 六、我现在的诚实评估

房间类已经找到**三个致命 bug**（都是"服务端按错误模型生成字节"）：

1. `ROOM_READY_BATCH` 16 字节常量（ol-mod 3.3.3.3 的抓包）
2. `_is_ready_bitstream` 判据恒 False（漏了 4 字节长度前缀）
3. **`BitWriter` 伪 1 位头（整体错位）**

前两个是"判据错"，第三个是"生成错"。

**但我依然不能说房间类修好了**，因为：

- 这三条全是静态推出，**没有一条被真实样本验证过**
- 客户端收到正确字节之后会不会进房间，**没有任何证据**
- `srpc+0x4F4` 那个闸门开没开，**没测过**

## 七、关于"房间类永远有大型致命黑箱"

我现在理解这句话的真正含义了。

不是因为"结构解不出来"——结构我已经解到地址级。
是因为**每解一层，都会暴露下层还有一层**：

```
判据对不对？ → 查真实报文 → 33 个 run 全是空应答
格式对不对？ → 查真实位流 → 从没真实传输过
闸门开没开？ → 需要运行时状态
```

而且每层都需要"客户端真实反应"才能收敛，这个东西**只能实机拿**。

★ 我能做的是**把静态能推到的最深处推到，并且每一条都标注证据强度**。

这轮做到的：**找到第三个致命 bug（伪头）并修掉**，且验证了 109 字节的位运算自洽。

下一条可以静态做的：**`build_room_push` 的信封层**（`u32(8)+sender+room_id+blob+u32(0)`）是否也用了错误模型。那是 TLV 不是位流，我还没核。
