# `IWff0100` 的最终结论：解密不在此分支，也不在 IFS 层

> 承接 `lobby/35`、`lobby/36`
> 本轮完成对这条分支的完整追踪。

---

## 1. 结论先行

**`IWff0100` 分支在本 build 里不做解密。**
**它只做：校验魔数/版本 → 读头字段 → 注册到全局表 → 链接。**

**且 IFS 层也不解密（`.ifs` 内与磁盘独立的同名 `.ff` 字节不同，但都是高熵）。**

---

## 2. 完整证据链

### 2.1 分派器只校验，不解密

`0x483db0`（`this` 方法，被 `0x49f07d` 唯一调用）：

```
读 8 字节 → cmp "IWff0100" → 匹配则 jmp 0x483e2b
                        → cmp "IWffu100" → 不匹配则报错
0x483e2b: 读 u32 版本 → 必须 == 461
0x483e68: 读 1+4+4+8 字节字段
0x483e94: 再次 cmp "IWffu100" → 不等则 jne 0x483ee4（跳过解密）
0x483ed3: call 0x483b40（只有 IWffu100 才到）
```

**`IWff0100` 永远走 `0x483ee4`，不调用 `0x483b40`。**

### 2.2 跳过后的动作是"登记"，不是"解密"

`0x483f41`–`0x483f82`：

```
mov [0x2f79af4], [ebx]
mov [0x2f79af8], [ebx+8]
mov [0x2f79afc], [ebx+0x10]
mov [0x2f79b00], [ebx+0x18]
mov [0x2f79b04], [ebx+0x20]
mov [0x2f79b08], [ebx+0x28]
mov [0x2f79b0c], [ebx+0x30]
mov [0x2f79b10], [ebx+0x38]
```

**把加载器结构里的 8 个 u64 抄到全局表。**

**注意：源是 `ebx`（加载器对象），不是 `.ff` 文件头。**

### 2.3 反向验证：`.ff` 头后的 8 个 u64 不是偏移

实测 `mp_playlists.ff` 的 `+0x14` 起：

```
0xe2c1d35735ed9100  = 16,339,573,294,597,247,232
0xc8c8390f770741c6  = 14,467,876,541,511,975,366
0x55b1fe33ffad1327  =  6,174,996,063,387,980,583
```

**全部远大于文件长度 49,493。**

**⇒ 这些是密文，不是指针。**

### 2.4 AES 解密循环的两个入口都被同一个门挡住

`0x4834f0`（8192 字节块 AES 解密）有两个调用点：

| 调用点 | 前置条件 |
|---|---|
| `0x484a48` | `cmp [0x1c4b700], 0; jne → 不调用` |
| `0x4a0cd8` | 同上 |

**`0x1c4b700` 只在 `IWffu100` 分支（`0x483b49` 的 `push 0x6044 / push 0 / push 0x1c4b700` + memset）被置位。**

**⇒ 对磁盘上的 `IWff0100`，这条解密循环从不执行。**

### 2.5 全量样本一致性

| 文件 | 大小 | magic | ver | f12 | f16 | 熵 |
|---|---|---|---|---|---|---|
| `mp_playlists.ff` | 49,493 | IWff0100 | 461 | 1 | 0 | 7.947 |
| `common_mp.ff` | 77,605,093 | IWff0100 | 461 | 1 | 0 | 7.950 |
| `common_loadscreen.ff` | 24,885 | IWff0100 | 461 | 1 | 0 | 7.959 |
| `localized_common_mp.ff` | 192,434 | IWff0100 | 461 | 1 | 0 | 7.959 |
| `code_pre_gfx_mp.ff` | 74,085 | IWff0100 | 461 | 1 | 0 | 7.958 |

**5 个、跨 3 个目录，头字段完全一致，每 4KB 熵全在 7.95–7.96。**

### 2.6 `.ifs` 内 vs 磁盘独立：不同字节

同一个 `common_mp.ff`：

| 来源 | 大小 | MD5 |
|---|---|---|
| `.ifs` 内嵌（`ff_init_common_mp_V111.ifs` @ `0x15d`） | 77,817,667 | `b6ec57d45598cb80503f698adf734a44` |
| 磁盘独立（`backups\GOLDEN_RUNTIME_...\sandbox\`） | 77,605,093 | `14f1ee908f9d59d72ea2034c7a1e2443` |

**大小差 212,574 字节，内容完全不同。**

**但两者都是高熵（7.950）。**

---

## 3. 这三个事实合起来意味着什么

```
① IWff0100 加载路径不解密
② AES 解密循环被 IWffu100 专属门挡住
③ .ifs 内与磁盘版本的 .ff 字节不同、且都是高熵
```

**结论：**

> **`.ff` 的内容在磁盘上永远是熵 7.95 的密文。
>  解密发生在"读取之后、使用之前"的另一层，
>  且这一层不参与 .ifs 打包（所以两份字节不同）。**

**最可能的位置：**

1. **游戏运行时由 TP3 保护层在内存中解密**
2. **或由 `IFS2.dll` / `IIPSVFS.dll` 的某个 RWFilter 在 VFS 读时解密**

---

## 4. 为什么之前的所有尝试都失败

| 尝试 | 失败原因 |
|---|---|
| 在 `.ff` 里找 RSA 块 | **假阳性**（8192 个窗口 × 1/65536 ≈ 12.5% 命中率） |
| 用 `0x483b40` 的 RSA+AES 链 | **该链只服务 `IWffu100`，磁盘上没有这种文件** |
| 前 16 字节解出 `IWffs100` | **CFB 首块只依赖 IV，反推必然成立** |
| 每块重置 / 换 IV / 换模式 | 都是在一个**不该被走的代码路径**上调参 |

---

## 5. 下一步（明确）

**不再调参数。改为找"读取之后、使用之前"那一层。**

候选：

1. `IIPSVFS.dll` 的 `ICreateCoderRWFilter` / `ICreateZlibRWFilter`（已读过，是半字节表和 zlib，未见 AES）
2. `IFS2.dll` 的扇区读取函数（`SFileRead` 系列）—— 看是否在返回前解密
3. TP3 保护层（`.tp3` / `.tvm0` 段）

**第 2 条最直接**：`IFS2.dll` 有 `ReadFile` / `MapViewOfFile` 导入，
且日志串里有 `_ReadHead fails`、`[VFS]_mount file open fails`，
说明它是真正的 IFS 读取实现。
