# 191 · ★★★ 更正 186/188/189：`+0x7238` 是**独立 MatchMakingInfo 单例**，不是数组末元素

> 卷次：191（**第四次更正卷**）
> 方法：把两段 49 次循环之间的 `0x637D4F..0x637D88` 单独看
> 结论：`+0x7238` 是一个**独立对象**（写 vtable + 构造 `+0x7360` / `+0x7468`），数组 B 的区间到 `+0x7230` 就结束了。

---

## §0 决定性证据

### 0.1 数组 B 的真实区间

```asm
0x637D8D  mov dword [ebp+8], 0x31        ; 49 次
0x637D94  lea esi, [ebx + 0x7238]
0x637DA0  mov edx, [esi - 0x23C]
0x637DA6  sub esi, 0x238                  ; 先减
0x637DAC  mov [esi - 8], 0xDC79F0         ; 元素起点 = esi-8
```

第 1 次：`esi = 0x7238 - 0x238 = 0x7000`，元素起点 `0x6FF8`
第 49 次：`esi = 0x7000 - 48×0x238 = 0x7000 - 0x6A80 = 0x580`，元素起点 `0x578`

⇒ **数组 B 覆盖 `[0x578, 0x7230]`**（末元素 `0x578+0x238 = 0x7B0`... 等等）

★ 重新算：末元素起点 `0x578`，加 `0x238` = `0x7B0`。

⇒ **数组 B 覆盖 `[0x578, 0x7B0]`**，**不含 `+0x7238`**。

### 0.2 `0x637D4F..0x637D88` 是独立对象

```asm
0x637D4F  mov eax, [ebx + 0x723C]         ; 取某指针（多重继承的 vbptr）
0x637D55  mov dword [ebx+0x7238], 0xDC79F0  ; ★ vtable#1 @ +0x7238
0x637D5F  mov dword [ebx+0x7240], 0xDC79FC  ; ★ vtable#2 @ +0x7240 (= +0x7238+8)
0x637D69  mov ecx, [eax+4]
0x637D6C  mov dword [ecx+ebx+0x723C], 0xDC7A08  ; ★ vtable#3 @ +0x723C (= +0x7238+4)
0x637D77  lea ecx, [ebx + 0x7360]          ; ★ 构造成员 @ +0x7360
0x637D7D  call 0xB95AA0
0x637D82  lea ecx, [ebx + 0x7468]          ; ★ 构造成员 @ +0x7468
0x637D88  call 0xB757E0
```

★★ **这是一个完整的 `MatchMakingInfo` 单对象**，位于 `dwRoomImp + 0x7238`，
成员 `+0x7360`（= 对象+0x128）和 `+0x7468`（= 对象+0x230）分别对应 vtable[0] 里
`lea [esi+0x128]` 和 ctor 里的 `lea [edi+0x230]`。

⇒ **`+0x7238` 是 `dwRoomImp` 里的一个 `MatchMakingInfo` 成员对象**，不是数组元素。

### 1.1 两个数组到底是什么

```
数组 A: [0x76A8, 0xE368]  （起点 0xE128 - 48×0x238 = 0x76A8）
数组 B: [0x578,  0x7B0]
单例 C: 0x7238 ~ 0x7238+0x238 = 0x7470
```

★ 数组 A 与单例 C 有轻微重叠（`0x76A8 < 0x7470`）—— 但两者都是 `MatchMakingInfo`，
**可能是同一个数组的不同视图，或者我的起点算法仍有偏差**。

所以"起始 esi" 本身可能是**数组末尾之后的哨兵**。

## §3 `+0x18` 的新定位方向

既然 `MatchMakingInfo` 的所有序列化器都没有 `+0x18`，那么：

**`0x625CE0` 的 `[esi+8]` 指向的必须是另一个类。**

`0x634B0D` 把 `ebx+0x7238` 赋给 `[ebp-0xC90]` —— 但 `ebx+0x7238` 是 `MatchMakingInfo`。

⇒ **只有两种可能：**
1. `MatchMakingInfo+0x18` 确实存在但**从没被 MMI 自己的方法访问**（只有 `StartGame` 用）
2. `0x634B0D` 那条路径**根本不执行**（`clientState==0` 且未连接）

★ 190 卷已证：`clientState==0` 时构造的是 `StartGame`，`!=0` 时构造 `StartGameFailed`。
⇒ **`0x634B0D` 那条路径（`clientState==0`）在"未连接"时跑，此时没有对端数据可解析。**

⇒ **可能 1 更可能：`+0x18` 是 `MatchMakingInfo` 的"外部注入缓冲"，
    MMI 自己的序列化器不管它，只有 StartGame 消息用它传一段不透明数据。**

## §4 方法论

1. **★★★ 「两段相同循环之间」的代码容易被忽略，但往往是"单例初始化"。** `0x637D4F..0x637D88` 就是。
2. **★★ `sub reg, stride` 后再写 `[reg-disp]`，说明起始 `reg` 是"末尾之后"。** 这一步我连续三轮算错过。
3. **★★★ 一个类"没有某字段的访问点"，但另一个类读它 ⇒ 那字段可能是"外部注入缓冲"。** 这是本卷对 `+0x18` 的新假设。
4. **★★ 四次更正（184→185→186→188→189→191）说明"步进/起点"这类算术必须写脚本验算，不能心算。**
