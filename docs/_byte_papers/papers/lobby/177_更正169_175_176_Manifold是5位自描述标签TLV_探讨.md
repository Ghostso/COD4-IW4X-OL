# 177 探讨 · 我连续四卷读错了同一个函数

## 一、事情是这样的

从 169 卷开始，我一直在说 Manifold 位流是：

```
[3 位 tag][8 位 type][8 位 0][32 位 count]
```

这个模型被 169、175、176 三卷反复确认、写进代码、还"位级对账通过"。

**它是错的。**

真相：

```
[5 位 标签=3][8 位 type][5 位 标签=8][32 位 count]
```

区别在哪：`push 3` 我读成"写 3 位"，实际是"写 5 位，值是 3"。

## 二、为什么会连错四卷

因为我每次只读了 `0xB77B10` 的**开头**。

```asm
0xB77B10  push ebp
0xB77B11  mov ebp, esp
0xB77B13  cmp byte ptr [ecx+0x21], 0
0xB77B17  je  0xB77B28          ← 到这里我就停了
0xB77B28  pop ebp
0xB77B29  ret 4
```

`je` 跳到的地址是 `0xB77B28`，紧接着就是 `pop ebp / ret`。**看起来这个函数就是"查个 flag，然后返回"。**

但实际上 `je` **没跳**的时候（正常路径），中间还有：

```asm
0xB77B19  mov  eax, [ebp+8]     ; n
0xB77B1C  push 0
0xB77B1E  push 0x1F             ; ★ 31
0xB77B20  push 0
0xB77B22  push eax
0xB77B23  call 0xB77A70         ; ★ 真正的写
```

我上一轮（174 卷）确实读到了 `call 0xB77A70`，但当时我判断它是"零填充"，因为 `push 0 / push 0x1F / push 0` 看起来像 `(start=0, end=31, value=0)` —— 也就是"把 0..31 位清零"。

**这个解读在参数顺序上就错了。** 真实顺序是 `(n, start=0, end=31, flags=0)`，`n` 是第一个参数。

## 三、怎么发现的

这次我为了回答"房间类全闭合"，回头重新读 `0xB77B10`。

发现 `0xB77A70` 里有一行：

```asm
0xB77ACF  call 0xB75D40
0xB77AD7  inc  eax
```

我 176 卷已经逆出 `0xB75D40` = "位宽（找最高有效位）"。`0xB75D40(31) + 1 = 5 + 1 = 6`？

不对，再看寄存在哪：

```asm
0xB77AEB  push eax             ; 位数
0xB77AEF  mov [ebp+0x14], ecx  ; 值 = min(n,31)
0xB77AF5  call 0xB777C0        ; 写
```

`eax` 是位数，`[ebp+0x14]` 是值。而 `0xB777C0` 的签名（我这次也读了）是 `(stream, ptr, nbits)`。

**所以：写 `eax` 位，值是 `min(n,31)`。而 `eax` 来自 `bits_of(31)=5`。**

## 四、最硬的一条证据

真正让我确认的，不是上面那些算术，而是**读侧**。

`0x6256C0` 里：

```asm
0x6256F0  call 0xB774E0     ; R_TAG(3)
0x6256F5  test al, al       ; ★ 检查返回值
0x6256F7  je   0x62570F     ;   失败就退出
```

**如果 `0xB774E0` 只是"读 n 位"，它的返回值不可能是有意义的 bool。** 读 3 位、读 8 位，读多少都不产生"成功/失败"。

只有一种设计需要返回 bool：**读固定 5 位，然后与期望标签比较**。

我读了 `0xB774E0` 内部：

```asm
0xB77509  call 0xB77630     ; 读
0xB77517  mov  esi, [ebp-0x58]   ; 读到的值
0xB7751A  cmp  esi, eax          ; eax = 期望 n
0xB7751C  sete bl                ; ★ bl = (读值 == n)
```

**坐实了。**

## 五、这条错误的代价

如果我没发现，会发生什么：

服务端生成 `count=0` 的应答时，我现有代码产出 `00 00 00 00 00 00 00`（全零，7 字节）。

真实格式应该是 `18 02 00 00 00 00 00`。

**客户端收到全零后：**
- `R_TAG(3)` 读第一段 5 位 = `00000` = 0，期望 3 → **不匹配 → 直接失败退出**

于是客户端认为这条应答无效。而我在日志里会看到"应答已发送 (7 字节)"，一切正常。

**这就是那种"静态全对、实机全错"的典型。**

## 六、前几卷那些"验证"为什么没抓到

169 卷说"3+8+8+32 = 51 位 = 7 字节，与 67 卷观察到的 7 字节头吻合，**反向验证结构**"。

这个"反向验证"是假的：
- 51 位 → 7 字节（补 1 位）
- 50 位 → 7 字节（补 6 位）

**两个模型都得 7 字节。** 字节数对不上位宽。

我在 175 卷甚至把这个当成"铁证"写进论文。**用总字节数验证内部位宽，本来就不成立。**

## 七、我现在给这条结论多强的把握

诚实说：

- **「5 位标签」**：强。三重证据（`0x1F` 钳位 / 读侧 bool 检查 / 读写对称）。
- **「50 位头」**：强。5+8+5+32 直接相加。
- **「MSB-first」**：弱。只是从 `0xB777C0` 的 `shl` 方向推断。
- **「item 48+len×8」**：中。对称性支持，但 `eax|ecx != 0` 那个条件分支没完全展开。
- **实机对账**：**零**。33 个 run 的 6/5 全是空应答，客户端从没收到过位流。

**所以我不敢说"这条已经证实"。我说的是"这条有强静态证据，且旧结论有明确的反证"。**

## 八、教训

1. **读到 `ret` 为止。** `je` 跳到的地址紧接着 `ret`，不代表函数就结束了 —— 它是错误分支。
2. **`push imm` 先别当位宽。** 看它进了哪个函数，那个函数内部怎么用它。
3. **钳位上限**（`push 0x1F`）是位宽的强提示：能存 0..31 ⇒ 恰好 5 位。
4. **读侧对返回值的处理方式**决定语义。`test al,al / je` ⇒ 返 bool ⇒ 不是纯读。
5. **别用"总字节数"验证"内部位宽"。** 50 和 51 都能补到 7 字节。
