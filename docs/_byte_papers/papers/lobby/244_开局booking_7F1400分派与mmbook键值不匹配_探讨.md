# 244 探讨：`strcmp` 两边必须都读 —— 我差点把「动态应答串 vs 编译期常量」当成「恒定相等」

## 判据

1. **`strncmp(a, b, n)` 的两个操作数必须分别追来源。**
   - `0x7F153C push 6 / 0x7F153F push 0xDC6724 / 0x7F1544 call 0xC3C678` —— 这里 `a`（`ebx`）是**远端应答**，`b` 是**常量 "mmbook"**。
   - 所以「`"mmbook"` 匹配」只是**命令字匹配**，不代表整个应答合法。
   - 真正的「成功」判据在 `0x632680` 门 6：`strcmp(参3, "mmbook accepted")`。**参3 是动态的。**

2. **判断「0x632680 为什么失败」必须同时有两个字符串的地址。**
   - 门 6 的常量：`0xDC69B0 = "mmbook accepted"`（`0x632680` 内 `push 0xDC69B0`）
   - 传入的参 3：`edi = [esp+0x30]`，由 `0x7F3440` 填 —— **不是常量**
   - ⇒ **只有远端精确回 `"mmbook accepted"` 才成立。**

## 自我推翻记录

- **第一版（已写入 227 卷的延伸）**：我以为 `0x7F156F` 是 `0x7F1110` 的一部分，于是说「HTTPS booking 成功后调 0x632680，门6 应该能过」。
  **错。** 我在读 `0x7F1110` 时发现它是 `ret 0x14` 的 12 条指令短函数，**根本没有 strncmp**。于是沿 `0xDE07C4` 指针往回找，才定位到真正的分派器 `0x7F1400`。
- **第二版**：我以为 `0x632680` 是「超时检测」所以与开局无关。
  **不对**：它有**两个**调用点，`0x632FC4`（FrameUpdate，传 `"mmbook timedout"`）和 `0x7F156F`（传动态应答串）。
  **两个点都调同一个函数，但传的参3 不同** —— 所以「超时」和「成功」是同一个函数的两个入口，靠参3 区分。**这一点 227 卷说对了（两个调用点），但把函数名定为「超时检测」会误导后续。**
- **第三版**：我一开始把 `0x7F1110` 的唯一引用 `0xDE07C4` 当成了代码里的 `call`。
  实际 `b'\x10\x11\x7f'` + 后续字节是 **little-endian dword `0x007F1110` 存在数据区** ⇒ 是**函数指针表的一项**，不是 `E8` 调用。**判据：看它前后是不是 `.text` 的指令流 —— 是字符串/表区就是数据。**

## 方法论

- **`strncmp(a,b,n)` 的 `n` 是常量时，先看 `b` 是常量还是变量。** 若 `b` 是常量而 `a` 来自网络，那这次比较**只能证明"命令字对"**，不能证明"整体对"。
- **一个函数的两个调用点传不同参 → 它不是「X 检测」，是「X 处理」。** 命名要给「处理」而不是「检测」。
- **`ret N` 是函数边界的廉价判据。** `0x7F1110` 有 `ret 0x14`，`0x7F1400` 也有 `ret 0x14` —— **两个 5 参函数不可能是同一个**（除非中间没有 `int3`）。`0x7F13FF` 恰好是 `int3`，坐实了边界。
- **数据区里的 dword 要按「它落在哪个 section」判断用途。** `0xDE07C4` 在 `.tp3 a`（`0xCA8000..0xE16000`）—— 那是数据段，不是代码段。
