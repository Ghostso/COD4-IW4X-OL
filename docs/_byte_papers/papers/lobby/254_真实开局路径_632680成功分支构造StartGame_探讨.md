# 254 探讨 · 方法、批判与自我更正

## 一、为什么 227 会错

227 卷的目标是回答「为什么房间开不了局」。它的推理链：
1. 找到 `0x632680` 被 FrameUpdate 调用；
2. 读调用点参数 = `"mmbook timedout"`；
3. 读被调函数门 6 = `strcmp(参数, "mmbook accepted")`；
4. 两者不等 ⇒ 恒失败 ⇒ "客户端从不因此开局"。

第 4 步是**逻辑跳跃**：`strcmp` 不等只说明"这条调用点走超时分支"，
**不说明"被调函数的另一条分支不存在"**。`strcmp` 是个二值判断，相等那条分支必须去读。

**本卷的做法**：从 `0x632680` 起点逐指令到每个 `ret`，把 `test eax,eax / jne 0x632876` 的**两条路都读**。
`jne` 落空 = `eax==0` = `strncmp` 相等 = 成功 ⇒ 落空目标 `0x6326EF` 就是成功体。

★ **这是一次典型的"读了分流点、没读分流两头"**。项目记忆里已有
`「反汇编必须从函数起点且遇 ret/int3 即停」`（`codol-mmi-lowregion-vs-networkregion`），
本次补充：**遇到条件跳转，要读两个目标，而不是只读跳转目标**。

## 二、我中途自己踩的坑（诚实记录）

**坑：`ebx` 被中途重新赋值，导致我一度以为门6 比较的是"命令串"。**

初读 `0x7F1400` 时，我按 `0x7F141E mov ebx,[ebp+0x14]` 认定 `ebx` = 命令串，
于是把 `0x7F1563 push ebx` 当成"参4=命令串"，与 244 卷"参4=解析文本"冲突。

重读发现 `0x7F14E2 lea ebx,[esp+0xB0]` —— **`ebx` 在第 0x14E2 处被改写为"解析出的文本缓冲指针"**。
所以 `0x7F1563 push ebx` 传的是**解析文本**，与 244 一致。

★★ **教训：一个寄存器在某点取值，不能假设它到调用点还是那个值；中间每一处写点都要扫。**
这与记忆里 `「常见偏移写点按所在函数筛」` 同源。

## 三、批判本卷

1. **"成功分支发送 StartGame" 的证据强度**：
   - 构造 `vtable 0xDC751C` = StartGame（`[0]=0x625BE0` serialize）——**强**（与 P1/198 的读侧 `0x625CE0` 成对）。
   - `0x62ABF0` 走 `msg.vt[0]` 序列化——**强**。
   - `vt+0x148 = 0x62C580 → 0x62C380(kind=2)`——**中**。`0x62C380` 里 `cmp edi,4 / jne 0x62C4BE`，
     kind=2 走 `0x62C4BE`（另一条），该路是否真出网未在本卷追到出口。**这是本卷最大弱点。**
2. **未验证 `0x632876` 超时分支"到底发什么"**：只看到 `vtable 0xDC7528` + `type=2/4`，未读 `0x6328B9..E8` 全链。
3. **`vt+0x148 = 0x62C580 → 0x62C380(kind=2)`——已补强**：kind=2 走 `0x62C4BE` → `0x656A10`
   （建 32 字节节点入链表，`0x656A75 inc [ebx+8]`）⇒ 是"发送队列入队"。kind=4 才直发 `0x7E8240`。
4. **"成功分支可达"是静态可达性**，不是运行时观测。**服务端是否回 `"mmbook accepted"` 仍未定**（246 卷边界）。
5. **独立复核已做**：子代理逐字节复现确认了 C1–C5（`jne 0x6326E9`、成功体、`0xC3C678`=strncmp、四个 `ret 0x14`）。
   它给出一个措辞修正：`0xDC751C` 严格说是"4 项描述符 `{0x625BE0,0x625CE0,0xDF9364,0x628320}`"，
   "StartGame 消息 vtable"是**解释**而非指令直接给出。★ **佐证**：`0xDC6B9D` 有字面量 `"startgame"`，
   `0xDC751C` 的 4 个构造点（`0x62FB3E/0x6327ED/0x63460C/0x634B09`）与 190 卷 StartGame 分叉一致 ⇒ 解释成立，但**保留为"解释"**。
