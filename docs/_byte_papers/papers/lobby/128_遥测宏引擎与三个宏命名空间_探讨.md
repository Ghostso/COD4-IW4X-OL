# 128 探讨 · 三种"引用"，我混用了其中两种

> 配套：[128 · 遥测宏引擎与三个宏命名空间](128_遥测宏引擎与三个宏命名空间.md)
> 性质：方法论复盘 + 一次当场撤回。**主题：引用点搜索搜到的到底是什么。**

## 一、结论先认错

我在 §3 一度写了"存在第二遍引擎，它把 `${TIMESTAMP_OFFSET(%d)}` 再展开一次"。这个假设在第 159 行被我自己的逐字节核对推翻了：

`0xdc6fc4` 的字节是 `c4 6f dc 00`。它出现在文件偏移 **`0x240B87`**。

而引擎里那条 `push 0xdc6fc4` 指令在 `0x240B86` —— 操作码 `68` 在 `0x240B86`，立即数从 `0x240B87` 开始。

**⇒ 搜到的"引用点"就是那条 push 的立即数本身。不是新东西。**

如果我当时没去核对字节偏移差的那 1 个字节，我会写出一整节"第二遍引擎"，而且它看起来极其自洽：有入口、有循环、有格式串、有"第一遍/第二遍"的分工叙事。

**好看。假。**

## 二、为什么会犯

我的搜索函数是：

```python
def refs(off):
    return [m.start() for m in re.finditer(re.escape(struct.pack("<I", off + VA)), d)]
```

这是**字节串匹配**。它不区分：

| 匹配到的位置 | 语义 |
|---|---|
| `.rdata` 里的指针数据 | 真·指针引用（表项、结构体字段） |
| 指令里的 `push imm32` / `mov reg, imm32` / `cmp mem, imm32` | **立即数**（指令本身"知道"这个地址） |
| 巧合重叠 | 噪声（概率 ~32MB / 2^32 ≈ 0.7%，不低） |

**"引用"这个词把三种东西塞进了一个桶。**

对于 127 卷的"48/54 只有 1 个引用点"结论，**结论仍然成立**（那 1 个引用点确实是 `push` 模板串的日志函数，而且如果真有表，这些 push 位置不会彼此孤立地散布在 3.5MB 代码里）。**但我的推理链写错了**：我不是"证明了没有表"，我是"看到引用点都在代码段里、彼此孤立"。

**⇒ 正确写法应该是：「48/54 的引用点都是 `push imm32` 指令，分布在代码段，彼此不相邻 ⇒ 不存在把它们成对组织起来的数据结构」。** 这比"只有 1 个引用点"更精确，也更打不翻。

## 三、这次捡到的东西，都是从"顺手核一下"来的

### 3.1 `push` 顺序把调用约定钉死了

`0x49AA26 push ${TIMESTAMP_PLACEHOLDER}` → `0x49AA2B push <ClientLoadTime 模板>`。

cdecl 从右往左压 ⇒ 模板是 arg1、占位符是 arg2。

**这一条不是我"设计"去验证的，是我在 `macro_placeholder_hits.py` 打印上下文时顺手看到的 6 行反汇编。**

但它解释了一件大事：127 卷里 13 条事件有 11 条"第 2 字段 = 时间表达式"，我原以为是巧合或语料偏差。**现在它是结构性的：每条事件的第二个实参就固定是那句占位符。**

★ **上下文打印是无成本的高收益动作。** 只打印一个地址，你只得到一个地址；打印±24 字节反汇编，你得到调用约定、得到参数顺序、得到理由。

### 3.2 `${TIMESTAMP}` vs `${TIMESTAMP_PLACEHOLDER}` 是两套口径

`${TIMESTAMP}` 有 9 个引用点，其中 8 个正好是 `LoadoutChangeEvent`/`ClientException`/`ComError` 这类"需要绝对时间"的事件。

语料里 `LoadoutChangeEvent|${TIMESTAMP}|16701785630074219790|…` —— **字面量原样出现在报文里**。

如果没有看到那几个 `push`，我会以为所有事件都是相对偏移时间。**一个占位符的分叉，是两种时间语义的分叉。**

★ 我一度想用"宏定义表"解释它，结果发现 `${TIMESTAMP}` 根本不在这张表里——它连常量都不是，**它是个"不被替换的文本"**。这就带出了下一个结论。

### 3.3 `${ZONEID}` 引用数 = 0，反而是最强的结论

最开始我认为"引用数=0"是搜索失败、要换个姿势再搜。

后来想通了：**如果 `${ZONEID(%llu)}` 全程只在模板中段出现、从没被独立引用，那唯一合理的解释就是"没人解释它"。**

**⇒ 空集合本身可以是证据。** 但前提是我能证明"我搜对了"：我能列出 `${CODOID(%s)}`(1 引用)、`${CODOID(%llu)}`(2 引用)、`${CODO_OPENID}`(2 引用)……这些都能搜到，说明搜法有效。**搜法有效 + 目标搜不到 = 目标不存在。**

★ 这就是为什么 §5 里我要把 `${CODO_*}` 那 6 条逐条列出引用点——**它们是本节"搜索有效"的对照组**，不是为了凑内容。

## 四、"栈上 6 个 mov"这件事我要多说一句

`0xB6D2C..0xB6D5E` 6 条 `mov [ebp-0x42c], imm`，就是一个 `void* macros[6]` 初始化。

如果从"找数据结构"的角度去看 `.rdata`，永远找不到。
如果从"找代码怎么用"的角度去看，一眼就看到。

**这和 127 卷"48/54 单引用点 ⇒ 无表"是同一个教训的第二次:** 这张客户端的**编译期就被摊平了**。能查表的都查不到。

**但这也是一个正面规律：**
> 想知道"哪些配置项存在"，去 `.rdata` 里搜；
> 想知道"它们怎么组合、什么顺序、和谁一起用"，只能看代码。

`0xB6A70` 和 `0xB6D10` 是同一个 6 项集合的两种用法的证据：一个用 `if/else` 挑单项（按名字替换），一个用数组扫全部（把出现的按先后处理）。**这两种用法在同一处并存，说明这 6 个宏既支持"按名取"也支持"全文替换"。**

## 五、三套宏，为什么不合并

我一度想写成"客户端有一套 `${...}` 宏系统"。查到 `0xB6A70` / `0xB6D10` / `0xA567xx` / `0x640AB0` 4 个实现，才明白：

| 实现 | 宏 | 谁产出它 |
|---|---|---|
| `0x640AB0` | `TIMESTAMP_PLACEHOLDER` / `CLIENT_IP_PLACEHOLDER` / `TIMESTAMP_OFFSET` | 遥测（TLog 日志上报） |
| `0xB6A70` / `0xB6D10` | `CODO_OPENID` / `CODO_ZONE` / `CODO_NAME` / … | 腾讯运营配置（跨系统） |
| `0xA567xx` | `CODO_MSG` / `CODO_CODE` / `CODO_EVENTTIME` / … | 腾讯 TLog 消息（SDK 侧） |

三套都叫"宏"，都长得一样，都引用 `0x...` 串，**但语义完全隔离**：遥测只认两个 `PLACEHOLDER` + 一个 `TIMESTAMP_OFFSET`；腾讯配置只认 6 个 `CODO_*` + `TITLE_ID`；TLog 消息只认 5 个 `CODO_*`（不同的 5 个）。

**⇒ "${...}" 只是**语法记号**，不是**语义命名空间**。** 只要有人写新系统，都可以用同一个记号。**以后看到 `${X}`，先查它是哪套实现的引用点，不要默认是同一套。**

这就是"宏名空间必须按实现分隔，而不是按字符串形状分隔"。

## 七、方法论（可迁移）

1. **字节串搜"引用"时，必须区分指针数据 vs `push/mov imm32`。**
   `push imm32` 的立即数也长得像指针，且两者只差 1 个字节（操作码位置 vs 立即数位置）。**搜到就在结果边注一句"这是 push/是数据"。**
2. **上下文反汇编是零成本高收益。** 打印 ±24 字节能顺手捡到调用约定、参数顺序、相邻代码——这是反汇编工具该默认做的事。
3. **"搜不到"能当证据，前提是先证明"搜法有效"。** 列出同一类能搜到的对照组，空集才有证明力。
4. **"好看"不是"存在"。** 一个自洽的叙事（"第二遍引擎""宏注册表""UIPage 模板"）如果少了那 1 个字节的核对，就会变成真的论文。
5. **同名 ≠ 同系统。** `${CODO_*}` 出现在 3 个互不相干的实现里，只有查引用点才能分开。
6. **栈上临时数组是这张客户端的常态。** 编译器会摊平 `{名, 值}` 表，别在 `.rdata` 里找。
7. **写完一个"结论"立刻拿字节打自己一次。** 本卷 §3 的那次自我撤回，是本卷最硬的一条。
