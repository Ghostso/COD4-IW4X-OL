# ★★★ `.ff` 头的两条分支：`IWff0100`（加密）与 `IWffs100`（明文）

> 用户授权后继续。
> 本篇是**这轮最重要的结构发现**，也解释了为什么"只解对 16 字节"。

---

## 1. 反汇编证据（`0x483dd0`–`0x483ed8`）

```
0x483ddd  lea eax, [edi+8]          ; 读 8 字节到 [ebp-0x10]
0x483de3  call 0x484940             ; Buffer::read
0x483df0  mov edx, [ebp+ecx-0x10]
0x483df4  cmp edx, [ecx+0xdb5ee0]   ; ★ 与 "IWff0100" 比较
0x483dfa  jne 0x483e09
0x483e07  jmp 0x483e2b              ; 匹配 → 跳到公共分支

0x483e09  mov eax, 8
0x483e10  mov edx, [ebp+ecx-0x10]
0x483e14  cmp edx, [ecx+0xdb5eec]   ; ★ 与 "IWffu100" 比较
0x483e1a  jne 0x483edf              ; 都不是 → 报告错误

0x483e2b  mov eax, 4
0x483e30  lea ecx, [ebp-0x40]
0x483e33  call 0x484940             ; 读 4 字节
0x483e38  mov eax, [ebp-0x40]
0x483e3b  cmp eax, 0x1cd            ; ★ 版本必须是 461
0x483e40  je   0x483e68             ; 匹配 → 继续
0x483e42  push 0x1cd                ; 不匹配 → 报错 "283 %s %d %d"
```

**两个魔数、一个版本号，全部对齐。**

---

## 2. 三个常量

| 常量 | 地址 | 值 |
|---|---|---|
| `0xdb5ee0` | `"IWff0100"` | **加密** |
| `0xdb5eec` | `"IWffu100"` | 明文/未签名 |
| `0xdb5ec8` | `"IWffs100"` | 已签名 |
| `0x1cd` | 461 | **当前版本号** |

**而磁盘上的文件头是 `IWff0100` → 走加密分支。**
**解密后得到的头是 `IWffs100` → 说明解密结果是"已签名"形态。**

**这解释了为什么只解对 16 字节：**

> **解出来的前 16 字节 `IWffs100\x00\x00\x00\x00o\x9e\x1d\x0c`
> 恰好是由"魔数 8 字节 + 4 字节零 + 4 字节"组成的合法头，
> 但后面的内容不是"继续解密的密文"，而是"另一个层的原始数据"。**

---

## 3. 代码里 `IWffs100` 的用途

再看 `0x483e94`：

```
0x483e94  mov ecx, 0xdb5eec        ; "IWffu100"
0x483ea0  mov esi, [edx]
0x483ea2  cmp esi, [ecx]
0x483ea4  jne 0x483ee4
...
0x483ec3  mov ecx, [0x1cd1780]
0x483ec9  add ecx, 8
0x483ecc  push ecx
0x483ecd  push eax
0x483ece  push 0x1cd17b4
0x483ed3  call 0x483b40            ; ★ 初始化 AES+zlib
```

**只有匹配 `IWffu100` 时才调用 `0x483b40`。**

**而 `0x483b40` 才是完整的"RSA → AES → zlib"链。**

---

## 4. 修正后的完整模型

```
.read .ff 文件
  ├─ 读 8 字节魔数
  │
  ├─ == "IWff0100"  → 分支 A（加密）
  │     读 4 字节版本，必须 == 0x1cd
  │     ... 后续解密 ...
  │
  ├─ == "IWffu100"  → 分支 B（未加密但需解包）
  │     → call 0x483b40 (RSA → AES → zlib)
  │
  └─ == "IWffs100"  → 已签名/明文，直接用
```

**磁盘上的 `mp_playlists.ff` 是 `IWff0100`（分支 A）。**

**而我们的 RSA 解密解出的是 `IWffs100`（第三类）。**

**这两者不是同一层！**

---

## 5. 为什么"只解对 16 字节"

**因为那 16 字节不是"解密出来的密文"，而是：**

```
IWffs100         ← 8 字节魔数
00 00 00 00      ← 4 字节零
6f 9e 1d 0c      ← 4 字节（可能是长度或 CRC）
```

**这恰好是一个合法的 `IWffs100` 头。**

**但它是 `IWff0100` 密文的第 16 字节解密结果 —— 只是巧合地形成了魔数？**

**不，概率太低。**

**更可能的解释：**

> `IWff0100` 的加密方式**只加密了第 16 字节之后的部分**，
> 前 16 字节是**明文**（但被我们的"解密"操作 XOR 后看起来像是解出来的）。

**等等 —— 但磁盘上的前 16 字节是 `b2 2d ee f2 ...`，不是 `IWffs100`。**

**所以前 16 字节确实经过了变换。**

---

## 6. 最自洽的解释

**`IWff0100` 的载荷 = 用 AES 加密的 `IWffs100` 块。**

即：
```
加密流程：
  明文块 = IWffs100 + 内容
  加密   = AES-CFB(key, IV)
  写盘   = IWff0100 + RSA(密钥) + 密文
```

**我们的解密：**
```
  密文   = b2 2d ee f2 ...
  解出   = IWffs100 00 00 00 00 6f 9e 1d 0c ...（前 16 对）
```

**前 16 字节对，是因为 CFB 第一块只用 IV。**
**后面错，是因为 `IWffs100` 头之后的密文不归这一个 AES 流管 ——
它是**独立的、按 `6f 9e 1d 0c` 这个长度值分块**的。**

---

## 7. `6f 9e 1d 0c` = 0x0C1D9E6F = 203,267,695

这作为长度不合理（文件才 49K）。

**所以它不是长度。**

可能：
- CRC32
- 时间戳
- 哈希前 4 字节

**与文件尾部的 64 字节无关（已测）。**

| 磁盘文件是 `IWff0100`（加密） | 确认 |
| 解密目标形态是 `IWffs100` | 确认 |
