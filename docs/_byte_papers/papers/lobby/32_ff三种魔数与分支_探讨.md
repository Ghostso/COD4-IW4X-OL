# `.ff` 三种魔数 · 探讨：一次反汇编把"只解对 16 字节"讲通了

> 对应：`lobby/32_ff三种魔数与分支.md`

## 一、之前的困境

我一直在问："为什么 key/IV 都对，但只有前 16 字节能解？"

尝试了 8 类参数组合，全部失败。

**因为我从来没去看"调用解密链的那个函数，它在干什么"。**

---

## 二、反汇编 `0x483dd0` 的收获

我看到三组比较：

```
0x483df4  cmp edx, [0xdb5ee0]   ; "IWff0100"
0x483e14  cmp edx, [0xdb5eec]   ; "IWffu100"
0x483e3b  cmp eax, 0x1cd        ; 版本 461
```

**这是"文件头分派"的经典写法。**

再看 `0x483e94`：

```
0x483e94  mov ecx, 0xdb5eec     ; "IWffu100"
...
0x483ed3  call 0x483b40         ; 只有匹配才调用
```

**所以 `0x483b40`（RSA+AES+zlib 链）只服务 `IWffu100` 这一种。
不是服务全部 `.ff`。**

---

## 三、这解释了什么

**磁盘上的 `mp_playlists.ff` 是 `IWff0100`。**

它走的是**另一条分支**。

**而我们用 RSA 解出的前 16 字节是 `IWffs100` —— 第三种形态。**

**这说明：**

> `IWff0100` 解密后，得到的是 `IWffs100`。
> `IWffu100` 解密后，得到的是另一种东西。

**两条路径，不同的目标。**

---

## 四、16 字节正确的真正原因

**AES-CFB128 的第一块：**
```
C0 = P0 XOR E(IV)
```

**只要 key 和 IV 对，P0 一定对。**

**这是"第一块正确"的充分条件。**

**但第二块：**
```
C1 = P1 XOR E(C0)
```

**如果 P1 不在同一个流里（例如 P1 属于另一个独立的加密段），
那么 C1 就不是这个流的一段。**

**所以 P1 解不出来。**

---

## 五、代码里的分块线索

`0x483787` 分支：

```
0x4837a2  call 0xbc5f60   ; cipher init
0x4837be  call 0xbc8840   ; decrypt 8192
0x4837cb  call 0xbc7c40   ; SHA-256 init
0x4837e5  call 0xbc7c90   ; SHA-256 update
0x4837fa  call 0xbc7d60   ; SHA-256 final
0x483810  cmp  [esi], [ecx]  ; 32 字节摘要比较
```

**每 8192 字节：解密 → SHA-256 → 比对。**

**而 `0xbc5f60`（cipher init）在每个块前都会调用。**

**这意味着每块都是独立的 AES 会话。**

**但每次都用同一个 key，IV 呢？**

**如果 IV 也固定，那么块 1 的解密应该和块 0 一样正确。**

**但实测不是。**

**所以 IV 一定变了，而我们不知道它怎么变。**

---

## 六、可能的 IV 变化方式

1. **`IV = 前块的 SHA-256`** —— 我们没试过（用 tail 试的是别的）
2. **`IV = 前块的最后 16 字节明文`** —— 试过，失败
3. **`IV = 前块的最后 16 字节密文`** —— 试过，失败
4. **`IV` 存在块头的某个字段里** —— 还没找

**第 4 种最可能：块头有个字段存 IV。**

**`6f 9e 1d 0c` 可能就是 IV 的一部分。**

---

## 七、方法论收获（第三次同类教训）

> **不要只看"被调用的函数"，要看"调用它的函数"。**

前面三次：
1. `0x791eb0` —— 以为是加载器，其实是 zlib
2. `0x484940` —— 以为是构造器，其实是 Buffer::write
3. **`0x483b40` —— 以为是通用解密链，其实只服务 `IWffu100`**

**每次都是"往上再看一层"，才发现真正的语义。**

**所以我应该养成习惯：追踪到"最上层的分派点"再下结论。**
