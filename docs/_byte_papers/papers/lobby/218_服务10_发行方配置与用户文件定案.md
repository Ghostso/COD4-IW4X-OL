## §2 三条 schema（逐字节）

语法同 217 卷 §1.3：`tag:1B + value`，消息以 `0x00` 结尾；`0x10`=string（裸字节+`00`），`0x08`=u32，`0x0A`=u64，`0x05`=u16，`0x06`=s16。

### 2.1 `10/21` —— 取发行方文件

```
+0   10 00                       string ""              ← 命名空间/目录（空）
+2   10 <ASCII> 00               string <文件名>
+末  00                          终止
```
10 个 distinct（`declared = len+3`，与日志的 `declared` 逐条吻合）：

| 文件名 | 载荷 len | declared | 次数 |
|---|---|---|---|
| `mp_playlists_shipRetail_1.0.0.info` | 39 | 42 | 93 |
| `daily_challenge_config.info` | 32 | 35 | 93 |
| `whitelist_tester.info` | 26 | 29 | 93 |
| `activities_v1.info` | 23 | 26 | 93 |
| `market-down.info` | 21 | 24 | 93 |
| `tlogconfig.info` | 20 | 23 | 93 |
| `configs_s.info` | 19 | 22 | 93 |
| `broadcast.info` | 19 | 22 | 93 |
| `market_ui.info` | 19 | 22 | 93 |

**实测发送顺序**（一个 run 内，seq 递增）：`mp_playlists → activities_v1 → configs_s → daily_challenge → broadcast → tlogconfig → market_ui → market-down → whitelist_tester → MOTD`
——对应登记表下标 **[1,3,0,8,2,4,9,5,6,7]**，**与下标顺序不同**（见 §3.3）。

+0   10 00                       string ""              ← 命名空间
+2   10 <名> 00                  string "the.json" / "FileBriefMessage"

| 名 | 载荷 len | 次数 |
|---|---|---|
| `the.json` | 24 | 93 |
| `FileBriefMessage` | 32 | 93 |

★ 账号 u64 `0xE7C8A9A96B4C2D0E` 是全项目"三核心 ID"之一（见 `codol-frame-crypto-verified` 合并卷）。命中说明 **10/12 的第三字段是玩家身份，不是文件 id**。

### 2.3 `10/20` —— 14 字节，零变化

```
+0   10 00              string ""
+2   08 00 00 00 00     u32 = 0
+7   06 20 00           s16 = 32
+10  06 00 00           s16 = 0
+13  00                 终止
```
98/98 条完全一致。**没有任何文件名、没有账号**。语义见 O-4。

## §3 客户端：发行方文件登记表（10 条目）

### 3.1 派发器与跳转表

```asm
0x50E930  push edi
0x50E931  jmp dword [eax*4 + 0x50EA88]     ; ★ 10 条目跳转表
```

跳转表 `0x50EA88` 解出（每 4 字节一个 VA）：

| idx | 目标 | 分支里 push 的文件名 | 文件名字符串地址 | 回调 |
|---|---|---|---|---|
| 0 | `0x50E96B` | `configs_s.info` | `0xDBDEAC` | `0x50EB80` |
| **1** | `0x50E938` | `mp_playlists_shipRetail_1.0.0.info`（**全局缓冲 `0x333AC78`**） | `0x333AC78` | `0x50EBC0` |
| 2 | `0x50E9C2` | `broadcast.info` | `0xDBDED0` | `0x50DC70` |
| 3 | `0x50E989` | `activities_v1.info` | `0xDBDEBC` | `0x50DC10` |
| 4 | `0x50E9E0` | `tlogconfig.info` | `0xDBDEE0` | `0x50DD20` |
| 5 | `0x50EA12` | `market-down.info` | `0xDBDF00` | `0x50DF80` |
| 6 | `0x50EA29` | `whitelist_tester.info` | `0xDBDF14` | `0x50E2C0` |
| 7 | `0x50EA40` | `MOTD.info` | `0xDBDF2C` | `0x50E260` |
| 8 | `0x50EA57` | `daily_challenge_config.info` | `0xDBDF38` | `0x50E500` |
| 9 | `0x50E9FB` | `market_ui.info` | `0xDBDEF0` | `0x50E5A0` |

**字符串唯一性**：镜像里每条 `.info` 只有 3 处命中（`0xDBDExx` 的 C++ 常量 / `0x337Exx` 的 AS3 资源串 / `0x8262xxx` 的 AVM2 导出区），而 `0xDBDExx` 那组**每条都只有 1 个代码引用**（`0x50E980..0x50EA68` 全在同一个函数内）⇒ **这张表是唯一的登记点，无第二份实现**。

### 3.2 条目结构：`index × 0x130 + 0xC7AE9A8`

```asm
0x50E9AA / 0x50EA75   imul edi, esi, 0x130
…                     add  edi, 0xC7AE9A8
0x50E9B1 / 0x50EA7B   call 0x66A650        ; (index, 文件名, 回调)
```
`0x66A650` 里的 fill（case 体 `0x66A684`）：

| 偏移 | 写入 | 来源 |
|---|---|---|
| `+0x00` | `arg2` | 调用方（本卷的 10 个调用点都传同名对象） |
| `+0x100` | `[+0x114]` | 拷贝 |
| `+0x104` | `[+0x110]` | 拷贝 |
| `+0x110` / `+0x114` | — | 由 `0x66A710`（完成回调）写入 |
| `+0x118` | `0` | byte 标志（"是否已到最新"） |
| `+0x11C` | `[edi+0x11C]` | 由 `0x66A5E0` 消费 |
| `+0x124` | `index` | ★ 自指下标 |
| `+0x128` | `arg3` | ★ 该文件的解析回调 |

### 3.3 "是否需要下载"的门与"版本号改写"

```asm
0x50DB90(index)
  mov ecx,[eax*4 + 0xDA9FC8]      ; 每 index 一个"文件类别 id"
  mov eax,0xE56FFE0
loop: cmp [eax],ecx ; je found
      add eax,0x50 ; cmp eax,0xE5713E0 ; jl loop
      xor al,al ; ret              ; 未登记 → 0
found: mov al,1 ; ret              ; 已登记 → 1
```
⇒ `0xE56FFE0 .. 0xE5713E0` 是 **64 条目 × 0x50** 的"已下载文件注册表"；`0xDA9FC8[index]` 是文件类别 id。
⇒ `0x50DB90` 返回 **1 = 已经有了 ⇒ 各 case 里 `test al,al / jne 0x50EA83` 直接跳过请求**。
⇒ **全新 run 注册表为空 ⇒ 10 个文件全部请求** —— 这就是 `10 × 每 run` 的来源。

`mp_playlists` 分支额外做版本改写：

```asm
0x50E938  mov eax,1 ; call 0x50DB90        ; 只对 idx=1 检查
0x50E94A  mov ecx,[0x33EA594] ; mov edx,[ecx+0xC] ; push edx
0x50E954  call 0x50E700                    ; ★ 用版本号改写文件名
0x50E961  push 0x333AC78                   ; 改写后的全局缓冲
```
`0x50E700(name)`：`strncpy(0x333AC78, name, 0xFF)` → 找**最后一个 `.`** → 若找到走 `0x50E7F6` 在扩展名前插版本 —— 这正是镜像里同时存在 `mp_playlists_shipRetail.info`（`0xDBD5F8`，DVAR 默认值）与 `mp_playlists_shipRetail_1.0.0.info`（`0x333AC78`）的原因。

### 3.4 出网链与闸门

存在**两个平行入口**（`10/21` 与 `10/12` 各一个），形状完全一样：

```asm
; ---- 10/21（发行方文件）----
0x7F9830                                 ; "发出这条文件请求"
0x7F9835 call 0x803830                   ; srpc 单例
0x7F9846 call 0xB7A670 ; cmp eax,2 ; jne fail   ; ★ srpc+0x4F4 会话必须已认证
0x7F985B call 0xB80EC0(push 0xDAE091="")        ; 取通道
0x7F9897 call 0xB9C9D0                   ; 组请求对象
0x7F98CB call 0x7FAB00(0x66A710, …)      ; 入队，完成回调 0x66A710

; ---- 10/12（用户文件）----
0x7F9910 … call 0xB7A670 ; cmp eax,2     ; 同一道 srpc 闸
0x7F99D6 call 0xB9C750                   ; ★ 另一套 builder
0x7F9A16 call 0x7FAB00(0x7F9A50, …)      ; 入队，完成回调 0x7F9A50

; ---- 唯一下沉漏斗（154 卷）----
0x7FAB35 / 0x7F9A16 → call 0x7FA800
```

★★★ **task 号硬编码在 builder 里**（这一条把"哪个入口发哪个任务"钉死）：

| builder | 被谁调 | 立即数（push 序） | ⇒ (service, task) |
|---|---|---|---|
| `0xB9C9D0` | `0x7F9830`（10 条目登记表路径） | `0x400 / 0x15 / 0x0A` | **(10, 21)** |
| `0xB9C750` | `0x7F9910`（`the.json` / `FileBriefMessage` 路径） | `0x400 / 0x0C / 0x0A` | **(10, 12)** |

> `push` 序（cdecl 从右到左）依次是 `size=0x400` → `task` → `service`；两条共同的那个数就是 **service=10**，差异数就是 **task（21 / 12）**。
> 佐证：`10/21` 与 `10/12` **恰好共享 `service=10`**；若把 `0x0A` 当 task、`0x15` 当 service，就会得到 `21/10` 与 `12/10` 两个**在语料里根本不存在的任务**。

两个 builder 的字段数差异也吻合载荷：`0xB9C750` 比 `0xB9C9D0` 多传一个参数（`push [ebp+0x14]` → `call 0xBA71C0`）——对应 `10/12` 比 `10/21` 多的那个 **u64 账号字段 + 末尾空串**。

`0x66A650` 自身另有三道前置：

```asm
0x66A654  cmp byte [0x849BA3D],0 ; jne 直接返回
0x66A66C  mov eax,[0x84ABA50] ; cmp eax,5 ; ja 直接返回
0x66A676  jmp [eax*4 + 0x66A6F8]        ; 按 clientState 0..5 分派
```

⇒ **`10/21` 不出网的必要条件**（与 172/173 卷的 `srpc+0x4F4` 结论同源）：
1. `[0x849BA3D]==0` 且 `[0x84ABA50] <= 5`；
2. `srpc+0x4F4` 的 HMAC 会话已认证（`0xB7A670()==2`）。
（`0x7F9910`/`10-12` 没有第 1 条那两道，只有 srpc 闸。）

## §4 响应格式

服务端 `reply_objects()`（`lobby_server.py:737-760`）对 `10/21` 与 `10/12` 都回
`cc.serialize_file_data(d)` = **`0x13 0x08 <u32 长度> <原始字节>`**（`codol_crypto.py:252`）。

客户端侧的镜像证据：`0xB767D0` = writeBlob（`push 0x13` → `call 0xB766B0` 写 u32 长度 → 写数据），**与 `serialize_file_data` 逐字节同构** ⇒ 读写两侧一致，不存在"服务端写 7 字节、客户端读 6 字节"的错位。

拿到字节后由 `+0x128` 里登记的**每文件回调**解析：

idx0 configs_s.info        → 0x50EB80
idx1 mp_playlists_*.info   → 0x50EBC0
idx2 broadcast.info        → 0x50DC70
idx3 activities_v1.info    → 0x50DC10

## §7 方法论

1. **"880 次"这种数字先做整除**：930 能被 10 整除、186 能被 2 整除、98 是质数倍 ⇒ 立刻看出"每 run 固定条数"，而不是"按 UI 动作触发"。**整除性比逐条看报文快一个数量级。**
2. **字符串的唯一代码引用是最强锚**：10 个 `.info` 每个只有 1 个代码 xref，且全部落在一个函数的跳转表里 ⇒ 一次反汇编就把"10 条目 + 每条目回调 + 每条目 index"全拿到。
3. **`imul reg, N` 紧跟 `add reg, BASE` 就是步进式数组的身份证**（`0x50E9AA imul edi,esi,0x130` + `add edi,0xC7AE9A8`）。
4. **"全样本零变化"不等于"常量"**：`10/20` 的 98 条一模一样，只能说明它不含可变字段，**不能**说明字段语义（`32` 和 `0` 到底是什么，仍然未知）。**结构与语义必须分开下结论。**
5. **空串字段会被误读成报文头**：`10 00` 连着出现三次在不同任务的开头，很容易当成"固定头"。**回到写侧找到 `0xB76700`（写 `0x10` + 裸字节 + `0x00`）后，`10 00` 立刻变成 `len=0 的字符串`。**
6. **同一族闸门要写全**：`10/21` 出网要过 `[0x849BA3D]`、`[0x84ABA50]<=5`、`srpc+0x4F4` 三关。**只报最后一关会漏掉"clientState 不对就静默不发"这一层**。
7. ★★★ **两个 `push imm` 里"共同的那个"就是共享维度**：`0xB9C9D0` = `push 0x15,0x0A`、`0xB9C750` = `push 0x0C,0x0A`。语料里只有 `10/21` 与 `10/12` 两个任务 ⇒ 二者共享的 `0x0A` 必然是 **service**，差异的 `0x15/0x0C` 必然是 **task**。**这条判据不依赖任何符号表**，只要"两个样本共享一个字段、另一个字段不同"，就能把 (service,task) 的**位置**定下来。反过来若把 `0x0A` 当 task，会得到 `21/10`、`12/10` 两个语料中不存在的任务 —— **自证伪**。
8. **接口形态相同 ≠ 同一个入口**：`0x7F9830` 与 `0x7F9910` 的门/流程/下沉调用几乎逐条镜像，唯一区别是 builder（`0xB9C9D0` vs `0xB9C750`）与完成回调（`0x66A710` vs `0x7F9A50`）。**先看"它调了哪个 builder"，再看"它长什么样"。**
