## §1 ★★★ `0x4B55E0` —— 第二个用 `reply+5` 判据的大厅服务

### 1.1 与商城同构的三段

```asm
; ① reply+5 判据（与 231 卷 0x4A7FB0 逐字同构）
0x4B5601  mov  edi, [ebp + 8]        ; reply 对象
0x4B5604  mov  eax, [edi + 0x40]     ; 字段
0x4B5607  mov  esi, [edi + 0x44]     ; 字段
0x4B5610  cmp  byte ptr [edi + 5], 0 ; ★★ 同一个 +5 状态字节
0x4B5614  jne  0x4B5729              ; 非 0 → 直接跳过（不发送）

; ② srpc 三段（234 卷骨架）
0x4B561A  call 0x803830              ; srpc 单例
0x4B562B  call 0xB7A670              ; 认证
0x4B5630  cmp  eax, 2
0x4B5633  jne  0x4B5729
0x4B563B  call 0xB7A9B0              ; ★ 另一种宿主 getter（第三变体）

; ③ 出口漏斗
0x4B56DC  push 0x87                  ; ★ 通道号 135
0x4B56E1  call 0x7FA800              ; ★★ 与商城同一个出口
```

### 1.2 ★★ 关键语义差异

商城的 `0x4A7FB0`：

```asm
0x4A7FBE  cmp byte [eax+5], 0
0x4A7FC2  je  0x4A7FCD        ; ★ ==0 → 走失败分支（置 state=2）
```

本服务的 `0x4B55E0`：

```asm
0x4B5610  cmp byte [edi+5], 0
0x4B5614  jne 0x4B5729        ; ★ !=0 → 跳过（不发）
```

**恰好相反！**

| 服务 | `reply+5 == 0` 时 | `reply+5 != 0` 时 |
|---|---|---|
| 商城 `0x4A7FB0` | **失败**（`state=2`） | 继续处理数据 |
| 本服务 `0x4B55E0` | **继续处理**（发请求） | **跳过** |

★ **⇒ `reply+5` 不是"有无数据"的通用语义，而是"是否已完成/是否需跳过"的服务私有语义。** 231 卷说它是"数据有无状态字节"，这个表述**只在商城上下文成立**。

### 1.3 ★★★ 由此纠正一个推论

231 卷 §5 / 232 卷 §4.3 我写过：

> 「同样的风险适用于上表每一项：空 ACK 会让客户端走失败分支。」

**本卷证明不能一概而论** —— `reply+5` 的极性因服务而异，甚至可能根本不是同一个字段语义。

**⇒ 正确表述**：**每个服务必须单独确认它的响应判据（偏移 + 极性 + 后果），不能用商城的结论外推。**

## §2 `reply+5` 全库 6 处清单

| 地址 | 寄存器 | 是否大厅服务 | 备注 |
|---|---|---|---|
| `0x4A7FBE` | eax | ✅ 商城 | 231 卷已定：`==0` ⇒ `state=2` |
| `0x4B5610` | edi | ✅ **大厅服务（通道 135）** | **本卷新定**：`==0` ⇒ 继续，`!=0` ⇒ 跳过 |
| `0x61B026` | edi | ❓ | 未分析 |
| `0x61C562` | edi | ❓ | 同函数内有两次判据 |
| `0x61CB3C` | edi | ❓ | 邻接哈希比对循环（`0x61CB0E xor [0xE4DD90]`） |
| `0x684D93` | edi | ❓ | 与 `[edi+6]`/`[edi+0x64]`/`[edi+4]` 三个字节联合判定 |
| `0xB4A1D1` | edi | ❓ | 网络层 |

★ **`0x684D93` 值得注意**：它同时查 `[edi+6]`、`[edi+0x64]`、`[edi+5]`、`[edi+4]` **四个布尔** —— 说明 `+4/+5/+6` 是一个 `{b4,b5,b6}` 三元标志组，不是单一状态字节。

★ **⇒ 231 卷「reply+5 = 数据有无」的定性过窄，应为「reply 对象头部 +4/+5/+6 是一个标志组，各服务按自己需要的位判定」。**

## §3 服务宿主 getter 的第三个变体

234 卷确认了两个宿主 getter：`0xB80D90`(svc3) / `0xB81250`(svc80)。

本卷发现**第三个**：`0xB7A9B0`（`0x4B563B` 调用），**命名空间不同**（`0xB7Axxx` 而非 `0xB80xxx`/`0xB81xxx`）。

| getter | 区段 | 用于 |
|---|---|---|
| `0xB80D90` | `0xB80xxx` | svc 3 |
| `0xB81250` | `0xB81xxx` | svc 80 |
| `0xB7A9B0` | `0xB7Axxx` | 通道 135 的服务 |

★ **⇒ 234 卷「26 个工厂函数都在 `0xB80xxx~0xB81xxx`」需要更正**：至少还有 `0xB7Axxx` 一组。

## §6 方法论

1. **★★★★★ 一个判据在一个服务里成立，不代表它是通用语义。** 231 卷把 `reply+5==0` 定性为"数据有无"，本卷发现另一服务极性相反 —— **判据的极性是服务私有的**。
2. **★★★★ 「同偏移」≠「同语义」。** `+5` 在商城是"失败"，在通道 135 是"跳过"。这与 176 卷「同偏移读写两侧可不同值」是同一类，但更进一步：**同一偏移在不同服务也可以是不同含义**。
3. **★★★ 找"通用机制"要靠「同构的多点证据」，不能靠单点外推。** 本卷之所以能定 `reply+5` 是通用判据族，是因为它有 6 个独立落点；而它的**语义**各不相同，恰恰证明"通用的是形态，不是含义"。
4. **★★ 234 卷的「工厂都在 `0xB80xxx~0xB81xxx`」已被本卷推翻** —— 第三变体在 `0xB7Axxx`。**范围断言必须扫全库，不能从两个样本归纳。**
