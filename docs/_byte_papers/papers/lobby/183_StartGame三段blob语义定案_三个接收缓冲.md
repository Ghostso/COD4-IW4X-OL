# 183 · `StartGame` 三段 blob 语义定案：三个不同容量的接收缓冲，不是三个自拼字段

> 卷次：183（房间类 · 182 卷追问的答案）
> 方法：读 `StartGame::deserialize (0x625CE0)`，它是**对端真实解析器**
> 结论：**写侧的三个 blob = 读侧的三个缓冲**（容量 255 / 8 / 16）。我们的实现只有容量对，**第 1 段内容是错的**。

---

## §0 结论

`StartGame::deserialize (0x625CE0)` 三次调用 `0x4F3EB0(buf, &cap)`：

| # | 缓冲地址 | 容量常量 | 读完后 | 与前卷对照 |
|---|---|---|---|---|
| 1 | `[this+8]+0x18` | `0x625D18 mov [ebp+8], 0xff` = **255** | `[+0x118] = 实际长度` | 写侧 `W_VAL(len1,32)`，len1 就是它 |
| 2 | `[this+8]+0x10` | `0x625D4B mov [ebp+8], 8` = **8** | — | 写侧 `W_VAL(8,32)` ✅ |
| 3 | `[this+8]+0x1CC` | `0x625D72 mov [ebp+8], 0x10` = **16** | — | 写侧 `W_VAL(0x10,32)` ✅ |

★★ **写侧长度 = 读侧容量上限。** 三段完全对应，不存在"读侧只读一部分"的问题。

## §1 `0x4F3EB0` 的参数语义（关键）

```asm
0x4F3EB4  push 0x13 / call 0xB774E0     R_TAG(19)
0x4F3EC6  push 8   / call 0xB774E0     R_TAG(8)
0x4F3ED5  push 0x20 / lea [ebp-4] / call 0xB772E0    R_VAL(32) → esi = 声明长度
0x4F3EF2  mov ecx, [edi+0x1C]          ; 当前位置
0x4F3EF8  mov ecx, [ebp+8]             ; ★ 参数1 = 缓冲指针
0x4F3EFB  test ecx,ecx / je ...        ; 空则跳过拷贝
0x4F3EFF  mov edx, [ebp+0xC]           ; ★ 参数2 = 容量指针
0x4F3F02  mov eax, [edx]               ;   eax = 容量
0x4F3F04  cmp eax, esi / jb / mov eax,esi  ; eax = min(容量, 声明长度)
0x4F3F0A  add eax,eax ×3               ; ★ ×8 → 位数
0x4F3F14  call 0xB772E0                ; 读 (min×8) 位
0x4F3F20  cmp esi, eax / jbe           ; 声明长度 <= 容量 ?
0x4F3F26  call 0x8435D0                ; ★ 超容量 → 空桩（静默丢弃）
0x4F3F44  mov [eax], esi               ; ★ 把声明长度写回 [&cap]
```

★★ **语义：`read_blob(buf, &cap)` —— 读一段声明长度、但最多拷 `cap` 字节到 `buf`，并把声明长度写回 `cap`。**

### 1.1 为什么 `+0x118` 会被写

```asm
; 0x625CE0
0x625D18  mov dword [ebp+8], 0xff        ; cap = 255
0x625D28  lea edx,[ebp+8] / push         ; &cap
0x625D2C  add eax,0x18 / push eax        ; buf  = [this+8]+0x18
0x625D30  call 0x4F3EB0
0x625D3F  mov edx, [ebp+8]               ; ★ 读完后 = 声明长度
0x625D42  mov ecx, [esi+8]
0x625D45  mov [ecx+0x118], edx           ; ★★★ 存回对象
```

⇒ **`[+0x118]` 不是"发送前的源长度"，而是"接收方解析出的实际长度"。**

### 1.2 写侧为什么读它

```asm
; 0x625BE0
0x625C0C  mov eax, [esi+8]
0x625C0F  mov edx, [eax+0x118]           ; ★ 同一个字段
0x625C17  add eax, 0x18
0x625C1A  push 0x13 / call 0xB77B10      ; W_TAG(19)
...
0x625C35  push 0x20 / call 0xB777C0      ; W_VAL(edx, 32)
0x625C4B  lea eax,[edx*8] / call 0xB777C0 ; W_VAL(edx*8 bits)
```

★★★ **同一个对象 `[this+8]`，同一个字段 `+0x118`，同一个缓冲 `+0x18`。**
⇒ **`StartGame` 消息是"可转发的"：它把自己收到的第 1 段原样再发出去。**

## §2 我们的实现错在哪（只有第 1 段）

```python
w.write_blob(addr_67)   # 67 字节，自拼的 bdCommonAddr
```

| | 客户端 | 我们 |
|---|---|---|
| 容量/长度 | 255 容量，实际长度运行时定 | 硬编码 67 |
| 内容 | `[this+8]+0x18`，来自对端发来的数据 | 自拼地址块 |

**⇒ 若对端发来的第 1 段不是 67 字节，我们的实现就完全对不上。**

★ 但反向看：**如果 67 字节的 `bdCommonAddr` 就是"对端会发给我们的第 1 段"，那我们就对了。**
这一点本卷无法确认 —— 需要知道"谁给这个对象填 `+0x18`"。

## §3 位宽公式（定案）

```
bits = 5 + 8
     + (5 + 5 + 32 + len1*8)
     + (5 + 5 + 32 + 8*8)      ; 64
     + (5 + 5 + 32 + 16*8)     ; 128
     = 13 + (42 + len1*8) + 106 + 170
     = 331 + len1*8

len1 = 67  →  331 + 536 = 867 位 = 109 字节 ✓
```

★ 与 `verify9.py` 一致。

## §7 方法论

1. **★★★ 找"对端解析器"比找"本端序列化器"更可靠。** `0x625CE0` 直接暴露出三段容量 255/8/16，而 `0x625BE0` 只暴露"从内存读"。
2. **★★ 同一对象同一字段读写 = 转发型消息。** `+0x118`/`+0x18` 在 deserialize 里被写、在 serialize 里被读，说明这条消息**原样转发**。
3. **★★ 容量常量（`mov [ebp+8], N`）与长度立即数（`mov [ebp+8], N`）在同一函数里，要靠上下文区分。** 本卷靠"传给 `0x4F3EB0` 的第 2 参是 `&cap`"判定为容量。
4. **★★ 空桩 `0x8435D0` 出现在哪里，哪里就是"静默失败点"。** 超容量丢数据无日志。
