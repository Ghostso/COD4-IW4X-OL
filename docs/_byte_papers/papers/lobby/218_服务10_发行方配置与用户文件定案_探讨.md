# 服务 10 发行方配置与用户文件 · 探讨：两个 `push` 定死两个任务

> 对应：`lobby/218_服务10_发行方配置与用户文件定案.md`

---

## 一、这一卷最漂亮的一步，是"把两个函数摆在一起"

服务 10 的请求结构本身很好解（就是两个字符串），真正难的是回答："**到底哪个入口发 `10/21`，哪个发 `10/12`？**"

镜像里有**两个几乎一模一样**的入口：

```
0x7F9830   →  call 0xB9C9D0  →  call 0x7FAB00(0x66A710, …)
0x7F9910   →  call 0xB9C750  →  call 0x7FAB00(0x7F9A50, …)
```

闸门一样：`0x803830`（srpc 单例）→ `0xB7A670()==2`（`srpc+0x4F4` 会话已认证）→ `0xB80EC0("")`。
拷贝一样：`[esi+0x100]/[esi+0x104]` → `[esi+0xF0]/[esi+0xF4]`。
下沉一样：`0x7FAB00` → `0x7FA800`。

**唯一不同的就是中间那个 builder。**

于是我翻开两个 builder 的开头——它们都把参数打包给同一个 SDK 函数 `0xBA72C0`：

```asm
; 0xB9C9D0 （被 0x7F9830 调）
push eax ; push 0x400 ; push 0x15 ; push 0x0A ; call 0xBA72C0

; 0xB9C750 （被 0x7F9910 调）
push eax ; push 0x400 ; push 0x0C ; push 0x0A ; call 0xBA72C0
```

**两条里共同的那个数是 `0x0A`。**

而语料里服务 10 只有两个任务：**`10/21` 和 `10/12`**。

⇒ 两者**共享** `service=10`，**差异**在 task（`0x15=21` / `0x0C=12`）。
⇒ `0x0A=10` 必然是 **service**，`0x15/0x0C` 必然是 **task**。

---

## 二、这个推理不依赖任何符号表

它只用了两个事实：

1. 两个调用者调的是**同一个** SDK 函数（参数位置一致）；
2. 语料里这两个任务**共享 service、不同 task**。

**只要"两个样本共享一个字段、另一个字段不同"，共享的那个就是共享维度。** 这条判据可以迁移到任何"多态 SDK 调用"的场合。

而且它**自证伪**：如果反过来把 `0x0A` 当 task、`0x15` 当 service，就会得到 `21/10` 和 `12/10` 两个任务——**语料里根本没有**。

⇒ **一个能自动排除错误分配的判据，比"看起来合理"的判据强得多。**

## 三、我差点把 `0x7F9910` 当成"遥测"

第一遍看 `0x7F9910` 的时候，它出现在 `0x71ED90`（一次性惰性初始化）里，同段还有 `0x7F9B10`、`0x7F9910` 之类的调用，我第一反应是"这是日志/遥测"。

**差一点就写进 O-5 说"`the.json` 是诊断路径，与 `10/12` 无关"。**

救回来的动作是：**不要按"它在哪被调"判断它是什么，要按"它内部调了什么"判断。**

一展开 `0x7F9910` 就露馅了：

- 它 gate 在 **`srpc` 会话已认证**（`0xB7A670()==2`）；
- 它用 **`0xB9C750`**（含 `push 0x0C,0x0A`）组报文；
- 它最后 **`call 0x7FAB00`** —— 全项目唯一的下沉漏斗。

**遥测函数不会卡在 `srpc+0x4F4` 上，也不会走 `0x7FA800`。**

⇒ `0x7F9910` = **`10/12` 的入口**。

⇒ 教训：**"谁调它"是弱证据，"它调谁"是强证据。**

## 四、`requested_name()` 一直能用，但它是"猜"的

台账里服务端取文件名的方式是：

```python
m = re.search(rb"[0-9A-Za-z_\-\.]{3,}\.(?:info|json|dat|txt|cfg|result)", plain)
```

**正则猜文件名。** 为什么不解析真正的 TLV？

因为它**一直能用**——所有要取的文件都有 `.info` / `.json` 扩展名。

⇒ 但这是**巧合级**的鲁棒性。本次剖出的 `10/21`/`10/12` 明文里，文件名前面的字段就是一个空字符串（`10 00`），千真万确的结构是 `[ns ""][name]`。写死正则以后，**任何没有点号的名字都会失败**。

⇒ 又一次撞上那条规律：**"有源码" ≠ "源码是对的"**；**"一直没出错" ≠ "逻辑正确"**。

## 五、我不太放心的地方

**1. `10/20` 我完全没解开。**

载荷是 14 字节，98 个 run 一模一样：

```
10 00 | 08 00 00 00 00 | 06 20 00 | 06 00 00 | 00
```

`[空串][u32 0][s16 32][s16 0]`。我按 `push 0x20`（=32）当锚去附近扫，没扫到形状吻合的写入簇。

⇒ 台账里**根本没有 `10/20` 的分支**，客户端镜像里我**没定位到发送点**。

⇒ 这是本轮唯一一个"三个材料都缺"的任务。**它很可能是个"请求文件清单/摘要"之类的东西**（`32` 可能是个分页大小），但这是**猜**，我不写进结论。

**2. 我把"每 run 10 条"归因到注册表为空，这一步是推断。**

`0x50DB90(index)` 查 64 条目注册表（`0xE56FFE0`, stride `0x50`），命中就跳过。**全新 run 注册表为空 ⇒ 10 个全请求**，这条链是通的。

但我**没有**制造一个"注册表非空"的实例去验证"命中就跳过"。所以"这是缓存机制"只是**结构推断**，不是行为验证。

**3. builder 里的 `push 0x400` 我当成了"缓冲大小"。**

`0xBA72C0(buf, service, task, 0x400, name)`——`0x400=1024`。它也可能是"最大字段数"或"版本"。**我没展开 `0xBA72C0`。** 若它不是大小，不影响 `(service,task)` 的结论（那两个数是被**跨函数比较**钉住的），但它会影响我对"参数含义"的描述。

---

## 六、这一卷教我的三件事

1. **"它调谁"比"谁调它"重要**。判定一个函数是不是出网入口，看它内部有没有 `srpc` 闸 + 下沉漏斗，别看它被谁调。
2. **两个样本的差异字段 = 维度**。会自证伪的判据优先。
3. **`imul reg, N` + `add reg, BASE` = 步进数组**。这一条让我在 10 秒内拿到了 10 条目的完整表。
