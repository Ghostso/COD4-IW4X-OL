## 1. 出发点：`0x70` 挖出的一个陷阱

**`lobby/103` 里我发现 8/3 含 `0x70`，就在顺带统计时看到大量 `27 00 00 07` 重复。**

**第一次的解读（错的）：**

> "`27 00 00 07` 是一个 5 字节记录头，后面 1 字节数据，共 119 条，间隔恒为 5。"

**⇒ 这个"发现"看起来很漂亮：定长 5、119 条、间隔无一例外。**

**⇒ 但它错了。而且是以我最熟悉的方式错。**

---

## 2. ★ 真相：`27 00 00` 是**上一个 i32 的高 3 字节**

**`27 00 00 07` 的四个字节，在文法里属于两个元素：**

```
... 07 2c 27 00 00 | 07 1a 27 00 00 | 07 41 27 00 00 ...
     ↑  tag  val(i32=0x272c)   ↑  tag  val(i32=0x271a)
```

**⇒ `27 00 00` 是 `i32 = 0x0000272c` 的高 3 字节（小端）。**
**⇒ `07` 是下一个 i32 的标签。**

**⇒ 所谓"5 字节记录"，其实是"i32 元素（5 字节：1 标签 + 4 数据）
紧邻下一个 i32 标签"，而这两个相邻 i32 的四字节数据里恰好都是 `xx 27 00 00`。**

**★ 这是 `lobby/89` 里 D3 缺陷的**同一个错误**：把窗口内相邻两元素当成一个结构。**

**⇒ 教训重复了。这一次我因为"间隔恒为 5 且无一例外"而更加确信，
这恰恰是最危险的状态。**

---

## 3. 8/3 的真实结构

**用文法 v5 完整解析（84 条样本，全部解析成功）：**

```
8/3 = 
  u32 ×3           (0x08, 0x08, 0x08)      ← 值 (a,1,1)
  u32 ×1           (0x08)                  ← blob 内容 ID，见 §6
  blob ×1          (0x13)                  ← 长度可变，见下
  i32 ×125         (0x07)                  ← 恒定 125 个
  [终止符]
```

**实测元素标签分布：`0x07 ×10500、0x08 ×336、0x13 ×84`
⇒ 84 条样本 × (125 + 4 + 1) = 84×130，完全吻合。**

**★ 长度分布（12 种，主要 1416）：**

```
1413×1  1414×1  1416×70  1417×2  1418×2
1436×2  1437×1  1438×1  1874×1  1912×1  1913×1  1914×1
```

**⇒ 长度差异**全部来自 blob**（761~1262 字节），不是 i32。**

**⇒ i32 个数 84 条全部恒为 125（`125 × 84 = 10500`，与标签计数一致）。**

**★ 这纠正了一个初稿错误：我曾写"764 字节 blob 恒定"。
实际只有 70/84 是 764，其余分布在 761~1262。**

**⇒ 换句话说：`8/3` 是"4 个 u32 + 1 个变长 blob + 125 个定长 i32"。**

## 4. 125 个 i32 的排布（本卷核心）

**完整序列（样本间只有第 6 个值有 3 种变体）：**

```
[0]      0
[1]  30060   (0x756C)
[2]  30059   (0x756B)
[3]      0
[4]  30061   (0x756D)
[5]  10001   (0x2711)   ← ★ 3 种变体：10001 / 10106
—— 之后 120 个，以 10 为周期重复 12 轮 ——
每轮：10001 10028 10010 10049 10015 10042 10001 10028 10001 10028
```

**⇒ 周期 = 10，120 / 10 = 12 轮，完整闭合。**

**★ 各值的十六进制：**

```
10001 = 0x2711    10028 = 0x272C    10010 = 0x271A
10049 = 0x2741    10015 = 0x271F    10042 = 0x273A
```

**⇒ 六个值全部落在 `0x2711..0x2741` 区间（差 0x30 = 48）。**

**⇒ 这是一个**连续编号段**，不是任意值。**

**⇒ 高度可能：这是"解锁项 / 武器配件 / 成就"的 ID 段。**

## 5. 前 5 个 i32 的语义推断

```
0         = 保留/未使用
30060 = 0x756C
30059 = 0x756B
0
30061 = 0x756D
```

**⇒ `0x756B / 0x756C / 0x756D` 三个连号（30059, 30060, 30061），
与 `0` 交错出现。**

**⇒ 这个模式和 `0x27xx` 那段完全同构：连号 ID + 0 占位。**

**★ 假设：**
**- `0x27xx` 段 = 一类 ID（约 0x2711..0x277A，109 个可能值）**
**- `0x756x` 段 = 另一类 ID**

**⇒ 但 `0x756x` 只有 3 个值出现，而 `0x27xx` 有 7 个值。
数量级不对等 ⇒ 前段更可能是"版本/协议号"而非同类 ID。**

**⇒ 无法静态判定，记为待测。**

## 6. ★★ 第 4 个 u32 与 blob 一一对应（最强的结构证据）

**4 个 u32 的值：**

| # | 取值 | 说明 |
|---|---|---|
| 1 | 0..8（5 占 67/84） | 一个枚举（可能"模式/槽位"） |
| 2 | **恒为 1** | 常量 |
| 3 | **恒为 1** | 常量 |
| 4 | 15 种不同值 | 见下 |

**第 4 个 u32 的关键性质：**

```
15 种 u32#4 值  ↔  15 种不同的 blob 内容（MD5 一一对应）
```

**⇒ 没有一个 u32#4 对应两种 blob，也没有两种 blob 共享 u32#4。**

**⇒ 这是**一一映射**（已用含变长 blob 的全 84 条复检：15 个 u32#4，0 个一对多）。**

**它**不是** CRC32（`u32#4=1b97d354` 而 `crc32(blob)=4d89f17f`），
**也不是** MD5 前 4 字节（`423a8dba`）。**

**⇒ 所以它是 blob 的某种**自定义哈希 / 版本标签 / 内容 ID**。**

**★ 这个一一映射是"8/3 是一个内容分发报文"的直接证据：
u32#4 标识这份 blob 是哪一版内容，客户端据此决定是否采用。**

## 7. `u32#1` 与 blob 的交叉

**`u32#1` 与 `u32#4` 的关系（实测）：**

```
u32#1=5  ->  u32#4 恒为 0x1b97d354      （67/84 条）
u32#1=6  ->  u32#4 有 4 种
u32#1=7  ->  u32#4 有 5 种
u32#1=8  ->  u32#4 有 2 种
u32#1=0..3 -> 各 1 种
```

**⇒ `u32#1=5` 时 blob 恒定（最常见的那版）；
其余值对应多种 blob ⇒ 说明 u32#1 与 u32#4 不独立。**

**⇒ 最简解释：`u32#1` = 内容类别，`u32#4` = 该类别下的具体版本。**

```
10028 (0x272C) ×2892

10010 (0x271A) × 964
10049 (0x2741) × 964
10015 (0x271F) × 964
```

**⇒ 周期内前两个值（10001, 10028）出现 3 倍，后四个各 1 倍。
这与 §4 的 10 周期里 `10001 10028` 出现三次完全吻合。**
