# UI 层定位 · 探讨：从 23GB 收缩到 40MB

> 对应：`lobby/18_UI层定位_gfx容器.md`

---

## 一、这一步是怎么走出来的

### 起点

974 个 `.ifs`，23 GB，全部是未知。

### 第 1 步：读清单（明文）

发现每个 `.ifs` 里有明文 `.lst` + 资源路径。

### 第 2 步：按 `.ff` 归类

得到 589 个 `.ff` 名，按前缀分组：

- `common_gametype_*` → 模式
- `common_mp` → 大厅数据
- `common_marketplace_*` → 市场
- **`ui_mp`** → UI

### 第 3 步：反查 `ui_mp` 在哪个 `.ifs`

`tools/ifs_find_keyword.py` 扫所有清单，命中：

```
ff_init_common_gfx_V109.ifs
```

### 第 4 步：读这个 `.ifs` 的完整清单

10 个 `.ff`，全部是 UI/脚本/播放列表。

**定位完成。**

---

## 二、为什么 `ui_mp` 会在 `gfx` 容器里

`ff_init_common_gfx_V109.ifs` 这名字看着像"图形"。

但里面装的是：

```
code_pre_gfx_mp.ff     ← 前置脚本
code_post_gfx_mp.ff    ← 后置脚本
ui_mp.ff               ← UI
mp_playlists.ff        ← 播放列表
development_mp.ff      ← 开发模式
common_mp_reload.ff    ← 热重载
```

**`gfx` 是个误导性的名字** —— 它装的其实是"启动链 + UI + 脚本"。

**教训：不要按容器名字猜内容，要读清单。**

---

## 三、这个发现的实际价值

### 之前

> "大厅在某个 34MB 或 777MB 的 `.ifs` 里，具体哪个不知道。"

### 之后

> "大厅 UI 在 `ff_init_common_gfx_V109.ifs` 的 `ui_mp.ff` 里；
>  模式配置在同一个文件的 `mp_playlists.ff` 里；
>  大厅逻辑在 `code_post_gfx_mp.ff` 里。"

**从"一片黑"变成"三个具体文件"。**

---

## 四、还差什么

**还差"打开加密容器"这一步。**

10 个 `.ff` 都是 AES 加密的。
但这次定位让"打开"这件事有了明确的目标：

- 不需要解 23GB
- 只需要解 **40MB 里的 3 个关键 `.ff`**

---

## 五、一条可能的旁路

`mp_playlists.ff` 和 `10/21` 的
`mp_playlists_shipRetail_1.0.0.info` 可能是同一份数据的两种形态。

如果服务端下发的 `.info` 会覆盖磁盘上的 `mp_playlists.ff`，
那么：

> **改模式列表 / 改可用地图，只需要改服务端下发的 `.info`，不需要碰 `.ff`。**

这条旁路**绕开了 AES**。

**这需要验证**：改 `.info` 后客户端是否采纳。

（这是下一步最有价值的实验。）

---

## 六、方法论收获

> **定位比解密更优先。**

在拿到 AES 密钥之前，先做一次完整的"东西在哪"的梳理，是值得的。

因为：
- 定位不依赖密钥
- 定位后，解密的目标从"未知"变成"已知的几个文件"
- 有些功能可能根本不需要解密（服务端下发路径）

**"把所有东西找出来" 和 "把东西都解开" 是两件事，
前者成本低、收益高，应该先做。**
