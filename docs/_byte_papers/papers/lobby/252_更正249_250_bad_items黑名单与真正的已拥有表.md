## §0 结论

1. **★★★★★ `[0xC9113CC]` 不是「已拥有表」，是 `bad_items` 黑名单**（dvar `ui_config` / `"bad_items"` 驱动）。
2. **★★★★★ 真正的「已拥有表」= `0x8269FC8`**，计数 `[0x84ABB4C]`（dump 时 = **32**）。
3. **★★★★★ 已拥有表 ≠ 服务端库存**：dump 里 **121 在库存里、却不在已拥有表**；32 项中只有 26 项与库存重合。
4. **★★★★ 60027 / 60028 / 60220 / 60221 四项都不在已拥有表** ⇒ 4/5 号背包与徽章槽 idx1/2 锁定的直接原因。

## §2 ★★★★★ 真正的「已拥有表」= `0x8269FC8`

### 2.1 查询器 `0x80A5E0(item_id)`

```asm
0x80A5E8  mov esi, [0x84ABB4C]        ; ★ 计数（运行时变量）
0x80A5F1  test esi,esi / jle → false
0x80A5F5  mov edi, [0xE4DD90]         ; 种子
0x80A5FB  mov ecx, 0x8269FD0          ; 项内指针（entry 基址 = 0x8269FC8 + k*12）
0x80A600  cmp byte [ecx - 4], 0       ; 存在标志
0x80A606  mov eax, [ecx - 8]
0x80A609  xor eax, edi
0x80A60B  xor eax, [ecx]
0x80A60D  rol eax, 8                  ; ★ 同一解码式（与 250 卷徽章表一致）
0x80A614  cmp eax, ebx                ; == item_id ?
0x80A616  je 0x80A627                 ; ★ 命中 → al=1
0x80A618  inc edx / add ecx,0xC / cmp edx,esi / jl ...
```

**⇒ `0x80A5E0(item)` = 「item 是否在已拥有表里」。**

### 2.2 dump 结果（表 `0x8269FC8`，计数 32）

⇒ **已拥有表是从徽章表一类"源表"搬运来的**。

## §3 ★★★★★ `0x5E3760(item, out)` 的完整「可用」判据

```asm
0x5E3760  ... 在 bad_items 里？ → 是 → out+4 = 0
0x5E378A  cmp [0x82E1310], 0 / je 0x5E381B
0x5E37AE  call 0x4A9F60
0x5E37B3  jne 0x5E3814
0x5E37B7  call 0x5E3550               ; ① item == onboardCharacterID || 0x80A5E0(item)
0x5E37BE  jne 0x5E37CD                ;   true → out+4 = 1
0x5E37C1  call 0x5E3580               ; ② 扫表 0x826A550
0x5E37CB  je  0x5E37F6                ;   false → out+4 = 0
0x5E37CD  or eax,-1 ... out+4 = 1     ; ★ 可用
```

**归约式**：
```
可用(item) = 不在 bad_items  且  ( item == onboardCharacterID
                                  || 在已拥有表 0x8269FC8
                                  || 在表 0x826A550 )
```

★ `0x5E3580` 扫的 `0x826A550`（7 组 × 12，22 项，解码式相同）与已拥有表**是两张不同的表**。

## §4 ★★★★ 「已拥有表」的填充：`0x80B5xx` 族搬运

```asm
0x80B5A6  mov ebx, 0x8269B74          ; ★ 源表
0x80B5AB  xor edi, [0xE4DD90] / rol edi,8
0x80B5B4  test edi,edi / je next      ; item == 0 → 跳过
0x80B5B8  cmp esi, 0x64               ; ★★ 上限 100
0x80B5BB  jge next
0x80B5BE  call 0x80A5E0               ; ★ 已在表里 → 跳过（去重）
0x80B5C8  jne next
0x80B5CD  lea esi, [esi*4 + 0x8269FC8]
0x80B5D6  call 0x810B20               ; ★ 写入条目
0x80B5E1  inc esi
0x80B5E2  mov [0x84ABB4C], esi        ; ★ 计数++
```

**⇒ 逐张源表扫描 → 去重 → 追加进 `0x8269FC8`，上限 100。**

★ 该族有 **十几处**同样形态（`0x80B5E2` / `0x80B634` / `0x80B686` / `0x80B6D8` / … / `0x80B98F`），
外加一批 `inc [0x84ABB4C]`（`0x80B9DA` / `0x80BA3B` / `0x80BA79` / …）⇒ **多来源、分批搬运**。

## §9 方法论

1. **★★★★★ 「命中 ⇒ true」不成立时必须读命中分支的赋值。** `0x5E3783 je` 跳到 `0x5E37F8 mov word [edi+4], bx` —— 写的是 **0**（不可用）。如果不是逐条算，会把黑名单读成白名单。
2. **★★★★ 变量的「名字」是最直接的语义证据。** `bad_items` 这个名字一开始就提示"黑名单"，我仍然先按"已拥有"解释了 249/250 两卷 —— **名字与推断冲突时，先查名字。**
3. **★★★★★ 「两个概念都在"物品列表"里」不等于它们是同一张表。** 库存(`Items`)、`bad_items`、已拥有表(`0x8269FC8`)、`0x826A550` —— **四张不同的表**。`121 在库存却不在已拥有表`这个反例，比任何正面证据都更能区分它们。
4. **★★★ 用"反例"验证概念区分。** 找到"属于 A 但不属于 B"的一个实例，就能证伪 `A == B`。
