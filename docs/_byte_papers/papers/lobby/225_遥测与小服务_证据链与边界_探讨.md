# 探讨：遥测与小服务的证据链与边界

> 与 225 卷配套，记录"哪些是铁证、哪些是负结论、下一步该往哪走"。

## 一、本卷最值钱的东西：读侧库

一整套 Demonware 值流读取器，全在 `0xB75E80..0xB76C20` 这不到 3KB 里：
- `0xB76310` 是**唯一的类型校验闸门**（读 1 字节 == 期望 tag，否则 `0xB773D0` 打名字）；
- 11 个读取器 1:1 对应 11 个 tag；且能反查出 **`0x0D=f32` 这种"台账没有"的类型**。

为什么它比"逐个服务找发起者"值钱：**它覆盖全部 7645 条样本**。任何新抓到的帧，只要 tag 属于这 11 个，就能直接解析，不用管是哪个服务。

副产品：读侧出现 `0x16` 特例（`0xB76354 cmp ecx,0x16`），与 170/178 卷"P2PInfo 子类型"吻合——八卷之外又一处闭环。

## 二、写侧为什么难，以及我怎么判它"穷尽"

写侧的格式其实早就定了——台账 `codol_crypto.Buf` 一行行写出了 `13 08 <len>`、`6c 08 <byteLen><count>`，和实测 wire 1:1。缺的只是"客户端里哪个函数在写"。

试了五路，全部落空，而且**每一条都给了"假阳的正面归属"**：
1. `C6 /0 imm08` 全镜像扫 → 1891 命中，但 `0xB6..0xBA` 段那 11 处反汇编是 `81 C6`（add）里的 `C6` 字节；
2. capstone 对齐重扫 B7 → 0 命中；
3. `b0 <tag>; … 88` → 113 命中，多为 `b0 01`（布尔真）；
4. `push <tag>; call X` → `0xAF98A0` 一度最像，反汇编后是**定长日志环**，假阳；
5. 结论：写路径大概走"tag 由参数传入的写入器"，静态不形成可枚举的函数族。

**关键方法论**：负结论不能只写"没找到"，要写"那些候选是谁"。否则下一个人会重复这五路。

## 三、服务名：一张"看着像协议表、其实是配置表"的坑

`0xE4E8F8` 那张表 `{name_ptr, enabled}` 和 `[dw_service_info]` 逐位吻合（5 个 =1）。**它就在可执行文件里、长得像注册表、还带名字**——很容易顺手当成"wire id 表"。
但它没有 id 字段。而且我去搜"id|ptr / ptr|id"邻接，0 命中。所以：**"名字在文件里"≠"能反推编号"**。这条防线救了本卷，否则会给 3/4/9/12/28/29/68 安上错名字。

## 四、下一步（按性价比排序）

1. **找"按名字注册服务"的初始化**：谁把 `"matchmaking"` 这个串和数字 `21/138` 连起来？这函数一找到，3/4/9/12/28/29/68 的名字一次全解。（线索：`0xE4E8F8` 表被哪个函数遍历；或搜 `0xDE0BD0`(matchmaking 串) 的代码引用。）
2. **拿一条 >96B 的 71/15 原始帧**（不被日志截断）→ 解 zlib → 补齐"事件总数"口径。
3. **18 种 vs 9 种的对账**：翻出旧卷分母，确认是否算了 71/15 内的压缩事件。
4. **写侧**：若确定要，可换思路——找"`Buf` 对象的构造点"（`push 0x08` 的调用者里不属于环/CRT 的那些），但性价比低。

## 五、一句话总结

**读侧有铁证（地址级）、写侧格式有铁证（字节级）、服务名编号是负结论（有穷尽证据）。** 三者边界清楚，是本轮最该守住的东西。
