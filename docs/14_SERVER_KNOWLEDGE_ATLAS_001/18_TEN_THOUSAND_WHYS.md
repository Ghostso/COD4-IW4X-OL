## 类别 A — 为什么两个实现相同？

### WHY-A01
- **问题：** 为什么 OLD 服务端的 `huffman.c` 与 CoD4x 有 99.7% 的行级相同？
- **项目：** OLD / 1113 / CoD4x　**类型：** 血统
- **当前结论：** 因为 OLD 源码**就是** CoD4x 的 fork（IW4OL）。
- **证据：** EV-R-OldSrc；`q_shared.h:6` 字面 "fork of CoD4x"；Jaccard 99.7%
- **候选原因：** H1 共同祖先 / H2 fork / H3 架构共性 / H4 同规范
- **反证：** H3/H4 无法产生 99.7% 行级一致与逐字相同版权头
- **未解决项：** 无（已闭合）
- **后续行动：** 无
- **状态：** **已解决**

### WHY-A02
- **问题：** 为什么 OLD 与 1113 的协议层看起来完全一样？
- **项目：** OLD / 1113　**类型：** 血统
- **当前结论：** 因为它们是同一份源码的两个构建（216/217 文件字节相同）。
- **证据：** EV-R-OldSrc-1113（唯一差异 `g_sv_main.c`）
- **候选原因：** H1 / H10
- **反证：** 无
- **未解决项：** 为什么作者要维护两个几乎相同的构建
- **后续行动：** 查启动器侧分发意图（非协议问题）
- **状态：** **已解决（协议层）** / 动机层 OPEN

### WHY-A03
- **问题：** 为什么 MSG_WriteByte/Short/Long 在 OLD 与 CoD4x 中同名同结构？
- **项目：** OLD / CoD4x　**类型：** 血统
- **当前结论：** 同源于 Quake3/Id Tech 的消息游标接口（并因 fork 而保持）。
- **证据：** EV-R-OldSrc；`msg.c` 行；CoD4x 同名函数
- **候选原因：** H1
- **反证：** 无
- **未解决项：** Quake3 原始实现与 CoD4x 之间的中间版本链
- **后续行动：** 若允许外部资料，追 Id 上游（当前禁止联网）
- **状态：** **已解决**

## 类别 B — 为什么两个实现不同？

### WHY-B01
- **问题：** 为什么 CODOL 的战斗握手与 CoD4x 完全不同？
- **项目：** CODOL / CoD4x / IW4x　**类型：** 设计
- **当前结论：** CODOL 在 fork 骨架之上**独立实现**了 cookie+ECDH P-224+MAC 握手。
- **证据：** EV-DTLS-Wire；EV-Battle-Distinct；CoD4x `grep CODOL|Xor|stride|1162` = 0
- **候选原因：** H5 独立实现 / H4 同规范 / H2 fork
- **反证：** H4 排除（对方无结构）；H2 只解释骨架不解释握手
- **未解决项：** CODOL 为何选择 P-224 而非更高强度曲线（产品决策无档案）
- **后续行动：** 无（属不可反推的产品决策）
- **状态：** **已解决（技术层）**

### WHY-B02
- **问题：** 为什么 2697 的 gamestate opcode 从 `0x02` 变成 `0x03`？
- **项目：** 2697 / Old / 1113　**类型：** 协议演化
- **当前结论：** 2697 引入**独立通道**，其 opcode 空间与旧通道并存但不共用编号。
- **证据：** EV-2697-MsgTypes（旧通道 0x02 仍在 2697 二进制中；2697 通道起 0x03）
- **候选原因：** H7 协议升级 / H4 规范 / H11 观察假象
- **反证：** 旧通道 opcode 常量在 2697 二进制中仍然存在 → 不是替换而是并存
- **未解决项：** 客户端如何区分两条通道（`NOT-OBSERVED`）
- **后续行动：** 找客户端通道选择点
- **状态：** **较强推断**（并存）；通道选择 **OPEN**

### WHY-B03
- **问题：** 为什么 2697 的 EOF 从 `0x05` 变成 `0x06`？
- **项目：** 2697　**类型：** 协议演化
- **当前结论：** 外层终止符由 `_CODOL_Target2697ArchivesActive` 选择，是**条件切换**而非全局替换。
- **证据：** EV-2697-Snap-Outer（RVA 0x87104：false→0x05，true→0x06）
- **候选原因：** H7
- **反证：** 无
- **未解决项：** 客户端是否同时支持 0x05 与 0x06
- **后续行动：** 客户端 EOF 分支定位
- **状态：** **较强推断**

### WHY-B04
- **问题：** 为什么 `0x06` 在 2697 snapshot 内部与外层都出现？
- **项目：** 2697　**类型：** 协议细节
- **当前结论：** 内部 `0x06`（RVA 0xA4CAF）是子记录/阶段终止；外层（RVA 0x87104）是消息终止。
- **证据：** EV-2697-Snap-Seq（内部 0x06 后仍继续写 HUD/entities）
- **候选原因：** H4 规范 / H11 假象
- **反证：** 若内部即 EOF，后续写入不可能
- **未解决项：** 客户端对内部 `0x06` 的处理
- **后续行动：** 客户端 snapshot 解析闭环
- **状态：** **较强推断**

## 类别 C — 为什么一个项目复用某模块，另一个重写？

### WHY-C01
- **问题：** 为什么 OLD/1113 直接用引擎的 netchan，而 CODOL 又要 `CODOL_NetchanProcess` 接管？
- **项目：** OLD / CoD4x　**类型：** 架构
- **当前结论：** CODOL 需要加密/分片/XOR 语义，所以用 `#ifdef CODOL_SERVER` 在 netchan 上**注入** CODOL 路径，而非另写一个传输层。
- **证据：** EV-R-OldSrc（`netchan.c:140` `return CODOL_NetchanProcess(chan,msg)`）
- **候选原因：** H2 派生 / H5 独立 / H6 定制
- **反证：** 新写传输层会重复 socket/超时/重传逻辑
- **未解决项：** ACK/重传调度为何未完成
- **后续行动：** 查 `codol_netchan.c` 的 TODO
- **状态：** **较强推断**

### WHY-C02
- **问题：** 为什么 OLMod 用插件重实现，而 2697 用原生 EXE 扩展？
- **项目：** OLMOD / 2697　**类型：** 架构
- **当前结论：** 二者目标与可用资产不同：OLMOD 目标是**闭源 3.3.3.3 客户端 + 无服务端源码**，只能注入+hook；2697 是**官方原生服务端构建**，可直接在 EXE 内扩展。
- **证据：** EV-R-OlMod（Injector32/Bootstrapper32/Plugin ABI）vs EV-2697-Modules（源文件名+原生模块）
- **候选原因：** H5 独立 / H9 中间层 / H8 职责边界
- **反证：** 若 2697 有源码，也不会采用注入路线
- **未解决项：** OLMod 是否曾评估原生路线
- **后续行动：** 查 ol-mod `.agents/` 决策记录
- **状态：** **较强推断**

### WHY-C03
- **问题：** 为什么大厅可由第三方 REF_LOBBY_KIT 实现，而战斗不能由 CoD4x 实现？
- **项目：** 大厅 / 战斗 / CoD4x　**类型：** 协议可替代性
- **当前结论：** 大厅协议是**应用层契约**（可用 Python 重实现）；战斗协议含**自定义握手+加密**，无现成替代。
- **证据：** EV-Lobby-Third（实机进大厅）；EV-Battle-Distinct（CODOL 独有握手）
- **候选原因：** H4 / H5 / H6
- **反证：** CoD4x 与 CODOL 骨架同源（CAUSAL-01），但握手无对应物（EV-Battle-Cmp）
- **未解决项：** 大厅契约的完整性（`FULL_PVE=NOT_REPRODUCED`）
- **后续行动：** 见 19 的验证计划
- **状态：** **已解决（可替代性）** / 完整性 OPEN

## 类别 D — 为什么协议格式相似但字段不同？

### WHY-D01
- **问题：** 为什么 2697 服务端 `0x02`（long+short+data）与客户端 `0xA2E50`（long+short+payload）字段一致却无法确认？
- **项目：** 2697 / C-2697　**类型：** 交叉验证
- **当前结论：** 字段形状一致，但客户端**无 opcode 0x02 分派**；恢复镜像有结构性缺口。

- **候选原因：** H4 规范 / H11 假象
- **反证：** 无法排除 H11
- **未解决项：** 分派位置；运行时是否命中
- **后续行动：** `.rimp` 还原；运行时 dump
- **状态：** **未解决（WEAK_INFERENCE）**

### WHY-D02
- **问题：** 为什么 2697 configstring 头/尾可确认，body 却不行？
- **项目：** 2697　**类型：** 逆向深度
- **当前结论：** body 是位打包循环（含 12-bit 子记录），未逐位还原。
- **证据：** EV-2697-CS-Format（bits_a ≤ 0x7FF、bits_b ≤ 0x3FF、payload 0x0A/0x07/0x04）
- **候选原因：** H11
- **反证：** 无
- **未解决项：** index 位打包、字符串索引规则
- **后续行动：** 静态逐指令还原 RVA 0xA0807..0xA0997
- **状态：** **未解决（BLOCKED）**

## 类别 E — 为什么同一协议在不同版本中变化？

### WHY-E01
- **问题：** 为什么 2697 的可靠命令要多一个 `0x02` 二进制格式？
- **项目：** 2697 / Old / 1113　**类型：** 协议演化
- **当前结论：** 2697 引入 profile 转换（`_CODOL2697_ProfileCommandBytes`），把命令转为二进制；旧格式（NUL 字符串）保留为回退。
- **证据：** EV-2697-RC-Format + EV-2697-RC-Gate（`CODOL2697_PROFILE_WIRE=text` 时回退 0x01）
- **候选原因：** H6 / H7
- **反证：** 若只是压缩，不需要**两套并存**与显式回退开关
- **未解决项：** profile 载荷的语义（J/K 前缀含义）
- **后续行动：** 追踪 `0x85D32` 的编码分支
- **状态：** **较强推断**

### WHY-E02
- **问题：** 为什么 2697 新增 file/handle 探测导入？
- **项目：** 2697　**类型：** 版本演化
- **当前结论：** 用于读取**注册导出**与**挂载 archive**（resource probe）。
- **证据：** EV-S-2697（新增 `GetFileType`/`GetFileInformationByHandle`/`_open_osfhandle`/`_get_osfhandle`/`_stati64`/`_fstati64`）+ EV-2697-Modules（`codol_archive_probe.c`）
- **候选原因：** H7 / H6
- **反证：** CRT 工具链升级也会改变导入集；但 `_stati64`/`GetFileInformationByHandle` 属于新增**功能**而非纯 CRT 换名
- **未解决项：** archive 探测的实际协议作用
- **后续行动：** 追踪 `_CODOL_MountTarget2697Archives`
- **状态：** **较强推断**

- **反证：** 客户端 `push 2` 与 8 位假设**直接矛盾**
- **状态：** **已解决（8 位 REFUTED）**

### WHY-S04
- **问题：** 为什么 `0x06` 可能不在字节边界？
- **项目：** 2697　**类型：** 位流
- **当前结论：** 因为 `0x06` 由 `WriteByte(6)`（8 位）写出，其起始位偏移 = body 已写位长；索引增量存在 14 位（1+13）形态，故位长不总被 8 整除。
- **证据：** EV-09-04/05（模型：44/53/61/72/129）
- **候选原因：** H4（协议规范）
- **反证：** 若设计者强制对齐，应见显式补位；代码中未见
- **未解决项：** 客户端如何定位终止
- **状态：** **服务端 INFERRED 已定 / 客户端 BLOCKED**

### WHY-S05
- **问题：** 为什么 A1 的字符串不影响位偏移？
- **项目：** 2697　**类型：** 实现细节
- **当前结论：** 因为 `MSG_WriteData`（0x9949B）只更新字节计数 `[msg+4]`，**不**更新位位置 `[msg+0x10]`；`WriteLenStr`（0x99651）全函数亦无 `[msg+0x10]` 访问。下一个位字段在字节边界触发重同步 `bitpos = used*8`，**自然跳过**这些裸字节。
- **证据：** EV-09-04
- **候选原因：** H4（Quake3 血统的位/字节双游标设计）
- **反证：** 若字符串占位，客户端就不可能用 NUL 扫描（0xA25F0 确实用 NUL 扫描）
- **状态：** **已解决**
