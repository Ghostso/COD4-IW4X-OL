# 15 — 最终版客户端 / 服务端证据对接 / CLIENT-SERVER CORRELATION

> 目标：把 C-2697（2.6.9.7）逆向结果与 2697 服务端证据**逐项对接**。
> **核心纪律（任务书 §5.3 硬要求）：** **不能**把 2697 服务端的**写入实现**直接当成最终版客户端的**读取实现**。必须寻找客户端侧独立证据，或明确标记为尚未闭合。

---

## 1. 对接总表（逐项十问）

对每个对应关系，回答任务书 §6 的 10 个问题。

### 1.1 Reliable Command 0x02 ↔ `0xA2E50`

| # | 问题 | 回答 |
|---|---|---|
| 1 | 服务端/客户端函数是否承担同一协议角色？ | **未证实**。服务端 0x8612E 是可靠命令 writer；客户端 0xA2E50 是长+短+payload reader，角色**候选**一致 |
| 2 | 字段布局是否匹配？ | **匹配**（long4 + short2 + payload），VERIFIED |
| 3 | 调用时机是否匹配？ | 未知（客户端无调用者） |
| 4 | 长度限制是否匹配？ | **匹配**（0x3FC），VERIFIED |
| 5 | 错误处理是否匹配？ | 未知（客户端错误串仅自引用） |
| 6 | 是否存在中间封装/平台代理？ | 未排除。`client_room2697.dll` / `client_native_loopback.dll`（ImageBase 0x10000000，导入 WS2_32）存在但未建立函数级对应 |
| 7 | 是否存在版本差异？ | 未排除（C-2697 打包 vs 恢复镜像） |
| 8 | 是否有真实字节/运行时证据？ | **无**（NOT-OBSERVED） |
| 9 | 现有反例是否推翻该映射？ | 无反例，但**无分派**这一事实不能证明映射成立 |
| 10 | 缺失的关键证据是什么？ | 客户端 opcode `0x02` 读取点 → 分派 → 0xA2E50 的调用链；或运行时命中 |

**裁定：`STRUCTURAL_MATCH`（字段形状）＋ 绑定 `UNKNOWN`。不得写成“客户端已支持 0x02”。**

## 3. 恢复镜像的证据限制（任务书 §6.1 硬要求）

| 限制 | 影响 | 本档案如何处置 |
|---|---|---|
| 原始最后 `.tp3`（VA 0xDC11000 起）未恢复 | **不能**把“全镜像无 xref”当作强否定 | 所有“未找到分派”一律标 `BLOCKED`，不标 `REFUTED` |
| `.rimp`（RVA 0xDC11000）修复 1536 B `.rdata` 指针表 | vtable/函数指针 xref 不代表运行时 | 候选函数**不**直接认定为消息解析器 |
| `.tvm0`（RVA 0xD958000）非线性代码岛（如 0xA04860、0x9FA070） | 无法线性追踪 | 保留为盲区 |
| 缺运行时解包 dump | 静态字节 ≠ 运行时映射 | 所有客户端结论上限为 STATIC-INFERENCE |

**明确禁止的四个升级（任务书 §6.1）：**
1. ❌ 把“恢复镜像缺少调用引用”当作“客户端不支持”的**强否定证据**。
2. ❌ 把 RVA 候选函数直接认定为消息解析器。
3. ❌ 把候选 `0xA2E50` / `0xA2D90` 直接认定为 Opcode `0x02` 处理函数。
4. ❌ 把 TenProxy、IIPS、TCLS、libcurl、SOCKS/QOS 的存在当成游戏协议调用链已闭合。

本档案对上述四点**全部保持 `BLOCKED`**。

## 4. 静态冲突的先决排除（任务书 §6.1）

当两个项目的静态结果冲突时，必须**先排除**：

| 排除项 | 本档案检查 |
|---|---|
| 样本身份 | C-2697（35375404…）vs C-2697-Rec（24b4ef25…）vs C-3333（36997674…）已分别登记 |
| 恢复质量 | aplib 静态恢复，`.tp3` 缺、`.rimp`/`.tvm0` 限制已登记 |
| RVA/VA 混淆 | 已用映射表校验（0x1AC1D0→VA 0x5AC1D0→off 0x1AB5D0；0xA2E50→VA 0x4A2E50→off 0xA2250） |
| 分析工具失效 | Capstone 确认为 `call/jmp dword ptr [IAT]` 才算网络调用点；字节命中不算 |

只有以上全部排除后，才讨论**真实实现差异**。

## 6. 对接结论

1. **全部 5 项 2697 应用层消息（gamestate/configstring/snapshot/reliable/EOF）在客户端侧均为 `BLOCKED` 或 `NOT-OBSERVED`。**
2. 唯一接近闭合的是 reliable command 的**字段形状**，但**opcode 绑定仍未证明**。
3. 客户端侧**已确认**的事实（Msg core、0xA2E50 形状、网络调用点、socket 枚举、端点解析器）都属**局部指令级**，无法拼成完整接收状态机。
4. 恢复镜像的三处结构性缺口（`.tp3`/`.rimp`/`.tvm0`）**先于**任何“实现差异”结论。
5. **最重要的一句：** 服务端能写 ≠ 客户端能读。本档案不把任何跨端映射升级为 `CONFIRMED`。

# === 追加：恢复镜像证据限制的量化（UPDATE-2, 2026-10-12） ===

## 新的限制项：`.data` 存在 99.86% 结构性缺失

| 项 | 值 |
|---|---|
| `.data` 声明虚拟大小 | `0x0D05C420` = 218,120,224 B（218 MB） |
| `.data` 文件中实际存在 | `0x00049600` = 300,544 B |
| 覆盖率 | **0.138%** |
| 缺失比例 | **99.86%** |

**因此（任务书 §6.1 的直接应用）：**

- **不能**把“在现有镜像中找不到 `0xA2E50` 的调用者/vtable”当作强否定证据——候选表项可能落在缺失的 99.86% `.data` 中。
- **也不能**把“`.rdata`/`.data` 指针表已被破坏”当作解释——`.rdata` 实测有 **30,895** 个 →`.text` 对齐指针与 **613** 个连续指针表；`.data` 现有部分也含 **2,375** 个 →`.text` 指针。措辞必须精确：**部分存在、部分缺失**。

## 另一项限制：`.tvm0` 的 E8/E9 不可作为调用者证据

| 区段 | E8 字节 | 目标在映像内 | 落在函数入口 | 可靠性 |
|---|---|---|---|---|
| `.text` | 168,888 | 137,010 | 130,362 | **95.1%** |
| `.tvm0` | 29,474 | 23,184 | **0** | **0.0%** |

- `.text` 扫描是**可信**工具 → 其 0 命中是**强负面信号**。
- `.tvm0` 扫描是**噪声** → 其 1 命中（RVA 0xD9D940F）**不构成**调用者。

## 修正后的四项证据限制（替代此前笼统表述）

| 限制 | 量化 | 影响 |
|---|---|---|
| 原始最后 `.tp3` 未恢复 | 打包客户端最后一节 VSize `0x03214000`（52.5 MB），恢复镜像对应区同址但 RawSize `0x2A00` | 不能作强否定 |
| `.data` 未恢复 | **99.86% 缺失** | 候选 vtable 可能在其中 |
| `.rdata` 指针 | 30,895 个真实 →`.text` 指针，但 →`0xA2E50` = **0** | 搜索有效但不完备 |
| `.tvm0` | E8 可靠性 **0.0%** | 原始字节扫描无效；需先解码 |

**净结论（对第 5 节对接表的影响）：** 全部客户端侧条目**维持** `BLOCKED` / `NOT-OBSERVED`，但**理由更精确**：不是“搜了没有”，而是“**搜索空间本身不完整（99.86% `.data` 缺失 + `.tvm0` 未解码）**”。
