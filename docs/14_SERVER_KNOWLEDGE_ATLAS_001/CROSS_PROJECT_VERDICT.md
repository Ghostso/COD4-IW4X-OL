## 二、哪些协议能够证明兼容？

### 已证明兼容（`CONFIRMED`）

**结论：目前没有任何一条“端到端协议兼容”被证明。**

- 服务端 `0x02 + long + short + data`（上限 0x3FC）↔ 客户端 `0xA2E50` 读取 `long + short + payload`（上限 0x3FC）：**字段形状匹配**（`CONFIRMED`），但 **opcode 绑定未证明**（`WEAK_INFERENCE`）。
- 2697 双门控机制：`CONFIRMED`。
- 2697 gamestate/configstring/snapshot **服务端写入格式**：`VERIFIED`。

### 部分证明（`PARTIAL` / `INFERRED`）

| 关系 | 状态 |
|---|---|
| OLD ↔ C-1113（1.1.1.13） | 两端静态身份 VERIFIED；**真实互操作从未跑通** |
| 2697 ↔ C-2697 | 服务端 VERIFIED；客户端 BLOCKED |
| OLMOD ↔ C-3333 | 文档声明双客户端实测；本机证据目录不存在 |
| CSHARP ↔ C-2697 | 自研；无真实互通 |

### 明确不能证明（`NOT-OBSERVED` / `BLOCKED`）

- 客户端 `0x02` 分派 → `0xA2E50`
- 客户端 `0x06`（EOF/EOS）处理
- 客户端 `0x03` gamestate parser
- 客户端 `0x04` configstring parser
- Snapshot delta 解码与帧边界
- **任何 2697 战斗通道的真实字节**

**纪律重申：** 服务端能写 ≠ 客户端能读。**不得**把“字段形状一致”宣布为“协议兼容”。

## 四、哪些业务逻辑必须从最终版客户端重新确认？

**全部客户端侧业务状态语义**都必须在 C-2697 上重新确认，特别是：

1. **gamestate state 字段语义**（state[0] / +4 / +8 / +0xC）——BLOCKED
2. **configstring body 位编码与索引语义**——BLOCKED（6519 条在 2697 中的对应关系未验证）
3. **snapshot 完整帧布局、delta 基准、实体字段范围**——BLOCKED
4. **reliable command 的 `0x02` opcode 绑定与 J/K 前缀语义**——WEAK
5. **`0x06` 的 EOF/EOS 语义与内部/外层分工**——NOT-OBSERVED
6. **2697 武器/附件/库存/Profile（PIK10、SKU、`CODOL_INVENTORY2697`、`CODOL_RUNTIME_WEAPONS2697`）**——BLOCKED
7. **2697 注册门控的 5 字段业务含义**——PARTIAL
8. **大厅↔战斗的端点/会话契约（Battle 端点下发后的拨号条件）**——PARTIAL
9. **安全档案（secure profile）/记分板/HUD 下行结构**——PARTIAL

**为何必须在客户端侧确认：** 服务端只定义**发出什么**；客户端定义**接受什么、如何解释、什么状态下才继续**。2697 门控已证明“服务端会主动不发”，客户端则可能“主动不接受”。两者**必须分别验证**。
