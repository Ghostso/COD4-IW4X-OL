## CAUSAL-01 — 为什么 OLD/1113 与 CoD4x 如此相似？

**问题：** OLD/1113 服务端源码与 CoD4x 大量结构、函数、文件同名同构。为什么？

**直接观察：**
- `q_shared.h:6` / `qcommon.h:6`：**"This file is part of IW4OL source code, a fork of CoD4x."**
- 行集合 Jaccard：`huffman.c` 99.7%、`cvar.c` 97.9%、`cmd.c` 97.6%、`netchan.c` 95.0%、`filesystem.c` 93.8%。
- CoD4x 中 `CODOL` 标记 = 0；OLD 中 = 1,844。

**跨项目对照：** OLD ≡ 1113（216/217 文件字节相同）；OLD 与 CODOL 专用层仅 OLD 有。

**候选原因：** H1 / H2 / H3 / H4。

**支持证据：** 字面 “fork of CoD4x” + 高 Jaccard + 版权链（Id / Ninja / TheKelm）。

**反证：** 若只是 H3/H4（同族/同规范），不会出现 **99.7%** 的行级相同，也不会出现逐字相同的版权块与注释。

**排除过程：**
- H3（架构继承）被高相似度**压倒**——架构共性不会产生 99.7% 行级一致。
- H4（同规范）同样无法解释逐字相同的注释与函数体。

**最终裁定：** **已证实（`PORTED_CODE`）——H2 直接 fork，且与 H1 共同祖先并存**（fork 自带 CoD4x 的共同祖先）。

**可证伪条件：** 发现 OLD 源码是从与 CoD4x 无关的第三份代码复制而 CoD4x 也是从该份复制（三方同源），且能给出该第三方源码。

**下一步最小证据：** 比较 CoD4x 与 OLD 的 `git log` / 版权头差异；已足够，无需新证据。

## CAUSAL-02 — 为什么 OLD 与 1113 几乎完全相同？

**问题：** OLD（`CODOL-AlphaBuild`）与 1113（`CODOL.NET\1.1.1.13`）服务端源码几乎一致。

**直接观察：** 顶层 217 文件，**216 个 SHA-256 逐字节相同**，仅 `g_sv_main.c` 不同（移除 `player_sprintTime` 的 `CVAR_CHEAT`，加“无限冲刺”注释）。`codol\` 子树递归差异 **0**。

**候选原因：** H1 / H10（样本混淆）／H7（版本演化）。

**支持证据：** 216/217 字节相同 + 唯一差异含中文玩法注释。

**反证：** H7（版本演化）不成立——若为版本演化，`codol\` 子树不会 0 差异。

**排除过程：** H10（样本身份错误）**反向成立**：不是“误认为相同”，而是**确实同源**，需在报告中显式标注避免把它们当作两个独立版本。

**最终裁定：** **已证实 `IDENTICAL_SOURCE`**。二者的差异属**启动器侧玩法改动**，**不是协议/引擎差异**。

**可证伪条件：** 发现更多差异文件。

**下一步最小证据：** 已足够。

## CAUSAL-03 — 为什么 2697 与 Old/1113 不同？

**问题：** 2697 服务端新增了大量 `codol_2697_*` 逻辑与不同 opcode。

**直接观察：**
- 2697 与 1113：同 EntryPoint 0x14e0、同 11 节区、同 Characteristics 0x326、同 DllCharacteristics 0x140、同 ld 2.47 / GCC 16.2.0。
- 仅 9 项导入差异 + 新模块层。
- 新增双门控（资源 `+0x78F4` / 注册 `+0x6408`）、新 opcode 集（gamestate 0x03、configstring 0x04、reliable 0x02、EOF 0x06）。

**候选原因：** H6（业务定制）／H7（版本演化/协议升级）／H8（职责边界）。

**支持证据：** 目标客户端从 1.1.1.13 变为 2.6.9.7；诊断串面向 `actual_client_crc` / `netconst`（**版本相关净约束**）；新增 file/handle 探测导入用于读取注册导出与 archive。

**反证：** 若 2697 是**新引擎**（推翻 H7），则 EntryPoint/节区布局/工具链不会与 1113 完全一致。

**排除过程：**
- H3（架构继承）：不足以解释“新增模块 + 新 opcode + 新门控”。
- H7（版本演化）：**被接受为主导**，因为新增内容与“适配 2.6.9.7”直接对应。
- H6（业务定制）：解释 game state/武器的具体新字段。

**最终裁定：** **较强推断** —— 2697 = 同族骨架 + **H7 协议升级** + **H6 业务定制**。

**可证伪条件：** 发现 2697 的骨架行级相似度显著低于 1113（例如 <70%），或发现 2697 与 1113 不是同一工具链产物。

**下一步最小证据：** 对 2697 与 1113 做**同名函数的控制流哈希**（静态可做）。

## CAUSAL-04 — 为什么 CODOL 的战斗握手与 CoD4x/IW4x 不同？

**问题：** CODOL 有 NAT/INIT/COOKIE + P-224 ECDH + MAC；CoD4x 只有 XOR 混淆，IW4x 无加密。

**直接观察：** EV-DTLS-Wire、EV-Battle-Distinct、EV-Netchan-Old/CoD4x/IW4x。

**候选原因：** H5（独立实现）／H4（同规范）／H2（fork）。

**支持证据：** CODOL 的握手是**独有**的 4 步自定义（NAT 29 B → INIT 16 B/cookie 38 B → cookie+pubkey/ack 114 B → data 06 02）。IW4x/CoD4x 中均不存在。

**反证：** 若来自共同规范（H4），CoD4x 作为同族服务端应能看到相应结构；实际 CoD4x `grep CODOL|Xor|stride|1162` = 0。

**排除过程：**
- H2（fork）：**部分成立**——CODOL 的**引擎骨架** fork 自 CoD4x（CAUSAL-01），但**握手不在** fork 范围内（CoD4x 无对应物）。因此 fork 只解释骨架，不解释握手。
- H4：排除（对方无对应结构）。

**最终裁定：** **已证实 `UNRELATED_OR_DIVERGED`（握手层）** —— CODOL 战斗通道 **DISTINCT**，属 **H5 独立实现 + H6 业务定制**。

**可证伪条件：** 在 CoD4x 或 IW4x 中找到 cookie+ECDH P-224 握手。

**下一步最小证据：** 无（已足够）；若要闭合，需 C-2697 抓包。

## CAUSAL-05 — 为什么 2697 服务端写入格式与客户端读取函数“匹配”却无法互通？

**问题：** 服务端 `0x02 + long + short + data`（上限 0x3FC），客户端 `0xA2E50` 读 `long + short + payload`（上限 0x3FC）。形状高度匹配，却无法证明互通。

**直接观察：**
- 字段顺序/上限匹配：CONFIRMED。
- 客户端分派：全映像 E8/E9 0 命中；绝对 VA 0x4A2E50 指针 0 命中；裸 RVA 指针 0 命中；已解析跳转表 0 命中。

**候选原因：** H4（同规范）／H5（独立实现）／H11（静态恢复假象）／H12（历史结论错误）。

**支持证据（H4）：** 两端字段顺序与上限一致，罕见地精确。

**支持证据（H11）：** `.tp3` 未恢复、`.rimp` 改写 `.rdata` 指针表、`.tvm0` 非线性代码岛、无运行时 dump。

**反证：** H4 无法解释“无任何分派路径”；一个真实使用的消息处理器在**恢复镜像**中通常至少有一条 xref（即使不完整）。

**排除过程：**
- **不能排除 H11**，因此**不能**把“形状匹配”升级为“实现一致”。
- H12 风险存在：早期报告可能把“形状相似”表述为“匹配”。

**最终裁定：** **弱推断（`STRUCTURAL_MATCH`）**。当前**最可能**的解释是 **H11（恢复镜像导致分派不可见）**，其次是 **H4**；但两者**都未被证明**。

**可证伪条件：**
- 推翻 H11：在完整运行时映射（0x1000–0xDC14000）中仍找不到到 0xA2E50 的回调/分派。
- 推翻 H4：抓到真实 2697 战斗字节，发现客户端对 `0x02` 无反应或语义不同。

**下一步最小证据：** ① 还原 `.rimp` 指针修复格式，重建 `.rdata` vtable/xref（静态可做）；② 运行时 dump / 断点（需授权）。

## CAUSAL-06 — 为什么内部 `0x06` 与外层 `0x05/0x06` 容易混淆？

**问题：** 2697 在 snapshot 内部（RVA 0xA4CAF）写 `0x06`，但**之后继续写** HUD 与第二遍 actors/entities；外层终止符在 RVA 0x87104 由 archive 激活选择 `0x05`/`0x06`。

**直接观察：** 见 `14` §5。

**候选原因：** H11（分析假象）／H4（协议规范）。

**支持证据：** 内部 `0x06` 后仍有写入调用 → 它**不是**消息终止。

**反证：** 若内部 `0x06` 就是 EOF，则后续 HUD/entities 写入将落在消息之外（不合逻辑）。

**排除过程：** 直接排除“内部 0x06 = 外层 EOF”。

**最终裁定：** **较强推断** —— 内部 `0x06` 是**子记录/阶段标记**（H4 协议规范）；外层才是消息终止（H4 + H7）。

**可证伪条件：** 抓到完整 snapshot 字节，发现内部 `0x06` 处消息确实结束。

**下一步最小证据：** 客户端 snapshot 解码闭环。

## CAUSAL-09 — 为什么大厅能进而战斗进不去？

## CAUSAL-10 — 为什么 2697 需要“注册导出”门控？

**问题：** 2697 在发送 gamestate 前要求一个通过 CRC 校验的注册导出文件，否则 `return 0`。

**直接观察：** EV-2697-Gate、EV-2697-RegRead、EV-2697-ResStruct、EV-Registration。

**候选原因：** H6（业务定制）／H8（职责边界）／H4（协议规范）。

**支持证据：** 诊断串 `Read-only verified client registration export for target gamestate publication`；`dry encode`/`netconst checksum` 面向特定客户端净约束。

**反证：** 若只是普通配置，不应有 **CRC 校验 + 隐藏 `+0x6408` 标志 + memcpy 0xC814**。

**排除过程：** H6 + H8 合并解释：这是**服务端面向特定客户端版本的合法性门控**。

**最终裁定：** **较强推断** —— H6 业务定制 + H8 职责边界。

**可证伪条件：** 找到绕过该门控仍能发布 gamestate 的合法路径。

**下一步最小证据：** 完整恢复注册 5 字段语义与 `+0x78F4` 资源标志的合法设置路径。

## CAUSAL-13 — 为什么 2697 的传输层常量与 CoD4x 不同，却与 OLD 源码一致？

**问题：** 2697 二进制含 `0x489`(1161)、`0x24500`(1162×128)、`0x70cc729`(=ceil(2³⁷/1162))，与 OLD 源码 `codol_wire.h` 精确对应，却与 CoD4x 的 `PACKET_HEADER 10` / `MAX_MSGLEN 0x20000` 不同。

**直接观察：** 反汇编 `_CODOL_NetchanTransmit`（RVA 0x999B6）`cmp eax,0x489`；`_CODOL_NetchanTransmitNextFragment`（RVA 0x998D8）`mov eax,0x70cc729 ; mul ; shr edx,5`。

**跨项目对照：**

| 项 | OLD 源码 | 2697 二进制 | CoD4x | IW4x |
|---|---|---|---|---|
| 分片大小 | 1162 | `1161 = 1162-1`（比较用） | 4B start + 2B len | 同 CoD4x |
| 上限 | 1162×128 | `0x24500 = 1162×128` | `0x20000` | `0x20000` |
| 除 1162 | — | `ceil(2³⁷/1162)` | — | — |

**候选原因：** H1（共同祖先，仅骨架）／H2（fork）／H7（版本演化）／H3（架构共性）／H5（独立实现）

**支持证据：**
- H1/H2：OLD 源码字面 "fork of CoD4x"（`q_shared.h:6`）；共享骨架符号（`_Com_Init`/`_SV_Frame`/`_MSG_*`/`_Netchan_*`）在三份构建中均存在。
- H7：2697 新增 2697 层与常量。

**反证：**
- 若为 H3（架构共性），CoD4x/IW4x 也应有 1162/128 常量——实际**没有**。
- 若为 H5（独立实现），不会出现 `ceil(2³⁷/1162)` 这种**精确魔数**对应关系。

**排除过程：**
- H3、H5 **排除**（对方无对应常量）。
- H2（fork）解释**骨架**；`codol_*` 层是 CODOL 在 fork 之上新增（CoD4x 中 `CODOL` 标记 = 0）。

**最终裁定：** **已证实** —— 2697 传输层是 CODOL 家族的延续（`PORTED_CODE`，常量级证据）。这与 CAUSAL-01（骨架 fork）一致，且**不矛盾**：fork 提供骨架，CODOL 提供传输层常量。

**可证伪条件：** 在 CoD4x 或 IW4x 中找到 1162/128 或 `ceil(2³⁷/1162)`。

**下一步最小证据：** 无（已闭合）。

## CAUSAL-14 — 为什么"搜索不到客户端分派"不能升级为"客户端不支持"？

**问题：** 恢复镜像中 `.text` 对 `0xA2E50` 的直接调用 = 0，是否等于"客户端不支持 `0x02`"？

**支持证据（H4）：** `.text` 与 `.rdata` 两个**高完备**搜索面均 0 命中。

**反证：**

- H11 无法单独解释 `.rdata` 30,895 个指针中无一指向 `0xA2E50`。

**排除过程：** **两者都不排除。**

**最终裁定：** **未解决（`BLOCKED`）**。措辞必须精确：
- 可以说"**不在 `.text` 线性直接调用图中**"（高完备搜索面）。

- **不能**说"客户端不支持 `0xA2E50`"。

**可证伪条件：** 获得完整 `.data` 与运行时映射后重搜。
