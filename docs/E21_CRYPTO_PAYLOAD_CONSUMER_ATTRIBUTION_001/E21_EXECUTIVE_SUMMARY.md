# E21 执行摘要

## 一句话结论

E-20 的 HMAC/加密载荷对象属于 Demonware 会话/加密边界，不是已证明的 CODOL 实时游戏消息解析器；在本次定向审计范围内未建立通向任何已知游戏解析候选的调用边。

## 本轮已证明事实

1. `0x6A84E0` 是对象构造器，写入 vtable VA `0xC5B0A4`（RVA `0x85B0A4`，.rdata）。
2. vtable 槽位为 `0xAA8570, 0xAA85A0, 0xAA83C0, 0xAA82E0, 0xAA88C0, 0xAA8720`。
3. 字符串 `HMAC calculation`、`HMAC mismatch`、`Bad recv counter`、`Bad frame/payload size` 的直接代码引用点全部位于函数 `0x6AAE70`。
4. `0x6AAE70` 由 `0x6AC0C0` 调用；后者读取连接状态 `[esi+0xC8]`、帧长 `[esi+0xAC]`、对象 `[esi+0xB0]`，再调用 `0xA85AD0` 并按键值 `[esi+0x5CC]` 分支处理。
5. `0x6A84E0` 有 34 个静态调用点，证明它是广泛复用的对象构造器，而非单一游戏消息处理分支。
6. `0xAAB1C0` 以后是 .tvm0/VM 混淆区域，线性反汇编不可作为语义证明。

## 被推翻或降级的旧假设

- E-19 的“type 1 -> size 1、type 2 -> size 9”被 `REFUTED`：类型 1 与 2 汇合至 `0x6A9978`，均执行 `mov ebx,9`。
- 不得仅凭 vtable 邻近字符串断言该对象承担 HMAC 校验；字符串引用已给出一个更强的强推断，但完整处理语义受混淆边界限制。
- 不得把 Demonware 长度前缀、类型 1/2、demo 子帧类型与游戏 opcode 等同。

## 是否找到实时游戏解析链

未找到。已检查的直接/静态调用边没有通向 `0xA2660`、`0xA2E50`、`0x350170`、`0x3547D0`、`0x354100`、`0x3524F0`、`0x352570`。

## 剩余最高风险阻塞项

`.tvm0` 混淆边界、间接调用目标、BSS 运行时构造和跨线程/队列交接。类型码 1/2 的真实语义仍为 `BLOCKED`。
