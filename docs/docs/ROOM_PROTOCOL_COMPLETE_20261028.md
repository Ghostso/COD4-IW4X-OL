# CODOL 房间协议 —— 完整线上格式规格

**证据来源**：客户端运行时内存里的发送缓冲区（`snap_003` @ `0x3AC62E40`）
+ 209 条真实上行样本（63 份 `lobby_srv.log`）。
本地实证，优先级最高。

---

## 一、三层结构（全部实测确认）

```
L1 外层信封
   08 <u32 service>            固定 11
   0a <u64 senderId>           实测 1
   10 <string> 00              "Player"
   13 08 <u32 payloadLen>      payload 起始

L2 payload
   0a <u64 roomId>             0x1122334455667788
   13 08 <u32 innerLen>        实测 145
       <u32 innerLen-4>        ★ declared 恒等于 innerLen-4
       <inner body>
   08 <u32 tail>               实测 1

L3 inner body
   见 §三
```

**`declared == innerLen - 4` 在全部 209 条样本中成立**，无例外。
这是嵌套长度前缀，不是校验和。

---

## 二、L1 信封与我们的实现对照

| 构造 | 与客户端共同前缀 | 判定 |
|---|---|---|
| `build_room_push` | **1 字节** | 错（第 1 字节写 `08 08`=kind 8，客户端是 `08 0b`=11） |
| `instant_push_body(kind=11)` | **24 字节** | 前 24 字节完全一致 |

⇒ **房间推送必须用 `instant_push_body(kind=11)`，不是 `build_room_push`。**

## 三、L3 inner body —— 两类消息

### A 类：`02 <sub> ...`（容器型）

前缀 `02 <sub> 0000 <u32 len>`：

| body 长度 | 样本数 | 恒定内容 |
|---|---|---|
| 12 B | 13 | `0202 0000 08000000 800800` |
| 16 B | 24 | `0202 0000 18000000 <u16> 00000000` |
| 20 B | 1 | `0202 0000 28000000 b8180000 ...` |
| 26 B | 2 | `0204 0000 18000000 a8080000 000030000000 5011 00000000` |
| 29 B | 1 | `0202 0000 4c000000 a0100000 000010000000 7068615a534c453e 0700` |
| 43 B | 1 | `0204 0000 28000000 b8180000 ...` |
| 59 B | 7 | `0206 0000 30000000 e068ab5bab63ab03 00000000 ...` |

`16B` 类的变化区 `u16@9` 取值：`0x00D0`、`0x10D0`、`0x08A8`。
低字节 `0xD0`/`0xD0`/`0xA8`，高字节 `0x00`/`0x10`/`0x08` —— 像
「值 + 类型」的打包。

### B 类：`18 <8B 恒定> cf01 <u32> 0000`（17 B，33 条）

```
18 1c5a98d6145391 cf01 <u32 LE> 00 00
   ^^^^^^^^^^^^^^   ^^^^
   8 字节恒定        固定 cf01
```

33 条样本的 `<u32>` 呈**严格 +2 递增**的成组序列：

```
17202 17204 17206 17208 17210 17212
21438 21440 21442
25412 25414 25416 25418 25420
65262 65264 65266 65268 65270 65272
88156 88158 ... 88178
```

步长恒为 2 ⇒ 这是**编号对**（如 `entity<<1 | team`），不是计数器。

## 四、roomId 在内存中的排布（重要）

全快照搜索：
- `roomId_lo, roomId_hi`（低在前）→ **4 处命中**
- `roomId_hi, roomId_lo`（高在前）→ **0 处**

⇒ 客户端内部一律**低 32 位在前**。路由表项 `+0x10=0x55667788`、
`+0x14=0x11223344` 即 `p1=lo, p2=hi`。

## 五、房间对象（snap_003 / snap_004）

```
0x08425C08                       0x08425C10（同一对象的 +8 视角）
  +000  7E9FCCB8                 +000  55667788   roomId_lo
  +004  00000000                 +004  11223344   roomId_hi
  +008  55667788  roomId_lo      +008  00000000
  +00C  11223344  roomId_hi      +00C  01010000   flag 字节对
  +010  00000000                 +010  00000001
  +014  01010000                 +014  0000056E
  +018  00000001                 +018  0000041A
  +01C  0000056E                 +01C  00000000
  +020  0000041A                 +020  0000219D
```

`0x7E79C0` 校验的正是 `[obj+8]==entry_hi`、`[obj+0xc]==entry_lo`，
与该对象布局吻合。

出现时间线：snap_001(29s) 全 0 → snap_002(61s) 仅 `+0xC=1`
→ **snap_003(89s) roomId 写入** → snap_004(118s) 不变。

## 六、已证否的路线（勿重走）

| 假设 | 结论 |
|---|---|
| 房间消息走 Demonware 位流 (`writeBits(3)`) | **证否**：7 条样本 × 160 bit 偏移穷举，零命中 |
| `0x82E1458` 是 type→类注册表，空则丢弃 | **证否**：表在 `.tp3` 无文件初值，且 `0x634870` 空时是跳过而非丢弃 |
| `0x00DE07A4` 读不到是 ASLR 地址漂移 | **证否**：EXE 未开 ASLR（`DllCharacteristics=0x8100`），真因是 ACE 拦 RPM |
| 活进程 RPM / 硬件断点可取数 | **不可行**：`PROCESS_ALL_ACCESS` 仍 err=5 |
