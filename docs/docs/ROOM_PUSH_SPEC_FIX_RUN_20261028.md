# 按实测规格重做房间推送后的实机结果（2026-10-28 第十轮）

## 一、本轮改动（有实测依据）

上一轮从客户端内存里取到了**发送缓冲区原文**
（`snap_003` @ `0x3AC62E40`），据此确认两条：

1. 外层信封是 `instant_push_body(kind=11)` 的结构，
   旧 `build_room_push` 写 `08 08`（kind=8）在第 1 字节就错。
2. body 是 A 类形态 `02 <sub> 00 00 00 <u32 len> <payload>`，
   不是位流。

已改 `kit_roommsg_20261028/lobby_server.py`：

- 新增 `build_room_payload()`：按实测封装 L2
  （`0a <roomId> | 13 08 <len> | <u32 len-4> | <body> | 08 <1>`）
- 重写 `build_room_push()`：改用 `cc.instant_push_body(..., kind=11)`
- 新增 `_room_body_state()`：按实测样本构造 A 类 body
- `createRoom` 的三条推送改用新构造器

## 四、本轮新发现的现象

把全部 209 条上行按 body 去重后，客户端**自己发过**这些 body：

```
020200000018000000d0000000000000      ← 我们也编了这个
020200000018000000a8080000000000
020200000028000000b818000000000000000000
02020000004c000000a01000000000100000007068615a534c453e0700
020400000028000000b8180000...
020600000030000000e068ab5bab63ab03...
181c5a98d6145391cf01<u32> 0000        ← 33 种，u32 严格 +2 递增
```

⇒ 我们推的 body 形态客户端**自己也会发**。所以它收到的若是"自己发过的同款"，
可能被当作回声忽略。

## 五、尚未解释的关键点

1. **客户端为何对同格式推送无反应**。两种可能：
   a. 推送根本没被当作房间消息解出来（信封某处仍不对）；
   b. 解出来了但内容不足以点亮按钮（缺的是客户端从没发过的字段）。

2. **战斗服零收包与房间 UI 是两件事**。`mmbook accepted` 在
   10-26 那轮确实让客户端连上了 28960，本轮同样发了却无效 ——
   说明还有别的条件。
