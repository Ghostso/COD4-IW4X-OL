## 更正：先前两处错误结论

1. **"这段字节被打乱"** —— 错。字节完全正常，是我从 `0x00808790` 起反汇编落到了指令中间。
2. **"函数一直到 0x808BF7 才结束"** —— 错。`0x808932` 就 `ret` 了；
   `0x808933` 之后是 `int3` 填充，`0x808940` 起是**另一个函数**。
   从 `0x808B00` 起解会跨进下一个函数，得到完全无关的代码
   （那段里的 `popup_acceptinginvite` 之类与本函数无关）。

**教训：反汇编必须先确定函数边界（`55 8B EC` 序言 + `ret`/`int3` 结尾），
再在边界内线性解。跨边界取任意起点都会产生看起来合理、实际错误的结论。**

## 排除掉的错误读数（避免以后重犯）

- `[0x0826982C] -> "1756"`、`[0x08269818] -> "3291"`、`[0x08269788] -> "1758"`：
  这些是**实测对象名**，不是从反汇编推的。
- 反汇编里 `mov [g], eax` 出现在 `call` **之后**，存的是**上一次**注册的返回值。
  所以「`push "3291"` 紧挨着 `mov [0x826982C]`」会被读成 `0x826982C` 存 "3291"，
  实际存的是更早那次（"1755"/"1756"）的。**句柄槽与名字必须按实测对象名对齐，不能按相邻关系推。**
- 反汇编必须**从函数序言开始**。从任意地址起解会得到完全错误的结果
  （本次就因为从 `0x00808790` 起解，把 `add byte ptr [eax+0x24], ch` 之类的伪指令当成真代码）。

## ★★★ 重大更正：0x63C5E0 与闸门B 属于两个不同的类

`0x63C5E0` **不在** `0x00DC7274` 里。全镜像里它只有两处引用：
`0x00DC79C4`（vtable 项）和 `0x608711DE`（数据区，未定性）。

两个 vtable 的 RTTI（用 `vtable[-1] -> COL -> [COL+12] = TypeDescriptor -> +8 = name`）：

| vtable | RTTI | 含 |
|---|---|---|
| `0x00DC795C` | **`.?AVdwRoomMatchUber@@`** | `0x63C5E0` 在 **+0x68** |
| `0x00DC7274` | **`.?AVdwRoomImp@@`** | 闸门B `0x62FE80` 在 **+0x64** |

而**单例对象 `0x3B2BBE80` 的 vtable 是 `0x00DC7274`（`dwRoomImp`）**，
所以闸门 B / 闸门 A / 状态 4 那些（全部来自 `0x00DC7274`）确实作用在单例上。

但 `0x63C5E0`（含状态 5 = 自动开局那段）属于 **`dwRoomMatchUber`**，
是**另一个类**的虚函数，**不是**在 `dwRoomImp` 单例上调用的。

### 因此前面把两条链拼成一条是错的

之前的表述「闸门B → 状态机 0x63C5E0 → 状态5 自动开局」**不成立**：
前半段在 `dwRoomImp`，后半段在 `dwRoomMatchUber`，中间没有直接调用关系。

**仍然成立的部分**：
- `dwRoomImp` 的 `+0x10614` 由 dvar "3291" 派生、实测为 0（`0x62CB11` / `0x6300CB` 两处搬运）
- `0x62FE80` 确实读它

**需要重新确认的部分**：
- `dwRoomMatchUber::+0x68`（`0x63C5E0`）到底有没有被调用、由谁调用
- 「战斗开始」页究竟由哪个类的哪个虚函数驱动

## ★★★★ 结论：真正缺的是 dwRoomMatchUber 对象本身，不是闸门 B

### 判定：是「从未被调用」，不是「调用后失败」

`0x0063E510` 在 `0x0063E5D6` 有**无条件**的 `mov [0x82E1514], ecx`，
位置在分配（`0x63E5DC`）之前。实测该槽为 0 ⇒ **函数体一句都没执行**。

两条分支都会写 `[0x82E1518]`（成功写对象指针，失败写 0），实测 0 与上述一致。

### 5 个静态调用点

```
0x005D34CF  ← 在 0x005D32B0 里，解析 type/league/map/mode/playListID/maxPlayer/content 的函数
0x0063A74D  ← 包装 0x0063A720（push 0）
0x0063A79E  ← 包装 0x0063A770（push 1）
0x0063A7EE  ← 包装 0x0063A7C0（push 2）
0x0063B5AC
```

三个包装函数 `0x63A720 / 0x63A770 / 0x63A7C0` **本身没有任何静态调用者**，
解析函数 `0x005D32B0` 也没有。⇒ 整条创建路径全部经由**函数指针表 / 虚函数**调用，
静态 `call rel32` 搜不到。这条线在这里断掉，只能靠运行时断点（已确认被 ACE 堵死）
或继续找上层表的分发点。

### 三个包装的参数差异（房间类型）

```
0x63A720: push 0 / push 0     -> type 0
0x63A770: push 0 / push 1     -> type 1
0x63A7C0: push 0 / push 2     -> type 2
```

对应三种房间类型，剧情模式应该用其中之一。

## 因此

- `0x63C5E0`（含状态 5 = 自动开局）是 **`dwRoomMatchUber::+0x68`**，
  而这个类**在本次运行里根本不存在** ⇒ 那段自动开局代码绝无可能执行。
- 闸门 B（`dwRoomImp::+0x64`，由 dvar "3291" 派生、恒为 0）分析本身正确，
  但它只是**旁支**；就算把 3291 打开，也不会让 `dwRoomMatchUber` 出现。

**真正的卡点层级更高：创建 `dwRoomMatchUber` 的函数 `0x0063E510` 从未被调用。**

## ★★★★★ 完整因果链闭合：MyEventHandler 从未被创建

顺着"三个包装函数出现在哪张表"往上追，链条完整解出来了：

### 第一层：三个包装函数是**控制台命令**，不是自动路径

`0x0063B0F0` 用 `0x4F37A0`（按 `[0x33303B0]` 链表做字符串比对的查找函数）注册命令：

```
"room.match.quick"   @0x00DC6D8C  -> 0x63A720
"room.match.ranked"  @0x00DC6DA0  -> 0x63A770
"room.match.coop"    @0x00DC6DB4  -> 0x63A7C0    ← 剧情模式的手动命令
"room.match.cancel"  @0x00DC6DC4  -> 0x63A810
```

⇒ 这三个包装是**玩家手动敲的控制台命令**，不是自动开局走的路径。

### 第二层：真正的建房分发是 `0x0063B500`

```asm
0063B500  push ebp / mov ebp,esp
0063B509  cmp  byte [ebp+8], 0
0063B50F  je   0x63b5c6                 ; 参数为 0 -> 直接返回
0063B515  cmp  dword [0x82e1518], 0     ; 已有房间?
0063B51C  jne  0x63b5c6                 ; 有 -> 返回
0063B522  mov  ecx, [0x82e13fc]         ; dwRoomImp 单例
0063B52A  call [eax+0x74]               ; 取 eventHandler 对象
0063B52F  mov  edi, eax
0063B531  cmp  byte [edi+0x24], 0
0063B535  je   0x63b56d                 ; ==0 -> 走 "combat" 分支
...
0063B5AC  call 0x63e510                 ; 建房
```

### 第三层：`0x0063B500` 是 `MyEventHandler` 的虚函数

`0x63B500` 在常量区只出现一处：`0x00DC78F0`。该 vtable 的 RTTI：

```
.?AVMyEventHandler@?5??Init@dwRoomMatch@@SAXXZ@
```

即 **`dwRoomMatch::Init` 内部匿名命名空间的 `MyEventHandler`**。
⇒ 建房是被 **`dwRoomMatch` 的事件回调**驱动的，不是轮询。

### 第四层（决定性的）：`MyEventHandler` 实例数为 0

在整份 1478MB 转储里搜 vtable `0x00DC78F0` 的实例，**一个都没有**。

⇒ `dwRoomMatch::Init` 没有完成（或没走到注册监听的步骤），
⇒ `MyEventHandler` 没被创建，
⇒ 它的回调 `0x0063B500` 永远不会被调用，
⇒ `0x0063E510` 永远不会被调用，
⇒ `dwRoomMatchUber` 永远不会被创建，
⇒ 自动开局状态机（`dwRoomMatchUber::+0x68`）永远不跑，
⇒ 客户端停在"战斗开始"，不连 28960。

## 结论

**卡点的真正位置：`dwRoomMatch` 的初始化/事件注册没有发生。**
`MyEventHandler` 不存在是整条链断裂的最上游可观测点。

这也解释了为什么闸门 B / dvar 3291 / 三个 room.match.* 命令的调查都没有结果——
它们全在这条断链的下游，而链在第一环就断了。
