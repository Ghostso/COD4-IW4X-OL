# 房间对象实测结构（2026-10-28 第八轮）

用既有快照 `EARLIEST2_20261027_132645`（snap_001..004，覆盖 createRoom 前后），
不碰活进程、不涉及 ACE。

## 一、房间对象的出现时间线

对象基址 `0x08425C08`（roomId 在 `+8`/`+0xC`），另有等价副本 `0x08425C10`：

| 快照 | t | 内容 |
|---|---|---|
| snap_001 | 29.2s | 全 0 |
| snap_002 | 60.9s | 仅 `+0x0C = 1` |
| **snap_003** | **89.3s** | **roomId 写入** `55667788 11223344` |
| snap_004 | 118.3s | 与 snap_003 相同 |

`createRoom` 应答与 roomId 写入在同一轮出现，说明客户端收到应答后才建对象。

## 二、完整对象布局（snap_003）

```
0x08425C08                    换算到 0x08425C10 视角
  +000  7E9FCCB8   ← 疑似 vtable（但 RTTI 解不出，见 §四）
  +004  00000000
  +008  55667788   ← roomId 低 32      (= 0x08425C10 的 +000)
  +00C  11223344   ← roomId 高 32      (= 0x08425C10 的 +004)
  +010  00000000
  +014  01010000   ← 两个 flag 字节
  +018  00000001
  +01C  0000056E   (1390)
  +020  0000041A   (1050)
  +024  00000000
  +028  0000219D   (8605)
  +02C  00000000
  +030  6B4C2D0E E7C8A98A   ← 8 字节标识
  +038  452D374D 43365338   ← ASCII "M7-E8S6Clie"（客户端实例名）
  +040  6E65696C 00000074   ← "...lient\0"
```

## 三、roomId 在内存中的字节序是确定的

全快照搜 `roomId_lo, roomId_hi`（低在前）→ **4 处命中**；
搜 `roomId_hi, roomId_lo`（高在前）→ **0 处**。

⇒ 客户端内部一律 **低 32 位在前**。
（此前我按 `0x11223344/0x55667788` 顺序解读路由表项，实际表项
`+0x10=0x55667788`、`+0x14=0x11223344`，即 **p1=lo, p2=hi**。）

## 四、没能解出的部分

- `0x7E9FCCB8` 当作 vtable 解 RTTI 得到乱码，`+004=0` 也不像正常对象头。
  该地址更像某个结构内部的字段，不是 vtable。
- `0x7E79C0` 里的 `edi` 没有在函数体内赋值，是调用者残留寄存器
  （`0x7F10C0` 传的 `[ebp+8]`），静态层追不到它指向什么。

## 五、对信封的直接推论

`0x7E79C0` 校验 `[obj+8] == entry[+0x10]` 且 `[obj+0xc] == entry[+0x14]`，
而实测 `entry[+0x10] = roomId_lo`、`entry[+0x14] = roomId_hi`。

⇒ 客户端期望：**消息解出一个对象，其 `+8` 是 roomId 低 32、`+0xC` 是 roomId 高 32。**

这与内存里房间对象的排布（`0x08425C08 + 8/+0xC`）完全一致 —— 客户端
是拿"消息里的房间对象"直接和自己那份做字段比对。

**仍未确定**：这个对象在信封里的字节位置。静态层已到尽头，
需要另找证据源（官方抓包 / 别的客户端实现 / 更早的转储窗口）。
