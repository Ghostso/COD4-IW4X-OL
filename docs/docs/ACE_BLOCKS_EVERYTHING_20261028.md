# ACE 内存拦截：实测结论（2026-10-28 第十六轮）

## 一、实测结果：句柄抢到即被拦

`probe_ace_window.py`，本轮 pid 2268：

```
句柄 pid=2268 handle=0x148 (t+0.01s)
  [t=0.01s] ★ PE_head 0x400000 首次失败 err=5
  [t=0.01s] ★ vtable  0xDE07A4 首次失败 err=5
  [t=0.01s] ★ code    0x634870 首次失败 err=5
```

**句柄抢到后 0.01 秒的第一次读取就已经 err=5，全程 240 秒从未恢复。**

三个目标全部失败：PE 头、vtable、代码段。
⇒ 不是"某段内存被保护"，是**整个进程的 ReadProcessMemory 被拦**。

## 二、与既有记忆的矛盾

既有记忆 `codol-ace-blocks-debug-and-read` 说：
- 早期句柄（t+15.39s）可读，`snap_003` 读到 1630MB / 0 失败块
- t+32.2s 之后永久 err=5

**本轮 t+0.01s 就失败。**

差异原因未知。可能是：
- 那次启动路径不同（非固化链 / 非提权方式启动）
- ACE 版本或策略变化
- 那次的 `OpenProcess` 成功了但实际读到的是缓存

无论如何：**按当前固化链启动，内存完全不可读。**

## 三、ACE 是内核驱动

```
ace-ats32.dll    1,758,784   COD OL
ACE-DRV32.dll    6,835,192   COD OL
ACE-BASE.sys     1,455,272   COD OL    ← 内核驱动
ACE-GAME.sys       383,680   COD OL    ← 内核驱动
```

有 `.sys` 驱动 ⇒ 拦截在内核层。
⇒ 用户态手段（换访问权限、抢早期句柄、调试器附加）**结构上绕不过**。

## 四、因此被排除的路线

| 路线 | 状态 |
|---|---|
| 活进程 ReadProcessMemory | **不可行**（t+0.01s 起 err=5） |
| 早期句柄窗口 | **不可行**（句柄抢到即失效） |
| 硬件写断点 | 不可行（依赖调试附加，ACE 拒绝） |
| 建房后抓转储 | 不可行（建房在 ~90s，此时早已被拦） |
| 比对建房前后 Scaleform 状态 | **不可行**（无法读内存） |

## 五、仍然可行的

1. **静态分析**（已有转储 `MEMDUMP_20261027_v4`、`EARLIEST2_20261027_132645`）
   —— 但这些快照只到 t=118s，且是**某次能读的运行**留下的。
2. **网络字节**（客户端上行 + 我们下行）
3. **文件系统**（`.ff` / `.ifs` / 配置）

## 六、如果要继续运行时取证，唯一可能的方向

在**不启动 ACE** 的前提下运行客户端。已知线索：
- `codoMP_client_shipRetail.exe.local\` 和 `...Base.dll.local\` 是 DLL 重定向壳
- 但 ACE 是驱动的 `.sys`，不是 DLL，重定向管不到
- 需要找到阻止 `ACE-BASE.sys` / `ACE-GAME.sys` 加载的办法
  ——这属于绕过反作弊，**不在我应当协助的范围内**

## 七、结论

**运行时取证这条路在当前环境下是关闭的。**

房间按钮问题只能靠静态分析推进，而按钮逻辑在 Scaleform `.gfx`
（编译过的 Flash）里，EXE 中零引用。

诚实的评估：**这条线目前没有可执行的下一步**，
除非能拿到 `.gfx` 的解析工具，或找到别的测试环境（例如不含 ACE 的离线客户端）。
