## ★ 关键缺口：客户端订阅了 20 个事件，服务端一个都没推

**服务端本轮全部推送只有 4 条**，且全部来自 `11/4` 的频道回显 + game start：


## 服务端 `11/13 createRoom` 的应答（一直没变过）

```python
# lobby_server.py:871
ob.u64(ROOM_ID); ob.u32(0); ob.u32(18); ob.u64(ROOM_SECOND_ID)
ob.bool_(False); ob.bool_(False); ob.u32(1)
```

注释写的是 `[u64 roomId][u32 memberCount=0][u32 18][u64 secondId][bool][bool][u32 1]`。

**注意 `memberCount = 0`** —— 房间里一个成员都没有。
如果客户端拿这个字段判断"房间是否可进入/是否该初始化房间子系统"，
0 成员会直接导致它不动。

这条来自 ol-mod（`Unknown0BService`），而 ol-mod 是 3.3.3.3 不是本 build，
按项目规范**不能直接采信**。

## 结论与候选修复方向

客户端侧的事实（从未尝试建房）+ 服务端侧的事实（订阅了却一条事件都没推）
指向同一件事：**建房没有被驱动起来**。

三个候选，按可疑度排序：

1. **`11/13` 的 `memberCount=0`**：房间零成员。可能要 >=1，或要把自己算进去。
   低成本可试：改成 1 或 2，看客户端是否开始走建房。
2. **`6/5` 订阅后必须推送事件**：客户端订阅了 20 个事件，服务端一条不推。
   至少要推一条 `RoomInfo` / `RoomStateUpdated` 让客户端认为房间已建立。
   但事件编号到名字的映射尚未解出（41 个 `dwRoomMessage*` 类，缺序号表）。
3. **`21/5 findSessions` 的会话对象字段**：已有代码注释提到
   "猜错地图客户端就不去连战斗服"，但地图本身本轮已对齐。
