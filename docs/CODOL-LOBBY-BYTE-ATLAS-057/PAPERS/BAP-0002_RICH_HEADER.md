## 2. 逐段解析

### 2.1 DOS stub 代码 `[0x40, 0x4E)`

| 偏移 | 字节 | 指令 |
|---|---|---|
| `0x40` | `0e` | `push cs` |
| `0x41` | `1f` | `pop ds` |
| `0x42` | `ba 0e 00` | `mov dx, 0x000E` |
| `0x45` | `b4 09` | `mov ah, 9`（DOS 打印字符串） |
| `0x47` | `cd 21` | `int 0x21` |
| `0x49` | `b8 01 4c` | `mov ax, 0x4C01`（带返回码 1 退出） |
| `0x4C` | `cd 21` | `int 0x21` |

**`mov dx, 0x000E`** 是关键：DOS 中字符串地址 = `CS:0x0E`，
而 `CS` 在加载时 = 程序基址 + `e_cs`(=0) 的段值。
`0x0E = 0x40`（stub 起点）− `0x32`… 需按 DOS 语义核对：
`0x40 + 0x0E = 0x4E` —— **正好是字符串 `This program...` 的起点**（见 `0x4E` 首字节 `54 'T'`）。
⇒ **E3：`mov dx,0x0E` 与字符串真实位置自洽**。

### 2.2 Stub 字符串 `[0x4E, 0x7C)`

```
"This program cannot be run in DOS mode.\r\r\n$"
```

字节 `0x0D 0x0D 0x0A 0x24`：
`\r\r\n$` —— `$` 是 DOS 字符串终止符，**双 `\r`** 是 MS 链接器的典型笔误
（不是 `\r\n`）。

⚠ 这一段已被 `ba02` 扫描器认定为 `ASCII_STRING`（≥6 可打印），
但**语义上属于 DOS stub**，论文归属以本文为准。

### 2.3 Rich Header `[0x80, 0x11C)`

```
DanS  xor key = 0x42F45604
```

`Rich` 标签位于 `0x118`，其后 4 字节 `04 56 f4 42` = **key 0x42F45604**。
`0x80` 处的 `40 37 9a 11` 与 key XOR：

```
0x119A3740 ^ 0x42F45604 = 0x536E6144 = "DanS" (小端 'D','a','n','S')
```

⇒ **E3**：Rich 块边界与 key 完全自洽，可解。

## 3. 语义推导（E3 级结论）

**结论 1：主工具链 = Visual Studio 2010 SP1（MSVC 10.0.40219）。**
证据：`build 40219` 的三个最大条目（170/171/175）合计 `983+843+748 = 2574`
个对象，占全部 3340 的 **77.1%**。

**结论 2（修订）：链接期混入了 `build 30729`（47 对象）与 `build 20115/21202`
的其它编译单元。** 具体是哪个库**无法从 Rich 判定**——prodid→库名映射
是社区表，未本地验证（见 BAP-0002D §1 H1）。

**结论 3：`prodid 1` 的 594 个对象**是链接器生成的桩（import 描述符、
`_chkstk`、`_security_cookie`、EH 展开桩、trampoline），**不是业务代码**，
分析时不应误判。

**结论 4（新增，E3）：`EXCEPTION` 目录 RVA=0 / SIZE=0（见 BAP-0003），
⇒ 本镜像无 SEH 展开表 ⇒ 函数边界只能靠线性扫描 + `0xCC` 填充确定。**
这是 `ba02_ledger_v3.py` 函数切分方法的合法性依据。

## 4. 引用关系

Rich header 只在**链接期**由 `link.exe` 写入，运行期**无任何代码读取**。
扫描镜像内对 `0x400080`–`0x40011B` 的 `xref`：**0 处**。
⇒ 它是纯构建指纹，对逆向的价值是"确定编译器版本 → 校准反汇编与结构体布局"。

**对本项目的实际含义**：MSVC 10 的 RTTI 格式就是我们在
`vtable_map.py` 里用的那套（TD = `{pVFTable, spare, name[]}`），
这为 BAP-0120 之后的 RTTI 全表提供**编译器版本层面的合法性依据**。
