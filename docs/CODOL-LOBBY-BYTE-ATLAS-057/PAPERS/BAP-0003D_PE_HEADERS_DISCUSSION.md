# BAP-0003D — 讨论：入口点的 1 字节疑云，与"目录 Size=0"的真伪

对应正论文：`BAP-0003_PE_HEADERS.md`

本文处理三个可能让整批结论作废的问题。它们都不是学术性的
——第三个直接关系到"我们这个镜像到底能不能代表真实客户端"。

---

## 1. 我的判断可能错在哪

### H1：入口点 `0x0E5DC690` 的 `call [0x0E9DC665]` 槽非 4 对齐，说明我读错了偏移

正论文说：`FF 15 65 C6 9D 0E` = `call dword ptr [0x0E9DC665]`，
并指出 `0x0E9DC665` 末位是 5，不符合 IAT 槽 4 对齐。

**这是本项目历史上最危险的错误类型**。055 轮曾因一处
**6 字节偏移错误**批量制造假发现。所以必须先怀疑自己。

**替代解释 A（我的读法对，槽确实非对齐）**：
加壳器把入口改写成 `call [绝对地址]`，槽地址可以是任意值，
只有 IAT 槽才需要 4 对齐。加壳器的跳板不需要。

**替代解释 B（我读错了，入口点其实不是 0x0E5DC690）**：
- 若 `SizeOfOptionalHeader` 读错 → 所有可选头字段错位。
  已实测 `0x13C` = `e0 00` = 224，标准 PE32+16 目录 = 224。**自洽**。
- 若 `TimeDateStamp` 位置读错 → 但 DEBUG 目录里同一个
  `0x6096930A` 独立出现。两处独立吻合 ⇒ 可选头起始位置正确。

**替代解释 C（入口点指向的确实是桩，但槽在别处）**：
`call [abs32]` 后紧跟 `00 00 00 00…` 全零。若入口是标准 CRT 启动，
后面应该有 `push`/`mov` 等指令，不是 32 字节全零。

**这一步是本讨论的关键**：我需要实测 `0x0E9DC665` 处的字节，
看它是否指向合法代码。

### H2：`IMPORT` / `RESOURCE` 目录 Size = 0 可能是我们提取镜像时写坏的

我们的镜像由 `extract_image_from_dump.py` 从活进程内存转储切出。
如果该脚本在写头部时把某些字段清零，那"Size=0"就是我们自己造成的，
而真实客户端里这两个目录是正常的。

**这是真正的风险**。若成立，则：
- "导入表被剥离"的结论作废；
- 依赖该结论的 `.idata2` 系列旧分析需要重新评估。

### H3：入口点附近的 `00 00...` 是未初始化页，不是代码

内存转储会包含 `.bss` 风格的全零页。若入口点落在这样一个页上，
说明**镜像的入口点区域未被正确转储**。

**反证**：入口点 `0x0E5DC690` 位于节 2（`VA 0x0A16000`，`vsz 0x0DBB1CC0`，
即 `0x0A16000`–`0x0E5D7CC0`）。节 2 是 `0xC0000040` = **可读写**，
**不可执行**（0x20000000 位未置）。

⚠ **这是一个严重矛盾**：入口点落在一个**不可执行**的节里！

重新核对节 2 的 Characteristics：`40 00 00 c0` 小端 = `0xC0000040`
= `WRITE (0x80000000) | READ (0x40000000) | INITIALIZED_DATA (0x40)`。
**没有 `EXECUTE`**。

而节 0 的 Characteristics = `20 00 00 60` = `0x60000020`
= `CODE (0x20) | EXECUTE (0x20000000) | READ (0x40000000)`。

⇒ **入口点不在可执行节内**。这几乎必然是加壳/重打包的结果：
原始链接器不会把入口点放进数据节。

### 2.3 节属性重核

| 节 | VA | VSize | Characteristics | R W X |
|---|---|---|---|---|
| 0 | `0x00001000` | `0x008A689A` | `0x60000020` | R–X |
| 1 | `0x008A8000` | `0x0016DA70` | `0x40000040` | RW– |
| 2 | `0x00A16000` | `0x0DBB1CC0` | `0xC0000040` | RW– |
| 3 | `0x0E5C8000` | `0x00000031` | `0xC0000040` | RW– |
| 4 | `0x0E5C9000` | `0x00009228` | `0x40000040` | R–– |
| 5 | `0x0E5D3000` | `0x00004000` | `0x60000020` | R–X |
| 6 | `0x0E5D7000` | `0x00082000` | `0xE0000020` | RWX |

⇒ 入口 `0x0E5DC690` ∈ 节 2（RW–），**不可执行**。

**但节 6 是 RWX**（`0xE0000020` = W|R|X|CODE），且
`0x0E5D7000`–`0x0E659000`，**入口点不在这里**。

这强烈暗示：**入口点字段被加壳器改写成了一个"跳板数据"地址**，
或者**节属性被加壳器改写了**（原始节 2 可能是 RWX）。

## 3. 若判断成立，下游会怎样

### 若 H1-解释A 成立（槽非对齐是正常跳板）

- 不影响任何其它结论。
- 但需要在 BAP-0020（函数边界）里单独处理"入口点不可执行"这一异常，
  避免线性扫描把节 2 当代码扫。

### 若 H1-解释B 成立（我读错）

- 055 轮的"6 字节偏移"教训重演，需要重新校准**整份论文的偏移基准**。
- 目前两处独立吻合（TimeDateStamp 双处、SizeOfImage 与节表和）已经
  排除了这种可能。⇒ **判为不太可能，但保留**。

### 若 H2 成立（提取脚本写坏目录 Size）

- **必须重读一遍转储原始数据**，对比本次读到的字节。
- 影响：BAP-0006（导出）、BAP-0009（导入）、BAP-0008（资源）三篇的
  "Size=0"结论。但**结构内容**（22 个导出、5 类资源）不受影响，
  因为它们是从 RVA 直接读的，不依赖目录 Size。

### 若 H3 成立（入口区域未正确转储）

- **这是最严重的情形**：说明我们的镜像在入口点附近有空洞，
  可能整片代码缺失。
- 反证：`SizeOfImage` 与实际长度逐字节相等，且节 2 声明大小
  `0x0DBB1CC0` 与文件实际内容一致（无空洞页）。

## 4. 最小可证伪实验

### 实验 E1（不需要启动游戏）：读 `0x0E9DC665` 处 64 字节

若该处是合法代码（可反汇编出 ≥3 条指令），则解释 A 成立；
若是数据/全零，则入口点指向数据，需要继续追。

### 实验 E2（不需要启动游戏）：对比磁盘原始 EXE 的目录 Size

读磁盘 `codoMP_client_shipRetail.exe`（7.8 MB 加壳版）的
`IMPORT.Size` / `RESOURCE.Size`。若磁盘版也是 0，则 H2 被反证。

### 实验 E3（不需要启动游戏）：检查节属性

读磁盘版节表，看节 2 是否也是 RW–。若磁盘版是 RWX，
则"节属性被改"这一说法成立；若也是 RW–，则入口点异常是
**原始构建就有的**（可能这个 build 的入口点确实是个 loader 桩）。
