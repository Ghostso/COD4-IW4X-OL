# BAP-0004 — 节表 `[0x000220, 0x000339)`

| 项 | 值 |
|---|---|
| 范围 | `0x000220` – `0x000338`（7 × 40 = 280 字节） |
| 结构 | 7 个 `IMAGE_SECTION_HEADER` |
| 最高判据 | **E3**（`VA+VSize` 链首尾相接 ∧ 末节末端 = 文件长度） |

---

## 0. 本篇首先要纠正一个**我自己的错误**

在建 BAP-0001 至 BAP-0003 时，我把节的 `VirtualAddress` 当成了 VA
（绝对虚拟地址），于是算 `file_offset = VirtualAddress − 0x400000`，
得到一批"数据对不上"的结果，并一度推断"镜像在节边界被平移"。

**这个推断是错的。** 正确的是：

```
RVA          = IMAGE_SECTION_HEADER.VirtualAddress      （已相对于 ImageBase）
file_offset  = RVA
VA           = RVA + ImageBase(0x400000)
```

判据 E3，两条独立验证：

1. 节 0：`VirtualAddress = 0x00001000`，文件偏移 `0x00001000`
   处字节 `55 8b ec 83 ec 50 a1 40 f2 e3 00` = `push ebp / mov ebp,esp /
   sub esp,0x50 / mov eax,[0x00E3F240]` —— 合法函数序言。
2. 节 4（资源）：`VirtualAddress = 0x0E5C9000`，文件偏移 `0x0E5C9000`
   处可完整解析出 `IMAGE_RESOURCE_DIRECTORY`（见 BAP-0008）。

按错误映射读，第 1 条会读到 `0x00601000` 处的随机字节。
⇒ **错的是我的减法，不是镜像。**

⚠ 本节纠正影响 BAP-0001D / BAP-0003D 中所有"VA − 0x400000"的推导。
已回填这两篇。

## 2. 逐节解析

`IMAGE_SECTION_HEADER` 布局（40 字节）：
`Name[8] / VirtualSize@8 / VirtualAddress@12 / SizeOfRawData@16 /
PointerToRawData@20 / PointerToRelocations@24 / PointerToLinenumbers@28 /
NumberOfRelocations@32(2) / NumberOfLinenumbers@34(2) / Characteristics@36`

| # | Name | VirtualSize | VirtualAddress (RVA) | SizeOfRawData | PointerToRawData | Characteristics | R W X |
|---|---|---|---|---|---|---|---|
| 0 | `.tp3` | `0x008A689A` | `0x00001000` | `0x008A7000` | `0x00001000` | `0x60000020` | R–X |
| 1 | `.tp3 a` | `0x0016DA70` | `0x008A8000` | `0x0016E000` | `0x008A8000` | `0x40000040` | RW– |
| 2 | `.tp3` | `0x0DBB1CC0` | `0x00A16000` | `0x00062000` | `0x00A16000` | `0xC0000040` | RW– |
| 3 | `.tp3` | `0x00000031` | `0x0E5C8000` | `0x00001000` | `0x00A78000` | `0xC0000040` | RW– |
| 4 | `.tp3` | `0x00009228` | `0x0E5C9000` | `0x0000A000` | `0x00A79000` | `0x40000040` | R–– |
| 5 | `.tp3` | `0x00004000` | `0x0E5D3000` | `0x00004000` | `0x00A83000` | `0x60000020` | R–X |
| 6 | `.tp3` | `0x00082000` | `0x0E5D7000` | `0x00006000` | `0x00771000` | `0xE0000020` | RWX |

### 2.1 结论 1：`VA + VSize` 首尾相接（E3）

```
节0  0x00001000 + 0x008A689A = 0x008A789A
节1  0x008A8000 + 0x0016DA70 = 0x00A15A70
节2  0x00A16000 + 0x0DBB1CC0 = 0x0E5C7CC0
节3  0x0E5C8000 + 0x00000031 = 0x0E5C8031
节4  0x0E5C9000 + 0x00009228 = 0x0E5D2228
节5  0x0E5D3000 + 0x00004000 = 0x0E5D7000
节6  0x0E5D7000 + 0x00082000 = 0x0E659000
```

- 节 5 末端 `0x0E5D7000` **恰好等于**节 6 起点。
- 节 6 末端 `0x0E659000` **恰好等于** `SizeOfImage` **且等于文件长度**。

⇒ 镜像用 RVA 空间 1:1 铺满了整个文件，**末尾无空洞**（E3）。

中间的空隙（如 `0x008A789A`→`0x008A8000` 共 `0x766` 字节，
`0x00A15A70`→`0x00A16000`，`0x0E5C7CC0`→`0x0E5C8000`，
`0x0E5C8031`→`0x0E5C9000`，`0x0E5D2228`→`0x0E5D3000`）
是 `SectionAlignment = 0x1000` 造成的段间填充，属正常。

### 2.2 结论 2：`PointerToRawData` 对节 0–2 有效，对节 3–6 **失效**

| # | PointerToRawData | 该处内容与 `RVA` 处相同? |
|---|---|---|
| 0 | `0x00001000` | **YES** |
| 1 | `0x008A8000` | **YES** |
| 2 | `0x00A16000` | **YES** |
| 3 | `0x00A78000` | YES（两者都是全零，弱证据） |
| 4 | `0x00A79000` | **NO**（RawPtr 处全零，RVA 处是资源目录） |
| 5 | `0x00A83000` | **NO** |
| 6 | `0x00771000` | **NO** |

节 4 实例（E3，最强）：

```
@PointToRawData 0x00A79000:  00 00 00 00 00 00 00 00 ... （全零）
@RVA            0x0E5C9000:  00 00 00 00 00 00 00 00 04 00 00 00 00 00 05 00
                             ^ IMAGE_RESOURCE_DIRECTORY：NumberOfIdEntries=5
```

而 `0x0E5C9000` 处**能完整解析出 5 类资源**（见 BAP-0008）。

⇒ **`PointerToRawData` 是原始磁盘文件的残留值，在内存镜像里无效。
一切按 `RVA = file_offset` 读取。**

**为什么这很重要**：任何按 `PointerToRawData` 读节的工具都会
在节 4/5/6 上读到错误数据。本项目此前的 `extract_image_from_dump.py`
若依赖 RawPtr，会漏掉资源、导入表和尾部代码。

### 2.3 结论 3：节 2 声明 `VirtualSize = 0x0DBB1CC0`（219 MB）但
`SizeOfRawData = 0x00062000`（401 KB）

标准 PE 里 `VirtualSize > SizeOfRawData` 表示 `.bss` 式的未初始化尾部。
但 219 MB 的差距、且文件里**实际有这 219 MB 的内容**
（文件总长 `0x0E659000`），说明：

**这个 PE 是"内存镜像伪造件"——节表沿用了原磁盘文件的
`SizeOfRawData`（真实文件只有 7.8 MB 加壳数据），
而数据区已经被解包后的完整 219 MB 覆盖。**

⇒ 与"7.8 MB 加壳 → 230 MB 解包"的既有认识一致（E3）。

### 2.4 结论 4：节名全部是 `.tp3`

7 个节全叫 `.tp3`（其中一个带后缀 `.tp3 a`，末尾 `0x61 = 'a'`）。
`.tp3` 是腾讯 TP3 保护（TenProtect 3）的节名。

**但节属性分布是正常的 PE 布局**：代码段 R–X、数据段 RW–、
资源 R––、尾部 RWX。⇒ **节名被改，布局未改**（E2/E3）。

### 2.5 结论 5：`0xE0000020` 的节 6 = RWX（唯一可执行的数据节）

`0xE0000020 = WRITE | EXECUTE | READ | CODE`。
- `WRITE + EXECUTE` 同时置位在现代 PE 里极罕见，是**自修改代码**的典型特征。
- 节 6 仅 `0x82000`（532 KB），位于镜像最尾部。
- 加壳器/虚拟机保护通常把"解密后的真实代码"放在这种尾部 RWX 节。

**这与 `.tvm0` 系列旧分析方向一致**（记忆：`.tvm0` 是密钥化分支派发器）。

### 2.6 结论 6：入口点落在节 2（RW–，**不可执行**）

`AddressOfEntryPoint = 0x0E5DC690` ∈ 节 2（`0x00A16000`–`0x0E5C7CC0`）。
节 2 的 Characteristics 无 `EXECUTE` 位。

三种解释（按可信度排序）：

1. **节属性在解包时被改**：原始磁盘版节 2 可能是 RWX，
   我们的镜像保留了错误的属性。- 可测：读磁盘 7.8 MB 原件的节表。
2. **入口点字段被加壳器指向"数据区跳板"**：
   `call dword ptr [0x0E9DC665]` 读一个数据槽，跳进真实代码。
3. **我们的镜像节属性来自转储页属性**，而非 PE 头。

三方都指向同一件事：**入口点是跳板，不是真实代码起点**。
这与 `0x0E5DC690` 之后 32 字节全零吻合（跳板后无代码）。

## 3. 引用关系

节的属性决定**页保护**，由 Windows 加载器设置，镜像内无读者。
但**加壳器/保护模块会读自己的节表**（反调试、完整性校验）。
xref `0x000220`–`0x000338` 的结果见 BAP-0004D。

## 4. 置信度

| 结论 | 级 |
|---|---|
| `RVA = file_offset`，`VA = RVA + 0x400000` | **E3**（节 0 序言 + 节 4 资源目录双重） |
| 7 节，`VA+VSize` 首尾相接，末节末端 = EOF | **E3** |
| `PointerToRawData` 在节 3–6 失效，须用 RVA | **E3** |
| 节 2 的 219 MB 是解包后覆盖，非 `.bss` | **E3** |
| 节名 `.tp3` = 腾讯 TP3 保护 | **E2** |
| 节 6 = RWX，疑似真代码区 | **E2（属性直读）/ 推测（用途）** |
| 入口点落在不可执行节，是跳板 | **E3（属性）/ 推测（机理）** |
