## 1. 我的判断可能错在哪

### 断言：`build 40219` 的三个最大条目 = VS2010 SP1 MFC/ATL/CRT

**替代假设 H1：prodid 170/171/175 的官方产品名与我的标注不符。**

Rich header 的 prodid→产品名映射**没有微软官方公开表**，现存对照表
（如 `rich_header.h` 与 `pefile` 的 constants）来自社区逆向，且不同来源
对 170/171/175 的命名有分歧：
- 部分表：`170 = VS2010 SP1 C++ Runtime`、`171 = VS2010 SP1 MFC`、
  `175 = VS2010 SP1 ATL`。
- 另一部分表：`170 = VS2008 MFC`（build 30319 那行才对应 VS2008）。

**反证尝试（本地）**：`build 40219` 是 VS2010 SP1 的构建号，
这是有独立出处的（MSDN 发布说明）。所以"`build 40219` → VS2010 SP1"
是 E3 级；"`prodid 170` → 具体哪个库" 只是 **E1 级对应关系，来自社区表**。

⇒ **正论文 §2.4 表格里"产品"一列应全部降级为"社区对照表，未本地验证"**。
真正影响结论的只有 `(prodid, build)` 二元组与 `count`，这三个是 E3。

### 替代假设 H2：`prodid 1 / build 0 / 594 个对象` 不是链接器产物。

594 这个数量远超任何一个独立库。若它是某个**被整体静态链接的第三方库**
（例如 Scaleform 或 Demonware），那它的 count 应更大且能对上某个
已知 SDK 的 `.lib` 数量。

**反证**：`prodid 1` 在 Rich 里固定表示"由 link.exe 自身生成的桩"
（`__imp_` 描述符、`_chkstk`、`_security_cookie`、EH 展开桩、trampoline）。
594 对 230 MB 的镜像来说是**偏低但不是不可能**。
无法从 Rich 本身证伪，也无需证伪 —— **它不影响任何大厅结论**。

### 替代假设 H3：Rich block 里的 `count` 是"对象数"还是"总大小"。

`count` 明确是 **#objects linked**，不是字节数。验证方法：
`175:748` 若真是字节，则 MFC 静态库只有 748 字节，显然荒谬。
⇒ 定论 E3：`count` = 对象数。

## 3. 若判断成立，下游会怎样

**对大厅逆向的直接价值只有一条**：
编译器版本 = MSVC 10，因此：

1. RTTI 布局就是 MSVC 10 的 `{pVFTable, spare, name[]}`，我们
   `vtable_map.py` 用的 `TD = name_va − 8` 是**正确的**（已由 1368 类实证）。
2. 异常表（`EXCEPTION` 目录）为 0，说明**本镜像剥离了 SEH 展开信息**，
   这与"代码被压缩/重排"一致 —— 反汇编时不能靠 `.pdata` 找函数边界，
   **只能靠线性扫描 + `0xCC` 填充**（这正是 `ba02` 的做法）。
3. 结构体对齐 = 4 字节（x86 MSVC 默认），影响后续所有字段偏移解读。

**若 H1 成立**（产品名标注错误），不会有任何下游影响，因为
我们从不用 prodid 的"库名"做推理，只用 build 号。

## 4. 最小可证伪实验

- **H3 可立即证伪**：取 `175` 的 748 个对象，若这些对象在镜像里
  能找到对应的 `.text` 区块（需先完成 BAP-0020 的函数边界表），
  则"对象数"成立；若找不到 748 个独立编译单元的特征，
  则该字段语义存疑。→ **依赖 BAP-0020，暂挂。**
- **H1 无法在本地证伪**（需要微软内部数据）。处理方式：
  正论文只写 `(prodid, build, count)` 三元组，产品名列统一加注
  "社区表，未验证"。
